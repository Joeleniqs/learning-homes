Lifetimes, Scopes & Captive Dependencies

Singleton, scoped and transient visualised across requests; captive dependencies, disposal, thread safety and scope validation.

Intermediate → Advanced~50 min studyBuilds on: DI FundamentalsUpdated 2026-11-03

The problem: a cache that works on your machine

A team adds a price cache to speed up checkout. It is registered as a singleton, because a cache should live for the whole app, and it asks for the EF Core AppDbContext in its constructor. Every unit test passes, and it works in the staging environment, where requests rarely overlap.

builder.Services.AddDbContext<AppDbContext>(...);   // scoped: one per request (the default for AddDbContext)
builder.Services.AddSingleton<PriceCache>();         // one for the whole app

public sealed class PriceCache(AppDbContext db)      // ← the singleton keeps the first request's context forever
{
    public Task<Price> GetAsync(string sku) => db.Prices.SingleAsync(p => p.Sku == sku);
}

In production, under real concurrency, three unrelated-looking symptoms appear:

  • InvalidOperationException: A second operation was started on this context instance before a previous operation completed. Two requests are now using one DbContext at the same time, and DbContext is not thread-safe.
  • Stale prices. The context's change tracker caches every entity it has loaded, so the "cache" never sees updates made by other requests.
  • Memory that grows until the pod is recycled, because that one context tracks every price ever read.

Nothing is wrong with PriceCache or with AppDbContext. The bug is in the lifetimes: a long-lived object holds on to a short-lived one, so the short-lived object is kept far past its intended life. This page shows exactly what each lifetime means at runtime, who owns and disposes every instance, and how to make the container catch this mistake at startup. It builds on DI Fundamentals.

A lifetime answers two questions: who shares this instance, and who disposes it? The one rule that prevents most lifetime bugs is that an object may only depend on objects that live at least as long as it does.

The three lifetimes

Every mainstream container has the same three basic answers, under different names:

  • Singleton. One instance for the whole application, created on first use and cached in the root container. Every request and every thread shares it, so it must be thread-safe. It is disposed at shutdown.
  • Scoped. One instance per scope. In a web app the framework opens one scope per HTTP request, so a scoped service is "one per request". The scope disposes it when the request ends.
  • Transient. A new instance for every resolution: every constructor parameter that asks for it, and every GetService call. If it is disposable, the scope (or root) that created it disposes it.

Singleton

  • Created: first resolution (or eagerly at startup).
  • Cached in: the root.
  • Disposed: at shutdown, by the root.
  • Shared by: every request and thread at once.
  • Typical: configuration, clocks, HttpClient handlers via IHttpClientFactory, connection pools, IMemoryCache, stateless services.

Scoped

  • Created: first resolution inside a scope.
  • Cached in: that scope.
  • Disposed: when the scope ends (the request completes).
  • Shared by: everything in one request.
  • Typical: DbContext / unit of work, the current user or tenant, per-request caches.

Transient

  • Created: on every resolution.
  • Cached in: nothing. The scope only records it if it is disposable.
  • Disposed: when the scope or root that created it ends.
  • Shared by: nobody, unless a longer-lived consumer keeps it.
  • Typical: lightweight, stateful-per-use helpers and builders.

Thread safety per lifetime

A lifetime is also a statement about concurrency. Choosing one is choosing how many threads can reach the object at the same time.

Lifetime Who can touch it concurrently What it must guarantee
Singleton Every in-flight request, background services, timers Fully thread-safe: immutable, or guarded with lock, ConcurrentDictionary, Interlocked, or similar. Its dependencies must also be safe to share.
Scoped Only code running for that request No cross-request sharing, but not automatically single-threaded. Task.WhenAll inside one request runs two operations on the same scoped DbContext in parallel.
Transient Only the consumer that received it Nothing extra, unless that consumer is long-lived. A transient injected into a singleton is shared exactly like the singleton is. 
// Both queries run on the request's single AppDbContext at the same time.
public async Task<Dashboard> LoadAsync(int userId)
{
    var orders = db.Orders.Where(o => o.UserId == userId).ToListAsync();
    var invoices = db.Invoices.Where(i => i.UserId == userId).ToListAsync();
    await Task.WhenAll(orders, invoices);   // "A second operation was started on this context instance..."
    return new Dashboard(orders.Result, invoices.Result);
}

// Option 1: await one at a time; the scoped context is used by one operation at a time.
var orders = await db.Orders.Where(o => o.UserId == userId).ToListAsync();
var invoices = await db.Invoices.Where(i => i.UserId == userId).ToListAsync();

// Option 2: real parallelism needs one context per operation.
// Register with services.AddDbContextFactory<AppDbContext>(...) and inject IDbContextFactory<AppDbContext>.
async Task<List<T>> Query<T>(Func<AppDbContext, Task<List<T>>> q)
{
    await using var ctx = await contexts.CreateDbContextAsync();   // you created it, so you dispose it
    return await q(ctx);
}
var (o, i) = (Query(c => c.Orders.Where(x => x.UserId == userId).ToListAsync()),
              Query(c => c.Invoices.Where(x => x.UserId == userId).ToListAsync()));
await Task.WhenAll(o, i);

Singletons need thread-safe dependencies as well. A singleton made of readonly fields is thread-safe only if every object those fields point to is also safe to share. "Stateless" means no mutable state reachable from the object, not "no fields".

The lifetime matrix: who may depend on whom

Read each row as "a consumer with this lifetime takes a dependency with that lifetime". The safe direction is always towards something that lives at least as long.

  • Singleton → scoped is the captive dependency. MS.DI rejects it when scope validation is on.
  • Singleton → transient is legal, but the transient is created once and then lives as long as the singleton: its effective lifetime becomes singleton. That is harmless for a stateless helper. It is a bug if the transient was transient for a reason, for example because it holds per-operation state or is not thread-safe.
  • Scoped → transient → scoped is fine: inside a request, everything resolves from the same scope.
  • Anything → singleton is always fine.

The validator below walks a dependency chain the way ValidateScopes does: it remembers whether there is a singleton above the current node and fails as soon as it reaches a scoped service underneath. It also tracks the effective lifetime, so you can see a transient being promoted. Type your own chain, or resolve it from the root provider to see the root-specific errors.

Captive dependencies

A captive dependency is a service held by a consumer that lives longer than the service was designed to live. The consumer "captures" it: the container would have disposed it and created a fresh one for the next request, but the consumer still holds the old one. The step-through below replays the opening story. Change the configuration to see what validation does, and what each fix changes.

Notice where the context lives in each run. With no validation, AppDbContext #1 is created while request 1 is being served, but the root creates and owns it, because a singleton and all of its dependencies are always built by the root. Request 1 ends and nothing is disposed. Request 2 then gets the same context, already tracking request 1's entities. When the two requests overlap, the context is used from two threads.

Fixes that do not work

  • A Func<AppDbContext> or Lazy<AppDbContext> in the singleton, registered as sp => () => sp.GetRequiredService<AppDbContext>(). The factory was created by the root, so sp is the root: with validation it throws, and without validation it hands out root-owned contexts that are never disposed until shutdown.
  • Making AppDbContext transient. That hides the error message but keeps the bug: the singleton still keeps its one transient context forever.
  • Injecting IServiceProvider and calling GetService in each method. The singleton's provider is the root, so it is the same problem behind a service locator.
  • Turning validation off because "it only fails in Development".

Fixes that work

  • Shorten the consumer. If PriceCache does not need to outlive a request, register it as scoped. This is the simplest correct fix.
  • Split state from work. Keep the long-lived part (a ConcurrentDictionary, an IMemoryCache) in a singleton that has no scoped dependencies, and do the database work in a scoped service that uses it.
  • Create a scope per unit of work. Inject IServiceScopeFactory, open a scope for each operation and resolve the context from it, as background services do.
  • Use a factory designed for it: IDbContextFactory<T> creates contexts that you own and dispose.

Scope validation: make the container catch it

MS.DI can detect captive dependencies, but you have to ask it to:

  • ValidateScopes checks every resolution at runtime. It throws if a singleton (directly or through transients) depends on a scoped service, or if a scoped service is resolved from the root provider. Without it, the root silently creates a "scoped" instance that it then keeps until shutdown.
  • ValidateOnBuild tries to build the call site for every registration when the provider is built. Missing registrations and captive chains then fail at startup instead of on the first request that needs them.

Both are on by default in the Development environment (WebApplication.CreateBuilder and Host.CreateDefaultBuilder) and off everywhere else, because validation costs startup time. That default explains the opening story: the unit tests built their own provider with a bare BuildServiceProvider(), staging ran as Staging, and nobody happened to start the app as Development after the change. Nothing ever validated the graph.

var builder = WebApplication.CreateBuilder(args);
// Turn validation on everywhere. It is a one-time cost at startup, and it turns a production
// incident into a deployment that fails immediately.
builder.Host.UseDefaultServiceProvider(o =>
{
    o.ValidateScopes = true;
    o.ValidateOnBuild = true;
});

var services = new ServiceCollection();
services.AddDbContext<AppDbContext>(o => o.UseSqlite("Data Source=app.db"));   // scoped
services.AddSingleton<PriceCache>();
// BuildServiceProvider() with no options validates nothing.
using var root = services.BuildServiceProvider(new ServiceProviderOptions
{
    ValidateScopes = true,
    ValidateOnBuild = true,   // throws here: Cannot consume scoped service 'AppDbContext' from singleton 'PriceCache'.
});

[Fact]
public void Container_is_valid()
{
    // WebApplicationFactory runs in the Development environment by default, so validation is on.
    // This test fails the build on any captive dependency or missing registration.
    using var app = new WebApplicationFactory<Program>();
    _ = app.Services;   // forces the host, and therefore the provider, to be built
}

The errors you will see, and what each one means:

Message Cause Fix
Cannot consume scoped service 'X' from singleton 'Y'. A singleton reaches a scoped service, possibly through transients. Shorten the consumer, split it, or use a scope factory.
Cannot resolve scoped service 'X' from root provider. app.Services.GetService<X>() or a constructor resolved by the root. Create a scope: using var s = app.Services.CreateScope();.
Cannot resolve 'T' from root provider because it requires scoped service 'X'. A transient that needs a scoped service, resolved from the root. The same: resolve it from a scope.

Validation cannot see inside factories. services.AddSingleton<IPriceCache>(sp => new PriceCache(sp.GetRequiredService<AppDbContext>())) hides the dependency inside a lambda. ValidateOnBuild cannot inspect it, and at runtime sp is the root, so the scoped context is resolved from the root. ValidateScopes catches that call when it runs, but only on the code path that runs it. Prefer constructor registrations, or keep factories trivial.

Disposal and ownership

The ownership rules in MS.DI are short. They are worth memorising because every disposal bug breaks one of them:

  1. The container disposes what it created, and only that. Instances that the container constructed, through a type registration or a factory lambda, are tracked if they implement IDisposable or IAsyncDisposable.
  2. It disposes them when their owner ends. Scoped instances, and transients created by a scope, are disposed when the scope ends. Singletons, and transients created by the root, are disposed only when the root is disposed, at shutdown.
  3. Newest first. Disposal runs in reverse creation order, so a service is disposed before the dependencies it might still use in its own Dispose.
  4. Instances you hand over are yours. AddSingleton(myInstance) is never disposed by the container: you created it, so you own it.
  5. Never dispose an injected dependency yourself. You do not own it, and the next consumer in the same scope would receive a disposed object.
  6. Async disposal needs an async owner. If a service implements only IAsyncDisposable, disposing its scope with the synchronous Dispose() throws. Use await using / CreateAsyncScope() / DisposeAsync().

Step through each scenario. The stack on the left is the owner's list of disposables, newest on top.

Transient disposables resolved from the root are a slow memory leak Every root.GetService<ReportBuilder>() on a transient that implements IDisposable adds the new instance to the root's disposables list, and the root lives until shutdown. A job that does this once a second keeps 86,400 builders alive per day. Resolve per-operation services from a scope that you dispose, or construct them directly if they do not need the container.

public sealed class ReportService(AppDbContext db) : IDisposable
{
    public void Dispose() => db.Dispose();   // AppDbContext is scoped: other services in this request still use it
}

public sealed class ReportService(AppDbContext db)   // borrows db; the scope owns it
{
    public Task<Report> BuildAsync() => ...;
}

public sealed class ExportJob(IDbContextFactory<AppDbContext> contexts)
{
    public async Task RunAsync()
    {
        await using var db = await contexts.CreateDbContextAsync();   // this code created it, so this code disposes it
        ...
    }
}

Background services and IServiceScopeFactory

A BackgroundService is registered as a singleton IHostedService. There is no request, so there is no scope. If it injects a scoped service, that service is either rejected by validation or captured for the life of the app. The fix is to own the scope yourself: inject IServiceScopeFactory (a singleton) and create one scope per unit of work, such as a message, a batch or a timer tick.

  • One scope per unit of work. It gives a fresh change tracker per batch, bounded memory, and a failure in one batch cannot poison the next.
  • CreateAsyncScope() with await using so that IAsyncDisposable services are disposed correctly.
  • Never pass a request's scoped objects to work that outlives the request: Task.Run, fire-and-forget calls, BackgroundTasks and queued callbacks. The request's scope is disposed when the response finishes, so the work later meets a disposed context (Cannot access a disposed context instance). Pass data (ids, DTOs) and let the background side create its own scope.
public sealed class OutboxWorker(IServiceScopeFactory scopes, ILogger<OutboxWorker> log) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken ct)
    {
        using var timer = new PeriodicTimer(TimeSpan.FromSeconds(1));
        while (await timer.WaitForNextTickAsync(ct))
        {
            await using var scope = scopes.CreateAsyncScope();               // one scope per batch
            var db = scope.ServiceProvider.GetRequiredService<AppDbContext>();
            var batch = await db.Outbox.Where(m => m.SentAt == null).Take(50).ToListAsync(ct);
            foreach (var m in batch) { await Publish(m, ct); m.SentAt = DateTime.UtcNow; }
            await db.SaveChangesAsync(ct);
        }                                                                    // context disposed here, every tick
    }
}

Lifetimes across ecosystems

The same three ideas exist everywhere. What differs is how far each framework goes to protect you from mixing them.

Ecosystem App-wide Per request Per resolution Outside a request Captive protection
.NET (MS.DI) Singleton Scoped (one scope per request) Transient IServiceScopeFactory, IDbContextFactory ValidateScopes, ValidateOnBuild at runtime (on in Development)
Spring singleton (default) request, session, application, websocket, via scoped proxies prototype @Scheduled and @Async have no request scope; use transactions A request bean without a proxy fails at startup; a prototype in a singleton is captured silently
Dagger / Hilt @Singleton (per component) Custom scopes on subcomponents; Hilt's @ActivityScoped, @ViewModelScoped Unscoped (@Reusable = cache if convenient) A new subcomponent Compile-time error for scope mismatches
NestJS Scope.DEFAULT Scope.REQUEST (bubbles up to consumers) Scope.TRANSIENT (one per consumer) ContextIdFactory.create() and moduleRef.resolve() None needed: request scope propagates up the chain instead
FastAPI Module level, lru_cache, or lifespan state Depends (cached once per request); yield for cleanup Depends(..., use_cache=False) Open your own session inside the task Your discipline: no container-level checks
Go Values built in main Values built in the handler A plain constructor call A goroutine opens its own transaction The compiler shows every wiring line; Wire and Fx generate or run the same wiring

Here is the same small app in each ecosystem: an app-wide clock, a per-request unit of work that must be cleaned up, a per-use PriceCalculator, and a background worker that needs its own unit of work.

var builder = WebApplication.CreateBuilder(args);
builder.Services.AddSingleton(TimeProvider.System);                         // app-wide; thread-safe
builder.Services.AddDbContext<AppDbContext>(o => o.UseNpgsql(connString));  // scoped: one per request
builder.Services.AddTransient<PriceCalculator>();                          // new per resolution
builder.Services.AddHostedService<OutboxWorker>();                          // singleton: needs its own scopes
builder.Host.UseDefaultServiceProvider(o => { o.ValidateScopes = true; o.ValidateOnBuild = true; });

var app = builder.Build();
app.MapGet("/price/{sku}", (string sku, PriceCalculator calc) => calc.PriceOfAsync(sku));
app.Run();   // each request: new scope → new AppDbContext → disposed when the response completes

        (await db.Prices.SingleAsync(p => p.Sku == sku)).At(clock.GetUtcNow());
}

// Lifetimes are explicit: where you construct a value decides how long it lives.
type App struct {
    clock Clock   // built once in main: shared by every goroutine, so it must be safe for concurrent use
    db    *sql.DB // a connection pool: designed to be shared
}

func (a *App) price(w http.ResponseWriter, r *http.Request) {
    tx, err := a.db.BeginTx(r.Context(), nil) // per request: this handler owns it
    if err != nil {
        http.Error(w, err.Error(), http.StatusServiceUnavailable)
        return
    }
    defer tx.Rollback() // cleanup when the request ends (a no-op after Commit)

    calc := NewPriceCalculator(a.clock, tx) // per use: just a constructor call
    p, err := calc.PriceOf(r.Context(), r.PathValue("sku"))
    if err != nil {
        http.Error(w, err.Error(), http.StatusInternalServerError)
        return
    }
    _ = tx.Commit()
    json.NewEncoder(w).Encode(p)
}

func (a *App) outbox(ctx context.Context) {
    for range time.Tick(time.Second) {
        _ = publishBatch(ctx, a.db) // opens and closes its own transaction per batch
    }
}

func main() {
    db, err := sql.Open("pgx", os.Getenv("DATABASE_URL"))
    if err != nil {
        log.Fatal(err)
    }
    defer db.Close() // singleton cleanup at shutdown

    app := &App{clock: realClock{}, db: db}
    go app.outbox(context.Background())
    http.HandleFunc("GET /price/{sku}", app.price)
    log.Fatal(http.ListenAndServe(":8080", nil))
}

}

@Injectable({ scope: Scope.TRANSIENT })               // a separate instance for each consumer
export class PriceCalculator {

@Controller('price')

@Injectable()
export class OutboxWorker {
  constructor(private readonly moduleRef: ModuleRef) {}

  @Interval(1000)
  async publish() {
    const contextId = ContextIdFactory.create();     // a fresh DI sub-tree, like a scope

Dagger (and Hilt on Android) handle lifetimes at compile time. A scope annotation binds an instance to a component: @Singleton means "one per AppComponent", and a custom @RequestScoped means "one per RequestComponent". A longer-lived component cannot see bindings that belong to a shorter-lived subcomponent, so the captive dependency does not compile.

@Scope @Retention(RetentionPolicy.RUNTIME) @interface RequestScoped {}

@Singleton @Component(modules = DataModule.class)
interface AppComponent {
    RequestComponent.Factory requests();                    // one RequestComponent per request
}

@RequestScoped @Subcomponent
interface RequestComponent {
    PriceController controller();
    @Subcomponent.Factory interface Factory { RequestComponent create(@BindsInstance HttpRequest req); }
}

@RequestScoped class UnitOfWork { @Inject UnitOfWork(DataSource ds) { ... } }       // one per request
@Singleton class PriceCache { @Inject PriceCache(Clock clock) { ... } }             // fine: singleton → singleton

// @Singleton class BadCache { @Inject BadCache(UnitOfWork uow) { ... } }
// does not compile: [Dagger/IncompatiblyScopedBindings] AppComponent scoped with @Singleton
// may not reference bindings with different scopes: @RequestScoped class UnitOfWork
// When a longer-lived object needs a fresh short-lived one, inject Provider<T> from the right component.

Why the ecosystems differ

  • .NET is explicit and runtime-checked. Scopes are visible objects (IServiceScope) that you can create yourself, which is why background services are easy to get right once you know to do it. Validation is opt-in outside Development for startup speed.
  • Spring hides the scope behind a proxy: a singleton that holds a request-scoped bean actually holds a proxy that looks up the current request's instance on every call. This is why Spring apps rarely capture an EntityManager: the injected one is a shared, thread-safe proxy bound to the current transaction. The catch is prototype: Spring creates it once when it builds a singleton, and never calls its destroy callbacks. Use ObjectProvider<T> or @Lookup when you want a new one per use.
  • Dagger turns lifetimes into types: a component is a scope, and the compiler checks the graph.
  • NestJS avoids captives by propagating scope instead of rejecting it: anything that depends on a REQUEST provider becomes request-scoped itself, all the way up to the controller. This is safe but has a cost: a deep request-scoped chain means many objects are created per request. TRANSIENT means one instance per consumer, not per call.
  • FastAPI has no container, only a per-request dependency graph. Depends caches each dependency once per request by default. A yield dependency is the per-request "scope": the code after yield is its dispose. Its exact timing relative to the response and to background tasks has changed between FastAPI versions, so never hand a yielded session to a BackgroundTask; open a new one inside it. App-wide objects are simply module-level objects, lru_cached factories, or values created in the lifespan handler.
  • Go has no container by default, so lifetime equals where you construct the value. Values built in main are singletons and must be safe for concurrent use: *sql.DB and *http.Client are designed for this; a map is not. Values built in a handler live for that request, and cleanup is a defer. context.Context carries request-scoped values (deadlines, trace ids), not services. Wire generates this wiring and supports cleanup functions; Fx builds singletons at startup and runs fx.Lifecycle OnStart/OnStop hooks.

Choosing a lifetime

Service Usual lifetime Why
DbContext, ISession (NHibernate), unit of work Scoped Change tracking and transactions are per request, and they are not thread-safe.
IOptions<T> / IOptionsMonitor<T> Singleton Immutable or change-notifying configuration. IOptionsSnapshot<T> is scoped: re-read per request.
ILogger<T>, TimeProvider, IMemoryCache Singleton Thread-safe by design.
Typed HttpClient (AddHttpClient<T>) Transient client over pooled handlers The factory pools and rotates the handlers. Do not capture a typed client in a singleton, or DNS changes are never seen.
Current user, tenant, correlation context Scoped Belongs to one request.
Stateless domain services, validators Singleton or transient Either works. Singleton saves allocations; transient avoids accidental shared state. Keep them stateless.
IHostedService / BackgroundService Singleton (fixed) Uses IServiceScopeFactory for anything scoped.

When not to reach for a particular lifetime

  • Not singleton "for performance" when the class has mutable fields, or depends on anything scoped. Allocation is cheap; data races and captured contexts are not. Measure first.
  • Not transient "to be safe". Transient disposables resolved from the root leak until shutdown, transients inside singletons are singletons anyway, and a transient DbContext breaks the shared unit of work within a request.
  • Not scoped outside a scope. In console apps, tests and workers there is no automatic scope: either create one, or use a factory and own the object yourself.

Pitfalls and production war stories

The captive DbContext behind a "harmless" cache The opening story. It was found only because the error rate rose with traffic: "A second operation was started on this context instance". The real cost was weeks of stale prices that nobody had noticed. Fix: the cache became a singleton IMemoryCache wrapper with no database dependency, and a scoped PriceService reads through it. ValidateOnBuild is now on in every environment, and a test builds the host.

Fire-and-forget with the request's context _ = Task.Run(() => audit.WriteAsync(db, evt)); in a controller works locally, where requests are slow and the audit write wins the race. In production the response completes first, the scope disposes db, and the audit write fails with "Cannot access a disposed context instance". It runs on a thread-pool thread, so nobody sees the exception. Fix: enqueue the data to a Channel<T> read by a BackgroundService that creates its own scope.

A singleton that is "stateless" but holds a non-thread-safe dependency A singleton ReportFormatter held a StringBuilder field "to avoid allocations", and a singleton ShippingCalculator held a Random. Both produced corrupted output only under load. System.Random is not thread-safe: under concurrent use its state can be corrupted until it returns only zeros. Fix: no mutable instance state in singletons. Use locals, Random.Shared, or make the service transient.

Spring prototype inside a singleton A @Scope("prototype") ShoppingCart was injected into a singleton controller, so every customer shared one cart. Spring injects the prototype once, when it creates the singleton, and validation does not flag it. Fix: ObjectProvider<ShoppingCart>.getObject() per use, or @SessionScope with a proxy, which is what was actually meant.

Resolving from app.Services at startup app.Services.GetRequiredService<AppDbContext>().Database.Migrate(); resolves a scoped service from the root. With validation on it throws "Cannot resolve scoped service from root provider". With validation off, the context lives in the root until shutdown. Fix: using (var scope = app.Services.CreateScope()) { scope.ServiceProvider.GetRequiredService<AppDbContext>().Database.Migrate(); }.

NestJS: one request-scoped provider makes the whole chain request-scoped Adding Scope.REQUEST to a small TenantContext made every service that depended on it, and every controller above them, request-scoped. Each request now constructed dozens of objects, and p99 latency doubled. Fix: keep request-scoped providers at the edges. Pass the tenant id as an argument, use AsyncLocalStorage (for example through nestjs-cls), or use durable providers (one sub-tree per tenant, not per request).

Best-practice checklist

  • Choose each lifetime deliberately: scoped for per-request state, singleton for thread-safe shared services, transient for cheap per-use objects.
  • No dependency arrow points to a shorter lifetime: singleton → scoped never; singleton → transient only for stateless helpers.
  • ValidateScopes and ValidateOnBuild are on, and a test builds the real host so validation runs in CI.
  • Singletons have no mutable state that is not thread-safe, and every dependency they hold is also safe to share.
  • Nothing calls Dispose on an injected dependency; code disposes only what it created.
  • Singletons that need scoped services inject IServiceScopeFactory and create one scope per unit of work with CreateAsyncScope().
  • Work that outlives a request receives data, not the request's scoped objects.
  • Scoped and transient services are never resolved from the root (app.Services) outside a scope.
  • Services with async cleanup implement IAsyncDisposable, and every scope that might own them is disposed with await using.
  • In other ecosystems, know the equivalents: Spring ObjectProvider for prototypes, Dagger subcomponents, NestJS scope bubbling, FastAPI per-request caching and yield, and Go's "where you construct it is its lifetime".

Self-check

PriceCalculator is transient and depends on a scoped AppDbContext. In one request it is resolved three times. How many contexts are created?

One. Each resolution creates a new PriceCalculator, but each of them asks the same scope for AppDbContext, and the scope caches it. Three calculators share one context, and therefore one unit of work. A second request gets a different context.

A singleton depends on a transient. Is that a captive dependency?

Technically yes: the transient's effective lifetime becomes singleton, because it is created once and held forever. MS.DI allows it, because it is harmless for a stateless helper. It is a real bug if the transient is transient because it is stateful or not thread-safe, or if it is disposable. Only singleton → scoped is rejected by ValidateScopes.

Why does injecting Func<AppDbContext> into a singleton not fix the captive dependency?

MS.DI has no built-in Func<T>, so you register one yourself (sp => () => sp.GetRequiredService<AppDbContext>()). The sp it closes over is the provider that built the singleton, which is the root. Each call either throws (with scope validation) or creates a root-owned context that is not disposed until shutdown. The fix needs a new scope: IServiceScopeFactory.CreateAsyncScope(), or an IDbContextFactory<T> whose contexts you dispose yourself.

Which instances does the container dispose: AddSingleton(new Cache()), AddSingleton<Cache>(), AddSingleton(sp => new Cache())?

The second and the third. The container disposes what it created, and that includes instances returned by a factory lambda, since the container called it. An instance you passed in yourself is yours to dispose.

A scope created a disposable Repo, and then a disposable UnitOfWork that uses Repo. In what order are they disposed, and why?

UnitOfWork first, then Repo: reverse creation order. A dependency is always created before its consumer, so disposing newest first guarantees that UnitOfWork.Dispose can still flush through a live Repo.

Your BackgroundService needs AppDbContext. What is the correct shape, and why is one scope for the whole loop not good enough?

Inject IServiceScopeFactory and create a scope (await using var scope = scopes.CreateAsyncScope()) for each unit of work: a batch, a message or a tick. One scope around the whole loop would be a captive in disguise: one context for the life of the app, with an ever-growing change tracker, and one failed SaveChanges would leave it in a bad state for every later batch.

In NestJS, OrdersService (default scope) depends on a Scope.REQUEST provider. What happens to OrdersService?

It becomes request-scoped too, as does every provider and controller that depends on it. NestJS propagates scope up the injection chain rather than rejecting the dependency. That is correct and safe, but it means more objects created per request. Keep request-scoped providers at the edges.

TransientNew per resolution. Owned by the scope that created it. In a singleton it lives forever.

CaptiveA longer-lived consumer holds a shorter-lived service: stale data, races, leaks.
