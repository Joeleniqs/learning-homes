Design Principles: SOLID, DRY, KISS, YAGNI

Each principle shown as a before/after picture of the dependency graph, with the trade-offs and the ways each one is over-applied.

Beginner → Advanced~60 min studyUpdated 2026-11-03

The problem: every change touches everything

A product owner asks for "SMS receipts as well as email". It sounds like a one-day job. Then the developer finds that OrderService builds the email itself, the email template is assembled inside the PDF renderer, the tests construct a real SmtpClient, and the admin page calls OrderService.SendEmail directly. The one-day job touches nine files owned by three teams, and the release slips a week.

None of that code was wrong. Each line worked. The problem was the shape: which pieces knew about which other pieces. Design principles (SOLID, DRY, KISS, YAGNI, the Law of Demeter, composition over inheritance, separation of concerns) are not style rules. They are heuristics that keep the cost of change low by controlling two things: what changes together (cohesion) and what breaks together (coupling).

The rule. A design is good if the changes you actually get are cheap. Put things that change for the same reason together, put things that change for different reasons apart, and make dependencies point from volatile code toward stable code. Apply a principle when it lowers the cost of a change you can name. Do not apply it to a change you are only imagining.

Recognize that your design is fighting you when

  • A small feature request needs edits in many files, across team boundaries (shotgun surgery).
  • One class changes for unrelated reasons: tax rules on Monday, PDF layout on Tuesday (divergent change).
  • You cannot unit test business rules without a database, an HTTP server or a clock.
  • A subclass overrides a method to throw NotSupportedException, or a base class change breaks subclasses you have never seen.
  • Shared helpers have five boolean parameters, and nobody knows which combinations are used.
  • Or the reverse: every class has an I-prefixed interface with one implementation, and a "simple" feature means changing a controller, a service, a manager, a factory and a provider.

The mental model: coupling, cohesion and the cost of change

Every principle on this page is a special case of one idea: draw module boundaries around things that change together.

  • Cohesion is how strongly the pieces inside a module belong together. High cohesion means a module has one job, and its methods use the same data.
  • Coupling is how much a module knows about other modules: their types, their internals, their order of calls, their data formats. Low coupling means you can change one module without opening the others.

Coupling is not inherently bad: a program with zero coupling does nothing. What matters is what kind of coupling you have and where it sits. Depending on a stable, small interface is cheap. Depending on another class's concrete types, field layout or call order is expensive, because those change often.

See a change ripple through tight and loose designs

Pick a change request. The visualizer runs a breadth-first search over the real dependency graph: a module must change if it uses the changed module's details (its concrete types appear in the module's code or signatures). If the changed module exposes those types in its own API, the ripple continues to its users. The search stops at an edge where the user only knows an interface that did not change.

Compare the four change requests. Ports and adapters (the core owns small interfaces, infrastructure implements them) win big for vendor and storage changes. They do almost nothing for "add a tax rule", because that change was inside one module in both designs. That is the honest trade-off: indirection pays only where change actually arrives.

Measure cohesion: LCOM4

LCOM4 (Lack of Cohesion of Methods, version 4) counts the connected groups in a class. Two methods are connected if they use the same field or one calls the other. LCOM4 = 1 means one cohesive class. LCOM4 = 2 or more means the class is several classes sharing a name. Edit the class description and watch the groups merge with union-find.

Try changing renderPdf to renderPdf:fonts: LCOM4 rises to 3, because PDF rendering no longer shares any data with email. Try making emailReceipt read items: everything collapses into one group. That is the honest result too. If email really needs the cart, the split is less obvious, and you might extract a Receipt value instead.

Measure coupling: instability and the main sequence

Robert C. Martin's package metrics turn coupling into numbers. For each package, Ca (afferent) counts the packages that depend on it, and Ce (efferent) counts the packages it depends on.

  • Instability I = Ce / (Ca + Ce). 0 means maximally stable (many depend on it, so it is hard to change). 1 means maximally unstable (free to change).
  • Abstractness A = abstract types / all types.
  • Distance from the main sequence D = |A + I − 1|. Stable packages should be abstract (interfaces that others implement). Unstable packages can be concrete.

The two warnings in the default example are both common in real code. Domain depends on Infra, which is less stable than Domain: a Stable Dependencies Principle violation, fixed by dependency inversion (the D in SOLID). Util is maximally stable and completely concrete, so it sits in the zone of pain: everything depends on it, and any change ripples everywhere. That is fine for truly stable code like string helpers, and a problem for a Util package that keeps growing.

Tip: get these numbers for your own code NDepend and Visual Studio code metrics (.NET), JDepend and ArchUnit (Java), go list -deps with goda (Go), import-linter and pydeps (Python), and dependency-cruiser or madge (TypeScript) all compute dependency graphs, and most can fail a build when a forbidden dependency appears. Use them to guard boundaries, not to chase a score.

SOLID, one letter at a time

SOLID is five principles for object-oriented and modular code, collected by Robert C. Martin in the early 2000s. They apply just as well to Go packages, Python modules and TypeScript files as to C# and Java classes.

S · SINGLE RESPONSIBILITYOne reason to change

A module answers to one actor. Split by who asks for changes.

O · OPEN/CLOSEDExtend without editing

New behaviour arrives as new code behind a stable interface.

L · LISKOV SUBSTITUTIONSubtypes keep promises

Any implementation must pass the base contract's tests.

I · INTERFACE SEGREGATIONSmall, client-owned interfaces

No client depends on methods it does not call.

D · DEPENDENCY INVERSIONPoint arrows at policy

Core code owns abstractions. Details implement them.

S: Single Responsibility Principle

"A module should be responsible to one, and only one, actor." The common phrasing "a class should do one thing" is misleading, because everything can be described as one thing ("it handles invoices"). The useful test is: who will ask for this code to change? If Finance, the brand team and the DBA all edit Invoice, their changes collide, and a tax fix can break PDF layout.

Over-applied as: one method per class

InvoiceTotalCalculator, InvoiceTaxApplier, InvoiceLineSummer, each with an interface. The code that changes together (the pricing rules) is now spread over six files, so cohesion drops. That is destructive decoupling.

Break it when

The "actors" are really one person or team, and the class is small. A 60-line class that formats and saves a CSV export for one internal tool is fine. Split when two people start colliding in it, or when one half needs testing without the other.

O: Open/Closed Principle

"Software entities should be open for extension but closed for modification." In practice: when the kind of change you get is "one more variant" (a new discount, a new payment method, a new file format), arrange the code so a new variant is new code, not an edit to a switch that already works and is already tested.

Before: each new customer type edits the calculator.

public decimal Price(Customer c, decimal list) => c.Type switch
{
    CustomerType.Regular => list,
    CustomerType.Gold    => list * 0.90m,
    CustomerType.Staff   => list * 0.70m,
    // Student? Edit here, retest everything above.
    _ => throw new ArgumentOutOfRangeException(nameof(c))
};

}

@Service
class PriceCalculator {
    private final List<DiscountRule> rules; // Spring injects every DiscountRule bean
    PriceCalculator(List<DiscountRule> rules) { this.rules = rules; }

    BigDecimal price(Customer c, BigDecimal list) {
        BigDecimal p = list;
        for (DiscountRule r : rules) if (r.applies(c)) p = r.apply(p);
        return p;
    }
}

Over-applied as: plug-in points everywhere

A strategy interface, a factory and a registry for a switch with three cases that has not changed in two years. This is speculative generality: you pay for flexibility nobody uses, and readers must chase indirection to find the actual rule.

Break it when

The set of variants is closed and known (the four suits of a card deck, the HTTP methods you support). A switch over a sealed type or a discriminated union, with the compiler checking exhaustiveness (C# switch expressions with sealed records, Java sealed + pattern matching, TypeScript never checks), is simpler and safer. When you add a case, the compiler finds every place to update.

L: Liskov Substitution Principle

"If S is a subtype of T, then objects of type T may be replaced with objects of type S without breaking the program." Barbara Liskov's point is about behaviour: a subtype must accept at least what the base accepts (no stronger preconditions), promise at least what the base promises (no weaker postconditions), and keep the base's invariants. Type checkers check signatures. Only tests check promises.

The classic trap: in geometry a square is a rectangle, so Square extends Rectangle looks right. Step through what happens when a function written against Rectangle's contract receives a Square, then switch the design to two implementations of a smaller Shape contract.

The fix is to stop promising what some subtypes cannot deliver. Mutable setters are the problem: an immutable Square and an immutable Rectangle can both honestly implement Area(). Then enforce substitutability by running one contract test suite against every implementation. That is the practical form of LSP, and it is how you keep an in-memory fake honest against the real database repository.

Over-applied as: banning all inheritance

LSP does not say "never subclass". Framework base classes designed for extension (ControllerBase, HttpServlet, unittest.TestCase, Exception) document what you may override, and they are fine to extend.

Bend it when

A subtype deliberately refuses part of a contract that the base marks as optional, such as a read-only collection that throws on Add while IsReadOnly returns true. It is legal because the contract said so. If you find yourself writing that, it is usually a sign the interface should be split (ISP).

I: Interface Segregation Principle

"Clients should not be forced to depend on methods they do not use." A fat interface couples every client to every method. When Fax() changes signature, a receipt printer that never faxes still recompiles, and implementers that cannot fax must stub it with an exception, which breaks LSP.

Before:

public interface IMachine { void Print(Doc d); Doc Scan(); void Fax(Doc d); void Staple(Doc d); }

public sealed class SimplePrinter : IMachine
{
    public void Print(Doc d) { /* ... */ }
    public Doc Scan() => throw new NotSupportedException();   // forced by the interface
    public void Fax(Doc d) => throw new NotSupportedException();
    public void Staple(Doc d) => throw new NotSupportedException();
}

After: role interfaces, each shaped by what a client calls. Note how Go and TypeScript let the client declare the interface it needs, after the fact.

Over-applied as: interface explosion

One interface per method, per class, "for testability": IOrderReader, IOrderWriter, IOrderDeleter, IOrderCounter, each with exactly one implementation and one caller. Navigation becomes "Go to implementation" five times. Split when different clients really use different subsets, not by default.

Break it when

The interface describes one cohesive concept that callers use as a whole, like IDbConnection, java.util.List or io.ReadWriteCloser (which is itself composed of small interfaces). Wide is fine if it is cohesive.

D: Dependency Inversion Principle

"High-level modules should not depend on low-level modules. Both should depend on abstractions. Abstractions should not depend on details." The key word is inversion: in the naive design, source-code dependencies follow the call direction, so business rules import the database. After inversion, the business layer owns the interface (IOrderRepository), and the database adapter imports the business layer to implement it. The call still goes down; the source-code arrow points up.

// Domain project: no reference to EF Core.
public interface IOrderRepository
{
    Task<Order?> GetAsync(OrderId id, CancellationToken ct);
    Task SaveAsync(Order order, CancellationToken ct);
}

public sealed class PlaceOrder(IOrderRepository orders, TimeProvider clock)
{
    public async Task<OrderId> Handle(Cart cart, CancellationToken ct)
    {
        var order = Order.From(cart, clock.GetUtcNow());
        await orders.SaveAsync(order, ct);
        return order.Id;
    }
}

Over-applied as: an interface for every class

IOrderValidator, IMoneyFormatter, IStringHelper, each with one implementation that will never be swapped and is pure, fast and deterministic. You do not need to invert a dependency on code that has no I/O and no volatility. Test it directly.

Apply it at the boundaries

Invert dependencies on things that are slow, non-deterministic, external or likely to change: databases, HTTP APIs, message brokers, the file system, the clock, randomness, and third-party SDKs. That is where the ripple visualizer showed the payoff. Inside the core, call concrete classes directly.

DRY, WET and the rule of three

DRY ("Don't Repeat Yourself", from The Pragmatic Programmer) says: every piece of knowledge must have a single, unambiguous, authoritative representation. It is about knowledge, not about text. Two functions that look alike but encode different business rules are not duplication. They are a coincidence, and merging them couples two things that will change for different reasons.

WET ("Write Everything Twice") and the rule of three are the counterweight. Tolerate the second copy. When the third one appears, you have enough examples to see what really varies, so extract then.

Step through what happens when an abstraction is extracted and then requirements diverge. Every caller-specific need becomes a parameter and an if inside the shared function, and the number of possible paths doubles each time. Add more requirements, or more callers, and watch the branches multiply.

Sandi Metz's summary is the most useful rule here: duplication is far cheaper than the wrong abstraction. When a shared function has grown flags, the fix is not another flag. Inline it back into each caller, delete what that caller does not use, and look again for what is truly shared.

Real duplication (merge it)

The VAT rate is hard-coded in the checkout, the invoice and the refund service. That is one fact in three places, and when it changes, missing one is a bug. Give it one home (config, a TaxPolicy, a shared constant).

Coincidental duplication (leave it)

MaxUsernameLength = 32 and MaxSkuLength = 32. Same number, different knowledge, different owners. Sharing one constant means a SKU change silently changes usernames.

Knowledge duplicated across layers

The same validation rule in the React form, the API and the database constraint. Some repetition is intended (defence in depth). Generate it from one source (OpenAPI or JSON Schema, Zod, FluentValidation rules shared with the client) where the tools allow.

KISS: keep it simple

"Keep it simple" is not "write less code". It means minimise the number of concepts a reader must hold to understand the code. A plain loop beats a clever reduce-with-tuple-accumulator. A switch beats a strategy registry when there are three cases. A function beats a class with one method and a constructor that stores its argument.

Clever

A generic IPipeline<TIn, TOut> with reflection-discovered steps, built to process one CSV file type. Correct, tested and impossible to debug at 3 a.m., because the call stack is 40 frames of framework code.

Simple

ReadRows() → Validate() → Save(): three functions called in order from one method. When a second file type arrives, you will know what varies, and you can add the abstraction then.

Simple is not easy

Simple code can take longer to write: you must understand the problem well enough to remove the incidental parts. "Simple" also does not mean "naive". A correct retry with backoff and jitter is simple; a hand-rolled one with a bug is merely short.

YAGNI: you aren't gonna need it

From Extreme Programming: do not build capability for a requirement you do not have yet. The argument is not that the future feature is unlikely. It is that building it now has four costs, and three of them are paid even if you guessed right.

COST OF BUILDTime spent now

Effort that did not go into a feature users are asking for today.

COST OF DELAYValue shipped later

The current feature reaches users later because of the extra work.

COST OF CARRYComplexity you maintain

Every reader, test and refactor pays for the unused code until it is deleted.

COST OF REPAIRThe guess was wrong

When the real requirement arrives it differs, and the speculative design is in the way.

YAGNI applies to features and flexibility, not to practices that keep code changeable: tests, clear names, small functions, and refactoring. Those make the future change cheap, which is exactly why you can afford to wait for it. It also does not apply to decisions that are expensive to reverse later, like public API shapes, data formats on disk, security and the ability to observe production. Spend thought on those up front.

Law of Demeter: talk to friends, not strangers

A method should only call methods on: itself, its parameters, objects it creates, and its own fields. Each . that reaches through an object into its internals couples the caller to one more class's shape. Then a change to Address breaks CheckoutPage.

Over-applied as: wrapper methods everywhere

Adding Order.GetCustomerAddressCityUppercased() for every caller's need turns Order into a God class. If many callers need customer data, pass them the Customer, not the Order.

Not a violation

Fluent APIs and pipelines return the same kind of object at each step: LINQ, Java streams, builders, strings.NewReplacer(...).Replace(...), Promise chains. Plain data (DTOs, records, JSON) is also fine to navigate. Demeter is about reaching into objects with behaviour and their private structure.

Composition over inheritance

Inheritance does two things at once: it makes Child a subtype of Parent (substitutable, LSP), and it lets Child reuse Parent's implementation. The second part is the dangerous one. The subclass becomes coupled to the parent's internals: which methods call which other methods, in what order. Those are implementation details the parent's author is free to change. This is the fragile base class problem.

The visualizer replays the example from Effective Java (Item 18). A CountingSet extends a library HashSet and overrides both add and addAll to count insertions. With library v1, addAll internally calls add once per item, so virtual dispatch sends each call back into your override, and every item is counted twice. With v2, the library inserts directly and the same subclass is correct. Switch to composition and the answer is right on both versions.

The trap has a second edge. If you "fix" the v1 bug by not overriding addAll, your class now relies on the self-call, and upgrading to v2 makes it silently undercount. Either way, your correctness depends on an undocumented detail. Composition removes the dependency: you hold a set and forward to it, so the set's internal calls never reach your code.

// C# methods are non-virtual by default, so HashSet<T>.Add cannot even be overridden.
// Composition is the natural shape:
public sealed class CountingSet<T>
{
    private readonly HashSet<T> _items = new();
    public int Added { get; private set; }
    public int Count => _items.Count;

    public bool Add(T item) { Added++; return _items.Add(item); }

    public void AddRange(IEnumerable<T> items)
    {
        foreach (var item in items) Add(item);
    }

    public bool Contains(T item) => _items.Contains(item);
}

// Guava's ForwardingSet: every call goes to delegate(), whose own
// internal self-calls stay inside the delegate.
public final class CountingSet<E> extends ForwardingSet<E> {
    private final Set<E> delegate = new HashSet<>();
    private int added;

    @Override protected Set<E> delegate() { return delegate; }

    @Override public boolean add(E e) {
        added++;
        return delegate.add(e);
    }

    @Override public boolean addAll(Collection<? extends E> c) {
        added += c.size();
        return delegate.addAll(c); // HashSet.addAll calls HashSet.add, not ours
    }

    public int added() { return added; }
}

# Subclassing built-ins has the same trap in reverse: dict.update() does NOT
# call your overridden __setitem__. Wrap instead of inheriting.
class CountingSet(Generic[T]):
    def __init__(self) -> None:
        self._items: set[T] = set()
        self.added = 0

    def add(self, item: T) -> None:
        self.added += 1
        self._items.add(item)

    def update(self, items: Iterable[T]) -> None:
        for item in items:
            self.add(item)

    def __len__(self) -> int:
        return len(self._items)

    def __contains__(self, item: object) -> bool:
        return item in self._items

// Go has no inheritance. Embedding promotes methods, but the embedded value's
// methods never dispatch back to the outer type, so this bug cannot happen.
type CountingSet[T comparable] struct {
    items map[T]struct{}
    added int
}

func NewCountingSet[T comparable]() *CountingSet[T] {
    return &CountingSet[T]{items: make(map[T]struct{})}
}

func (s *CountingSet[T]) Add(x T) {
    s.added++
    s.items[x] = struct{}{}
}

func (s *CountingSet[T]) AddAll(xs ...T) {
    for _, x := range xs {
        s.Add(x)
    }
}

func (s *CountingSet[T]) Len() int { return len(s.items) }

export class CountingSet<T> {
  readonly #items = new Set<T>();
  #added = 0;

  add(item: T): this {
    this.#added++;
    this.#items.add(item);
    return this;
  }

  addAll(items: Iterable<T>): this {
    for (const item of items) this.add(item);
    return this;
  }

  get added(): number { return this.#added; }
  get size(): number { return this.#items.size; }
  has(item: T): boolean { return this.#items.has(item); }
}

Inheritance is right when

There is a true is-a relationship that passes LSP, and the base class was designed and documented for extension: template-method hooks in frameworks, Exception hierarchies, sealed hierarchies of data types (sealed record Shape, sealed interface in Java). You own both sides, or the base documents its self-use.

Inheritance is wrong when

You only want to reuse code ("it already has the methods I need"), the base is a concrete class from another team or library, or you are building combinations of behaviours (logging + retry + caching), which explode into 2ⁿ subclasses.

Defaults that help

Mark classes sealed (C#) or final (Java, and Kotlin's default) unless they are designed for extension. Prefer interfaces with default methods or mixins only for small, stable behaviour. In Go, Rust and TypeScript-with-functions, composition is already the default.

Separation of concerns

Separation of concerns (Dijkstra's term) is the parent of most other principles: give each kind of knowledge its own place. HTTP details, workflow, business rules, storage and cross-cutting policies (auth, logging, retries) change for different reasons, at different speeds, and are tested in different ways. When they share a function, every change to one risks the others.

The concrete moves:

  • Transport (controllers, minimal API handlers, Spring @RestController, FastAPI routes, Express or Nest handlers) only translates HTTP to a command and the result back to HTTP.
  • Application (use cases) orchestrates: load, call domain logic, save, publish. It contains no SQL and no HTTP.
  • Domain holds the rules and can be unit tested with no infrastructure at all.
  • Infrastructure implements the ports: repositories, message publishers, email gateways.
  • Cross-cutting concerns run once in the request pipeline or as decorators, not copied into every handler.

Layers by concern

Each layer is easy to read and test alone. Works well when the domain logic is rich and long-lived. See Application architecture for clean, hexagonal and onion variants.

Vertical slices

Group by feature first (PlaceOrder/ with its endpoint, handler, validator and query), then separate concerns inside the slice. This keeps code that changes together close, and avoids touching five layer folders for one feature.

Over-applied as: pass-through layers

Controller → Service → Manager → Provider → Repository, where four of the five methods are one line that forwards the call. Every feature edits five files, and none of the layers holds a decision. Collapse layers that do not own a concern.

When to apply a principle, and when to break it

Principles are tools for one goal: cheap, safe change. Each one has a cost (more types, more indirection, more files to read). Apply it when you can name the change it makes cheaper.

Pitfalls

Pitfall: interfaces with exactly one implementation, everywhere The codebase has IUserService/UserService, IUserManager/UserManager, IUserHelper/UserHelper. The interfaces are copies of the classes ("header interfaces"), owned by the implementer, and never swapped. Fix: delete the interfaces for pure in-process code and test it directly. Keep interfaces at I/O boundaries, shaped by and owned by the consumer. Modern mocking (and fakes) do not need an interface per class.

Pitfall: DRY by appearance Two validators look the same, so they are merged into ValidateCode(string code, bool isSku, bool allowLower). Six months later it has four flags. Fix: inline it back into each caller (as in the wrong-abstraction visualizer), delete unused branches, and extract only what is genuinely the same knowledge.

Pitfall: inheriting for reuse AdminController : UserController to reuse three helper methods. Now admin routes inherit user routes and filters, and a change to UserController breaks the admin UI. Fix: move the helpers into a service both controllers use, and mark controllers sealed/final.

Pitfall: a domain that imports infrastructure Order.Save() calls DbContext, or a domain entity has [Table], @Entity or SQLAlchemy columns plus business rules that need a database to test. Fix: invert the dependency. The domain declares IOrderRepository, infrastructure implements it, and an architecture test (ArchUnit, NetArchTest, import-linter, dependency-cruiser) fails the build if the arrow points the wrong way.

Pitfall: principles as a review weapon "This violates SRP" with no change in mind, leading to a refactor that adds four files and helps nobody. Fix: in reviews, name the concrete change that the structure makes expensive, and the ripple it would cause. If you cannot, it is a preference, not a defect.

Checklist

  • [ ] For each module I can say who asks for it to change (one actor or reason).
  • [ ] Business rules can be unit tested without a database, network, file system or real clock.
  • [ ] Dependencies on I/O, vendors and frameworks go through small interfaces owned by the core; nothing in the domain imports infrastructure.
  • [ ] Interfaces are shaped by their clients. No implementation throws NotSupported for part of its interface.
  • [ ] Every interface with more than one implementation has a contract test suite run against all of them.
  • [ ] No shared helper takes boolean "mode" flags that only one caller uses.
  • [ ] Variants that keep arriving plug in as new code. Closed sets use exhaustive switch/pattern matching.
  • [ ] Inheritance only where the base is designed for extension. Everything else is sealed/final and reuses by composition.
  • [ ] Callers do not reach through two or more objects with behaviour (a.B.C.D()).
  • [ ] Cross-cutting concerns (auth, logging, retries, errors) live in the pipeline or decorators, once.
  • [ ] Every interface, layer and extension point pays for itself with a change that actually happened or is scheduled.
  • [ ] Module boundaries are guarded by an automated dependency rule.

Quiz

A class has methods CalculatePayroll(), ReportHours() and Save(). Accounting owns payroll, operations owns the hours report, and the DBAs own storage. Which principle is at risk, and how do you split it?

SRP: the class answers to three actors. If payroll and hours share a private helper (say RegularHours()), a change for accounting silently alters the operations report. Split into PayCalculator, HourReporter and EmployeeRepository over a shared EmployeeData record, and give each actor's logic its own copy of anything they may change independently.

ReadOnlyRepository extends Repository and throws on Save(). Is that an LSP violation?

Yes, unless Repository's contract explicitly says Save may be unsupported (and offers a way to check). Callers written against Repository expect Save to work. Better: split into IReadRepository and IWriteRepository (ISP), and let the read-only type implement only the first.

You have a switch over three shipping providers. Product says "we might add more one day". Do you introduce a strategy interface now?

Probably not (YAGNI, KISS). A switch over a closed enum with compiler exhaustiveness checking is clear, and turning it into a strategy later is a mechanical refactor. Introduce the interface when a fourth provider actually arrives, or immediately if providers are added by another team or loaded as plug-ins.

Two services both format a date as yyyy-MM-dd. One is the invoice PDF; the other is an ISO-8601 API field. Should they share a helper?

They encode different knowledge. The API format is fixed by a standard and must never change. The PDF format belongs to the brand team and may become "3 March 2026" next year. Use the platform's ISO formatter in the API, and a separate, owned formatter for the PDF. Merging them couples a contract to a style choice.

In the coupling visualizer, Util has I = 0 and A = 0. Is that always a problem?

No. It is in the "zone of pain" because changes ripple everywhere, but that only hurts if it changes. A truly stable, concrete package (string helpers, System.Math, the standard library) is fine there. The warning is for packages that are both heavily depended on and still evolving. Keep them small, or move the volatile parts out behind interfaces.

Your LoggingList extends ArrayList and overrides add to log. After a JDK upgrade, items added via addAll are no longer logged. What happened, and what is the fix?

The fragile base class problem: your override relied on ArrayList.addAll calling add, an undocumented internal detail that changed. Fix with composition: wrap a List (for example with Guava's ForwardingList, overriding both add and addAll explicitly), so the delegate's internal calls never reach your code.
