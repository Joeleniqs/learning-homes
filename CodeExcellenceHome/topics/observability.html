Observability: Logs, Metrics & Traces

Structured logging, RED/USE metrics, distributed tracing with OpenTelemetry, and how to make a 3 a.m. incident debuggable.

Intermediate → Advanced~55 min studyBuilds on: Middleware Patterns & OrderingUpdated 2026-11-03

The problem: flying blind at 3 a.m.

The pager goes off at 03:12: "checkout latency SLO burning". You open the service's logs and find 40,000 lines a minute that look like Processing order... and Done.. None of them says which request was slow. The dashboard shows average latency, which has barely moved. There is no trace, so you cannot tell whether the time went to the database, the pricing service or the payment gateway. Forty minutes later someone remembers that v42 went out at 02:40, and you roll it back on a hunch. It works. Nobody ever finds out why.

Every part of that night is an observability failure: logs with no structure or correlation, metrics that average away the tail, no traces, and an alert that fired without any path from symptom to cause. Observability is the ability to answer a new question about your running system without shipping new code. You get it by emitting the right signals, with the right shape, linked by the same ids, before the incident.

The rule. Emit metrics to detect (cheap, aggregated, alertable), traces to localize (where in the call graph), logs to explain (what happened to this one request), and profiles to find hot code. Put the same trace_id on all of them, alert on symptoms users feel (SLO burn), and never put unbounded values in metric labels or secrets in logs.

Recognize that your observability is not good enough when

  • An incident review says "we added logging and redeployed to find out".
  • Log lines are sentences built with string interpolation, so you search them with regexes.
  • Dashboards show averages, and nobody can say what the p99 was yesterday.
  • You cannot follow one request from the edge to the database across services.
  • Alerts fire on CPU > 80% at night and get acknowledged without action.
  • The metrics bill doubled after someone added a user_id label.

Four signals, four questions

Each signal type is optimised for a different question, and they are cheap or expensive in different ways. Metrics are numbers aggregated in-process, so their cost does not grow with traffic. Logs and traces are per-event, so their cost does. Profiles are statistical samples of what the CPU or heap is doing.

Pick an incident and step through how each signal does. Notice that no signal wins every time. A memory leak is invisible to traces, and a single customer's failed order is invisible to metrics.

Metrics are good at

  • Alerting: cheap to evaluate every 30 seconds for months.
  • Trends and capacity: "requests per second per region for the last 90 days".
  • Fixed cost: a counter costs the same at 10 or 10,000 req/s.

Metrics are bad at

  • Single events: one failed order disappears in a rate.
  • High-cardinality questions: "which user?" cannot be a label.
  • Explaining why: they tell you p99 went up, not which code path.

Logs and traces are good at

  • Rich context per event: ids, payload sizes, decisions taken, errors.
  • High cardinality is free: user_id, order_id and sku are just fields.
  • Following one request end to end.

Logs and traces are bad at

  • Cost: volume grows with traffic, so you sample or pay.
  • Alerting: counting log lines to alert is slow and fragile; emit a metric instead.
  • Long retention: weeks at full fidelity gets expensive fast.

Events vs aggregates. Some teams ("observability 2.0") emit one wide structured event per request with dozens of fields and derive metrics from those events at query time. It is powerful for exploring unknown questions, and it is the logical end of "structured logging + tracing". Most stacks still keep pre-aggregated metrics for alerting, because evaluating an alert over raw events every 30 seconds costs far more.

Structured logging

A log line is a record, not a sentence. A structured log line is a set of named fields (level, timestamp, message, order_id, elapsed_ms, trace_id) rendered as JSON or logfmt, so a log store can filter, group and aggregate on fields instead of parsing text.

Message templates, not string interpolation

The single most important logging habit is to pass values as arguments to a template, not to build the string yourself. The template ("Order {OrderId} took {Elapsed} ms") stays constant, so every event of that kind can be grouped. The values become typed, queryable fields. And when the level is disabled, the logger can skip all the work.

// The string is built before LogDebug runs, even when Debug is off.
// Every message is unique, so you cannot group by "kind of event".
// Elapsed is now text inside a sentence: querying "> 500" needs a regex.
_log.LogDebug($"Cache miss for {key}");
_log.LogInformation($"Order {order.Id} took {sw.ElapsedMilliseconds} ms");
_log.LogInformation("Order " + order.Id + " failed: " + ex.Message); // and the stack trace is lost

// The template is a constant; values are captured as named properties.
// If Debug is disabled, nothing is formatted or allocated for the value.
_log.LogDebug("Cache miss for {CacheKey}", key);
_log.LogInformation("Order {OrderId} took {ElapsedMs} ms", order.Id, sw.ElapsedMilliseconds);
_log.LogError(ex, "Order {OrderId} failed", order.Id); // exception as its own field, with the stack

// Hot path: source-generated, no boxing, no params array, IsEnabled checked for you.
static partial class Log
{
    [LoggerMessage(EventId = 1001, Level = LogLevel.Information,
        Message = "Order {OrderId} took {ElapsedMs} ms")]
    public static partial void OrderTook(ILogger logger, Guid orderId, long elapsedMs);
}

The same rule applies everywhere, with different syntax: SLF4J {} placeholders, Python's %s style with logger.info("…%s", x) (never an f-string), Go's key-value pairs, and pino's merge object as the first argument. Two caveats:

  • Placeholder formatting is lazy, argument evaluation is not. log.debug("{}", expensive()) still calls expensive(). Guard it with isDebugEnabled() / IsEnabled(LogLevel.Debug), or pass a supplier (log.atDebug().addArgument(() -> expensive()) in SLF4J 2).
  • Property names are a schema. OrderId in one service and order_id in another breaks cross-service queries. Agree on names; OpenTelemetry's semantic conventions (http.request.method, db.system, user.id) are a good default.

Structured logging in five ecosystems

The shapes are the same everywhere: a JSON sink, a logger per component, a way to attach context (order id, tenant, trace id) once per request so every line below it carries those fields, and named values on each event. What differs is how each runtime carries that per-request context across await points and threads.

// log/slog (standard library since Go 1.21). Context travels explicitly:
// a *slog.Logger with attributes, or a context.Context the handler reads.
package checkout

import (
    "context"
    "log/slog"
    "os"
    "time"
)

func NewLogger() *slog.Logger {
    return slog.New(slog.NewJSONHandler(os.Stdout, &slog.HandlerOptions{Level: slog.LevelInfo}))
}

func Handle(ctx context.Context, log *slog.Logger, o Order) error {
    log = log.With("order_id", o.ID, "tenant_id", o.TenantID) // context for every line below
    start := time.Now()
    if err := price(ctx, o); err != nil {
        log.ErrorContext(ctx, "pricing failed", "err", err)
        return err
    }
    log.InfoContext(ctx, "items priced",
        "item_count", len(o.Items),
        slog.Duration("elapsed", time.Since(start)))
    return nil
}

// AsyncLocalStorage makes the request's child logger available after any await.
import pino from "pino";

  store.run(base.child({ requestId: req.headers["x-request-id"] }), next));

export async function handle(order: Order): Promise<void> {
  const l = log().child({ orderId: order.id, tenantId: order.tenantId });
  const start = performance.now();
  await price(order);
  // merge object first, message second: fields stay fields
  l.info({ itemCount: order.items.length, elapsedMs: Math.round(performance.now() - start) },
         "items priced");
}

Why the context mechanisms differ. .NET (AsyncLocal), Python (contextvars) and Node (AsyncLocalStorage) all have an implicit async context that flows through await, so a scope set at the top of a request reaches every line. Java's MDC is a ThreadLocal, which is perfect for one thread per request but is lost when you hop executors. Go has no implicit context at all by design: you pass ctx and a logger explicitly, which is more typing but never surprising. In-process correlation middleware is covered in Middleware Patterns; this page is about what crosses the network.

Log levels: what each one is for

Levels are a contract with whoever reads the logs at 3 a.m. Use them consistently, and make the minimum level configurable per namespace without a redeploy (see Configuration & Secrets).

Level Use it for Example In production
Trace / Verbose Step-by-step internals, payloads "Parsed header X-Foo=…" Off. Turn on for one namespace, briefly.
Debug Diagnostic decisions a developer needs "Cache miss for {Key}", "Retrying in {Delay}" Usually off, or sampled
Information Normal, notable business events "Order {OrderId} placed", "Started on port {Port}" On. Keep it to a few lines per request.
Warning Unexpected but handled; might need attention "Retry {Attempt} for {Dependency}", "Config X deprecated" On. Never sampled.
Error This operation failed; a human may need to act "Payment {OrderId} failed" + exception On. Never sampled. Usually also a metric.
Critical / Fatal The process or a core capability is down "Cannot reach database at startup" On. Often followed by exit.

Log an error once, where it is handled. If every layer catches, logs and rethrows, one failure becomes five ERROR lines with five stack traces. Let exceptions propagate with context (wrap them, add fields to the span), and log at the boundary that decides what to do: the request handler, the message consumer, the background job loop.

Volume control: levels, sampling and flush-on-error

At high traffic even Information logs are expensive. There are three levers, applied in this order: drop below the minimum level (free), then sample, but never sample warnings or errors. How you sample decides whether the lines you keep still tell a story. Compare per-line, per-trace and flush-on-error sampling below, and count the failing requests that kept their full context.

  • Per-line random sampling keeps the right volume but shreds stories: you get the error line without the five lines that led to it.
  • Per-trace sampling hashes the trace id, so every service keeps or drops the same requests. Stories stay whole, but only for the lucky ones.
  • Flush-on-error buffers a request's lines in memory and writes them only if the request fails (or is slow). This keeps full context for every failure at a fraction of the volume. It costs memory per in-flight request, and you lose the buffer if the process crashes.
  • Rate limiting per message template ("at most 10/s of 'Cache miss for {Key}'") stops one noisy line from drowning everything else.

What never to log

Logs are copied to more places (log shippers, vendors, laptops, support tickets) and kept longer than almost any other data, with weaker access control than your database. Treat them as public-ish.

Never log Why Log this instead
Passwords, API keys, tokens, connection strings, Authorization / Cookie headers Anyone with log access can impersonate the user or service token_present=true, key id or last 4 characters of the key's hash
Full card numbers, CVV, bank details PCI DSS scope for your whole log pipeline Last 4 digits, card brand
Personal data (email, phone, address, national ids, health data) GDPR and similar laws: retention, deletion and access requests apply to logs too A stable internal user id, or a keyed hash
Whole request or response bodies They contain all of the above, sooner or later Size, content type, the specific fields you need
Free text typed by users Unbounded, may contain anything Length, language, a classification

Redact at the source, by type, so a careless log.info(user) cannot leak. Each ecosystem has an idiomatic hook:

    public static DataClassification Private => new("Shop", "Private");

public sealed class PrivateDataAttribute() : DataClassificationAttribute(Taxonomy.Private);

    r.SetRedactor<ErasingRedactor>(new DataClassificationSet(Taxonomy.Private)));
// Email is erased before any sink sees it. Use a HMAC redactor instead if you
// need to correlate the same user across lines without storing the address.

// Make sensitive types unable to print themselves. toString() is what
// SLF4J placeholders, string concatenation and most JSON encoders fall back to.
public record Email(String value) {
    @Override public String toString() {
        int at = value.indexOf('@');
        return at > 0 ? "***" + value.substring(at) : "***";   // keep the domain only
    }
}

public record ApiKey(String value) {
    @Override public String toString() { return "ApiKey[redacted]"; }
}

log.info("Signed up {}", new Email("ana@example.com"));   // Signed up ***@example.com
// For JSON encoders that serialise fields directly, add masking in the encoder too
// (logstash-logback-encoder has a MaskingJsonGeneratorDecorator for field paths).

# A structlog processor that redacts by key name, anywhere in the event dict.
import structlog

SENSITIVE = {"password", "token", "authorization", "api_key", "card_number", "email"}

def redact(_, __, event: dict) -> dict:
    def scrub(v):
        if isinstance(v, dict):
            return {k: ("[REDACTED]" if k.lower() in SENSITIVE else scrub(x)) for k, x in v.items()}
        if isinstance(v, list):
            return [scrub(x) for x in v]
        return v
    return scrub(event)

structlog.configure(processors=[redact, structlog.processors.JSONRenderer()])
structlog.get_logger().info("login", user={"id": 7, "email": "ana@example.com"}, password="hunter2")
# {"user": {"id": 7, "email": "[REDACTED]"}, "password": "[REDACTED]", "event": "login"}

// slog.LogValuer: a type decides how it is logged, wherever it is logged.
type Secret string

func (Secret) LogValue() slog.Value { return slog.StringValue("[REDACTED]") }

type Email string

func (e Email) LogValue() slog.Value {
    if i := strings.IndexByte(string(e), '@'); i > 0 {

Exceptions leak too. A database driver's exception message can contain the connection string; an HTTP client's can contain the full URL with a ?api_key= query parameter; a validation error can echo the input. Review what your exception types put in Message, and scrub URLs before logging them. Secret scanning on your log store is a good safety net (see Configuration & Secrets).

Correlation: one id across every hop

A request that touches a gateway, three services, a queue and an email worker leaves log lines in six places. Without a shared id, joining them means guessing by timestamp. The fix is to create a trace context at the edge and carry it on every outbound call and every message, so each service's logs, spans and errors carry the same trace_id.

The W3C Trace Context standard makes that header the same everywhere, so a .NET service, a Java service and a Node worker all understand each other:

Follow a request through five services. Then switch propagation to lost at the queue (a consumer that does not read the message headers) and to none, and try to answer the support question at the end.

Queues and background jobs are where context dies. HTTP clients are auto-instrumented in every OpenTelemetry SDK, so the header gets added for you. Messages are not always: you must write the context into message headers (or attributes) when producing and extract it when consuming. For batch consumers, one consumer span can link to many producer spans instead of having one parent. The same applies to scheduled jobs: start a new trace, and log the id of whatever triggered it.

// .NET: Activity is the span. HttpClient propagates traceparent automatically.
// For a message bus, inject and extract with the configured propagator.
using OpenTelemetry;
using OpenTelemetry.Context.Propagation;

static readonly ActivitySource Source = new("Shop.Orders");
static readonly TextMapPropagator Prop = Propagators.DefaultTextMapPropagator;

// producer
using (var act = Source.StartActivity("orders publish", ActivityKind.Producer))
{
    var headers = new Dictionary<string, string>();
    Prop.Inject(new PropagationContext(act!.Context, Baggage.Current), headers,
        (h, k, v) => h[k] = v);
    await bus.PublishAsync(orderPlaced, headers);
}

// consumer
var parent = Prop.Extract(default, msg.Headers,
    (h, k) => h.TryGetValue(k, out var v) ? [v] : []);
using var span = Source.StartActivity("orders process", ActivityKind.Consumer,
    parent.ActivityContext);

// Java: the OpenTelemetry Java agent instruments Kafka, JMS, RabbitMQ and HTTP clients.
// Manual inject/extract for anything it does not know about:
TextMapPropagator prop = openTelemetry.getPropagators().getTextMapPropagator();

// producer
Span span = tracer.spanBuilder("orders publish").setSpanKind(SpanKind.PRODUCER).startSpan();
try (Scope s = span.makeCurrent()) {
    Map<String, String> headers = new HashMap<>();
    prop.inject(Context.current(), headers, Map::put);
    bus.publish(orderPlaced, headers);
} finally { span.end(); }

// consumer
Context parent = prop.extract(Context.current(), msg.headers(), new TextMapGetter<>() {
    public Iterable<String> keys(Map<String, String> c) { return c.keySet(); }
    public String get(Map<String, String> c, String k) { return c == null ? null : c.get(k); }
});
Span consume = tracer.spanBuilder("orders process").setParent(parent)
        .setSpanKind(SpanKind.CONSUMER).startSpan();

# Python: opentelemetry.propagate uses the globally configured propagator (W3C by default).
from opentelemetry import trace
from opentelemetry.propagate import inject, extract
from opentelemetry.trace import SpanKind

tracer = trace.get_tracer("shop.orders")

# producer
with tracer.start_as_current_span("orders publish", kind=SpanKind.PRODUCER):
    headers: dict[str, str] = {}
    inject(headers)                      # adds traceparent (and tracestate, baggage)
    bus.publish(order_placed, headers=headers)

# consumer
ctx = extract(msg.headers)
with tracer.start_as_current_span("orders process", context=ctx, kind=SpanKind.CONSUMER):
    handle(msg)

// Go: context.Context carries the span; propagation.MapCarrier adapts a map.
import (
    "go.opentelemetry.io/otel"
    "go.opentelemetry.io/otel/propagation"
    "go.opentelemetry.io/otel/trace"
)

var tracer = otel.Tracer("shop/orders")

// producer
ctx, span := tracer.Start(ctx, "orders publish", trace.WithSpanKind(trace.SpanKindProducer))
headers := propagation.MapCarrier{}
otel.GetTextMapPropagator().Inject(ctx, headers)
bus.Publish(ctx, orderPlaced, headers)
span.End()

// consumer
ctx = otel.GetTextMapPropagator().Extract(context.Background(), propagation.MapCarrier(msg.Headers))
ctx, span = tracer.Start(ctx, "orders process", trace.WithSpanKind(trace.SpanKindConsumer))
defer span.End()

// Node: @opentelemetry/api propagation with the active context.
import { context, propagation, trace, SpanKind } from "@opentelemetry/api";

const tracer = trace.getTracer("shop.orders");

// producer
await tracer.startActiveSpan("orders publish", { kind: SpanKind.PRODUCER }, async (span) => {
  const headers: Record<string, string> = {};
  propagation.inject(context.active(), headers);
  await bus.publish(orderPlaced, headers);
  span.end();
});

// consumer
const parent = propagation.extract(context.active(), msg.headers);
await context.with(parent, () =>
  tracer.startActiveSpan("orders process", { kind: SpanKind.CONSUMER }, async (span) => {
    try { await handle(msg); } finally { span.end(); }
  }));

To get the trace id into every log line, let the logging library read the current span. Serilog and Microsoft.Extensions.Logging include TraceId/SpanId from Activity.Current; the OpenTelemetry Java agent puts trace_id and span_id into the Logback/Log4j MDC; Python's opentelemetry-instrumentation-logging adds otelTraceID to records; Go's otelslog bridge and pino's @opentelemetry/instrumentation-pino do the same. Then return the trace id to the caller in error responses (traceId in a Problem Details body), so a support ticket starts with the one id that finds everything.

Metrics: four instrument types

A metric is a named number, with labels (also called attributes or dimensions) that split it into time series. http_requests_total{route="/checkout", status="500"} is one series. Each instrument type answers a different kind of question:

Type What it records Question it answers Examples Gotcha
Counter A monotonically increasing total "How many per second?" (you query its rate) requests, errors, bytes sent, retries Never decrements. Resets on restart, which rate() handles.
Gauge A value that goes up and down, sampled now "How much right now?" queue depth, pool in-use, memory, temperature Sampling misses spikes between scrapes.
Histogram Counts of observations per bucket, plus sum and count "What is the distribution? p50/p99? Share under 300 ms?" request duration, payload size, batch size Bucket layout fixes your precision. Each bucket is a series.
Summary Quantiles computed in the client "p99 of this instance" legacy client-side latency Cannot be aggregated across instances. Prefer histograms.

Up-down counters (OpenTelemetry's UpDownCounter, e.g. active requests) and observable/asynchronous instruments (a callback reads the value at collection time, e.g. ObservableGauge for queue length) are variations on these. The rule of thumb: counters for events, histograms for durations and sizes, gauges for current levels.

// System.Diagnostics.Metrics is the .NET API; OpenTelemetry exports it.

Cardinality: the label that costs a fortune

Every unique combination of label values is its own time series, with its own memory in the collector and the store. The count multiplies: 4 methods × 40 routes × 8 status codes × 30 pods is already 38,400 combinations, and a histogram with 12 buckets stores 15 series for each of them. Add one unbounded label and the product explodes. Edit the label list and watch where it goes wrong.

Good labels (bounded, low cardinality)

  • method, route template (/orders/{id}), status_class (2xx, 5xx)
  • region, availability_zone, version, outcome
  • payment.method from a fixed enum, tenant_tier (free / pro / enterprise)

Bad labels (unbounded)

  • user_id, order_id, session_id, trace_id, email
  • The raw URL path (/orders/8812): one series per order
  • Error messages, exception text, SQL text, timestamps
  • tenant_id when you have 50,000 tenants (use tiers, or a separate per-tenant pipeline)

Put the unbounded value on the span or log line instead. A trace attribute user.id=8812 costs a few bytes on one event. As a metric label, it creates a new series that lives for hours. If you need "top 10 tenants by error rate", use a log/trace analytics query or exemplars, not a label. Protect yourself with guard rails too: OpenTelemetry SDK views can drop attributes, and most SDKs cap series per instrument (the .NET and Java SDKs default to 2,000) and send the overflow to an otel.metric.overflow series.

Percentiles, histograms and why averages lie

Latency distributions are skewed: most requests are fast, a few are very slow, and those few are what users complain about. The average hides the tail, so you track percentiles: p50 (the typical user), p95, p99 (the unlucky one in a hundred; on a page that makes 50 calls, most page loads include at least one p99 call).

There is a second trap. Each pod can tell you its p99, but you cannot average percentiles to get the fleet's p99. The correct method is to record a histogram on every pod, add up the bucket counts across pods, and estimate the percentile from the merged buckets. That is exactly what Prometheus histogram_quantile(0.99, sum by (le) (rate(..._bucket[5m]))) does. Run the simulation with two healthy pods and one slow one:

  • The bucket estimate's error is bounded by the width of the bucket the percentile lands in. Coarse buckets around your SLO threshold mean a vague answer to the one question you care about.
  • Put a bucket boundary exactly on each SLO threshold (300 ms above). Then "share of requests ≤ 300 ms" is exact: it is just a bucket count divided by the total.
  • Newer formats remove the guesswork: Prometheus native histograms and OpenTelemetry exponential histograms pick bucket boundaries automatically with a bounded relative error (a few percent) at every scale.

RED and USE: what to measure first

Two checklists cover almost every service. RED describes the work a service does, from the caller's point of view. USE describes each resource the work runs on. When RED says "it hurts", USE tells you which resource is the bottleneck.

RED (per endpoint / operation)

  • Rate: requests per second.
  • Errors: failed requests per second (or the error ratio).
  • Duration: the latency distribution (a histogram, read as p50/p95/p99).

These are your user-facing symptoms and the inputs to SLOs.

USE (per resource: CPU, memory, pool, queue, disk)

  • Utilization: share of time or capacity in use.
  • Saturation: work waiting that cannot be served yet (queue length, waiters).
  • Errors: resource-level failures (timeouts acquiring, OOM, disk errors).

Saturation is the early-warning signal: it rises before latency and errors do.

Ramp traffic past what a database connection pool can serve. Watch the order in which the signals move: utilization pins at 100%, then the waiter count (saturation) grows, then p99 latency climbs, and only at the end do errors appear when callers time out waiting for a connection.

With the defaults, the pool of 10 connections tops out around 250 requests per second. Saturation crosses its threshold about 16 seconds before errors cross 1%, and p99 flattens at the 1-second acquire timeout because the slow requests turn into errors instead. An alert on pool saturation would have bought those 16 seconds; an alert on errors alone fires once users are already failing. Google's SRE book calls the combination of latency, traffic, errors and saturation the four golden signals.

Distributed tracing with OpenTelemetry

A trace is the tree of work done for one request. Each node is a span: a named, timed operation (GET /checkout, SELECT orders, POST pricing/batch) with a start time, a duration, a status, attributes (http.response.status_code=200, db.system=postgresql) and the id of its parent span. The root span has no parent. Spans from different services join into one tree because the traceparent header carries the trace id and the caller's span id across the wire.

Reading a waterfall: the N+1 staircase

The single most common latency bug a trace reveals is a staircase: the same span repeated in sequence, once per item. Switch between sequential N+1 calls, one batched call and a parallel fan-out, and compare the critical path. Parallel fan-out shortens the request but still sends N calls to the dependency; batching shortens it and cuts the load. Batching and round-trip reduction are covered in Performance Patterns and Data Access.

Auto vs manual instrumentation

OpenTelemetry has two layers. Auto-instrumentation hooks well-known libraries (HTTP servers and clients, gRPC, database drivers, message clients) and gives you the skeleton of every trace with no code changes. Manual instrumentation adds the spans and attributes only your code knows about: "price cart", cart.items=12, pricing.batched=false. You want both: auto for coverage, manual for meaning.

Ship to a Collector, not straight to a vendor. Point every SDK at an OpenTelemetry Collector (as a sidecar, a node agent or a gateway). The Collector batches, retries, redacts attributes, does tail sampling, and fans out to whatever back ends you use. Switching vendor becomes a Collector config change, not a redeploy of every service. Configure SDKs through the standard OTEL_* environment variables (OTEL_SERVICE_NAME, OTEL_EXPORTER_OTLP_ENDPOINT, OTEL_TRACES_SAMPLER), which every language SDK reads.

Sampling: head vs tail

Keeping every span of every request is rarely affordable. Head sampling decides at the root, before the request runs, usually by hashing the trace id (TraceIdRatioBased), and the decision travels in the sampled flag so every service agrees. It is cheap, but it is blind: it keeps 10% of your errors, not all of them. Tail sampling waits until the trace is complete, then keeps it if it was slow, failed, or matches a rule. Run both on the same traffic:

  • Use ParentBased(TraceIdRatioBased(r)) in SDKs, so a service never breaks a trace its caller decided to keep.
  • Tail sampling lives in the Collector (tail_sampling processor) and needs a load-balancing exporter in front so all spans of a trace reach the same Collector instance.
  • Sampling changes the meaning of counts. Derive RED metrics from unsampled data (the SDK metrics, or a span-metrics connector placed before the sampler), never by counting sampled spans.

SLIs, SLOs and error budgets

An SLI (service level indicator) is a ratio of good events to valid events, measured where users feel it: "requests to POST /checkout that succeed in under 400 ms, divided by all requests". An SLO is the target for that SLI over a window: "99.9% over 30 days". The error budget is what is left: 0.1% of requests may fail, which is about 43 minutes of full outage a month. The budget turns reliability into a number both product and engineering can spend: when it is healthy, ship faster; when it is gone, pause risky releases and fix reliability.

Burn-rate alerts: alert on symptoms, at the right speed

A burn rate of 1 spends the whole budget in exactly the SLO window; a burn rate of 14.4 spends 2% of a 30-day budget in one hour. The Google SRE workbook's multiwindow, multi-burn-rate alerts page when the burn is fast and still happening (a long window to be sure, a short window to stop paging once it recovers), and open a ticket for slow leaks:

Severity Long window Short window Burn rate Budget spent when it fires
Page 1 hour 5 minutes 14.4 2%
Page 6 hours 30 minutes 6 5%
Ticket 3 days 6 hours 1 10%

Pick a scenario: a slow leak (from day 12 the error rate doubles to 0.2%, a burn rate of 2; nothing looks alarming, yet the budget is gone by day 25), a 45-minute outage at 10% errors, a 5-minute blip and a healthy month. Compare the multiwindow alerts with the naive "error ratio over the last 5 minutes is above the budget" alert.

Alert on symptoms (page a human)

  • SLO burn rate on availability and latency SLIs.
  • "No successful checkouts in 10 minutes" for low-traffic critical paths.
  • Synthetic probes failing from outside the network.
  • Every page must be urgent, actionable and user-visible, with a runbook link.

Do not page on causes

  • CPU > 80%, memory > 70%, one pod restarted, a disk at 75%.
  • A single error log line, or one failed health probe.
  • These go on dashboards, or become tickets when they predict trouble (disk full in 4 days).
  • If nobody acts on an alert, delete it or downgrade it: alert fatigue is how real pages get missed.

Health checks: liveness, readiness and startup

An orchestrator (Kubernetes, Azure Container Apps, ECS, a load balancer) asks your process three different questions. Mixing them up is one of the most common ways to turn a small outage into a big one.

Probe Question On failure Should check Must NOT check
Startup "Have you finished booting?" Keep waiting; kill only after the whole budget (failureThreshold × periodSeconds) That the app finished init (migrations, cache warm-up, JIT) Anything slow that is not part of boot
Liveness "Are you stuck beyond self-repair?" Restart the container That the process can serve: the event loop or thread pool responds, no deadlock Dependencies. A DB outage is not fixed by restarting you.
Readiness "Should I send you traffic right now?" Remove from the load balancer; keep running Warm caches, critical dependencies reachable, not shutting down, not overloaded Optional dependencies (degrade instead)

Watch three pods boot slowly and then lose their database for 30 seconds. Then try the two classic mistakes: a liveness probe that checks the database (every pod restarts, and they all reconnect at once when the DB returns) and no startup probe (liveness kills the pod before it ever finishes booting).

from fastapi import FastAPI, Response

app = FastAPI()
state = {"warm": False, "draining": False}

@app.get("/healthz/live")
async def live() -> dict:
    return {"status": "ok"}                       # if the loop is blocked, this times out

@app.get("/healthz/startup")
async def startup(resp: Response) -> dict:
    if not state["warm"]:
        resp.status_code = 503
    return {"warm": state["warm"]}

@app.get("/healthz/ready")
async def ready(resp: Response) -> dict:
    db_ok = await db.ping(timeout=0.5)            # short timeout: probes must be fast
    ok = state["warm"] and db_ok and not state["draining"]
    resp.status_code = 200 if ok else 503
    return {"warm": state["warm"], "db": db_ok, "draining": state["draining"]}

var ready atomic.Bool

func main() {
    mux := http.NewServeMux()
    mux.HandleFunc("GET /healthz/live", func(w http.ResponseWriter, _ *http.Request) {
        w.WriteHeader(http.StatusOK)
    })
    mux.HandleFunc("GET /healthz/ready", func(w http.ResponseWriter, r *http.Request) {
        ctx, cancel := context.WithTimeout(r.Context(), 500*time.Millisecond)
        defer cancel()
        if !ready.Load() || db.PingContext(ctx) != nil {
            http.Error(w, "not ready", http.StatusServiceUnavailable)
            return
        }
        w.WriteHeader(http.StatusOK)
    })
    go func() { warmCaches(); ready.Store(true) }()
    // on SIGTERM: ready.Store(false), wait a few seconds for endpoints to update, then Shutdown(ctx)
    http.ListenAndServe(":8080", mux)
}

Readiness that checks a shared dependency can still take everything down. If every pod's readiness pings the database and the database blips, all pods go unready at once and the load balancer has nowhere to send traffic, so users get connection errors instead of a friendly degraded response. Some teams therefore keep readiness local (warm-up, draining, overload) and handle dependency failures in the request path with timeouts, circuit breakers and fallbacks. Either way, never put dependencies in liveness, and set readiness failureThreshold above 1 if your dependency blips often.

Putting it together: investigating a slow checkout

Here is the 3 a.m. page from the top of this page, done properly. A canary of v42 is serving part of the traffic. Step through how each signal hands off to the next: the SLO alert detects, RED metrics narrow it, a version label splits it, an exemplar jumps from a histogram bucket to one slow trace, the trace localizes, the logs explain, and the same SLI confirms the fix. Change the canary share and see how it changes the size of the signal.

2 · SCOPERED by route

3 · SPLITBounded labels

version, region, route. Only v42 is slow.

4 · JUMPExemplar → trace

When to use what, and when not to

Do this from day one

  • Structured JSON logs to stdout, with a trace id on every line.
  • OpenTelemetry SDK with auto-instrumentation, exporting to a Collector.
  • RED metrics per route as histograms, with an SLO bucket boundary.
  • Liveness, readiness and startup endpoints that answer different questions.
  • One SLO for the most important user journey, with burn-rate alerts.

Do not do this

  • Log every request and response body "in case we need it".
  • Add a metric label for anything with an id in its name.
  • Build a dashboard for every metric you have; build them for questions you ask.
  • Page on resource thresholds; use them for diagnosis.
  • Write your own tracing headers: use W3C Trace Context.
Situation Reach for Not
"Is the service healthy right now?" RED metrics + SLO burn Grepping logs
"Why did this order fail?" Logs and the trace for that order's trace id A metric with an order_id label
"Which hop is slow?" Trace waterfall, then span metrics Timestamps in logs from five services
"Which code is using CPU?" Continuous profiler / flame graph (Performance Cadence) More spans around every function
"Is it getting worse over weeks?" Metrics with long retention Traces (too expensive to keep)

A library you publish ILogger/SLF4J/logging/slog interfaces, ActivitySource/OTel API only Configuring sinks or exporters inside the library

What it costs. Observability spend commonly lands at 5–15% of infrastructure cost, and it is dominated by log volume and metric cardinality. Spans, metrics and logs also cost CPU in your process: a span is roughly a microsecond and a few hundred bytes; a disabled log call with a template is nanoseconds; an enabled JSON log line with ten fields is a few microseconds. That is cheap per request and expensive in a tight loop. Instrument operations, not iterations.

Pitfalls and war stories

The label that cost more than the service A team added customer_id as a label on the request duration histogram to answer one sales question. With 40,000 customers × 12 buckets × 20 routes the metrics back end ran out of memory, ingestion dropped all metrics for that tenant, and the alerting went blind for an afternoon. Fix: remove the label, put customer.id on spans, answer per-customer questions with trace or log analytics, and configure a cardinality limit on the SDK view.

The health check that restarted the fleet A liveness endpoint called the database "to be thorough". During a 40-second failover, every pod failed liveness three times and was restarted. They all came back at once, opened their full connection pools against the freshly promoted primary, and knocked it over again. A 40-second blip became a 25-minute outage. Fix: liveness checks only the process; dependency checks belong in readiness (or in the request path with a circuit breaker).

The trace that stopped at the queue Traces showed POST /orders finishing in 30 ms, while customers waited minutes for confirmation emails. The work happened after a message queue, whose consumer started a fresh trace for every message. Nobody could connect a slow email to its order. Fix: inject traceparent into message headers on publish and extract it on consume (or add span links for batches), then put queue age (time from publish to consume) on a dashboard.

The access token in the request log A debug middleware logged all request headers. It was turned on in production for an investigation and left on. Six months later a vendor with log access was breached, and every Authorization: Bearer token from that period was in the dump. Fix: allow-list the headers you log, redact by type at the logger, run secret scanning on log storage, and make debug-level overrides expire automatically.

Averaging percentiles on the dashboard Each of 20 pods exported a summary with its own p99, and the dashboard showed avg(p99). One pod on a degraded node had a p99 of 4 s, but the average stayed under the 500 ms threshold, and the alert never fired for two days. Fix: export histograms, sum the buckets across pods, compute the quantile once; also alert per pod or per zone for outliers.

Sampled-away errors Head sampling at 1% kept costs down, but when a rare payment error hit 0.05% of requests, there were almost no traces of it to look at. Fix: tail-sample in the Collector with policies that keep all errors and slow traces, and use flush-on-error buffering for logs.

Checklist

  • [ ] Logs are structured (JSON), use message templates with named fields, and carry trace_id, span_id, service and version.
  • [ ] Log levels follow a written convention; errors are logged once, where they are handled; levels are configurable per namespace at runtime.
  • [ ] Sensitive data is redacted at the logger by type or path; request bodies and auth headers are never logged.
  • [ ] W3C traceparent propagates over HTTP, gRPC and messages; trace ids are returned in error responses.
  • [ ] RED metrics per route are histograms with a bucket boundary on each SLO threshold; no unbounded labels; SDK cardinality limits are set.
  • [ ] USE metrics exist for every pool, queue and resource that can saturate.
  • [ ] OpenTelemetry auto-instrumentation is on, manual spans add business attributes, and everything exports to a Collector.
  • [ ] Sampling is parent-based, errors and slow traces are kept (tail sampling), and RED metrics are computed before sampling.
  • [ ] At least one SLO on a critical user journey, with multiwindow burn-rate alerts that link to runbooks.
  • [ ] Pages are symptom-based only; resource thresholds go to dashboards or tickets.
  • [ ] Separate liveness, readiness and startup probes; liveness checks no dependencies.
  • [ ] Exemplars link histograms to traces; dashboards let you go from alert → trace → logs in three clicks.

Quiz

Why is log.LogInformation($"Order {id} took {ms} ms") worse than log.LogInformation("Order {OrderId} took {ElapsedMs} ms", id, ms), even if the output text is identical?

The interpolated string is built before the call, even when the level is disabled (wasted CPU and allocations). Every message is unique, so you cannot group events by template. And id and ms become text in a sentence instead of typed fields you can filter (ElapsedMs > 500) and aggregate. The template version keeps the template constant and the values structured.

A metric has labels method (4 values), route (50), status (6) and region (3). It is a histogram with 10 buckets. Roughly how many series is that, and what happens if you add user_id?

4 × 50 × 6 × 3 = 3,600 label combinations. A 10-bucket histogram stores 10 buckets + +Inf + _sum + _count = 13 series each, so about 46,800 series at most. Adding user_id multiplies that by the number of active users: with 100,000 users, billions of potential series. Put the user id on spans or logs instead.

Three pods report p99 latencies of 120 ms, 130 ms and 900 ms with equal traffic. Is the fleet p99 about 383 ms?

Not necessarily, and you cannot tell from these numbers. The fleet p99 is the latency exceeded by 1% of all requests. The fast pods contribute almost nothing above 130 ms, so that 1% must come almost entirely from the slow pod, which holds a third of the traffic: the fleet p99 is roughly the slow pod's p97. That could be anywhere between about 130 ms and 900 ms depending on the shape of its distribution. Averaging percentiles has no statistical meaning; merge the histogram buckets and compute the quantile once.

Your SLO is 99.9% over 30 days. An incident causes a 1-hour burn rate of 14.4. What fraction of the monthly budget does that hour spend, and why is that the classic paging threshold?

Burn rate 14.4 for 1 hour spends 14.4 / 720 hours = 2% of the budget. At that speed the whole budget is gone in about 2 days, which is urgent enough to wake someone, while the 1-hour window filters out blips. A 5-minute short window makes the alert stop as soon as the burn ends.

Your liveness probe checks the database. What happens during a 60-second database failover?

Every pod fails liveness, so the orchestrator restarts all of them. Restarting cannot fix the database; it only adds boot time, drops in-flight requests and causes a thundering herd of reconnections when the database returns. Liveness should check only the process itself; put the database in readiness or handle it with resilience patterns.

Head sampling at 5% is cheap. When is it the wrong choice, and what do you use instead?

When the traces you care about are rare (errors, slow requests, one customer's failure): head sampling decides before the outcome is known, so it keeps only 5% of them. Use tail sampling in the Collector to keep all errors and slow traces plus a percentage of the rest, or combine generous head sampling with tail policies.

An order message is published to a queue by service A and consumed by service B. B's spans show up as separate traces. What is missing?

Context propagation through the message. A must inject traceparent (and tracestate/baggage) into the message headers when publishing, and B must extract it and start its consumer span with that parent (or link to it, for batch consumers). HTTP clients are auto-instrumented; many message clients are not.
