Testing Strategy

The test pyramid and trophy, unit vs integration vs contract tests, mocks vs fakes vs stubs, TDD in practice, and property-based tests.

Beginner → Advanced~60 min studyBuilds on: DI FundamentalsUpdated 2026-11-03

The problem: a green build that proves nothing

A team has 1,400 tests and 92% line coverage. On Friday they ship a refactor that renames one JSON field, and the mobile app breaks for every user. On Monday a developer spends a day getting a two-line change through CI, because 38 tests mock the class she touched and each one asserts the exact order of its method calls. On Tuesday the nightly end-to-end suite is red again. Nobody looks; it's red three nights out of five.

Every part of that story is a testing strategy problem, not a lack of tests:

  • The JSON rename passed because no test sat between the two systems. Unit tests on each side were green.
  • The refactor was painful because the tests checked how the code worked (which methods it called), not what it did.
  • The nightly suite was ignored because it was flaky, and a flaky test teaches people that red means nothing.
  • 92% coverage hid all of this, because coverage measures which lines ran, not which behaviours are checked.

A test suite is worth exactly as much as the decisions it lets you make safely. Good tests fail when behaviour breaks, stay green when you refactor, run fast enough that you run them constantly, and give the same answer every time. Optimise the mix of tests for those four properties, not for the count or the coverage number.

This page assumes you're comfortable with dependency injection: almost every testing technique here is "inject something different at a seam". For the design side of testability, see design principles; for testing error paths and retries, see error handling and resilience.

The mental model: four properties, one budget

Every test trades between the same four properties. No single kind of test maximises all of them, which is why you need a mix:

Fast

Milliseconds, so you can run thousands on every save. Slow suites get run less often, so bugs are found later, when they cost more to fix.

Deterministic

Same code, same result. A test that fails 2% of the time is worse than no test: it trains people to ignore red.

Sensitive to behaviour

Fails when the outcome is wrong. Mutation testing measures this directly.

Insensitive to structure

Stays green when you refactor without changing behaviour. Over-mocked tests fail this one.

The more real the code under test (real database, real HTTP pipeline, real browser), the more bug classes you can catch and the more confident you are, but also the slower and flakier the test is. The shape of your suite is how you spend that budget.

Suite shapes: pyramid, trophy, honeycomb

Three shapes dominate the conversation. They disagree less than it seems: they're tuned to different kinds of systems.

  • Pyramid. Most of your tests are fast unit tests, fewer are integration tests, and a handful are end-to-end. It's the right shape when most of the risk is in logic: pricing engines, parsers, schedulers, algorithms.
  • Trophy. Static analysis (a type checker, linters) is the base; integration tests are the biggest layer. It's the right shape when most of the risk is in wiring: a typical web app or API, where a controller calls a service that calls a database and each unit is small.
  • Honeycomb. Spotify's shape for microservices. Each service is tested mostly through its own API with its real dependencies (database, queue), with few implementation-detail unit tests.
  • Ice-cream cone. The anti-pattern: mostly manual or end-to-end tests and very few unit tests. It's slow and flaky, and when it fails it can't tell you where the bug is.

The visualizer gives each layer a realistic cost (runtime and flake rate per test) and gives each bug class a probability of being exercised by one test at that layer. It then computes the probability that the suite catches each class: 1 − ∏(1 − q)n. Try the ice-cream cone, then turn static analysis off on a custom suite.

The numbers are a model, not a measurement, but the conclusions are robust:

  • Static analysis is the cheapest test you will ever write. tsc --strict, nullable reference types in C#, mypy/pyright, go vet and SpotBugs catch whole bug classes in seconds and are never flaky. Turn them on before you write the first test.
  • No amount of unit testing catches wiring bugs. A missing DI registration, middleware in the wrong order or a wrong column mapping only shows up when the real pieces run together.
  • End-to-end tests are the only layer that sees the UI wiring, but 200 of them make CI slow and almost always red. Keep a handful, on the journeys that make money.
  • Races slip through every shape. Concurrency bugs need dedicated tools: stress tests, go test -race, deterministic schedulers. See concurrency and async.

What each level catches, and what it costs

The names are used loosely, so here is the definition this page uses. The dividing line is what is real in the test.

Level What's real What's replaced Typical speed Catches Misses
Static analysis Source code only Nothing runs Seconds for the whole repo Type errors, nulls, unused code, common bug patterns, some security issues Anything about runtime values
Unit One class or function, plus pure collaborators I/O: DB, HTTP, clock, file system 1–10 ms Logic, edge cases, error paths Wiring, SQL, serialization, config
Integration Your service in-process: DI, middleware, ORM, a real database Other services, payment providers, email 50–500 ms Mapping, queries, transactions, DI wiring, HTTP pipeline, validation Other teams' changes, browser behaviour
Contract The request/response shape between two services Everything else 10–100 ms A provider breaking a consumer's expectations Business logic on either side
End-to-end Everything, deployed: browser, all services, real infra Usually only third parties 5–60 s Journeys broken by any layer, environment config Where the bug is; edge cases (too slow to enumerate)

"Unit" means a unit of behaviour, not a class Kent Beck and the classicist school define a unit test as one that runs fast and in isolation from other tests, not as one that isolates a single class from every collaborator. A test that exercises PriceCalculator together with its real DiscountPolicy and TaxTable is still a unit test: it's fast, deterministic and touches no I/O. Isolating every class with mocks is a choice, and usually a costly one (see the next section).

Test doubles: dummy, stub, spy, mock, fake

A test double is anything that stands in for a real collaborator in a test (the name comes from stunt doubles). Gerard Meszaros's xUnit Test Patterns names five kinds. People say "mock" for all of them, but they do very different jobs:

The rule of thumb that falls out of this:

  • Stub queries, verify commands. If a collaborator answers a question (GetPrice, Now, FindUser), stub it or use a fake, and never assert that it was called: if the code got the right answer without asking, good for it. If a collaborator causes a side effect the outside world cares about (charging a card, sending an email, publishing an event), check that it happened, through a fake's state or a spy.
  • Prefer fakes for things you own. An InMemoryOrderRepository takes twenty minutes to write, can be reused by hundreds of tests, and keeps working when the code switches from Save to SaveAll.
  • Don't mock what you don't own. Mocking HttpClient, DbContext or the AWS SDK encodes your guess of how a third-party library behaves. Wrap it in a thin adapter you own (IPaymentGateway), fake the adapter in unit tests, and test the real adapter against the real thing (or a container) in a few integration tests.

One test, three styles, four versions of the code

CheckoutService.PlaceOrder prices an order, saves it, charges the card and logs. Classicist vs mockist: a real disagreement

Martin Fowler's essay Mocks Aren't Stubs names the two schools. Both produce good software; they optimise for different things.

Classicist (Detroit / Chicago)

Use real objects wherever they're fast and deterministic; double only I/O and slow or non-deterministic things. Assert on state and outcomes. Tests survive refactoring, and one bug may fail several tests (which tells you its blast radius). Fakes take some up-front work.

Mockist (London)

Double every collaborator; assert on interactions. It drives design outside-in (Growing Object-Oriented Software, Guided by Tests): you discover the roles a class needs by mocking them before they exist. A failure points at exactly one class, but tests are coupled to the call structure.

A pragmatic blend that works for most teams: classicist by default, mocks at architectural boundaries where the interaction is the behaviour (publishing an event, sending a command to another service), and one strict mock where you must prove that something did not happen (no charge on a declined order).

Over-mocking: the smell to watch for Signs: the test has more Setup/when lines than assertions; the test re-states the implementation line by line; mocks return mocks (mock.Setup(x => x.GetRepo().GetUser())); a one-line refactor turns 30 tests red; or the test still passes when you delete the body of the method under test because every return value is mocked. The fix is usually a fake for the I/O and real objects for everything else. If a class needs six mocks to test, that's also a design signal: it has too many collaborators.

Anatomy of a good test

Arrange, act, assert

Every test has the same three parts. Keeping them visually separate (a blank line between each is enough) makes a test readable in five seconds:

  • Arrange: build the inputs and the object under test. It's often the longest part, so it's where builders help most.
  • Act: exactly one call to the behaviour being tested. Two "act" lines means two tests.
  • Assert: check the outcome. Several assertions are fine if they describe one behaviour ("the order is stored and the total is 90"); if you need the word "and also" to describe the test, split it.

BDD tools spell the same idea as Given / When / Then.

Names that read like a specification

When a test fails in CI, its name is often all you see. A good name says the scenario and the expected behaviour, in domain language, so the failure explains itself without opening the file.

Says nothing

Test1, TestPlaceOrder, PlaceOrderWorks, test_calculate_2, ShouldReturnTrue

Says what broke

Placing_an_order_with_an_expired_coupon_charges_the_full_price, test_rejects_transfer_when_balance_is_insufficient, TestParse/empty_input_returns_ErrEmpty, it("keeps the cart when payment is declined")

Patterns like Method_Scenario_Expected or should … sentences are both fine. Pick one per codebase. Avoid putting the method name first if a rename would make every test name stale.

Test data builders and object mothers

The biggest source of test noise is setting up valid objects. An Order might need a customer, an address, three items and a currency before its constructor stops throwing, and only one of those fields matters to the test.

  • An object mother is a class of factory methods for typical objects: Orders.Paid(), Customers.Gold(). It's simple, but it grows a method for every variation (PaidWithCouponShippedToGermany).
  • A test data builder starts from a valid default and lets each test override only what it cares about. The test then shows the one thing that matters.

Tip: make the irrelevant invisible and the relevant obvious If a value appears in the arrange section, a reader assumes it matters. Hide defaults in the builder, and name literal values that are the point of the test (var expiredCoupon = …). A test you can't read is a test nobody will fix correctly when it fails.

Rules that keep tests cheap

  • One behaviour per test. When it fails, you know what broke without debugging.
  • No logic in tests. No if, loops or calculations that mirror the production code. If the test computes the expected value the same way the code does, it will share the code's bugs. Write the expected value as a literal.
  • Tests don't depend on each other. Each test sets up its own world. Run order must not matter (the flaky-test visualizer below shows why).
  • Test through the public API. Testing private methods couples the test to the structure. If a private method is so complex it needs its own tests, it probably wants to be its own class.
  • A test that has never failed hasn't been tested. Break the code on purpose once and watch the test go red.

Testing through dependency injection

The payoff of constructor injection is in tests: the composition root decides what's real, so a test can boot the real application (routing, middleware, validation, serialization, DI wiring) and replace only the things that cross a process boundary: the clock, the payment provider, the email server and the database connection.

Every major framework has a hook for this, and they share one rule: the last registration wins. The test's overrides run after the app's own registrations, so they replace them. Pick a framework and an override set, and watch what each call resolves to during POST /orders.

The "forgot the email sender" case is the dangerous one: the test passes and a real customer gets an email. Two defences:

  • Make production adapters refuse to start without their configuration (no default SMTP host, no fallback API key), so a forgotten override fails loudly. Go's explicit wiring does this naturally: an unset interface field is nil and panics. See configuration and secrets.
  • Add one test that boots the test host and asserts that none of the resolved services are production adapters for external systems.

Real databases with Testcontainers

The classic shortcut for testing data access is an in-memory database: EF Core's InMemory provider, H2 in place of Postgres, SQLite in place of SQL Server. It's fast, and it lies:

  • EF Core InMemory isn't relational at all: no SQL, no transactions, no foreign keys, no unique constraints. Microsoft's own docs advise against it for testing.
  • H2 and SQLite accept SQL that Postgres rejects and reject SQL Postgres accepts. Case sensitivity, date arithmetic, ON CONFLICT, JSON operators, collations and isolation levels all differ.
  • The bugs you most need to catch (a migration that fails, a missing index, a unique-constraint race, a query that only works in one dialect) are exactly the ones a fake database can't show you.

Testcontainers starts a real database (or Kafka, Redis, RabbitMQ, LocalStack…) in a throwaway Docker container for the test run and gives you its connection string. Start one container per test class or per suite (not per test), and isolate tests with a transaction that rolls back, a fresh schema, or a reset tool such as Respawn.

// Testcontainers.PostgreSql + xUnit: one container for the whole test class.
public sealed class OrderRepositoryTests : IAsyncLifetime
{
    private readonly PostgreSqlContainer _pg = new PostgreSqlBuilder().WithImage("postgres:16-alpine").Build();

    public async Task InitializeAsync()
    {
        await _pg.StartAsync();
        await using var db = NewDb();
        await db.Database.MigrateAsync();               // run the REAL migrations
    }
    public Task DisposeAsync() => _pg.DisposeAsync().AsTask();
    private ShopDb NewDb() => new(new DbContextOptionsBuilder<ShopDb>().UseNpgsql(_pg.GetConnectionString()).Options);

    [Fact]
    public async Task Duplicate_order_numbers_are_rejected_by_the_unique_index()
    {
        await using var db = NewDb();
        db.Orders.AddRange(new Order("A-1"), new Order("A-1"));
        await Assert.ThrowsAsync<DbUpdateException>(() => db.SaveChangesAsync());
    }
}

Contract tests: catching the JSON rename

Integration tests prove your service works with its dependencies. They can't prove that another team's change won't break you, or that your change won't break them. End-to-end tests across services can, but they need every service deployed together, which is slow and flaky.

Consumer-driven contract testing (Pact is the common tool, with libraries for .NET, JVM, Python, Go and JS) splits that end-to-end check into two fast, independent halves:

  1. Consumer side. The consumer's test runs against a Pact mock server and declares exactly what it needs: "for GET /orders/42, I read id as an integer, total as a number and status as a string". The test produces a pact file.
  2. Provider side. The provider's CI downloads every consumer's pact from a broker and replays each request against the real provider, checking each response against the expectations.
  3. can-i-deploy. Before any deploy, the broker answers: "has this exact version been verified against the versions of its consumers currently in production?"

Notice what contracts make possible: removing legacyCode passes, because the broker knows no consumer reads it. Without contracts, the safe choice is to keep every field forever.

Use contract tests when

  • Two or more teams deploy services independently, and they talk over HTTP or messages.
  • You have been burnt by "they changed the API and didn't tell us".
  • Your end-to-end environment is the bottleneck for releases.

For a single team with a public API and unknown consumers, a published OpenAPI schema plus schema-diff checks in CI (for example oasdiff breaking) is usually the better tool. Versioning and compatibility rules are covered in API design.

End-to-end tests: few, stable, on the money paths

End-to-end tests drive the deployed system like a user: a browser (Playwright, Cypress, Selenium) or an API client against a real environment. They're the only tests that catch "the button posts to the wrong URL", and the most expensive ones you own. Keep them few (tens, not hundreds), on the journeys that make money (sign up, search, check out), and make them stable:

  • Select elements by role and accessible name (getByRole("button", { name: "Place order" })), not CSS classes or XPath that break when the design changes.
  • Wait for conditions, never for time. Playwright's locators auto-wait and its expect retries; a sleep(2000) is a flake waiting to happen.
  • Each test creates its own data (a fresh user and cart via the API), so tests can run in parallel and in any order.
  • Record a trace on failure (Playwright's trace viewer shows DOM, network and console for each step), so a red run can be diagnosed without rerunning it.
// Playwright: role-based locators, auto-waiting assertions, data created per test.
test("a signed-in user can check out with a saved card", async ({ page, request }) => {
  const user = await createUserWithSavedCard(request);          // API call, not UI clicks
  await page.goto(`/login?as=${user.token}`);
  await page.getByRole("link", { name: "Coffee grinder" }).click();
  await page.getByRole("button", { name: "Add to cart" }).click();
  await page.getByRole("link", { name: "Checkout" }).click();
  await page.getByRole("button", { name: "Place order" }).click();
  await expect(page.getByRole("heading", { name: /thank you/i })).toBeVisible();
});

TDD: red, green, refactor

Test-driven development flips the order: write a failing test, write the least code that makes it pass, then clean up while the tests stay green. Each loop takes minutes. The point isn't the tests you end up with (though you get them for free). It's that every line of production code exists because a test demanded it, and that you design the API from the caller's side before writing it.

1 · REDWrite one failing test

The smallest next behaviour. Run it and watch it fail for the right reason: that proves the test can fail.

2 · GREENMake it pass, simply

Hard-code if you must. Correctness first, elegance later. Don't add behaviour no test asks for.

3 · REFACTORClean up on green

Remove duplication, name things, extract. Tests stay green the whole time. Never refactor on red.

The visualizer runs a real TDD session on toRoman(n). Each implementation is real JavaScript, executed against the tests collected so far. Watch the if ladder grow until the duplication forces a table, and watch the edge-case test for 0 expose a quiet bug in otherwise "finished" code.

Where TDD shines, and where it doesn't TDD is strongest where the behaviour is clear and the design is not: parsers, pricing rules, state machines, bug fixes (write the test that reproduces the bug first, and the regression test is free). It's weakest for exploratory work where you don't yet know what you want (spike first, throw the spike away, then TDD the real thing) and for UI layout. You don't have to TDD everything to get the benefit: "test-first for logic and bugs" is a sustainable habit.

Property-based testing: let the computer find the edge cases

Example-based tests check the cases you thought of. Property-based tests state a rule that must hold for every input, then generate hundreds of inputs to try to break it. When one fails, the framework shrinks it to the smallest input that still fails, so you get [2, 10] instead of a 14-element array of random numbers.

The visualizer has a real generator and a real shrinker. Each property hides a bug that typical example tests miss. Step through the shrinking and watch the counterexample get smaller one accepted step at a time.

Round trip decode(encode(x)) == x serialize/parse, compress, encrypt/decrypt, DTO mapping

Oracle fast code agrees with a slow, obviously-correct version optimised search vs linear scan; new pricing engine vs the old one
Idempotence f(f(x)) == f(x) normalising, formatting, deduplicating, PUT handlers
Metamorphic a known change to the input has a known effect on the output adding a filter never returns more results; doubling every price doubles the total

Snapshot and approval tests

A snapshot test (also called an approval or golden-master test) serialises the output, saves it as a file the first time, and fails whenever the output differs from the saved file. You review the diff and either fix the code or approve the new snapshot. Tools: Verify (.NET), ApprovalTests (.NET and Java), syrupy (pytest), golden files in Go (a -update flag that rewrites testdata/*.golden), and toMatchSnapshot / toMatchInlineSnapshot in Jest and Vitest.

Great for

  • Characterization tests before refactoring legacy code: pin today's behaviour, bugs included.
  • Large structured outputs where writing assertions is tedious: rendered emails, generated SQL, API responses, compiler output.
  • Reviewing changes: the diff in the PR shows exactly what changed in the output.

Dangerous when

  • Snapshots are huge and nobody reads the diff, so --update becomes a reflex.
  • They contain timestamps, GUIDs or ordering noise (scrub them: Verify and syrupy have scrubbers and matchers).
  • They replace focused assertions on the one value the test is really about.

Coverage vs mutation: who tests the tests?

Line coverage answers "which lines ran during the tests?" That's useful in one direction: uncovered code is definitely untested. But covered code isn't necessarily tested. A test that calls a function and asserts nothing gives 100% coverage.

Mutation testing answers the real question: "if this code were wrong, would a test fail?" The tool makes small changes (mutants): flip < to <=, && to ||, replace a return value, delete a statement. It runs the suite against each one. A mutant that makes a test fail is killed; one where every test still passes survived, and points at a missing test.

The visualizer runs eight real mutants of a shipping-fee function against three suites. Two of them have 100% line coverage.

Language Mutation tool Run it

How to use the numbers. Mutation testing is slow (it runs the suite once per mutant), so run it on the changed files in a PR, or nightly on core modules. Don't make 100% mutation score a target either: some mutants are equivalent (they don't change behaviour, like i < n vs i != n in a simple loop), and chasing them wastes time. Use survivors as a list of tests to consider. As a gate, coverage works best as a floor on new code (say 80% of changed lines), not a target for the whole repo.

Why 100% coverage still lies Coverage can't see missing assertions, missing boundary values (the code ran with 80, never with exactly 50), missing branches you never wrote (there is no line for the null check you forgot), combinations of conditions (a && b ran, but never with a true and b false), or concurrency. Once coverage becomes a target, people write tests to execute lines instead of to check behaviour, which is Goodhart's law in action.

Flaky tests: causes and cures

A flaky test passes and fails on the same code. Google has reported that about 1.5% of its test runs show flakiness and that around 16% of its tests have flaked at some point. Even a small rate destroys trust: with 20 tests that each flake 1% of the time, about one run in five is red for no reason.

The visualizer runs a six-test suite twenty times with a shuffled order each run, a random "today" and a random CI load. Three tests hide the classic causes. Fix them one at a time and watch the red runs disappear.

Cause Symptom Cure
Shared mutable state (statics, singletons, a shared DB row, env vars) Passes alone, fails in the full run or in a different order A fresh instance per test, no statics, a transaction or schema per test. Run tests in random order in CI to surface it early.
Wall-clock time (DateTime.Now, LocalDate.now(), time.Now(), new Date()) Fails at month-end, at midnight, on 29 February, in another time zone or around DST Inject a clock: TimeProvider / FakeTimeProvider, java.time.Clock.fixed, a now callable or freezegun/time-machine, a func() time.Time, fake timers.
Sleeping instead of waiting Fails on a loaded CI agent Await the actual signal (a task, a channel, an event), or poll with a timeout: Awaitility, require.Eventually, vi.waitFor, expect.poll.
Concurrency and ordering Fails once in a few hundred runs; asserts on unordered results Assert on sets, not lists; deterministic schedulers (Go testing/synctest); run with -race.
Real network and third parties Fails when a sandbox API is slow or down Fakes or containers in the test; contract tests for the boundary.
Randomness Fails for some seeds Inject the random source and fix the seed; log the seed on failure.
Resource leaks and ports "Address already in use"; fails after another test Port 0 (let the OS choose), using/defer/fixtures that always clean up.

When to use what

Do

  • Turn on the strictest static checks you can (nullable, strict, mypy, vet, analyzers) before writing tests.
  • Write unit tests for logic with many cases: pricing, validation, parsing, state machines.
  • Write integration tests through the real HTTP pipeline with a real database for every endpoint's happy path and main error paths.
  • Use contract tests between independently deployed services.
  • Keep a handful of end-to-end tests on revenue-critical journeys.
  • Add property tests to anything with a round trip or an invariant.
  • Run mutation testing on critical modules to find weak spots.

Don't

  • Mock types you don't own, or mock everything by default.
  • Test private methods, getters, setters, framework code or the DI container itself.
  • Use an in-memory database to test SQL.
  • Chase a coverage number, or let snapshot updates become a reflex.
  • Sleep in tests, read the wall clock, or share state between tests.
  • Write 200 end-to-end tests and run them nightly where nobody looks.
  • Keep a test that has failed intermittently for a month "because it sometimes catches things".

Pitfalls

The mock that tested itself. A test stubbed repo.Find(id) to return a customer, called service.GetCustomer(id), and asserted the returned customer equalled the stub's. The service's mapping code was later deleted by mistake, and the test kept passing because the stub returned exactly what was asserted. Fix: assert on behaviour the code under test adds (mapping, rules, side effects), and use a fake repo seeded with data.

SQLite in tests, Postgres in production. All repository tests were green; the first deploy failed because a migration used ALTER TABLE … ADD CONSTRAINT, which SQLite doesn't support in the same way, and a case-insensitive LIKE behaved differently. Fix: Testcontainers with the same engine and version as production.

Month-end failures. A billing test asserted that today + 30 days falls in next month. It failed on 1 January, 30–31 January, 31 March, 1 May… and was "fixed" by a retry. Fix: inject a clock, then write explicit tests for 31 January, 28 February and leap years.

Integration test isolation by deletion order. Tests cleaned up by deleting rows in teardown; one failing test left data behind, and the next 40 failed with confusing errors. Fix: a transaction per test that always rolls back, or reset the database before each test (Respawn, TRUNCATE … CASCADE), never after.

Assertion roulette. One test with 25 unrelated assertions fails on the first and hides the other 24. Fix: one behaviour per test; if you need several checks, use soft/grouped assertions (Assert.Multiple, AssertJ SoftAssertions, assertAll).

Checklist

  • Static analysis is strict and runs before tests in CI.
  • Tests are named for the behaviour and scenario; each has a clear arrange, act and assert.
  • Builders or factories hide irrelevant setup; literals that matter are visible.
  • Doubles replace I/O and non-determinism only; types you don't own are wrapped by adapters you do.
  • Integration tests boot the real app with overrides only at process boundaries, against a real database.
  • Independently deployed services have contract tests and a can-i-deploy gate.
  • No test reads the wall clock, sleeps, depends on order or shares mutable state; CI runs tests in random order.
  • New code has a coverage floor; critical modules get periodic mutation testing.
  • Flaky tests are detected, quarantined, owned and fixed within days.
  • The whole pre-merge suite runs in minutes, not hours.

Self-check

Your service's tests mock the repository, the HTTP client and the pricing service, and they all pass. Production breaks because a column was renamed. Which test would have caught it, and why didn't the existing ones?

An integration test against a real database (via Testcontainers) running the real migrations and the real ORM mapping. The existing tests replaced the repository with a mock, so the SQL and the mapping, which is where the bug was, never ran. Mocks only check the code against your assumptions about the collaborator.

A refactor that changed no behaviour turned 30 tests red. What does that tell you about those tests?

They're coupled to implementation structure, typically through strict mocks or Verify calls on queries, or by testing private details. Good tests are sensitive to behaviour and insensitive to structure. Rewrite them to assert on outcomes (state of fakes, return values, HTTP responses), and keep interaction checks only for side effects that matter outside the unit.

Is it a stub or a mock: a test double that returns 0.2 from GetTaxRate(), with no assertion on it?

A stub. It provides an input to the code under test. Nothing verifies that it was called, which is right: GetTaxRate is a query. If you added Verify(x => x.GetTaxRate(), Times.Once) you would be turning it into a mock and coupling the test to how many times the code asks.

Coverage is 100% and the mutation score is 50%. What do the surviving mutants usually point to?

Missing boundary tests (no test sits exactly on >= 50, so >= → > survives), missing combinations of conditions (&& → || survives when no test has one side true and the other false), and weak or missing assertions. Each survivor names a test to write.

Why is "decode(encode(s)) == s" such a useful property?

It needs no expected values: you don't have to know what the encoding of a random string should be. It checks two functions against each other over any input the generator can produce, and it catches asymmetric bugs, like the encoder writing two-digit counts that the decoder reads as one digit.

A test passes alone and fails in the full suite, but only sometimes. Name the likely cause and how to prove it.

Shared mutable state (a static, a singleton, a shared database row, an environment variable) combined with a test order that varies. Prove it by running with a fixed random seed that reproduces the order (pytest-randomly -p randomly --randomly-seed=1234, JUnit's MethodOrderer.Random with junit.jupiter.execution.order.random.seed, go test -shuffle=<seed>, Jest --randomize --seed=<n>), then bisect which earlier test pollutes the state.

When would you use a strict mock on purpose?

When the absence of an interaction is the behaviour: "a declined card must not create a shipment", "a dry run must not send email". A strict mock (or VerifyNoOtherCalls, verifyNoInteractions) makes that explicit. Keep it to the one collaborator that matters, and use fakes or dummies for the rest.
