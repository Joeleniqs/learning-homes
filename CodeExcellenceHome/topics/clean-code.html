Clean Code & Refactoring

Naming, function shape, comments, code smells and safe step-by-step refactorings, animated as small transformations.

Beginner → Intermediate~50 min studyUpdated 2026-11-03

The problem: a one-character fix that took a day

A support ticket says VIP customers aren't getting free shipping on Sundays. The fix turns out to be one character, > instead of >=. Finding it takes most of a day, because the code looks like this:

// apply 10% discount
function calc(o, c, f, t) {
  let tmp = 0, tmp2 = 0;
  if (o) {
    if (c && c.s == 1) {
      for (let i = 0; i < o.l.length; i++) {
        if (o.l[i].q > 0) {
          if (f) { tmp += o.l[i].q * o.l[i].p * 0.85; } else { tmp += o.l[i].q * o.l[i].p; }
        }
      }
      if (t.getDay() == 0 && c.v && tmp > 50) tmp2 = 0; else tmp2 = 7.5;
      // ... 200 more lines like this

Every line on its own is simple. The whole is exhausting to read:

  • The names hide the meaning. What are c.s == 1, f and t? You have to find every caller to learn that f means "the customer has a coupon".
  • The comment lies. It says 10% while the code says 0.85. Which one is the bug?
  • Six levels of nesting. By the time you reach the shipping rule, you're holding five conditions in your head.
  • One function does pricing, discounts, shipping and tax, so you can't test the shipping rule alone. Nobody dares to touch it, so every fix gets bolted on as another if.

Over a year, three people read that function for every one who changes it: the author, the reviewer, and the on-call engineer at 3 a.m. Clean code is about those readers.

Clean code is code the next person can understand quickly and change safely. Choose names that say what things mean. Write functions that do one thing at one level of abstraction. Keep the structure flat enough that a reader holds only a few things in mind at once. Back it with tests, so you can reshape it in small steps without fear. Every rule on this page serves one of those goals; when a rule stops serving them, drop it.

This page covers the small scale: names, functions, comments, formatting, complexity, smells and refactoring. Other pages cover the rest:

  • The larger structure (coupling, SOLID, layering) is in design principles.
  • The big recurring mistakes (god objects, anaemic models, distributed monoliths) are in anti-patterns.
  • Expressing intent with types is in types and immutability; writing pipelines instead of loops is in functional patterns.
  • Refactoring is only safe with tests, so testing strategy is the companion page.

The mental model: the reader's working memory

People can hold roughly four unrelated things in working memory at once. Every unexplained abbreviation, every open if, every mutable variable that might have changed, and every hidden side effect takes one of those slots. When the slots run out, the reader starts re-reading, and that's when bugs slip past reviews.

Every technique on this page reduces the load on the reader:

Names carry meaning

isEligibleForFreeShipping replaces a condition you would otherwise have to decode. Each good name is a slot you don't spend.

Functions hide detail

A well-named function lets the reader skip its body. That only works if the name is honest and the function does one thing.

Flat structure

Guard clauses, early returns and pipelines close each condition as soon as it's checked, instead of leaving it open for 40 lines.

Tests make change safe

Without tests, nobody refactors; they bolt on another if. Tests are what let clean code stay clean.

Naming: the cheapest documentation you'll ever write

A name is read hundreds of times for every time it's typed. It's also the one piece of documentation that can't drift from the code, because it is the code. Good names follow a handful of rules:

  • Say what it means, not what it is. elapsedDays, not d or intValue. If a name needs a comment to explain it, the comment is telling you the better name.
  • Use the domain's words. If the business says "policyholder", don't call it customer in one file, client in another and user in a third. Domain-driven design calls this the ubiquitous language.
  • One word per concept. Pick fetch, get or retrieve for "load from the store", then use only that one. Two words make readers wonder what the difference is.
  • Scale the length with the scope. i is fine in a three-line loop. A field that lives for the whole program needs a name you can search for.
  • No encodings. Leave out type prefixes (strName), scope prefixes (m_) and type suffixes (customerList). The compiler knows the type, and the name becomes a lie when the type changes.
  • Booleans read as yes/no questions. Use isActive, hasShipped or canRetry. Avoid negatives like isNotDisabled, which turn !isNotDisabled into a puzzle.
  • Functions are verbs, types are nouns. sendInvoice() and Invoice. A class called InvoiceSender hints that a function got promoted to a class.
  • Put the unit in the name, or better, in the type. Write timeoutMs or delaySeconds rather than timeout. A TimeSpan/Duration/timedelta beats both.

When you struggle to name something, that's often a design signal. A function you can't name usually does two things.

Here is the same small service named idiomatically in each language. Notice what changes (casing, getters, how the clock is injected) and what doesn't: findOverdue, isOverdue and GRACE_PERIOD_DAYS say the same thing everywhere.

public sealed class InvoiceService(IInvoiceRepository invoices, TimeProvider clock)
{
    private const int GracePeriodDays = 14;

    public async Task<IReadOnlyList<Invoice>> FindOverdueAsync(CustomerId customerId, CancellationToken ct)
    {
        var today = DateOnly.FromDateTime(clock.GetUtcNow().UtcDateTime);
        var openInvoices = await invoices.ListOpenAsync(customerId, ct);
        return openInvoices.Where(invoice => IsOverdue(invoice, today)).ToList();
    }

    private static bool IsOverdue(Invoice invoice, DateOnly today) =>
        invoice.DueDate.AddDays(GracePeriodDays) < today;
}

}

Go is the outlier on purpose. Its style guide prefers short names for short scopes (inv, s, err) because Go functions are meant to be small and the type is always one glance away. It also avoids stutter: the package name is part of every call, so you write invoice.Service, not invoice.InvoiceService. A one-letter receiver in Go is idiomatic; a one-letter field in a Java class isn't.

Functions: small, focused, one level of abstraction

"Functions should be small" is the most quoted clean-code rule and the most misunderstood. Line count is a symptom; the real rules are about what a function asks the reader to think about:

  • Do one thing. Here's a practical test: if you can extract another function from it whose name isn't just a restatement of the code, it does more than one thing.
  • One level of abstraction per function. Don't mix "place the order" with sql.Append(", "). High-level steps call mid-level functions, which call low-level details. That way the code reads top-down like a newspaper: headline, summary, then details. This is the stepdown rule.
  • No surprises. The name promises everything the function does. A checkPassword that also starts a session is a bug waiting to happen.
// Mixed levels: the reader has to switch between "what" and "how" on every line
async function placeOrder(cart: Cart) {
  if (!cart.lines.length || cart.lines.some((l) => l.qty <= 0)) throw new Error("bad cart");
  let total = 0;
  for (const l of cart.lines) total += l.qty * l.unitPrice * (1 + TAX[l.category]);
  await db.query("UPDATE stock SET qty = qty - $1 WHERE sku = $2", [cart.lines[0].qty, cart.lines[0].sku]);
  await broker.send("orders", JSON.stringify({ type: "OrderPlaced", total }));
}

// One level: a table of contents. Each step is a function you can test and read alone.
async function placeOrder(cart: Cart): Promise<Order> {
  validate(cart);
  const order = price(cart);
  await reserveStock(order.lines);
  await publish(new OrderPlaced(order.id, order.total));
  return order;
}

Look at the "mixed" version again: it only reserves stock for the first line. That bug hides easily in the mixed version; in the one-level version, reserveStock(order.lines) makes the intent obvious.

Command–query separation

A function should either do something (a command: changes state, returns nothing) or answer something (a query: returns a value, changes nothing), not both. Queries are then safe to call any number of times, in any order, from a debugger, a log statement or a test.

// Violates CQS: a "get" that changes state
function getNextInvoiceNumber(): number {
  return ++this.lastNumber;
}
log.debug(`next invoice will be ${getNextInvoiceNumber()}`); // just skipped a number

// Separated: the query is safe anywhere; the command says what it does
function peekNextInvoiceNumber(): number { return this.lastNumber + 1; }
function allocateInvoiceNumber(): number { return ++this.lastNumber; } // named as a command

Be pragmatic about it. stack.pop(), Interlocked.Increment, map.putIfAbsent and queue.TryDequeue deliberately combine the two, because doing it in two calls would be a race. The rule is "no hidden side effects in things that look like questions", not "never return a value from a command".

Parameters: fewer, named, and typed by meaning

Every parameter is something the caller must get right and the reader must keep track of. Zero to two is easy, three needs a reason, and four or more is a smell (most linters flag it).

The real danger is parameters of the same type next to each other. The compiler checks types, not meaning, so (start, end) swapped, or (roomId, organizerId) swapped, compiles fine.

The visualizer binds the same six-argument call under four API designs, with a caller mistake of your choice. It type-checks each argument and shows where the mistake gets caught: at compile time, at the call site, far away in another service, or never.

Four techniques make long parameter lists safe:

  • Named arguments make the call site self-documenting and order-proof, where the language has them.
  • A parameter object groups values that travel together. It also gives defaults and validation one home.
  • Value types (RoomId, UserId, TimeSlot) turn swaps into compile errors and invalid ranges into immediate exceptions.
  • Enums instead of bare booleans make ScheduleMeeting(…, true, false) readable and swap-proof.

Two related smells:

  • Flag arguments. render(doc, true) means the function does two things, and the call site doesn't say which. Split it into renderPreview(doc) and renderFinal(doc). If the flag is really configuration, put it in an options object.
  • Output parameters. void fill(List<Error> errors) makes the reader check whether the argument is input or output. Return the result instead. C#'s TryParse(out x) pattern is the accepted exception.

Comments: why, not what

The code already says what it does. If it doesn't say it clearly, fix the code: rename, extract, or introduce a type. A comment is for what the code can't say: why this approach, why not the obvious one, what outside constraint forced the decision.

Comments have a cost that's easy to miss. The compiler doesn't check them and the tests don't run them, so they drift. A comment that was true when written and false now is worse than no comment, because readers believe it. The // apply 10% discount above * 0.85 at the top of this page is the classic case.

Comments that should be code

// check if the user is an adult
if (user.age >= 18) { ... }

// loop through orders
for (Order o : orders) { ... }

// 86400000 ms
long ttl = 86400000;

// returns the customer   (on getCustomer)
// TODO: fix this          (from 2019, no owner)
// } // end if             (closing-brace labels)
// int oldTotal = ...      (commented-out code)

Each one should be a name, a constant, a smaller function, a ticket, or a deletion. Git remembers deleted code; you don't need to keep it as a comment.

Comments that earn their place

// Stripe retries webhooks for up to 3 days, so the same event
// can arrive twice. Dedupe on event id, not on payload hash.

// Deliberately O(n²): n ≤ 8 seats per table, and the simple
// version is 3× faster than the sort for that size (bench #412).

// Regulatory: amounts must round half-even (EU 2023/1234 §4).

// WORKAROUND for driver bug PGJDBC-2903; remove after 42.7.4.

/** Returns the balance in minor units (cents); never null. */

Intent, constraints, references, warnings and the public contract: things nobody could work out from the code.

A few kinds of comment are always worth writing:

  • Public API documentation (/// XML docs, Javadoc, docstrings, Go doc comments, TSDoc). Callers read it in their IDE without opening your code. Describe the contract: what goes in, what comes out, what's thrown, thread-safety, units.
  • Why a surprising choice was made, with a link to the benchmark, ticket, incident or ADR.
  • Warnings: "not thread-safe", "called from the payment webhook, must be idempotent", "order matters: the auth middleware must run first".
  • TODO with an owner and a ticket: // TODO(joel, PAY-812): remove after the v1 API is retired. A TODO without one is a wish, and most linters can be set to reject it.

Before writing a comment, try to make it unnecessary. Ask yourself three questions. Could a better name say this? Could an extracted function's name say it? Could a type (Money, Percentage, NonEmptyList) make the invariant impossible to break? If all three answers are no, write the comment, and make it about why.

Formatting and linters: let the machines argue

Formatting debates are a waste of review time. Brace style, line length and import order matter far less than consistency, and consistency is exactly what tools are good at. The modern answer is the same in every language:

  1. A formatter rewrites the code into one canonical style. Run it on save and in CI. Nobody comments on whitespace again.
  2. A linter or analyzer finds likely bugs and smells: unused variables, unawaited tasks, == on strings in Java, mutable default arguments in Python, unchecked errors in Go, floating promises in TypeScript.
  3. A type checker on its strictest setting (where the type system is optional or lenient), so null and any don't leak everywhere.
1 · Editorformat on save

Formatter plus linter in the IDE; problems show while you type.

2 · Pre-commitfast hooks

Format and lint only the staged files, in seconds (pre-commit, Husky, lefthook).

3 · CIthe gate

Check mode (--verify-no-changes, --check); warnings as errors. Fails the PR.

4 · Reviewhumans on design

Reviewers never comment on style; the tools already did.

Complexity: putting a number on "hard to follow"

Two metrics are widely used. They measure different things:

  • Cyclomatic complexity (McCabe, 1976) counts the independent paths through a function: 1 plus each if, loop, case, &&, || and catch. It tells you how many tests you need to cover every branch. It treats ten flat ifs and ten nested ifs the same.
  • Cognitive complexity (SonarSource, 2017) estimates how hard the code is to understand. Each break in linear flow costs 1, plus 1 for every level of nesting it sits in. Sequences of the same boolean operator count once. A switch counts once in total, and early returns cost nothing. Nesting is what makes it grow.

The usual limits are about 10 for cyclomatic per function, and 15 for cognitive (Sonar's default). Treat them as prompts to look, not as laws.

Step through the visualizer to watch both scores accumulate line by line. Choose nested ifs (before), then guard clauses (after): the cyclomatic score barely moves because the same decisions are still there, but the cognitive score drops by more than half, because nothing is nested any more. Guards + named helpers splits the rules into named functions, so each one is trivial. The nested loops / pipeline pair shows the same effect for data processing, and else-if chain vs switch shows why a switch on one value is easier to read.

Go is where guard clauses are most visible: the if err != nil { return … } idiom is a guard clause, and Go's style guide asks for "the normal code path indented least". Other techniques that flatten code:

  • continue in loops instead of wrapping the loop body in if.
  • A lookup table or dictionary instead of a long if/else that maps values to values.
  • Pattern matching (switch expressions in C# and Java 21, match in Python 3.10) for a decision on the shape of data.
  • Polymorphism when the same type switch appears in several places (see the catalog below).
  • Pipelines (Where/Select, streams, comprehensions, filter/map) instead of loops with nested conditions. See functional patterns.

Refactoring: change the shape, keep the behaviour

Martin Fowler's definition is precise: refactoring is a change to the internal structure of software that makes it easier to understand and cheaper to modify, without changing its observable behaviour. Two consequences follow:

  • You need tests first. "Without changing behaviour" is a claim; tests are how you check it. With no tests, write characterization tests first: pin down what the code does today, including the odd parts, before you touch it. Approval and snapshot tests are ideal here (see testing strategy).
  • Refactoring and feature work are separate steps. Wear one hat at a time: either change behaviour (tests change) or change structure (tests don't change). Put them in separate commits, ideally separate PRs, so a reviewer can tell which is which.
1 · Greentests pass

Start from passing tests that cover the code you'll touch. No tests? Write characterization tests.

2 · One stepa small, named change

One refactoring from the catalog. Use the IDE's automated version where it exists.

3 · Green againrun the tests

Red? Undo, don't debug. The step was too big; take a smaller one.

4 · Commitsave the point

Small commits mean you can always get back to green.

// TypeScript: often a discriminated union plus an exhaustive switch is the
// better fit. The `never` check makes the compiler list every place to update.
type ShippingMethod =
  | { kind: "standard" }
  | { kind: "express" }
  | { kind: "pickup"; storeId: string };

function cost(method: ShippingMethod, s: Shipment): number {
  switch (method.kind) {
    case "standard": return 4.99;
    case "express": return 9.99 + 0.5 * s.weightKg;
    case "pickup": return 0;
    default: return assertNever(method);
  }
}

function assertNever(x: never): never {
  throw new Error(`Unhandled case: ${JSON.stringify(x)}`);
}
// Adding { kind: "drone" } turns every switch without that case into a compile error.

Polymorphism or an exhaustive switch? These are the two ends of the expression problem. With polymorphism, adding a new case is easy (one new class) and adding a new operation is hard (edit every class). With a closed union plus an exhaustive switch (TypeScript unions, Java sealed types, C# switch expressions, F#/Rust enums), adding an operation is easy and the compiler finds every switch to update when you add a case. Choose based on which one changes more often. The real smell is a non-exhaustive switch on a string, copied in three places.

Refactoring legacy code safely

Code with no tests and no clear seams needs a few extra techniques:

  • Characterization tests first: call the code with a wide range of inputs and record what comes out, right or wrong. Now you know when behaviour changes.
  • Sprout and wrap. Write the new logic in a new, tested function and call it from the old code (sprout). Or put a new function around the old one (wrap). The old code shrinks over time instead of growing.
  • Parallel change (expand → migrate → contract). To change a widely used signature, add the new version next to the old one. Then move callers over one PR at a time, and delete the old version when nothing uses it. Every step is deployable.
  • Strangler fig at the larger scale: route traffic piece by piece to a new implementation (see anti-patterns).

A smell is a surface sign that usually points to a deeper problem. It's not a bug, and not always wrong. Its value is that it has a name, and each name points to known refactorings. "This feels messy" turns into "this is feature envy; move the method".

The boy-scout rule: leave it a little better

"Always leave the campground cleaner than you found it." Applied to code: whenever you touch a file for a feature or a fix, improve one small thing on the way. Rename an unclear variable, extract a function, add a missing test, or delete dead code.

The strength of the rule is where the cleanup happens. Code is changed very unevenly: a few modules take most of the edits, and most code is barely touched for years. Cleanup that follows the work automatically lands in the hot spots, where it pays back on the very next change. A dedicated "cleanup sprint" spreads effort by how bad the code looks, which often isn't where people work.

The simulation below models a codebase of 24 modules with realistic, skewed change frequency. Each change adds a little debt, and debt makes later changes slower. Compare no cleanup, the boy-scout rule (each change spends a bit extra and removes some debt from the module it touched) and a cleanup sprint every 5th sprint, and watch how many features each delivers over 20 sprints.

Across seeds, the boy-scout rule delivers noticeably more features than either alternative, even though it "wastes" time on every change. The cleanup-sprint team pays the same price, but spends it on modules nobody would have touched. The model is simple, but it matches what code-churn research (Adam Tornhill's hot-spot analysis, for one) keeps finding: technical debt only costs you where you work, so clean where you work.

Keep it disciplined, though:

  • Small and related. Rename the variable in the method you're changing. Don't reformat the whole file or rewrite the module.
  • Separate commits. "refactor: extract isOverdue", then "feat: add grace period". Reviewers can check the refactor commit quickly because no tests change.
  • Big cleanups get their own PR, and ideally their own ticket. The boy-scout rule is for the five-minute improvements.
  • Use hot-spot data for bigger investments: git log change frequency × complexity points to the files where cleanup pays most.

When clean-code dogma hurts

Every clean-code rule is a heuristic with a cost. Applied mechanically, the rules produce code that passes every checklist and is still hard to work with. The three most common failures:

Over-abstraction and speculative generality

An IOrderService with one implementation, an OrderServiceFactory that creates one type, a IStrategy<TContext, TResult> used once, and a plugin system for a feature with one plugin. Each layer costs the reader a jump and costs a feature a change in several places, all for a flexibility nobody uses.

  • YAGNI: build the abstraction when the second real use case arrives, not when you imagine it.
  • An interface with one implementation is justified when it's a seam you need now: a test double for I/O, a module boundary, or an inversion that DI needs (see DI fundamentals). "We might swap databases one day" isn't one.
  • Prefer deep modules to shallow ones (John Ousterhout): a simple interface hiding a lot of work. A class whose methods just forward calls adds an interface without hiding anything.

Tiny-function sprawl

"Functions should be small" taken literally gives you 40 three-line functions, each called once, scattered across a file. To understand one behaviour, the reader jumps through eight of them and rebuilds the flow in their head, which is exactly the load clean code was supposed to remove.

# Sprawl: each piece is "clean", the whole is a scavenger hunt
def process(order):
    return _finalize(_apply(_prepare(order)))

def _prepare(order): return _with_defaults(_normalize(order))
def _normalize(order): return order.copy(currency=order.currency.upper())
def _with_defaults(order): return order if order.channel else order.copy(channel="web")
def _apply(order): return _taxed(_discounted(order))
# ... five more, each called exactly once

# Better: one function that reads top to bottom, with extraction only where a name adds meaning
def price_order(order: Order) -> PricedOrder:
    currency = order.currency.upper()
    channel = order.channel or "web"
    subtotal = sum(line.qty * line.unit_price for line in order.lines)
    discount = loyalty_discount(order.customer, subtotal)   # a real business rule: worth a name
    tax = tax_for(order.ship_to, subtotal - discount)        # reused and tested alone: worth a name
    return PricedOrder(currency, channel, subtotal, discount, tax)

The test for extraction isn't size. It's this: does the new name tell the reader something the code didn't? loyalty_discount does; _apply doesn't.

DRY versus WET, and the rule of three

DRY ("Don't Repeat Yourself") is about knowledge, not text. Andy Hunt and Dave Thomas defined it as "every piece of knowledge must have a single, unambiguous, authoritative representation". Two pieces of code that look the same but represent different decisions aren't duplication. They are coincidentally similar, and merging them couples things that will change for different reasons.

The usual failure goes like this:

  1. The invoice, the receipt and the order email format addresses the same way, so someone extracts formatAddress.
  2. Then the receipt needs the country left out, so it grows a bool includeCountry.
  3. Then the email needs HTML, so it grows a mode parameter.
  4. Two years later, formatAddress has seven flags, and every change risks breaking a screen nobody meant to touch.

Sandi Metz: "duplication is far cheaper than the wrong abstraction." The rule of three is the practical compromise: tolerate the second copy, and abstract on the third, when you can actually see what varies.

The simulation replays one stream of change requests against three screens, under each strategy. Each change is either shared (should apply to all three) or divergent (only one screen). With copies, a shared change can miss a copy and cause a bug. With the abstraction, a divergent change adds a flag and can cause a regression in the other screens. Switch the changes are between mostly shared and mostly divergent, and the winner flips.

Ask "do these change for the same reason?", not "do these look the same?". Tax calculation used in checkout and in refunds is the same knowledge: one rule, one place, or they will drift apart and you'll refund the wrong amount. Two validation methods that both check length > 0 for a username and a product code are coincidence; leave them apart. And when you discover a wrong abstraction, it's fine to go backwards: inline it into its callers, delete what each doesn't need, and look for the right abstraction again.

Performance and pragmatism

Clean-code techniques are usually free, because the JIT and compilers inline small functions. In a hot loop over millions of items, though, virtual dispatch, per-item allocations and data scattered across objects can cost real time. That's the core of the "clean code, horrible performance" critique. The answer isn't to give up readable code everywhere. Write it clean, measure, and only reshape the few hot paths a profiler points to, with a comment explaining why (see performance patterns).

When to use what

Do

  • Rename the moment you understand something better; renames are cheap and IDE-safe.
  • Use guard clauses and early returns so the main path runs down the left margin.
  • Give values with meaning a type (Money, RoomId, TimeSlot), and long parameter lists a parameter object.
  • Let a formatter and a strict linter settle style, in the editor and as a CI gate.
  • Refactor in small, named steps on green tests, in commits separate from behaviour changes.
  • Clean up a little in the code you're already changing.
  • Write comments about why: constraints, trade-offs, links to the decision.
  • Abstract on the third real use, when you can see what varies.

Don't

  • Abbreviate, encode types in names, or use data, info, manager, process, handle as a whole name.
  • Nest five levels deep, or leave a flag argument that switches between two behaviours.
  • Write comments that repeat the code, or keep commented-out code.
  • Argue about formatting in review.
  • Mix a large refactor into a feature PR, or refactor without tests.
  • Split a readable function into ten single-use fragments to meet a line limit.
  • Merge code that only looks alike, or add an interface for a flexibility nobody needs.
  • Rewrite a hot loop for "cleanliness" without measuring it.

Pitfalls

The rename that wasn't. Someone renamed GetUser to FindUser by search-and-replace. It also changed GetUserPreferences, a string in a SQL query, and a JSON property that a mobile app depended on. Fix: use the IDE's semantic rename, which only touches real references. Treat anything serialized (JSON fields, database columns, event names, public API routes) as a contract that needs a versioned migration, not a rename.

The refactor PR with a hidden behaviour change. A 1,200-line "cleanup" PR also changed rounding in one function. The reviewer skimmed it as "just moves", and invoices were off by a cent for a week. Fix: refactoring PRs change no tests. Behaviour changes go in their own small commit, with a test that shows the new behaviour.

Extract-method that changed evaluation order. if (isValid(x) && save(x)) became var valid = isValid(x); var saved = save(x); if (valid && saved), which saves invalid data, because && short-circuited and the extracted version doesn't. Fix: be careful with side effects when extracting conditions. Use the IDE's refactoring and keep a test that checks invalid input isn't saved.

The linter nobody can satisfy. Rules were copied from a blog post: max 5 lines per function, max 1 parameter, no else. Developers spread // eslint-disable everywhere and started ignoring all warnings. Fix: fewer rules, agreed by the team, each one catching real bugs or real readability problems. Every disabled warning should carry a reason comment.

The shared helper that coupled two teams. A "utils" package with formatAddress(includeCountry, html, legacy, …) was used by billing and shipping. Any change needed both teams' sign-off, so nobody changed it, and both teams built workarounds around it. Fix: inline the wrong abstraction back into each caller, then let each team own its own version until a real shared concept appears.

Checklist

  • Names say what things mean, use the domain's words, and follow the language's conventions; no encodings or abbreviations.
  • Booleans read as questions; functions are verbs; types are nouns.
  • Each function does one thing at one level of abstraction; queries don't change state.
  • No more than three parameters without a reason; same-typed neighbours are named, grouped or given distinct types; no flag arguments.
  • Nesting stays at two levels or fewer; special cases leave early.
  • Cognitive complexity is under about 15 per function, enforced by a linter where possible.
  • Comments explain why; public APIs document their contract; TODOs have an owner and a ticket.
  • A formatter, a linter and strict type checking run on save and as a CI gate, configured in the repo.
  • Refactoring happens on green tests, in small steps, in commits separate from behaviour changes.
  • Duplication of knowledge is removed; coincidental similarity is left alone until the rule of three.

Self-check

Guard clauses reduced a function's cognitive complexity from 16 to 6, but its cyclomatic complexity stayed at 7. Why didn't the cyclomatic score move, and what does each number tell you?

Cyclomatic complexity counts decision points, and guard clauses keep every decision; they only stop nesting them. So the number of paths, and therefore the number of tests needed to cover every branch, is unchanged. Cognitive complexity charges extra for nesting, and that's what the reader feels. Use cyclomatic to size the tests, and cognitive to judge readability.

A method is void Transfer(string fromAccount, string toAccount, decimal amount, bool notify, bool audit). Name three smells and the refactoring for each.

Same-typed neighbours (fromAccount, toAccount): swapping them compiles and moves money the wrong way. Use an AccountId value type, or named arguments at least. Flag arguments (notify, audit): the call Transfer(a, b, 10m, true, false) is unreadable. Use an options object or enums, or make notification and auditing separate concerns (a decorator or a domain event). Primitive obsession (decimal amount): the amount has no currency and can be negative. Use a Money type that validates. Also consider a TransferRequest parameter object.

You're asked to add a feature to a 900-line method with no tests. What do you do first, and what goes in your PR?

First, write characterization tests that pin down what the method does today around the area you'll change; approval tests work well. Then use sprout: put the new logic in a new, small, tested function, and call it from the old method with a one-line change. If you also refactor (say, extracting the block you needed to understand), do that in a separate commit or PR that changes no tests. Don't try to rewrite the whole method in a feature PR.

Two functions both do if (!value.trim()) throw new Error("required") followed by a regex check. One validates a username and the other a product SKU. Should you extract a shared function?

Probably not. They look alike, but they encode different business rules that will change for different reasons (username policy versus the SKU format from a supplier). Merging them couples the two, and the first divergent change adds a flag. If a third, genuinely identical rule appears, or if both truly come from one rule ("all identifiers in our system are …"), then extract. A tiny generic helper like requireNonBlank is fine; the regex rules should stay apart.

Your team adds a cleanup sprint every quarter, yet velocity keeps falling. What's a likely reason, and what would you change?

The cleanup is probably landing on code that looks worst rather than code people change most, so the hot spots keep accumulating debt between sprints. Switch to the boy-scout rule (small improvements on every change, which automatically targets hot spots). Use churn × complexity data to choose any larger cleanup, and give it its own PR.

When is a comment the right tool rather than a better name or function?

When it says something the code can't express. Why this approach was chosen over the obvious one. An external constraint: a regulation, an API quirk, a bug workaround with a link. A warning about thread-safety, idempotency or ordering. A public API contract read by callers in their IDE. If the comment says what the code does, turn it into a name instead.
