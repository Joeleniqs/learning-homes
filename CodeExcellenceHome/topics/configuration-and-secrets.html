Configuration, Feature Flags & Secrets

Layered configuration, the options pattern, twelve-factor apps, feature flags and safe rollouts, and secret management with managed identity.

Intermediate~40 min studyBuilds on: Advanced DI: Decorators, Factories, Options & TestingUpdated 2026-11-03

The problem: the setting nobody could find

Release v42 of the checkout service went out at 02:40. By 03:00 the pricing service was taking 25 times its normal traffic. Nobody had changed the code path. Someone had changed a default in appsettings.json: Pricing:BatchLookups went from true to false during a refactor, and every basket line now made its own pricing call. Production had no override for that key, so the new default won. When the team found it, they fixed it in two minutes by setting an environment variable, with no redeploy. That story appears in Observability from the metrics side. This page is the configuration side of it.

Configuration is everything that changes between deployments of the same build: connection strings, URLs, timeouts, pool sizes, log levels, feature switches and credentials. Get it right and one artifact runs everywhere, changes are safe, and secrets never touch a repository. Get it wrong and you get the classics: a typo that crashes only in production, a flag nobody dares remove, an API key in Git history forever, and a password rotation that takes the site down.

The rule. Build one artifact and change its behaviour only through layered configuration with a documented precedence. Bind settings into typed objects and validate them at startup, so bad config fails the deploy instead of the 3 a.m. request. Treat feature flags as short-lived code with an owner and an expiry. Keep secrets out of source and out of files: fetch them from a secret store, preferably with an identity instead of a secret, and design every credential so it can be rotated without downtime.

Recognize that your configuration needs work when

  • You build a different artifact per environment (Release-Prod, webpack.prod.js with hard-coded URLs).
  • A wrong value is discovered by the first request that reads it, not by the deploy.
  • Nobody can answer "where does this value come from in production?" without reading three files and a pipeline.
  • if (env == "Production") appears in business code.
  • There are flags in the code that were fully rolled out a year ago.
  • A connection string or key is in appsettings.json, application.yml, a .env file in Git, or a CI log.
  • Rotating a database password needs a maintenance window.

Configuration as layers

Every modern stack composes configuration from providers stacked in order. Each provider contributes key/value pairs; when two providers define the same key, the later one wins. Nothing is merged at the object level unless you ask for it: each key is decided on its own. That gives you a simple mental model: defaults at the bottom, the most specific and most operational sources at the top.

Two consequences catch people out:

  • A layer that does not mention a key cannot protect you from a change below it. In the v42 incident, Production had no Pricing:BatchLookups, so a changed default in the base file went straight through. If a value matters in production, set it explicitly in the production layer or validate it.
  • Higher layers are harder to see. Defaults and files are in the repository and code-reviewed. Environment variables live in a deployment manifest, command-line arguments in a startup script, and secrets in a vault. When debugging, always look at the effective value and where it came from, not at a file.

Try it below. Pick an environment, then type overrides as you would set them on a container. Use __ (double underscore) for the : separator, as .NET does, and watch which layer wins each key. Note what happens to PRICING_BATCHLOOKUPS with a single underscore: it is a perfectly valid environment variable that no key reads, so it silently does nothing.

Ask the runtime, not the files. Every stack can tell you where a value came from. In .NET, ((IConfigurationRoot)config).GetDebugView() prints every key with its provider. Spring Boot Actuator's /actuator/env and /actuator/configprops list property sources in order (mask the values). With pydantic-settings, print settings.model_dump() at startup with secret fields as SecretStr. Viper has viper.AllSettings(). Expose a redacted version on an admin endpoint or log it once at startup, and the "where does this come from?" question takes seconds.

The default stack in each ecosystem

The six layers above are the common shape. Each framework ships a slightly different default order, and that order is part of its contract.

Stack Default order, lowest to highest Environment selector
ASP.NET Core (WebApplication.CreateBuilder) appsettings.json → appsettings.{Environment}.json → user secrets (Development only) → environment variables → command line ASPNETCORE_ENVIRONMENT / DOTNET_ENVIRONMENT
Spring Boot defaults → @PropertySource → application.yml → application-{profile}.yml → OS environment → Java system properties → command line (plus config trees and spring.config.import of vaults) SPRING_PROFILES_ACTIVE
pydantic-settings field defaults → secrets directory → .env file → environment variables → __init__ arguments you choose (often APP_ENV selecting the .env file)
Go (viper) SetDefault → config file → key/value store → environment (AutomaticEnv) → flags → explicit Set you choose (often APP_ENV)
Node (@nestjs/config, dotenv) .env files (first file wins) → process.env (wins by default) → your schema defaults if not set NODE_ENV (by convention)

The details differ in ways that matter. Spring Boot has more than a dozen ordered sources; pydantic-settings lets you reorder them with settings_customise_sources; dotenv will not overwrite a variable that is already set in the process unless you pass override: true. Do not memorise every list. Learn where yours is documented and check the effective value.

Mapping hierarchical keys to environment variables

Configuration is hierarchical (Pricing → TimeoutMs), but environment variables are flat strings, and many shells do not allow : or . in names. Each stack has a convention for flattening keys, and getting it wrong produces the silent no-op you saw above.

Stack Key Environment variable Rule
.NET Pricing:TimeoutMs Pricing__TimeoutMs __ becomes :; case-insensitive
.NET array Pricing:Regions:0 Pricing__Regions__0 index as a key segment
Spring Boot pricing.timeout-ms PRICING_TIMEOUTMS relaxed binding: uppercase, . becomes _, dashes removed
Spring Boot list pricing.regions[0] PRICING_REGIONS_0_ index wrapped in underscores
pydantic-settings pricing.timeout_ms APP_PRICING__TIMEOUT_MS env_prefix="APP_", env_nested_delimiter="__"
viper pricing.timeout_ms APP_PRICING_TIMEOUT_MS SetEnvPrefix("APP") plus SetEnvKeyReplacer(strings.NewReplacer(".", "_"))
Node / zod pricing.timeoutMs PRICING_TIMEOUT_MS whatever your loader maps; usually flat names

Catch typos in environment variables. A misspelled variable is ignored by every provider. Two defences: validate that every required value is present (next section), and at startup log a warning for any variable with your app prefix (APP_, Pricing__) that did not bind to a known key. A few lines of code do it: list the variables that start with your prefix and compare them with the keys your settings types declare. (pydantic-settings' extra="forbid" rejects unknown keys in a .env file, but not unknown environment variables.)

Binding to typed settings

Reading config["Pricing:TimeoutMs"] as a string in fifty places is how typos and parsing bugs spread. Every ecosystem has a better way: bind a section once into a typed object, validate it, and inject that object. Code that uses settings then depends on a small, testable type, not on the configuration system. This is the same principle as dependency injection: depend on what you need, not on where it comes from.

// appsettings.json: { "Pricing": { "BaseUrl": "https://pricing.internal", "TimeoutMs": 800, "BatchLookups": true } }
using System.ComponentModel.DataAnnotations;

public sealed class PricingOptions
{
    public const string Section = "Pricing";

    [Required, Url] public string BaseUrl { get; init; } = "";
    [Range(50, 10_000)] public int TimeoutMs { get; init; } = 800;
    public bool BatchLookups { get; init; } = true;
    [Range(0, 5)] public int Retries { get; init; } = 2;
}

var builder = WebApplication.CreateBuilder(args);   // json, env json, user secrets, env vars, args

    .Bind(builder.Configuration.GetSection(PricingOptions.Section))
    .ValidateDataAnnotations()

A few things in those snippets are worth stealing whatever language you use:

  • Durations as durations. Duration, time.Duration and TimeSpan parse 800ms or 00:00:00.800. A key called Timeout holding 800 invites someone to read it as seconds. If you must use a number, put the unit in the name: TimeoutMs.
  • Booleans from strings are a trap. In JavaScript, Boolean("false") is true, and so is zod's z.coerce.boolean() for any non-empty string. Parse booleans explicitly.
  • The settings object is immutable. init-only properties, Java records, frozen objects. Code that changes settings at runtime is hiding a feature flag or a state machine.
  • Only the composition root touches the configuration system. Everything else receives a typed object. That makes unit tests trivial: new PricingClient(http, Options.Create(new PricingOptions { TimeoutMs = 50 })).

Which IOptions? In .NET, the choice between IOptions<T>, IOptionsSnapshot<T> and IOptionsMonitor<T> is a lifetime question: singleton read once, scoped re-read per request, or singleton with change notifications. DI advanced has a visualizer that steps through all three during a reload, and DI lifetimes explains why injecting a scoped IOptionsSnapshot<T> into a singleton fails. The short version: use IOptions<T> unless you have a specific reason to reload; hot reload below explains why.

Fail fast: validate at startup

Most configuration bugs are not subtle. A timeout of 3000 where the code expects seconds. A connection string that is missing in one region. A URL without its scheme. A variable name with a typo. What makes them expensive is when you find out. If the value is only parsed when the first request needs it, the new version passes its health checks, takes traffic, and fails real customers until someone notices. If the value is validated at startup, the new pod never becomes ready, the rolling deployment stops, and the old version keeps serving.

Pick a mistake below and compare the two modes. Watch the timeline: with lazy validation the failure spreads to every new pod while the dashboard is still green; with validation on start the deployment stalls on the first pod and nobody outside the team ever sees it.

Validation at startup only protects you if the orchestrator is told about it. The process must exit non-zero (or report not-ready) when validation fails, and the deployment must use readiness probes with a rolling update that waits for readiness (Kubernetes maxUnavailable: 0, App Service deployment slots with a warm-up, ECS minimum healthy percent). Observability explains which probe does what.

// Cross-field and environment-specific rules: IValidateOptions<T> runs with ValidateOnStart().
public sealed class PricingOptionsValidator(IHostEnvironment env) : IValidateOptions<PricingOptions>
{
    public ValidateOptionsResult Validate(string? name, PricingOptions o)
    {
        var errors = new List<string>();
        if (env.IsProduction() && !o.BaseUrl.StartsWith("https://", StringComparison.Ordinal))
            errors.Add("Pricing:BaseUrl must use https in Production.");
        if (o.TimeoutMs * (o.Retries + 1) > 5_000)
            errors.Add($"Pricing timeout budget {o.TimeoutMs * (o.Retries + 1)} ms exceeds the 5 s request budget.");
        return errors.Count == 0 ? ValidateOptionsResult.Success : ValidateOptionsResult.Fail(errors);
    }
}

// @Validated on the @ConfigurationProperties record (previous section) already runs Bean Validation
// while the context starts. Add cross-field rules with a method-level constraint:
@Validated
@ConfigurationProperties(prefix = "pricing")
public record PricingProperties(
        @NotBlank @Pattern(regexp = "https://.*") String baseUrl,
        @NotNull Duration timeout,
        boolean batchLookups,
        @Min(0) @Max(5) int retries) {

    @AssertTrue(message = "timeout x (retries + 1) must fit the 5 s request budget")
    public boolean isWithinBudget() {
        return timeout.multipliedBy(retries + 1L).compareTo(Duration.ofSeconds(5)) <= 0;
    }
}

// Validate returns every problem at once; main exits non-zero before opening a listener.
func (c Config) Validate() error {
    var errs []error
    u, err := url.Parse(c.Pricing.BaseURL)
    if err != nil || u.Scheme == "" || u.Host == "" {
        errs = append(errs, fmt.Errorf("APP_PRICING_BASE_URL %q is not an absolute URL", c.Pricing.BaseURL))
    } else if c.Environment == "Production" && u.Scheme != "https" {
        errs = append(errs, errors.New("APP_PRICING_BASE_URL must use https in Production"))
    }
    if c.Pricing.Timeout < 50*time.Millisecond || c.Pricing.Timeout > 10*time.Second {
        errs = append(errs, fmt.Errorf("APP_PRICING_TIMEOUT %s out of range [50ms, 10s]", c.Pricing.Timeout))
    }
    if budget := c.Pricing.Timeout * time.Duration(c.Pricing.Retries+1); budget > 5*time.Second {
        errs = append(errs, fmt.Errorf("pricing timeout budget %s exceeds 5s", budget))
    }
    return errors.Join(errs...) // Go 1.20+
}

What to validate, roughly in order of value:

  1. Presence of everything required in this environment. A missing connection string is the most common production config bug.
  2. Type and unit: numbers parse, durations have units, enums are one of the known values, URLs are absolute.
  3. Ranges that encode real limits: pool sizes, timeouts, batch sizes, percentages.
  4. Cross-field rules: timeout × attempts fits inside the caller's deadline; MinPoolSize <= MaxPoolSize; if TLS is on, a certificate is configured.
  5. Environment rules: production requires https, a real secret store, a non-default admin password.
  6. Reachability, carefully. Checking that the database answers at startup is tempting, but if every pod refuses to start during a 30-second database blip you have turned a blip into an outage. Report dependencies through readiness, not by crashing.

Validation messages must not print secrets. "Invalid connection string Server=…;Password=hunter2" in a crash log is a leak. Name the key and the rule, never the value, for anything that could be sensitive. pydantic's SecretStr and Spring's sanitised configprops endpoint help, but check what your validator prints.

Twelve-factor configuration

The Twelve-Factor App put one rule at the centre: store config in the environment, strictly separated from code. The test it proposes is still the best one: could you open-source this repository right now without leaking any credentials? The point behind it is build once, deploy many: the same immutable artifact is promoted from test to staging to production, and only the environment changes.

Twelve-factor was written in 2011, and "the environment" has grown since. The intent survives better than the letter:

Twelve-factor said What still holds What changed
Config in environment variables Config is outside the artifact, injected per deployment Env vars are a transport, not a store: they come from ConfigMaps, App Configuration, Parameter Store or a vault
No config files grouped by environment Avoid named environment bundles that multiply (qa2, prod-eu-hotfix) Per-environment overlay files are fine when small and reviewed; Helm values, Kustomize overlays and appsettings.Production.json are normal
Secrets as env vars Never in the code Env vars leak into crash dumps, /proc/<pid>/environ, child processes and debug pages. Prefer identity plus a vault, or files mounted from a secret store
Strict separation of config and code Yes Feature flags blur the line on purpose; they are runtime config with a lifecycle (below)

Environment checks in business code. if (env.IsProduction()) SkipFraudCheck = false; hides configuration inside code, so you cannot test the production path anywhere else, and the next environment (Production-EU) silently behaves like test. Express the difference as a setting (Fraud:Enabled) with a safe default, and let each environment's layer set it.

Where configuration lives in production

Files and environment variables are the start. Real systems usually add a central configuration service for values shared by many services or changed without a deploy, and a secret store for credentials.

Need Typical home Examples
Per-service defaults Repository, code-reviewed appsettings.json, application.yml, field defaults
Per-environment values Deployment manifests, versioned Kubernetes ConfigMap, Helm values, Bicep/Terraform app settings
Shared or dynamic values, flags Configuration service with history Azure App Configuration, AWS AppConfig, Spring Cloud Config, Consul KV
Credentials and keys Secret store with access control and audit Azure Key Vault, AWS Secrets Manager, HashiCorp Vault, GCP Secret Manager

Whatever the store, treat configuration changes like code changes: reviewed, versioned, auditable and revertible. A large share of production incidents in public post-mortems are configuration pushes, not code deploys, and a config change often reaches every instance faster than any code deploy would.

Hot reload: useful and dangerous

Most stacks can reload configuration without a restart: .NET's JSON provider has reloadOnChange, Kubernetes updates mounted ConfigMaps, App Configuration and Spring Cloud Config push refreshes, viper has WatchConfig. That is how the v42 team fixed BatchLookups in two minutes. It is also how you get failures that never happen at startup, because a reload bypasses everything that made startup safe.

The classic bug: two settings that must change together, such as an endpoint URL and the API key for that endpoint, are updated in two writes. Between those writes, a reader that fetches the keys one at a time sees the new URL with the old key. Step through the three strategies below and watch the red cells:

  • A reads each key at the moment it needs it, so a request can straddle the two writes.
  • B takes one snapshot per request (like IOptionsSnapshot<T>), so a request is consistent with itself, but requests that start between the writes still pair the new URL with the old key.
  • C binds and validates a candidate object, keeps the last good one if the candidate is invalid, and swaps a single reference atomically.
// Keep the last good value; validate before swapping; swap one immutable reference.
public sealed class PaymentsEndpoint : IDisposable
{
    private volatile PaymentsOptions _current;
    private readonly IDisposable? _sub;

    public PaymentsEndpoint(IOptionsMonitor<PaymentsOptions> monitor, ILogger<PaymentsEndpoint> log)
    {
        _current = monitor.CurrentValue;                  // validated by ValidateOnStart
        _sub = monitor.OnChange(candidate =>
        {
            if (!candidate.IsConsistent(out var why))     // e.g. key id matches the URL's tenant
            {
                log.LogWarning("Rejected Payments reload: {Reason}; keeping last good config", why);
                return;
            }
            _current = candidate;                         // one reference write: readers see old or new, never half
        });
    }

    public PaymentsOptions Current => _current;           // read once per request, then use the local copy
    public void Dispose() => _sub?.Dispose();
}
// Note: if ValidateOnStart validators fail on reload, IOptionsMonitor.CurrentValue throws
// OptionsValidationException on access. Decide deliberately whether you want that or last-good.

// Spring Cloud: @RefreshScope rebuilds the bean on /actuator/refresh or a bus event.
// Rebinding @ConfigurationProperties re-runs @Validated; an invalid refresh fails the refresh.
@Component
class PaymentsEndpoint {
    private final AtomicReference<PaymentsProperties> current;

    PaymentsEndpoint(PaymentsProperties initial) { current = new AtomicReference<>(initial); }

    @EventListener(EnvironmentChangeEvent.class)
    void onChange(EnvironmentChangeEvent e) {
        if (e.getKeys().stream().noneMatch(k -> k.startsWith("payments."))) return;
        PaymentsProperties candidate = Binder.get(environment)
                .bind("payments", PaymentsProperties.class).orElseThrow();
        if (candidate.isConsistent()) current.set(candidate);   // atomic swap of an immutable record
        else log.warn("Rejected payments reload; keeping last good config");
    }

    PaymentsProperties current() { return current.get(); }
    @Autowired private Environment environment;
    private static final Logger log = LoggerFactory.getLogger(PaymentsEndpoint.class);
}

Some settings cannot be reloaded safely, no matter how good the reader is, because they were consumed once to build something long-lived:

Setting Why reload does nothing (or worse) What to do instead
Listen ports, TLS certificates for the listener The socket is already bound Restart, or use a server with explicit certificate reload (Kestrel's ServerCertificateSelector)
Connection pool size, thread-pool limits The pool was created at startup Rolling restart
Database connection strings Existing pooled connections keep the old target Restart, or design for it with a pool you can drain

When to use hot reload. Log levels, feature flags, rate limits, timeouts on a non-critical path, and kill switches. These are exactly the "operational" settings you want to change during an incident. When not to: anything structural (above), anything that changes in pairs without an atomic write, and anything where a mistake hits every instance at once. A reload goes to the whole fleet in seconds; a deployment goes to one pod at a time behind readiness checks. For risky changes, a deployment's slowness is a feature.

Feature flags

A feature flag (feature toggle) is a runtime decision point: if (flags.IsEnabled("new-checkout", user)). It separates deploying code from releasing behaviour. You merge and deploy unfinished work dark, turn it on for employees, then 1% of users, then everyone, and you can turn it off in seconds without a rollback. Flags are configuration, but configuration that is evaluated per request and per user, with rules, and that is why they deserve their own section.

The flag rule. Every flag has a kind, an owner, a safe default for when the flag service is unreachable, and (unless it is an ops or permission flag) an expiry. Evaluate flags once per request at the edge of the feature, not deep in loops. Delete release flags as soon as they reach 100%: a flag is a branch in production that you have to keep testing.

Four kinds of flag

Pete Hodgson's classification (on martinfowler.com) is the one most teams use. The kinds differ in how long they live and how dynamic the decision is, and mixing them up is the root of most flag pain: a "temporary" release flag that turns into a permanent customer entitlement, or a kill switch that nobody dares delete because nobody knows which kind it is.

Kind Purpose Lifetime Decided by Example
Release Ship unfinished or risky code dark, then ramp Days to weeks Percentage, employees first new-checkout
Ops (kill switch, circuit) Degrade gracefully under load or during incidents Long-lived, by design An operator, a runbook or automation recommendations, pricing-batch-lookups
Experiment A/B test: compare variants on a metric Weeks, until significant Sticky random assignment, stratified price-test with control, A, B
Permission (entitlement) Turn features on for plans, tenants, beta groups Long-lived, part of the product Attributes of the user or tenant bulk-export for enterprise

Flags are the right tool for

  • Merging to main daily while a feature is unfinished (trunk-based development).
  • Progressive delivery: ramp a risky change while watching error rates.
  • Kill switches for expensive, non-essential features (recommendations, live search suggestions).
  • Experiments where you need the same user to see the same variant for weeks.
  • Beta programmes and per-tenant enablement.

Flags are the wrong tool for

  • Values that are just configuration (timeouts, URLs): use typed settings.
  • Permanent product tiers modelled as hundreds of release flags: build an entitlement model.
  • Security controls ("disable auth for this tenant"): a flag service outage must not open a door.
  • Database schema changes: a flag cannot un-migrate data; use expand/contract migrations (Data Access).
  • Hiding bad code from tests: every flag doubles the paths you must test.

How a flag is evaluated

Every flag system evaluates in roughly the same order: is the flag switched on at all? Do any targeting rules match this user (employees, a country, a plan, a list of beta tenants)? If not, put the user in a bucket from 0 to 99 by hashing the flag key with a stable user id, and compare the bucket with the rollout percentage. Hashing flag:user rather than user alone matters: otherwise the same 10% of users would be the guinea pigs for every flag you ever ship.

Pick a flag and a user, then step through. Try emp-17 as the user id, switch the flag off, or change the plan to enterprise, and watch the bucket gauge and the population bars underneath: for 10,000 simulated users they show how many get each variant.

Things the evaluation order teaches:

  • The switch beats everything. "Off" must mean off for everybody, including employees. That is what makes it a kill switch.
  • Rules are ordered. "Employees first" before "hold back enterprise" means an employee on an enterprise tenant gets the new checkout. Write rules so the order is obvious, and test the overlaps.
  • The default is a decision. When the flag service times out, the SDK returns your code's default. For a release flag that is off; for an ops flag that protects a dependency, think about which side is safe.
  • Evaluation is local. Good SDKs download the rules and evaluate in-process in microseconds. A network call per evaluation would put the flag service on every request's critical path.

Ramping safely

A percentage rollout is only safe if two things hold. The assignment is sticky (a user who got the new checkout keeps it on every request, so they do not flicker between two UIs and two carts), and the ramp is guarded (something compares the error rate of the new path with the old path at each stage and stops the ramp automatically). Set a bug rate below and step through. Then switch to "random per request" and count the users who see both versions.

The guard is where flags meet observability. To compare old and new you need the flag variant on your telemetry: a span attribute (feature_flag.key, feature_flag.variant are OpenTelemetry semantic conventions) and a bounded metric label such as variant="new". Never put the user id on the metric; the flag variant is fine because it has two or three values.

Ramp shape. 1% → 5% → 25% → 50% → 100% is a common default. The first steps find crashes; the middle steps find load problems that only appear at scale (a new query that is fine at 1% and saturates the database at 50%). Hold each step long enough to see a full traffic cycle, and make "roll back" a single click or an automatic action, never a deploy.

Flag lifecycle and flag debt

A release flag that reached 100% three months ago is not harmless. It is a branch that every reader must understand, a configuration surface that someone can flip by accident, and a test matrix that doubles with every flag. With 10 independent boolean flags there are 1,024 combinations, and nobody tests them all.

The most famous flag accident: in 2012 a trading firm deployed new code to its servers but missed one of eight. The new code reused an old flag whose original meaning, on the server still running old code, activated long-dead test logic. The firm lost about $440 million in 45 minutes. Reusing a flag name, leaving dead code behind a flag, and a partial deployment combined into a company-ending event.

Step through two years of flag creation below under three policies. Without a policy, the stale (red) part keeps growing; with a removal ticket filed at creation, most finished flags are gone within weeks.

1 · CREATEKind, owner, expiry

Declare the flag in code and in the flag service with its kind, owning team, default and a removal date.

2 · DARKOff in production

Merged and deployed, on in dev and test. Both paths are tested in CI.

3 · RAMPEmployees → 1% → 100%

Sticky buckets, a variant label on telemetry and an automatic guard.

4 · CLEAN UPDelete the flag

Remove the old path and the flag check in one PR, then archive the flag. Never reuse the name.

Ways teams keep flag debt down:

  • Expiry dates enforced by tooling: the flag service shows stale flags, a CI check warns when an expired flag is still referenced, and a weekly report goes to the owner.
  • The cleanup PR is written with the feature. Some teams open the "remove flag" PR when they add the flag, and merge it once the ramp completes.
  • One flag check per feature, at the edge (controller, route or composition root), selecting an implementation. Fifty if (flag) checks scattered through the code are fifty places to clean up.
  • Never reuse a flag name. Archive it; create a new one.
  • Ops and permission flags are documented as permanent, so nobody "cleans them up" by accident.

Secrets

A secret is any value that grants access: passwords, connection strings with credentials, API keys, client secrets, signing keys, certificates' private keys, webhook signing secrets, tokens. Secrets are configuration with three extra requirements: confidentiality (only the workload that needs it can read it), auditability (you can tell who read or changed it) and rotatability (you can replace it without an outage). Plain files and environment variables give you none of those.

Never in source, and the .env trap

Once a secret is committed, assume it is public. Deleting it in a later commit does not remove it from history, forks, clones, CI caches or the bots that scrape public repositories within minutes of a push. The only fix is to revoke and rotate it.

Local development is where most leaks start, and the .env file is the usual suspect. It is a convenient way to set environment variables locally, but:

  • It gets committed. A missing .gitignore line, or a git add -A in a new repo. Commit a .env.example with names and dummy values instead, and put .env* (except the example) in .gitignore from day one.
  • It gets baked into images. COPY . . in a Dockerfile without a .dockerignore puts .env in a layer, and every layer of a pushed image is downloadable. Add .env to .dockerignore.
  • It gets bundled into front-ends. Variables prefixed NEXT_PUBLIC_, VITE_ or REACT_APP_ are inlined into the JavaScript sent to every browser. There is no such thing as a secret in a browser bundle.
  • It becomes the production mechanism. A .env on a VM, copied by hand, with no rotation, audit or access control, is a secret store in name only.

Environment variables in production are better than files in Git, but they still leak: they appear in docker inspect, in /proc/<pid>/environ, in crash reports and diagnostic dumps, in "print environment" debug pages, and they are inherited by every child process. Prefer fetching secrets from a store at startup (or mounting them as files from the store, which Kubernetes CSI secret drivers do), and better still, prefer an identity that needs no secret at all.

A secret store keeps secrets encrypted (backed by HSMs or a KMS), controls who can read each one, logs every access, and versions every change, which is what makes rotation possible. The big three have the same shape:

Two patterns from that table deserve a highlight. Key Vault references (App Service, Functions, Container Apps) let an app setting be @Microsoft.KeyVault(SecretUri=...): the platform resolves it with the app's identity, and the app sees an ordinary setting. Dynamic secrets (Vault, and IAM database authentication on AWS and Azure) issue a fresh, short-lived credential per workload, so there is nothing long-lived to leak or rotate.

Managed identity: no secret at all

To read from a secret store, the app must authenticate, and if it authenticates with a client secret, you have just moved the problem: now that secret is in configuration. The way out is identity provided by the platform. On Azure, a managed identity is an Entra ID identity attached to the VM, App Service, Function or container. The app asks a local endpoint on the host (IMDS) for a token, and the platform proves who it is. On Kubernetes, workload identity lets a pod exchange its service-account token (signed by the cluster's OIDC issuer) for a cloud token through federation. AWS does the same with IAM roles for EC2, ECS tasks and EKS pods (IRSA, Pod Identity); GCP with Workload Identity.

Step through the three modes below. In client-secret mode, count the places the secret exists and what happens when it expires. In the identity modes, notice that nothing long-lived is ever stored by the app: tokens last about an hour and are refreshed automatically.

Rotation without downtime

Every secret should be rotatable at any time: on a schedule, when someone leaves, and immediately after a leak. Rotation is hard because a secret has two sides (the issuer that checks it and the clients that present it) and many clients that cache it. If you replace the value in place, every client still holding the old value fails until its cache refreshes.

The fix is two valid credentials with an overlap window. Create key 2 while key 1 still works, let every client pick up key 2 through its normal refresh, verify that nobody is using key 1 any more, then revoke key 1. Step through both strategies below and change the cache refresh: with in-place replacement, the outage lasts as long as the slowest client's cache; with overlap, there is no outage as long as you revoke after every cache has refreshed.

Many systems support this natively: Azure Storage and Cosmos DB have primary and secondary keys, Entra ID app registrations allow several client secrets and certificates, AWS Secrets Manager's rotation moves AWSPENDING to AWSCURRENT while AWSPREVIOUS still works, and databases let a user have two passwords (MySQL 8 dual passwords) or let you alternate between two users. For secrets you verify, such as webhook signatures or API keys you issue, build the overlap yourself: accept a key ring of current and previous keys, and sign with the current one.

// Verify a webhook signature against every active key; sign only with the newest.
public sealed class WebhookVerifier(IOptionsMonitor<WebhookKeys> keys)
{
    public bool IsValid(ReadOnlySpan<byte> body, string signatureHex)
    {
        byte[] expected = Convert.FromHexString(signatureHex);
        foreach (string secret in keys.CurrentValue.Active)          // e.g. [key2, key1] during overlap
        {
            byte[] actual = HMACSHA256.HashData(Encoding.UTF8.GetBytes(secret), body);
            if (CryptographicOperations.FixedTimeEquals(actual, expected)) return true;
        }
        return false;
    }
}
// Record which key matched in a metric (key="1"/"2") so you know when key 1 can be revoked.

// Accept any active key, compare in constant time.
boolean isValid(byte[] body, String signatureHex, List<String> activeSecrets) throws Exception {
    byte[] expected = HexFormat.of().parseHex(signatureHex);
    for (String secret : activeSecrets) {                       // [key2, key1] during the overlap
        Mac mac = Mac.getInstance("HmacSHA256");
        mac.init(new SecretKeySpec(secret.getBytes(StandardCharsets.UTF_8), "HmacSHA256"));
        if (MessageDigest.isEqual(mac.doFinal(body), expected)) return true;
    }
    return false;
}

    if err != nil {
        return false
    }

        mac := hmac.New(sha256.New, []byte(secret))

        }
    }

import { createHmac, timingSafeEqual } from "node:crypto";

export function isValid(body: Buffer, signatureHex: string, activeSecrets: string[]): boolean {
  const expected = Buffer.from(signatureHex, "hex");
  return activeSecrets.some((secret) => {         // [key2, key1] during the overlap
    const actual = createHmac("sha256", secret).update(body).digest();
    return actual.length === expected.length && timingSafeEqual(actual, expected);
  });

Clients need their half of the bargain too: refresh secrets periodically (Key Vault provider ReloadInterval, Secrets Manager caching clients, Vault Agent templates) and, on an authentication failure, refresh once and retry once before failing. Never retry auth failures in a loop: a revoked credential will not start working, and you will lock the account or flood the issuer. Resilience covers which errors are worth retrying.

Secret scanning and push protection

People will paste secrets into code. Scanning catches them, ideally before they leave the laptop or reach the remote. Scanners combine two techniques: provider patterns (a GitHub token starts with ghp_ and has a checksum, an AWS access key id starts with AKIA, an Azure Storage connection string has AccountKey=) with almost no false positives, and entropy heuristics that flag long random-looking strings, which catch unknown formats at the cost of false alarms on hashes, ids and test fixtures. Tune the scanner below and watch the trade-off between missed secrets and false alarms. (The "secrets" in this visualizer are generated randomly when it runs.)

Where to scan, in order of how early it catches a leak:

Stage Tooling Catches
Editor and pre-commit hook gitleaks, detect-secrets, trufflehog as a pre-commit hook Before the secret is in any commit
Push protection GitHub push protection, GitLab secret push protection, Azure DevOps Advanced Security Blocks the push to the remote; requires an explicit, audited bypass
CI on every PR gitleaks or trufflehog in the pipeline Anything that slipped past hooks (hooks are optional on laptops)
Repository and history scanning GitHub secret scanning, partner programme Old commits; partners such as cloud providers are notified and may revoke keys automatically

When a secret leaks: revoke first, clean up second. Rewriting Git history (git filter-repo, BFG) does not un-publish anything: clones, forks, caches and scrapers already have it. The order is (1) revoke or rotate the credential immediately, (2) check the store's and the provider's audit logs for use since the leak, (3) then clean history if you want to stop future scanners alarming. A leaked secret you rotated in ten minutes is a non-event; one you "deleted from Git" is still live.

Pitfalls and war stories

The changed default. v42 changed Pricing:BatchLookups in the base file and Production had no override, so the default shipped straight to production and multiplied pricing calls. Fix: set business-critical values explicitly per environment, cover them in validation ("in Production, BatchLookups must be true unless the ops flag says otherwise"), and diff the effective configuration between releases in CI.

The silent no-op variable. PRICING_BATCHLOOKUPS=false with a single underscore, SPRING_PROFILE_ACTIVE without the S, DB__TIMEOUTSECOND. Each one is a valid variable that no provider reads, so the override appears to work in the manifest and does nothing. Fix: fail or warn at startup on prefixed variables that did not bind to a known key, and log the effective value of important keys.

Units in the wrong place. Timeout: 30 read as seconds by one library and milliseconds by another, or "30" interpreted as 30 ticks. Fix: use duration types (TimeSpan, Duration, time.Duration, "30s"), or put the unit in the key name, and range-check it.

Config pushed to the whole fleet at once. Several widely reported cloud and CDN outages started with a configuration or rules file that was valid enough to deploy and bad enough to crash every instance that loaded it, everywhere, within minutes. Fix: treat configuration like code: validation in CI, staged rollout by ring or region, automatic rollback on health regression, and a last-known-good fallback in the reader.

The reused flag. A flag name that once meant one thing was repurposed for another, and a server running old code read it with the old meaning. Fix: never reuse a flag key; archive it and create a new one. Delete the code behind a flag in the same PR as the flag.

The flag service as a single point of failure. Every request evaluates flags remotely, the flag service slows down, and so does everything. Fix: SDKs that evaluate locally from a cached rule set, sensible defaults in code, and a startup that does not block forever waiting for the flag service.

The secret that expired on a Saturday. A client secret or certificate created with a two-year lifetime, by someone who has since left, expires and takes production down. Fix: prefer identities that need no secret; otherwise, alert on expiry (Key Vault near-expiry events, certificate monitors) at 30 and 7 days, and practice rotation so it is routine.

The secret in the image. COPY . . picked up .env and appsettings.Development.json with a real connection string, and the image was pushed to a registry that more people can pull than can read the vault. Fix: .dockerignore, multi-stage builds that copy only build outputs, and image scanning for secrets in CI.

Checklist

  • [ ] One artifact is promoted through every environment; nothing environment-specific is baked into it.
  • [ ] The precedence of configuration sources is documented, and the effective value plus its source can be inspected (redacted) at runtime.
  • [ ] Settings are bound to typed, immutable objects; only the composition root reads the configuration system.
  • [ ] Required values, types, units, ranges and cross-field rules are validated at startup; a failure exits non-zero and the rollout waits for readiness.
  • [ ] Business-critical values are set explicitly in the production layer, not inherited from defaults.
  • [ ] Only operational settings hot-reload; reloads validate a candidate, keep the last good value and swap atomically.
  • [ ] Every flag has a kind, owner, safe default and (for release and experiment flags) an expiry; stale flags are reported; flag keys are never reused.
  • [ ] Rollouts are sticky (hash of flag key and user id), carry the variant on telemetry and have an automatic guard.
  • [ ] No secret is in source, images, front-end bundles, logs or CI output; .env is git-ignored and docker-ignored.
  • [ ] Workloads authenticate with managed identity, workload identity or IAM roles; each has least-privilege access to only its own secrets.
  • [ ] Every secret can be rotated without downtime (two keys or two users, an overlap window, clients that refresh), and rotation has been practised.
  • [ ] Pre-commit scanning, push protection and CI scanning are on; the leak runbook says "revoke first".

Quiz

Production sets Pricing__TimeoutMs=1500 as an environment variable, and appsettings.Production.json sets "Pricing": { "TimeoutMs": 900 }. The app runs with --Pricing:TimeoutMs=600. What is the effective value in ASP.NET Core's default setup, and what is Pricing:Retries if only appsettings.json sets it?
  1. The default order is appsettings.json → appsettings.Production.json → environment variables → command line, and the last provider that defines a key wins: 900 is overridden by 1500, which is overridden by 600. Pricing:Retries comes from appsettings.json, because no higher layer mentions it. Precedence is decided key by key, not file by file.
A team sets PRICING_BATCHLOOKUPS=false on a .NET service to turn batching off during an incident. Nothing changes. Why, and how should they have noticed?

.NET maps __ (double underscore) to the : separator, so the variable must be Pricing__BatchLookups (case-insensitive). PRICING_BATCHLOOKUPS is a flat key that nothing binds. They would notice by checking the effective value (GetDebugView(), an admin endpoint or a startup log line), or with a startup warning for prefixed variables that did not bind to any known key.

Lazy validation and validation on start both report the same error eventually. Why does the timing matter so much in a rolling deployment?

With validation on start, the first new pod exits or never becomes ready, so the rollout stops and the old version keeps serving all traffic: no customer sees the error. With lazy validation, the new pods pass their health checks, the rollout continues, the old pods are removed, and the error appears only when real requests reach the code that reads the value. By then every instance has the bad config and the fix is a rollback under pressure.

An endpoint URL and its API key are stored as two keys in a configuration service and updated one after the other. Some requests get 401s for a few seconds after each change, even though the code uses IOptionsSnapshot. Why, and what is the fix?

IOptionsSnapshot makes each request consistent with itself, but a request that starts between the two writes snapshots the new URL with the old key. The fix is to make the pair change atomically: store them as one value (or with a sentinel key that triggers a single refresh, as Azure App Configuration supports), validate the candidate as a pair, and swap one immutable reference, keeping the last good value if the candidate is inconsistent.

Why hash flag-key + ":" + userId for a percentage rollout instead of just userId or a random number per request?

A random number per request makes users flicker between old and new behaviour, which breaks sessions and makes bugs impossible to reproduce. Hashing only userId is sticky, but it puts the same users in the lowest buckets for every flag, so the same 1% of customers absorb the risk of every rollout and every experiment is correlated. Including the flag key gives each flag an independent, stable assignment.

Your app reads a database password from Key Vault using a client secret stored in an environment variable. What did you gain, and what would be better?

You gained a central place for the database password (audit, versioning, one place to rotate it). But the client secret is now the real key to everything, and it lives in an environment variable with all the old problems, plus it expires. Better: a managed identity or workload identity to reach Key Vault (no secret at all), and ideally Entra or IAM authentication to the database itself, so there is no database password either.

Clients cache an API key for up to 15 minutes. You create key 2 and revoke key 1 five minutes later. What happens, and what is the minimum safe overlap?

Clients whose cache has not refreshed yet still send key 1 and get rejected, for up to ten more minutes. The overlap must be at least the longest client refresh interval (15 minutes here) plus margin for clock skew and slow pods, and you should confirm with metrics (which key each request used) that key 1 traffic has dropped to zero before revoking it.

A developer accidentally pushed an AWS access key to a public repository and immediately force-pushed a commit that removes it. Is the incident over?

No. Public pushes are scraped within minutes, and forks, clones and caches keep the old commit. The key must be treated as compromised: deactivate and delete it now, issue a new one (better, switch to a role so there is no long-lived key), and review CloudTrail for any use since the push. Cleaning history comes last and only reduces future noise.
