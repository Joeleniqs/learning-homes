Data Access Patterns

ORMs vs micro-ORMs vs SQL, N+1 made visible, transactions and isolation levels animated, connection pooling, and optimistic concurrency.

Intermediate → Advanced~60 min studyBuilds on: Cross-Language Mental ModelsUpdated 2026-11-03

The problem: one innocent endpoint, six production bugs

Here is an endpoint that passes code review in most teams. It lists a customer's orders, it's short, it uses the ORM "properly", and it works perfectly on a laptop with 20 rows.

// GET /customers/{id}/orders?page=3
app.MapGet("/customers/{id:int}/orders", async (int id, int page, ShopDb db) =>
{
    var orders = await db.Orders                                  // (1) tracked entities
        .Where(o => o.CustomerId == id)
        .OrderByDescending(o => o.CreatedAt)
        .Skip((page - 1) * 50).Take(50)                           // (2) OFFSET paging
        .ToListAsync();

    foreach (var o in orders)
        o.Total = o.Lines.Sum(l => l.Qty * l.UnitPrice);          // (3) lazy load: 1 query per order

    return Results.Ok(orders);                                    // (4) entity → JSON: Customer, Lines,
});                                                               //     Payments... and a cycle

In production, with 40 million orders, the same code produces these symptoms:

# What you see in production The cause Section
1 p99 latency is 4 s; the database CPU is at 90% Lines loads lazily: 1 + 50 queries per request, an N+1 Loading related data
2 Page 2,000 takes 9 s; users see duplicates when paging OFFSET 99950 reads and discards 99,950 rows; new orders shift the pages Pagination
3 The query does a full scan of orders there's no index on (customer_id, created_at) Indexes
4 Responses are 2 MB and leak internal columns; occasionally the serializer loops it returns entities, not a projection Projections
5 Under load: Timeout expired. The timeout period elapsed prior to obtaining a connection from the pool each request holds a connection for 51 round trips Connection pooling
6 Two admins edit the same order, and one edit silently disappears no concurrency token Optimistic vs pessimistic

None of these is an ORM bug, and none is fixed by "writing raw SQL instead". Each one comes from not knowing what the code makes the database do. This page teaches you to see that: the round trips, the rows read, the locks held, the connections borrowed. With that model, the choice of tool (Dapper or EF Core, jOOQ or Hibernate, sqlc or GORM) becomes a trade-off rather than a religion.

The rule of data access

Know, for every request, how many round trips it makes, how many rows the database touches to answer it, and how long it holds a connection, a transaction and its locks. Every tool on this page is a way to change one of those four numbers. If you can't state them, turn on SQL logging and look before you optimise anything.

The prerequisite is the runtime picture from language mental models (references, allocation, async). The async I/O part builds on concurrency and async, and the caching you put in front of a database is covered in caching.

The mental model: every query crosses six boundaries

A line like db.Orders.Where(...).ToListAsync() looks like a method call on a collection. It's actually a journey through six layers, and each layer has its own cost and its own failure mode.

Why round trips dominate

An index seek on a warm table takes tens of microseconds inside the database. A round trip inside one data centre takes 0.2 to 1 ms, and across availability zones 1 to 2 ms. So one query that returns 50 rows is usually faster than 50 queries that return one row each, even though they do the "same work". That one fact explains why N+1 hurts, why batching helps, and why chatty repository methods are slow. You'll see it measured in the batching visualizer.

Raw SQL vs micro-ORM vs full ORM

Every ecosystem offers the same three rungs. They differ in who writes the SQL and who tracks changes.

The real differences, and the ones to weigh when choosing:

Raw driver Micro-ORM / typed SQL Full ORM
Who writes SQL you you (or a typed builder) the ORM, from LINQ / JPQL / criteria / method calls
Mapping rows → objects by hand automatic automatic, including relations
Change tracking + unit of work none none yes (EF Core, Hibernate, SQLAlchemy ORM, TypeORM; not Prisma or GORM)
Schema migrations separate tool separate tool (Drizzle Kit is the exception) usually built in
Hidden queries none none lazy loading, cascades, flush order: watch the log
Performance ceiling highest about the same as raw close for simple reads; tracking and graph materialisation cost CPU and memory
Refactoring safety strings: rename breaks at runtime typed builders and sqlc check at compile time checked at compile time
Best at hot paths, bulk work, exotic SQL read models, reporting, services that think in SQL rich domain writes: load an aggregate, change it, save

The pragmatic default: use both

Most mature codebases use a full ORM for the write side (load an aggregate, apply business rules, save; change tracking and optimistic concurrency come for free) and a micro-ORM or projection query for the read side (screens, lists, reports, exports), where you want exactly the columns you need and no tracking. That split is CQRS in its simplest form, and it doesn't need two databases. See application architecture and domain-driven design.

The same query, SQL-first, in five stacks

The task: a customer's 20 most recent paid orders, with the order total. Notice how similar these are: the SQL is the contract, and the library only binds parameters and maps columns.

Now the ORM version. You write queries against entities and navigation properties, and the ORM generates SQL. Look at the comment on each one: it's the SQL you should expect to see in the log.

How the ecosystems differ, and why:

  • .NET has LINQ in the language, so EF Core can translate ordinary C# expressions into SQL. That's uniquely powerful, and it's also why "this LINQ can't be translated" exceptions exist. Dapper is the near-universal escape hatch, and the two share one DbConnection.
  • Java has no language-integrated query, so JPA invented JPQL (strings) and the Criteria API (verbose). jOOQ fills the "typed SQL" gap with generated classes. Hibernate is the JPA implementation behind Spring Data.
  • Python's SQLAlchemy is unusual: Core and ORM are one library, and you can mix them in a single session. Django's ORM is the other giant, active-record style.
  • Go culture distrusts magic: database/sql plus sqlc (SQL-first codegen) is the mainstream; GORM and ent exist but many teams avoid reflection-heavy ORMs on hot paths.
  • TypeScript splits into codegen (Prisma, generating a client from schema.prisma) and type inference (Drizzle and Kysely, which compute result types from your query with no build step).

Choosing a rung

  • Full ORM when the service is mostly CRUD over a rich model, writes go through aggregates with invariants, and the team will actually read the SQL log.
  • Micro-ORM / typed SQL for read-heavy services, reporting, complex SQL (window functions, CTEs, LATERAL), and teams fluent in SQL.
  • Raw driver for bulk loads (COPY, SqlBulkCopy), streaming huge result sets, and the few hottest queries after profiling.
  • Never because of a benchmark of the mapper alone: the database and the round trips dominate, as the mental model shows.

Connection pooling: borrow, return, wait

Opening a database connection is expensive: a TCP handshake, a TLS handshake, authentication, and on PostgreSQL a whole new server process (several MB of RAM). That's 5 to 50 ms, more than most queries. So every driver keeps a pool: a small set of open connections that requests borrow and give back.

Run the pool yourself. Requests arrive at different times and hold their connection for different lengths of time. Watch which ones reuse an idle connection (cheap), which pay to open one, which wait, and which time out. Then set "request that forgets Dispose" to a request number and watch a leak slowly kill the pool.

Three things the visualizer makes obvious:

  1. Pool exhaustion is a latency problem before it's an error. Requests wait long before they time out, so the first symptom is p99 latency, not exceptions.
  2. Hold time, not request count, is what matters. A request that holds a connection across a slow HTTP call, or across 51 lazy loads, occupies a slot for the whole time. Fix the hold time and the same pool serves several times more traffic.
  3. A leak is permanent. A connection that's never returned is gone until the process restarts. A few leaks per hour turn into an outage overnight.

Sizing: smaller than you think

It's tempting to set Max Pool Size=1000. Don't. The database has a fixed number of CPU cores and disks; past a point, more concurrent queries just context-switch and fight over locks and memory. A widely used starting formula (from the PostgreSQL wiki, popularised by HikariCP) is:

connections per database ≈ (CPU cores × 2) + effective spindles      e.g. 8 cores, SSD → about 17–20 in total
total across the fleet  = pool max × app instances                   10 pods × 100 = 1,000 → Postgres falls over

The second line is the one that bites. Pools are per process, so autoscaling to 40 pods multiplies your connection count by 40. PostgreSQL's max_connections defaults to 100. When the sum exceeds what the database can take, put a server-side pooler in between: PgBouncer (transaction pooling), RDS Proxy, Azure's built-in PgBouncer, or the pooler in Supabase/Neon. Serverless functions almost always need one, because every cold start creates a new pool.

Pool pitfalls

  • Sync-over-async. In .NET, .Result and .Wait() on async database calls block thread-pool threads; under load the pool and the thread pool starve together. Go async all the way, as in concurrency and async.
  • One pool per request. Creating an Engine, sql.DB, HikariDataSource, Pool or PrismaClient per request or per function call opens fresh connections every time. Make it a singleton.
  • Holding a connection across remote calls. Calling a payment API inside a transaction holds a connection and locks for the length of that call. Do remote calls before or after; see outbound pipelines and resilience.
  • Different connection strings per tenant. ADO.NET keys pools by exact connection string; 500 tenants means 500 pools. Use one pool and set the tenant per session, or use a pooler.

Transactions and isolation levels

A transaction groups statements so they succeed or fail together (atomicity), move the database from one valid state to another (consistency), survive crashes once committed (durability), and don't see each other's half-finished work (isolation). The first three are mostly free. Isolation is a dial, and its default setting surprises nearly everyone.

Full isolation ("as if transactions ran one after another", called serializable) costs throughput, so databases default to weaker levels that allow specific anomalies. Here they are, as two interleaved transactions:

Dirty read possible prevented prevented prevented prevented

Lost update (read-modify-write) possible possible aborted: retry aborted: retry aborted: retry

What the major databases actually default to:

Database Default Notes
PostgreSQL READ COMMITTED REPEATABLE READ is snapshot isolation; SERIALIZABLE is SSI (aborts with SQLSTATE 40001)
SQL Server READ COMMITTED (locking) turn on READ_COMMITTED_SNAPSHOT so readers don't block writers; SNAPSHOT must be enabled per database
Azure SQL Database READ COMMITTED snapshot RCSI is on by default
MySQL InnoDB REPEATABLE READ consistent snapshot for reads, but UPDATE and locking reads see the latest committed row
Oracle READ COMMITTED its SERIALIZABLE is snapshot isolation

READ COMMITTED does not protect read-modify-write

SELECT stock then UPDATE … SET stock = @newValue in the default level loses updates under concurrency. Fix it with one of: an atomic update (SET stock = stock - 1 WHERE stock >= 1), an optimistic version check, a pessimistic SELECT … FOR UPDATE, or a higher isolation level plus a retry loop. Raising the level without the retry loop just turns lost updates into errors.

{

// SQL Server serialization failures surface as deadlocks (1205), which SqlServerRetryingExecutionStrategy retries.

// Spring: declarative transactions. The method runs in one transaction; an exception rolls it back.
@Transactional(isolation = Isolation.SERIALIZABLE)
@Retryable(retryFor = ConcurrencyFailureException.class,  // spring-retry; Spring maps 40001 and deadlocks to subclasses

public void goOffCall(long doctorId, long shiftId) {
    long onCall = doctors.countByShiftIdAndOnCallTrue(shiftId);
    if (onCall < 2) throw new DomainException("At least one doctor must stay on call.");

}
// Pitfall: @Transactional works through a proxy. Calling this method from the same class bypasses the proxy:
// no transaction, no retry. The retry must wrap the transaction (retry outside, transaction inside).

# SQLAlchemy: session.begin() commits on success and rolls back on exception.
from sqlalchemy import func, select
from sqlalchemy.exc import OperationalError

def go_off_call(Session, doctor_id: int, shift_id: int, attempts: int = 3) -> None:
    for attempt in range(attempts):
        try:
            with Session() as s, s.begin():
                s.connection(execution_options={"isolation_level": "SERIALIZABLE"})
                on_call = s.scalar(select(func.count()).select_from(Doctor)
                                   .where(Doctor.shift_id == shift_id, Doctor.on_call))
                if on_call < 2:
                    raise ValueError("At least one doctor must stay on call.")
                s.get(Doctor, doctor_id).on_call = False
            return
        except OperationalError as e:            # psycopg raises SerializationFailure (SQLSTATE 40001)
            if getattr(e.orig, "sqlstate", None) != "40001" or attempt == attempts - 1:
                raise

// pgx: BeginTx with options. pgx.BeginTxFunc commits if fn returns nil and rolls back otherwise.
func GoOffCall(ctx context.Context, pool *pgxpool.Pool, doctorID, shiftID int64) error {
    for attempt := 0; ; attempt++ {
        err := pgx.BeginTxFunc(ctx, pool, pgx.TxOptions{IsoLevel: pgx.Serializable}, func(tx pgx.Tx) error {
            var onCall int
            if err := tx.QueryRow(ctx,
                `SELECT count(*) FROM doctors WHERE shift_id = $1 AND on_call`, shiftID).Scan(&onCall); err != nil {
                return err
            }
            if onCall < 2 {
                return ErrLastDoctor
            }
            _, err := tx.Exec(ctx, `UPDATE doctors SET on_call = false WHERE id = $1`, doctorID)
            return err
        })
        var pgErr *pgconn.PgError
        if errors.As(err, &pgErr) && pgErr.Code == "40001" && attempt < 2 {
            continue // serialization failure: run the whole transaction again
        }
        return err
    }
}

Keep transactions short

A transaction holds locks (or, under MVCC, holds back cleanup of old row versions) for as long as it's open. Never wait for user input, an HTTP call or a message broker inside one. Read what you need, compute, then open the transaction for the writes only. When the work genuinely spans services, a database transaction is the wrong tool: use the outbox and sagas from distributed architecture.

Optimistic vs pessimistic concurrency

The most common concurrency bug in business software isn't a race between two threads in one process. It's two people. Alice opens order 42 at 10:00, Bob opens it at 10:01, Bob saves at 10:03, Alice saves at 10:05, and Bob's change is gone. No isolation level helps, because the edits happen in separate HTTP requests and separate transactions, minutes apart.

There are two families of fixes:

  • Optimistic concurrency: assume conflicts are rare. Every row carries a version (a counter, a timestamp or SQL Server's rowversion). The update says UPDATE … WHERE id = 42 AND version = 7. If someone else saved first, the version is now 8, zero rows match, and the second writer gets a conflict to resolve. No locks are held while people think.
  • Pessimistic concurrency: assume conflicts are likely. Lock the row when you read it (SELECT … FOR UPDATE, or WITH (UPDLOCK, ROWLOCK) on SQL Server) so others wait. This works only within one transaction, so it fits short server-side operations, not human edits.

Run the three strategies on the same timeline:

Optimistic (version check)

  • No locks held between read and write: scales well, nothing to deadlock.
  • Works across HTTP requests: send the version to the client as an ETag and require If-Match on PUT/PATCH. A mismatch is 412 Precondition Failed. See ETags and conditional requests.
  • The loser must re-read and retry or merge. Good when conflicts are rare.

Pessimistic (row lock)

  • The second writer waits instead of failing, so no work is thrown away.
  • Lock only inside one short transaction. Holding a lock across user think time blocks everyone.
  • Risk of deadlocks (lock rows in a consistent order) and lock waits (set lock_timeout or use NOWAIT / SKIP LOCKED).
  • Good for hot rows under heavy contention: counters, seat allocation, job queues (FOR UPDATE SKIP LOCKED).

Change tracking and the unit of work

A full ORM's signature feature is that you don't write UPDATE statements. You load objects, change their properties, and call SaveChanges() / commit() / flush(). The ORM works out what changed and writes it, in one transaction. Three mechanisms make that work:

Type operations and watch what the context does: which find hits the database and which is served from the identity map, how each set changes an entity's state, and what SQL comes out of save. Switch to AsNoTracking to see why setting a property on an untracked object writes nothing.

Things to take from it:

  • set writes nothing. The UPDATE happens at save, and only for columns that changed. Setting a property to its current value produces no SQL.
  • Order matters. The ORM sorts statements by foreign-key dependencies, not by the order you made changes.
  • No tracking, no save. Objects from AsNoTracking(), a projection or a different context are just objects. To update them you Attach/Update (EF), merge (JPA) or session.merge (SQLAlchemy). Update marks every column modified, which overwrites concurrent changes to columns you never touched.
  • The context is a cache with a lifetime. A long-lived context grows without bound and serves stale data. Make it per request (scoped), per unit of work, never a singleton.

Unit-of-work pitfalls

  • A singleton DbContext / EntityManager / Session. Not thread-safe, grows forever, and serves stale data. In EF Core you'll see "A second operation was started on this context instance before a previous operation completed".
  • Tracking queries for read-only screens. Loading 10,000 tracked rows to render a grid allocates snapshots and runs change detection for nothing. Use no-tracking or projections, and see memory and GC for why those allocations hurt.
  • SaveChanges in a loop. One transaction and one round trip per item. Make the changes, then save once (or in chunks for huge sets).
  • Calling Update(entity) on a DTO-built object. It overwrites every column, including ones other users changed. Load, apply the DTO's changed fields, save; or use a concurrency token.

Make lazy loading impossible on the request path

Lazy loading is convenient in a console app and dangerous in a web API: it fires queries from a foreach, from a serializer, from a view, anywhere a navigation property is touched. Turn it off (EF Core: don't install the proxies; SQLAlchemy: raiseload; Hibernate: spring.jpa.open-in-view=false so it throws outside the transaction instead of silently querying), load deliberately with eager loading or projections, and log or count SQL statements per request in tests.

Projections: don't return entities from APIs

The bug list at the top of the page had "returns entities" as item 4. Returning an entity directly from an endpoint (return Ok(order)) couples four things that should be independent, and each coupling eventually breaks something:

Returning the entity

  • The schema becomes the API. Renaming a column breaks mobile clients; adding PasswordHash or InternalNotes leaks it.
  • The serializer walks the graph. It touches navigation properties: lazy loads fire (N+1 in the serializer), or Order.Customer.Orders[0].Customer... loops.
  • You read every column. SELECT * including the 40 KB notes column the screen doesn't show.
  • Mass assignment on the way in. Binding a request body to an entity lets a client set IsAdmin or Price. See API security.
  • Entities are tracked: extra memory for objects that are serialized and dropped.

Projecting to a DTO / read model

  • The response contract is a deliberate type, versioned with the API (API design).
  • The query asks for exactly those columns, so it can be served by a covering index (see below).
  • No tracking, no proxies, no cycles, no lazy loads.
  • Input DTOs list exactly the fields a client may set.
  • The mapping is in one visible place, instead of hidden in serializer settings.

Pagination: offset vs keyset

OFFSET is how everyone starts: ORDER BY created_at DESC OFFSET 100000 LIMIT 50. It has two problems that grow with the data. The database can't jump to row 100,000; it reads and discards 100,000 rows to find the start. And if a row is inserted while someone is paging, everything shifts by one, so they see a duplicate, or a deletion makes them skip a row.

Keyset pagination (also called seek or cursor pagination) remembers where the last page ended and asks for "the next 50 after this one": WHERE (created_at, id) < (@lastCreatedAt, @lastId) ORDER BY created_at DESC, id DESC LIMIT 50. With an index on (created_at, id) that's a seek straight to the right spot, the same cost for page 1 as for page 20,000, and insertions don't shift anything.

Page through a table both ways. Set "new rows inserted after page 1" to see the duplicates offset produces, and raise the page count to see rows-read grow for offset while keyset stays flat.

Rules for keyset pagination that actually work:

  • The sort must be unique. ORDER BY created_at alone ties when two rows share a timestamp, and rows at the page boundary get skipped. Add the primary key as the last sort column, and compare as a row value: (created_at, id) < (@c, @i). SQL Server lacks row-value comparison, so expand it: created_at < @c OR (created_at = @c AND id < @i).
  • Index the sort exactly. CREATE INDEX ON orders (customer_id, created_at DESC, id DESC) for WHERE customer_id = @x ORDER BY created_at DESC, id DESC.
  • Make the cursor opaque. Base64-encode {createdAt, id} (and sign it if clients mustn't forge it). The API contract is "pass back next", per API design pagination.
  • Offset is fine for small tables, admin screens and the first few pages of search results. Total counts (COUNT(*)) are expensive on big tables too: show "more" instead of "page 1 of 8,412", or estimate.

Indexes: how the database finds rows

Without an index, finding WHERE email = 'ada@x.io' means reading every row of the table: a scan. With an index it's a seek: a handful of page reads, however big the table. Almost every relational database (and MongoDB, and most others) uses the same structure for its default index: the B+tree.

Build one and query it. Compare the pages a seek touches with a full scan, then try a range (lo-hi) and watch the walk along the linked leaves.

Try WHERE customer_id = 4 ORDER BY created_at DESC LIMIT 2 with (customer_id) and then with (customer_id, created_at): the second one needs no sort and stops after two entries.

The rules that fall out of it:

  1. Leftmost prefix. A composite index helps only queries that constrain its first column (and then the next, and so on). The order of columns in the index matters; the order in your WHERE clause doesn't.
  2. Equality first, range last. In (customer_id, created_at), customer_id = 4 AND created_at > X is one contiguous range. In (created_at, customer_id) the same query reads every customer's rows in the date range and filters.
  3. The index can deliver the order. If the index order matches ORDER BY, the database reads entries in order and stops at LIMIT. No sort, no reading everything first. This is what makes keyset pagination fast.
  4. Covering indexes skip the table. If every column the query needs is in the index, there's no lookup per row. SQL Server and PostgreSQL 11+ let you add non-key columns with INCLUDE (status, total): they ride along in the leaves without affecting the sort.
  5. Selectivity matters. An index on is_deleted (99% false) is rarely useful by itself; a seek that matches 30% of the table plus a lookup per row is slower than a scan, and the planner knows it. Partial (filtered) indexes help here: CREATE INDEX … WHERE status = 'pending'.

Queries that can't use the index you have (not "sargable")

  • A function on the column: WHERE YEAR(created_at) = 2025 or WHERE lower(email) = @e. Rewrite as a range (created_at >= '2025-01-01' AND created_at < '2026-01-01'), or index the expression (CREATE INDEX ON users (lower(email))).
  • A leading wildcard: LIKE '%smith'. Use full-text search or a trigram index (pg_trgm).
  • An implicit conversion: comparing an nvarchar parameter to a varchar column in SQL Server converts every row. Match parameter types to column types (EF Core: HasColumnType/IsUnicode(false); JDBC: sendStringParametersAsUnicode=false).
  • OR across different columns: often becomes a scan; a UNION ALL of two seeks can be far faster.
  • Too many indexes. Each one is updated on every INSERT, on UPDATE of its columns, and on DELETE. Five unused indexes can halve write throughput. Check pg_stat_user_indexes or sys.dm_db_index_usage_stats for indexes that are never read.

Migrations: changing the schema without downtime

Schema changes are code changes, so they live in version control and run in order: migrations. Every ecosystem has a tool: EF Core Migrations, Flyway or Liquibase (Java), Alembic (Python), golang-migrate, Atlas or goose (Go), and Prisma Migrate or Drizzle Kit (TypeScript). The hard part isn't the tool. It's that during a rolling deploy, old and new versions of your app run at the same time against one database, so every schema change must work with both.

Run a rolling deploy with 2 to 4 instances and pick a strategy. The visualizer tracks the schema, which instance runs which version, and which requests fail or write data that's lost.

Migration pitfalls

  • Migrating on startup. Ten pods starting at once race to apply the same migration, and a slow migration fails health checks. Run migrations as a separate deploy step (a job, an init container or a pipeline stage), once.
  • Locks you didn't expect. ALTER TABLE takes an exclusive lock; if a long-running query holds a conflicting lock, the ALTER waits, and every new query queues behind the ALTER. Set lock_timeout (e.g. 5 s) and retry, rather than taking the site down.
  • Auto-generated destructive diffs. ORMs sometimes generate drop-and-recreate for a rename. Review every generated migration as you'd review code.
  • Down migrations that can't work. Once data is written to the new shape, "down" usually loses it. Prefer roll-forward fixes, and keep every step backward-compatible so the app can roll back without touching the schema.

The repository pattern debate

"Should I wrap my ORM in repositories?" starts more arguments than any other data-access question. Both sides are right about something, so it's worth being precise.

A repository (from Domain-Driven Design) is a collection-like interface for aggregates: orders.Get(id), orders.Add(order). It hides how persistence works, so the domain model doesn't depend on the database. A generic repository is IRepository<T> with GetAll(), GetById(), Add(), Update(), Delete() for every table.

When a repository helps

  • The domain is rich and you want aggregates to be loaded and saved whole, with their invariants. IOrderRepository.GetWithLinesAsync(id) states exactly what an order needs. See domain-driven design.
  • The persistence is genuinely swappable or awkward: several stores, a legacy stored-procedure API, a document store behind the same interface.
  • Raw drivers or micro-ORMs (Dapper, JDBC, database/sql): you need somewhere to put the SQL, and a repository per aggregate is a good place.
  • Named queries: GetOverdueInvoices(asOf) reads better than a LINQ chain repeated in five handlers.

When it's a pointless wrapper

  • A generic IRepository<T> over EF Core. DbSet<T> already is a repository and DbContext already is a unit of work. The wrapper adds code and removes features: no Include, no projections, no AsNoTracking, no ExecuteUpdate.
  • IQueryable<T> GetAll() leaks the ORM through the abstraction anyway, so you get the cost of the wrapper and none of the isolation.
  • "So we can switch databases." You won't, and if you do, the SQL dialect, transactions and performance profile all change regardless of the interface.
  • "For unit testing." Mocking a repository tests your mocks. Test queries against a real database (Testcontainers) and mock at a higher level.
// The generic repository: every method is a one-line pass-through, and the useful features are gone.
public class Repository<T>(ShopDb db) : IRepository<T> where T : class
{
    public Task<T?> GetByIdAsync(long id) => db.Set<T>().FindAsync(id).AsTask();
    public Task<List<T>> GetAllAsync() => db.Set<T>().ToListAsync();            // loads the whole table
    public void Add(T entity) => db.Set<T>().Add(entity);
    public Task SaveAsync() => db.SaveChangesAsync();                            // each repo saves: no shared UoW
}
// Callers end up writing: (await repo.GetAllAsync()).Where(o => o.CustomerId == id)   ← filters in memory

}

The same split holds in other languages. Spring Data's JpaRepository is a generated repository, so don't wrap it again; add query methods to it or write a custom fragment. In SQLAlchemy, the Session is the unit of work and a thin repository per aggregate is common in "clean architecture" codebases. In Go, a Store struct with methods wrapping sqlc queries is idiomatic. In TypeScript, Prisma's client is already a typed data mapper; wrap it only to name aggregate operations. The structural ideas behind wrapping (adapter, facade) are in structural patterns, and where the boundary goes is in application architecture.

The test for any data-access abstraction

Does it add a name (intent), an invariant (always load the aggregate whole) or isolation you actually use? Then keep it. Is it a pass-through that hides features of the tool underneath? Delete it, and inject the DbContext / EntityManager / Session / *sql.DB / PrismaClient directly.

Batching, bulk operations, compiled queries and async I/O

Inserting 10,000 rows is where the "round trips dominate" rule is most visible. Here are the four ways to do it, all writing the same rows:

The model behind the bars: every statement pays a round trip, every commit pays a log flush (an fsync, about 1 ms on many disks), and every row pays a small server cost that no technique avoids. One-at-a-time with autocommit pays all three per row. One transaction removes the per-row commits. Batching removes most round trips. Bulk copy (COPY, SqlBulkCopy) also skips per-statement parsing, which is why it's 10–100× faster again for big loads.

db.Products.AddRange(rows);
await db.SaveChangesAsync(ct);                       // one transaction, few round trips

// Set-based: one statement, no entities loaded (EF Core 7+).
await db.Products.Where(p => p.CategoryId == 3).ExecuteDeleteAsync(ct);

// Bulk load into SQL Server: the TDS bulk protocol.
using var bulk = new SqlBulkCopy(connection) { DestinationTableName = "products", BatchSize = 5_000 };
await bulk.WriteToServerAsync(dataTable, ct);
// PostgreSQL: Npgsql's BeginBinaryImportAsync("COPY products (name, price) FROM STDIN (FORMAT BINARY)")

// JDBC batching: one round trip per executeBatch(). For MySQL add rewriteBatchedStatements=true;
// for PostgreSQL, reWriteBatchedInserts=true turns them into multi-row INSERTs.
try (Connection c = ds.getConnection();
     PreparedStatement ps = c.prepareStatement("INSERT INTO products (name, price) VALUES (?, ?)")) {

    int n = 0;

        ps.setString(1, p.name());
        ps.setBigDecimal(2, p.price());
        ps.addBatch();
        if (++n % 1_000 == 0) ps.executeBatch();

    ps.executeBatch();
    c.commit();
}

Compiled queries and prepared statements

Before a query runs, two translations happen: the ORM turns your expression into SQL, and the database turns SQL into a plan. Both are cached, and both caches can be defeated.

  • Database plan cache. Parameterized SQL (WHERE id = @id) is one cache entry reused for every id. SQL built by concatenation (WHERE id = 42, WHERE id = 43, …) is a new statement each time: a parse and plan per call, a polluted cache, and SQL injection (below). Drivers can also use server-side prepared statements: Npgsql auto-prepares with Max Auto Prepare, pgx prepares by default, and JDBC prepares after prepareThreshold executions.
  • ORM query cache. EF Core caches the translation of each LINQ shape. Shapes that vary (an IN list with a different number of items, dynamically built expressions) produce new entries. For a hot query, EF.CompileAsyncQuery skips the cache lookup entirely:
private static readonly Func<ShopDb, long, IAsyncEnumerable<OrderSummary>> RecentOrders =
    EF.CompileAsyncQuery((ShopDb db, long customerId) =>
        db.Orders.Where(o => o.CustomerId == customerId)
                 .OrderByDescending(o => o.CreatedAt)
                 .Take(20)
                 .Select(o => new OrderSummary(o.Id, o.CreatedAt, o.Status, o.Total)));

await foreach (var row in RecentOrders(db, customerId)) { /* ... */ }

Measure before you reach for compiled queries: they typically save tens of microseconds per call, which matters at thousands of calls per second and not at all for a query that waits 5 ms on I/O. That's a recurring theme in performance patterns.

Async I/O

A database call spends nearly all its time waiting for the network and the disk. With synchronous I/O, the calling thread sits blocked for that time. With async I/O, the thread goes back to the pool and serves other requests, so a server handles many more concurrent requests with the same threads. How each runtime does it, and the traps (sync-over-async, async void, unbounded fan-out), are in concurrency and async. For data access specifically:

  • Use the async API end to end: ToListAsync/SaveChangesAsync, asyncpg or SQLAlchemy's AsyncSession, pgx (Go's goroutines make blocking calls cheap anyway), Prisma (always async). In Java, JDBC is blocking; virtual threads (Java 21+) make that cheap without rewriting to R2DBC.
  • Pass cancellation through: CancellationToken, context.Context, AbortSignal. When the client disconnects or the deadline passes, the query should be cancelled, not finish for nobody.
  • One context, one operation at a time. A DbContext, a SQLAlchemy AsyncSession and a single connection can't run two queries concurrently. To run queries in parallel, use separate contexts and connections, and remember each one borrows from the pool.
  • Async doesn't make a query faster. It makes waiting cheaper. A slow query is still slow; fix it with the index section above.

Read replicas and replication lag

When reads outgrow one server, the usual next step is read replicas: copies of the primary that receive its changes through replication and serve read-only queries. Writes still go to the primary. Replication is almost always asynchronous, so a replica is behind the primary by some lag: usually milliseconds, sometimes seconds, and minutes during a big batch job or a network hiccup.

Write a script of writes and reads, set the lag, and compare routing strategies. "Read your writes" is the guarantee users notice: after I change something, I see the change.

The strategies, from simplest to most precise:

Strategy How Cost
All reads to the primary no replicas simple and fresh; doesn't scale reads
Replicas for tolerant reads only reports, search, dashboards, other users' data you must classify every query
Sticky primary after a write after a user writes, route that user's reads to the primary for N seconds (cookie or session flag) simple and effective; N must exceed typical lag
Wait for the position remember the write's log position (PostgreSQL LSN, MySQL GTID); a replica serves the read only once it has replayed that far, else go to the primary precise; needs driver or proxy support
Synchronous replication the primary waits for a replica to confirm before committing every write gets slower; usually for durability, not read scaling

In code, routing usually means two connection strings and a decision per query: EF Core with two DbContext registrations (or ApplicationIntent=ReadOnly for SQL Server Always On), Spring's AbstractRoutingDataSource keyed on @Transactional(readOnly = true), SQLAlchemy with two engines and a custom Session.get_bind, Go with two *sql.DB pools, and Prisma's readReplicas extension (prisma.$primary() to force the primary). Caching has exactly the same staleness question, and the same answers, in caching.

Sharding at a glance

Replicas scale reads. When writes or data size outgrow one primary, you split the data across several databases by a shard key: each shard owns a subset of tenants, customers or ids.

Sharding is the last resort, not the next step. Before it: indexes and query fixes, caching, read replicas, bigger hardware (vertical scaling goes a long way), archiving cold data, and table partitioning (one database, data split by range or hash inside it). When you do need it, managed options (Citus for PostgreSQL, Vitess for MySQL, Azure SQL elastic pools, or a distributed SQL database such as CockroachDB, YugabyteDB or Spanner) do the routing for you. Cross-shard consistency is covered in distributed architecture.

SQL injection and parameterization

SQL injection is decades old and still in the OWASP Top 10, because it's so easy to write. Whenever user input is concatenated into SQL text, the input can close the string literal and continue as SQL. The fix is equally old: send the SQL and the values separately, as a parameterized query. The database parses the SQL once, with placeholders, and the values can never become code.

Type into the login box and switch between concatenation and parameters. Watch the tokens the database's parser sees: with concatenation, quotes in the input turn into SQL syntax; with parameters, the whole input is one value.

// BAD: string concatenation or interpolation into SQL text
var sql = $"SELECT * FROM users WHERE name = '{name}'";
conn.Query<User>(sql);
db.Users.FromSqlRaw($"SELECT * FROM users WHERE name = '{name}'");   // FromSqlRaw + interpolation = injection

// GOOD
conn.Query<User>("SELECT * FROM users WHERE name = @name", new { name });        // Dapper parameter
db.Users.FromSql($"SELECT * FROM users WHERE name = {name}");                     // EF Core: FormattableString → parameter
db.Users.Where(u => u.Name == name);                                              // LINQ is always parameterized

// BAD
stmt.executeQuery("SELECT * FROM users WHERE name = '" + name + "'");
em.createQuery("from User u where u.name = '" + name + "'");                     // JPQL injection is real too

// GOOD
PreparedStatement ps = conn.prepareStatement("SELECT * FROM users WHERE name = ?");
ps.setString(1, name);
em.createQuery("from User u where u.name = :name", User.class).setParameter("name", name);
dsl.selectFrom(USERS).where(USERS.NAME.eq(name));                                // jOOQ binds values

# BAD: f-strings, %, .format() into SQL
cur.execute(f"SELECT * FROM users WHERE name = '{name}'")
session.execute(text(f"SELECT * FROM users WHERE name = '{name}'"))

# GOOD: the driver's placeholders (psycopg: %s; sqlite3: ?) or SQLAlchemy bound parameters
cur.execute("SELECT * FROM users WHERE name = %s", (name,))
session.execute(text("SELECT * FROM users WHERE name = :name"), {"name": name})
session.scalars(select(User).where(User.name == name))

// BAD
db.QueryContext(ctx, "SELECT * FROM users WHERE name = '"+name+"'")
db.QueryContext(ctx, fmt.Sprintf("SELECT * FROM users WHERE name = '%s'", name))

// GOOD: placeholders ($1 for PostgreSQL, ? for MySQL/SQLite, @p1 for SQL Server)
db.QueryContext(ctx, "SELECT * FROM users WHERE name = $1", name)
gormDB.Where("name = ?", name).Find(&users)   // NOT gormDB.Where("name = '" + name + "'")

// BAD
await pool.query(`SELECT * FROM users WHERE name = '${name}'`);

// GOOD
await pool.query("SELECT * FROM users WHERE name = $1", [name]);
await prisma.$queryRaw`SELECT * FROM users WHERE name = ${name}`;        // tagged template → parameter
await db.selectFrom("users").selectAll().where("name", "=", name).execute(); // Kysely
await db.execute(sql`SELECT * FROM users WHERE name = ${name}`);          // Drizzle sql`` tag

Where injection still sneaks in when "we use an ORM"

  • Raw SQL escape hatches with interpolation: FromSqlRaw, ExecuteSqlRaw, $queryRawUnsafe, text(f"..."), createNativeQuery("..." + x), GORM Where(fmt.Sprintf(...)). Look for the "Raw" and "Unsafe" names in code review.
  • Identifiers can't be parameters. Column names in ORDER BY, table names and sort directions are SQL, not values. Map user input through an allowlist: sort switch { "date" => "created_at", "total" => "total", _ => "created_at" }.
  • LIKE patterns. Parameterizing stops injection but % and _ in the input are still wildcards; escape them if users shouldn't be able to search for "everything".
  • IN lists. Build one placeholder per item (Dapper and EF Core expand lists for you), or pass an array: = ANY($1) on PostgreSQL.
  • Stored procedures that build dynamic SQL inside with string concatenation are just as vulnerable. Use sp_executesql with parameters, or format('%I', …) / quote_ident for identifiers in PL/pgSQL.

Least privilege is the second line of defence: the app's database user shouldn't be able to DROP TABLE. The broader picture is in API security.

When to pick NoSQL

"NoSQL" is four quite different families, each optimised for an access pattern that relational databases handle less well. The honest default for a new business application is still a relational database: it does transactions, ad hoc queries and constraints, and PostgreSQL's jsonb covers much of what people reach for a document store to get. Pick something else when your access pattern clearly matches one of these:

Family Data model Great at Weak at Design rule
Relational tables, rows, foreign keys transactions, joins, ad hoc queries, constraints horizontal write scaling (without sharding) normalise, then denormalise deliberately for reads
Key-value key → opaque value O(1) get/put, caching, counters, sessions, locks any query not by key design keys for every lookup you'll need
Document JSON documents in collections aggregates read whole, flexible schema, partitioned scale joins, multi-document transactions (supported but costly) model documents around access patterns; embed what's read together
Wide-column partitions of sorted rows massive writes, time-ordered reads within a partition ad hoc queries, aggregations, updates one table per query; the partition key decides scale
Graph nodes and edges with properties variable-depth traversals (friends of friends of friends) bulk aggregations, simple CRUD at scale model the relationships you'll traverse as edges

The rule that transfers across all of them: in NoSQL you design the schema from the queries, because the database won't join or re-index for you later. Modelling aggregates (what's read and written together) is the same skill as in domain-driven design.

Common pitfalls

Pitfalls and production war stories

  • "It was fast in dev." Dev has 50 rows; production has 50 million. Test with production-sized data, or at least look at the plan and count rows touched.
  • The Black Friday pool outage. A payment call inside a transaction slowed from 100 ms to 8 s. Every request held a connection for 8 s, the pool of 100 emptied in a second, and the whole site queued behind it, including pages that never touch payments. Fix: no remote calls inside transactions; a timeout on the payment call; a separate pool (bulkhead) for slow work, as in resilience.
  • The silent overwrite. Two support agents edited the same customer; the second "Save" wiped the first agent's address change. Nothing logged an error. Fix: a rowversion column, an ETag on the form, 412 on conflict, and a "someone else changed this" screen.
  • The serializer N+1. An endpoint returned List<Order> with lazy loading on. JSON serialization touched order.Customer for each order: 501 queries per call, invisible in the controller code. Fix: projections; lazy loading off.
  • The migration that locked the table. ALTER TABLE orders ADD COLUMN … DEFAULT now() on an old MySQL version rewrote 200 GB under a lock. Fix: test migrations on a production-sized copy; use online DDL tools (gh-ost, pt-online-schema-change) or the database's online options.
  • The isolation surprise. Stock went negative under load because "we use transactions". The default READ COMMITTED doesn't stop read-modify-write races. Fix: UPDATE … SET stock = stock - @q WHERE stock >= @q.
  • Replica confusion. Users reported "my settings don't save" for a few seconds after saving. The reads hit a replica. Fix: sticky primary for that user after a write.

Checklist

Before shipping data-access code

  • [ ] SQL logging is on in development, and you've read the SQL each new endpoint generates. A test asserts the number of queries for key endpoints.
  • [ ] No lazy loading on request paths. Related data is loaded with eager loading, split queries or projections.
  • [ ] Read endpoints project to DTOs and use no-tracking. Write endpoints load aggregates, change them, and save once.
  • [ ] Every query that filters or sorts large tables has a supporting index, checked with EXPLAIN on realistic data. Foreign keys are indexed.
  • [ ] Lists use keyset pagination (or offset with a hard maximum page) and a stable, unique sort.
  • [ ] Transactions are short, contain no remote calls, and use the isolation level the logic needs, with a retry loop for serialization failures.
  • [ ] Concurrent edits are detected: a version column and ETag/If-Match, or atomic updates.
  • [ ] The pool is sized for the database, not the traffic; every connection is disposed via using / try-with-resources / with / defer / finally; acquisition has a timeout; leak detection is on.
  • [ ] All SQL is parameterized. Identifiers come from allowlists. The app's database user has least privilege.
  • [ ] Migrations are reviewed, backward-compatible (expand / contract), run once per deploy outside app startup, and tested on production-sized data.
  • [ ] Reads that go to replicas tolerate lag; read-your-writes paths go to the primary.
  • [ ] Database time is visible: slow query log or pg_stat_statements / Query Store, plus database spans in traces (observability).

Self-check

An endpoint lists 100 orders and their customer names. It's slow, and the SQL log shows 101 queries. Name three fixes and the one you'd pick.

It's N+1: one query for the orders and one lazy load per order for its customer. Fixes: eager-load the customer (Include, join fetch, joinedload, Prisma include), which is a JOIN that adds columns but not rows for a many-to-one; batch-load customers with WHERE id IN (…) (split query, selectinload, @BatchSize); or project new { o.Id, o.Total, CustomerName = o.Customer.Name }. The projection is usually best for a read endpoint: one query, only the needed columns, nothing tracked.

Two requests run SELECT stock, both see 1, and both run UPDATE … SET stock = 0 and create an order. You're in a transaction at READ COMMITTED. Why didn't that help, and what's the simplest fix?

READ COMMITTED only guarantees you don't see uncommitted data. Both transactions read the committed value 1 before either wrote, so this is a lost update. The simplest fix is to make the check and the change one statement: UPDATE products SET stock = stock - 1 WHERE id = @id AND stock >= 1, and treat "0 rows affected" as out of stock. Alternatives: SELECT … FOR UPDATE, a version column, or SERIALIZABLE with a retry loop.

You have an index on (status, customer_id). Which of these can seek: WHERE customer_id = 4; WHERE status = 'paid'; WHERE customer_id = 4 AND status = 'paid'?

The second and third. The index is sorted by status first, so any query constraining status has a leftmost prefix; the order of predicates in WHERE doesn't matter. customer_id = 4 alone has no prefix: customer 4's entries are spread across every status group, so it scans (or, on some engines, does a skip scan when status has few distinct values). If customer_id alone is a common query, (customer_id, status) is the better index: it serves both.

A list endpoint pages with OFFSET. Users on page 3 sometimes see an item they saw on page 2. What's happening, and how do you fix it?

New rows were inserted at the top of the sort order between the two requests, so every row shifted down by one and the last item of page 2 is now the first of page 3. Keyset pagination fixes it: page 3 asks for rows after the last key it saw (WHERE (created_at, id) < (@c, @i)), so insertions above don't move the boundary. It's also faster at depth, because it seeks instead of reading and discarding.

Why is services.AddSingleton<ShopDb>() a bug, but AddSingleton(NpgsqlDataSource) correct?

A DbContext is a unit of work: it holds an identity map and snapshots, isn't thread-safe, and grows with every query. As a singleton it's shared by concurrent requests (exceptions, corrupted state) and serves stale cached entities forever. A data source is a thread-safe factory that owns the connection pool, which should be shared process-wide. Make the context scoped (or use AddDbContextPool, which resets and reuses contexts safely).

You must rename customers.name to full_name on a system that deploys with rolling updates. Outline the steps.

Expand / contract: (1) add full_name nullable; (2) deploy code that writes both columns and still reads name; (3) backfill old rows in batches; (4) deploy code that reads full_name (still writing both); (5) deploy code that writes only full_name; (6) once no running version reads name, drop it and add NOT NULL if needed. Every intermediate schema works with both the old and new running versions, so no deploy causes errors.

A code review shows db.Users.FromSqlRaw($"SELECT * FROM users WHERE email = '{email}'"). What's wrong, and what's the smallest fix?

FromSqlRaw with an interpolated string concatenates the input into SQL text: email = x' OR '1'='1 returns every user. The smallest fix is FromSql($"SELECT * FROM users WHERE email = {email}") (or FromSqlInterpolated), which turns each interpolation hole into a DbParameter. Better still, db.Users.Where(u => u.Email == email).

Inserting 50,000 rows takes 90 seconds with a loop of INSERT statements. Where does the time go, and what gets it under a second?

Mostly per-row round trips (50,000 × ~1 ms) and, with autocommit, a log flush per row (another ~1 ms each). Wrapping the loop in one transaction removes the flushes; batching (executeBatch, executemany, EF Core's batched SaveChanges, a multi-row INSERT) removes most round trips; a bulk path (COPY, SqlBulkCopy, pgx CopyFrom) streams rows in one operation and is usually well under a second for 50,000 rows.
