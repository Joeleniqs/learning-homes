Application Architecture Styles

Layered, hexagonal (ports & adapters), clean/onion and vertical slices compared as dependency diagrams, and when each one fits.

Intermediate → Advanced~60 min studyBuilds on: Design Principles: SOLID, DRY, KISS, YAGNI, DI FundamentalsUpdated 2026-11-03

The problem: where does the business rule live?

Open almost any five-year-old business application and look for the rule "an order over $10,000 needs manual approval". You will usually find it in several places. Part of it is in a controller action that also parses JSON, opens a SqlConnection and calls Stripe. A copy sits in a background job that "re-checks orders", and another copy is in a stored procedure someone added during an incident. None of these places can be unit-tested without a database. Changing the rule means a search across the whole repository, and upgrading the ORM means touching business code.

[ApiController, Route("orders")]
public class OrdersController : ControllerBase
{
    [HttpPost]
    public async Task<IActionResult> Place(PlaceOrderDto dto)
    {
        using var db = new SqlConnection(Environment.GetEnvironmentVariable("DB"));     // infrastructure
        var customer = await db.QuerySingleAsync<CustomerRow>(
            "select * from customers where id = @id", new { dto.CustomerId });          // SQL in the web layer
        var total = dto.Lines.Sum(l => l.Qty * l.UnitPrice);                             // business rule #1
        if (total > 10_000 && !customer.IsTrusted) return StatusCode(202);               // business rule #2
        var charge = await new StripeClient(Environment.GetEnvironmentVariable("STRIPE"))
            .ChargeAsync(customer.CardToken, total);                                     // vendor SDK
        if (!charge.Ok) return BadRequest("card declined");
        await db.ExecuteAsync("insert into orders ...", new { dto.CustomerId, total });  // persistence
        await new SmtpClient("smtp.corp").SendMailAsync("shop@corp", customer.Email, "Thanks!", "..."); // email
        return Ok();
    }
}

This controller mixes four concerns: HTTP, SQL, Stripe and SMTP, and the business rule is buried in the middle of them. The rule cannot be tested without all four, cannot be reused from a message consumer, and is rewritten by anyone who needs it elsewhere. Application architecture is the set of decisions about where code goes and which code may know about which, so that this does not happen.

The one rule behind every modern style: source-code dependencies point toward the business rules. The code that decides (domain + use cases) never names the code that delivers (HTTP, UI, queues) or the code that stores and calls out (databases, SDKs). Those details depend on the core, through interfaces the core owns.

This page builds on Design Principles, especially the Dependency Inversion Principle, and on Dependency Injection Fundamentals, which explains how the concrete adapters get plugged in. It compares the four classic styles (layered, hexagonal, onion and clean), then covers vertical slices, CQRS, modular monoliths and per-language project layout. It finishes with the part most tutorials skip: when not to use any of these.

Two pictures of every application

The most important idea on this page is that every application has two dependency graphs, and they do not have to match.

  • Runtime flow: who calls whom while a request is being served. Control always flows from the outside in and back out: HTTP → your code → database → your code → HTTP.
  • Source dependencies: whose name appears in whose source file (import, using, a constructor parameter type). This graph decides what must be recompiled, retested and understood when something changes.

In a naive design the two graphs are identical: the order service calls the SQL repository, so it imports the SQL repository. Every architecture style on this page is a way of making the source graph differ from the runtime graph, so that the source arrows point at the stable thing (the business rules) instead of the volatile thing (the database, the framework, the vendor SDK).

Why the source graph is the one that matters If PlaceOrder.cs contains the word SqlConnection, then you cannot compile, test or read PlaceOrder without SQL. If it only contains IOrderRepo, a five-line in-memory fake replaces the whole database in a test. Changing ORMs then touches only the adapter, and a second adapter (a message consumer, a CLI or a batch job) can drive the same use case. The runtime path is identical in both cases, so none of this costs any performance.

Four styles at a glance

The four classic styles are, at heart, two ideas. Layered architecture arranges code in horizontal tiers that call downward, with the database at the bottom. Hexagonal, onion and clean architecture are three vocabularies for one idea: put the business rules in the centre and make everything else point inward. They differ mostly in how many rings they name.

Layered (n-tier)

The oldest and still the most common style. You have a presentation layer (controllers, views), a business layer (services), a data-access layer (repositories, ORM entities), and the database underneath. Each layer may call only the layer directly below it (strict layering) or any layer below it (relaxed layering). It is easy to explain, and every framework tutorial produces it by default.

Its weakness is the direction of the arrows. The business layer sits above data access, so it imports data-access types. In practice the ORM entity becomes the domain model, with public setters, navigation properties and lazy loading, and every schema change ripples upward. You can still unit-test the services, but only by mocking repositories that return ORM entities. Layered is a fine choice for CRUD-heavy apps where there are few rules to protect.

Hexagonal (ports and adapters)

Alistair Cockburn's 2005 idea: the application is a hexagon (the number of sides does not matter) with ports on its boundary and adapters outside. Ports come in two kinds:

  • Driving (primary) ports are the use-case interfaces that the outside world calls into, such as IPlaceOrder. HTTP controllers, CLI commands, message consumers and tests are driving adapters.
  • Driven (secondary) ports are the interfaces the application calls out through, such as OrderRepository, Payments or Clock. They are declared by the application, in its own vocabulary. A SQL repository, a Stripe client and a fake are driven adapters that implement them.

The original motivation was symmetry: "allow an application to equally be driven by users, programs, automated test or batch scripts, and to be developed and tested in isolation from its eventual run-time devices and databases." The style says nothing about what is inside the hexagon, so you can organise it however you like.

Onion

Jeffrey Palermo's 2008 refinement names the inside. The domain model sits at the centre, wrapped in domain services and then application services. The outer ring holds infrastructure, UI and tests. Its signature rule is that repository interfaces belong to the domain rings, and only their implementations live outside. All coupling points toward the centre; the outer ring is the only one allowed to touch the database or the framework.

Clean

Robert C. Martin's 2012 synthesis has four rings. Entities hold enterprise-wide business rules; use cases (interactors) hold application-specific rules; interface adapters hold controllers, presenters and gateways; frameworks and drivers hold the web framework, the database and devices. Its one hard rule is the Dependency Rule: source code dependencies can only point inwards. Clean also adds explicit input ports, output ports and presenters. Most real projects skip presenters and return a result object instead.

Same idea, different words

Hexagonal Onion Clean What it is
inside of the hexagon domain model + domain/application services entities + use cases the code that decides

driven port repository / service interface in the domain output port / gateway interface what the core needs from outside

If a team argues about whether they are "doing onion or clean", the answer is usually "yes". Pick one vocabulary per codebase and write it down.

Step through the same feature in each style below. The first half of each run animates the runtime calls, which look identical in every style. The second half draws the source dependencies and checks each one against the style's rule. The final step searches for any path from the business rules to a driver or SDK. Try layered first: every arrow is legal, but the rules can still reach the database. Then switch on the shortcut and watch a single new break a clean architecture.

Layered

Arrows point at the database. Business code names data-access types, and the ORM entity often is the domain model. Simple, familiar and fast to start. Fine for CRUD; it gets expensive when the rules grow or when the persistence technology changes.

Hexagonal

Symmetric ports. Driving adapters (HTTP, CLI, tests, consumers) and driven adapters (DB, SDKs) sit outside, and both depend on the core. It says nothing about the core's internals. It has the smallest vocabulary and is a good default for "rules + several integrations".

Onion

Names the domain rings. It puts repository interfaces in the domain, and tests live in the outer ring with infrastructure. Its vocabulary is close to DDD (domain services, application services).

Clean

Four rings and the Dependency Rule. It adds input and output ports and presenters. It is the most prescriptive, and the easiest to over-apply: one interface per use case plus a presenter per screen is a lot of files for a small app.

The same feature in code: place order

Words are cheap, so here is the same feature written in ports-and-adapters style in five ecosystems. The rules are:

  • an order needs at least one line, and quantities must be positive;
  • an order over $10,000 waits for manual approval instead of being charged;
  • otherwise the customer's card is charged, and the order becomes Paid or PaymentFailed.

Money is kept in integer cents everywhere, which avoids floating-point errors and keeps the five versions comparable.

The core: domain and use case, with zero framework imports

Read the import and using lines first. The core names no web framework, ORM, HTTP client or vendor SDK. It declares two driven ports, OrderRepository and Payments, in its own vocabulary, and one use case that a driving adapter calls.

// Shop.Core/Ordering/Order.cs  (project references: none)
namespace Shop.Core.Ordering;

public sealed class DomainException(string message) : Exception(message);

public sealed record OrderLine(string Sku, int Qty, long UnitPriceCents)
{
    public long TotalCents => Qty * UnitPriceCents;
}

public enum OrderStatus { New, AwaitingApproval, Paid, PaymentFailed }

public sealed class Order
{
    public const long ApprovalLimitCents = 10_000_00;
    private readonly List<OrderLine> _lines;

    public Guid Id { get; }
    public string CustomerId { get; }
    public OrderStatus Status { get; private set; }
    public IReadOnlyList<OrderLine> Lines => _lines;
    public long TotalCents => _lines.Sum(l => l.TotalCents);

    private Order(Guid id, string customerId, List<OrderLine> lines)
    {
        (Id, CustomerId, _lines) = (id, customerId, lines);
        Status = TotalCents > ApprovalLimitCents ? OrderStatus.AwaitingApproval : OrderStatus.New;
    }

    public static Order Place(string customerId, IEnumerable<OrderLine> lines)
    {
        var list = lines.ToList();
        if (list.Count == 0) throw new DomainException("An order needs at least one line.");
        if (list.Any(l => l.Qty <= 0)) throw new DomainException("Quantities must be positive.");
        return new Order(Guid.NewGuid(), customerId, list);
    }

    public void MarkPaid() => Status = Status == OrderStatus.New ? OrderStatus.Paid
        : throw new DomainException($"Cannot pay an order that is {Status}.");
    public void MarkPaymentFailed() => Status = Status == OrderStatus.New ? OrderStatus.PaymentFailed
        : throw new DomainException($"Cannot fail payment of an order that is {Status}.");
}

// Shop.Core/Ordering/PlaceOrder.cs: the ports are declared here, by the code that needs them
public interface IOrderRepository { Task SaveAsync(Order order, CancellationToken ct); }
public interface IPayments { Task<bool> ChargeAsync(string customerId, long amountCents, CancellationToken ct); }

public sealed record PlaceOrderCommand(string CustomerId, IReadOnlyList<OrderLine> Lines);
public sealed record PlaceOrderResult(Guid OrderId, OrderStatus Status, long TotalCents);

public sealed class PlaceOrder(IOrderRepository orders, IPayments payments)
{
    public async Task<PlaceOrderResult> HandleAsync(PlaceOrderCommand cmd, CancellationToken ct = default)
    {
        var order = Order.Place(cmd.CustomerId, cmd.Lines);          // rules live on the entity
        if (order.Status == OrderStatus.New)
        {
            if (await payments.ChargeAsync(order.CustomerId, order.TotalCents, ct)) order.MarkPaid();
            else order.MarkPaymentFailed();
        }
        await orders.SaveAsync(order, ct);
        return new(order.Id, order.Status, order.TotalCents);
    }
}

// shop-core/src/main/java/com/shop/ordering/Order.java   (no Spring, no JPA imports)
package com.shop.ordering;

import java.util.List;
import java.util.UUID;

public final class Order {
    public static final long APPROVAL_LIMIT_CENTS = 10_000_00L;
    public enum Status { NEW, AWAITING_APPROVAL, PAID, PAYMENT_FAILED }
    public record Line(String sku, int qty, long unitPriceCents) {
        public long totalCents() { return qty * unitPriceCents; }
    }

    private final UUID id;
    private final String customerId;
    private final List<Line> lines;
    private Status status;

    private Order(UUID id, String customerId, List<Line> lines) {
        this.id = id; this.customerId = customerId; this.lines = List.copyOf(lines);
        this.status = totalCents() > APPROVAL_LIMIT_CENTS ? Status.AWAITING_APPROVAL : Status.NEW;
    }

    public static Order place(String customerId, List<Line> lines) {
        if (lines.isEmpty()) throw new DomainException("An order needs at least one line.");
        if (lines.stream().anyMatch(l -> l.qty() <= 0)) throw new DomainException("Quantities must be positive.");
        return new Order(UUID.randomUUID(), customerId, lines);
    }

    public void markPaid()          { requireNew(); status = Status.PAID; }
    public void markPaymentFailed() { requireNew(); status = Status.PAYMENT_FAILED; }
    private void requireNew() {
        if (status != Status.NEW) throw new DomainException("Order is " + status);
    }

    public long totalCents() { return lines.stream().mapToLong(Line::totalCents).sum(); }
    public UUID id() { return id; }
    public String customerId() { return customerId; }
    public Status status() { return status; }
    public List<Line> lines() { return lines; }
}

// DomainException.java, OrderRepository.java, Payments.java, PlaceOrder.java (same package)
public class DomainException extends RuntimeException {
    public DomainException(String message) { super(message); }
}
public interface OrderRepository { void save(Order order); }
public interface Payments { boolean charge(String customerId, long amountCents); }

public final class PlaceOrder {
    public record Command(String customerId, List<Order.Line> lines) {}
    public record Result(UUID orderId, Order.Status status, long totalCents) {}

    private final OrderRepository orders;
    private final Payments payments;
    public PlaceOrder(OrderRepository orders, Payments payments) {
        this.orders = orders; this.payments = payments;
    }

    public Result handle(Command cmd) {
        Order order = Order.place(cmd.customerId(), cmd.lines());
        if (order.status() == Order.Status.NEW) {
            if (payments.charge(order.customerId(), order.totalCents())) order.markPaid();
            else order.markPaymentFailed();
        }
        orders.save(order);
        return new Result(order.id(), order.status(), order.totalCents());
    }
}

from __future__ import annotations

import uuid
from dataclasses import dataclass, field
from enum import Enum
from typing import Protocol

APPROVAL_LIMIT_CENTS = 10_000_00


class DomainError(Exception):
    pass


class Status(str, Enum):
    NEW = "new"
    AWAITING_APPROVAL = "awaiting_approval"
    PAID = "paid"
    PAYMENT_FAILED = "payment_failed"


@dataclass(frozen=True)
class Line:
    sku: str
    qty: int
    unit_price_cents: int

    @property
    def total_cents(self) -> int:
        return self.qty * self.unit_price_cents


@dataclass
class Order:
    customer_id: str
    lines: tuple[Line, ...]
    id: uuid.UUID = field(default_factory=uuid.uuid4)
    status: Status = field(init=False)

    def __post_init__(self) -> None:
        self.status = Status.AWAITING_APPROVAL if self.total_cents > APPROVAL_LIMIT_CENTS else Status.NEW

    @classmethod
    def place(cls, customer_id: str, lines: list[Line]) -> Order:
        if not lines:
            raise DomainError("An order needs at least one line.")
        if any(l.qty <= 0 for l in lines):
            raise DomainError("Quantities must be positive.")
        return cls(customer_id, tuple(lines))

    @property
    def total_cents(self) -> int:
        return sum(l.total_cents for l in self.lines)

    def mark_paid(self) -> None:
        self._require_new()
        self.status = Status.PAID

    def mark_payment_failed(self) -> None:
        self._require_new()
        self.status = Status.PAYMENT_FAILED

    def _require_new(self) -> None:
        if self.status is not Status.NEW:
            raise DomainError(f"Order is {self.status.value}")


class OrderRepository(Protocol):          # driven port: structural, no base class needed
    async def save(self, order: Order) -> None: ...


class Payments(Protocol):
    async def charge(self, customer_id: str, amount_cents: int) -> bool: ...


@dataclass(frozen=True)
class PlaceOrderCommand:
    customer_id: str
    lines: list[Line]


@dataclass(frozen=True)
class PlaceOrderResult:
    order_id: uuid.UUID
    status: Status
    total_cents: int


class PlaceOrder:
    def __init__(self, orders: OrderRepository, payments: Payments) -> None:
        self._orders, self._payments = orders, payments

    async def __call__(self, cmd: PlaceOrderCommand) -> PlaceOrderResult:
        order = Order.place(cmd.customer_id, cmd.lines)
        if order.status is Status.NEW:
            if await self._payments.charge(order.customer_id, order.total_cents):
                order.mark_paid()
            else:
                order.mark_payment_failed()
        await self._orders.save(order)
        return PlaceOrderResult(order.id, order.status, order.total_cents)

// internal/ordering/order.go  (imports: standard library + a UUID value type)
package ordering

import (
    "context"
    "errors"
    "fmt"

    "github.com/google/uuid" // a value library, not infrastructure
)

const ApprovalLimitCents int64 = 10_000_00

var ErrInvalidOrder = errors.New("invalid order")

type Status string

const (
    StatusNew              Status = "new"
    StatusAwaitingApproval Status = "awaiting_approval"
    StatusPaid             Status = "paid"
    StatusPaymentFailed    Status = "payment_failed"
)

type Line struct {
    SKU            string
    Qty            int
    UnitPriceCents int64
}

type Order struct {
    ID         uuid.UUID
    CustomerID string
    Lines      []Line
    status     Status // unexported: only methods in this package change it
}

func Place(customerID string, lines []Line) (*Order, error) {
    if len(lines) == 0 {
        return nil, fmt.Errorf("%w: an order needs at least one line", ErrInvalidOrder)
    }
    for _, l := range lines {
        if l.Qty <= 0 {
            return nil, fmt.Errorf("%w: quantities must be positive", ErrInvalidOrder)
        }
    }
    o := &Order{ID: uuid.New(), CustomerID: customerID, Lines: append([]Line(nil), lines...), status: StatusNew}
    if o.TotalCents() > ApprovalLimitCents {
        o.status = StatusAwaitingApproval
    }
    return o, nil
}

func (o *Order) TotalCents() (t int64) {
    for _, l := range o.Lines {
        t += int64(l.Qty) * l.UnitPriceCents
    }
    return t
}

func (o *Order) Status() Status { return o.status }

func (o *Order) settle(paid bool) error {
    if o.status != StatusNew {
        return fmt.Errorf("%w: order is %s", ErrInvalidOrder, o.status)
    }
    o.status = map[bool]Status{true: StatusPaid, false: StatusPaymentFailed}[paid]
    return nil
}

// Ports: in Go the consumer declares the interface, which is exactly what a port is.
type Repository interface {
    Save(ctx context.Context, o *Order) error
}

type Payments interface {
    Charge(ctx context.Context, customerID string, amountCents int64) (bool, error)
}

type PlaceOrderCommand struct {
    CustomerID string
    Lines      []Line
}

type PlaceOrder struct {
    Orders   Repository
    Payments Payments
}

func (uc PlaceOrder) Handle(ctx context.Context, cmd PlaceOrderCommand) (*Order, error) {
    o, err := Place(cmd.CustomerID, cmd.Lines)
    if err != nil {
        return nil, err
    }
    if o.status == StatusNew {
        ok, err := uc.Payments.Charge(ctx, o.CustomerID, o.TotalCents())
        if err != nil {
            return nil, fmt.Errorf("charge: %w", err)
        }
        if err := o.settle(ok); err != nil {
            return nil, err
        }
    }
    if err := uc.Orders.Save(ctx, o); err != nil {
        return nil, fmt.Errorf("save order: %w", err)
    }
    return o, nil
}

// src/ordering/core/order.ts  (no @nestjs/*, no ORM imports)
import { randomUUID } from "node:crypto";

export const APPROVAL_LIMIT_CENTS = 10_000_00;
export class DomainError extends Error {}
export type Status = "new" | "awaiting_approval" | "paid" | "payment_failed";
export interface Line { readonly sku: string; readonly qty: number; readonly unitPriceCents: number }

export class Order {
  private constructor(
    readonly id: string,
    readonly customerId: string,
    readonly lines: readonly Line[],
    private _status: Status,
  ) {}

  static place(customerId: string, lines: Line[]): Order {
    if (lines.length === 0) throw new DomainError("An order needs at least one line.");
    if (lines.some((l) => l.qty <= 0)) throw new DomainError("Quantities must be positive.");
    const total = lines.reduce((s, l) => s + l.qty * l.unitPriceCents, 0);
    return new Order(randomUUID(), customerId, [...lines], total > APPROVAL_LIMIT_CENTS ? "awaiting_approval" : "new");
  }

  get status(): Status { return this._status; }
  get totalCents(): number { return this.lines.reduce((s, l) => s + l.qty * l.unitPriceCents, 0); }

  markPaid(): void { this.requireNew(); this._status = "paid"; }
  markPaymentFailed(): void { this.requireNew(); this._status = "payment_failed"; }
  private requireNew(): void {
    if (this._status !== "new") throw new DomainError(`Order is ${this._status}`);
  }
}

}

Notice what is not here. There are no [Table] attributes, no @Entity, no Depends, no @Injectable() and no *sql.DB. The core is plain code in each language, which makes it the easiest code in the whole system to read and to test.

Language notes

  • Go gets ports almost for free. Interfaces are satisfied implicitly and are idiomatically declared by the consumer, so ordering.Repository sits next to the code that uses it, and the Postgres package never has to import a shared "interfaces" package.
  • Python Protocol gives the same structural typing, so an adapter does not need to inherit from anything.
  • TypeScript and NestJS need a runtime token for DI, because interfaces disappear at compile time. An abstract class works both as the type and as the token, with no Nest import in the core.
  • Java commonly splits the core into its own Maven or Gradle module with no Spring dependency, so the build tool itself enforces the rule.
  • C# does the same with a separate Shop.Core.csproj that has no package references.

The adapters and the composition root

Everything that knows about a framework, a database or a vendor lives out here. Each driven adapter implements a core port. The driving adapter (the HTTP endpoint) translates JSON into a command and maps domain errors to status codes. The composition root is the only place that names every concrete type; see Dependency Injection Fundamentals for why there should be only one.

{
    public async Task<bool> ChargeAsync(string customerId, long amountCents, CancellationToken ct)
    {
        var form = new FormUrlEncodedContent(new Dictionary<string, string>
        {
            ["amount"] = amountCents.ToString(), ["currency"] = "usd",
            ["customer"] = customerId, ["confirm"] = "true",
        });
        using var res = await http.PostAsync("v1/payment_intents", form, ct);
        return res.IsSuccessStatusCode;
    }
}

func (p Payments) Charge(ctx context.Context, customerID string, amountCents int64) (bool, error) {
    form := url.Values{"amount": {strconv.FormatInt(amountCents, 10)}, "currency": {"usd"},
        "customer": {customerID}, "confirm": {"true"}}
    req, err := http.NewRequestWithContext(ctx, http.MethodPost,
        "https://api.stripe.com/v1/payment_intents", strings.NewReader(form.Encode()))
    if err != nil {
        return false, err
    }
    req.Header.Set("Content-Type", "application/x-www-form-urlencoded")
    req.SetBasicAuth(p.Key, "")
    res, err := p.Client.Do(req)
    if err != nil {
        return false, err
    }
    defer res.Body.Close()
    return res.StatusCode < 300, nil
}

    SKU            string `json:"sku"`
    Qty            int    `json:"qty"`
    UnitPriceCents int64  `json:"unitPriceCents"`

func PlaceOrder(uc ordering.PlaceOrder) http.HandlerFunc {
    return func(w http.ResponseWriter, r *http.Request) {
        var in struct {
            CustomerID string   `json:"customerId"`
            Lines      []lineIn `json:"lines"`
        }
        if err := json.NewDecoder(r.Body).Decode(&in); err != nil {
            http.Error(w, err.Error(), http.StatusBadRequest)
            return
        }
        cmd := ordering.PlaceOrderCommand{CustomerID: in.CustomerID}
        for _, l := range in.Lines {
            cmd.Lines = append(cmd.Lines, ordering.Line{SKU: l.SKU, Qty: l.Qty, UnitPriceCents: l.UnitPriceCents})
        }
        o, err := uc.Handle(r.Context(), cmd)
        switch {
        case errors.Is(err, ordering.ErrInvalidOrder):
            http.Error(w, err.Error(), http.StatusUnprocessableEntity)
            return
        case err != nil:
            http.Error(w, "internal error", http.StatusInternalServerError)
            return
        }
        w.Header().Set("Content-Type", "application/json")
        w.WriteHeader(http.StatusCreated)
        _ = json.NewEncoder(w).Encode(map[string]any{"orderId": o.ID, "status": o.Status(), "totalCents": o.TotalCents()})
    }
}

A dependency rule that only lives in a wiki page will be broken within a month, usually by someone fixing an incident at 2 a.m. The fix is to make the rule a test that fails the build. Every ecosystem has a tool that reads the compiled code (or the import graph), checks each dependency against your rules, and looks for cycles.

Vertical slice architecture

Layers and rings slice the code horizontally, by technical role. But changes rarely arrive horizontally. Nobody files a ticket that says "please change all repositories". Tickets say "add a gift note to checkout", and that one change cuts vertically through the endpoint, the validation, the logic and the data access of a single feature.

Vertical slice architecture (named by Jimmy Bogard) organises code around those cuts. Each request or use case is a slice that owns everything it needs, usually in one file or one folder. Slices share as little as possible: a domain model where real rules live, and infrastructure such as the DbContext. Each slice may choose its own approach. A simple query can hit the database directly, while a complex command can go through a rich domain model.

The visualizer below runs two realistic changes in parallel, made by two developers, against both folder layouts. It counts the files and folders each change touches and the files both changes edit, which is where merge conflicts happen.

One file per use case

A slice is usually a single file containing the request type, the validation, the handler and the endpoint mapping. You can read the whole feature without jumping around, and deleting the feature means deleting the file.

  async cancel(@Param("id", ParseUUIDPipe) id: string, @Body() body: CancelOrderBody): Promise<void> {
    const row = await this.prisma.order.findUnique({ where: { id } });
    if (!row) throw new NotFoundException();
    const order = Order.fromRow(row);
    order.cancel(body.reason);                       // domain rule
    await this.prisma.order.update({ where: { id }, data: order.toRow() });
  }
}

Slices and rings are not rivals Vertical slices decide how you group code (by feature). Hexagonal and clean decide which way dependencies point (inward). Most healthy codebases use both: feature folders at the top level, a framework-free domain model that the slices share, and ports only where something really needs swapping or faking. The Go example above shows the cheap end of the scale, with SQL straight in the handler and the rule enforced by the WHERE clause. That is fine for a simple state change, and it is not fine once the rule grows beyond a single condition.

CQRS: from light to full

Command Query Responsibility Segregation means that the code which changes state (commands) and the code which reads state (queries) take different paths. The motivation is simple. Writes need invariants, transactions and an aggregate loaded in full. Reads need joins, projections, paging and speed, and they never change anything. A single model that serves both ends up as a compromise that does neither job well: entities bloated with display properties, or queries that load whole aggregate graphs just to show three columns.

CQRS is a dial, not a switch. Most teams should stop at the second step.

Run the same script of operations through each mode. Watch the read side in full mode: a query issued right after a command can miss it until the projector catches up. This is the "I clicked Save and my order is not in the list" bug that full CQRS introduces.

func (q OrderQueries) Summaries(ctx context.Context, customerID uuid.UUID) ([]OrderSummary, error) {
    rows, err := q.DB.QueryContext(ctx, `
        SELECT o.id, o.status, SUM(l.qty * l.unit_price_cents)

CQRS is

  • Separate code paths for writes and reads.
  • Free to use different models: aggregates for writes, flat DTOs for reads.
  • Optionally separate stores, but only when read load or shape really demands it.
  • Compatible with any architecture style: layered, hexagonal or slices.

CQRS is not

  • Event sourcing. You can do CQRS with plain tables, and that is the normal case. Event sourcing is covered in distributed architecture.
  • A message bus. MediatR and @nestjs/cqrs are in-process dispatchers, so a "command bus" is just a method call with indirection.
  • Mandatory for every entity. Apply it to the parts with complex rules or heavy reads, and keep simple CRUD simple.
  • Free. Full CQRS makes every read potentially stale, and the UI must cope with that.

The mediator tax MediatR-style dispatch adds a level of indirection: "Go to definition" on Send(cmd) lands on an interface, not the handler. That is worth it when you use pipeline behaviours for validation, logging and transactions in one place (see behavioral patterns and outbound pipelines). It is pure overhead when every handler is called from exactly one endpoint and you have no behaviours. A plain handler class injected into the endpoint gives you the command/query split without the bus.

Modular monolith

A modular monolith is one deployable unit split into modules along business boundaries such as Catalog, Ordering, Billing and Shipping. Each module has a small public API and hides everything else. Modules talk only through those APIs (in-process calls) or through events. Each module owns its own tables, and no other module may query them.

This gives you most of the design benefits people want from microservices (clear ownership, independent reasoning, the option to extract later) without the network, the distributed transactions, or the operational bill. For most teams it is the right default; distributed architecture covers when to go further.

Build your own module graph below. Each reference names its target and how it is reached: .Api and .Events are legal, .Internal and db: are violations. The tool selector shows how the same rule is written in your ecosystem's checker.

When NOT to: the cost of extra layers

Every layer and interface is a bet that something will vary or need isolating. When the bet does not pay off, you are left with pass-through layers: classes whose only job is to call the next class with the same arguments. They double the files you touch per change, hide the real logic, and teach newcomers that architecture means typing.

Classic symptoms:

  • IOrderService with exactly one implementation, OrderService, which forwards every method to IOrderManager, which forwards to IOrderRepository.
  • DTO → Model → Entity → Record mappers where all four types have identical fields.
  • A "domain" layer of classes with only getters and setters (an anemic model), while all the rules live in services. This is covered in domain-driven design.
  • Unit tests that mock the next layer and assert it was called, so they test the wiring rather than any behaviour.

Mark each layer below as map (translates between shapes), pass (forwards unchanged) or logic (makes a decision). The visualizer counts the hops, the files touched by a new field, and how many layers actually earn their place. Then it shows the lean version.

Pitfalls and war stories

The four-hour field A team with a textbook n-tier layout (Controller, Service, Manager, Repository, plus DTO, Model and Entity mappers) needed to add PreferredName to a customer. The change touched 14 files across 4 projects, and the AutoMapper profile silently dropped the field in one direction, so the value was saved but never returned. Feature slices with one DTO and a projection would have been 3 files, and the bug would have been visible in a single diff.

Ports that leak the adapter IOrderRepository.Query(): IQueryable<OrderEntity> looks like a port but exposes EF Core's query provider and the persistence entity. Every caller now writes LINQ that only works against EF, and the "swap the database" promise is fiction. Ports should speak the domain's language: FindOpenOrdersFor(customerId), returning domain types.

The shared "Common" project It starts with StringExtensions. A year later it holds OrderStatus, CustomerDto, EmailSender and a static DbHelper, every module references it, and every change to it rebuilds and redeploys everything. Shared code should be either truly generic (and stable), or owned by one module and exposed through its API.

Clean architecture as a template Generating Domain, Application, Infrastructure and WebApi projects from a template for a 12-endpoint internal admin tool gives you four projects, a mediator, pipeline behaviours, AutoMapper and FluentValidation before the first rule exists. The ceremony is real and the benefit is hypothetical. Start with slices and earn each ring.

Architecture without enforcement The diagram in the README showed perfect onion rings. An ArchUnit run added two years later found 212 violations, mostly @Entity and RestTemplate imports in the domain package. A rule that is not tested is a wish. Add the architecture test on day one, when it has zero violations.

Transactions that span adapters by accident A use case saves the order and then calls the payment gateway inside the same database transaction. When the gateway is slow, the transaction holds row locks for 30 seconds and the whole orders table backs up. Keep external calls outside the database transaction, and use the outbox pattern from distributed architecture when a state change and a message must both happen.

Best-practice checklist

  • I can draw my application's source dependency arrows, and they point inward towards the domain.
  • The core (domain and use cases) has no references to the web framework, ORM, HTTP clients or cloud SDKs, and a test enforces that.
  • There is exactly one composition root where adapters are created and wired.
  • Each interface in the core has a reason: an external system, a second implementation, or a test seam.
  • Code is grouped by feature at the top level; technical roles are subfolders, if anything.
  • No layer exists only to forward calls; mappers exist only where the shapes really differ.
  • Queries that only read return DTOs straight from a projection, not full aggregates.
  • Modules own their data; nothing joins across module schemas.
  • Cross-module calls go through a small published API or events, and an architecture test enforces this.
  • External calls (payments, email, other services) happen outside database transactions.
  • The most important business rules can be unit-tested in milliseconds without a database.
  • I can explain why this codebase uses its style, in terms of its domain and team, not fashion.

Self-check

1. In hexagonal architecture, where does the `IPaymentGateway` interface live, and where does `StripePaymentGateway` live? Why?

The interface (the port) lives in the core, next to the use case that needs it, and is written in the core's language: Charge(Money, CustomerRef). The implementation (the adapter) lives outside, with the Stripe SDK. The runtime call goes core → adapter, but the source dependency goes adapter → core, because the adapter implements an interface the core owns. That inversion is what keeps the core free of Stripe.

2. What is the real difference between onion and clean architecture?

Almost none in practice. Both put the domain at the centre and require dependencies to point inward. Clean names the rings Entities, Use Cases, Interface Adapters and Frameworks & Drivers, and is explicit about use-case input/output boundaries and presenters. Onion names them Domain Model, Domain Services, Application Services and Infrastructure/UI/Tests. The shared idea, and the only one that matters, is the dependency rule.

3. Your team adds a field and touches Controller, Service, Manager, Repository, three DTOs and two mapper profiles. What would you change first?

Delete the pass-through layers (Manager, and probably Service if it only forwards), and collapse mappers where the shapes are identical. Then move to feature folders so the remaining pieces of a feature sit together. Keep a layer only where it makes a decision or translates between shapes that really differ.

4. Does using CQRS mean you need event sourcing or a message bus?

No. CQRS only means commands and queries take different paths. The most common and most useful form, CQRS light, uses one database: commands go through aggregates and repositories, and queries are SQL projections into DTOs, with no events and no staleness. Event sourcing and separate read stores are optional extras with real costs.

5. In a modular monolith, Ordering needs the customer's credit limit, which Billing owns. Name two legal ways to get it and one illegal way.

Legal: call Billing's published API (IBillingApi.GetCreditLimit(customerId)) in-process, or subscribe to a CreditLimitChanged event and keep a local read copy in Ordering's own schema. Illegal: SELECT credit_limit FROM billing.accounts from Ordering, or referencing Billing's internal AccountRepository. Both couple Ordering to Billing's internals and block later extraction.

6. How does Go enforce module boundaries without a separate tool, and what can it not enforce?

The compiler refuses imports of any package under an internal/ directory from outside the tree rooted at its parent, so billing/internal/store is private to billing. Go also forbids import cycles between packages. It cannot enforce direction among packages that are allowed to see each other (for example "domain must not import net/http"). For that you need a test over go list -deps, or a linter such as depguard in golangci-lint.

7. When is a plain layered architecture with three layers the right choice?

When the domain has some real rules but no need to swap infrastructure, the team is small, and everyone already understands it. Layered is fine as long as the business logic layer holds real decisions in a rich model and the layers are not pass-through. Its weakness, the domain depending on data access, is manageable when the data access is simple and stable.

The ruleSource dependencies point inward: adapters → use cases → domain. Never the reverse.
LayeredUI → Logic → Data. Simple and familiar; the domain depends on data access.
HexagonalThe core owns ports (interfaces); adapters implement or drive them. Swap and fake I/O freely.
Onion / CleanRings around the domain with the same dependency rule; clean names use cases explicitly.
Composition rootOne place (Program.cs, @Configuration, main.py, main.go, AppModule) wires adapters to ports.
Vertical sliceGroup by feature; one file per use case; each slice picks its own depth.
CQRS lightCommands through aggregates; queries as SQL projections to DTOs; one DB.
Full CQRSSeparate read store fed by events; reads become eventually consistent.
Modular monolithOne deployable; modules with public APIs, private internals and owned schemas.
EnforceNetArchTest, ArchUnit and Spring Modulith, import-linter, Go internal/, dependency-cruiser and eslint-plugin-boundaries.
Port whenExternal, slow or non-deterministic, a second implementation, or the core must not know.
SmellPass-through layers, I-twins with one implementation, anemic entities, cross-module joins.
