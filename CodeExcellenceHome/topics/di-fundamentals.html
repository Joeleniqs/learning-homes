DI Fundamentals

From 'new' everywhere to the composition root: constructor injection, pure DI, and what a container actually does (animated resolution).

Beginner → Intermediate~50 min studyBuilds on: Design Principles: SOLID, DRY, KISS, YAGNIUpdated 2026-11-03

The problem: a class that builds its own world

Here is a perfectly ordinary order service. It works in production, and nobody can change or test it.

public class OrderService
{
    private readonly SqlConnection _db = new("Server=prod-db;Database=shop;Integrated Security=true");
    private readonly FileLogger _log = new(@"C:\logs\app.log");

    public Receipt PlaceOrder(Order order)
    {
        _log.Info($"placing {order.Id}");
        var http = new HttpClient();                                   // a fresh connection pool per call
        var stripe = new StripeGateway(http, Environment.GetEnvironmentVariable("STRIPE_KEY"));
        var charge = stripe.Charge(order.Total);                       // a real charge, every time
        if (!charge.Approved) return Receipt.Declined(order.Id);

        order.PlacedAt = DateTime.UtcNow;                              // ambient time: cannot be frozen
        new SqlOrderRepository(_db).Save(order);                       // writes to the prod database
        return Receipt.Ok(order.Id, charge.Id);
    }
}

public sealed class OrderService(
    IOrderRepository repo,          // every collaborator is visible in the signature
    IPaymentGateway payments,
    TimeProvider clock,
    ILogger<OrderService> log)
{
    public Receipt PlaceOrder(Order order)
    {
        log.LogInformation("placing {OrderId}", order.Id);
        var charge = payments.Charge(order.Total);
        if (!charge.Approved) return Receipt.Declined(order.Id);

        order.PlacedAt = clock.GetUtcNow();
        repo.Save(order);
        return Receipt.Ok(order.Id, charge.Id);
    }
}

The "before" version decides four things that are not its job: which database, which log file, which payment provider and which clock. Each new is a hard edge in the dependency graph. Draw the graph and the problem becomes obvious:

The costs are concrete, not theoretical:

  • Untestable. A unit test for "a declined card saves nothing" charges a real card and writes to the production database. Nobody writes that test, so the rule goes unchecked.
  • Rigid. Moving from Stripe to Adyen, or from a file log to OpenTelemetry, means editing OrderService, and every other class that copied the same new.
  • Dishonest signature. new OrderService() looks free. You only learn that it needs a database, a network and a disk by reading its body or by watching it fail at runtime.
  • Lifetimes by accident. new HttpClient() per call exhausts sockets under load; one SqlConnection field shared across threads corrupts state. The class is making lifetime decisions it cannot see the consequences of.

Dependency injection in one sentence: a class asks for its collaborators (usually through its constructor) instead of creating them, and a single place at the entry point of the application, the composition root, decides which concrete objects exist and how long they live.

The visualizer below runs the same PlaceOrder under three wirings. Watch which object handles each call, and what that costs the test: time, side effects, and whether the assertion even means anything.

The point of the "fakes" run is not that it is faster (although 0 ms vs ~460 ms adds up over 2,000 tests). It is that the test can choose the scenario: "the card is declined" is one constructor argument, not a Stripe test card and a prayer. The place where a test can substitute behaviour without editing the class is called a seam; constructor parameters are the cleanest seams a language offers.

IoC, DIP and DI: three different ideas

These three terms get used interchangeably, and that blurs the reasoning. They answer different questions:

Inversion of Control (IoC)

A broad principle about who drives. Your code no longer controls some part of the flow; a framework does and calls you back ("don't call us, we'll call you"). ASP.NET Core calls your controller, JUnit calls your test, the browser calls your click handler. Creating your collaborators is just one more thing you can hand over.

Dependency Inversion Principle (DIP)

A design rule about which way source-code dependencies point (the D in SOLID). High-level policy (OrderService) must not depend on low-level detail (SqlOrderRepo). Both depend on an abstraction, and the abstraction is owned by the policy side (IOrderRepository is shaped by what orders need, not by what SQL offers).

Dependency Injection (DI)

A concrete technique for delivering collaborators. Something outside the object passes the dependencies in, through the constructor, a property or a method parameter. DI is IoC applied to object creation. It is the usual delivery mechanism for DIP, but either can exist without the other.

Because they are independent, all four combinations exist in real code:

Uses DI? Follows DIP? Example What you get
No No new SqlOrderRepository(conn) inside OrderService Rigid and untestable: the "before" code above.
Yes No OrderService(SqlOrderRepository repo): a concrete class is injected Wiring has moved out, so the lifetime is controlled. But OrderService still compiles against SQL, so a fake has to subclass a SQL class.
No Yes OrderService depends on IOrderRepository but calls RepoFactory.Create() The direction is right, but a hidden static choice remains: tests must mutate global state.
Yes Yes OrderService(IOrderRepository repo), wired at the root The goal: swappable, honest and testable.

Why DIP says the abstraction belongs to the policy If IOrderRepository lives next to SqlOrderRepository and mirrors its methods (ExecuteSql, BeginTransaction), you have inverted nothing: the high-level code still speaks SQL. Define the interface in the orders module with the operations orders need (Save(order), FindOpen(customer)). Then the SQL module depends on the orders module, not the other way round. See Design Principles for SOLID in full.

Three ways to inject

There are three places a dependency can enter an object. They differ in when the object becomes valid, and that is the whole decision.

Constructor injection (the default)

Dependencies are required constructor parameters stored in readonly/final fields. The object is valid from the moment it exists and can never be half-built. Use it for every required dependency, which is nearly all of them.

Property (setter) injection

A settable property, assigned after construction. The object is invalid between new and the assignment, and the dependency can be swapped mid-life. Use it only for a genuinely optional dependency with a safe local default (for example Logger = NullLogger.Instance).

Method injection

The dependency is a parameter of the method that uses it. It is valid for that call only. Use it when the dependency varies per call (the current request's CancellationToken, a culture, a per-request HttpContext) or when a long-lived object needs a short-lived collaborator.

Step through what each style does when a caller makes a mistake. The constructor version refuses to exist in an invalid state, the property version fails later, far from the bug, and the method version moves the burden to every call site:

public sealed class ReportService
{
    private readonly TimeProvider _clock;                      // required, never null, never swapped
    private readonly IReportStore _store;

    public ReportService(TimeProvider clock, IReportStore store)
    {
        _clock = clock ?? throw new ArgumentNullException(nameof(clock));
        _store = store ?? throw new ArgumentNullException(nameof(store));
    }

    public void Generate(ReportRequest req) =>
        _store.Save(new Report(req, _clock.GetUtcNow()));
}

public sealed class ReportService
{
    public TimeProvider? Clock { get; set; }                   // anyone can set these, or forget to
    public IReportStore? Store { get; set; }
    public ILogger Logger { get; set; } = NullLogger.Instance; // fine: optional, with a safe default

    public void Generate(ReportRequest req) =>                 // NullReferenceException here,
        Store!.Save(new Report(req, Clock!.GetUtcNow()));      // far from the line that forgot
}

public sealed class ReportService(TimeProvider clock, IReportStore store)
{
    // The formatter really does vary per call (CSV today, PDF next), so it is a parameter.
    // The clock and store do not vary, so they stay in the constructor.
    public void Generate(ReportRequest req, IReportFormatter formatter) =>
        store.Save(formatter.Format(new Report(req, clock.GetUtcNow())));
}

Frameworks use all three. ASP.NET Core uses constructor injection for services, and method injection for middleware InvokeAsync(HttpContext ctx, IMyScoped svc) and minimal-API handler parameters. Spring supports constructor, setter and field injection, but the Spring team recommends constructors for required dependencies. FastAPI's Depends is method injection at the endpoint. Microsoft.Extensions.DependencyInjection has no property injection at all; that is a deliberate nudge.

Pitfall: field injection Spring's @Autowired private PaymentGateway payments; and similar attribute-on-a-private-field tricks look tidy, but they produce a class you cannot construct without the container (tests need reflection or a Spring context), fields that cannot be final, and a constructor that hides how many collaborators there are. Constructor injection makes "this class needs nine things" painfully visible, and that pain is useful feedback.

The composition root, and pure DI first

If no class creates its own collaborators, someone must. That someone is the composition root: one place, as close to the entry point as possible, that knows every concrete type and assembles the object graph. Everything else in the application only knows abstractions.

Ecosystem Where the composition root lives
ASP.NET Core / .NET Program.cs: builder.Services.Add… calls, then builder.Build()
Spring Boot The application context: @SpringBootApplication component scanning plus @Configuration @Bean methods
Go main() (or a run() function it calls); plain constructor calls
FastAPI / Python main() / create_app() and the dependency functions passed to Depends
NestJS / Node AppModule provider lists plus main.ts; or plain new calls in main.ts

Start without a container. Wiring by hand is called pure DI (Mark Seemann's term; older texts say "poor man's DI", which undersells it). Here is the graph that the container visualizer further down builds, written as plain code:

// Program.cs: the composition root, by hand. Creation order = leaves first.
var settings  = Settings.Load("appsettings.json");                 // app-wide
var dbFactory = new SqlDbFactory(settings);                         // app-wide
var logger    = new ConsoleLogger();                                // app-wide, thread-safe
var http      = new HttpClient();                                   // app-wide: reuse the pool

app.MapPost("/orders", (Order order) =>
{
    var repo     = new SqlOrderRepo(dbFactory, logger);             // per request
    var payments = new StripePayments(http, logger);                // per use
    var service  = new OrderService(repo, payments, logger);        // per request
    return service.PlaceOrder(order);
});

That is the whole idea. There is nothing magic about it: the compiler checks every edge, "go to definition" works, and the lifetimes are visible as where the new sits (outside the lambda means one per app; inside means one per request).

Why one root matters: change ripples

When ConsoleLogger grows a constructor parameter, how many files change? With new scattered through the classes, every class that creates a logger must change, and each of those creates its own logger, so you also have duplicate instances. With a composition root, exactly one line changes. Try each class and each wiring:

Notice the container row: when a constructor grows, the container needs no edit at all, because it reads constructor signatures itself. That is the main thing a container buys you, and it is why the cost of pure DI grows with the number of classes and the cost of a container does not.

What a container actually does

A DI container (also called an IoC container) is a library that automates the composition root. Every container, from Microsoft.Extensions.DependencyInjection to Spring to Dagger, does the same four jobs:

1 · REGISTERDescribe, don't create

Map service → implementation + lifetime. AddScoped<IOrderRepo, SqlOrderRepo>() creates nothing yet.

2 · BUILDFreeze and validate

Compile the table into a provider. Optionally walk every graph now (ValidateOnBuild) so mistakes fail at startup.

3 · RESOLVERecursive construction

Look up the implementation, read its constructor, resolve each parameter the same way, create leaves first, cache per lifetime.

4 · RELEASEDispose what it created

When a scope (or the app) ends, dispose the tracked IDisposable instances in reverse creation order.

Step 3 is the interesting one. It is a depth-first walk of the constructor graph: to create OrderService the container must first have every one of its arguments, and each argument is resolved the same way. The walk keeps a resolve chain (a call stack) so it can detect cycles, and it consults each lifetime's cache before creating anything: singletons are cached for the whole app, scoped instances for the current scope (one HTTP request), and transients never.

Edit the registrations (Service=Impl(Dep,Dep)@lifetime, separated by ;), pick 2 requests to see what survives between scopes, or press Randomize to cycle through a cycle, a missing registration and an all-transient graph. The right-hand panel writes the equivalent pure-DI line for every object the container creates:

Things to notice:

  • Leaves first. Settings is created before SqlDbFactory, which is created before SqlOrderRepo. Constructor arguments must exist before the constructor runs, so creation order is a post-order walk.
  • Reuse is per lifetime. ConsoleLogger (singleton) is created once and then appears as reused every time; StripePayments (transient) is new every time it is asked for. In request 2, scoped OrderService and SqlOrderRepo are new again, while every singleton is reused.
  • The container never "knows" the graph. It knows only the flat registration table and discovers the edges by reading constructors. That is why a constructor change needs no registration change, and also why errors appear only at resolution time unless you validate on build.

Circular dependencies

If SqlOrderRepo needs IAuditLog and DbAuditLog needs IOrderRepo, there is no order in which the constructors can run: each needs the other to exist first. The container notices when a service it is already resolving appears again on its own resolve chain, and it refuses:

A cycle is a design signal, not a container problem. Fixes, best first:

  1. Extract the shared part. Usually both classes need a third concept (here, "record an audit entry" does not need the whole repository). Move it into a new class that both depend on.
  2. Invert one edge with an event. The repository publishes OrderSaved; the audit log subscribes. Neither constructor needs the other.
  3. Defer one edge (Lazy<T>, Func<T>, Spring ObjectProvider<T>/@Lazy). This compiles and runs, but it hides the cycle rather than removing it. Treat it as a last resort.

Spring Boot 2.6 and later rejects circular references by default (spring.main.allow-circular-references=false), and constructor-injection cycles have always failed with BeanCurrentlyInCreationException. Dagger and Wire report cycles at compile or generate time.

Pure DI or a container?

Pure DI

  • The compiler checks every edge; no runtime "unable to resolve" errors.
  • Zero reflection, zero startup cost, trivially debuggable.
  • Lifetimes are visible as where the new sits.
  • Cost: every constructor change edits the root; lifetime and disposal bookkeeping is manual; it grows linearly with the class count.

Container

  • Auto-wiring: constructor changes need no registration edits.
  • Lifetime caching and disposal handled for you, per scope.
  • Framework integration: controllers, middleware, hosted services, typed HttpClients and options all come from the same container.
  • Cost: errors move to runtime (mitigate with build-time validation), "magic" wiring, a framework dependency, and a learning curve for lifetimes (see DI Lifetimes).

Service locator: the look-alike

A service locator also inverts creation: classes get their collaborators from a central registry instead of new. The difference is direction. With DI, dependencies are pushed in through the signature. With a locator, the class pulls them from the registry inside its method bodies. Injecting IServiceProvider, ApplicationContext or a global Container.Resolve<T>() into a business class turns the container into a locator.

Both versions run the same code path when everything is registered. The difference shows up when something is missing, and when someone tries to test the class:

Service locator (pull) Constructor injection (push)
What the class needs Hidden in method bodies; read the code to find out Listed in the constructor
A missing registration Fails mid-request, possibly after a card was charged Fails when the graph is built: at startup with ValidateOnBuild, at compile time with pure DI, Dagger or Wire
Unit test setup Build a container, guess which services the method touches Pass the arguments; the compiler tells you what is missing
Coupling Every class depends on the locator API Classes depend only on their abstractions

When pulling is fine. Infrastructure inside the composition root has to resolve things: the framework creating a controller per request, a factory that creates a scope per message, a plug-in host. Pulling from the container is acceptable at the edge of the app, in code whose job is wiring. It is the anti-pattern only when business classes do it.

The same app in five ecosystems

The application is the one above: OrderService needs an order repository, a payment gateway (which needs an HTTP client) and a clock. First, the service. Notice that in every language it is a plain class or struct that receives its collaborators. None of these service files mentions a container.

public interface PaymentGateway { ChargeResult charge(BigDecimal amount); }

@Service                                     // a @Component stereotype: Spring will create it
public class OrderService {
    private final OrderRepository repo;      // final: constructor injection makes immutability possible
    private final PaymentGateway payments;
    private final Clock clock;               // java.time.Clock: the JDK's injectable clock

    @Autowired                               // optional since Spring 4.3 when there is one constructor
    public OrderService(OrderRepository repo, PaymentGateway payments, Clock clock) {
        this.repo = repo;
        this.payments = payments;
        this.clock = clock;
    }

    public Receipt placeOrder(Order order) {
        ChargeResult charge = payments.charge(order.total());
        if (!charge.approved()) return Receipt.declined(order.id());
        repo.save(order.withPlacedAt(clock.instant()));
        return Receipt.ok(order.id(), charge.id());
    }
}

from dataclasses import dataclass
from datetime import datetime
from decimal import Decimal
from typing import Callable, Protocol


@dataclass
class Order:
    id: int
    total: Decimal
    placed_at: datetime | None = None


@dataclass(frozen=True)
class ChargeResult:
    approved: bool
    charge_id: str = ""


@dataclass(frozen=True)
class Receipt:
    order_id: int
    approved: bool
    charge_id: str = ""


class PaymentGateway(Protocol):            # structural: implementations never import this
    def charge(self, amount: Decimal) -> ChargeResult: ...


class OrderRepository(Protocol):
    def save(self, order: Order) -> None: ...


Clock = Callable[[], datetime]             # a function is the simplest possible abstraction


class OrderService:
    def __init__(self, repo: OrderRepository, payments: PaymentGateway, clock: Clock) -> None:
        self._repo, self._payments, self._clock = repo, payments, clock

    def place_order(self, order: Order) -> Receipt:
        charge = self._payments.charge(order.total)
        if not charge.approved:
            return Receipt(order.id, approved=False)
        order.placed_at = self._clock()
        self._repo.save(order)
        return Receipt(order.id, approved=True, charge_id=charge.charge_id)

package orders

// Interfaces are declared by the consumer, and satisfied implicitly:
// postgres.OrderRepository never imports this package.
type PaymentGateway interface {
    Charge(ctx context.Context, amountCents int64) (ChargeResult, error)
}

type Repository interface {
    Save(ctx context.Context, o *Order) error
}

type Service struct {
    repo     Repository
    payments PaymentGateway
    now      func() time.Time
}

// "Accept interfaces, return structs."
func NewService(repo Repository, payments PaymentGateway, now func() time.Time) *Service {
    return &Service{repo: repo, payments: payments, now: now}
}

func (s *Service) PlaceOrder(ctx context.Context, o *Order) (Receipt, error) {
    charge, err := s.payments.Charge(ctx, o.TotalCents)
    if err != nil {
        return Receipt{}, fmt.Errorf("charge order %d: %w", o.ID, err)
    }
    if !charge.Approved {
        return Receipt{OrderID: o.ID}, nil
    }
    o.PlacedAt = s.now()
    if err := s.repo.Save(ctx, o); err != nil {
        return Receipt{}, fmt.Errorf("save order %d: %w", o.ID, err)
    }
    return Receipt{OrderID: o.ID, Approved: true, ChargeID: charge.ID}, nil
}

export interface PaymentGateway { charge(amountCents: number): Promise<ChargeResult>; }
export interface OrderRepository { save(order: Order): Promise<void>; }
export type Clock = () => Date;

export class OrderService {
  // parameter properties: declare and assign the fields in one go
  constructor(
    private readonly repo: OrderRepository,
    private readonly payments: PaymentGateway,
    private readonly clock: Clock,
  ) {}

  async placeOrder(order: Order): Promise<Receipt> {
    const charge = await this.payments.charge(order.totalCents);
    if (!charge.approved) return { orderId: order.id, approved: false };
    order.placedAt = this.clock();
    await this.repo.save(order);
    return { orderId: order.id, approved: true, chargeId: charge.id };
  }
}

Now the wiring. This is the only code that changes between "by hand" and "with a container", and the only code that names concrete types:

// Spring Boot: the composition root is spread over annotations, scanned at startup.
@Repository                                    // @Component + persistence exception translation
class JdbcOrderRepository implements OrderRepository {
    private final JdbcClient jdbc;             // auto-configured by Spring Boot 3.2+
    JdbcOrderRepository(JdbcClient jdbc) { this.jdbc = jdbc; }

@Component
class StripePaymentGateway implements PaymentGateway {
    private final RestClient http;
    StripePaymentGateway(RestClient.Builder builder, @Value("${stripe.key}") String key) {
        this.http = builder.baseUrl("https://api.stripe.com")
                           .defaultHeader("Authorization", "Bearer " + key).build();
    }
    public ChargeResult charge(BigDecimal amount) {
        return http.post().uri("/v1/charges").body(Map.of("amount", amount))
                   .retrieve().body(ChargeResult.class);
    }
}

from typing import Annotated

def utc_now() -> datetime:
    return datetime.now(timezone.utc)

# --- Option A: pure DI. The composition root is a function. ---
def main() -> None:
    engine = create_engine(os.environ["DATABASE_URL"])
    with httpx.Client(base_url="https://api.stripe.com", timeout=10) as http, Session(engine) as session:
        service = OrderService(SqlOrderRepository(session), StripeGateway(http, os.environ["STRIPE_KEY"]), utc_now)
        print(service.place_order(Order(42, Decimal("99.00"))))

# --- Option B: FastAPI's Depends builds the graph per request ---
app = FastAPI()
engine = create_engine(os.environ["DATABASE_URL"])               # module level: one per process
http = httpx.Client(base_url="https://api.stripe.com", timeout=10)

def get_session():
    with Session(engine) as session:                             # yield dependency: closed after the request
        yield session

def get_payments() -> PaymentGateway:
    return StripeGateway(http, os.environ["STRIPE_KEY"])

def get_order_service(
    session: Annotated[Session, Depends(get_session)],
    payments: Annotated[PaymentGateway, Depends(get_payments)],
) -> OrderService:
    return OrderService(SqlOrderRepository(session), payments, utc_now)

@app.post("/orders")
def place_order(body: OrderIn, svc: Annotated[OrderService, Depends(get_order_service)]) -> Receipt:
    return svc.place_order(Order(body.id, body.total))

// main.go: the composition root is ordinary code. This is the idiomatic default in Go.
func main() {
    db, err := sql.Open("pgx", os.Getenv("DATABASE_URL"))
    if err != nil {
        log.Fatal(err)
    }

Why the ecosystems look so different

Language What shapes its DI style
C# Constructor parameter types survive to runtime, so MS.DI reflects over constructors and compiles fast activators. DI is built into the host: ASP.NET Core, the worker service, options, logging and HttpClientFactory all share one container, so "just use the built-in one" is the default.
Java Spring creates beans by classpath scanning, annotations and runtime proxies (for transactions and AOP). That is powerful, but it means wiring is spread over many files. Dagger (Android, and servers that start fast) does the same job by generating plain Java at compile time, so a missing binding is a compile error.
Python Duck typing, first-class functions and modules-as-singletons mean many apps need no container: pass objects in, or use a function as a dependency. FastAPI's Depends introspects function signatures and builds a per-request graph. Containers exist (dependency-injector, lagom) but are optional.
Go Implicit interfaces, a culture of explicitness and no annotations make pure DI in main the norm. When main becomes hundreds of lines, Wire generates that code (compile-time, no reflection) and Fx wires by reflection at startup, adding lifecycle hooks.
TypeScript Types are erased. A container can only see constructor parameter types if the compiler emits design:paramtypes metadata (emitDecoratorMetadata with reflect-metadata; some fast transpilers such as esbuild do not emit it), and interfaces never exist at runtime. That is why NestJS, InversifyJS and tsyringe use decorators plus class or symbol tokens.

Testing: the payoff

With constructor injection, a unit test is just a composition root with different leaves. A fake is a small working implementation (an in-memory repository, a gateway that always declines). A stub returns canned answers, and a mock records and verifies calls. Fakes keep tests readable and resilient to refactoring, so prefer them for your own interfaces.

When NOT to use a container

DI the principle (ask, don't create) almost always pays. A DI container is a tool with costs: runtime errors instead of compile errors, wiring that you cannot "go to definition" through, and a framework dependency. Choose deliberately:

A library that forces a container

  • Constructors that take IServiceProvider, or a static MyLib.Container.
  • A dependency on Autofac or Spring that every consumer inherits.
  • Public types that only work when resolved, with no usable constructor.

Consumers using pure DI, another container, or Go-style main wiring cannot use it without workarounds.

A DI-friendly library

  • Public types with honest constructors and sensible defaults (new StripeClient(apiKey)).
  • An optional services.AddStripe(o => …) that depends only on Microsoft.Extensions.DependencyInjection.Abstractions, using TryAdd… so callers can override.
  • Factories or builders for complex graphs, so pure-DI users have one line to write.

Inject volatile dependencies: anything that does I/O, is non-deterministic (time, randomness, GUIDs), needs configuration, or that you might replace. Do not inject stable ones: List<T>, StringBuilder, pure functions, value objects and entities. new Money(10, "EUR") and new Order(...) are fine: data objects are newables, not services. An interface per class "for testability", when nothing will ever substitute it, adds indirection without a seam that anyone uses.

Pitfalls and production war stories

Constructor over-injection A constructor with 9 parameters is not a DI problem; it is a class with too many jobs, and constructor injection is simply making that visible. Fix the design: split the class by responsibility, or group collaborators that are always used together behind a facade service (IOrderNotifications wrapping email, SMS and push). Do not "fix" it with property injection or a locator, which only hide the count.

The container leaks into business code A team injected IServiceProvider into a domain service "for flexibility". Every test passed. Months later a rarely used refund path called GetRequiredService<IRefundPolicy>(), which had never been registered in production, and it threw after the payment reversal had been sent. Fix: constructor-inject IRefundPolicy, and turn on ValidateOnBuild so a missing registration fails at startup, not on the 1,000th refund.

Work in constructors A constructor that opens a connection, calls an API or reads a file makes resolution slow and fallible: building an innocent controller suddenly hits the network, and failures surface as confusing activation exceptions. Constructors should only check and store their arguments. Do the I/O lazily, in methods, or in an explicit StartAsync/lifecycle hook.

Duplicate and ambiguous registrations In MS.DI, registering IPaymentGateway twice means GetService returns the last one while IEnumerable<IPaymentGateway> returns both, so a library's default can silently replace yours. Libraries should use TryAdd…. Multiple public constructors are another trap: MS.DI picks the one with the most parameters it can satisfy and throws if that is ambiguous; Spring needs @Autowired to choose. Keep exactly one public constructor on services.

A second container by accident Calling services.BuildServiceProvider() inside startup code (to "just get one service") creates a second container with its own singletons: two caches, two connection pools, and options read twice. ASP.NET Core flags this with analyzer warning ASP0000. Use the options pattern, a factory overload AddSingleton(sp => …), or IConfigureOptions<T> instead.

Ambient dependencies sneak back in DateTime.UtcNow, Guid.NewGuid(), Random.Shared, System.currentTimeMillis(), time.Now() and environment variables read deep inside a method are dependencies too, just invisible ones. A test of "orders placed after 17:00 ship tomorrow" becomes impossible. Inject TimeProvider (.NET 8+), java.time.Clock, a now func() time.Time or a clock callable.

Lifetimes have their own family of bugs: a singleton that captures a scoped DbContext, transient disposables that leak from the root, and background services without a scope. They get a full page in DI Lifetimes.

Best-practice checklist

  • Required dependencies come through the constructor, stored in readonly/final fields; one public constructor per service.
  • Business classes never reference the container (IServiceProvider, ApplicationContext, ModuleRef).
  • Exactly one composition root, at the entry point; it is the only code that names concrete implementations.
  • Abstractions are shaped by and live with the consumer (DIP), not mirrored from an implementation.
  • Time, randomness, I/O and configuration are injected; data objects are simply new-ed.
  • Constructors only validate and assign; no I/O.
  • The container validates the graph at startup (ValidateOnBuild, Spring context startup, Dagger/Wire at compile time).
  • Libraries expose plain constructors, plus at most an optional AddX() helper that uses TryAdd.
  • Unit tests construct the class directly with fakes; integration tests replace single registrations.

Self-check

Is "my class depends on IOrderRepository and gets it from RepositoryFactory.Create()" dependency injection?

No. It follows the Dependency Inversion Principle (it depends on an abstraction) but it is not DI: the class still fetches its collaborator, through a hidden static call, so a test must alter global factory state to substitute it. DI means the collaborator is passed in from outside.

Why does a container create Settings before SqlDbFactory before SqlOrderRepo?

A constructor cannot run until all of its arguments exist. The container therefore walks the constructor graph depth-first and creates objects in post-order: leaves first, then their consumers, and the root last. The same order appears naturally when you write pure DI by hand.

In the resolve visualizer with two requests, why is ConsoleLogger reused in request 2 but OrderService is new?

ConsoleLogger is a singleton: cached in the root for the life of the app. OrderService is scoped: cached per scope, and each request gets a new scope, so request 2 starts with an empty scoped cache. A transient (StripePayments) is never cached at all.

A needs B and B needs A. Why does making one of them a singleton not help?

Lifetime decides how long an instance is cached, not how it is constructed. The first A still cannot be constructed until a B exists, and that B cannot be constructed until an A exists. Break the cycle in the design: extract the shared responsibility, or replace one edge with an event.

Your library has 12 classes. Should it ship with Autofac and a pre-built container?

No. That forces every consumer into Autofac, and into your container rather than theirs. Give the public types honest constructors and defaults. Optionally add an AddMyLibrary(this IServiceCollection) helper that depends only on the DI abstractions package and uses TryAdd so consumers can override any registration.

When is property injection the right choice?

Only for a genuinely optional dependency that has a safe local default, for example ILogger Logger { get; set; } = NullLogger.Instance. For anything required, property injection creates a window where the object exists but is invalid, and it allows the dependency to change mid-life. MS.DI deliberately does not support it.

Why do NestJS providers often use abstract classes instead of interfaces as tokens?

TypeScript interfaces are erased at compile time, so there is nothing at runtime for the container to use as a key, and the emitted design:paramtypes metadata for an interface-typed parameter is just Object. An abstract class compiles to a real JavaScript value that can serve as the token and as the type, without @Inject('TOKEN') strings.
