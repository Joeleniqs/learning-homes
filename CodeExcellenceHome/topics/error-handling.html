FOUNDATIONS OF CRAFT

Error Handling Strategies

Exceptions vs result types vs error values (Go) vs Option, error boundaries, and what to catch, wrap, log or let crash.

Intermediate → Advanced~45 min studyBuilds on: Cross-Language Mental ModelsUpdated 2026-11-03

The problem: the error happened, then it disappeared

Most outages are not caused by the first error. They are caused by what the code did next: it swallowed the error, logged it four times without the cause, retried it until the database fell over, or turned "the user typed a bad email" into a 500. Error handling is the part of the program that only runs when things are already going wrong, so it is the part that is least tested and most likely to make things worse.

Language The code that shipped What happened The missing idea
C# catch (Exception) { return new List<Order>(); } in a repository The database was down for 40 minutes. The API returned 200 [] and customers saw "You have no orders". No alert fired. Wrap, don't swallow
Java catch (IOException e) { throw new RuntimeException("failed"); } The cause was dropped. The log said failed with a stack trace that ended in the catch block. Finding the real file took a day. Keep the cause
Python except: pass around a loop body It also caught KeyboardInterrupt, so Ctrl+C could not stop the job. It also hid a TypeError that skipped every row. Catch narrowly
Go go func() { _ = publish(evt) }() The broker rejected every event for a week. The error was assigned to _. Async errors
TypeScript sendEmail(user); without await The promise rejected; Node 15+ treated the unhandled rejection as fatal and restarted the server mid-traffic. Async errors

All five have the same shape: the error was produced correctly, but its journey to code that could act on it was broken. This page is about designing that journey across C#, Java, Python, Go and TypeScript: which channel carries the error, where it is caught, what context is added, what is cleaned up, what is logged, and when the right move is to let the process die.

Rule. Classify every failure before you handle it. Bugs fail fast. Expected outcomes are values in the return type. Environmental failures propagate with context added at each layer, are retried in at most one place, and are translated, logged and reported once at a boundary. Cleanup always runs. Never swallow an error you cannot fully handle.

The columns are not about the type of the error, they are about who can do something about it. A FileNotFoundException is an expected outcome when the file is an optional user setting, an environmental failure when it is a mounted secret that should be there, and a bug when the path was built with the wrong variable. The same exception type lands in different columns depending on the call site, which is why the decision belongs to the code that knows the context, not to a global rule like "always catch IOException".

Three channels for failure: exceptions, error values, Result

Every language gives a function two ways to finish: return normally, or fail. They differ in how the failure travels back to the caller.

Expected outcomes bool TryX(out T), T?, Result libraries Optional<T>, checked exceptions None, exceptions (EAFP) (T, error), sentinel errors union return types, undefined

Here is one function, "read the port number from a config file", in each language's idiomatic style. It has three failure modes in three different columns: the file is missing (expected here: there is a default), the content is not a number, and the number is out of range (both are configuration bugs: fail at startup).

public static int ReadPort(string path)
{
    string text = File.ReadAllText(path).Trim();      // throws FileNotFoundException, IOException...
    if (!int.TryParse(text, out var port))              // Try-pattern: expected failure without an exception
        throw new FormatException($"'{path}' does not contain a number: '{text}'");
    if (port is < 1 or > 65535)
        throw new ArgumentOutOfRangeException(nameof(path), port, "port must be 1-65535");
    return port;
}

int port;
try { port = ReadPort("port.txt"); }
catch (FileNotFoundException) { port = 8080; }        // the one failure this caller can fully handle
// FormatException and ArgumentOutOfRangeException propagate: a bad deployment must fail at startup.

import { readFileSync } from "node:fs";

type PortError =
  | { kind: "missing"; path: string }
  | { kind: "notANumber"; text: string }
  | { kind: "outOfRange"; port: number };
type Result<T, E> = { ok: true; value: T } | { ok: false; error: E };

function readPort(path: string): Result<number, PortError> {
  let text: string;
  try {
    text = readFileSync(path, "utf8").trim();
  } catch (e) {
    if ((e as NodeJS.ErrnoException).code === "ENOENT") return { ok: false, error: { kind: "missing", path } };
    throw e;                                          // EACCES, EISDIR...: not ours to decide
  }
  const port = Number(text);
  if (!Number.isInteger(port)) return { ok: false, error: { kind: "notANumber", text } };
  if (port < 1 || port > 65535) return { ok: false, error: { kind: "outOfRange", port } };
  return { ok: true, value: port };
}

function fail(e: PortError): never { throw new Error(`bad port config: ${JSON.stringify(e)}`); }
const r = readPort("port.txt");
const port = r.ok ? r.value : r.error.kind === "missing" ? 8080 : fail(r.error);

Notice what each version makes visible. In Go, every failure point is a line you can read. In the TypeScript Result version, the three expected failures are in the signature and the caller must narrow r.ok to get the number, while truly unexpected I/O errors still throw. In C#, Java and Python, the signature says nothing about FormatException or ValueError: you learn about them from documentation, tests or production.

Option is not Result Option/Maybe (T?, Optional<T>, T | None, T | undefined) says "there may be no value" and nothing about why. Use it when absence is the only failure and it is normal: a lookup that finds nothing. Use Result (or (T, error)) when the caller needs to know which failure happened, so it can respond differently to each. Functional Patterns covers composing both with map and bind; this page covers when to choose them over exceptions.

Java: checked vs unchecked exceptions

Java is the only mainstream language where the compiler tracks exceptions. Everything under Exception except RuntimeException is checked: a method that can throw it must declare throws, and every caller must catch it or declare it too.

The idea is sound: an environmental failure like IOException is part of the contract, so make it visible. In practice checked exceptions leak implementation details through every layer (throws SQLException on a service method tells callers you use JDBC) and fight lambdas, because Function<T, R> cannot throw checked exceptions. So modern Java code tends to:

  • Use unchecked exceptions for anything the immediate caller can't handle (Spring translates every SQLException into an unchecked DataAccessException hierarchy for exactly this reason).
  • Wrap checked exceptions at the layer that knows what they mean: throw new UncheckedIOException(e) inside a stream, or throw new OrderStoreException("load order " + id, e) at the repository boundary.
  • Keep checked exceptions for library APIs where the failure really is the caller's to handle and the caller is close by (Files.readString, HttpClient.send).
  • Never catch Throwable or Error in business code. Catching Exception is only for boundaries.
// A lambda can't throw IOException, so wrap it with context and keep the cause.
List<String> contents = paths.stream()
    .map(p -> {
        try { return Files.readString(p); }
        catch (IOException e) { throw new UncheckedIOException("read " + p, e); }
    })
    .toList();

Python: EAFP and the exception hierarchy

Python's culture is EAFP, "easier to ask forgiveness than permission": try the operation and handle the exception, instead of checking first (LBYL, "look before you leap"). This is not just style. Checking first is a race: the file can be deleted between exists() and open(). Exceptions are also cheap in CPython, and since 3.11 a try block that doesn't raise costs nothing.

import os

if os.path.exists(path):          # another process can delete it right here
    with open(path) as f:         # ...and this still raises FileNotFoundError
        data = f.read()
else:
    data = DEFAULT

try:
    with open(path) as f:
        data = f.read()
except FileNotFoundError:         # exactly the expected failure, nothing broader
    data = DEFAULT

The rules that make EAFP safe:

  • Catch the narrowest class that means what you expect. except Exception in the middle of business code hides TypeError and AttributeError, which are bugs.
  • Never use a bare except: (or except BaseException) unless you re-raise. It catches KeyboardInterrupt and SystemExit, which live outside Exception precisely so that ordinary handlers don't stop Ctrl+C.
  • Keep the try body small. Put the code that should run only on success in else:, so an exception from it isn't mistaken for the one you meant to catch.
  • Chain with raise NewError(...) from e; use from None only when the original is noise. Python 3.11 added e.add_note("while loading order 42") to add context without changing the type, and ExceptionGroup with except* for several errors at once.

Go: errors are values

Go has no exceptions for ordinary failures. A function that can fail returns error as its last result, and the caller checks it on the next line. error is a one-method interface (Error() string), so an error can be a constant, a struct with fields, or a wrapper around another error.

// 1. Sentinel errors: a fixed value callers compare against with errors.Is.
var ErrNotFound = errors.New("not found")

// 2. Error types: carry data; callers extract them with errors.As.
type ConflictError struct {
    ID      string
    Version int
}

func (e *ConflictError) Error() string { return fmt.Sprintf("order %s: version %d is stale", e.ID, e.Version) }

func (r *Repo) Load(ctx context.Context, id string) (*Order, error) {
    row := r.db.QueryRowContext(ctx, "select ... where id = $1", id)
    var o Order
    if err := row.Scan(&o.ID, &o.Total); err != nil {
        if errors.Is(err, sql.ErrNoRows) {
            return nil, fmt.Errorf("load order %s: %w", id, ErrNotFound) // translate, keep it matchable
        }
        return nil, fmt.Errorf("load order %s: %w", id, err) // 3. wrap with %w: context + cause
    }
    return &o, nil
}

// Caller: inspect the chain, never the message text.
o, err := repo.Load(ctx, id)
var conflict *ConflictError
switch {
case errors.Is(err, ErrNotFound):
    http.Error(w, "no such order", http.StatusNotFound)
case errors.As(err, &conflict):
    http.Error(w, conflict.Error(), http.StatusConflict)
case err != nil:
    return fmt.Errorf("show order: %w", err)
}

The rules: wrap with %w (not %v, which flattens the cause into text) and add what you were doing, not "error occurred". Compare with errors.Is/errors.As, never == or strings.Contains(err.Error(), ...), because wrapping breaks both. Go 1.20 added errors.Join and multiple %w verbs for several causes. Either handle an error or return it; doing both (log and return) is how one failure becomes five log lines. panic is reserved for bugs and impossible states; see Panics and fatal errors.

C#: exception filters and rethrowing correctly

C# exceptions are all unchecked. Two features matter more than they look:

  • Exception filters (catch (X e) when (condition)) are evaluated before the stack unwinds. If the filter is false, the exception keeps searching for a handler as if that catch didn't exist, and no finally has run yet. A crash dump or debugger still shows the original throwing frame. Compare that to "catch, check, throw;", which unwinds first and then throws again.
  • throw; vs throw e;: throw; rethrows the current exception with its original stack trace; throw e; resets the trace to the current line, destroying the most useful piece of evidence. To rethrow later (for example on another thread), use ExceptionDispatchInfo.Capture(e).Throw().
try
{
    return await http.GetFromJsonAsync<Order>($"orders/{id}", ct);
}
catch (HttpRequestException e) when (e.StatusCode == HttpStatusCode.NotFound)
{
    return null;                                         // expected: absence
}
catch (HttpRequestException e) when (e.StatusCode is >= HttpStatusCode.InternalServerError)
{
    throw new OrderServiceUnavailableException($"GET orders/{id}", e);   // context + cause
}
catch (OperationCanceledException) when (ct.IsCancellationRequested)
{
    throw;                                               // the caller cancelled: not an error, don't wrap
}

TypeScript: anything can be thrown

JavaScript lets you throw any value: a string, undefined, an object without a stack. So in TypeScript the catch variable is unknown (with strict, via useUnknownInCatchVariables), and you must narrow it before using it. ES2022 added cause, which finally gives JavaScript standard error chaining.

class OrderNotFoundError extends Error {
  override name = "OrderNotFoundError";
  constructor(readonly orderId: string, options?: ErrorOptions) {
    super(`order ${orderId} not found`, options);
  }
}

async function loadOrder(id: string): Promise<Order> {
  try {
    return await db.orders.findOrThrow(id);
  } catch (e: unknown) {
    if (e instanceof RecordNotFound) throw new OrderNotFoundError(id, { cause: e });
    throw new Error(`load order ${id}`, { cause: e });   // context, original kept as .cause
  }
}

function toError(e: unknown): Error {                   // for code that receives arbitrary throws
  return e instanceof Error ? e : new Error(`non-Error thrown: ${String(e)}`);
}

Only throw Error subclasses, so there is always a stack. Set name, because instanceof fails across realms (iframes, some test runners, duplicated packages) and name is the fallback. For expected outcomes, many TypeScript codebases return discriminated unions ({ ok: true, value } | { ok: false, error }) instead of throwing, because the compiler then forces the caller to look at the failure. That's the same trade-off as Go, with exhaustive switch checks on error.kind as a bonus.

What happens when you throw: stack unwinding

When an exception is thrown, the runtime walks up the call stack looking for a handler whose type (and filter) matches. Every frame it leaves is unwound: its finally blocks run, its using/with/try-with-resources resources are disposed, and its local variables go out of scope. If no handler matches, the exception is unhandled and the process (or thread, or request) dies.

Pick a language and a failure, then step through. Watch three things: the order of the console lines, when the file is closed relative to the handler, and what happens when nothing handles the exception.

What to take from the simulation:

  • finally runs on every exit: normal completion, return, and exceptions passing through. It is for cleanup only. A return inside finally silently discards an in-flight exception in Java, Python and JavaScript (C# forbids it with error CS0157; Python 3.14 warns, per PEP 765). Never return from finally.
  • The resource is closed before the outer handler runs. By the time main catches the IOException, the file opened in handle is already closed. Handlers can't inspect resources from frames that were unwound.
  • Inner handlers that don't match are invisible. handle catches only NotFound; for an IOException its catch is skipped, but its finally still runs.
  • Go has no unwinding for errors, only for panics. A returned error is a value; deferred calls run because the function returns, not because of the error. A panic unwinds the goroutine, running defers in LIFO order, until a deferred recover() stops it, or the program dies.

Cleanup that always runs

Files, sockets, locks, transactions and database connections must be released whatever happens. Each language has a construct that ties release to scope, so the release runs on success, on early return and on exceptions. Memory and GC explains why the garbage collector can't do this for you. This section covers the error-handling half: what happens when cleanup itself fails.

Language Construct Release order Cleanup throws while another error is in flight
C# using, await using, finally reverse of declaration the Dispose exception replaces the original, which is lost
Java try-with-resources reverse of declaration the close exception is added as suppressed to the original (getSuppressed())
Python with, contextlib.ExitStack reverse of entry the new exception propagates, with the original kept as __context__
Go defer LIFO whatever you do with Close()'s return value; defer f.Close() drops it
TypeScript using, await using (TS 5.2+), finally reverse of declaration a SuppressedError with .error (new) and .suppressed (original); plain finally replaces

Choose a language and a failure combination. The resources are opened A then B, so they close B then A. Watch the "lost forever" list: that is evidence you will not have during the incident.

The same two-resource copy in each language. Note which close error each version keeps.

public static async Task CopyAsync(string from, string to, CancellationToken ct)
{
    await using var src = File.OpenRead(from);     // disposed second
    await using var dst = File.Create(to);         // disposed first (LIFO)
    await src.CopyToAsync(dst, ct);
    await dst.FlushAsync(ct);                      // flush explicitly: surface write errors here,
}                                                  // not from DisposeAsync where they could mask another

static void copy(Path from, Path to) throws IOException {
    try (var in = Files.newInputStream(from);
         var out = Files.newOutputStream(to)) {    // closed in reverse: out, then in
        in.transferTo(out);
    } catch (IOException e) {
        for (Throwable s : e.getSuppressed())      // close() failures ride along here
            log.warn("also failed while closing", s);
        throw e;
    }
}

import shutil
from contextlib import ExitStack

def copy(src: str, dst: str) -> None:
    with open(src, "rb") as fin, open(dst, "wb") as fout:   # exits fout, then fin
        shutil.copyfileobj(fin, fout)

def concat(paths: list[str], dst: str) -> None:
    with ExitStack() as stack:                              # a runtime-sized set of resources
        out = stack.enter_context(open(dst, "wb"))
        for p in paths:
            shutil.copyfileobj(stack.enter_context(open(p, "rb")), out)

func Copy(dst, src string) (err error) {
    in, err := os.Open(src)
    if err != nil {
        return fmt.Errorf("open source: %w", err)
    }
    defer in.Close() // read-only: a Close error here tells us nothing

    out, err := os.Create(dst)
    if err != nil {
        return fmt.Errorf("create destination: %w", err)
    }
    defer func() {
        // Close flushes: for a file you wrote, its error means data loss. Join it, don't drop it.
        err = errors.Join(err, out.Close())
    }()

    if _, err = io.Copy(out, in); err != nil {
        return fmt.Errorf("copy: %w", err)
    }
    return nil
}

import { open } from "node:fs/promises";

// TS 5.2+ with lib "esnext.disposable"; Node 20+ FileHandle implements Symbol.asyncDispose.
async function copy(from: string, to: string): Promise<void> {
  await using src = await open(from, "r");     // disposed second
  await using dst = await open(to, "w");       // disposed first
  await dst.writeFile(await src.readFile());
}

// The pre-5.2 equivalent: nested try/finally, and a close() error replaces the original.
async function copyClassic(from: string, to: string): Promise<void> {
  const src = await open(from, "r");
  try {
    const dst = await open(to, "w");
    try { await dst.writeFile(await src.readFile()); }
    finally { await dst.close(); }
  } finally {
    await src.close();
  }
}

Make the important failure happen before cleanup For writable resources, call Flush()/Commit()/Sync() explicitly as the last step of the try body. Then a write failure surfaces as a normal exception with nothing else in flight, and Dispose/close has nothing left to fail on. This sidesteps the C# "dispose replaces the original" problem, and it's what tx.Commit() before the end of a using block already does for transactions.

Wrap with context, don't swallow

An error that reaches the top of a request should answer three questions: what were we trying to do (the operation and its identifiers), what went wrong at the bottom (the root cause, with its original type and stack trace), and how it got there (each layer's contribution). Each layer adds one line of context and passes the cause along. Russian dolls: the outer error says "place order 42", inside it "load customer 7", inside that the SqlException.

Pick a language and a strategy for every layer, then watch what the boundary can still decide. It needs the root cause to choose between 404 and 500, and it needs the chain to give the on-call engineer a useful log line.

// Repository: translate the driver's error into the domain's, keep it as InnerException.
catch (SqlException e) when (e.Number == 1205)   // deadlock victim
{

// Service: add what you were doing only if it adds meaning; otherwise let it pass untouched.
catch (OrderStoreBusyException e)

// Boundary: decide on the type, log the whole chain once. ToString() prints every InnerException.
catch (Exception e) when (e.GetBaseException() is SqlException { Number: 1205 })

    return Results.Problem(statusCode: 503);

// Repository

// Boundary: walk the chain instead of parsing messages.

    while (t.getCause() != null && t.getCause() != t) t = t.getCause();

// log.error("checkout failed", e) prints every "Caused by:" section with its stack trace.

Do

  • Add what you were doing and the identifiers involved: "load order 42", "GET /v1/rates".
  • Keep the original as the cause (inner, cause, from e, %w, { cause }).
  • Translate at layer boundaries: the domain shouldn't leak SqlException to callers that can't import it.
  • Decide by type or sentinel (errors.Is, instanceof, when), never by message text.

Careful

  • Rethrow unchanged (throw;, raise, return err) when your layer has nothing to add. Not every frame needs a wrap.
  • Don't put secrets or personal data in messages: they end up in logs, traces and sometimes HTTP responses.
  • Don't repeat the inner message in the outer one; the chain already prints it.
  • Translating can hide a type callers matched on. Keep it reachable (%w, cause) or translate deliberately.

Don't

  • Drop the cause: throw new X("failed") inside a catch.
  • Swallow: catch { }, except: pass, _ = err, an empty .catch(() => {}).
  • Return a fake success: [], 0, null, 200 OK for "I couldn't find out".
  • Reset the stack: throw e; in C#, %v instead of %w in Go, raise X(str(e)) in Python.

Where to catch: error boundaries

Most code should not catch at all. A catch belongs only where the code can do one of four things: recover (use a default, try another source), translate (turn a driver error into a domain error with context), retry (at one chosen layer), or report (at a boundary). Everywhere else, let it propagate.

A boundary turns "something failed" into a response for its world: an HTTP status and problem details for an API, a dead-letter for a queue message, a non-zero exit code for a CLI, a toast for a UI. It is also the one place that logs the error with full context. Each framework has a built-in hook for it; use it instead of try/catch in every controller action.

Log once, where the error is handled

The most common error-handling anti-pattern in real codebases is log and rethrow: every layer catches, logs, and throws again "just in case". One failure becomes five log entries, each with a partial stack trace, the alert counts five errors, and the one entry with the real context is buried. The rule: log where you handle (decide what to do), and nowhere else. Intermediate layers add context to the error itself, not to the log.

Compare the three strategies below, then raise the failure rate: log volume is a cost (ingestion is billed per GB) and a signal problem (alerts on noisy logs get muted).

A good error log entry, written once at the boundary, has:

  • A message about the operation, not the error: "checkout failed for cart {CartId}". The exception already says what went wrong.
  • The exception object, not e.Message: logging frameworks print the type, the whole cause chain and every stack trace (LogError(e, ...), log.error("...", e), log.exception(...), slog with "err", err, pino's { err }).
  • Correlation: the trace or request ID, so this line joins the distributed trace (see Observability).
  • Structured fields for the route, tenant and entity IDs, never passwords, tokens or full request bodies.
  • The right level: Error means "someone should look", so an expected 404 is Information or nothing, a handled and retried timeout is Warning, and an unhandled bug is Error.

Retry or fail fast?

Some failures go away if you ask again: a dropped connection, a 503 during a deploy, a deadlock victim, a 429 from a rate limiter. Most don't: a 400, a 404, a constraint violation or a bug gives the same answer every time, so retrying only adds latency and load. The skill is classifying the failure, then retrying the transient ones with backoff and jitter, in one layer, under a deadline.

Edit the sequence of server answers (the last one repeats), the attempt budget and the number of layers that retry. Try 503 503 503 503 503 with 3 layers, then 404, then 429 200.

Failure Transient? What to do
connection reset, DNS blip, 502, 503, 504 yes retry with exponential backoff and full jitter
429 Too Many Requests yes wait for Retry-After exactly; don't add to the overload
timeout maybe retry only if the operation is idempotent: the first attempt may have succeeded
500 Internal Server Error maybe the server has a bug or a dependency failed; retry once at most, only if idempotent
deadlock victim, serialization failure yes retry the whole transaction, not the last statement
optimistic concurrency conflict (409, stale version) yes, after re-reading reload, re-apply the change, save again
400, 401, 403, 404, 422, validation, constraint violation no fail fast: return the error to the caller
NullReferenceException, KeyError, nil dereference no (a bug) fail fast, fix the code

The rules that keep retries from making an incident worse:

  • Retry in one layer only, as close to the failing call as possible (the HTTP client pipeline or the SDK). The simulation's "layers that retry" input shows why: 3 layers × 5 attempts = 125 calls per user click against a dependency that is already struggling.
  • Back off exponentially with jitter. Without jitter, every client that failed at the same moment retries at the same moment, in synchronized waves.
  • Bound it by time, not just by count. Pass a deadline or cancellation token, and give up when it expires.
  • Make writes idempotent before you retry them: idempotency keys, upserts, "insert if not exists".
  • Stop retrying a dependency that is down. That is the circuit breaker's job. See Resilience and timeouts.

// No standard library helper; the loop is short enough to own.
func WithRetry(ctx context.Context, maxAttempts int, base time.Duration, op func(context.Context) error) error {
    var err error
    for attempt := 1; attempt <= maxAttempts; attempt++ {
        if err = op(ctx); err == nil || !IsTransient(err) {
            return err
        }
        if attempt == maxAttempts {
            break
        }
        backoff := base << (attempt - 1)                          // base * 2^(attempt-1)
        sleep := time.Duration(rand.Int64N(int64(backoff) + 1))   // full jitter, math/rand/v2
        select {
        case <-time.After(sleep):
        case <-ctx.Done():
            return errors.Join(err, ctx.Err())
        }
    }
    return fmt.Errorf("gave up after %d attempts: %w", maxAttempts, err)
}

func IsTransient(err error) bool {
    var ne net.Error
    var he *HTTPStatusError
    return (errors.As(err, &ne) && ne.Timeout()) ||
        (errors.As(err, &he) && (he.Code == 429 || (he.Code >= 502 && he.Code <= 504)))
}

async function withRetry<T>(op: (signal: AbortSignal) => Promise<T>, signal: AbortSignal,
                            maxAttempts = 4, baseMs = 200): Promise<T> {
  for (let attempt = 1; ; attempt++) {
    try {
      return await op(signal);
    } catch (e) {
      if (!isTransient(e) || attempt >= maxAttempts) throw e;
      await sleep(Math.random() * baseMs * 2 ** (attempt - 1), undefined, { signal });  // full jitter
    }
  }
}

Fail fast is the other half. For bugs and bad configuration, the earliest failure is the cheapest one:

  • Validate configuration at startup and refuse to start (ValidateOnStart() in .NET options, @Validated @ConfigurationProperties in Spring, a Pydantic BaseSettings, a Load() that returns an error in Go, a zod schema over process.env). A missing connection string should fail the deploy, not the first request at 3 a.m.
  • Guard arguments at public entry points: ArgumentNullException.ThrowIfNull(x), Objects.requireNonNull(x, "x"), if x is None: raise TypeError, if x == nil { return errNilX }. A bad argument is a bug in the caller; the stack trace should point at the call, not at a null three layers deeper.
  • Assert invariants that "can't happen", and crash with a clear message when they do (C# UnreachableException, Java IllegalStateException/AssertionError, Python assert_never, Go panic, TS never checks).

Validation errors are not exceptions

"The email is malformed" is not exceptional: it is one of the most common things an API does. It has a different audience from a crash (the user, not the on-call engineer), a different status code (400/422, not 500), a different log level (usually none), and a different shape: the user wants every problem at once, not the first one. So validation should collect failures into a value and return it, and the boundary turns it into a problem details response.

Type in a sign-up request. Switch between collecting all errors and throwing on the first, and take the database down to see how an environmental failure is reported differently from a validation failure.

Four kinds of "no" an API gives, and how each one should look on the wire:

Failure Example Status Body Log level
Malformed request invalid JSON, wrong types 400 problem details none or Debug
Validation email format, age below 18 400 (FastAPI: 422) problem details with an errors map per field none
Business rule or state insufficient funds, order already shipped 409 or 422 problem details with a specific type URI Information
Not found / not allowed unknown ID, wrong tenant 404, 403 problem details none or Information
Rate limited too many requests 429 + Retry-After problem details Warning (aggregated)
Dependency down database, downstream API 503 + Retry-After generic problem details + traceId Warning or Error
Bug null dereference 500 generic problem details + traceId, no stack trace Error

The error contract of an API is as much a part of its interface as the success shape. Use RFC 9457 problem details (application/problem+json) for every error, give each kind of business failure a stable type URI that clients can switch on, and never leak stack traces, SQL or internal hostnames. Panics, fatal errors and crash-only design

Some failures mean the process itself can no longer be trusted: memory is exhausted, the stack overflowed, an invariant in shared state is broken, or a required secret is missing at startup. Catching these and carrying on turns a crash, which is loud, quick and recoverable, into silent corruption, which is none of those. The better design is crash-only: make the process safe to kill at any moment (transactions, idempotent consumers, durable queues), let it die on fatal errors, and let a supervisor (Kubernetes, systemd, App Service, a process manager) start a clean one. Erlang made this a philosophy: "let it crash".

Language Fatal mechanism Do cleanup handlers run? Last-chance hook
C# Environment.FailFast(msg); StackOverflowException can't be caught no: writes the event log and a dump, then terminates AppDomain.CurrentDomain.UnhandledException (log only; can't cancel termination)
Java Error subclasses (OutOfMemoryError); System.exit; Runtime.halt exit: shutdown hooks yes, finally no; halt: nothing Thread.setDefaultUncaughtExceptionHandler
Python sys.exit() raises SystemExit; os._exit() sys.exit: yes (finally, with, atexit); os._exit: no sys.excepthook, threading.excepthook, loop.set_exception_handler
Go panic (unwinds the goroutine); log.Fatal/os.Exit panic: defers run; os.Exit/log.Fatal: defers are skipped none for panics in other goroutines: they always kill the process
TypeScript (Node) an uncaught exception; process.exit() process.exit() cuts off pending async work (log flushes) process.on("uncaughtException"), process.on("unhandledRejection")

Go deserves its own note. panic is for programmer errors (nil map write, impossible switch case), never for "file not found". A library must not let a panic escape its API: if it uses panics internally (as the regexp parser does, per Effective Go), it recovers at the package boundary and returns an error. And recover only works in a deferred function in the same goroutine as the panic, which is why one panicking goroutine takes down a whole server: see the async simulation below.

Let it crash when

  • Startup configuration or dependencies are wrong: fail the deploy, not the first request.
  • An invariant of shared state is broken (balances diverged, cache corrupted): continuing spreads the damage.
  • The runtime says so: OutOfMemoryError, stack overflow, a panic you didn't expect.
  • A worker can be restarted cleanly and its unit of work retried (queue redelivery, idempotent handlers).

Don't crash for

  • One bad request: the boundary returns 4xx/5xx and the process serves the next one.
  • One bad message: retry it, then dead-letter it; don't take the consumer down for everyone.
  • A dependency outage: degrade, shed load, open a circuit; a crash loop makes recovery slower.
  • Code you don't own throwing on a background thread: contain it at that thread's entry point.

Async errors: where does the exception go?

In synchronous code an exception has an obvious destination: the caller. In asynchronous code the caller may have already returned. The failure is stored in a Task, Future, Promise or channel, and it reaches your code only if something awaits or inspects that object. If nothing does, each runtime does something different, from "nothing at all" to "kill the process". Concurrency and Async covers the scheduling model; this section is only about where the errors go.

Pick a language and a pattern. Each lane is a task; the bottom lane is the runtime. A failure is "observed" only when it reaches code that can act on it.

Not awaited / not joined Several fail at once Crashes the process
C# stored in the Task; UnobservedTaskException at GC, no crash (since .NET 4.5) await Task.WhenAll throws the first; task.Exception holds all async void throwing; any exception on a raw Thread
Java CompletableFuture: lost silently; executor.submit: lost in the Future allOf(...).join() throws one CompletionException nothing by default; an uncaught exception kills only its thread
Python "Task exception was never retrieved" logged at GC gather raises the first, the rest are dropped; TaskGroup raises an ExceptionGroup with all nothing by default; exceptions in threads are printed
Go an error nobody receives is simply gone errgroup returns the first and cancels the rest; errors.Join keeps all a panic in any goroutine without its own recover
TypeScript (Node) unhandledRejection; fatal since Node 15 Promise.all rejects with the first; allSettled reports all unhandled rejections (default), uncaught exceptions

The rules are the same in every language:

  1. Every task has an owner who awaits it. If the caller can't wait, hand the work to something with a lifetime and an error policy: a background queue, a hosted service, a supervisor.
  2. Fire-and-forget still needs a handler, attached at the moment you start it.
  3. Prefer structured concurrency (TaskGroup, errgroup, Task.WhenAll with inspection): child tasks can't outlive the scope, and their failures surface at its end.
  4. Report all failures, not just the first, when they are independent. The second failure is often the clue.
  5. Propagate cancellation, and don't log OperationCanceledException/CancelledError/context.Canceled as errors when the caller cancelled. See cancellation.

        }
    }()
    if err := sendWelcome(context.WithoutCancel(ctx), userID); err != nil {
        slog.Error("welcome email failed", "user", userID, "err", err)
    }
}()

// Several at once: the first error cancels the rest.
g, ctx := errgroup.WithContext(ctx)
for _, id := range ids {
    g.Go(func() error { return load(ctx, id) }) // Go 1.22+: id is per-iteration
}
if err := g.Wait(); err != nil {
    return fmt.Errorf("load orders: %w", err)
}

// Fire and forget, done right: the handler is part of the same expression.
void sendWelcome(user).catch((err) => logger.error({ err, userId: user.id }, "welcome email failed"));

// Several at once: wait for all, report every failure.
const results = await Promise.allSettled(ids.map((id) => load(id)));
const failures = results.flatMap((r) => (r.status === "rejected" ? [r.reason] : []));
if (failures.length) throw new AggregateError(failures, `${failures.length} of ${ids.length} loads failed`);
// Lint with @typescript-eslint/no-floating-promises so a missing await fails the build.

Throw, return an error, or return a Result?

Every section above comes down to one decision you make for each failure a function can produce. Four questions settle it, in this order:

  1. Is it a bug? A null argument, an index out of range or an impossible state means the code is wrong, and no caller can handle that. Throw (or panic in Go) and fix the code.
  2. Can the process continue safely? If not, crash: see panics.
  3. Is it an expected outcome the caller must decide about? "Insufficient funds" or "slug already taken" belongs in the signature: a Result, a Go error, or at least a documented TryX method. If the caller usually can't do anything except pass it up (a disk is full, the database is down), it is an environmental failure: throw in C#/Java/Python/TS, return a wrapped error in Go, and let a boundary handle it.
  4. Is "not found" just absence? Then return null/Optional/None/(v, ok)/undefined, not an error.

Pick a situation and step through the questions; the table at the bottom shows the idiom in each language.

1 · BUG?Throw / panic

Guard clauses: ArgumentNullException, IllegalArgumentException, ValueError, panic, TypeError. Don't catch; fix.

2 · UNSAFE?Crash

FailFast, halt, os.Exit(1) at the top. The supervisor restarts a clean process.

3 · EXPECTED?In the signature

Result, Go error sentinel, TryX, checked exception. The caller must branch on it.

3 · ENVIRONMENT?Throw with context

Wrap once with what you were doing; one boundary logs, retries or maps it to a status.

4 · ABSENT?Option / null

"No row" is an answer, not a failure: T?, Optional, None, (v, ok), undefined.

Use… When Don't use it when
Exception (C#, Java, Python, TS) a bug; an environmental failure most callers pass up; a constructor that can't build a valid object the failure is a normal outcome in a hot loop (parsing user input: exceptions cost microseconds each) or the caller must always handle it
Checked exception (Java) a recoverable condition the immediate caller can really act on it crosses a lambda, a stream or a layer that can only rethrow it
Go error every failure that isn't a bug the function can't fail: don't add an error "just in case"
Result / Either domain outcomes the caller must branch on; validation that collects several errors; pipelines of fallible steps the language fights it (a deep Result chain in Java with no ? operator) or the team won't use it consistently
TryX / (v, ok) / Optional one obvious failure mode with no detail needed: parse, lookup, dequeue the caller needs to know why it failed
Crash startup misconfiguration, broken invariants, runtime-fatal conditions one bad request, message or dependency

Consistency beats perfection A codebase that throws for environmental failures and returns a Result for domain outcomes, everywhere, is easier to work in than one where each team picked the "best" mechanism per module. Write the policy down: which exceptions the boundary maps to which status, which domain operations return Result, and where logging happens.

Pitfalls and war stories

The catch that ate the outage A Java repository wrapped every call in catch (Exception e) { return Collections.emptyList(); }. When the database password rotated, search returned "no results" for six hours: no errors, no alerts, just a dip in sales that someone eventually noticed. Fix: catch only what you can handle; let the boundary turn the rest into a 500 that pages someone.

The return in finally A Python helper had return default inside finally "to always return something". That return silently discarded every exception from the try, including KeyboardInterrupt. C# forbids it (CS0157); Java allows it with a lint warning; Python 3.14 warns about it (PEP 765). Fix: never return, break or throw out of a finally.

throw ex erased the crime scene A C# service logged NullReferenceException at OrderController.Post line 41: the line of the throw ex; rethrow, not the line that failed eleven frames deeper. Fix: throw; to rethrow, or throw new OrderException("…", ex) to add context; never throw ex;.

The same error, logged five times Each layer did log.error(e); throw e;. One timeout produced five stack traces, five alerts and a dashboard that counted five failures. During an incident, nobody could tell how many requests were actually failing. Fix: add context while propagating; log once at the boundary (try the "log and rethrow" strategy in the boundary simulation).

The goroutine that killed the API A Go handler started go audit(r) and the audit code dereferenced a nil field for one rare tenant. The recover middleware protected the handler's goroutine, not this one, so the whole server restarted, dropping every in-flight request, a dozen times an hour. Fix: every go statement gets its own defer recover(), or the work goes to a queue.

Retrying a payment that had succeeded A client retried POST /charges after a 30-second timeout. The first request had succeeded; it was just slow. Customers were charged twice. Fix: retry only idempotent operations, or send an idempotency key the server deduplicates on; see resilience.

Checklist

  • [ ] Every catch block either handles the error (recover, retry, translate, compensate) or doesn't exist.
  • [ ] No empty catch blocks, no catch (Exception) returning a default, no bare except:, no _ = err in Go.
  • [ ] Rethrows preserve the original: throw;, throw new X(msg, e), raise … from e, %w, { cause }.
  • [ ] Wrapping adds what this layer was doing (IDs, file names, operation), not "error occurred".
  • [ ] One boundary per entry point (HTTP, message consumer, job, CLI) maps errors to responses and logs once.
  • [ ] Clients get Problem Details with a stable type, never a stack trace.
  • [ ] Validation returns all field errors as 400/422 and never reaches the exception path.
  • [ ] Resources are released with using/try-with-resources/with/defer/await using, not manual close calls.
  • [ ] Retries happen in one layer only, only for transient errors on idempotent operations, with backoff, jitter and a budget.
  • [ ] Every async task is awaited or owned; fire-and-forget attaches a handler; Go goroutines recover their own panics.
  • [ ] Cancellation is propagated and not logged as an error.
  • [ ] Startup validates configuration and fails fast; os.Exit/FailFast live only at the top.
  • [ ] Tests cover the failure paths: the wrapped message, the mapped status, and that cleanup ran.

Self-check

A try block returns 1 and its finally block sets the returned variable to 2. What does the method return in C# and Java?
  1. The return value is evaluated and stored when the return statement runs; finally runs afterwards and changing the local variable doesn't change the stored value. (If finally itself executed return 2, Java and Python would return 2 and discard any exception; C# doesn't allow it.)
In Go, why does errors.Is(err, fs.ErrNotExist) work through three layers of wrapping but err == fs.ErrNotExist doesn't?

Each fmt.Errorf("...: %w", err) creates a new error value that contains the previous one. == compares only the outer value. errors.Is follows Unwrap() down the chain (and through errors.Join trees) until it finds a match. Wrapping with %v instead of %w breaks the chain: the text survives but errors.Is can't see the cause.

A service catches Exception, logs it, and rethrows in the repository, the service and the controller. What's wrong, and what's the fix?

Each failure is logged three times, which inflates error counts and alerts and hides how many requests really failed. Only the boundary has the full context (request ID, user, route) and knows the final outcome. Inner layers should add context by wrapping and let it propagate; the boundary logs once and maps it to a response.

Name the two C# patterns that let an async exception escape to nowhere or crash the process.

Fire-and-forget (_ = SaveAsync();): the exception is stored in a Task nobody awaits and is only reported to TaskScheduler.UnobservedTaskException when it is garbage collected. And async void: there is no Task to store it in, so it is rethrown on the synchronization context or thread pool and crashes the process. Use async Task and await it, or hand the work to an owner such as a background queue.

Should a "username already taken" check throw an exception?

No. It is an expected domain outcome the caller must handle (show a message, suggest a name). Return it in the signature (a Result, a validation error, a Go sentinel error) and map it to a 409 or 422 at the API boundary. Exceptions are for bugs and for environmental failures that most callers just pass up.

Why are os.Exit and log.Fatal dangerous deep inside a Go program?

They terminate immediately without running deferred calls, so files aren't flushed, transactions aren't rolled back and locks aren't released. Libraries can't be reused by callers who want to handle the error. Return an error and call os.Exit(1) only in main (or a run() error pattern).

An HTTP call fails with a 400. Should the client retry it?

No. A 400 means the request itself is wrong; it will fail the same way every time. Retry only transient failures (timeouts, connection resets, 408, 429, 502, 503, 504) on idempotent operations, with backoff and jitter. Fail fast on 4xx (except 408/429) and on bugs.

Python's asyncio.gather(a(), b()) and both coroutines fail. What do you see, and how does TaskGroup differ?

gather raises the first exception; the second is stored in its task and at best logged later as "exception was never retrieved", and the other tasks keep running. asyncio.TaskGroup (3.11+) cancels the siblings on the first failure and raises an ExceptionGroup containing all the failures, which you handle with except*.

DecideBug → throw. Unsafe → crash. Expected → in the signature. Environment → throw with context. Absent → Option.
RethrowC# `throw;` · Java `new X(msg, e)` · Python `raise … from e` · Go `%w` · TS `{ cause }`.
InspectC# `catch when` · Java `getCause()` · Python `__cause__` · Go `errors.Is/As` · TS `instanceof` on `unknown`.
Cleanup`using` · try-with-resources · `with` · `defer` · `await using`. Never return or throw out of finally.
BoundaryOne per entry point: map to Problem Details, log once with request ID, never leak stack traces.
RetryTransient + idempotent only, one layer, exponential backoff with jitter, a budget. Otherwise fail fast.
