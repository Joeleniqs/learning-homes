PERFORMANCE

The Performance Cadence

The measure → profile → hypothesise → change → verify loop, benchmarking done right (BenchmarkDotNet, JMH, go test -bench, pyperf, tinybench), and setting budgets.

Intermediate → Advanced~60 min studyUpdated 2026-11-03

The problem: speed work without a loop

A team gets a ticket: "the orders page is slow". Someone is sure the JSON serializer is to blame, so they spend two weeks rewriting it with hand-tuned buffers. The serializer gets 3× faster. The page does not get noticeably faster, because the serializer was 6% of the request and the real cost was 31 sequential database round trips. Months later a refactor quietly brings back an N+1 query, and nobody notices until a customer complains.

Each step in that story is a skipped part of one loop. Nobody wrote down a goal. Nobody measured a baseline or profiled. The change was not tied to a hypothesis that could be proved wrong, and the win had no guard. Performance work is a cadence, not a talent. Run the loop and you get a faster system, along with proof of why it is faster.

The rule. Never optimise without (1) a numeric goal, (2) a profile that points at the cost, and (3) a benchmark that proves the change helped. Make one change per loop, keep it only if the statistics say it is real, then add a guard so it stays fixed.

Recognize that you are skipping the cadence when

  • Someone says "I think X is slow" and nobody has a flame graph or trace.
  • A PR says "performance improvements" and changes six things at once.
  • Results are a single number ("it took 412 ms") with no runs, no spread and no percentile.
  • The dashboard shows average latency only.
  • A fix from last quarter has silently regressed.

The cadence at a glance

Here is the whole loop run on a simulated endpoint. Watch each component's bar shrink. Notice the change that gets reverted because the statistics said it did nothing, and notice where the loop stops even though ideas are left. Change the target or the noise and run it again.

1 · GOALA number users feel

p95/p99 latency, throughput, memory or cost, at a stated load. Not "faster".

2 · MEASUREBaseline with spread

Same environment, realistic data, many runs. Record a distribution, not a value.

3 · PROFILEFind the widest cost

Flame graphs for CPU, traces for waiting, allocation profiles for GC.

4 · HYPOTHESISPredict before coding

"Batching cuts DB from 155 to ~40 ms because of 31 round trips."

5 · CHANGEOne variable

One commit per idea, so the result is attributable.

6 · VERIFYStatistics, not vibes

Compare distributions. Keep it only if it is significant and matches the prediction.

7 · GUARDLock in the win

A CI benchmark gate or a deterministic budget test (allocations, queries).

8 · REPEATThe profile changed

Fixing the top item reshuffles the ranking. Measure again.

1 · Define the goal: SLOs, percentiles and why averages lie

A performance goal has four parts: a metric (latency, throughput, memory, cost), a statistic (p95, p99, max), a threshold, and a load. For example: "GET /orders p95 ≤ 140 ms and p99 ≤ 400 ms at 200 req/s, error rate < 0.1%". A Service Level Objective (SLO) is that sentence with a time window ("over 28 days").

Latency is never a bell curve. It has a hard floor (the fast path) and a long tail (cache misses, GC pauses, lock waits, retries, cold connections). Step through the visualizer below to see why the mean misleads, what a tail regression looks like, how fan-out turns a backend's p99 into a page's typical case, and how a load tester can hide a stall completely (coordinated omission).

Insight Percentiles answer "how bad is it for the unluckiest X% of requests?", which is the question users and SLOs ask. The mean answers "how much total time did we spend?", which matters for capacity and cost. Use the mean for throughput math. Use percentiles for anything a human waits for.

Pitfall: you cannot average percentiles The average of ten hosts' p99 is not the fleet p99. Neither is a p99 of per-minute p99s. To combine, merge the histograms and then compute the percentile. That is why HdrHistogram, OpenTelemetry exponential histograms, Prometheus histograms (not summaries) and DDSketch exist. Record histograms at the source; derive percentiles at query time.

2 · Measure the baseline, then profile

Measure the way production runs: Release build, production-like data volume, the same hardware class, the target load, and enough runs to see the spread. Write the baseline down. Every later number is compared against it.

Profile to find where the time goes. A sampling profiler interrupts the program many times a second and records the call stack. A flame graph folds identical stacks together. The width of a box is its share of samples, and the y-axis is stack depth. Step through one being built from 23 samples, then look for the cost that hides by being spread across several callers.

CPU (on-CPU) profile

Samples threads that are running. Answers "what burns cycles?". Use it for hot loops, serialisation, regex, hashing and allocation-heavy code. Tools: dotnet-trace, async-profiler -e cpu, pprof CPU, py-spy, --cpu-prof.

Wall-clock / off-CPU profile

Samples threads whether they run or wait (locks, I/O, sleeps). A request that is slow because it waits on the database looks idle in a CPU profile. Use async-profiler -e wall, py-spy --idle, dotnet-trace thread time, Go's block and mutex profiles, or distributed tracing.

Instrumenting profiler

Wraps every function call with timing code. Exact call counts, but the overhead distorts small functions, so they look slower than they are. cProfile is this kind. Use it to count calls, and confirm timings with a sampler.

Tip: profile the right thing Profile Release / optimised builds with symbols. Inlined functions vanish from stacks, so a function can "disappear" into its caller. Older JVM profilers only sampled at safepoints (safepoint bias), so hot loops were blamed on the wrong line. async-profiler and JFR avoid this. In production, continuous profilers sample at about 1% overhead and show the real workload, not the one you guessed.

3 · Hypothesis: let Amdahl's law pick the target

Before you write code, write a falsifiable sentence: "Batching the 31 queries into one should cut DB time from 155 ms to about 40 ms, because the trace shows 31 sequential round trips of ~5 ms." The prediction lets you tell a real cause from a lucky coincidence.

The profile bounds the prize. If a part takes fraction p of the time and you make it s times faster, the whole thing becomes 1 / ((1 − p) + p / s) times faster. The best you can ever do is 1 / (1 − p), which is what you get if you delete that part entirely.

Insight A 2× speed-up of the 60% part (1.43× overall) beats deleting the 10% part (1.11× at best). Rank ideas by profile share × plausible local speed-up ÷ effort, not by how fun or clever they are. Amdahl also applies to parallelism: the serial fraction caps how much more cores can help.

4 · Change one thing, then verify with statistics

Change one variable per experiment. If you upgrade a library, change a pool size and rewrite a loop in one PR, a 10% improvement could be one 25% win hiding a 15% regression.

Then verify. A benchmark is a measurement experiment, and measurements have noise. The visualizer below runs a simulated micro-benchmark and shows each classic trap: JIT warm-up tiers, noisy neighbours, outliers, confidence intervals, an A/B comparison with Welch's t-test, too few runs, and dead-code elimination.

Every harness exists to handle those traps for you. Compare the hand-rolled version with a harness in C#.

using System.Text;
using BenchmarkDotNet.Attributes;
using BenchmarkDotNet.Running;

[MemoryDiagnoser]                                  // adds Gen0 collections and bytes allocated per op
public class JoinBench
{
    private int[] _items = [];

    [Params(10, 1000)]                             // check how the cost scales, not one size
    public int N;

    [GlobalSetup]
    public void Setup() => _items = Enumerable.Range(0, N).ToArray();

    [Benchmark(Baseline = true)]
    public string Concat()
    {

        foreach (var x in _items) s += x + ",";
        return s;                                  // returning the result defeats dead-code elimination
    }

    [Benchmark]
    public string Builder()
    {
        var sb = new StringBuilder();
        foreach (var x in _items) sb.Append(x).Append(',');
        return sb.ToString();
    }
}

public static class Program
{
    // dotnet run -c Release -- --filter *JoinBench*
    public static void Main(string[] args) =>
        BenchmarkSwitcher.FromAssembly(typeof(Program).Assembly).Run(args);
}

BenchmarkDotNet launches a separate process, runs pilot and warm-up iterations, picks an iteration count, removes outliers, and reports the mean, error (half the 99.9% confidence interval), standard deviation, a ratio against the baseline, and allocated bytes. On one laptop, N = 1000 concatenation took ~330 µs and 3.8 MB per call against ~31 µs and 17 KB for StringBuilder.

5 · Guard against regressions in CI

A win without a guard lasts until the next refactor. There are two kinds of guard, and you want both.

Deterministic budget tests catch most real regressions (an N+1 query, an accidental allocation per item) with zero flakiness:

[Fact]
public void Serialize_order_stays_within_allocation_budget()
{
    var order = TestData.Order(lines: 20);
    OrderSerializer.Serialize(order);                          // warm up: JIT, static caches

    long before = GC.GetAllocatedBytesForCurrentThread();
    OrderSerializer.Serialize(order);
    long allocated = GC.GetAllocatedBytesForCurrentThread() - before;

    Assert.True(allocated <= 2_048, $"Serialize allocated {allocated} B; budget is 2048 B");
}

@Test

Runtimes behave differently, and that changes how you benchmark them:

JIT runtimes: .NET, JVM, V8

Code starts interpreted or in a quick tier, then is recompiled with optimisations once it is hot (.NET tier-0 → tier-1 with dynamic PGO; HotSpot C1 → C2; V8 Ignition → Sparkplug → Maglev → TurboFan). Warm-up is mandatory, results depend on what ran before (profile pollution), and the optimiser can delete unused work. Use BenchmarkDotNet or JMH, which fork fresh processes.

Ahead-of-time: Go, Native AOT

No tiering, so the first call is close to the steady state. You still need warm CPU caches and many iterations, and the garbage collector shows up as variance. Watch allocs/op. Inlining and escape analysis decide whether a value lives on the heap: go build -gcflags=-m shows the decisions.

Interpreted: CPython

Each bytecode has a fixed overhead, so the fastest Python is usually "do less Python": push loops into C (built-ins, str.join, NumPy). 3.11+ specialises hot bytecodes, 3.13 has an experimental JIT, and the GIL limits CPU parallelism in threads. pyperf spawns worker processes and calibrates loops for you.

One micro-benchmark, five languages

Here is the same experiment in every stack: build a comma-separated string from 1,000 integers, comparing naive += concatenation with a builder or join. Each version returns or sinks the result so the optimiser cannot delete the work.

// dotnet add package BenchmarkDotNet; dotnet run -c Release -- --filter *JoinBench*
[MemoryDiagnoser]
public class JoinBench
{
    private int[] _items = [];

    [GlobalSetup]
    public void Setup() => _items = Enumerable.Range(0, 1000).ToArray();

    [Benchmark(Baseline = true)]
    public string Concat()
    {
        var s = "";
        foreach (var x in _items) s += x + ",";
        return s;
    }

    [Benchmark]
    public string Builder()
    {
        var sb = new StringBuilder();
        foreach (var x in _items) sb.Append(x).Append(',');
        return sb.ToString();
    }
}

// JMH: mvn archetype jmh-java-benchmark-archetype; java -jar target/benchmarks.jar JoinBench -prof gc
@BenchmarkMode(Mode.AverageTime)
@OutputTimeUnit(TimeUnit.MICROSECONDS)
@Warmup(iterations = 5, time = 1)
@Measurement(iterations = 10, time = 1)
@Fork(3)                                   // three fresh JVMs: JIT decisions differ per process
@State(Scope.Benchmark)
public class JoinBench {
    int[] items;

    @Setup
    public void setup() { items = IntStream.range(0, 1000).toArray(); }

    @Benchmark
    public void concat(Blackhole bh) {
        String s = "";
        for (int x : items) s += x + ",";
        bh.consume(s);                     // Blackhole: the JIT cannot prove the result is unused
    }

    @Benchmark
    public String builder() {              // returning a value is an implicit Blackhole
        StringBuilder sb = new StringBuilder();
        for (int x : items) sb.append(x).append(',');
        return sb.toString();
    }
}

# pip install pyperf; python bench.py -o new.json; python -m pyperf compare_to old.json new.json
import pyperf

ITEMS = list(range(1000))


def concat(items):
    s = ""
    for x in items:
        s += str(x) + ","
    return s


def join(items):
    return "".join(f"{x}," for x in items)


runner = pyperf.Runner()       # spawns worker processes, calibrates loops, reports mean ± std dev
runner.bench_func("concat", concat, ITEMS)
runner.bench_func("join", join, ITEMS)

// join_test.go; go test -bench=. -benchmem -count=10 > new.txt; benchstat old.txt new.txt
package join

import (
    "strconv"
    "strings"
    "testing"
)

var sink string // package-level sink: the compiler cannot delete the work

func items(n int) []int {
    xs := make([]int, n)
    for i := range xs {
        xs[i] = i
    }
    return xs
}

func BenchmarkConcat(b *testing.B) {
    xs := items(1000) // setup before b.Loop is not timed
    b.ReportAllocs()
    for b.Loop() { // Go 1.24+: replaces for i := 0; i < b.N; i++
        s := ""
        for _, x := range xs {
            s += strconv.Itoa(x) + ","
        }
        sink = s
    }
}

func BenchmarkBuilder(b *testing.B) {
    xs := items(1000)
    b.ReportAllocs()
    for b.Loop() {
        var sb strings.Builder
        for _, x := range xs {
            sb.WriteString(strconv.Itoa(x))
            sb.WriteByte(',')
        }
        sink = sb.String()
    }
}

// npm i -D tinybench; npx tsx bench.ts
import { Bench } from "tinybench";

const items = Array.from({ length: 1000 }, (_, i) => i);
export let sink = "";

const bench = new Bench({ time: 1000, warmupTime: 250 });
bench
  .add("concat", () => {
    let s = "";
    for (const x of items) s += x + ",";
    sink = s;
  })
  .add("join", () => {
    sink = items.map((x) => x + ",").join("");
  });

await bench.run();
console.table(bench.table());   // ops/s, average time, margin of error, samples

Insight: the "obvious" answer depends on the runtime In .NET, Java and Go, strings are immutable and += copies everything so far, so the loop is O(n²) in bytes copied. On one laptop the C# version was about 10× slower and allocated 230× more. In CPython, += on a string with a single reference is resized in place, so it was only ~1.7× slower than join. In V8, += builds a rope and beat map().join() by about 2×. Same idea, three different verdicts. That is why you measure instead of applying folklore.

Macro benchmarks and load testing

A micro-benchmark tells you a function got faster. Only a load test tells you whether the service meets its SLO at the target rate, and where it falls over. There are two load models, and choosing the wrong one hides exactly the stalls you are hunting (coordinated omission, from the latency visualizer above).

Why does latency explode near capacity? Queueing. Step utilisation up for a service with 4 workers and watch the mean barely move while the p99 takes off past the knee:

The same open-model load test, with the SLO written as pass/fail thresholds, in five tools:

Tip: a load-test plan Ramp the arrival rate in steps (50, 100, 150 … req/s) and hold each step for several minutes. Plot p50/p95/p99 against rate to find the knee. Run a soak test (hours at target load) for leaks and slow drift, and a spike test for autoscaling and cold starts. Test from a machine that is not itself the bottleneck: check the load generator's CPU.

Latency numbers every programmer should know

These are order-of-magnitude figures for modern server hardware. Exact values vary by a factor of 2 or 3. What matters is the ratios: a network round trip costs as much as thousands of memory reads.

Operation Approx. time If 1 ns were 1 second Design consequence
L1 cache reference ~1 ns 1 s Sequential, compact data (arrays of structs) is fast.
Main memory reference ~100 ns 1.7 min Pointer chasing (linked lists, object graphs) costs 100× an L1 hit.
Compress 1 KB ~2 µs 33 min Compressing before sending over a network is almost always worth it.
Random 4 KB read, NVMe SSD ~50 µs 14 h Indexes and caches exist to avoid storage reads.
Round trip in one datacenter ~500 µs 6 days 31 sequential queries ≈ 15 ms of pure waiting. Batch, join, or parallelise.
HDD seek ~5 ms 2 months Spinning disks want sequential access (logs, LSM trees).
Round trip, US ↔ Europe ~150 ms 4.8 years Put data near users. Avoid chatty cross-region calls.

Performance budgets

A budget turns a goal into an engineering constraint that each team owns. Split the end-to-end target across the components on the critical path, and keep some headroom.

Budgets come in several currencies. Choose the ones your users and your bill actually feel:

Latencyp95 / p99 per endpoint, at a stated load. The SLO itself.
Throughputreq/s per instance at the latency SLO (not at 100% CPU).
ResourcesCPU ms per request, bytes allocated per op, memory RSS, connections.
Web vitalsAt p75 of page loads: LCP ≤ 2.5 s, INP ≤ 200 ms, CLS ≤ 0.1.
PayloadJavaScript kB (gzip) per route, image weight, API response size.
Cost$ per million requests. Often the budget that finally gets attention.

When NOT to optimise

Donald Knuth's famous line is usually quoted half-way. The full sentence is: "We should forget about small efficiencies, say about 97% of the time: premature optimization is the root of all evil. Yet we should not pass up our opportunities in that critical 3%." The cadence is how you find the 3%.

Do it up front: these are design, not optimisation

Pick the right algorithm and data structure (O(n log n), not O(n²)). Avoid N+1 queries. Page and stream large results. Use async I/O for I/O-bound services. Add indexes for known query shapes. Set timeouts. Changing these later is expensive, and they rarely cost readability.

Do NOT do it without a profile

Micro-tuning (manual loop unrolling, object pooling, unsafe, stackalloc, bit tricks, caching every call). Rewriting in a "faster" language. Adding a cache "just in case" (now you have invalidation bugs). Parallelising code that is waiting on one database.

Stop when the goal is met

Past the goal, every gain costs engineering time and usually clarity, and buys nothing users notice. Record the remaining ideas with their estimated prize and move on. Re-open them when the goal or the load changes.

Pitfalls and war stories

The Debug-build benchmark A team "proved" a new parser was 4× faster. Both versions had been run in Debug with the debugger attached, where the old code's small methods were never inlined. In Release the difference was 6%. Benchmark Release builds with no debugger attached. BenchmarkDotNet refuses to run otherwise, for good reason.

The benchmark that measured nothing A Go hashing benchmark reported 0.3 ns/op, which is one clock cycle. The result was never used, so the compiler removed the call. Anything below about a nanosecond per op deserves suspicion. Sink the result to a package-level variable, return it from a BenchmarkDotNet method, or consume it in a JMH Blackhole.

The load test that could not see the outage A closed-loop test with 50 threads reported p99 = 80 ms. Production had 2-second pauses every few minutes during GC. Each pause blocked all 50 test threads, so only 50 slow samples were recorded against hundreds of thousands of fast ones. An open-model test (wrk2, k6 arrival-rate) at the same rate reported p99 = 1.9 s.

The averaged dashboard An API's average latency stayed flat at 45 ms through a release that doubled the p99 for the largest tenants: their requests had moved from the fast path to the slow path. Alert on percentiles from merged histograms, and break them down by the dimension that matters (tenant, endpoint, region).

Optimising the benchmark, not the product A micro-benchmark with a 100-element input fits in L1 cache. Production lists had 2 million elements, and the "optimised" layout was slower once data came from RAM. Benchmark realistic sizes (use [Params], @Param, or sub-benchmarks) and confirm with a macro benchmark.

Checklist

  • [ ] A written goal: metric, percentile, threshold and load (and, for SLOs, a time window).
  • [ ] Baseline measured in a production-like environment, as a distribution with enough runs.
  • [ ] A profile (CPU and wall-clock or trace) identifies the widest cost before any code changes.
  • [ ] A written hypothesis with a predicted number. Amdahl confirms that the prize is worth it.
  • [ ] Exactly one change per experiment, on its own branch or commit.
  • [ ] Verified with a harness (BenchmarkDotNet, JMH, testing.B + benchstat, pyperf, tinybench) and a significance test or non-overlapping intervals.
  • [ ] Load tests use an open model at the target arrival rate, with SLO thresholds that fail the build.
  • [ ] A guard: a deterministic budget test (allocations, queries, bytes) plus a timing gate where the runners allow it.
  • [ ] Re-profiled after each change. Stopped when the goal was met.

Quiz

Your service's mean latency is 50 ms and the SLO is "p99 ≤ 300 ms". Can you tell from the mean whether you meet it?

No. Latency is right-skewed, and the mean says nothing about the tail. The latency visualizer has a mean of ~51 ms with a p99 of ~358 ms. Only a histogram (or the raw samples) can answer a percentile question.

Parsing takes 25% of a request. A colleague makes parsing 5× faster. What is the best-case overall speed-up?

Amdahl: 1 / (0.75 + 0.25/5) = 1 / 0.8 = 1.25×. Even deleting parsing entirely caps out at 1 / 0.75 ≈ 1.33×.

A flame graph shows no single wide plateau, but the function Regex.Match appears at the top of many thin towers. What view do you switch to, and why?

The bottom-up (callers, butterfly or "self by function") view. It sums self time per function across every call site, which shows that a function spread over many callers can be the biggest single cost.

Benchmark A: 120 ± 25 ns (n = 5). Benchmark B: 112 ± 24 ns (n = 5). Is B faster?

You cannot tell. The intervals overlap almost completely, and with n = 5 the t-test is inconclusive. Run more iterations and several process forks, interleave A and B, and compare with benchstat, pyperf compare_to or a Welch t-test.

Why does a closed-loop load tester under-report latency during a server stall?

Because it waits for each reply before sending the next request, it stops sending during the stall. The requests real users would have sent in that window are never made, so their long waits are never recorded. This is coordinated omission. Use an open model (fixed arrival rate) or correct the measurements to the intended send times.

CPU is at 45%, but p95 latency is 4× over budget. What kind of profile do you need?

A wall-clock or off-CPU profile, or a distributed trace. The time is spent waiting (database, locks, downstream calls, thread-pool starvation), and a CPU profile only sees threads that are running.
