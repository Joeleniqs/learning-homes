Memory, Allocation & Garbage Collection

Generational GC animated; .NET, JVM, Go and Python memory managers compared; allocation hot spots, Span/pooling, and leak hunting.

Intermediate → Expert~65 min studyBuilds on: Cross-Language Mental ModelsUpdated 2026-11-03

The problem: the service that was fast at 9 a.m. and slow by lunch

An order-pricing API is benchmarked before launch: p50 4 ms, p99 11 ms. In production it goes wrong in three different ways over three weeks.

  1. p99 drifts from 11 ms to 180 ms between deploys. CPU is fine. The GC log shows a gen2 (full) collection every 40 seconds that stops every request thread for 150 ms. The cause is a "temporary" List<PriceRow> of 200,000 rows per request. Arrays over 85,000 bytes go straight to the Large Object Heap, which is only collected together with gen2.
  2. Memory climbs 30 MB an hour until the pod is OOM-killed. Nobody allocates anything "big". A heap dump shows 1.9 million PriceChangedHandler delegates. Each request subscribed a short-lived object to a long-lived event and never unsubscribed. The GC was working perfectly: every one of those objects was still reachable.
  3. A "zero-copy" optimisation corrupts data. A developer added ArrayPool<byte>.Shared to cut allocations and returned the buffer before an await finished writing it. Another request rented the same array. One customer's invoice now contained the tail of another customer's invoice.

None of these are bugs in the garbage collector. All three come from not knowing where a value lives, how long it lives, and what the runtime does to reclaim it. This page builds that picture for C#, Java, Python, Go and TypeScript, and animates each collector until you can predict what it will do with your code.

The rule. Every heap allocation costs twice: once when you allocate it (cheap) and again when the GC has to find, copy or scan it (not cheap, and paid by someone else later). Make objects that die young or live forever, never "medium". Keep reachability under control, because a managed leak is just a reference you forgot. Release non-memory resources deterministically (using, try-with-resources, with, defer) and never rely on the GC to close a file. Optimise allocations only on paths a profile has shown to be hot.

Recognize a memory problem when

  • Latency percentiles have regular spikes that line up with GC events (the "sawtooth" in a heap graph has steep drops at the same moments).
  • The lowest point of the heap sawtooth rises over hours or days. That is a leak, even if each GC still frees plenty.
  • CPU time in the GC (% Time in GC, gc_cpu_fraction, JFR GC events) is above roughly 5–10% on a service.
  • Throughput drops as load rises, while CPU looks "busy" but app code is not on the flame graph.
  • A container is OOM-killed while the runtime thinks it has plenty of headroom (the GC did not know the container limit).

This is the memory chapter of the performance track. Performance Cadence covers how to measure (goals, profiles, benchmarks, statistics); this page covers what the runtime is doing underneath the numbers. Concurrency and Async covers threads and tasks, which are heap objects too. Pooling and batching as system-level patterns live in Performance Patterns. Value vs reference semantics are introduced in Language Mental Models and Types and Immutability.

Two places to put a value: stack and heap

Every running thread has a stack: a contiguous block of memory (typically 1 MB for a .NET or Java platform thread on 64-bit; a goroutine starts at 2 KB and grows on demand) that holds one frame per active method call. A frame stores the method's local variables, arguments and return address. Calling a method pushes a frame; returning pops it. Freeing a whole frame is one pointer move, so stack memory costs nothing to reclaim.

The heap is shared by all threads and holds anything that must outlive the call that created it, or whose size is not known at compile time. Heap memory is reclaimed later by a garbage collector (or reference counting in CPython), and that is where the cost hides.

A common myth is "value types live on the stack, reference types on the heap". The accurate rule is: a value type lives wherever its container lives. An int local is in the frame; an int field of a class is inside that object on the heap; a struct inside an array is inline in the array on the heap. A reference type's object is always on the heap (unless the JIT proves it never escapes, see escape analysis below); the reference to it lives wherever its container lives.

Step through each program and watch where every value goes:

  • C#: struct vs class. Copying the struct copies its fields, so changing the copy leaves the original alone. Copying the class copies only the reference, so both variables see the change. The struct cost no GC work.
  • C#: boxing. Assigning a struct to object copies it into a new heap box. Changing the box does not change the original. This is why ArrayList, Hashtable and string.Format("{0}", 42) allocated so much before generics and interpolation handlers.
  • C#: closure capture. A lambda that captures a local turns that local into a field of a hidden heap object (a "display class"), so the variable outlives the stack frame. The same happens in Java (captured effectively-final values are copied into the lambda object), Go, Python and JavaScript.
  • Go: escape analysis. Returning &p from a function forces p to the heap ("moved to heap: p"). Returning p by value keeps it on the stack.

Why "value type" is a performance word

An array of 1,000 C# Point structs is one heap object with 8,000 bytes of payload laid out contiguously. An array of 1,000 Java Point records is 1,001 objects: the array of references plus 1,000 separate objects, each with its own header, scattered around the heap. Walking the first array streams through memory and the CPU cache loves it; walking the second chases a pointer per element. The GC also has 1,000 extra objects to trace. This is the single biggest reason .NET and Go can beat Java on data-heavy code, and why Project Valhalla exists.

What an object costs: headers and allocation

A heap object is never just its fields. Every runtime adds a header so the GC and the language can find the object's type, lock it, and hash it.

Runtime (64-bit) Header Smallest object Notes
.NET 8-byte object header (sync block index / hash / lock bits) + 8-byte method table pointer 24 bytes Arrays add an 8-byte length. A string is 22 + 2 bytes per char, rounded up to 8.
JVM (HotSpot) 8-byte mark word + 4-byte compressed class pointer 16 bytes Compact object headers (JEP 519, a product option since JDK 25: -XX:+UseCompactObjectHeaders) cut the header to 8 bytes.
CPython refcount + type pointer (16 bytes); 16 more bytes of GC links for container objects 16 bytes (object()) int 28 bytes, float 24, empty list 56, plus a __dict__ per instance unless you use __slots__.
Go No header. The type and pointer layout are kept in the span's metadata 0 bytes (empty struct) Objects are rounded up to one of about 68 size classes (8, 16, 24, 32, 48, …). Interfaces are two words: type + data pointer.
V8 Map (hidden class) pointer + properties + elements, 4 bytes each with pointer compression 12 bytes Objects with the same shape share a Map; adding properties in different orders creates different Maps.

So a List<int> in .NET with 10 numbers is two objects (the list and its int[] of capacity 16, about 32 + 88 bytes). A List<Integer> in Java with 10 numbers outside the −128..127 cache is twelve objects. A Python list of 10 floats is eleven objects. This is why "it's only a few small objects" adds up: allocation volume, not allocation size, is usually what drives GC frequency.

Allocation itself is almost free

Managed runtimes allocate with a bump pointer: each thread owns a private chunk of the young generation (a TLAB, thread-local allocation buffer, on the JVM; an allocation context in .NET; a per-P mcache with size-class spans in Go; the new-space linear area in V8). Allocating is: check that ptr + size <= limit, return ptr, add size. About ten instructions, with no lock.

That is why the rule says allocations cost twice: the bump is ~10 ns, but the bill comes as more frequent GCs, more tracing and copying of survivors, and worse cache locality. CPython is different: small objects (up to 512 bytes) come from pymalloc pools of fixed-size blocks and are freed the moment their reference count reaches zero.

Escape analysis: when the compiler keeps "heap" objects on the stack

If the compiler can prove an object never outlives the current call and is never visible to another thread, it does not need the heap at all. This proof is escape analysis. A value escapes when it is returned, stored in a field or global, captured by a closure that outlives the frame, sent on a channel, or passed to code the compiler cannot see (an interface call, reflection).

  • Go does escape analysis at compile time and it decides stack vs heap for everything. Ask the compiler: go build -gcflags=-m ./... prints moved to heap: p, &Point{...} escapes to heap or does not escape. Common reasons for escaping: returning a pointer, storing in an interface (fmt.Println(x) boxes x into any), closures, and slices whose size is not a constant.
  • JVM (C2 and Graal JIT) does escape analysis at run time, after inlining. An object that does not escape can be scalar-replaced: its fields become locals in registers and the object is never created. It only works if the allocating code is inlined, so small methods and monomorphic call sites matter.
  • .NET added object stack allocation to the JIT in .NET 9 and widened it in .NET 10 (small non-escaping objects, boxes and delegates can live on the stack). In C# you still get the predictable version by choosing a struct or a ref struct like Span<T>.
  • V8 (TurboFan) also does escape analysis for optimised functions. CPython does not: every object is a heap object.

Reachability: what "garbage" means

A tracing collector never asks "is this object still needed?". It cannot know that. It asks a narrower, provable question: can the program still reach this object by following references from a root? Roots are the starting points the runtime knows about:

  • local variables and arguments in every live stack frame of every thread (and CPU registers),
  • static fields and globals,
  • handles held on behalf of native code (GC handles, JNI global refs, pinned objects),
  • objects waiting for finalization, and some runtime-internal tables.

Anything reachable is live. Everything else is garbage, no matter how recently it was used. Two consequences follow, and both cause real bugs:

  1. A cycle of objects that point to each other but are not reachable from a root is garbage. Tracing collectors handle cycles for free. Reference counting does not.
  2. An object you will never use again, but that is still referenced from a static list, an event, a cache or a closure, is not garbage. That is a managed memory leak.

Mark, sweep, compact

The basic tracing algorithm has two or three phases:

  1. Mark. Start at the roots and do a graph traversal, setting a mark bit on every object you reach.
  2. Sweep. Walk the heap. Every unmarked object's memory goes back to a free list.
  3. Compact (optional). Slide the survivors together so free memory is one contiguous block again, and update every reference to the moved objects.

The default graph has a cycle reachable from the root (A → B → C → A), a cycle that is not reachable (E ⇄ G), an object pointing into live data (H → D, but nothing points to H) and a self-loop (I). Things to try:

  • Step through mark and notice that E, G, H and I are never visited. The E ⇄ G cycle is freed even though each object has a reference to it. A reference to an object proves nothing; only a path from a root does.
  • Switch to mark-sweep and look at the heap strip at the end: the freed slots are holes between survivors. A later allocation larger than any one hole fails even though the total free space is enough. That is fragmentation.
  • Add root>H and run again. H, and through it D, stay alive. One forgotten reference can keep a whole subgraph alive.

Which runtimes compact? .NET (young generations always, gen2 when worthwhile, the LOH only on request), all HotSpot collectors, and V8 for fragmented old pages. Go and CPython never move objects: Go groups like-sized objects in size-class spans so fragmentation stays bounded, and a CPython object's id() is its address.

The generational hypothesis

Tracing the whole heap on every collection would be slow, because the cost of mark is proportional to the number of live objects, and a server can have gigabytes of them. Generational collectors exploit one empirical fact, measured over decades on real programs:

Most objects die young. The few that survive a while tend to live for a very long time.

Request DTOs, LINQ iterators, strings built for a log line, Task objects and lambda closures die within milliseconds. Caches, configuration, connection pools and DI singletons live for the whole process. So the heap is split by age, and the young part is collected often and cheaply: only live young objects are traced, and since almost none are live, a young GC is fast regardless of how big the old heap is.

The catch: if an old object points to a young one, the young GC must treat that pointer as a root, or it would free a live object. Runtimes track those pointers with a write barrier that records "old → young" writes in a card table (.NET, JVM) or remembered set (G1, V8). That is why writing a reference field costs slightly more than writing an int, and why mutating long-lived objects to point at short-lived ones makes young GCs slower.

.NET: gen0, gen1, gen2, LOH and POH

The .NET GC has three generations plus two special heaps:

Area What goes there When it is collected
gen0 Every new small object When its allocation budget is used (dynamic, roughly the size of the L3 cache up to hundreds of MB on Server GC). Survivors are promoted to gen1.
gen1 Survivors of one GC; a buffer between young and old With every gen1 collection; survivors go to gen2.
gen2 Long-lived objects Only in a full (gen2) collection, which is usually done as a background GC concurrently with your threads.
LOH Objects of 85,000 bytes or more (big arrays, big strings) Only with gen2. Not compacted by default, so it fragments.
POH Pinned buffers allocated with GC.AllocateArray<T>(n, pinned: true) (.NET 5+) With gen2; never moved, so they do not block compaction elsewhere.

Since .NET 7 the heap is made of regions rather than large fixed segments, which lets the GC move memory between generations and return it to the OS more easily. Since .NET 9, Server GC enables DATAS (dynamic adaptation to application sizes) by default, which grows and shrinks the number of heaps with load, a big win for containers.

Each chip is an object (hover it to see the tick at which it dies); gen0 shows its remaining budget as empty slots. Run all four workloads with the same budget and compare the final summary line:

  • Request-scoped objects die in gen0. 30 allocations cause only three cheap gen0 GCs, one gen1 and no gen2. This is the healthy shape.
  • Mid-life crisis: objects live a few seconds (an in-memory batch, a session cache with a short TTL, a List that accumulates per-minute stats). They survive gen0 and gen1, get copied twice, land in gen2, and then die there, where only an expensive full GC can reclaim them. Count the copies.
  • Growing static cache: everything survives, so every GC copies and promotes. gen2 grows without limit. A cache needs a size bound and an eviction policy (see Caching).
  • 100 KB buffers per request skip the young generations entirely and go to the LOH. They die young, but the LOH is only collected with gen2, so they force full GCs. The fix is to reuse those buffers (pooling, below) or stream instead of buffering.

JVM: G1 regions, ZGC and choosing a collector

HotSpot ships several collectors, and choosing one is a real design decision:

Collector Flag Pauses Best for
G1 (default since JDK 9) -XX:+UseG1GC Pause-time goal (-XX:MaxGCPauseMillis=200 by default), typically 5–50 ms General-purpose services with heaps from a few hundred MB to tens of GB
ZGC (generational by default since JDK 23) -XX:+UseZGC Under 1 ms, independent of heap size Latency-sensitive services, very large heaps (up to 16 TB)
Parallel -XX:+UseParallelGC Long stop-the-world pauses, highest throughput Batch jobs and offline processing, where only total time matters
Serial -XX:+UseSerialGC Stop-the-world, one thread Tiny containers; the JVM picks it automatically with fewer than 2 CPUs or under ~1.8 GB of memory

G1 splits the heap into equal regions (1–32 MB each, chosen from the heap size). A region has no fixed generation: it becomes eden, survivor, old or humongous when it is handed out, and it is free again once collected. Each young pause evacuates (copies) live objects out of the eden and survivor regions and frees those regions whole. When old regions pass the IHOP threshold (initiating heap occupancy, 45% by default and adaptive), G1 marks the old generation concurrently and then runs mixed collections that also evacuate the old regions with the most garbage first. That is where the name Garbage First comes from.

Read the region map from left to right: E (eden), S (survivor), O (old), H (humongous) and free. The darker part of each bar is still-live data. Things to try:

  • Run the defaults: six young pauses and two mixed collections, no full GC. Each pause only touches the regions in its collection set, so its cost is proportional to the live data in those regions, not to the heap.
  • Set survival % to 0 and see young pauses copy nothing. Then set it to 70: survivors overflow into old regions quickly, IHOP is crossed early and mixed GCs start.
  • Set humongous every N cycles to 1. An object of at least half a region skips eden and takes contiguous old regions. Lots of humongous allocations fragment the region map and are a classic cause of G1 full GCs. Fix it in code (smaller chunks, reuse buffers) or raise -XX:G1HeapRegionSize.
  • Try eden 8, survival 50, humongous every 2, 10 cycles. G1 eventually cannot find free regions to evacuate into ("to-space exhausted") and falls back to a full GC: a stop-the-world compaction of the whole heap, and the pause you were trying to avoid.

ZGC relocates objects while your threads run. References carry metadata bits ("coloured pointers"), and a load barrier on every heap reference read fixes up pointers to moved objects on the spot. Pauses only scan thread stacks, so they stay under a millisecond. The price is barrier overhead and more memory headroom, since collection must keep up with allocation while it runs.

The JVM uses 25% of your container by default

Without -Xmx, the JVM sizes its maximum heap at MaxRAMPercentage, which defaults to 25% of the container's memory limit. A 4 GB pod gets a 1 GB heap, runs GC constantly and can still OOM while 3 GB sit unused. Set -XX:MaxRAMPercentage=75 (leave room for metaspace, thread stacks, direct buffers and the code cache), or set -Xmx explicitly. .NET defaults to 75% of the container limit (GCHeapHardLimitPercent), Go knows nothing about the limit unless you set GOMEMLIMIT, and Node needs --max-old-space-size.

Go: a concurrent, non-moving, non-generational collector

Go made unusual choices: its GC is concurrent mark-sweep, does not move objects, and (until recently) was not generational. Go relies on escape analysis to keep short-lived data on the stack, on value types to keep objects few and dense, and on concurrency to keep pauses tiny. A typical stop-the-world pause is tens to hundreds of microseconds. The cost is paid instead in CPU: during marking the GC takes about 25% of GOMAXPROCS, and goroutines that allocate quickly are drafted into mark assists that slow them down.

Marking concurrently with your code creates a race. The GC colours objects white (not yet seen), grey (seen, children not yet scanned) and black (scanned). When the grey set is empty, white objects are garbage. But your goroutines keep writing pointers while marking runs. If a black object gets the only pointer to a white object, and the white object's last grey path is removed, the GC will never see it, and frees a live object.

The default interleaving shows the lost object: the GC finishes scanning A (black), then the program stores A.next = C and removes B → C. C is reachable but white, so the sweep frees it. Things to try:

  • Insertion barrier (Dijkstra). Every pointer write shades the new target grey. A.next = C greys C, so it survives. It keeps the strong invariant: no black object ever points to a white one.
  • Deletion barrier (Yuasa). Every pointer overwrite or delete shades the old target. Removing B → C greys C. It keeps a snapshot of the heap as it was when marking started.
  • Hybrid barrier (Go since 1.8). Shade both. This lets Go treat goroutine stacks as black once scanned and skip re-scanning them at the end, which is what took Go's pauses from milliseconds to microseconds.
  • Edit the schedule to GGGMMG (all scanning first) and the bug disappears even without a barrier. That is why such races escape testing: they need a specific interleaving.

GOGC and GOMEMLIMIT

Go has only two GC knobs, and both are about when to start the next cycle:

  • GOGC (default 100): the next GC starts when the heap has grown by GOGC% over the live heap left by the previous one (plus stacks and globals). With 100 MB live, the next cycle starts at about 200 MB. Higher GOGC means fewer GCs and more memory; lower means the opposite.
  • GOMEMLIMIT (Go 1.19+): a soft limit on total Go memory. As the heap approaches it, the GC runs more often regardless of GOGC. Set it to roughly 90% of the container limit. GOGC=off together with GOMEMLIMIT means "collect only when near the limit", which is efficient for batch jobs but dangerous with a large live heap: the GC caps itself at about 50% CPU to avoid a death spiral, so you get a very slow program instead of a crash.

Go 1.25 shipped an experimental new marking algorithm, Green Tea (GOEXPERIMENT=greenteagc), which scans memory a whole page (span) at a time for better cache locality and is enabled by default from Go 1.26. The model above, a concurrent non-moving tri-colour collector, does not change.

Python: reference counting plus a cycle detector

CPython manages memory in two layers:

  1. Reference counting does almost all the work. Every object header holds a count of references to it. Binding a name, storing in a list or passing an argument increments it; rebinding, del and leaving a scope decrement it. When the count reaches zero, the object is freed immediately, and freeing it decrements everything it pointed to.
  2. A generational cycle detector (the gc module) handles what refcounting cannot: groups of container objects that reference each other but are unreachable. It runs automatically based on allocation counts (thresholds (700, 10, 10) in 3.11) and when you call gc.collect().

The default program builds A ⇄ B, points C at B, then drops all three names. Watch C disappear the instant c = None runs, while A and B keep a count of 1 each. Each is held only by the other. Then gc.collect() runs the actual algorithm: copy each refcount into gc_refs, subtract one for every reference between tracked objects, and whatever still has gc_refs > 0 must be referenced from outside, so it is alive. Things to try:

  • Delete gc.collect() from the end. A and B are reported as leaked: a reference cycle without a collection pass.
  • Replace the program with x = Node("A"); y = x; del x and watch the count go 1, 2, 1. del deletes a name, not an object.
  • The visualizer's results match real CPython (checked with weakref.finalize on 3.11).

A few facts that matter in practice:

  • Immortal objects (PEP 683, Python 3.12+): None, True, small ints and interned strings have a fixed refcount that is never updated, so shared read-only data stays on shared memory pages after fork().
  • Refcount writes break copy-on-write. A forked worker that merely reads a big inherited dict still writes to each object's refcount, so the page gets copied. Call gc.freeze() before forking so the cycle collector at least does not touch those objects.
  • The free-threaded build (3.13t/3.14t, PEP 703) replaces plain refcounts with biased reference counting (cheap for the owning thread, atomic for others), because unsynchronised counts were the main reason for the GIL.
  • Python 3.14 makes the cycle collector incremental, which shortens the long pauses that a full collection of a big heap used to cause.

JavaScript and TypeScript: V8's scavenger and mark-compact

V8 (Chrome, Node, Deno, Edge) splits the heap into a small young generation (a few MB to tens of MB) and an old generation. The two use different algorithms because their objects behave differently:

  • Young objects are collected by a scavenger: a copying collector over two equal semi-spaces. Only survivors are touched, so the cost is proportional to what survives, which is usually very little.
  • Old objects are collected by mark-sweep-compact, with marking done mostly concurrently and incrementally (the Orinoco project), and compaction only for fragmented pages.

This is Cheney's algorithm (1970). Two pointers walk the to-space: everything between scan and free is a queue of copied objects whose fields still need scanning. Each copied object leaves a forwarding pointer behind, so a second reference to it (the cycle B ⇄ D) is just redirected and the object is copied exactly once. E survived a scavenge before, so it is promoted straight to the old generation. Things to try:

  • Add root>A and see how the work grows with each survivor, while dead objects never cost anything.
  • Make E point at more young objects: a promoted object's fields can point back into the young generation, which is exactly what V8's remembered set and write barrier exist for.
  • Put every object in the "survived before" list: everything is promoted, and the old generation fills with data that will die soon. That is the JavaScript version of the .NET mid-life crisis.

For allocation-heavy Node services, --max-semi-space-size (in MB) makes the young generation bigger so fewer objects are promoted prematurely; --max-old-space-size sets the old-generation limit. Measure both with --trace-gc before and after.

Pause time vs throughput: the trade-off every collector makes

There is no best garbage collector, only a position on three axes that pull against each other:

  • Pause time (latency): how long your threads are stopped. This drives p99 and p999.
  • Throughput: the fraction of CPU time your code gets instead of the GC. This drives cost per request.
  • Footprint: how much memory the heap needs beyond the live data. This drives container size and cost.

Concurrent collectors cut pauses by doing work while your threads run, but they need barriers (a small tax on every pointer write or read), extra GC threads, and headroom so the application can keep allocating during the cycle. Stop-the-world collectors are simpler and faster in total, but the whole application waits.

Managed memory leaks: references you forgot

A garbage collector cannot leak an unreachable object. Every "memory leak" in C#, Java, Go, Python or JavaScript is an object that is still reachable from a root but will never be used again. The heap graph tells the story: each GC still frees memory, so the graph is a sawtooth, but the floor (the live set after each full GC) keeps rising until the process is killed.

Pick a leak, step through it and read the retention path at the end: the chain from a GC root to the leaked objects. That chain is exactly what a heap-dump tool shows you ("GC root path", "paths to GC roots", "retainers"). Then switch the version to fixed with the same requests and watch the floor go flat. A leaked HttpClient per request, an undisposed FileStream, a JDBC Connection not closed, an unclosed Go resp.Body: these leak sockets, file handles and connection-pool slots, not just memory. Pooling: reuse instead of allocate

When a hot path allocates big, short-lived buffers (I/O buffers, serialisation scratch space, image tiles), allocation volume drives GC frequency, and in .NET anything over 85,000 bytes lands on the LOH. Pooling keeps a set of buffers and hands them out again: rent, use, return.

The visualizer serves requests with a 64 KB buffer each, with a few in flight at once. Compare the four modes on the same input:

  • new byte[64 KB] per request: one LOH-sized allocation per request. GCs happen regularly, and each one is a gen2.
  • ArrayPool Rent / Return: the pool only ever allocates as many arrays as there are concurrent requests (3 for 12 requests by default) and GCs stop.
  • Bug: forgot to Return: the pool keeps allocating new arrays. You get the cost of pooling plus the cost of allocating. Not catastrophic, just wasted effort.
  • Bug: Return, then keep using it: another request rents the same array while the first is still writing. Data from one request shows up in another. This is the bug from the opening story, and it is a security bug when buffers carry customer data.
using System.Buffers;

async Task CopyAsync(Stream source, Stream destination, CancellationToken ct)
{
    byte[] buffer = ArrayPool<byte>.Shared.Rent(64 * 1024);   // may return a LARGER array

            await destination.WriteAsync(buffer.AsMemory(0, read), ct);   // only use [0, read)
    }
    finally
    {
        ArrayPool<byte>.Shared.Return(buffer, clearArray: true);  // exactly once; clear if sensitive
    }
    // Never touch 'buffer' after Return, and never Return it twice.
}

Pool when

  • Objects are large (≥ 85 KB in .NET, humongous in G1) or expensive to create (connections, threads, compiled regexes, HttpClient handlers).
  • A profile shows allocation or GC time on that exact path.
  • The lifetime is short and obvious: rent and return in the same method, ideally in try/finally or defer.

Do not pool when

  • Objects are small and short-lived. A young GC of dead objects is nearly free, and a pool adds synchronisation, keeps objects alive (making them old), and makes old-to-young pointers.
  • Ownership is unclear (the buffer is passed across awaits, threads or callbacks). One mistake turns a performance win into data corruption.
  • You have not measured. Pooling makes code harder to read and review.

Pooling as an architecture pattern (connection pools, worker pools, bulkheads) is covered in Performance Patterns. Here it is only about memory.

Views instead of copies: Span, Memory and slices

The cheapest allocation is the one you never make. A lot of garbage in real services comes from copying pieces of data you only want to look at: Split to read one field, Substring to compare a prefix, ToArray() to pass part of a buffer, bytes[a:b] to parse a header. Every runtime has a way to make a view (a pointer plus a length into existing memory) instead of a copy.

The default parses id=42;name=Ada;role=admin. With Split + Substring, every piece becomes a new string, plus the array that Split returns: 13 allocations and 480 bytes to read a 25-character string. Switch to ReadOnlySpan<char> slicing: every piece is a window (start, length) over the original string and the heap row stays empty. Then try a longer input and watch the copy version's bytes grow with it.

C#: Span<T>, ReadOnlySpan<T> and Memory<T>

  • Span<T> / ReadOnlySpan<T> is a ref struct: a reference plus a length, over an array, a string, stackalloc memory or native memory. Slicing it (span[2..5]) is free. It can only live on the stack: it cannot be a field of a class, be boxed, be captured by a lambda, or live across an await (C# 13 allows span locals in async methods, but still not across an await). Those rules are what make it safe and fast.
  • Memory<T> / ReadOnlyMemory<T> is the heap-friendly version. Store it in a field, pass it across await, then call .Span when you actually process the data.
  • Most of the BCL accepts spans: int.Parse(ReadOnlySpan<char>), Utf8Parser, Stream.ReadAsync(Memory<byte>), string.Create, MemoryExtensions.Split (.NET 9+), System.IO.Pipelines, Utf8JsonReader.
// Zero allocations: every piece is a view over the input.
static (int Id, string? Name) Parse(ReadOnlySpan<char> s)
{
    int id = 0;
    string? name = null;
    foreach (Range r in s.Split(';'))                 // .NET 9+: yields Ranges, no string[]
    {
        ReadOnlySpan<char> part = s[r];
        int eq = part.IndexOf('=');
        if (eq < 0) continue;
        ReadOnlySpan<char> key = part[..eq], value = part[(eq + 1)..];
        switch (key)
        {
            case "id": id = int.Parse(value); break;  // parses the span directly
            case "name": name = value.ToString(); break;  // allocate only what you keep
        }
    }
    return (id, name);
}

Views are fast and dangerous for the same reason: they share memory. Two bugs follow from that. A small view can keep a huge parent alive (a 10-byte Go substring of a 50 MB response body pins all 50 MB), and a writable view can change data someone else is reading. Go slices: one backing array, two views

A Go slice is a three-word header: pointer, length, capacity. b := a[:2] creates a new header over the same array, with the remaining capacity of a. If you append to b while it has spare capacity, the append writes into a's array.

With the defaults, b := a[:2] and appending 90, 91, 92, 93 overwrites a[2], a[3] and a[4] before b runs out of capacity and moves to a new array. The program prints [1 2 90 91 92] [1 2 90 91 92 93]. Things to try:

  • Switch to b := a[:k:k] (a full slice expression sets the capacity to k). The first append must allocate a new array, and a is untouched: [1 2 3 4 5] [1 2 90 91 92 93].
  • Append only 7, 8. Both fit in the spare capacity, so b never moves and both values land in a: [1 2 7 8 5].
  • Watch the capacities when b grows. Go roughly doubles small slices, then rounds up to a memory size class, so cap is not always exactly double.

Rules for sharing slices safely

  • Returning buf[:n] from a function that reuses buf gives the caller a view that will be overwritten. Return a copy (slices.Clone, Go 1.21+) if the caller keeps it.
  • Handing a sub-slice to code that might append: use a[lo:hi:hi] or slices.Clip.
  • Keeping a small piece of a big buffer for a long time: copy it so the big buffer can be collected.

Why finalizers are a last resort

A finalizer (~T() in C#, finalize() in Java, __del__ in Python, runtime.SetFinalizer in Go, FinalizationRegistry in JavaScript) runs some time after the GC notices an object is unreachable. It looks like a destructor but behaves very differently:

  • No timing guarantee. It runs when the GC happens to collect that object, possibly never before the process exits.
  • Extra GC cost. In .NET a finalizable object survives at least one extra collection (it is promoted while it waits in the finalization queue), and so does everything it references.
  • One thread. .NET and Java run finalizers on a single finalizer thread. One slow or blocked finalizer stalls them all, and the queue grows into a leak.
  • No order. Objects a finalizer touches may already have been finalized.

Use them only as a safety net behind a proper Dispose/close, and prefer the modern tools: SafeHandle (.NET), Cleaner (Java), weakref.finalize (Python), runtime.AddCleanup (Go). In C#, call GC.SuppressFinalize(this) from Dispose if the type has a finalizer, so a disposed object skips the queue.

Tooling: see the heap instead of guessing

Performance Cadence covers profiling and benchmarking in general. For memory you need three specific views, and every runtime has tools for all three:

  1. Counters over time: heap size, GC count per generation, % time in GC, allocation rate. They tell you whether there is a problem and what shape it has (a sawtooth with a rising floor means a leak; very frequent GCs mean allocation volume).
  2. Allocation profile: which code allocates the most bytes. Use it to fix GC pressure.
  3. Heap snapshot or dump: what is alive right now, grouped by type, with the path from a GC root. Use it to fix leaks.

A leak hunt, step by step

1 · CONFIRMIs the floor rising?

Plot heap size after each full GC over hours. A rising floor is a leak. A high but flat floor is just a big working set.

2 · TWO SNAPSHOTSBefore and after load

Warm up, take a heap snapshot, run N requests, force or wait for a full GC, take another.

3 · DIFFSort by count delta

The type whose count grew by about N (or a multiple of N) is your suspect. Ignore types that only grew by a constant.

4 · ROOT PATHWho holds it?

Ask for the path to a GC root (gcroot, MAT "path to GC roots", DevTools retainers). The first long-lived object on the path is the bug.

5 · VERIFYFlat floor again

Fix, rerun the same load and confirm the floor stays flat. Add a test that asserts allocations or live objects if it regressed before.

When NOT to optimise allocations

Allocation tuning has the worst effort-to-benefit ratio in performance work when it is done without data. Modern collectors are extremely good at short-lived garbage, and readable code is worth far more than a few kilobytes per request. Follow the Performance Cadence: a goal, a profile, then one change.

Do it up front: these are design, not micro-optimisation

  • Stream large data instead of loading it whole (IAsyncEnumerable, Stream, iterators, io.Reader, Node streams).
  • Bound every cache and queue.
  • Unsubscribe, dispose, close and cancel what you start.
  • Choose value types and primitive arrays for big numeric data.
  • Set the container memory limit and tell the runtime about it.

Do NOT do it without a profile

  • Replacing LINQ, streams or comprehensions with hand-written loops everywhere.
  • Pooling small objects "to reduce GC".
  • Turning classes into structs to "avoid the heap" (large structs are copied on every assignment and call).
  • GC.Collect(), System.gc(), runtime.GC() or gc.collect() in application code.
  • Tuning GC flags you copied from a blog post for a different workload.

A practical threshold: if % time in GC is under about 5% and p99 meets the goal, allocation is not your problem. Look at I/O, locks and algorithms first. When GC is the problem, the allocation profile usually points at one or two call sites (a serializer, a logger, a string builder in a loop) and fixing those gives most of the gain.

Allocation-free code is a library concern more than an application concern

Kestrel, System.Text.Json, Netty, Go's standard library and V8 builtins are written allocation-free so that your code can afford to allocate. Call their span-, stream- and buffer-friendly APIs; hand-roll zero-allocation code only where a profile points.

Pitfalls and war stories

GC.Collect() "to free memory"

A team added GC.Collect() after every batch because a dashboard showed memory "too high". p99 tripled. Each call was a blocking full GC, and it promoted every in-flight object to gen2, where it then needed more full GCs to die. A high heap with a flat floor is not a problem; it means the GC has not needed to work yet. Remove explicit collections and set a heap limit if memory really is constrained.

The blocked finalizer thread

A class wrapped a native SDK handle and released it in a finalizer that took a lock. One day the lock was held by a thread waiting for... memory. The single finalizer thread blocked, the finalization queue grew by millions of objects, and the process ran out of memory with a heap full of objects that were already garbage. Implement IDisposable with a SafeHandle, keep finalizers trivial, and never block in one.

The LOH and the 2 MB JSON string

An API built each response as one big string with StringBuilder.ToString() and then serialised it again to UTF-8 bytes. Each response created three LOH objects, so gen2 GCs ran every few seconds under load. Writing straight to the response body with JsonSerializer.SerializeAsync(stream, ...) removed the big strings entirely. The same mistake on the JVM creates humongous objects in G1, and in Node a giant JSON.stringify string blocks the event loop as well.

The 40-byte token that held a 30 MB response

A Node service extracted a session token from a large upstream response with body.slice(i, j) and cached it in a Map. V8 represented the result as a sliced string pointing into the 30 MB body, so every cached token kept a whole response alive. Heap snapshots showed thousands of 30 MB "(string)" retainers. Copying the token out fixed it, and so does storing a parsed field instead of a substring. Go has the same trap with substrings (strings.Clone), and older Java (before 7u6) did too.

Checklist

Before you merge

  • Is every cache, queue, map and list that lives longer than a request bounded?
  • Is every subscription, timer and background loop stopped in Dispose/close/cancel?
  • Is every file, socket, connection and response body closed with using, try-with-resources, with or defer?
  • Does any long-lived callback or closure capture request data it does not need?

Hot paths

  • Did a profile point here? (If not, stop.)
  • Are large buffers streamed, pooled or reused, not allocated per call?
  • Are you parsing with views (spans, memoryview, subarray, index arithmetic) instead of Split/substring?
  • Are pooled buffers returned exactly once and never used afterwards?

Production

  • Does the runtime know the container limit (MaxRAMPercentage, GOMEMLIMIT, --max-old-space-size)?
  • Are GC counters (heap, % time in GC, gen2/full counts) on a dashboard with the deploy markers?
  • Can you take a heap dump from a live instance, and has someone practised it?

Quiz

1. A C# method creates 10,000 small objects per request and all of them are garbage when the request ends. Is that a GC problem?
Show answer

Usually not. They die in gen0, and a gen0 GC only traces live objects, so its cost barely depends on how much garbage there is. It becomes a problem when the allocation rate makes gen0 GCs so frequent that requests in flight survive and get promoted (mid-life crisis), or when a profile shows GC time is significant. Measure % time in GC before changing anything.

2. Memory grows steadily, yet every GC frees hundreds of MB. Leak or not? How do you find out?
Show answer

Look at the floor: heap size right after each full GC. If the floor rises over time, it is a leak; how much each GC frees is irrelevant. Take two heap snapshots under the same load some time apart, diff by type count, and follow the retention path of the growing type to its GC root.

3. In Python, a.partner = b; b.partner = a; del a, b. When are the two objects freed, and what would change with a weak reference?
Show answer

Not at del: each still has a refcount of 1 from the other. They are freed when the cycle detector runs (automatically after enough allocations, or on gc.collect()). If one direction used weakref.ref, there would be no cycle in strong references, and both would be freed immediately and deterministically by refcounting.

4. Go: b := a[:2]; b = append(b, 9) where a is [1 2 3] with capacity 3. What is a now, and how do you prevent it?
Show answer

a is [1 2 9]. b shares a's array and has spare capacity, so append writes in place. Use the full slice expression a[:2:2] (capacity 2 forces a new array on append), slices.Clip, or copy with slices.Clone.

5. Why does Go need a write barrier during marking, and why does .NET's gen0 GC need a card table?
Show answer

Both protect against pointers the collector would otherwise miss. Go marks concurrently, so the program can store the only pointer to a white object into an already-scanned black one; the barrier shades it grey. A .NET gen0 GC does not scan gen2, so a gen2 object pointing to a gen0 object would be invisible; the write barrier marks the card for that gen2 memory so the young GC scans it as an extra root.

6. A Java service in a 4 GB container has OutOfMemoryError while the pod uses 1.3 GB. No -Xmx is set. What happened?
Show answer

The default MaxRAMPercentage is 25%, so the maximum heap was about 1 GB. Set -XX:MaxRAMPercentage=75 (or an explicit -Xmx), leaving headroom for metaspace, thread stacks, direct buffers and the code cache.
