REQUEST PIPELINES & MIDDLEWARE

The Request Delegate Pipeline

Build ASP.NET Core's RequestDelegate chain from scratch, watch a request go in and the response come back out, then compare Express/Koa, Go handlers, servlet filters and ASGI.

Intermediate → Advanced~60 min studyBuilds on: Behavioral Patterns, DI FundamentalsUpdated 2026-11-03

The problem: every endpoint doing everyone's job

Here is a typical first version of an endpoint. One line does the actual work: it loads an order. Everything else is plumbing that every endpoint in the service needs too.

app.MapGet("/orders/{id:int}", async (int id, HttpContext ctx, OrdersDb db, ILogger<Program> log) =>
{
    var sw = Stopwatch.StartNew();                       // timing
    log.LogInformation("→ GET /orders/{Id}", id);         // request logging
    try
    {
        if (!ApiKeys.IsValid(ctx.Request.Headers["X-Api-Key"]))
            return Results.Unauthorized();               // auth
        var order = await db.Orders.FindAsync(id);       // ← the only real work
        return order is null ? Results.NotFound() : Results.Ok(order);
    }
    catch (Exception ex)                                 // error handling
    {
        log.LogError(ex, "GET /orders/{Id} failed", id);
        return Results.Problem(statusCode: 500);
    }
    finally
    {
        log.LogInformation("← {Ms} ms", sw.ElapsedMilliseconds);
    }
});
// ...copied into the next 40 endpoints, each copy drifting a little.

builder.Services.AddProblemDetails();

app.UseExceptionHandler();                       // errors → ProblemDetails, once
app.UseMiddleware<RequestTimingMiddleware>();    // timing + logging, once
app.UseMiddleware<ApiKeyMiddleware>();           // auth, once

app.MapGet("/orders/{id:int}", async (int id, OrdersDb db) =>
    await db.Orders.FindAsync(id) is { } order ? Results.Ok(order) : Results.NotFound());

The "before" version has three real problems. The plumbing is duplicated, so the copies drift: one endpoint forgets the auth check and nobody notices. It is mixed into business code, so you can't read what the endpoint does. And it is incomplete: errors thrown by model binding, by routing or by the JSON serializer happen outside the lambda, so its try/catch never sees them.

The "after" version moves each concern into a layer that wraps every request. That is all middleware is. ASP.NET Core, Express, Koa, Go's net/http, servlet filters, Django and ASGI all use the same idea. This page builds ASP.NET Core's version from nothing, so that the ordering rules in Middleware: Order and Patterns become obvious rather than memorised.

The pipeline rule. A middleware is a function that receives the next handler and returns a new handler that wraps it. The pipeline is all of them folded into one delegate, so code before next runs on the way in, in registration order, and code after next runs on the way out, in reverse order. Not calling next short-circuits everything inside.

The mental model: an onion

Draw each middleware as a layer around the endpoint. A request has to pass through every outer layer to reach the core, and the response has to pass back out through the same layers. Registration order in Program.cs is the order from the outside in.

The onion is not a metaphor laid on top of the code. It is the call stack. When layer ② runs await next(ctx), it is literally calling layer ③ and waiting for it to return. So "the response travels back out" just means "the calls return". Step through it and change the inputs: remove the token to see a short-circuit, or make the endpoint throw to see an exception unwind.

Three things to notice in the visualizer:

  1. Short-circuit. With no token, Auth sets 401 and returns without calling next. The endpoint is greyed out because it never ran. But Timing and Logging still run their after-code, because Auth returned to them normally.
  2. Exceptions unwind the same stack. When the endpoint throws, Logging's line after await next(ctx) is skipped, because an await that throws skips the rest of the method. Timing's finally still runs. Only the outermost try/catch turns the exception into a 500.
  3. HasStarted. Once the endpoint writes the body, the status code and headers have been sent. Outer layers can still read the status on the way out, but they can no longer change it.

Here is the same flow as a sequence diagram, which makes the "in, then out in reverse" shape explicit.

Insight Every layer gets two chances to act: once with the request before the inner layers run, and once with the result after they finish. Everything else, including short-circuits, error handling and timing, follows from that.

Build it from scratch

ASP.NET Core's whole pipeline rests on two types. If you understand these two lines, you understand the design:

public delegate Task RequestDelegate(HttpContext context);   // "handle this request"
// a middleware component:  Func<RequestDelegate, RequestDelegate>  // "given next, make a handler"

A RequestDelegate is anything that can handle a request: the endpoint, or the whole app. A component is a factory. You give it the next delegate and it returns a new delegate that does some work and (usually) calls next. IApplicationBuilder.Use just appends a component to a list:

public interface IApplicationBuilder
{
    IApplicationBuilder Use(Func<RequestDelegate, RequestDelegate> middleware);
    RequestDelegate Build();
    // ...plus ApplicationServices, Properties, New()
}

Folding from the end

Build() turns the list into one delegate. It can't start at the front, because the first component needs its next to already exist. So it starts at the end, with a terminal delegate that returns 404, and walks backwards, wrapping each time.

Try it. Put a Run in the middle of the list and watch it throw away everything that was already built behind it.

This is the real algorithm. ApplicationBuilder.Build() in ASP.NET Core loops over _components in reverse in exactly this way. Its terminal delegate has one extra check: if routing selected an endpoint but nothing ran it, it throws "The request reached the end of the pipeline without executing the endpoint" instead of returning 404.

The whole thing in about 40 lines

Here is a working pipeline builder with Use, Run, Map, MapWhen and UseWhen. It compiles and runs on .NET 10 with a minimal HttpContext that has Path, PathBase and StatusCode.

public delegate Task RequestDelegate(HttpContext context);

public sealed class PipelineBuilder
{
    private readonly List<Func<RequestDelegate, RequestDelegate>> _components = new();

    public PipelineBuilder Use(Func<RequestDelegate, RequestDelegate> component)
    {
        _components.Add(component);
        return this;
    }

    public PipelineBuilder Use(Func<HttpContext, RequestDelegate, Task> middleware) =>
        Use(next => ctx => middleware(ctx, next));

    public void Run(RequestDelegate handler) => Use(_ => handler);  // ignores next

    public PipelineBuilder MapWhen(Func<HttpContext, bool> when, Action<PipelineBuilder> configure)
    {
        var branch = new PipelineBuilder();
        configure(branch);
        RequestDelegate branchApp = branch.Build();          // own 404 terminal
        return Use(next => ctx => when(ctx) ? branchApp(ctx) : next(ctx));
    }

    public PipelineBuilder UseWhen(Func<HttpContext, bool> when, Action<PipelineBuilder> configure) =>
        Use(next =>
        {
            var branch = new PipelineBuilder();
            configure(branch);
            RequestDelegate branchApp = branch.Build(next);  // terminal = main next
            return ctx => when(ctx) ? branchApp(ctx) : next(ctx);
        });

    public PipelineBuilder Map(string prefix, Action<PipelineBuilder> configure) =>
        MapWhen(ctx => ctx.Path.Equals(prefix, StringComparison.OrdinalIgnoreCase)
                    || ctx.Path.StartsWith(prefix + "/", StringComparison.OrdinalIgnoreCase),
            branch =>
            {
                branch.Use(async (ctx, next) =>                 // move prefix to PathBase
                {
                    var (path, pathBase) = (ctx.Path, ctx.PathBase);
                    ctx.PathBase = pathBase + path[..prefix.Length];
                    ctx.Path = path[prefix.Length..];
                    try { await next(ctx); }
                    finally { (ctx.Path, ctx.PathBase) = (path, pathBase); }
                });
                configure(branch);
            });

    public RequestDelegate Build(RequestDelegate? terminal = null)
    {
        RequestDelegate app = terminal ?? (ctx => { ctx.StatusCode = 404; return Task.CompletedTask; });
        for (int i = _components.Count - 1; i >= 0; i--)
            app = _components[i](app);                          // wrap: last first
        return app;
    }
}

Read it slowly, because every API you use in Program.cs falls out of it:

  • Use((ctx, next) => …) is sugar. It wraps your two-argument lambda in a component that captures next.
  • Run is a component that ignores next. That is the entire difference between Use and Run.
  • MapWhen builds a separate pipeline at startup. Its branch has its own 404 terminal, so a request that enters the branch can never come back.
  • UseWhen builds its branch inside the component factory, where next is in scope, and passes next as the branch's terminal. That single argument is what "rejoins the main pipeline" means.
  • Map is MapWhen with a segment-aware prefix test, plus a first branch layer that moves the prefix from Path to PathBase and restores it in finally on the way out.

Use, Run, Map, MapWhen and UseWhen

Method What the component does with next Rejoins main pipeline? Changes the path? Typical use
Use Calls it (or doesn't, to short-circuit) n/a No Almost all middleware
Run Ignores it: terminal n/a No A catch-all final handler
Map("/x", …) Calls the branch instead when the path starts with segment /x No Moves /x to PathBase Mounting a sub-app, e.g. a health or admin UI
MapWhen(pred, …) Calls the branch instead when pred is true No No Splitting on header, query or host

Pitfall: Map strips the prefix Inside app.Map("/api", …), Request.Path for /api/orders is /orders. Code that matches on Path.StartsWithSegments("/api") inside the branch silently never matches, and links built from Path alone lose the prefix. Build URLs from PathBase + Path. Also note that Map matches segments, case-insensitively: /apix does not match /api, but /API does.

Middleware classes and dependency injection

Inline lambdas are fine for a few lines. Anything real belongs in a class. ASP.NET Core supports two class shapes, and the difference is about when the instance is created, which decides what you can safely inject. This builds on DI Fundamentals and Lifetimes and Scopes.

// Created ONCE, when the pipeline is built. Behaves like a singleton.
public sealed class RequestTimingMiddleware
{
    private readonly RequestDelegate _next;
    private readonly ILogger<RequestTimingMiddleware> _log;   // singleton: safe here

    public RequestTimingMiddleware(RequestDelegate next, ILogger<RequestTimingMiddleware> log)
    {
        _next = next;
        _log = log;
    }

    // Extra parameters are resolved from ctx.RequestServices on EVERY call.
    public async Task InvokeAsync(HttpContext ctx, IRequestMetrics metrics)   // scoped: safe here
    {
        long start = Stopwatch.GetTimestamp();
        try
        {
            await _next(ctx);
        }
        finally
        {
            TimeSpan elapsed = Stopwatch.GetElapsedTime(start);
            metrics.Record(ctx.Request.Path, ctx.Response.StatusCode, elapsed);
            _log.LogInformation("{Method} {Path} -> {Status} in {Ms:0.0} ms",
                ctx.Request.Method, ctx.Request.Path, ctx.Response.StatusCode, elapsed.TotalMilliseconds);
        }
    }
}

app.UseMiddleware<RequestTimingMiddleware>();

// Resolved from the request scope on EVERY request by IMiddlewareFactory.
public sealed class TenantMiddleware(TenantDbContext db) : IMiddleware   // scoped: safe here
{
    public async Task InvokeAsync(HttpContext ctx, RequestDelegate next)
    {
        string id = ctx.Request.Headers["X-Tenant"].ToString();
        Tenant? tenant = await db.Tenants.FindAsync(id);
        if (tenant is null)
        {
            ctx.Response.StatusCode = StatusCodes.Status404NotFound;
            return;                                   // short-circuit
        }
        ctx.Items["tenant"] = tenant;
        await next(ctx);
    }
}

builder.Services.AddScoped<TenantMiddleware>();       // required: it must be registered
app.UseMiddleware<TenantMiddleware>();

The conventional class has no interface. UseMiddleware<T> finds a public Invoke or InvokeAsync method that returns Task and takes HttpContext first, constructs T with ActivatorUtilities (so RequestDelegate next plus any singleton services), and caches the instance. Because the constructor runs once, a scoped service injected there is captured for the app's lifetime. Put scoped services on InvokeAsync instead, or use IMiddleware, which is resolved per request. The visualizer shows all three choices.

Inline app.Use(async (ctx, next) => …)

Shortest. Captures whatever is in scope, so it is easy to accidentally capture a scoped service from app.Services. Good for a few lines of glue. Prefer the RequestDelegate next overload: the older Func<Task> next overload allocates a closure on every request.

Conventional class

One instance for the app. Constructor takes RequestDelegate and singletons; InvokeAsync parameters take scoped services, per request. Testable, no registration needed. The default choice.

IMiddleware

A new instance per request (or whatever lifetime you register). Strongly typed, constructor injection of scoped services just works. Costs a resolve per request and must be registered in DI, or the first request fails.

Endpoint routing: where the endpoint becomes known

Since ASP.NET Core 3.0, routing is split into two middleware. UseRouting selects an endpoint and stores it on the context with SetEndpoint. UseEndpoints (the endpoint middleware) runs it. Everything between the two can call ctx.GetEndpoint() and read the endpoint's metadata: [Authorize], CORS policies, rate-limit policies, your own attributes. That gap is the reason authorization, CORS and rate limiting must sit between them, and it is the main fact behind the ordering rules in Middleware: Order and Patterns.

WebApplication (the minimal hosting model) adds UseRouting at the start and UseEndpoints at the end for you if you map any endpoints and don't call them yourself. Call app.UseRouting() explicitly when something must run before route matching, for example static files or URL rewriting, and when you need your own middleware to sit between routing and the endpoint. Step through the visualizer with different users and paths: try GET /admin as alice, POST /orders anonymously, GET /orders/abc and DELETE /orders.

Your own middleware can use the same mechanism. Attach metadata to an endpoint and read it after routing:

[AttributeUsage(AttributeTargets.Method | AttributeTargets.Class)]
public sealed class AuditAttribute : Attribute { }

app.UseRouting();
app.UseAuthentication();
app.UseAuthorization();
app.Use(async (ctx, next) =>
{
    if (ctx.GetEndpoint()?.Metadata.GetMetadata<AuditAttribute>() is not null)
    {
        var audit = ctx.RequestServices.GetRequiredService<IAuditLog>();
        audit.Write(ctx.User.Identity?.Name, ctx.Request.Method, ctx.Request.Path);
    }
    await next(ctx);
});

app.MapDelete("/orders/{id:int}", DeleteOrder).WithMetadata(new AuditAttribute());

Tip If middleware placed after UseRouting sees GetEndpoint() as null, no route matched: the request is heading for a 404. If middleware before UseRouting needs the endpoint, it is in the wrong place. Move it, don't re-match routes by hand.

The same idea in other stacks

Every major web stack has this pipeline. They differ in three ways: what next is (a delegate, a promise, a chain object, or an inner app), whether "after" code is really after the inner layers finish, and whether the chain is folded once at startup or walked by index on every request.

One timing layer and one short-circuit, five ways

Each tab has a timing layer that wraps everything inside it, and an API-key layer that answers 401 without calling the next layer.

// Jakarta Servlet filters (Spring Boot registers Filter beans; @Order sets position)
@Component
@Order(1)
public class TimingFilter implements Filter {
    private static final Logger log = LoggerFactory.getLogger(TimingFilter.class);

    @Override
    public void doFilter(ServletRequest req, ServletResponse res, FilterChain chain)
            throws IOException, ServletException {
        long t0 = System.nanoTime();
        try {
            chain.doFilter(req, res);                        // the rest of the pipeline
        } finally {
            HttpServletRequest http = (HttpServletRequest) req;
            log.info("{} {} -> {} in {} ms", http.getMethod(), http.getRequestURI(),
                    ((HttpServletResponse) res).getStatus(), (System.nanoTime() - t0) / 1_000_000);
        }
    }
}

@Component
@Order(2)
public class ApiKeyFilter extends OncePerRequestFilter {
    @Override
    protected void doFilterInternal(HttpServletRequest req, HttpServletResponse res,
                                    FilterChain chain) throws ServletException, IOException {
        if (req.getHeader("X-Api-Key") == null) {
            res.setStatus(HttpServletResponse.SC_UNAUTHORIZED);
            return;                                          // chain.doFilter never called
        }
        chain.doFilter(req, res);
    }
}

# Starlette / FastAPI (ASGI). Pure ASGI middleware wraps the inner app.
class TimingMiddleware:
    def __init__(self, app):
        self.app = app

    async def __call__(self, scope, receive, send):
        if scope["type"] != "http":
            return await self.app(scope, receive, send)
        start, status = time.perf_counter(), 500

        async def send_wrapper(message):
            nonlocal status
            if message["type"] == "http.response.start":
                status = message["status"]
            await send(message)

        try:
            await self.app(scope, receive, send_wrapper)   # the rest of the pipeline
        finally:
            log.info("%s %s -> %s in %.1f ms", scope["method"], scope["path"],
                     status, (time.perf_counter() - start) * 1000)

class ApiKeyMiddleware(BaseHTTPMiddleware):  # Starlette's call_next style
    async def dispatch(self, request, call_next):
        if "x-api-key" not in request.headers:
            return PlainTextResponse("missing key", status_code=401)  # short-circuit
        return await call_next(request)

app = Starlette(routes=routes, middleware=[
    Middleware(TimingMiddleware),            # first in the list = outermost
    Middleware(ApiKeyMiddleware),
])

// net/http: a middleware is func(http.Handler) http.Handler
type Middleware func(http.Handler) http.Handler

func Timing(logger *slog.Logger) Middleware {
    return func(next http.Handler) http.Handler {
        return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
            rec := &statusRecorder{ResponseWriter: w, status: http.StatusOK}
            start := time.Now()
            defer func() {
                logger.Info("request", "method", r.Method, "path", r.URL.Path,
                    "status", rec.status, "ms", time.Since(start).Milliseconds())
            }()
            next.ServeHTTP(rec, r) // the rest of the pipeline
        })
    }
}

func APIKey(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        if r.Header.Get("X-Api-Key") == "" {
            http.Error(w, "missing key", http.StatusUnauthorized)
            return // without this return, next still runs
        }
        next.ServeHTTP(w, r)
    })
}

type statusRecorder struct {
    http.ResponseWriter
    status int
}

func (s *statusRecorder) WriteHeader(code int) {
    s.status = code
    s.ResponseWriter.WriteHeader(code)
}

// Chain folds from the end, exactly like ApplicationBuilder.Build.
func Chain(h http.Handler, mws ...Middleware) http.Handler {
    for i := len(mws) - 1; i >= 0; i-- {
        h = mws[i](h)
    }
    return h
}

Why they look different:

  • C# has async/await and first-class delegates, so next is just a RequestDelegate you await. The status code is readable on the way out because HttpResponse is a mutable object.
  • Java servlets predate lambdas, so next is a FilterChain object and you call chain.doFilter. The call is synchronous and blocking, which makes it a true onion. OncePerRequestFilter exists because a servlet container can run the same filter again on internal forwards and error dispatches.
  • Python ASGI has no response object at all: the response is a stream of send messages. To read the status you wrap send. BaseHTTPMiddleware gives you the friendlier call_next, at the cost of buffering and some overhead for streaming responses.
  • Go has no framework: http.Handler is a one-method interface and middleware is a plain higher-order function. ResponseWriter does not expose the status, so you wrap it. Forgetting return after http.Error is the classic Go middleware bug: the 401 is written and the handler still runs.
  • TypeScript with Koa gets the onion from Promises: await next() resolves only when everything inside has finished. Express is different, as the next section shows.

Recognize it when

  • A framework function takes "the next handler" and returns a handler: Django's get_response factory and Go's func(http.Handler) http.Handler are exactly Func<RequestDelegate, RequestDelegate>.
  • The framework has a list whose order is the request order: MIDDLEWARE in Django settings, @Order on Spring filters, r.Use calls in chi, app.use calls in Express.

Express next() vs Koa await next()

Express and Koa look almost identical, but in Express 4 next() returns undefined. If anything downstream is asynchronous, the call to next() returns at the first await, and the code after it runs before the response exists. Express 5 only adds handling for rejected promises from async handlers; next() is still not something you can await.

// Express: time with the response's 'finish' event, not with code after next()
app.use((req, res, next) => {
  const start = performance.now();
  res.on("finish", () => {
    const ms = (performance.now() - start).toFixed(1);
    console.log(`${req.method} ${req.path} -> ${res.statusCode} in ${ms} ms`);
  });
  next();
});

Callback-shaped interceptors

Some stacks don't give you next at all. They call you before and after, and you have to carry state between the two callbacks yourself. The order is still an onion: "before" callbacks run forward and "after" callbacks run in reverse.

public class TimingInterceptor implements HandlerInterceptor {
    @Override
    public boolean preHandle(HttpServletRequest req, HttpServletResponse res, Object handler) {
        req.setAttribute("t0", System.nanoTime());   // no local variable survives to "after"
        return true;                                 // false = short-circuit
    }

    @Override
    public void afterCompletion(HttpServletRequest req, HttpServletResponse res,
                                Object handler, Exception ex) {
        long t0 = (long) req.getAttribute("t0");      // runs even if the handler threw
        log.info("{} -> {} in {} ms", req.getRequestURI(), res.getStatus(),
                (System.nanoTime() - t0) / 1_000_000);
    }
}
// postHandle also exists, but it is skipped when the handler throws.
// Register with WebMvcConfigurer.addInterceptors(registry).

@Component
public class TimingWebFilter implements WebFilter {
    private static final Logger log = LoggerFactory.getLogger(TimingWebFilter.class);

    @Override
    public Mono<Void> filter(ServerWebExchange exchange, WebFilterChain chain) {
        long t0 = System.nanoTime();
        return chain.filter(exchange)                 // the rest of the pipeline, lazily
                .doFinally(signal -> log.info("{} -> {} in {} ms",
                        exchange.getRequest().getPath(),
                        exchange.getResponse().getStatusCode(),
                        (System.nanoTime() - t0) / 1_000_000));
    }
}

# settings.py: MIDDLEWARE = ["myapp.timing.timing_middleware", ...]  top = outermost
def timing_middleware(get_response):         # runs once, at startup
    def middleware(request):                 # runs per request
        start = time.perf_counter()
        response = get_response(request)     # the rest of the pipeline
        response["Server-Timing"] = f"app;dur={(time.perf_counter() - start) * 1000:.1f}"
        return response
    return middleware

Insight Django's middleware factory is Func<RequestDelegate, RequestDelegate>. The outer function receives get_response (next) once, at startup, and returns the per-request function. Django builds the chain by walking MIDDLEWARE from the bottom up, the same reverse fold as Build().

Fold once, or dispatch by index?

There are two ways to turn a list of middleware into a running pipeline, and you'll meet both.

Fold at startup

ASP.NET Core, Go Chain, chi, Django, WSGI/ASGI stacks. Each component is called once to produce a closure that holds next. A request just calls nested closures: no lookups, no allocation for the chain itself. The list can't change after Build(), which is why chi panics if you call Use after defining routes.

Dispatch by index per request

Koa (koa-compose), the Express router, the servlet container's FilterChain. The chain keeps an index; next() means "call stack[i + 1]". This makes it easy to detect next() being called twice and to add middleware dynamically, at the cost of a little work per request.

Here is koa-compose in miniature. The index check is how Koa reports "next() called multiple times":

type Next = () => Promise<void>;
type Middleware<C> = (ctx: C, next: Next) => Promise<void> | void;

export function compose<C>(stack: Middleware<C>[]) {
  return function run(ctx: C): Promise<void> {
    let index = -1;
    function dispatch(i: number): Promise<void> {
      if (i <= index) return Promise.reject(new Error("next() called multiple times"));
      index = i;
      const fn = stack[i];
      if (!fn) return Promise.resolve();          // past the end: nothing left
      try {
        return Promise.resolve(fn(ctx, () => dispatch(i + 1)));
      } catch (err) {
        return Promise.reject(err);
      }
    }
    return dispatch(0);
  };
}

Which design patterns is this?

A middleware pipeline combines two classic patterns from Behavioral Patterns and Structural Patterns, and seeing both explains its behaviour.

Chain of Responsibility

Pass a request along a chain until someone handles it. Middleware borrows the "may stop the chain" part: auth answers 401, static files answer with a file, health checks answer 200. Classic CoR handlers usually do either handle or forward; middleware usually does both.

Decorator

Wrap an object in another with the same interface and add behaviour around the call. Middleware borrows the "same interface, wrapped" part: every layer is a RequestDelegate around a RequestDelegate. This is why the response comes back through the same layers.

The same shape elsewhere

HttpClient's DelegatingHandler is the same onion on the outbound side (see Outbound Pipelines). MediatR behaviours, gRPC interceptors and Polly's resilience pipelines are all "a handler that wraps the next handler" too.

When to use middleware, and when not

Middleware is the right tool when a concern applies to HTTP requests as such, mostly regardless of which endpoint handles them. It is the wrong tool when the concern needs to know about your actions, models or business rules.

You need to… Use Why
Handle errors, log, time, add correlation IDs, set security headers for every request Middleware Applies to all requests, including ones that never reach an endpoint (404s, static files).
Reject requests early (auth, API keys, IP filtering, rate limits) Middleware, after UseRouting if it depends on the endpoint Short-circuiting early is cheaper than doing the work and discarding it.
Serve something that isn't an endpoint (static files, a health page, a sub-app) Middleware or Map/MapWhen It answers the request itself.
Behaviour for one endpoint or a group Endpoint metadata read by middleware, an endpoint filter, or a route group Keep the decision next to the endpoint, not in a path check inside global middleware.
Validate bound arguments, change an action's result, handle errors per controller MVC filters / endpoint filters Middleware runs before model binding and can't see your arguments or IActionResult. See Middleware: Order and Patterns.
Business rules (discounts, permissions on a specific order) Neither: application code Hiding business rules in the pipeline makes them invisible and untestable.
Retry, log or authenticate outgoing HTTP calls DelegatingHandler Same pattern, client side. See Outbound Pipelines.

Costs to keep in mind:

  • Every layer runs for every request. A slow or allocating middleware taxes the whole service, including health checks. Keep the per-request path cheap, and short-circuit early for things like static files.
  • Order is implicit coupling. Nothing in the type system says "auth must come after routing". The order is a contract that lives only in Program.cs and in your head, which is why Middleware: Order and Patterns exists.
  • Debugging is indirect. A 401 or a missing header might come from any layer. Good middleware logs when it short-circuits.

Pitfalls

Pitfall: calling next twice, or after writing the response A retry layer that calls await next(ctx) again after a failure runs the endpoint twice on the same HttpContext. If the first attempt already wrote headers, the second throws "StatusCode cannot be set because the response has already started". Retries belong on outgoing calls, not around the inbound pipeline. Likewise, never call next after you have written a response yourself.

Pitfall: not awaiting next next(ctx); without await (or returning a Task you never await) lets your middleware finish before the inner layers do. Your after-code runs too early, exceptions from inside are not observed by your try/catch, and the HttpContext may be used after the request is finished, which can crash the server. Express has this behaviour built in; in C# it is always a bug.

Pitfall: Run or a terminal component in the middle app.Run(...) ignores next, so every Use registered after it is dead code. There is no warning. The same is true for any middleware that never calls next, for example a catch-all MapFallback style handler registered too early.

Pitfall: scoped services in a conventional middleware constructor The constructor runs once. A DbContext injected there becomes a single shared instance: not thread-safe, never disposed, and leaking state between requests. In Development, scope validation turns this into a startup error; in Production it silently works until it doesn't. Inject scoped services into InvokeAsync, or implement IMiddleware.

Pitfall: per-request state in middleware fields For the same reason, a field like private int _count or private string _currentUser in a conventional middleware is shared by every concurrent request. Keep per-request state in locals, HttpContext.Items, or a feature on the context.

Pitfall: changing headers after the response has started Code after await next(ctx) often wants to add a header, for example Server-Timing. If the endpoint already wrote the body, the headers are gone. Use ctx.Response.OnStarting(...) to add headers just before they are sent. Middleware: Order and Patterns covers this in detail.

Pitfall: Go middleware that forgets to return, Express middleware that never ends In Go, http.Error(w, …, 401) followed by next.ServeHTTP(w, r) writes the 401 and runs the handler, which then fails to write its own status ("superfluous WriteHeader call"). In Express, a middleware that neither sends a response nor calls next() leaves the request hanging until the client times out.

Pitfall: blocking in middleware .Result or .Wait() on a task inside middleware blocks a thread-pool thread for every request in flight. Under load this starves the thread pool and the whole service stalls. Middleware is on the hot path: keep it fully async.

Checklist

  • Each middleware does one cross-cutting job and is named after it.
  • Code that must always run on the way out is in finally (or defer in Go, doFinally in WebFlux).
  • next is awaited exactly once, or deliberately not called (a short-circuit), never both.
  • Short-circuits set a status code (and ideally a ProblemDetails body) and log why.
  • Middleware that needs endpoint metadata sits after UseRouting; middleware that must avoid routing work sits before it.
  • No Run or other terminal middleware before middleware that is supposed to run.
  • Conventional middleware: only singletons in the constructor; scoped services on InvokeAsync.
  • No per-request state in middleware fields.
  • Headers added late use Response.OnStarting.
  • Branches use Map for path prefixes (remembering PathBase), UseWhen when you need to rejoin.
  • Middleware on the hot path is async, cheap and allocation-aware.

Self-check

You register Use A, Use B, Run C, Use D. A and B log before and after next. What is logged for one request?

A before, B before, C, B after, A after. D never runs: Run C ignored its next, so when Build() folded the list, the delegate for D was created and immediately thrown away.

Why must the exception handler be registered first?

A layer can only catch exceptions thrown inside it, that is, by layers registered after it. If the exception handler were registered after authentication, an exception thrown by authentication would unwind straight past it to the server, which would return a bare 500 with no ProblemDetails and none of your logging.

Inside app.Map("/api", …), a request for /api/orders/7 arrives. What are Path and PathBase in the branch, and after it returns?

In the branch: PathBase = "/api", Path = "/orders/7". After the branch returns, Map restores the originals: PathBase = "", Path = "/api/orders/7". /apix/orders would not enter the branch at all, because Map matches whole segments.

Middleware registered before UseRouting calls ctx.GetEndpoint() to read an [Audit] attribute, and always gets null. Why, and what is the fix?

The endpoint is only selected inside UseRouting, which calls SetEndpoint. Before that there is nothing to read. Move the middleware after UseRouting (and after auth, if it needs the user).

A conventional middleware takes AppDbContext in its constructor. What happens in Development, and in Production?

In Development, scope validation is on by default, so resolving a scoped service from the root provider throws at startup: "Cannot resolve scoped service … from root provider". In Production validation is off, so one AppDbContext is created and shared by every request for the app's lifetime: a captive dependency that is not thread-safe. Move it to an InvokeAsync parameter.

An Express timing middleware always logs about 0 ms even though requests take 100 ms. Why? What does the same code do in Koa?

In Express, next() returns as soon as the downstream handler reaches its first await, so the "after" line runs before the response is produced. Measure on res.on("finish"). In Koa, await next() waits until every inner layer has finished, so the same shape measures the full 100 ms.

What is the one difference between MapWhen and UseWhen in the from-scratch builder?

The terminal delegate of the branch. MapWhen builds the branch with its own 404 terminal, so it never returns to the main pipeline. UseWhen builds the branch with the main pipeline's next as its terminal, so when the branch's last middleware calls next, control continues in the main pipeline.
