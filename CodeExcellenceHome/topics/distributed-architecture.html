Services, Messaging & Events

Modular monolith vs microservices, sync vs async calls, queues and pub/sub, the outbox pattern, sagas, CQRS and event sourcing.

Advanced → Expert~70 min studyBuilds on: Application Architecture StylesUpdated 2026-11-03

The problem: "let's split it into microservices"

A team of nine maintains a successful e-commerce monolith. Builds are slow and merges are painful, so they decide to "go microservices". Eighteen months later they have fourteen services. Checkout now looks like this:

[HttpPost("/checkout")]
public async Task<IActionResult> Checkout(CheckoutRequest req)
{
    var cart     = await _http.GetFromJsonAsync<Cart>($"http://cart/carts/{req.CartId}");          // hop 1
    var customer = await _http.GetFromJsonAsync<Customer>($"http://customers/{cart.CustomerId}");  // hop 2
    var prices   = await _http.PostAsJsonAsync("http://pricing/quote", cart.Lines);                // hop 3
    await _http.PostAsJsonAsync("http://inventory/reservations", cart.Lines);                      // hop 4: side effect
    await _http.PostAsJsonAsync("http://payments/charges", new { customer.CardToken, total });     // hop 5: side effect
    await _db.ExecuteAsync("INSERT INTO orders ...");             // the SAME database Inventory and Payments read
    await _http.PostAsJsonAsync("http://email/send", new { customer.Email });                      // hop 6
    return Ok();
    // Payment fails after the stock was reserved? Email times out after the charge? Nobody undoes anything.
}

Every checkout is now six synchronous network calls. If any one of fourteen services is down, checkout is down. A release of Pricing must be coordinated with Cart because they share DTOs. All services still read and write one shared database, so a column rename needs four teams. Nobody can answer "why is checkout slow?" without opening six dashboards. The team got all of the cost of distribution and none of the independence: a distributed monolith.

The patterns on this page exist to get the independence without the chaos:

  • Boundaries and data ownership: each service owns its data, and only that service writes it.
  • Asynchronous messaging: services tell each other facts instead of waiting on each other.
  • The outbox and the inbox: messages are never lost, and duplicates are harmless.
  • Sagas: a business process spans services without a distributed transaction.
  • Events, event sourcing and consistency models: you design for "eventually" on purpose.
  • Gateways, the mesh and the strangler fig: you reach and migrate services safely.

The most important pattern is the first decision: whether to distribute at all.

The distribution rule: a network call is not a method call. It can fail, it is slow, and it has no shared transaction. Split a system only along boundaries where those costs buy you something specific: independent deployment, independent scaling, team autonomy or fault isolation. Inside a boundary keep calls in-process. Across boundaries prefer asynchronous messages over synchronous chains, and accept eventual consistency deliberately.

This page builds on Application Architecture Styles, especially modular monoliths and CQRS, and on Domain-Driven Design Essentials, where bounded contexts become service candidates and integration events become messages. It links to, rather than repeats, Resilience Patterns (timeouts, retries, circuit breakers), Outbound HTTP Pipelines, Caching and Async & Concurrency.

The spectrum: monolith → modular monolith → microservices

"Monolith vs microservices" is a false choice. There is a spectrum, and every step to the right buys some independence and pays for it in operational cost:

Monolith Modular monolith Microservices
Deployables 1 1 one per service (10–1000)
Calls between areas method calls method calls through a module's public API HTTP / gRPC / messages over the network
Transactions one ACID transaction one ACID transaction (if you allow it across modules) local only; sagas across services
Data shared tables schema per module, no cross-module joins database per service
Boundary enforcement none build-time: ArchUnit, NetArchTest, import-linter, Go internal/ physical: the network
Failure modes process crash process crash partial failure, timeouts, duplicates, reordering
Debugging stack trace stack trace distributed tracing (Observability)
Team scaling painful past ~10 devs good to ~50+ devs with module ownership good for many teams, if boundaries are right
Ops cost lowest low highest: CI/CD per service, platform, on-call

The modular monolith is not a stepping stone you're embarrassed about

Shopify runs one of the largest Rails monoliths in the world as a modular monolith. Many companies that went all-in on microservices have publicly merged services back together. A modular monolith gives you the most valuable thing microservices promise, clear ownership boundaries enforced in the build, without the network. If a module later needs to scale or deploy independently, its boundary is already clean, so extracting it is a mechanical job. The Application Architecture page shows how to enforce the boundaries.

What actually changes when a call crosses the network

In-process call Network call
~ nanoseconds ~ 0.5–5 ms in a data centre, 50–150 ms across regions, with a long tail
succeeds or throws succeeds, fails, or you don't know (a timeout after the server did the work)
exactly once maybe zero times, once, or twice (retries)
shared transaction no shared transaction
refactor with the IDE a versioned contract that old clients still call
same version always caller and callee deploy independently, so versions overlap
no security boundary needs TLS, authentication and authorization
one stack trace needs a trace id propagated across every hop

The third row is the one that bites. "I called Payments and got a timeout" doesn't mean the charge failed. It may have succeeded a millisecond after you gave up. Every pattern in the rest of this page (idempotency keys, the outbox, the inbox, sagas) exists because of that row.

The first two fallacies compound in a way that surprises people. If every service is up 99.9% of the time, a request that needs six of them in a row is up 0.9996 = 99.4% of the time. That is about 4.3 hours of downtime a month instead of 43 minutes. Latency compounds too: if every hop has a 1% chance of being slow, a six-hop request hits at least one slow hop 1 − 0.996 ≈ 6% of the time. Play with it: add services and switch the call style.

Availability multiplies; asynchrony breaks the chain

A synchronous chain is only as available as the product of its links. Three tactics cut the chain:

  • Fewer hops. Merge services that always change together, or call one service that already has the data.
  • Parallel calls instead of sequential. Latency becomes the maximum rather than the sum, but availability still multiplies.
  • Asynchronous messages. The caller only needs itself and the broker to be up. Everything else happens later.

This is why architects push for async messaging between bounded contexts. It is not fashion; it is arithmetic. The cost is that "later" means eventual consistency, which the rest of this page teaches you to handle.

Service boundaries and data ownership

The single most important rule for services is about data, not code: each service owns its data, and no other service reads or writes it directly. Other services ask through its API, or keep their own copy built from its events.

"Database per service" doesn't have to mean one database server per service. The rule is about ownership. A schema per service on a shared server, with credentials that can only reach their own schema, is a perfectly good start.

How do I query across services then?

The first question everybody asks. There are three answers, in order of preference:

Technique How it works Use when Cost
Don't need to Redraw the boundary so the data lives together Two services always change and query together A merge, but less to run
Replicated read model Subscribe to the owner's events and keep a local, query-shaped copy Frequent reads; staleness of seconds is fine Eventual consistency; an event contract to version
API composition Call the owners and join in memory (often in a gateway or BFF) Rare queries, small result sets, must be fresh Latency and availability multiply (see the fallacies)

The anti-pattern is reading the other service's tables "just for this report". It works until that team renames a column. For analytics, stream every service's events into a data warehouse or lake, which is built for cross-domain queries.

Where do the boundaries go?

Use bounded contexts from Domain-Driven Design as the starting point. A service is at most one bounded context; one context may later split into a few services for scaling. Good boundaries share these properties:

  • High cohesion inside. Things that change together for the same business reason live together.
  • Low chattiness across. If two services exchange ten calls per user request, they are one service.
  • Own their invariants. A rule like "stock can't go negative" must be checkable inside one service and one local transaction.
  • One team owns it. Conway's law: the system mirrors the org chart, so align them on purpose.

Recognize a distributed monolith

  • You must deploy several services together, in a specific order.
  • Services share a database, or a "common" library of domain classes.
  • One user request fans out into a long synchronous chain.
  • A change to one business rule touches many repos.
  • The services can't run or be tested on their own.

If several apply, you've paid for distribution without getting independence. Merge services back into modules, or redraw the boundaries around data ownership.

Sync vs async communication

There are three kinds of messages between services. Naming them correctly avoids half of all design arguments:

Kind Meaning Name Direction Typical transport
Query "Tell me something", no side effects GetOrder request → response HTTP GET, gRPC
Command "Please do this"; may be rejected ChargePayment to exactly one owner HTTP POST, gRPC, or a queue
Event "This happened"; a fact, can't be rejected OrderPlaced to zero or more subscribers a topic (pub/sub)

Commands are imperative and owned by the receiver. Events are past tense and owned by the sender. If you find yourself publishing SendWelcomeEmail to a topic, that's a command pretending to be an event: the sender is still deciding what the receiver should do.

Watch the difference when a service breaks. Pick a style, then make Email, Inventory or Payment misbehave:

Prefer synchronous when Prefer asynchronous when
The user needs the answer now (a query, validation, a price) The work can finish after the response (email, invoicing, analytics)
The operation is a read with no side effects Several services must react to the same fact
The callee is highly available and fast The callee is slow, batchy or often down
Strong consistency is required for this step A short window of staleness is acceptable
The interaction is simple and you want simple debugging You want to absorb load spikes (queue as a buffer)

Sync calls still need their seatbelts

Every synchronous call needs a timeout, a bounded retry with jitter for idempotent operations, and a circuit breaker. Those belong in your outbound HTTP pipeline, not hand-written at each call site. See Resilience Patterns and Outbound HTTP Pipelines. For the protocol choice (REST, gRPC, GraphQL, WebSockets, SSE), see API Protocols.

// orders: chi handler
func (h *Handler) Place(w http.ResponseWriter, r *http.Request) {
    var cmd PlaceOrder
    if err := json.NewDecoder(r.Body).Decode(&cmd); err != nil { http.Error(w, err.Error(), 400); return }
    order, err := h.svc.Place(r.Context(), cmd)
    if err != nil { http.Error(w, err.Error(), 422); return }
    evt, _ := json.Marshal(contracts.OrderPlacedV1{EventID: uuid.New(), OrderID: order.ID, CustomerID: order.CustomerID,
        Total: order.Total.Amount, Currency: order.Total.Currency, OccurredAt: time.Now().UTC()})
    err = h.writer.WriteMessages(r.Context(), kafka.Message{Key: []byte(order.ID.String()), Value: evt})
    if err != nil { http.Error(w, "publish failed", 500); return }   // …and the order is already saved: see "outbox"
    w.WriteHeader(http.StatusAccepted)
    json.NewEncoder(w).Encode(map[string]any{"id": order.ID, "status": "pending"})
}

// shipping: consumer loop
func Consume(ctx context.Context, repo ShipmentRepo) error {
    rd := kafka.NewReader(kafka.ReaderConfig{Brokers: []string{"kafka:9092"}, GroupID: "shipping", Topic: "orders.order-placed.v1"})
    defer rd.Close()
    for {
        m, err := rd.FetchMessage(ctx)                 // fetch, don't auto-commit
        if err != nil { return err }
        var evt contracts.OrderPlacedV1
        if err := json.Unmarshal(m.Value, &evt); err != nil { /* poison: send to DLQ */ continue }
        if err := repo.CreateFor(ctx, evt.OrderID); err != nil { return err }   // restart ⇒ redelivery
        if err := rd.CommitMessages(ctx, m); err != nil { return err }
    }
}

Notice what every version has in common. The event is a versioned contract (V1) that carries ids plus the data consumers need. It is keyed by orderId, so all events for one order stay in order. The consumer acknowledges only after its work commits. And every version has the same hidden bug on the publishing side: the database commit and the publish are two separate writes. The outbox section fixes that.

Message brokers: queues, topics and partitions

A broker stores messages durably so the sender and receiver don't have to be up at the same time. Brokers come in two families, and they deliver very differently.

Delivery guarantees

No broker can give you "exactly-once delivery" across a network. A crash can always happen between "did the work" and "told the broker". What you choose is where the duplicate or the loss happens:

Guarantee Consumer does On crash Result Use for
At-most-once ack, then process message lost 0 or 1 times metrics, telemetry you can afford to drop
At-least-once process, then ack message redelivered 1 or more times almost everything (the default to design for)
Effectively-once at-least-once + an idempotent handler redelivered, ignored the effect happens once money, stock, anything with side effects

Kafka's "exactly-once semantics" is real, but it covers read-process-write inside Kafka (transactions across topics and offsets). The moment your handler writes to a database or calls an API, you're back to at-least-once plus idempotency. That's the inbox section.

Ordering

  • Queues with competing consumers give up ordering as soon as you have two workers or a retry. Message 2 can finish before a retried message 1.
  • Partitioned logs order messages per partition. Key by the entity whose history matters (orderId), and all events for one order arrive in order.
  • Session or group ids (Azure Service Bus sessions, SQS FIFO message group id, RabbitMQ single active consumer) give per-key ordering on queue brokers.
  • Design for disorder anyway. Carry a version or sequence number in each event, and have consumers ignore anything older than what they already applied.

Poison messages and dead-letter queues

A poison message fails every time: bad data, a bug, a schema mismatch. Without a limit, it blocks a partition forever or burns CPU in a retry loop. Every consumer needs:

  1. Retry with backoff for transient errors (a database timeout).
  2. A maximum delivery count, after which the message moves to a dead-letter queue (DLQ).
  3. No retries for permanent errors, such as a validation or deserialization failure: dead-letter immediately.
  4. An alert on DLQ depth, plus a tool to inspect messages and replay them after the fix.

Now play with it. Switch between a queue, a partitioned topic and fan-out subscriptions, then add a slow consumer or a crash before the ack. Watch the duplicate and out-of-order counters:

Broker Model Strong at Watch out for

Use a messaging library, not the raw client

Retries, DLQ routing, serialization, outbox and inbox are the same in every service. Libraries such as MassTransit or NServiceBus (.NET), Spring Cloud Stream (Java), Watermill (Go) and NestJS's microservices transports provide them, so your code handles messages instead of plumbing. Keep the raw client for when you need a feature the library hides.

The transactional outbox

Here's the hidden bug from the code above. "Save the order, then publish OrderPlaced" is a dual write: two systems with no shared transaction. A crash between the two writes leaves them disagreeing, forever.

The fix is simple once you see it. Don't publish in the request. Write the event as a row in an outbox table in the same local transaction as the business change. A separate relay reads unsent rows, publishes them, and marks them sent. If the relay crashes after publishing but before marking, the row is published again. That's at-least-once, which consumers already handle (see the inbox section).

Try all three strategies against each failure:

The outbox table

CREATE TABLE outbox (
    id            uuid PRIMARY KEY,              -- doubles as the message/event id for consumer dedup
    aggregate_id  text        NOT NULL,          -- used as the partition key ⇒ per-aggregate order
    type          text        NOT NULL,          -- 'orders.order-placed.v1'
    payload       jsonb       NOT NULL,
    occurred_at   timestamptz NOT NULL DEFAULT now(),
    sent_at       timestamptz NULL,              -- NULL = not yet published
    attempts      int         NOT NULL DEFAULT 0
);
CREATE INDEX outbox_unsent ON outbox (occurred_at) WHERE sent_at IS NULL;

-- Relay: claim a batch without blocking other relay instances.
SELECT id, aggregate_id, type, payload FROM outbox
WHERE sent_at IS NULL ORDER BY occurred_at
LIMIT 100 FOR UPDATE SKIP LOCKED;

There are two ways to run the relay:

  • Polling publisher. A background loop runs the query above. Simple, and portable to any SQL database. Adds a polling delay (typically 100 ms to 1 s) and some database load.
  • Change data capture (CDC). A tool like Debezium tails the database's transaction log and publishes outbox inserts. Near-real-time with no polling queries, but one more piece of infrastructure to run.

Outbox write and relay in five stacks

// 1) Write: the event row joins the same DbContext transaction as the order.
public sealed class PlaceOrderHandler(OrdersDb db)
{
    public async Task<Guid> Handle(PlaceOrder cmd, CancellationToken ct)
    {
        var order = Order.Place(cmd.CustomerId, cmd.Lines);
        db.Orders.Add(order);
        db.Outbox.Add(OutboxMessage.From(order.Id, new OrderPlacedV1(
            Guid.NewGuid(), order.Id, order.CustomerId, order.Total.Amount, order.Total.Currency, DateTimeOffset.UtcNow)));
        await db.SaveChangesAsync(ct);           // one transaction: both rows or neither
        return order.Id;
    }
}

// 2) Relay: a hosted service that drains the table.
public sealed class OutboxRelay(IServiceScopeFactory scopes, IPublishEndpoint bus, ILogger<OutboxRelay> log) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stop)
    {
        while (!stop.IsCancellationRequested)
        {
            await using var scope = scopes.CreateAsyncScope();
            var db = scope.ServiceProvider.GetRequiredService<OrdersDb>();
            await using var tx = await db.Database.BeginTransactionAsync(stop);
            var batch = await db.Outbox
                .FromSql($"SELECT * FROM outbox WHERE sent_at IS NULL ORDER BY occurred_at LIMIT 100 FOR UPDATE SKIP LOCKED")
                .ToListAsync(stop);
            foreach (var m in batch)
            {
                await bus.Publish(m.Deserialize(), ctx => ctx.MessageId = m.Id, stop);
                m.SentAt = DateTimeOffset.UtcNow;
            }
            await db.SaveChangesAsync(stop);
            await tx.CommitAsync(stop);
            if (batch.Count == 0) await Task.Delay(TimeSpan.FromMilliseconds(500), stop);
        }
    }
}

func drainOnce(ctx context.Context, db *sql.DB, w *kafka.Writer) error {
    tx, err := db.BeginTx(ctx, nil)
    if err != nil { return err }
    defer tx.Rollback()
    rows, err := tx.QueryContext(ctx, `SELECT id, aggregate_id, type, payload FROM outbox
        WHERE sent_at IS NULL ORDER BY occurred_at LIMIT 100 FOR UPDATE SKIP LOCKED`)
    if err != nil { return err }
    var msgs []kafka.Message
    var ids []uuid.UUID
    for rows.Next() {
        var id uuid.UUID; var key, typ string; var payload []byte
        if err := rows.Scan(&id, &key, &typ, &payload); err != nil { rows.Close(); return err }
        msgs = append(msgs, kafka.Message{Topic: typ, Key: []byte(key), Value: payload,
            Headers: []kafka.Header{{Key: "message-id", Value: []byte(id.String())}}})
        ids = append(ids, id)
    }
    rows.Close()
    if len(msgs) == 0 { return nil }
    if err := w.WriteMessages(ctx, msgs...); err != nil { return err }   // w has no fixed Topic; RequiredAcks: kafka.RequireAll
    if _, err := tx.ExecContext(ctx, `UPDATE outbox SET sent_at = now() WHERE id = ANY($1)`, pq.Array(ids)); err != nil { return err }
    return tx.Commit()
}

Outbox pitfalls

  • Publishing from a domain-event handler that runs after commit. That's the dual write again. The outbox insert must be in the transaction.
  • Never cleaning up. Delete or archive sent rows after a retention window, or the table and its index grow without limit.
  • Unordered relays. Several relay instances with SKIP LOCKED can publish two events for the same aggregate out of order. Partition the relay by aggregate key, or let consumers handle versions.
  • Assuming exactly-once. The relay will publish duplicates after a crash. The outbox row id becomes the message id, which consumers use to deduplicate.

Inbox and idempotent consumers

At-least-once delivery means every consumer will see duplicates: after a relay crash, a broker redelivery, a consumer-group rebalance or a retry. The consumer has to make sure a duplicate has no extra effect. There are two classic tools:

  • Inbox (deduplication table). Record each processed message id in the same transaction as the handler's writes. A duplicate hits the primary key and is skipped.
  • Naturally idempotent operations. Write the operation so that doing it twice gives the same result. "Set status = Paid" is idempotent; "add 10 points" is not. An upsert keyed by the business id is idempotent; a blind insert is not.

The trap is in the middle: "check the inbox, do the work, record the id" as separate commits. A crash between the work and the record re-runs the work. Try each strategy below, with each operation, and then add the crash:

Strategy How Survives crash between work and record? Use when
Natural idempotency SET status = 'Paid', upsert by key, PUT semantics yes, nothing to record you can phrase the change as "make it so"
Inbox in the same transaction INSERT INTO inbox(message_id) + business writes, one commit yes, both roll back together the handler writes to its own database
Version / sequence check apply only if event.version = current + 1 yes ordered streams of one aggregate (projections)
Idempotency key at the downstream API pass the message id as Idempotency-Key to Stripe and similar APIs yes, if the API honours it the side effect is an external call
Check, act, record (separate commits) read inbox, act, insert later no: a duplicate effect never on its own

The inbox only covers your own database

The inbox works because the dedup row and the business change share one local transaction. If the handler calls an external API (send an email, charge a card), no transaction covers it. Pass the message id as an idempotency key to that API, or accept the rare duplicate (a second email is usually fine; a second charge is not).

Sagas: business transactions across services

Placing an order touches Orders, Payment, Inventory and Shipping, and each has its own database. There's no transaction spanning all four, so how do you keep them consistent?

A saga is a sequence of local transactions. Each step commits in one service and triggers the next. If a step fails, the saga runs compensating transactions for the steps that already committed, in reverse order. The result is eventually consistent: for a short time the order is "Pending", and the rest of the system must handle that state.

Pick a style and a failure, then step through. Watch the order's state and which compensations run:

Orchestration

  • The flow is readable in one place: a state machine or workflow.
  • Easy to answer "where is order 42 stuck?": query the saga state.
  • Services stay simple: handle a command, reply.
  • Cost: the orchestrator is one more component, and it can grow into a god service that holds business rules belonging to the participants.
  • Best for: 4+ steps, branching, timeouts, anything a human will ask about.

Choreography

  • No central component; services are loosely coupled through events.
  • Adding a new reaction (send a survey after delivery) means just a new subscriber.
  • Cost: the flow is implicit. Nobody can see it end to end without tracing, cyclic dependencies creep in, and "why didn't it ship?" becomes archaeology.
  • Best for: 2–3 steps, simple fan-out reactions, and teams that already have good distributed tracing.

Designing compensations

A compensation is not a rollback. The charge happened and the customer may have seen it, so the compensation is a new business action, a refund, with its own rules. Design rules that make sagas survivable:

Make every step safe to repeat and every undo possible

  • Semantic lock. Mark in-flight records with a state such as Pending, so other operations know not to treat them as final (no shipping a pending order, no counting reserved stock as sold).
  • Order steps by risk. Put the steps most likely to fail (validation, stock check) first, and the hard-to-undo ones (send the parcel, email the customer) last.
  • Pivot transaction. The step after which the saga only goes forward (for example, the charge is captured). Steps after the pivot must be retriable until they succeed, not compensated.
  • Compensations must eventually succeed. Retry them with backoff, and when retries run out, dead-letter and alert a human (the viz shows this). Design an API that can always refund.
  • Every step and compensation is idempotent, because the messages that drive them are at-least-once.
  • Timeouts are failures too. If Payment never replies, the orchestrator must decide after N minutes, not wait forever.

            .Then(c => c.Saga.Total = c.Message.Total)
            .Send(c => new ChargePayment(c.Saga.CorrelationId, c.Saga.Total))
            .TransitionTo(Charging));

        During(Charging, When(Charged)
            .Then(c => c.Saga.PaymentId = c.Message.PaymentId)
            .Send(c => new ReserveStock(c.Saga.CorrelationId))
            .TransitionTo(Reserving));

        During(Reserving,
            When(Reserved).Send(c => new ConfirmOrder(c.Saga.CorrelationId)).Finalize(),
            When(NoStock)                                          // compensate in reverse
                .Send(c => new RefundPayment(c.Saga.CorrelationId, c.Saga.PaymentId!.Value))
                .TransitionTo(Refunding));

        During(Refunding, When(Refunded)
            .Send(c => new CancelOrder(c.Saga.CorrelationId, "out of stock"))
            .Finalize());

        SetCompletedWhenFinalized();
    }
}

            await workflow.execute_activity(confirm, order.id, **STEP)
            return "confirmed"
        except Exception:

                await workflow.execute_activity(undo, arg, start_to_close_timeout=timedelta(seconds=30),
                                                retry_policy=RetryPolicy(maximum_attempts=0))  # retry forever
            await workflow.execute_activity(cancel, order.id, **STEP)
            return "cancelled"

// a is the registered activities struct: var a *OrderActivities
func PlaceOrderSaga(ctx workflow.Context, order OrderInput) (string, error) {
    ctx = workflow.WithActivityOptions(ctx, workflow.ActivityOptions{
        StartToCloseTimeout: 30 * time.Second,
        RetryPolicy:         &temporal.RetryPolicy{MaximumAttempts: 5},
    })
    var compensations []func(workflow.Context) error
    compensate := func() {
        undo := workflow.WithRetryPolicy(ctx, temporal.RetryPolicy{MaximumAttempts: 0}) // retry until it works
        for i := len(compensations) - 1; i >= 0; i-- {
            _ = compensations[i](undo)
        }
        _ = workflow.ExecuteActivity(ctx, a.Cancel, order.ID).Get(ctx, nil)
    }

    var paymentID string
    if err := workflow.ExecuteActivity(ctx, a.Charge, order).Get(ctx, &paymentID); err != nil {
        compensate(); return "cancelled", nil
    }
    compensations = append(compensations, func(c workflow.Context) error {
        return workflow.ExecuteActivity(c, a.Refund, paymentID).Get(c, nil)
    })
    if err := workflow.ExecuteActivity(ctx, a.ReserveStock, order).Get(ctx, nil); err != nil {
        compensate(); return "cancelled", nil
    }
    compensations = append(compensations, func(c workflow.Context) error {
        return workflow.ExecuteActivity(c, a.ReleaseStock, order.ID).Get(c, nil)
    })
    if err := workflow.ExecuteActivity(ctx, a.BookCourier, order).Get(ctx, nil); err != nil {
        compensate(); return "cancelled", nil
    }
    return "confirmed", workflow.ExecuteActivity(ctx, a.Confirm, order.ID).Get(ctx, nil)
}

  const compensations: Array<() => Promise<void>> = [];
  try {
    const paymentId = await step.charge(order);
    compensations.unshift(() => undo.refund(paymentId));         // unshift ⇒ runs in reverse order
    await step.reserveStock(order);

    await step.bookCourier(order);
    await step.confirm(order.id);
    return 'confirmed';
  } catch {
    for (const c of compensations) await c();
    await step.cancel(order.id);
    return 'cancelled';
  }
}

Event-driven architecture: three different things

"Event-driven" gets used for three patterns that have very different costs. Know which one you're proposing:

Pattern What the event carries Consumer does Benefit Cost
Event notification just ids: OrderPlaced { orderId } calls back to the owner for details tiny contracts, low coupling a callback storm; the owner must be up
Event-carried state transfer the data consumers need: ids, totals, address keeps a local copy; never calls back consumers are autonomous and fast bigger contracts to version; data duplicated
Event sourcing every state change, as the source of truth rebuilds state by replaying events full audit, time travel, new projections a different way to store data; hard to change

The first two are about communication between services, and most systems use them. Event sourcing is about how one service stores its own data, and few services need it. Don't confuse "we publish events" with "we're event-sourced".

Event sourcing basics

A normal service stores current state and overwrites it. An event-sourced service stores the sequence of facts that led to the state, and computes the state by folding over them. The event log is the source of truth; tables for querying are projections built from it.

Event sourcing fits when

  • An audit trail is a requirement, not a nice-to-have (ledgers, claims, trading, healthcare).
  • The business asks "how did we get here?" or "what did we know on 3 March?"
  • You need many read models of the same facts, including ones you haven't thought of yet.
  • The domain is naturally a sequence of events (accounting, logistics tracking, workflows).

Avoid it when

  • It's CRUD: the history nobody asked for costs you every day.
  • The team is new to it and the deadline is close. The learning curve is real: versioning events, projections, rebuilds.
  • You need ad-hoc queries on current state with no time to build projections.
  • Data must be truly deleted (GDPR) and you haven't planned crypto-shredding or stream rewriting.
  • You'd use it for the whole system. Apply it to the one or two contexts that benefit.

CQRS across services

Inside one service, CQRS separates the write model from read models. Across services, the same idea solves "how do I query data owned by five services?": build a dedicated read model (a search index, a reporting store, a BFF's cache) that subscribes to all of their events. The read side is eventually consistent, so the UI must tolerate a write that isn't visible yet. Common answers are returning the new state in the command's response, or showing "processing…" until the read model catches up.

CAP, PACELC and consistency models

Once data is replicated across machines (and every service with a replicated database, a cache or a read model does this), you face a choice that no technology removes:

  • CAP. When a network Partition happens, a replicated system must choose: refuse some requests to stay Consistent, or answer every request and stay Available, possibly with stale or conflicting data. Partitions aren't optional, so the real choice is C or A during a partition.
  • PACELC. Else, when there's no partition, you still choose between Latency and Consistency. Waiting for a quorum in another region costs round trips on every request. This is the trade-off you pay every day, not only during outages.

Choose consistency per use case, not per system

The checkout's stock decrement needs strong consistency inside one service: one database, one transaction, one aggregate. The product page's "only 3 left!" can be seconds stale. Most systems are strong inside a service, eventual between services. That's exactly the line a bounded context draws. When a requirement says "must be consistent with" another service, push back: what is the business cost of five seconds of staleness? Often there isn't one, and you can use a saga or a read model.

Distributed transactions, and why 2PC is avoided

The obvious way to keep several databases consistent is two-phase commit (2PC), as in XA or MSDTC. A coordinator asks every participant to prepare (do the work, hold the locks, promise to commit), and if all vote YES, tells them to commit. It's atomic. So why does almost every microservices guide say "don't"?

Run the coordinator crash: after voting YES, participants are in doubt. They can't commit, because they don't know the decision, and they can't abort, because they promised. They hold their locks until the coordinator comes back. 2PC is a blocking protocol: its availability is the product of every participant's availability, plus the coordinator's.

Two-phase commit Saga
Consistency atomic (ACID across resources) eventual, with compensations; intermediate states are visible
Isolation yes, via locks held across the network none by default: use semantic locks (Pending)
Availability every participant and the coordinator must be up each step needs only its own service
Latency locks held for at least 2 round trips × the slowest participant each local transaction is short
Failure mode in-doubt transactions block resources a stuck saga needs an operator, but nothing else is blocked
Support needs XA-capable resources; most brokers, NoSQL stores and HTTP APIs aren't works with anything that can receive a message
Use it for a few databases in one data centre, under one team, when you truly need atomicity business processes across services

Before reaching for 2PC or a saga

Ask whether the two pieces of data belong in one service. If two things must change atomically every time, that's a strong signal they're inside the same consistency boundary: one aggregate, one bounded context, one database. The best distributed transaction is the one you designed away.

API gateway and backend for frontend (BFF)

Clients shouldn't know your service topology. If the mobile app calls Orders, Catalog, Reviews and Shipping directly, every service becomes a public API, every client needs to know every address, and you can never split or merge a service without shipping a new app. An API gateway is the single front door.

Service discovery and service mesh at a glance

With many services and many instances that come and go, "where is Payment?" needs an answer that changes every minute.

  • Service discovery. A registry maps a service name to healthy instances. On Kubernetes this is built in: a Service gets a stable DNS name (payment.shop.svc.cluster.local) that load-balances to healthy pods. Outside Kubernetes, there's Consul, Eureka, or a cloud load balancer.
  • Service mesh. A sidecar proxy (Envoy, or linkerd2-proxy) next to every instance intercepts all traffic, and a control plane configures it. The mesh moves network concerns out of your code: mTLS between services, retries and timeouts, traffic splitting for canaries, and uniform metrics and traces.

Retries, timeouts, circuit breaking Polly / Microsoft.Extensions.Http.Resilience, Resilience4j, tenacity mesh route policy (per destination)

You probably don't need a mesh on day one

A mesh pays off with many services, many languages and a platform team to run it. With five .NET services, a shared resilience handler in the outbound HTTP pipeline (see Outbound HTTP Pipelines), OpenTelemetry (Observability) and Kubernetes DNS cover most of it. Don't run both mesh retries and library retries: they multiply into a retry storm.

Strangler fig: migrating without a rewrite

The big-bang rewrite ("we'll stop features for a year and rebuild it right") has a long history of failure. The old system keeps changing, the new one chases a moving target, and the cut-over is a single high-stakes night. The strangler fig pattern, named by Martin Fowler after a vine that grows around a tree until it replaces it, migrates one route at a time.

For a canary, split a route by percentage. Envoy, Istio, Azure API Management and Spring Cloud Gateway (the Weight predicate) have weighted routing built in. With YARP, add a small custom load-balancing policy, or route by a header or cookie that a feature flag sets.

Strangling is mostly a data problem

Routing is the easy part. The hard part is that the new service needs data the monolith owns, and the monolith still needs data the new service now owns. Typical moves:

  1. Start with a read-mostly capability (search, catalog) that can be fed by CDC or events from the monolith.
  2. Put an anti-corruption layer between the new model and the old schema.
  3. Only then move a capability that writes, and move ownership of its tables with it.
  4. Delete the old code path once traffic is at 100%. A strangler that never removes anything is just two systems.

Pitfalls and war stories

The distributed monolith

Twelve services, one shared database, a "common" NuGet or Maven package of domain classes, and a release train that deploys them all together. You have every cost of distribution (latency, partial failure, harder debugging) and none of the benefits (independent deploys, fault isolation). Fix the data ownership first, then the deploy coupling.

Entity services

CustomerService, OrderService, ProductService, each a CRUD wrapper over one table. Every business operation now needs several of them, chained synchronously. Services should be built around capabilities (checkout, fulfilment, pricing), which own their entities and rules, not around nouns.

Synchronous call chains

The checkout calls Pricing, which calls Promotions, which calls Customer, which calls Loyalty. Five hops at 99.9% each give 99.5% availability, and p99 latency is the sum of the slowest. Prefer async events for anything that doesn't need an answer now, and replicate the data you read often.

Dual writes everywhere

"Save, then publish" appears in a code review and looks fine. Six months later, support finds orders that were never shipped and no log explains why. Every event that matters goes through an outbox; every consumer is idempotent.

Retry storms

A dependency slows down, every caller retries 3 times, the gateway retries 3 times, the mesh retries 3 times: 27× the load on a service that was already struggling. Retry at one layer, with backoff, jitter and a retry budget, and put circuit breakers in front. See Resilience Patterns.

Breaking event contracts

Someone renames total to amount in OrderPlaced, and three consumers they didn't know about start dead-lettering. Treat events as public APIs: version them (.v1, .v2), make only additive changes within a version, use a schema registry or contract tests, and run old and new versions side by side during a migration.

No way to see a request end to end

A customer says "my order disappeared". It touched 6 services and 3 topics, and each team has its own logs. Without correlation ids and distributed tracing (W3C traceparent propagated through HTTP and message headers), nobody can answer. Build it before the second service. See Observability.

Testing only in a shared environment

Every service is tested by deploying all of them to one "integration" environment that's always broken. Test each service alone, with consumer-driven contract tests (Pact) for its APIs and events, and keep end-to-end tests to a few critical journeys. See Testing Strategy.

Best-practice checklist

  • Start with a modular monolith; extract a service only for a concrete reason (team independence, scale, isolation).
  • Draw service boundaries around bounded contexts and business capabilities, not entities.
  • Give every service exclusive ownership of its data; no shared tables, no cross-service joins.
  • Use queries for reads, commands for requests, and events for facts. Name events in the past tense.
  • Prefer asynchronous events for work that doesn't need an immediate answer.
  • Give every synchronous call a timeout, bounded retries with jitter, and a circuit breaker, in one pipeline.
  • Publish integration events through a transactional outbox; never dual-write.
  • Make every consumer idempotent (an inbox in the same transaction, or naturally idempotent writes).
  • Key messages by aggregate id for per-entity ordering, and carry a version for consumers to check.
  • Configure retries, a maximum delivery count and a dead-letter queue, plus an alert and a replay tool.
  • Model multi-service business processes as sagas with explicit, idempotent compensations and timeouts.
  • Prefer orchestration once a flow has more than about three steps or needs to be inspected.
  • Avoid 2PC across services; if two things must change atomically, move them into one boundary.
  • Choose the consistency level per use case: strong inside a service, eventual between services.
  • Version event and API contracts; make only additive changes within a version; use contract tests.
  • Propagate trace context through HTTP and message headers from day one.
  • Put a gateway at the edge and a BFF per client type; keep business rules out of both.
  • Migrate with a strangler fig: facade, one capability at a time, canary, then delete the old path.

Self-check

1. Your team of six wants to split a two-year-old monolith into eight microservices "to make the code cleaner". What do you suggest?

A modular monolith. "Cleaner code" is a modularity problem, and modules with enforced boundaries (see Application Architecture) solve it without network calls, distributed transactions or eight deploy pipelines. Six people can't own eight services well. Extract a service later if one module develops a real need: independent scaling, a separate team, or isolation.

2. Billing needs the customer's name and the order total for each invoice. Should it call the Orders and Customers APIs for every invoice?

Usually not. Billing should subscribe to OrderPlaced and CustomerUpdated (event-carried state transfer) and keep a local copy of the fields it needs. Invoicing then works even when Orders or Customers is down, and adds no latency. Make sure the events carry the data, and accept that the copy can be a few seconds stale. Use API composition only for rare queries that must be fresh.

3. A handler saves an order and then calls kafka.send(...). What can go wrong, and what's the fix?

It's a dual write. If the process crashes or the broker is unreachable after the commit, the order exists but OrderPlaced is never published, so it never ships. If you publish first and the commit fails, consumers act on an order that doesn't exist. The fix is a transactional outbox: insert the event into an outbox table in the same transaction, and let a relay (polling or CDC) publish it, with at-least-once delivery.

4. A consumer adds loyalty points for each OrderPlaced. Customers sometimes get double points. Why, and how do you fix it?

The broker delivers at least once, so duplicates are normal: relay retries, rebalances, crashes before the ack. "Add 10 points" isn't idempotent. Record the message id in an inbox table in the same transaction as the points update; a duplicate then violates the primary key and is skipped. Checking the inbox and recording in separate commits doesn't work, because a crash between the two re-applies the points.

5. In an order saga, payment succeeded but stock reservation failed. What happens, and what makes a good compensation?

The saga runs compensations for the completed steps in reverse: refund the payment, then cancel the order. A good compensation is a real business action (a refund, not "delete the charge row"). It is idempotent, it is retried until it succeeds, and it is dead-lettered and alerted if it can't. Using a Pending state (a semantic lock) means nobody acted on the order as if it were final in the meantime.

6. Why not just use two-phase commit across the Orders, Payments and Inventory databases?

2PC holds locks across the network until every participant votes and the coordinator decides. If the coordinator crashes after the votes, participants are in doubt and stay blocked. Availability becomes the product of all participants, latency follows the slowest one, and most brokers, NoSQL stores and HTTP APIs can't take part anyway. Sagas trade atomic isolation for availability. If you truly need atomicity, the data probably belongs in one service.

7. During a network partition, your replicated inventory store keeps accepting writes in both regions. What did you choose, and what happens when the partition heals?

You chose AP: availability over consistency. Both sides accepted conflicting writes, so on heal the replicas must reconcile. Last-writer-wins silently drops one update; a merge (CRDTs, or keeping both versions for the app to resolve) preserves them. For stock that must never oversell, choose CP (majority quorum) for the decrement. The minority side then refuses writes during the partition.

8. Choreography or orchestration for a 7-step onboarding flow with timeouts, and a support team that asks "where is customer X stuck?"

Orchestration. Seven steps with timeouts and branches are hard to follow as scattered event subscriptions. An orchestrator (a MassTransit state machine, a Temporal workflow, a persisted state machine) puts the flow in one place and stores its state, so "where is X?" is a single query. Keep choreography for short flows and independent reactions.
