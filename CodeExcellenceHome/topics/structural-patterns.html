DESIGN PATTERNS

Structural Patterns

Adapter, Decorator, Proxy, Facade, Composite, Bridge and Flyweight, drawn as wrappers you can see objects pass through.

Intermediate~55 min studyBuilds on: Design Principles: SOLID, DRY, KISS, YAGNIUpdated 2026-11-03

The problem: one class that does everything around its real job

Here is a product lookup as it often looks after a year in production. The real work is one line: load a product. Everything else (talking to a vendor API in its own format, logging, caching, permission checks, retrying) got added inline, one ticket at a time.

public class ProductService
{
    private static readonly Dictionary<int, Product> cache = new();   // never expires, not thread-safe

    public async Task<Product> GetAsync(int id, User user)
    {
        if (!user.Roles.Contains("catalog-reader")) throw new UnauthorizedAccessException(); // security
        _log.LogInformation("GET product {Id}", id);                                     // logging
        if (cache.TryGetValue(id, out var hit)) return hit;                               // caching

        for (var attempt = 1; ; attempt++)                                                // retry
        {
            try
            {
                var xml = await _legacyErp.FetchItemXmlAsync(id.ToString("D8"));         // vendor format
                var p = new Product(id, xml.Element("DESCR")!.Value,
                                    decimal.Parse(xml.Element("PRC_CENTS")!.Value) / 100m); // translation
                cache[id] = p;
                return p;
            }
            catch (TimeoutException) when (attempt < 3) { await Task.Delay(200 * attempt); }
        }
    }
}

// One job per class. Each wrapper has the SAME interface as what it wraps.
public interface IProductService { Task<Product> GetAsync(int id); }

public sealed class ErpProductAdapter(LegacyErpClient erp) : IProductService      // adapter: speaks ERP
{
    public async Task<Product> GetAsync(int id)
    {
        var xml = await erp.FetchItemXmlAsync(id.ToString("D8"));
        return new Product(id, xml.Element("DESCR")!.Value, decimal.Parse(xml.Element("PRC_CENTS")!.Value) / 100m);
    }
}
public sealed class CachingProducts(IProductService inner, IMemoryCache cache) : IProductService   // decorator
{
    public Task<Product> GetAsync(int id) =>
        cache.GetOrCreateAsync(id, e => { e.AbsoluteExpirationRelativeToNow = TimeSpan.FromMinutes(5); return inner.GetAsync(id); })!;
}
// Retry, logging and authorization: an HttpClient handler, middleware and [Authorize] (framework-built wrappers)

// Composition root: the ONE place that decides the layering
services.AddScoped<IProductService>(sp =>
    new CachingProducts(new ErpProductAdapter(sp.GetRequiredService<LegacyErpClient>()),
                        sp.GetRequiredService<IMemoryCache>()));

The "after" version has more types but each one is tiny, testable on its own and replaceable. You can change the ERP without touching caching, turn caching off in a test, or reorder layers in one line. Structural patterns are the named shapes of that composition: how objects hold and forward to each other so that each concern lives in one place. They're composition over inheritance and the open/closed principle turned into concrete, recognisable designs.

Keep the real object focused on its one job. Put translation, simplification, extra behaviour and access control in separate objects that hold a reference and forward the call. Choose the pattern by what changes for the caller: the interface, the behaviour, the access, or the number of things to know.

The mental model: wrap one, simplify many, arrange many

Every structural pattern answers one of three questions. Underneath, all of them are the same mechanism: a field that holds another object, and a method that delegates to it.

Pattern One-line intent What changes for the caller You've used it as
Adapter Make an existing class fit the interface you need The interface (A becomes B) StreamReader, Arrays.asList, http.HandlerFunc
Facade One simple entry point over a complicated subsystem How many things it must know File.ReadAllText, requests.get, http.Get
Decorator Add behaviour without changing the interface Behaviour, invisibly BufferedStream, DelegatingHandler, @lru_cache, middleware
Proxy A stand-in that controls access to the real object Whether, when or where it runs Lazy<T>, EF lazy loading, gRPC stubs, Spring @Transactional
Composite Treat a single object and a group the same way Nothing: leaves and trees share a type The DOM, JUnit suites, io.MultiWriter
Bridge Let two dimensions vary independently Nothing: combinations are chosen at runtime JDBC drivers, database/sql, ILogger providers
Flyweight Share the heavy, repeated, immutable part Nothing, but memory drops string.Intern, Integer.valueOf, sys.intern

In modern languages, several of these shrink to a function. A decorator in Python is literally @decorator. An adapter in Go is often a one-line function type (http.HandlerFunc(f)). TypeScript's structural typing means an object that already has the right shape needs no adapter at all. A DI container can apply decorators (Decorate<T> in Scrutor, @Primary wrappers in Spring) and build proxies (DispatchProxy, Spring AOP) for you. Learn the intent and the vocabulary, so you can say "put a caching decorator around the repository" in a review, then write the smallest idiomatic thing that does it.

Adapter: make the class you have fit the interface you need

You depend on an interface you designed (IWeather, IPaymentGateway, Logger). Then you need to use a class you can't or shouldn't change (a vendor SDK, a legacy module, an older version of your own API) whose shape doesn't match. An adapter is a small class that implements your interface and translates each call into the other class's terms.

The pain it removes

// Vendor types, units and error codes leak into every caller
var resp = await legacyWeather.GetForecastAsync(ZipDirectory.CityFor(zip));   // copied in 6 files
if (resp.Status == 17) return null;                                           // magic number, copied
var celsius = (resp.TempF - 32) * 5 / 9;                                      // copied, rounded differently

When the vendor changes (or you switch vendors), you edit every caller. Tests need the real vendor or a fake of its API. The vendor's concepts (city names, Fahrenheit, status 17) have leaked into your domain. Domain-driven design calls the fix an anti-corruption layer: an adapter, sometimes plus a facade, at the boundary.

How it works

The adapter translates in three directions: inputs (ZIP code to city), outputs (°F to °C, vendor DTO to your type) and errors (status 17 to WeatherUnavailableException). The third is the one people forget. Step through it, then switch the vendor select: the client's calls stay exactly the same. Switch who translates to see the version without an adapter.

In five languages

public interface IWeather { Task<double> GetTempCAsync(string zip); }          // YOUR interface

public sealed class LegacyWeatherAdapter(LegacyWeatherClient vendor, IZipDirectory zips) : IWeather
{
    public async Task<double> GetTempCAsync(string zip)
    {
        var city = zips.CityFor(zip) ?? throw new LocationNotFoundException(zip);   // input
        ForecastResponse r;
        try { r = await vendor.GetForecastAsync(city); }
        catch (SoapException ex) { throw new WeatherUnavailableException(zip, ex); } // errors
        if (r.Status != 0) throw new WeatherUnavailableException(zip);
        return Math.Round((r.TempF - 32) * 5 / 9, 1);                                // output
    }
}
// Registration: callers never learn which vendor is behind IWeather
services.AddSingleton<IWeather, LegacyWeatherAdapter>();

public interface Weather { double tempC(String zip); }

public final class LegacyWeatherAdapter implements Weather {
    private final LegacyWeatherClient vendor;
    private final ZipDirectory zips;
    public LegacyWeatherAdapter(LegacyWeatherClient vendor, ZipDirectory zips) { this.vendor = vendor; this.zips = zips; }

    @Override public double tempC(String zip) {
        String city = zips.cityFor(zip).orElseThrow(() -> new LocationNotFoundException(zip));
        ForecastResponse r = vendor.getForecast(city);
        if (r.status() != 0) throw new WeatherUnavailableException(zip);
        return Math.round((r.tempF() - 32) * 5 / 9.0 * 10) / 10.0;
    }
}

type legacyAdapter struct {
    vendor *legacy.Client
    zips   ZipDirectory

func (a legacyAdapter) TempC(ctx context.Context, zip string) (float64, error) {
    city, ok := a.zips.CityFor(zip)
    if !ok {
        return 0, fmt.Errorf("zip %s: %w", zip, ErrLocationNotFound)
    }
    r, err := a.vendor.GetForecast(ctx, city)
    if err != nil || r.Status != 0 {

    }
    return math.Round((r.TempF-32)*5/9*10) / 10, nil
}

interface Weather { tempC(zip: string): Promise<number>; }

// An adapter can be a plain object: no class required
export function legacyWeatherAdapter(vendor: LegacyWeatherClient, zips: ZipDirectory): Weather {
  return {
    async tempC(zip) {
      const city = zips.cityFor(zip);
      if (!city) throw new LocationNotFoundError(zip);
      const r = await vendor.getForecast(city);
      if (r.status !== 0) throw new WeatherUnavailableError(zip);
      return Math.round(((r.tempF - 32) * 5) / 9 * 10) / 10;
    },
  };
}

Where you already use it

  • .NET: StreamReader/StreamWriter adapt a byte Stream to text; Task.Factory.FromAsync adapts the old Begin/End async pattern to Task; HttpClient message handlers adapt sockets to HTTP.
  • Java: InputStreamReader (bytes to chars), Arrays.asList (array to List), Collections.enumeration, Spring's HandlerAdapter (any controller style to one dispatcher interface).
  • Python: io.TextIOWrapper (binary to text), functools.cmp_to_key, asyncio.to_thread (blocking function to awaitable).
  • Go: http.HandlerFunc, sort.Slice (a less-function to sort.Interface), bufio.NewReader wrapping any io.Reader.
  • TypeScript/Node: util.promisify, Readable.fromWeb / Readable.toWeb between Node and web streams.

Use an adapter when

  • You need a class whose interface you can't change (third-party, generated, legacy).
  • You want vendor concepts to stop at one boundary (an anti-corruption layer).
  • You're migrating: the old and new implementations both sit behind your interface while traffic moves over.
  • You need to plug a function into an API that wants an object (or the reverse).

Don't use one when

  • You own both sides. Change one of them to match instead of adding a translation layer.
  • The "adapter" only forwards calls one-to-one with the same names and types. That's an empty wrapper; in TypeScript and Go the type may already satisfy the interface structurally.
  • It starts making decisions (pricing rules, workflows). Business logic belongs in the domain, not in a translation layer.

Leaky adapters. An adapter that returns the vendor's DTO, lets vendor exceptions escape, or exposes GetUnderlyingClient() hasn't adapted anything; callers still depend on the vendor. Return your types, map every error, and write a contract test that runs the same assertions against each adapter implementation.

Facade: one simple entry point over a subsystem

A facade gives a simple, task-shaped API over a group of classes that are each fine on their own but tedious and error-prone to use together. The classic signal: the same five-call sequence, with the same error handling, appears in several places.

The pain it removes

// In the web controller, the mobile API and the admin tool: the same dance, three copies
var r = await inventory.ReserveAsync(cart.Items);
var c = await payments.ChargeAsync(cart.Total);
if (!c.Ok) { await inventory.ReleaseAsync(r); return BadRequest("declined"); }
var s = await shipping.BookAsync(cart.Address);
if (!s.Ok) { await payments.RefundAsync(c); /* the admin copy forgot to release the reservation */ }

Each client knows four subsystems, their order, and how to undo partial work. When the rules change ("refund before release", "email failure is not fatal"), you hunt down every copy. One copy will be wrong.

How it works

The facade owns the sequence and the rules: what order, what to undo on failure, which steps are critical. Step through a failure, then switch to client calls each subsystem and compare the call counts.

In five languages

public sealed class CheckoutFacade(IInventory inventory, IPayments payments, IShipping shipping, IOutbox outbox)
{
    public async Task<OrderResult> PlaceOrderAsync(Cart cart, CancellationToken ct = default)
    {
        var reservation = await inventory.ReserveAsync(cart.Items, ct);
        var charge = await payments.ChargeAsync(cart.Total, ct);
        if (!charge.Ok) { await inventory.ReleaseAsync(reservation, ct); return OrderResult.Declined(charge.Reason); }

        var label = await shipping.BookAsync(cart.Address, ct);
        if (!label.Ok)
        {
            await payments.RefundAsync(charge, ct);                   // undo in reverse order
            await inventory.ReleaseAsync(reservation, ct);
            return OrderResult.Unavailable();
        }
        var orderId = await inventory.CommitAsync(reservation, ct);
        await outbox.EnqueueAsync(new SendConfirmation(orderId, cart.Email), ct);   // not critical: retried later
        return OrderResult.Placed(orderId, label.TrackingNumber);
    }
}

@Service
public class CheckoutFacade {
    private final Inventory inventory; private final Payments payments;
    private final Shipping shipping; private final Outbox outbox;
    public CheckoutFacade(Inventory i, Payments p, Shipping s, Outbox o) { inventory = i; payments = p; shipping = s; outbox = o; }

    public OrderResult placeOrder(Cart cart) {
        var reservation = inventory.reserve(cart.items());
        var charge = payments.charge(cart.total());
        if (!charge.ok()) { inventory.release(reservation); return OrderResult.declined(charge.reason()); }
        var label = shipping.book(cart.address());
        if (!label.ok()) { payments.refund(charge); inventory.release(reservation); return OrderResult.unavailable(); }
        var orderId = inventory.commit(reservation);
        outbox.enqueue(new SendConfirmation(orderId, cart.email()));
        return OrderResult.placed(orderId, label.trackingNumber());
    }
}

class Checkout:
    def __init__(self, inventory, payments, shipping, outbox) -> None:
        self._inv, self._pay, self._ship, self._outbox = inventory, payments, shipping, outbox

    def place_order(self, cart: Cart) -> OrderResult:
        reservation = self._inv.reserve(cart.items)
        charge = self._pay.charge(cart.total)
        if not charge.ok:
            self._inv.release(reservation)
            return OrderResult.declined(charge.reason)
        label = self._ship.book(cart.address)
        if not label.ok:
            self._pay.refund(charge)
            self._inv.release(reservation)
            return OrderResult.unavailable()

// In Go a facade is usually a package with a small exported API over unexported pieces.
type Checkout struct {
    inv  Inventory
    pay  Payments
    ship Shipping
    out  Outbox
}

func (c *Checkout) PlaceOrder(ctx context.Context, cart Cart) (OrderResult, error) {
    res, err := c.inv.Reserve(ctx, cart.Items)
    if err != nil {
        return OrderResult{}, err
    }
    charge, err := c.pay.Charge(ctx, cart.Total)
    if err != nil {
        _ = c.inv.Release(ctx, res)
        return Declined(err), nil
    }
    label, err := c.ship.Book(ctx, cart.Address)
    if err != nil {
        _ = c.pay.Refund(ctx, charge)
        _ = c.inv.Release(ctx, res)
        return Unavailable(), nil
    }
    id, err := c.inv.Commit(ctx, res)
    if err != nil {
        return OrderResult{}, err
    }
    _ = c.out.Enqueue(ctx, SendConfirmation{OrderID: id, Email: cart.Email})
    return Placed(id, label.Tracking), nil
}

// A module IS a facade: export one function, keep the subsystems private to the module
export async function placeOrder(cart: Cart, deps: CheckoutDeps): Promise<OrderResult> {
  const { inventory, payments, shipping, outbox } = deps;
  const reservation = await inventory.reserve(cart.items);
  const charge = await payments.charge(cart.total);
  if (!charge.ok) { await inventory.release(reservation); return { kind: "declined", reason: charge.reason }; }

  const label = await shipping.book(cart.address);
  if (!label.ok) {
    await payments.refund(charge);
    await inventory.release(reservation);
    return { kind: "unavailable" };
  }
  const orderId = await inventory.commit(reservation);
  await outbox.enqueue({ type: "SendConfirmation", orderId, email: cart.email });
  return { kind: "placed", orderId, tracking: label.trackingNumber };
}

Where you already use it

  • .NET: File.ReadAllText (opens a FileStream, wraps a StreamReader, detects encoding, disposes), WebApplication.CreateBuilder (configuration, logging, DI and hosting in one call), HttpClient.GetFromJsonAsync.
  • Java: SLF4J (one logging API over Logback, Log4j and JUL), Spring's JdbcTemplate and RestClient, Files.readString.
  • Python: requests.get over urllib3 connection pools, subprocess.run over Popen, shutil.copytree.
  • Go: http.Get over http.Client, Transport and Request; os.ReadFile.
  • TypeScript: fetch over streams, headers and the network stack; an SDK's top-level client over its service modules.

Use a facade when

  • Several callers repeat the same sequence across the same subsystems.
  • The sequence has rules (order, compensation, what's critical) that must be the same everywhere.
  • You want a stable API in front of a subsystem that's still changing, or a seam between layers or teams.

Don't use one when

  • There's one caller and one subsystem. That's a pass-through layer.
  • It becomes a god object: ShopFacade with 60 methods for every feature. Split by task (checkout, returns, catalogue).
  • It's used to hide the subsystem completely. Advanced callers should still be able to go around it.

Facade versus "service layer that forwards everything". A class whose methods each call exactly one subsystem method with the same arguments adds a layer and no simplification. A facade earns its place by combining calls and owning the rules between them. If every method is one line, delete it and inject the subsystem.

Decorator: add behaviour, keep the interface

A decorator implements the same interface as the object it wraps, holds a reference to it, and does something before and/or after forwarding the call. Because the outside is unchanged, decorators stack: caching around logging around retry around the real service. Callers can't tell how many layers there are.

If you've written ASP.NET Core middleware, Express middleware or a Go func(http.Handler) http.Handler, you've written decorators. The middleware patterns page covers the pipeline form in depth; this section is about the object form and when to choose it.

The pain it removes

// Option 1: subclass per combination
class CachedProductService : ProductService { … }
class LoggedCachedProductService : CachedProductService { … }
class RetryingLoggedCachedProductService : LoggedCachedProductService { … }   // 2^n classes, fixed order

// Option 2: flags inside the class
if (_options.EnableCache) { … } if (_options.EnableLogging) { … } if (_options.EnableRetry) { … }

Subclassing explodes (every combination is a class, and the order is frozen into the hierarchy). Flags turn one class into four, each concern tangled with the others and with the real job. Both violate single responsibility.

How it works

Each layer is an onion ring. A call travels inward through every layer to the real service, and the result travels outward back through them. That's why order matters: whatever is outside sees everything inside; whatever is inside never sees what an outer layer short-circuited.

Type the layers outermost first, and add requests (a ! means "this call fails once"). The default order puts cache outside logging, so cache hits are never logged. Swap them and run again. Then move retry outside cache and watch what a retry repeats.

Rules of thumb for ordering, outermost first: metrics/tracing (measure everything the caller experiences), authorization (refuse early, before spending work), caching (avoid the work), retry (only around the expensive, transient part), the real service. Log where you want to see events: outside the cache to count every request, inside it to log only real fetches. Never cache errors, and keep retry inside the cache so a successful retry is what gets cached.

In five languages

public interface IProducts { Task<Product?> GetAsync(int id, CancellationToken ct = default); }

public sealed class CachingProducts(IProducts inner, IMemoryCache cache) : IProducts
{
    public async Task<Product?> GetAsync(int id, CancellationToken ct = default)
    {
        if (cache.TryGetValue(id, out Product? hit)) return hit;              // short-circuit: inner never runs
        var p = await inner.GetAsync(id, ct);
        if (p is not null) cache.Set(id, p, TimeSpan.FromMinutes(5));         // don't cache misses/errors
        return p;
    }
}

public sealed class LoggingProducts(IProducts inner, ILogger<LoggingProducts> log) : IProducts
{
    public async Task<Product?> GetAsync(int id, CancellationToken ct = default)
    {
        var sw = Stopwatch.StartNew();
        try { return await inner.GetAsync(id, ct); }
        finally { log.LogInformation("GetAsync({Id}) took {Ms} ms", id, sw.ElapsedMilliseconds); }
    }
}

// Stack them by hand, or let Scrutor do it: the LAST Decorate is the OUTERMOST layer
services.AddScoped<IProducts, ProductService>();
services.Decorate<IProducts, LoggingProducts>();
services.Decorate<IProducts, CachingProducts>();     // Caching(Logging(ProductService))

public interface Products { Optional<Product> get(int id); }

public final class CachingProducts implements Products {
    private final Products inner;
    private final Cache<Integer, Product> cache = Caffeine.newBuilder().expireAfterWrite(Duration.ofMinutes(5)).build();
    public CachingProducts(Products inner) { this.inner = inner; }

    @Override public Optional<Product> get(int id) {
        Product hit = cache.getIfPresent(id);
        if (hit != null) return Optional.of(hit);
        Optional<Product> p = inner.get(id);
        p.ifPresent(v -> cache.put(id, v));
        return p;
    }
}

import functools, logging, time

def logged(fn):
    @functools.wraps(fn)                      # keep __name__, __doc__, signature for tools and tracebacks
    def wrapper(*args, **kwargs):
        start = time.perf_counter()
        try:
            return fn(*args, **kwargs)
        finally:
            logging.info("%s took %.1f ms", fn.__name__, (time.perf_counter() - start) * 1000)
    return wrapper

class ProductService:
    @functools.lru_cache(maxsize=1024)        # stdlib caching decorator (note: also caches on `self`)
    @logged                                   # applied first: logging is INSIDE the cache
    def get(self, product_id: int) -> Product: ...

# Object form, when you need state or an interface (Protocol) rather than a function:
class CachingProducts:
    def __init__(self, inner: Products, cache: dict[int, Product]) -> None:
        self._inner, self._cache = inner, cache
    def get(self, product_id: int) -> Product:
        if product_id not in self._cache:
            self._cache[product_id] = self._inner.get(product_id)
        return self._cache[product_id]

// Same idea for your own interfaces:
type Products interface{ Get(ctx context.Context, id int) (Product, error) }

type caching struct {
    inner Products
    mu    sync.Mutex
    m     map[int]Product
}

func (c *caching) Get(ctx context.Context, id int) (Product, error) {
    c.mu.Lock()
    p, ok := c.m[id]
    c.mu.Unlock()
    if ok {
        return p, nil
    }
    p, err := c.inner.Get(ctx, id)
    if err == nil {
        c.mu.Lock()
        c.m[id] = p
        c.mu.Unlock()
    }
    return p, err
}

interface Products { get(id: number): Promise<Product | undefined>; }

// Function-wrapping decorator: works for any async function, keeps its type
function withRetry<A extends unknown[], R>(fn: (...a: A) => Promise<R>, attempts = 3) {
  return async (...args: A): Promise<R> => {
    for (let i = 1; ; i++) {
      try { return await fn(...args); }
      catch (e) { if (i >= attempts) throw e; await new Promise(r => setTimeout(r, 100 * 2 ** i)); }
    }
  };
}

export const caching = (inner: Products, cache = new Map<number, Product>()): Products => ({
  async get(id) {
    const hit = cache.get(id);
    if (hit) return hit;
    const p = await inner.get(id);
    if (p) cache.set(id, p);
    return p;
  },

Where you already use it

  • .NET: BufferedStream, GZipStream, CryptoStream wrap any Stream; DelegatingHandler for HttpClient (each handler wraps the next: retry, auth, logging); ASP.NET Core middleware; Scrutor's Decorate<T>. See DI decorators and interception.
  • Java: the whole java.io stream family, Collections.unmodifiableList / synchronizedList, Servlet filters, Spring's BeanPostProcessor wrappers.

Use a decorator when

  • You want to add a cross-cutting concern (cache, retry, log, metrics, auth, validation) to something that already works.
  • You need to combine concerns in different orders or switch them per environment.
  • You can't or don't want to modify the wrapped class.

Don't use one when

  • The interface is huge. A decorator over a 40-method interface is 39 forwarding methods for one interesting one (consider a dynamic proxy or splitting the interface).
  • The behaviour belongs to the business logic itself (a discount rule isn't a cross-cutting concern).
  • One layer is enough and will stay one layer. A private method or a parameter is simpler.
  • Callers need to reach the inner object's identity or concrete type (decorators break is ConcreteType and reference equality).

Five classic decorator bugs: (1) wrong order, such as caching outside authorization, so user B gets user A's cached data; (2) caching exceptions or nulls; (3) forgetting to forward one method (or CancellationToken/context.Context), so that path silently skips the inner layers; (4) in Python, dropping functools.wraps, so every function is called wrapper in logs; (5) functools.lru_cache on a method keeps self alive forever and shares one cache across instances.

Proxy: control access to the real object

A proxy also has the same interface as the real object and forwards to it. The difference from a decorator is intent: a proxy controls access (whether, when, where or how often the real object is reached), and the real object usually doesn't exist as an independent, composable piece from the caller's point of view. You ask for "the reports service", and get a stand-in.

The pain it removes

// Every caller must remember to: build the expensive object only when needed,
// check permissions, consult the cache, and handle the network.
if (_reports is null) _reports = new ReportsEngine(LoadTemplates(), ConnectWarehouse()); // 2 seconds
if (!user.IsAdmin && id >= 3) throw new UnauthorizedAccessException();
if (_cache.TryGetValue(id, out var r)) return r;

Four kinds, one shape

Kind Controls The real object… Everyday example
Virtual When it's created …is created on first use Lazy<T>, EF Core lazy-loading navigation, Hibernate proxies
Protection Whether the caller may call …is only reached if allowed Spring Security @PreAuthorize, [Authorize] filters
Caching How often it's reached …is skipped on a hit Spring @Cacheable, a CDN in front of an origin
Remote Where it runs …lives in another process gRPC/WCF client stubs, Java RMI, a fetch-based SDK client

Pick a kind and run the operations. alice is an admin; bob and carol are viewers and can't open reports with id 3 or above. In remote mode, report 4 times out, so you see why a remote proxy must translate network failures into your own exceptions (like an adapter does).

Hand-written and dynamic proxies

You can write a proxy by hand (one class per interface), or generate it at runtime: a dynamic proxy implements any interface by routing every call through one handler method. That's how frameworks add transactions, caching, security and lazy loading without you writing a class per service.

// Hand-written virtual + protection proxy
public sealed class ReportsProxy(Func<IReports> create, ICurrentUser user) : IReports
{
    private readonly Lazy<IReports> _real = new(create);              // virtual: built on first use, thread-safe
    public Task<Report> GetAsync(int id)
    {
        if (!user.IsAdmin && id >= 3) throw new UnauthorizedAccessException();   // protection
        return _real.Value.GetAsync(id);
    }
}

public class TimingProxy<T> : DispatchProxy where T : class
{
    public T Target { get; set; } = default!;
    protected override object? Invoke(MethodInfo? m, object?[]? args)
    {
        var sw = Stopwatch.StartNew();
        try { return m!.Invoke(Target, args); }
        finally { Console.WriteLine($"{m!.Name}: {sw.ElapsedMilliseconds} ms"); }
    }
    public static T Wrap(T target) { var p = Create<T, TimingProxy<T>>(); ((TimingProxy<T>)(object)p).Target = target; return p; }
}

    def __init__(self, create: Callable[[], Reports], user: User) -> None:
        self._create, self._user, self._real = create, user, None

            raise PermissionError(report_id)
        return self._target().get(report_id)

    def _target(self) -> Reports:
        if self._real is None:
            self._real = self._create()        # not thread-safe: add a lock if shared across threads
        return self._real

    def __getattr__(self, name: str):          # dynamic forwarding for every other attribute
        return getattr(self._target(), name)

function protect<T extends object>(target: T, user: User): T {
  return new Proxy(target, {
    get(t, prop, receiver) {
      const value = Reflect.get(t, prop, receiver);
      if (typeof value !== "function") return value;
      return (...args: unknown[]) => {
        if (!user.isAdmin && prop === "get" && (args[0] as number) >= 3) throw new Error("forbidden");
        return value.apply(t, args);
      };
    },
  });

Use a proxy when

  • Creating the real object is expensive and often unnecessary (virtual).
  • Access needs a policy applied every time, which callers mustn't be able to skip (protection).
  • The real object is remote, and you want callers to use a normal interface (remote).
  • You need the same handling for many methods or many interfaces (dynamic proxy, AOP).

Don't use one when

  • The hidden cost matters to callers. A remote proxy that looks like a local call invites chatty loops (for each id: proxy.Get(id)), the classic N+1 problem. Make remote calls look remote: async, batched, with explicit failure types.
  • Debugging and stack traces matter more than saved boilerplate. Dynamic proxies hide control flow.
  • A plain function call with an explicit check is clearer, and there's only one caller.

Proxies that silently don't apply. In Spring (and any proxy-based AOP), a method calling another method on this goes straight to the real object: @Transactional, @Cacheable and @Async are skipped. The same happens with private/final methods (can't be overridden) and with objects created by new instead of the container. EF Core lazy-loading proxies need virtual navigation properties, and they load one query per navigation access: a lazy loop over 100 orders becomes 101 queries.

Composite: treat one and many the same way

A composite lets a group of objects pretend to be one object of the same type. A folder and a file both have Size(); a folder's size is the sum of its children's sizes, whatever they are. Clients call Size() on the root and never write a type check.

The pain it removes

long Total(object item)
{
    if (item is File f) return f.Bytes;
    if (item is Folder d) { long s = 0; foreach (var c in d.Items) s += Total(c); return s; }
    if (item is Shortcut) return 0;      // every new kind: edit every function like this one
    throw new NotSupportedException();
}

Every operation (size, count, search, render, permissions) repeats the same type switch, and adding a node kind means editing all of them.

How it works

Edit the tree (name(children…) for a folder, name:size for a file) and pick the operation. Watch the call go down the tree and the results come back up: each folder only knows how to combine its children's answers.

public interface INode { string Name { get; } long Size(); }

public sealed record FileNode(string Name, long Bytes) : INode { public long Size() => Bytes; }

public sealed class Folder(string name) : INode
{
    private readonly List<INode> _children = [];
    public string Name => name;
    public Folder Add(INode child) { _children.Add(child); return this; }
    public long Size() => _children.Sum(c => c.Size());          // recursion through the shared interface
}

var root = new Folder("src")
    .Add(new FileNode("app.cs", 12))
    .Add(new Folder("lib").Add(new FileNode("util.cs", 4)).Add(new FileNode("io.cs", 7)));
Console.WriteLine(root.Size());   // 23

public sealed interface Node permits FileNode, Folder { String name(); long size(); }

public record FileNode(String name, long bytes) implements Node { public long size() { return bytes; } }

public record Folder(String name, List<Node> children) implements Node {
    public long size() { return children.stream().mapToLong(Node::size).sum(); }
}

// With sealed interfaces + pattern matching, an operation can also live OUTSIDE the tree:
static long count(Node n) {
    return switch (n) {
        case FileNode f -> 1;
        case Folder d -> d.children().stream().mapToLong(Main::count).sum();
    };   // the compiler checks every kind is handled
}

// Functional composite: a discriminated union plus one recursive function

  n.kind === "file" ? n.bytes : n.children.reduce((sum, c) => sum + size(c), 0);

Transparent versus safe composite. Transparent: Add/Remove are on the shared interface, so clients never check types, but calling Add on a file must throw. Safe: only Folder has Add, so misuse is a compile error, but building the tree needs the concrete type. Prefer safe: building a tree happens in one place, reading it happens everywhere. In languages with sum types (TypeScript unions, Java sealed interfaces, F#/Rust enums), you can also keep operations outside the nodes in one recursive function, as the Java and TypeScript tabs show. That's often clearer than adding a method to every node class.

Where you already use it

  • UI trees: the DOM, WPF/WinUI visual trees, React components, Swing Container.
  • .NET: CompositeFileProvider, CompositeChangeToken, CancellationTokenSource.CreateLinkedTokenSource, AggregateException, expression trees.
  • Java: JUnit test suites (a suite is a test), java.awt.Container, Spring's CompositeCacheManager.
  • Python: ast nodes, unittest.TestSuite, ExitStack (many context managers as one).
  • Go: io.MultiWriter, io.MultiReader, errors.Join, http.ServeMux (many handlers as one handler).

Use a composite when

  • The data is a tree (files, menus, org charts, UI, documents, ASTs, rule groups like "A and (B or C)").
  • Clients should treat one item and a group uniformly ("notify this user" and "notify this team").

Don't use one when

  • The structure is flat. A list and a loop are enough.
  • Leaves and groups need genuinely different operations; forcing a shared interface means lots of "not supported" methods.
  • The tree is very deep or may contain cycles (symlinks, graph data). Plain recursion overflows the stack or never ends; use an explicit stack and a visited set.

Bridge: two dimensions that vary independently

A bridge splits one class hierarchy that's growing in two directions into two hierarchies connected by a reference. The abstraction (what you're doing: a message, an alert, a report) holds an implementor (how it's delivered: email, SMS, Slack). Each side grows independently.

The pain it removes

Notification
├── EmailMessage   ├── SmsMessage   ├── SlackMessage
├── EmailAlert     ├── SmsAlert     ├── SlackAlert
└── EmailReminder  ├── SmsReminder  └── SlackReminder          3 × 3 = 9 classes
Add "Push"   → 3 more classes.  Add "Digest" → 4 more classes.   m × n keeps growing

How it works

Enter the abstractions and the implementations, and compare inheritance (one class per combination) with bridge (one class per item, combined at runtime). The last step adds one more channel: with inheritance that's m new classes; with a bridge it's one.

public interface IChannel { Task SendAsync(string to, string subject, string body); }   // implementor

public sealed class EmailChannel(SmtpClient smtp) : IChannel { public Task SendAsync(string to, string s, string b) => smtp.SendMailAsync("noreply@x.com", to, s, b); }
public sealed class SmsChannel(ISmsApi api) : IChannel { public Task SendAsync(string to, string s, string b) => api.SendAsync(to, $"{s}: {b}"); }

public abstract class Notification(IChannel channel)                                   // abstraction
{
    protected IChannel Channel { get; } = channel;
    public abstract Task NotifyAsync(string to);
}
public sealed class Message(IChannel channel, string text) : Notification(channel)
{
    public override Task NotifyAsync(string to) => Channel.SendAsync(to, "Message", text);
}
public sealed class Alert(IChannel channel, string system, int severity) : Notification(channel)
{
    public override Task NotifyAsync(string to) => Channel.SendAsync(to, $"[SEV{severity}] {system}", "Check the dashboard now.");

Where you already use it

  • JDBC (Connection vs Driver), Go's database/sql (sql.DB vs driver.Driver), Python's DB-API.

Use a bridge when

  • You can name two independent dimensions that both genuinely grow ("what" × "how", "shape" × "renderer").
  • You need to pick the implementation at runtime or configuration time.
  • Several teams own different sides (your app vs third-party drivers).

Don't use one when

  • One dimension has a single member and no realistic second. That's speculative generality; inject the interface when you need it.
  • The "abstraction" side has no real behaviour of its own. Then it's just strategy/DI: a class that depends on an IChannel. That's fine, and it's simpler to call it that.

If only the implementation side varies, you're just doing dependency injection; see DI fundamentals and the strategy pattern in behavioral patterns.

Flyweight: share what's identical, store only what differs

When you have a huge number of small objects and most of each object is the same as many others, a flyweight splits each object into two parts:

  • Intrinsic state: immutable, shareable (a glyph's font outline, a tree species' mesh, a string's characters). Stored once in a factory or cache.
  • Extrinsic state: what's unique to each use (position, colour, which document). Stored per use, alongside a reference to the shared part.

How it works

Type some text and switch between naive (every character owns its own glyph data) and flyweight (one glyph per distinct character, plus a small position record per character). The memory bar uses illustrative sizes: 1,200 bytes per glyph, 16 bytes of position and an 8-byte reference per placement. The more repetition, the bigger the win.

Where you already use it

  • String interning in every runtime: string.Intern (.NET), String.intern (Java), sys.intern (Python), unique.Make (Go), automatic interning of literals in all of them.
  • Boxed small values: Java's Integer.valueOf cache (-128..127), Boolean.TRUE; CPython's small-int cache (-5..256); .NET caches boxed true/false and some small Task results (Task.CompletedTask).
  • Games and graphics: shared meshes and textures with per-instance transforms (GPU instancing), tile maps, font glyph caches.
  • Immutable value objects: Color.Red, TimeZoneInfo.Utc, enum instances, BigInteger.ONE.

Use a flyweight when

  • You have many objects (hundreds of thousands or more), and a profiler shows they dominate memory.
  • Most of each object's state is duplicated and immutable.
  • Object identity doesn't matter to callers.

Don't use one when

  • You haven't measured. It adds a factory, a cache, and a split that makes the code harder to read. See memory and GC for measuring first.
  • The shared part is mutable. Changing one shared glyph changes every place it's used.
  • The cache is unbounded and keyed by user input. Your "memory optimisation" becomes a memory leak.

Flyweights and identity. Because the runtime shares some instances, == sometimes "works" in tests and fails in production: Java's Integer compares equal by reference up to 127, CPython's is is True for small ints and interned strings. Never use reference equality on values: use equals(), == on value types, or == in Python, never is.

How to tell them apart in a code review: if the wrapper's interface differs from the wrapped one, it's an adapter (one object) or a facade (many objects). If the interface is the same: does the wrapper add something and always delegate (decorator), or does it decide whether, when or where to delegate (proxy)? A caching wrapper sits on the border and is called both. That's fine; what matters is that everyone agrees on what it may do.

Two more patterns use the same "hold and forward" shape and are covered elsewhere: chain of responsibility (each handler may pass the call to the next one; see middleware and behavioral patterns) and strategy (a field holding an interchangeable algorithm). The request pipeline page shows how ASP.NET Core combines several of them in one feature.

Which structural pattern? Decide for your case

Pick a scenario (or custom) and answer the questions. The first "yes" on the chain wins, and if nothing matches, the answer is plain composition: inject the dependency and call it. That's the most common correct answer.

When NOT to use structural patterns

Wrappers for their own sake

An IUserRepositoryAdapter around your own UserRepository with the same methods. A UserFacade whose every method calls one UserService method. A "decorator" that adds nothing yet "in case we need logging later". Each layer is another file to read, another frame in every stack trace, and another place to forget to forward a parameter. YAGNI.

A pattern the platform already gives you

Hand-written logging and retry decorators around HttpClient when DelegatingHandler and the resilience handlers exist. A hand-rolled proxy class per service when Spring AOP or a DispatchProxy does it. A Python decorator class when a function decorator is three lines. An adapter in TypeScript for an object that already has the right shape.

A real boundary or concern, in one place

A vendor you don't control (adapter), a multi-step workflow with rules (facade), a cross-cutting concern you'll want to toggle or reorder (decorator), an access policy no caller may skip (proxy), a real tree (composite), two independently growing hierarchies (bridge), or measured memory pressure from duplicates (flyweight).

Common pitfalls

Decorators in the wrong order. A cache outside the authorization check serves one user's data to another. A retry outside a rate limiter multiplies the load it was supposed to limit. Logging inside a cache misses every hit. Write the order down once (the composition root) and test it: one test per important ordering rule.

Forgetting to forward. A wrapper that implements 9 of 10 methods by delegating and the tenth as throw new NotImplementedException(), or forgets to pass CancellationToken / context.Context through. Prefer narrow interfaces, generate forwarding code, and add a test that checks the token reaches the inner object.

Remote proxies that look local. foreach (var id in ids) total += client.GetPrice(id); reads like a loop over a dictionary and runs 500 network calls. Make remote interfaces async, batch-friendly (GetPrices(ids)), and explicit about failure.

AOP proxies that silently don't apply. Self-invocation, private/final/non-virtual methods and objects created with new all bypass a framework proxy, so @Transactional, @Cacheable or an interceptor quietly does nothing. If behaviour must always apply, make it explicit (a decorator registered in DI) or add a test that proves the proxy is in place.

Recursion on untrusted trees. Composite operations are recursive. A deeply nested JSON document, a directory with symlink cycles or a malicious XML file can overflow the stack or loop forever. Limit depth, track visited nodes, or iterate with an explicit stack.

Mutable flyweights. Shared objects must be immutable. If someone sets glyph.Color = Red on a shared glyph, every "a" in the document turns red. Freeze the shared part (record, frozen=True, Object.freeze) and keep anything per-use in the extrinsic part.

Checklist

  • The real object does one job; translation, simplification, cross-cutting behaviour and access control each live in their own wrapper.
  • Adapters return your types and map every vendor error; no vendor type appears outside the adapter's file.
  • Facades combine calls and own the sequence rules (order, compensation, what's critical); they're split by task, not one per subsystem.
  • Decorators are composed in one place, their order is documented, and important ordering rules have tests.
  • Every wrapper forwards every method and every CancellationToken / context.Context.
  • Proxies that cross a network are async, batch-friendly, and translate transport failures into domain errors.
  • Framework proxies (@Transactional, @Cacheable, interceptors) aren't relied on through self-calls or non-virtual methods.
  • Composite operations handle depth limits and cycles when the tree comes from outside.
  • Bridges exist only where both dimensions really vary; otherwise it's plain DI.
  • Flyweights are immutable, bounded and justified by a memory profile.

Self-check

You wrap a PaymentsClient from a vendor SDK in a class that implements your IPayments, converts their ChargeResult into your PaymentOutcome, and maps their error codes to your exceptions. Is that an adapter, a facade or a decorator?

An adapter: one object, and the interface changes from theirs to yours. It isn't a decorator, because a decorator keeps the same interface. If the class also coordinated several vendor clients (tokenise, then charge, then capture) behind one PayAsync, it would be a facade too. In DDD terms, this boundary is an anti-corruption layer. The test of a good one: no vendor type or vendor exception escapes it.

Your stack is Caching(Authorization(Repository)). User A (allowed) reads document 7, then user B (not allowed) reads document 7. What happens, and how do you fix it?

User A's call misses the cache, passes authorization, and the result is cached. User B's call is a cache hit: the cache returns document 7 without ever reaching the authorization layer. B sees data they shouldn't. Fix it by putting authorization outside the cache (Authorization(Caching(Repository))), or by including the user or permission in the cache key. This is the most dangerous decorator-ordering bug, and the reason ordering belongs in one composition root with tests.

In Spring, getReport(id) is annotated @Cacheable. Another method in the same class calls this.getReport(id) in a loop, and every call hits the database. Why?

Spring implements @Cacheable with a proxy around the bean. Callers from outside hold the proxy, so their calls go through the caching logic. A call on this inside the class goes straight to the real object and skips the proxy entirely. Fixes: move the cached method to another bean, inject the bean's own proxy (@Lazy self-injection or AopContext.currentProxy()), or use explicit caching (a decorator or a Cache call) instead of the annotation. The same applies to @Transactional and @Async.

A notifications module has EmailAlert, SmsAlert, SlackAlert, EmailDigest, SmsDigest and SlackDigest. Product wants Teams and a new "Reminder" type. How many classes does each design need?

With inheritance: 3 types × 4 channels = 12 classes (6 new). With a bridge: 3 notification types + 4 channels = 7 classes (2 new: TeamsChannel and Reminder), combined at runtime. The bridge turns multiplication into addition. Only use it if both dimensions genuinely grow; if there were only ever one channel, a plain class would do.

A log analyser holds 20 million parsed log entries in memory, each with Region, Service and Level strings that only have a few hundred distinct values. Memory is 9 GB. What would you try, and what would you avoid?

That's a flyweight opportunity: the repeated strings are intrinsic, immutable and shared. Deduplicate them through a bounded lookup (a dictionary per field, StringPool, sys.intern for a known small set of values, unique.Make in Go), or replace them with small enum or integer IDs. Measure before and after with a memory profiler. Avoid string.Intern in .NET for values that come from input you don't control: the intern pool lives for the whole process and never shrinks. Also avoid comparing the interned values by reference elsewhere in the code.

In TypeScript, you need an ILogger with info(msg) and error(msg), and a library gives you an object whose methods are exactly info(msg: string) and error(msg: string). Do you write an adapter?

No. TypeScript is structurally typed: an object with the right members already satisfies the interface, so you pass it directly. You'd only write an adapter if the shapes differ (say the library's method is log(level, msg)), or if you want to stop the library's types and errors from spreading through your code. Go interfaces work the same way: a type satisfies an interface implicitly if it has the methods. C# and Java need an explicit implements, so they need adapters more often.

Cheat sheet

The shapeA field holding another object plus methods that forward to it. The intent gives it its name.
AdapterWrong interface → your interface. Translate inputs, outputs and errors. One object.
FacadeMany calls → one task-shaped call. Owns order and compensation. Split by task.
DecoratorSame interface + extra behaviour. Stacks. Order matters: outside sees everything inside.
ProxySame interface, controls access: virtual (when), protection (whether), caching (how often), remote (where).
Dynamic proxyDispatchProxy, Castle, JDK Proxy, Spring AOP, JS Proxy. Self-calls bypass it.
CompositeLeaf and group share one interface; the operation recurses. Prefer safe composite; beware cycles and depth.
BridgeTwo growing dimensions → two hierarchies + a reference. m × n classes become m + n.
FlyweightShare immutable intrinsic state; store extrinsic state per use. Measure first; bound the cache.
OrderMetrics → auth → cache → retry → real. Never cache errors; never cache before authorization.
