DESIGN PATTERNS

Creational Patterns

Factory Method, Abstract Factory, Builder, Prototype and Singleton, and why DI containers replaced most singletons.

Intermediate~50 min studyBuilds on: Design Principles: SOLID, DRY, KISS, YAGNIUpdated 2026-11-03

The problem: every new is a decision, and you've scattered them everywhere

Here is a checkout service that a team ships quickly. It works. Then someone asks for SMS receipts, a test suite that doesn't send real email, a second payment provider for one region, and connection settings that come from configuration. Each request turns out to be hard, and the reason is the same every time: the code that uses objects also decides which objects exist, how they're put together and how many of them there are.

public class CheckoutService
{
    public async Task<Receipt> CheckoutAsync(Cart cart, string channel)
    {
        // decision 1: WHICH concrete classes (hard-coded, so untestable)
        var db = new SqlConnection("Server=prod-sql;Database=shop;...");   // secret in code
        var gateway = new StripeGateway("sk_live_...");                    // can't fake it in tests

        // decision 2: HOW to assemble a complex object (positional soup)
        var request = new PaymentRequest(cart.Total, "EUR", null, null, true, 3, 30);

        // decision 3: WHICH implementation at runtime (this switch is copy-pasted in 4 files)
        INotifier notifier = channel switch
        {
            "email" => new EmailNotifier(new SmtpClient("smtp.contoso.com", 587)),
            "sms"   => new SmsNotifier(new TwilioClient("AC...", "token")),
            _       => throw new ArgumentException(channel)
        };

        // decision 4: HOW MANY (a hidden global, shared by every test)
        var rates = TaxRates.Instance;

        var charge = await gateway.ChargeAsync(request);
        await notifier.SendAsync(cart.Customer, $"Paid {charge.Amount}");
        return new Receipt(charge.Id, rates.For(cart.Country));
    }
}

// The service only USES things. Every decision moved somewhere with one job.
public class CheckoutService(
    IPaymentGateway gateway,                 // which class: decided by the composition root
    INotifierFactory notifiers,              // runtime choice: one factory, one switch
    ITaxRates rates)                         // how many: a DI singleton, not a static
{
    public async Task<Receipt> CheckoutAsync(Cart cart, string channel)
    {
        var request = PaymentRequest.For(cart.Total, "EUR")   // static factory: named, validated
            with { Capture = true, Retries = 3 };             // record 'with' instead of a builder

        var charge = await gateway.ChargeAsync(request);
        await notifiers.Create(channel).SendAsync(cart.Customer, $"Paid {charge.Amount}");
        return new Receipt(charge.Id, rates.For(cart.Country));
    }
}

// Program.cs: the ONE place that knows concrete types, secrets and lifetimes
builder.Services.AddSingleton<ITaxRates, TaxRates>();
builder.Services.AddScoped<IPaymentGateway, StripeGateway>();
builder.Services.AddKeyedTransient<INotifier, EmailNotifier>("email");
builder.Services.AddKeyedTransient<INotifier, SmsNotifier>("sms");
builder.Services.AddSingleton<INotifierFactory, KeyedNotifierFactory>();

The "after" code isn't shorter. What changed is that it says what it needs and lets someone else decide. That is what creational patterns are for. Each one moves one kind of construction decision out of business code into a single, named place, which is the Single Responsibility and Dependency Inversion principles applied to object creation.

Separate using an object from deciding which object it is, how it's assembled and how many exist. Put each decision in exactly one place, and reach for the lightest tool that does that: a constructor parameter, then a function, then a pattern.

The mental model: three questions about creation

Every creational pattern answers one of three questions. Once you know which question you're facing, the pattern more or less picks itself.

Question Classic pattern What it usually looks like in modern code
Which concrete type? Factory Method, Abstract Factory Constructor injection; a Func<T> or keyed service; a registry map[string]func() T; a static factory function
How is it assembled? Builder, Prototype Named/optional arguments, records with with, options objects, Go functional options, copy.replace
How many, for how long? Singleton, Object Pool DI lifetimes (singleton / scoped / transient), Lazy<T>, sync.Once, built-in pools (ArrayPool, connection pools)

Patterns shrink as languages grow. The 1994 Design Patterns catalogue was written for C++ and Smalltalk, which had no lambdas, no named arguments, no modules and no DI containers. Many of its patterns were workarounds for those gaps. Today a Python class is already a factory (call it), a C# record is already a prototype (with), a Go package-level sync.OnceValue is already a lazy singleton, and a container is a factory, a lifetime manager and a registry rolled into one. Learn the patterns for their intent and vocabulary, then write the smallest idiomatic thing that achieves that intent in your language. Writing a ShapeFactoryFactory because a book drew one is the anti-pattern, not the pattern.

Static factory functions: the smallest creational pattern

Before any Gang-of-Four pattern there's a simpler tool: a named function that returns a new instance. It's sometimes called a static factory method (Effective Java, Item 1) and it's everywhere: TimeSpan.FromSeconds(5), Integer.valueOf(42), List.of(1, 2), Path.of("a"), datetime.fromisoformat(s), strings.NewReader(s), Array.from(x).

The pain it removes

var t1 = new TimeSpan(0, 0, 5);            // hours? minutes? which argument is which?
var m  = new Money(1999, "eur", 2);        // cents? scale? is "eur" valid?
var c  = new Connection(cs);               // ...then you must remember to call OpenAsync()

A constructor has no name, must return exactly its own type, can't return a cached instance, can't be async, and can only fail by throwing. A static factory function removes all five restrictions.

What a factory function can do Constructor Example
Have a meaningful name no TimeSpan.FromMinutes(5) vs new TimeSpan(0, 5, 0)
Return a cached instance no Integer.valueOf(127) reuses one of the cached boxes for −128 to 127
Return a subtype or hidden class no List.of(...) returns an internal immutable list class
Be async no await Connection.OpenAsync(cs): constructors can't await
Return errors as values no (throws) Money.TryCreate(...), Go's NewX(...) (*X, error) 
public sealed record Money
{
    public decimal Amount { get; }
    public string Currency { get; }
    private Money(decimal amount, string currency) => (Amount, Currency) = (amount, currency);

    public static Money Of(decimal amount, string currency)          // named, validated
    {
        if (currency is not { Length: 3 }) throw new ArgumentException("ISO 4217 code", nameof(currency));
        return new Money(decimal.Round(amount, 2), currency.ToUpperInvariant());
    }
    public static readonly Money ZeroEur = new(0, "EUR");             // a cached instance

    // constructors can't await, so async creation goes through a factory
    public static async Task<Money> ConvertAsync(Money m, string to, IRates rates) =>
        Of(m.Amount * await rates.GetAsync(m.Currency, to), to);
}

public final class Money {
    private final BigDecimal amount;
    private final String currency;
    private Money(BigDecimal amount, String currency) { this.amount = amount; this.currency = currency; }

    public static Money of(String amount, String currency) {             // named, validated
        if (currency == null || currency.length() != 3) throw new IllegalArgumentException("ISO 4217 code");
        return new Money(new BigDecimal(amount).setScale(2, RoundingMode.HALF_EVEN), currency.toUpperCase());
    }
    public static final Money ZERO_EUR = new Money(BigDecimal.ZERO, "EUR"); // cached
}
// The JDK does this everywhere: Integer.valueOf, List.of, Optional.of, Path.of, Duration.ofSeconds

// Often a module-level function is all you need: export function createMoney(...) {}

Default to a factory function for value objects whose constructor needs validation or normalisation. Make the constructor private so there's only one way in. This is also how you get async creation (await Client.ConnectAsync()), which no language allows in a constructor.

A simple factory is the same idea with a switch inside: NotifierFactory.Create("sms"). It isn't in the GoF book, but it's the version most people mean when they say "factory". It's fine as long as the switch lives in one place. Once the same switch appears in a second file, turn it into a registry (next section) so that adding a kind means adding a line, not editing a function.

Factory Method: let something else pick the class

The pain it removes

// The same switch, copy-pasted into OrderService, RefundService, ReminderJob, AdminController...
INotifier n = channel switch
{
    "email" => new EmailNotifier(new SmtpClient(host, 587)),
    "sms"   => new SmsNotifier(new TwilioClient(sid, token)),
    _       => throw new ArgumentException(channel),
};
// Add "push": edit four files, forget one, and ship a bug that only fires for push users.

Intent (GoF): define an interface for creating an object, but let subclasses decide which class to instantiate. In the original form a base class has an algorithm with a creation step it doesn't implement itself. Subclasses override that one step:

The textbook shape, in C#:

public abstract class NotificationSender
{
    public async Task SendAsync(string to, string msg)
    {
        var channel = CreateChannel();                 // the factory method
        await channel.DeliverAsync(to, Format(msg));   // the algorithm only knows IChannel
    }
    protected abstract IChannel CreateChannel();       // subclasses decide the class
    protected virtual string Format(string msg) => msg;
}

public sealed class EmailSender(SmtpOptions o) : NotificationSender
{
    protected override IChannel CreateChannel() => new SmtpChannel(o.Host, o.Port);
}

You've used this shape without noticing. IEnumerable<T>.GetEnumerator() and Java's Iterable.iterator() are factory methods: every collection decides which enumerator class to create, and foreach only knows the interface. document.createElement("video") returns an HTMLVideoElement. Calendar.getInstance(), NumberFormat.getInstance(locale) and MessageDigest.getInstance("SHA-256") pick a class from their argument.

The modern form: a registry or a delegate

Inheritance to vary one new is heavy. Most modern code keeps the intent (one place decides the class) but replaces the subclass with a map from key to creation function. That's the version in the visualizer: the client passes a key, the factory looks up a function, and the only new for each class lives in the registration.

Try fax in the requests: a good factory fails at once with a message that lists the kinds it does know. Switch to reuse one per kind and notice that the client can't tell the difference. Choosing how many instances to make is also the factory's call, which is exactly how logging.getLogger(name) and ILoggerFactory.CreateLogger(category) behave (same name, same logger).

// .NET 8+: keyed services make the container the registry.

# A class is already a callable that makes instances, so a dict of classes IS the factory.
NOTIFIERS: dict[str, type[Notifier]] = {
    "email": EmailNotifier,
    "sms": SmsNotifier,
}

def create_notifier(kind: str, **settings) -> Notifier:
    try:
        cls = NOTIFIERS[kind]
    except KeyError:
        raise ValueError(f"unknown channel {kind!r}; known: {sorted(NOTIFIERS)}") from None
    return cls(**settings)

# Registration by decorator keeps the registry next to each class:
def notifier(kind: str):
    def register(cls):
        NOTIFIERS[kind] = cls
        return cls
    return register

# stdlib: logging.getLogger(name) caches per name; codecs.lookup("utf-8") is a registry lookup.

// database/sql is the canonical Go registry factory:
//   import _ "github.com/jackc/pgx/v5/stdlib"   // the driver's init() calls sql.Register("pgx", ...)
//   db, err := sql.Open("pgx", dsn)               // the factory looks the name up
type Factory func(cfg Config) (Notifier, error)

var (
    mu        sync.RWMutex
    factories = map[string]Factory{}
)

func Register(kind string, f Factory) {
    mu.Lock()
    defer mu.Unlock()
    if _, dup := factories[kind]; dup {
        panic("notify: Register called twice for " + kind) // what database/sql does too
    }
    factories[kind] = f
}

func New(kind string, cfg Config) (Notifier, error) {
    mu.RLock()
    f, ok := factories[kind]
    mu.RUnlock()
    if !ok {
        return nil, fmt.Errorf("notify: unknown channel %q", kind)
    }
    return f(cfg)
}

// A record of creation functions. The type system can even check the keys.
const notifiers = {
  email: (cfg: Config) => new EmailNotifier(cfg.smtp),
  sms: (cfg: Config) => new SmsNotifier(cfg.twilio),
} satisfies Record<string, (cfg: Config) => Notifier>;

type Channel = keyof typeof notifiers;                 // "email" | "sms"

export function createNotifier(kind: Channel, cfg: Config): Notifier {
  return notifiers[kind](cfg);                         // unknown kinds don't compile
}

// For strings from outside (HTTP, config) validate first:
export function parseChannel(s: string): Channel {
  if (s in notifiers) return s as Channel;
  throw new Error(`unknown channel "${s}"; known: ${Object.keys(notifiers).join(", ")}`);
}
// DOM: document.createElement("video") returns HTMLVideoElement, typed by tag name.

Use a factory when

  • The concrete class depends on runtime data: a message type, a tenant, a file extension, a user's choice.
  • The same choice would otherwise be repeated in several places.
  • Creation needs things the caller shouldn't know about: secrets, pools, handlers, options.
  • You want to control how many (cache per key) without callers knowing.

Don't use one when

  • The type is fixed at startup. Then it's just constructor injection; the container already is the factory.
  • There's one implementation and no realistic second one (YAGNI).
  • You'd be wrapping new Foo() in FooFactory.Create() with nothing else inside. That's ceremony, and it hides the dependency.
  • The "factory" takes IServiceProvider and resolves arbitrary types. That's a service locator.

Misuse: the factory that returns null for unknown keys. Create("fax") returns null, the caller doesn't check, and you get a NullReferenceException three frames later, in code that has nothing to do with notifications. Fix: throw (or return an error) at the factory, and list the known keys in the message. Better still, make the key a closed type (an enum, a TypeScript union, a sealed hierarchy) so unknown keys can't be written at all.

Abstract Factory: families that must match

The pain it removes

// Each call site picks its own classes. One of them is from a different family.
var conn = new NpgsqlConnection(cs);
var cmd  = new SqlCommand("select * from orders where id = @id");   // SQL Server command...
cmd.Connection = conn;                                               // ...on a Postgres connection
// compiles fine; throws InvalidCastException at runtime, in production, on the first query

Sometimes you don't create one object; you create several that must belong together: a connection, a command and a parameter for the same database; a button, a checkbox and a menu for the same UI theme; a client, a serializer and a credential for the same cloud. Intent (GoF): provide an interface for creating families of related or dependent objects without specifying their concrete classes. The client holds one factory, so it can't mix families.

ADO.NET's DbProviderFactory is the textbook example in a real framework: SqlClientFactory.Instance, NpgsqlFactory.Instance and SqliteFactory.Instance each create a matching DbConnection, DbCommand and DbParameter. The visualizer starts with each call site uses new: edit the call sites to mix providers and watch the mismatch get through the compiler and fail at runtime. Then switch to one abstract factory and pick a family: there's no way left to ask for a mismatched pair.

Use it when

  • Several products must come from the same family, and mixing them is a real bug (database objects, themed widgets, cloud SDK clients).
  • The family is chosen once (by config, tenant or platform), and many places create products.
  • You want tests to swap a whole family at once (an in-memory database family, a fake cloud).

Don't use it when

  • There's only one product. That's a factory method or simply injection.
  • There's only one family. You'd have an interface with one implementation for no reason.
  • New products are added often. Every new product means editing every factory: the pattern makes new families cheap and new products expensive.

A DI container often replaces a hand-written abstract factory. If the family is fixed at startup, register the matching implementations together (an AddPostgres() or AddSqlServer() extension method) and inject the products directly. The extension method is the family. Write an explicit abstract factory only when the family is chosen at runtime (per tenant, per request) or when the products are created many times during an operation.

Builder: assembling complex objects step by step

The pain it removes

// The telescoping constructor: which `true` is which? Which null can be omitted?
var req = new HttpRequest("https://api.contoso.com/orders", "POST", null, headers,
                          true, 30, 3, null, false, "application/json");
// Swap two booleans and it still compiles. Add a field and every call site breaks.

Intent (GoF): separate the construction of a complex object from its representation, so the same construction process can create different representations. In practice it means a mutable helper that collects settings step by step, then validates them and produces an immutable result in one Build() call.

There are two flavours:

  • Fluent builder: every setter returns this, so calls chain in any order. Build() checks required fields and cross-field rules at runtime.
  • Step builder (sometimes "type-state builder"): each step returns a different interface that only offers the next legal steps, so a missing required field is a compile error, not a runtime exception.

Type a chain of calls in the visualizer. The default chain calls timeout(5) before auth(...): a fluent builder accepts any order, but switch to step builder and the same chain is a compile error. Then try leaving out url(...), passing timeout(0), header(bad) or retries(99), or calling a method after build(). Compare when each mistake is caught: in a method, in build(), or by the compiler.

// Most of the time C# doesn't need a builder: required + init + records do the job.

// Java has no named or default arguments, so builders are common and idiomatic.
public final class HttpCall {
    private final URI url; private final String method; private final Duration timeout; private final int retries;
    private HttpCall(Builder b) { url = b.url; method = b.method; timeout = b.timeout; retries = b.retries; }

    public static Builder builder(URI url) { return new Builder(url); }   // required arg up front

    public static final class Builder {
        private final URI url; private String method = "GET";
        private Duration timeout = Duration.ofSeconds(30); private int retries;
        private Builder(URI url) { this.url = Objects.requireNonNull(url); }
        public Builder method(String m) { this.method = m; return this; }
        public Builder timeout(Duration d) { this.timeout = d; return this; }
        public Builder retries(int n) { this.retries = n; return this; }
        public HttpCall build() {
            if (timeout.isZero() || timeout.isNegative()) throw new IllegalStateException("timeout must be > 0");
            return new HttpCall(this);
        }
    }
}

type Client struct {

A builder earns its place when

  • The object has many optional parts and the language lacks named/default arguments (Java, and Go before options).
  • Construction is staged: collect configuration, then freeze it (WebApplication.CreateBuilder → Build()).
  • You accumulate many small pieces efficiently (StringBuilder, strings.Builder, query builders).
  • Invalid combinations must be rejected before an object exists (validate in Build()), or at compile time (step builder).

Prefer something lighter when

  • The language has named and default arguments: C# required/init, Python keyword-only args, Kotlin, TypeScript options objects.
  • You only need "a copy with one change": records with, dataclasses.replace, spread.
  • The object has three fields. A builder doubles the code for no gain.
  • The builder becomes a mutable object that leaks around the system half-built. Keep builders local to one method.

Misuse: a builder that doesn't validate. If Build() just copies fields, you've reinvented a mutable object with extra steps, and new Builder().build() happily produces an object with a null URL. Fix: required values go in the builder's constructor (or step interfaces), and Build() checks every cross-field rule (body only with POST/PUT; retries only with idempotent methods) and throws one clear message.

Misuse: reusing a builder after Build(). StringBuilder is designed to be reused, but most domain builders aren't. If the built object shares a mutable list with its builder, a later builder.addHeader(...) changes an object that's already been built. Fix: copy collections in Build() (List.copyOf, [...headers], ToImmutableList()).

Prototype: create by copying an existing object

The pain it removes

// "Make another order like this one": copy every field by hand, forget the new one added last sprint,
// and share a mutable list by accident.
var copy = new Order { Id = 0, Customer = order.Customer, Lines = order.Lines, Notes = order.Notes };
copy.Lines.Add(new Line("SKU-9", 1));   // oops: also added to the ORIGINAL order's lines

Intent (GoF): specify the kinds of objects to create using a prototypical instance, and create new objects by copying this prototype. You clone something that's already configured instead of building it up again, and the copy decides how deep to go.

The whole pattern hinges on one question: how deep is the copy?

  • A shallow copy duplicates the top object, but its reference fields still point to the same children. Change a child through the copy and the original changes too.
  • A deep copy duplicates the whole graph that the object owns.
  • Most real code needs something in between: copy what the object owns (its order lines), share what it only references (the customer, a product catalogue, an immutable value).

Pick a copy depth, then mutate the clone with commands such as clone.lines[0].qty=5, clone.customer.name=Bo or clone.lines.push(SKU-9). Watch which changes leak back into the original.

// Records give you a shallow prototype for free: 'with' copies, then overrides.
public sealed record Order(int Id, Customer Customer, ImmutableList<Line> Lines);
var draft = order with { Id = 0 };       // shallow, but Lines is immutable, so sharing is SAFE

// With mutable collections, write the copy deliberately, field by field:
public sealed class MutableOrder
{
    public int Id { get; set; }
    public Customer Customer { get; set; } = default!;      // shared on purpose (an entity reference)
    public List<Line> Lines { get; set; } = [];

    public MutableOrder CloneAsDraft() => new()
    {
        Id = 0,
        Customer = Customer,                                   // share
        Lines = Lines.Select(l => l with { }).ToList(),        // own: new list, new lines
    };
}
// object.MemberwiseClone() is shallow and protected. ICloneable doesn't say whether it's deep
// or shallow, so the .NET design guidelines advise against exposing it in public APIs.

// Avoid Cloneable/clone(): it's shallow, bypasses constructors and needs casts (Effective Java, Item 13).
// Prefer a copy constructor or a copy factory, which says exactly what is copied:
public final class Order {
    private final Customer customer;      // shared
    private final List<Line> lines;       // owned

    public Order(Order other) {           // copy constructor
        this.customer = other.customer;
        this.lines = new ArrayList<>(other.lines.size());
        for (Line l : other.lines) this.lines.add(new Line(l)); // deep for what we own
    }
}
// Records + List.copyOf give immutable values that can be shared instead of copied.
// Spring's "prototype" scope means "a new bean per lookup". That's a lifetime, not cloning.

import copy

deep = copy.deepcopy(order)       # deep: follows every reference (handles cycles via a memo dict)

# Control the depth per class instead of trusting deepcopy blindly:
class Order:
    def __copy__(self):
        new = Order.__new__(Order)
        new.__dict__.update(self.__dict__)
        new.lines = [copy.copy(l) for l in self.lines]   # own the lines, share the customer
        return new

}

// The usual idiom: copy exactly what you own.

Use a prototype when

  • Creating from scratch is expensive (parsed templates, a configured document, a loaded game unit) and copies are cheap.
  • Users build "like this one, but…" objects: duplicating a slide, an order or a test fixture.
  • You need snapshots for undo, what-if calculations or optimistic edits.

Don't use it when

  • The objects are immutable. Share them; there's nothing to copy. with covers "change one field".
  • The object holds resources (connections, file handles, locks). Copying a handle doesn't copy the resource.
  • You'd rely on a generic deep copy for entities with identity. Copying an Order shouldn't copy its Customer entity.

Misuse: "deep copy everything" as a safety blanket. deepcopy/structuredClone on an object that references a big shared graph (a cache, a catalogue, a DbContext) copies all of it: slow, memory-hungry, and it silently breaks identity (two "same" customers that are no longer the same object). Fix: decide per field (own → copy, reference → share, immutable → share) and write that down in one Clone/copy-constructor method with a test that mutates the copy and asserts the original is unchanged.

Singleton: one instance, and why the container should own it

The pain it removes, and the pain it adds

// Without any control, every class creates its own expensive, stateful thing:
var cfg1 = new ConfigLoader().Load("appsettings.json");   // parsed in OrderService
var cfg2 = new ConfigLoader().Load("appsettings.json");   // parsed again in TaxService; now two can disagree
var http = new HttpClient();                               // per request: exhausts sockets under load

Intent (GoF): ensure a class only has one instance, and provide a global point of access to it. That sentence bundles two different things, and only the first is usually a good idea:

  1. One instance: legitimate for expensive, thread-safe, shared things such as configuration, an HttpClient handler pool, a compiled regex cache or a metrics registry.
  2. Global access (Config.Instance from anywhere): a hidden dependency. Any method can reach it, so you can't see from a constructor what a class really depends on, and tests can't substitute it.

Thread-safe lazy initialisation: harder than it looks

The classic lazy singleton checks "is it null?", then creates it. With two threads, both can see null. The visualizer lets you pick the exact interleaving: each letter in the schedule is a thread that runs one step. Start with naive and ABABAB, and you'll get two instances. Then try double-checked, NO volatile with AAAAAB: thread B can see the reference published before the constructor's writes are visible, and uses a half-built object. That's the bug that took Java until JSR-133 (Java 5) to define precisely.

You should almost never write that double-checked lock yourself. Every language has a built-in that's correct and fast:

// Best: let the container own the lifetime. No static, still one instance.
builder.Services.AddSingleton<ITaxRates, TaxRates>();

{

    public static Clock Instance => _instance.Value;
    private Clock() { }
}

// Or a static readonly field: the CLR runs type initializers exactly once, thread-safely.

{
    public static readonly Regex Sku = new(@"^SKU-\d+$", RegexOptions.Compiled);
}

// Spring beans are singletons by default (one per ApplicationContext): prefer that.

// because the JVM initializes the nested class exactly once, on first use.

Why a DI singleton beats a static singleton

The behaviour you usually want is one instance per application. A container gives you that as a lifetime while keeping the dependency visible in constructors. The static version turns it into a global. The difference shows up first in tests. Run the four tests below in different orders: with static state, T2 passes or fails depending on whether T1 ran first.

Static Instance DI singleton (AddSingleton, @Component)
Dependency visible in the constructor no, hidden yes
Swap in a test hard (needs a reset hook or reflection) pass a fake, or build a fresh container per test
Scope per process (per AppDomain/ClassLoader/interpreter) per container: one per test is easy
Thread safety of creation you write it the container guarantees it
Disposal at shutdown rarely done the container disposes it
Can depend on other services only via more globals constructor injection

Misuse: a singleton that holds per-request or per-user state. A CurrentUser singleton, or a singleton that captures a scoped DbContext, will serve user A's data to user B under load. That's a captive dependency. Fix: singletons must be stateless or hold only shared, thread-safe state; anything per-request is scoped. Turn on scope validation (ValidateScopes/ValidateOnBuild in .NET) so the container refuses to build the bad graph.

Misuse: mutable singletons without synchronisation. One instance means every thread hits the same fields. A singleton Dictionary used as a cache will corrupt itself under concurrent writes. Use ConcurrentDictionary, ConcurrentHashMap or sync.Map, or make the state immutable and swap whole references. See thread safety per lifetime.

Object Pool: reuse expensive objects instead of re-creating them

The pain it removes

// Per request: open a TCP connection, TLS handshake, authenticate. 20-50 ms before the first query.
await using var conn = new NpgsqlConnection(cs);
await conn.OpenAsync();           // with pooling this is ~microseconds after the first time
// Per message: a fresh 64 KB buffer, so the GC churns through gigabytes per minute.
var buffer = new byte[65536];

An object pool keeps a set of ready-to-use instances. Callers rent one, use it, and return it. The pool resets it and hands it to the next caller. It's not in the GoF book, but it's one of the most widely used creational patterns, mostly inside frameworks rather than in your code.

The visualizer runs a sequence of operations: +a rents an object for borrower a, *a makes a write into it, -a returns it. The default script contains two classic bugs: a double return (-c -c), after which two later renters receive the same object, and no reset on return, which shows c's data to d. Switch on return to clear the buffer and change max retained to see what the pool keeps.

// Items can be dropped at ANY garbage collection: never use it for connections.
var bufPool = sync.Pool{New: func() any { return new(bytes.Buffer) }}

    buf.Reset()                         // reset on GET (or before Put): it may hold old data
    defer bufPool.Put(buf)
    if err := json.NewEncoder(buf).Encode(v); err != nil {
        return err
    }
    _, err := w.Write(buf.Bytes())      // don't keep buf.Bytes() after Put
    return err
}

Pool when

  • Creation is expensive in time or external resources: connections, TLS sessions, threads, processes, GPU buffers.
  • The resource is limited elsewhere (the database allows 100 connections), so the pool's maximum is also a throttle.
  • A profiler shows large or frequent allocations dominating GC time on a hot path (buffers ≥ 85 KB in .NET land on the Large Object Heap).

Don't pool when

  • Objects are small and short-lived. Modern generational GCs make young-generation allocation nearly free (a pointer bump), and a pool keeps objects alive into older generations, which can make GC worse. See memory and GC.
  • The framework already pools it (DB drivers, HttpClient handlers, thread pools). A pool on top of a pool causes leaks and deadlocks.
  • You can't guarantee reset and single return on every path, including exceptions.

The three pool bugs. (1) No reset: the next renter sees the previous renter's data, which is a security bug when it's a buffer with a password or another user's response. (2) Double return: two renters later share one object and corrupt each other's work. (3) Use after return: a reference kept after Return (a Span over a rented array, buf.Bytes() after Put) now aliases someone else's data. Fix: return in finally/defer/using, exactly once; reset in the pool policy; never let a pooled object escape the method that rented it.

Unbounded pools are a memory leak with a nicer name. Always cap what the pool retains, and cap the total that can be rented (or block/fail fast when exhausted).

Which creational pattern? Decide for your case

Answer the questions for something you're building. The path lights up and the leaf tells you what to write, which is often no pattern at all.

When NOT to use creational patterns

Pattern for its own sake

IUserFactory with one method Create() that returns new User(). An AbstractRepositoryFactoryProvider. These add indirection, hide the real type from readers and IDE navigation, and buy nothing. KISS: new is fine for values, entities and anything without dependencies.

A pattern the language already has

A builder for a C# record, a singleton class in Python, a prototype interface for a TypeScript object, an abstract factory where an object literal of functions would do. Use named arguments, with, modules, spread and closures first.

A real decision, in one place

A runtime choice made in many places, a family that must match, a costly resource that must be bounded, or an object that's only valid once several parts are set. That's when the pattern pays for its extra type.

Common pitfalls

Factories that hide failure. Returning null or a default "no-op" object for an unknown key turns a configuration error into a mystery later. Fail fast, at startup if possible (ValidateOnBuild, a startup check that every configured key resolves).

Singletons as global variables. AppState.Instance.CurrentOrder = order; is a global mutable variable dressed as a pattern. It leaks between requests, between tests and between users. Pass the order as a parameter, or make it scoped.

Lazy initialisation written by hand. Double-checked locking without volatile in Java, a check-then-create without a lock in C#, or a Python if _x is None: in multithreaded code can produce two instances or a half-built one. Use Lazy<T>, the holder idiom, sync.Once, or let the container do it.

Shallow copies of mutable children. {...order}, copy.copy, MemberwiseClone and Go struct assignment all share nested lists and maps. Mutating the copy's lines changes the original. Copy what you own, or make the children immutable.

Builders that build invalid objects. No required-field checks, no cross-field validation, or a built object that shares mutable state with its builder. Validate in Build() and copy collections.

Pools without discipline. No reset, double return, use after return, and no upper bound. Or pooling something the framework already pools. Every one of these is a production incident waiting for load.

Checklist

  • Business code asks for services (constructor parameters); only the composition root or a factory calls new on them.
  • Every runtime "which class?" decision lives in exactly one factory or registry, and unknown keys fail fast with a helpful message.
  • Families that must match (database objects, themed widgets) come from one injected factory.
  • Value objects with rules have a named factory function and a private constructor; async creation goes through CreateAsync/NewX.
  • Builders exist only where named/optional arguments don't cover it; Build() validates and copies collections.
  • Every copy method states, per field, whether it copies or shares, and a test proves the original is unaffected.
  • "One instance" is a DI lifetime, not a static Instance; singletons are stateless or thread-safe and never capture scoped services.
  • Lazy statics use the platform primitive (Lazy<T>, holder idiom, sync.Once, module scope), never hand-written double-checked locking.
  • Pools exist only for measured, expensive or limited resources; they're bounded, reset on return, and returned exactly once in finally/defer.
  • Tests build a fresh object graph per test, so no state leaks between them.

Self-check

A colleague adds OrderServiceFactory with one method, Create(), that returns new OrderService(new SqlOrderRepository(cs), new SmtpMailer()), and injects the factory into the controller. Good idea?

No. It doesn't decide anything at runtime; it just moves the new calls into another class and hides the dependency graph from the container. The controller still can't be tested with a fake repository unless you also fake the factory. Register OrderService, IOrderRepository and IMailer in the composition root and inject OrderService (or an interface) directly. Keep a factory only if the controller must create services later or per key, and then make it typed (Func<string, IOrderService> or a keyed lookup), not a wrapper around new.

Why is if (_instance == null) _instance = new Config(); unsafe even though it "only runs once at startup"?

"At startup" is often concurrent: the first few requests arrive together, or several background services start in parallel. Two threads can both read null and both construct, so you get two instances (and two loads of configuration, which may differ). Without a memory barrier, a thread can also see the reference before the constructor's writes are visible and use a half-initialised object. Use Lazy<T>, a static readonly field, the holder idiom, sync.Once, or a DI singleton.

You need 5 test fixtures that are like a "standard order" but each differs in one or two fields. Builder, prototype or something else?

A prototype with overrides, which in modern languages is just a copy-with: StandardOrder with { Country = "DE" } (C# records), dataclasses.replace(standard_order, country="DE"), { ...standardOrder, country: "DE" }. If the order has mutable children, either make them immutable or write one copy method that duplicates the lines. A test data builder (AnOrder().WithCountry("DE").Build()) is a good alternative in Java, where there's no with, and when fixtures need sensible defaults for many fields.

A team pools OrderDto objects (8 small fields) "to reduce GC pressure" in an ASP.NET Core API. What can go wrong, and what would you check first?

Small, short-lived objects die young in gen0, where allocation is a pointer bump and collection is cheap. A pool keeps them alive, so they get promoted to gen1/gen2, which makes collections more expensive. It also adds reset bugs (one customer's data showing up in another's response), double-return bugs and lock contention. Check a profile first (allocation rate, GC pause time, % time in GC). If allocation really matters, reduce it at the source: avoid intermediate copies, use struct/Span<T> for hot paths, and pool only the large buffers (ArrayPool).

Why does an abstract factory make adding a new family easy but adding a new product hard?

A new family is one new class that implements the existing factory interface: nothing else changes (open/closed). A new product means a new method on the factory interface, so every existing family must implement it. If products change more often than families, an abstract factory is the wrong axis. Use separate factories or keyed registrations per product instead.

In Go, what's wrong with keeping database connections in a sync.Pool?

sync.Pool may drop any item at any garbage collection, without calling a close function, so connections leak (they're never closed) and the pool doesn't bound how many exist. It's designed for temporary memory such as buffers. For connections use *sql.DB, which is already a bounded pool with lifetime management (SetMaxOpenConns, SetConnMaxLifetime), or a driver pool such as pgxpool.
