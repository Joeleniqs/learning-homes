Choosing a Protocol: REST, gRPC, GraphQL, WebSockets, SSE

The same feature built five ways, with a decision chart for latency, streaming, browser support and team cost.

Intermediate → Advanced~50 min studyBuilds on: REST API DesignUpdated 2026-11-03

The problem: one feature, five protocols, five different bills

A customer opens the app and watches their order go from placed to packed to shipped. The feature sounds simple, but the protocol you choose decides your latency, your server bill, whether a proxy breaks it, and how much your team has to learn. Here is the same feature, an order tracker, built five ways:

GET /v1/orders/42            → 200 {"status":"placed"}    ETag: "1"
… 5 s later …
GET /v1/orders/42            If-None-Match: "1"   → 304 Not Modified     ← nothing changed; you paid a round trip anyway
… 5 s later …
GET /v1/orders/42            If-None-Match: "1"   → 200 {"status":"packed"}  ETag: "2"
Cost: one request per client every 5 s, whether or not anything happened. Latency: up to 5 s stale.
Wins: works everywhere, cacheable, debuggable with curl. Loses: wasteful at scale, never "live".

service Orders { rpc WatchOrder(WatchOrderRequest) returns (stream OrderEvent); }
client → HEADERS  POST /shop.Orders/WatchOrder  grpc-timeout: 1H   + DATA {order_id: 42}
server ← DATA {status: PACKED}  …  DATA {status: SHIPPED}  …  trailers grpc-status: 0
Cost: one HTTP/2 stream per watcher, binary frames, typed contract and generated stubs.
Wins: lowest overhead, deadlines, flow control. Loses: browsers can't speak it natively (needs grpc-web/Connect + a proxy).

subscription { orderUpdated(id: 42) { status eta courier { name } } }
→ over a WebSocket (graphql-ws protocol): {"type":"next","payload":{"data":{"orderUpdated":{"status":"PACKED",...}}}}
Cost: a socket per client plus a pub/sub backplane; resolvers run per event.
Wins: the client picks exactly the fields it wants, in the same schema as its queries. Loses: the heaviest server stack.

GET /v1/orders/42/events     Accept: text/event-stream
200 OK  Content-Type: text/event-stream
id: 17
event: status
data: {"status":"packed"}

id: 18
event: status
data: {"status":"shipped"}
Cost: one long-lived HTTP response per client. Reconnects automatically and resends Last-Event-ID: 18.
Wins: plain HTTP, works through most proxies, five lines of browser code. Loses: server→client only, text only.

(the tracker is a partner's system, not a browser)
POST https://partner.example/hooks/orders
Webhook-Id: evt_9c1   Webhook-Timestamp: 1767225600   Webhook-Signature: v1,Kq3…
{"type":"order.shipped","data":{"orderId":"42"}}
Cost: nothing while idle; you retry with backoff until they answer 2xx.
Wins: server-to-server push with no open connection. Loses: you must sign, retry and they must deduplicate.

None of these is "the best protocol". Each is the right answer to a different question: who is calling, which way does data flow, how big and how frequent is it, and what can your team operate? This page teaches each protocol from the wire up, with simulators you can break, so you can answer that question with evidence instead of fashion.

The rule

Pick the protocol from the caller and the direction of data flow first, then from performance. REST for public and cacheable request/response; gRPC for internal, typed, low-latency and streaming calls; GraphQL when many clients need different shapes of a rich graph; SSE for server push to browsers; WebSockets only when both sides really talk; webhooks and messaging when the receiver shouldn't be waiting at all.

This page builds on API design, which covers resources, status codes, pagination, idempotency keys and ETags for REST. Here we go under and beside REST: the transports it runs on, and the alternatives. Security for all of them (authentication, rate limits, input limits) is in API security.

The mental model: protocols are layers, and most of them ride on HTTP

When people say "gRPC vs REST vs GraphQL vs WebSockets", they compare things on different layers. gRPC is an RPC convention on top of HTTP/2. GraphQL is a query language usually carried in an HTTP POST. SSE is just an HTTP response that never ends. Seeing the layers tells you what each one inherits for free, and what breaks when a proxy in the middle doesn't understand a layer.

Three consequences fall straight out of this picture:

  • Your API style and your transport are independent choices. A REST API can run on HTTP/3 and benefit from it without changing one endpoint. A GraphQL API inherits whatever HTTP version the server and client negotiate.
  • Anything that sits between client and server must understand your layer. A load balancer that terminates HTTP/2 and forwards HTTP/1.1 is fine for REST, but gRPC trailers don't survive it. A reverse proxy with response buffering turned on holds SSE events until its buffer fills. Most "gRPC works locally but not in production" stories are a middlebox that only speaks the lower layer.
  • Serialization is orthogonal. gRPC usually means Protobuf, but it can carry JSON. REST usually means JSON, but it can carry Protobuf or MessagePack. Serialization formats gets its own section below.

HTTP/1.1 vs HTTP/2 vs HTTP/3: head-of-line blocking, from the wire up

Every API on this page rides on HTTP, so the version underneath matters. Each new version fixed one specific bottleneck of the previous one, and the bottleneck in all three cases is head-of-line (HOL) blocking: a slow or lost thing at the front of a queue holds up everything behind it.

HTTP/1.1 (1997) HTTP/2 (2015) HTTP/3 (2022)
Transport TCP (+TLS) TCP (+TLS) QUIC over UDP (TLS 1.3 built in)
Requests per connection at once One. The next waits for the whole previous response. Pipelining exists but is broken in practice. Many multiplexed streams, interleaved as frames Many streams, and each stream is independently ordered
Encoding Text headers Binary frames, HPACK header compression Binary frames, QPACK header compression
Head-of-line blocking At the HTTP layer: a slow response blocks the connection, so browsers open ~6 connections per host Fixed at HTTP layer, but TCP's remains: one lost packet stalls every stream Fixed at both layers: a lost packet stalls only its own stream
Connection setup TCP handshake + TLS 1.3 = 2 round trips Same 2 round trips 1 round trip (0-RTT on resumption, for idempotent requests only)
Network change (Wi-Fi → 4G) New connection New connection Connection migration: the connection ID survives the IP change
Server push n/a Exists, but removed from browsers; don't use it Defined, rarely implemented

The simulator below runs the same five responses over each transport. Each response is a number of frames; the network delivers one frame per tick per connection; a lost packet is retransmitted after the timeout you choose. Watch what happens to the other responses while one packet is missing.

What to notice:

  • HTTP/1.1 with one connection serialises everything: response 5 waits for 1 to 4 even if it's tiny. That is HTTP-level HOL blocking, and it's why browsers open six connections per host and why "domain sharding" and sprite sheets existed.
  • HTTP/1.1 with six connections fixes that, but pays six handshakes, six TCP slow-starts and six times the server memory, and a lost packet still stalls its connection.
  • HTTP/2 interleaves frames from all streams on one connection, so small responses finish early. But TCP delivers bytes in order: when packet 9 is lost, every frame behind it is held in the kernel's receive buffer, including frames of other streams that arrived perfectly well. On a lossy mobile link HTTP/2 can be slower than six HTTP/1.1 connections.
  • HTTP/3 puts streams into QUIC, which retransmits per stream. The lost packet delays only the stream it belonged to; the others are delivered to the application immediately. It also saves a round trip on setup.

Why this matters for API design, not just browsers

gRPC multiplexes all calls from a client onto one HTTP/2 connection. That's efficient, but it means a single connection carries a whole service's traffic, inherits TCP HOL blocking, and pins to one backend behind an L4 load balancer. That is why gRPC needs L7 or client-side load balancing, and why "one huge message" on a stream delays the small ones (keep messages small and stream them).

What you actually configure

You rarely implement transports, but you do turn them on. Kestrel (ASP.NET Core) negotiates HTTP/2 by default over TLS and supports HTTP/3 with Protocols = HttpProtocols.Http1AndHttp2AndHttp3. Go's net/http does HTTP/2 automatically over TLS; HTTP/3 needs quic-go. Java's HttpClient speaks HTTP/2; Netty and Jetty add HTTP/3. Node has http2 built in. In practice, HTTP/3 is usually enabled at the CDN or edge proxy (Cloudflare, Azure Front Door, Envoy, nginx) while services talk HTTP/2 inside the data centre. Browsers discover HTTP/3 through the Alt-Svc: h3=":443" header or an HTTPS DNS record, then switch on the next request.

Cleartext HTTP/2 ("h2c") has no ALPN negotiation, so both ends must be told to use it ("prior knowledge"). It's common between a sidecar and the app inside a pod, and is the usual cause of "gRPC works with TLS but not without".

REST in one minute (and where it stops)

REST is covered in depth in API design: resources and methods, the status-code chain, problem details, cursor pagination, idempotency keys and ETags. The short version of why it remains the default:

  • Universality. Every language, tool, proxy, CDN, browser and junior engineer speaks it. curl is the debugger.
  • The web's machinery works for free. HTTP caching, conditional requests, content negotiation, redirects, compression. GET responses can be cached by a CDN you don't even run; see HTTP caching.
  • Loose coupling. Clients depend on resources and media types, not on generated stubs.

REST starts to hurt in four specific situations, and each of the other protocols on this page exists to address one of them:

Chatty or over-fetching screensA mobile screen needs 6 calls and uses 10% of each payload. → GraphQL, or a backend-for-frontend.
Hot internal call pathsJSON parsing and text headers cost CPU on every hop; no typed contract. → gRPC.
Server needs to pushREST is request/response; polling wastes requests and is never live. → SSE, WebSockets, gRPC streaming.
Receiver shouldn't waitThe caller doesn't need an answer now, or there are many consumers. → Webhooks, messaging.

gRPC: typed contracts and streams over HTTP/2

gRPC is a remote procedure call framework: you describe a service and its messages in a .proto file, a code generator produces client stubs and server base classes for each language, and calls travel as HTTP/2 streams carrying length-prefixed Protobuf messages. You call client.GetOrder(req) as though it were a local method, and get compile-time types on both sides.

The contract: a .proto file

syntax = "proto3";
package shop;

import "google/protobuf/timestamp.proto";

option csharp_namespace = "Shop.Grpc";
option java_package = "com.example.shop.grpc";
option java_multiple_files = true;
option go_package = "example.com/shop/gen/shoppb";

service Orders {
  rpc GetOrder(GetOrderRequest) returns (Order);                  // unary
  rpc WatchOrder(WatchOrderRequest) returns (stream OrderEvent);  // server streaming
  rpc UploadLines(stream OrderLine) returns (UploadSummary);      // client streaming
  rpc Chat(stream ChatMessage) returns (stream ChatMessage);      // bidirectional streaming
}

message GetOrderRequest   { int64 id = 1; }
message WatchOrderRequest { int64 id = 1; }

message Order {
  int64 id = 1;
  string customer = 2;
  reserved 3;                 // was "int32 qty": never reuse the number…
  reserved "qty";             // …or the name (it would break JSON mapping)
  bool gift = 4;
  repeated OrderLine lines = 5;
  OrderStatus status = 6;
  google.protobuf.Timestamp created_at = 7;
  optional string note = 8;   // "optional" gives presence: unset vs "" are distinguishable
}

enum OrderStatus {
  ORDER_STATUS_UNSPECIFIED = 0;   // proto3 enums must start at 0; make 0 mean "unknown"
  ORDER_STATUS_PLACED = 1;
  ORDER_STATUS_PACKED = 2;
  ORDER_STATUS_SHIPPED = 3;
}

message OrderLine     { string sku = 1; int32 qty = 2; }
message OrderEvent    { int64 order_id = 1; OrderStatus status = 2; google.protobuf.Timestamp at = 3; }
message UploadSummary { int32 accepted = 1; int32 rejected = 2; }
message ChatMessage   { string from = 1; string text = 2; }

The single most important thing to understand about Protobuf is this: field names never go on the wire, only field numbers and a 3-bit wire type. A message is a sequence of (field number, wire type) → value pairs. The decoder looks up each number in its own copy of the schema. That is what makes schema evolution possible, and it's also exactly how you corrupt data silently if you reuse a number.

Schema evolution: the rules, and what breaks when you ignore them

Producers and consumers deploy at different times, so for a while an old reader will decode a new writer's bytes, and vice versa. Encode a v1 Order below, then decode it with a changed schema. Try the safe changes first (rename, add a field, delete with reserved, widen int32 to int64), then the dangerous ones (renumber, reuse a number with the same wire type, change a type).

The "reuse 3 as int64 discount_cents" case is the nightmare: nothing fails. Old messages carrying qty = 2 are read as a two-cent discount. No exception, no log line, just wrong data in production. That is why reserved exists.

Safe (wire-compatible)

  • Add a new field with a new number. Old readers skip it; new readers see the default in old messages.
  • Delete a field, and add reserved <n> and reserved "<name>".
  • Rename a field (the wire doesn't care; JSON transcoding and reflection-based code do).
  • Widen int32 → int64, and swap among int32/uint32/int64/uint64/bool within limits.
  • Add a value to an enum (readers must handle unknown values: proto3 keeps the number).
  • Turn a single field into a member of a new oneof.

Breaking

  • Change a field's number: the data appears to vanish.
  • Reuse a deleted number for another meaning: silent corruption.
  • Change a field's type across wire types (int64 → string): the field is dropped or the parse fails.
  • Narrow int64 → int32: large values are truncated.
  • Move fields into an existing oneof, or change repeated ↔ scalar for messages.
  • Rename a service or method: its path /shop.Orders/GetOrder is the address.

Let a tool enforce it. buf breaking --against '.git#branch=main' fails CI when a change is wire- or source-incompatible, and buf lint enforces naming rules such as ORDER_STATUS_UNSPECIFIED = 0. Treat the .proto files as a published contract, in their own module or repository, just like an OpenAPI document (see contracts in API design).

The four call types

Every gRPC call, of any type, is one HTTP/2 stream: request headers (:path /shop.Orders/WatchOrder, content-type: application/grpc, grpc-timeout), then zero or more length-prefixed messages in DATA frames, then response headers, response messages, and finally trailers containing grpc-status and grpc-message. The status is in the trailers because a streaming response can fail after it has started sending. That's also why gRPC needs a proxy that forwards HTTP trailers.

Call type Shape Use it for Watch out for
Unary 1 request → 1 response 90% of calls: get, create, update Nothing special; it's a function call with a network in the middle
Server streaming 1 request → N responses Watching changes, large result sets in chunks, progress, LLM token streams Long-lived streams pin a connection to one backend; set keepalives; resume after reconnects
Client streaming N requests → 1 response Uploads, telemetry batching, bulk import with one summary The server can't answer until the client half-closes
Bidirectional N ↔ M, independent Chat, collaborative editing, game state, interactive sessions Ordering within each direction only; you need your own application protocol and flow control discipline

Cancellation is a first-class signal

When the client cancels (user navigates away, deadline fires), the client sends RST_STREAM(CANCEL). The server's call context (ServerCallContext.CancellationToken, Go's ctx.Done(), grpc-java's Context or ServerCallStreamObserver.setOnCancelHandler, Python's cancelled task) fires immediately. Pass it to every database call and outbound call, or the server keeps working for a client that has gone. This is the same lesson as cancellation in async code.

The same service in five stacks

All five generate code from the same .proto. The ecosystems differ in how streaming is expressed: C# uses IAsyncEnumerable and stream writers, Java uses StreamObserver callbacks (or Kotlin coroutines / Reactor with extra libraries), Python's grpc.aio uses async generators, Go uses blocking Send/Recv on a stream object (because goroutines make blocking cheap), and Node uses event emitters.

// ASP.NET Core + Grpc.AspNetCore (the .proto is listed in the .csproj: <Protobuf Include="orders.proto" />)
var builder = WebApplication.CreateBuilder(args);
builder.Services.AddGrpc(o => o.Interceptors.Add<LoggingInterceptor>());
var app = builder.Build();
app.MapGrpcService<OrdersService>();
app.Run();

public sealed class OrdersService(IOrderStore store) : Orders.OrdersBase
{
    public override async Task<Order> GetOrder(GetOrderRequest req, ServerCallContext ctx) =>
        await store.FindAsync(req.Id, ctx.CancellationToken)
        ?? throw new RpcException(new Status(StatusCode.NotFound, $"order {req.Id} not found"));

    public override async Task WatchOrder(WatchOrderRequest req,
        IServerStreamWriter<OrderEvent> stream, ServerCallContext ctx)
    {
        // The token fires when the client cancels or its deadline passes.
        await foreach (var ev in store.WatchAsync(req.Id, ctx.CancellationToken))
            await stream.WriteAsync(ev, ctx.CancellationToken);
    }
}

// grpc-java (protoc + protoc-gen-grpc-java). Spring Boot users: spring-grpc wires this as beans.
public final class OrdersService extends OrdersGrpc.OrdersImplBase {
  private final OrderStore store;
  public OrdersService(OrderStore store) { this.store = store; }

  @Override
  public void getOrder(GetOrderRequest req, StreamObserver<Order> out) {
    store.find(req.getId()).ifPresentOrElse(
        o -> { out.onNext(o); out.onCompleted(); },
        () -> out.onError(Status.NOT_FOUND
            .withDescription("order " + req.getId() + " not found").asRuntimeException()));
  }

  @Override
  public void watchOrder(WatchOrderRequest req, StreamObserver<OrderEvent> out) {
    var serverOut = (ServerCallStreamObserver<OrderEvent>) out;
    Subscription sub = store.watch(req.getId(), out::onNext);   // pushes events as they happen
    serverOut.setOnCancelHandler(sub::close);                   // client left or deadline fired
  }
}

Server server = ServerBuilder.forPort(9090)
    .addService(ServerInterceptors.intercept(new OrdersService(store), new LoggingInterceptor()))
    .build().start();

# grpcio + grpcio-tools (python -m grpc_tools.protoc ... --python_out --grpc_python_out)
import grpc
from shop import orders_pb2 as pb, orders_pb2_grpc as rpc

class OrdersService(rpc.OrdersServicer):
    def __init__(self, store):
        self.store = store

    async def GetOrder(self, request, context: grpc.aio.ServicerContext):
        order = await self.store.find(request.id)
        if order is None:
            await context.abort(grpc.StatusCode.NOT_FOUND, f"order {request.id} not found")
        return order

    async def WatchOrder(self, request, context):
        # An async generator: each yield is one DATA frame. If the client cancels,
        # grpc.aio cancels this task, so the loop stops at the next await.
        async for event in self.store.watch(request.id):
            yield event

async def serve(store):
    server = grpc.aio.server(interceptors=[LoggingInterceptor()])
    rpc.add_OrdersServicer_to_server(OrdersService(store), server)
    server.add_insecure_port("[::]:50051")          # TLS: add_secure_port(..., grpc.ssl_server_credentials(...))
    await server.start()
    await server.wait_for_termination()

# Client
async def track():
    async with grpc.aio.secure_channel("orders:50051", grpc.ssl_channel_credentials()) as ch:
        stub = rpc.OrdersStub(ch)
        order = await stub.GetOrder(pb.GetOrderRequest(id=42), timeout=2.0)

// google.golang.org/grpc (protoc-gen-go + protoc-gen-go-grpc)
type ordersServer struct {
    shoppb.UnimplementedOrdersServer // forward compatibility: new RPCs return Unimplemented
    store OrderStore
}

func (s *ordersServer) GetOrder(ctx context.Context, req *shoppb.GetOrderRequest) (*shoppb.Order, error) {
    o, err := s.store.Find(ctx, req.GetId())
    if errors.Is(err, ErrNotFound) {
        return nil, status.Errorf(codes.NotFound, "order %d not found", req.GetId())
    }
    return o, err
}

func (s *ordersServer) WatchOrder(req *shoppb.WatchOrderRequest,
    stream grpc.ServerStreamingServer[shoppb.OrderEvent]) error {
    for ev := range s.store.Watch(stream.Context(), req.GetId()) { // channel closes when ctx is done
        if err := stream.Send(ev); err != nil {
            return err
        }
    }
    return stream.Context().Err() // nil on normal end; Canceled / DeadlineExceeded otherwise
}

Deadlines and cancellation propagation

A timeout is "give up after 2 seconds"; a deadline is "give up at 10:00:02.000". The difference matters as soon as calls chain. gRPC sends the remaining time in the grpc-timeout header, and each server turns it back into an absolute deadline. If the server passes that same deadline to its own outbound calls, the whole chain gives up together. If each hop invents a fresh timeout, downstream services keep working long after the original caller has gone.

Run the three strategies below: a gateway calls Orders, which calls Inventory, which calls Pricing. The defaults (1000 ms budget, Pricing slow at 900 ms) show the difference: propagating the deadline stops everything at 1000 ms with no wasted work; fresh per-hop timeouts waste 750 ms of server time on an answer nobody will read; no timeouts at all means the user waits 1300 ms (or forever, if Pricing hangs).

// Inside a gRPC handler: pass the incoming deadline and token to outbound calls.
public override async Task<Order> GetOrder(GetOrderRequest req, ServerCallContext ctx)
{
    var stock = await _inventory.CheckAsync(new CheckRequest { Id = req.Id },
        deadline: ctx.Deadline, cancellationToken: ctx.CancellationToken);
    // ...
}

// Or let the client factory do it for every call made inside a gRPC request:
builder.Services.AddGrpcClient<Inventory.InventoryClient>(o => o.Address = new("https://inventory"))
    .EnableCallContextPropagation();

// grpc-java propagates automatically: the incoming deadline lives in io.grpc.Context,
// and stubs called from that Context inherit it. Just don't detach from it:
Context.current().getDeadline();                 // what's left of the caller's budget
var stock = inventoryStub.check(CheckRequest.newBuilder().setId(req.getId()).build());

// Careful: work handed to another executor loses the Context unless you wrap it:
executor.execute(Context.current().wrap(() -> callPricing()));

Deadline anti-patterns

  • No deadline at all. The default in most gRPC clients is infinite. One hung dependency then holds a connection, a thread or task, and memory for ever. Every client call needs a deadline.
  • Retrying DEADLINE_EXCEEDED with the same budget. The caller has already given up. Retries belong to the outermost layer, with a fresh budget, and only for idempotent calls; see resilience.
  • Losing the context. Starting a background task, a new thread or a fire-and-forget call drops the deadline and the cancellation. That's sometimes what you want (send an email even if the user leaves), but it should be a deliberate choice.

gRPC in production: load balancing, proxies and the browser

Three things surprise teams the first time they put gRPC behind real infrastructure.

1. Load balancing. A gRPC client opens one long-lived HTTP/2 connection and multiplexes everything over it. An L4 (TCP) load balancer balances connections, so every request from that client lands on the same backend, and new pods get no traffic until clients reconnect. Fix it with an L7 proxy that balances requests (Envoy, Linkerd, Istio, YARP, nginx with grpc_pass), or client-side balancing (dns:///orders plus a round_robin policy, or xDS). Also set MaxConnectionAge on servers so clients periodically reconnect and rebalance.

2. Browsers. Browser JavaScript can't control HTTP/2 framing or read trailers, so it can't speak native gRPC. There are three ways around that:

  • grpc-web: a variant protocol that browsers can speak, translated by Envoy, YARP, or in-process with ASP.NET Core's app.UseGrpcWeb() plus .EnableGrpcWeb(). Client and server streaming are limited (no client streaming from browsers).
  • Connect (connectrpc.com): a protocol and a family of libraries (Go, TypeScript, Kotlin, Swift) that serve gRPC, grpc-web and a simple POST-JSON protocol from the same handler. curl -d '{"id":42}' -H 'content-type: application/json' https://api/shop.Orders/GetOrder just works.
  • JSON transcoding: annotate the RPC and get a REST endpoint for free. ASP.NET Core: builder.Services.AddGrpc().AddJsonTranscoding(). Go: grpc-gateway. Envoy: the grpc_json_transcoder filter.

3. Operating it. You can't curl a binary protocol. Turn on server reflection in non-production environments and use grpcurl or Postman; implement the standard grpc.health.v1.Health service so Kubernetes probes and load balancers can check you; raise the 4 MB default maximum message size only deliberately (stream big payloads instead); and configure HTTP/2 keepalive pings so idle streams through NATs and load balancers aren't silently dropped.

gRPC is a good fit when

  • You own both ends (service-to-service inside your platform), and several languages need the same contract.
  • Calls are frequent and small, and JSON parsing or header overhead shows up in profiles.
  • You need streaming in either direction, with flow control, deadlines and cancellation built in.
  • Not when the consumer is a third party with curl, when you need HTTP caching at a CDN, or when a team can't run L7 load balancing.

How a query executes: a tree of resolvers

The server parses and validates the query against the schema (unknown fields, wrong argument types and missing variables are rejected before anything runs). Then it walks the query tree, calling a resolver function for every field of every object. A resolver receives its parent object and returns the field's value. Scalars resolve trivially from the parent; relationships (customer, items, product) usually hit a database or another service.

The N+1 problem, and DataLoader

That's the classic N+1 query problem (1 query for the list, then N more, one per row), which GraphQL makes structural: resolvers are deliberately independent, so the natural implementation of Order.customer is "look up this order's customer", and it runs once per order. The ORM version of the same bug is explained, with its own visualizer, in anti-patterns and data access.

The fix is DataLoader: instead of fetching, a resolver calls loader.load(key), which returns a promise and remembers the key. When the current level of resolvers has finished queuing keys (the end of the event-loop tick in JavaScript; a scheduler hook in other runtimes), the loader calls your batch function once with all the distinct keys: SELECT … WHERE id IN (…). It also caches per request, so the same customer appearing on three orders is fetched once.

With the defaults (4 orders, 2 items each, 2 distinct customers, 3 distinct products) naive resolvers make 17 queries; DataLoader makes 4: one per level of the tree, regardless of how many rows. Increase the order count to 50 and naive grows to hundreds while the loader stays at 4.

Three DataLoader rules that every implementation shares

  • One loader instance per request. The cache isn't a shared cache; it holds data fetched with this user's permissions. A singleton loader leaks one user's data to another and never sees updates. (For cross-request caching, see caching.)
  • The batch function returns results in the same order and the same count as the keys, with null (or an error) for missing keys. Building a dictionary by id and mapping the keys through it is the standard idiom.
  • Batch by the foreign key you have. items is batched by order id (WHERE order_id IN (…), then grouped), not by item id.

Query cost: one request can ask for a million rows

The flexibility that makes GraphQL pleasant also makes it easy to abuse. A REST endpoint has a fixed cost; a GraphQL query's cost is chosen by the client. Nested lists multiply: 50 customers × 20 orders × 10 items is 10,000 product lookups from a 90-byte query. Because the query is parsed and validated before execution, the server can compute the cost first and refuse expensive queries with no work done.

The analyser below parses a GraphQL subset, multiplies list sizes by their first: arguments, and checks the depth and node count against limits. The default query costs 11,050 nodes at depth 5, so a 5,000-node limit rejects it. Edit the query or the limits and step through the scoring.

Persisted queries: smaller requests, CDN caching, and an allowlist

GraphQL requests are usually POSTs with the full query text in the body, so nothing caches them and anyone can send any query. Persisted queries replace the text with a hash.

  • APQ saves bandwidth and enables GET + CDN caching, but any client can still register any query.
  • Trusted documents / persisted operations (Relay's persisted queries, Apollo's operation manifests, HotChocolate's persisted operations) extract every query from the client code at build time. In production the server accepts only those hashes. For a first-party API, this removes most of the abuse surface, and cost limits become a second line of defence.

Caching, errors and other differences from REST

  • HTTP caching mostly disappears. One URL, POST, and every response is a different shape. Caching moves to the client (Apollo Client and Relay normalise objects by __typename + id), to persisted GETs, and to the server's resolvers and loaders. If CDN caching of public data is your scaling strategy, that's a strong vote for REST.
  • Errors are data. Responses are 200 with an errors array and partial data. Monitoring that counts 5xx sees nothing. Instrument the errors array, and model expected business errors as typed results (PlaceOrderPayload.errors: [UserError!]! or a union such as Order | OutOfStock) instead of top-level errors.
  • Versioning is replaced by evolution. Add fields freely; mark old ones @deprecated(reason: "use totalMoney"); track field usage before removing anything. It's the same compatibility discipline as API design, applied per field.
  • Subscriptions carry the same selection set over a WebSocket (the graphql-ws protocol) or SSE. They need the same scaling machinery as any real-time connection.
  • Federation composes one graph from many services' subgraphs (Apollo Federation, HotChocolate Fusion, WunderGraph Cosmo). It's an organisational tool for many teams sharing one graph; see distributed architecture.

GraphQL earns its cost when

  • Several clients (web, iOS, Android, partners) need different slices of the same rich, connected data.
  • Screens compose data from many sources, and round trips on mobile networks dominate latency.
  • You want one strongly typed, introspectable contract and client codegen across teams.
  • A backend-for-frontend would otherwise be hand-written per client.

Prefer REST or gRPC when

  • The API is simple CRUD or one client: GraphQL adds a server runtime, cost analysis and loaders for nothing.
  • Public data that should be HTTP-cached at the edge.
  • Server-to-server calls with fixed shapes (gRPC is faster and simpler).
  • File uploads and downloads, or bulk exports (use plain HTTP endpoints next to the graph).
  • The team hasn't budgeted for N+1 prevention, query limits and per-field authorization.

SSE in five stacks

The protocol is tiny: respond with Content-Type: text/event-stream, then write id:, event: and data: lines, each event ending with a blank line. Disable response buffering and compression for that route, send a comment line (: ping) every 15–30 seconds so proxies don't close idle connections, and use Last-Event-ID to replay what the client missed.

  req.on("close", () => { clearInterval(ping); unsubscribe(); });
});

WebSockets, SignalR and Socket.IO

A WebSocket starts as an HTTP request with Upgrade: websocket; after the 101 Switching Protocols response, the TCP connection carries framed messages in both directions with no HTTP semantics at all. That means no status codes, no retries, no request ids, no auth per message: you design that application protocol yourself. Raw WebSocket libraries are System.Net.WebSockets (ASP.NET Core), Spring's WebSocketHandler, FastAPI's WebSocket, github.com/coder/websocket in Go, and ws in Node.

Most teams should use a library that adds the missing layer:

  • SignalR (.NET, with JavaScript, Java and Swift clients): hubs with typed method calls, groups, automatic transport fallback (WebSocket → SSE → long polling), reconnection, and a scale-out backplane (Redis or Azure SignalR Service).
  • Socket.IO (Node, with many clients): rooms, acknowledgements, reconnection, and a Redis adapter for scale-out. It's its own protocol, so a plain WebSocket client can't talk to it.
  • Spring STOMP over WebSocket: a pub/sub messaging protocol with destinations, optionally relayed to a broker.

Real-time war stories

  • "SSE works locally but events arrive in bursts in production." A reverse proxy (nginx, an API gateway) or response compression is buffering the stream. Turn off buffering for that route (X-Accel-Buffering: no, proxy_buffering off) and don't gzip event streams.
  • Reconnect storms. A deploy drops 50,000 sockets, all clients reconnect in the same second, and the new pods fall over. Add jittered reconnect delays on clients and drain connections gradually.
  • Lost events during a reconnect. Without event ids and a replay buffer, anything published while a client was reconnecting is gone. SSE's Last-Event-ID is the protocol for this; with WebSockets you must build it.
  • Authorization only at connect time. A socket opened at 9:00 is still open at 17:00, after the user's permissions were revoked. Re-check periodically, or close sockets when tokens expire.
  • HTTP/1.1 connection limits. Browsers allow about six connections per host on HTTP/1.1, and each SSE stream holds one. Serve SSE over HTTP/2, or share one stream across tabs.

Webhooks: push to servers you don't control

A webhook is an HTTP POST that your system sends to a URL that a customer registered: "tell me when an order ships". It's the server-to-server answer to polling. It's simple to send and hard to send well, because the receiver is someone else's code on someone else's network. They will be down, slow, and occasionally attacked.

The simulator follows one event through delivery. Pick a scenario: a receiver that's down, a slow receiver that times out (so the provider retries an event that was actually processed), a body tampered with in transit, or an old request replayed by an attacker. The HMAC is computed for real, so change the secret and watch the signature change. Then flip deduplication on and off in the slow-receiver scenario.

1 · SIGNHMAC over id + timestamp + body

Shared secret per endpoint; the timestamp is inside the signature so it can't be swapped.

2 · DELIVERPOST, short timeout

2xx = done. Anything else, or no answer within ~10 s, is a failure.

3 · RETRYExponential backoff for days

Then disable the endpoint and tell its owner. Offer a manual replay.

4 · RECEIVEVerify, dedupe, enqueue, 200

Do the real work asynchronously; delivery is at-least-once.

Webhook delivery is at-least-once: receivers must be idempotent

A timeout doesn't mean "not processed"; it means "don't know". The provider must retry, so the receiver will sometimes get the same event twice. Store each processed webhook-id (with a unique constraint, in the same transaction as the side effect) and answer duplicates with 200. This is the same idea as idempotency keys, with the roles reversed.

Use the Standard Webhooks conventions (webhook-id, webhook-timestamp, webhook-signature: v1,<base64 HMAC-SHA256 of "id.timestamp.body">) rather than inventing a scheme. Verification must use the raw body bytes (re-serialising parsed JSON changes whitespace and breaks the signature) and a constant-time comparison.

// ASP.NET Core minimal API
app.MapPost("/webhooks/orders", async (HttpRequest req, IWebhookInbox inbox) =>
{
    using var ms = new MemoryStream();
    await req.Body.CopyToAsync(ms);
    var body = ms.ToArray();
    string id = req.Headers["webhook-id"]!, ts = req.Headers["webhook-timestamp"]!;
    if (Math.Abs(DateTimeOffset.UtcNow.ToUnixTimeSeconds() - long.Parse(ts)) > 300) return Results.BadRequest();

    var signed = Encoding.UTF8.GetBytes($"{id}.{ts}.").Concat(body).ToArray();
    var expected = Encoding.UTF8.GetBytes("v1," + Convert.ToBase64String(HMACSHA256.HashData(secret, signed)));
    var ok = req.Headers["webhook-signature"].ToString().Split(' ')     // may hold several (key rotation)
        .Any(s => CryptographicOperations.FixedTimeEquals(Encoding.UTF8.GetBytes(s), expected));
    if (!ok) return Results.Unauthorized();

    await inbox.AddIfNewAsync(id, body);   // unique key on id; a duplicate is a no-op
    return Results.Ok();                   // the real work happens in a background consumer
});

// Spring MVC: take the raw body as byte[]
@PostMapping("/webhooks/orders")
ResponseEntity<Void> receive(@RequestHeader("webhook-id") String id,
                             @RequestHeader("webhook-timestamp") long ts,
                             @RequestHeader("webhook-signature") String sigHeader,
                             @RequestBody byte[] body) throws Exception {
  if (Math.abs(Instant.now().getEpochSecond() - ts) > 300) return ResponseEntity.badRequest().build();
  Mac mac = Mac.getInstance("HmacSHA256");
  mac.init(new SecretKeySpec(secret, "HmacSHA256"));
  mac.update((id + "." + ts + ".").getBytes(StandardCharsets.UTF_8));
  byte[] expected = ("v1," + Base64.getEncoder().encodeToString(mac.doFinal(body))).getBytes(StandardCharsets.UTF_8);
  boolean ok = Arrays.stream(sigHeader.split(" "))
      .anyMatch(s -> MessageDigest.isEqual(s.getBytes(StandardCharsets.UTF_8), expected));
  if (!ok) return ResponseEntity.status(401).build();
  inbox.addIfNew(id, body);
  return ResponseEntity.ok().build();
}

func receive(w http.ResponseWriter, r *http.Request) {
    body, err := io.ReadAll(http.MaxBytesReader(w, r.Body, 1<<20))
    if err != nil {
        http.Error(w, "too large", http.StatusRequestEntityTooLarge)
        return
    }
    id, ts := r.Header.Get("webhook-id"), r.Header.Get("webhook-timestamp")
    sec, err := strconv.ParseInt(ts, 10, 64)
    if err != nil || math.Abs(float64(time.Now().Unix()-sec)) > 300 {
        http.Error(w, "stale", http.StatusBadRequest)
        return
    }
    mac := hmac.New(sha256.New, secret)
    mac.Write([]byte(id + "." + ts + "."))
    mac.Write(body)
    expected := []byte("v1," + base64.StdEncoding.EncodeToString(mac.Sum(nil)))
    ok := false
    for _, s := range strings.Fields(r.Header.Get("webhook-signature")) {
        ok = ok || hmac.Equal([]byte(s), expected) // constant-time
    }
    if !ok {
        http.Error(w, "bad signature", http.StatusUnauthorized)
        return
    }
    _ = inbox.AddIfNew(r.Context(), id, body)
    w.WriteHeader(http.StatusOK)
}

Async APIs: messaging and AsyncAPI

Webhooks push events to the outside world. Inside your platform, the same decoupling is usually done with a message broker: the producer publishes OrderPlaced to a topic and moves on; any number of consumers (billing, email, analytics) subscribe independently, at their own pace, even if they're down when it's published.

AsyncAPI is OpenAPI's sibling for event-driven APIs: it documents channels, operations and message schemas, and generates docs and code the same way.

          type: object

Event schemas evolve under the same rules as Protobuf (add optional fields; never change meaning). Kafka shops usually enforce them with a schema registry (Avro or Protobuf), which rejects incompatible producer schemas before they can break consumers. CloudEvents standardises the envelope (id, source, type, time) across brokers and webhooks.

Serialization formats: JSON, Protobuf, MessagePack, Avro

The protocol decides how messages move; the format decides what the bytes look like. Encode the same product four ways below and watch where the bytes go: JSON repeats every field name as text in every message; MessagePack keeps the names but encodes them in binary; Protobuf replaces names with field-number tags; Avro writes no tags at all, because the reader must already have the writer's schema.

Measured on this machine (Python 3.11, 1,000 messages of the same product with three tags; json, msgpack, protobuf with the upb backend, fastavro schemaless):

Format Bytes / message Encode Decode Schema Human-readable
JSON 104 4.1 µs 5.3 µs optional (JSON Schema) yes
MessagePack 78 1.9 µs 1.0 µs none no
Protobuf 49 0.4 µs 0.6 µs required, tags on the wire no (protoc --decode)
Avro 44 4.6 µs 3.7 µs required, writer's schema needed to read no

Read benchmarks as orders of magnitude, not rankings

The library matters more than the format: fastavro pays per-message Python overhead here, while Avro in Java is fast; System.Text.Json source-generated serializers come close to binary formats; compression (gzip, Brotli, zstd) shrinks JSON's repeated keys dramatically for larger payloads. The robust conclusions are: binary formats are 2–4× smaller for small records; schema-based formats are safer to evolve; and JSON wins on debuggability and reach. Measure with your own payloads before switching. See performance patterns and memory and GC for allocation-free serialization.

Common pitfalls

Pitfalls across protocols

  • Choosing by hype. Rewriting a simple CRUD API in GraphQL or gRPC adds a runtime, codegen and new failure modes for no user benefit. Start from the caller and the data flow.
  • gRPC behind an L4 load balancer. All traffic from a client goes to one pod. Use L7 or client-side balancing, and set MaxConnectionAge.
  • Missing deadlines. gRPC's default is no deadline. Every outbound call needs one, propagated from the incoming request.
  • Reusing Protobuf field numbers. Silent corruption. Delete with reserved, and run buf breaking in CI.
  • GraphQL without DataLoader or limits. N+1 makes it slow; unbounded nesting makes it a denial-of-service endpoint.
  • A shared DataLoader across requests. One user's data appears in another user's response.
  • Buffered SSE. A proxy or compression middleware holds events; nothing looks wrong until production.
  • WebSockets without reconnect, resume or backplane. Works with one server and a perfect network; loses events everywhere else.
  • Webhooks verified against re-serialised JSON, compared with ==, without a timestamp window, or processed synchronously before returning 200.
  • Non-idempotent consumers. Webhooks and message brokers deliver at least once. Duplicates will happen.

Before you ship a non-REST API

  • [ ] The choice is justified by the caller and data flow (the decision tree), and documented in an ADR.
  • [ ] gRPC: .proto in a shared module; buf lint and buf breaking in CI; deadlines on every call and propagated; status codes mapped deliberately; health service, reflection in non-prod, L7 load balancing, keepalives, message size limits.
  • [ ] GraphQL: per-request DataLoaders for every relationship; depth and cost limits; first required with a maximum; trusted documents for first-party clients; per-field authorization; errors monitored.
  • [ ] Real-time: SSE unless clients stream; heartbeats; event ids with replay; jittered reconnects; backplane for more than one server; authorization re-checked for long-lived connections.
  • [ ] Webhooks: Standard Webhooks headers; HMAC over id, timestamp and raw body; 5-minute tolerance; constant-time comparison; retries with backoff for days; receivers dedupe on webhook-id; SSRF-safe sender.
  • [ ] Messaging: AsyncAPI document; schema registry or contract tests; idempotent consumers; outbox for publishing (see distributed architecture).
  • [ ] Security applies to all of them: TLS, authentication, rate limits and input limits, per API security. Traces flow across every hop, per observability.

Self-check

HTTP/2 multiplexes requests on one connection. Why can it still be slower than HTTP/1.1 on a lossy mobile network?

TCP delivers bytes in order. When one packet is lost, every byte after it waits in the receive buffer until the retransmission arrives, including frames from other streams that arrived fine. All multiplexed streams stall together. Six HTTP/1.1 connections each stall independently. HTTP/3 fixes this because QUIC orders bytes per stream, not per connection.

You delete the field int32 qty = 3 and later add int64 discount_cents = 3. What happens, and how do you prevent it?

Both are varints, so old messages decode without any error: their qty values are read as discounts. It's silent data corruption. When deleting a field, add reserved 3; and reserved "qty"; so the compiler rejects reuse, and run buf breaking in CI.

A gateway gives a request 1 s. Orders calls Inventory with its own 2 s timeout. What's wrong?

Inventory keeps working for up to a second after the user has received a timeout: wasted capacity exactly when the system is slow, which is when you can least afford it. Pass the incoming deadline (not a fresh timeout) to outbound calls: ctx in Go, ctx.Deadline / EnableCallContextPropagation in .NET, Context in grpc-java, time_remaining() in Python, parent: call in grpc-js.

A GraphQL query for 50 orders with their customers makes 51 SQL queries. Fix it without changing the schema.

Resolve Order.customer through a per-request DataLoader keyed by customer id. All 50 load(id) calls in the same level are collected and the batch function runs once: SELECT … WHERE id IN (…), returning results in key order. That's 2 queries in total, and repeated customers are fetched once.

The UI needs live order status. Your colleague proposes WebSockets. What do you ask, and what would you probably choose?

Does the client send a stream of messages too, or does it only receive? Status updates flow server → client; the client's actions are ordinary POSTs. SSE gives that over plain HTTP with automatic reconnection and Last-Event-ID resume, and far less infrastructure. Use WebSockets only for genuinely bidirectional, high-frequency traffic.

Your webhook receiver charges a card, then returns 200. Sometimes customers are charged twice. Why, and what's the fix?

Charging took longer than the provider's timeout, so the provider marked the delivery failed and retried the same event. Fix: verify, store the webhook-id with a unique constraint (in the same transaction as the work, or in an inbox table), return 200 quickly, process asynchronously, and treat a duplicate id as already done.

Why is the gRPC status sent in trailers rather than the HTTP status line?

A streaming response may fail after it has started sending messages, when the :status 200 headers are already gone. Trailers come at the end of the stream, so they can report the final outcome. That's also why gRPC needs proxies that forward HTTP/2 trailers, and why browsers need grpc-web, which moves the trailers into the body.
