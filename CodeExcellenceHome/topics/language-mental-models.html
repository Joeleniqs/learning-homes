FOUNDATIONS OF CRAFT

Cross-Language Mental Models

Value vs reference, stack vs heap, generics, closures, interfaces vs traits vs duck typing, and nullability, compared across C#, Java, Python, Go and TS.

Beginner → Advanced~60 min studyUpdated 2026-11-03

The problem: one line, five languages, five behaviours

You know how to write a loop, call a function and compare two values. The trouble starts when you move between languages. Each line below looks harmless, and each one caused a real production bug when someone carried the mental model from a language they knew into a language they didn't.

Language The line that looked fine What actually happened The model that was missing
Go head := items[:2]; head = append(head, fee) It overwrote items[2], because head shares the backing array and had spare capacity. Argument passing and slices
Java if (order.getQty() == other.getQty()) with Integer true in tests (qty 5), false in production (qty 500): == compares references and only −128..127 are cached. Equality
Python def add(item, bucket=[]): Every call shares one list, created when the def ran. Scope and closures
C# var p = points[0]; p.X = 5; on a List<Point> of structs Nothing changed in the list: a struct is copied out on read. What a variable holds
TypeScript if (!order.discount) applyDefault() A deliberate discount of 0 was treated as "missing" because 0 is falsy. Nullability

None of these are obscure. They come from six questions every language answers in its own way. Learn those answers once per language and the "weird" behaviour becomes predictable.

Rule. Before you trust a line of code in an unfamiliar language, answer six questions: when is it checked and compiled, what does a variable hold (a value or a reference), what does passing it copy, what does == compare, what does a closure capture, and can this be null.

This page is about the fundamentals that sit underneath everything else in this home. It keeps each idea at the level you need to read and write code in all five languages. Deeper dives live in their own topics: Memory, Allocation & GC for the heap and the collector, Concurrency & Async for threads and event loops, Functional Patterns for Option/Result and pattern matching, and Types, Immutability & Domain Modelling for using the type system as a design tool.

From source to running code: compiled, interpreted, JIT

"Compiled vs interpreted" is too coarse to be useful. All five languages compile something. What differs is what the compiler produces, when machine code is created, and how much the runtime learns while your program runs. Those three facts explain startup time, peak speed, how big your deployment is, and why your benchmark lied to you on the first run.

The middle languages (C#, Java, JavaScript) use tiered compilation. A method starts in a cheap form: an interpreter or a quick, unoptimized JIT. The runtime counts calls and loop iterations, and records which types actually flow through. When a method is hot, it recompiles it with aggressive optimizations based on that profile: inlining, devirtualization, register allocation. If an assumption breaks later, for example a + that has only seen integers suddenly gets a float, a speculative engine (V8, HotSpot C2) deoptimizes back to the slow tier and tries again. CPython 3.11+ does a lighter version of the same trick inside its interpreter: it rewrites a generic BINARY_OP into a specialized BINARY_OP_ADD_INT after a few calls, and falls back if a float arrives.

Run the simulation. Pick a language, set how many calls the hot function receives, and optionally make floats arrive from some call onwards. Watch the tier ladder, the per-call cost and the deoptimization events.

Insight JIT languages pay for speed with warm-up. The first few thousand calls of a .NET, Java or Node service are slower than the steady state, which is why a benchmark that runs a method ten times measures the interpreter, and why a freshly deployed pod can breach its latency SLO before it has warmed up. Use BenchmarkDotNet, JMH, pyperf and testing.B because they run warm-up iterations for you. Go has no JIT, so it pays nothing for warm-up, but it also can't optimize based on what your program does at run time unless you feed it a profile (PGO).

Ahead-of-time (Go, .NET Native AOT, GraalVM native-image)

Fast startup, small memory, single file to deploy. Good for CLIs, serverless and sidecars. You give up some reflection and dynamic code loading, and there is no run-time profile to optimize from.

Tiered JIT (.NET, JVM, V8)

Best long-run throughput because the compiler sees real types and real hot paths. Costs warm-up time and memory for the compiler itself. Good for long-lived services.

Bytecode interpreter (CPython)

Simple, portable and dynamic; the slowest per operation. Put the hot loops in C-backed libraries (NumPy, pandas, str.join) or move them to a compiled service. Don't fight it with micro-optimizations.

What this means when you write code:

  • TypeScript types do not exist at run time. if (x instanceof User) works only for classes; an interface can't be checked at run time. Validate untrusted JSON with a schema library (zod, valibot) rather than casting with as.
  • Python is checked when a line runs. A typo in an error-handling branch is invisible until that branch fires. Run mypy/pyright in CI, as shown in the typing visualizer below.
  • C# and Java check at compile time, but reflection and casts move checks to run time. (Customer)obj throws InvalidCastException or ClassCastException. Prefer pattern matching (obj is Customer c, obj instanceof Customer c).
  • Go's binary contains everything. That's why Go containers can start FROM scratch. It also means a library upgrade requires a rebuild; there's no shared runtime to patch.

Typing: static vs dynamic, nominal vs structural

Two independent questions hide behind "is this language strongly typed?":

  1. When are types checked? Static: before the program runs (compiler or checker). Dynamic: when the line executes.
  2. How does a type qualify? Nominal: it must declare the relationship (class Duck : IQuacker). Structural: it qualifies if it has the right shape (the methods and fields), whatever it is called.

The visualizer below runs four classic scenarios through five type checkers. Each scenario is a rule engine: it looks at what the code declares and what shape it has, then reports exactly what each language says and when it says it. Turn mypy on to see Python move from the bottom-right square to the top-right one.

Interfaces vs traits vs duck typing

All five languages let you write code against "something that can do X". They differ in who declares the relationship, when it's checked, and whether you can retrofit a type you don't own.

Who declares it Checked Retrofit a type you don't own? Default method bodies Typical dispatch
C# interface the implementing class compile no: write an adapter (extension methods don't satisfy interfaces) yes (C# 8+) virtual call; generic constraints let the JIT devirtualize
Java interface the implementing class compile no: adapter or lambda for functional interfaces yes (default, Java 8+) virtual call; HotSpot inlines monomorphic sites
Go interface nobody: implicit compile yes: define a small interface where you consume it no itab lookup at run time
TS interface / type nobody: structural compile, then erased yes, any value with the shape n/a (types only) ordinary JS property lookup
Python Protocol nobody (Protocol) or the class (ABC) by mypy/pyright only yes yes on ABCs attribute lookup at run time
Rust trait (for reference) an explicit impl Trait for Type compile yes, if you own the trait or the type yes static (generics) or dynamic (dyn Trait)

Nominal (C#, Java)

Intent is explicit and searchable: "find all implementations" works. Unrelated types can't satisfy an interface by coincidence. The cost: you need an adapter for third-party types, and interfaces tend to be defined by the provider and grow large.

Structural (Go, TS, Python Protocol)

Interfaces belong to the consumer: define the two methods you need, right where you need them, and anything that fits works, including types from other libraries. Go's proverb: "accept interfaces, return structs". The cost: accidental matches, and "who implements this?" needs a tool.

Duck typing (plain Python, JS)

Maximum flexibility and zero ceremony. Every mistake is a run-time error, so it only scales with tests and, in practice, a type checker. Treat Protocols as duck typing that your CI can verify.

Tip Structural typing can't tell a Celsius from a Fahrenheit if both are number. Go solves this with named types (type Celsius float64), TypeScript with branded types, C# and Java with small record types. That technique, and why it matters for IDs and money, is covered in Types, Immutability & Domain Modelling.

What a variable holds: values and references

A variable is a named slot. The question is what goes in the slot: the data itself (a value), or the address of data that lives somewhere else (a reference). Assignment, argument passing, equality and thread safety all follow from that one fact.

Language Value semantics (assignment copies the data) Reference semantics (assignment copies the arrow) Your own value type
C# int, double, bool, decimal, DateTime, enums, struct, record struct, tuples class, record, string, arrays, List<T>, delegates readonly record struct Money(decimal Amount, string Currency)
Java the 8 primitives: int, long, double, boolean, char, byte, short, float everything else, including Integer, String, arrays and records none yet (Project Valhalla); records are immutable references
Python none: every name refers to an object everything; int, str, tuple and frozenset are immutable, so they behave like values @dataclass(frozen=True) behaves like a value
Go everything: numbers, structs, arrays [3]int pointers *T; slices, maps, channels and funcs are small values that contain pointers any struct
TypeScript number, string, boolean, bigint, symbol, null, undefined objects, arrays, functions, class instances none; use readonly and spread copies

Insight "Stack vs heap" is an implementation detail; "value vs reference" is a semantic one. C# and Java move references to the stack when escape analysis proves an object doesn't outlive the method, and Go's compiler puts a struct on the heap if its address escapes. Reason about semantics (copy the data or share it?) and let the profiler tell you about placement.

The difference shows up the moment you read an element out of a collection and modify it:

public struct PointS { public int X, Y; }
public class PointC { public int X, Y; }

var structs = new List<PointS> { new() { X = 1 } };
var p = structs[0];   // the indexer returns a COPY of the struct
p.X = 5;              // modifies the copy only
// structs[0].X = 5;  // error CS1612: cannot modify the return value because it is not a variable
Console.WriteLine(structs[0].X);   // 1
structs[0] = p;                    // fix: write the copy back (or use an immutable record struct + with)

var classes = new List<PointC> { new() { X = 1 } };
var c = classes[0];   // copies the reference
c.X = 5;
Console.WriteLine(classes[0].X);   // 5

// Java has no user-defined value types (yet), so every element is shared.
record Point(int x, int y) {}             // immutable: no setter to misuse
class MutablePoint { int x, y; }

var points = new ArrayList<MutablePoint>(List.of(new MutablePoint()));

p.x = 5;
System.out.println(points.get(0).x);   // 5: same object

var recs = new ArrayList<>(List.of(new Point(1, 2)));
recs.set(0, new Point(5, recs.get(0).y()));   // records: replace, don't mutate

Argument passing: everything is a copy of something

Here is the rule that removes most of the confusion: in all five languages, a normal parameter receives a copy of the caller's variable. If the variable holds a value, the callee gets a copy of the value. If it holds a reference, the callee gets a copy of the reference: a second arrow to the same object. Java and Python people call this pass by value and call by sharing; the behaviour is identical.

That gives the callee exactly two things it can try, and they behave very differently:

The simulation below runs a small bump(p) function that mutates, reassigns, then mutates again, for 14 language/type combinations. Each step draws the stack frames and heap, and the "visible to caller" variable is computed from the arrows, not looked up. Try the Go slice cases in particular: the same code gives different answers depending on spare capacity.

static void Bump(List<int> items, ref int count, PointS point)
{
    items.Add(4);          // mutation through a copied reference: caller sees it
    items = new List<int>(); // reassigns the local copy only
    count++;               // ref: this IS the caller's variable
    point.X = 99;          // struct passed by value: a private copy
}

var xs = new List<int> { 1, 2, 3 };
int n = 0;
var pt = new PointS();
Bump(xs, ref n, pt);
Console.WriteLine($"{xs.Count} {n} {pt.X}");   // 4 1 0
// 'in' passes a struct by read-only reference (no copy); 'out' must be assigned by the callee.

static void bump(List<Integer> items, int count, int[] box) {
    items.add(4);              // caller sees it
    items = new ArrayList<>(); // local only
    count++;                   // primitive copy: caller does not see it
    box[0]++;                  // the classic workaround: mutate a shared holder
}

var xs = new ArrayList<>(List.of(1, 2, 3));
int n = 0;
int[] box = {0};
bump(xs, n, box);
System.out.println(xs.size() + " " + n + " " + box[0]);   // 4 0 1
// Better than a holder: return a value (or a record with several values).

def bump(items: list[int], count: int) -> int:
    items.append(4)    # mutation through the shared object: caller sees it
    items = []         # rebinds the local name only
    count += 1         # ints are immutable: rebinds the local name only
    return count       # the Pythonic way to "return" a changed value

xs = [1, 2, 3]
n = 0
n = bump(xs, n)
print(len(xs), n)      # 4 1

type Point struct{ X int }

func bump(items []int, count *int, p Point, pp *Point) []int {

    items = append(items, 4) // may or may not reallocate: never rely on the caller seeing this
    *count++                 // pointer: writes the caller's variable
    p.X = 1                  // struct value: private copy
    pp.X = 1                 // pointer: caller sees it
    return items             // idiom: return the slice, the caller reassigns it
}

xs := []int{1, 2, 3}

var a, b Point

function bump(items: number[], count: number, opts: { retries: number }): number {
  items.push(4);       // caller sees it
  items = [];          // local only
  count++;             // numbers are values: local only
  opts.retries = 5;    // caller sees it: objects are shared
  return count;
}

const xs = [1, 2, 3];

console.log(xs.length, n, opts.retries); // 4 1 5

Go slices: a header passed by value

A Go slice is a three-word struct: a pointer to a backing array, a length and a capacity. Passing or slicing it copies the header and shares the array. append writes into the shared array when there is spare capacity, and allocates a new one when there isn't. That's the bug from the top of this page.

Pitfall Mutable default arguments in Python. def add(item, bucket=[]) evaluates [] once, when the def statement runs, so every call without bucket appends to the same list. Use bucket: list | None = None and create the list inside the function. JavaScript/TypeScript default parameters are evaluated on each call, so the same code is safe there, which is exactly why people carry the habit across and get burned.

Equality: same object, or same value?

There are two different questions, and every language gives them different operators:

  • Identity: are these two arrows pointing at the same object?
  • Value (structural) equality: do these two things represent the same value, even if they are separate objects?
Identity Value equality Default for your own class Gotchas
C# ReferenceEquals(a, b) a.Equals(b), == when overloaded class: identity; record/struct: value == is chosen at compile time: object a = s1; a == s2 compares references
Java a == b for objects a.equals(b), Objects.equals(a, b) identity, unless you override equals and hashCode; records: value Integer == works only for −128..127 (cache); BigDecimal("5.0").equals(new BigDecimal("5.00")) is false
Python a is b a == b (calls __eq__) identity; @dataclass: value use is only for None and sentinels; small ints and some strings are cached, so is "works" by accident
Go p == q on pointers a == b for comparable types: field by field structs are compared by value slices, maps and funcs are not comparable (only to nil); use slices.Equal, maps.Equal
TypeScript a === b for objects none built in: write equals() identity == coerces ("0" == 0); NaN !== NaN, use Number.isNaN or Object.is

Equality has a partner: hashing. Hash sets and dictionaries first compare hash codes, then call equality. If two objects are equal they must have the same hash code, or a HashSet will contain "duplicates" and lookups will miss. Records and data classes generate both for you, which is the main reason to use them for values:

public readonly record struct Money(decimal Amount, string Currency);

var a = new Money(5.00m, "EUR");
var b = new Money(5.0m, "EUR");
Console.WriteLine(a == b);                       // True: decimal compares by value, 5.00m == 5.0m
Console.WriteLine(new HashSet<Money> { a, b }.Count);   // 1
// A record (class) also gets value equality; a plain class keeps identity unless you implement IEquatable<T>.

public record Money(BigDecimal amount, String currency) {
    public Money {                                  // compact constructor: normalise once
        amount = amount.stripTrailingZeros();       // so 5.0 and 5.00 are equal
    }
}

var a = new Money(new BigDecimal("5.00"), "EUR");
var b = new Money(new BigDecimal("5.0"), "EUR");
System.out.println(a.equals(b));          // true (false without the normalisation: BigDecimal.equals checks scale)
System.out.println(a == b);               // false: two objects
System.out.println(Set.of(a).contains(b)); // true: records generate equals AND hashCode

from dataclasses import dataclass
from decimal import Decimal

    amount: Decimal

interface Money { readonly cents: number; readonly currency: string }

const a: Money = { cents: 500, currency: "EUR" };
const b: Money = { cents: 500, currency: "EUR" };
console.log(a === b);                       // false: two objects

const equals = (x: Money, y: Money) => x.cents === y.cents && x.currency === y.currency;
console.log(equals(a, b));                  // true

// Map and Set use identity (SameValueZero), so key by a string you build:
const key = (m: Money) => `${m.currency}:${m.cents}`;
const seen = new Set([key(a)]);
console.log(seen.has(key(b)));              // true

Pitfall Mutating an object while it's a key in a hash set. Its hash code changes, it now sits in the wrong bucket, and contains returns false for an object that is visibly in the set. It happens in every language that hashes mutable objects (C#, Java, Python with a custom __hash__). The fix is structural: make keys immutable. Python refuses to hash a plain mutable @dataclass (eq=True sets __hash__ = None) for exactly this reason.

Floating point is not a language quirk. 0.1 + 0.2 == 0.3 is false in all five languages because they all use IEEE 754 doubles. Compare with a tolerance (Math.Abs(a - b) < 1e-9, math.isclose), and use decimal / BigDecimal / Decimal / integer cents for money.

Scope, closures and hoisting

Scope decides which declaration a name refers to. A closure is a function that keeps using variables from the scope where it was created, after that scope has finished. The single most important fact about closures in C#, Python, Go and JavaScript: they capture the variable, not its current value. If the variable changes later, the closure sees the change.

The simulation keeps an explicit environment: every variable is a cell, every closure stores a pointer to the cell it captured. It runs the loop, then calls each closure and reads the cell. Compare C#: for loop with C#: foreach, and Go ≤ 1.21 with Go 1.22+ (the Go team changed loop semantics in 1.22 because this bug was so common).

Closures are how you get private, persistent state without a class. The canonical example is a counter factory:

static Func<int> MakeCounter()
{
    int count = 0;              // hoisted by the compiler into a hidden "display class" on the heap
    return () => ++count;       // the lambda captures the variable, so it can change it
}

var next = MakeCounter();
next(); next();
Console.WriteLine(next());      // 3
// Hot paths: a capturing lambda allocates. 'static () => ...' forbids capture, so the compiler can cache it.

static IntSupplier makeCounter() {
    int[] count = {0};          // captured locals must be effectively final...
    return () => ++count[0];    // ...so mutate a shared holder (or use AtomicInteger) instead
}

IntSupplier next = makeCounter();
next.getAsInt(); next.getAsInt();
System.out.println(next.getAsInt());   // 3
// Java lambdas capture VALUES (copies of final locals). That's why the loop bug can't happen in Java.

def make_counter():
    count = 0
    def next_value():
        nonlocal count          # without this, 'count += 1' makes count local: UnboundLocalError
        count += 1
        return count
    return next_value

next_value = make_counter()
next_value(); next_value()
print(next_value())             # 3

func makeCounter() func() int {
    count := 0 // escapes to the heap because the closure outlives makeCounter
    return func() int {
        count++
        return count
    }
}

next := makeCounter()
next()
next()
fmt.Println(next()) // 3

function makeCounter(): () => number {
  let count = 0;
  return () => ++count;
}

const next = makeCounter();
next(); next();
console.log(next());            // 3

Modules, packages and visibility

Every language has a unit of code organization (a namespace or package) and a unit of compilation or distribution (an assembly, a jar, a module). Visibility rules sit on top of those units, and they're what keep a large code base from becoming one big ball of public classes.

Organize code with Ship / version as Visibility levels Default visibility
C# namespace (any folder layout) assembly (.dll) in a NuGet package public, internal (assembly), protected, private, file internal for types, private for members
Java package (must match folders) .jar; JPMS module-info.java exports packages public, protected, package-private, private; module exports package-private
Python module = file, package = folder distribution (wheel) on PyPI none enforced: _name = "internal by convention", __all__ for import * everything is public
Go package = folder module (go.mod), versioned by git tag capitalisation: Exported vs unexported; internal/ folders unexported (lowercase)
TypeScript ES module = file npm package; exports in package.json export or not; private/#private for class members not exported

Tip Use the narrowest level your language offers. In C#, make classes internal (and sealed) by default and expose an interface or a small public facade. In Go, put implementation packages under internal/ so other modules cannot import them. In Python, prefix implementation modules with _ and keep __init__.py as your public API. In TypeScript, export from an index.ts barrel only what callers need, and enforce it with package.json "exports". Smaller public surfaces are what make refactoring safe.

Generics: reified, erased, stenciled or hints

Generics let you write Max<T> once and use it for every T. How the language implements that decides what you can do with T at run time and what it costs.

The same Max in each language, including the constraint that says "T can be compared":

static T Max<T>(IReadOnlyList<T> items) where T : IComparable<T>
{
    if (items.Count == 0) throw new ArgumentException("Empty list", nameof(items));
    T best = items[0];
    foreach (var x in items)
        if (x.CompareTo(best) > 0) best = x;
    return best;
}

// Generic math (C# 11+): where T : INumber<T> lets you write T.Zero and a + b for any numeric type.

function max<T>(items: readonly T[], compare: (a: T, b: T) => number): T {
  if (items.length === 0) throw new Error("Empty list");
  return items.reduce((best, x) => (compare(x, best) > 0 ? x : best));

Nullability: the billion-dollar mistake, five ways

Tony Hoare called the null reference his "billion-dollar mistake": any reference might secretly be "nothing", and the type system doesn't say which. Modern languages fix this by tracking nullability in the type: string means "never null", string? means "maybe null", and the compiler makes you check before you dereference.

"No value" Tracked by the compiler? Turn it on Safe access Default value
C# null yes, as warnings <Nullable>enable</nullable> (+ WarningsAsErrors nullable) a?.b a ?? d, a ??= d
Java null no JSpecify @Nullable + NullAway or the Checker Framework; Optional<T> for return values Optional.map opt.orElse(d), Objects.requireNonNullElse
Python None by mypy/pyright annotate Optional[User] (or the union with None); run the checker in CI none built in x if x is not None else d
Go nil (pointers, slices, maps, interfaces, channels, funcs) no; other types have zero values instead nilaway (Uber) explicit if p != nil zero values: "", 0, false

Pitfall || and or are not null checks. discount || 10 in TypeScript and discount or 10 in Python replace 0, "" and false too, which is the discount bug from the top of this page. Use ?? in TS and C#, and x if x is not None else d in Python. Go has the mirror-image problem: the zero value 0 is indistinguishable from "not set" unless you use a pointer (*int) or a separate ok flag.

Pitfall Go's nil interface that isn't nil. An interface value is a pair (type, pointer). Returning a typed nil pointer as an error gives (*MyErr, nil), which is not equal to nil, so if err != nil is true and the caller reports an error that doesn't exist. Return a literal nil for "no error", never a typed nil variable.

Null is only one way to say "no value". Option/Maybe types make absence a value you must unwrap, and Result types do the same for failure; both are covered in Functional Patterns, and how errors flow through a system is the subject of Error Handling Strategies.

Pitfall Changing a collection while you iterate it. C# throws InvalidOperationException: Collection was modified, Java throws ConcurrentModificationException, Python raises RuntimeError: dictionary changed size during iteration for dicts but silently skips elements for lists, Go allows it for maps (new keys may or may not be visited), and JavaScript visits entries added to a Map during iteration. Choosing the right tool: when to, and when not to

Each mechanism on this page exists for a reason, and each has a cost. Use this table when you're deciding, not just when you're debugging.

Mechanism Use it when Don't use it when
Value types (C# struct, Go struct values) small (≤ ~16–24 bytes), immutable, value-like data: Money, Point, IDs; you want no aliasing and no allocation it's large (every copy costs), mutable (copies diverge silently), or has identity (an Order that changes over time)
ref/out (C#), pointers to locals (Go) a hot path must avoid copying a large struct (in/ref readonly), or an API like TryParse needs a second result you just want two results: return a tuple / record / (T, error) instead
Mutating a parameter's object the function's name says so (Sort(list), FillDefaults(cfg)) the caller won't expect it. Return a new value instead and keep functions pure, see Functional Patterns
Structural interfaces (Go, TS, Protocol) you consume a small capability (io.Reader) and want any type, including third-party ones, to fit two types share a shape but not a meaning (UserId and OrderId are both string): use nominal wrappers
Nominal interfaces (C#, Java) the relationship is part of the design and you want "find implementations" to be exact you control neither side: write a small adapter instead of forcing an inheritance link
Closures callbacks, small factories, configuring behaviour (Where(x => x.Total > min)) in a hot loop that allocates a capturing lambda per call (C#, Java), or when the captured variable will change later
Generics algorithms and containers that work for many types with the same code you have one or two concrete types today: write concrete code; generics add reading cost
Null + checker (C# NRT, TS strict, mypy, NullAway) always: turn it on for new code, and enforce it in CI never off for new code; for old code, enable it file by file (#nullable enable)
AOT compilation CLIs, serverless, sidecars, containers that scale from zero heavy reflection, dynamic plugins, or long-lived services that benefit from run-time PGO
1 · READWhat does a variable hold?

Value or reference decides what assignment and passing share.

2 · CALLWhat can the callee change?

Mutation travels; reassignment doesn't, except ref and pointers.

3 · COMPAREIdentity or value?

Pick the operator that asks the question you mean.

4 · CAPTUREVariable or value?

Closures see later changes to captured variables.

5 · GUARDCan it be null?

Turn the checker on so the compiler answers for you.

Pitfalls and war stories

The deploy that breached its latency SLO for two minutes A .NET service rolled out new pods behind a load balancer that sent them full traffic immediately. For the first couple of minutes every method was running Tier-0 code, so p99 latency tripled and alerts fired on every deploy. Fix: a warm-up endpoint hit by the readiness probe, ReadyToRun images to start from precompiled code, and a slow-start ramp on the load balancer. Java services see the same thing; there, a CDS/AOT cache or GraalVM helps.

The Go goroutines that all processed the last item for _, job := range jobs { go func() { process(job) }() } on Go 1.21 ran process on the last job N times, because every goroutine captured the same job variable. Go 1.22 changed loop variables to be per iteration. Fix on older versions: pass it as an argument, go func(j Job) { process(j) }(job), or copy it, job := job. Check the go line in go.mod, since the new semantics depend on it.

The TypeScript cast that let bad data through const order = (await res.json()) as Order; compiled cleanly. The upstream service renamed total to amount, and order.total.toFixed(2) threw TypeError: Cannot read properties of undefined in production, because TS types don't exist at run time and as is a promise, not a check. Fix: validate untrusted input at the edge with a schema (zod, valibot, or JSON Schema in the API layer). The same applies to Python dicts from json.loads.

The C# struct that "lost" updates A List<Counter> of mutable structs was updated with var c = list[i]; c.Hits++;. Nothing changed, and tests passed because they checked a different code path. Fix: make small structs readonly record struct so the mistake can't compile, and write back with list[i] = c with { Hits = c.Hits + 1 }, or use a class if the thing has identity.

Checklist

  • [ ] I know whether my language checks types before or during execution, and CI runs the checker (mypy/pyright, tsc --noEmit, NRT warnings as errors).
  • [ ] For every type I design, I've chosen value or reference semantics on purpose; small value-like data is immutable.
  • [ ] Functions don't mutate their arguments unless their name says so; they return new values otherwise.
  • [ ] I use the right equality operator (equals/Equals, == in Python, === plus a custom equals in TS) and never is/== on references by accident.
  • [ ] Types used as dictionary keys or set members are immutable and have consistent equality and hashing.
  • [ ] Closures don't capture loop variables or other variables that change later, unless that's the point.
  • [ ] Null checking is on (C# <Nullable>enable</nullable>, TS strict, mypy, NullAway, nilaway), and I use ?? instead of ||/or for defaults.
  • [ ] Strings are built with a builder or join in loops; text length is measured in the unit I actually mean.
  • [ ] Visibility is as narrow as possible: internal, package-private, internal/, unexported, _private.
  • [ ] Benchmarks include warm-up (BenchmarkDotNet, JMH, testing.B, pyperf), and services warm up before taking full traffic.

Self-check

A Java method receives a List<String>, calls list.add("x"), then list = new ArrayList<>(). What does the caller see?

The caller's list contains "x". The parameter was a copy of the reference, so add mutated the shared object. The reassignment only changed the callee's copy of the reference; the caller's variable still points to the original list.

Why does Integer a = 127, b = 127; a == b print true, but the same with 128 prints false?

== on Integer compares references. Autoboxing uses Integer.valueOf, which returns cached objects for −128..127, so both 127s are the same object. 128 creates two different objects. Use a.equals(b) or compare ints.

In Go, func add(s []int) { s = append(s, 1) }. When can the caller observe the new element?

Never through its own slice header: the caller's len doesn't change. If cap > len, the 1 is written into the shared backing array, so a later s[:len+1] reslice by the caller (or another slice of the same array) can see it. That's why the idiom is s = add(s) with add returning the new slice.

Go, TypeScript and Python Protocols are all structural. What's the practical risk, and how do you counter it?

Two types with the same shape but different meanings are interchangeable: Celsius and Fahrenheit as plain numbers, or UserId and OrderId as plain strings. Counter it with nominal wrappers: Go named types, TS branded types, Python NewType, small records in C# and Java.

Why can't you write new T() in Java or TypeScript, when C# allows it with a constraint?

Java and TypeScript erase type arguments, so at run time there is no T to construct. C# generics are reified: the run time knows T for each instantiation, so where T : new() lets it call the constructor. In Java, pass a Supplier<T> or Class<T>; in TS, pass a constructor function.

What does discount || 10 return when discount is 0, and what should you write instead?

It returns 10, because 0 is falsy. Use discount ?? 10, which only falls back for null and undefined. In Python, discount or 10 has the same bug; write 10 if discount is None else discount.

Cheat sheet

PipelineGo: native binary. C#/Java: bytecode + tiered JIT. Python: bytecode VM. TS: types erased, JS on V8.
TypingC#/Java nominal + static. Go/TS structural + static. Python dynamic; Protocol + mypy = structural static.
Value vs referenceC# struct, Go struct, primitives = value. Classes, Python objects, JS objects = reference.
PassingAlways a copy of the variable. Mutate = visible; reassign = not. Exceptions: C# ref/out, Go *T.
EqualityIdentity: ReferenceEquals, Java ==, is, ===. Value: Equals/equals, Python ==, Go == on structs.
ClosuresCapture variables, not values. Per-iteration: C# foreach, JS let, Go 1.22+. Java: effectively final.
GenericsC# reified; Java/TS erased; Go GC-shape stencils; Python hints only.
NullC# NRT, TS strict: compiler-checked. Java NullAway, Go nilaway, mypy: add-on. Use ?? not ||.
StringsImmutable everywhere. Loop + builder/join. len: UTF-16 units (C#, Java, TS), code points (Python), bytes (Go).
