DEPENDENCY INJECTION

DI Across Languages & Frameworks

.NET Microsoft.Extensions.DependencyInjection, Spring, Dagger/Guice, Go (manual, Wire, Fx), Python and TypeScript (NestJS, InversifyJS) side by side.

Intermediate → Advanced~65 min studyBuilds on: Lifetimes, Scopes & Captive DependenciesUpdated 2026-11-03

The problem: the same idea, eleven different machines

You already know the idea from Dependency Injection Fundamentals. A class asks for what it needs, and a composition root builds the object graph once, at the edge of the program. You also know the rules about how long objects live from Lifetimes, Scopes & Captive Dependencies. The idea is the same in every language. The machinery is not.

Move from a .NET team to a Spring team and services.AddScoped<IOrderRepository, SqlOrderRepository>() turns into an annotation on a class that nobody registers. Move to Go and the container disappears. main() simply calls NewService(repo, clock) and people look at you oddly if you ask where the container is. In FastAPI, dependencies are function parameters. In NestJS, everything breaks the day someone swaps tsc for esbuild, and the error message talks about "index [1]".

These are not cosmetic differences. Each one decides when a wiring mistake is found, what it costs at startup, how cross-cutting code (transactions, logging) gets attached, and which bugs are even possible. A developer who carries one ecosystem's habits into another writes code that compiles and then fails in a way that ecosystem's veterans never see.

Rule. Every DI tool answers the same four questions: where does the recipe come from (reflection, generated code, or your own code), when is the graph checked (build, startup, first use, or never), who creates and caches instances (lifetimes and scopes), and how do cross-cutting concerns attach (decorators, proxies, interceptors). Learn a new ecosystem by answering these four questions first. Write it the way that ecosystem writes it, not the way your last one did.

This page takes one small app and wires it in every major ecosystem. The app is an OrderService that needs an OrderRepository (database), a Clock, a logger and a PaymentGateway (an HTTP client to a payment provider). It shows what each tool does with that app, step by step. You will see the actual error messages, generated code, proxies, lifecycles and request scopes, and you will be able to break each one on purpose.

1 · RECIPEWhere does it come from?

Constructor reflection, annotations read at build time, or lines of code you write yourself.

2 · CHECKWhen is the graph verified?

By the compiler, by a code generator, when the app starts, on the first request, or never.

3 · CREATEWho builds and caches?

Singletons, scopes per request, transients, or no lifetimes at all because you hold the references.

4 · WRAPHow is cross-cutting code added?

Runtime proxies (Spring, Guice), decorators you register (.NET), wrappers you write (Go), interceptors (Nest).

The mental model: four mechanisms

Strip the brand names away and there are only four ways to turn "OrderService needs a repository" into a running object. Every tool on this page is one of them, or a mix of two.

Why the ecosystems split this way. It comes down to what the runtime knows about types.

  • The CLR and the JVM keep full type information at runtime. A container can ask "what does this constructor need?" and get a real answer, so reflection containers are natural there.
  • Android and fast-startup services cannot afford that reflection. On Android, Dagger moved it into the compiler.
  • Go's culture values explicit code over magic, and Go has no constructors to inspect. So Go writes the wiring by hand, or generates it with Wire.
  • TypeScript erases types at compile time. A container only sees them if the compiler is told to write them down as metadata, and that is the root of most NestJS weirdness.
  • Python is so dynamic that a module-level object is already a singleton. Most code just passes things in. FastAPI added a per-request graph of functions.

When does each tool find a mistake?

The most practical difference between the ecosystems is when a broken graph is found. Here is the same set of mistakes plotted against the life of a deployment. Further right means more expensive: a compile error costs you ten seconds, while a silent captive dependency can cost you a week.

Now see it per mistake. Pick a mistake below and step through: each of eleven tools lights up in the phase where it reports it, with the exact message you would see. Note how the same mistake is a compile error in one column and a silent wrong answer in another.

Recognize it. If you are new to an ecosystem, ask three questions on day one:

  1. "If I delete a registration, where will I find out: the build, startup, or production?"
  2. "If I register two implementations, which one wins?"
  3. "Is there a switch that makes the container validate everything at startup, and is it on?"

The answers tell you which tests you must write yourself.

One graph, eight containers

The object graph is the same everywhere. What differs is when each node is built, how many times, and who keeps it. Pick a tool and step through three requests. Watch which nodes are created at startup, which per request and which never, and read the "recipe" each tool uses. On the first request, MS.DI builds a resolution plan with reflection. Spring has already built every singleton before the first request arrives. In Go, main() simply runs top to bottom.

Bad and good: porting one ecosystem's idiom into another

The commonest cross-language DI mistake is not a bug in a container. It is bringing a container to an ecosystem that does not want one, or leaving one out where the ecosystem relies on it. Here is the classic case: a team from .NET or Java builds a small reflection container in Go so that it "feels like home".

// container.go: a homemade service locator with stringly-typed keys
type Container struct{ factories map[string]func(*Container) any }

func (c *Container) Register(name string, f func(*Container) any) { c.factories[name] = f }
func (c *Container) Resolve(name string) any {
    f, ok := c.factories[name]
    if !ok {
        panic("no registration for " + name) // found at runtime, on first use
    }
    return f(c) // a new instance every time: is that transient? nobody decided
}

func main() {
    c := &Container{factories: map[string]func(*Container) any{}}
    c.Register("db", func(*Container) any { return mustOpen(os.Getenv("DB_URL")) })
    c.Register("repo", func(c *Container) any { return postgres.NewRepo(c.Resolve("db").(*sql.DB)) })
    c.Register("orders", func(c *Container) any {
        return orders.NewService(
            c.Resolve("repo").(orders.Repository),     // a typo here compiles fine
            c.Resolve("payments").(orders.Payments),   // never registered: panics in production
        )
    })
    // handlers call c.Resolve("orders").(*orders.Service): every caller depends on the locator
    http.ListenAndServe(":8080", api.NewRouter(c))
}

// main.go: the composition root is ordinary code. The compiler is the container.
func main() {
    cfg := config.MustLoad()

    db := mustOpen(cfg.DatabaseURL)
    defer db.Close() // you own it, so you close it

    httpClient := &http.Client{Timeout: 5 * time.Second}
    repo := postgres.NewOrderRepository(db)
    payments := stripe.NewGateway(httpClient, cfg.StripeKey)
    logger := slog.New(slog.NewJSONHandler(os.Stdout, nil))

    svc := orders.NewService(repo, payments, time.Now, logger)
    // forget payments and this is a compile error:
    // not enough arguments in call to orders.NewService

    srv := &http.Server{Addr: ":8080", Handler: api.NewRouter(svc, logger)}
    log.Fatal(srv.ListenAndServe())
}

What went wrong in the first version:

  • It threw away the one advantage Go has: the compiler checking the graph. Resolve returns any, so every type assertion is a runtime gamble.
  • It invented a lifetime model nobody chose. Every Resolve builds a new instance, including a new database pool on each call.
  • The container leaks into handlers. Once api.NewRouter(c) takes the container, every handler becomes a service locator client.

The second version is about the same length and has one file fewer. Its "registrations" are statements, and its "validation" is go build. The reverse mistake also exists. Hand-wiring 400 Spring beans in a Java main() throws away component scanning, AOP and the testing support, and gives you nothing back.

Pitfall: idiom transplant. Every ecosystem has a "normal". In .NET and Spring the normal is a container. In Go and Rust it is explicit constructors in main(). In Python it is mostly explicit, with FastAPI's Depends at the HTTP edge. In TypeScript it is NestJS if you chose Nest, and plain factories otherwise. Fighting the normal costs you twice: once in code, and again every time a new teammate has to learn your private framework.

.NET: Microsoft.Extensions.DependencyInjection

What it really is: a list of descriptors

IServiceCollection is literally a List<ServiceDescriptor>. Each descriptor records four things:

  • a service type;
  • how to make it: an implementation type, a factory lambda, or a ready-made instance;
  • a lifetime;
  • since .NET 8, an optional key.

Nothing is built while you call Add…. BuildServiceProvider() (which the host calls for you) freezes the list into a provider. The provider then resolves each service type lazily, the first time somebody asks for it.

Production .NET wiring for the order feature usually looks like this: one extension method per feature, typed options, a typed HTTP client, and validation switched on.

// Orders/OrdersServiceCollectionExtensions.cs: the feature's "module"
public static class OrdersServiceCollectionExtensions
{
    public static IServiceCollection AddOrders(this IServiceCollection services, IConfiguration config)
    {
        services.AddOptions<PaymentOptions>()
            .Bind(config.GetSection("Payments"))
            .ValidateDataAnnotations()
            .ValidateOnStart();                       // bad config fails the deploy, not request #1

        services.AddHttpClient<IPaymentGateway, StripeGateway>((sp, http) =>
        {
            var o = sp.GetRequiredService<IOptions<PaymentOptions>>().Value;
            http.BaseAddress = o.BaseUrl;
            http.Timeout = TimeSpan.FromSeconds(5);
        });                                           // typed client: registered as TRANSIENT

        services.TryAddSingleton(TimeProvider.System); // library-friendly: only if absent
        services.AddScoped<IOrderRepository, SqlOrderRepository>();
        services.AddScoped<OrderService>();
        return services;
    }
}

// Program.cs: the composition root
var builder = WebApplication.CreateBuilder(args);
builder.Services.AddDbContext<AppDbContext>(o => o.UseNpgsql(builder.Configuration.GetConnectionString("Db")));
builder.Services.AddOrders(builder.Configuration);

builder.Host.UseDefaultServiceProvider(o =>
{
    o.ValidateScopes = true;   // on by default in Development only
    o.ValidateOnBuild = true;  // walk every registration when the host starts
});

var app = builder.Build();
app.MapPost("/orders", (PlaceOrder cmd, OrderService svc) => svc.PlaceAsync(cmd));
app.Run();

The .NET-specific details that matter:

  • TryAdd* is for libraries, Add* is for apps. A library calls TryAddSingleton<IClock, SystemClock>() so that an app which already registered its own clock keeps it. If the library used AddSingleton, its registration would come later and silently win, because last registration wins. Advanced DI animates TryAdd, TryAddEnumerable, Replace and RemoveAll step by step.
  • AddHttpClient<TClient, TImpl> registers a transient typed client. The factory rotates the underlying HttpMessageHandler (two minutes by default) so DNS changes are picked up. Inject the typed client into a singleton and it becomes a captive: that one HttpClient and its handler live forever. Inject IHttpClientFactory into singletons instead.
  • Keyed services (.NET 8+) give you named registrations without a third-party container: AddKeyedSingleton<IPaymentGateway, StripeGateway>("stripe") plus [FromKeyedServices("stripe")]. The details are in Advanced DI.
  • The options pattern turns configuration into typed, validated objects. IOptions<T> is a singleton snapshot, IOptionsSnapshot<T> is scoped, and IOptionsMonitor<T> notifies you of changes. See Configuration & Secrets and Advanced DI.
  • MS.DI is deliberately minimal. It has no decorators, no Lazy<T>/Func<T> relationship types, no property injection and no assembly scanning. If you need those, plug in Autofac, Lamar or DryIoc through IServiceProviderFactory, or add Scrutor for scanning and Decorate. Compile-time containers exist too: Jab, Pure.DI and StrongInject use source generators, so a missing registration is a build error.
  • Native AOT and trimming. MS.DI works under Native AOT. Where it cannot generate code at runtime it uses a reflection-based activator, so it keeps working, but startup is a little slower. Trimming warnings point at registrations whose constructors the trimmer cannot see.

Hosting matters. In ASP.NET Core, ValidateScopes and ValidateOnBuild are both on in the Development environment and off elsewhere. A graph that "works on my machine" (Development, validated) and also "works in production" (unvalidated) is consistent. A graph that was never started in Development, such as a worker deployed straight to staging, may hide a captive dependency. Turn both switches on everywhere unless you have measured the startup cost and decided against it.

Java: Spring, Guice and Dagger

Java has three DI cultures:

  • Spring: a runtime container with scanning, proxies, and almost everything else built in.
  • Guice: a smaller runtime container configured in explicit Java modules.
  • Dagger: a compile-time code generator, mandatory in modern Android through Hilt.

They share the jakarta.inject annotations (@Inject, @Singleton, @Named, Provider<T>), so a constructor annotated with @Inject works in all three.

Spring: scanning, @Bean and auto-configuration

Spring finds most beans by component scanning. Classes annotated @Component, @Service, @Repository or @Controller under your application's package become singleton beans. Spring builds all of them eagerly when the context refreshes. A class with one constructor needs no @Autowired.

@Service
public class OrderService {
    private final OrderRepository repo;
    private final PaymentGateway payments;
    private final Clock clock;

    // single constructor: Spring injects it, no @Autowired needed
    public OrderService(OrderRepository repo, PaymentGateway payments, Clock clock) {
        this.repo = repo; this.payments = payments; this.clock = clock;
    }

    @Transactional                       // applied by a proxy around this bean (see below)
    public Order placeOrder(PlaceOrder cmd) {
        var order = Order.create(cmd, clock.instant());
        repo.save(order);
        payments.charge(order.total(), cmd.cardToken());
        return order;
    }
}

@Configuration(proxyBeanMethods = false)  // "lite" mode: @Bean methods are plain factory methods
@EnableConfigurationProperties(PaymentProperties.class)
class PaymentsConfig {
    @Bean
    Clock clock() { return Clock.systemUTC(); }

    @Bean
    PaymentGateway paymentGateway(RestClient.Builder http, PaymentProperties props) {
        return new StripeGateway(http.baseUrl(props.baseUrl()).build(), props.apiKey());
    }
}

Four Spring features have no direct equivalent elsewhere and are worth knowing well.

1. Full vs lite @Configuration.

  • By default, Spring subclasses @Configuration classes with CGLIB. A call from one @Bean method to another then returns the singleton instead of a new object.
  • proxyBeanMethods = false ("lite" mode) skips that subclass. Startup is faster and the class is friendlier to native images. But clock() called from another @Bean method now returns a new Clock every time.
  • In lite mode, take dependencies as @Bean method parameters, never by calling another @Bean method.

2. Auto-configuration and @ConditionalOnMissingBean.

  • Spring Boot's starters register defaults (a DataSource, an ObjectMapper, a RestClient.Builder) only if you have not defined your own.
  • This is Spring's version of .NET's TryAdd: the library backs off when the app speaks.
  • --debug prints the condition report, which shows why each auto-configuration did or did not apply.

3. Choosing between beans.

  • Two beans of one type cause a NoUniqueBeanDefinitionException. The exception is not thrown if one bean is @Primary, if the injection point has a @Qualifier, or if the parameter name happens to equal a bean name.
  • That last rule is a quiet fallback. Rename a parameter and your app stops starting.
  • Inject List<PaymentGateway> to get all of them, in @Order order.

4. ObjectProvider<T>.

  • ObjectProvider<T> gives lazy, optional or per-call lookup without making your class a service locator.
  • It is the right way for a singleton to use a prototype bean.

@Profile and @ConditionalOnProperty choose beans by environment. Spring evaluates them when the context starts. Under Spring AOT (native images) they are evaluated at build time, so the bean graph is fixed.

Spring's proxies: why @Transactional sometimes does nothing

@Transactional, @Cacheable, @Async, @Retryable and @PreAuthorize are not run by your class. When Spring creates the OrderService bean, a post-processor notices the annotations and puts a proxy in the context instead of your object. Spring Boot uses a CGLIB subclass by default, or a JDK dynamic proxy for interfaces if you configure it. Callers hold the proxy. The proxy starts the transaction, calls your real object, then commits or rolls back.

That design has three consequences that catch everyone at least once. Try them below:

  1. Self-invocation. this.audit() inside the bean skips the proxy, so @Transactional(propagation = REQUIRES_NEW) on audit does nothing.
  2. final methods. A CGLIB subclass cannot override a final method. The call runs on the proxy instance itself, whose fields were never injected, so you get a NullPointerException inside your own code. Spring logs a notice at startup that the method cannot be proxied.
  3. Checked exceptions commit. By default, Spring rolls back only on unchecked exceptions (RuntimeException, Error). A checked exception propagates and the transaction commits. Use rollbackFor = Exception.class if that is not what you want.

Why this matters beyond Spring. Every runtime-proxy system has the same blind spot: Guice AOP, Castle DynamicProxy in .NET, and Python decorators applied to bound methods. Interception happens at the boundary of the object the container handed out. Code inside the object is invisible to it. If you need the behaviour on an internal call, move the method to another bean, or make the boundary explicit with a decorator or wrapper you can see. Advanced DI compares decorators with interceptors across languages.

Guice: explicit modules, still at runtime

Guice keeps reflection but moves the configuration into Java code: a Module with bind(...).to(...) and @Provides methods. Guice.createInjector(modules) checks every explicit binding and its dependencies at once, so most mistakes surface at startup.

public class OrdersModule extends AbstractModule {
    @Override
    protected void configure() {
        binder().requireExplicitBindings();       // no surprise just-in-time bindings
        binder().disableCircularProxies();        // a cycle is an error, not a hidden proxy
        bind(OrderRepository.class).to(JdbcOrderRepository.class);
        bind(PaymentGateway.class).to(StripeGateway.class).in(Singleton.class);
        bind(OrderService.class);
    }

    @Provides @Singleton
    Clock clock() { return Clock.systemUTC(); }
}

Injector injector = Guice.createInjector(Stage.PRODUCTION, new OrdersModule(), new DbModule());
OrderService svc = injector.getInstance(OrderService.class);

Two Guice defaults deserve a switch:

  • Just-in-time bindings. Any concrete class with an @Inject (or no-argument) constructor can be created without being bound. That is convenient until it hides a missing binding behind a default constructor. requireExplicitBindings() turns that off.
  • Circular proxies. For interfaces, Guice silently breaks cycles with a proxy. disableCircularProxies() makes a cycle an error.

Stage.PRODUCTION creates singletons eagerly. That is slower to start, but failures happen at startup rather than at first use.

Dagger and Hilt: the graph is checked by javac

Dagger is an annotation processor. You describe the graph with @Module/@Provides/@Binds, @Inject constructors, and a @Component interface that names the roots you need. While javac runs, Dagger generates DaggerAppComponent: ordinary Java that calls constructors. It contains no reflection, no proxies and no runtime container. A missing binding, a cycle, a duplicate or a scope mismatch is a compile error.

@Module
interface OrdersModule {
    @Binds OrderRepository repo(JdbcOrderRepository impl);   // interface → implementation
    @Binds PaymentGateway payments(StripeGateway impl);

    @Provides @Singleton
    static Clock clock() { return Clock.systemUTC(); }
}

@Singleton
@Component(modules = { OrdersModule.class, DbModule.class })
interface AppComponent {
    OrderService orderService();          // a root: Dagger generates the code to build it
}

// main: the generated class is just constructor calls
AppComponent app = DaggerAppComponent.create();
OrderService svc = app.orderService();

Hilt is Dagger with Android conventions. It provides predefined components (SingletonComponent, ActivityComponent, ViewModelComponent), so the scopes follow Android lifecycles. Dagger's cost is the build: annotation processing adds time to every compile. Its error messages are long but precise, and they name the whole dependency path.

The visualizer below shows what a code generator does with a list of providers. Edit the provider list, pick a scenario (forget a provider, add a cycle, register two providers for one type, leave one unused) and compare three outcomes. Wire (Go) and Dagger (Java) fail the build with the error shown. A runtime container happily starts and fails later.

Tip. Look at the generated output in the visualizer: it is the code you would have written by hand in main(). That is the point of compile-time DI. It is "pure DI" that a tool keeps up to date for you. When the generated file is short and readable, you can always delete the tool and keep the file.

Go: constructors first, then Wire or Fx

Go's default is the "Good" tab above: NewX(deps...) functions and a main() that calls them in order. Three language features make that pleasant, not painful:

  • Interfaces are satisfied implicitly. orders declares the small PaymentGateway interface it needs, and stripe.Gateway satisfies it without importing orders. The consumer owns the abstraction, which is exactly the Dependency Inversion Principle, and it costs no annotations.
  • Functions are values. A clock is just func() time.Time, so you inject time.Now and pass a fixed function in tests. No IClock interface is needed.
  • Multiple return values carry errors and cleanup. NewDB(cfg) (*sql.DB, func(), error) says "this can fail, and here is how to close it". main() handles both visibly.

When main() passes about 200 lines, teams reach for one of two tools. They are opposites.

Wire: generate the main() you would have written

Google's Wire is a code generator. You write an injector stub that lists provider functions. The wire command (run with go generate) works out the call order and writes wire_gen.go, which is plain Go that you commit. At runtime, Wire does not exist.

//go:build wireinject

package main

import "github.com/google/wire"

var ordersSet = wire.NewSet(
    postgres.NewOrderRepository,
    wire.Bind(new(orders.Repository), new(*postgres.OrderRepository)),
    stripe.NewGateway,
    wire.Bind(new(orders.PaymentGateway), new(*stripe.Gateway)),
    orders.NewService,
)

// The body is never executed: wire replaces it.
func InitializeServer(cfg config.Config) (*api.Server, func(), error) {
    wire.Build(ordersSet, provideDB, provideHTTPClient, provideClock, api.NewServer)
    return nil, nil, nil
}

// A provider can return a cleanup function and an error; Wire chains them.
func provideDB(cfg config.Config) (*sql.DB, func(), error) {
    db, err := sql.Open("pgx", cfg.DatabaseURL)
    if err != nil {
        return nil, nil, err
    }
    return db, func() { db.Close() }, nil
}

// Code generated by Wire. DO NOT EDIT.

//go:generate go run -mod=mod github.com/google/wire/cmd/wire
//go:build !wireinject

package main

func InitializeServer(cfg config.Config) (*api.Server, func(), error) {
    db, cleanup, err := provideDB(cfg)
    if err != nil {
        return nil, nil, err
    }
    orderRepository := postgres.NewOrderRepository(db)
    client := provideHTTPClient()
    gateway := stripe.NewGateway(client, cfg)
    clock := provideClock()
    service := orders.NewService(orderRepository, gateway, clock)
    server := api.NewServer(service)
    return server, func() {
        cleanup()
    }, nil
}

Wire is strict in useful ways:

  • It needs exactly one provider per type.
  • It rejects providers that are passed to wire.Build but never used.
  • It has no lifetimes. Every call to an injector builds a fresh graph, and anything per-request is passed as an argument.

Its one operational risk is a stale wire_gen.go. Someone edits a constructor's signature, forgets go generate, and the build fails with an error in a generated file. Add a CI step that runs wire (or go generate ./...) and fails on git diff. Wire is feature-complete and changes rarely, so check the repository's maintenance status before adopting it for a new project.

Fx: a runtime container with a lifecycle

Uber's Fx (built on dig) is the other road. It is a reflection-based container whose real value is the application lifecycle: ordered OnStart hooks, reverse-ordered OnStop hooks, and rollback when a start fails. It is popular in large Go monorepos where dozens of modules each contribute servers, consumers and background loops.

func main() {
    fx.New(
        fx.Provide(
            config.Load,
            NewDB,
            fx.Annotate(postgres.NewOrderRepository, fx.As(new(orders.Repository))),
            fx.Annotate(stripe.NewGateway, fx.As(new(orders.PaymentGateway))),
            provideClock,
            orders.NewService,
            api.NewServer,
        ),
        fx.Invoke(func(*api.Server) {}), // the root: nothing is built unless an Invoke needs it
    ).Run() // runs OnStart hooks, waits for SIGINT/SIGTERM, then OnStop in reverse
}

func NewDB(lc fx.Lifecycle, cfg config.Config) (*sql.DB, error) {
    db, err := sql.Open("pgx", cfg.DatabaseURL)
    if err != nil {
        return nil, err
    }
    lc.Append(fx.Hook{
        OnStart: func(ctx context.Context) error { return db.PingContext(ctx) },
        OnStop:  func(ctx context.Context) error { return db.Close() },
    })
    return db, nil
}

The rule that surprises newcomers is that fx.Provide is lazy. A provider runs only if something reachable from an fx.Invoke needs its output. Leave out the Invoke and fx.New succeeds, Run() starts nothing, and your server never listens. Step through it below. Toggle the invokes and a failing OnStart, and watch the rollback run in reverse.

Wire

  • A build-time check, and zero runtime cost
  • Generated code you can read and debug
  • No lifecycle: you write start/stop yourself
  • Best for services and CLIs with modest graphs

Fx

  • Lifecycle hooks, modules (fx.Module), value groups
  • Startup-time checks, and only for reachable providers
  • Reflection, plus stack traces through dig
  • Best for big apps built from many teams' modules

Python: explicit by default, Depends at the edge

Python needs no container to do DI. Classes take their collaborators in __init__, and a function that builds them is a composition root. Because a module is imported once, a module-level object is already a process-wide singleton. That is convenient, and it is also the most common Python DI bug (see the pitfalls below).

This is runnable as-is:

from dataclasses import dataclass
from datetime import datetime, timezone
from typing import Callable, Protocol


class OrderRepository(Protocol):
    def save(self, order: dict) -> None: ...


class PaymentGateway(Protocol):
    def charge(self, amount: int, token: str) -> str: ...


@dataclass
class OrderService:
    repo: OrderRepository
    payments: PaymentGateway
    now: Callable[[], datetime]

    def place(self, amount: int, token: str) -> dict:
        order = {"amount": amount, "at": self.now().isoformat()}
        order["charge"] = self.payments.charge(amount, token)
        self.repo.save(order)
        return order


class InMemoryRepo:
    def __init__(self) -> None:
        self.rows: list[dict] = []

    def save(self, order: dict) -> None:
        self.rows.append(order)


class FakePayments:
    def charge(self, amount: int, token: str) -> str:
        return f"ch_{token}_{amount}"


def build_app(settings: dict) -> OrderService:
    """The composition root: the only place that knows concrete types."""
    repo = InMemoryRepo()                      # in production: SqlOrderRepository(engine)
    payments = FakePayments()                  # in production: StripeGateway(httpx.Client(...))
    return OrderService(repo, payments, lambda: datetime.now(timezone.utc))


svc = build_app({})
print(svc.place(4200, "tok1")["charge"])      # ch_tok1_4200

typing.Protocol gives Python Go-style implicit interfaces. InMemoryRepo never mentions OrderRepository, yet a type checker (pyright, mypy) accepts it wherever an OrderRepository is needed. Combine that with a composition root and you already have everything a container would give a small app.

dependency-injector: when the graph grows

dependency-injector (Cython-backed, mature) is the most popular explicit container. You declare providers (Singleton, Factory, Resource for things that need closing, Configuration) on a container class. You override them in tests, and check_dependencies() finds holes. This also runs as shown (the printed output is in the comments):

from dependency_injector import containers, providers


class Container(containers.DeclarativeContainer):
    config = providers.Configuration()
    payments = providers.Dependency()               # must be supplied by the app or a test
    repo = providers.Singleton(InMemoryRepo)
    clock = providers.Object(lambda: datetime.now(timezone.utc))
    orders = providers.Factory(OrderService, repo=repo, payments=payments, now=clock)


c = Container()
try:
    c.check_dependencies()
except Exception as e:
    print(e)    # Container "Container" has undefined dependencies: "Container.payments"

c.payments.override(providers.Object(FakePayments()))
c.check_dependencies()                              # passes now
print(c.orders().place(100, "t")["charge"])         # ch_t_100

Other Python containers are lighter. punq and lagom resolve from type hints, and injector is Guice-style. They all share one property: Python checks nothing until code runs. Add a test that builds the whole container (and calls check_dependencies() if you use dependency-injector). That test is your compile step.

FastAPI Depends: a per-request graph of functions

FastAPI took a different path: dependencies are functions named in parameter defaults. Depends(get_session) means "call get_session and pass the result". FastAPI reads the signatures when the route is registered, builds a tree, and on every request it:

  • calls the tree bottom-up;
  • caches each dependency within that request, so two parameters that need get_session share one session (use_cache=False opts out);
  • runs yield dependencies like context managers, with the code after yield as cleanup.
from typing import Annotated
from fastapi import Depends, FastAPI, HTTPException

app = FastAPI()


def get_session():
    session = Session(engine)          # opened per request
    try:
        yield session
        session.commit()               # runs AFTER the response has been sent (default scope)
    except Exception:
        session.rollback()             # endpoint exceptions are thrown in here first
        raise
    finally:
        session.close()


def get_payments() -> PaymentGateway:
    return StripeGateway(http_client)  # module-level httpx.Client, shared and pooled


def get_order_service(
    session: Annotated[Session, Depends(get_session)],
    payments: Annotated[PaymentGateway, Depends(get_payments)],
) -> OrderService:
    return OrderService(SqlOrderRepository(session), payments, utc_now)


@app.post("/orders", status_code=201)
def place_order(cmd: PlaceOrder, svc: Annotated[OrderService, Depends(get_order_service)]):
    if svc.is_duplicate(cmd):
        raise HTTPException(status_code=409, detail="duplicate order")
    return svc.place(cmd)


# tests: swap any function in the tree, by identity
app.dependency_overrides[get_payments] = lambda: FakePayments()

Verified on FastAPI 0.162 with TestClient: commit after the response. With the default dependency scope, a yield dependency's exit code runs after the response has been sent. If session.commit() fails there, the client has already received 201 Created for an order that was never saved. There are two fixes:

  • declare Depends(get_session, scope="function"), so the exit code runs before the response (the same failure then produces a 500);
  • or commit explicitly inside the endpoint or service, and keep only rollback and close in the dependency.

This behaviour has changed across FastAPI versions, so check the "Dependencies with yield" page for the version you run.

Step through it. Choose the session scope, the endpoint's outcome and whether the commit fails, then watch the event log and what the client receives:

FastAPI's model in DI terms.

  • Every Depends function is a transient factory, cached per request. So "scoped" is the default and there is no singleton lifetime inside the graph.
  • App-wide objects (an httpx.Client, an engine, a settings object) live at module level, or are created in the lifespan handler and stored on app.state.
  • Because nothing app-wide can receive a Depends value, a captive dependency is nearly impossible to write by accident.
  • The price: wiring for anything outside HTTP (a CLI, a worker, a scheduled job) must be done separately, usually with a plain composition-root function both can share.

TypeScript: decorators, metadata and tokens

TypeScript has the hardest job of the five, because types do not exist at runtime. When tsc compiles constructor(private repo: OrderRepository), the type annotation is erased. A container that wants to inject "an OrderRepository" has two ways to find out what to inject:

  1. The compiler writes the type down as metadata: legacy experimentalDecorators plus emitDecoratorMetadata emit design:paramtypes. NestJS, tsyringe and InversifyJS (with @injectable) rely on this.
  2. You name the dependency explicitly with a token: @Inject(PAYMENTS), @inject(TYPES.Repo), or a registration function that lists its inputs.

This is why "it works with nest start but fails in Vitest" is a rite of passage. Vitest uses esbuild, and esbuild does not emit decorator metadata. The NestJS docs recommend the SWC plugin (unplugin-swc) for Vitest for exactly this reason. Try the combinations:

NestJS: modules, providers and tokens

NestJS is Angular-style DI for servers. Providers live in modules. A provider is visible only inside its module unless that module exports it and the consumer imports the module. During NestFactory.create() Nest instantiates every provider, so missing dependencies fail at bootstrap with the well-known "Nest can't resolve dependencies of X (?, …)" message.

export const PAYMENTS = Symbol('PaymentGateway');   // interfaces vanish at runtime: use a token
export const CLOCK = Symbol('Clock');

@Injectable()
export class OrderService {
  constructor(
    private readonly repo: OrderRepository,               // a class: its type IS the token
    @Inject(PAYMENTS) private readonly payments: PaymentGateway,
    @Inject(CLOCK) private readonly now: () => Date,
  ) {}
}

@Module({
  imports: [DatabaseModule, HttpModule.register({ timeout: 5000 })],
  providers: [
    OrderService,
    OrderRepository,
    { provide: PAYMENTS, useClass: StripeGateway },
    { provide: CLOCK, useValue: () => new Date() },
  ],
  exports: [OrderService],                               // visible to modules that import OrdersModule
})
export class OrdersModule {}

The details that differ from other ecosystems:

  • Interfaces need tokens. An interface becomes Object in metadata, so constructor(p: PaymentGateway) cannot work. Use a Symbol or string token with @Inject(...), or use an abstract class as the token, since abstract classes survive compilation.
  • Last provider wins within a module. Two { provide: PAYMENTS } entries do not raise an error. The later one replaces the earlier one.
  • Request scope bubbles up. Mark a provider Scope.REQUEST and every provider that depends on it also becomes request-scoped. That is safe from captives, but it means a new object graph per request. Durable providers (per tenant) exist to limit the cost.
  • Circular imports between files show up as ? in the error. The class was still undefined when the decorator ran. forwardRef(() => X) is the escape hatch, and a design smell.

InversifyJS, tsyringe, awilix and plain factories

  • InversifyJS: explicit bindings to symbols (container.bind<PaymentGateway>(TYPES.Payments).to(StripeGateway)), with @inject(TYPES.Payments) on constructor parameters. It resolves lazily at container.get(), so missing bindings surface at first use. Its inRequestScope() means "once per get() call", not "per HTTP request".
  • tsyringe (Microsoft): small, decorator-based, and relies on emitDecoratorMetadata. Without metadata it fails with TypeInfo not known for "OrderService".
  • awilix: no decorators at all. By default (PROXY mode) a constructor receives a single "cradle" object and destructures what it needs: constructor({ orderRepository, payments }). Its CLASSIC mode parses parameter names from the function source and breaks under minification.
  • Plain factories: for many Express, Fastify, serverless and Next.js apps, createApp({ repo, payments }) and a buildDeps() function are the whole story. They are type-checked end to end by tsc, have zero runtime cost, and are trivially testable.

A word on Rust

Rust has no mainstream DI container. Dependencies are traits, injected either as generics (OrderService<R: OrderRepository>, monomorphized into direct calls) or as Arc<dyn PaymentGateway> when the choice is made at runtime. main() builds everything, Axum carries shared dependencies in a typed State<AppState>, and the borrow checker turns lifetimes into an ownership question.

Cross-cutting concerns are the fourth job. Transactions, retries, caching, metrics and authorization attach differently everywhere:

  • Spring and Guice use runtime proxies.
  • .NET uses decorators registered in the container (Scrutor's Decorate) or middleware and filters.
  • Go uses wrapper structs that implement the same interface, and func(http.Handler) http.Handler middleware.
  • Python uses function decorators and ASGI middleware.
  • NestJS uses interceptors, guards and pipes.

Advanced DI covers decorator chains and interception in depth. Middleware Patterns covers the HTTP-pipeline flavour.

When to use a container, and when not to

Dependency Injection Fundamentals already makes the general case for and against containers. The cross-language version of the question is sharper: what does this ecosystem's container give you that its compiler does not? In Spring, the answer is a lot: AOP, auto-configuration and test slices. In Go, it is very little, unless you need Fx's lifecycle. Walk the decision for your situation:

Use the ecosystem's container when

  • The framework is built on it. ASP.NET Core, Spring Boot and NestJS hand you middleware, controllers and configuration through it. Opting out means rebuilding that plumbing.
  • The graph is large and shared by many teams, and modules need to contribute registrations without editing one main().
  • You need lifetimes and scopes: per-request units of work, per-tenant state, owned disposal.
  • Cross-cutting behaviour (transactions, caching, security) is applied by the container's proxies or decorators.
  • There is a compile-time option (Dagger, Wire, a source-generated .NET container) and build time is acceptable. You get container convenience with compiler safety.

Skip it (wire by hand) when

  • The ecosystem's normal is manual: Go, Rust, most Python, small TypeScript services.
  • It is a library. Accept dependencies in constructors and let the host app choose its container. At most, ship an optional AddMyLibrary() extension that uses TryAdd.
  • Cold start is the budget: serverless functions, CLIs, mobile. Reflection and eager bean creation cost hundreds of milliseconds you will pay on every invocation.
  • The graph fits on one screen. A 30-line composition root is easier to read than any container configuration.
  • AOT or native images are required and the container relies on runtime reflection. Prefer code generation there.

The costs, so you can weigh them honestly:

Cost Runtime reflection containers Code generation Manual wiring
Startup time highest (scanning, reflection, eager singletons in Spring/Nest) none at runtime none
When errors appear startup or first use; needs a composition test build build
Build time none annotation processing / go generate on every change none
Learning curve the container's rules, scopes, proxies the generator's rules and its error messages none beyond the language
Boilerplate lowest low (provider lists) grows with the graph
Debuggability stack traces through the container generated code you can step through your own code

Pitfalls and war stories

The library that won the registration. A team's .NET app registered its own IClock (a fake used in staging tests) and then called services.AddAcmeBilling(). The billing library's extension used services.AddSingleton<IClock, SystemClock>(), not TryAdd. Because the last registration wins, every IClock in the app was quietly replaced by the system clock. Staging tests of time-dependent invoices started failing a week later, far from the change. Fix: libraries use TryAdd* (and TryAddEnumerable for plug-ins); apps register their overrides after library calls, and assert the final choice in a composition test.

The typed HttpClient that never saw the new DNS record. A .NET singleton ExchangeRateCache took a typed client ExchangeRateClient in its constructor. The typed client is transient. Captured in a singleton, it pinned one HttpClient and its handler for the life of the process. When the provider failed over to a new IP, the cache kept calling the old one until a restart. Fix: inject IHttpClientFactory and call CreateClient per operation, or make the consumer transient/scoped. This is the captive dependency pattern again, in a form validation does not flag.

"Nest can't resolve dependencies of OrderService (?, PaymentGateway)." A developer moved a provider into a new file. Two files now imported each other, so when OrderService's decorator ran, OrderRepository was still undefined and the metadata recorded undefined at index 0, shown as ?. No Nest configuration was wrong. Fix: break the import cycle by moving the shared type into a third file. Use forwardRef(() => OrderRepository) only as a last resort.

Green locally, undefined in Vitest. A NestJS service worked with nest start (tsc, metadata emitted) but this.repo was undefined in unit tests running under Vitest (esbuild, no metadata). Nest had built the class with zero constructor arguments. Fix: use unplugin-swc with decorator metadata enabled for Vitest, or use explicit @Inject(TOKEN) everywhere. Run your composition test under the same transform as production.

Python: "singletons" created at import time. payments.py had client = httpx.Client(base_url=os.environ["PAYMENTS_URL"]) at module level. Three problems followed:

  • The client was built when the module was first imported, before settings were loaded, so tests had to set environment variables before importing.
  • Gunicorn's --preload created it in the master process, so it was shared by every forked worker.
  • app.dependency_overrides could not replace it.

A related trap is def __init__(self, now=datetime.now()):. A default argument is evaluated once, when the def runs, so every instance gets the same frozen time. Fix: create app-wide objects in lifespan or a composition-root function, and default callables to None, or pass the function itself (now=datetime.now) rather than calling it.

Spring: the upgrade that refused to start. Spring Boot 2.6 changed the default to spring.main.allow-circular-references=false. Services that had depended on each other for years (OrderService ↔ InvoiceService via field injection) suddenly failed at startup with a cycle diagram. Setting the property back to true "fixes" it. Extracting the shared logic into a third bean is the real fix, and it usually reveals a missing concept in the domain.

Go: the stale wire_gen.go and the silent Fx app.

  • Wire: a developer added a parameter to stripe.NewGateway but did not run go generate. CI failed with a confusing error inside a generated file. Fix: a CI step go generate ./... && git diff --exit-code.
  • Fx: a refactor removed the only fx.Invoke that referenced the HTTP server. fx.New succeeded, the app "started", and nothing listened on the port, because Fx only builds providers reachable from an invoke. Fix: keep the root invoke next to fx.New, and add a test that hits /healthz.

Best-practice checklist

  • [ ] I can answer the four questions for my stack: where the recipe comes from, when the graph is checked, who owns instances, and how cross-cutting code attaches.
  • [ ] I write DI the way this ecosystem writes it: a container in .NET, Spring and Nest; constructors in Go, Rust and Python; Depends at FastAPI's HTTP edge.
  • [ ] Everything is constructor-injected. No field injection, no @Autowired on fields, no container in business code.
  • [ ] Graph validation is on everywhere it exists: ValidateOnBuild/ValidateScopes, Guice requireExplicitBindings + disableCircularProxies, Boot's circular-reference ban.
  • [ ] There is one composition test that builds the full production graph, wherever the graph is not checked by the compiler.
  • [ ] Duplicate registrations are deliberate: keyed/qualified, collected as a list, or overridden after library calls. Libraries use TryAdd/@ConditionalOnMissingBean.
  • [ ] Interfaces in TypeScript have tokens. The test runner emits decorator metadata, or everything uses explicit tokens.
  • [ ] Generated wiring (Wire, Dagger) is regenerated and diffed in CI.
  • [ ] Configuration is typed and validated at startup (ValidateOnStart, @Validated, pydantic-settings, zod).
  • [ ] Startup and shutdown are ordered: hooks start in dependency order and stop in reverse. Pools and clients are closed by whoever created them.
  • [ ] I know where my stack's proxies do not apply: self-invocation, final methods, private methods.

Self-check

1. A .NET service resolves the wrong `INotifier` implementation, and nothing throws. What is the likely cause, and how would Spring have behaved?

Two registrations for INotifier exist, and MS.DI returns the last one for a single resolve. The second one is often added by a library extension method that used Add instead of TryAdd. Spring would refuse to start with NoUniqueBeanDefinitionException, unless one bean is @Primary, the injection point has a @Qualifier, or the parameter name matches a bean name. Fix it in .NET with keyed services, an explicit single registration made after the library call, or IEnumerable<INotifier> if you really want all of them.

2. You annotate `audit()` with `@Transactional(propagation = REQUIRES_NEW)` and call it from `placeOrder()` in the same Spring bean. Does `audit()` get its own transaction?

No. The call goes through this, not through the proxy that Spring put in the context, so the transaction advice never runs. audit() joins placeOrder()'s transaction, or runs without one. Move audit() to a separate bean, so the call crosses a proxy, or use TransactionTemplate explicitly.

3. Your Go service uses Fx. You delete an `fx.Invoke` during a refactor; `fx.New` succeeds and the process runs, but nothing listens on port 8080. Why?

fx.Provide is lazy. Providers run only when something reachable from an fx.Invoke needs them. With no invoke that needs the server, its constructor (and the OnStart hook it registers) never runs. Keep an explicit root invoke, and test with fx.ValidateApp plus a health-check request.

4. A NestJS provider works in the app but its dependency is `undefined` under Vitest. What differs, and what are two fixes?

The app is compiled by tsc with emitDecoratorMetadata, which records design:paramtypes. Vitest transforms with esbuild, which emits no decorator metadata, so Nest sees a constructor with no known parameters. Fixes:

  • use the SWC plugin (unplugin-swc) with decorator metadata in Vitest;
  • or name every dependency with @Inject(TOKEN).
5. In FastAPI, the commit is after `yield` in a dependency. The commit fails. With the default scope, what does the client see, and how do you make the failure visible?

The client sees the endpoint's success response (for example 201), because with the default scope the exit code of a yield dependency runs after the response is sent. Declare Depends(get_session, scope="function") so cleanup runs before the response (the client then gets a 500), or commit explicitly in the endpoint or service.

6. Which of these find a missing binding at build time: Spring Boot, Dagger, Fx, Wire, NestJS, manual Go, MS.DI with ValidateOnBuild?

Dagger, Wire and manual Go. Dagger reports it during annotation processing, Wire during go generate, and manual Go wiring as an ordinary compile error. Spring Boot, NestJS, Fx and MS.DI with ValidateOnBuild find it at startup. That is still before traffic, but only if the process is actually started by a test or a deployment health check.
