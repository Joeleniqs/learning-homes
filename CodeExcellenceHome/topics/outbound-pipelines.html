REQUEST PIPELINES & MIDDLEWARE

Outbound Pipelines & Interceptors

HttpClient DelegatingHandlers, OkHttp/Axios interceptors, gRPC interceptors and MediatR-style behaviors: the same onion on the client side.

Advanced~45 min studyBuilds on: The Request Delegate PipelineUpdated 2026-11-03

The problem: every call site doing the client's job

Your service calls three others: orders, payments and inventory. Every one of those calls needs the same handful of things: a bearer token that is fresh, a correlation id so logs line up across services, a traceparent header so the distributed trace stays in one piece, a timeout, a retry for the occasional 503, and a log line that does not print the token. Here is how that usually starts:

public class CheckoutService(ITokenService tokens, ILogger<CheckoutService> log)
{
    public async Task<Order?> GetOrderAsync(int id)
    {
        using var http = new HttpClient();                       // new pool, new sockets, every call
        http.BaseAddress = new Uri("https://orders.internal");
        var token = await tokens.GetAsync();                     // 50 call sites, 50 copies
        http.DefaultRequestHeaders.Authorization = new("Bearer", token);
        http.DefaultRequestHeaders.Add("x-correlation-id", Activity.Current?.Id);
        log.LogInformation("GET /orders/{Id} {Headers}", id,
            http.DefaultRequestHeaders);                         // token in the logs
        for (var attempt = 1; ; attempt++)                       // hand-rolled retry, no jitter
        {
            try
            {
                var res = await http.GetAsync($"/orders/{id}");  // default timeout: 100 s
                if ((int)res.StatusCode >= 500 && attempt < 3) { await Task.Delay(200); continue; }
                return await res.Content.ReadFromJsonAsync<Order>();
            }
            catch (HttpRequestException) when (attempt < 3) { await Task.Delay(200); }
        }
    }
    // ...and the same 20 lines again in GetPaymentAsync, ReserveStockAsync, ...
}

// Program.cs: the pipeline is configured once, per downstream service
builder.Services.AddTransient<AuthHandler>();
builder.Services.AddTransient<CorrelationHandler>();
builder.Services.AddHttpClient<OrdersClient>(c =>
    {
        c.BaseAddress = new Uri("https://orders.internal");
    })
    .AddHttpMessageHandler<CorrelationHandler>()   // outermost of yours
    .AddHttpMessageHandler<AuthHandler>()          // token on every request, refreshed once
    .AddStandardResilienceHandler();               // timeouts + retry with jitter + breaker

// The call site is now only about the business call
public class OrdersClient(HttpClient http)
{
    public Task<Order?> GetAsync(int id, CancellationToken ct) =>
        http.GetFromJsonAsync<Order>($"/orders/{id}", ct);
}

The "before" version has six separate problems, and none of them is visible in a code review of a single call site: a new connection pool per call (socket exhaustion), token handling duplicated fifty times, a secret in the logs, no deadline smaller than 100 seconds, a retry storm waiting to happen, and no consistent tracing. The "after" version moves each concern into a handler that wraps the network call. Every request made with that client goes through the same chain, so the concern is written, tested and fixed in exactly one place.

If you have read The Request Delegate Pipeline and Middleware Patterns, you already know this shape. It is the same onion, turned around to face the other way.

An outbound pipeline is middleware for the requests you send. Each handler gets the outgoing request, may change it, calls the next handler, and gets the response on the way back. Put a cross-cutting concern of outbound calls (auth, tracing, logging, retries, timeouts) in a handler once, and keep call sites about the business call.

The mental model: the same onion, facing outward

On the server, the request arrives from the network, travels inward through middleware, and your endpoint sits in the middle. On the client, your code sits outside, the request travels inward through handlers, and the network sits in the middle. The innermost layer on the client is the one component that does real I/O: SocketsHttpHandler in .NET, CallServerInterceptor in OkHttp, http.Transport in Go, the transport in httpx, the dispatcher in Node's fetch.

Three consequences fall straight out of this picture, and the rest of the page keeps coming back to them:

  1. Order is behaviour. A logging handler outside the retry handler logs one line per logical call, timed end to end. Inside the retry handler it logs one line per attempt. Both are useful; they are different. A timeout outside the retry is a total budget; inside it, it is a per-attempt limit.
  2. Anything above the core is plain in-process code. A handler that adds a header costs nanoseconds. Only the primary handler waits on the network. So it is cheap to have five or six handlers.
  3. A handler can call next zero, one or many times. Zero times is a short-circuit (a cache, a circuit breaker that is open, a test fake). Many times is a retry or a hedge. That is exactly why retries live in a handler and not at the call site.

Step through a real chain below. The simulation keeps a clock, a stack of deadlines and the headers on the wire. Change the order (for example Timeout,Retry,Log,Auth,Trace) or the server's behaviour and watch what changes: how many lines the logger writes, whether the timeout limits each attempt or the whole call, whether the token refresh happens once, and how many client spans the trace gets.

Insight Every handler only knows "the next one". It doesn't know whether the next one is another handler, a retry loop or the real socket. That ignorance is the design: you can add, remove or reorder layers, or swap the primary handler for a fake in tests, without touching any other layer.

Build one from scratch

DelegatingHandler: a decorator with an InnerHandler

In .NET everything that can send an HttpRequestMessage is an HttpMessageHandler. HttpClient itself is only a friendly wrapper that holds one handler and calls its SendAsync. A DelegatingHandler is a handler that has another handler, its InnerHandler, and by default forwards to it. You override SendAsync, do your work before and after base.SendAsync(...), and you have a layer.

Here is a complete, working pipeline with no DI at all, so you can see every moving part. It is exactly what IHttpClientFactory builds for you later.

public sealed class CorrelationHandler : DelegatingHandler
{
    protected override Task<HttpResponseMessage> SendAsync(HttpRequestMessage request, CancellationToken ct)
    {
        // before: the request is going down
        if (!request.Headers.Contains("x-correlation-id"))
            request.Headers.Add("x-correlation-id", Activity.Current?.TraceId.ToString() ?? Guid.NewGuid().ToString("N"));
        return base.SendAsync(request, ct);           // nothing to do on the way back: return the task
    }
}

public sealed class TimingHandler(ILogger log) : DelegatingHandler
{
    protected override async Task<HttpResponseMessage> SendAsync(HttpRequestMessage request, CancellationToken ct)
    {
        var start = Stopwatch.GetTimestamp();
        try
        {
            var response = await base.SendAsync(request, ct);    // everything below happens in here
            log.LogInformation("{Method} {Path} -> {Status} in {Ms:0} ms", request.Method,
                request.RequestUri?.AbsolutePath, (int)response.StatusCode, Stopwatch.GetElapsedTime(start).TotalMilliseconds);
            return response;
        }
        catch (Exception ex) when (ex is HttpRequestException or TaskCanceledException)
        {
            log.LogWarning(ex, "{Method} {Path} failed after {Ms:0} ms", request.Method,
                request.RequestUri?.AbsolutePath, Stopwatch.GetElapsedTime(start).TotalMilliseconds);
            throw;                                        // observe, don't swallow
        }
    }
}

// Wire it by hand: outermost first. This is all IHttpClientFactory does for you.
var primary = new SocketsHttpHandler { PooledConnectionLifetime = TimeSpan.FromMinutes(5) };
var pipeline = new TimingHandler(logger) { InnerHandler = new CorrelationHandler { InnerHandler = primary } };
var client = new HttpClient(pipeline) { BaseAddress = new Uri("https://orders.internal"), Timeout = TimeSpan.FromSeconds(10) };

Five rules make the difference between a handler that works in a demo and one that survives production:

  • Be stateless or thread-safe. One handler instance serves every concurrent request on that client. Never keep per-request state in a field.
  • Don't swallow exceptions or cancellation. Observe them, add context, rethrow. Return a fabricated response only when that is the explicit job of the layer (a fallback or a cache).
  • Pass the CancellationToken through. Every await inside a handler should observe the token you were given, or the caller's timeout cannot stop you.
  • Dispose responses you throw away. A retry handler that drops a 503 must call response.Dispose() before trying again; otherwise the connection is not returned to the pool until the GC finds it.
  • Don't mutate shared things. Set headers on the request, never on HttpClient.DefaultRequestHeaders from inside a handler: those are shared by every concurrent call.

Tip Need a per-call switch, like "skip auth for this one request" or "this call is idempotent, retry it"? Don't add a header that leaks onto the wire. Use HttpRequestMessage.Options: request.Options.Set(new HttpRequestOptionsKey<bool>("Idempotent"), true) at the call site, request.Options.TryGetValue(...) inside the handler. Other stacks have the same idea: OkHttp Request.tag(), Go context.WithValue, httpx request.extensions.

Testing a handler: put a fake at the core

Because the core is just another HttpMessageHandler, you test a handler by giving it a fake inner handler that records the request and returns a canned response. No network, no mocking library, and it runs in microseconds.

sealed class StubHandler(Func<HttpRequestMessage, HttpResponseMessage> respond) : HttpMessageHandler
{
    public List<HttpRequestMessage> Seen { get; } = [];
    protected override Task<HttpResponseMessage> SendAsync(HttpRequestMessage r, CancellationToken ct)
    {
        Seen.Add(r);
        return Task.FromResult(respond(r));
    }
}

[Fact]
public async Task Adds_correlation_id_once()
{
    var stub = new StubHandler(_ => new HttpResponseMessage(HttpStatusCode.OK));
    var client = new HttpClient(new CorrelationHandler { InnerHandler = stub }) { BaseAddress = new("https://x") };

    await client.GetAsync("/a");

    Assert.Single(stub.Seen[0].Headers.GetValues("x-correlation-id"));
}

HttpClient lifetimes: socket exhaustion vs stale DNS

Before handlers can be useful, the thing at the core has to be used correctly. Every client library keeps a connection pool inside its primary handler or transport. A pooled connection has already paid for DNS, the TCP handshake and the TLS handshake (often 50–150 ms across regions), and the next request on it pays nothing. Two opposite mistakes break this, and the fix for one tends to cause the other.

A new client per call: socket exhaustion

using var http = new HttpClient() creates a new pool, opens a new connection, and closes it at the end of the using. The side that closes a TCP connection first keeps the port in TIME_WAIT (60 s on Linux, up to 240 s on Windows) so stray packets can't confuse a new connection. At a few hundred calls a second you run out of ephemeral ports (about 16k on Windows, 28k on Linux) and new calls fail with SocketException: Only one usage of each socket address.... Each call also pays a full TLS handshake.

One client forever: stale DNS

A static readonly HttpClient fixes that: few connections, all reused. But a connection is bound to the IP address it resolved when it was opened. If the downstream moves (blue/green swap, failover, a Kubernetes service behind a changing load balancer IP), long-lived connections keep talking to the old address until something closes them. Failover appears to "not work" for this one service.

Long-lived pool, bounded connection age

Keep one pool, but retire each connection after a few minutes, so DNS is re-resolved on a rolling basis. In .NET: SocketsHttpHandler.PooledConnectionLifetime, or IHttpClientFactory, which rotates whole handlers every HandlerLifetime (2 minutes by default). Both give you reuse and freshness.

The simulation below runs a 10 ms-tick model of a client pool for ten minutes: requests arrive at a steady rate, take about 40 ms each, connections are opened, reused, idled out and closed, closed sockets sit in TIME_WAIT, and at the DNS mark the service moves to a new IP. The top chart is sockets in use (open plus TIME_WAIT) against the port limit; the bottom chart is the share of requests in each 10 s that succeeded, hit the old IP, or failed to get a socket. Try each strategy, then try raising the rate.

IHttpClientFactory: what it actually does

AddHttpClient registers a factory that pools HttpMessageHandler chains, not HttpClient objects. Each time you ask for a client you get a cheap new HttpClient wrapping a pooled handler chain. Every HandlerLifetime the factory builds a fresh chain for new clients; the old chain stays alive until the clients that use it are gone, and then it is disposed, closing its connections.

There are three ways to ask the factory for a client, and they produce exactly the same pipeline:

builder.Services.AddHttpClient<OrdersClient>(c => c.BaseAddress = new("https://orders.internal"))
    .AddHttpMessageHandler<AuthHandler>()
    .AddStandardResilienceHandler();

// Registered as TRANSIENT. Inject it where you need it; don't store it in a singleton.
public sealed class OrdersClient(HttpClient http)
{
    public Task<Order?> GetAsync(int id, CancellationToken ct) => http.GetFromJsonAsync<Order>($"/orders/{id}", ct);
}

builder.Services.AddHttpClient("orders", c => c.BaseAddress = new("https://orders.internal"))
    .AddHttpMessageHandler<AuthHandler>();

public sealed class CheckoutService(IHttpClientFactory factory)
{
    public async Task<Order?> GetAsync(int id, CancellationToken ct)
    {
        var http = factory.CreateClient("orders");          // cheap: a new wrapper over a pooled chain
        return await http.GetFromJsonAsync<Order>($"/orders/{id}", ct);
    }
}

builder.Services.AddHttpClient();                            // default (unnamed) client, no handlers

public sealed class Probe(IHttpClientFactory factory)
{
    public Task<HttpResponseMessage> PingAsync(Uri uri, CancellationToken ct) =>
        factory.CreateClient().GetAsync(uri, ct);
}

Pitfall: the captive typed client A typed client injected into a singleton is captured forever, so its handler chain never rotates and you are back to stale DNS (and any scoped service a handler depends on is captured too). This is the same captive-dependency bug as in DI Lifetimes. If a singleton needs HTTP, inject IHttpClientFactory and call CreateClient per operation, or use a single HttpClient over a SocketsHttpHandler with PooledConnectionLifetime set.

Handlers also have a DI subtlety: each handler chain is created in its own DI scope, which lives as long as the chain (minutes), not as long as your HTTP request. A handler that injects a scoped service such as a DbContext or "the current user" gets a different instance from the one your controller sees. To use request data, read it explicitly (for example through IHttpContextAccessor, or by putting it on request.Options at the call site) rather than injecting scoped services into handlers.

Insight Go's MaxIdleConnsPerHost = 2 is the quiet killer for service-to-service traffic: with 50 concurrent requests to one host, 48 connections are closed every time a burst ends and reopened on the next burst, which looks like socket exhaustion in slow motion. Set MaxIdleConnsPerHost (and MaxConnsPerHost if you want a cap) on a transport you own. The simulator's last strategy shows the churn.

Cross-cutting concerns that belong in the pipeline

These are the concerns that are the same for every call to a given downstream service, so the call site should never see them. Each one has a natural place in the chain.

Auth: token injection and refresh

Injecting a token is one line; refreshing it correctly under concurrency is where most hand-written handlers go wrong. Picture 20 concurrent requests that all get 401 the moment the token expires. If each one calls the identity provider, you get 20 refresh calls (a stampede, the same shape as a cache stampede in Caching). Worse, if the IdP rotates refresh tokens (each refresh token is single-use, as the OAuth 2.0 Security Best Current Practice recommends for public clients), the second caller presents a refresh token that was just used. The IdP treats that as theft and revokes the whole token family: the user is logged out.

The fix is the same as for a cache miss: single-flight. Only one refresh runs at a time; everyone who finds the token expired waits for that one result. Better still, refresh proactively, a little before expiry (the skew), so requests rarely see a 401 at all.

The "seen" token is the subtle part. A caller that got a 401 passes the token it used to the refresh method. Inside the lock, if the current token is no longer the one it saw, somebody else already refreshed, and it simply uses the new one. Without that check, the callers queued behind the lock would each refresh again, one after another.

public sealed class TokenCache(IIdentityClient idp, TimeProvider time)   // register as SINGLETON
{
    private static readonly TimeSpan Skew = TimeSpan.FromMinutes(1);
    private readonly SemaphoreSlim _gate = new(1, 1);
    private volatile AccessToken? _current;

    public async ValueTask<AccessToken> GetAsync(CancellationToken ct)
    {
        var t = _current;
        if (t is not null && t.ExpiresAt - Skew > time.GetUtcNow()) return t;   // fast path, no lock
        return await RefreshAsync(t, ct);                                       // proactive refresh
    }

    public async Task<AccessToken> RefreshAsync(AccessToken? seen, CancellationToken ct)
    {
        await _gate.WaitAsync(ct);                                              // single flight
        try
        {
            if (!ReferenceEquals(_current, seen)) return _current!;             // someone beat us to it
            return _current = await idp.RefreshAsync(ct);
        }
        finally { _gate.Release(); }
    }
}

public sealed class AuthHandler(TokenCache tokens) : DelegatingHandler            // register as TRANSIENT
{
    protected override async Task<HttpResponseMessage> SendAsync(HttpRequestMessage req, CancellationToken ct)
    {
        var token = await tokens.GetAsync(ct);
        req.Headers.Authorization = new("Bearer", token.Value);
        var res = await base.SendAsync(req, ct);
        if (res.StatusCode != HttpStatusCode.Unauthorized) return res;

        res.Dispose();                                      // give the connection back
        token = await tokens.RefreshAsync(token, ct);       // N callers, one IdP call
        req.Headers.Authorization = new("Bearer", token.Value);
        return await base.SendAsync(req, ct);               // retry exactly once
    }
}

// OkHttp: an interceptor adds the token; an Authenticator handles 401 (OkHttp calls it for you).
final class TokenCache {
    private Token current;
    synchronized Token current() {
        if (current == null || current.expiresAt().minusSeconds(60).isBefore(Instant.now()))
            current = idp.refresh(current);                       // proactive, under the same lock
        return current;
    }
    synchronized Token refreshIfStill(String failedHeader) {      // single flight via the monitor
        if (current != null && !("Bearer " + current.value()).equals(failedHeader)) return current;
        current = idp.refresh(current);
        return current;
    }
}

final class TokenAuthenticator implements Authenticator {
    private final TokenCache tokens;
    TokenAuthenticator(TokenCache tokens) { this.tokens = tokens; }

    @Override public Request authenticate(Route route, Response response) {
        if (response.priorResponse() != null) return null;        // already retried once: give up
        String failed = response.request().header("Authorization");
        Token fresh = tokens.refreshIfStill(failed);
        return response.request().newBuilder().header("Authorization", "Bearer " + fresh.value()).build();
    }
}

OkHttpClient client = new OkHttpClient.Builder()
    .addInterceptor(chain -> chain.proceed(chain.request().newBuilder()
        .header("Authorization", "Bearer " + tokens.current().value()).build()))
    .authenticator(new TokenAuthenticator(tokens))
    .build();
// Spring: RestClient.builder().requestInterceptor(new OAuth2ClientHttpRequestInterceptor(manager))

import threading, time, httpx

class TokenCache:
    def __init__(self, fetch, skew=60.0):
        self._fetch, self._skew = fetch, skew      # fetch() -> Token(value, expires_at)
        self._lock = threading.Lock()
        self._tok = None

    def current(self):
        tok = self._tok
        if tok is not None and tok.expires_at - self._skew > time.time():
            return tok                              # fast path, no lock
        return self.refresh(seen=tok)

    def refresh(self, seen):
        with self._lock:                            # single flight
            if self._tok is not seen:               # someone else refreshed while we waited
                return self._tok
            self._tok = self._fetch()
            return self._tok

class BearerAuth(httpx.Auth):                       # httpx's built-in hook for exactly this
    def __init__(self, tokens: TokenCache):
        self.tokens = tokens

    def auth_flow(self, request):
        tok = self.tokens.current()
        request.headers["Authorization"] = f"Bearer {tok.value}"
        response = yield request                    # send, and get the response back
        if response.status_code == 401:
            tok = self.tokens.refresh(seen=tok)
            request.headers["Authorization"] = f"Bearer {tok.value}"
            yield request                           # retry exactly once

client = httpx.Client(base_url="https://orders.internal", auth=BearerAuth(tokens))

// golang.org/x/oauth2 already does single-flight refresh: ReuseTokenSource holds a mutex
// and refreshes shortly before expiry. Wrap any transport with it.
src := (&clientcredentials.Config{
    ClientID:     id,
    ClientSecret: secret,
    TokenURL:     "https://login.example.com/oauth2/token",
    Scopes:       []string{"orders.read"},
}).TokenSource(ctx)

client := &http.Client{
    Timeout: 10 * time.Second,
    Transport: &oauth2.Transport{
        Source: oauth2.ReuseTokenSource(nil, src), // cached, refreshed once, goroutine-safe
        Base:   otelhttp.NewTransport(http.DefaultTransport),
    },
}

type Token = { value: string; expiresAt: number };
let current: Token | undefined;
let inflight: Promise<Token> | undefined;          // the single flight

function refresh(seen?: Token): Promise<Token> {
  if (current !== seen && current) return Promise.resolve(current);   // already refreshed
  inflight ??= fetchToken()
    .then((t) => (current = t))
    .finally(() => { inflight = undefined; });
  return inflight;
}

async function getToken(): Promise<Token> {
  if (current && current.expiresAt - 60_000 > Date.now()) return current;
  return refresh(current);
}

export const withAuth = (next: typeof fetch): typeof fetch => async (input, init) => {
  let tok = await getToken();
  const send = (t: Token) => {
    const headers = new Headers(init?.headers);
    headers.set("Authorization", `Bearer ${t.value}`);
    return next(input, { ...init, headers });
  };
  const res = await send(tok);
  if (res.status !== 401) return res;
  await res.body?.cancel();                         // release the connection
  tok = await refresh(tok);
  return send(tok);                                 // retry exactly once
};

In real projects, prefer the library that already does this: Azure.Identity / MSAL (token caches with proactive refresh), Duende.AccessTokenManagement for ASP.NET Core, Spring Security's OAuth2 client interceptors, golang.org/x/oauth2, authlib's httpx integration. Write your own only when you understand why the "seen" check is there.

Pitfall: retrying a 401 forever A refresh that returns a token the server still rejects (wrong audience, wrong scope, revoked client) leads to an infinite 401 → refresh → 401 loop. Retry exactly once, and treat a second 401 as a real error. OkHttp's priorResponse() check and the "retry once" line above are both doing this.

Trace and correlation propagation

A distributed trace only exists if every hop forwards the context it received. The W3C Trace Context standard puts it in one header:

traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
             ver  trace-id (same for the whole request)  parent span-id   flags (01 = sampled)

The server side extracts it (that is request pipeline middleware), and the client side has to inject it on every outbound call. That is a handler's job. If one hop forgets, the trace splits in two: the downstream service starts a brand-new trace, and nobody can join the halves when debugging an incident. Pick the broken hop below and watch the waterfall fall apart.

The good news is that you rarely write this handler yourself:

Stack Who injects traceparent on outbound calls
.NET Built in: HttpClient's diagnostics handler creates the client Activity and injects the header. Add AddHttpClientInstrumentation() (OpenTelemetry) to export the spans.
Java OpenTelemetry Java agent (zero code), or the OkHttp / Spring instrumentation libraries; Spring Boot 3 with Micrometer Tracing instruments RestClient / WebClient built from the auto-configured builders.
Python HTTPXClientInstrumentor().instrument(), RequestsInstrumentor().instrument(), or opentelemetry-instrument for zero-code.
Go You: wrap the transport with otelhttp.NewTransport(base) and pass req.Context() down, or the context is lost.
Node / TS OpenTelemetry UndiciInstrumentation (for fetch) and HttpInstrumentation; register them before your code loads.

Two neighbouring concerns travel the same way:

  • Baggage (baggage: header): key-value pairs such as tenant=contoso that every hop can read. Useful, but it is sent to every downstream, including third parties: never put secrets or personal data in it, and strip it at your trust boundary.
  • Custom correlation headers (X-Correlation-Id, X-Request-Id, X-Tenant): for these, ASP.NET Core has header propagation, which copies selected incoming headers onto outgoing calls:
builder.Services.AddHeaderPropagation(o => o.Headers.Add("X-Correlation-Id"));
builder.Services.AddHttpClient<OrdersClient>().AddHeaderPropagation();   // a DelegatingHandler
app.UseHeaderPropagation();                                              // middleware that captures them

Tip: in Go, the context is the propagation otelhttp.NewTransport reads the current span from req.Context(). Build outbound requests with http.NewRequestWithContext(ctx, ...), using the ctx of the incoming request, never context.Background(). The same ctx also carries cancellation and the deadline, which is why it matters even more for Resilience.

See Observability for spans, sampling and exporters.

Logging and redaction

An outbound log line should say what was called, how it ended and how long it took. It should not contain the bearer token, the cookie, the API key in the query string or the customer's card number in the body. That's an easy rule to state and easy to break: the first time someone debugs with LogInformation("{Request}", request), the Authorization header goes to your log store, where far more people can read it than can read your secrets vault.

Logs everything

GET https://pay.example.com/v1/charges?api_key=sk_live_51H...
Authorization: Bearer eyJhbGciOi...
{"card":"4111111111111111","cvc":"123"}
-> 200 in 182 ms

Logs the shape

GET pay.example.com /v1/charges?api_key=[REDACTED]
-> 200 in 182 ms (attempt 1 of 1)
headers: Authorization=[REDACTED] (allow-list only)
body: not logged

Rules that hold in every language:

  1. Allow-list headers, don't block-list them. New sensitive headers will appear; an allow-list stays safe by default.
  2. Redact query strings (or log only the path template, such as /orders/{id}). Tokens and signatures end up in URLs more often than you would hope.
  3. Don't log bodies by default. If you must, sample them, cap their size, run them through a redactor, and never for auth endpoints.
  4. Log duration per attempt and per logical call. That is exactly the "logging both outside and inside retry" trick from the chain demo.
  5. Read streamed bodies only once. A logging handler that buffers the response "to log it" breaks streaming and doubles memory.

Library support: .NET 8+ has Microsoft.Extensions.Http.Diagnostics with AddExtendedHttpClientLogging() plus the redaction framework (Microsoft.Extensions.Compliance.Redaction), and RemoveAllLoggers() / AddLogger<T>() to replace the default logging handlers. OkHttp's HttpLoggingInterceptor has redactHeader("Authorization") and levels (BASIC does not log bodies). Logbook (Zalando) does the same for Spring. In Python and Go you usually write a small hook or transport yourself; keep the allow-list in one place.

Retries and timeouts: one layer, one owner

Retries and timeouts belong in the outbound pipeline, and they are deep enough to deserve a page of their own: Resilience. Three rules matter here, because they are about where they go:

  • Exactly one retry layer per hop. If the SDK retries 3 times, your handler retries 3 times and Polly retries 3 times, one slow dependency gets 27 calls. Find out which layers already retry: the Azure SDKs, the AWS SDKs, urllib3.Retry, gRPC service config, OkHttp's retryOnConnectionFailure and service meshes all can.
  • Set every timeout explicitly. Defaults range from 100 s (.NET) to forever (Go http.Client, Python requests, Node fetch). An infinite timeout turns one slow dependency into a thread or socket leak in every caller.
  • Total timeout outside retry, attempt timeout inside. Otherwise a "3 retries with a 10 s timeout" policy can take 30 s plus backoff, which is longer than your own caller is willing to wait.
builder.Services.AddHttpClient<OrdersClient>()
    .AddStandardResilienceHandler();   // rate limiter → total timeout → retry → breaker → attempt timeout

Compression

The primary handler can negotiate compression and decompress responses transparently. Do it there, not in a handler of your own.

Compressing request bodies is rarer and needs the server's agreement (Content-Encoding: gzip on a POST). It's worth it for large JSON uploads to services that support it. Don't compress small payloads (below about 1 KB the CPU cost is larger than the saving), and never compress secrets alongside attacker-controlled text in the same compressed stream over TLS (that is how the CRIME/BREACH attacks work).

type Middleware func(http.RoundTripper) http.RoundTripper

type roundTripperFunc func(*http.Request) (*http.Response, error)

func (f roundTripperFunc) RoundTrip(r *http.Request) (*http.Response, error) { return f(r) }

func Timing(log *slog.Logger) Middleware {
    return func(next http.RoundTripper) http.RoundTripper {
        return roundTripperFunc(func(req *http.Request) (*http.Response, error) {
            req = req.Clone(req.Context()) // RoundTrip must not modify the caller's request
            req.Header.Set("X-Correlation-Id", CorrelationID(req.Context()))
            start := time.Now()
            res, err := next.RoundTrip(req) // call next
            if err != nil {
                log.Warn("outbound failed", "host", req.URL.Host, "ms", time.Since(start).Milliseconds(), "err", err)
                return nil, err
            }
            log.Info("outbound", "method", req.Method, "host", req.URL.Host,
                "status", res.StatusCode, "ms", time.Since(start).Milliseconds())
            return res, nil
        })
    }
}

    for i := len(mws) - 1; i >= 0; i-- {
        base = mws[i](base)
    }
    return base
}

Who runs first? Registration order is not the same everywhere

This is the most common source of "my auth header is missing in the logs" bugs. In most libraries the first one registered is the outermost, but not in all of them, and some of them (axios, httpx hooks) aren't an onion at all. OkHttp: application interceptors vs network interceptors

OkHttp has two places to add interceptors, on either side of its own built-in layers (retry and redirects, the bridge that adds Host/Accept-Encoding/cookies, the HTTP cache, and the connection setup). Which one you pick changes what your interceptor sees and how often it runs.

addInterceptor (application)

  • Runs once per call, even if OkHttp follows redirects or retries a dead route.
  • Sees the request as your code built it and the final response (decompressed, after redirects).
  • Runs even for cache hits (no network at all).
  • May short-circuit (return a response without calling proceed) or call proceed more than once.
  • Use for: auth, logging the logical call, correlation IDs, metrics per call.

addNetworkInterceptor (network)

  • Runs once per network request: twice for a redirect, never for a cache hit.
  • Sees the real wire request, including Host, Accept-Encoding: gzip and conditional cache headers, and the raw (still gzip) response.
  • Has access to chain.connection() (the route, IP and TLS handshake in use).
  • Must call proceed exactly once.
  • Use for: wire-level debugging, per-hop metrics, inspecting what was actually sent.

Python: hooks, transports and Auth

Python's two big clients give you three different tools, and only one of them is an onion:

  • event_hooks={"request": [...], "response": [...]} (httpx) and hooks={"response": ...} (requests) are flat callbacks. A request hook can't see the response, can't time the call (except by stashing a start time on the request's extensions), and can't retry. They're perfect for "log the URL" and "call raise_for_status() on every response".
  • A custom transport (httpx.BaseTransport / AsyncBaseTransport) wraps the real transport, so it is a true decorator: timing, retries, circuit breaking and test fakes all belong here. httpx.MockTransport(handler) is the built-in stub for tests.
  • httpx.Auth.auth_flow is a generator built for auth: yield request sends it, the response comes back, and you may yield again (once) after refreshing. That is the cleanest refresh-on-401 in any language.

With requests, the transport-level extension point is the HTTPAdapter, mounted per URL prefix; urllib3's Retry plugs in there:

Go: the RoundTripper contract

The http.RoundTripper documentation is short and strict, and every rule matters for a middleware:

  1. Don't modify the request. Clone it (req.Clone(ctx)) before setting headers; the caller may reuse it, and other goroutines may be reading it.
  2. Don't interpret the response. A RoundTripper returns an error only for transport failures; a 500 is a successful round trip. (Your middleware may still decide to retry on 503, as long as it closes the first body.)
  3. Always close the body. If you discard a response (for example before a retry), drain and close it (io.Copy(io.Discard, res.Body); res.Body.Close()), or the connection is not returned to the pool.
  4. Be safe for concurrent use. One Transport is shared by every goroutine.
  5. Retrying needs a replayable body: set req.GetBody (done automatically for bytes.Reader, bytes.Buffer and strings.Reader bodies) and call it for each new attempt.

TypeScript: fetch wrappers vs axios interceptors

fetch has no interceptor API, which turns out to be an advantage: a (next) => fetch wrapper is a real onion, fully typed and trivially testable (pass a fake next). axios has interceptors, but request and response interceptors are two separate lists, not one wrapping chain, so "time this call" needs a side channel:

gRPC interceptors: the same onion over HTTP/2

gRPC clients have interceptors with exactly the same shape, and the same concerns go there: metadata (gRPC's headers), auth, deadlines, logging and tracing. Two gRPC-specific points:

  • Deadlines are part of the protocol. A client deadline travels as the grpc-timeout header, so the server knows how long it has. An interceptor that sets a default deadline when the caller didn't is one of the most valuable five lines you can write; without one, a gRPC call can wait forever.
  • Retries and hedging can be configured in the service config (retryPolicy, hedgingPolicy) instead of in an interceptor. Use one or the other, not both.
public sealed class DefaultsInterceptor : Interceptor
{
    public override AsyncUnaryCall<TRes> AsyncUnaryCall<TReq, TRes>(TReq request,
        ClientInterceptorContext<TReq, TRes> context, AsyncUnaryCallContinuation<TReq, TRes> continuation)
    {
        var headers = context.Options.Headers ?? new Metadata();
        headers.Add("x-correlation-id", Correlation.CurrentOrNew());
        var options = context.Options.WithHeaders(headers);
        if (options.Deadline is null) options = options.WithDeadline(DateTime.UtcNow.AddSeconds(5));
        return continuation(request, new ClientInterceptorContext<TReq, TRes>(context.Method, context.Host, options));
    }
}

In-process pipelines: MediatR-style behaviors

The onion doesn't need a network. When an application sends commands and queries through a mediator (await mediator.Send(new PlaceOrder(...))), the mediator can wrap every handler in a pipeline of behaviors: logging, authorization, validation, transactions, caching, metrics. It is the same pattern as middleware, one level further in: cross-cutting concerns around use cases instead of around HTTP requests.

The order matters here just as much, and the failures are more expensive: validate inside a transaction and every invalid request opens (and rolls back) a database transaction; authorize after validation and an unauthenticated caller learns which fields your command has. Reorder the behaviors and send different commands:

public sealed class ValidationBehavior<TReq, TRes>(IEnumerable<IValidator<TReq>> validators)
    : IPipelineBehavior<TReq, TRes> where TReq : notnull
{
    public async Task<TRes> Handle(TReq request, RequestHandlerDelegate<TRes> next, CancellationToken ct)
    {
        var results = await Task.WhenAll(validators.Select(v => v.ValidateAsync(request, ct)));
        var failures = results.SelectMany(r => r.Errors).ToList();
        if (failures.Count > 0) throw new ValidationException(failures);   // short-circuit: no handler, no transaction
        return await next();                                                // call the next behavior (or the handler)
    }
}

C, R = TypeVar("C"), TypeVar("R")
Handler = Callable[[C], Awaitable[R]]

def build(handler: Handler, *behaviors: Behavior) -> Handler:
    """First behavior listed = outermost, like the C# registration."""
    for behavior in reversed(behaviors):
        handler = (lambda b, nxt: lambda cmd: b(cmd, nxt))(behavior, handler)
    return handler

type Handler[C, R any] func(ctx context.Context, cmd C) (R, error)
type Behavior[C, R any] func(next Handler[C, R]) Handler[C, R]

// Build wraps in reverse so the first behavior listed is the outermost.
func Build[C, R any](h Handler[C, R], bs ...Behavior[C, R]) Handler[C, R] {
    for i := len(bs) - 1; i >= 0; i-- {
        h = bs[i](h)
    }
    return h
}

func Validation[C interface{ Validate() error }, R any](next Handler[C, R]) Handler[C, R] {
    return func(ctx context.Context, cmd C) (R, error) {
        if err := cmd.Validate(); err != nil {
            var zero R
            return zero, err // short-circuit
        }
        return next(ctx, cmd)
    }
}

If you can't take that on, alternatives with the same pipeline idea are the source-generated Mediator library (martinothamar/Mediator), Wolverine (middleware around message handlers), or no library at all: a handful of decorators registered in DI (see Structural Patterns, Decorator) give you the same onion with less magic.

A mediator pipeline earns its keep when

  • You have many use cases (dozens of commands) that all need the same 3–5 concerns.
  • You want transactions, auditing and authorization to be impossible to forget on a new command.
  • Handlers are invoked from several entry points (HTTP, a queue consumer, a scheduled job) and the concerns must apply to all of them, which HTTP middleware can't do.

It's ceremony when

  • There are five endpoints and each calls one service method. The indirection costs more to read than it saves.
  • It's used for queries that just read a row: "Go to definition" on Send(new GetOrder(id)) lands on an interface, not on code.
  • The behaviors duplicate what HTTP middleware already does (auth, logging) for HTTP-only apps.
  • Handlers call mediator.Send on each other: now the pipeline runs twice and transactions nest unexpectedly.

When to use a pipeline layer, and when not to

Not every outbound concern deserves a handler. A handler is code that runs on every call through that client, invisibly. That's the point, and also the risk.

Concern Handler? Why
Bearer token / API key Yes Same for every call; refresh needs a shared cache and single-flight
Correlation / tenant header Yes (or header propagation) Same for every call; forgetting it once breaks debugging
Tracing Use the instrumentation It also creates spans and follows the semantic conventions
Retry, timeout, circuit breaker Yes, via a resilience library Order and jitter are easy to get wrong; see Resilience
Logging with redaction Yes, one place A single allow-list is the only way redaction stays correct
Caching responses Rarely HTTP caching semantics (Vary, revalidation) are subtle; cache domain objects in the caller instead (see Caching)
Mapping errors to exceptions No That's the typed client's job: OrdersClient turns 404 into null and 409 into OrderConflict
Business rules ("skip if VIP") Never Invisible behavior in plumbing is how bugs hide for months
Request signing (HMAC, AWS SigV4) Yes, innermost It must sign the final bytes and headers, after everything else changed them

Pitfalls and war stories

Pitfall: a handler that buffers the body A logging handler did await response.Content.ReadAsStringAsync() "to log errors". It worked fine until the service started streaming 2 GB exports: every export was buffered in memory, and the pods were OOM-killed. Fix: never read bodies in a general-purpose handler; if you need error details, read at most a few KB, and only for non-success status codes with a known small content type.

Pitfall: sending the same request twice from the outside HttpClient.SendAsync(request) throws InvalidOperationException if you pass the same HttpRequestMessage again, and a request with a streamed body can't be replayed at all. Retrying inside a handler (re-sending request to base.SendAsync) is fine for buffered content; that is how the resilience handlers work. Fix: retry inside the pipeline, not around HttpClient, and buffer bodies you intend to retry (or don't retry non-idempotent streamed uploads).

Pitfall: Go response bodies never closed A Go service gradually slowed and then hit "too many open files". A retry middleware returned on 503 without closing the first response's body, so every retried call leaked a connection. Fix: io.Copy(io.Discard, res.Body); res.Body.Close() before every retry and every discarded response, and a lint rule (bodyclose) in CI.

Pitfall: a scoped service inside a handler An AuthHandler injected ICurrentUser (scoped) to forward the user's identity. Because handler chains live in their own long-lived scope, requests for user B were sent with user A's identity for up to two minutes. Fix: never inject per-request services into handlers; pass the identity on request.Options, or use header propagation, which captures headers per request correctly.

Pitfall: the token in the trace An enrichment handler added all request headers as span attributes "for debugging". The tracing backend had a 30-day retention and broad read access, so every bearer token was readable there. Fix: an allow-list, as for logs; tracing data is log data.

Pitfall: two retry layers The Azure SDK client retried 3 times with backoff, and the team wrapped it in a Polly retry with 3 more attempts. During a storage incident each user request made 16 calls and took over a minute, which kept the incident going for longer. Fix: one retry owner per hop; turn the outer one off or configure the SDK with MaxRetries = 0.

Best-practice checklist

Share the pool

One long-lived client (or IHttpClientFactory) per downstream. Never a new client per call.

Bound connection age

PooledConnectionLifetime or factory rotation, so DNS changes are picked up within minutes.

Set every timeout

Connect, attempt and total. Never rely on 100 s, or on "none".

One retry owner

Exactly one layer retries per hop, idempotent calls only, with jitter.

Auth with single-flight

Proactive refresh with a skew, one refresh at a time, retry a 401 exactly once.

Propagate context

traceparent on every hop; pass the incoming ctx/token down; no secrets in baggage.

Redact by allow-list

Headers and query strings allow-listed; bodies off by default; same for spans.

Test the order

A unit test with a stub at the core asserts the layer order and the headers on the wire.

  • [ ] Every outbound client has a name, a base address and explicit timeouts.
  • [ ] Typed clients are not captured by singletons; handlers don't inject scoped services.
  • [ ] Response bodies are always disposed / closed, including on error and retry paths.
  • [ ] Only one layer retries; SDK retries are accounted for.
  • [ ] Logs and spans contain no tokens, cookies, keys or personal data.
  • [ ] Outbound calls appear as child spans of the incoming request in your tracing tool.
  • [ ] The handler order is written down in a test, not only in someone's head.

Self-check

You register .AddHttpMessageHandler<LoggingHandler>() and then .AddStandardResilienceHandler(). A call fails twice and then succeeds. How many log lines does LoggingHandler write?

One. It was added first, so it is outermost, outside the retry. It sees one logical call, with a duration that includes both failures and the backoff. Register it after the resilience handler and you get three lines, one per attempt. Both are useful; the factory's built-in logging gives you both.

Why doesn't a static readonly HttpClient exhaust sockets, and what does it break instead?

It keeps one pool, so connections are reused and few ever enter TIME_WAIT. But connections never close on their own, so they keep using the IP address resolved when they were opened. After a DNS change (failover, blue/green) the client keeps talking to the old address. Fix it with PooledConnectionLifetime or IHttpClientFactory.

Twenty requests get a 401 at the same moment. With single-flight refresh, how many calls reach the identity provider, and why does the "seen token" check matter?

One. The first caller takes the lock and refreshes; the others wait. When each waiting caller gets the lock, it compares the current token with the one it saw fail. They differ, so it uses the new token without refreshing. Without the check, each of the 19 would refresh in turn, and with rotating refresh tokens the second one would reuse a spent refresh token and revoke the whole family.

OkHttp: you want to log the exact Accept-Encoding header sent on the wire and the IP address you connected to. Application or network interceptor?

Network. Application interceptors run before OkHttp's bridge (which adds Accept-Encoding: gzip) and before a connection exists. A network interceptor sees the final wire request and has chain.connection(). It also runs once per redirect hop and not at all for cache hits.

In Go, you build a middleware chain with for _, mw := range mws { rt = mw(rt) }. Which middleware runs first?

The last one in the slice. Each iteration wraps the previous result, so the final wrap is the outermost. Iterate backwards if you want "first listed = outermost", as Chain above does.

A MediatR pipeline is registered as Logging, Transaction, Validation, Authorization. What goes wrong for an invalid command from an unauthorized user?

A transaction is opened before anything rejects the request, and the validation errors are returned to a user who isn't allowed to call the command at all (an information leak). Authorization should come before validation, and both should come before the transaction, so rejected requests cost nothing.

Your Go service calls another service, but the traces show two separate traces instead of one. Name two likely causes.
  1. The transport isn't wrapped with otelhttp.NewTransport, so nothing injects traceparent.
  2. The outbound request was built with context.Background() (or http.NewRequest without a context) instead of the incoming request's ctx, so there is no current span to propagate. (A third: a proxy or gateway in between strips the header.)
