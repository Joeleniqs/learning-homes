Functional Patterns in Mainstream Languages

Pure functions, composition, higher-order functions, pipelines, map/filter/reduce, and how functions replace many OO patterns.

Intermediate → Advanced~45 min studyBuilds on: Types, Immutability & Domain ModellingUpdated 2026-11-03

The problem: code you can't reason about locally

Here is a small pricing function from a real-looking codebase. Read it and predict what Quote(cart) returns.

public static class Pricing
{
    public static decimal TaxRate = 0.2m;                     // changed by an admin endpoint at runtime
    private static int _quotesToday;

    public static decimal Quote(Cart cart)
    {
        _quotesToday++;                                       // hidden write
        cart.Items.RemoveAll(i => i.Qty == 0);                // mutates the caller's object
        var subtotal = cart.Items.Sum(i => i.Price * i.Qty);
        if (DateTime.Now.DayOfWeek == DayOfWeek.Friday)       // hidden input: the clock
            subtotal *= 0.9m;
        if (_quotesToday > 1000) subtotal *= 1.05m;           // hidden input: call history
        return subtotal * (1 + TaxRate);                      // hidden input: a mutable global
    }
}

You can't. The answer depends on the day of the week, a global anyone can change, how many quotes ran before this one, and the call also changes the cart you passed in. To test it you need a fake clock, a reset of two statics, and a fresh cart per assertion. Running two quotes in parallel races on _quotesToday. Caching the result is wrong on Fridays and after quote 1000.

Now the same rules as a function of its inputs:

public static decimal Quote(IReadOnlyList<Item> items, DateOnly today, decimal taxRate, int quotesToday)
{
    var subtotal = items.Where(i => i.Qty > 0).Sum(i => i.Price * i.Qty);
    if (today.DayOfWeek == DayOfWeek.Friday) subtotal *= 0.9m;
    if (quotesToday > 1000) subtotal *= 1.05m;
    return subtotal * (1 + taxRate);
}

Every dependency is in the signature. The function changes nothing. The same arguments always give the same answer, so you can test it with one line per rule, run it on any thread and cache it by its arguments. The clock, the counter and the tax setting still exist, but they are read once, at the edge, by the code that calls Quote.

Functional patterns are about making behaviour depend only on what you can see. Push effects (I/O, time, randomness, mutation) to the edges, keep the middle made of functions that take values and return values, and build bigger behaviour by combining small functions instead of subclassing.

You do not need Haskell for this. C#, Java, Python, Go and TypeScript all have lambdas, closures and immutable records, and the mainstream frameworks are already functional underneath: LINQ and Java Streams are map/filter/reduce, ASP.NET Core middleware is function composition, React components are meant to be pure functions of props, Redux reducers are (state, action) => state. This page names the patterns so you can use them on purpose. It builds on types and immutability and the design principles, and it ends by showing which behavioral patterns quietly turn into a lambda.

Pure functions and referential transparency

A function is pure when two things hold:

  1. Its result depends only on its arguments. It doesn't read a clock, a random generator, a mutable field, a file, an environment variable or a database.
  2. It has no observable side effects. It doesn't write to anything outside itself: no mutation of arguments or globals, no logging, no I/O, no exceptions that depend on hidden state.

The payoff has a name: referential transparency. An expression is referentially transparent when you can replace it with its value without changing the program. If Price(3) is 7.5, every Price(3) in the program can become 7.5. That one property is what makes memoization, parallelism, reordering, lazy evaluation and simple unit tests safe.

The visualizer memoizes every call. Pick an impure version, change the global with rate=4, and watch the memo hand back a wrong answer. Then pick the refactored version: the hidden input became a parameter, so it is part of the cache key and the problem disappears.

Before and after

public class LateFeeService
{
    private readonly AppDbContext _db;
    public LateFeeService(AppDbContext db) => _db = db;

    public decimal Apply(int invoiceId)
    {
        var inv = _db.Invoices.Find(invoiceId)!;          // I/O
        var days = (DateTime.UtcNow - inv.DueDate).Days;  // clock
        if (days > 0)
            inv.Fee = Math.Min(days * 1.5m, inv.Amount * 0.1m); // mutation
        _db.SaveChanges();                                // I/O
        return inv.Fee;
    }
}

// Pure: easy to test exhaustively, no database or clock needed.
public static decimal LateFee(decimal amount, DateOnly due, DateOnly today)
{
    var days = today.DayNumber - due.DayNumber;
    return days <= 0 ? 0m : Math.Min(days * 1.5m, amount * 0.1m);
}

// Thin shell: does the I/O, calls the pure function, writes the result.
public decimal Apply(int invoiceId)
{
    var inv = _db.Invoices.Find(invoiceId)!;
    inv.Fee = LateFee(inv.Amount, inv.DueDate, DateOnly.FromDateTime(_clock.UtcNow));
    _db.SaveChanges();
    return inv.Fee;
}

The rule itself is now a five-line pure function. You test it with a table of (amount, due, today) → fee rows. The shell is so thin that one integration test covers it. This split has a name, functional core, imperative shell, and it is the single most useful functional pattern for everyday OO code.

What counts as a side effect?

Effect Example Why it breaks referential transparency Where it belongs
Reading the clock DateTime.Now, time.Now(), Date.now() Same call, different answer each second Pass today in; inject TimeProvider / Clock
Randomness Random.Shared, Math.random() Different answer every call Pass a seed or the random value in
Mutable global or static static decimal TaxRate Answer changes when someone else writes it Pass it as a parameter or config value
Mutating an argument list.Sort(), cart.Items.Remove(...) The caller's data changes under them Return a new value
I/O database, HTTP, file, console, logger Can fail, is slow, changes the world The imperative shell
Throwing on bad input throw new ArgumentException Arguably fine if it depends only on the input; it's a second return path Often better as a Result (below)

Logging is a side effect, and that's usually fine. Purity is a tool, not a religion. A debug log line inside a pure calculation doesn't change its answer, so caching and testing still work. What breaks things is an effect the result depends on, or one other code observes. Be strict about those and pragmatic about tracing.

Real framework examples

  • Redux / NgRx / Elm-style reducers: (state, action) => newState must be pure. That is what makes time-travel debugging and replaying actions possible.
  • React components and useMemo: rendering must be pure. Side effects go into useEffect, which is literally the imperative shell.
  • Java Streams: the docs require lambdas passed to map/filter to be non-interfering and stateless. Mutating a shared list inside forEach on a parallel stream is a race.
  • Spark, Flink, Beam, Kafka Streams: transformations must be deterministic so a failed partition can be recomputed on another machine and give the same result.
  • Build systems (Bazel, Nix, MSBuild incremental builds): a build step is cached by its inputs. If a step reads an undeclared file, the cache returns stale output.

When strict purity is the wrong goal

  • The code is mostly I/O. A controller that loads, saves and returns has nothing to extract. Don't invent a "pure core" that just forwards arguments.
  • A local mutable variable is clearer. A for loop that builds a StringBuilder inside a function is still pure from the outside. Purity is about the function's boundary, not about banning +=.
  • The hot path is allocation-sensitive. Returning new objects instead of updating in place costs allocations. In a tight loop, measure first (see When functional style hurts).

Immutability: values that can't change under you

Mutation itself isn't evil. Shared mutation is: two pieces of code holding a reference to the same object, one changes it, and the other is surprised. That is aliasing, and it causes some of the hardest bugs to find.

DEFAULT_TAGS = ["new"]

def make_product(name, tags=DEFAULT_TAGS):
    return {"name": name, "tags": tags}

a = make_product("lamp")
b = make_product("desk")
a["tags"].append("sale")
print(b["tags"])   # ['new', 'sale']  <- b changed because a and b share one list

The same bug shows up as a cached object that a caller edits (now every future cache hit is wrong), a DateTime-like value type that turns out to be a reference type, or a list handed to a background thread and then cleared by the sender. If values can't change, none of this is possible: sharing becomes free.

Default to immutable data; make mutation local and deliberate. A record, a frozen dataclass or a readonly type is safe to share across threads, cache, use as a dictionary key and pass to code you don't trust. When you need a change, create a new value with the change applied (with, replace, spread) and let the old one live on for whoever still holds it.

Immutable records in five languages

public sealed record Money(decimal Amount, string Currency);
public sealed record Order(Guid Id, ImmutableList<Line> Lines, Money Total);

public record Money(BigDecimal amount, String currency) {}

    public Order withTotal(Money t) { return new Order(id, lines, t); }
}

// There is no 'with' yet, so you write withX methods (JEP 468, "derived record
// creation", proposes one). List.copyOf gives an unmodifiable list.

type Money struct {

// readonly is compile-time only; Object.freeze is a shallow runtime check.
// 'as const' makes literals deeply readonly. Immer lets you write mutating
// code against a draft and gives you back a new, structurally shared object.

The five languages differ in how deep the guarantee goes, and it's the main trap:

Deep enough

  • C# record holding ImmutableList<T>, ImmutableDictionary, FrozenDictionary or other records.
  • Java record with List.copyOf / Map.copyOf in the compact constructor.
  • Python frozen dataclass holding tuples, frozenset, MappingProxyType or other frozen dataclasses.
  • TypeScript Readonly<T> / readonly T[] all the way down, or as const.

Looks immutable, isn't

  • C# record Order(List<Line> Lines): order.Lines.Add(...) works fine.
  • Java record holding an ArrayList passed in by the caller, who keeps a reference and edits it.
  • Python @dataclass(frozen=True) with a list field.
  • Go struct copied by value but containing a slice or map: both copies share the backing array.
  • Object.freeze(obj): nested objects stay mutable.

Persistent collections: changing a big structure cheaply

"Create a new value" sounds expensive for a list of a million items. It isn't, because immutable collections use structural sharing: a new version reuses every part of the old one that didn't change. For a tree, an insert copies only the nodes on the path from the root to the change, about log₂(n) of them, and points the copies at the untouched subtrees.

That is how ImmutableList<T> / ImmutableDictionary in .NET, Clojure's vectors and maps, Scala's collections, Immutable.js, Immer and Python's pyrsistent work (most use wide trees, 32-way tries, so a path is only a few nodes deep even for millions of items). The old version stays valid, which gives you three things almost for free:

  • Snapshots and undo: keep a reference to the previous version. Compare this with the memento pattern, which has to copy state explicitly.
  • Lock-free reads: a reader holding version 3 never sees a half-applied update. Writers publish a new root with one atomic reference swap (ImmutableInterlocked.Update in .NET, AtomicReference.updateAndGet in Java).
  • Cheap change detection: if the reference didn't change, nothing inside changed. React, Redux and Angular OnPush rely on this instead of deep comparisons.

Pick the right immutable collection in .NET. ImmutableList<T> is a tree: O(log n) for everything, slower indexed reads than List<T>. ImmutableArray<T> is a plain array wrapper: fast reads, but every "change" copies the whole array, so build it once with a builder. FrozenDictionary / FrozenSet (.NET 8+) are optimized for "build once at startup, read millions of times". Choose by your write/read ratio.

When immutability costs more than it saves

  • Large, hot, single-owner buffers: image processing, a game loop, a parser's working buffer. Nobody else sees them, so there is no aliasing to protect against, and copying would dominate the runtime.
  • Huge deep updates in a tight loop: changing one field five levels deep means rebuilding five records per change. Use a builder (ImmutableList.CreateBuilder, Immer's draft) or mutate a private copy and freeze it at the end.
  • ORM entities: EF Core and Hibernate track changes by mutating entity objects. Fighting that with immutable entities makes persistence painful. Keep entities mutable behind methods, and use immutable records for DTOs, events, commands and value objects (domain-driven design).

Higher-order functions and pipelines

A higher-order function takes a function as an argument or returns one. You use them constantly: list.Sort(comparer), button.addEventListener("click", handler), retry(3, () => call()), app.Use(next => ...). The point is to separate the shape of a computation (loop over items, keep some, transform them, combine them) from the specific decision at each step (which items, what transformation).

Three higher-order functions cover most data processing:

Operation Takes Returns Also called
map a collection and T → U a collection of the same length Select (LINQ), map (Streams, JS, Python), list comprehension [f(x) for x in xs]
filter a collection and T → bool a collection, maybe shorter Where, filter, [x for x in xs if p(x)]
reduce a collection, a seed and (acc, T) → acc one value Aggregate, reduce, fold, functools.reduce; specialised as Sum, Count, Max, groupBy

Chained, they form a pipeline: data goes in one end, each stage does one job, a result comes out the other end. Type a source and your own stages below. Then flip between eager (each stage runs over everything and builds a new array, like JavaScript's array methods) and lazy (one element travels all the way through before the next is read, like LINQ, Java Streams and Python generators). Watch the counters when a take is in the pipeline.

One pipeline, five languages

The task: the total of the three largest paid orders over 100, in euros.

var top3 = orders
    .Where(o => o.Status == Status.Paid && o.Total > 100m)
    .OrderByDescending(o => o.Total)
    .Take(3)
    .Sum(o => o.Total * fx.EurRate(o.Currency));
// LINQ to Objects is lazy and fused (yield-based iterators). Against EF Core,
// the same chain becomes an expression tree and is translated to SQL.
// Since .NET 9 there is also CountBy / AggregateBy for group-and-reduce.

BigDecimal top3 = orders.stream()
    .filter(o -> o.status() == Status.PAID && o.total().compareTo(HUNDRED) > 0)
    .sorted(Comparator.comparing(Order::total).reversed())
    .limit(3)
    .map(o -> o.total().multiply(fx.eurRate(o.currency())))
    .reduce(BigDecimal.ZERO, BigDecimal::add);
// Streams are lazy and single-use. Collectors.groupingBy / toMap / joining do
// most real-world reductions. Gatherers (final in Java 24) add custom stages.

from heapq import nlargest

paid = (o for o in orders if o.status == "paid" and o.total > 100)
top3 = sum(o.total * fx.eur_rate(o.currency)
           for o in nlargest(3, paid, key=lambda o: o.total))
# Pythonic style prefers comprehensions and generator expressions over
# map/filter with lambdas. itertools (islice, groupby, accumulate) covers
# the rest. functools.reduce exists but a for loop is usually clearer.

paid := make([]Order, 0, len(orders))

    if o.Status == Paid && o.Total > 100 {
        paid = append(paid, o)
    }
}
slices.SortFunc(paid, func(a, b Order) int { return cmp.Compare(b.Total, a.Total) })

    top3 += o.Total * fx.EurRate(o.Currency)
}
// Idiomatic Go uses plain loops. Generics (1.18) and iterators (iter.Seq, 1.23)
// make Map/Filter helpers possible, but the community still favours loops.

const top3 = orders
  .filter(o => o.status === "paid" && o.total > 100)
  .sort((a, b) => b.total - a.total)     // sorts in place! use toSorted() (ES2023)
  .slice(0, 3)
  .reduce((sum, o) => sum + o.total * fx.eurRate(o.currency), 0);
// Array methods are eager: every stage allocates a new array. For big or
// infinite sources, use generators or Iterator helpers (ES2025: .map/.filter/.take
// directly on iterators, which are lazy).

Go is the outlier on purpose. Go's designers value code that reads the same everywhere, and a for loop needs no knowledge of library combinators. With iter.Seq (Go 1.23) you can write lazy Filter/Map helpers, and slices/maps give you Collect, SortFunc, Index. Use them for reusable sequences; don't translate every LINQ chain into Go generics.

Eager vs lazy, side by side

Eager (JS arrays, Python lists, ToList() after each step) Lazy (LINQ, Java Streams, generators, iter.Seq)
When work happens Immediately, stage by stage When the result is consumed, element by element
Intermediate collections One per stage None (stages are fused)
take/first/any Every earlier stage already ran over everything Stops pulling from the source as soon as it's satisfied
Infinite sources Impossible Fine, as long as something downstream stops
Reusing the result Safe: it's a list Danger: re-runs (C#, Go), throws (Java) or is empty (Python, TS). See lazy sequences
Debugging Inspect each array Breakpoints jump between stages; harder to follow

Reduce is the general one

map, filter, count, sum, max, groupBy are all special cases of reduce. That's useful to know, and a bad thing to act on: a hand-written reduce is usually harder to read than the named operation.

const byCustomer = orders.reduce<Record<string, number>>(
  (acc, o) => ({ ...acc, [o.customer]: (acc[o.customer] ?? 0) + o.total }),
  {},
);
// Also O(n²): the spread copies the whole accumulator on every element.

const byCustomer = new Map<string, number>();
for (const o of orders) {
  byCustomer.set(o.customer, (byCustomer.get(o.customer) ?? 0) + o.total);
}
// Or: Object.groupBy(orders, o => o.customer) (ES2024), then sum each group.
// A local mutable Map inside a function is still a pure function from outside.

Side effects inside map and filter. items.map(x => { audit.log(x); return f(x); }) looks harmless. In a lazy pipeline it runs zero times (if nothing consumes the result), several times (if it's enumerated twice), or out of order (parallel streams). Keep lambdas in pipelines pure, and put effects in a final forEach/foreach that clearly does something.

Currying, partial application and composition

Two techniques let you build new functions out of existing ones without writing a class.

  • Partial application fixes some arguments now and returns a function waiting for the rest. const addTax = multiply(1.2) gives a one-argument function. In C# and Java you do this with a lambda that captures the fixed value; Python has functools.partial.
  • Currying turns a function of several arguments into a chain of one-argument functions: add(a, b) becomes add(a)(b). It's the default in F# and Haskell, and makes partial application automatic. In mainstream languages you rarely curry everything; you partially apply where it helps.
  • Composition glues functions end to end: compose(f, g)(x) = f(g(x)). pipe is the same thing in reading order: pipe(g, f)(x) = f(g(x)). Pipelines of named small functions are how you build behaviour from parts.

Build a pipeline of small functions below. The first frames show the function values (closures holding their fixed argument) before any data flows. Switch between pipe and compose to see that the same list runs in opposite orders.

Func<decimal, Func<decimal, decimal>> multiply = factor => x => x * factor; // curried
var addVat   = multiply(1.2m);                       // partial application
var discount = multiply(0.9m);

public static class Fn   // extension methods live in a static class
{
    public static Func<T, V> Then<T, U, V>(this Func<T, U> f, Func<U, V> g)
        => x => g(f(x));
}

var finalPrice = discount.Then(addVat).Then(x => Math.Round(x, 2));
finalPrice(100m);                                    // 108.00

// Where you've seen it: ASP.NET Core middleware is Func<RequestDelegate,
// RequestDelegate>, i.e. a function that takes "next" and returns a new handler.

Function<BigDecimal, Function<BigDecimal, BigDecimal>> multiply =
    factor -> x -> x.multiply(factor);                    // curried
Function<BigDecimal, BigDecimal> addVat   = multiply.apply(new BigDecimal("1.2"));
Function<BigDecimal, BigDecimal> discount = multiply.apply(new BigDecimal("0.9"));

Function<BigDecimal, BigDecimal> finalPrice =
    discount.andThen(addVat).andThen(x -> x.setScale(2, RoundingMode.HALF_UP));
// andThen = pipe order, compose = maths order. Both are built into Function.
// Comparator.comparing(...).thenComparing(...) is composition you already use.

from functools import partial, reduce

def multiply(factor, x):
    return x * factor

add_vat = partial(multiply, 1.2)
discount = partial(multiply, 0.9)

def pipe(*fns):
    return lambda x: reduce(lambda acc, f: f(acc), fns, x)

final_price = pipe(discount, add_vat, lambda x: round(x, 2))
final_price(100)        # 108.0
# Decorators are higher-order functions too: @cache, @retry, @app.get("/").

func Multiply(factor float64) func(float64) float64 {
    return func(x float64) float64 { return x * factor } // closure over factor
}

func Pipe[T any](fns ...func(T) T) func(T) T {
    return func(x T) T {
        for _, f := range fns {
            x = f(x)
        }
        return x
    }
}

finalPrice := Pipe(Multiply(0.9), Multiply(1.2), func(x float64) float64 {
    return math.Round(x*100) / 100
})
// Go's net/http middleware is func(http.Handler) http.Handler: composition.
// "Functional options" (WithTimeout(5*time.Second)) are partial application.

const multiply = (factor: number) => (x: number) => x * factor; // curried
const addVat = multiply(1.2);
const discount = multiply(0.9);

const pipe = <T>(...fns: Array<(x: T) => T>) => (x: T) =>
  fns.reduce((acc, f) => f(acc), x);

const finalPrice = pipe(discount, addVat, x => Math.round(x * 100) / 100);

You already use composition every day.

  • Middleware pipelines: each layer is next => context => .... See middleware patterns and the request pipeline.
  • Decorators: Python's @retry @cache def f(), Go's Logging(Auth(handler)).
  • Comparators: comparing(Person::last).thenComparing(Person::first).
  • Functional options in Go: NewServer(WithPort(8080), WithTLS(cfg)).
  • Polly / Resilience4j pipelines: retry wrapping timeout wrapping circuit breaker. See resilience.

Use partial application and composition when

  • You'd otherwise write a one-method interface plus a class just to hold one configured value (new TaxCalculator(0.2m).Apply(x) → multiply(1.2m)).
  • The same small steps get combined in different orders for different callers (pricing rules, validation, text normalisation).
  • You're building middleware, decorators or handler chains.

Avoid it when

  • Point-free chains hide what's going on. pipe(map(prop("total")), filter(gt(__, 100)), sum) is clever; orders.Where(o => o.Total > 100).Sum(o => o.Total) is readable.
  • The language fights you. Curried Func<A, Func<B, Func<C, D>>> in C# or Java is noisy; use a lambda that captures instead.
  • The composed function is debugged often. Each layer is an anonymous frame in the stack trace; give the pieces names.

Closures: functions that remember

A closure is a function plus the variables it captured from the scope where it was created. multiply(1.2) above returns a closure: the inner function keeps factor alive after multiply has returned. Closures are how lambdas carry configuration, how callbacks remember context and how a function can have private state.

function counter() {
  let n = 0;                    // captured: lives as long as the returned function does
  return () => ++n;
}
const next = counter();
next(); next();                 // 1, 2: state hidden inside the closure

The key fact, in every one of the five languages: a closure captures the variable, not the value. If the variable changes after the closure is created, the closure sees the new value. Usually that's what you want. Inside a loop, it's the most famous bug in the language. Pick each language below and step through it: the boxes at the top are storage cells, and the arrows show which cell each closure points to.

Closures have costs too

Lifetime: closures keep things alive

A closure holds a reference to everything it captured. An event handler lambda that captures this keeps the whole page, view model or controller alive as long as the event source does. This is the same leak as the forgotten observer unsubscribe. In C#, a lambda that captures one variable from a method makes all lambdas in that method share one display-class object, so a short-lived lambda can keep a big local alive.

Allocation: closures are objects

In C# and Java, a lambda that captures nothing is cached and allocated once. A lambda that captures a local allocates a closure object (and a delegate) every time the enclosing code runs. In a hot path, prefer static lambdas (C# 9) that can't capture, pass state explicitly (dict.GetOrAdd(key, static (k, arg) => ..., arg)), or hoist the lambda out of the loop. Go's escape analysis may move captured variables to the heap. See memory and GC.

Option/Maybe and Result/Either

Two everyday problems hide in ordinary signatures:

  • User FindUser(string email): what happens when there's no such user? null? An exception? The signature doesn't say, and the caller forgets to check. Tony Hoare called the null reference his "billion-dollar mistake".
  • Order PlaceOrder(Cart cart): what happens when stock runs out, or the card is declined? An exception, probably, which the signature also doesn't mention, and which turns an expected business outcome into a stack unwind.

Functional languages answer both with types that make absence and failure part of the return value:

Type Means Cases Mainstream equivalents
Option<T> / Maybe<T> there might not be a value Some(value) or None C# nullable reference types (User?), Java Optional<T>, Python T \| None, Go (T, bool), TS T \| undefined
Result<T, E> / Either<E, T> the operation may fail in an expected way Ok(value) or Error(reason) Go (T, error), Rust Result, TS discriminated union, C#/Java/Python libraries or your own small type

The pattern is not "wrap everything in a box". It is: the compiler, or at least the signature, forces the caller to deal with the empty or failed case, and you get combinators (map, bind) so that dealing with it doesn't mean an if after every line.

Railway-oriented programming

Scott Wlaschin's picture: a function returning Result is a railway switch with one input track and two output tracks, Ok and Error. bind (also called flatMap, then, SelectMany, and_then) connects two switches: if the first returned Ok, the value goes into the second; if it returned Error, the error rides the bottom track straight past every remaining step. map lifts a plain function that can't fail onto the Ok track.

Try a bad email, qty of 0 or two, a stock lower than the quantity, or a balance under qty × 12. Then switch to validate all: independent checks run anyway and report every problem at once, which is what you want for form validation. Steps that need a previous step's output still have to wait for it.

public abstract record Result<T>
{
    public sealed record Ok(T Value) : Result<T>;
    public sealed record Error(string Reason) : Result<T>;

    public Result<U> Bind<U>(Func<T, Result<U>> next) => this switch
    {
        Ok ok => next(ok.Value),
        Error e => new Result<U>.Error(e.Reason),
        _ => throw new UnreachableException(),
    };
    public Result<U> Map<U>(Func<T, U> f) => Bind(v => (Result<U>)new Result<U>.Ok(f(v)));
}

Exceptions or Result?

Return a Result (or Option) when

  • Failure is an expected business outcome: validation, "not found", "insufficient funds", "slot already booked".
  • The caller is supposed to branch on it and show something to the user.
  • You want to collect several errors (form validation) instead of stopping at the first.
  • It sits on a hot path where exceptions are costly (they capture stack traces).

Throw an exception when

  • It's a bug or broken invariant: null where none is allowed, an index out of range, an impossible state.
  • It's an infrastructure failure the immediate caller can't fix: database down, disk full. Let it travel up to a boundary handler (and resilience policies).
  • The ecosystem expects it: Python and Java libraries raise; fighting that everywhere makes your code foreign to its readers.

Result everywhere becomes noise. Wrapping every method in Result<T> and threading Bind through code that has only one realistic failure (an exception from the database) just reinvents exceptions with more typing. Use Result at the edges where failures are part of the domain, and convert to HTTP responses or exceptions at the boundary. More in error handling.

Don't wrap Option inside nullable. In C#, turn on nullable reference types and use User?; in TypeScript, enable strictNullChecks. The compiler then does what an Option type would, with zero ceremony. Java's Optional is for return values; an Optional field or parameter is a well-known anti-pattern, and an Optional variable that is itself null is the worst of both worlds.

Pattern matching and discriminated unions

A discriminated union (also called a sum type, tagged union or algebraic data type) says "a value is exactly one of these cases, and each case carries its own data". A payment method is a card or PayPal or a bank transfer or crypto. The usual OO encodings are weak:

  • One class with nullable fields (CardNumber, PayPalEmail, Iban, Type): any combination is representable, including nonsense like a card payment with an IBAN and no card number.
  • An enum plus a switch in ten places: adding a case means finding all ten. The compiler might not tell you.

Pattern matching is the other half: a switch that destructures the value, tests its shape, binds its fields to names and, when the set of cases is closed, checks that you handled every one. Together they let you make illegal states unrepresentable: if a card payment must have a card number, put the card number only on the Card case.

Step through a payment below. Then put the general Card arm before the guarded big-payment arm (the guarded arm can never run, so a 5000 payment skips review), or forget the Crypto case. The table shows which language catches which mistake, and when.

Pattern matching replaces the visitor pattern for closed hierarchies. The visitor pattern exists to add operations to a fixed set of types without editing them, using double dispatch. A switch over a sealed hierarchy does the same job in one function, and Java and TypeScript even check exhaustiveness for you. Keep visitors for open hierarchies or when a framework (Roslyn, ANTLR, JavaParser) hands you one.

Use discriminated unions when

  • A value is one of a fixed set of shapes that carry different data: payment methods, API responses (Loading | Loaded(data) | Failed(error)), commands, events, AST nodes, state-machine states.
  • You keep writing classes with nullable fields that are only valid "when Type == X".
  • The operations change more often than the set of cases (new reports, new views over the same events).

Prefer polymorphism (methods on each class) when

  • The set of cases is open: plugins, third-party providers, things other teams add.
  • New cases arrive more often than new operations. Then each case carrying its own behaviour means adding a case touches one file, not every switch. This trade-off is the "expression problem", covered in behavioral patterns.

Lazy sequences: work on demand

A lazy sequence is a recipe for producing values, not a container of values. Nothing runs until a consumer asks for the next item, and then only enough work happens to produce that one item. You met this in the pipeline visualizer (lazy mode stopped reading the source once take was satisfied) and in iterators and generators.

Laziness buys you three things: infinite or huge sources (read a 50 GB log line by line), early exit (First, Any, take stop the whole pipeline), and composition without intermediate collections. It also has one sharp edge that each language handles differently: what happens when you consume the same lazy sequence twice? Pick a language below and find out. Then switch to "materialize once".

Language Lazy type Consume it twice Materialize with
C# IEnumerable<T> (LINQ, yield return), IAsyncEnumerable<T> Re-runs the whole query: double database calls, possibly different data. Analyzer CA1851 warns. .ToList(), .ToArray(), .ToHashSet()
Java Stream<T> Throws IllegalStateException: streams are single-use .toList() (16+), collect(...); or a Supplier<Stream<T>> to make fresh streams
Python generators, generator expressions, map/filter/zip objects Empty the second time, no error. Partly consumed generators resume where they stopped. list(...), tuple(...)

Functional core, imperative shell

This is the pattern that brings everything above into ordinary application code. Gary Bernhardt named it: put all the decisions in a core of pure functions that take data and return data (including "commands" describing what should happen), and wrap it in a thin shell that does the I/O: load, call the core, execute the commands it returned.

The renewal job below decides, per account, whether to remind, charge and extend, or suspend. Compare the two designs. In the mixed version, every business rule is tangled with database, clock, payment and email calls, so testing a rule means mocking four things. In the core/shell version, the rules are a pure Decide(now, accounts) that returns a list of commands, and the test is one Assert.Equal.

// Core: pure. Commands are data.
public abstract record RenewalCommand;
public sealed record Remind(string Account, int DaysLeft) : RenewalCommand;

public static IEnumerable<RenewalCommand> Decide(DateOnly today, Account a, decimal price)
{
    var days = a.RenewsOn.DayNumber - today.DayNumber;
    if (days > 3) yield break;
    if (days > 0) { yield return new Remind(a.Id, days); yield break; }
    if (a.Balance >= price) yield return new Charge(a.Id, price);
    else yield return new Suspend(a.Id);
}

    long days = ChronoUnit.DAYS.between(today, a.renewsOn());
    if (days > 3) return List.of();
    if (days > 0) return List.of(new Remind(a.id(), days));
    return a.balance().compareTo(price) >= 0
        ? List.of(new Charge(a.id(), price))
        : List.of(new Suspend(a.id()));
}

void run() {                                       // shell
    LocalDate today = LocalDate.now(clock);
    for (Account a : repo.dueWithin(3))
        for (RenewalCommand c : decide(today, a, price))
            switch (c) {
                case Remind r  -> email.remind(r.account(), r.daysLeft());
                case Charge ch -> payments.charge(ch.account(), ch.amount());
                case Suspend s -> repo.suspend(s.account());
            }
}

from dataclasses import dataclass
from datetime import date

@dataclass(frozen=True)
class Remind:
    account: str
    days_left: int

@dataclass(frozen=True)
class Charge:
    account: str
    amount: int

@dataclass(frozen=True)
class Suspend:
    account: str

def decide(today: date, renews_on: date, account: str, balance: int, price: int) -> list:
    days = (renews_on - today).days
    if days > 3:
        return []
    if days > 0:
        return [Remind(account, days)]
    return [Charge(account, price)] if balance >= price else [Suspend(account)]

assert decide(date(2025, 1, 1), date(2025, 1, 3), "bo", 40, 10) == [Remind("bo", 2)]
assert decide(date(2025, 1, 1), date(2024, 12, 31), "di", 5, 10) == [Suspend("di")]

type Command interface{ isCommand() }
type Remind struct{ Account string; DaysLeft int }
type Charge struct{ Account string; Amount int64 }
type Suspend struct{ Account string }

func (Remind) isCommand()  {}
func (Charge) isCommand()  {}
func (Suspend) isCommand() {}

func Decide(today time.Time, a Account, price int64) []Command { // pure
    days := int(a.RenewsOn.Sub(today).Hours() / 24)
    switch {
    case days > 3:
        return nil
    case days > 0:
        return []Command{Remind{a.ID, days}}
    case a.Balance >= price:
        return []Command{Charge{a.ID, price}}
    default:
        return []Command{Suspend{a.ID}}
    }
}
// The shell: accounts := repo.DueWithin(ctx, 3); for each Decide(...) result,
// a type switch calls email, payments or repo.

type RenewalCommand =
  | { kind: "remind"; account: string; daysLeft: number }
  | { kind: "charge"; account: string; amount: number }
  | { kind: "suspend"; account: string };

export function decide(today: Date, a: Account, price: number): RenewalCommand[] {
  const days = Math.round((a.renewsOn.getTime() - today.getTime()) / 86_400_000);
  if (days > 3) return [];
  if (days > 0) return [{ kind: "remind", account: a.id, daysLeft: days }];
  return a.balance >= price
    ? [{ kind: "charge", account: a.id, amount: price }]
    : [{ kind: "suspend", account: a.id }];
}

export async function run(deps: Deps) {            // shell
  const today = deps.now();
  for (const a of await deps.repo.dueWithin(3))
    for (const c of decide(today, a, deps.price))
      await deps.exec[c.kind](c as never);
}

Where you've seen it

  • Redux / Elm architecture / MVU: update(state, msg) → (newState, commands); the runtime executes the commands.
  • Event sourcing: decide(state, command) → events and evolve(state, event) → state are pure; the event store is the shell.
  • Domain model methods that return events instead of calling services (domain-driven design).
  • Terraform / Kubernetes controllers: compute a plan (pure diff of desired vs actual), then apply it.

It's not worth it when

  • The use case is a CRUD pass-through with no decisions. The "core" would be empty.
  • The decision needs I/O half-way through (look up price, then decide whether to look up a discount). You can still split it into core-shell-core steps, or pass a small function in, but don't contort the code to stay pure.

Functions replace many OO patterns

Several classic object-oriented patterns exist because older Java and C# had no first-class functions. With lambdas, many of them collapse to "pass a function". The behavioral patterns page shows each in full; this is the functional view.

OO pattern What it really is Functional form Keep the class when
Strategy a swappable algorithm a function parameter: Func<Order, decimal> shipping the strategy has several methods, state, or needs DI
Command a request as a value a closure () => ..., or a record + a handler you need undo, serialization or a queue across processes
Template method fixed steps, variable parts a higher-order function taking the variable parts a framework requires subclassing
Observer notify subscribers a list of callbacks, events, Rx IObservable subscribers need lifecycle (unsubscribe, backpressure)
Chain of responsibility handlers in order function composition: next => ctx => ... each handler has heavy dependencies (still a class, composed)
Iterator sequential access a generator (yield) almost never: generators win
Visitor operations over a closed set of types pattern matching on a union the hierarchy is open or a framework gives you a visitor
Factory (creational patterns) create objects without naming the class a Func<T> / Supplier<T> / factory function creation needs configuration, validation or pooling
Decorator (structural patterns) wrap behaviour a higher-order function f => x => ..., Python @decorator the wrapped interface has many methods

One-method interface? Consider a function. If an interface has exactly one method and implementations hold little or no state, a delegate / functional interface / function type is usually simpler for callers and tests. Keep the interface when you need a name in the DI container, several related methods, or documentation that a lambda can't carry.

When functional style hurts

Functional patterns are tools with costs. These are the ones that bite in practice.

Readability

  • Long point-free chains and nested Bind/flatMap read like puzzles to people who don't live in FP.
  • Ten-stage LINQ queries with anonymous tuples (x.Item1.Item2) lose all meaning. Name the intermediate results.
  • Currying in C#/Java produces Func<A, Func<B, Func<C, D>>> types nobody wants to read.
  • Fix: name small functions, break long chains into named steps, and prefer the language's idiom (comprehensions in Python, loops in Go).

Allocation and speed

  • Every LINQ/Stream stage allocates an iterator, every capturing lambda allocates a closure, every "change" to an immutable value allocates a new one.
  • reduce with spread ({...acc, [k]: v}) is O(n²).
  • Persistent collections are several times slower than arrays for reads and iteration.
  • Fix: keep functional style on the 95% of code that isn't hot; measure with a profiler, then use loops, Span<T>, pooled buffers or local mutation in the hot 5%. See performance cadence.

Debugging

  • Stack traces through lazy pipelines show framework frames (MoveNext, ReferencePipeline$3$1.accept) instead of your code.
  • You can't easily put a breakpoint "between" Where and Select.
  • Lazy evaluation runs your lambda later, far from where it was written, so exceptions appear at the foreach.
  • Fix: use the IDE's stream/LINQ debuggers, materialize temporarily, add .Peek() / tap stages, and keep lambdas short and named.

Fighting the ecosystem

  • ORMs want mutable entities. Logging and DI frameworks are object-oriented. Python's culture is "raise exceptions"; Go's is "write the loop".
  • Importing a full FP library (LanguageExt, fp-ts, Vavr) changes how every file reads, and new team members need training.
  • Fix: adopt the patterns (purity, immutability, unions, core/shell), not necessarily the library. Introduce one idea at a time.

Choosing a functional tool: a decision guide

1Is there business logic mixed with I/O?

Split it: functional core, imperative shell. Biggest win, lowest risk.

2Is data shared between components or threads?

Make it immutable: records, frozen dataclasses, readonly types, immutable collections.

3Is a value one of a fixed set of shapes?

Model it as a discriminated union and pattern-match, with an exhaustiveness check.

4Can the operation fail in an expected way?

Return a Result (or Option for absence). Keep exceptions for bugs and infrastructure.

5Is there a one-method interface or a loop over a collection?

Pass a function; use map/filter/reduce or a comprehension. Profile before replacing loops in hot code.

Pitfalls

"It's immutable" (it isn't). A C# record or Java record with a List<T> field, a frozen dataclass with a list, a Go struct holding a slice. Someone mutates the inner collection and every holder of the "immutable" value sees it. Fix: use immutable collection types, defensive copies in constructors (List.copyOf, tuple(...), slices.Clone) and readonly arrays in TypeScript.

Enumerating a lazy query twice. A dashboard ran if (orders.Any()) then foreach (var o in orders) on an EF Core query: two round-trips per request, and under load the count and the list disagreed. Fix: materialize once (ToList), return IReadOnlyList<T> from repositories, and enable CA1851.

Loop variable captured by an async callback. A Go service before 1.22 launched go process(item) correctly but go func(){ process(item) }() in another place, so most goroutines processed the last item. Fix: upgrade the module to go 1.22+, pass values as arguments, and turn on go vet.

Side effects inside a "pure" pipeline. A Java parallel stream did .map(x -> { results.add(x); return x; }) into an ArrayList. Items went missing and occasionally it threw ArrayIndexOutOfBoundsException. Fix: never mutate shared state in stream lambdas; collect with toList() or a concurrent collector.

Memoizing an impure function. @functools.cache on a function that read the current user's locale returned the first user's language to everyone. Fix: only cache pure functions, and make every input that affects the result a parameter (and therefore part of the cache key).

Exhaustiveness bypassed by a default arm. A TypeScript switch with default: return null meant that adding a new kind to the union compiled cleanly and silently returned null in production. Fix: use default: return assertNever(x), Java switches without default over sealed types, and C# arms that throw.

Checklist

  • Business decisions live in pure functions that take values and return values; I/O happens at the edges.
  • Time, randomness, configuration and the current user are parameters, not ambient reads.
  • Data shared across threads, caches or components is immutable all the way down (no List<T> inside a record).
  • Collections returned from methods are either materialized (IReadOnlyList<T>, List, list) or documented as single-use.
  • No side effects inside map/filter/Select/Where lambdas.
  • Closures in loops capture a per-iteration variable; linters (no-loop-func, go vet) are on.
  • "One of these shapes" data is a sealed hierarchy / union with exhaustive matching, not nullable fields plus a type code.
  • Expected failures return a Result/Option/(T, error); exceptions are for bugs and infrastructure.
  • Hot paths have been profiled before and after introducing LINQ/Streams/immutability.
  • Long chains are broken into named steps that a newcomer can read.

Self-check

A function reads DateTime.UtcNow but never writes anything. Is it pure? What would you change?

No. Its result depends on a hidden input (the clock), so calling it twice with the same arguments can give different answers and it can't be memoized or tested without a fake clock. Make the time a parameter (DateOnly today) and read the clock once in the shell, or inject TimeProvider / java.time.Clock / a func() time.Time.

In Python, fs = [lambda: i for i in range(3)] then [f() for f in fs] gives [2, 2, 2]. Why, and how do you fix it?

Python closures look up i when the lambda runs, and by then the loop has finished with i == 2. All three lambdas share the same variable. Bind the value at definition time: lambda i=i: i, or use functools.partial(f, i).

Your C# method returns IEnumerable<Order> built from an EF Core query. The caller calls .Count() and then loops. What happens?

The query runs twice: once for Count() and once for the loop, two database round-trips, and the data can change in between. Materialize with ToListAsync() inside the method and return IReadOnlyList<Order>, so callers can't trigger hidden re-execution.

When would you return a Result instead of throwing?

When the failure is an expected outcome that the caller should handle: validation errors, "not found", "insufficient funds". It shows up in the signature, can be combined with bind, and can collect several errors. Throw for bugs (broken invariants) and infrastructure failures the caller can't handle locally.

An immutable tree has a million nodes. How many nodes does inserting one key allocate?

Only the nodes on the path from the root to the insertion point, plus the new leaf: about log₂(1,000,000) ≈ 20 for a balanced binary tree, and around 4–5 for the 32-way tries used by real persistent collections. Everything else is shared with the old version, which stays valid.

Which language turns "you forgot a case" into a compile error with no extra helper: C#, Java 21, TypeScript, Python or Go?

Java 21, for a switch without default over a sealed interface. TypeScript does it with the assertNever(x: never) helper in the default branch. Python needs a type checker plus assert_never. C# can't prove a class hierarchy is closed, so it warns and needs a discard arm. Go has no sum types; you rely on a default branch or a linter.
