Secure Coding Fundamentals

The OWASP Top 10 as attack animations: injection, broken access control, SSRF, deserialization, and the coding habits that prevent them.

Intermediate → Advanced~55 min studyBuilds on: API Security: AuthN, AuthZ & Rate LimitingUpdated 2026-11-03

The problem: one product page, six breaches

An online shop has a product page. It looks harmless. In one quarter, a penetration test finds all of this in it:

  • The category filter builds SQL with string concatenation. Typing ' OR 1=1 -- lists hidden products; a UNION SELECT lists every user's email and password hash.
  • Those hashes are unsalted SHA-256, so most of them are cracked in an afternoon on one gaming GPU.
  • Product reviews are rendered with Html.Raw "to keep the bold text", so a review containing <img src=x onerror=...> runs JavaScript in every visitor's browser.
  • The "preview an image from a URL" feature fetches http://169.254.169.254/latest/meta-data/ and hands back the server's cloud credentials.
  • The "download your invoice" endpoint takes a file name, so ../appsettings.json returns the production connection string.
  • A transitive npm dependency published a malicious minor version. There's no lockfile, so the next CI build installed it and its postinstall script sent the CI secrets to the attacker.

None of these needed a clever attacker or an exotic bug. Each one is the same handful of mistakes, and each has a fix that is a habit rather than a heroic effort.

Never let untrusted data become code, a path, a destination or an object type. Keep data and instructions in separate channels (parameters, argv lists, text nodes, IDs). Validate input at the boundary, encode output at the sink for that sink's language, give every component the least privilege it needs, and assume each layer will eventually fail.

This page is about secure coding habits: the vulnerabilities that come from how application code is written. Authentication, authorization, JWTs, CORS, CSRF tokens and rate limiting are covered in API security; read that first if you haven't. Secret storage is in configuration and secrets, and logging hygiene in observability.

The mental model: two channels, one interpreter

Almost every injection bug has the same shape. Your program builds a string and hands it to an interpreter: a SQL engine, a shell, the browser's HTML parser, an LDAP server, a URL fetcher, the filesystem, a deserializer. The interpreter can't tell which characters you wrote and which ones came from the user. If the user's bytes can change the structure of what the interpreter sees, the user is programming your server.

Three more ideas run through the whole page:

Validate at the boundary

Check shape where data enters: type, length, range, format, allowlists. It rejects nonsense early and shrinks the attack surface. It is not a complete injection defence, because a valid name like O'Brien is still dangerous to concatenate.

Encode at the sink

Right before data enters an interpreter, use that interpreter's safe API: parameters for SQL, argv lists for processes, HTML encoding for markup, URL encoding for query strings. The sink knows the context; the boundary doesn't.

Least privilege everywhere

Assume something will fail. The DB user can't DROP, the container can't reach the metadata service, the CI job's token can't publish packages. Limits turn a breach into an incident.

Injection: SQL, shell and LDAP

Injection is the textbook vulnerability, and it is still found in new code every week, usually in the corners an ORM doesn't cover: dynamic ORDER BY, reporting queries, admin tools, scripts that "only run internally".

The visualizer below runs real interpreters. The SQL engine tokenizes and evaluates the query against two in-memory tables (products and users), the shell splitter is a simplified /bin/sh that understands ;, &&, ||, |, $( ) and backticks, and the LDAP part parses filters per RFC 4515. Pick a payload and step through. Then switch to the safe version and watch the same payload become an inert value.

Things to notice:

  • In the SQL view, the token row is the giveaway. With concatenation, the user's bytes become OR, UNION, SELECT and -- tokens: code. With a parameter, the whole input is one placeholder and the parser never looks inside it.
  • ' OR 1=1 -- doesn't need to guess anything; -- comments out the rest of your query, including the AND visible = 1 that was supposed to hide products.
  • In the shell view, ;, &&, | and $(...) each start a new command. The safe version doesn't escape them; it doesn't start a shell at all, so they're just characters in one argument.
  • The argument-injection payload (-f) is the subtle one: even without a shell, a value starting with - can be read as an option. The -- separator and the allowlist both stop it.

Parameterized queries in five languages

Every mainstream database driver supports parameters, and every one of them sends the SQL text and the values separately (or escapes them in the driver, which is the driver's job and well-tested). The placeholder syntax differs per driver:

// ADO.NET (Microsoft.Data.SqlClient). Dapper: conn.QueryAsync<Product>(sql, new { category })
const string sql = "SELECT name, price FROM products WHERE category = @category AND visible = 1";
await using var cmd = new SqlCommand(sql, conn);
cmd.Parameters.Add("@category", SqlDbType.NVarChar, 40).Value = category;
await using var reader = await cmd.ExecuteReaderAsync(ct);

// EF Core: FromSql takes a FormattableString and turns {category} into a parameter.
var rows = await db.Products
    .FromSql($"SELECT * FROM products WHERE category = {category}")
    .ToListAsync(ct);
// DANGER: FromSqlRaw("... = '" + category + "'") is plain concatenation.

// JDBC
String sql = "SELECT name, price FROM products WHERE category = ? AND visible = 1";
try (PreparedStatement ps = conn.prepareStatement(sql)) {
    ps.setString(1, category);
    try (ResultSet rs = ps.executeQuery()) { /* ... */ }
}

// Spring JdbcTemplate / JPA
jdbc.query("SELECT name, price FROM products WHERE category = ?", mapper, category);
em.createQuery("select p from Product p where p.category = :c", Product.class)
  .setParameter("c", category).getResultList();

# sqlite3 uses ?, psycopg uses %s. Both are PLACEHOLDERS, not Python string formatting.
cur.execute(
    "SELECT name, price FROM products WHERE category = ? AND visible = 1",
    (category,),
)

# psycopg 3
cur.execute("SELECT name, price FROM products WHERE category = %s", (category,))

# SQLAlchemy
session.execute(text("SELECT * FROM products WHERE category = :c"), {"c": category})
# DANGER: cur.execute(f"... WHERE category = '{category}'")

// database/sql: $1 for PostgreSQL drivers (pgx, lib/pq), ? for MySQL and SQLite.

    "SELECT name, price FROM products WHERE category = $1 AND visible = true",
    category)

    return err
}
defer rows.Close()
// DANGER: fmt.Sprintf("... WHERE category = '%s'", category)

// node-postgres

  "SELECT name, price FROM products WHERE category = $1 AND visible = true",
  [category],
);

// postgres.js and Prisma: tagged templates turn ${} into parameters.

const viaPrisma = await prisma.$queryRaw`SELECT * FROM products WHERE category = ${category}`;
// DANGER: prisma.$queryRawUnsafe(`... = '${category}'`) or pool.query(`... = '${category}'`)

The pattern to remember: tagged templates and FormattableString APIs are safe because the library receives the pieces separately; string interpolation done by you before the call is not. That's why EF Core's FromSql($"...") is safe and FromSqlRaw(string) with your own concatenation is not, even though they look almost identical in the editor.

What parameters can't do: identifiers and keywords

Parameters hold values. You can't parameterize a table name, a column in ORDER BY, or the ASC/DESC keyword. When those come from the request, map them through an allowlist:

private static readonly Dictionary<string, string> SortColumns = new(StringComparer.OrdinalIgnoreCase)
{
    ["name"] = "name", ["price"] = "price", ["newest"] = "created_at",
};

var column = SortColumns.GetValueOrDefault(sort ?? "", "name");   // unknown -> default
var direction = desc ? "DESC" : "ASC";                              // never from the request text
var sql = $"SELECT name, price FROM products WHERE category = @category ORDER BY {column} {direction}";

SORT_COLUMNS = {"name": "name", "price": "price", "newest": "created_at"}

column = SORT_COLUMNS.get(sort, "name")
direction = "DESC" if desc else "ASC"
sql = f"SELECT name, price FROM products WHERE category = ? ORDER BY {column} {direction}"
cur.execute(sql, (category,))   # only allowlisted constants were interpolated

The interpolated strings in that code come from your dictionary, never from the request. A code reviewer can check that in five seconds, which is the point.

OS commands: don't start a shell

Shell injection happens when a single string goes to /bin/sh -c or cmd.exe /c. Every language has an API that starts the program directly with an argument vector; use it, and put -- before user values so they can't be read as options:

var psi = new ProcessStartInfo("ping")
{
    ArgumentList = { "-c", "1", "--", host },   // each item is one argv entry; no shell
    UseShellExecute = false,
    RedirectStandardOutput = true,
};
using var proc = Process.Start(psi)!;
// DANGER: Process.Start("/bin/sh", $"-c \"ping -c 1 {host}\"")

Process p = new ProcessBuilder("ping", "-c", "1", "--", host)
        .redirectErrorStream(true)
        .start();
// Runtime.exec(String) splits on spaces without a shell, but it still allows
// argument injection, and quoting rules surprise people. Prefer ProcessBuilder.

import subprocess

out = subprocess.run(
    ["ping", "-c", "1", "--", host],   # a list, and shell=False (the default)
    capture_output=True, text=True, timeout=5, check=False,
)
# DANGER: subprocess.run(f"ping -c 1 {host}", shell=True) or os.system(...)

// exec.Command never invokes a shell; each argument is passed as-is.
cmd := exec.CommandContext(ctx, "ping", "-c", "1", "--", host)
out, err := cmd.CombinedOutput()
// DANGER: exec.Command("sh", "-c", "ping -c 1 "+host)

import { execFile } from "node:child_process";
import { promisify } from "node:util";

const run = promisify(execFile);
const { stdout } = await run("ping", ["-c", "1", "--", host], { timeout: 5000 });
// DANGER: exec(`ping -c 1 ${host}`) and spawn(cmd, { shell: true }) both use a shell.

Better still, don't shell out. Most things people run commands for (DNS lookups, image resizing, zipping, git operations) have a library. A library call has no parsing step to inject into, and it's easier to test.

LDAP and other query languages

The same rule applies to every query language: LDAP filters, XPath, NoSQL query objects, GraphQL strings, regular expressions built from user input. LDAP filters use *, (, ), \ and NUL as syntax, so a user name of * matches everyone, and admin)(&) can close your clause early. Use the library's filter-argument API or its escaping function (RFC 4515):

Language Safe filter building
C# No built-in escaper in System.DirectoryServices.Protocols; write the five-character RFC 4515 escape, and test it
Java JNDI ctx.search(base, "(uid={0})", new Object[]{ user }, controls); Spring LDAP LdapQueryBuilder
Python ldap3.utils.conv.escape_filter_chars(user); python-ldap ldap.filter.filter_format
Go ldap.EscapeFilter(user) from github.com/go-ldap/ldap/v3
TypeScript Build filters with the client library's filter objects (e.g. EqualityFilter) rather than strings

For MongoDB-style query objects, the injection is type confusion: the JSON body {"user": {"$ne": null}} turns an equality check into "not equal to null". Validate that fields are strings before they reach the query (a schema validator such as Zod, Pydantic or a DTO with typed properties does this for free).

"We escape quotes, so we're fine." Hand-rolled escaping fails on encodings, numeric contexts (WHERE id = 1 OR 1=1 has no quotes at all), backslash handling that differs between databases, and second-order injection: a value stored safely, read back later, then concatenated into a different query. Parameters work in all of these cases; escaping works in the cases you thought of.

Cross-site scripting (XSS): injection into the browser

XSS is injection where the interpreter is the victim's browser. If attacker text ends up in your page as markup or script, it runs with your origin's privileges: it can read the DOM, call your APIs with the user's cookies, change the password, and send everything elsewhere. The three flavours differ only in how the payload arrives:

Flavour Where the payload lives Example
Stored your database, rendered for every viewer a product review or a display name
Reflected the request, echoed straight back /search?q=<script>… in a phishing link
DOM-based client-side code moves it from the URL into the DOM el.innerHTML = location.hash.slice(1)

The fix is output encoding for the exact context the value lands in. HTML has several contexts, and each one has different dangerous characters. The visualizer puts one value into four contexts, with three encoders and an optional Content Security Policy, and runs a small browser model to find out which script would execute.

What to take away from it:

  • HTML-encoding is correct for the HTML body and quoted attributes, and wrong elsewhere. In an href, javascript:alert(1) contains no characters to encode, so it survives HTML encoding and runs on click. URLs need a scheme allowlist (http, https, maybe mailto).
  • Inside a <script> block, HTML-encoding breaks your data and still doesn't protect you. The JS string context needs JavaScript string escaping (or better, JSON-encode the value into a data- attribute or a <script type="application/json"> block and read it with JSON.parse).
  • CSP is a second line of defence. A strict nonce-based policy blocks injected <script> tags and inline event handlers, but it can't help when the attacker's text lands inside a script that already has the right nonce.

What your framework already does (and how people turn it off)

Every modern template engine encodes by default. Almost every real XSS bug is someone using the escape hatch:

// Razor encodes @ expressions for HTML automatically.
<p>@Model.Review.Text</p>                         // safe
<p>@Html.Raw(Model.Review.Text)</p>               // DANGER: raw markup from the database

// Need rich text? Sanitize with an allowlist (Ganss.Xss HtmlSanitizer), then output.
var sanitizer = new HtmlSanitizer();              // allows b, i, a href=http(s) ...; drops script, on*
<p>@Html.Raw(sanitizer.Sanitize(Model.Review.Html))</p>

// Data for scripts: serialize to JSON (System.Text.Json escapes <, >, & by default).
<script id="cfg" type="application/json">@Json.Serialize(Model.Config)</script>

// Thymeleaf: th:text encodes, th:utext does not.
<p th:text="${review.text}">…</p>                 <!-- safe -->
<p th:utext="${review.text}">…</p>                <!-- DANGER -->

// Rich text: OWASP Java HTML Sanitizer with an explicit policy.
PolicyFactory policy = Sanitizers.FORMATTING.and(Sanitizers.LINKS);
String safeHtml = policy.sanitize(untrustedHtml);

// Building HTML by hand? Encode for the context: OWASP Java Encoder.
String attr = Encode.forHtmlAttribute(name);
String js = Encode.forJavaScript(name);

# Jinja2 (Flask enables autoescape for .html templates): {{ }} is encoded.
<p>{{ review.text }}</p>                           {# safe #}
<p>{{ review.text | safe }}</p>                    {# DANGER #}

# Rich text: nh3 (Rust ammonia bindings) with an allowlist of tags.
import nh3
safe_html = nh3.clean(untrusted_html, tags={"b", "i", "a", "p"})

# Django templates also autoescape; mark_safe() and |safe are the escape hatches.

// html/template escapes by CONTEXT automatically: HTML body, attributes,
// URLs (javascript: becomes #ZgotmplZ) and JS strings each get the right encoder.

tmpl.Execute(w, review)

// DANGER: template.HTML(userText) tells the engine "trust me".
// DANGER: text/template does no escaping at all; never use it for HTML.

// React escapes {expressions} in JSX text and attributes.
<p>{review.text}</p>                                            // safe
<p dangerouslySetInnerHTML={{ __html: review.html }} />          // DANGER

// Rich text: sanitize first (DOMPurify), and only then inject.
<p dangerouslySetInnerHTML={{ __html: DOMPurify.sanitize(review.html) }} />

// URLs: validate the scheme yourself before putting user URLs in href/src.
const safeUrl = (u: string) => (["http:", "https:"].includes(new URL(u, location.href).protocol) ? u : "#");
// DOM code: prefer textContent over innerHTML; enable Trusted Types to make innerHTML assignments fail.

Go's html/template deserves a special mention: it is contextually aware, so it picks HTML, attribute, URL or JavaScript escaping depending on where {{.}} sits. That is the gold standard the other engines approximate with separate helpers.

Content Security Policy

CSP is a response header that tells the browser which scripts are allowed to run. A strict policy uses a per-response random nonce:

Content-Security-Policy: script-src 'nonce-r4nd0m' 'strict-dynamic'; object-src 'none'; base-uri 'none'

Only <script nonce="r4nd0m"> tags run, plus scripts they load (strict-dynamic). Inline onclick= handlers and javascript: URLs are blocked. Domain allowlists (script-src cdn.example.com) look stricter than they are: if any allowed domain hosts a JSONP endpoint or an old Angular copy, attackers use it as a script gadget. Roll a CSP out with Content-Security-Policy-Report-Only first, collect violations, fix them, then enforce.

XSS checklist for a code review: search the diff for Html.Raw, th:utext, |safe, mark_safe, template.HTML, dangerouslySetInnerHTML, innerHTML, outerHTML, insertAdjacentHTML, document.write, eval, new Function and href={ with user data. Each hit needs a sanitizer or a reason.

CSRF in one paragraph

Cross-site request forgery makes the victim's browser send a request to your site from someone else's page, carrying the victim's cookies. It only matters when you authenticate with cookies. The defences are SameSite=Lax (or Strict) cookies, an anti-forgery token on state-changing requests, and never changing state on GET. Bearer tokens in an Authorization header aren't sent automatically, so token-only APIs are not CSRF-able (but a token kept in localStorage is readable by any XSS, which is why XSS is the bigger threat). The animated walkthrough is in API security: CSRF.

SSRF: making your server fetch for the attacker

Server-side request forgery happens whenever your server fetches a URL that a user influences: link previews, webhooks, "import from URL", PDF renderers that load images, OAuth metadata discovery. Your server sits inside the network, so it can reach things the attacker can't: the cloud metadata service at 169.254.169.254 (which hands out credentials), internal admin panels, Redis, Elasticsearch, Kubernetes APIs.

Blocking "bad URLs" by looking at the text fails, because there are many ways to spell an address and DNS is under the attacker's control. The visualizer has a real IPv4 parser that accepts the forms inet_aton accepts (decimal 2852039166, hex 0xA9FEA9FE, short 127.1), IPv4-mapped IPv6, a fake DNS with a rebinding name (first answer public, second answer private), and an open redirect on a trusted host. Try each URL against each defence:

The defence that holds against all of them has four parts:

  1. Resolve the host name yourself.
  2. Check every resolved IP (not the text) against a denylist of private, loopback, link-local, unique-local and metadata ranges, after un-mapping IPv4-in-IPv6.
  3. Connect to the IP you checked. If the HTTP library resolves the name again, an attacker's DNS can return a different answer the second time (rebinding).
  4. Don't auto-follow redirects, or re-run the check on every hop.

The cleanest place to do this is the HTTP client's connect hook, because that's where the library has already resolved the name and is about to open the socket:

var handler = new SocketsHttpHandler
{
    AllowAutoRedirect = false,                       // follow redirects yourself, if at all
    ConnectCallback = async (ctx, ct) =>
    {
        var addrs = await Dns.GetHostAddressesAsync(ctx.DnsEndPoint.Host, ct);
        if (addrs.Length == 0 || addrs.Any(IsBlocked))
            throw new HttpRequestException($"Destination {ctx.DnsEndPoint.Host} is not allowed");
        var socket = new Socket(SocketType.Stream, ProtocolType.Tcp) { NoDelay = true };
        try
        {
            await socket.ConnectAsync(addrs, ctx.DnsEndPoint.Port, ct);   // connects to a checked IP
            return new NetworkStream(socket, ownsSocket: true);
        }
        catch { socket.Dispose(); throw; }
    },
};

static bool IsBlocked(IPAddress ip)
{
    if (ip.IsIPv4MappedToIPv6) ip = ip.MapToIPv4();
    if (IPAddress.IsLoopback(ip) || ip.IsIPv6LinkLocal || ip.IsIPv6SiteLocal || ip.IsIPv6UniqueLocal) return true;
    if (ip.Equals(IPAddress.Any) || ip.Equals(IPAddress.IPv6Any)) return true;
    var b = ip.GetAddressBytes();
    return ip.AddressFamily == AddressFamily.InterNetwork &&
        (b[0] is 0 or 10 or 127 || (b[0] == 169 && b[1] == 254) || (b[0] == 172 && b[1] is >= 16 and <= 31) ||
         (b[0] == 192 && b[1] == 168) || (b[0] == 100 && b[1] is >= 64 and <= 127));
}

import ipaddress, socket
from urllib.parse import urlsplit
import urllib3

def vetted_ip(host: str, port: int) -> str:
    infos = socket.getaddrinfo(host, port, type=socket.SOCK_STREAM)
    ips = {ipaddress.ip_address(info[4][0]) for info in infos}
    for ip in ips:
        if ip.version == 6 and ip.ipv4_mapped:
            ip = ip.ipv4_mapped
        if not ip.is_global:                  # private, loopback, link-local, reserved, CGNAT ...
            raise ValueError(f"destination {ip} not allowed")
    return str(next(iter(ips)))

def fetch(url: str) -> bytes:
    parts = urlsplit(url)
    if parts.scheme != "https" or not parts.hostname:
        raise ValueError("https URLs only")
    port = parts.port or 443
    ip = vetted_ip(parts.hostname, port)      # connect to THIS ip, keep TLS checks on the name
    pool = urllib3.HTTPSConnectionPool(ip, port, server_hostname=parts.hostname,
                                       assert_hostname=parts.hostname, timeout=5.0, retries=False)
    path = parts.path or "/"
    resp = pool.request("GET", path + ("?" + parts.query if parts.query else ""),
                        headers={"Host": parts.hostname}, redirect=False, preload_content=False)
    return resp.read(1_000_000)               # cap the body size too

dialer := &net.Dialer{
    Timeout: 5 * time.Second,

            return err
        }

        if err != nil {
            return err
        }

        if !ip.IsGlobalUnicast() || ip.IsPrivate() || ip.IsLoopback() || ip.IsLinkLocalUnicast() {
            return fmt.Errorf("destination %s not allowed", ip)
        }
        return nil
    },
}

Path traversal: escaping the folder

Any time a request parameter becomes part of a file path, ../ can climb out of the folder you meant to serve. The visualizer runs the real sequence: the framework URL-decodes, your code "sanitizes", joins, checks, and the operating system resolves the .. segments.

Four bugs to remember from it:

  • Blocklists lose. Removing ../ once turns ....// into ../. URL-encoding (%2e%2e%2f), double encoding, backslashes on Windows and Unicode lookalikes give attackers many more spellings.
  • Join drops the base for absolute paths. Path.Combine("/srv/app/uploads", "/etc/passwd") returns /etc/passwd. So do Python's os.path.join, Java's Path.resolve and Node's path.resolve.
  • Check the resolved path, not the string you built. "/srv/app/uploads/../appsettings.json".StartsWith("/srv/app/uploads") is true.
  • A string prefix isn't a folder check. /srv/app/uploads-private starts with /srv/app/uploads. Compare against the base plus a separator, or use a path-aware comparison.

The best fix is not to accept paths at all: store files under server-generated names (a GUID), keep a table that maps an ID to the stored name and owner, and look it up. When you must accept a relative path, canonicalize and check:

Insecure deserialization: when data chooses the type

Most serializers just fill fields of a type you chose: JsonSerializer.Deserialize<OrderDto>(body) can only ever produce an OrderDto. The dangerous ones let the byte stream choose the type. Then the attacker picks a class that's on your classpath, sets its fields, and lets the deserializer call its constructor, setters or readObject hook. Chained together, these "gadgets" end in a method that runs a command.

Broken access control: the number-one risk, in brief

Broken access control is first on both the 2021 and 2025 lists. It covers a request that should be refused but isn't: reading another customer's order by changing an ID (BOLA/IDOR), calling an admin endpoint that is only hidden in the UI, or updating a field the user shouldn't own (mass assignment). The deep dive with animations is in API security. The coding habits behind it:

  • Deny by default. A new endpoint without an explicit policy should fail closed (FallbackPolicy requiring an authenticated user in ASP.NET Core, anyRequest().authenticated() in Spring Security).
  • Check ownership on every object access, in the query itself: WHERE id = @id AND owner_id = @userId. Returning 404 rather than 403 avoids confirming that the ID exists.
  • Bind requests to explicit DTOs, never to entities, so "isAdmin": true in a body has nowhere to land.
  • Authorize on the server for every request. Hiding a button is UX, not security.

Password storage: plan for the leak

Assume that your user table will leak one day, through a backup, a SQL injection, or an over-shared analytics export. Password storage decides what happens next. Users reuse passwords, so a cracked hash for your site often unlocks their email and their bank as well.

The key point is speed. SHA-256 is designed to be fast, and a single modern GPU computes tens of billions of them per second. A password hash such as bcrypt or Argon2 is designed to be slow and memory-hungry, so each guess costs the attacker real time and hardware. Pick an algorithm and a password below. The hashes are real (computed in your browser for MD5 and SHA-256); the crack times use published GPU benchmark rates:

Things to notice:

  • Unsalted fast hashes fall to lookup tables. Every user with 123456 gets the same SHA-256, so one lookup cracks all of them at once.
  • A salt makes each hash unique (so no precomputed tables, and no "crack once, get everyone"), but it doesn't make guessing any slower. SHA-256 + salt still falls to a word list in seconds.
  • Slow hashes change the arithmetic by a factor of millions. Weak passwords from the top of a leaked list are still found, which is why you also screen new passwords against breach lists.
  • Long random passwords are safe under any scheme. You can't control what users choose, though, so the storage scheme has to carry the weight.

Around the hash:

  • Pepper (optional). A secret key kept outside the database (in a vault or HSM), mixed in with an HMAC before hashing, or used to encrypt the stored hash. A database-only leak is then useless on its own. Plan how you'll rotate it before you add one.
  • Screen against breached passwords. The Have I Been Pwned range API uses k-anonymity: you send the first 5 hex characters of the SHA-1 and compare the returned suffixes locally, so the password never leaves your server.
  • Follow NIST SP 800-63B: favour length over composition rules ("one uppercase, one symbol"), don't force periodic rotation, allow paste so password managers work, and add MFA. Rate-limit and lock out per account, which is covered in API security.
  • Make verification take the same time for unknown users. If "no such user" returns instantly but a wrong password takes 200 ms, the timing tells an attacker which emails have accounts. Verify against a dummy hash in that branch.

Cryptography: use the library, not the primitives

The first rule of applied cryptography is that you don't design it. You pick a high-level, authenticated construction from your platform's standard library and use it exactly as documented. Nearly every real-world crypto failure is a correct algorithm used incorrectly: a reused nonce, ECB mode, a missing authentication tag, a key in the source code.

Do

  • AES-256-GCM or ChaCha20-Poly1305 for symmetric encryption. Both are authenticated: tampering makes decryption fail.
  • A fresh random 96-bit nonce for every message, stored next to the ciphertext.
  • Keys from a KMS or vault, with envelope encryption (a data key per object, wrapped by a master key that never leaves the KMS).
  • TLS 1.2+ for everything in transit, including internal traffic.
  • HMAC-SHA256 for "has this been tampered with?"; Ed25519 or ECDSA P-256 for signatures.
  • The platform's CSPRNG for every token, ID, salt and key.

Don't

  • Invent schemes, or "encrypt" with XOR, Base64 or a hand-written cipher.
  • Use ECB (identical blocks leak patterns) or CBC without a MAC (padding-oracle attacks).
  • Reuse a nonce with the same key. With GCM that leaks plaintext and the authentication key.
  • Use MD5 or SHA-1 for anything security-related.
  • Use Random, Math.random(), random or math/rand for secrets.
  • Hard-code keys, commit them, or log them.
  • Compare MACs or tokens with == (see timing attacks below).

Why nonce reuse is catastrophic

GCM (like every stream-cipher mode) encrypts by XOR-ing your data with a keystream derived from the key and the nonce. Same key, same nonce, same keystream. XOR two such ciphertexts together and the keystream cancels out, leaving plaintext1 ⊕ plaintext2. If the attacker knows or can guess one message (JSON structure is very guessable), they recover the other one. The visualizer does it byte by byte:

With GCM it is even worse: a repeated nonce also leaks the internal authentication key, so the attacker can forge messages that decrypt successfully. Random 96-bit nonces are safe for about 2^32 messages per key; past that, rotate keys, or use a counter you can guarantee never repeats (which is hard across multiple servers and restarts). Libraries such as Google Tink, libsodium's secretbox and Go 1.24's NewGCMWithRandomNonce handle nonces for you.

Timing attacks: when "how long" leaks "what"

A normal equality check stops at the first byte that differs. That's efficient, but it means a guess with a correct first character takes a few nanoseconds longer to reject than one without. Measure enough requests, average out the network noise, and you can recover a secret one character at a time. The visualizer simulates an attacker guessing an API key against a server, with Gaussian network noise, so you can see when the signal rises above it:

Averaging N samples shrinks the noise by √N, which is why "it's only a few nanoseconds over the internet" isn't a defence; it's a cost the attacker pays with more requests. The fix is a comparison that always takes the same time, whatever the inputs:

using System.Security.Cryptography;

bool ok = CryptographicOperations.FixedTimeEquals(
    Encoding.UTF8.GetBytes(presentedKey), Encoding.UTF8.GetBytes(expectedKey));
// Lengths that differ return false at once; that leaks only the length.

boolean ok = MessageDigest.isEqual(
    presented.getBytes(StandardCharsets.UTF_8), expected.getBytes(StandardCharsets.UTF_8));
// Constant-time since Java 6u17. String.equals is NOT.

import hmac

ok = hmac.compare_digest(presented.encode(), expected.encode())
# (secrets.compare_digest is the same function)

import "crypto/subtle"

ok := subtle.ConstantTimeCompare([]byte(presented), []byte(expected)) == 1
// Returns 0 immediately for different lengths; bytes.Equal is NOT constant-time.

import { createHash, timingSafeEqual } from "node:crypto";

// timingSafeEqual throws if lengths differ, so compare fixed-length digests instead.
const digest = (s: string) => createHash("sha256").update(s).digest();
const ok = timingSafeEqual(digest(presented), digest(expected));

Better still, don't compare secrets at all: store a hash of the API key (SHA-256 is fine here, since API keys are long and random, unlike passwords), look the hash up, and the timing of the lookup tells the attacker nothing useful. The same rule applies to HMAC signatures on webhooks: verify with the constant-time function, never ==.

Secrets in logs, errors and URLs

Many breaches don't involve any clever exploit: a token was simply written somewhere readable. Common leaks:

  • Logs. A request logger that dumps headers (Authorization, Cookie), a logger.info("user {}", user) where the object's ToString includes the password hash, or an exception message that includes the connection string. Logs get shipped to third-party services and are read by far more people than your database.
  • URLs. Tokens in query strings end up in proxy logs, browser history and Referer headers. Put them in headers or the body.
  • Error responses. Stack traces and SQL errors in production responses help attackers map your system. Return a problem-details body with a correlation ID instead, as in error handling.
  • Source control. Keys committed "temporarily". Rotating the key is the only fix; deleting the commit doesn't help once it's been pushed.

Add to that redaction in the logging pipeline (an allowlist of fields to log beats a denylist of fields to hide), secret scanning in CI and on push (gitleaks, GitHub push protection), and short-lived credentials (managed identities, workload identity federation) so a leaked secret expires on its own. Logging and redaction are covered in observability; where secrets live and how they're rotated is in configuration and secrets.

Supply chain: the code you didn't write

A typical service is 5% your code and 95% dependencies, plus their dependencies, plus the build tools that produce the artifact. Attackers have noticed. Instead of breaking into your app, they publish a package called colour-utils next to the real color-utils, take over an abandoned maintainer account, slip a backdoor into a build script, or compromise the registry mirror your CI uses. Habits that matter more than any tool:

  • Look before you add. Who maintains it, how many maintainers, when was the last release, how many transitive dependencies does it pull in? A 10-line helper you can write yourself is often better than a dependency.
  • Update continuously, in small steps. Dependabot or Renovate PRs with your test suite as the gate. Teams that are three major versions behind can't patch quickly when a critical CVE lands.
  • Prevent dependency confusion. If you publish internal packages, use a scope or prefix you own on the public registry, and map package sources so internal names can only come from your feed.
  • Pin your CI actions and build images by digest or commit SHA, not by a mutable tag. Build steps run with your secrets.
  • Verify provenance where you can: npm provenance, Sigstore signatures, and the SLSA framework describe how to prove which source and which build produced an artifact.

Least privilege and defence in depth

Every control on this page can fail. Least privilege decides how bad the failure is. When the SSRF works, the instance role determines what the attacker gets. When SQL injection works, the database user's grants determine whether it's "read the products table" or "drop every table and run xp_cmdshell".

  • Database: the app's runtime user gets SELECT/INSERT/UPDATE/DELETE on its own schema, nothing else. Migrations run as a separate user, in the deploy pipeline. Reporting reads from a replica with a read-only user.
  • Cloud identities: one managed identity per service, scoped to the specific resources it uses (this storage container, not "Storage Blob Data Contributor on the subscription"). No long-lived keys where workload identity is available.
  • Containers and processes: run as non-root, with a read-only root filesystem, drop Linux capabilities, and give network policies that only allow the calls the service actually makes.
  • People and pipelines: just-in-time admin access, production access through audited break-glass procedures, CI tokens scoped to one repository with the minimum permissions.
  • Fail closed. When the authorization service is down, deny. When the input is unexpected, reject. OWASP 2025's new category, Mishandling of Exceptional Conditions, is largely about code that fails open.

Defence in depth means layering independent controls so one mistake isn't a breach: parameterized queries and a least-privilege DB user; output encoding and CSP; the SSRF check in code and a network with no route to the metadata service.

Threat modeling with STRIDE

All of the above is reactive: a list of known bug classes. Threat modeling asks the question earlier, at design time: what could go wrong with what we're building? The simplest effective version takes an hour with the team and a whiteboard:

1 · MODELDraw the data flow

External actors, processes, data stores, the flows between them, and the trust boundaries the flows cross.

2 · FINDApply STRIDE per element

For each element and each flow that crosses a boundary, ask the six STRIDE questions.

3 · FIXDecide per threat

Mitigate, eliminate (remove the feature), transfer (a provider handles it), or accept it, in writing.

4 · CHECKVerify and revisit

Turn the mitigations into tests and tickets. Revisit when the diagram changes.

STRIDE is a mnemonic for six kinds of threat, each the violation of one security property:

Letter Threat Property violated Typical mitigation
S Spoofing: pretending to be someone or something else Authentication OIDC login, mTLS between services, signed webhooks
T Tampering: modifying data or code Integrity TLS, HMAC/signatures, parameterized queries, integrity hashes
R Repudiation: "I never did that", with no way to prove otherwise Non-repudiation Append-only audit log with user, time and correlation ID
I Information disclosure Confidentiality Authorization checks, encryption, redaction, minimal error details
D Denial of service Availability Rate limits, timeouts, size limits, quotas, autoscaling
E Elevation of privilege Authorization Deny by default, least privilege, server-side checks

Not every letter applies to every element. External actors can be spoofed and can repudiate; data stores can be tampered with, disclosed and denied (and repudiated, when the store holds audit logs); data flows can be tampered with, disclosed and denied; processes are subject to all six. Pitfalls

"We escape quotes." A team replaced ' with '' before building SQL strings. It held until a numeric ID parameter (ORDER BY 1; DROP TABLE … needs no quotes) and a database configured to treat backslashes as escapes. Fix: parameters everywhere; there is no safe way to concatenate.

The trusted-domain fetcher. Link previews were allowed only for *.partner.com. One partner page had an open redirect (/out?to=), and the HTTP client followed it to http://169.254.169.254/. The instance role's credentials were in the preview text. Fix: no auto-redirects; resolve and check every hop; IMDSv2; network egress rules.

Hashed, technically. Passwords were stored as SHA-256(salt + password) "because it's salted". A leaked backup was 80% cracked in a weekend on rented GPUs. Fix: a password hash (Argon2id, scrypt, bcrypt), rehash on next login, force resets for anyone not yet migrated.

The static IV. An encryption helper used a constant IV "because random IVs broke the unit tests". Every record shared a keystream; anyone with database read access and one known record could decrypt the rest. Fix: a random nonce per message, stored with the ciphertext; test round trips, not fixed ciphertexts.

Debug mode in production. A framework's developer exception page was enabled by an environment variable that defaulted to Development. Every 500 error showed the stack trace, source lines and configuration values. Fix: fail-closed defaults (production unless explicitly told otherwise), generic problem-details responses, and a DAST baseline scan in CI.

The friendly dependency. A developer added requets while fixing a bug late at night. Its install script read environment variables and posted them to a pastebin, including the CI deploy token. Fix: review new dependency names in PRs, lockfiles with hashes, --ignore-scripts where possible, and CI tokens that are short-lived and narrowly scoped.

Checklist

  • Every query, command and LDAP filter is built with parameters or argv lists; identifiers come from allowlists.
  • Templates auto-escape; each use of a raw-HTML escape hatch is sanitized and justified; user URLs are scheme-checked.
  • A strict, nonce-based CSP is deployed (report-only first), with the other security headers set centrally.
  • Cookie-authenticated endpoints use SameSite cookies and anti-forgery tokens; GET never changes state.
  • Server-side fetches resolve and check every IP, connect to the checked IP and don't auto-follow redirects; IMDSv2 is enforced.
  • User input never becomes a file path directly; containment is checked on the canonical path.
  • Deserializers produce only concrete DTO types; pickle, BinaryFormatter, Java native serialization and default typing are absent.
  • Passwords use Argon2id, scrypt or bcrypt with rehash-on-login and breached-password screening.
  • Encryption uses AES-GCM or ChaCha20-Poly1305 from the standard library, a fresh nonce per message, and keys from a KMS.
  • Tokens and keys come from the CSPRNG; secrets are compared in constant time.
  • Secrets have wrapper types or redaction, never appear in URLs or logs, and are scanned for in CI.
  • Dependencies are locked with hashes, scanned, updated continuously, and reviewed when added; an SBOM is produced per build.
  • Every service and person has the least privilege that works; failures fail closed.
  • New features with new data flows get a one-hour STRIDE session.

Self-check

A search endpoint lets users sort by any column: ORDER BY {sort}. You can't use a parameter for a column name. What do you do?

Map the user's choice through an allowlist of known column names ({"name": "p.name", "price": "p.price"}), and fall back to a default for anything else. The user's text never reaches the SQL; only your own constant strings do. Escaping or quoting the identifier is fragile and database-specific.

Your review form HTML-encodes all output. A security tester still gets script to run via the "website" field on the profile page. How?

The website is written into an href. javascript:alert(document.cookie) contains no <, >, " or &, so HTML encoding leaves it unchanged, and it runs on click. URLs need a scheme allowlist (http:/https:) on input and when rendering; a strict CSP blocks javascript: URLs as a second layer.

A teammate says the link-preview feature is safe from SSRF because it blocks URLs containing "127.0.0.1", "localhost" and "169.254". Give three ways around it.

Any three of: the decimal form http://2852039166/ (169.254.169.254), hex 0xA9FEA9FE, short forms like 127.1, IPv4-mapped IPv6 [::ffff:169.254.169.254], a DNS name that resolves to a private IP, DNS rebinding (public on the check, private on the fetch), or an open redirect on an allowed host. The fix is to check the resolved IP at connect time, not the URL text.

Why is SHA-256 fine for storing API keys but wrong for storing passwords?

Both need a one-way function, but the attacker's strategy differs. API keys are long and random (for example 256 bits), so guessing is impossible however fast the hash is, and a fast hash keeps lookups cheap. Passwords are short and human-chosen, so attackers guess them from word lists, and the hash's speed decides how many guesses per second they get. Slow, memory-hard password hashes cut that from billions to thousands per GPU.

An encryption helper uses AES-GCM with a nonce derived from the record ID. What can go wrong?

If the same record is ever encrypted twice with the same key (an update, a re-encryption, a restore into another environment that shares the key), the nonce repeats. Two ciphertexts with the same key and nonce XOR to the XOR of the plaintexts, and with GCM the authentication key leaks too, allowing forgeries. Use a fresh random 96-bit nonce per encryption, stored with the ciphertext, and put the record ID in the associated data instead.

In a STRIDE session, which threats do you consider for the flow from the payment provider's webhook to your API, and what mitigates each?

It's a data flow crossing a trust boundary, so Tampering (verify the HMAC signature with a constant-time compare over the raw body), Information disclosure (TLS; don't log the full payload), and Denial of service (size limits, rate limits, quick acknowledgment with queued processing). The sender itself is an external entity, so also Spoofing (only signed requests count) and Repudiation (store the event ID and signature; process idempotently).
