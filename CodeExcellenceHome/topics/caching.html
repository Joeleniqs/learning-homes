DATA & CACHING

Caching: When To, When Not To, and How

Cache-aside, read/write-through, write-behind, eviction policies, TTLs, stampedes, invalidation, HTTP caching and distributed caches, with a decision tree for whether to cache at all.

Intermediate → Expert~75 min studyUpdated 2026-11-03

The problem: the fastest query is the one you never run

A product page runs three queries, about 40 ms in total, and it is requested 2,000 times a second. Nearly every one of those requests asks for the same few hundred products, and a product changes perhaps twice a day. So the database spends most of its time computing answers it computed a moment ago. A cache keeps a copy of the answer close to the code that needs it, and turns 40 ms into 0.5 ms.

That is the whole appeal, and it is real. The trouble is what tends to come with it. Here is the first version that most teams write:

public class ProductService(AppDb db)
{
    // static: shared by every request, forever
    private static readonly Dictionary<int, Product> Cache = new();

    public async Task<Product?> GetAsync(int id)
    {
        if (Cache.TryGetValue(id, out var p)) return p;   // not thread-safe
        p = await db.Products.FindAsync(id);              // 500 concurrent misses = 500 queries
        if (p != null) Cache[id] = p;                     // no size limit, no expiry
        return p;                                         // callers can mutate the cached object
    }

    public async Task UpdatePriceAsync(int id, decimal price)
    {
        var p = await db.Products.FindAsync(id);
        p!.Price = price;
        await db.SaveChangesAsync();                      // cache never told: old price forever
    }
}

public class ProductService(AppDb db, HybridCache cache)
{
    private static readonly HybridCacheEntryOptions Options = new()
    {
        Expiration = TimeSpan.FromMinutes(5),             // bound staleness (L2 + L1)
        LocalCacheExpiration = TimeSpan.FromMinutes(1),   // in-process copy lives less
    };

    public ValueTask<ProductDto?> GetAsync(int id, CancellationToken ct) =>
        cache.GetOrCreateAsync(
            $"product:v1:{id}",                           // namespaced, versioned key
            async token => await db.Products.AsNoTracking()
                .Where(p => p.Id == id)
                .Select(p => new ProductDto(p.Id, p.Name, p.Price))   // immutable DTO
                .FirstOrDefaultAsync(token),
            Options, tags: ["products"], cancellationToken: ct);      // one load per key at a time

    public async Task UpdatePriceAsync(int id, decimal price, CancellationToken ct)
    {
        await db.Products.Where(p => p.Id == id)
            .ExecuteUpdateAsync(s => s.SetProperty(p => p.Price, price), ct);  // DB first
        await cache.RemoveAsync($"product:v1:{id}", ct);                       // then invalidate
    }
}

The "before" version has five bugs, and none of them shows up in a unit test. It grows without bound until the process runs out of memory. It never expires, so a missed invalidation is permanent. The price update doesn't invalidate, so the page shows the old price until the next deploy. When the cache is cold (after every deploy), 500 concurrent requests for the same product cause 500 identical queries. That is a stampede. And it hands out shared mutable objects, so one request that changes p.Name for display changes it for everyone. Every one of those bugs comes from treating a cache as a dictionary. A cache is really a second copy of your data, with its own lifetime and its own consistency rules.

Cache only when a stale copy is acceptable, the copy will be read many times before it changes, and a miss costs much more than a lookup. Then bound every entry: a size, a TTL, and a write path that invalidates it.

This topic is about that decision first, and the mechanics second. It leans on Data Access Patterns (what you're caching in front of), Performance Patterns (measure before you optimise) and Resilience Patterns (what happens when the cache itself fails).

Should you cache at all?

Caching is a bet. You trade memory, code complexity and a second source of truth for latency and database load. Six questions decide whether the bet pays off. Ask them in this order, because each one is cheaper to answer than the next, and any of them can end the discussion.

  1. Can readers tolerate stale data? A cache is a copy, and copies lag. If the answer must be exact at the moment it is read (an account balance before a withdrawal, stock count at checkout, "is this user still allowed?"), don't cache that read path.
  2. Is a miss much more expensive than a lookup? A Redis round trip costs about 0.5 ms. Putting it in front of a 0.8 ms primary-key lookup buys almost nothing, and every miss now pays both costs.
  3. Is the data read much more often than it is written? Every write invalidates the entry. If an entry is replaced before anyone reads it twice, the cache only adds work.
  4. Will the hit rate be high? The same key has to be requested again while its copy is still valid, and the working set has to fit in memory.
  5. Is the data shared or per-user? Shared data (catalogue, configuration, exchange rates) gives one entry for millions of reads. Per-user data multiplies memory by the number of users, gets fewer hits per key, and risks leaking one user's data to another.
  6. Do users need to read their own writes? If they do, expiry alone isn't enough: the write path must invalidate.

Put your own numbers into the tree. The hit-rate estimate uses a deliberately pessimistic model: uniform traffic over every key. Each key is read reads ÷ keys times a second, and an entry lives for the shorter of its TTL and the time to the next write. So one miss buys about n = reads per key × lifetime hits, and the hit rate is roughly n ÷ (n + 1), scaled down by the fraction of keys that fit in the cache. Real traffic is usually skewed (a few keys get most of the reads), which only improves the hit rate. If the uniform estimate already says yes, you're safe.

Try Randomize a few times. Each preset is a real kind of workload: a hot catalogue (cache it), a write-heavy counter (don't), a long tail of a million keys (the uniform model says no, so check how skewed the real traffic is), and a sub-millisecond lookup behind Redis (don't).

Insight Hit rate is set by reuse within the entry's lifetime, not by how popular the data feels. A key read once a minute, with a 30-second TTL, never hits, however important it is. That's why the tree asks about reads per key and lifetime instead of "is it slow?".

What a cache costs you

The benefits are easy to see in a benchmark. The costs show up later, in production:

Cost What it looks like in production
A second source of truth Two copies can disagree. Every caching bug is a variant of "the copy is wrong and nobody knows".
Staleness bugs "I changed my address and the confirmation email used the old one." These are hard to reproduce, because they depend on timing.
Invalidation code Every write path must know which keys it affects. A new write path (an admin tool, a batch job, a second service) that forgets is a latent bug.
Memory In-process caches compete with your app for heap and add GC pressure (see Memory and GC). Distributed caches are another system to size and pay for.
Cold starts After a deploy, a restart or a flush, every request misses at once. If the database can't take full traffic, a cache restart becomes an outage.
Hidden load-bearing At a 95% hit rate the database only sees 5% of traffic, and it gets sized for that. The cache has quietly become something the system can't run without.
Security A key that forgets the tenant or user, or a CDN that stores a personalised page, serves one user's data to another.
Masking A cache in front of a slow query hides it until the cache misses, which happens at the worst possible moment.

Pitfall: the cache becomes load-bearing If the database can't survive the cache being empty, the cache isn't an optimisation any more: it's a critical dependency with no durability. Either size the source for a cold cache, or plan for one explicitly. Warm the cache gradually after deploys, use request coalescing, rate-limit misses, or serve stale data during an outage (see Resilience Patterns).

When NOT to cache

The tree's red leaves come up often enough to deserve their own list. Each card shows a case where caching is the wrong tool, and what to do instead.

Data that must be exact

Balances, inventory you decrement, seat maps, permissions, feature entitlements, rate-limit counters. A stale read here is a bug, not a trade-off. Instead: make the source fast (an index, a projection), or cache the immutable inputs (product names, plan definitions), never the decision.

Write-heavy or read-once data

Counters, presence, "last seen", audit rows, one-off search queries, report exports. Each entry is overwritten or abandoned before its second read. Instead: batch the writes, aggregate in the database, or use a data structure built for it (a Redis counter is a primary store, not a cache).

Already-fast sources

A primary-key lookup with hot pages in the buffer pool takes about 1 ms. A Redis hop plus deserialization costs 0.3–1 ms. You've added a dependency and a staleness window for little gain. Instead: let the database's own cache work, or use a tiny in-process cache if the profile says so.

Per-user data in a shared cache

It's legitimate, but it's where the leaks happen. Every key must include the user or tenant, the hit rate per key is low, and memory grows with users. Prefer the browser (Cache-Control: private) or the session, with short TTLs.

Huge or cheap-to-compute values

A 2 MB object that takes 3 ms to serialize, sent over the network to save a 4 ms computation, is a loss. It also blocks single-threaded Redis while it's transferred. Instead: cache a smaller projection, compress, or keep it in-process.

A slow query you haven't looked at

A cache in front of a 2-second query turns a performance bug into a correctness and availability risk. First run EXPLAIN, add the index, fix the N+1 (see Data Access Patterns). Cache what is still slow after that.

War stories

The revoked admin who stayed an admin Permissions were cached per user for an hour, to save a join on every request. An employee left, their role was removed, and they kept admin access until the entry expired. The fix was to stop caching the decision (does this user have this role?). The service now caches the role definitions, which rarely change and aren't per-user, and reads the user's role assignments fresh, or invalidates them with an event when access changes.

The CDN that served other people's accounts A change in CDN configuration let account pages for signed-in users be cached at the edge, so visitors briefly saw other users' account details. This is a well-known failure, and it was widely reported for Valve's Steam store in December 2015. Responses that depend on who is asking need Cache-Control: private or no-store. When the edge could cache by mistake, a Vary on the auth header or cookie is the backstop. And the safe default is to cache only what you have explicitly marked as public.

Cache restart, database outage A Redis failover emptied the cache at peak traffic. The hit rate dropped from 97% to zero, so database load jumped about 30 times, queries timed out, retries doubled the load, and the site went down. Nothing was "wrong" with the cache. The system had just never been tested with it empty. Facebook's widely cited September 2010 outage had a similar feedback loop: clients that saw an invalid cached configuration value all went to the database to fix it at once.

"User not found", cached for a day A sign-up flow read the user back right after creating it, and hit a read replica that hadn't caught up yet. The "not found" result was cached with the default 24-hour TTL. New users couldn't log in until the next day. Negative results need their own, much shorter TTL. Errors and timeouts must never be cached as if they were answers.

Where caches live

"Add a cache" isn't specific enough. Caches exist at every layer between the user and the disk, and each layer trades latency for scope and for how much control you have. The useful question is: which hop am I trying to skip?

Layer Typical latency Shared by Who can invalidate it Good for
CPU caches (L1/L2/L3) 1–40 ns one core / socket hardware only data layout: arrays beat pointer chasing (Performance Patterns)
Browser cache ~0 (no request) one user nobody (you can't recall it) static assets, per-user GETs with private
CDN / reverse proxy 10–30 ms (edge RTT) everyone near a PoP you, by purge API or tag public pages, images, API responses that are identical for everyone
In-process (L1) ~100 ns one process that process only small, hot, read-mostly data: config, reference data, compiled templates
Distributed (L2): Redis, Memcached 0.2–1 ms every app instance any instance shared session-like data, computed views, rate-limit state, larger working sets
Database buffer pool ~1 ms for an indexed query every query the DB, automatically everything; it's free and always consistent

Two things in this table are easy to miss. First, the database already caches. PostgreSQL's shared buffers, SQL Server's buffer pool and MySQL's InnoDB buffer pool keep hot pages in RAM, so an indexed query on hot data is often within 2× of a Redis round trip. And unlike Redis, it is never stale. Second, the closer a cache is to the user, the harder it is to invalidate. You can delete a Redis key. You can purge a CDN, but it takes time to propagate. A response sitting in a browser can't be recalled at all.

Pick where the request is answered and compare the totals. The insight is in the bars: the network hop you skip matters far more than how fast the store is.

Recognize it "We added Redis and it barely helped." Look at what it replaced. If the query it fronts was already ~1 ms from the buffer pool, a ~0.5 ms Redis hop plus deserialization is a wash. The wins come from skipping an expensive computation, or a wide-area round trip.

Five caching patterns

The patterns differ in two ways: who talks to the database (your code, or the cache), and when a write reaches the database (before the cache, with it, or later). Cache-aside is the default, and it's what most of this topic assumes.

Each visualizer below plays a list of operations against a cache and a database that start with a=10, b=20, c=30. The operations are R a (read), W a=5 (write), wait 3 (let time pass, in ticks), and for write-behind, crash. Edit the operations to try your own sequences, and watch the cache and database panels drift apart and come back together.

Cache-aside (lazy loading)

The application owns both conversations: ask the cache; on a miss, query the database and set the cache; on a write, update the database and delete the key. The cache is a dumb key-value store. It's the most flexible pattern, and it works with any cache, but the read path has a gap between "load" and "set" that matters later, in the race section.

Read-through

Same behaviour, but the cache owns the loader: your code only calls cache.get(key), and the cache calls the database on a miss. HybridCache.GetOrCreateAsync, a Caffeine LoadingCache and lru-cache's fetchMethod are all read-through. Because all misses go through one place, the cache can coalesce concurrent misses for the same key, which is exactly what stops a stampede.

Write-through

Writes go to the cache, and the cache writes them to the database synchronously before acknowledging. Readers always see the latest value, and a read right after a write is a hit. The cost is write latency (both stores) and memory spent on values that may never be read. It's usually paired with read-through.

Write-behind (write-back)

Writes are acknowledged once they're in cache memory, and flushed to the database later in batches, so several writes to the same key collapse into one. That's very fast and very kind to the database. It's also the only pattern where the cache holds data the database doesn't have: the crash step loses every queued write. Use it only where losing recent writes is acceptable (view counters, analytics) or the cache is itself durable and replicated.

Refresh-ahead

When a hot entry is read near the end of its life (here, with less than half its TTL left), the cache serves the current value and reloads it in the background. A key that keeps being read never expires, so nobody pays the miss. Caffeine's refreshAfterWrite and stale-while-revalidate in HTTP are both refresh-ahead. The cost is loads for keys that turn out not to be read again.

Pattern Read miss handled by Write goes to Stale window Risk Reach for it when
Cache-aside your code DB, then delete key until delete or TTL load/set race, forgotten invalidation the default; any cache, any data
Read-through the cache's loader (usually) DB + delete until delete or TTL loader must be idempotent you want coalescing and one place for loading
Write-through the cache's loader cache → DB, synchronously ~none for this cache slower writes, cold data in memory reads right after writes are common
Write-behind the cache's loader cache now, DB later DB lags the cache data loss on crash write bursts on loss-tolerant data
Refresh-ahead background reload (any of the above) up to one refresh wasted reloads a few very hot keys that must never miss

Eviction: what to throw away

A bounded cache has to choose a victim when it's full. The policy decides which keys survive, and the hit rate depends on how well that guess matches your access pattern.

  • LRU (least recently used) evicts the key untouched for longest. It's great when recent use predicts future use, which is most of the time. Its weakness is scans: one pass over 10,000 cold keys pushes out every hot key.
  • LFU (least frequently used) evicts the key with the fewest hits. It resists scans, but old popularity lingers: yesterday's hot key, with 10,000 hits, outlives today's. Real implementations age the counts.
  • FIFO evicts the oldest insert, regardless of use. It's simple and cheap, and it's usually worse than LRU. It's included here as a baseline.
  • TTL isn't a replacement policy. It bounds staleness, not memory. Expired entries die whatever the pressure; you still need a size limit.
  • Size limits can count entries, or weigh them (bytes, cost). With a count limit, one 50 MB value counts the same as a 50-byte one.
  • W-TinyLFU (Caffeine, and ristretto's admission policy) combines a small LRU window with a frequency sketch that decides whether a newcomer is worth more than the victim. It's near-optimal across most workloads, so you don't have to choose. Use it when your library offers it.

Check your Redis eviction policy Redis's maxmemory-policy defaults to noeviction: when memory is full, writes fail with an error instead of evicting. For a cache, set maxmemory and use allkeys-lru or allkeys-lfu. Use the volatile-* policies only if the same Redis also holds data that must never be evicted, and then ask whether it should be a separate instance.

Type an access sequence, choose a capacity and a policy, and step through. The final frame compares the policy with OPT, Bélády's optimal policy, which evicts the key that will be used furthest in the future. It needs to see the future, so no real cache can implement it, but it gives the upper bound on the hit rate. The default sequence has a hot pair (A, B) and some one-off keys. Try A B C D E A B C D E with capacity 4: every policy scores 0, because the loop is one key bigger than the cache. That's the classic LRU worst case.

TTL, sliding expiration and jitter

A TTL is your staleness budget. It bounds how wrong a cached value can be if every invalidation fails. Choose it from the business tolerance ("prices may lag by a minute"), not from what makes the hit-rate graph look good.

  • Absolute expiration ends an entry a fixed time after it was written. This is the one that bounds staleness.
  • Sliding expiration extends an entry each time it's read. A hot key with sliding expiration never expires, so it can be stale forever. Only use sliding expiration with an absolute cap as well, and for things like sessions, where "idle timeout" is what you mean.
  • Separate TTLs for separate truths. Positive results, negative results ("not found") and errors each get their own (see negative caching).

The trap: entries loaded together expire together. A deploy, a cache flush or a nightly warm-up loads thousands of keys in the same second, and exactly one TTL later they all miss in the same second, and do so again every TTL after that. Jitter spreads the expiry times out: ttl × (1 ± random × jitter).

With no jitter, 1,000 keys expire in one bucket and the database sees one massive spike per TTL. With ±10–20% jitter, the reloads become a gentle hump that stays under what the database can absorb, and the second and third waves smooth out further. Jitter costs one line of code:

static TimeSpan Jittered(TimeSpan ttl, double spread = 0.15) =>
    ttl * (1 + spread * (2 * Random.Shared.NextDouble() - 1));   // ttl ± 15%

Cache stampede (thundering herd)

A hot key expires. In the time it takes to recompute it (say 200 ms), every request for it misses, and every one of them starts the same expensive query. At 1,000 requests a second that's 200 identical queries, all arriving at once at a database that is already slow because of the load. Recompute time goes up, so more requests miss, and the herd feeds itself. The same thing happens on a cold start, when every key is missing.

There are three families of fixes:

  • Coalesce (single-flight, or a lock). The first miss for a key does the load. Everyone else who misses meanwhile waits for that result instead of starting their own. One load per key per process; with a distributed lock, one per cluster.
  • Serve stale while one caller refreshes. Keep the expired value around a little longer. One caller refreshes it, and everyone else gets the old value at once. Nobody waits, as long as stale is acceptable.
  • Refresh early, probabilistically (XFetch). Before the expiry, each request recomputes with a probability that rises as the expiry gets closer, scaled by how long the recompute takes. Usually one request refreshes the value just before it expires, with no coordination at all. The rule is: recompute when now − Δ·β·ln(rand()) ≥ expiry, where Δ is the recompute time and β ≥ 1 makes it more eager.

Compare them on the same traffic. Each row is a tick, and each cell is one request: H hit, M miss that recomputes, W waits for someone else's load, S served stale, R served stale and also starts the one background refresh, E won the early-refresh roll and recomputes before the expiry (that one request waits). The bottom row is database load.

With the defaults, no protection costs a dozen recomputes for one expiry. Coalescing costs one, but eleven requests wait for it. Serve-stale costs one and nobody waits. XFetch refreshes before the expiry, so callers rarely see a miss at all; with a recompute this long relative to the TTL, a few early rolls overlap, which a lock would remove. Raise recompute to 6 ticks and watch the no-protection row get much worse: the herd grows with recompute time × request rate.

The tabs show request coalescing in each ecosystem. Most mature caching libraries do it for you, if you use their get-or-load API instead of a separate get and set.

// HybridCache (.NET 9+): concurrent callers for the same key share one factory call,
// per process. IMemoryCache.GetOrCreateAsync does NOT do this: every caller runs the factory.
public ValueTask<ProductDto?> GetAsync(int id, CancellationToken ct) =>
    cache.GetOrCreateAsync(
        $"product:v1:{id}",
        async token => await LoadProductAsync(id, token),
        cancellationToken: ct);

// Caffeine: get(key, loader) is atomic per key; other threads block until the one load finishes.
LoadingCache<Long, Product> products = Caffeine.newBuilder()
    .maximumSize(10_000)
    .expireAfterWrite(Duration.ofMinutes(5))
    .refreshAfterWrite(Duration.ofMinutes(1))   // refresh-ahead: readers get the old value meanwhile
    .recordStats()
    .build(id -> repository.findById(id).orElse(null));

// Spring: sync = true makes concurrent misses for the same key wait for one load (per JVM).
@Cacheable(cacheNames = "products", key = "#id", sync = true)
public Product find(long id) { return repository.findById(id).orElseThrow(); }

import asyncio, json

class SingleFlight:
    """At most one in-flight load per key; other callers await the same future."""
    def __init__(self) -> None:
        self._inflight: dict[str, asyncio.Future] = {}

    async def do(self, key: str, load):
        fut = self._inflight.get(key)
        if fut is None:
            fut = asyncio.ensure_future(load())
            self._inflight[key] = fut
            fut.add_done_callback(lambda _: self._inflight.pop(key, None))
        return await asyncio.shield(fut)   # one caller's cancellation must not cancel the rest

flight = SingleFlight()

async def get_product(pid: int) -> dict | None:
    key = f"product:v1:{pid}"
    if (raw := await r.get(key)) is not None:      # r = redis.asyncio.Redis(...)
        return json.loads(raw)

    async def load():
        row = await db.fetch_product(pid)
        await r.set(key, json.dumps(row), ex=300)
        return row

    return await flight.do(key, load)

var group singleflight.Group // golang.org/x/sync/singleflight

func (s *Service) Product(ctx context.Context, id int) (*Product, error) {
    key := fmt.Sprintf("product:v1:%d", id)
    if p, ok := s.cache.Get(key); ok {
        return p, nil
    }
    v, err, _ := group.Do(key, func() (any, error) {
        // Detach from the first caller's cancellation: everyone shares this result.
        p, err := s.db.Product(context.WithoutCancel(ctx), id)
        if err != nil {
            return nil, err // errors are shared too, but not cached
        }
        s.cache.SetWithTTL(key, p, 1, 5*time.Minute)
        return p, nil
    })
    if err != nil {
        return nil, err
    }
    return v.(*Product), nil
}

import { LRUCache } from 'lru-cache';

// fetch() is read-through: concurrent fetches for the same key share one promise.
const products = new LRUCache<number, Product>({
  max: 10_000,
  ttl: 5 * 60_000,
  allowStale: true,                         // return the stale value while it refreshes
  fetchMethod: async (id, _stale, { signal }) => db.product(id, { signal }),
});

const p = await products.fetch(42);

Insight: coalescing is per process Single-flight stops the herd inside one process. Fifty instances can still send fifty loads for the same key. That's usually fine: 50 is not 50,000. When it isn't, add a short distributed lock (SET lock:key token NX EX 10, released with a compare-and-delete script so you never delete someone else's lock), and have the losers serve stale data or retry the cache after a short wait. Always give the lock an expiry, so a crashed holder can't block the key forever.

Invalidation strategies and their races

"There are only two hard things in computer science: cache invalidation and naming things." The joke is popular because invalidation really is a distributed-systems problem: two stores, no transaction across them, and concurrent readers and writers.

Strategy How Staleness Good for Watch out for
TTL only entries expire; writes don't touch the cache up to the TTL data that changes on its own (feeds, rates), or where a lag is fine choosing the TTL from the hit rate instead of the tolerance
Delete on write after the DB commit, DEL key until the delete (ms) + races the default with cache-aside every write path must know every affected key
Update DB, then delete strictly in this order, after commit as above always prefer it to delete-then-update delete-then-update lets a reader refill the old value before your commit
Versioned keys key includes a version: product:v42:7, or a group generation catalog:gen:19:… none for the new version invalidating a whole group with one increment; deploys that change the schema old versions linger until evicted (set a TTL)
Event-driven a change event (outbox, CDC, pub/sub) triggers invalidation in every service event lag (ms–s) caches owned by other services (Distributed Architecture) lost or reordered events; the consumer must be idempotent
Tags entries carry tags; evict by tag until the eviction "everything about product 7", CDN surrogate keys tag sets that grow without bound

Why delete rather than set the new value on write? A set races with other writers: if A writes 2 and B writes 3, but their cache sets arrive in the opposite order, the cache ends at 2 while the database says 3, until the TTL expires. A delete is idempotent: whatever order deletes arrive in, the next read loads the committed value.

Deleting isn't completely safe either. The classic remaining race is a stale set after delete:

Step through the six scenarios. The verdict at the end of each one says whether the cache and the database agree.

  • Stale set after delete: the race above. It's rare (it needs a slow reader and a write in a small window), but on hot keys at scale it happens daily.
  • Leases: on a miss the cache hands out a token, and a delete invalidates every outstanding token. A set with an invalidated token is rejected. Facebook described this mechanism in its 2013 paper on scaling memcache. It also helps with stampedes, because the cache can tell other missers to wait instead of issuing a second lease.
  • Delayed double delete: delete, then delete again a few hundred ms later, to remove anything a slow reader put back. It's cheap and narrows the window, but the delay is a guess.
  • Two writers, set on write: last arrival wins, not last commit, so the cache ends at the older value.
  • Two writers, delete on write: the order of the deletes doesn't matter, so the cache ends correct.
  • Versioned set: store a version with the value and reject a set whose version is older than the stored one (a compare-and-set, for example a short Lua script in Redis). Now the newest version wins, whatever the arrival order.

Write the database first, then delete the key, and always keep a TTL as the backstop. Whatever race you didn't think of, the TTL bounds how long it can last.

Invalidate after commit, not inside the transaction If you delete the key inside the transaction, a reader can reload the old committed value before your commit lands. If you delete it and the transaction then rolls back, you've only cost a miss, which is harmless. Delete after the commit. For cross-service caches, write an outbox row in the same transaction and let a relay publish the invalidation event, so it can't be lost if the process dies between the commit and the delete.

Negative caching, keys and serialization

Negative caching

If "product 999 doesn't exist" isn't cached, every request for 999 goes to the database. A bug, a crawler or an attacker enumerating IDs can then bypass the cache completely (this is sometimes called cache penetration). The fix is to cache absence too, with care:

  • Store an explicit sentinel ("not found"), not null. Many cache APIs use null to mean "miss", so a cached null looks like a miss forever.
  • Give negative entries a much shorter TTL (seconds, not hours). Things get created, and replicas catch up.
  • Never cache errors or timeouts as answers. A database blip would become an hour of "not found".
  • Delete the negative entry when the thing is created. Otherwise "create, then read" fails for one negative TTL.
  • For huge ID spaces, a Bloom filter of the IDs that exist can reject impossible keys before they reach either store.

Key design

A key must capture every input that changes the output, and nothing else. Too little and users see each other's data. Too much and the hit rate collapses.

{app}:{entity}:v{schema}:{tenant}:{id}[:{variant}]
shop:product:v3:t42:1007:en-GB:GBP
  • Namespace and version. The v3 lets a deploy that changes the cached shape use new keys instead of deserializing old bytes into a new type.
  • Tenant and user whenever the data depends on them. Most cache leaks between users are a missing key component.
  • Variants: locale, currency, role, feature flags, anything else the response depends on.
  • Normalize inputs: lowercase, trim, sort query parameters. ?a=1&b=2 and ?b=2&a=1 should be one entry.
  • Hash long inputs (SHA-256 of a normalized query), but keep a readable prefix for debugging and metrics.
  • No secrets or personal data in keys. Keys show up in logs, MONITOR output and metrics labels.
  • Watch the cardinality. A timestamp or a random ID in a key means every entry is read once.

Serialization cost

An in-process cache stores references, so a hit costs nothing extra. Every distributed cache stores bytes, so every hit pays to deserialize and every set pays to serialize. For large objects that can cost more than the network hop.

  • Cache projections (the DTO the page needs), not entity graphs with lazy-loaded navigation properties.
  • Measure. JSON is easy to debug. MessagePack or Protobuf is often several times smaller and faster. Compress values over a few KB.
  • Keep values small. Redis runs commands on one thread, so a multi-megabyte value blocks every other client while it's sent. Very hot keys concentrate load on one shard: put them in L1, or replicate them.
  • Cache immutable values. If a cached object is mutable and shared, one caller's edit changes it for every reader in the process. Use records or frozen copies, or have the cache hand out copies.

Two-level caches (L1 + L2) and the backplane

An in-process L1 is about 1,000× faster than a distributed L2, but each instance has its own copy. A layered cache checks L1, then L2, then the source, and fills both on the way back. That gives you most of L1's speed and most of L2's sharing. The new problem: when instance 1 writes, instance 2's L1 copy is stale, and deleting the L2 key doesn't reach it.

The operations are 1:get (instance 1 reads), 2:set 7 (instance 2 writes 7) and wait 30 (seconds pass). Run the default with the backplane off: instance 2 keeps reading its old L1 copy until the L1 TTL ends. Switch it on and the stale read disappears.

  • Without a backplane, the L1 TTL is your staleness bound across instances. Keep it short (seconds to a minute) and keep L2's TTL longer.
  • With a backplane, invalidations are fast but best-effort: pub/sub messages sent while an instance is disconnected are lost. Keep the short L1 TTL anyway.
  • .NET: HybridCache provides L1 + L2 (any registered IDistributedCache), stampede protection and tags. As of .NET 9 it doesn't ship a backplane for L1 invalidation across instances, so rely on LocalCacheExpiration. FusionCache is a popular library that adds one. HybridCache only reuses a single L1 instance for types it knows are immutable (sealed and marked [ImmutableObject(true)]). Otherwise it deserializes a fresh copy per call, which protects you from shared mutation at some CPU cost.
  • Java: Caffeine (L1) in front of Redis, with Redisson or Spring's cache abstraction; invalidate via Redis pub/sub.

HTTP caching: let someone else store it

HTTP has a complete caching protocol built in, and it reaches places your own cache can't: the user's browser and CDN edges a few milliseconds from the user. You don't write a cache. You describe your responses with headers, and every cache along the path obeys them.

Header Meaning
Cache-Control: max-age=60 fresh for 60 s; any cache may reuse it without asking
s-maxage=300 overrides max-age for shared caches (CDN, proxies) only
public / private private: only the user's browser may store it (personalized responses)
no-cache store it, but revalidate before every use. It does not mean "don't cache"
no-store never store it anywhere. For secrets and one-time data
stale-while-revalidate=60 after expiry, serve the stale copy for up to 60 s while refreshing in the background
immutable this URL's content never changes; don't even revalidate. For fingerprinted assets (app.3f9a1c.js)
ETag: "v7" + If-None-Match: "v7" the validator: "I have v7, has it changed?" If not, a 304 Not Modified with no body
Last-Modified + If-Modified-Since the same thing with a date (1-second resolution)
Vary: Accept-Encoding, Accept-Language the response differs by these request headers, so caches must key on them too
Age: 42 how long a shared cache has held this copy

Two browsers (A and B) request the same resource through one CDN edge, at the times in the requests box. The content changes at t = 90. Change the Cache-Control value and watch three totals: requests that reach the origin, bytes transferred, and responses served stale (older than the origin's current version).

With public, max-age=60 and an ETag, the origin sees three requests and one user sees the old version after the change: that's the staleness you agreed to. no-cache sends every request to the origin, but most are cheap 304s and nobody sees stale content. private keeps the CDN out of it, and no-store sends the full body every time. There's no best setting, only the right staleness for each resource.

Pitfall: an ETag computed from the body saves bandwidth, not work Express's automatic ETag, Spring's ShallowEtagHeaderFilter and similar features hash the response after you've built it. The 304 saves the transfer, but your server still ran every query. To save the work as well, derive the ETag from something cheap (a row version or an updated-at timestamp) and check it before building the response, as the C# and Java tabs do.

Output caching is server-side, and conservative by default ASP.NET Core's output caching (AddOutputCache / UseOutputCache / .CacheOutput("policy")) stores whole responses on the server. Pitfall: lru_cache on a method @lru_cache on an instance method puts self in the key, so the cache holds a strong reference to every instance it has seen. They're never garbage-collected, and with the default maxsize=128 most of them never hit anyway. Cache module-level functions, or use a per-instance cache that dies with the instance. The same leak happens with any unbounded dict used as a cache, in any language.

Recognize it: the cache that fails the request A cache is an optimisation, so a cache outage should make you slower, not broken. Wrap cache reads and writes so that errors fall through to the source (as the Go tab does), with a short client timeout. A Redis client stuck on a 5-second connect timeout turns a cache outage into a site outage. Then apply the herd protections above, because the source is about to get every request. See Resilience Patterns.

Monitoring a cache

A cache you don't measure is a guess. Track these for each cache (and for each key prefix, if you can):

Metric Healthy Investigate when
Hit ratio hits ÷ (hits + misses) stable, and matches your estimate it drops after a deploy (key change? cold start?) or slowly decays (working set outgrew the cache)
Eviction rate low and steady it rises with traffic: capacity is too small, so entries die before their TTL and the hit ratio follows
Memory / entry count under the limit with headroom it's flat at the limit (constant evictions), or growing without bound (no limit!)
Load latency and load count loads ≈ misses loads ≫ unique keys (stampedes), or slow loads (the source is the problem)
Cache latency (p99) sub-ms for Redis it spikes: big values, hot keys, a saturated network or a slow command (KEYS *)
Errors / timeouts ~0 any sustained rate: your fallback path is now carrying the load

Where to read them: Redis INFO stats (keyspace_hits, keyspace_misses, evicted_keys, expired_keys) and INFO memory; IMemoryCache.GetCurrentStatistics() (with TrackStatistics = true); Caffeine's cache.stats() (with recordStats()); Python's fn.cache_info(); ristretto's Metrics (with Metrics: true). Export them as metrics (see Observability) and alert on the hit ratio dropping relative to its baseline: a single absolute threshold rarely fits more than one cache.

Insight: a hit ratio is only meaningful with the miss cost A 99% hit ratio on a 1 ms query saves less than an 80% hit ratio on a 500 ms query. Report time saved (hits × miss cost) or the database load avoided, not just the ratio. And note that a falling hit ratio may simply mean traffic got more diverse, which is not a cache bug.

Testing caches

Caches fail in ways that ordinary tests miss: time passes, many callers arrive at once, and the cache itself breaks. Test those explicitly.

  • Control time. Inject a clock (Caffeine's ticker, cachetools' timer, a func() time.Time in Go) so expiry tests run instantly and deterministically. Never sleep in a cache test.
  • Count loads. Wrap the loader with a counter and assert hits don't call it: get, get → 1 load, and write, get → 2 loads (the invalidation worked).
  • Test the herd. Start 50 concurrent gets for one cold key and assert exactly one load.
  • Test the write path. For every write operation, assert that the next read returns the new value. This catches forgotten invalidations, which are the most common cache bug.
  • Test with the cache down. Point the client at a dead port: requests should succeed (slower), not fail.
  • Test key isolation. The same ID for two tenants, two locales or two users must give different entries.
  • Don't let the cache hide bugs in other tests. Use a fresh cache per test, or none at all in tests that aren't about caching. See Testing Strategy.

Common pitfalls

  • Caching without a bound. Every cache needs a size limit and an expiry. "It's only a few keys" lasts until someone puts a user ID or a timestamp in the key.
  • Caching the decision instead of the data. Cache the role definitions, not "user 7 is an admin"; cache the price list, not "this cart is valid".
  • Setting instead of deleting on write. It races other writers. Write the DB, then delete the key.
  • Invalidating inside the transaction, or before it. Readers can reload the old row. Invalidate after the commit.
  • Forgetting a write path. An admin screen, a batch import or another service writes the table and nobody deletes the key. A TTL is your only safety net, so always set one.
  • Caching errors, timeouts or empty results with the normal TTL. One blip becomes hours of wrong answers.
  • Sliding expiration on hot keys. They never expire, so they're never refreshed.
  • Synchronized expiry. Thousands of keys loaded at once expire at once. Add jitter.
  • No stampede protection on hot keys. Use a get-or-load API that coalesces, or serve stale while one caller refreshes.
  • Mutable cached objects shared between requests in an in-process cache.
  • A key missing a dimension: tenant, user, locale, currency, role. That's how one user's data reaches another.
  • Personalized responses with public or no Cache-Control behind a CDN.
  • A cache that fails the request when the cache is down. Fall back to the source, with a short timeout.
  • A load-bearing cache nobody has tested empty. Know what the database does at a 0% hit rate.

Checklist

  • The data can tolerate the staleness of its TTL, and that TTL came from the business, not the hit-rate graph.
  • A miss costs well over 5× a lookup, and the expected hit rate (reads per key within the entry's lifetime) is high.
  • Every entry has a size bound and an absolute expiry; hot keys have jitter.
  • Writes update the source first, then delete (not set) the affected keys, after the commit.
  • Every write path that touches cached data invalidates it, or the TTL is short enough to accept missing ones.
  • Hot keys go through a coalescing get-or-load API or serve-stale; there's a plan for a cold cache.
  • Keys include every dimension that changes the value (tenant, user, locale, version) and nothing unbounded.
  • Negative results use a sentinel and a short TTL; errors are never cached.
  • Cached values are immutable or copied; large values are projected, compressed or kept out of the distributed cache.
  • Cache failures fall through to the source with a short timeout.
  • HTTP responses state their cacheability explicitly: private/no-store for anything personal, ETags for revalidation, immutable for fingerprinted assets.
  • Hit ratio, evictions, memory, load counts and cache errors are on a dashboard, with alerts relative to the baseline.
  • Tests cover expiry (with a fake clock), invalidation after each write, concurrent misses and the cache being down.

Self-check

A team wants to cache account balances for 5 seconds "because the balance endpoint is slow". What do you tell them?

Don't cache the balance. A balance is read before decisions (withdrawals, transfers, limit checks), so a 5-second-old value can authorise something that should have been refused: that's a correctness bug, not a trade-off. Make the read fast instead (an index, a maintained balance column, a projection), or cache only the immutable parts of the page (account name, product details). If a display-only page really can show a slightly old balance, label it ("as of 10:42") and never use that value for a decision.

2,000 reads/s are spread evenly over 1,000,000 keys, with a 60-second TTL. Roughly what hit rate should you expect, and why?

Very low: about 11%. Each key is read 0.002 times a second, so about 0.12 times per 60-second lifetime. One miss buys about 0.12 hits, and the hit rate is n ÷ (n + 1) ≈ 0.12 ÷ 1.12. Hit rate comes from reuse within the lifetime, and here most entries expire before their second read. It only works if real traffic is heavily skewed towards a small hot set, so measure the distribution before building it.

Why delete the key on write instead of setting the new value?

Two concurrent writers can commit in one order and set the cache in the other, leaving the older value cached until the TTL. Deletes are idempotent and order-independent: whatever order they arrive in, the next read loads the committed value from the database. (Write-through caches that serialize writes per key, or versioned compare-and-set, are the exceptions.)

You write the DB, then delete the key, and a reader still occasionally caches the old value. How?

The stale-set-after-delete race. The reader missed, loaded the old value, and then paused; the writer committed and deleted; the reader then set its old value. The delete happened before the stale set, so it didn't help. The TTL bounds the damage. Leases (the cache rejects sets after an invalidation), versioned compare-and-set, or a delayed second delete reduce or prevent it.

A hot key takes 2 s to recompute and is read 500 times a second. It expires. What happens, and what are three fixes?

Around 1,000 requests miss during the 2 seconds of recompute, and each one starts the same expensive query: a stampede that slows the database, which makes the recompute even slower. Fixes: coalesce (one load per key; the others wait for its result), serve stale while one caller refreshes, or refresh early (refresh-ahead or XFetch), so the key never expires under load. Add TTL jitter so many keys don't do this at the same moment.

What's the difference between Cache-Control: no-cache and no-store?

no-cache allows storing, but requires revalidation before every use. With an ETag, that's a cheap 304 when nothing changed, so you get bandwidth savings with no staleness. no-store forbids storing anywhere, so every request is a full response. Use no-store for sensitive one-time data, and no-cache (or a short max-age) for data that must always be current.

Instance 1 updates a product and deletes the Redis key. Instance 2 keeps serving the old price for 30 seconds. Why?

Instance 2 has its own in-process L1 copy, and deleting the L2 (Redis) key doesn't reach it. It stays until the L1 expiration (here, 30 s). Fix it with a backplane (pub/sub invalidation of every L1), a shorter L1 TTL, or no L1 for data where 30 seconds of staleness across instances isn't acceptable.

Your Redis cache fills up and suddenly writes start failing with OOM errors. What's wrong?

Redis is using the default maxmemory-policy noeviction: at the memory limit it refuses writes instead of evicting. For a pure cache, set maxmemory and an eviction policy such as allkeys-lru or allkeys-lfu. Also check that every key has a TTL and that nothing unbounded (timestamps, request IDs) is in the keys.

Users report that after they sign up, login says "user not found" for a while. Sign-up and login both work in tests. What would you look for?

A negative result cached during replication lag. Login read the user from a replica that hadn't seen the insert yet, and the "not found" was cached, probably with the normal TTL. Give negative entries a short TTL, delete the negative key when the user is created, and read your own writes from the primary (or skip caching) right after creating something. Tests miss it because they have no replica lag and a fresh cache.

Don't cacheMoney, stock, permissions, rate limits, write-heavy or read-once data, sub-ms sources, slow queries you haven't fixed.
