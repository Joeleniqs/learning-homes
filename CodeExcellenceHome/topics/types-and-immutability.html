FOUNDATIONS OF CRAFT

Types, Immutability & Domain Modelling

Make illegal states unrepresentable: value objects, records, sum types, immutability and parse-don't-validate.

Intermediate → Advanced~50 min studyBuilds on: Cross-Language Mental ModelsUpdated 2026-11-03

The problem: the type said string, the bug said otherwise

Most production bugs are not clever. They are a value that should never have existed: an order that is both cancelled and shipped, a customer ID passed where an account ID belonged, a list that someone else changed while you were holding it. In each case the language would have stopped the bug if the types had said what the code meant. They didn't, so the bug waited for production.

Language The code that compiled What happened The missing idea
C# Charge(order.AccountId, order.CustomerId, total) Both IDs were Guid. The arguments were swapped and a customer was charged on someone else's card. Strongly-typed IDs
TypeScript { status: "shipped", cancelledAt: new Date() } Five optional fields allowed 32 combinations; the UI showed "Shipped" and "Refund issued" on the same order. Illegal states
Java return this.items; from a getter A caller sorted the returned list in place, and the domain object's invariant "lines in insertion order" broke. Defensive copying vs immutability
Python cache[key] = value where key was a mutable dataclass The key was changed after insertion; the entry became unreachable and the cache leaked. Value objects and records
Go switch m := p.(type) { case Card: ...; case Bank: ... } A new Wallet payment method fell through silently and refunds returned zero. Tagged unions

All five bugs have the same shape: the type was wider than the meaning. A Guid can be any Guid, a string can be any text, a List can be changed by anyone who holds it. This page is about narrowing types until they match the meaning, across C#, Java, Python, Go and TypeScript, and about knowing when not to.

Rule. Use types to make wrong code fail to compile, not just to describe the data. Model each concept with its own type, make values immutable by default, parse untrusted input once at the boundary, and represent "one of several things" as a closed union that the compiler can check exhaustively.

Prerequisite: Language Mental Models, especially values vs references and equality. Sum types are introduced here at the level of design; Functional Patterns goes deeper into pattern matching and Option/Result.

Types are design tools, not paperwork

A type is a promise the compiler checks every time the code builds. The more a type promises, the less every function that receives it has to check. Compare two signatures for the same operation:

void Ship(string orderId, string address, bool expedited, DateTime? shippedAt)
void Ship(PaidOrder order, ShippingAddress to, ShippingSpeed speed)

The first accepts 2 strings that may be empty, a boolean whose meaning you read from the docs, and a nullable timestamp that might already be set. Every caller and every implementer must remember the rules. The second cannot be called with an unpaid order, an unparsed address or a speed that doesn't exist. The rules moved from comments and if statements into types, where the compiler enforces them for free on every build.

Four techniques do almost all of the work. The rest of the page takes them one at a time:

Technique What it promises Where the check lives C# Java Python Go TypeScript
Value object / record equal by value, valid by construction constructor or factory record, readonly record struct record @dataclass(frozen=True) struct + constructor func readonly type + factory
Immutability nobody changes it after creation compiler (C#, Java, TS), convention (Python, Go) init, ImmutableList final, List.of frozen, tuple unexported fields readonly, as const
Closed union exactly one of N known shapes compiler exhaustiveness switch + sealed records sealed interface + records Literal/union + assert_never interface + type switch (linter) discriminated union + never
Parse at the boundary "this was checked once" the type of the parsed value Email.Parse Email.parse Email.parse ParseEmail returning (Email, error) parseEmail returning a branded type

Where the guarantee comes from matters C#, Java and TypeScript enforce most of these at compile time. Python enforces nothing at run time unless you write the check yourself (frozen=True and __post_init__ do run), so the promise comes from mypy or pyright in CI. Go has no unions, no readonly and no generic variance, so the promise comes from unexported fields, constructor functions and linters such as exhaustive. Know which kind of promise you're relying on.

Make illegal states unrepresentable

The phrase comes from Yaron Minsky (OCaml): design your types so that a value which would be a bug can't be built. The most common violation is a bag of optional fields plus a set of rules that live only in someone's head:

// Before: 4 independent fields, 2^4 = 16 combinations, 5 of them legal
interface Order {
  paidAt?: Date;
  shippedAt?: Date;
  cancelledAt?: Date;
  trackingNo?: string;
}

Which combinations are legal? Shipped implies paid. Tracking number implies shipped. Cancelled excludes shipped. None of that is in the type, so every function must re-check it, and one of them will forget. The fix is to list the legal states as cases of a union, each carrying exactly the data that state needs:

// After: 5 cases, 5 legal states, 0 illegal ones
type Order =
  | { kind: "draft" }
  | { kind: "paid"; paidAt: Date }
  | { kind: "shipped"; paidAt: Date; shippedAt: Date; trackingNo: string }
  | { kind: "cancelled"; cancelledAt: Date }
  | { kind: "refunded"; paidAt: Date; cancelledAt: Date };

The visualizer enumerates every combination of the optional fields, runs the business rules on each, and then shows which union case (if any) can represent it. Illegal combinations have no case, so they simply can't be constructed. Try the three models: the counts are computed, not hard-coded.

The same design in all five languages. Notice where the language does the work and where you must:

{
    private Order() { }
    public sealed record Draft() : Order;

    public sealed record Cancelled(DateTimeOffset CancelledAt) : Order;
    public sealed record Refunded(DateTimeOffset PaidAt, DateTimeOffset CancelledAt) : Order;

Transitions become signatures Once each state is its own type, a transition is a function from one state type to another: Ship(Paid) -> Shipped. Shipping a draft isn't a runtime check any more; it's a compile error. Where the state is only known at run time (loaded from the database), switch once at the edge and call the typed transition from the matching arm.

Value objects and records

A value object is defined entirely by its values: two Money(10, "EUR") are interchangeable, the same way two 5s are. Compare that with an entity such as Customer, which has an identity that survives changes to its fields. Value objects should be:

  1. Immutable. "Changing" one creates a new one, so it can be shared, cached, used as a dictionary key and passed across threads without locks.
  2. Equal by value. ==/Equals compares fields, and the hash code agrees with equality.
  3. Valid by construction. The constructor or factory rejects bad input, so an instance is proof of validity.

Every one of the five languages now has a short way to declare the first two. The third is always up to you.

"Immutable record" is shallow everywhere A record whose field is a mutable List is only immutable at the top level. with, replace and object spread copy the reference to the list, so the original and the copy share it. Change the list through one and the other changes too, and in C# the two records still compare unequal, because List<T> compares by reference. The visualizer below runs this exact sequence and computes a == c per language.

The fix is the same in every language: make the fields themselves immutable (an immutable collection, a tuple, a ReadonlyArray, or a Go array/copied slice), and validate in one place. Here is a complete Money value object:

public readonly record struct Money
{
    public decimal Amount { get; }
    public string Currency { get; }

    public Money(decimal amount, string currency)
    {
        if (amount < 0) throw new ArgumentOutOfRangeException(nameof(amount), "Amount can't be negative.");
        if (currency is not { Length: 3 } || !currency.All(char.IsAsciiLetterUpper))
            throw new ArgumentException("Use an ISO 4217 code like EUR.", nameof(currency));
        (Amount, Currency) = (decimal.Round(amount, 2), currency);
    }

    public Money Add(Money other) => other.Currency == Currency
        ? new Money(Amount + other.Amount, Currency)
        : throw new InvalidOperationException($"Can't add {other.Currency} to {Currency}.");

    public override string ToString() => $"{Amount:0.00} {Currency}";
}

public record Money(BigDecimal amount, String currency) {
    public Money {                                     // compact constructor: runs for every instance
        Objects.requireNonNull(amount); Objects.requireNonNull(currency);
        if (amount.signum() < 0) throw new IllegalArgumentException("Amount can't be negative.");
        if (!currency.matches("[A-Z]{3}")) throw new IllegalArgumentException("Use an ISO 4217 code like EUR.");
        amount = amount.setScale(2, RoundingMode.HALF_EVEN);   // normalize so equals agrees: 10 vs 10.00
    }

    public Money add(Money other) {
        if (!other.currency.equals(currency)) throw new IllegalArgumentException("Currency mismatch");
        return new Money(amount.add(other.amount), currency);
    }
}

@dataclass(frozen=True, slots=True)
class Money:
    amount: Decimal
    currency: str

    def __post_init__(self) -> None:
        if self.amount < 0:
            raise ValueError("Amount can't be negative.")
        if not re.fullmatch(r"[A-Z]{3}", self.currency):
            raise ValueError("Use an ISO 4217 code like EUR.")
        # frozen blocks normal assignment; object.__setattr__ is the sanctioned escape hatch inside __post_init__
        object.__setattr__(self, "amount", self.amount.quantize(Decimal("0.01"), ROUND_HALF_EVEN))

    def add(self, other: "Money") -> "Money":
        if other.currency != self.currency:
            raise ValueError("Currency mismatch")
        return Money(self.amount + other.amount, self.currency)

    if cents < 0 {
        return Money{}, errors.New("amount can't be negative")
    }
    if !ccy.MatchString(currency) {
        return Money{}, fmt.Errorf("currency %q: use an ISO 4217 code like EUR", currency)
    }
    return Money{cents, currency}, nil
}

func (m Money) Cents() int64      { return m.cents }
func (m Money) Currency() string  { return m.currency }
func (m Money) Add(o Money) (Money, error) { // value receiver: works on a copy, returns a new value
    if o.currency != m.currency {
        return Money{}, fmt.Errorf("can't add %s to %s", o.currency, m.currency)
    }
    return Money{m.cents + o.cents, m.currency}, nil
}

// Money is comparable (only int64 and string fields), so a == b compares values and it works as a map key.
// Caveat: the zero value Money{} exists without NewMoney. Make "" currency mean invalid, or accept it.

// Brand + private constructor-like factory. Types vanish at run time, so the factory is the real guard.
declare const brand: unique symbol;
export type Money = Readonly<{ cents: number; currency: string }> & { readonly [brand]: "Money" };

export function money(cents: number, currency: string): Money {
  if (!Number.isSafeInteger(cents) || cents < 0) throw new RangeError("cents must be a non-negative integer");
  if (!/^[A-Z]{3}$/.test(currency)) throw new RangeError("Use an ISO 4217 code like EUR.");
  return Object.freeze({ cents, currency }) as Money;   // freeze: also immutable at run time
}

export const add = (a: Money, b: Money): Money => {
  if (a.currency !== b.currency) throw new Error(`Can't add ${b.currency} to ${a.currency}`);
  return money(a.cents + b.cents, a.currency);
};

export const equals = (a: Money, b: Money) => a.cents === b.cents && a.currency === b.currency;
// money(1000, "EUR") === money(1000, "EUR")  -> false: objects compare by identity. Use equals().

C# with skips your constructor with clones the record and then runs init setters. It does not run the constructor body, so validation in the constructor is bypassed. If a record enforces invariants, give its properties no init accessor (as above), or validate inside each init accessor. Python's dataclasses.replace does call __init__ and __post_init__, and Java has no with, so this trap is C#-specific.

Records vs classes vs structs: which one?

Record (reference) for value objects and messages

Money, Address, DTOs, events, commands, query results. Value equality and ToString for free, cheap to pass around. In C# prefer a record class unless profiling says allocation matters.

Struct / record struct for small hot values

Point, Rgb, Instant, IDs: up to roughly 16–24 bytes, immutable (readonly). No heap allocation, but every assignment copies, and a large struct copied around is slower than a reference. Go structs are values by default; pass a pointer only when the struct is large or must be mutated.

Class for entities with identity and lifecycle

Order, Customer, Account: identity stays the same while fields change, so value equality is wrong. Two customers named "Ada Lovelace" are different people. Equality should compare the ID (or stay reference equality).

Defensive copying vs immutability

When an object holds a mutable collection, two other parties can change it behind the object's back:

  • the caller who passed the list in and keeps using its own reference, and
  • any consumer who reads the list through a getter and then writes to it.

Both are aliasing: two names for one heap object. In the values and references model, a field that stores a reference shares the object with whoever else holds that reference. There are two defences, and they differ in cost:

  • Defensive copying. Copy on the way in (new List<>(tags)) and copy or wrap on the way out. It works in every language, but costs an allocation and an O(n) copy per call, and every author must remember to do it.
  • Immutability. Store a collection nobody can change. Sharing becomes free and safe, with no copies at all.

Immutability turns copying from a duty into an optimization With mutable data, every boundary must copy "just in case", and forgetting once is a bug. With immutable data, nobody needs to copy, so you copy once when converting from a mutable source and then share freely. That is also why immutable objects are thread-safe: there are no writes to race with (see Concurrency and Async).

Structural sharing: persistent data structures

The obvious objection to immutability is cost: if "adding" to an immutable list creates a new list, isn't every change O(n)? For a flat array, yes (ImmutableArray.Add copies everything). Persistent data structures avoid it with structural sharing: the new version reuses every part of the old one that didn't change, and only the path to the change is copied.

Run it on your own keys. The simulation builds v1 by inserting the keys in order, then inserts one more key persistently: it walks down, creates the leaf, and copies each node on the way back up. The final counters compare the nodes allocated with what a full copy would cost.

Spread is shallow structural sharing { ...state, cart: { ...state.cart, total: 42 } } in TypeScript (or with in C#) already shares every unchanged branch: only the objects on the path to total are new. Enums and tagged unions

An enum is a closed set of names: Card, BankTransfer, Wallet. Use a union when the set of cases is yours and closed

Order states, payment methods, API results, parse outcomes, commands in a CLI. Adding a case is a deliberate change, and the compiler lists every place that must handle it.

Use an interface (open polymorphism) when others add cases

Plugins, storage providers, notification channels. New implementations arrive without touching existing code (the open/closed principle, see Design Principles), so a central switch would be wrong.

Don't use a boolean or a string for a state

isShipped, isCancelled, status: string. Two booleans give four states when you meant three; a string allows "shiped". Both reappear as if chains in every function.

Recognize it: expression problem Unions make it easy to add operations (a new function with a switch) and hard to add cases (every switch changes). Interfaces are the opposite: easy to add cases (a new class), hard to add operations (every class changes). Choose by which one you expect to change more often.

Parse, don't validate

Alexis King's phrase names a subtle but important shift. A validator checks input and returns a boolean (IsValidEmail(s)), then the code carries on with the same string. The knowledge "this was checked" lives only in the programmer's head, so every layer either re-checks (wasted work and duplicated rules) or trusts that someone upstream did (and one day nobody did). A parser checks input and returns a new type (Email) or the errors. The knowledge is now in the type, and every function that takes an Email gets the proof for free.

There is a second, quieter benefit: a parser can normalize. " Ada@Example.COM " and "ada@example.com" are the same address. A validator that returns true for both leaves two different strings flowing through the system, and the duplicate check in the database misses. A parser returns the canonical form, so equality works.

The visualizer runs the real rules on your input, collecting all failures instead of stopping at the first. The two lanes then show what each layer receives. The database already contains ada@example.com; try the default input, then grace@@example.com, a b@example, or anything else.

    public Email {                                   // even 'new Email(...)' can't bypass the rules
        var errors = problems(value);
        if (!errors.isEmpty()) throw new IllegalArgumentException(String.join("; ", errors));
    }

    public static Either<List<String>, Email> parse(String raw) {     // Either from Vavr, or your own Result
        var s = raw == null ? "" : raw.strip();
        var errors = problems(s);
        return errors.isEmpty() ? Either.right(new Email(s.toLowerCase(Locale.ROOT))) : Either.left(errors);
    }

    static List<String> problems(String s) {
        var errs = new ArrayList<String>();
        if (s.isEmpty() || s.length() > 254) errs.add("length 1–254");
        int at = s.lastIndexOf('@');
        if (s.chars().filter(c -> c == '@').count() != 1) errs.add("exactly one @");
        if (at <= 0 || at > 64) errs.add("local part 1–64 chars");
        if (!DOMAIN.matcher(at >= 0 ? s.substring(at + 1) : "").matches()) errs.add("domain needs an inner dot");
        if (s.chars().anyMatch(Character::isWhitespace)) errs.add("no spaces");
        return errs;
    }
}

Variance: covariance and contravariance

If a Cat is an Animal, is a List<Cat> a List<Animal>? It feels like it should be, and the answer decides whether some of the most confusing type errors are protecting you or merely in your way. The rule is short:

  • A type that only produces T (returns it, yields it) can be covariant: a producer of Cats is a producer of Animals. IEnumerable<out T>, Sequence[T], readonly T[], ? extends T.
  • A type that only consumes T (takes it as a parameter) can be contravariant: a consumer of Animals is a consumer of Cats. Action<in T>, Comparer<in T>, Callable[[T], ...], ? super T.
  • A type that does both (a mutable list: get and add) must be invariant. Otherwise you could add a Dog through the List<Animal> view into what is really a list of Cats.

// Readonly views are safely covariant; mutable arrays are covariant too, which is unsound.
const cats: Cat[] = [new Cat("Tom")];
const view: readonly Animal[] = cats;      // safe
const animals: Animal[] = cats;            // compiles...
animals.push(new Dog("Rex"));              // ...and now cats[1] is a Dog
// Prefer readonly parameters: function totalWeight(xs: readonly Animal[]) accepts Cat[] safely.

// TS 4.7+ lets you annotate type parameters: interface Producer<out T> { next(): T }
// Method-syntax members stay bivariant even under strictFunctionTypes; use property syntax for callbacks:
interface Handlers { onCat: (c: Cat) => void }   // checked contravariantly

When mutability is the right choice

Immutability is a default, not a religion. Mutation is faster and simpler when nobody else can see it. The rule of thumb: mutate locally, publish immutably. A function may build a result with a mutable list, a StringBuilder or a dictionary, as long as what escapes is immutable or exclusively owned by the caller.

Mutate freely

  • Local accumulation: building a list inside a function, then returning it (or a frozen copy).
  • Builders: StringBuilder, ImmutableList.CreateBuilder, strings.Builder, Java Stream.Builder.
  • Hot paths with measured cost: buffers, pooled arrays (ArrayPool<T>), Span<T> parsing, numeric kernels.
  • Single-owner state: an aggregate mutated only through its own methods, inside one transaction.

Mutate with care

  • Entities with identity: Order.AddLine() is natural, but keep collections private and invariants checked.
  • ORM-tracked objects: EF Core and JPA track changes by mutation. Keep them in the data layer and map to immutable DTOs at the edge (see Data Access).
  • UI state: allowed in frameworks built for it (MobX, Vue reactivity), harmful in ones that compare by reference (React, Redux).

Don't mutate

  • Anything shared across threads without a lock.
  • Dictionary keys and set members after insertion.
  • Arguments the caller didn't hand over for mutation.
  • Configuration, cached values, static data: freeze them at startup.
  • Messages and events once published.

A builder gives you the convenience of mutation while constructing and the safety of immutability afterwards. It's the standard answer to "my immutable type has 12 fields and some are optional":

// Records + object initializers act as a builder; 'required' makes fields mandatory at compile time.
public sealed record HttpOptions
{
    public required Uri BaseAddress { get; init; }
    public TimeSpan Timeout { get; init; } = TimeSpan.FromSeconds(10);
    public int MaxRetries { get; init; } = 3;
    public ImmutableDictionary<string, string> Headers { get; init; } = ImmutableDictionary<string, string>.Empty;
}

var opts = new HttpOptions { BaseAddress = new("https://api.example.com"), MaxRetries = 5 };

// Building a big collection: mutate a builder, publish once.
var b = ImmutableArray.CreateBuilder<Order>(initialCapacity: rows.Count);
foreach (var row in rows) b.Add(Map(row));
ImmutableArray<Order> orders = b.MoveToImmutable();   // no copy when Count == Capacity

// Classic builder for an immutable class (Lombok's @Builder generates this).
public final class HttpOptions {
    private final URI baseAddress; private final Duration timeout; private final int maxRetries;
    private HttpOptions(Builder b) { baseAddress = Objects.requireNonNull(b.baseAddress); timeout = b.timeout; maxRetries = b.maxRetries; }
    public static Builder builder() { return new Builder(); }

    public static final class Builder {
        private URI baseAddress; private Duration timeout = Duration.ofSeconds(10); private int maxRetries = 3;
        public Builder baseAddress(URI v) { baseAddress = v; return this; }
        public Builder timeout(Duration v) { timeout = v; return this; }
        public Builder maxRetries(int v) { maxRetries = v; return this; }
        public HttpOptions build() { return new HttpOptions(this); }   // validate here
    }
}
var opts = HttpOptions.builder().baseAddress(URI.create("https://api.example.com")).maxRetries(5).build();

// Functional options: Go's idiomatic builder.
type HTTPOptions struct {
    baseAddress string
    timeout     time.Duration
    maxRetries  int
}

type Option func(*HTTPOptions)

func WithTimeout(d time.Duration) Option { return func(o *HTTPOptions) { o.timeout = d } }
func WithMaxRetries(n int) Option        { return func(o *HTTPOptions) { o.maxRetries = n } }

func NewHTTPOptions(base string, opts ...Option) HTTPOptions {
    o := HTTPOptions{baseAddress: base, timeout: 10 * time.Second, maxRetries: 3}
    for _, apply := range opts {
        apply(&o) // mutation, but only on a local value before it escapes
    }
    return o // returned by value: the caller gets its own copy
}

var opts = NewHTTPOptions("https://api.example.com", WithMaxRetries(5))

const defaults = { timeoutMs: 10_000, maxRetries: 3 } as const;

function httpOptions(o: Pick<HttpOptions, "baseAddress"> & Partial<HttpOptions>): HttpOptions {
  return Object.freeze({ ...defaults, ...o });
}

Measure before you trade safety for speed An immutable update allocates. In request-handling code that's noise next to I/O; in a loop over a million elements it can dominate. Profile first (Performance Patterns), then use a builder, a pooled buffer or local mutation in the measured hot spot, and keep the public surface immutable.

Choosing: when to, and when not to

Technique Use it when Don't use it when
Union / sealed hierarchy a value is exactly one of a known, closed set of shapes (states, results, commands) third parties need to add cases: use an interface
Value object a concept has rules (format, range, unit) or can be confused with a same-typed sibling it's a local, short-lived value with no rules
Strongly-typed ID IDs of different entities share a representation (Guid, long, string) a single-entity service where only one kind of ID exists, and the cost of mapping outweighs the risk
Record / value equality the object is defined by its data: DTOs, messages, money, coordinates it has identity that persists through change (entities)
Immutable collection it's stored in a field, shared, cached, used as a key or crosses threads it's a local accumulator inside one function
Defensive copy you must keep a mutable type (legacy API, ORM) at a trust boundary the type is already immutable: copying is wasted work
Persistent collection many versions are kept (undo, snapshots, MVCC) or small updates to big data are frequent read-mostly data built once: a frozen/array-backed collection is faster
Parse at the boundary input arrives from outside (HTTP, queue, file, env vars, database) data was produced by your own typed code
Variance annotations you design a generic interface that only produces or only consumes T the type both reads and writes T: keep it invariant
1 · NAME ITIs it a concept?

If it has rules or a confusable sibling, give it a type.

2 · SHAPE ITOne of N, or all of N?

"One of" is a union; "all of" is a record.

3 · FREEZE ITWho else can change it?

Make fields and collections immutable by default.

4 · PARSE ITWhere does it come from?

Untrusted input is parsed once, at the edge.

5 · CHECK ITWill the compiler notice?

No catch-alls; checkers and linters in CI.

Pitfalls and war stories

The HashSet that lost an order A C# HashSet<OrderKey> used a mutable class with Equals/GetHashCode over Region and Number. A background job normalized Region from "eu" to "EU" on objects already in the set. Contains looked in the bucket for the new hash, found nothing, and the dedupe logic sent the order twice. Fix: keys are readonly record structs; normalization happens in the constructor, before the value is ever hashed.

The "immutable" config that changed at runtime A TypeScript service exported export const config: Readonly<Config> = loadConfig(). A test helper did (config as any).retries = 0 to speed up tests, and because modules are singletons, the next test file ran with zero retries and flaked for weeks. Fix: Object.freeze (deeply) at load time, and inject config instead of importing a mutable singleton (see DI Fundamentals).

The Go enum that grew a value type Status int with iota constants was stored in the database as an integer. A new StatusOnHold was inserted in the middle of the const block, shifting every later value by one. Old rows now decoded as the wrong status. Fix: assign explicit values (StatusShipped Status = 3), never reorder, persist names rather than ordinals where possible, and run the exhaustive linter. Java's enum.ordinal() and C# enums without explicit values have the same trap.

The Python dataclass default that every instance shared @dataclass class Cart: items: list = None with if self.items is None: self.items = [] worked, until someone "simplified" it to a module-level EMPTY = [] default passed explicitly. Every cart shared EMPTY, and items appeared in strangers' carts. Fix: field(default_factory=list), or better, tuple fields on a frozen dataclass.

The validated string that wasn't An API validated email in the controller with a regex and passed a string on. A later batch-import path called the same service method directly, skipping the controller, and wrote 40,000 unvalidated rows. Fix: the service method takes Email, so the import path had to parse: the compiler found the second entry point.

Checklist

  • [ ] Every "one of several" concept (status, kind, result) is a closed union, not a set of booleans or a free string.
  • [ ] Switches over closed unions have no catch-all arm (or one that throws), and exhaustiveness warnings are errors in CI.
  • [ ] IDs of different entities have different types; money carries its currency; units are in the type or the name.
  • [ ] Value objects are immutable, equal by value, and validated in exactly one place (constructor or factory).
  • [ ] Records don't hold mutable collections: fields use ImmutableArray/List.copyOf/tuple/readonly T[] or copies.
  • [ ] Getters never return a mutable internal collection.
  • [ ] Untrusted input (HTTP, queue, file, env) is parsed once into typed values at the boundary, collecting all errors.
  • [ ] Dictionary keys and set members are immutable.
  • [ ] Shared, cached and static data is frozen at startup.
  • [ ] Mutation is local or single-owner; anything published (returned, stored, sent) is immutable.
  • [ ] Python and TypeScript type checkers run in CI with strict settings (mypy --strict / pyright strict, tsc --strict).
  • [ ] Generic interfaces that only produce or only consume T declare it (out/in, ? extends/? super, readonly).

Self-check

An order has optional paidAt, shippedAt and trackingNo. How many combinations can the type represent, and how would you shrink it?

2 × 2 × 2 = 8 combinations, but only Draft (none), Paid (paidAt) and Shipped (all three) are legal: 3 of 8. Replace the optional fields with a union Draft | Paid(paidAt) | Shipped(paidAt, shippedAt, trackingNo), so the 5 illegal combinations can't be constructed.

A C# record Order(int Id, List<string> Lines) is copied with var b = a with { Id = 2 };, then b.Lines.Add("x"). What does a.Lines contain, and is a with { } == a still true?

a.Lines contains "x" too: with is a shallow copy, so both records hold the same list. a with { } == a is true because both records hold the same list reference. But two records with different lists of equal contents compare unequal, because List<T> uses reference equality. Use ImmutableArray<string> with a custom equality, or ImmutableList plus SequenceEqual in an overridden Equals.

Why is Collections.unmodifiableList(items) not enough to make a Java record immutable?

It's a view, not a copy. Writes through the view throw, but whoever still holds items can change it, and the change shows through. Use List.copyOf(items) in the compact constructor: it copies (unless already immutable) and the result can't be changed by anyone.

In Go, type CustomerID int64 protects Charge(c CustomerID, a AccountID) from swapped variables. What still slips through, and what about type CustomerID = int64?

Untyped constants convert implicitly, so Charge(42, 7) compiles. type CustomerID = int64 is an alias: it is int64, so it offers no protection at all, not even against swapped variables.

Why does Java reject List<Animal> a = new ArrayList<Cat>() but accept Animal[] a = new Cat[1]?

Generics are invariant because a List<Animal> reference could add(new Dog()) into a list of Cats, and erased generics have no run-time element type to check. Arrays are covariant for historical reasons and are reified, so the JVM checks every store and throws ArrayStoreException. The compile-time error is the better deal.

What's the difference between validating an email and parsing one?

Validation answers yes/no and leaves you with the same string, so the knowledge is lost and must be re-checked or trusted. Parsing returns a new Email type (or all the errors), normalized to a canonical form. Every function that takes Email is guaranteed a valid, canonical value without checking.
