REQUEST PIPELINES & MIDDLEWARE

Middleware Patterns & Ordering

Exception handling, logging and correlation, auth, CORS, rate limiting and compression: what goes where in the order and why getting it wrong breaks things.

Intermediate → Advanced~55 min studyBuilds on: The Request Delegate PipelineUpdated 2026-11-03

The problem: the same eleven lines, in the wrong order

The Request Pipeline showed that a pipeline is a list of layers folded into one delegate, so registration order decides who wraps whom. This page is about the consequence. Every line below is correct. The program compiles, starts and passes a smoke test that calls GET /api/orders with a token. In production it fails in four separate ways.

var app = builder.Build();

app.UseStaticFiles();            // ❶ before HTTPS redirection
app.UseRouting();
app.UseAuthentication();
app.UseAuthorization();
app.UseCors("spa");              // ❷ after authorization
app.UseExceptionHandler();       // ❸ not first
app.UseRateLimiter();
app.UseHsts();
app.UseHttpsRedirection();
app.MapControllers();
app.Run();

// ❶ http://shop.example/css/site.css is served over plain HTTP, no redirect.
// ❷ The SPA's preflight OPTIONS has no Authorization header (browsers never
//    send credentials on a preflight), so it gets 401 and the browser reports
//    a "CORS error" for every API call.
// ❸ An exception in auth, CORS or routing escapes to Kestrel: a bare 500,
//    no ProblemDetails, no correlation id in the logs.
// ❹ HSTS is added after the static-file and redirect responses are decided,
//    so the very responses that should pin HTTPS don't carry the header.

var app = builder.Build();

app.UseExceptionHandler();       // 1. outermost: catches everything inside
app.UseHsts();                   // 2. every HTTPS response gets the header
app.UseHttpsRedirection();       // 3. nothing is served over plain HTTP
app.UseStaticFiles();            // 4. cheap public files exit early
app.UseRouting();                // 5. the endpoint (and its metadata) is chosen
app.UseCors("spa");              // 6. answers preflights before auth sees them
app.UseAuthentication();         // 7. credentials → ctx.User
app.UseAuthorization();          // 8. needs User (7) and [Authorize] (5)
app.UseRateLimiter();            // 9. needs the endpoint policy and the user
app.UseMiddleware<AuditMiddleware>(); // 10. custom, endpoint-aware
app.MapControllers();            // 11. the endpoint runs at the end
app.Run();

None of these bugs is visible to the compiler, and most are invisible to a test that only sends a happy-path request. They show up as a browser console full of CORS errors, a pen-test finding, or an incident where the logs have no trace of a 500. The cure is to understand why each middleware sits where it does. Once the reasons are clear, the order stops being something you memorise and becomes something you can derive.

The ordering rule. A middleware can only catch, time or decorate what runs inside it, and can only use what was decided before it. So put the layers that must cover everything (errors, transport security) outermost, put cheap exits (static files) before expensive work, put Routing before anything that reads endpoint metadata, put CORS before anything that might reject a preflight, and put AuthN → AuthZ → policies in the order in which each needs the previous one's result.

The canonical order, and why each layer is where it is

Every position in the canonical order follows from one of three kinds of dependency:

  1. Wrap: "I must see everything that happens inside me". The exception handler must catch errors from every other layer, so it goes first.
  2. Needs: "I need a value someone else computes". Authorization needs ctx.User (from authentication) and the endpoint's [Authorize] metadata (from routing), so it comes after both.
  3. Exit early: "I can answer without the rest". Static files and CORS preflights are answered without touching routing, auth or your endpoint. Putting them early saves work, and for preflights it is the only way to avoid a 401.

The same information as a table, with the failure you get when each rule is broken. The visualizer below simulates every row.

Position Must come… Because… If you get it wrong
UseExceptionHandler first A layer only catches exceptions thrown inside it. Errors from earlier layers escape: a bare 500 with an empty body and no ProblemDetails.
UseHsts early, before anything that can answer It sets the header on the way in, so only responses produced inside it get it. Static files and redirects lack Strict-Transport-Security.
UseHttpsRedirection before static files and endpoints Nothing should be served over plain HTTP. http://…/css/site.css is served in clear text instead of a 307.
UseStaticFiles before routing and auth Public assets are the most frequent requests and need no endpoint or user. With a fallback authorization policy, CSS and JS need a login; otherwise routing and auth run for nothing.
UseRouting before CORS, auth, rate limiting, custom It chooses the endpoint; GetEndpoint() is null before it. Everything that reads metadata sees nothing: policies are not applied, or the endpoint middleware throws.
UseCors after routing, before authentication/authorization Preflights carry no credentials; CORS must answer them before anyone demands a token. Every cross-origin call fails with a "CORS error" because the preflight got 401.
UseAuthentication before authorization It sets ctx.User. Authorization always sees an anonymous user: every protected call is 401.
UseAuthorization after routing and authentication It needs both the user and the endpoint's requirements. Before routing: the endpoint middleware throws "contains authorization metadata, but a middleware was not found".
UseRateLimiter after routing (and after auth for per-user limits) Endpoint policies are metadata; per-user partitions need ctx.User. Before routing: nothing is limited. Before auth: all users share the anonymous bucket.
custom after the layers whose results it needs Audit, tenant resolution, feature flags usually need the endpoint and the user. It reads nulls, or runs work for requests that will be rejected anyway.
endpoints last It is the terminal handler. Anything after it never runs for a matched request.

How to use the visualizer:

  • Pick a preset to load a known misordering, or edit the order text directly (names such as Exception, Hsts, Https, Static, Routing, Cors, AuthN, AuthZ, RateLimit, Correlation, Endpoints). The code panel rewrites itself to match.
  • Pick a request. Each preset breaks some requests and not others, which is exactly why these bugs survive testing. "CORS after auth" only breaks the SPA preflight. "Exception handler not first" only shows when the limiter store is down (an exception thrown by a layer outside the handler). "Limiter before routing" only shows on the 101st request.
  • The lint panel lists every rule the order breaks, even rules the current request doesn't trigger.

Insight Misordered middleware rarely breaks the happy path. It breaks the request you didn't test: the preflight, the plain-HTTP asset, the 101st call, the error thrown by infrastructure rather than by your code. A good integration test suite sends one of each (see Testing middleware).

What the framework does for you (and when it doesn't)

Minimal hosting (WebApplication, .NET 6+) adds some layers implicitly, which hides the order until you need to change it:

  • If you don't call UseRouting, WebApplication adds it at the start of your pipeline, and adds the endpoint middleware at the end. So app.MapGet(...) works without either call. As soon as you need something before routing (static files, HTTPS redirection) and something after it (CORS, auth), call UseRouting() explicitly so the boundary is where you want it.
  • When authentication or authorization services are registered, WebApplication also adds UseAuthentication/UseAuthorization automatically if you didn't. Calling them explicitly makes the order visible and lets you put CORS before them.
  • The developer exception page is added automatically in the Development environment. That is why "errors look fine locally" while production returns bare 500s if UseExceptionHandler is missing or late.

Endpoint-agnostic (before UseRouting)

Exception handler, HSTS, HTTPS redirection, static files, response compression, forwarded headers, request logging, correlation id. They treat every request the same, so they don't need to know the endpoint. They are cheap and must cover 404s and static files too.

Endpoint-aware (between UseRouting and endpoints)

CORS, authentication, authorization, rate limiting, output caching, request timeouts, antiforgery, your audit or tenant middleware. They read metadata the endpoint declared ([Authorize], RequireCors, RequireRateLimiting, CacheOutput) and so must run after routing has chosen the endpoint.

Special cases

UseForwardedHeaders goes before HSTS, HTTPS redirection and auth, because they read Request.Scheme and the client IP that it rewrites. UseResponseCompression goes before anything that writes a body it should compress. UseCors must come before UseResponseCaching/UseOutputCache, so cached responses don't skip CORS headers.

Writing good middleware

The built-in layers are well behaved. Your own middleware is where most production bugs hide. The sections below cover the patterns you will write most often: turning exceptions into ProblemDetails, adding correlation ids and request logs, timing, reading the request body, and short-circuiting. Each comes with the specific trap that catches people.

Exceptions to ProblemDetails

Clients should never get a stack trace, and they should never get an empty 500 either. RFC 9457 Problem Details gives errors a standard JSON shape (type, title, status, detail, instance, plus extensions such as traceId) with the media type application/problem+json. ASP.NET Core has three pieces that work together:

  • AddProblemDetails() registers IProblemDetailsService, which writes that JSON (and adds traceId). It also makes empty error responses from the framework, such as a bare 404 or 405, get a ProblemDetails body when you add UseStatusCodePages().
  • UseExceptionHandler() is the outermost try/catch. On an exception it logs it, clears the response, sets 500, asks each IExceptionHandler in turn, and if none handles it, writes a default ProblemDetails.
  • IExceptionHandler (.NET 8+) is where you map your exception types to status codes. Return true if you handled it, false to let the next handler try.
app.MapGet("/orders/{id:int}", async (int id, OrderService svc) =>
{
    try { return Results.Ok(await svc.GetAsync(id)); }
    catch (OrderNotFoundException) { return Results.NotFound(); }      // no body
    catch (Exception ex) { return Results.Problem(ex.ToString()); }  // leaks the stack trace
});
// Exceptions thrown by model binding, auth, CORS or the JSON serializer
// never reach this catch: they happen outside the lambda.

builder.Services.AddProblemDetails(o => o.CustomizeProblemDetails = c =>
    c.ProblemDetails.Extensions["instance"] = $"{c.HttpContext.Request.Method} {c.HttpContext.Request.Path}");
builder.Services.AddExceptionHandler<DomainExceptionHandler>();   // tried in registration order

app.UseExceptionHandler();          // first: wraps everything, including routing and auth
app.UseStatusCodePages();           // empty 404/405 bodies become ProblemDetails too

sealed class DomainExceptionHandler(IProblemDetailsService problems) : IExceptionHandler
{
    public async ValueTask<bool> TryHandleAsync(HttpContext ctx, Exception ex, CancellationToken ct)
    {
        var status = ex switch
        {
            OrderNotFoundException => StatusCodes.Status404NotFound,
            ValidationException    => StatusCodes.Status400BadRequest,
            ConcurrencyException   => StatusCodes.Status409Conflict,
            _ => 0,
        };
        if (status == 0) return false;               // not ours: the default 500 ProblemDetails
        ctx.Response.StatusCode = status;
        return await problems.TryWriteAsync(new() { HttpContext = ctx, Exception = ex });
    }
}

The visualizer follows one exception from the endpoint outwards. It shows what the client receives, what gets logged, and the two cases no handler can fix.

Three things the visualizer makes visible:

  1. Mapping is a lookup, not a catch-all. DomainErrors returns false for the NullReferenceException, so the exception handler writes its default 500 ProblemDetails, without the exception message. That is correct: a bug is a 500, and its details belong in your logs, not in the response.
  2. Inner layers see the exception first. RequestLogging sits inside the handler. Its finally block runs while the exception unwinds, before the handler has set the status code, so it logs 200: the default value, not the status the client will get. Log the final status from a layer that wraps the exception handler, or let the hosting layer's request log do it.
  3. After the response has started, nothing can be fixed. Switch when to "after streaming started". The endpoint has already sent 200 OK and part of the body, so the handler can only log "The response has already started, the error handler will not be executed" and rethrow. The server aborts the connection, and the client sees a truncated body. A cancelled request (the client went away) is not an error at all: it is logged at Debug level and no handler runs.

The response has started: the one-way door

HTTP sends the status line and headers before the body. ASP.NET Core buffers headers until the first byte of the body is written (or flushed). From then on Response.HasStarted is true, and any attempt to change the status code or headers throws "StatusCode cannot be set because the response has already started" or "Headers are read-only, response has already started".

The rules that follow:

  • Before changing the response, check HasStarted. Exception and status-code middleware must handle the "too late" case by logging and rethrowing, never by writing a second response.
  • To add a header "on the way out", use OnStarting. Code after await next(ctx) usually runs after the body was written. ctx.Response.OnStarting(() => { … }) runs just before the headers are sent, whoever triggers the send.
  • Stream only when you have to. A streaming endpoint (IAsyncEnumerable, server-sent events, large file exports) commits to 200 with the first chunk. Do the validation and the risky work before the first write. If a failure later is likely, produce the result first and then stream it, or put the error in the stream format itself (an error event in SSE, a trailer in gRPC).

Correlation ids and request logging with scopes

When a request fans out across services, a correlation id lets you find every log line that belongs to it. The middleware has three jobs: accept an id from the caller (or create one), attach it to every log line written while the request runs, and send it back in a response header.

The tempting implementation stores the id in a static field or a singleton property. That is a race condition: requests overlap, so the field holds whichever request wrote it last. The visualizer runs three overlapping requests through both implementations.

ILogger.BeginScope stores the scope in an AsyncLocal<T>. An AsyncLocal value is part of the execution context, which is captured at every await and restored when the continuation runs. So each request's continuations see that request's scope, no matter how the awaits interleave or which thread-pool thread runs them. A static field has one value for the whole process.

// ASP.NET Core: scope flows through AsyncLocal; validate what you accept.
public sealed class CorrelationIdMiddleware(RequestDelegate next, ILogger<CorrelationIdMiddleware> log)
{
    private const string Header = "X-Correlation-ID";

    public async Task InvokeAsync(HttpContext ctx)
    {
        string incoming = ctx.Request.Headers[Header].ToString();
        string id = IsSafe(incoming) ? incoming
                  : Activity.Current?.TraceId.ToString() ?? ctx.TraceIdentifier;

        ctx.Response.OnStarting(() => { ctx.Response.Headers[Header] = id; return Task.CompletedTask; });

        using (log.BeginScope(new Dictionary<string, object> { ["CorrelationId"] = id }))
        {
            await next(ctx);          // every log line inside carries CorrelationId
        }
    }

    // Untrusted input goes into your logs: bound the length and the alphabet (log injection).
    private static bool IsSafe(string s) =>
        s.Length is > 0 and <= 64 && s.All(c => char.IsAsciiLetterOrDigit(c) || c is '-' or '_');
}

// Spring MVC: a servlet Filter + SLF4J MDC (a ThreadLocal). Fine for thread-per-request;
// for WebFlux or virtual-thread handoffs, use Micrometer context propagation instead.
@Component
@Order(Ordered.HIGHEST_PRECEDENCE)
public class CorrelationIdFilter extends OncePerRequestFilter {
    private static final String HEADER = "X-Correlation-ID";
    private static final Pattern SAFE = Pattern.compile("[A-Za-z0-9_-]{1,64}");

    @Override
    protected void doFilterInternal(HttpServletRequest req, HttpServletResponse res, FilterChain chain)
            throws ServletException, IOException {
        String in = req.getHeader(HEADER);
        String id = in != null && SAFE.matcher(in).matches() ? in : UUID.randomUUID().toString();
        res.setHeader(HEADER, id);            // before the chain: headers can't change after commit
        MDC.put("correlationId", id);
        try {
            chain.doFilter(req, res);
        } finally {
            MDC.remove("correlationId");      // the thread goes back to the pool
        }
    }
}

# Starlette / FastAPI: a contextvar is the Python AsyncLocal. Pure ASGI middleware.
import contextvars, logging, re, uuid

correlation_id = contextvars.ContextVar("correlation_id", default="-")
SAFE = re.compile(r"^[A-Za-z0-9_-]{1,64}$")

class CorrelationFilter(logging.Filter):
    def filter(self, record):
        record.correlation_id = correlation_id.get()   # use %(correlation_id)s in the format
        return True

class CorrelationIdMiddleware:
    def __init__(self, app):
        self.app = app

    async def __call__(self, scope, receive, send):
        if scope["type"] != "http":
            return await self.app(scope, receive, send)
        incoming = dict(scope["headers"]).get(b"x-correlation-id", b"").decode("latin-1")
        cid = incoming if SAFE.match(incoming) else uuid.uuid4().hex
        token = correlation_id.set(cid)

        async def send_with_header(message):
            if message["type"] == "http.response.start":
                message.setdefault("headers", []).append((b"x-correlation-id", cid.encode()))
            await send(message)

        try:
            await self.app(scope, receive, send_with_header)
        finally:
            correlation_id.reset(token)

// net/http + slog: put a request-scoped logger in the context and pass ctx everywhere.
type ctxKey struct{}

var safe = regexp.MustCompile(`^[A-Za-z0-9_-]{1,64}$`)

func CorrelationID(base *slog.Logger) func(http.Handler) http.Handler {
    return func(next http.Handler) http.Handler {
        return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
            id := r.Header.Get("X-Correlation-ID")
            if !safe.MatchString(id) {
                id = rand.Text() // Go 1.24+; or a UUID library
            }
            w.Header().Set("X-Correlation-ID", id) // before next writes anything
            logger := base.With("correlation_id", id)
            next.ServeHTTP(w, r.WithContext(context.WithValue(r.Context(), ctxKey{}, logger)))
        })
    }
}

func Logger(ctx context.Context) *slog.Logger {
    if l, ok := ctx.Value(ctxKey{}).(*slog.Logger); ok {
        return l
    }
    return slog.Default()
}

// Express: AsyncLocalStorage is Node's AsyncLocal; it follows promises and callbacks.
import { AsyncLocalStorage } from "node:async_hooks";
import { randomUUID } from "node:crypto";
import type { Request, Response, NextFunction } from "express";

export const requestContext = new AsyncLocalStorage<{ correlationId: string }>();
const SAFE = /^[A-Za-z0-9_-]{1,64}$/;

export function correlationId(req: Request, res: Response, next: NextFunction) {
  const incoming = req.get("x-correlation-id") ?? "";
  const correlationId = SAFE.test(incoming) ? incoming : randomUUID();
  res.setHeader("x-correlation-id", correlationId);
  requestContext.run({ correlationId }, () => next());
}

// In the logger (pino, winston...): read requestContext.getStore()?.correlationId

How the ecosystems differ, and why:

  • C# and Python have language-level async context (AsyncLocal, contextvars) that flows across await automatically, so a scope set in middleware reaches every log call made by that request.
  • Java's MDC is a ThreadLocal. That matches the classic servlet model, where one thread handles one request. It breaks when work hops threads (CompletableFuture, reactive pipelines), which is why WebFlux uses the Reactor Context and Micrometer's context propagation.
  • Go has no hidden context at all, by design. The request's context.Context is passed explicitly, so the logger (or the id) travels inside it.
  • Node gets the same flow from AsyncLocalStorage. Express 4 and 5 both work with it as long as you call next() inside run().

Some practical notes:

  • Prefer the trace id you already have. ASP.NET Core starts an Activity for every request, honouring an incoming W3C traceparent header, and the default host includes TraceId and SpanId in log scopes. With OpenTelemetry, that id is your correlation id across services. A custom X-Correlation-ID is still useful for callers that don't speak traceparent.
  • Validate before you trust. The id goes into every log line. An unbounded or multi-line value is a log-injection and log-volume attack. Accept a bounded alphabet, or replace it.
  • Place it outside the exception handler if you want the handler's own error log to carry the id. It is one of the few layers that may go before UseExceptionHandler, because it is tiny and only wraps. Request logging (UseHttpLogging, Serilog's UseSerilogRequestLogging) goes early for the same reason: it should see 404s and static files too, and it should log the final status.

Timing

A timing middleware measures how long the inner layers take. Two details make it correct: put the measurement in finally, so failed requests are timed too, and add any timing header in OnStarting, because by the time await next returns the headers have usually been sent.

public sealed class ServerTimingMiddleware(RequestDelegate next, ILogger<ServerTimingMiddleware> log)
{
    public async Task InvokeAsync(HttpContext ctx)
    {
        long start = Stopwatch.GetTimestamp();          // no Stopwatch allocation per request
        ctx.Response.OnStarting(() =>
        {
            var ms = Stopwatch.GetElapsedTime(start).TotalMilliseconds;   // time to first byte
            ctx.Response.Headers["Server-Timing"] = $"app;dur={ms:0.0}";
            return Task.CompletedTask;
        });
        try
        {
            await next(ctx);
        }
        finally
        {
            log.LogInformation("{Method} {Path} {Status} in {Ms:0.0} ms",
                ctx.Request.Method, ctx.Request.Path, ctx.Response.StatusCode,
                Stopwatch.GetElapsedTime(start).TotalMilliseconds);       // full duration
        }
    }
}

The two numbers differ on purpose. Server-Timing is time to first byte: it has to be computed before the body is sent. The log line is the full duration, including writing the body. For dashboards, prefer the built-in http.server.request.duration metric (.NET 8+) over hand-written timers: it is a histogram, tagged by route template and status code.

Reading the request body without stealing it

Sooner or later someone wants middleware that reads the request body: to audit it, to verify a webhook signature (an HMAC over the raw bytes), or to log it. The trap is that Request.Body is a forward-only stream read straight off the connection. Read it in middleware and the endpoint gets nothing, so model binding fails with a 400 that has nothing to do with the client.

Try each mode. Only "EnableBuffering + rewind" works, and it has two costs that the visualizer shows:

  • EnableBuffering() wraps the body in a FileBufferingReadStream that keeps a copy of every byte read. Up to 30 KB stays in memory; beyond that it spills to a temp file. Buffering every request body doubles the I/O for uploads. Do it only on the routes that need it, behind a size limit.
  • Rewind with Body.Position = 0 before calling next. Without EnableBuffering, seeking throws NotSupportedException.
  • leaveOpen: true on the StreamReader, or disposing the reader disposes the body, and the endpoint gets ObjectDisposedException.
  • Size limits still apply. Kestrel rejects bodies above MaxRequestBodySize (about 28.6 MB by default) with 413, whether or not you buffer.

Often the better answer is not to read the body in middleware at all:

  • To log bodies, UseHttpLogging with HttpLoggingFields.RequestBody records the bytes as the endpoint reads them, up to RequestBodyLogLimit (32 KB by default), without buffering the whole body. Be careful: bodies contain personal data and secrets.
  • To validate or audit a typed payload, use an endpoint or action filter, which gets the already-bound Order object for free (see the next section).
  • To verify a signature, read the raw body in the endpoint (or a filter on webhook endpoints only), verify, then deserialize.
// Only for /webhooks, with a size limit, and rewound for the endpoint.
app.UseWhen(ctx => ctx.Request.Path.StartsWithSegments("/webhooks"), branch => branch.Use(async (ctx, next) =>
{
    if (ctx.Request.ContentLength > 64 * 1024) { ctx.Response.StatusCode = 413; return; }
    ctx.Request.EnableBuffering(bufferThreshold: 64 * 1024);      // stays in memory up to 64 KB
    using var ms = new MemoryStream();
    await ctx.Request.Body.CopyToAsync(ms, ctx.RequestAborted);
    ctx.Request.Body.Position = 0;                                // rewind for model binding

    if (!Signature.IsValid(ms.ToArray(), ctx.Request.Headers["X-Signature"]))
    {
        ctx.Response.StatusCode = StatusCodes.Status401Unauthorized;
        return;                                                   // short-circuit
    }
    await next(ctx);
}));

// Spring: ContentCachingRequestWrapper caches bytes AS THE CHAIN READS THEM.
// The content is only available after chain.doFilter returns, so it suits logging,
// not pre-checks. For a pre-check (signature), read the bytes yourself and wrap the
// request in an HttpServletRequestWrapper that replays them.
public class BodyAuditFilter extends OncePerRequestFilter {
    @Override
    protected void doFilterInternal(HttpServletRequest req, HttpServletResponse res, FilterChain chain)
            throws ServletException, IOException {
        var wrapped = new ContentCachingRequestWrapper(req, 64 * 1024);   // cache limit
        chain.doFilter(wrapped, res);
        byte[] body = wrapped.getContentAsByteArray();                   // what the controller read
        audit.record(req.getRequestURI(), body);
    }
}

# ASGI: the body arrives as http.request messages from receive(). Read them all,
# then hand the app a receive() that replays them.
class SignatureMiddleware:
    def __init__(self, app, max_bytes=64 * 1024):
        self.app, self.max_bytes = app, max_bytes

    async def __call__(self, scope, receive, send):
        if scope["type"] != "http" or not scope["path"].startswith("/webhooks"):
            return await self.app(scope, receive, send)
        chunks, size, more = [], 0, True
        while more:
            message = await receive()
            if message["type"] == "http.disconnect":
                return
            chunks.append(message.get("body", b""))
            size += len(chunks[-1])
            more = message.get("more_body", False)
            if size > self.max_bytes:
                return await send_status(send, 413)
        body = b"".join(chunks)
        if not signature_is_valid(body, dict(scope["headers"]).get(b"x-signature", b"")):
            return await send_status(send, 401)

        replayed = False
        async def replay():
            nonlocal replayed
            if not replayed:
                replayed = True
                return {"type": "http.request", "body": body, "more_body": False}
            return await receive()            # later calls: wait for disconnect

        await self.app(scope, replay, send)

async def send_status(send, status):
    await send({"type": "http.response.start", "status": status, "headers": []})
    await send({"type": "http.response.body", "body": b""})

// net/http: read (bounded), then put a fresh reader back on r.Body.
func VerifySignature(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        body, err := io.ReadAll(http.MaxBytesReader(w, r.Body, 64<<10))
        if err != nil {
            http.Error(w, "body too large", http.StatusRequestEntityTooLarge)
            return
        }
        if !signatureValid(body, r.Header.Get("X-Signature")) {
            http.Error(w, "bad signature", http.StatusUnauthorized)
            return
        }
        r.Body = io.NopCloser(bytes.NewReader(body)) // the handler reads it again
        next.ServeHTTP(w, r)
    })
}

// Express: the JSON parser consumes the stream. Its verify hook sees the raw bytes first.
import express from "express";

app.use(
  "/webhooks",
  express.json({
    limit: "64kb",
    verify: (req, _res, buf) => {
      if (!signatureValid(buf, req.headers["x-signature"])) {
        throw Object.assign(new Error("bad signature"), { status: 401 });
      }
    },
  }),
);

Short-circuit patterns

Short-circuiting means answering without calling next. It is the whole point of auth, CORS preflights, static files, rate limiting and health checks. Done well, a short-circuit is fast, explicit and visible in the logs.

Return without next

Set a status (ideally a ProblemDetails body) and return. Log why at Debug or Information level, or the 401 will look like a mystery. Outer layers still run their after-code, so logging, timing and CORS headers still apply.

Branch: Map / MapWhen

A sub-pipeline for a path or a predicate that never rejoins the main one. Use it for a separate app (an admin UI, a legacy handler) with its own middleware. Covered in The Request Pipeline.

.ShortCircuit() and MapShortCircuit (.NET 8+)

app.MapGet("/healthz", ...).ShortCircuit() makes routing run the endpoint immediately when it matches, skipping every middleware between UseRouting and the endpoints (CORS, auth, rate limiting, yours). app.MapShortCircuit(404, "robots.txt", "favicon.ico") answers those prefixes with a status straight from routing. Use it for cheap, public, high-volume probes. Never use it on an endpoint that needs auth or CORS, because those layers are skipped.

Pitfall: short-circuiting with an empty body and no log ctx.Response.StatusCode = 403; return; is correct but unhelpful. The client gets no reason and your logs show nothing. Write a ProblemDetails (await Results.Problem(statusCode: 403, title: "IP not allowed").ExecuteAsync(ctx)) and log the reason. And never short-circuit by throwing an exception: exceptions are slow, they go to the exception handler as a 500, and they pollute error dashboards.

Middleware, filters and interceptors

Middleware sees every request as HTTP: a path, headers and a body stream. It runs before routing has bound any arguments, and it can't see your action, its parameters or its result. Frameworks therefore add a second, inner pipeline that runs inside the endpoint, after the endpoint has been selected and its arguments bound. In ASP.NET Core MVC these are filters; in minimal APIs, endpoint filters; in Spring, HandlerInterceptors and @ControllerAdvice; in NestJS, guards, interceptors and pipes.

The visualizer runs the same five requests against an MVC controller and against a minimal API endpoint, and shows which stage handles each one.

What to take from it:

  • A request that never matches an endpoint never reaches a filter. A 404 for /api/nope and a 401 for an anonymous caller are decided by middleware. If your exception or logging logic lives only in filters, it misses all of these.
  • Validation happens inside the endpoint. With [ApiController], the ModelStateInvalidFilter turns an invalid body into a 400 ValidationProblem before your action runs. Minimal APIs have no ModelState, so an endpoint filter (ValidateOrder) does the same job.
  • Exception filters only see MVC's exceptions. An MVC exception filter catches what the action, action filters and binding throw, and can turn a domain exception into a 409 with controller-specific knowledge. Minimal APIs have no exception filters: the exception goes out to UseExceptionHandler. Exceptions from middleware are never seen by any filter.

{
    public async ValueTask<object?> InvokeAsync(EndpointFilterInvocationContext ctx, EndpointFilterDelegate next)
    {
        var result = await next(ctx);               // the handler's return value, before it is written

        if (req.getAttribute("auditStart") instanceof Long start) {

    }
}

Which one to use

You need to… Use Why
Handle every request, including 404s, static files and preflights Middleware Filters only run for matched endpoints.
Turn exceptions into ProblemDetails for the whole app Middleware (UseExceptionHandler + IExceptionHandler) Exceptions can come from middleware, routing and serialization, not just actions.
Decide based on the endpoint's attributes or metadata Middleware after UseRouting, reading GetEndpoint()?.Metadata Works for MVC and minimal APIs alike.
Validate or transform bound arguments Endpoint filter / action filter / FastAPI dependency / Nest pipe Only these see typed values, after binding.
Change or inspect the result object before it is serialized Result filter, endpoint filter, Nest interceptor Middleware sees only bytes, after the result was written.
Map domain exceptions differently per controller MVC exception filter or @ControllerAdvice Close to the code that knows the domain. Keep a global handler as the safety net.
Cache a response before binding happens Resource filter or output caching Runs before model binding, so a cache hit skips it.
Retry, log or authenticate outgoing calls DelegatingHandler / client interceptors Same pattern, client side. See Outbound Pipelines.

Insight Push each concern to the outermost layer that has the information it needs. Exception handling and logging need nothing but HTTP, so they go in middleware, which covers everything. Argument validation needs typed arguments, so it goes in a filter. A concern placed too far in misses requests; placed too far out, it lacks the data to decide.

Rate limiting

A rate limiter answers "too many" before the work happens, which protects your service from abusive clients and protects your quotas from runaway scripts. In ASP.NET Core (.NET 7+) it is middleware with endpoint-level policies. That is why it goes after UseRouting (so it sees the endpoint's policy) and after authentication (so it can give each user their own budget).

The algorithm decides how bursts are treated. The visualizer sends the same arrivals through all three built-in window algorithms. The default traffic is a burst that straddles the window boundary at 6 s.

Fixed window

A counter that resets at each boundary. It is the cheapest option and easy to explain, but a client can send limit requests at the end of one window and limit more at the start of the next: up to 2 × limit in a short span. Fine for coarse quotas ("1000 per hour").

Sliding window

The window is split into segments. Permits used in a segment come back only when that segment slides out of the window, so there is no fresh allowance at a boundary. More segments make it smoother, at the cost of a little more state per partition.

Token bucket

Allows a burst up to the bucket size, then a steady rate of TokensPerPeriod per ReplenishmentPeriod. It matches how clients really behave (bursty page loads, then idle). Its "per window" count can exceed the limit; what it bounds is the burst size and the long-run rate. The concurrency limiter (not shown) bounds requests in flight instead of per time.

A realistic setup partitions by user, falls back to the client IP for anonymous callers, and returns 429 with Retry-After:

builder.Services.AddRateLimiter(o =>
{
    o.RejectionStatusCode = StatusCodes.Status429TooManyRequests;     // the default is 503
    o.OnRejected = (ctx, _) =>
    {
        if (ctx.Lease.TryGetMetadata(MetadataName.RetryAfter, out var retry))
            ctx.HttpContext.Response.Headers.RetryAfter = ((int)retry.TotalSeconds).ToString();
        return ValueTask.CompletedTask;
    };
    o.AddPolicy("per-user", ctx => RateLimitPartition.GetTokenBucketLimiter(
        partitionKey: ctx.User.Identity?.Name                       // needs UseAuthentication first
                      ?? ctx.Connection.RemoteIpAddress?.ToString()  // needs UseForwardedHeaders behind a proxy
                      ?? "anonymous",
        factory: _ => new TokenBucketRateLimiterOptions
        {
            TokenLimit = 20,
            TokensPerPeriod = 10,
            ReplenishmentPeriod = TimeSpan.FromSeconds(1),
            QueueLimit = 0,                                          // reject, don't queue
        }));
});

// Spring: no built-in limiter. Bucket4j (token bucket) in a filter, keyed per user.
@Component
public class RateLimitFilter extends OncePerRequestFilter {
    private final Map<String, Bucket> buckets = new ConcurrentHashMap<>();   // bound it in production

    @Override
    protected void doFilterInternal(HttpServletRequest req, HttpServletResponse res, FilterChain chain)
            throws ServletException, IOException {
        String key = req.getUserPrincipal() != null ? req.getUserPrincipal().getName() : req.getRemoteAddr();
        Bucket bucket = buckets.computeIfAbsent(key, k -> Bucket.builder()
                .addLimit(limit -> limit.capacity(20).refillGreedy(10, Duration.ofSeconds(1)))
                .build());
        ConsumptionProbe probe = bucket.tryConsumeAndReturnRemaining(1);
        if (probe.isConsumed()) {
            chain.doFilter(req, res);
        } else {
            res.setStatus(429);
            res.setHeader("Retry-After", String.valueOf(
                    TimeUnit.NANOSECONDS.toSeconds(probe.getNanosToWaitForRefill()) + 1));
        }
    }
}

// golang.org/x/time/rate is a token bucket. One limiter per key.
type keyedLimiter struct {
    mu       sync.Mutex
    limiters map[string]*rate.Limiter // evict idle keys in production
}

func (k *keyedLimiter) get(key string) *rate.Limiter {
    k.mu.Lock()
    defer k.mu.Unlock()
    l, ok := k.limiters[key]
    if !ok {
        l = rate.NewLimiter(rate.Limit(10), 20) // 10 tokens/s, burst 20
        k.limiters[key] = l
    }
    return l
}

func RateLimit(k *keyedLimiter, keyOf func(*http.Request) string) func(http.Handler) http.Handler {
    return func(next http.Handler) http.Handler {
        return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
            if !k.get(keyOf(r)).Allow() {
                w.Header().Set("Retry-After", "1")
                http.Error(w, "too many requests", http.StatusTooManyRequests)
                return
            }
            next.ServeHTTP(w, r)
        })
    }
}

Production notes:

  • 429 vs 503. 429 Too Many Requests tells the client it should slow down, and Retry-After tells it when to try again. 503 Service Unavailable says the server is overloaded. ASP.NET Core rejects with 503 by default, so set RejectionStatusCode = 429 for per-client limits.
  • Behind a proxy, the client IP is the proxy's. Without UseForwardedHeaders (with KnownProxies or KnownNetworks configured), every anonymous user shares one partition. The same is true for Express's trust proxy and Go's RealIP.
  • The built-in limiters are in-memory, per instance. Ten instances with a limit of 100 allow 1000. For a global limit, use a distributed limiter (Redis) or limit at the gateway, and treat the in-process limiter as a per-instance safety valve.
  • The algorithms in depth, and API-key and per-tenant quotas, are in API Security.

The integration tests worth having for every service, because they catch every misordering in the visualizer above:

  • A preflight OPTIONS with Origin and Access-Control-Request-Method gets 204/200 with Access-Control-Allow-Origin, and no 401.
  • A request without credentials to a protected endpoint gets 401 with a ProblemDetails body, and a request with them gets 200.
  • An endpoint that throws returns application/problem+json with a traceId, and no stack trace.
  • A static file is served without credentials, and not over plain HTTP in environments with HTTPS.
  • The (limit + 1)th request in a window gets 429 with Retry-After.
  • A request with a correlation id gets it echoed, and an unsafe id is replaced.

The same ordering in other stacks

The rules come from HTTP and from the onion, not from ASP.NET Core, so every framework has the same order. What differs is how you express it, and two frameworks invert the direction of registration.

// Express: registration order = outermost first. The error handler is the exception:
// it has FOUR parameters and goes LAST, because Express forwards errors forward.
import express from "express";
import helmet from "helmet";
import cors from "cors";

const app = express();
app.set("trust proxy", 1);                         // like UseForwardedHeaders
app.use(correlationId);                            // covers everything, including errors
app.use(helmet());                                 // security headers incl. HSTS
app.use(httpsRedirect);                            // often done by the proxy instead
app.use(express.static("public"));                 // cheap exit
app.use(cors({ origin: "https://spa.example" }));  // answers preflights with 204
app.use(authenticate);                             // sets req.user, never rejects
app.use("/api", perUser);                          // rate limit after auth
app.use("/api", apiRouter);                        // routes (authorization per route)
app.use((req, res) => res.status(404).type("application/problem+json")
  .json({ title: "Not Found", status: 404 }));
app.use((err, req, res, next) => {                 // 4 args = error middleware, last
  if (res.headersSent) return next(err);           // too late: let Express abort
  res.status(err.status ?? 500).type("application/problem+json")
    .json({ title: err.status ? err.message : "Internal Server Error", status: err.status ?? 500 });
});

When to use middleware, and when not

Middleware is the right place for concerns that apply to HTTP traffic as a whole. The more a concern depends on a specific endpoint, its arguments or your domain, the further inwards it belongs.

1 · EVERY REQUEST?Middleware

Applies to almost every request, including 404s and static files: errors, logging, correlation, security headers, HTTPS, compression.

2 · ENDPOINT METADATA?Middleware after UseRouting

Depends on attributes or policies: read GetEndpoint(). Auth, CORS, rate limits, output caching.

3 · TYPED ARGUMENTS?Endpoint or action filter

Needs bound arguments or the result object (a Nest pipe or interceptor, a FastAPI dependency).

4 · BUSINESS RULE?Application code

Neither middleware nor filter: put it where it can be read and tested.

When not to write custom middleware:

  • A built-in one exists. Exception handling, HSTS, CORS, auth, rate limiting, output caching, request timeouts, HTTP logging, health checks and forwarded headers are all built in. They encode years of edge cases, such as the preflight rule.
  • It only applies to a few endpoints. A path check inside global middleware (if (path.StartsWith("/api/admin"))) is endpoint metadata in disguise. Use a route group with a filter, or an attribute that middleware reads.
  • It needs the body as an object. Model binding already did the work. Use a filter.
  • It is retry logic. Retrying the inbound pipeline re-runs the endpoint on a response that may have started. Retry outgoing calls instead.
  • The gateway does it. TLS, compression, global rate limits and CORS are often better handled once at the edge (API gateway, reverse proxy, CDN). Keep the in-process version as defence in depth, not as a second, conflicting policy.

The costs to remember: every middleware runs for every request, so a 1 ms layer adds 1 ms to your health checks; the order is an implicit contract that no compiler checks; and debugging "who answered 401?" means walking the onion. Middleware that logs when it short-circuits pays for itself.

Pitfalls

Pitfall: CORS after authentication Browsers never send credentials on a preflight OPTIONS. If authentication or authorization runs first, the preflight gets 401, and the browser reports a "CORS error" that hides the real cause. Fix: UseCors after UseRouting and before UseAuthentication. In Spring, enable http.cors() so the CorsFilter runs inside Spring Security before authentication.

Pitfall: the exception handler is not first, or not configured Anything registered before it can throw past it: a bare 500 with no body, no ProblemDetails and, often, no useful log. UseExceptionHandler() without arguments also needs AddProblemDetails() (or an ExceptionHandlingPath), or the app throws at startup. Fix: register it first, with AddProblemDetails() and your IExceptionHandlers.

Pitfall: request logging inside the exception handler logs the wrong status The logging layer's finally runs while the exception is still unwinding, before the handler sets 500, so it logs 200. Fix: put request logging outside the exception handler, or rely on the hosting layer's request log and metrics, which see the final status.

Pitfall: "StatusCode cannot be set because the response has already started" Some layer tries to change the status or headers after the body began. Common causes: an exception during streaming, a middleware that sets headers after await next, or calling next twice. Fix: check Response.HasStarted, use OnStarting for late headers, and validate before streaming.

Pitfall: correlation id in a static field or a middleware field Conventional middleware is a singleton, and static fields are shared by every request. Under concurrency, log lines carry another request's id, and nobody notices until an incident. Fix: ILogger.BeginScope (AsyncLocal), HttpContext.Items, or Activity.Current.

Pitfall: middleware eats the request body Reading Request.Body without EnableBuffering and a rewind leaves the endpoint an empty stream, which shows up as a 400 for a valid client request. Disposing a StreamReader without leaveOpen: true disposes the body. And buffering every request doubles upload I/O. Fix: buffer only the routes that need it, with a size limit, or use a filter.

Pitfall: .ShortCircuit() on an endpoint that needs auth or CORS ShortCircuit() runs the endpoint straight from routing, skipping everything registered between UseRouting and the endpoints. That includes authentication, authorization and CORS, so a short-circuited endpoint with RequireAuthorization() is public. Fix: use it only for anonymous, cheap endpoints such as health probes and robots.txt.

Pitfall: rate limiting by IP behind a proxy, or per instance Without forwarded-header handling, every client has the load balancer's IP and shares one bucket: one noisy client throttles everyone. And an in-memory limiter on N instances allows N times the limit. Fix: UseForwardedHeaders with known proxies, per-user partitions after authentication, and a distributed limiter or gateway for global limits.

Pitfall: registration direction in Starlette, and error-handler position in Express app.add_middleware in Starlette and FastAPI inserts at the front, so the last call is the outermost layer. Code copied from an Express or ASP.NET Core mental model ends up inverted. In Express, an error handler with three parameters is ordinary middleware and never receives errors, and one registered before the routes never sees their errors.

Pitfall: compressing HTTPS responses that mix secrets with user input Turning on EnableForHttps (or gzip for everything at the proxy) on pages that contain a CSRF token or a session secret next to reflected attacker input enables BREACH-style attacks, which recover the secret from response sizes. Fix: leave HTTPS compression off for such responses, or mask secrets per response.

Checklist

  • UseExceptionHandler (with AddProblemDetails and IExceptionHandlers) is the first layer; stack traces never reach clients.
  • UseForwardedHeaders runs before anything that reads the scheme or the client IP, and only trusts known proxies.
  • HSTS and HTTPS redirection come before anything that serves content; static files come before routing and auth.
  • UseRouting is called explicitly when you have endpoint-agnostic layers before it and endpoint-aware layers after it.
  • UseCors comes after routing and before authentication, authorization and any response or output cache.
  • UseAuthentication → UseAuthorization → UseRateLimiter → endpoint-aware custom middleware → endpoints.
  • Request logging and correlation ids cover everything, validate incoming ids, and use scopes rather than fields.
  • Middleware that adds headers late uses OnStarting; anything that changes the response checks HasStarted.
  • Body-reading middleware is limited to the routes that need it, bounded, buffered and rewound with leaveOpen: true.
  • Short-circuits return a ProblemDetails body and log why; .ShortCircuit() is only on anonymous endpoints.
  • Concerns that need typed arguments or results live in filters, not middleware.
  • Rate limits reject with 429 and Retry-After, partition per user, and account for multiple instances.
  • Integration tests cover a preflight, an anonymous call, a throwing endpoint, a static file and the (limit + 1)th request.

Self-check

Your SPA's API calls all fail with "CORS error" in the browser, but curl with a token works. What is the most likely cause?

The preflight. curl doesn't send one, but the browser sends OPTIONS with Origin and Access-Control-Request-Method and no credentials. If authentication or authorization runs before CORS, the preflight gets 401 with no Access-Control-Allow-Origin header, so the browser blocks the real request and reports it as a CORS error. Move UseCors before UseAuthentication.

A custom middleware registered before UseExceptionHandler throws. What does the client get?

A bare 500 with an empty body. The exception handler only catches exceptions thrown by layers inside it, so this one escapes to the server, which can only set 500 if the response hasn't started. No ProblemDetails, and none of your IExceptionHandler logic runs.

An endpoint streams a CSV export and throws halfway. Why does the client receive 200 OK and a truncated file instead of a ProblemDetails 500?

The status line and headers were sent with the first chunk, so Response.HasStarted is true. The exception handler logs "The response has already started, the error handler will not be executed" and rethrows, and the server aborts the connection. Validate and do the risky work before the first write, or signal the error inside the stream format.

Where should a per-user rate limiter go, and what happens if it is placed before UseAuthentication?

After UseRouting (to see the endpoint's RequireRateLimiting policy) and after UseAuthentication (to know the user). Before authentication, ctx.User is anonymous for everyone, so every caller falls into the same anonymous (or IP) partition, and one busy client exhausts the budget for all of them.

You need to reject orders with Qty <= 0. Middleware or endpoint filter? Why?

An endpoint filter (or an action filter, or validation attributes). Middleware runs before model binding and sees only a body stream: it would have to read, buffer, parse and rewind the body itself. A filter runs after binding and gets the typed Order from GetArgument<Order>(0), and it only runs for the endpoints it is attached to.

A fixed-window limiter allows 4 requests per 6 seconds. Can a client get 8 requests accepted within one second? How do the other algorithms prevent that?

Yes: 4 at t = 5.6 s (end of the first window) and 4 at t = 6.1 s (start of the next). A sliding window keeps counting the permits used in the last few segments, so the boundary gives no fresh allowance. A token bucket caps any burst at its bucket size and refills at a steady rate.

In FastAPI you call add_middleware(CorrelationId) and then add_middleware(Auth). Which runs first on a request, and does the auth middleware's 401 carry the correlation id?

Auth runs first, because add_middleware inserts at the front: the last one added is the outermost. Its 401 short-circuits before CorrelationId runs, so the 401 has no correlation id header and its log lines have no id. Add CorrelationId last, or pass middleware=[...] in outermost-first order.

Why does reading Request.Body in middleware make a valid POST fail with 400, and what three things fix it?

The body is a forward-only stream: once the middleware has read it, the endpoint's JSON binding reads zero bytes and reports that it failed to read the parameter. Fix: call EnableBuffering() before reading, read with leaveOpen: true so the reader doesn't dispose the body, and set Body.Position = 0 before calling next.
