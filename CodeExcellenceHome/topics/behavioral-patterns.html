The problem: one method that knows everything

Here is a checkout service that started small and grew for two years. Nothing in it is wrong line by line. The trouble is that every new requirement lands in the same place.

public sealed class CheckoutService
{
    public async Task<Receipt> Checkout(Order order, string user)
    {
        if (order.Status != "Draft" && order.Status != "Submitted")          // lifecycle rules, inline
            throw new InvalidOperationException($"Cannot check out a {order.Status} order");

        decimal shipping = order.Method switch                                // algorithm choice, inline
        {
            "standard" => 5m + 1.2m * order.Kg,
            "express"  => 12m + 2.5m * order.Kg,
            "drone"    => order.Kg <= 2 ? 15m : throw new InvalidOperationException("too heavy"),
            _          => throw new ArgumentException(order.Method),
        };

        var receipt = await _payments.Charge(order, order.Total + shipping);
        order.Status = "Paid";

        await _email.SendReceipt(user, receipt);                              // everyone who cares, hard-wired
        await _sms.Notify(user, "Paid!");
        _dashboard.Refresh(order.Id);
        _audit.Write($"{user} paid {order.Id}");

        if (order.Total > 1000 && user != "admin" && !order.Customer.Blocked) // business rule, copy #4
            await _loyalty.AddPoints(user, (int)order.Total / 10);

        return receipt;
    }
}

Count the reasons this method changes: a new shipping method, a new notification channel, a new order status, a new loyalty rule, a request to undo or queue a checkout. Each one edits Checkout, re-runs every test around it, and risks breaking the other four. The class also knows the concrete type of every collaborator, so you can't test pricing without email.

Behavioral patterns move a decision out of the code that runs it. Each pattern answers one question: who decides which algorithm, who gets told, who handles the request, what happens next. You pull that decision into its own object (or, very often, just a function) so the caller stops knowing the details.

The patterns differ only in what varies and who calls whom. Learn that map and you can pick the right one from the symptom instead of from a catalogue.

This page assumes Design Principles: most of these patterns are the Open/Closed and Dependency Inversion principles applied to one specific axis of change, and nearly all of them are composition over inheritance in practice. Object creation patterns (factory, builder, singleton) are in Creational Patterns; wrappers (decorator, adapter, proxy, facade, composite) are in Structural Patterns.

Most of these patterns shrink to a function in modern languages The Gang of Four book (1994) was written for C++ and Smalltalk, before lambdas were mainstream. A Strategy with one method is a function. An Observer is a callback list. A Command with no undo is a closure. An Iterator is a generator. Each section below shows the full object version first, because you will meet it in frameworks, and then where it collapses into a lambda, closure, channel or generator. Reach for the class only when the thing needs state, several methods, a name in your domain, or a DI registration.

Strategy: choose the algorithm at runtime

The pain. The switch (order.Method) above is fine with two stable cases. It hurts when the list grows, when the same switch is copied into Eta(), Label() and CanShipTo(), or when one case needs dependencies the others don't (the drone case needs an airspace API client). Then every new method edits a busy class in four places.

The idea. Put each algorithm behind one small interface (or function type). The context holds a reference to "some strategy" and calls it; it never names a concrete class. New algorithms are new types, registered once.

Where you already use it. IComparer<T> and LINQ's OrderBy(keySelector); ASP.NET Core authentication schemes and IPasswordHasher<T>; Java's Comparator, Spring's injected List<Strategy> / Map<String, Strategy>; Python's key= functions and Django's pluggable AUTHENTICATION_BACKENDS; Go's sort.Slice less function and http.Handler; Passport.js strategies in Node.

Use a strategy when

  • The same choice is made in several places, or the list of options keeps growing.
  • One option needs dependencies the others don't (a client, a config section).
  • You want to choose at runtime: per tenant, per feature flag, per request.
  • You want to unit-test each algorithm in isolation.

Skip it when

  • There are two or three cases that haven't changed in a year. A switch expression is shorter, and the compiler checks exhaustiveness over an enum.
  • The "strategies" share most of their code and differ by one number. That's a parameter, not a strategy.
  • Only one implementation exists and none is planned. That's speculative generality.

Misuses

  • A strategy per if. Five interfaces for a 40-line feature. Each indirection costs a jump in the reader's head; spend it only where change actually happens.
  • Stateful strategies registered as singletons. If DroneShipping caches "the current order" in a field, two concurrent requests corrupt each other. Strategies should be stateless, or scoped per request.
  • Choosing the strategy with the same switch you removed. if (method == "express") s = new ExpressShipping() just moves the switch. Let the registry (a dictionary or the DI container) do the lookup.
  • Silent fallback. _byKey.GetValueOrDefault(key, standard) turns a typo in config into wrong prices. Fail loudly on unknown keys, preferably at startup.

Observer: tell whoever cares, without knowing who they are

The pain. In the checkout method, the payment code calls email, SMS, dashboard and audit directly. Adding a Slack alert means editing checkout, and a slow SMS provider now slows down payment. The publisher knows too much about its audience.

The idea. The subject keeps a list of subscribers and notifies them all when something happens. It knows only "a callback that takes an OrderPlaced". Subscribers add and remove themselves.

The bug every observer ships once: forgetting to unsubscribe

A subscription is a reference from the subject to the subscriber. If the subject lives longer than the subscriber (an app-wide event bus, a singleton service, window), then a closed screen that never unsubscribed stays reachable. The garbage collector can't free it, and it keeps receiving events. You get a memory leak and ghost deliveries: handlers running on disposed views, duplicate log lines, ObjectDisposedException.

Run the default script, then switch the mode. Weak references fix the leak but not the ghosts: delivery then depends on when the GC happens to run.

type OrderPlaced struct{ ID string }

type Bus struct {
    mu   sync.Mutex
    next int
    subs map[int]func(OrderPlaced)
}

func NewBus() *Bus { return &Bus{subs: map[int]func(OrderPlaced){}} }

// Subscribe returns the unsubscribe func. Go has no destructors, so the caller
// must keep it and call it (typically with defer, or when ctx is cancelled).
func (b *Bus) Subscribe(f func(OrderPlaced)) (unsubscribe func()) {
    b.mu.Lock()
    defer b.mu.Unlock()
    id := b.next
    b.next++
    b.subs[id] = f
    return func() {
        b.mu.Lock()
        delete(b.subs, id)
        b.mu.Unlock()
    }
}

func (b *Bus) Publish(e OrderPlaced) {
    b.mu.Lock()
    fs := make([]func(OrderPlaced), 0, len(b.subs))
    for _, f := range b.subs { // map order is random: don't rely on handler order
        fs = append(fs, f)
    }
    b.mu.Unlock()
    for _, f := range fs { // call outside the lock: a handler may unsubscribe
        f(e)
    }
}

class Emitter<T> {

Use observers / events when

  • The publisher should not know its audience, and the audience will grow (plugins, UI panels, audit, metrics).
  • Reactions are side effects that may fail independently of the main action.
  • You need to fan out one fact to many places (OrderPlaced → email, search index, analytics).

Don't when

  • The caller needs the result or must know it succeeded. A method call is clearer than an event someone "should" handle.
  • There is exactly one listener and always will be. A direct call (or a strategy) is easier to read and debug.
  • Order matters between handlers. Events don't promise order; make it an explicit sequence.

Cross the process boundary carefully

In-process events vanish if the process crashes after the database commit. If the reaction must happen, use an outbox table and a broker, not an in-memory event. See Resilience.

Misuses

  • Event spaghetti. Handler A raises event B, whose handler raises C, which triggers A again. Nobody can answer "what happens when an order is placed?" without a debugger. Keep event chains shallow, and log the causation id.
  • Throwing from a handler. In C# event invocation, the first handler that throws stops the rest. Catch inside each handler, or iterate GetInvocationList() yourself.
  • Async void handlers. Placed += async (s, e) => await ... becomes async void: exceptions crash the process and nobody awaits completion. Use a real async notification mechanism (a channel, a mediator notification, a broker).
  • Subscribing in a constructor, never disposing. The leak in the visualizer. Tie the subscription to the subscriber's lifetime: IDisposable, AbortSignal, ctx.Done(), takeUntil.

Command: turn a request into a value

The pain. A button handler calls doc.Uppercase() directly. Now product wants undo, a macro recorder, a "retry failed jobs" screen and an audit log of who did what. A direct method call leaves nothing behind to undo, replay, queue or log.

The idea. Wrap the request in an object: the operation plus its parameters, with Execute() (and optionally Undo()). The invoker (button, queue worker, history) handles commands without knowing what they do. Because a command is a value, you can put it on a stack, in a queue, in a database row or on the wire.

Type some text, undo, redo, and then make a new edit after undoing: the redo history is discarded. Then switch to memento snapshots and compare the memory column.

Two ways to undo appear in the visualizer, and real editors mix them:

  • Inverse operations: the command stores just enough to reverse itself (the insert position, the deleted text). Cheap, but every command must be exactly reversible.
  • Snapshots (mementos): the command saves the state before it ran. Always correct, but memory grows with document size × history depth. Uppercase needs this even in inverse mode, because you can't recover "Hello" from "HELLO".
public interface IEditCommand
{

    void Undo(Document doc);

public sealed class Insert(string text) : IEditCommand

{

public sealed class History(Document doc)
{

    public void Execute(IEditCommand c) { c.Do(doc); _undo.Push(c); _redo.Clear(); }
    public void Undo() { if (_undo.TryPop(out var c)) { c.Undo(doc); _redo.Push(c); } }
    public void Redo() { if (_redo.TryPop(out var c)) { c.Do(doc); _undo.Push(c); } }

type Command interface {
    Do(d *Doc)
    Undo(d *Doc)
}

type Insert struct {
    Text string
    at   int
}

func (c *Insert) Do(d *Doc)   { c.at = len(d.Text); d.Text += c.Text }
func (c *Insert) Undo(d *Doc) { d.Text = d.Text[:c.at] }

type History struct {
    doc        *Doc
    undo, redo []Command
}

func (h *History) Execute(c Command) {
    c.Do(h.doc)
    h.undo = append(h.undo, c)
    h.redo = h.redo[:0]
}

func (h *History) Undo() {
    if n := len(h.undo); n > 0 {
        c := h.undo[n-1]
        h.undo = h.undo[:n-1]
        c.Undo(h.doc)
        h.redo = append(h.redo, c)
    }
}

Use commands when

  • You need undo/redo, macros, or replay.
  • Work must be queued, retried, scheduled or sent to another process (jobs, outbox, message bus).
  • You want one place for cross-cutting behaviour around every operation: logging, permissions, transactions (a pipeline over commands).

Don't when

  • You just need to call a method now. A command class per CRUD endpoint adds two files and zero benefit.
  • The "undo" is really a database transaction rollback. Use the transaction.

Misuses

  • Commands that capture live objects and go on a queue. A command holding a DbContext or an entity serialises badly and runs against stale state later. Queue ids and values, and load fresh state in the handler.
  • Non-idempotent queued commands. Queues redeliver. ChargeCard(orderId) must check whether it already ran, or carry an idempotency key.
  • Undo that isn't exact. Inverse operations drift when commands interact (delete after format). When in doubt, snapshot.

Template method vs strategy: inheritance or composition?

Both patterns fix the skeleton of an algorithm and let some steps vary. The difference is the mechanism:

  • Template method: a base class owns the non-virtual algorithm and calls protected abstract hooks; subclasses fill them in. The base calls down into the subclass ("don't call us, we'll call you").
  • Strategy: the algorithm's owner receives the varying steps as an object or functions, and calls across to them.

Pick a format and compare who calls whom. The calls are identical; what changes is whether the varying part is a subclass or a collaborator.

Chain of responsibility: pass it along until someone handles it

The pain. An expense approval method checks if (amount <= 1000) lead... else if (amount <= 10000) manager..., and every reorganisation edits it. The idea: each handler either handles the request or forwards it to its successor. The sender knows only the head of the chain, and the chain is assembled from configuration.

Change the amount, or put the handlers out of order to see a broad handler shadow a narrower one. Push an amount past the last limit to see the most common bug: a request that falls off the end silently.

public abstract class Approver(Approver? next)
{

        CanApprove(e) ? Approve(e)
      : next is not null ? next.Handle(e)
      : Decision.Unhandled(e);                        // make the end of the chain explicit
    protected abstract bool CanApprove(Expense e);
    protected abstract Decision Approve(Expense e);
}

public abstract class Approver {

    protected abstract Decision approve(Expense e);

Handler = Callable[[Expense], Decision | None]      # None means "not mine, pass it on"


def run_chain(handlers: list[Handler], e: Expense) -> Decision:
    for h in handlers:
        if (d := h(e)) is not None:
            return d
    return Decision.unhandled(e)

type Handler func(e Expense) (Decision, bool) // ok=false means "pass it on"

            return d
        }
    }
    return Unhandled(e)
}

The pattern has two variants. In the classic one, exactly one handler handles the request (approvals, event bubbling in the DOM, exception catch blocks walking up the stack). In the pipeline variant, every handler does some work and calls next(): that is HTTP middleware, DelegatingHandler, servlet filters and Express. The pipeline variant is covered in depth in the request pipeline, with ordering rules in middleware patterns and the outbound side in outbound pipelines.

Misuses

  • No terminal handler. Always decide what happens at the end: a default handler, an explicit "unhandled" result, or a thrown error. Never silent null.
  • Order that only lives in DI registration. If correctness depends on order, assert it in a test or build the chain in one visible place.
  • A chain of three fixed ifs. If the handlers never change and are never reused, a switch is clearer.

Mediator: components talk to a hub, not to each other

The pain. In a booking dialog, choosing a date refreshes the room list, which enables the guest count, which recomputes the price, which toggles the Book button. With direct references, each widget knows four others. With n components, that can be up to n(n−1)/2 links, and changing one widget means reading every widget that references it.

The idea. Components only notify a mediator ("date changed"), and the mediator owns the coordination rules. The links drop from O(n²) to n. The cost: the mediator now knows everyone, and it grows.

Increase the component count, then change one component in each wiring mode and compare the ripple. Watch for the final frame: the hub is where coupling went, not where it disappeared.

MediatR is not quite the GoF mediator

In .NET, "mediator" usually means MediatR: await mediator.Send(new PlaceOrder(...)) finds the single IRequestHandler<PlaceOrder> and runs it through pipeline behaviours. That is really a command dispatcher (with in-process pub/sub via Publish). It doesn't coordinate peers the way a dialog director does; it decouples a caller from a handler type.

What it buys you

  • Thin controllers: one request type, one handler.
  • Pipeline behaviours for validation, logging and transactions around every handler.
  • A vertical-slice folder structure falls out naturally.

The criticism

  • Hidden control flow: "Go to definition" on Send lands in the library, not your handler. The compiler can't tell you a handler is missing.
  • It's an extra layer for what is often one method call; an injected PlaceOrderHandler gives the same decoupling with plain DI.
  • Publish to many in-process handlers runs them sequentially in one transaction scope by default. It's not a message bus.
  • From v13 (July 2025), MediatR moved to a commercial licence for larger companies. Check before adopting; see outbound pipelines.

Iterator and generators: pull one value at a time

The pain. A method returns List<Order> of all 2 million rows so the caller can find the first three overdue ones. Every element is loaded, filtered and allocated before the caller sees anything, and the caller can't stop early.

The idea. An iterator exposes "give me the next element" and hides the source: an array, a tree, a file, a database cursor, an infinite sequence. Generators (yield) let you write an iterator as a normal-looking loop; the compiler turns it into a state machine that pauses at each yield. Chained iterators form a lazy pipeline: nothing runs until the consumer pulls, and only as much as it pulls.

Pick a language and take N. In lazy mode, each element travels the whole pipeline before the next one is read, and the source stops as soon as the consumer has enough. Switch to eager mode and count the work done for nothing.

Iterator traps that bite in production

  • Multiple enumeration. In C#, enumerating an IEnumerable from a LINQ-to-EF query twice runs the query twice (analyzer CA1851 warns). Java streams throw on reuse; Python and JS generators return nothing the second time. Materialise once with ToList() / list() when you need two passes.
  • Deferred validation. A C# iterator method with if (x is null) throw inside it doesn't throw until the first MoveNext(), far from the bug. Validate in a non-iterator wrapper, then call a private iterator.
  • Modifying while iterating. InvalidOperationException (C#), ConcurrentModificationException (Java), RuntimeError: dictionary changed size during iteration (Python). Iterate a copy or collect changes and apply them afterwards.
  • Disposal. An iterator over a file or DB cursor holds the resource until it's disposed. foreach, for…of, with and Go's range clean up on break, but a hand-rolled MoveNext() loop must dispose explicitly.
  • Lazy + side effects. A lazy query that logs or writes runs when (and as often as) it is enumerated, possibly after the DbContext is gone.

Visitor: add operations without touching the classes

The pain. An expression tree has Num, Add, Mul and Div nodes. You need evaluation, pretty-printing, RPN output, and a node counter. Putting each as a virtual method on every node class means every new operation edits every class, and the node classes fill up with unrelated concerns.

The idea: double dispatch. node.Accept(visitor) dispatches on the node's runtime type, which calls visitor.Visit(this), which dispatches on the visitor's type with the node type now known statically. Two virtual calls select a method by two runtime types. Operations become classes; adding one touches no node.

Modern languages: pattern matching over a closed hierarchy

When the set of node types is closed (sealed), pattern matching gives the same "operations outside the classes" benefit with far less ceremony, and the compiler checks exhaustiveness.

public abstract record Expr;
public sealed record Num(double V) : Expr;
public sealed record Add(Expr L, Expr R) : Expr;
public sealed record Mul(Expr L, Expr R) : Expr;

// Classic visitor: double dispatch.
public interface IVisitor<T> { T Visit(Num n); T Visit(Add a); T Visit(Mul m); }
// each node: public override T Accept<T>(IVisitor<T> v) => v.Visit(this);

// Pattern matching: one function per operation, no Accept methods.
static double Eval(Expr e) => e switch
{
    Num n => n.V,
    Add(var l, var r) => Eval(l) + Eval(r),
    Mul(var l, var r) => Eval(l) * Eval(r),
    _ => throw new UnreachableException(),   // C# can't prove exhaustiveness over records yet
};
// Roslyn's CSharpSyntaxVisitor and EF Core's ExpressionVisitor are classic visitors.

}

This is the expression problem: which kind of change should be cheap?

You will mostly add… Prefer Why
New types (another payment provider, another shape) Virtual methods / strategy A new class is one file; operations stay inside each type.
New operations over a fixed set of types (compilers, ASTs, document models) Visitor or pattern matching A new operation is one function; the types never change.
Both, often Neither is free Accept one cost, or use a plugin/registry design.

Misuses

  • Visitor over an open hierarchy. Every new node type breaks every visitor interface. If plugins add node types, visitor is the wrong shape.
  • Visitors that mutate the tree while walking it. Return a new tree (a rewriting visitor) instead.
  • Visitor in a language with exhaustive matching. In Java 21+, Kotlin, Rust, F#, Scala or TypeScript, a switch over a sealed type is usually clearer than Accept boilerplate.

Specification: business rules as composable, named objects

The pain. "VIP customer" is c.Active && (c.Premium || c.Spent > 1000) && !c.Blocked. It appears in the checkout service, in a repository query, in a report and in a nightly job, each with a small difference. When marketing changes the threshold, three of the four get updated.

The idea. Wrap each rule in an object with IsSatisfiedBy(candidate) and combinators And, Or and Not. Name the composites (Vip), test them once, and reuse them in memory and, in good implementations, translated into the database query.

        return true
    }

Misuses

  • Specs that can't translate. A Func<T,bool> (not an Expression) passed to EF Core forces client-side evaluation: the whole table is loaded and filtered in memory. Keep query specs as expressions.
  • A specification framework for one Where. One rule used once is a lambda. Reach for specs when the same rule appears in several places or when users compose filters.
  • Specs with side effects or I/O. A predicate must be pure; otherwise short-circuiting changes behaviour.

Which pattern? A decision guide

An algorithm varies by input or configStrategy

A dictionary of functions or implementations, chosen at runtime.

Others react to something happeningObserver

Events, callbacks, Rx. Own the unsubscribe.

An action must be undone, queued or replayedCommand

The request becomes a value.

Legal operations depend on a lifecycleState

Transition table first; state objects for rich behaviour.

Several handlers might deal with a requestChain

Or a pipeline, when every one does a bit.

New operations over fixed node typesVisitor / match

Prefer exhaustive pattern matching.

Pitfalls

Across all behavioral patterns

  • Pattern names in class names as decoration. OrderStrategyFactoryVisitor signals pattern-driven design. Name things by the domain: ShippingRates, OrderLifecycle.
  • Indirection without variation. A strategy with one implementation, a chain with one handler, a mediator with one handler: all pay the cost and earn nothing. See speculative generality.
  • Lost control flow. Observers, mediators and chains all make "what happens next?" harder to answer. Compensate with good names, logging at dispatch points, and tests of the wiring.

Checklist

  • The varying part is real: at least two implementations exist or are scheduled.
  • I tried the function form (lambda, delegate, closure) before introducing an interface.
  • Every subscription has an owner who disposes it.
  • Queued commands carry ids and values, and their handlers are idempotent.
  • State transitions live in one place, and Status has no public setter.
  • Chains have an explicit terminal behaviour, and order is tested.
  • Lazy sequences are enumerated once, or materialised deliberately.
  • Query specifications stay as expressions so they translate to SQL.

Self-check

A strategy interface has exactly one implementation and no plans for a second. Keep it?

Usually no. Call the class directly; extract the interface when the second implementation (or a real test need) arrives. The interface is cheap to add later with refactoring tools.

A page component subscribes to a singleton event bus in its constructor. Memory grows on every navigation. Why?

The singleton's handler list holds a strong reference to each component instance, so none can be collected, and each still runs its handler. Unsubscribe in Dispose / ngOnDestroy / useEffect cleanup, or use a subscription object owned by the component's lifetime.

Why does a new edit clear the redo stack?

The redo commands were recorded against a document state that no longer exists. Replaying them after a different edit would apply operations to the wrong positions or content. Editors that keep alternative histories use an undo tree instead.

Template method or strategy for a report exporter in application code?

Strategy. It can be chosen at runtime, tested in isolation, and combined with other axes (format × destination) without a subclass per combination. Template method fits framework base classes that must guarantee step order.

An iterator method validates its argument with a throw, but the exception appears much later. Why?

The body of an iterator method (generator) runs only when enumeration starts, so the check is deferred to the first MoveNext() / next(). Validate in a wrapper method that then returns the iterator.

When is the visitor pattern better than a switch over a sealed hierarchy?

When the language can't check exhaustiveness and you want the compiler to force every operation to handle every node type (each Visit overload is a required interface method), or when the framework you extend already exposes a visitor (Roslyn, ast.NodeVisitor, go/ast).
