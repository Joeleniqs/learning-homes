Performance Patterns & Anti-Patterns

Batching, pooling, streaming, lazy loading, precomputation, back-pressure, plus the sync-over-async and chatty-I/O traps.

Advanced~55 min studyBuilds on: The Performance Cadence, Concurrency & AsyncUpdated 2026-11-03

The problem: the endpoint that was fast on Tuesday

The reporting service had a /orders/export endpoint. It was fine in testing with 2,000 orders. In production a large customer had 1.8 million, and every Monday morning their finance team clicked Export. The endpoint loaded all the rows into a list, mapped each one to a DTO, looked up each customer's name with its own query, built a CSV by appending to a string, and finally sent the result. The pod's memory climbed past 3 GB, the GC spent more time collecting than the app spent working, other requests on the same pod timed out, and Kubernetes killed it for exceeding its memory limit. Then the client retried.

Nothing in that endpoint was exotic. Every line was a pattern you have written: load everything, one query per item, string concatenation in a loop, no limit on concurrency. Each one is harmless at small sizes and catastrophic at large ones. The fix was not a faster CPU. It was five well-known patterns: stream the rows, batch the customer lookups, write to a buffered stream, bound the concurrency, and compress the response. The same endpoint then ran in 40 MB of memory, and the first byte arrived after 30 ms instead of 90 seconds.

Performance Cadence taught you how to find the problem: measure, profile, fix, verify. This page is the catalogue of what to do once you've found it: the recurring shapes of slow code and the pattern that fixes each one, across C#, Java, Python, Go and TypeScript, with the cost of each fix and when not to apply it.

The rule. Optimise only what a measurement points at, and fix it with the biggest lever first: a better algorithm, then fewer round trips (batching), then less data held at once (streaming, laziness, back-pressure), then less work repeated (precomputation, caching, connection reuse), and only then fewer allocations and better memory layout. Every pattern on this page has a cost in complexity; pay it on the hot path, not everywhere.

Recognize that you need these patterns when

  • Latency or memory grows faster than linearly with input size: twice the rows takes four times as long.
  • A trace shows dozens or hundreds of identical short spans (one per item) under one request: chatty I/O.
  • Memory rises with request size and falls back after the request: you are loading everything before processing it.
  • The GC is busy (high allocation rate, frequent gen-0/young collections, long pauses) and a profile shows the allocations come from a few lines.
  • CPU is high but the flame graph has no single hot function; the time is smeared across allocation, copying and serialization.
  • Thread-pool threads are all blocked while CPU is idle: sync-over-async or missing async I/O.
  • Cold starts are slow enough that autoscaling, serverless functions or rolling deploys hurt users.
  • A queue between two stages keeps growing until the process runs out of memory: no back-pressure.

Measure first, then choose a pattern

You already know the cadence: set a target, measure, profile, change one thing, verify. If not, read Performance Cadence first; it covers the tools (BenchmarkDotNet, JMH, pyperf, go test -bench, tinybench), flame graphs, Amdahl's law and latency numbers. The point to carry over is that a profile tells you which pattern you need. The table below maps what you see to where to look on this page.

Premature optimisation versus a known hot path

"Premature optimisation is the root of all evil" is half a sentence. Knuth went on: "yet we should not pass up our opportunities in that critical 3%." The skill is telling the two apart. Two measurements decide it: how much of the total time this code accounts for, and how often it runs. Then weigh the gain against what the change costs to read and maintain.

The visualizer asks the same five questions you should ask before every optimisation. Try a 35% share with a 3× speedup, then 2% with a 10× speedup: Amdahl's law makes the second one nearly worthless however clever it is. Then try a fix with no readability cost at all. That one is never premature.

"Free" improvements are not premature. If the faster version is just as clear (a HashSet instead of a List for lookups, presizing a collection whose size you know, hoisting an invariant out of a loop, reusing an HttpClient), write it that way the first time. Premature optimisation means paying clarity for speed you haven't shown you need. When the price is zero, there is nothing to weigh.

Algorithmic wins first

No amount of pooling, SIMD or clever memory layout rescues a quadratic algorithm at scale. A 10× micro-optimisation on an O(n²) loop is overtaken by the next doubling of the data. So before reaching for anything else on this page, check the complexity of what the hot code does. You don't need contest-level algorithms; most production wins come from a handful of substitutions:

Smell in the code Complexity Replacement Becomes
list.Contains(x) / x in list inside a loop O(n·m) Build a hash set once O(n + m)
Find the matching item with a nested loop (join in memory) O(n·m) Dictionary keyed by the join key O(n + m)
Sort the whole collection to take the top 10 O(n log n) Heap / priority queue of size k O(n log k)
Re-sort after every insert O(n² log n) Sorted structure (SortedSet, TreeMap, bisect.insort, heap) O(n log n)
list.Remove(x) / list.pop(0) in a loop O(n²) Mark and compact once, or use a deque O(n)
String += in a loop O(n²) bytes copied Builder or join O(n)
Recomputing an aggregate on every request O(n) per request Maintain it incrementally, or precompute O(1) per request
Recursive function with overlapping calls Exponential Memoize Polynomial

Look for hidden loops. The quadratic code is rarely two visible for statements. It hides in Contains, IndexOf, Remove, includes, in on a list, Array.find inside map, an ORM lazy-loading a navigation property inside a loop, or a regular expression compiled inside a function that is called per item. When you read a hot loop, ask of every call in its body: what does this cost, and does it depend on n?

Allocation reduction

In managed runtimes, allocating is cheap (a pointer bump) but not free: every allocated byte must be zeroed, it pushes the next GC closer, and objects that live a little too long get promoted and cost much more to collect. Memory & Garbage Collection explains the generational GC, the large object heap, escape analysis, pooling and spans in depth. This section is the practical checklist for a hot path: find the allocations the profiler shows, then remove them with one of five moves.

1 · MeasureAllocated bytes per operation

BenchmarkDotNet [MemoryDiagnoser], JMH -prof gc, tracemalloc, go test -benchmem, --inspect heap sampling.

2 · AvoidDon't create it

Hoist out of the loop, presize, use a value type, use a view instead of a copy.

3 · ReusePool it

ArrayPool, ObjectPool, sync.Pool, a reused buffer per worker.

4 · ShrinkMake it smaller

Primitive arrays instead of boxed collections, structs instead of classes, fewer fields.

5 · VerifyRe-measure

Bytes/op down, GC count down, and the latency or CPU win actually shows up end to end.

Building strings

Strings are immutable in C#, Java, Python, Go and JavaScript. So s += piece cannot change s; it allocates a new string and copies both parts into it. Do that in a loop and every iteration copies everything built so far: n appends copy about n²/2 characters. A builder keeps one growable buffer instead; when it fills up, it doubles, so the total copying stays linear.

Step through s += piece with 5,000 pieces, then switch to the presized builder. The quadratic curve is not a constant factor worse; it is a different shape. Note what the last frame says about single expressions: a + b + c is compiled into one concat call in C# and Java, and that is fine. The problem is only the loop.

// Bad in a loop: O(n²) copying, n intermediate strings.
string csv = "";
foreach (var o in orders) csv += $"{o.Id},{o.Total}\n";

// Good: one growable buffer. Presize when you can estimate the length.
var sb = new StringBuilder(capacity: orders.Count * 24);
foreach (var o in orders) sb.Append(o.Id).Append(',').Append(o.Total).Append('\n');
string csv2 = sb.ToString();

// Better for output: don't build the string at all; write to the stream.
await using var writer = new StreamWriter(response.Body, bufferSize: 64 * 1024);
foreach (var o in orders) { await writer.WriteAsync(o.Id.ToString()); /* ... */ }

// Joining existing strings: string.Join measures first, then allocates once.

// Bad in a loop: each += creates a new String (javac's StringConcatFactory
// makes a single a + b + c fast, but cannot fix the loop).

// Good: StringBuilder, presized when you can estimate.

// Joining: String.join or Collectors.joining.

    csv += f"{o.id},{o.total}\n"

# Good: collect the pieces, join once (measures the total, allocates once).

// Clear and predictable: collect, then join once.

// For responses, write to the stream instead of building the whole string.

Pooling buffers and objects

A pool keeps objects that would otherwise become garbage and hands them out again. It pays off for large or expensive objects that are needed briefly and often: I/O buffers, StringBuilders, serializer state, compression contexts. It does not pay off for small, cheap objects: young-generation allocation of a 40-byte object is faster than any pool's bookkeeping. The memory-and-gc page has a visualizer of a pool's rent and return cycle; here is how each language spells it.

using System.Buffers;
using Microsoft.Extensions.ObjectPool;

// ArrayPool: rent at least n bytes; the array may be LARGER than requested.
byte[] buffer = ArrayPool<byte>.Shared.Rent(64 * 1024);
try
{
    int read = await stream.ReadAsync(buffer.AsMemory(0, 64 * 1024));
    Process(buffer.AsSpan(0, read));            // use only what you filled
}
finally
{
    ArrayPool<byte>.Shared.Return(buffer, clearArray: containsSecrets);
}

// ObjectPool for reusable objects (Microsoft.Extensions.ObjectPool package).
ObjectPool<StringBuilder> sbPool = new DefaultObjectPoolProvider().CreateStringBuilderPool();
var sb = sbPool.Get();
try { sb.Append("..."); return sb.ToString(); }
finally { sbPool.Return(sb); }                  // the policy clears it on return

// Java's GC handles short-lived objects very well; pool only expensive things.
// Netty's PooledByteBufAllocator is the standard for network buffers:
ByteBuf buf = PooledByteBufAllocator.DEFAULT.buffer(64 * 1024);
try {
    buf.writeBytes(in, 64 * 1024);              // fill from an InputStream
    process(buf);
} finally {
    buf.release();                              // reference-counted: release exactly once
}

// A per-thread reusable buffer for a CPU-bound hot loop (platform threads only:
// with virtual threads, ThreadLocal caches multiply per virtual thread).
private static final ThreadLocal<byte[]> SCRATCH = ThreadLocal.withInitial(() -> new byte[64 * 1024]);
byte[] scratch = SCRATCH.get();

# Python objects are reference counted and freed immediately; pooling small
# objects rarely helps. Reusing a large buffer for I/O does:
buf = bytearray(64 * 1024)
view = memoryview(buf)
with open(path, "rb") as f:
    while (n := f.readinto(buf)) > 0:          # fills the existing buffer, no new bytes object
        process(view[:n])                      # zero-copy slice

# Connection and session objects are the pools that matter most in Python:
# reuse one requests.Session / httpx.Client / DB engine (see "Reuse connections").

// sync.Pool: a per-P cache of reusable objects. It is emptied over GC cycles,
// so it never leaks, but never assume an item survives.
var bufPool = sync.Pool{
    New: func() any { return new(bytes.Buffer) },
}

func render(w io.Writer, v any) error {
    buf := bufPool.Get().(*bytes.Buffer)
    buf.Reset()                        // always reset: it holds the previous user's data
    defer bufPool.Put(buf)
    if err := json.NewEncoder(buf).Encode(v); err != nil {
        return err
    }
    _, err := w.Write(buf.Bytes())
    return err
}
// Don't Put very large buffers back: one huge request would pin that memory.

// Node keeps an internal pool for small Buffers: Buffer.allocUnsafe(n) for
// n < 4 KB slices from it (contents are NOT zeroed: overwrite before reading).
const header = Buffer.allocUnsafe(16);
header.writeUInt32BE(length, 0);

// For your own hot paths, reuse one buffer per worker instead of allocating per message.
const scratch = Buffer.alloc(64 * 1024);
function encode(msg: Message): Buffer {
  const n = writeMessage(scratch, msg);        // fills scratch, returns bytes written
  return scratch.subarray(0, n);               // a view; copy it if it must outlive the next call
}

Pools trade GC work for correctness risk. A returned object can still be referenced by the code that returned it (use-after-return), a rented array can contain the previous user's data (information leak), and an object returned twice is handed to two users at once. Pool only what a profile shows, keep the rent/return in one try/finally or defer, and clear buffers that held secrets.

Views instead of copies: Span, Memory, slices

Parsing, splitting and trimming usually produce copies: Substring, Split, bytes[a:b], Arrays.copyOfRange. A view describes a window into existing memory instead: no allocation, no copying. The memory-and-gc page shows how spans and slices share their backing memory. The rules of thumb:

Language View type Notes
C# Span<T>, ReadOnlySpan<T>, Memory<T> Span is stack-only (no fields, no await across it); use Memory<T> across awaits. stackalloc gives a span on the stack for small temporary buffers.
Java ByteBuffer.slice(), CharBuffer.wrap, CharSequence String.substring copies (since Java 7u6). The FFM API's MemorySegment.asSlice (Java 22+) is the modern off-heap view.
Python memoryview Slicing bytes copies; slicing a memoryview doesn't. Works with bytes, bytearray, array, NumPy.
Go slices (b[i:j]) Slicing never copies. Gotcha: a small slice keeps the whole backing array alive; bytes.Clone or slices.Clone when keeping a small piece of a big buffer.
TypeScript Buffer.subarray, TypedArray.subarray Zero-copy views. Buffer.slice is deprecated because it looked like Array.slice (a copy) but wasn't. 
// Parse "key=value;key=value" without allocating substrings.
static int SumValues(ReadOnlySpan<char> input)
{
    int sum = 0;
    foreach (Range part in input.Split(';'))            // .NET 9: MemoryExtensions.Split(span, char)
    {
        ReadOnlySpan<char> pair = input[part];
        int eq = pair.IndexOf('=');
        if (eq >= 0 && int.TryParse(pair[(eq + 1)..], out int v)) sum += v;   // parses a span: no string
    }
    return sum;
}

// stackalloc: a small temporary buffer on the stack, no GC involvement.
Span<byte> hash = stackalloc byte[32];
SHA256.HashData(payload, hash);
string hex = Convert.ToHexString(hash);

// Work on a window of a buffer without copying it.
ByteBuffer packet = ByteBuffer.wrap(data);

ByteBuffer body = packet.slice(16, data.length - 16);

// Parse a number from part of a CharSequence without substring (Java 9+).
int v = Integer.parseInt(line, start, end, 10);

data = sock.recv(65536)                 # bytes

Boxing, value types and struct versus class

Boxing wraps a value (an int, a double, a struct) in a heap object so it can be treated as a reference. It happens silently when a value type meets object, an interface or a generic collection of references. Each box is an allocation, and a collection of boxes is a collection of pointers to scattered objects, which is slow to scan (see data-oriented design).

Language Where boxing hides Fix
C# Passing a struct as object or an interface; ArrayList, non-generic APIs; string.Format("{0}", 42) (a params object[] argument); LINQ over structs through IEnumerable<T> Generics (List<int> stores ints inline), generic constraints (where T : IComparable<T>), interpolated string handlers (.NET 6+)
Java List<Integer>, Map<Long, Double>, Stream<Integer>; every autoboxed value above the small-integer cache (-128..127) Primitive arrays, IntStream/LongStream, primitive collections (fastutil, Eclipse Collections); value classes are coming with Project Valhalla
Python Everything is an object: a list of a million floats is a million float objects array.array('d'), NumPy arrays, struct; vectorise the loop
Go Converting a value to any / an interface (fmt.Println(x), []any) may allocate if the value escapes Concrete types and generics; check with go build -gcflags=-m
TypeScript Numbers outside the small-integer range are heap numbers; arrays of mixed types Typed arrays (Float64Array, Int32Array) for numeric data; keep arrays monomorphic

Struct or class? In C# (and Go, where every type can be a value), a small value type avoids an allocation and is stored inline in arrays and other objects. Make it a struct when it is small (up to about 16–24 bytes), immutable and has value semantics (a point, a money amount, an ID). Keep it a class when it is large (structs are copied on every assignment and pass-by-value), mutable, shared, or used polymorphically. Pass large structs with in / ref readonly to avoid copies.

// Boxing: every int becomes an object.
ArrayList legacy = new();               // non-generic: stores object
for (int i = 0; i < n; i++) legacy.Add(i);          // n boxes

List<int> ints = new(n);                // generic: ints stored inline, no boxes
for (int i = 0; i < n; i++) ints.Add(i);

// A struct through an interface is boxed; through a generic constraint it is not.
static int CompareBoxed(IComparable a, object b) => a.CompareTo(b);           // boxes both
static int Compare<T>(T a, T b) where T : IComparable<T> => a.CompareTo(b);   // no boxing

readonly record struct Money(decimal Amount, string Currency);  // small, immutable: a good struct

// Autoboxing: each Long above 127 is a separate heap object.
Map<Long, Long> counts = new HashMap<>();
for (long id : ids) counts.merge(id, 1L, Long::sum);  // boxes the key and the value every time

// Primitive alternatives.

Data-oriented design: cache lines and branches

The CPU does not read memory one value at a time. It reads 64-byte cache lines, and a read from main memory costs about 100 ns, the time for a few hundred instructions (the latency table has the full ladder). Caches and the hardware prefetcher hide that cost when access is sequential and dense: the prefetcher sees you walking forward and fetches the next lines before you ask. They can't hide it when access jumps around (following pointers to objects scattered across the heap) or when most of each fetched line is data you don't need.

Data-oriented design means arranging data for the way the hot loop reads it. The classic example is array of structs (AoS) versus struct of arrays (SoA).

Try the three layouts with 8 fields, then with 2 fields. With 2 fields AoS is almost as good as SoA, because each line still holds 4 useful masses. With object references (what you get by default from a List<Particle> of classes in C# or Java, a Python list of objects, or a JavaScript array of objects), each element is a pointer read plus a jump to wherever the allocator put the object. Over millions of elements those cache misses dominate everything else.

Branch prediction

A modern CPU works on many instructions at once in a deep pipeline. When it reaches a conditional jump it can't wait to learn which way it goes, so it predicts and runs ahead speculatively. A correct guess is free. A wrong guess throws away the speculative work: about 15–20 cycles each time. The predictor learns from history, so branches that go the same way most of the time, or follow a simple pattern, are nearly free. Branches that depend on random data are expensive.

Run it with random bytes, then sorted bytes, then branchless code. Sorted data mispredicts only around the single point where values cross the threshold. Random data mispredicts about half the time. The branchless version computes both outcomes and selects one with arithmetic (often a cmov instruction), so it costs the same whatever the data looks like.

When branch behaviour matters

  • Tight loops over large arrays with a data-dependent if (filters, histograms, parsers, interpreters).
  • The profiler or perf stat shows a high branch-misses rate in the hot function.
  • You can sort or partition the data once and reuse it, or the compiler can turn the condition into a select.

When it doesn't

  • Anything dominated by I/O, allocation or cache misses: a mispredict costs about 5 ns, a cache miss 100 ns, a network call milliseconds.
  • Branches that almost always go one way (error checks, null checks): they predict well already.
  • Code where branchless tricks hurt readability without a measured gain. Compilers often emit cmov for simple conditionals on their own.

False sharing is the multi-core cousin. Two threads updating different variables that happen to share one 64-byte line make the cores fight over that line, and a "lock-free" counter per thread can run slower than one shared counter. Pad hot per-thread data to separate lines ([StructLayout] with explicit size in C#, @Contended in the JDK, padding fields in Go), or better, keep per-thread state local and combine at the end. See Concurrency & Async for the threading side.

Fewer round trips: batching and buffering

Every call to a database, a cache, another service, a message broker or the disk pays a fixed cost before doing any useful work: network latency, a syscall, parsing, authentication, a query plan lookup, a lock. When the useful work per call is small, the fixed cost dominates. Batching pays the fixed cost once for many items.

The defaults are a typical in-region call: 2 ms round trip, 0.5 ms of server overhead per call, 0.05 ms of real work per item. For 200 items, one call per item takes 510 ms, and 98% of that is per-call cost (the round trip plus server overhead), not work. Try a 40 ms round trip (cross-region) and the sequential version takes over eight seconds. Then compare batching with parallelism: both cut wall time, but only batching also cuts the load on the other side. Parallel single-item calls hit the server with the same 200 requests, just faster, and that is how one slow page turns into a self-inflicted denial of service.

Micro-batching: batch by size or by time

Batching inside one request is easy: you have all the items. Batching across requests (log shipping, metrics export, writes to Kafka, inserts from many concurrent users) needs a buffer that flushes on whichever comes first: enough items, or a maximum wait. The maximum wait bounds the added latency; the size bounds memory and payload size.

Batching shows up at every layer. The same trade-off (a little latency for much higher throughput) applies each time:

Where Unbatched Batched
Database writes One INSERT and commit per row Multi-row INSERT, SqlBulkCopy, JDBC addBatch, COPY, executemany, one transaction for the batch
Database reads Query per item (N+1) Join, IN (...), ANY($1), selectinload, DataLoader
Cache GET per key MGET, Redis pipelining
HTTP APIs Call per item Bulk endpoint (POST /prices:batchGet), GraphQL with DataLoader
Messaging Send and await each message Producer batching (Kafka linger.ms), SendMessageBatch (SQS), Service Bus batches
Files and sockets write() per small piece BufferedStream, BufferedOutputStream, bufio.Writer, Python's default buffered I/O
Telemetry Export per span Batch span processor (see Observability)

Batches have failure modes of their own. One bad item can fail a whole batch (decide: reject the batch, or return per-item results). Very large batches hit payload limits, lock many rows, and make a retry expensive. Pick a batch size by measuring: throughput usually flattens out between 100 and 1,000 items, long before the limits.

Back-pressure: bound every queue

Whenever one stage hands work to another (a request handler to a background worker, a reader to a parser, a consumer loop to a database writer), there is a queue between them, even if it's only implicit (a list, a channel, the thread pool's queue, unawaited tasks). If the producer is faster than the consumer, an unbounded queue grows until memory runs out, and every item in it waits longer and longer. Back-pressure means the queue has a limit, and something sensible happens when it is full. Concurrency & Async animates the producer/consumer mechanics; here are the policies and the code.

When the queue is full Effect Use it for
Block / await the producer Producer slows to the consumer's pace; latency moves upstream Pipelines inside one process, file and stream processing
Reject new work (429 / 503) Caller learns immediately, can retry later or elsewhere Request admission at the edge; see load shedding in Resilience
Drop oldest Freshest data wins Telemetry, live prices, sensor readings
Drop newest Existing work completes Best-effort side work (non-critical notifications)
Unbounded Nothing, until out-of-memory Almost never; only when the producer is provably bounded

Streaming instead of loading everything

"Read it all, then process it, then send it" is the simplest code, and its memory use grows with the data. A 2 GB export loaded into a list needs at least 2 GB of heap (often three times that once objects and the serialized response are counted), and the client waits for the very last row before seeing the first byte. Streaming handles one item or one chunk at a time: memory stays flat, and the first byte goes out almost immediately.

Stream when

  • The data is large or unbounded (exports, logs, file uploads and downloads, ETL).
  • Each item can be processed independently and in order.
  • Time to first byte matters, or the client can render progressively (NDJSON, server-sent events, gRPC server streaming).

  • The data is small and bounded (a page of 50 results): streaming adds complexity for nothing.
  • You need the whole set first: sorting in memory, totals in a header, or a transaction you might roll back.

Lazy vs eager

Eager means doing the work up front, whether or not anyone needs it. Lazy means doing it on first use. Lazy initialisation speeds up startup and skips work that's never needed. Eager loading makes the first request fast and fails at deploy time rather than at 3 a.m. Neither is "the fast one": it depends on how likely the value is to be used, and on who pays the delay.

The third mode is the trap: a lazy sequence enumerated several times re-runs the whole pipeline each time. IEnumerable in C#, a Java Supplier<Stream>, a Python generator function called again, or an Iterable in TypeScript recomputes everything on each pass. A Python generator or Java Stream used twice is worse: the second pass is silently empty, or throws IllegalStateException. Materialise once (ToList(), toList(), list()) when you will read the result more than once.

Async I/O and the sync-over-async trap

While a request waits on the network or the disk, the CPU has nothing to do. Blocking I/O parks an OS thread for the whole wait (about 1 MB of stack and a scheduler slot). Async I/O hands the wait to the operating system and frees the thread to serve other requests. On a service that spends 95% of each request waiting on downstream calls, that is the difference between needing 400 threads and needing 8.

The trap is mixing them. Calling .Result or .Wait() on a task (C#), .join() / .get() on a future from an event-loop thread (Java reactive stacks), a blocking requests.get() inside an async def (Python), or a synchronous fs.readFileSync in a Node request handler blocks the thread that async code was counting on. Under load that causes thread-pool starvation (watch it happen in the starvation visualizer) or a frozen event loop.

// BAD: sync-over-async. Blocks a pool thread; under load the pool starves and latency explodes.
public Order Get(int id) => _client.GetFromJsonAsync<Order>($"/orders/{id}").Result;

// GOOD: async all the way up to the framework.
public async Task<Order?> GetAsync(int id, CancellationToken ct) =>
    await _client.GetFromJsonAsync<Order>($"/orders/{id}", ct);

// Spring MVC on virtual threads (Java 21+, spring.threads.virtual.enabled=true):
// blocking calls become cheap, so plain blocking code is fine.
Order get(long id) { return restClient.get().uri("/orders/{id}", id).retrieve().body(Order.class); }

// BAD on WebFlux / Netty: block() on an event-loop thread stalls every request on that loop.
Order bad = webClient.get().uri("/orders/{id}", id).retrieve().bodyToMono(Order.class).block();
// GOOD on WebFlux: return the Mono and let the framework subscribe.
Mono<Order> good(long id) { return webClient.get().uri("/orders/{id}", id).retrieve().bodyToMono(Order.class); }

# BAD: a blocking call inside async def freezes the event loop for every request.
@app.get("/orders/{id}")
async def get_order(id: int):
    return requests.get(f"{BASE}/orders/{id}").json()

# GOOD: an async client...
@app.get("/orders/{id}")

# (FastAPI also runs plain "def" endpoints in a thread pool for you.)

// GOOD: async I/O; CPU-heavy work goes to a worker thread (node:worker_threads).
app.get("/report", async (req, res) => res.send(await fs.promises.readFile("report.html", "utf8")));

Reuse connections and clients

Opening a connection is expensive: DNS, the TCP handshake, the TLS handshake (one or two more round trips plus public-key cryptography), and for databases, authentication and session setup. On a 20 ms round trip that is 40–80 ms before your request is even sent. Connection pooling and HTTP keep-alive pay this once and reuse the connection for thousands of requests.

The rule is the same everywhere: create one long-lived client (or pool) and share it. Creating an HTTP client per request leaks sockets in TIME_WAIT and can exhaust ephemeral ports. Keeping one forever can pin stale DNS. Outbound pipelines covers that trade-off in detail, along with retries and timeouts.

Bigger pools aren't faster. A database with 8 cores can execute only about 8 queries at once. A pool of 200 connections per instance, times 20 instances, is 4,000 connections all contending for those cores and locks, and throughput drops. Start small (around 2 × cores of the database, divided across instances), watch pool wait time as a metric, and grow only if the database has idle capacity.

Serialization performance

On a typical JSON API, turning objects into bytes and back takes a surprising share of CPU: 20–40% of a request's processing is common once the database work is cached. There are three levers, in order of impact:

  1. Send less. Project to a DTO with only the fields the client needs, paginate, and skip nulls. No serializer is faster than not serializing.
  2. Use the fast path in your library. Avoid runtime reflection: reuse the configured serializer instance, and use code generated at build time where it exists.
  3. Change the format only when the profile says JSON is the bottleneck, or for internal service-to-service traffic. Binary formats (Protobuf, MessagePack, Avro) are smaller and faster but harder to debug and need a schema. API Protocols compares the formats.

Startup performance

Startup time used to matter only to developers. Now it decides how quickly autoscaling can add capacity, how long a rolling deploy takes, and whether serverless functions and CLI tools feel instant. A JIT runtime also starts slow on its first requests: it interprets or runs unoptimised code until the hot methods are compiled. Startup has two parts: time to ready (the process can serve) and time to peak (it serves at full speed).

Pick a scenario, then compare the runtime modes. Ahead-of-time compilation (Native AOT, GraalVM native image) wins time-to-ready by a wide margin, but its peak throughput can trail a warmed-up JIT, which optimises with profile data from the live workload. For a long-running service behind a load balancer, warm-up is a one-time cost. For a CLI or a function that scales from zero, it's paid on every cold start.

Response compression

Compression trades CPU on both ends for fewer bytes on the wire. Text formats (JSON, HTML, CSS, JavaScript) typically shrink 70–90%, so on a slow or metered link compression is a large win. On a fast data-centre link with small payloads, compressing can cost more time than the transfer it saves.

Try a 2 KB response on a 1 Gbps link (compression is pure overhead), then a 500 KB JSON response on a 10 Mbps mobile link (a big win). Already-compressed content (JPEG, PNG, MP4, ZIP, WOFF2) barely shrinks, so never compress it again. For static assets, precompress at build time at the highest level (Brotli 11) and serve the .br or .gz file directly: maximum ratio, zero request-time CPU.

BREACH: compression can leak secrets. If a response is compressed over HTTPS and contains both a secret (a CSRF token, a session value) and text an attacker can influence (a reflected query parameter), the attacker can guess the secret byte by byte by watching the compressed size change. That's why ASP.NET Core leaves EnableForHttps off by default. Mitigations: don't compress responses that mix secrets with reflected input, mask tokens per request, or add random padding. Security Fundamentals covers the wider picture.

Precompute and memoize

The cheapest work is work done once, before or instead of on every request. Precomputation moves work to build time or startup: compiled regular expressions, lookup tables, serializers, prepared statements, rendered templates. Memoization caches a pure function's result by its arguments. Both are caching in the small. The big-cache questions (eviction, invalidation, stampedes, distributed caches) are covered in Caching.

function memoize<A extends string | number, R>(fn: (a: A) => R): (a: A) => R {
  const cache = new Map<A, R>();
  return (a) => {
    if (!cache.has(a)) cache.set(a, fn(a));
    return cache.get(a)!;
  };

An unbounded memo is a memory leak with good intentions. Memoizing by user id, URL or free-text input grows forever. Bound it (lru_cache(maxsize=...), Caffeine, MemoryCache with a size limit, lru-cache), memoize only pure functions (same input, same output, no side effects), and remember that a memo on an instance lives as long as the instance. Python's lru_cache on a method keeps self alive. Memory & GC shows how these leaks look in a heap dump.

Pitfalls and war stories

The pooled buffer that leaked other customers' data. A service rented a buffer from ArrayPool, filled part of it and returned the whole array in a response instead of the slice it had written. The tail of the buffer still held the previous user's data. Fix: always track the length you wrote and send buffer.AsSpan(0, written); pass clearArray: true when returning buffers that held secrets; never return a rented array to a caller you don't control.

The parallel loop that took down the database. A nightly job "optimised" 50,000 sequential lookups by running them all with Task.WhenAll. The connection pool hit its limit within a second, every other service sharing the database timed out, and the job itself was slower than before. Fix: batch the lookups (WHERE id = ANY(...) in chunks of 1,000) and, if parallelism is still needed, bound it to a handful of concurrent calls.

The cache key that grew forever. A @cache-decorated function took a request object as its argument. Every request was a new key, the memo held every request and its body, and the pods were OOM-killed every few hours. Fix: memoize on small, bounded, hashable keys (an id, a currency pair), use a size-bounded cache, and alert on process memory growth.

The micro-benchmark that lied. A developer replaced a LINQ query with a hand-written loop after a benchmark showed it was 5× faster. In production nothing changed: the method ran 30 times a minute and the request spent 400 ms waiting on a downstream call. Fix: profile the real workload first (the cadence), and let Amdahl's law choose the target. Saving 2 µs from a 400 ms request is noise.

The streamed export that returned "200 OK" and half a file. A streaming CSV endpoint hit a database timeout after 2 million rows. The status code had already been sent, so the client saw a successful, truncated download. Fix: write a final marker (a trailer row, or a count to check), use cursor timeouts suited to long exports, or for very large exports switch to an async job that writes to storage and returns a link.

Checklist

  • [ ] There's a profile or metric showing this code is hot before any micro-optimisation (see Performance Cadence).
  • [ ] Algorithm and data structure checked first: no nested scans, lookups use hashes, sorting happens once.
  • [ ] No N+1 queries: related data is loaded with joins, IN (...) or a DataLoader; reads use projections.
  • [ ] Every queue and every fan-out is bounded, with a deliberate policy when full.
  • [ ] HTTP clients, serializers, regexes and database pools are created once and shared.
  • [ ] No sync-over-async: no .Result, .Wait(), block(), or blocking calls inside async def or Node handlers.
  • [ ] Large results are streamed end to end, or paginated.
  • [ ] Hot-path allocations are measured; pooling is used only where the profile shows GC pressure, and rented buffers are always returned.
  • [ ] Memos and caches are bounded and only wrap pure functions.
  • [ ] Compression is on for text responses above about 1 KB, off for already-compressed content, and BREACH has been considered.
  • [ ] Startup cost is known; the right mode (JIT, ReadyToRun, AOT, native image) was chosen for the deployment model.
  • [ ] Every optimisation has a benchmark or load test that guards it against regression.

Quiz

A profile shows 30% of CPU in a hot loop, and you make that loop 10× faster. Roughly how much faster is the request?

About 1.37× (not 10×). By Amdahl's law the new time is 0.70 + 0.30 / 10 = 0.73 of the old time. The unchanged 70% now dominates, which is why the next profile matters more than the last fix.

Why can summing one field over a million objects be several times faster with struct-of-arrays than with an array of object references?

The CPU loads memory in 64-byte cache lines. With SoA, every byte of every line loaded is a value you sum, and the prefetcher streams it sequentially (and SIMD can add several values per instruction). With object references, each element is a pointer to an object somewhere on the heap: a likely cache miss of about 100 ns per element, and most of each loaded line is fields you don't need.

Running 200 single-item calls in parallel and sending one batched call of 200 items both finish quickly. Why prefer the batch?

Parallelism cuts your wall time but still sends 200 requests: the downstream service pays 200 times the per-call overhead, and your burst can exhaust its connection pool or rate limit. Batching cuts both wall time and the load on the other side. Use parallelism, bounded, only when no batch API exists.

A producer writes to an unbounded in-memory queue faster than the consumer can drain it. What happens, and what are the fixes?

The queue grows without limit: latency for each item keeps rising (it waits behind everything before it) until the process runs out of memory. Bound the queue and pick a policy when it's full: block or await the producer (back-pressure), reject new work (429/503), or drop oldest or newest for best-effort data.

What is wrong with calling .Result on an HttpClient task inside an ASP.NET Core request handler?

It's sync-over-async: the request thread blocks until the I/O completes, so the thread can't serve other requests. Under load many threads are blocked at once, the thread pool injects new threads only slowly, and queued work (including the continuations that would complete those tasks) waits, which is thread-pool starvation. Use await all the way up.

When does response compression make a request slower?

When the payload is small or already compressed, and the link is fast. Compressing and decompressing cost CPU time on both ends; on a 1 Gbps data-centre link a 2 KB JSON response takes microseconds to send, so compression adds more time than it saves. It pays off for larger text payloads on slower links.

A CLI tool written in Java takes 1.5 s to print its help text. Which options help, and why does the JIT not?

The JIT optimises code that runs many times; a short-lived CLI exits before warm-up pays off, so the time goes to class loading and interpretation. AppCDS or the JDK 24+ AOT cache cut class-loading time; GraalVM native image compiles ahead of time for millisecond startup. (Rewriting it in Go would also start fast, but that's rarely the cheapest option.)

A teammate adds @lru_cache (or a ConcurrentDictionary memo) to a function that takes a user id and returns that user's current cart total. What could go wrong?

The function isn't pure: the cart changes, so the memo returns stale totals. If unbounded, it also grows with every user id. Memoize only pure functions of bounded inputs; for changing data use a real cache with a TTL and invalidation (see Caching).
