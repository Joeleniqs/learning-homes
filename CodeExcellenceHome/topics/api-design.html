REST API Design

Resources, verbs and status codes, problem details, pagination, filtering, idempotency keys, ETags, versioning and evolution without breaking clients.

Beginner → Advanced~65 min studyUpdated 2026-11-03

The problem: an API is a promise you can't take back

Here is an orders API that a team shipped in a sprint. It works. The demo went fine. Then the first mobile release went out, a partner integrated, and every one of these decisions became permanent:

POST /api/getOrders                         ← a verb in the URL; reads via POST, so nothing caches it
{ "customerId": 42, "page": 3 }

200 OK                                      ← 200 even when it failed
{ "success": false, "error": "NOT_FOUND" }  ← clients must parse the body to learn it failed

POST /api/createOrder                       ← the network times out; the client retries…
{ "items": [{ "sku": "pen", "qty": 2 }] }   ← …and the customer is charged twice

POST /api/updateOrder                       ← two people edit the same order;
{ "id": 7, "status": "shipped", ... }       ← the second save silently erases the first

GET /api/orders?page=3                      ← someone inserts a row; page 3 now repeats an order from page 2

GET /v1/customers/42/orders?status=open&sort=-createdAt&maxpagesize=20
200 OK                                       { "value": [...], "nextLink": "/v1/customers/42/orders?cursor=eyJ0Ijo..." }

GET /v1/orders/7
404 Not Found                                Content-Type: application/problem+json
{ "type": "https://api.contoso.com/problems/not-found", "title": "Order not found", "status": 404, "detail": "No order 7." }

POST /v1/orders                              Idempotency-Key: 9f2c6c1e-3c1b-4d5e-9a0b-6e2f1d8c7b10
201 Created                                  Location: /v1/orders/8        ← a retry with the same key replays this

PUT /v1/orders/8                             If-Match: "3"
412 Precondition Failed                      ← someone changed it since you read version 3: re-read, re-apply

GET /v1/orders?cursor=…                       ← keyset cursor: inserts and deletes never shift the pages

Every line on the left is a bug that no unit test catches, because each one only appears when a second client, a flaky network or a concurrent user shows up. And none of them can be fixed later without breaking the clients that already depend on the broken behaviour. That's what makes API design different from the rest of your code: your internal classes can be refactored tomorrow; your public contract is frozen the moment someone else's code depends on it.

Design the contract for the client that retries, races, caches, pages while data changes and upgrades a year after you. Use nouns for resources, HTTP methods for their real semantics, status codes that machines can act on, and only make changes that old clients survive.

This page teaches the mechanics with simulations you can break: retrying requests, paging a table that changes under you, double-submitting a payment, two users saving the same document, and running real client code against a "harmless" schema change. It builds on Request Pipelines and Middleware Patterns (where cross-cutting API concerns live), and leads into API Security, Caching (ETags and Cache-Control), Resilience Patterns (the client side of retries) and API Protocols (when REST is the wrong choice).

Resources: model nouns, not procedures

REST is "transfer representations of resources". In practice, that means one thing: the URL names a thing, and the HTTP method says what you're doing to it. Once you hold that line, the rest of the design falls out. Caches know GET is safe to store, proxies know PUT is safe to retry, and every HTTP client library in every language already understands your API.

Modelling rules that survive contact with real clients

  • Collections are plural nouns; items are collection/{id}. /orders, /orders/7, /orders/7/items/3. Never /getOrder, /order/list or /orders/delete/7.
  • Nest only for true ownership, and at most two levels. /customers/42/orders is a useful view ("this customer's orders"), but an order also has a canonical home, /orders/7. Deep nesting (/regions/eu/stores/9/customers/42/orders/7/items/3) forces clients to know the whole ancestry just to fetch one item.
  • IDs are opaque strings to clients, even if they're integers to you. Then you can move to GUIDs, snowflakes or prefixed IDs (ord_8Kx2) later. Sequential integers also invite enumeration attacks (see BOLA in API Security).
  • Pick one case convention and never mix them. Microsoft and Google both use camelCase JSON properties; paths are lowercase, often kebab-case for multi-word segments (/payment-methods). Consistency matters more than which one you pick.
  • Actions that aren't CRUD are still modelled as resources when possible. "Cancel an order" can be POST /orders/7/cancellation (create a cancellation) or a state change, PATCH /orders/7 {"status": "cancelled"}. When neither reads naturally, Google's AIP-136 custom methods are an honest escape hatch: POST /orders/7:cancel. Use it rarely and deliberately.
  • Don't leak your database. The resource is the client's model. Table names, join tables, internal flags and audit columns don't belong in it. A Customer resource can be assembled from five tables, and one table can back three resources.

RPC over HTTP (avoid)

  • POST /api/getCustomerOrders
  • GET /api/deleteOrder?id=7 (a crawler or link prefetcher deletes data)
  • POST /api/orders/updateStatus
  • GET /api/Orders/List?CustomerID=42
  • Every response is 200 with {"success": false}

Resource-oriented

  • GET /customers/42/orders
  • DELETE /orders/7
  • PATCH /orders/7 with {"status": "shipped"}
  • GET /orders?customerId=42
  • Status codes carry the outcome; bodies carry details

Insight: REST maturity is about what intermediaries can do for you Using real nouns and real methods isn't purity. It's what lets a CDN cache your GETs, a load balancer retry your PUTs, an HTTP client follow your Location headers, and a gateway apply per-route rate limits, all without knowing anything about your domain. An RPC-over-POST API opts out of all of that.

Methods: safe, idempotent, or neither

HTTP defines two properties for each method (RFC 9110 §9.2). Everything that retries (browsers, proxies, Polly, Resilience4j, urllib3, service meshes) makes decisions based on them, so your handlers must honour them.

  • Safe: the request doesn't change server state, as far as the client is concerned. Logging and metrics don't count. Crawlers, prefetchers and caches assume they can send safe requests freely.
  • Idempotent: sending the request N times has the same effect on the server as sending it once. The response may differ (the second DELETE gets 404), but the state doesn't.
Method Meaning Safe Idempotent Typical success Request body Cacheable
GET Read a representation ✓ ✓ 200, 304 no ✓
HEAD GET without the body ✓ ✓ 200 no ✓
OPTIONS What's allowed here (also CORS preflight) ✓ ✓ 204 no no
PUT Replace the whole resource at this URL (create if absent, when the client picks the id) ✓ 200, 201, 204 full no
DELETE Remove it ✓ 204, 202 no no
POST Create a subordinate resource, or "process this" ✗ 201 + Location, 202, 200 yes rarely
PATCH Partial update ✗ (unless designed so) 200, 204 partial no

The table is easy to memorise and easy to violate. PUT /items/7 {"qty": 3} is idempotent because "set qty to 3" lands in the same place every time. PATCH /items/7 {"op": "increment", "qty": 1} isn't, because each copy adds one more. POST /items creates a new row on every send. Don't take my word for it: run them.

Pick POST, then PATCH with an increment, then PUT, and compare the final state after one send with the state after three. That difference is the difference between "retry safely" and "charge the customer twice". Two practical consequences:

  1. Make PATCH idempotent by design when you can. JSON Merge Patch (RFC 7396, application/merge-patch+json) only sets fields, so it's naturally idempotent. JSON Patch (RFC 6902) can add to arrays, which isn't. Combine either with If-Match (below) and even non-idempotent patches become safe to retry, because the retry fails its precondition.
  2. POST needs help to be retry-safe. That help is an idempotency key, which gets its own section below.

Pitfall: state changes behind GET GET /orders/7/approve, GET /unsubscribe?u=42, GET /cart/add?sku=pen. Link prefetchers, antivirus URL scanners, chat-app link previews and search crawlers all issue GETs on their own. Teams have lost data to Slack unfurling a "delete" link. If it changes state, it isn't a GET.

Status codes: a decision chain, not a lookup table

A status code is the one part of the response that every client, proxy, retry policy and dashboard reads. Its job is to tell a machine what to do next: retry later (429, 503), re-authenticate (401), stop and fix the request (400, 422), reload and try again (412), or follow a link (201, 202, 303). That's why "200 with success: false" is so harmful: every generic tool now believes the call succeeded.

The useful way to choose a code is to ask questions in the order your pipeline evaluates them. Rate limiting runs before authentication (it's cheaper), authentication before routing details, validation before you touch the database, and so on. The first "yes" decides the answer.

The ordering encodes real decisions:

  • 401 vs 403. 401 Unauthorized really means unauthenticated: "I don't know who you are; send credentials". It must carry WWW-Authenticate. 403 Forbidden means "I know who you are, and the answer is no"; re-authenticating won't help.
  • 403 vs 404 for things you may not see. If a caller can't access order 7, answering 403 confirms that order 7 exists. For per-object access, answer 404. That's why the chain checks authorization on the object only after it knows the object exists, and then hides the difference.
  • 400 vs 422. 400 for a request you can't parse (bad JSON, wrong types); 422 Unprocessable Content for one you can parse whose values break the rules. Many stacks use 400 for both (ASP.NET Core's [ApiController]), and FastAPI uses 422 for both. Either is fine; consistency is what matters, plus a problem-details body listing every invalid field.
  • 409 vs 412. 409 Conflict is about the resource's state ("this order is already shipped", "this email is taken"). 412 Precondition Failed is specifically "your If-Match/If-Unmodified-Since didn't hold": you're working from a stale copy.
  • 5xx is the server admitting fault. 500 is a bug. 502/504 mean an upstream failed or timed out. 503 means "overloaded or in maintenance, come back" (add Retry-After). Never return 5xx for bad input: clients retry 5xxs, and your error dashboards and SLOs count them as your failures.

Errors: problem details (RFC 9457)

Once the status code has said what kind of failure it was, the body says exactly what went wrong, in a format every client can parse without reading your docs. RFC 9457 (which obsoletes RFC 7807) defines application/problem+json:

HTTP/1.1 422 Unprocessable Content
Content-Type: application/problem+json

{
  "type": "https://api.contoso.com/problems/validation",
  "title": "Your request has invalid fields.",
  "status": 422,
  "detail": "2 fields failed validation.",
  "instance": "/v1/orders",
  "traceId": "00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01",
  "errors": [
    { "pointer": "#/items/0/qty", "detail": "must be between 1 and 100" },
    { "pointer": "#/items/1/sku", "detail": "unknown sku \"ghost\"" }
  ]
}
Member What it's for Rules
type A URI that identifies the kind of problem. Clients branch on this, not on title Stable forever. Ideally it resolves to human docs. Default about:blank means "just the status code"
title A short human summary of the type Same for every occurrence of this type; may be localised
status The HTTP status, repeated for convenience Must match the real status line

Tip: put a trace id in every error Add the W3C traceparent trace id (see Observability) as an extension member. When a customer sends you a screenshot of an error, that one string takes you straight to the distributed trace. Never put stack traces, SQL, connection strings or internal hostnames in detail: that's free reconnaissance for an attacker.

func writeProblem(w http.ResponseWriter, r *http.Request, p Problem) {
    if p.Type == "" {
        p.Type = "about:blank"
    }
    if p.Title == "" {
        p.Title = http.StatusText(p.Status)
    }
    p.Instance = r.URL.Path
    body := map[string]any{"type": p.Type, "title": p.Title, "status": p.Status, "detail": p.Detail, "instance": p.Instance}
    for k, v := range p.Ext {
        body[k] = v // extension members sit at the top level
    }
    w.Header().Set("Content-Type", "application/problem+json")
    w.WriteHeader(p.Status)
    _ = json.NewEncoder(w).Encode(body)
}

Pagination: offset drifts, cursors don't

Any collection that can grow needs paging from day one. Adding it later is a breaking change, because clients that expected "everything" now silently get page 1. There are two families:

  • Offset (?offset=40&limit=20, or ?page=3). The server runs ORDER BY … OFFSET 40 LIMIT 20. Easy to build, and it lets users jump to page 37.
  • Keyset / cursor (?cursor=eyJ0Ijo…). The cursor encodes the sort key of the last row the client saw, and the server runs WHERE (createdAt, id) < (:t, :id) ORDER BY createdAt DESC, id DESC LIMIT 20. It's opaque to the client, and it only moves forward (or backward with a second cursor).

Offset has two problems that keyset doesn't. The first is correctness: an offset is a position, and positions shift when rows are inserted or deleted ahead of you. Watch two clients page through the same table while other users write to it:

Every insert above the reader's position pushes rows down into the next page, so the reader sees them twice. Every delete pulls rows up past the boundary, so the reader never sees them at all. For a UI, that's a duplicate in an infinite scroll. For a sync job, an export or a billing run, a skipped row is silent data loss. Keyset doesn't care, because "everything older than order 9" means the same thing whatever happens above it.

The second problem is cost. The database can't jump to row 10,000; it walks the index and throws rows away:

The cursor must name a unique position

Keyset has one classic bug. If the sort key isn't unique, "everything after the last price I saw" either skips rows that share that price (>) or returns them forever (>=). The fix is to make the sort key unique by adding the primary key as the last sort column and comparing the tuple:

Row-value comparison (price, id) > (:p, :id) is supported natively by PostgreSQL, MySQL 8, SQLite and Oracle. For SQL Server and ORMs that don't translate it, expand it: price > :p OR (price = :p AND id > :id). You need a composite index on (price, id) for either form to seek.

import base64, json

def encode_cursor(created_at: str, id_: int) -> str:
    raw = json.dumps([created_at, id_], separators=(",", ":")).encode()
    return base64.urlsafe_b64encode(raw).decode().rstrip("=")

def decode_cursor(cursor: str) -> tuple[str, int]:
    pad = "=" * (-len(cursor) % 4)
    created_at, id_ = json.loads(base64.urlsafe_b64decode(cursor + pad))  # ValueError → 400
    return str(created_at), int(id_)

def list_orders(db, max_page_size: int = 20, cursor: str | None = None) -> dict:
    size = max(1, min(max_page_size, 100))
    sql, args = "SELECT id, created_at, status FROM orders", []
    if cursor:
        sql += " WHERE (created_at, id) < (?, ?)"            # row-value comparison: a unique position
        args += decode_cursor(cursor)
    sql += " ORDER BY created_at DESC, id DESC LIMIT ?"
    rows = db.execute(sql, [*args, size + 1]).fetchall()    # one extra row tells us if there's more
    page, more = rows[:size], len(rows) > size
    return {
        "value": [{"id": r[0], "createdAt": r[1], "status": r[2]} for r in page],
        "nextCursor": encode_cursor(page[-1][1], page[-1][0]) if more else None,
    }

type cursor struct {
    At time.Time `json:"t"`
    ID int64     `json:"i"`
}

func (c cursor) encode() string { b, _ := json.Marshal(c); return base64.RawURLEncoding.EncodeToString(b) }

func decodeCursor(s string) (c cursor, err error) {
    b, err := base64.RawURLEncoding.DecodeString(s)
    if err == nil {
        err = json.Unmarshal(b, &c)
    }
    return c, err
}

func (s *Store) ListOrders(ctx context.Context, maxPageSize int, after string) ([]Order, string, error) {
    size := min(max(maxPageSize, 1), 100)
    q, args := `SELECT id, created_at, status FROM orders`, []any{}
    if after != "" {
        c, err := decodeCursor(after)
        if err != nil {
            return nil, "", ErrBadCursor // → 400
        }
        q += ` WHERE (created_at, id) < ($1, $2)`
        args = append(args, c.At, c.ID)
    }
    q += fmt.Sprintf(` ORDER BY created_at DESC, id DESC LIMIT %d`, size+1) // an int, never user text
    rows, err := s.db.QueryContext(ctx, q, args...)
    if err != nil {
        return nil, "", err
    }
    defer rows.Close()
    var out []Order
    for rows.Next() {
        var o Order
        if err := rows.Scan(&o.ID, &o.CreatedAt, &o.Status); err != nil {
            return nil, "", err
        }
        out = append(out, o)
    }
    next := ""
    if len(out) > size {
        out = out[:size]
        next = cursor{At: out[size-1].CreatedAt, ID: out[size-1].ID}.encode()
    }
    return out, next, rows.Err()
}

Convention Shape Notes
Microsoft REST / Azure guidelines { "value": [...], "nextLink": "https://…" } nextLink is a full URL that already contains the cursor and every filter; clients just follow it. Absent on the last page.
Google AIP-158 { "orders": [...], "nextPageToken": "…" } The client sends pageToken and pageSize. An empty token means the end.
RFC 8288 Link header Link: <…?cursor=abc>; rel="next" Keeps the body a plain array. GitHub's API uses it.
  • The page size is a maximum, not a promise. The server may return fewer items (even zero) and still have a next page, for example when filtering on top of a scan. Clients must loop until there's no next link, not until a page comes back short.
  • Cursors are opaque. Base64 stops clients from depending on the format, not attackers from reading it. If a cursor contains anything sensitive or abusable, encrypt or sign it. Always validate it as untrusted input.
  • Cursors must carry the query. If page 2 is requested with a different filter or sort than page 1, reject it (400), or embed the filter in the cursor and ignore the new parameters.
  • Total counts are expensive. COUNT(*) over a big filtered table can cost more than the page itself. Make it opt-in (?count=true), approximate, or leave it out.
  • Offset is still fine for small, slowly changing collections that a human pages through and wants "jump to page 7" (an admin grid of 300 rows). Use keyset for anything large, fast-changing or machine-consumed.

Filtering, sorting and field selection

Filters are query parameters on the collection. Keep the grammar boring and predictable:

Need Common convention Example
Equality filter field=value ?status=open&customerId=42
Range suffixed names or operators ?createdAfter=2026-01-01T00:00:00Z, ?total.gte=100
Rich expressions OData $filter, Google AIP-160 filter ?$filter=status eq 'open' and total gt 100
Sorting comma list, - for descending ?sort=-createdAt,id (OData: $orderby=createdAt desc)
Sparse fields fields / $select / read_mask ?fields=id,status,total
Embedding related data expand / $expand ?expand=customer

Every filterable and sortable field is a promise of an index. A free-form sort parameter lets any client ask for ORDER BY notes on 50 million rows. So: allow-list fields explicitly, map public names to columns (never interpolate the parameter into SQL), and reject unknown fields with 400 rather than ignoring them, so a typo like ?staus=open doesn't silently return everything.

Pitfall: filters that leak or explode A generic $filter over your ORM can let a client filter on fields it's not allowed to see (?$filter=salary gt 100000 reveals salaries one bit at a time), or build a query that scans the whole table. Idempotency keys: making POST safe to retry

POST is the one method that clients most need to retry (create the order, charge the card) and the one that HTTP says isn't safe to retry. A timeout doesn't tell the client whether the server never got the request or processed it and lost the response. Retrying risks a duplicate; not retrying risks losing the order.

The fix, popularised by Stripe and now an IETF draft (the Idempotency-Key header), is for the client to generate a unique key per intended operation and send it with every attempt. The server remembers the key with a fingerprint of the request and the response it produced:

  1. First time it sees the key: atomically record it as "in progress", do the work, store the response.
  2. Key seen, finished, same fingerprint: replay the stored response. Don't do the work again.
  3. Key seen, still in progress: 409 Conflict. Two attempts are racing (double-click, aggressive retry).
  4. Key seen with a different request body: 422 Unprocessable Content. The client reused a key for a different operation, which is a client bug worth surfacing loudly.

Run all three scenarios with the key off, then on. Without a key, the "lost response" scenario creates two orders and charges twice. With one, the retry gets the original 201 back byte for byte, and the payment provider is called once. The design details are where implementations go wrong:

  • The claim must be atomic. "Check if the key exists, then insert" races. Use SET key value NX EX ttl in Redis, or an INSERT that relies on a unique constraint in SQL.
  • Scope keys to the caller. Store account:key, never just key, or one customer can replay another customer's response.
  • Fingerprint the request (method, path, canonical body) so a reused key with a different payload is detected instead of silently replaying the wrong order.
  • Keep the record for longer than any client retries: 24 hours is the usual choice.
  • Store the key in the same transaction as the business write when they share a database. Otherwise a crash between "order committed" and "key marked done" leaves a key stuck in progress, or, worse, a forgotten key that permits a duplicate.
  • Failures before any side effect release the key so the client can retry. Failures after a side effect must be stored and replayed like successes.

        var fp = Convert.ToHexString(SHA256.HashData(JsonSerializer.SerializeToUtf8Bytes(body)));
        var claim = JsonSerializer.Serialize(new Entry(fp, "in_progress", null, null));

        if (!await redis.StringSetAsync(scope, claim, Ttl, When.NotExists))   // atomic: SET NX EX

            if (raw.IsNull) return TypedResults.Problem(statusCode: 409, title: "Please retry");
            var e = JsonSerializer.Deserialize<Entry>(raw.ToString())!;
            if (e.Fingerprint != fp)
                return TypedResults.Problem(statusCode: 422, title: "Idempotency-Key reused with a different body");
            if (e.State == "in_progress")
                return TypedResults.Problem(statusCode: 409, title: "A request with this key is in progress");
            return TypedResults.Created(e.Location, e.Order);                   // replay the original 201
        }
        try
        {
            var order = await orders.CreateAsync(body);
            var done = new Entry(fp, "done", $"/v1/orders/{order.Id}", order);
            await redis.StringSetAsync(scope, JsonSerializer.Serialize(done), Ttl);
            return TypedResults.Created(done.Location, order);
        }
        catch (ValidationException)
        {
            await redis.KeyDeleteAsync(scope);    // nothing happened: let the client fix and retry
            throw;
        }
    }
}

import hashlib, json, threading, time
from dataclasses import dataclass

@dataclass
class Entry:
    fingerprint: str
    state: str                       # "in_progress" | "done"
    response: tuple | None = None
    expires: float = 0.0

class IdempotencyStore:
    """In-memory for clarity. Production: Redis SET NX EX, or a SQL table with a unique key."""
    def __init__(self, ttl: float = 24 * 3600):
        self._lock, self._data, self._ttl = threading.Lock(), {}, ttl

    def begin(self, scope: str, fingerprint: str):
        now = time.monotonic()
        with self._lock:                                   # check-and-claim is ONE atomic step
            e = self._data.get(scope)
            if e is None or e.expires < now:
                self._data[scope] = Entry(fingerprint, "in_progress", None, now + self._ttl)
                return "new", None
            if e.fingerprint != fingerprint:
                return "mismatch", None
            return ("busy", None) if e.state == "in_progress" else ("replay", e.response)

    def finish(self, scope: str, response: tuple) -> None:
        with self._lock:
            e = self._data[scope]
            e.state, e.response = "done", response

    def release(self, scope: str) -> None:
        with self._lock:
            self._data.pop(scope, None)

def fingerprint(method: str, path: str, body: dict) -> str:
    canonical = json.dumps(body, sort_keys=True, separators=(",", ":"))
    return hashlib.sha256(f"{method} {path} {canonical}".encode()).hexdigest()

def create_order(store: IdempotencyStore, account: str, key: str, body: dict, create) -> tuple:
    scope = f"{account}:{key}"
    state, saved = store.begin(scope, fingerprint("POST", "/v1/orders", body))
    if state == "replay":
        return saved
    if state == "busy":
        return 409, {"title": "A request with this key is in progress"}
    if state == "mismatch":
        return 422, {"title": "Idempotency-Key reused with a different body"}
    try:
        response = (201, create(body))
    except ValueError:                 # validation failed before any side effect
        store.release(scope)
        raise
    store.finish(scope, response)
    return response

  if (!key) return next(new Problem(400, "Idempotency-Key header is required"));
  const scope = `idem:${res.locals.accountId}:${key}`;
  const fp = createHash("sha256").update(`${req.method} ${req.path} ${JSON.stringify(req.body)}`).digest("hex");

  const claimed = await redis.set(scope, JSON.stringify({ fp, state: "in_progress" }), "EX", 86_400, "NX");
  if (!claimed) {
    const saved = JSON.parse((await redis.get(scope)) ?? "null");
    if (!saved) return next(new Problem(409, "Please retry"));
    if (saved.fp !== fp) return next(new Problem(422, "Idempotency-Key reused with a different body"));
    if (saved.state === "in_progress") return next(new Problem(409, "A request with this key is in progress"));
    if (saved.location) res.location(saved.location);
    return res.status(saved.status).json(saved.body);              // replay
  }
  const json = res.json.bind(res);
  res.json = (body: unknown) => {                                    // capture what the handler sends
    const write = res.statusCode >= 500 || res.statusCode === 400 || res.statusCode === 422
      ? redis.del(scope)                                             // nothing happened: allow a retry
      : redis.set(scope, JSON.stringify({ fp, state: "done", status: res.statusCode,
          location: res.get("Location"), body }), "EX", 86_400);
    write.catch(() => {});
    return json(body);
  };
  next();
};

Insight: idempotency is end to end An idempotency key on your API only helps if everything behind it is idempotent too. Pass a derived key to the payment provider (Stripe, Adyen and others accept one), make queue consumers deduplicate by message id, and use "insert if absent" for side effects. A retry that's safe at the front door but sends two emails at the back is still a bug. See Resilience Patterns for the client side: retry only idempotent operations, with backoff and jitter.

ETags and conditional requests: no more lost updates

Two people open the same document. Alice changes the title, Bob changes the status, and both press Save. With a plain PUT, the server accepts both, and whoever saves second overwrites the other's change with the stale copy they loaded. Nobody gets an error. This is the lost update, and it's the default behaviour of almost every CRUD API.

HTTP's built-in fix is optimistic concurrency with entity tags:

  1. Every representation carries an ETag: an opaque version (a row version, a hash or a counter).
  2. The client sends it back on writes: If-Match: "3".
  3. The server applies the write only if the current version is still "3"; otherwise it answers 412 Precondition Failed, and the client re-reads, re-applies its change and tries again.

Compare the three modes. Last-write-wins loses Alice's title and tells her nothing. If-Match turns the silent loss into a 412 that Bob's client handles by re-reading and re-applying, so both changes survive. A field-level PATCH happens to survive here because the edits touch different fields, but it still silently overwrites when two people change the same field. PATCH plus If-Match is the safe default.

Tip: strong vs weak ETags W/"3" is a weak ETag ("semantically equivalent", for example the same data with different gzip). If-Match uses strong comparison, so weak ETags never match it. Use strong ETags derived from a version column for anything you write against. Weak ETags generated by hashing the response body (Express does this by default) are fine for 304s but useless for concurrency.

Long-running operations: 202 and a status monitor

Some requests take longer than anyone should hold an HTTP connection open for: generating a report, provisioning a VM, transcoding a video. Load balancers and gateways time out after 30–120 seconds, mobile networks drop, and a thread blocked for minutes is a thread that can't serve anyone else. The standard answer is the asynchronous request-reply pattern:

  1. POST /reports validates the request, queues the work, and answers immediately with 202 Accepted and the URL of a status monitor resource (Location or Azure's Operation-Location), plus Retry-After.
  2. The client polls GET /operations/{id}. It returns 200 with {"status": "Running", "percentComplete": 40} while the work runs.
  3. When the status is terminal, the monitor links to the result (resourceLocation) or carries an error. The client follows the link.

Polling is a trade-off between latency (how soon the client notices) and load (how many requests it spends noticing). Retry-After lets the server choose the trade-off, which is why well-behaved clients honour it. Change the client behaviour below and watch the wasted polls and the detection delay move in opposite directions:

import time
import httpx

TERMINAL = {"Succeeded", "Failed", "Canceled"}

def run_report(client: httpx.Client, body: dict, timeout_s: float = 600) -> dict:
    r = client.post("/v1/reports", json=body)
    if r.status_code != 202:
        r.raise_for_status()
        return r.json()                                    # finished synchronously after all
    monitor = r.headers.get("Operation-Location") or r.headers["Location"]
    deadline = time.monotonic() + timeout_s
    while True:
        time.sleep(min(float(r.headers.get("Retry-After", 5)), 60))
        r = client.get(monitor)
        r.raise_for_status()
        op = r.json()
        if op["status"] in TERMINAL:
            break
        if time.monotonic() > deadline:
            raise TimeoutError(f"operation {monitor} still {op['status']}")
    if op["status"] != "Succeeded":
        raise RuntimeError(op.get("error", op["status"]))
    return client.get(op["resourceLocation"]).json()

// Client side in Go: the same loop, cancellable through the context.
func waitForOperation(ctx context.Context, c *http.Client, monitor string) (Operation, error) {
    delay := 5 * time.Second
    for {
        select {
        case <-ctx.Done():
            return Operation{}, ctx.Err()
        case <-time.After(delay):
        }
        req, _ := http.NewRequestWithContext(ctx, http.MethodGet, monitor, nil)
        resp, err := c.Do(req)
        if err != nil {
            return Operation{}, err
        }
        var op Operation
        err = json.NewDecoder(resp.Body).Decode(&op)
        resp.Body.Close()
        if err != nil {
            return Operation{}, err
        }
        switch op.Status {
        case "Succeeded", "Failed", "Canceled":
            return op, nil
        }
        if s, err := strconv.Atoi(resp.Header.Get("Retry-After")); err == nil && s > 0 {
            delay = time.Duration(min(s, 60)) * time.Second // the server sets the pace
        }
    }
}

Use 202 + a status monitor when

  • The work routinely takes longer than a few seconds, or its duration is unpredictable.
  • The work must survive the client disconnecting (and ideally the server restarting: persist operations).
  • Clients need progress, cancellation, or to look the result up later.

Prefer webhooks or server-sent events on top of it when clients can receive callbacks and latency matters. Keep polling as the fallback: callbacks get lost.

Bulk operations: all or nothing, or per-item results

Clients that need to create 500 orders shouldn't make 500 round trips. A batch endpoint (POST /orders:batch, or POST /orders with an array) saves latency but raises a question a single request never has to answer: what happens when item 37 is invalid?

Atomic (all or nothing) Partial success (per-item results)
Response 201/200 if all succeed; 422/409 with problem details listing every bad index if any fail 200 (or 207 Multi-Status) with one result per item, each with its own status
Client logic Simple: fix and resend everything Must inspect every item; retry only the failures
Server cost One transaction; long transactions lock more rows Independent writes; no giant transaction
Retry safety Retry the whole batch with one idempotency key Per-item keys (or the batch key plus the item index)

Rules either way: validate every item before deciding, so the client sees all the errors in one response; cap the batch size (and document it) so one request can't hold a transaction for a minute; and return results in request order with the index, so clients can correlate them without guessing. If the batch is big enough to take a while, combine it with the long-running operation pattern.

Versioning and evolution: change without breaking

The hardest part of API design is time. Your API will change; the clients already in production won't. Every change is either compatible (old clients keep working without changes) or breaking (some old client's code now fails). The difficulty is that "breaking" depends on what the client code does, not on what your schema diff looks like. So run the clients:

Try every change in the list. Three lessons fall out:

  1. Adding a response field is only safe if clients are tolerant readers. A strict deserializer that rejects unknown properties (Jackson's FAIL_ON_UNKNOWN_PROPERTIES, DisallowUnknownFields in Go, a .strict() zod schema) breaks on the most harmless change there is. That's why the Microsoft, Google and Zalando guidelines all require clients to ignore unknown fields. Publish that rule, and make your own SDKs follow it.
  2. Adding an enum value breaks exhaustive switches. Generated SDKs and switch statements without a default case crash on a value they've never seen. Document enums as extensible from day one and give clients an Unknown/Other fallback, or treat every new value as a breaking change.
  3. Some breaks don't throw. Removing an optional field parses fine and silently loses data in every client that displayed or stored it. Changing the meaning of a field (total now excludes tax) is the worst kind: every client compiles, runs and is wrong.
Compatible (usually) Breaking
Add a new endpoint or resource Remove or rename an endpoint, field or query parameter
Add an optional request field or query parameter Add a required request field, or make an optional one required
Add a response field (tolerant readers required) Remove a response field, or change its type or format (42 → "ord_42")
Relax validation (accept a wider range) Tighten validation (reject what used to be accepted)
Add an error type for a new condition Change the status code or error type for an existing condition
Add an enum value, if documented as extensible Add an enum value to a closed enum; change a default; change the meaning of a field
Add a new optional header Change authentication, pagination style, or the shape of a collection response

Evolve without a new version first

Most changes don't need a new version at all. Expand, migrate, contract (also called parallel change) handles renames and type changes in place:

  1. Expand: add amount next to total. Write both, accept either.
  2. Migrate: update SDKs and docs, mark total as deprecated, and watch usage in your telemetry (log which clients still read or send it).
  3. Contract: remove total only when usage is zero, or at the next major version.

When you do have to break the contract, signal it in the protocol, not just in a blog post:

HTTP/1.1 200 OK
Deprecation: @1782864000                                    ← RFC 9745: deprecated since this date (Unix time)
Sunset: Thu, 01 Jul 2027 00:00:00 GMT                         ← RFC 8594: stops working after this date
Link: <https://api.contoso.com/docs/migrate-v2>; rel="deprecation"; type="text/html"

Contracts: OpenAPI, contract-first or code-first

An OpenAPI document describes every path, parameter, schema, status code and security scheme of your API in a machine-readable form. From it you get docs, client SDKs in every language, mock servers, request validation and, most valuably, an automated breaking-change check on every pull request. The real question is which comes first: the document or the code.

Contract-first (design-first)

Write the OpenAPI (or TypeSpec) first, review it like code, then generate server stubs and clients.

  • Consumers can review and mock the API before any code exists.
  • The contract is deliberate; implementation details can't leak into it.
  • Best for public and partner APIs, and for several teams working in parallel.
  • Cost: the spec and the code can drift unless CI validates the implementation against the spec.

Code-first

Annotate the code; the framework generates the OpenAPI document at build time or runtime.

  • Fastest to start; the document always matches what the code does.
  • Best for internal APIs owned by one team.
  • Cost: refactoring a DTO silently changes the public contract. You must diff the generated document in CI to notice.

Whichever direction you choose, put two checks in CI: a linter (Spectral with a style guide, so naming, pagination and error conventions are enforced, not just written down), and a diff against the last released contract (oasdiff, openapi-diff or Azure's breaking-change tooling) that fails the build on breaking changes unless the version changes too.

func routes(s *OrderStore) http.Handler {
    mux := http.NewServeMux()
    mux.HandleFunc("GET /v1/orders/{id}", func(w http.ResponseWriter, r *http.Request) {
        id, err := strconv.ParseInt(r.PathValue("id"), 10, 64)
        if err != nil {
            writeProblem(w, http.StatusBadRequest, "invalid-id", "id must be an integer")
            return
        }
        order, ok := s.Find(id)
        if !ok {
            writeProblem(w, http.StatusNotFound, "not-found", "order not found")
            return
        }
        etag := fmt.Sprintf("%q", strconv.Itoa(order.Version))
        if r.Header.Get("If-None-Match") == etag {
            w.WriteHeader(http.StatusNotModified)
            return
        }
        w.Header().Set("ETag", etag)
        writeJSON(w, http.StatusOK, order)
    })
    mux.HandleFunc("POST /v1/orders", func(w http.ResponseWriter, r *http.Request) {
        var cmd CreateOrder
        dec := json.NewDecoder(http.MaxBytesReader(w, r.Body, 1<<20))
        if err := dec.Decode(&cmd); err != nil {
            writeProblem(w, http.StatusBadRequest, "malformed", "body is not valid JSON")
            return
        }
        if errs := cmd.Validate(); len(errs) > 0 {       // map[field][]message
            writeValidationProblem(w, errs)                  // 422 with "errors"
            return
        }
        order := s.Add(cmd)
        w.Header().Set("Location", fmt.Sprintf("/v1/orders/%d", order.ID))
        writeJSON(w, http.StatusCreated, order)
    })
    return mux
}

When NOT to use REST

REST over HTTP + JSON is the right default for public, resource-oriented APIs that browsers, partners and caches must understand. It's the wrong tool when the interaction isn't "transfer a representation of a resource":

Need Better fit Why
Low-latency service-to-service calls, strict contracts, streaming gRPC HTTP/2, Protobuf, generated stubs, bidirectional streams
Many clients that each need a different slice of a deep graph GraphQL The client picks fields; one round trip instead of N
Server pushes updates to a browser Server-sent events, WebSockets Polling a REST resource wastes requests and adds latency
Fire-and-forget work, fan-out, or decoupled producers and consumers A message broker (queues, topics, events) No one waits; load is levelled; consumers can be offline
An action that really isn't CRUD (approve, cancel, restart) A REST custom method (POST /orders/42:cancel, AIP-136) Don't twist it into a fake PATCH {status}, and don't switch protocols just for it

Common pitfalls

Pitfalls that show up in every API review

  • Returning 200 with {"success": false}. Proxies, retries, monitoring and SDKs all read the status code. Use the right one and a problem-details body.
  • Leaking your database. Auto-incrementing ids reveal volume and invite enumeration, and table columns become contract fields you can never rename. Map entities to DTOs.
  • Unbounded collections. A list without a page-size cap is a denial-of-service endpoint and a time bomb as data grows.
  • Retrying POST without an idempotency key. Duplicate payments come from timeouts, not from bugs in your business logic.
  • Last-write-wins updates. Without ETags, two editors silently overwrite each other.
  • Breaking changes in a "minor" release, such as renaming a field, adding a required field, or tightening validation. Run a contract diff in CI.
  • Chatty APIs that need 20 calls to render one screen. Offer composite resources, expand, or a backend-for-frontend.
  • Inconsistency. customerId here, customer_id there, created vs createdAt, different error shapes per team. Adopt a published guideline and lint for it.

Checklist

Before you publish an endpoint

  • [ ] Plural noun resources, at most two levels of nesting, opaque string ids, one casing convention.
  • [ ] Methods match their semantics: GET is safe; PUT and DELETE are idempotent; POST is protected with Idempotency-Key.
  • [ ] Status codes come from the decision chain; every error is application/problem+json with a stable type.
  • [ ] Collections are paginated (cursor-based for large or changing data), with a default and a maximum page size and a nextLink.
  • [ ] Filter and sort fields are allow-listed and backed by indexes.
  • [ ] Updates use ETag + If-Match; 412 on a mismatch; 428 if the precondition is required and missing.
  • [ ] Anything slower than a few seconds returns 202 + a status monitor + Retry-After.
  • [ ] Batch endpoints have a documented size cap and an explicit atomic or partial-success contract.
  • [ ] Version strategy chosen; tolerant readers documented; Deprecation/Sunset headers before removal.
  • [ ] OpenAPI published, linted (Spectral), and diffed against the last release in CI.
  • [ ] Authentication, authorization, rate limits and input limits applied: see API security.

Self-check

A client's PUT request times out. Is it safe to retry? What about POST?

PUT is idempotent: sending the same full representation twice leaves the same state, so it's safe to retry. POST isn't. A retry may create a second order unless the request carries an Idempotency-Key that the server records together with the original response.

Why does offset pagination skip or repeat items, and what fixes it?

OFFSET counts positions at query time. An insert before the current page shifts every row down, so the client sees a repeat; a delete shifts rows up, so it skips one. Keyset (cursor) pagination continues "after the last key I saw", which isn't affected by changes on earlier pages. Make the sort key unique by adding the id as a tie-breaker.

User A asks for an order belonging to another tenant. Should it be 403 or 404?

404. A 403 confirms the resource exists, which leaks information and helps enumeration (BOLA). Return 403 only when the caller is allowed to know the resource exists but not to perform this action.

Two people edit the same order; the second save wins silently. Which headers prevent this?

The server returns ETag with every GET. Clients send it back in If-Match on PUT or PATCH. The server performs a compare-and-set (UPDATE … WHERE version = @v) and returns 412 Precondition Failed if someone else changed the order first. The client then re-reads, merges and retries.

You add a new value "OnHold" to the order status enum. Is that a breaking change?

It can be. Clients with exhaustive switch statements or generated enums without an unknown fallback will throw. It's compatible only if the enum was documented as extensible from day one and clients handle unknown values.

An export takes about 3 minutes. Design the API.

POST /exports returns 202 Accepted with Operation-Location: /operations/{id} and Retry-After: 10. GET /operations/{id} returns {status, percentComplete}. When the status is Succeeded, it includes resourceLocation pointing to the file. Include a cancel action, keep terminal operations around for a while, and offer a webhook for clients that can receive one.

Contract-first or code-first for a public partner API built by three teams?

Contract-first. Partners and teams review and mock the OpenAPI or TypeSpec before code exists, and CI checks the implementation against it. Code-first suits a single team's internal API, but even then the generated document should be diffed in CI.
