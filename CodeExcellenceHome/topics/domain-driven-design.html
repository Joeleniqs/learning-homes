Domain-Driven Design Essentials

Bounded contexts, aggregates, entities vs value objects, domain events and repositories, without the ceremony.

Advanced~55 min studyBuilds on: Types, Immutability & Domain Modelling, Application Architecture StylesUpdated 2026-11-03

The problem: one model to rule them all

A growing e-commerce company has one Product class. Catalog needs a description, images and SEO slugs. Sales needs list price, discounts and tax category. The warehouse needs weight, bin location and hazmat flags. Shipping needs dimensions. Marketing needs badges. Five years later the class has 74 properties and 11 nullable foreign keys, and nobody can change it without breaking someone. Every team uses the word "product", and every team means something different by it.

In the same codebase, the rule "an order can't be changed after it has shipped" exists in four services. Each one checks order.Status != 3 (three means "shipped", unless you ask the person who added status 7). The Order class itself is a bag of public setters. Nothing stops the next service from writing order.Status = 1.

public class Product                       // used by Catalog, Sales, Warehouse, Shipping, Marketing...
{
    public int Id { get; set; }
    public string Name { get; set; }
    public string? SeoSlug { get; set; }       // Catalog
    public decimal Price { get; set; }         // Sales: gross or net? which currency?
    public decimal? WeightKg { get; set; }     // Warehouse
    public string? BinLocation { get; set; }   // Warehouse
    public int? HazmatClass { get; set; }      // Shipping
    public string? Badge { get; set; }         // Marketing
    // ...66 more
}

public class OrderService
{
    public void ChangeQuantity(Order order, int lineId, int qty)
    {
        if (order.Status == 3) throw new Exception("shipped");   // copy #1 of the rule
        order.Lines.First(l => l.Id == lineId).Qty = qty;        // qty = 0? -5? nobody checks
        order.Total = order.Lines.Sum(l => l.Qty * l.Price);     // forget this line and Total is wrong
    }
}

Domain-Driven Design (DDD) is a set of tools for exactly these two failures:

  • Strategic design fixes the first one. Instead of one model of the whole business, you split the system into bounded contexts. Each context has its own model and its own vocabulary, and the relationships between contexts are explicit.
  • Tactical design fixes the second one. Inside a context, you use entities, value objects and aggregates that protect their own rules, so an invalid order cannot be built in the first place.

The DDD rule of thumb: model the business in the language of the business, one bounded context at a time, and put each rule inside the object whose data it protects. A model is only valid inside its boundary. Never try to build one model of the whole enterprise.

This page assumes you know Types, Immutability & Domain Modelling (value objects, records, "make illegal states unrepresentable") and Application Architecture Styles (where the domain layer lives and why it depends on nothing). DDD is what you put inside that domain layer. Services, Messaging & Events covers what happens when bounded contexts become separate services.

Why the order matters

A perfect aggregate in the wrong boundary is still wrong. If "Product" means five things, no amount of tactical modelling makes one Product class right. Draw the boundaries first and the tactical design becomes much smaller and simpler, because each model only has to serve one purpose.

Ubiquitous language

A ubiquitous language is a vocabulary shared by developers and domain experts inside one bounded context. It is used in conversations, in tickets, in tests and in the code itself. If the business says "a customer places an order" and "a warehouse allocates stock", the code has order.Place() and stock.Allocate(), not OrderManager.UpdateStatus(2) and InventoryHelper.Process().

It sounds cosmetic. It isn't, for three reasons:

  1. Translation is where bugs live. Each time someone converts "a refund after dispatch needs a return label" into if (s >= 3 && r), meaning is lost. Code that uses the expert's words can be read back to the expert.
  2. The words carry the rules. "Cancel" and "void" may look like synonyms to a developer. To an accountant, a voided invoice never existed, while a cancelled one needs a credit note. Two words mean two operations with different rules.
  3. New words reveal missing concepts. When an expert keeps saying "back-order", and there is no BackOrder in the code, the model is missing something real.
// Developers' words. The expert can't read it, and the rule is hidden in numbers.
orderManager.UpdateStatus(orderId, 4);
orderManager.SetFlag(orderId, "RL", true);
invoiceHelper.Process(invoiceId, mode: 2);

// The expert's words. Each method is a business operation with its own rules.
order.Dispatch(trackingNumber);
order.RequestReturn(reason, ReturnLabel.Prepaid);
invoice.Void(because: "duplicate");          // not Cancel(): a cancel needs a credit note

A small glossary per context, kept next to the code, is enough. Note how the same word changes meaning between contexts. That is not a bug in the glossary; it is the signal that you have found a context boundary.

Term In Sales In Warehouse In Billing

Customer a buyer with a cart, a loyalty tier and addresses (not a concept: only a delivery address) a legal entity with a tax id and payment terms

Make the language visible in code reviews

Reject names such as Manager, Helper, Processor, Data, Info and Util in the domain layer, and boolean parameters such as Process(true, false). Ask "what would the expert call this?" If nobody knows, that is a question for the expert, not a naming decision for the developer.

Subdomains: where to spend your effort

A domain is the business area your software serves. It splits into subdomains, and they do not all deserve the same investment. This is the most practical idea in strategic DDD, because it tells you where not to use the rest of it.

The in-house identity server

A team spent eight months building login, MFA, password reset and token issuance "because it's central to everything". It is central, but it is also generic: it doesn't make the company different, and it is a security liability to maintain. Central does not mean core. Ask "would a customer choose us because of this?" If the answer is no, buy it and put an anticorruption layer in front of it.

Bounded contexts

A bounded context is a boundary inside which one model and one language apply consistently. Inside the boundary, "Product" means exactly one thing. Outside, other contexts are free to define their own "Product" with different data and rules. A context is usually owned by one team, and has its own code module or service, and its own schema or database.

How do you find the boundaries? Look for these signals:

  • The language changes. The same word means different things, or different people use different words for the same thing.
  • The rules change. Pricing rules and packing rules never touch the same data.
  • The people change. Different departments, different experts, different teams.
  • The rate of change differs. The pricing engine changes weekly, while the address book hasn't changed in years.
  • Consistency needs differ. If two pieces of data must be consistent immediately, they probably belong in the same context. If "a few seconds later" is fine, they can be separated.

Recognize the missing boundary

  • One class or table has dozens of nullable columns, each used by a different team.
  • Meetings about "the order model" need people from four departments.
  • A change to a field breaks a report in a module you've never heard of.
  • Code is full of if (type == "B2B") branches that select a completely different set of rules.

A bounded context is not necessarily a microservice. In a modular monolith (see Application Architecture Styles), each context is a module with its own namespace and schema, and the boundary is enforced by architecture tests. Splitting into services is a later, separate decision, covered in Services, Messaging & Events.

Context maps: how contexts relate

Contexts must talk to each other: Sales needs product names from Catalog, Billing needs to know what was sold. A context map shows each relationship, and, more importantly, who has to adapt when the other side changes. Each relationship has an upstream side (whose model influences the other) and a downstream side (which depends on it).

Pattern What it means Who pays when upstream changes Use when
Shared kernel Two contexts share a small piece of model (a library or schema) and change it together both teams, every time: coordinated releases two closely cooperating teams, very small stable shared part (Address, Money)
Customer / supplier Downstream's needs feed into upstream's planning; upstream agrees not to break them upstream, by negotiating and versioning teams in the same organisation with aligned goals
Conformist Downstream adopts the upstream model as-is downstream: every rename ripples through its code upstream won't negotiate and its model is good enough
Anticorruption layer (ACL) Downstream translates the upstream model into its own model at the edge downstream, but only inside the translator upstream is legacy, external or messy; protects your core
Open host service (OHS) Upstream offers a stable, documented protocol for everyone upstream maintains versions many consumers; a public API
Published language (PL) A shared, documented exchange format (JSON schema, Avro, OIDC) nobody, as long as versions are respected almost always paired with OHS and integration events

Context maps describe politics as well as code

"Conformist" is often not a technical choice. It is what happens when the upstream team is a vendor, or another department that doesn't take requests. Drawing the map honestly ("we are conformist to the ERP, and it hurts") is how you justify an ACL to management.

The anticorruption layer, up close

An anticorruption layer is a translator that sits at the edge of your context. It is the only code that knows the foreign model. Everything it hands to your domain uses your types and your language. Legacy oddities such as status letters, amounts in minor units, padded strings and magic defaults are handled once, in one place.

The ACL is the Adapter pattern (often with a Facade in front) applied at a context boundary. In hexagonal terms it lives in an outbound adapter: the domain declares a port such as ILegacyCustomerSource in its own language, and the ACL implements it.

// Domain port, in Sales' language.
public interface IImportedOrders { Task<ImportedOrder> GetAsync(LegacyOrderNo no, CancellationToken ct); }

// ACL: the only class that knows the ERP's model.
public sealed class ErpOrderTranslator(ErpClient erp) : IImportedOrders
{
    private static readonly Dictionary<string, CustomerStatus> Status = new()
    { ["A"] = CustomerStatus.Active, ["S"] = CustomerStatus.Suspended, ["C"] = CustomerStatus.Closed };

    public async Task<ImportedOrder> GetAsync(LegacyOrderNo no, CancellationToken ct)
    {
        ErpOrderRecord r = await erp.FetchAsync(no.Value, ct);            // foreign model
        if (!Status.TryGetValue(r.STAT, out var status))
            throw new AclTranslationException($"Unknown STAT '{r.STAT}' for order {no}");
        var ccy = Currency.FromCode(r.CCY ?? throw new AclTranslationException("CCY missing"));
        return new ImportedOrder(
            new CustomerId($"C-{int.Parse(r.CUST_NO)}"),
            status,
            Money.FromMinorUnits(r.AMT, ccy),                            // knows JPY has 0 decimals
            r.SHIP_CD switch { "EXP" => DeliverySpeed.Express, _ => DeliverySpeed.Standard },
            string.IsNullOrWhiteSpace(r.NOTE) ? null : new DeliveryNote(r.NOTE.Trim()));
    }
}

Test the ACL with recorded payloads

The ACL is where integration surprises show up, so test it with real (anonymised) payloads captured from the upstream system: a JPY order, a blank note, an unknown status. These tests document the foreign model better than its own documentation does, and they fail loudly when upstream changes.

Tactical design: the building blocks

Once the boundaries are drawn, tactical design shapes the code inside one context. The building blocks fit together like this:

Value object defined entirely by its attributes no no (replace it) Money, Email, DateRange, Address
Entity has a thread of identity that survives changes yes yes, through methods Customer, Payment, OrderLine
Aggregate a cluster of objects changed together under one root, guarding its invariants via its root yes, via the root Order + its lines
Domain event a fact that happened in the domain, past tense an event id no OrderPlaced, PaymentRefunded
Repository a collection-like interface to load and save whole aggregates – – IOrderRepository
Domain service domain logic that doesn't belong to one entity no stateless TransferFunds, PricingPolicy
Application service orchestrates a use case: load, call domain, save, publish no stateless PlaceOrderHandler
Factory creates complex aggregates in a valid state – – Order.Create(...), QuoteFactory
Specification a named, combinable business predicate no no IsOverdue, IsPremiumCustomer

Entities vs value objects

The first tactical question about any concept is: does it have an identity that matters, or is it just a value?

  • A value object is defined by its attributes. Ten euros is ten euros, and you don't care which ten-euro object you hold. Two value objects with the same attributes are equal and interchangeable. They are immutable: to "change" one, you make a new one.
  • An entity has an identity that persists while its attributes change. Payment P-17 is the same payment before and after a partial refund. Two entities are equal if and only if their ids are equal, even if every other field differs.

The same real-world thing can be either, depending on the context. In an online shop, an Address is a value object: if the customer moves, you replace it. In the postal service's context, an address is an entity with an id, a delivery round and a history.

Pick a kind below and watch == and the shared reference c = a. The mutable class is the trap most code falls into by default: it compares like an entity (by reference) and can be changed by anyone holding a reference.

Value object

  • equality: all attributes
  • immutable: operations return new instances
  • validates itself in the constructor, so an invalid one never exists
  • safe to share, cache and use as a dictionary key
  • no table of its own: stored as columns of its owner (EF owned types, JPA @Embeddable)
  • most of your domain types should be these

Entity

  • equality: id only
  • mutable, but only through intention-revealing methods (Refund, not set Refunded)
  • identity assigned at creation, ideally by the domain (UUID or ULID), not by the database
  • has a lifecycle: created, changed, archived
  • usually part of an aggregate; the root is the only one referenced from outside
  • keep them few and small

The same pair in five languages

Each tab defines a Money value object (validated, immutable, structural equality, currency-safe arithmetic) and a Payment entity (identity equality, a guarded Refund method). The interesting part is how each language gets value semantics:

// record = value equality + ToString for free. Get-only properties mean even `with` can't skip validation.
public sealed record Money
{
    public decimal Amount { get; }
    public string Currency { get; }

    public Money(decimal amount, string currency)
    {
        if (amount < 0) throw new ArgumentOutOfRangeException(nameof(amount), "Money cannot be negative");
        if (currency is not { Length: 3 }) throw new ArgumentException("ISO 4217 code expected", nameof(currency));
        Amount = decimal.Round(amount, 2);
        Currency = currency.ToUpperInvariant();
    }

    public static Money Zero(string currency) => new(0, currency);
    public Money Plus(Money other) => new(Amount + Same(other).Amount, Currency);
    public Money Minus(Money other) => new(Amount - Same(other).Amount, Currency);   // throws if negative
    private Money Same(Money o) =>
        o.Currency == Currency ? o : throw new InvalidOperationException($"{Currency} vs {o.Currency}");
    public override string ToString() => $"{Amount:0.00} {Currency}";
}

// Entity: equality by id only; state changes through a guarded method.
public sealed class Payment : IEquatable<Payment>
{
    public PaymentId Id { get; }
    public Money Captured { get; }
    public Money Refunded { get; private set; }

    public Payment(PaymentId id, Money captured)
    {
        Id = id;
        Captured = captured;
        Refunded = Money.Zero(captured.Currency);
    }

    public void Refund(Money amount)
    {
        var total = Refunded.Plus(amount);
        if (total.Amount > Captured.Amount)
            throw new DomainException($"Cannot refund {total} of a {Captured} payment");
        Refunded = total;
    }

    public bool Equals(Payment? other) => other is not null && other.Id == Id;
    public override bool Equals(object? obj) => Equals(obj as Payment);
    public override int GetHashCode() => Id.GetHashCode();
}

public sealed class DomainException(string message) : Exception(message);

// record = final fields, equals/hashCode/toString over all components.
public record Money(BigDecimal amount, Currency currency) {
    public Money {                                   // compact constructor: validate + normalise
        Objects.requireNonNull(currency, "currency");
        if (amount.signum() < 0) throw new IllegalArgumentException("Money cannot be negative");
        // BigDecimal.equals compares scale: 10.0 != 10.00. Normalise so equal money is equal.
        amount = amount.setScale(currency.getDefaultFractionDigits(), RoundingMode.HALF_EVEN);
    }
    public static Money zero(Currency c) { return new Money(BigDecimal.ZERO, c); }
    public Money plus(Money o)  { return new Money(amount.add(same(o).amount), currency); }
    public Money minus(Money o) { return new Money(amount.subtract(same(o).amount), currency); }
    private Money same(Money o) {
        if (!o.currency.equals(currency)) throw new IllegalArgumentException(currency + " vs " + o.currency);
        return o;
    }
}

public record PaymentId(UUID value) {
    public static PaymentId newId() { return new PaymentId(UUID.randomUUID()); }
}

// Entity: equality by id only. (With JPA, assign the id here, not with @GeneratedValue,
// or two new entities are "equal" with null ids and Sets misbehave.)
public final class Payment {
    private final PaymentId id;
    private final Money captured;
    private Money refunded;

    public Payment(PaymentId id, Money captured) {
        this.id = Objects.requireNonNull(id);
        this.captured = captured;
        this.refunded = Money.zero(captured.currency());
    }

    public void refund(Money amount) {
        Money total = refunded.plus(amount);
        if (total.amount().compareTo(captured.amount()) > 0)
            throw new DomainException("Cannot refund " + total + " of " + captured);
        refunded = total;
    }

    public PaymentId id() { return id; }
    public Money refunded() { return refunded; }
    @Override public boolean equals(Object o) { return o instanceof Payment p && p.id.equals(id); }
    @Override public int hashCode() { return id.hashCode(); }
}

from __future__ import annotations
from dataclasses import dataclass, field
from decimal import Decimal
from uuid import UUID, uuid4


class DomainError(Exception):
    pass


@dataclass(frozen=True, slots=True)          # frozen: immutable, __eq__ and __hash__ over all fields
class Money:
    amount: Decimal
    currency: str

    def __post_init__(self) -> None:          # also runs for dataclasses.replace(...)
        if self.amount < 0:
            raise ValueError("Money cannot be negative")
        if len(self.currency) != 3:
            raise ValueError("ISO 4217 code expected")
        object.__setattr__(self, "amount", Decimal(self.amount).quantize(Decimal("0.01")))
        object.__setattr__(self, "currency", self.currency.upper())

    @staticmethod
    def zero(currency: str) -> Money:
        return Money(Decimal(0), currency)

    def plus(self, other: Money) -> Money:
        return Money(self.amount + self._same(other).amount, self.currency)

    def minus(self, other: Money) -> Money:
        return Money(self.amount - self._same(other).amount, self.currency)

    def _same(self, other: Money) -> Money:
        if other.currency != self.currency:
            raise ValueError(f"{self.currency} vs {other.currency}")
        return other


@dataclass(frozen=True, slots=True)
class PaymentId:
    value: UUID = field(default_factory=uuid4)


class Payment:                                # entity: plain class, equality by id
    def __init__(self, id: PaymentId, captured: Money) -> None:
        self.id = id
        self.captured = captured
        self._refunded = Money.zero(captured.currency)

    @property
    def refunded(self) -> Money:              # read-only from outside
        return self._refunded

    def refund(self, amount: Money) -> None:
        total = self._refunded.plus(amount)
        if total.amount > self.captured.amount:
            raise DomainError(f"cannot refund {total.amount} of {self.captured.amount}")
        self._refunded = total

    def __eq__(self, other: object) -> bool:
        return isinstance(other, Payment) and other.id == self.id

    def __hash__(self) -> int:
        return hash(self.id)

// Value object: private constructor + factory validation, readonly fields, frozen instance.
// === compares references in JS, so value equality needs an explicit equals().
export class Money {
  private constructor(readonly minor: number, readonly currency: string) {
    Object.freeze(this);
  }

  static of(minor: number, currency: string): Money {
    if (!Number.isSafeInteger(minor) || minor < 0) throw new RangeError("Money must be a non-negative integer of minor units");
    if (!/^[A-Z]{3}$/.test(currency)) throw new RangeError(`currency ${currency}: ISO 4217 code expected`);
    return new Money(minor, currency);
  }

  static zero(currency: string): Money { return Money.of(0, currency); }
  plus(o: Money): Money { return Money.of(this.minor + this.same(o).minor, this.currency); }
  minus(o: Money): Money { return Money.of(this.minor - this.same(o).minor, this.currency); }
  equals(o: Money): boolean { return this.minor === o.minor && this.currency === o.currency; }
  toString(): string { return `${(this.minor / 100).toFixed(2)} ${this.currency}`; }   // also a safe Map key

  private same(o: Money): Money {
    if (o.currency !== this.currency) throw new Error(`${this.currency} vs ${o.currency}`);
    return o;
  }
}

How the languages differ, and why:

  • C# and Java records generate equality, hashing and ToString from the components. That is exactly what a value object needs. Validation goes in the (compact) constructor. In C#, avoid init setters on value objects: with { Amount = -5 } would bypass your constructor. Get-only properties make with a compile error instead.
  • Java's BigDecimal.equals compares scale, so 10.0 and 10.00 are not equal. Normalising the scale in the compact constructor is what makes "ten euros equals ten euros" true.
  • Python's @dataclass(frozen=True) gives __eq__ and __hash__ over all fields and blocks assignment. Normalising inside __post_init__ needs object.__setattr__. dataclasses.replace() re-runs __post_init__, so copies are validated too.
  • Go structs compare with == field by field when all fields are comparable, so a small value struct is a value object almost for free. Unexported fields and value receivers stop outside packages from mutating it. Entities use pointer receivers and an explicit SameAs, because neither form of == means "same id".
  • TypeScript has no value equality at all: === compares references, and Map keys use reference identity for objects. Add equals() and a canonical toString() key. readonly is compile-time only, so Object.freeze adds the runtime guarantee. Branded types (string & {__brand}) stop a CustomerId being passed where a PaymentId is expected.

Primitive obsession: the value objects you didn't write

void Transfer(string from, string to, decimal amount, string currency) compiles happily with the accounts swapped, with a negative amount, or with "eur " as the currency. Each primitive that has rules (an IBAN, an email, a percentage, a quantity) is a missing value object. Write the small class once; every method that takes it gets the validation for free. Types, Immutability & Domain Modelling goes deeper on this.

Storing value objects

Value objects don't need their own table. Map them as columns of their owner: EF Core OwnsOne / complex types, JPA @Embeddable, SQLAlchemy composite(). In Go and TypeScript, map them explicitly in the repository. Collections of value objects can be stored as JSON columns or a child table without its own identity in the domain.

Aggregates: consistency boundaries

Some rules involve more than one object. "The order total must not exceed the customer's credit limit" involves every order line. "No more than 99 of one item" and "no changes after submit" also cover the whole order. If any code can reach in and change an OrderLine directly, nothing can guarantee those rules.

An aggregate is a cluster of entities and value objects that is treated as one unit for data changes. One entity is the aggregate root: the only member that outside code may hold a reference to, and the only way in. The root checks every invariant before any change is accepted. A repository loads and saves the whole aggregate, in one transaction.

The aggregate rules (after Vaughn Vernon): (1) protect true invariants inside one boundary; (2) design small aggregates; (3) reference other aggregates by id only; (4) change one aggregate per transaction, and use eventual consistency (domain events) to update the others.

    def add_line(self, sku: Sku, qty: Quantity, unit_price: Money) -> None:

        merged = existing.quantity.plus(qty) if existing else qty     # Quantity enforces 1..99
        self._ensure_within_limit(self.total.plus(unit_price.times(qty.value)))

        self._events.append(OrderSubmitted(self.id, self.customer_id, self.total))

    def pull_events(self) -> list[DomainEvent]:
        events, self._events = self._events, []

        if self.status is not OrderStatus.DRAFT:

func (o *Order) AddLine(sku Sku, qty Quantity, unitPrice Money) error {
    if err := o.ensureDraft(); err != nil {
        return err
    }
    idx := slices.IndexFunc(o.lines, func(l OrderLine) bool { return l.sku == sku })
    merged := qty
    if idx >= 0 {
        var err error
        if merged, err = o.lines[idx].qty.Plus(qty); err != nil { // Quantity enforces 1..99
            return err
        }
    }
    newTotal, err := o.Total().Plus(unitPrice.Times(qty.Value()))
    if err != nil {
        return err
    }
    if newTotal.Minor() > o.creditLimit.Minor() {
        return fmt.Errorf("%w: total %d exceeds limit %d", ErrRuleViolated, newTotal.Minor(), o.creditLimit.Minor())
    }
    if idx >= 0 {
        o.lines[idx].qty = merged
    } else {
        o.lines = append(o.lines, OrderLine{sku: sku, qty: merged, unitPrice: unitPrice})
    }
    o.events = append(o.events, OrderLineAdded{OrderID: o.id, Sku: sku, Qty: qty.Value()})
    return nil
}

func (o *Order) Submit() error {
    if err := o.ensureDraft(); err != nil {
        return err
    }
    if len(o.lines) == 0 {
        return fmt.Errorf("%w: an empty order cannot be submitted", ErrRuleViolated)
    }
    o.status = Submitted
    o.events = append(o.events, OrderSubmitted{OrderID: o.id, CustomerID: o.customerID, Total: o.Total()})

}

How big should an aggregate be?

The aggregate boundary is a trade-off. A big aggregate makes every rule inside it strictly consistent, but every change locks (or version-checks) the whole thing, and every load reads all of it. Small aggregates load fast and rarely conflict, but rules that span them become eventually consistent: enforced a moment later by a policy reacting to events.

Heuristics for sizing:

  • Start with the root alone and add an entity only when a true invariant requires it. "Lines must sum to ≤ the limit" justifies lines in the order; "the customer has orders" does not justify orders in the customer.
  • Watch for unbounded collections. Customer.Orders, Forum.Posts and Conference.Registrations grow forever. They are almost always separate aggregates referencing the parent by id.
  • Count your conflicts. If concurrent users regularly get concurrency exceptions on the same aggregate, it is too big, or the rule it protects should become eventual.
  • Ask whether the rule is real. Many "invariants" turn out to be reporting needs or rules the business already handles manually, such as overbooking.

Domain events vs integration events

A domain event is a fact the business cares about, named in the past tense in the ubiquitous language: OrderSubmitted, SeatRegistered, PaymentRefunded. Aggregates record events when their state changes, and other parts of the system react to them. This is how "one aggregate per transaction" still lets several aggregates cooperate.

There are two kinds of event, and mixing them up is a classic source of coupling:

Domain event Integration event
Audience Handlers inside the same bounded context Other bounded contexts or services
Transport In-process (mediator, event bus, function call) Message broker (Kafka, RabbitMQ, Service Bus, SNS/SQS)
Shape Rich: may hold value objects and domain types Flat, versioned, serialisable DTO; part of the published language
Timing Dispatched before or right after commit, in the same unit of work Published after commit, reliably, through an outbox

When you publish is the subtle part. Choose a publishing strategy and a failure, and see what the database and the consumers end up believing:

The dual-write problem

Writing to the database and to a broker are two separate systems, and there is no transaction that spans both. Publish first and a rollback leaves a "ghost" event for an order that doesn't exist. Commit first and a crash before the publish loses the event forever. The outbox turns the two writes into one: the event is a row committed with the order, and publishing becomes a retryable background job. The cost is at-least-once delivery, so consumers must be idempotent.

class UnitOfWork:
    def __init__(self, session: Session) -> None:
        self.session, self.seen = session, []

    def commit(self) -> None:
        for root in self.seen:                       # aggregates touched in this unit of work
            for event in root.pull_events():
                for handler in _handlers[type(event)]:
                    handler(event, self.session)     # same session, same transaction
        self.session.commit()

// The application service pulls events and dispatches them inside the same *sql.Tx.
type EventHandler func(ctx context.Context, tx *sql.Tx, e DomainEvent) error

type Dispatcher struct{ handlers map[string][]EventHandler }

func (d *Dispatcher) On(name string, h EventHandler) { d.handlers[name] = append(d.handlers[name], h) }

func (d *Dispatcher) Dispatch(ctx context.Context, tx *sql.Tx, events []DomainEvent) error {
    for _, e := range events {
        for _, h := range d.handlers[e.EventName()] {
            if err := h(ctx, tx, e); err != nil {
                return err // the caller rolls back the whole transaction
            }
        }
    }
    return nil
}

Before or after commit?

Handlers that must be atomic with the change (outbox rows, updating another table in the same database) run before commit, inside the transaction. Handlers with external side effects (emails, HTTP calls, cache invalidation) run after commit, or better, from the outbox, so they never act on a change that was rolled back.

Repositories: one per aggregate root

A repository gives the domain the illusion of an in-memory collection of aggregates: Get(id), Add(order), and nothing else unless a use case needs it. There is one repository per aggregate root. There is no OrderLineRepository, because a line only exists inside its order. The interface lives in the domain (it is a port); the implementation with EF Core, JPA, SQLAlchemy or SQL lives in infrastructure (an adapter). The generic repository over an ORM

IRepository<T> with GetAll(), Find(Expression<…>), Update(T) and Delete(T) for every table is a leaky wrapper. It hides nothing (EF Core's DbSet and Spring Data are already repositories and units of work), it exposes OrderLine as if it were an aggregate, and Find(predicate) lets query logic leak everywhere. Write narrow, aggregate-specific repositories for the write side. For reads, skip the repository and query directly (a Dapper or SQL query, or a projection) into DTOs.

Domain services vs application services

Not every behaviour belongs on an entity. When an operation involves several aggregates, or a policy that doesn't naturally belong to any one of them, put it in a domain service: a stateless object named in the ubiquitous language. Don't confuse it with the application service, which orchestrates a use case and contains no business rules.

Factories and specifications

Two more tactical patterns appear often, though neither is needed in every codebase:

  • A factory builds a valid aggregate when construction is complex: several value objects to assemble, a policy to consult, or a choice of subtype. Often it is just a static method on the root (Order.Start(...)). Use a separate factory class when creation needs dependencies. Reconstitution from the database is a different job: it skips the creation rules and raises no events.
  • A specification names a business predicate so you can reuse it for validation, selection and querying: IsEligibleForFreeShipping, OverdueInvoice. It is worth having when the same rule appears in two places, such as a domain check and a database query.

}

Anemic vs rich domain model

An anemic domain model has entities that are bags of getters and setters, with all the rules in "service" classes. It looks object-oriented, but it is procedural code with an extra mapping step. The result: rules get duplicated across services, and any code path can create an invalid state. You saw this in the "anemic" mode of the aggregate visualizer above, where every bad operation went through.

Anemic

public class Order { public List<OrderLine> Lines { get; set; } = new(); public string Status { get; set; } = "Draft"; }

public class OrderService
{
    public void AddLine(Order o, string sku, int qty, decimal price)
    {
        if (o.Status != "Draft") throw new InvalidOperationException();
        o.Lines.Add(new OrderLine { Sku = sku, Qty = qty, Price = price });   // no qty or limit check here...
    }
}
public class ImportJob { void Fix(Order o) => o.Lines[0].Qty = 0; }       // ...and nothing stops this
  • Rules live in whichever service someone remembered to put them in.
  • Every caller must know the order of calls and checks.
  • Tests have to set up services to test one rule.

Rich

public sealed class Order
{
    private readonly List<OrderLine> _lines = [];
    public IReadOnlyList<OrderLine> Lines => _lines;
    public OrderStatus Status { get; private set; }

    public void AddLine(Sku sku, Quantity qty, Money price) { /* I1–I5 checked here */ }
    public void Submit() { /* ... */ }
}
// order.Lines[0].Qty = 0;  -> does not compile
  • Rules live in one place, next to the data they protect.
  • Invalid states are unrepresentable or rejected.
  • Rules are unit-tested with plain objects and no mocks.

Anemic is not always wrong

For a CRUD screen with no rules beyond "required" and "max length", a plain data class with validation attributes is the right model. Calling it anemic only makes sense when there are business rules it fails to protect. The smell is rules outside the object, duplicated or forgotten, not "a class without methods".

Event storming: discovering the model

Event storming (Alberto Brandolini) is a workshop technique for discovering a domain with the people who know it. Everyone stands at a long wall of paper. Each sticky-note colour has a meaning, and the group builds the story of the business process as a timeline of domain events: orange notes in the past tense.

A session typically runs in phases:

  1. Chaotic exploration. Everyone writes the events they know, in the past tense, in any order.
  2. Timeline. Sort them left to right; remove duplicates; argue about the words (that argument is ubiquitous language work).
  3. Hot spots. Mark every disagreement, unknown or pain point in pink. Do not resolve them yet.
  4. Commands and actors. What triggered each event? Who or what issued it?
  5. Policies. Which events cause commands automatically? ("Whenever payment fails, release the stock.")
  6. Aggregates and boundaries. Which thing accepts the command and protects the rule? Where does the language change? Draw the context boundaries.

When DDD is overkill

The tactical patterns have a cost: more types, more mapping, more ceremony. That cost only pays off where the domain logic is complex and changing. Strategic design (contexts, language) is cheap and helps almost everyone. The full tactical toolkit is for your core domain.

Answer five questions about a system you know, and see which level of DDD the answers suggest:

Situation Recommendation
CRUD admin screen, reporting app, ETL job Skip tactical DDD. Use a transaction script or active record and thin endpoints. Still use clear names.
Generic subdomain (auth, email, invoicing PDFs) Buy or adopt a library. Wrap it behind an ACL. Do not model it.
Supporting subdomain with moderate rules DDD-lite: value objects, a few rich entities, a clear module boundary. No full aggregate or event machinery.
Core domain, complex rules, domain experts available Full DDD: ubiquitous language, aggregates, domain events, bounded contexts, event storming.
Several teams, one large product Strategic DDD first (contexts and a context map), even if each context uses simple code inside.
No access to domain experts The modelling part of DDD will be guesswork. Start with strategic boundaries; revisit when you can learn the domain.

Common pitfalls

Tactical patterns without strategic design

Teams add AggregateRoot, ValueObject and IRepository<T> base classes everywhere but never draw a context boundary, so there is still one giant Customer model. The patterns add ceremony without delivering the benefit. Start with the boundaries and the language.

One model to rule them all

Trying to make a single Product class serve Catalog, Sales, Warehouse and Billing produces a class with 80 nullable properties and rules that contradict each other. Different contexts may use the same word with different models. That is the whole point of bounded contexts.

Huge aggregates

Customer containing Orders containing Lines containing Shipments: every operation loads megabytes and conflicts with every other. Split along true invariants; reference by id; make cross-aggregate rules eventual.

Changing two aggregates in one transaction "just this once"

It works until the two aggregates move to different databases or services, or until the lock contention shows up in production. Use a domain event and a handler, or ask whether the boundary is wrong.

Leaking domain events as integration events

Publishing your internal OrderLineAdded (with its value objects) straight to Kafka makes every internal refactoring a breaking change for other teams. Translate to a flat, versioned integration event at the boundary.

Persistence driving the model

Starting from the database schema and generating entities gives you tables-as-classes and an anemic model. Design the aggregate around behaviour and invariants first, then map it. Modern ORMs (EF Core owned types and backing fields, JPA embeddables, SQLAlchemy imperative mapping) can map a rich model without public setters.

Best-practice checklist

  • Build a glossary with domain experts, and use the same words in code, tests, APIs and conversations.
  • Classify your subdomains as core, supporting or generic; invest modelling effort only in the core.
  • Draw a context map; make every relationship (ACL, conformist, open host, shared kernel) an explicit decision.
  • Put an anti-corruption layer in front of every legacy or third-party model you don't control.
  • Prefer value objects; make them immutable, self-validating and compared by value.
  • Keep aggregates small; reference other aggregates by id only.
  • Change one aggregate per transaction; use domain events for the rest.
  • Use optimistic concurrency (a version column) on every aggregate root.
  • Keep collections private; expose intention-revealing methods instead of setters.
  • Define one repository per aggregate root, with the interface in the domain and a narrow API.
  • Keep application services free of business rules; move cross-aggregate rules into domain services.
  • Separate domain events (internal) from integration events (versioned contracts, published via an outbox).
  • Use plain queries and DTOs for reads; don't load aggregates to render lists.
  • Skip tactical DDD for CRUD and generic subdomains.

Self-check

1. What is a bounded context, and why can "Product" mean different things in two of them?

A bounded context is an explicit boundary (usually owned by one team and often one deployable or module) inside which a model and its language are consistent. Catalog's Product (descriptions, images, categories) and Warehouse's StockItem (bin location, quantity on hand) have different rules and change for different reasons. Forcing them into one class couples teams and creates contradictions; separate models linked by an id avoid that.

2. Is `Address` an entity or a value object?

It depends on the context. For an order, the shipping address is a value object: two identical addresses are interchangeable, and you replace it rather than mutate it. For a postal service that tracks delivery points over time, an address may have its own identity and lifecycle, making it an entity. The question to ask is: "do we care which one it is, or only what it is?"

3. Two users add seats to the same conference at the same moment, and the save of the second fails with a concurrency exception. Is that a bug?

No. It is optimistic concurrency doing its job: both loaded version 57, the first saved version 58, and the second save matched zero rows. The handler should reload and retry (or report a conflict). If this happens often, the aggregate is too big. Consider making each session its own aggregate, with the venue limit enforced by a policy.

4. Why not publish the integration event directly to the broker after `SaveChanges` succeeds?

Because a crash or broker outage between the commit and the publish loses the event forever, and other services never hear about the order. Publishing before the commit has the opposite problem: a rollback leaves a ghost event. The outbox writes the event in the same transaction as the order and publishes it later with retries, which gives at-least-once delivery. Consumers must therefore be idempotent.

5. You need an `OrderLineRepository` to update one line's quantity. What is wrong with that?

OrderLine is not an aggregate root, so it must not have a repository. Changing a line directly bypasses the order's invariants (the credit limit, "no changes after submit"). Load the Order and call order.ChangeQuantity(sku, qty); the repository saves the whole aggregate.

6. A handler contains `if (customer.Tier == Gold && order.Total > 100) discount = 10%`. Where should that rule live?

It is a business rule spanning two aggregates, so it belongs in a domain service such as PricingPolicy.DiscountFor(tier, order). The application service only orchestrates: load both aggregates, call the policy, apply the result to the order, save. The rule can then be unit-tested with no infrastructure.

7. Your team is building an internal admin tool that edits reference data. A colleague proposes aggregates, domain events and an event store. What do you say?

That is overkill. There are no complex invariants to protect, so tactical DDD would only add mapping and ceremony. Use a simple CRUD approach with validation. Keep the good habits that are cheap (clear names, a module boundary) and save the full toolkit for the core domain.
