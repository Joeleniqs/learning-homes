API Security: AuthN, AuthZ & Rate Limiting

OAuth 2.0 and OIDC flows animated, JWT validation step by step, scopes vs roles vs policies, API keys, mTLS and rate-limiting algorithms.

Intermediate → Advanced~60 min studyBuilds on: REST API Design, Middleware Patterns & OrderingUpdated 2026-11-03

The problem: a valid token is not permission

An online shop ships a mobile app. Its API checks every request carefully: no token gives a 401, an expired token gives a 401, and a forged token gives a 401. The penetration test passes. Six months later a customer notices that GET /orders/1018 works while signed in as themselves, even though order 1018 is someone else's. They change the number again, and again. A script then downloads two million orders with names and home addresses, using one perfectly valid token.

Nothing in that API was broken in the way people usually picture "security". The tokens were real, and so were the signatures. The API answered the question who are you? correctly, and then never asked the next one: is this order yours? That missing check is called Broken Object Level Authorization (BOLA). It's number one on the OWASP API Security Top 10, and it causes more API data breaches than anything else.

The rule

Every request must pass several different checks, each answering its own question:

  • Authentication: who is calling?
  • Endpoint authorization: may this caller do this kind of thing?
  • Resource authorization: may they do it to this object?
  • Abuse limits: are they asking too often?

A token answers only the first question. Your code has to answer the other three, on every request.

The layers stack up in your middleware pipeline like this. The cheap, general checks run first. The specific checks that need data run last, inside the handler.

Play with that pipeline below. Try the other-tenant order with the response set to 403 and then 404, and notice that one of them confirms the order exists. Then compare "Bob reads Alice's order" with and without the manager role.

Authentication vs authorization: 401, 403 or 404

The two words are confusingly similar. HTTP makes the confusion worse by naming status 401 "Unauthorized" when it actually means unauthenticated. Keep them apart:

Authentication (AuthN) Authorization (AuthZ)
Question Who is calling, and can they prove it? Is this caller allowed to do this, to this?
Input Credentials: token, certificate, key The authenticated identity, the operation, the resource, context
Who does it Mostly delegated to an identity provider; your API only validates the result Your API. Always. Only you know who owns order 42
Fails with 401 + WWW-Authenticate: Bearer (try again with credentials) 403 (you're known, the answer is no), or 404 to hide that it exists
Typical bug Accepting tokens meant for another API Checking the role but not the owner (BOLA)

The WWW-Authenticate header on a 401 is required, and RFC 6750 defines error codes for it. A good client uses them to decide what to do next:

HTTP/1.1 401 Unauthorized
WWW-Authenticate: Bearer realm="orders", error="invalid_token", error_description="The token expired"

HTTP/1.1 403 Forbidden
WWW-Authenticate: Bearer error="insufficient_scope", scope="orders.write"

invalid_token means "get a new token": refresh it, or sign the user in again. insufficient_scope means "this token is genuine but too narrow". The client must ask the user to consent to more, and retrying with the same token is pointless.

403 or 404 for someone else's object?

A 403 confirms the object exists. That's fine when the caller is allowed to know it exists, for example a colleague in the same tenant. Across tenants, or for anything whose existence is itself sensitive (a user's email address, a medical record id), answer 404, exactly as if the object weren't there. GitHub does this for private repositories you can't see. Whichever you choose, make the 404 indistinguishable from a real one: same body, same headers, and roughly the same timing.

OAuth 2.0 and OpenID Connect, without the fog

OAuth 2.0 (RFC 6749) is a framework for delegated authorization: a user lets an app call an API on their behalf without giving the app their password. OpenID Connect (OIDC) is a thin layer on top that adds authentication: an ID token that tells the app who signed in. Four parties are involved:

A grant type (or flow) is a way for a client to get a token. Today only a few are worth knowing; the others are deprecated by the OAuth 2.0 Security Best Current Practice (RFC 9700) and the upcoming OAuth 2.1. Step through each one below. The legend colours show which messages carry a secret proof and which bring tokens back.

Who is calling Flow Notes
A user, through a web app with a server side Authorization code + PKCE, confidential client The server keeps tokens; the browser gets a session cookie
A user, through a SPA Auth code + PKCE, ideally via a BFF (backend for frontend) A BFF keeps tokens out of JavaScript entirely (see CSRF below)
A user, through a mobile or desktop app Auth code + PKCE with the system browser Never an embedded web view: the app could read the password
A device with no browser (TV, CLI) Device authorization grant (RFC 8628) "Go to example.com/device and enter ABCD-EFGH"
A service, no user Client credentials Prefer a certificate or managed identity over a client secret
An API calling another API for the same user On-behalf-of / token exchange (RFC 8693) Never forward the incoming token
~~Implicit grant~~ Deprecated Tokens in the URL fragment leak through history and Referer headers
~~Resource owner password~~ Deprecated The app sees the password, which defeats the point; it also can't do MFA

Three kinds of token come out of these flows, and mixing them up is a classic bug:

Access token

  • Audience: your API (aud = api://orders).
  • Purpose: authorizes calls. The API validates it.
  • Lifetime: short, from minutes to an hour.
  • Format: JWT or opaque. Clients should treat it as opaque and never parse it.

ID token (OIDC)

  • Audience: the client app (aud = client_id).
  • Purpose: tells the app who signed in.
  • Never send it to an API as a bearer token. Its audience is wrong, and it carries no scopes.

Refresh token

  • Audience: the authorization server only.
  • Purpose: gets new access tokens without bothering the user.
  • Lifetime: long. Treat it like a password. Rotate it on every use, or bind it to the client.

PKCE: why a stolen code is worthless

In the authorization code flow the code comes back through the browser, in a redirect URL. That's the weak link. On a phone, another app can register the same custom URL scheme and receive the redirect. On the web, codes leak into logs, Referer headers and browser history. PKCE (Proof Key for Code Exchange, RFC 7636) binds the code to the app that asked for it:

  1. The app makes a random secret, the code_verifier, and sends only its SHA-256 hash, the code_challenge, through the browser.
  2. When it redeems the code, it sends the verifier over the direct back channel.
  3. The authorization server hashes the verifier and compares the result with the challenge it stored. A thief has the code and maybe the challenge, but not the verifier.

The visualizer below runs real SHA-256. The default verifier is the example from RFC 7636, and it produces the RFC's challenge E9Melhoa2OwvFrEMTJguCHaoeK1t8URWbuGJSstw-cM. Switch the method to plain with the "attacker sees the URL" attack and watch it fail. Then try "no PKCE".

import base64, hashlib, secrets

def b64url(b: bytes) -> str:
    return base64.urlsafe_b64encode(b).rstrip(b"=").decode()

verifier = b64url(secrets.token_bytes(32))                   # 43 chars, keep it in memory
challenge = b64url(hashlib.sha256(verifier.encode()).digest())
# /authorize?...&code_challenge={challenge}&code_challenge_method=S256
# later: POST /token  grant_type=authorization_code&code=...&code_verifier={verifier}

Use PKCE for every client, including confidential ones

PKCE was designed for mobile apps, but RFC 9700 now recommends it for all clients using the authorization code flow, because it also stops authorization code injection: an attacker pasting their own code into your callback. Use S256 only, and validate state (or rely on PKCE plus the OIDC nonce) on the redirect. In practice you won't write any of this yourself: the MSAL libraries, Spring Security's OAuth2 client, Authlib and oidc-client-ts all do it for you. Learn it so that you can recognise when it's missing.

JWT anatomy: three base64url strings and a dot

Most access tokens your API receives are JSON Web Tokens (JWT, RFC 7519), signed as a JWS. A JWT is three base64url segments joined by dots: a header, a payload and a signature. Anyone can decode the first two (they're encoded, not encrypted), so never put anything secret in them.

Claim Meaning Check
iss Issuer: who minted it Exactly equals your configured issuer (per tenant if multi-tenant)
aud Audience: who it's for Contains your API's identifier. Skipping this lets any token from the same issuer in
exp / nbf Valid until / not before (Unix seconds) Now is inside the window, with a small clock skew (30–60 s, not the 5 min some defaults use)
sub / oid Subject: the user or app Use a stable, immutable id as the key for ownership. Never email or name
scp / scope Delegated permissions the user consented to Endpoint authorization
roles App roles assigned to the user or app Endpoint authorization; app-only tokens carry roles, not scp
azp / client_id Which client app asked Optional allow-list of calling apps
tid Tenant (Entra ID) Multi-tenant APIs must check it against allowed tenants
jti Unique token id Replay detection, if you need it

Validation, step by step, and the famous attacks

Here is a real token validator running real RS256 (a small toy RSA key, but the same maths as production) against nine tokens. It has three validator settings: one strict, one naive, and one that "just decodes". Try the two famous attacks:

  • alg: none: the token says "no signature needed". A library that trusts the header accepts it.
  • Algorithm confusion: the token says HS256 and is HMAC-signed with the API's public key as the shared secret. The public key is public, so the attacker has it. A validator that picks the algorithm from the header computes the HMAC with "its key" (the same public key bytes), and the signature matches.

Then flip to the expired and nbf tokens and change the clock skew.

"Decode" is not "validate"

jwt.decode(token, options={"verify_signature": False}), new JwtSecurityTokenHandler().ReadJwtToken(t), jwt-decode in JavaScript, and jwt.ParseUnverified in Go all exist to read a token, for example in a client that wants to show the user's name. Used inside an API they accept any token anyone types. Search your codebase for them. Every one in a request path is a critical bug unless a real validation happened first.

The fix is the same in every stack. Configure the validator once in middleware: issuer, audience and an algorithm allow-list, with keys fetched from the issuer's metadata (/.well-known/openid-configuration → jwks_uri). Then never touch tokens in handlers.

// ASP.NET Core 10 — Program.cs  (package: Microsoft.AspNetCore.Authentication.JwtBearer)

            ClockSkew = TimeSpan.FromSeconds(60),                  // default is 5 minutes
            NameClaimType = "name",
            RoleClaimType = "roles",
        };
    });

# FastAPI + PyJWT 2.x (pip install "pyjwt[crypto]")
import jwt
from fastapi import Depends, HTTPException, Security
from fastapi.security import HTTPAuthorizationCredentials, HTTPBearer, SecurityScopes

ISSUER = "https://login.example.com/contoso/v2.0"
AUDIENCE = "api://orders"
jwks = jwt.PyJWKClient(f"{ISSUER}/discovery/v2.0/keys", cache_keys=True)  # read jwks_uri from metadata
bearer = HTTPBearer(auto_error=False)

def current_user(scopes: SecurityScopes,
                 cred: HTTPAuthorizationCredentials | None = Depends(bearer)) -> dict:
    challenge = {"WWW-Authenticate": "Bearer"}
    if cred is None:
        raise HTTPException(401, "missing token", headers=challenge)
    try:
        key = jwks.get_signing_key_from_jwt(cred.credentials).key
        claims = jwt.decode(cred.credentials, key,
                            algorithms=["RS256"],              # the allow-list: never read it from the header
                            audience=AUDIENCE, issuer=ISSUER, leeway=60,
                            options={"require": ["exp", "iss", "aud", "sub"]})
    except jwt.InvalidTokenError as e:
        raise HTTPException(401, "invalid token",
                            headers={"WWW-Authenticate": 'Bearer error="invalid_token"'}) from e
    granted = set(claims.get("scp", "").split())
    missing = [s for s in scopes.scopes if s not in granted]
    if missing:
        raise HTTPException(403, "insufficient scope", headers={
            "WWW-Authenticate": f'Bearer error="insufficient_scope", scope="{" ".join(missing)}"'})
    return claims

// Go net/http + github.com/golang-jwt/jwt/v5 + github.com/MicahParks/keyfunc/v3 (JWKS cache)
func RequireJWT(kf jwt.Keyfunc, next http.Handler) http.Handler {
    parser := jwt.NewParser(
        jwt.WithValidMethods([]string{"RS256"}), // rejects none and HS256 confusion
        jwt.WithIssuer("https://login.example.com/contoso/v2.0"),
        jwt.WithAudience("api://orders"),
        jwt.WithLeeway(60*time.Second),
        jwt.WithExpirationRequired(),
    )
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        raw, ok := strings.CutPrefix(r.Header.Get("Authorization"), "Bearer ")
        if !ok {
            w.Header().Set("WWW-Authenticate", "Bearer")
            http.Error(w, "missing token", http.StatusUnauthorized)
            return
        }
        claims := jwt.MapClaims{}
        if _, err := parser.ParseWithClaims(raw, claims, kf); err != nil {
            w.Header().Set("WWW-Authenticate", `Bearer error="invalid_token"`)
            http.Error(w, "invalid token", http.StatusUnauthorized)
            return
        }
        next.ServeHTTP(w, r.WithContext(context.WithValue(r.Context(), claimsKey{}, claims)))
    })
}

How each stack differs, and why:

  • ASP.NET Core maps short claim names to long XML URIs (scp becomes http://schemas.microsoft.com/identity/claims/scope) unless you set MapInboundClaims = false. Half the "my policy never matches" questions online come from that.
  • Spring turns every scope into a SCOPE_ authority, and checks the audience only when you configure audiences.
  • PyJWT makes algorithms mandatory on purpose, after the alg: none era. It verifies aud whenever the token has one, and raises if you didn't pass audience.
  • golang-jwt v5 only enforces exp when present, unless you add WithExpirationRequired.
  • passport-jwt delegates to jsonwebtoken, which refuses none unless you explicitly allow it.

Opaque tokens, introspection and revocation

A JWT is self-contained, so your API can validate it offline in microseconds. The price is that you can't revoke it: a stolen token works until exp. The options:

Approach How Cost
Short-lived JWTs (5–60 min) + refresh tokens Revoke the refresh token; the access token dies soon A window of minutes. Usually the right default
Opaque tokens + introspection (RFC 7662) API asks the authorization server "is this token active?" One network call per request (cache for seconds)
Deny-list of jti / continuous access evaluation IdP pushes revocation events (Entra CAE, Shared Signals) Infrastructure; worth it for high-value APIs
Sender-constrained tokens (mTLS RFC 8705, DPoP RFC 9449) Token only works with the client's private key A stolen token alone is useless

Scopes, roles, policies: endpoint authorization

Once you know who's calling, you decide whether they may do this kind of thing. Three vocabularies get mixed up:

Scopes (scp)

What the app may do on the user's behalf, as consented by the user: orders.read, orders.write. A scope limits the app, not the user. Alice may be an admin, but if she signed in to a reporting tool that asked only for orders.read, that tool can't write, even as Alice.

Roles (roles)

What the user (or app) is: Orders.Manager, Billing.Reader. They're assigned by an admin in the identity provider. App-only tokens (client credentials) carry application roles and no scopes, because no user consented to anything.

Policies

Your code's named rules that combine both with anything else: "CanEditOrders = scope orders.write AND (role Manager OR the order's owner) AND same tenant". Endpoints reference the policy name, so the rule lives in one place.

Delegated access is the intersection

A delegated call (a user signed in through an app) is allowed only if both of these hold: the app was granted the scope, and the user has the permission. Checking only the scope trusts every user of the app. Checking only the role trusts every app the user ever signed in to. Then add the resource check, because neither one knows which tenant or owner the order belongs to.

The visualizer runs eight requests against four policies and counts the holes. Look at Carol, a manager signed in through a read-only reporting app, and at Mallory, who has a valid token from another tenant.

// ASP.NET Core: named policies, then attach them to endpoints
builder.Services.AddAuthorizationBuilder()
    .AddPolicy("orders.read", p => p.RequireAssertion(ctx =>
        HasScope(ctx.User, "orders.read") || ctx.User.IsInRole("Orders.Read.All")))   // delegated or app-only
    .AddPolicy("orders.write", p => p
        .RequireAuthenticatedUser()
        .RequireAssertion(ctx => HasScope(ctx.User, "orders.write")
                              && (ctx.User.IsInRole("Orders.Manager") || ctx.User.IsInRole("Orders.Editor"))));

static bool HasScope(ClaimsPrincipal u, string s) =>
    u.FindAll("scp").SelectMany(c => c.Value.Split(' ')).Contains(s);

// Go + chi: authorization as composable middleware
func RequireScope(scope string, roles ...string) func(http.Handler) http.Handler {
    return func(next http.Handler) http.Handler {
        return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
            c := r.Context().Value(claimsKey{}).(jwt.MapClaims)
            scp, _ := c["scp"].(string)
            if !slices.Contains(strings.Fields(scp), scope) || !hasAnyRole(c, roles) {
                w.Header().Set("WWW-Authenticate", fmt.Sprintf(`Bearer error="insufficient_scope", scope=%q`, scope))
                http.Error(w, "forbidden", http.StatusForbidden)
                return
            }
            next.ServeHTTP(w, r)
        })
    }
}

// NestJS: a metadata decorator plus a guard
export const Scopes = (...s: string[]) => SetMetadata("scopes", s);

@Injectable()
export class ScopesGuard implements CanActivate {
  constructor(private reflector: Reflector) {}
  canActivate(ctx: ExecutionContext): boolean {
    const need = this.reflector.getAllAndOverride<string[]>("scopes", [ctx.getHandler(), ctx.getClass()]) ?? [];
    const granted = new Set(String(ctx.switchToHttp().getRequest().user?.scp ?? "").split(" "));
    if (!need.every((s) => granted.has(s))) throw new ForbiddenException("insufficient scope");
    return true;
  }
}

Resource-based authorization and BOLA

Endpoint policies run before the handler, using only the token. They can't know that order 1018 belongs to Bob, because finding that out needs a database read. So the ownership check has to happen after loading the resource and before returning or changing it. It's easy to forget, it's different in every handler, and no framework attribute adds it for you. That's why BOLA tops the OWASP list.

What the simulation shows:

  • With sequential ids and no check, the attacker walks the id space and every hit is a breach.
  • UUIDs slow down guessing. But ids leak through shared links, logs, Referer headers, support tickets and other API responses, and one leaked UUID is enough. Unguessable ids are defence in depth, not authorization.
  • A 403 stops the leak of data but still answers "does order 1018 exist?". A 404 reveals nothing, because the attacker can't tell "not yours" from "not there".
// ASP.NET Core: resource-based authorization handler
public sealed class OrderEditHandler : AuthorizationHandler<OperationAuthorizationRequirement, Order>
{
    protected override Task HandleRequirementAsync(AuthorizationHandlerContext ctx,
        OperationAuthorizationRequirement req, Order order)
    {
        var sub = ctx.User.FindFirstValue("sub");
        var tid = ctx.User.FindFirstValue("tid");
        if (order.TenantId == tid && (order.OwnerId == sub || ctx.User.IsInRole("Orders.Manager")))
            ctx.Succeed(req);
        return Task.CompletedTask;                     // not calling Succeed = deny
    }
}
builder.Services.AddSingleton<IAuthorizationHandler, OrderEditHandler>();

app.MapPatch("/orders/{id:int}", async (int id, UpdateOrder body, ClaimsPrincipal user,

Recognise BOLA in code review

  • A handler takes an id from the route, query or body and calls FindAsync(id), findById(id) or get(id) with nothing else.
  • The only authorization is an attribute on the endpoint ([Authorize], @PreAuthorize("isAuthenticated()")).
  • A list endpoint filters by ?customerId= taken from the query instead of from the token.
  • Child resources (/orders/{id}/invoice) re-check the child but not the parent, or neither.
  • An "internal" or "admin" endpoint is exposed through the same gateway, protected only because nobody knows its URL.

The function-level cousin is BFLA (broken function level authorization, API5): a normal user calls DELETE /admin/users/7 or PUT instead of GET and it works. Endpoint policies with a deny-by-default fallback are the fix.

Input validation and mass assignment

Every byte in a request is attacker-controlled: path, query, headers, body and file names. Validation is your first resource-protection layer, and it has two jobs that are often confused:

  1. Shape and bounds (syntactic): types, lengths, ranges, formats, maximum array sizes, maximum body size. Reject with 400 or 422 and a problem details body (see API design). This also protects you: an unbounded ?pageSize=1000000 or a 50 MB JSON array is a denial of service (OWASP API4, unrestricted resource consumption).
  2. Which fields the caller may set (semantic). This is where mass assignment lives (OWASP API3, broken object property level authorization). If you bind the request body straight onto your database entity, the caller can set any property, including role, balance, tenantId and emailVerified.

The same API3 entry covers the mirror image: excessive data exposure. Returning the entity serialises every property, including password hashes, internal flags and other users' emails in nested objects, and relies on the client to "only show what it needs". The fix is the same in both directions: explicit DTOs for input and output, with an allow-list of fields.

Validation is not sanitisation, and neither replaces parameterised queries

Validate input against what it should be (an allow-list), and reject it if it isn't. Don't try to strip out "dangerous" characters. Then still use parameterised SQL, encode output for its context (HTML, URL, shell), and never pass user input to eval, a shell, an XML parser with external entities enabled, or a URL fetcher without an allow-list (SSRF, API7). The injection details live in Security fundamentals.

Not every caller is a user behind an OAuth client. For machine callers you have a few choices, and they differ mostly in what happens when the credential leaks.

API keys are identification, not authorization

They're fine for "which customer is this, and what is their quota?". If you use them:

  • Send them in a header (X-Api-Key or Authorization: ApiKey …), never in the URL, where they end up in logs and browser history.
  • Store only a hash (SHA-256 of a high-entropy key is fine; it doesn't need bcrypt).
  • Give them a prefix so secret scanners can find leaked ones: sk_live_…, ghp_….
  • Support several active keys per client so they can rotate without downtime.
  • Scope them, expire them, and rate limit per key.

Prefer identities you never have to type

In Azure, a managed identity gets tokens from the platform without any secret. In Kubernetes, workload identity federation trades the pod's service-account token for an Entra ID or AWS token. GitHub Actions do the same with OIDC. There's nothing to leak, rotate or forget in a config file (see Configuration & secrets).

A bearer token is like cash: whoever holds it can spend it. Sender-constrained tokens are like a card with a PIN. With mTLS the authorization server puts the client certificate's thumbprint in the token (cnf.x5t#S256), and your API checks that the certificate on this TLS connection matches. With DPoP the client signs a small JWT per request, covering the method, the URL and a timestamp, with a key whose thumbprint is in the token. Either way, a token copied out of a log is useless.

mTLS behind a load balancer

TLS usually terminates at a gateway (Azure Front Door, Application Gateway, NGINX, Envoy), so your app never sees the client certificate. The gateway either validates it itself or forwards it in a header (X-Client-Cert, X-Forwarded-Client-Cert). If you trust that header, make sure only the gateway can reach your app. Otherwise anyone can send the header directly. ASP.NET Core's AddCertificateForwarding and Spring's x509() with a custom extractor handle the header case.

CORS: a browser rule that protects users, not your API

CORS (cross-origin resource sharing) is the most misunderstood security feature on the web. It's not an API firewall. Browsers enforce the same-origin policy: JavaScript on https://evil.example may send many requests to https://api.contoso.com, but may not read the responses. CORS is how your API tells the browser "it's OK, let JavaScript from https://app.contoso.com read my responses". It relaxes a protection; it doesn't add one.

That last sentence is the key to the whole topic, so try it below. With a form POST from evil.example the transfer runs on the server under every CORS policy, including "no CORS headers at all", because the request was simple and needed no permission. CORS only decided whether evil JavaScript could read the reply. Then try reflecting any Origin with credentials, which is the worst policy: now evil JavaScript can read the victim's data too.

What CORS does

  • Stops other websites' JavaScript from reading responses from your API in a victim's browser.
  • With credentials (cookies), that protects users' data from being read by pages they happen to visit.
  • Preflights stop non-simple cross-origin requests before they're sent, if you don't allow them.

What CORS does NOT do

  • It doesn't stop curl, Postman, scripts or servers: they ignore CORS entirely.
  • It doesn't stop simple cross-origin requests (form POSTs) from reaching your server and running. That's CSRF, next section.
  • It doesn't authenticate anyone. Origin can be anything outside a browser.
  • It doesn't apply to bearer-token APIs the way people fear: evil.example has no way to get the victim's token.
// ASP.NET Core: an explicit allow-list; never AllowAnyOrigin with AllowCredentials (it throws anyway)

Origin-matching bugs

Dynamic allow-lists written by hand go wrong in predictable ways:

  • origin.endsWith("contoso.com") also matches evilcontoso.com.
  • origin.includes("contoso.com") also matches contoso.com.evil.example.
  • A regex without anchors or escaped dots: https://app.contoso.com matches https://appXcontoso.com.
  • Allowing null, which sandboxed iframes and file:// pages send.

Compare exact strings from a set. When you return a dynamic Access-Control-Allow-Origin, also send Vary: Origin, or a cache or CDN will serve one origin's CORS headers to another.

CSRF: when cookies vote on your behalf

Cross-site request forgery happens when a page on evil.example makes the victim's browser send a request to bank.example, and the browser attaches the victim's cookies automatically. The server sees a perfectly authenticated request. No JavaScript reading is needed, so CORS doesn't help. The defences are:

  • SameSite cookies, which stop the browser from attaching the cookie to cross-site requests: Strict always, Lax except for top-level GET navigations.
  • Anti-forgery tokens: a secret the evil page can't read, sent back in a header or form field.
  • Origin checks on state-changing requests.
  • Not using cookies at all for APIs: bearer tokens are immune to CSRF, because the browser never adds them by itself.

The grid of results is worth studying:

  • SameSite=Lax, the modern browser default, blocks the form POST, but not a state-changing GET. The link is a top-level navigation, so Lax sends the cookie, and token and Origin checks usually skip GETs. The real fix is to never change state on GET (see API design).
  • SameSite=None (needed for some cross-site embeds) brings the whole attack back, and only a token or Origin check stops it.
  • fetch with credentials: "include" and a JSON body is not simple, so the preflight fails under a sane CORS policy and the request is never sent.
  • Bearer tokens are safe in every row, because nothing is attached automatically.

The BFF pattern: cookies for the browser, tokens for the APIs

Storing access tokens in localStorage makes them readable by any XSS. A backend for frontend keeps the tokens on a small server owned by the SPA. The browser holds only an HttpOnly; Secure; SameSite=Strict session cookie. The BFF swaps it for a token and proxies the API call. You now need CSRF protection on the BFF (SameSite plus a custom header such as X-CSRF: 1, which forces a preflight), but tokens never touch JavaScript. Duende BFF (.NET), Spring Cloud Gateway with the token relay filter, and Next.js route handlers all implement it.

Rate limiting: fair use, abuse control and self-defence

Authentication tells you who's calling, and rate limiting decides how often they may. It does three different jobs, and each needs a different key and a different limit:

Job Key Example limit On exceed
Stop brute force and credential stuffing IP + username, per endpoint 5 failed sign-ins / 15 min 429, plus growing delays or CAPTCHA
Fair use between customers (quotas) API key / client id / tenant 1,000 req/min, 1M/month 429 with Retry-After; billing tier upgrade
Protect the service from overload Global / per instance 500 concurrent requests 503 + load shedding (see Resilience)
Expensive operations User + operation 10 exports/hour, 3 SMS/hour 429; this is OWASP API6, business flows

The algorithm decides how bursty the allowed traffic can be. The visualizer runs five classic algorithms on the same traffic, with a limit of 10 requests per 10 seconds (a rate of 1 per second). The interesting row is Burst at a window edge. A fixed window lets 20 requests through in under 3 seconds, because 10 arrive just before the boundary and 10 just after. The sliding log never lets more than 10 into any 10-second span. The token bucket allows its capacity of 10 as a burst, then refills at 1 per second.

Fixed window

A counter per key per window (key:12:00). It's trivial in Redis (INCR + EXPIRE), but allows 2× the limit at a window boundary.

Sliding window counter

It weights the previous window's count by how much of it still overlaps the sliding window. It uses two counters per key, and its error is small enough for almost everything. Cloudflare and many gateways use it.

Sliding log

It stores every timestamp, so it's exact, but uses memory O(limit) per key. Use it for low limits such as sign-in attempts.

Token bucket

A bucket holds up to C tokens and refills at R per second; each request takes one. It allows bursts up to C with a long-run rate of R. It's the usual choice for APIs (AWS API Gateway, Stripe, golang.org/x/time/rate).

Leaky bucket (queue)

Requests queue up and leave at a steady rate. The output is smooth, which is good for protecting a fragile downstream, but it adds latency instead of rejecting, and the queue needs a bound.

Concurrency limit

It doesn't count requests over time; it limits how many are in flight. That's the right tool for overload protection (a bulkhead), and a poor tool for quotas.

Tell the client what happened, so a well-behaved one can back off instead of hammering you:

HTTP/1.1 429 Too Many Requests
Retry-After: 6
RateLimit-Policy: "per-client";q=10;w=10
RateLimit: "per-client";r=0;t=6
Content-Type: application/problem+json

{"type":"https://api.contoso.com/problems/rate-limited","title":"Too many requests","status":429,
 "detail":"Limit is 10 requests per 10 seconds for this client. Retry in 6 s."}

Retry-After is standard (RFC 9110). The RateLimit and RateLimit-Policy fields come from an IETF draft (draft-ietf-httpapi-ratelimit-headers). Their syntax changed between draft versions, and many APIs still send the older X-RateLimit-Limit/Remaining/Reset triple. Pick one format and document it.

// Spring Boot + Bucket4j (in memory here; bucket4j-redis / -jcache for clusters)
@Component
class RateLimitFilter extends OncePerRequestFilter {
    private final Map<String, Bucket> buckets = new ConcurrentHashMap<>();   // bound this (Caffeine) in production

    private Bucket newBucket(String key) {
        return Bucket.builder()
            .addLimit(limit -> limit.capacity(10).refillGreedy(1, Duration.ofSeconds(1)))
            .build();
    }

    @Override
    protected void doFilterInternal(HttpServletRequest req, HttpServletResponse res, FilterChain chain)
            throws ServletException, IOException {
        var auth = SecurityContextHolder.getContext().getAuthentication();
        var key = auth != null ? auth.getName() : req.getRemoteAddr();
        var probe = buckets.computeIfAbsent(key, this::newBucket).tryConsumeAndReturnRemaining(1);
        if (probe.isConsumed()) { chain.doFilter(req, res); return; }
        res.setStatus(429);
        res.setHeader("Retry-After", String.valueOf(
            Math.max(1, TimeUnit.NANOSECONDS.toSeconds(probe.getNanosToWaitForRefill()))));
    }
}

# Token bucket, the algorithm itself (what slowapi / limits / a gateway does for you)
import math, time

class TokenBucket:
    def __init__(self, capacity: float, rate: float, now=time.monotonic):
        self.capacity, self.rate, self.now = capacity, rate, now
        self.tokens, self.last = capacity, now()

    def try_take(self) -> tuple[bool, int]:
        t = self.now()
        self.tokens = min(self.capacity, self.tokens + (t - self.last) * self.rate)
        self.last = t
        if self.tokens >= 1:
            self.tokens -= 1
            return True, 0
        return False, math.ceil((1 - self.tokens) / self.rate)   # seconds until a token exists

# FastAPI middleware: buckets keyed by client id, 429 + Retry-After when empty
# (use Redis with a Lua script for the same logic across instances)

// Go: golang.org/x/time/rate is a token bucket; one limiter per client
type limiters struct {
    mu sync.Mutex
    m  map[string]*rate.Limiter // evict idle entries in production
}

func (l *limiters) get(key string) *rate.Limiter {
    l.mu.Lock()
    defer l.mu.Unlock()
    lim, ok := l.m[key]
    if !ok {
        lim = rate.NewLimiter(rate.Limit(1), 10) // R = 1/s, burst C = 10
        l.m[key] = lim
    }
    return lim
}

func (l *limiters) Middleware(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        res := l.get(clientKey(r)).Reserve()
        if d := res.Delay(); d > 0 {
            res.Cancel() // don't consume a future token
            w.Header().Set("Retry-After", strconv.Itoa(int(math.Ceil(d.Seconds()))))
            http.Error(w, "too many requests", http.StatusTooManyRequests)
            return
        }
        next.ServeHTTP(w, r)
    })
}

Rate limiting pitfalls

  • Keying by IP only. Thousands of users behind one corporate NAT share a limit, while an attacker with a botnet has thousands of IPs. Key by the authenticated client or user, and use IP only for anonymous endpoints.
  • Trusting X-Forwarded-For blindly. Anyone can send it. Take the address your own proxy appended (ASP.NET Core ForwardedHeadersOptions.KnownProxies, Spring server.forward-headers-strategy, Express app.set("trust proxy", 1)).
  • Per-instance limits in a scaled-out service: with 8 instances, "100 per minute" really means 800. Enforce at the gateway or in shared storage.
  • Counting before authentication for per-user limits, so unauthenticated junk eats real users' quota. Have a cheap per-IP limit first, then per-user after authentication.
  • No limit on expensive operations: a "send verification SMS" endpoint without a per-user limit is a bill, not a feature.

API10 Unsafe consumption of APIs Trusting a partner API's response blindly; following its redirects Validate third-party responses like user input; timeouts; TLS

Secrets, logs and headers: the boring layer that leaks

Never put secrets in tokens. A JWT payload is base64url, not encryption: paste one into any decoder and you can read it. Keep tokens to identifiers and permissions. If an API needs sensitive attributes, it should look them up, or you should use an encrypted JWE, which is rarely worth the complexity.

Never log credentials. Logs are copied to more places, kept longer and read by more people than any database. Specifically:

  • Redact Authorization, Cookie, Set-Cookie, X-Api-Key, Proxy-Authorization, and query strings containing code=, token=, key=, sig=.
  • Log the token's jti, sub, azp and exp if you need to correlate, never the token itself.
  • Request-body logging middleware is the usual culprit; allow-list fields instead of logging everything.
  • Error messages go to clients without internals: no stack traces, SQL, or "user exists but password wrong" (that's an enumeration oracle).

See Observability for structured logging with redaction, and Configuration & secrets for where signing keys and client secrets should live (a vault, never appsettings.json or .env in Git).

A JSON API needs a much shorter header list than a website, but these still matter:

Header Value for a JSON API Why
Strict-Transport-Security max-age=31536000; includeSubDomains Browsers never try plain HTTP again
Content-Type application/json; charset=utf-8 (always explicit) Prevents content sniffing into HTML
X-Content-Type-Options nosniff Same, for older browsers
Cache-Control no-store on anything personal Shared caches and the browser's disk must not keep it
Content-Security-Policy default-src 'none'; frame-ancestors 'none' If a response is ever rendered as a page, it can't run or be framed

@app.middleware("http")
async def security_headers(request, call_next):
    resp = await call_next(request)
    resp.headers.update({
        "Strict-Transport-Security": "max-age=31536000; includeSubDomains",
        "X-Content-Type-Options": "nosniff",
        "Content-Security-Policy": "default-src 'none'; frame-ancestors 'none'",
        "Referrer-Policy": "no-referrer",
    })
    resp.headers.setdefault("Cache-Control", "no-store")
    return resp

func SecurityHeaders(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        h := w.Header()
        h.Set("Strict-Transport-Security", "max-age=31536000; includeSubDomains")
        h.Set("X-Content-Type-Options", "nosniff")
        h.Set("Content-Security-Policy", "default-src 'none'; frame-ancestors 'none'")
        h.Set("Referrer-Policy", "no-referrer")
        h.Set("Cache-Control", "no-store")
        next.ServeHTTP(w, r)
    })
}

When to use what (and what not to build)

Decision guide, in order

  1. Is there a user? Yes: authorization code + PKCE through a standard library and a hosted identity provider. No: client credentials, with a certificate or managed identity.
  2. Is the client a browser app? Prefer a BFF with an HttpOnly SameSite=Strict cookie. A pure SPA holds tokens in memory only, never localStorage.
  3. Does your API call another API for the user? Use on-behalf-of / token exchange. Never forward the incoming token, and never fall back to a god-mode service identity.
  4. Can you revoke fast enough? Keep access tokens to 5–60 minutes. For high-value APIs, add sender-constrained tokens (mTLS or DPoP) or continuous access evaluation.
  5. Every endpoint: deny by default, then a policy (scope + role), then a resource check, then input and output DTOs, then rate limits keyed by client.

Don't build these yourself

  • A login page with password storage, MFA, reset and lockout, when an identity provider exists.
  • Your own token format or signing scheme ("HMAC of user id + timestamp").
  • JWT parsing and validation by hand, or a JWKS cache with a home-made rotation.
  • Session tokens in JWTs "to be stateless", when you then need a server-side deny-list anyway.

Don't over-build either

  • OAuth for a single internal tool used by three colleagues: platform authentication (Easy Auth, an IAP, a VPN with SSO) may be enough.
  • mTLS everywhere inside a cluster that already runs a service mesh: the mesh does it.
  • A distributed rate limiter for a service with one instance and an API gateway in front.
  • JWE-encrypted tokens to hide claims you could just leave out.

Common pitfalls

Accepting any token from your identity provider

Validating the signature and issuer but not the audience means a token minted for another API in the same tenant (Microsoft Graph, a colleague's service) works on yours. With multi-tenant Entra ID apps, also check tid. Otherwise "any Microsoft account in the world" is your user base.

Reading roles from the wrong place

The user's role must come from the validated token or your own database, never from the request body, a header such as X-User-Role, or a client-side flag. An "admin" toggle in the SPA that the API trusts is API5 in one line.

Different rules on different paths

GET /orders/42 checks ownership, but GET /orders/42/invoice.pdf, GET /search?q= or the GraphQL resolver for order(id:) doesn't. Put authorization in the service or repository layer that every path uses, not only in controllers.

Long clock skew and long-lived tokens

ASP.NET Core's default ClockSkew is 5 minutes. Combined with 24-hour access tokens, a stolen token is usable for a day. Use 30–60 s of skew, 5–60 minute access tokens, and rotating refresh tokens.

Checklist

Before an API ships

  • [ ] Tokens are validated by a maintained library: signature, iss, aud, exp/nbf with skew ≤ 60 s, and an algorithm allow-list.
  • [ ] A fallback policy requires authentication; anonymous endpoints are explicitly marked.
  • [ ] Every endpoint has a scope or role policy, and delegated calls check scope and user permission.
  • [ ] Every id from the client is checked for ownership and tenant (or the query is scoped); cross-tenant answers 404.
  • [ ] Input is bound to DTOs with bounds; unknown fields are rejected; responses use output DTOs.
  • [ ] 401s carry WWW-Authenticate; 403s say insufficient_scope where relevant; errors use problem details without internals.
  • [ ] Rate limits exist per client, per sign-in, and per expensive flow, with 429 and Retry-After, enforced globally.
  • [ ] CORS is an exact allow-list; no state changes on GET; cookie auth has SameSite plus a token or Origin check.
  • [ ] Machine callers use managed identity or certificates; any API keys are hashed, prefixed, scoped and rotatable.
  • [ ] Authorization, cookies and keys are redacted in logs; tokens carry no secrets.
  • [ ] Security headers and HSTS are set; Server/X-Powered-By are removed.
  • [ ] There are tests for the negative cases: no token, wrong audience, other user's id, other tenant's id, extra fields, burst traffic. See Testing strategy.

Self-check

An access token validates, its scope is orders.read, and the caller sends PATCH. Status code and header?

403 with WWW-Authenticate: Bearer error="insufficient_scope", scope="orders.write". The caller is authenticated, so 401 is wrong, and retrying with the same token won't help. The client needs a token with more consent.

Why does the HS256 "algorithm confusion" attack work, and what single setting stops it?

The validator lets the token's header choose the algorithm. For HS256 it uses "the key" as an HMAC secret, and that key is the RSA public key, which the attacker can download. So the attacker can compute a valid HMAC. Fix it by configuring an algorithm allow-list (ValidAlgorithms, algorithms=["RS256"], WithValidMethods) and keying by algorithm type.

You switched order ids from integers to UUIDs. Is the BOLA bug fixed?

No. Guessing becomes impractical, but ids leak through shared links, logs, Referer headers and other responses. One leaked id still returns someone else's order. You need an ownership check, or a query scoped by owner and tenant.

Your API sets Access-Control-Allow-Origin to an exact allow-list. Is a cookie-authenticated POST /transfer safe from evil.example?

Not necessarily. A form-encoded POST is a simple request. The browser sends it without a preflight, with cookies (unless SameSite blocks them), and the server runs it. CORS only stops evil.example's JavaScript from reading the response. You need SameSite=Lax/Strict plus an anti-CSRF token or Origin check, or bearer-token auth.

A fixed-window limiter allows 100 requests per minute. What's the most a client can send in a few seconds without a single 429?

200: 100 at the end of one window and 100 at the start of the next. A sliding window or token bucket bounds this. A token bucket allows its capacity C as a burst, then R per second.

Orders API needs to call Inventory API for the signed-in user. Which token should it send?

A new token for the Inventory API, obtained with on-behalf-of / token exchange (RFC 8693) using the incoming token as the assertion. Forwarding the incoming token fails the audience check, and it should. Using the Orders API's own app identity loses the user's permissions and lets one user act with the service's powers (the confused deputy problem).

Where should the check "Bob may edit only his own orders, managers may edit any in their tenant" live?

In a resource-based check that runs after the order is loaded, or in a repository query scoped by tenant and owner. It must be shared by every path that touches orders. An endpoint attribute can't do it, because it runs before the order is known.

Cheat sheet

401 vs 403 vs 404401 = who are you? (+ WWW-Authenticate). 403 = known, not allowed. 404 = not yours and you shouldn't know it exists.
FlowsUser: auth code + PKCE (S256). Service: client credentials with a cert or managed identity. API → API: on-behalf-of. Never implicit or password.
TokensAccess token → your API (aud). ID token → the client only. Refresh token → the authorization server only, rotated.
JWT validationAlgorithm allow-list → key by kid from JWKS → signature → iss → aud → exp/nbf (≤ 60 s skew) → scopes.
AuthZ layersFallback: authenticated. Endpoint: scope ∧ role. Resource: owner/tenant after load. Delegated = app scope ∩ user permission.
BOLAEvery client-supplied id is untrusted. Scope queries by tenant and owner; answer 404. UUIDs are not authorization.
Mass assignmentInput DTO with allowed fields only; reject unknown ones; output DTO, never the entity.
CORSLets your front end read responses. Doesn't stop curl, servers or simple form POSTs. Exact allow-list + Vary: Origin.
CSRFCookies are attached automatically; bearer headers aren't. SameSite=Lax/Strict + token or Origin check; no state change on GET.
Rate limitsToken bucket (C burst, R/s) for APIs; sliding log for sign-in; concurrency limits for overload. 429 + Retry-After; key by client.
Machine credentialsManaged identity > certificate > client secret > API key. Keys: header only, hashed, prefixed, rotatable.
NeverSecrets in JWTs; tokens in URLs or logs; decode without verify; roles from the request; Allow-Origin reflecting any origin with credentials.
