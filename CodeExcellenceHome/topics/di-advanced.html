Advanced DI: Decorators, Factories, Options & Testing

Keyed services, factories and Lazy<T>, decorators and interception, the options pattern, modules, and swapping dependencies in tests.

Advanced~50 min studyBuilds on: Lifetimes, Scopes & Captive Dependencies, Structural PatternsUpdated 2026-11-03

The problem: the container works until the app grows

You know the basics from Dependency Injection Fundamentals: constructor injection and one composition root. You know the lifetime rules and how a captive dependency happens from Lifetimes, Scopes & Captive Dependencies. You have seen how each ecosystem wires the same graph in DI Across Languages & Frameworks. Then the real app arrives with its requirements:

  • The repository needs caching and logging, but nobody wants to edit SqlOrderRepository to add them.
  • Payments go to Stripe or Adyen depending on the country of the order.
  • One endpoint needs a PDF renderer that takes 300 ms to construct, and 95% of requests never use it.
  • A NuGet package or a Spring starter registers its own default INotifier, and you want yours to win.
  • Every tenant has its own database and must never see another tenant's connection.
  • The payment timeout lives in configuration that changes without a redeploy.
  • A token cache must fetch signing keys over HTTP before it can serve, and constructors cannot await.
  • The integration tests must swap the real payment gateway for a fake.

Each of these tempts a shortcut. People write new CachingRepository(new SqlRepository(...)) inside a class, or if (country == "NL") inside a service. They inject IServiceProvider everywhere "for flexibility", read a static config singleton, or call .Result in a constructor. Every shortcut works on day one. Every one of them hides a dependency from the container, and so from validation, from tests and from the next reader.

Rule. Advanced DI is the art of expressing every variation as a registration. Which implementation, when it is created, what wraps it, for which T, inside which boundary, with which settings and replaced by what in tests: each question has a declarative answer the container can see. What the container can see, it can validate, test, override and explain. What you hide inside a lambda, a method body or an if, it cannot.

WHICH ONE?Multi and keyed

Lists of implementations, defaults, "last one wins", and lookup by key.

WHEN?Factories, Lazy, Func

Defer or repeat creation, and mix container and runtime arguments.

WRAPPED HOW?Decorators

Add caching, retries and logging around a service without touching it.

FOR WHICH T? WHERE?Generics, scopes, modules

One registration for every entity, per-tenant boundaries, public and private providers.

WITH WHAT? INSTEAD OF WHAT?Options and overrides

Typed settings that can reload, and swapping dependencies in tests.

The mental model: the registration list is a program

In Microsoft.Extensions.DependencyInjection (MS.DI) the container is literally an ordered list of descriptors: service type, implementation, lifetime and an optional key. Several parties append to that list, in a fixed order. Build() turns it into lookup tables. Every advanced technique is either a different way of writing to the list or a different way of reading from it. Other containers store bean definitions in maps with their own override rules, but you can picture them the same way.

Why ordering rules differ across containers. MS.DI was designed as the lowest common denominator for ASP.NET Core: an append-only list where the last entry wins and the whole list is still available as a collection. Spring Boot went the other way. Since Boot 2.1, overriding a bean definition with the same name is an error by default (spring.main.allow-bean-definition-overriding=false), and two beans of one type are an ambiguity error unless one is @Primary or you ask for a @Qualifier. Guice refuses duplicate bindings outright unless you use Modules.override. NestJS behaves like MS.DI: the last provider with a token wins. Go and Python have no list at all, because you pass the value you mean. Know which rule your container follows before you trust a default.

Many implementations: lists, defaults and "last one wins"

Some abstractions legitimately have several implementations alive at the same time: notification channels, validation rules, health checks, startup filters, message handlers. MS.DI gives you five verbs for writing to the list, and they behave differently enough to cause real bugs. Here is what each one does:

Verb What it does Typical author
Add… Always appends. The last entry wins GetService<T>; all entries appear in IEnumerable<T>. your app
TryAdd… Appends only if no entry for the service type exists yet. libraries that ship a default
TryAddEnumerable Appends only if this exact service + implementation pair is not there yet. libraries that contribute one item to a list
Replace Removes the first entry for the service type, then appends the new one. tests, rarely apps
RemoveAll Removes every entry for the service type. tests, before adding a fake

Run the scripts below. Watch the left column, which is the actual list, and the right column, which shows what a constructor asking for one INotifier or for IEnumerable<INotifier> would receive at that moment. The "test swap with Replace" preset shows the most surprising rule: Replace takes out only the first registration, so the fake becomes the single answer while the old SMS notifier is still in the list and still sends real messages from a fan-out.

These rules come from running the code on .NET 10, not from memory. [Email, Sms] followed by Replace(Push) gives a single Push, but the collection is [Sms, Push]. Calling TryAddEnumerable(Email) twice adds Email only once. TryAddEnumerable with a factory lambda throws ArgumentException: "Implementation type cannot be 'INotifier' because it is indistinguishable from other services registered for 'INotifier'". It must know the implementation type to compare pairs, and a lambda does not say.

The composite that contains itself. A natural design is a FanOutNotifier : INotifier that takes IEnumerable<INotifier> and calls each one. Register it as an INotifier next to Email and Sms and the collection it asks for now includes itself. MS.DI reports: "A circular dependency was detected for the service of type 'System.Collections.Generic.IEnumerable<INotifier>'. INotifier(Composite) -> IEnumerable<INotifier> -> IEnumerable<INotifier>." ValidateOnBuild catches this at startup, but other containers may recurse until the stack overflows. Fix: give the parts their own interface (INotificationChannel). The composite implements INotifier and consumes the channels, so the cycle cannot form.

The same fan-out in five ecosystems

Each ecosystem has a name for "inject all implementations of X": a collection in MS.DI, List<T> injection in Spring, a Multibinder in Guice, @IntoSet in Dagger, value groups in Fx, and a factory in NestJS. In plain Python you simply pass a list.

public interface INotifier { Task SendAsync(Message m, CancellationToken ct); }
public interface INotificationChannel { Task SendAsync(Message m, CancellationToken ct); }

public sealed class FanOutNotifier(IEnumerable<INotificationChannel> channels) : INotifier
{
    private readonly INotificationChannel[] _channels = channels.ToArray();   // materialize once
    public Task SendAsync(Message m, CancellationToken ct) =>
        Task.WhenAll(_channels.Select(c => c.SendAsync(m, ct)));
}

Order is an API only where the container promises it. MS.DI returns IEnumerable<T> in registration order, and Spring sorts List<T> by @Order or Ordered. Guice Multibinder keeps binding order. Dagger sets and Fx value groups make no order promise. If the order matters, for example validation rules that must run cheapest-first or middleware-like chains, make it explicit with a Priority property you sort by, or build the chain by hand. Do not rely on "it happened to work".

Keyed and named resolution

Sometimes you need one particular implementation out of several. Ask first: when is the choice known?

  • When you write the code (the refund job always uses Stripe): inject that one by key. Use [FromKeyedServices("stripe")] in .NET 8+, @Qualifier("stripe") in Spring, @Named in Guice and Dagger, a token in NestJS, or simply the concrete constructor in Go and Python.
  • Only at runtime (the order's country decides): this is the Strategy pattern. Put the lookup behind one small router type. Do not sprinkle GetRequiredKeyedService(country) across your business code.

.NET 8 added keyed services to MS.DI. The lookup rules, verified on .NET 10, are:

  1. An exact key match wins.
  2. Otherwise a registration with KeyedService.AnyKey serves any key. With a [ServiceKey] constructor parameter, it receives the key that was asked for. If the registration is a singleton, you get one instance per key, not one in total.
  3. Otherwise GetRequiredKeyedService throws "No keyed service for type 'IPaymentGateway' using key type 'System.String' has been registered.", and GetKeyedService returns null.
  4. Keyed registrations are invisible to non-keyed lookups. GetService<IPaymentGateway>() returns null when only keyed entries exist, and IEnumerable<IPaymentGateway> leaves them out.

Try different lookups, including the same key twice and a key nobody registered:

Recognize the smell. Look for a switch on a string that calls new in each branch, or a class that takes IServiceProvider only to call GetRequiredKeyedService(someVariable). Both mean a runtime choice has leaked into business code. Replace them with a router that receives all candidates through its constructor, so the container validates every candidate at startup. The router also checks its routing table once, when it is built.

The pattern that scales is the same in every ecosystem: inject the candidates as a map, validate the routing configuration in the constructor, and expose one method.

// static choice: the key is part of the code
public sealed class RefundJob([FromKeyedServices("stripe")] IPaymentGateway stripe) { /* ... */ }

public interface IPaymentGateway { string Name { get; } Task<Receipt> ChargeAsync(Charge c, CancellationToken ct); }

public sealed class GatewayRouter : IGatewayRouter
{
    private readonly Dictionary<string, IPaymentGateway> _byName;
    private readonly IReadOnlyDictionary<string, string> _byCountry;
    private readonly string _default;

    public GatewayRouter(IEnumerable<IPaymentGateway> gateways, IOptions<RoutingOptions> options)
    {
        _byName = gateways.ToDictionary(g => g.Name, StringComparer.OrdinalIgnoreCase);
        _byCountry = options.Value.GatewayByCountry;
        _default = options.Value.Default;
        var unknown = _byCountry.Values.Append(_default).Where(n => !_byName.ContainsKey(n)).ToList();
        if (unknown.Count > 0) throw new InvalidOperationException($"Routing refers to unknown gateways: {string.Join(", ", unknown)}");
    }

    public IPaymentGateway For(string country) =>
        _byName[_byCountry.TryGetValue(country, out var name) ? name : _default];
}

from typing import Mapping, Protocol

class PaymentGateway(Protocol):

class GatewayRouter:

        if unknown:

        self._gateways = dict(gateways)
        self._by_country = dict(by_country)
        self._default = default

    def for_country(self, country: str) -> PaymentGateway:
        return self._gateways[self._by_country.get(country, self._default)]

Keyed injection is right when

  • The key is a compile-time constant at the injection site ([FromKeyedServices("stripe")], @Qualifier).
  • Two configurations of the same type must coexist, such as two HttpClient setups or two database connections ("primary" and "replica").
  • A framework hands you the key, for example a message type name or a route parameter, and one router class does the lookup.

Keyed lookup is a smell when

  • Business methods call GetRequiredKeyedService(variable). That is a service locator with a string attached.
  • Keys are typo-prone strings scattered through the code. Use constants or an enum, so a rename cannot silently break the lookup.
  • Each key has a different interface in practice. Then they are different services and should be different types.

Deferring creation: factories, Lazy, Func and assisted injection

Constructor injection is eager. Resolve a controller and you build everything it might need, even if this request takes a branch that needs none of it. For cheap objects that does not matter. For a PdfRenderer that loads fonts for 300 ms, it does. There are three related needs:

  • Later. Build it on first use, then reuse it. This is Lazy<T>, Spring's ObjectProvider<T>, sync.OnceValue in Go, and functools.cached_property in Python.
  • Many. Build a fresh one each time you ask. This is Func<T>, Provider<T>, or a factory function.
  • With runtime arguments. The container supplies some constructor parameters and the caller supplies the rest, such as an order id. This is called assisted injection. It is ActivatorUtilities in .NET, @Assisted in Guice and Dagger, functools.partial in Python, and a closure in Go and TypeScript.

MS.DI does not understand Lazy<T> or Func<T> by itself. Ask it for Lazy<PdfRenderer> and you get null (verified on .NET 10). You must register them yourself, and the lifetime you give that registration decides which provider the lambda receives. Autofac, by contrast, supports Lazy<T>, Func<T> and Owned<T> implicitly. Its Owned<T> hands you a disposable "ownership" token, so you can dispose a transient before the scope ends.

The visualizer below runs a list of requests against four strategies. Pay special attention to the last one. A Func<PdfRenderer> registered as a singleton is built by the root provider, so its lambda captures the root. A scoped renderer then either throws "Cannot resolve scoped service 'PdfRenderer' from root provider" (with ValidateScopes) or silently becomes a shared singleton (without it). A disposable transient renderer is tracked by the root until shutdown, which is a slow memory leak. This bug passes ValidateOnBuild, because a lambda's body is opaque to the validator.

Why "the factory has the lifetime of what it creates" is the rule. A factory is a closure over some provider. A singleton closes over the root, a scoped one over the request scope, and only the scope knows when the request ends. So register a factory with the shortest lifetime of anything it can create. If a long-lived object really must create scoped work, such as a background service or a message consumer, inject IServiceScopeFactory and create and dispose an explicit scope for each unit of work. Lifetimes, Scopes & Captive Dependencies covers that pattern in detail.

Prefer a named factory interface (IReportExporterFactory.Create(orderId)) over a bare Func<int, ReportExporter>. It reads better in a constructor, it can be faked in a test, and it puts the assisted-injection plumbing in one place.

Lazy hides a cost; it does not remove it. A Lazy<T> that is opened on every request saves nothing and adds an allocation plus a lock. It also moves the failure: a renderer that cannot find its fonts now fails at the first PDF request instead of at startup. Use deferral when a meaningful share of requests never need the dependency. Otherwise fix the slow constructor, by moving I/O out of it, or make the object a warmed-up singleton.

Decorators and interception

A decorator implements the same interface as the thing it wraps and adds behaviour before and after delegating to it. The pattern is covered in Structural Patterns. DI makes it powerful because consumers never know: OrderService asks for IOrderRepository and receives Logging(Caching(Sql)). Request-level wrapping (authentication, logging per HTTP call) is the job of the pipeline, covered in Middleware Patterns & Ordering. Decorators do the same job around one dependency.

In .NET, the Scrutor library adds services.Decorate<TService, TDecorator>(). It rewrites the existing descriptor into a factory that builds the old implementation and passes it to the decorator's constructor. Each call wraps whatever is registered now, so the last Decorate call is the outermost layer (verified: Caching then Logging gives Logging(Caching(Sql))). Decorate on a service with several registrations wraps each one. Decorate on a service that is not registered throws DecorationException: "Could not find any registered services for type …".

Order changes behaviour, not just structure. Set the order and a scenario, then compare how many database queries, log lines and metric points each arrangement produces:

A default order that is usually right, from outermost to innermost:

  1. Logging, tracing and metrics. They see every call, including cache hits, and measure what the caller experiences.
  2. Caching. A hit skips everything below it.
  3. Resilience (retry, timeout, circuit breaker). It sits around the unreliable call only.
  4. The real implementation.

Deviate on purpose. For example, put metrics inside retry when you want one data point per attempt. The details of ordering resilience strategies are in Resilience.

Decorators versus interception (dynamic proxies)

There are two ways to wrap a dependency. A decorator is a class you write: one per interface, checked by the compiler and visible in the code. Interception generates a proxy at runtime and runs interceptors chosen by a rule ("every method on types ending in Repository", "every method annotated @Transactional"). Spring AOP, Guice bindInterceptor, Castle DynamicProxy and .NET's DispatchProxy all work this way.

Prefer a decorator when

  • The behaviour is specific to one abstraction: caching orders, or auditing payments.
  • You want the order and the logic visible in code and in stack traces.
  • The language makes it cheap: one small class (C#, Java, TypeScript), a struct embedding the interface (Go), or a wrapper class (Python).

Consider interception when

  • The same concern applies to many types: transactions, method-level security, timing every repository.
  • A framework already gives it to you (@Transactional, @Cacheable, @PreAuthorize), with documented rules about what is proxied.
  • You accept the costs: no self-invocation, no final or non-virtual methods, and behaviour you cannot see at the call site.

Open generics: one registration for every T

.NET can register an unbound generic type: services.AddScoped(typeof(IRepository<>), typeof(EfRepository<>)). When someone asks for IRepository<Order>, the container closes the template with T = Order and builds EfRepository<Order>. ILogger<T> and IOptions<T> work this way. So do the "pipeline behaviours" of mediator libraries, where one ValidationBehavior<TRequest, TResponse> wraps every handler.

The resolution rules were verified on .NET 10. Read them alongside the visualizer:

  • A closed registration beats the open one for a single resolve, regardless of registration order. This is the one place where "last wins" does not apply.
  • IEnumerable<IRepository<Order>> returns both the closed and the closed-over open implementation, in registration order.
  • Generic constraints are checked when the type is closed. IRepository<string> violates where T : IEntity, so a single resolve throws "GenericArguments[0], 'System.String', on 'EfRepository1[T]' violates the constraint of type 'T'". In anIEnumerable` the open registration is skipped silently.
  • ValidateOnBuild cannot check an open generic. It has no T, so there is no concrete constructor to inspect. An open generic with a missing dependency passes validation and fails on first use (see the blind-spots visualizer below).

Why open generics are mostly a .NET feature. The CLR has reified generics: EfRepository<Order> is a real runtime type that can be created by reflection. Java erases generics at runtime, so Spring can match Repository<Order> against beans whose declared type says Repository<Order>, but it cannot create "EfRepository for any T" from one definition. Python and TypeScript erase type parameters too. Go generics are instantiated at compile time, and each instantiation is a separate call you write. In those ecosystems the equivalent of an open generic is a function that produces a closed provider per type. TypeORM's forFeature([Order, Customer]) in NestJS is exactly that.

Two more verified details matter in practice. Scrutor can decorate the closed registrations of a generic service with an open decorator type (Decorate(typeof(IHandler<>), typeof(LoggingHandler<>)) wrapped IHandler<string> and IHandler<int>). But it throws DecorationException when the only registration is an open generic, because MS.DI has no factory hook for open types. Autofac's RegisterGenericDecorator handles that case.

Child scopes and per-tenant containers

Most apps need two levels of sharing: the process (singletons) and the request (scoped). Multi-tenant SaaS apps often need a third level between them: objects shared by all requests of one tenant, such as its settings, its database connection factory, or a client built with its API key. Objects at that level must never leak to another tenant, and they must be rebuilt when that tenant's settings change.

A hierarchical container models this with child scopes that can add registrations. Autofac's BeginLifetimeScope(tag, builder => …), Guice's createChildInjector and Spring's parent and child ApplicationContext all work this way. A child sees its parent's objects. A parent never sees its children's objects. And disposal runs inside-out: requests first, then tenants, then the root. Step through a few requests and an eviction:

MS.DI scopes are flat. Calling CreateScope() on a scope's provider creates a sibling scope under the root, not a child, and a scope cannot add registrations. To get a real tenant level in .NET you have three choices. In order of preference:

  1. A scoped ITenantContext plus singleton caches keyed by tenant. This is the most common choice and needs no special container. For example, use a ConcurrentDictionary<string, TenantDbFactory> and dispose an entry yourself when you evict it.
  2. Autofac.Multitenant (or Autofac's BeginLifetimeScope directly), which gives true per-tenant registrations and disposal.
  3. One ServiceProvider per tenant, cached and disposed on eviction. This is simple to reason about, but every singleton is now duplicated per tenant, including heavy ones such as HttpClient handlers and caches.

Async initialization: constructors cannot await

Some dependencies need I/O before they are usable: signing keys from an identity provider, a schema check, a cache warm-up. In C#, Java, Python, Go and TypeScript a constructor cannot be async, and containers resolve synchronously (Python's dependency-injector and NestJS's async providers are partial exceptions). So the tempting fix is to block inside the constructor with .GetAwaiter().GetResult(). On a thread pool, that is how a service goes down at startup: every request thread blocks waiting for an I/O continuation that needs a free thread to run. The pool adds about one thread per half second, so a burst of traffic can stall for many seconds. This is thread-pool starvation.

Compare four strategies under the same load. Then make the first attempt fail and see why Lazy<Task<T>> is not enough on its own: it caches the faulted task (verified on .NET 10), so every later caller gets the same exception until the process restarts.

The safest default has two parts. Warm up before taking traffic, and keep an async, retrying accessor for the rare case where the value must be refreshed later. Each ecosystem has a "before traffic" hook:

// AsyncLazy that does NOT cache failures: the next caller starts a new attempt
public sealed class AsyncLazy<T>(Func<CancellationToken, Task<T>> factory)
{
    private readonly Lock _gate = new();
    private Task<T>? _task;

    public Task<T> GetAsync(CancellationToken ct = default)
    {
        lock (_gate)
        {
            if (_task is null || _task.IsFaulted || _task.IsCanceled)
                _task = factory(CancellationToken.None); // shared attempt: one caller's cancellation must not fail the others
            return _task.WaitAsync(ct);                   // each caller can still stop waiting
        }
    }
}

What validation cannot see

ValidateOnBuild, Dagger, Wire and Nest's bootstrap all prove the graph from what registrations declare. The pages on lifetimes and ecosystems showed what that catches: missing constructor parameters and captive dependencies. This section is about what it cannot catch. Several of the techniques above create opaque edges, that is, dependencies the validator cannot see:

  • A factory lambda is just Func<IServiceProvider, T>. What it will ask for is unknown until it runs (verified: a lambda that requests a missing service passes ValidateOnBuild).
  • A GetService call inside a method happens long after construction.
  • An open generic has no T yet, so there is no concrete constructor to check.
  • A singleton Func<T> captures the root. The validator sees a Func, not the scoped service it will produce.

Two habits close most of the gap. First, prefer registrations the container can see: AddSingleton<PaymentClient>() with a constructor is better than a lambda that calls new. Smoke tests catch "missing", not "captive". Resolving a singleton Func<T> does not call the Func, and resolving a service does not run its methods. A service-locator call inside a method stays invisible. Ban IServiceProvider outside the composition root (see the service locator section below) and the remaining blind spots are rare enough to review by hand.

The options pattern: typed, validated, and sometimes reloadable

The basics of typed configuration and failing the deploy on bad config are in DI Across Languages (Job 2) and Configuration, Feature Flags & Secrets. Here is the advanced part that trips people up: .NET gives you three ways to read the same options, and they deliberately see different values after a reload.

Interface Lifetime Value after the file changes Use it in
IOptions<T> Singleton Never changes; computed once on first .Value Most code. Settings that need a restart anyway
IOptionsSnapshot<T> Scoped New value per request, fixed within a request Request handlers that must see one consistent config
IOptionsMonitor<T> Singleton Always current, plus OnChange callbacks Singletons that must react (pool sizes, rate limits)

Change the file in the middle of a long request, then write an invalid value, and watch each column. This shows the verified .NET 10 behaviour: an invalid reload makes CurrentValue throw rather than keep the old value, and the file watcher often fires twice for one save.

Named options, post-configuration and cross-field validation complete the pattern. The pipeline for every options instance is Configure → PostConfigure → Validate, in registration order within each stage:

public sealed class PayOptions
{
    [Range(1, 10_000)] public int TimeoutMs { get; set; } = 2_000;
    [Range(0, 10)] public int Retries { get; set; } = 2;
}

// one options type, several named instances (one per gateway)
builder.Services.AddOptions<PayOptions>("stripe").BindConfiguration("Pay:Stripe").ValidateDataAnnotations().ValidateOnStart();
builder.Services.AddOptions<PayOptions>("adyen").BindConfiguration("Pay:Adyen").ValidateDataAnnotations().ValidateOnStart();

builder.Services.PostConfigureAll<PayOptions>(o => o.TimeoutMs = Math.Min(o.TimeoutMs, 5_000)); // runs after every binding
builder.Services.AddSingleton<IValidateOptions<PayOptions>, PayBudgetValidator>();               // rules across fields

public sealed class PayBudgetValidator : IValidateOptions<PayOptions>
{
    public ValidateOptionsResult Validate(string? name, PayOptions o) =>
        (o.Retries + 1) * o.TimeoutMs > 30_000
            ? ValidateOptionsResult.Fail($"Pay:{name}: (Retries + 1) x TimeoutMs exceeds the 30 s request budget.")
            : ValidateOptionsResult.Success;
}

public sealed class StripeGateway(IOptionsMonitor<PayOptions> options)
{
    private PayOptions Current => options.Get("stripe");   // named options: IOptions<T>.Value only returns the unnamed one
}

Reloadable settings are worth it for

  • Limits and thresholds an operator may tune during an incident: rate limits, timeouts, log levels.
  • Values that are read on every call anyway, so a reload costs nothing extra.
  • Cases where you have a test proving that a bad reload is rejected or contained.

Avoid reloading when

  • The value builds something expensive at startup: connection strings, pool sizes, certificates. A reload silently does nothing unless you rebuild the object.
  • Two values must change together. A reader can see one updated and the other not.
  • A restart is cheap and safer. Most settings should simply use IOptions<T>.

Other ecosystems reload differently. Spring rebinds @ConfigurationProperties and refreshes @RefreshScope beans when Spring Cloud publishes an EnvironmentChangeEvent. Go code usually keeps an atomic.Pointer[Config] that a file or remote watcher swaps after validating the new value. Python apps rebuild a pydantic-settings object and swap one reference. NestJS's ConfigModule reads at startup, so reloading needs your own provider. In every language the safe shape is the same: validate first, then swap one immutable snapshot atomically, and let readers take the current snapshot once per unit of work.

Swapping dependencies in tests: override the root, not the code

Unit tests do not need a container at all: you pass fakes to the constructor, as shown in DI Fundamentals. The container override is for integration tests. You start the real app with its real composition root, and replace only the edges that leave the process: the payment gateway, the clock, the email sender. Everything in between is the production wiring, so a test also proves the registrations.

"Add the fake" is not "replace the real one" when there is a list. In .NET, s.AddSingleton<INotifier, FakeNotifier>() makes the fake win a single resolve, because the last registration wins. But a fan-out that injects IEnumerable<INotifier> still receives the real email and SMS notifiers too, so the test sends real messages. Replace does not help either: it removes only the first match (verified). Use RemoveAll<T>() before adding fakes. In Python, forgetting dependency_overrides.clear() leaks a fake into every later test in the session. In Spring, every different set of @MockitoBeans creates a new application context, so give test classes shared base configurations to keep the context cache effective.

Service locator: allowed at the edges, banned in the middle

DI Fundamentals explains why a class that pulls from IServiceProvider hides its dependencies. Several techniques on this page legitimately touch the provider: a keyed router, a factory, a background worker opening scopes, a plugin host. So the useful rule is about where the provider may appear, not "never use it".

Recognize a locator in disguise: a constructor parameter of type IServiceProvider, ApplicationContext, Injector, ModuleRef or a whole container object; a GetService call inside a loop or an if; a "context" or "services" bag object passed to every method; a test that has to build a container just to construct one class.

Resolution performance: what a container really costs

Containers are fast enough that resolution is almost never your bottleneck. These numbers come from a rough Release-mode loop on .NET 10 on one laptop. They show orders of magnitude, not a benchmark:

Operation Approximate cost What it means
new the same 4 objects by hand ~27 ns The baseline
Resolve a transient with 3 dependencies ~120 ns About 4× hand-wiring, still nothing next to one database call (~1 ms)
Resolve an already-created scoped service ~43 ns A dictionary lookup in the scope
CreateScope + resolve + Dispose ~350 ns Per-request overhead of scoping
First resolve on a new provider (cold, includes JIT) ~0.6 ms Paid once per service type at startup

Where DI really costs time:

  • Startup. Classpath scanning (Spring), reflection over every constructor, building proxies, and eager singletons. Dagger and Wire move this cost to compile time. Spring AOT and GraalVM, and .NET Native AOT, which MS.DI supports without runtime code generation, reduce it.
  • Big per-request graphs. A request-scoped provider in NestJS makes its whole dependency chain request-scoped, so every request rebuilds it.
  • Leaks, not lookups. Disposable transients resolved from the root are kept until shutdown (verified), and a captured Func<T> can create objects nobody disposes.

Measure before optimizing. Then prefer singletons for stateless services, never resolve inside a hot loop (resolve once, then reuse), and warm the graph at startup. Performance Cadence and Performance Patterns show how to measure.

When to use each technique, and when not to

Reach for it when

  • Multi-registration: a real fan-out or pipeline where every implementation must run.
  • Keyed: a small, closed set chosen by a value known at the call site.
  • Factories, Lazy: a meaningful share of requests never need an expensive dependency, or you need runtime arguments.
  • Decorators: one cross-cutting concern around one abstraction, in an order you want to see in code.
  • Open generics: one implementation that is truly identical for every T.
  • Tenant scopes: objects whose configuration differs per tenant and must be isolated.
  • Options monitor: an operator must change a value without a restart.
  • Container overrides: integration tests that replace only out-of-process edges.

Skip it when

  • Multi-registration: ordering matters but nobody documents it. Use an explicit pipeline type instead.
  • Keyed: the key arrives from the user. Use a router with validation and a default.
  • Factories, Lazy: every request opens it anyway. Fix the constructor instead.
  • Decorators: the behaviour needs the inner object's private state. Change the class.
  • Open generics: half the types need a special case. Write explicit closed types.
  • Tenant scopes: the only difference is a connection string. Use a scoped tenant context.
  • Options monitor: the value builds a pool or client at startup. Restart instead.
  • Container overrides: a plain unit test with constructor arguments would do.

Every technique on this page adds indirection: one more place a reader must look to know what runs. Use the simplest wiring that expresses the variation, and write down the reason in the registration.

Pitfalls and production war stories

The retry that hammered a dead database. A team added Decorate<IOrderRepository, RetryRepo>() after the caching decorator, which made retry the outermost layer. During a database outage every request retried three times, and each attempt re-checked the cache, logged and recorded metrics. Database connections tripled at the worst moment. Fix: put retry innermost, around the database call only, add a circuit breaker, and pin the decorator order with a test that resolves the service and asserts the type chain.

The token cache that never recovered. Lazy<Task<Keys>> fetched signing keys on first use. The identity provider had a 30-second blip just as one instance started. The faulted task was cached, so every authenticated request on that instance failed until someone restarted it hours later, while its health check was green. Fix: an AsyncLazy that drops failed tasks, warm-up before readiness, and a health check that exercises the keys.

The test that emailed customers. An integration test registered FakeNotifier with AddSingleton and asserted that "a notification was sent". It passed. It also sent a real email to the test customer's address, because the order flow injected IEnumerable<INotifier> and still received the SMTP notifier. Fix: RemoveAll<INotifier>() before adding fakes, and point the test environment's SMTP at a sink.

The config reload that half-applied. An operator lowered Pay:TimeoutMs during an incident. The retry policy used IOptionsMonitor and changed immediately. The HttpClient timeout had been set from IOptions at startup and did not. For twenty minutes the retry budget assumed 500 ms calls while each call could still take 5 s. Fix: decide per setting whether it reloads, document it next to the option, and rebuild dependent objects in OnChange (or require a restart).

Best-practice checklist

  • [ ] Every variation is a registration the container can see. Factory lambdas and GetService calls are rare and commented.
  • [ ] Libraries use TryAdd and TryAddEnumerable. Applications register their choices after library calls.
  • [ ] Keyed lookups by runtime value go through a router that validates the key at startup and has an explicit default.
  • [ ] Factories are registered with the shortest lifetime of what they create. Long-lived code uses IServiceScopeFactory.
  • [ ] Decorator order is deliberate (observability → caching → resilience → real) and pinned by a test.
  • [ ] Open generics are covered by a smoke test that closes them for every type you use.
  • [ ] Constructors do no I/O. Async initialization happens in a warm-up step before readiness, with bounded retries.
  • [ ] Options are validated on start. Each setting is documented as reloadable or restart-only.
  • [ ] Integration tests replace only out-of-process edges, with RemoveAll (or the ecosystem's equivalent) before adding fakes.
  • [ ] IServiceProvider appears only in the composition root and infrastructure, enforced by an architecture test.

Self-check

1. You call Decorate<IRepo, CachingRepo>() and then Decorate<IRepo, LoggingRepo>(). Are cache hits logged?

Yes. Each Decorate wraps what is registered at that moment, so the last call is outermost: Logging(Caching(Sql)). Every call enters Logging first. Calls the cache answers return before reaching Sql, but they have already passed through Logging. Reverse the calls and cache hits become invisible in the logs.

2. A singleton Func<AppDbContext> passes ValidateOnBuild and ValidateScopes. Why does it fail later?

A singleton is created by the root provider, so the lambda's sp is the root. The validator sees a registration of type Func<AppDbContext> and cannot look inside the lambda. When the function is called, it asks the root for a scoped service and throws "Cannot resolve scoped service 'AppDbContext' from root provider." Without ValidateScopes, it silently creates a captive AppDbContext shared by everyone. Inject IServiceScopeFactory and create a scope per unit of work.

3. A request starts, then the config file changes, then the same request reads its options again. What do IOptions, IOptionsSnapshot and IOptionsMonitor return?

IOptions returns the value computed on its first read and never changes. IOptionsSnapshot returns the old value: it is computed once per scope, so one request never sees two configs. IOptionsMonitor.CurrentValue returns the new value, or throws OptionsValidationException if the new value is invalid.

4. Why is Lazy<Task<T>> risky for initialization that calls a network service?

Lazy<T> caches whatever its factory returned, and here that is a Task. If the first attempt fails, the cached task is faulted, and every later await rethrows the same exception for the life of the process. Use an async lazy that discards faulted or cancelled tasks, and do the first attempt during warm-up so failures stop the rollout instead of failing users.

5. NestJS says it cannot resolve PaymentGateway "in the OrdersModule context", but OrdersModule imports PaymentsModule. What is missing?

PaymentsModule must list PaymentGateway in its exports. Importing a module gives access only to what it exports; everything else is private. Do not "fix" it by making PaymentsModule @Global(), which hides the dependency instead of declaring it.

6. In which situations is a feature flag in a registration (if (flag) services.Add…) correct?

Only when the choice is meant to be fixed for the life of the process: the environment, the edition, or a deployment-time setting. Registrations run once at startup, so a runtime flag read there never turns off without a restart. For per-request or runtime choices, register all implementations and choose in a router that reads the flag (or the options monitor) on each call.
