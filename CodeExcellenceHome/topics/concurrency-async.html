Concurrency & Async

Threads, thread pools, async/await state machines, goroutines and channels, the event loop, locks vs lock-free, and the classic deadlocks, all animated.

Intermediate → Expert~75 min studyBuilds on: Cross-Language Mental ModelsUpdated 2026-11-03

The problem: three bugs that only show up under load

A checkout service passes every test. In production, three separate bugs show up within one month.

  1. The counter is wrong. A dashboard says 9,812 orders were placed today, but the database has 10,004. The in-memory counter used count++ from many request threads. Two threads read 41, both wrote 42, and one order disappeared from the count. No exception was thrown and no log line was written.
  2. The app freezes. A developer "simplified" a desktop admin tool by calling GetOrderAsync(id).Result inside a button handler. It worked on their machine because the data was cached. On the first cache miss in production, the window froze forever, at 0% CPU.
  3. Latency explodes at 0% CPU. The same .Result pattern moved into a web API. At 50 requests per second, p99 latency went from 80 ms to 40 seconds. CPU was at 6%. The thread pool had run out of threads, and every thread was blocked waiting for a continuation that needed a thread to run.

These are the three classic concurrency failures: a race, a deadlock and starvation. All three come from one gap: not knowing which thread runs which code, when. This page builds that picture across C#, Java, Python, Go and TypeScript and animates each failure until you can see it coming.

The rule. Use concurrency to overlap waiting and parallelism to use more cores. Never block a thread while you wait for asynchronous work. Never let two threads touch the same mutable state without a happens-before edge (a lock, an atomic or a channel). Bound every queue, fan-out and pool, and pass cancellation all the way down.

Recognize a concurrency bug when

  • A number is slightly wrong under load and always right in tests (lost update).
  • The process hangs at 0% CPU, and a dump shows threads waiting on each other (deadlock).
  • Latency climbs while CPU stays low, and the thread count keeps creeping up (thread-pool starvation).
  • A bug disappears when you add a log line or attach a debugger: timing changed, so the interleaving changed.
  • A test is "flaky" only on the CI machine with more (or fewer) cores.

This is the concurrency chapter of the performance track. Performance Cadence covers how to measure (goals, profiles, benchmarks); this page covers the execution models you are measuring. Memory and GC covers the other half of runtime behaviour. Batching, pooling and backpressure as optimisation patterns live in Performance Patterns. The language basics come from Language Mental Models.

Concurrency is not parallelism

These two words are used interchangeably, and that causes bad decisions.

  • Concurrency is about structure: several tasks are in progress at the same time, and their lifetimes overlap. One cook making three dishes is concurrent. While the pasta water heats, the cook chops onions.
  • Parallelism is about execution: several things literally run at the same instant on different cores. Three cooks are parallel.

You can have concurrency without parallelism (a JavaScript event loop on one thread serves 10,000 sockets) and parallelism without much concurrency (one big matrix multiply split across 16 cores).

The practical question is always: what is the work waiting on?

Work is mostly… What helps What does not help
Waiting on I/O (HTTP, database, disk, queue) Concurrency: async/await, goroutines, virtual threads, an event loop More cores. The CPU is idle anyway.
Computing (parsing, image work, compression, ML) Parallelism: one worker per core, data parallel loops, processes in Python More async. await does not make arithmetic faster.
Waiting on a lock or a shared resource Less sharing: partition, shard, immutable data, message passing More threads. They only queue on the same lock.
Waiting on a slow downstream with a limit A concurrency limit (semaphore, bounded pool) plus backpressure Unbounded fan-out. It overloads the downstream and gets slower.

Five execution models on the same work

Every runtime picks a point in the same design space: how many OS threads exist, and what happens to a thread when its task waits. The visualizer runs the same tasks under five models. Each task is a list of CPU segments (C3 = 3 ticks of computing) and I/O segments (I4 = 4 ticks of waiting). Step through, then read the final frame, which compares every model on the same input.

Things to try:

  • Keep the default (three tasks, mostly I/O) and switch between sequential and event loop. The event loop uses one thread and still overlaps all the waits.
  • Use C5; C5; C5 with 2 cores. Now event loop is no better than sequential, because nothing waits. Threads and async on a pool use both cores; Python threads + GIL cannot.
  • Use four tasks of C1 I6 C1. Thread per task finishes as fast as async, but needs four blocked OS threads. At 10,000 tasks that is 10,000 stacks.

Threads, thread pools and work stealing

An OS thread is the unit the kernel schedules. It has its own stack, registers and thread-local storage. It is expensive in three ways:

  • Memory. Each thread reserves a stack: 1 MB by default for .NET and Java on Windows, and often 8 MB of virtual address space on Linux (most of it never touched). 10,000 threads is gigabytes of reservation.
  • Creation. Creating a thread is a system call plus allocating the stack: tens of microseconds.
  • Context switches. When more threads are runnable than there are cores, the kernel swaps them in and out. Each switch costs a few microseconds and, worse, cold CPU caches.

So nobody creates a thread per work item. A thread pool keeps a few threads alive (roughly one per core for CPU work) and feeds them a queue of work items. The pool's queue design matters a lot. One shared queue needs a lock that every push and pop goes through, so with many cores the lock itself becomes the bottleneck. Modern pools give each worker its own double-ended queue (deque):

  • The worker pushes and pops at the newest end (LIFO). That needs no lock, and the newest item's data is still in the cache.
  • An idle worker steals from the oldest end of a victim's deque. Old items in a divide-and-conquer job are the big unsplit pieces, so one steal gets a lot of work. Thieves and the owner work at opposite ends, so they rarely collide.

Run the default, then switch to one shared global queue with the same inputs. Count the red lock-wait cells. This is why .NET's ThreadPool (per-thread local queues since .NET 4), Java's ForkJoinPool (which also backs parallel streams and virtual threads), Go's scheduler and Rust's Tokio all use work stealing.

What the pool does not know

A pool sizes itself for CPU work: about one thread per core. It cannot tell a thread that is computing from a thread that is blocked in Thread.Sleep, .Result or a synchronous socket read. A blocked thread is a lost core. The .NET pool notices that its queue is not draining and slowly injects extra threads. The JVM ForkJoinPool can compensate only through ManagedBlocker. Neither can save you from blocking at scale. That is the root of thread-pool starvation, covered below.

// Divide and conquer: ForkJoinPool with work stealing.
class SumTask extends RecursiveTask<Long> {
    final int[] a; final int lo, hi;
    SumTask(int[] a, int lo, int hi) { this.a = a; this.lo = lo; this.hi = hi; }
    protected Long compute() {
        if (hi - lo <= 10_000) { long s = 0; for (int i = lo; i < hi; i++) s += a[i]; return s; }
        int mid = (lo + hi) >>> 1;
        SumTask right = new SumTask(a, mid, hi);
        right.fork();                                      // push onto my deque
        return new SumTask(a, lo, mid).compute() + right.join();
    }
}
long sum = ForkJoinPool.commonPool().invoke(new SumTask(data, 0, data.length));

from concurrent.futures import ProcessPoolExecutor

def count_primes(lo: int, hi: int) -> int:
    return sum(1 for n in range(max(lo, 2), hi) if all(n % d for d in range(2, int(n**0.5) + 1)))

# CPU-bound: processes, because the GIL lets one thread run Python bytecode at a time.

    ranges = [(i, i + 50_000) for i in range(0, 200_000, 50_000)]

// Go has no pool API: goroutines are cheap and the runtime is the pool.
// You bound parallelism yourself, here with a fixed number of workers.
func sumParallel(a []int) int {
    workers := runtime.GOMAXPROCS(0)
    parts := make([]int, workers)
    var wg sync.WaitGroup
    chunk := (len(a) + workers - 1) / workers
    for w := 0; w < workers; w++ {
        lo, hi := w*chunk, min((w+1)*chunk, len(a))
        if lo >= hi {
            break
        }
        wg.Add(1)
        go func() {
            defer wg.Done()
            s := 0
            for _, v := range a[lo:hi] {
                s += v
            }
            parts[w] = s // each goroutine writes its own slot: no sharing
        }()
    }
    wg.Wait()
    total := 0
    for _, s := range parts {
        total += s
    }
    return total
}

.NET: Task, async/await and the thread pool

What the compiler does with await

An async method is not run on "a new thread". The C# compiler rewrites it into a state machine: a struct with a state field, fields for every local that lives across an await, and a MoveNext() method containing your code cut into pieces at each await.

Four facts follow from that picture, and most async bugs come from forgetting one of them:

  1. It starts synchronously. Everything before the first incomplete await runs on the caller's thread. A "fire and forget" async method that does 200 ms of CPU work before its first await blocks the caller for 200 ms.
  2. An already-completed await does not suspend. If the awaited task is done (cache hit, buffered data), execution just continues: no allocation and no thread hop.
  3. After a real suspension, the rest may run on a different thread. Thread-local state, [ThreadStatic] fields and locks taken before the await do not come with you. You cannot await inside a lock block for exactly this reason.
  4. Where the continuation runs is decided by the captured context. That is the SynchronizationContext (UI frameworks, old ASP.NET) or the TaskScheduler. With neither, it runs on the thread pool.

Step through the state machine, the queues and the threads. Start with the default (a UI thread calling .Result), which deadlocks. Then change one input at a time.

What to notice:

  • UI + .Result + plain await = deadlock. The continuation is posted to the UI thread, and the UI thread is blocked waiting for that same continuation.
  • The same code with "both hit a cache" does not deadlock. Nothing really suspends. This is why the bug ships: it only appears on the first slow call.
  • ConfigureAwait(false) inside the library avoids that deadlock, because the continuation goes to the pool. The UI is still frozen while it waits, though. The real fix is to await in the handler.
  • "none" (ASP.NET Core) has no SynchronizationContext, so .Result cannot deadlock this way. It still burns a pool thread per request, which leads straight to the next problem.

Thread-pool starvation

Blocking on async code (.Result, .Wait(), GetAwaiter().GetResult()) inside a pool thread is called sync over async. It holds a thread for the whole I/O. It also needs a second pool thread to run the inner method's continuation, and that continuation waits in the same FIFO queue as new requests. Under load, every thread is blocked, new requests take the threads that free up and block them too, and the pool only adds threads slowly. Throughput collapses at near-zero CPU.

Compare the two modes with the same inputs: async serves the same load with the starting threads and a flat latency, while sync over async grows the pool and still falls behind. In a real service the symptoms are:

  • dotnet-counters monitor -n MyApp System.Runtime shows ThreadPool Queue Length above zero and climbing, and ThreadPool Thread Count rising by about one per second.
  • CPU is low, yet latency is high.
  • A dump (dotnet-dump analyze, then clrstack -all) shows hundreds of threads in Task.Wait or ManualResetEventSlim.Wait.

"Just raise the minimum thread count"

ThreadPool.SetMinThreads(500, 500) makes the graph look better for a while, because the pool skips its slow injection. You now have 500 blocked threads (500 MB of reserved stacks, more context switches), and the cliff simply moves to a higher load. Use it as a stopgap during an incident at most. The fix is to make the call chain async all the way up.

Async all the way: the rules

public class OrdersController : ControllerBase
{
    [HttpGet("{id}")]
    public IActionResult Get(int id)
    {
        var order = _repo.GetOrderAsync(id).Result;   // blocks a pool thread for the whole query
        return Ok(order);
    }

    [HttpPost]
    public async void Post(OrderDto dto)               // async void: exceptions crash the process,
    {                                                  // and nobody can await it
        await _repo.SaveAsync(dto);
    }

    public Task<int> ParseAll(string[] files) =>
        Task.Run(async () => {                         // pointless hop: the work is I/O
            int n = 0;
            foreach (var f in files) n += (await File.ReadAllLinesAsync(f)).Length;
            return n;
        });
}

public class OrdersController : ControllerBase
{
    [HttpGet("{id}")]
    public async Task<ActionResult<Order>> Get(int id, CancellationToken ct)
    {
        var order = await _repo.GetOrderAsync(id, ct); // thread returns to the pool during the query
        return order is null ? NotFound() : Ok(order);
    }

    [HttpPost]
    public async Task<IActionResult> Post(OrderDto dto, CancellationToken ct)
    {
        await _repo.SaveAsync(dto, ct);                // exceptions flow to the caller
        return Accepted();
    }

    public async Task<int> ParseAll(string[] files, CancellationToken ct)
    {
        var counts = await Task.WhenAll(files.Select(async f =>
            (await File.ReadAllLinesAsync(f, ct)).Length));
        return counts.Sum();
    }
}

The rules, each with its reason:

  • Never block on a Task (.Result, .Wait(), .GetAwaiter().GetResult()) in code that can run on the pool or a UI thread. The only safe places are Main before anything async starts (and C# has async Task Main anyway) or a dedicated thread you own.
  • No async void except event handlers. Exceptions in async void go to the SynchronizationContext or crash the process, and the caller cannot await completion.
  • Use Task.Run for CPU work, not for I/O. It moves work to the pool. Wrapping an already-async call in Task.Run adds a hop and hides nothing.
  • Accept and pass a CancellationToken on every async API. ASP.NET Core gives you HttpContext.RequestAborted as an action parameter.
  • Do not hold a lock across an await. Use SemaphoreSlim.WaitAsync for async mutual exclusion.

ConfigureAwait(false): when it matters

ConfigureAwait(false) means "I do not need to resume on the captured context". Guidance as of .NET 8+:

Code Use ConfigureAwait(false)? Why
General-purpose library (NuGet package) Yes, on every await It might be called from a UI app or legacy ASP.NET; avoids the deadlock above and an unnecessary hop to the UI thread.
ASP.NET Core app code Optional, no effect There is no SynchronizationContext. Many teams omit it for readability.
UI app code (WPF, WinForms, MAUI) No, where you touch UI afterwards You want to resume on the UI thread to update controls.
Code after the await that needs HttpContext (classic ASP.NET) No The context carries the request's culture and identity.

ConfigureAwait(false) only affects the await it is on, and only when that await actually suspends. One plain await deeper in the chain is enough to capture the context again. .NET 8 added ConfigureAwaitOptions (SuppressThrowing, ForceYielding) for advanced cases.

Task vs ValueTask

Task<T> is a class, so every asynchronously completing call allocates one. For methods that usually complete synchronously (a buffered stream read, a cache hit), ValueTask<T> is a struct that wraps either a result or a task, so the fast path allocates nothing.

Use ValueTask<T> when

  • The method is on a hot path and usually completes synchronously (profiling shows Task allocations).
  • You implement an interface that already uses it: IAsyncEnumerator<T>.MoveNextAsync, IAsyncDisposable.DisposeAsync, Stream.ReadAsync(Memory<byte>).

Rules you must follow with ValueTask

  • Await it exactly once. Never await it twice or from two places.
  • Never call .Result unless IsCompletedSuccessfully is true.
  • Never call WhenAll on it directly; call .AsTask() first.
  • Default to Task<T> for everything else. It is simpler and safe to cache, share and await many times.

Java: platform threads, virtual threads and structured concurrency

For 25 years, Java's answer was one platform (OS) thread per request plus pools. It is simple: blocking code, readable stack traces, debuggers that work. But it caps a server at a few thousand concurrent requests, so the ecosystem built reactive libraries (CompletableFuture, Reactor, RxJava) that are fast but hard to read and debug.

Virtual threads (final in Java 21, JEP 444) bring back the simple style at async scale. A virtual thread is a Thread object scheduled by the JVM, not the OS. When it blocks on I/O, a lock or sleep, the JVM unmounts it: its stack frames are copied to the heap and the underlying carrier thread (from a ForkJoinPool with one carrier per core) runs another virtual thread. When the I/O completes, the virtual thread is mounted again, possibly on a different carrier. That is the same M:N idea as Go.

// One virtual thread per task. Blocking calls are fine: they unmount, not block a carrier.
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    List<Future<Order>> futures = ids.stream()
        .map(id -> executor.submit(() -> orderClient.fetch(id)))   // plain blocking HTTP call
        .toList();
    for (var f : futures) process(f.get());
}   // close() waits for all tasks

// Limit concurrency against a downstream: a Semaphore, NOT a small pool of virtual threads.
private static final Semaphore DB_PERMITS = new Semaphore(20);
Order load(long id) throws InterruptedException {
    DB_PERMITS.acquire();
    try { return repository.findById(id); }
    finally { DB_PERMITS.release(); }
}

// CompletableFuture: the pre-Loom async style, still useful for composition.
CompletableFuture<Order> order = CompletableFuture.supplyAsync(() -> orders.fetch(id), ioPool);
CompletableFuture<Price> price = CompletableFuture.supplyAsync(() -> pricing.quote(sku), ioPool);
CompletableFuture<Invoice> invoice = order
    .thenCombine(price, Invoice::new)           // runs when both complete
    .orTimeout(2, TimeUnit.SECONDS)              // Java 9+
    .exceptionally(ex -> Invoice.failed(ex));
// Pass an explicit executor: the default commonPool is sized for CPU work.

// Structured concurrency (preview: JDK 21-24 shape shown; JDK 25 uses StructuredTaskScope.open()).
// Subtasks cannot outlive the scope; if one fails, the others are cancelled.
Invoice build(long id, String sku) throws Exception {
    try (var scope = new StructuredTaskScope.ShutdownOnFailure()) {
        Subtask<Order> order = scope.fork(() -> orders.fetch(id));
        Subtask<Price> price = scope.fork(() -> pricing.quote(sku));
        scope.join().throwIfFailed();            // waits for both; first failure cancels the other
        return new Invoice(order.get(), price.get());
    }
}

Virtual-thread traps

  • Pinning. Before Java 24 (JEP 491), blocking inside a synchronized block pinned the virtual thread to its carrier, so a few pinned threads could exhaust all carriers. On Java 21–23, prefer ReentrantLock around blocking calls, and find pinning with -Djdk.tracePinnedThreads=full or the JFR event jdk.VirtualThreadPinned. Native calls (JNI) still pin.
  • Do not pool virtual threads. They are cheap; create one per task. A pool of 10 virtual threads is just a slow way of writing a semaphore.
  • ThreadLocal caches (for example one SimpleDateFormat per thread) become one per task, so with a million virtual threads you get a million copies. Use ScopedValue (preview) or immutable shared objects.
  • CPU-bound work gains nothing. There are still only as many carriers as cores.

Python: the GIL, threads, processes and asyncio

CPython protects its interpreter state (reference counts, object internals) with the Global Interpreter Lock. Only the thread holding the GIL executes Python bytecode. Threads are real OS threads, but:

  • I/O releases the GIL. socket.recv, time.sleep, file reads and most C extensions that do heavy work (NumPy, hashlib on large inputs, zlib) release it. So threads do overlap I/O.
  • Pure-Python CPU work does not run in parallel. A thread holding the GIL is asked to drop it every switch interval (sys.getswitchinterval(), 5 ms by default). Two CPU-bound threads just take turns, plus switching overhead. Use multiprocessing or ProcessPoolExecutor: separate interpreters, separate GILs, at the cost of pickling the arguments and results.
  • The GIL does not make your code thread-safe. counter += 1 is several bytecodes (load, add, store), and a switch can happen between them. You still need threading.Lock.

Free-threaded Python. Python 3.13 ships an optional, experimental free-threaded build (PEP 703, usually installed as python3.13t) with no GIL. Python 3.14 makes it officially supported (PEP 779) but still optional, not the default. Pure-Python code can then use all cores with threads; single-threaded code runs somewhat slower, and C extensions must declare support or the GIL is re-enabled at import. Check with sys._is_gil_enabled(). Plan for it, but do not assume it in production yet.

asyncio is Python's event loop. One thread runs coroutines; await on I/O suspends the coroutine and the loop runs another. It scales to tens of thousands of sockets in one thread, as long as nothing blocks the loop. A single requests.get() or time.sleep(1) inside a coroutine freezes every other coroutine for that long.

import asyncio

async def fetch(i: int) -> str:
    await asyncio.sleep(0.1)          # stands in for an HTTP call with an async client (httpx, aiohttp)
    if i == 3:
        raise ValueError(f"job {i} failed")
    return f"result {i}"

async def main() -> None:
    # TaskGroup (3.11+): structured concurrency. If one task fails, the rest are cancelled,
    # and all errors come back as an ExceptionGroup.
    try:
        async with asyncio.TaskGroup() as tg:
            tasks = [tg.create_task(fetch(i)) for i in range(5)]
    except* ValueError as eg:
        print("failed:", [str(e) for e in eg.exceptions])

    # A deadline for a whole block (3.11+).
    try:
        async with asyncio.timeout(0.05):
            await fetch(0)
    except TimeoutError:
        print("timed out")

    # Blocking code must leave the loop: to_thread (3.9+) runs it on a worker thread.
    data = await asyncio.to_thread(lambda: sum(range(1_000_000)))
    print(data)

asyncio.run(main())

# The GIL does not protect compound operations.
import threading

counter = 0
lock = threading.Lock()

def unsafe(n: int) -> None:
    global counter
    for _ in range(n):
        counter += 1          # LOAD, ADD, STORE: a switch can land in between

def safe(n: int) -> None:
    global counter
    for _ in range(n):
        with lock:
            counter += 1

for fn in (unsafe, safe):
    counter = 0
    threads = [threading.Thread(target=fn, args=(200_000,)) for _ in range(4)]
    for t in threads: t.start()
    for t in threads: t.join()
    print(fn.__name__, counter)   # unsafe may print less than 800000 (more likely on 3.13t)

Go: goroutines, channels and the G/M/P scheduler

A goroutine is a function running on Go's own scheduler. It starts with a 2 KB stack that grows and shrinks as needed, so a server can run hundreds of thousands of them. You write plain blocking code (conn.Read, time.Sleep, <-ch), and the runtime turns each block into a cheap park/unpark. There is no async keyword, so there are no "colored" functions: any function can block.

The scheduler has three kinds of objects:

  • G: a goroutine (stack, instruction pointer, status).
  • M: an OS thread ("machine").
  • P: a processor, a scheduling slot with its own local run queue. There are exactly GOMAXPROCS Ps (the number of CPUs by default; since Go 1.25 it also respects container CPU limits). An M must hold a P to run Go code.

Step through it. Goroutine scripts use R (run), N (wait on the network) and S (a blocking syscall such as a file read):

Try GOMAXPROCS = 1 with the default goroutines: still correct, but everything is interleaved on one P. Then try the second preset (S5 syscalls) and watch the M count rise above the P count. Since Go 1.14, goroutines are also preempted asynchronously, so a tight loop without function calls can no longer hog a P forever.

Channels and select

"Do not communicate by sharing memory; instead, share memory by communicating." A channel is a typed, synchronised queue.

  • An unbuffered channel (make(chan T)) is a rendezvous: the send blocks until a receiver takes the value. That is a synchronisation point as well as a data transfer.
  • A buffered channel (make(chan T, 64)) accepts up to 64 values without a receiver, then blocks the sender. That is backpressure for free.
  • select waits on several channel operations and takes whichever is ready first. With ctx.Done() as one case, every wait becomes cancellable.
func worker(ctx context.Context, jobs <-chan Job, results chan<- Result) error {
    for {
        select {
        case <-ctx.Done():
            return ctx.Err()                       // cancelled or deadline exceeded
        case j, ok := <-jobs:
            if !ok {
                return nil                         // producer closed the channel: done
            }
            r, err := process(ctx, j)
            if err != nil {
                return err
            }
            select {                               // the send must be cancellable too,
            case results <- r:                     // or a slow consumer leaks this goroutine
            case <-ctx.Done():
                return ctx.Err()
            }
        }
    }
}

Goroutine leaks

A goroutine blocked forever on a channel that nobody will ever read or close is never collected: its stack and everything it references stay alive. The classic case is a request handler that starts a goroutine to call a backend, then times out and returns. The goroutine finishes later, tries results <- r on an unbuffered channel nobody reads, and blocks forever. Fixes: give the channel a buffer of 1, or select on ctx.Done() for every send and receive. Watch runtime.NumGoroutine() or the goroutine profile in pprof for steady growth.

JavaScript and TypeScript: the event loop

JavaScript runs your code on one thread. There are no data races between two pieces of JS, because two pieces of JS never run at the same instant. Concurrency comes from the event loop: the host (browser or Node) does I/O and timers in the background and queues callbacks for the single thread to run.

Two queues decide the order, and the difference between them explains almost every "why did this print first?" question:

  • Task queue (macrotasks): timer callbacks, I/O callbacks, UI events, MessageChannel. The loop runs one task at a time.
  • Microtask queue: promise reactions (.then, the code after await) and queueMicrotask. After each task, the loop drains the whole microtask queue, including microtasks queued while draining, before it takes the next task or renders.

Pick a program and predict the console output before you press Run. Each program's output was checked against real Node.

Choose the right combinator:

Combinator Resolves when Rejects when Use for
Promise.all all fulfil the first rejection (others keep running) independent calls that must all succeed
Promise.allSettled all settle never best-effort batches; inspect each result
Promise.any the first fulfils all reject (AggregateError) redundant replicas, hedged requests
Promise.race the first settles the first settles with a rejection timeouts (prefer AbortSignal.timeout)

None of the combinators cancel anything

When Promise.all rejects, the other promises keep running. A promise is a result, not a handle to the work. To stop the work, pass an AbortSignal to every call and abort it. AbortSignal.timeout(ms) and AbortSignal.any([a, b]) (Node 20+, modern browsers) build deadlines and combined cancellation without hand-written timers.

Shared state: races, locks and atomics

The lost update, step by step

count++ looks like one operation. The CPU does three: read the value into a register, add one, write it back. If another thread writes in between your read and your write, you overwrite its update with a value computed from stale data. This is a data race: two threads touch the same memory, at least one writes, and nothing orders the accesses.

The scheduler string decides who runs each step (A or B). The default schedule loses an update. Change the mode to a lock, a CAS loop or Interlocked.Increment and the final count is always right, whatever the schedule. Then type your own schedules and try to break them.

What each fix does:

  • Lock. Only one thread can be between lock and unlock at a time, so read-add-write becomes one indivisible step as seen by other threads that also take the lock. The cost is waiting: B parks while A holds the lock.
  • Compare-and-swap (CAS). A single CPU instruction (lock cmpxchg on x86): "if the value is still 41, make it 42, and tell me whether you did". If someone else changed it, retry with the new value. No thread ever waits on another; one may just retry. This is lock-free.
  • Atomic increment. The hardware does read-add-write as one instruction (lock xadd). It is the fastest option for a single counter.

The same three fixes in every language:

private int _count;
private readonly object _gate = new();                // .NET 9+: private readonly Lock _gate = new();

public void AddMaxCas(int candidate)                  // CAS loop for something with no built-in atomic

Async code has races too, even on one thread

The TypeScript example oversells with no threads at all. Any await between a check and an act is a gap where another task can run. The same bug appears with C# async methods on a single-threaded SynchronizationContext and with Python asyncio. Fix it by doing the check and the act with no await in between, by using an async lock (SemaphoreSlim(1,1), asyncio.Lock), or best of all by letting the database enforce it: UPDATE stock SET n = n - 1 WHERE id = @id AND n > 0 and check the affected row count.

Rules for locks that do not hurt

  • Keep the critical section short: no I/O, no logging, no callbacks into unknown code inside a lock.
  • Lock on a private object, never on this, a Type or an interned string that outside code can also lock.
  • A read-write lock is slower than a plain mutex when sections are short. Measure before switching.
  • Prefer not sharing to any lock: thread-local accumulation, partitioning by key, or one owner per piece of state.

Deadlock: the cycle

A deadlock needs four conditions at once (the Coffman conditions): mutual exclusion, hold and wait (a thread holds one lock while waiting for another), no preemption (locks are not taken away), and a circular wait. Remove any one and deadlock is impossible. In practice you remove the cycle.

The dining philosophers: N threads sit in a ring with one lock between each pair, and each needs both neighbouring locks. With the naive strategy and a fair scheduler, everyone takes their left lock and the cycle closes. Switch to global order (the last thread takes the lower-numbered lock first, which breaks the ring) or tryLock + back-off (give up your lock if the second is busy, wait a random time, retry; watch for livelock, where everyone keeps backing off in step).

// Transfer locks the source first, then the destination.
// Transfer(a, b) and Transfer(b, a) at the same time: each holds one, waits for the other.
public static void Transfer(Account from, Account to, decimal amount)
{
    lock (from)
    {
        lock (to)
        {
            from.Balance -= amount;
            to.Balance += amount;
        }
    }
}

// Always lock in a global order (here: by Id), whatever the direction of the transfer.
public static void Transfer(Account from, Account to, decimal amount)
{
    var (first, second) = from.Id < to.Id ? (from, to) : (to, from);
    lock (first.Gate)
    {
        lock (second.Gate)
        {
            from.Balance -= amount;
            to.Balance += amount;
        }
    }
}
// Better still for money: one database transaction, and let the database detect deadlocks.

Other deadlock shapes you will meet:

  • Sync over async on a single-threaded context (shown in the await visualizer): a thread waits for a continuation that only it can run.
  • Lock plus callback. You hold a lock and raise an event; the handler calls back into a method that takes another lock, which a second thread holds while waiting for yours.
  • Pool-induced deadlock. All N threads of a bounded pool run tasks that submit a subtask to the same pool and wait for it. The subtasks never get a thread.
  • Database deadlocks. Two transactions update rows in opposite order. The database detects the cycle and kills one victim; your code must retry (Resilience).
  • Go "all goroutines are asleep". The Go runtime detects a global deadlock (every goroutine blocked) and crashes with that message. A partial deadlock (some goroutines stuck) is not detected; it looks like a leak.

Memory visibility: why "it works on my machine"

Atomicity is half of the problem. The other half is visibility and ordering. Compilers and CPUs reorder reads and writes, and each core has caches and store buffers. Without synchronisation, thread B may never see thread A's write, or may see writes in a different order than A made them.

// Broken: the JIT may hoist the read of _stop out of the loop, so it never sees true.
private bool _stop;
void Worker() { while (!_stop) { DoWork(); } }
void Stop() => _stop = true;

// Broken: another thread can see _ready == true but _data == null (reordered writes).
_data = Load();
_ready = true;

Every memory model (the C# ECMA/CLR model, the Java Memory Model, the Go memory model, C++11) defines happens-before: if action X happens-before Y, then Y sees X's effects. You get happens-before edges from:

  • Unlocking a lock → a later lock of the same lock.
  • Writing a volatile/atomic → a later read of it (volatile in C# and Java, Volatile.Read/Write, AtomicXxx, Go sync/atomic).
  • Sending on a channel → the matching receive completing (Go).
  • Starting a thread → its first action; a thread's last action → Join returning; a task completing → await resuming.
  • Publishing through a concurrent collection (ConcurrentQueue, BlockingQueue, Channel<T>).

Rule of thumb. If two threads touch the same variable and one of them writes, every access must go through the same lock, an atomic, or a channel. "It is only a bool" is not an exception: use volatile, Volatile.Read/Write, AtomicBoolean or atomic.Bool, or better, a CancellationToken / context.Context.

Immutability and message passing

The cheapest synchronisation is none. Data that never changes after construction can be shared by any number of threads without locks, because there are no writes to race with. Data that is owned by one thread at a time and handed over through a queue needs no locks either: the queue provides the happens-before edge, and the sender stops touching the data.

Producer / consumer and backpressure

A producer/consumer pipeline decouples the code that creates work from the code that processes it, through a queue. The essential design decision is what happens when the queue is full, because a producer that is faster than its consumers fills any queue eventually:

  • Wait (backpressure): the producer blocks or awaits until there is room. Nothing is lost; the slowdown propagates upstream to whoever can deal with it.
  • Drop: keep the newest, keep the oldest, or reject the write. Right for telemetry, UI updates and sensor samples, where fresh data beats complete data.
  • Unbounded: never full, until the process runs out of memory. Latency grows without limit because every item waits behind all the earlier ones.

Run Wait with 2 producers and 1 consumer, then switch to Unbounded with the same inputs. Same throughput, but the queue (and each item's wait) keeps growing. Then try DropOldest with a capacity of 2. func pipeline(ctx context.Context, orders []Order) error {
    ch := make(chan Order, 100) // bounded: sends block when full
    g, ctx := errgroup.WithContext(ctx)

    g.Go(func() error {
        defer close(ch) // closing is how the producer says "no more"
        for _, o := range orders {
            select {
            case ch <- o:
            case <-ctx.Done():
                return ctx.Err()
            }
        }
        return nil
    })

    for i := 0; i < 4; i++ {
        g.Go(func() error {
            for o := range ch { // ends when ch is closed and drained
                if err := handle(ctx, o); err != nil {
                    return err // cancels ctx for everyone
                }
            }
            return nil
        })
    }
    return g.Wait()
}

Cancellation: pass it all the way down

Cancellation in every modern runtime is cooperative. Nobody kills a thread from outside (that leaves locks held and state half-written). Instead, the caller signals "please stop", and the code checks the signal at safe points: before starting expensive work, inside loops, and by passing it to every I/O call, which then aborts the socket read or the database command.

Fan-out / fan-in with bounded parallelism

Fan-out starts many operations; fan-in collects their results. The two decisions are how many at once and what happens when one fails. Unbounded fan-out (Task.WhenAll(ids.Select(Fetch)) over 10,000 ids) sends 10,000 requests to a dependency that can handle 50, and everything gets slower, including other callers. Without cancellation, one early failure still lets all the other jobs run to completion for nothing.

Experiments:

  • Set the limit to 8 (no limit) and the dependency capacity to 3: everything slows down because the dependency is overloaded.
  • Default inputs, then switch to fail fast: the jobs after the failure are cancelled and the wasted work drops.
  • Set a deadline of 12 to see a timeout cancel the stragglers.
// .NET 6+: bounded and fail-fast in one call.
await Parallel.ForEachAsync(ids,
    new ParallelOptions { MaxDegreeOfParallelism = 8, CancellationToken = ct },
    async (id, token) =>
    {
        var item = await _client.GetAsync(id, token);   // first exception cancels token
        await _store.SaveAsync(item, token);
    });

// Virtual thread per task + a semaphore as the limit + structured scope for fail-fast.
List<Item> fetchAll(List<Long> ids) throws Exception {
    var permits = new Semaphore(8);
    try (var scope = new StructuredTaskScope.ShutdownOnFailure()) {
        List<Subtask<Item>> tasks = ids.stream()
            .map(id -> scope.fork(() -> {
                permits.acquire();
                try { return client.get(id); } finally { permits.release(); }
            }))
            .toList();
        scope.join().throwIfFailed();
        return tasks.stream().map(Subtask::get).toList();
    }
}

func FetchAll(ctx context.Context, ids []int) ([]Item, error) {
    g, ctx := errgroup.WithContext(ctx) // first error cancels ctx
    g.SetLimit(8)                       // at most 8 goroutines at once
    items := make([]Item, len(ids))
    for i, id := range ids {
        g.Go(func() error { // Go 1.22+: i and id are per-iteration
            it, err := client.Get(ctx, id)
            if err != nil {
                return err
            }
            items[i] = it // distinct index per goroutine: no race
            return nil
        })
    }
    return items, g.Wait()
}

// A tiny concurrency limiter (p-limit does the same).
async function mapLimit<T, R>(items: T[], limit: number,
  fn: (item: T, signal: AbortSignal) => Promise<R>): Promise<R[]> {
  const controller = new AbortController();
  const results = new Array<R>(items.length);
  let next = 0;
  async function worker() {
    while (next < items.length) {
      const i = next++;                       // safe: single-threaded between awaits
      try { results[i] = await fn(items[i], controller.signal); }
      catch (e) { controller.abort(e); throw e; }   // fail fast
    }
  }
  await Promise.all(Array.from({ length: Math.min(limit, items.length) }, worker));
  return results;
}

When NOT to go async or parallel

Concurrency has real costs: harder debugging, non-deterministic tests, coordination overhead and new failure modes. Skip it when:

Do not add concurrency when

  • The work is tiny. Parallelising a loop over 1,000 integers costs more in scheduling than it saves. As a rough guide, each parallel chunk should take well over 100 µs.
  • The work is CPU-bound and you reach for async. async does not add cores. Make it parallel or leave it synchronous.
  • The bottleneck is shared. Ten threads writing to one SQLite file, one lock or one rate-limited API just queue up.
  • Order matters and the steps depend on each other. A pipeline of strictly sequential steps gains nothing.
  • A sync API is all you have, in a short-lived tool. A CLI that reads three files does not need async I/O.
  • The machine is already saturated. A web server already handles requests concurrently; parallelising inside each request steals cores from the other requests.

Do add it when

  • The code waits on I/O and handles many requests (servers, crawlers, gateways): async, goroutines or virtual threads.
  • Several independent calls sit on the latency path: fan them out (with a limit).
  • A big CPU job runs on an otherwise idle machine and can be split into independent chunks.
  • A UI must stay responsive while work happens.
  • Producers and consumers run at different speeds and a bounded queue smooths bursts.

Amdahl's law sets the ceiling

If 10% of a job is inherently sequential, no number of cores makes it more than 10 times faster: speed-up = 1 / (s + (1 − s) / N). With s = 0.1 and N = 16 you get 6.4×, not 16×. Measure the sequential part first (Performance Cadence shows how to profile it), and shrink it before you buy cores.

Decision guide

1 · WAITING OR COMPUTING?Profile it

Low CPU and high latency means waiting: go to 2. High CPU means computing: go to 3.

2 · WAITINGOverlap the waits

async/await (C#, TS, Python), goroutines (Go), virtual threads (Java 21+). Add a concurrency limit and pass cancellation.

3 · COMPUTINGUse cores

Parallel.For / PLINQ, ForkJoin / parallel streams, worker goroutines, ProcessPoolExecutor, worker_threads. One worker per core.

4 · SHARED STATE?Avoid, then protect

Immutable data, confinement or channels first. Otherwise an atomic for one value, a lock for an invariant.

5 · VERIFYRace detectors and load tests

go test -race, stress tests, dotnet-counters, JFR, thread dumps under load.

Pitfalls and war stories

The static Dictionary that hung the server

A service cached lookups in a static Dictionary<string, Rate> and wrote to it from request threads. Usually fine. Then one day several threads sat at 100% CPU forever. Concurrent writes had corrupted the dictionary's internal bucket chain into a loop, so TryGetValue spun endlessly. Non-thread-safe collections do not just lose data under concurrent writes; they can corrupt themselves. Use ConcurrentDictionary (or ConcurrentHashMap, or a sync.Map / a mutex-guarded map in Go, where concurrent map writes crash the process with "fatal error: concurrent map writes").

Fire and forget, forgotten

_ = SendEmailAsync(order); in a controller. The request returns, the DI scope is disposed, and the email task then uses a disposed DbContext. Exceptions vanish because nobody awaits the task. Background work belongs in a queue processed by a hosted service (BackgroundService + Channel<T>), a message broker, or at least a tracked task with its own scope and logging.

The asyncio service that "randomly" froze

One endpoint used the synchronous requests library inside an async def. Each call blocked the event loop for the whole HTTP round trip, so every other request on that worker froze too. p99 matched the slowest backend. Run with PYTHONASYNCIODEBUG=1 (or loop.set_debug(True)) and asyncio logs every callback that takes over 100 ms. The fix is an async client (httpx.AsyncClient) or await asyncio.to_thread(...).

Checklist

Before you merge concurrent code

  • Is the work waiting or computing, and did you choose the model to match?
  • Is every fan-out bounded, and is every queue bounded with a stated full policy?
  • Is cancellation (token, context, signal) accepted and passed down to every I/O call?
  • Is there no .Result, .Wait(), time.sleep or sync I/O on an async path?

Shared state

  • List every variable two threads can touch. Is each guarded by one lock, an atomic or a channel?
  • Are locks always taken in one global order, and never held across I/O or awaits?
  • Are collections shared between threads concurrent ones?
  • Is there any check-then-act separated by an await?

Operations

  • Do dashboards show thread-pool queue length, goroutine count or event-loop lag?
  • Has the code run under a race detector (go test -race) or a stress test with more threads than cores?
  • Is background work tracked, logged and shut down gracefully?
  • Are timeouts set at every network boundary (Resilience)?

Quiz

1. A C# method does await Task.Delay(1000) 1,000 times concurrently. How many threads are blocked during that second?
Show answer

None. Task.Delay registers a timer; each awaiting method is a state machine object on the heap. When the timers fire, continuations are queued to the thread pool and run briefly on a few threads. Replace it with Thread.Sleep(1000) inside Task.Run and you need 1,000 pool threads (and you will starve the pool).

2. Why does GetDataAsync().Result deadlock in a WPF button handler but not in an ASP.NET Core controller?
Show answer

WPF installs a DispatcherSynchronizationContext, so the await inside GetDataAsync posts its continuation to the UI thread, which is blocked in .Result waiting for that continuation. ASP.NET Core has no SynchronizationContext, so the continuation runs on another pool thread and .Result eventually returns. It is still wrong in ASP.NET Core: it holds a pool thread for the whole wait and causes starvation under load.

3. Python: four threads each run a pure-Python loop for 1 second of CPU. Roughly how long does the whole thing take with the GIL, and how do you fix it?
Show answer

About 4 seconds (sometimes slightly more, because of switching). Only one thread runs bytecode at a time. Use ProcessPoolExecutor (about 1 second on 4+ cores, plus process start-up and pickling), move the hot loop into a C extension or NumPy that releases the GIL, or try the free-threaded 3.13t/3.14t build.

4. What does this print in Node? setTimeout(() => log("T"), 0); Promise.resolve().then(() => log("P")); log("S");
Show answer

S, P, T. The script is the current task, so S logs first. When the task ends, the loop drains all microtasks (P) before it takes the next task, the timer callback (T).

5. Two goroutines call transfer(a, b) and transfer(b, a), each locking the source then the destination. What can happen, and what are two fixes?
Show answer

A deadlock: each holds one mutex and waits for the other. If no other goroutine can run, the runtime crashes with "all goroutines are asleep - deadlock!"; otherwise those two goroutines just hang forever. Fixes: lock in a global order (by account id), or route all transfers through one goroutine that owns the balances (message passing), or use a database transaction.

6. A Java 21 service moved to virtual threads, and throughput got worse under load. Thread dumps show carriers blocked inside synchronized blocks that call a JDBC driver. What is happening?
Show answer

Pinning. Before Java 24, a virtual thread that blocks inside synchronized cannot unmount, so it holds its carrier thread. With only one carrier per core, a few pinned threads stall everything. Replace synchronized with ReentrantLock around blocking calls (or upgrade to Java 24+, JEP 491), and confirm with the JFR event jdk.VirtualThreadPinned.

Cheat sheet

C# / .NET

  • I/O: async Task + await, all the way up.
  • CPU: Task.Run, Parallel.For, PLINQ.
  • Limit: SemaphoreSlim, Parallel.ForEachAsync.
  • Queue: Channel.CreateBounded.
  • Cancel: CancellationToken.
  • Atomic: Interlocked; lock: lock / Lock.

Java

  • I/O: virtual threads (21+).
  • CPU: fixed pool, ForkJoinPool, parallel streams.
  • Limit: Semaphore.
  • Queue: ArrayBlockingQueue.
  • Cancel: interrupts, StructuredTaskScope.
  • Atomic: AtomicXxx, LongAdder; lock: ReentrantLock.

Python

  • I/O: asyncio + TaskGroup; threads for sync SDKs.
  • CPU: ProcessPoolExecutor (GIL).
  • Limit: asyncio.Semaphore.
  • Queue: asyncio.Queue(maxsize=…).
  • Cancel: task.cancel(), asyncio.timeout.
  • Lock: threading.Lock, asyncio.Lock.

Go

  • I/O and CPU: goroutines.
  • Limit: errgroup.SetLimit, buffered channel.
  • Queue: make(chan T, n).
  • Cancel: context.Context.
  • Atomic: atomic.Int64; lock: sync.Mutex.
  • Check: go test -race.

TypeScript / Node

  • I/O: async/await, Promise.all.
  • CPU: worker_threads, piscina.
  • Limit: p-limit or a worker pool.
  • Queue: streams with highWaterMark.
  • Cancel: AbortController, AbortSignal.timeout.
  • Never block the event loop.
