PRODUCTION EXCELLENCE

Code Review, Git & Engineering Habits

What great reviewers look for, small PRs, commit hygiene, ADRs and docs-as-code, and turning feedback into lasting skill.

Beginner → Advanced~40 min studyUpdated 2026-11-03

The problem: the pull request nobody could review

Maya opens a pull request on Monday: "Refactor orders + add search + misc fixes". It's 2,300 changed lines across 41 files, in 37 commits with messages like wip, fix, fix again and address comments. Then this happens:

  • Day 1–4. Nobody picks it up. Everyone means to "block out an hour for it".
  • Day 5. A reviewer scrolls for six minutes, leaves three comments about naming and a missing semicolon, and approves with "LGTM 👍".
  • Day 6. main has moved 40 commits. The rebase hits conflicts in eleven files. Maya resolves them at 7 p.m., gets one wrong, and the tests still pass because the conflicting branch had no tests.
  • Day 9. In production, the search endpoint turns out to build SQL with string concatenation. Paging silently skips the first 50 results. A pricing rule that was correct last week is now off by a cent.
  • Day 10. The team runs git bisect to find which change broke pricing. Half the 37 commits don't compile, so bisect gives up and points at a range.

Nobody here was careless. The process made carelessness the easy path. A 2,300-line diff can't be reviewed well, so it wasn't. A 9-day-old branch is guaranteed to conflict, so it did. Commit history nobody can read can't be searched. And because the formatter wasn't in CI, the reviewer's limited attention went to semicolons.

Engineering habits exist to keep feedback loops short and changes understandable. Integrate small changes often. Review them in priority order, with your best attention on correctness and security. Let machines enforce everything machines can check. Write history, PR descriptions and decisions for the person who reads them a year from now. Every practice on this page shortens a loop or makes a change easier to understand later; judge new practices by the same test.

This page covers the team side of software: Git workflows, pull requests, review, CI and documentation. The code-level side is in Clean Code and Design Principles. For what to look for in tests and security, see Testing Strategy and Security Fundamentals.

The mental model: a change is a batch moving through feedback loops

Every change travels the same path, from an idea in your head to behaviour that users depend on. Each arrow below is a place where you can learn you were wrong. The longer a change waits at any step, the more expensive that lesson becomes.

Three consequences follow, and the rest of the page is built on them:

  1. Batch size is the master variable. A small change passes every loop faster, is easier to review, is less likely to conflict, and is trivial to revert. Most of the habits below (trunk-based development, small PRs, feature flags, atomic commits) are ways to make batches smaller.
  2. Machines first, humans last. Anything a tool can check (format, lint, types, tests, known vulnerabilities, secrets) should be checked before a human looks. Human attention is the scarcest resource in the pipeline, so spend it on what only humans can judge: is this correct, is it the right design, is it safe?
  3. Write for the future reader. The commit message, the PR description and the decision record are read far more often than they're written: by the reviewer, by git blame during an incident, and by the new hire next year.

Deploy is not release. With feature flags, deploy means the code is running in production, and release means users can see it. Separating them is what makes trunk-based development safe: unfinished work can be merged and deployed every day while staying invisible. The DORA research links this pattern of small batches and frequent deploys to both higher speed and higher stability. The two aren't a trade-off.

Git workflows: how work flows back to main

A branching workflow answers three questions: how long do branches live, where do they merge, and when does merged code reach users? Those answers decide how much you integrate at once, and that decides how often you fight conflicts.

Trunk-based GitHub flow GitFlow
Branch lifetime hours, at most a day or two a few days features: days to weeks; release branches: days
Where work merges main (the trunk) main develop, then release/* into main
Unfinished features merged behind a flag stay on the branch until done stay on the branch until done
Release cadence continuous continuous (each merge) scheduled, versioned
Needs strong CI, flags, small tasks CI, fast reviews release management
Fits best services you deploy yourself most web services and open source installed or versioned software with several supported versions (mobile apps, SDKs, on-prem products)

Run the same backlog through each workflow. Four developers, ten days, the same features: only the integration habits change.

What the simulation shows is a general rule: the risk of integration grows with the product of branch lifetime and team activity. A branch open for 4 days on a team that merges 12 commits a day must absorb 48 foreign commits. A branch that lives 4 hours absorbs 2. Conflicts are just the visible part. The invisible part is semantic drift: your code compiles against an API another developer has since changed in meaning.

Trunk-based development

  • Merge to main at least daily; break features into slices that are each safe to ship.
  • Unfinished work is hidden by a feature flag, or by branch by abstraction (build the new implementation behind an interface, switch over, delete the old one).
  • Requires fast CI and fast reviews; otherwise people batch up to avoid the wait.
  • Many teams use short-lived branches + PRs and still call it trunk-based, as long as branches live less than a day or two.

GitFlow (and long-lived branches)

  • Created for software shipped as numbered versions, where several versions are supported at once.
  • For a continuously deployed web service, develop and release/* mostly add waiting, merge-backs and "which branch is the truth?" confusion. Its author added a note in 2020 recommending simpler workflows for web apps.
  • If you need to support old versions, keep release/x.y branches cut from main and cherry-pick fixes into them. That's simpler than full GitFlow.

Feature flags: separate deploy from release

A feature flag is a runtime decision: if (flags.isEnabled("new-checkout", user)) newFlow() else oldFlow(). It lets you merge and deploy incomplete code safely, roll out to 1% of users first, and turn a bad feature off in seconds, without a rollback deploy.

The interesting part is who gets the feature. A good rollout is deterministic and sticky: the same user always gets the same answer, and raising the percentage only adds users, never flips existing ones back. The standard trick is to hash the flag key and the user id into a bucket from 0 to 9,999 and compare it with the rollout percentage. The simulation below does that for 1,000 users, with an error-rate SLO that can trip a kill switch.

Not every flag is the same. Pete Hodgson's taxonomy, from Martin Fowler's Feature Toggles article, is worth knowing, because the lifetime of the flag decides how you manage it:

Kind Purpose Lifetime Decided by
Release flag hide unfinished or risky work; progressive rollout days to weeks, then delete it percentage, internal users first
Experiment flag A/B test two variants and measure the length of the experiment random but sticky cohort
Ops flag / kill switch turn off an expensive or failing dependency under load long-lived, tested regularly operators, automation on SLOs
Permission flag entitlements: beta testers, premium plans permanent (really configuration) user attributes

OpenFeature is a CNCF standard API for flags with SDKs in every language below. You code against one interface, and the provider (LaunchDarkly, Flagsmith, Unleash, flagd, Azure App Configuration, or your own) is configured at startup, the same way you'd register any dependency with DI. The targeting key is what makes the bucket sticky.

// OpenFeature .NET SDK. The provider is registered once at startup:
// await Api.Instance.SetProviderAsync(new FlagdProvider());
using OpenFeature;
using OpenFeature.Model;

public sealed class CheckoutController(IFeatureClient flags, NewCheckout next, LegacyCheckout legacy)
{
    public async Task<IResult> Checkout(Cart cart, ClaimsPrincipal user)
    {
        var ctx = EvaluationContext.Builder()
            .SetTargetingKey(user.FindFirstValue("sub")!)   // same user -> same bucket
            .Set("plan", user.FindFirstValue("plan") ?? "free")
            .Build();

        // The default (false) is used if the provider is down: fail safe, not fail open.
        bool useNew = await flags.GetBooleanValueAsync("new-checkout", false, ctx);
        return useNew ? await next.Run(cart) : await legacy.Run(cart);
    }
}

// OpenFeature Java SDK. At startup: OpenFeatureAPI.getInstance().setProviderAndWait(new FlagdProvider());
import dev.openfeature.sdk.*;

@RestController
class CheckoutController {
    private final Client flags = OpenFeatureAPI.getInstance().getClient("checkout");
    private final NewCheckout next;
    private final LegacyCheckout legacy;

    CheckoutController(NewCheckout next, LegacyCheckout legacy) { this.next = next; this.legacy = legacy; }

    @PostMapping("/checkout")
    Receipt checkout(@RequestBody Cart cart, @AuthenticationPrincipal Jwt user) {
        var ctx = new ImmutableContext(user.getSubject(),               // targeting key
                Map.of("plan", new Value(user.getClaimAsString("plan"))));
        boolean useNew = flags.getBooleanValue("new-checkout", false, ctx);
        return useNew ? next.run(cart) : legacy.run(cart);
    }
}

# OpenFeature Python SDK. At startup: api.set_provider(FlagdProvider())
from fastapi import Depends
from openfeature import api
from openfeature.evaluation_context import EvaluationContext

flags = api.get_client("checkout")

@app.post("/checkout")
async def checkout(cart: Cart, user: User = Depends(current_user)) -> Receipt:
    ctx = EvaluationContext(targeting_key=user.id, attributes={"plan": user.plan})
    # False is the safe default if the provider can't be reached.
    if flags.get_boolean_value("new-checkout", False, ctx):
        return await new_checkout(cart)
    return await legacy_checkout(cart)

// OpenFeature Go SDK. At startup: openfeature.SetProviderAndWait(flagd.NewProvider())
import "github.com/open-feature/go-sdk/openfeature"

var flags = openfeature.NewClient("checkout")

func (h *Handler) Checkout(w http.ResponseWriter, r *http.Request) {
    user := auth.UserFrom(r.Context())
    evalCtx := openfeature.NewEvaluationContext(user.ID, map[string]any{"plan": user.Plan})

    // On error the default (false) is returned, so a flag outage falls back to the old flow.
    useNew, _ := flags.BooleanValue(r.Context(), "new-checkout", false, evalCtx)
    if useNew {
        h.next.Run(w, r)
        return
    }
    h.legacy.Run(w, r)
}

// OpenFeature server SDK. At startup: await OpenFeature.setProviderAndWait(new FlagdProvider());
import { OpenFeature } from "@openfeature/server-sdk";

const flags = OpenFeature.getClient("checkout");

app.post("/checkout", async (req, res) => {
  const user = req.user!;
  const useNew = await flags.getBooleanValue("new-checkout", false, {
    targetingKey: user.id, // same user -> same bucket
    plan: user.plan,
  });
  res.json(useNew ? await newCheckout(req.body) : await legacyCheckout(req.body));
});

How the ecosystems differ: .NET also has Microsoft.FeatureManagement (flags in appsettings.json or Azure App Configuration, [FeatureGate] on endpoints). Spring teams often use Togglz or Unleash. Go and Python codebases tend to call a flag SDK directly. All of them evaluate flags locally from a cached rule set, refreshed by streaming or polling, so a flag check costs microseconds rather than a network call. Where flag configuration lives and how it's secured is covered in Configuration & Secrets.

Flag debt. Every flag doubles the number of states your code can be in. Five live flags give 32 combinations, and nobody tests them all. Knight Capital lost $440 million in 45 minutes in 2012, partly because an old, unused flag was reused for new behaviour, and one server was still running code that read it the old way. Fix: every release flag gets an owner and an expiry date when it's created. Remove it within a sprint or two of reaching 100%: delete the old path and the flag together. Never reuse a flag name.

Small pull requests, and stacking them

The single most effective review habit is the author's: send smaller changes. A well-known study of 2,500 reviews at Cisco (SmartBear, 2006) found that reviewers stay effective up to about 200–400 lines and 60–90 minutes; past that, the defect-finding rate collapses. Google's engineering practices guide, Small CLs, says the same thing from a decade of experience: small changes are reviewed faster and more thoroughly, are less likely to introduce bugs, are easier to merge and easier to roll back.

The mechanism is in the simulation. Same feature, same planted defects (about one per 100 lines), shipped three ways. Watch two things: how long each PR waits before anyone starts, and how likely each defect is to be noticed.

Two effects compound. Big PRs wait longer, because nobody has a free two-hour block, so they get postponed. Then they are reviewed worse, because attention runs out and the reviewer starts skimming. "LGTM" on a 2,000-line diff usually means "I scrolled".

How to split a change

"Make it smaller" is useless advice without techniques. These work in every codebase:

Technique Example Why it helps
Preparatory refactor first PR 1: extract OrderRepository (no behaviour change). PR 2: add search that uses it. Structure changes are easy to review when they come alone; Clean Code calls this wearing one hat at a time.
Vertical slices "Search by customer name" end to end, then "filter by date", then "paging". Each slice is shippable and testable on its own.
Behind a flag Merge the new flow with the flag off; turn it on in a later PR. Unfinished work can merge without being visible.
Expand, then contract Add the new column → write both → backfill → read new → drop old, one PR each. Each step is backwards compatible, so deploys and rollbacks stay safe.
Generated and mechanical changes separately One PR for the dependency bump or the codemod, one for the hand-written logic. The reviewer can skim the mechanical part and focus on the logic.
Tests and docs travel with the code Never "tests in a follow-up PR". The test is how the reviewer knows what the code is meant to do.

A useful limit: a PR should be reviewable in one sitting of under 30 minutes, which usually means under ~400 changed lines of hand-written code. That's a guideline, not a law: a 600-line PR that renames a type mechanically is fine, and a 40-line PR that changes the locking strategy deserves an hour.

Stacked pull requests

Small PRs have a cost: if PR 2 needs PR 1, do you wait for PR 1 to merge before starting PR 2? Stacking removes the wait. Each PR targets the branch of the one below it, so reviewers see only that layer's diff, and you keep working on top.

The price is restacking: when review changes PR 1, every branch above it must be rebased. Since Git 2.38, one command does it, moving every branch ref in the stack:

# build the stack
git switch -c orders/1-repository main          # commit, push, open PR against main
git switch -c orders/2-search-api               # commit, push, open PR against orders/1-repository
git switch -c orders/3-search-ui                # commit, push, open PR against orders/2-search-api

# review asked for a change in PR 1: fix it there...
git switch orders/1-repository
git commit -am "refactor(orders): make repository async"

# ...then replay everything above it in one go
git switch orders/3-search-ui
git rebase --update-refs orders/1-repository     # also moves orders/2-search-api
git push --force-with-lease origin orders/2-search-api orders/3-search-ui

Tools such as Graphite, ghstack, git-branchless, spr and gh stack extensions automate this further. Gerrit and Phabricator were built around stacks from the start: each commit is reviewed on its own.

Self-review first. Before you request a review, read your own diff in the PR UI, not your editor. You will find debug logging, a commented-out block and a missing test about half the time. Then write the description. Both take five minutes and save a review round-trip, which costs hours.

Commit messages and Conventional Commits

A commit message is a note to whoever runs git blame on this line in two years, quite possibly during an incident. The diff shows what changed. Only the message can say why.

fix(cart): round each line to whole cents before tax

Totals were rounded once, after tax, so a three-item cart could differ
by one cent from the invoice service, which rounds per line. Finance
reconciles the two every night and flagged 212 mismatches last week.

Round each line first, matching the invoice service and the rule in
ADR-0012. Rounding mode stays MidpointRounding.ToEven (banker's).

Fixes: #482

The long-standing conventions (Chris Beams's widely cited seven rules, and what Git itself expects):

  1. A short subject line, ideally ≤ 50 characters and never more than 72, because tools truncate it.
  2. Imperative mood: "add", "fix", "remove". A good subject completes the sentence "If applied, this commit will …".
  3. No trailing period.
  4. A blank line, then a body that explains what and why, not how (the diff shows how). Wrap it at about 72 columns.
  5. Footers for machine-readable metadata: Fixes: #482, Co-authored-by:, BREAKING CHANGE:, Signed-off-by:.
  6. One logical change per commit. A commit that both reformats a file and changes logic can't be reviewed, reverted or bisected cleanly.

Conventional Commits adds a machine-readable header, type(scope)!: subject, so tools can compute the next semantic version and write the changelog for you. (Conventional Commits keeps the subject lowercase after the type, which overrides Beams's "capitalize the subject".)

Type Meaning Release effect
feat a new capability for users MINOR (1.4.2 → 1.5.0)
fix a bug fix PATCH (1.4.2 → 1.4.3)
perf a performance improvement with no behaviour change PATCH
refactor restructuring with no behaviour change none
docs, test, style, build, ci, chore documentation, tests, formatting, build system, pipeline, housekeeping none
revert reverts an earlier commit depends on what's reverted
! after the type, or a BREAKING CHANGE: footer an incompatible API change MAJOR (1.4.2 → 2.0.0)

Try it. Pick a history, or type your own commit, and watch the parser, the linter and the version bump. Use \n for line breaks to add a BREAKING CHANGE: footer.

Enforce the convention with tools, not with review comments. A commit-msg hook rejects bad messages locally in milliseconds, and a CI check catches anyone who skipped the hook.

Ecosystem Local hook Version + changelog from commits
C# / .NET Husky.Net, or lefthook, running commitlint Versionize, GitVersion, release-please (simple strategy)
Java lefthook or a Maven/Gradle git-hook plugin, running commitlint release-please (maven/java strategy), semantic-release, JReleaser
Python pre-commit with the commitizen hook commitizen (cz bump), python-semantic-release
Go lefthook running commitlint release-please (go strategy), GoReleaser's changelog groups, svu
TypeScript husky + @commitlint/config-conventional semantic-release, release-please, Changesets

With squash merges, only the PR title needs the convention. The squash commit takes the PR title as its subject, so you can lint the title in CI (for example with amannn/action-semantic-pull-request on GitHub) and let people commit freely on their branch. That's the lowest-friction way to adopt Conventional Commits.

Merge, rebase or squash

When your branch is ready, how do its commits land on main? This is the most argued-about question in Git, and the arguments make more sense once you see the graph. In the simulation, every hash is computed from the commit's parents, message and content, exactly as in Git. Watch which commits get new hashes.

What the graph shows:

  • A merge commit preserves history exactly as it happened. Nothing is rewritten, so it's always safe on shared branches, and a conflict is resolved once. The cost is a non-linear history, and every wip and fix typo commit lands on main.
  • Rebase replays your commits on top of main, giving them new parents and therefore new hashes. History becomes linear, but conflicts are resolved once per commit that touches the conflicting lines (git rerere remembers repeated resolutions). Because hashes change, anyone else who built on the old commits now has to rebase too.
  • Squash turns the whole branch into one new commit. Main gets exactly one commit per PR, easy to revert, with the PR title as its message. The individual steps are gone from main (the PR page keeps them).
  • Interactive rebase (git rebase -i) lets you curate first: fold fixups into the commits they fix, reword messages, reorder, drop. You get a linear history of meaningful commits, each of which builds.

The golden rule: never rewrite commits that others have built on. Rebase, squash and amend freely on your own branch before it's shared, or when you are its only user. Once someone else has based work on your commits, merge instead. If you must update a pushed branch, use git push --force-with-lease. It refuses to overwrite commits you haven't seen, while plain --force silently deletes a colleague's work.

Sensible team defaults:

  • Most teams: squash merge, with a Conventional Commit PR title. One commit per PR on main, linear history, trivial reverts.
  • Teams that curate commits (open source, kernel-style, stacked commits): rebase-and-merge, with each commit required to build.
  • Merge commits where topology matters: merging release branches back, or long-lived integration branches.
  • Locally, always git pull --rebase, so you don't create pointless "Merge branch 'main' into main" commits.
# a sane global git setup
git config --global pull.rebase true            # rebase local commits on pull instead of merging
git config --global rebase.autoStash true       # stash and unstash uncommitted work around a rebase
git config --global rebase.updateRefs true      # always move stacked branch refs (Git 2.38+)
git config --global rerere.enabled true         # remember conflict resolutions and reuse them
git config --global push.autoSetupRemote true   # first push creates the upstream branch
git config --global fetch.prune true            # drop remote branches that were deleted

# clean up before review: fold a fix into the commit it belongs to
git commit --fixup=3f2a9c1                      # creates "fixup! <subject of 3f2a9c1>"
git rebase -i --autosquash main                 # moves it next to 3f2a9c1 and folds it in

git bisect: history as a debugging tool

Here's the payoff for all that history hygiene. When something broke in the last 200 commits, git bisect does a binary search: test the middle commit, mark it good or bad, and halve the suspects. 200 commits take about 8 tests. Try a history that contains WIP commits that don't compile.

Bisect only works if every commit on main builds and passes tests. That's one more reason for squash merges or curated rebases, and for CI on every merge. Automate the search with git bisect run, giving it a script that exits 0 for good, 1–127 for bad (except 125), and 125 for "can't test this one, skip it":

git bisect start HEAD v1.4.0          # first bad, then last known good
git bisect run sh -c '
  dotnet build -c Release -warnaserror:false || exit 125
  dotnet test --no-build -c Release --filter "FullyQualifiedName~PricingTests"'
git bisect reset                      # back to where you started

git bisect start HEAD v1.4.0
git bisect run sh -c '
  ./mvnw -q -DskipTests package || exit 125
  ./mvnw -q test -Dtest=PricingTest'
git bisect reset

git bisect start HEAD v1.4.0
git bisect run sh -c '
  pip install -q -e . || exit 125
  pytest -q tests/test_pricing.py'
git bisect reset

git bisect start HEAD v1.4.0
git bisect run sh -c '
  go build ./... || exit 125
  go test ./pricing/ -run TestTotal'
git bisect reset

git bisect start HEAD v1.4.0
git bisect run sh -c '
  npm ci --silent && npx tsc --noEmit || exit 125
  npx vitest run pricing'
git bisect reset

Write the failing test first (outside the repo, or as an untracked file that the script copies in), so the same check runs at every step. When bisect lands on a 40-line commit with a clear message, the investigation is usually over. When it lands on "misc fixes (2,300 lines)", it has only just started.

How to review

A code review has three jobs, in this order: catch defects that would hurt users, keep the codebase healthy so the next change stays easy, and share knowledge so more than one person understands every part. Google's guide sets the bar like this: approve once the change definitely improves the overall code health, even if it isn't perfect. "Perfect" isn't the standard. "Better than before, and nothing dangerous" is.

What to look for, in order

Your attention is limited, so spend it from the top of this list down. A reviewer who leaves fourteen naming nits and misses the SQL injection has done worse than no review at all, because the author now believes the code was checked.

0 · ContextRead the description

What problem, why this approach, how was it tested? No description: ask for one before reading the code.

1 · CorrectnessDoes it do the right thing?

Logic, edge cases (empty, null, zero, max), error paths, concurrency, data migrations, backwards compatibility.

2 · DesignIs it the right shape?

Right layer, right abstraction, fits the architecture, no hidden coupling, not over-engineered.

3 · SecurityCan it be abused?

Untrusted input, injection, authz checks, secrets, logging of personal data, new dependencies.

4 · TestsWould a bug be caught?

Do the tests fail if the code is wrong? Is the risky path tested, not just the happy one?

5 · ReadabilityCan the next person change it?

Names, function size, comments that explain why, consistency with the codebase.

6 · NitsPolish, if time allows

Label as nit. Anything a tool could check should be automated, not commented.

Area Questions worth asking Typical finds
Correctness What happens with an empty list, a null, a duplicate, a retry, two requests at once? What if the call times out halfway? Off-by-one, missing await, non-idempotent retry, race on a shared dictionary, wrong time zone
Design Does this belong here? Will the next feature fit? Is there a simpler way? Is a new abstraction earning its keep? Business logic in a controller, a new static singleton, a speculative interface with one implementation (design principles, anti-patterns)
Security Where does each input come from? Who is allowed to call this? What ends up in logs? String-built SQL, missing ownership check (IDOR), token in a log line, new package nobody has heard of (security fundamentals, API security)
Tests If I break the code, does a test go red? Are the assertions specific? Tests that assert only "no exception", mocks that make the test tautological, no test for the bug being fixed (testing strategy)
Operability How will we know it's broken in production? Can we roll it back? No log or metric on the new failure path, a migration with no way back, no timeout on a new HTTP call (observability, resilience)
Readability Would a new team member understand this in six months? Misleading names, a 90-line method, a comment that repeats the code (clean code)

The simulation below gives two reviewers the same diff and the same time budget. One reads in priority order; the other starts at the top of the file and comments on everything as they meet it. Change the budget and see what each one finds before time runs out.

You are reviewing in the wrong order if most of your comments are about naming and formatting, you approved a PR whose description you didn't read, you can't say in one sentence what the change does, or you never run the code or open the files around the diff. The diff view hides the callers. For anything non-trivial, check out the branch and look at the whole file.

Writing review comments

Text loses tone. "Why did you do it this way?" can be curiosity or an accusation, and the author will usually read it as the second. Three habits fix most of this.

1. Label every comment so the author knows what's required. Conventional Comments is a lightweight, widely used scheme:

Label Means Blocks merge?
issue (blocking): A real problem: bug, security hole, data loss Yes
suggestion: A concrete improvement, with the reason Author decides, unless marked blocking
question: I don't understand; please explain (maybe in a code comment) Until answered
nit: Trivial preference or polish No
thought: / note: An idea for later, or useful context No
praise: Something done well, said specifically No

2. Talk about the code, not the person, and give the reason. Ask questions when you are unsure, but be direct when you are sure.

Comments that hurt

  • "Why would you do it like this?"
  • "This is wrong."
  • "Use a dictionary."
  • "Did you even test this?"
  • "We don't do it that way here."
  • 23 separate comments about spacing.

Comments that help

  • "question: Find is called once per order in this loop, so 1,000 orders = 1,000 queries. Could we load them in one query?"
  • "issue (blocking): amount comes from the request body, so a client can set its own price. Look it up from catalog instead."
  • "suggestion: a Dictionary<Sku, Price> makes this O(1) instead of a list scan. Not urgent at our sizes."
  • "nit: the formatter would fix these; can we turn on dotnet format in CI instead of me commenting?"
  • "praise: the test names read like a spec. I learned the rules from them."

3. Say what you expect. End the review with a summary: "Approved, two nits, take them or leave them", or "Requesting changes for the price issue; the rest is optional." Approve-with-comments ("LGTM once the null check is in, no need for another round") saves a full round-trip when you trust the author.

Move long discussions to a call. If a thread has gone back and forth three times, talk for five minutes, then write the outcome in the thread so the decision is recorded. A design disagreement in PR comments can burn days.

Review latency and process

Review speed matters more than most teams think. A PR that waits a day for review makes the author context-switch away and come back cold. DORA's research links short lead times with both better delivery and better stability.

  • Respond within one business day, and ideally within a few hours. "Respond" can mean "I'll look this afternoon", or a first pass on the design before the details. Google's guidance is that a review response should come quickly, though the full review can take longer.
  • Review between tasks, after lunch, after a meeting, not in the middle of deep work. Batching reviews twice a day is fine.
  • Use CODEOWNERS so the right people are asked automatically, and require one approval for normal code, two for risky areas (auth, payments, migrations).
  • Automate everything mechanical in CI: formatting, linting, tests, coverage, dependency scanning. A human shouldn't spend attention on anything a machine can check.
  • Review tests first. They're the spec: they tell you what the code is supposed to do before you read how.
  • Track it. Time to first review, time to merge and PR size are worth watching as team metrics, never as individual targets.

Receiving feedback

The author's half of the conversation matters just as much.

  • You are not your code. A comment on a function is not a verdict on you. The reviewer is spending their time to make your work better.
  • Assume good intent, and ask when unsure. "Do you mean this is blocking, or a preference?" is a fine reply.
  • Reply to every comment, even with "Done" or a commit link. Resolve the threads you've fixed so the reviewer knows what's left.
  • Disagree with reasons, not feelings. "I kept the loop because the list is ≤ 5 items and the query version needs a new index; happy to change it if you feel strongly." When it's genuinely a matter of taste, the author's choice should usually win.
  • If you had to explain it, the code isn't clear yet. When a reviewer asks "what does this do?", the best answer is often a better name or a comment in the code, not a reply in the PR that nobody will find later.
  • Don't argue in the 40th comment. Talk, decide, record.
  • Say thanks when a reviewer catches a real bug. It encourages the behaviour you want.

Turning feedback into lasting skill

A review comment fixes one line. The real return comes when the pattern behind the comment never needs to be written again, by you or anyone else. Every repeated comment should move one step up this ladder:

Practical ways to climb it:

  1. Keep a personal "things reviewers caught" list. Once a week, group the comments you received. If three are about missing null checks or unclear names, that's your self-review checklist for the next month.
  2. Fix the class, not the instance. When a reviewer finds a bug, search for the same pattern elsewhere: grep for other string.Format SQL, other async void, other unbounded caches.
  3. Write the test that would have caught it. The comment disappears when the PR merges; a regression test stays forever.
  4. Promote repeated comments to tools. Most ecosystems let you turn a convention into a build-breaking rule: a Roslyn analyzer severity in .editorconfig (dotnet_diagnostic.CA2007.severity = error), an Error Prone or ArchUnit check in Java, a ruff rule in Python, a golangci-lint linter or a go vet analyzer in Go, an ESLint rule in TypeScript. ArchUnit, NetArchTest and import-linter can even enforce architecture rules ("controllers never touch the DbContext").
  5. Review others' code to learn. Reading reviews by senior colleagues on other people's PRs is one of the fastest ways to absorb a codebase's standards. Many teams let juniors review from week one, as a learning exercise, with a second approver.

Architecture decision records

Some decisions shape a codebase for years: "we use PostgreSQL, not Cosmos DB", "services talk through events, not direct calls", "we chose squash merges". Six months later nobody remembers why, so the decision is either followed blindly or reversed without knowing what it was protecting. An architecture decision record (ADR) is a short document that captures one such decision, its context and its consequences, stored in the repository next to the code.

Michael Nygard's original 2011 format is still the most common. It fits on one screen:

<!-- docs/adr/0012-round-money-per-line.md -->
# 12. Round money per line, half-to-even, before tax

Date: 2026-03-14
Status: Accepted  <!-- Proposed | Accepted | Deprecated | Superseded by ADR-0019 -->

Context
-------
Cart, invoice and refund services each rounded money differently. Finance
reconciles them nightly and found 212 one-cent mismatches in a week. The tax
authority requires invoice lines to be rounded individually.

Decision
--------
Every service rounds each line amount to the currency's minor unit, using
half-to-even (banker's) rounding, *before* applying tax. Totals are sums of
rounded lines. All money uses the shared `Money` type; `double` is banned for
money by an analyzer rule.

Consequences
------------
+ Cart, invoice and refund totals match by construction.
+ One rule to test, in one library.
- Totals can differ from "mathematically exact" by up to n/2 minor units for n lines.
- Existing open carts are recalculated on the next change (one-off migration).

Alternatives considered
-----------------------
- Round only the total: simpler, but violates the tax rule and keeps the mismatches.
- Half-away-from-zero: matches what most people expect, but biases totals upwards over volume.

How to make ADRs work:

  • One decision per file, numbered, never deleted. docs/adr/0001-record-architecture-decisions.md is traditionally the first one. When a decision changes, write a new ADR and mark the old one Superseded by ADR-0019. The history of why is the whole point.
  • Review ADRs like code, in a PR. The PR discussion is part of the record.
  • Write one when a decision is costly to reverse, affects more than one team, or when you catch yourself explaining the same choice for the third time. Don't write one for which logging library to use in a script.
  • Link them from code comments and PR descriptions ("see ADR-0012"), so they're found when they matter.
  • Variants: MADR adds explicit "considered options" and "decision drivers"; Y-statements fit a decision in one sentence ("In the context of …, facing …, we decided … to achieve …, accepting …"). Tools such as adr-tools and log4brains create and index the files.

CI quality gates

Every check a machine can do should run on every PR, before a human looks at it. That way reviewers spend their attention on design and correctness, and "it works on my machine" stops being an argument. The simulation runs a pipeline of eight jobs against different kinds of breakage. Compare the layouts: how long until the author hears that something is wrong, and how many runner-minutes it burns.

Notice that "fail fast" doesn't always win. Every separate job pays for a runner, a checkout and a cache restore (half a minute in this model, often more in real life), so for a small project one sequential job can report a failing unit test sooner and use far less compute. Splitting pays off when the slow stages are genuinely slow: long integration suites, container builds, multi-platform matrices. Put the cheapest, most-often-failing checks first, and split only where parallelism saves more than the setup costs.

Build, warnings as errors Compile errors, nullable warnings, analyzer findings 1–3 min Treat new warnings as errors; keep a baseline for old code if needed.
Lint / static analysis Bug patterns, complexity, banned APIs 1–2 min Promote repeated review comments into rules here.
Unit tests Logic regressions 1–5 min Must be fast and deterministic, or people learn to re-run until green.
Integration tests Wiring, SQL, serialization, real databases via Testcontainers 3–10 min Run in parallel with unit tests (testing strategy).

A CI pipeline only protects main if it's required. Turn on branch protection (GitHub rulesets, or Azure Repos branch policies): require the status checks to pass, require at least one approving review, require branches to be up to date (or use a merge queue, which tests the PR as it would be merged with everything ahead of it), and block force-pushes to main.

Hooks are for speed, CI is for truth. CI is the gate that can't be skipped. Run the same commands in both, from the same config, so they never disagree.

Pair and mob programming

Review after the fact isn't the only way to get a second pair of eyes. Pairing puts them there while the code is written: two people, one problem, one keyboard (or a shared editor session such as VS Code Live Share or JetBrains Code With Me). Mob (or ensemble) programming puts the whole team on one problem.

Style How it works Good for
Driver / navigator The driver types; the navigator thinks ahead, watches for mistakes and keeps the bigger picture. Swap every 15–30 minutes. General feature work
Ping-pong A writes a failing test, B makes it pass and writes the next failing test, and so on. TDD, and keeping both people engaged
Strong-style "For an idea to go from your head into the computer, it must go through someone else's hands." The navigator decides, the driver types. Onboarding, and transferring knowledge from expert to newcomer
Mob / ensemble The whole team, one screen, a driver who rotates every few minutes. Hard design problems, a new codebase, incidents, setting team conventions
Async pairing Hand over a branch with a short note at the end of the day, across time zones. Distributed teams

Pairing costs two people's time, but it isn't twice the cost: pairs get stuck less, produce fewer defects, and the review is effectively done when they finish. Many teams that pair let a paired change merge with a single quick approval. It's at its best for complex or risky code, onboarding, and unfamiliar areas, and at its worst for routine work that one person can do on autopilot. Pairing all day, every day is exhausting; a few focused hours with breaks works better.

Documentation as code

Documentation goes stale when it lives somewhere else. Docs as code means keeping docs in the repository, in plain text (Markdown, AsciiDoc), changed in the same PR as the code, reviewed the same way, and built and published by CI. A PR that changes behaviour and leaves the README wrong should fail review for the same reason a PR without tests would.

The README is the front door

A newcomer should get from git clone to a running app and a passing test suite using only the README, in under an hour. Aim for these sections, in this order:

  1. What it is, in two sentences, and who uses it.
  2. Quick start: prerequisites with versions, then one command to build, one to run, one to test.
  3. Configuration: environment variables and where secrets come from (never the secrets themselves; see configuration and secrets).
  4. Architecture at a glance: one diagram and links to the ADRs.
  5. How to contribute: link to CONTRIBUTING.md (branching, commit convention, how to run checks locally, review expectations).
  6. Ownership and support: team, chat channel, on-call, dashboards, runbooks.

Four kinds of documentation

The Diátaxis framework explains why so much documentation feels unhelpful: it mixes four different kinds of document that serve four different needs.

Diagrams, API docs and onboarding as code

  • Diagrams as code: Mermaid renders in GitHub and Azure DevOps Markdown; PlantUML and Structurizr (for C4 models) are common alternatives. Text diagrams get diffed, reviewed and updated in the same PR, unlike a PNG exported from a drawing tool two years ago.
  • API reference generated from code: OpenAPI from ASP.NET Core / springdoc / FastAPI / NestJS, published in CI.
  • Onboarding as code: a dev container (.devcontainer/devcontainer.json) or a make setup / ./scripts/bootstrap script, so "set up your machine" is a command, not a wiki page. Add CONTRIBUTING.md, CODEOWNERS, the PR template, and a "good first issue" label.
  • Check docs in CI: link checkers, Markdown lint, spell check (cspell, Vale), and run the code samples (doctests) so examples can't rot.

Doc comments: the contract, not the implementation

Public APIs deserve a doc comment that says what the caller needs to know: what it does, what each parameter means, units and ranges, what it returns, what it throws. Your IDE shows it on hover, and generators turn it into reference docs. Don't restate the code; say what the code can't. (See Clean Code on comments that explain why.)

Working with AI assistants

AI coding assistants write a lot of plausible code very quickly. That shifts the bottleneck to review, and every habit on this page matters more, not less. Treat AI output like a PR from a fast, well-read contributor who has never seen your codebase, can't run it, and never says "I'm not sure".

Failure mode What it looks like Defence
Hallucinated APIs A method or config option that doesn't exist, or existed three versions ago Compile and run it; read the real docs for anything unfamiliar.
Hallucinated packages ("slopsquatting") pip install / npm install of a plausible package name that attackers have registered Check every new dependency exists, is maintained and is the one you meant (supply chain). Let SCA run in CI.
Insecure defaults String-built SQL, disabled TLS validation, allow all CORS, secrets in code, MD5 for passwords Review AI code for security as strictly as anyone's; keep secret scanning and analyzers on.
Tests that test nothing Tests that mock the unit under test, assert only "not null", or were written to match the (wrong) code Read the assertions. Break the code on purpose and check a test fails; mutation testing does this automatically (testing strategy).
Confident, subtle logic errors Off-by-one, wrong time zone, missing await, a race Same priority order as any review: correctness first.
Off-pattern code A new HTTP client instead of the shared one, a different error-handling style, a new library for something you already do Point the assistant at examples in your codebase; review for design fit.
Huge diffs 800 lines generated in a minute The small-PR rule still applies. Generate in small steps and commit each one.

Tests as the spec

The most reliable way to work with an assistant is to write (or at least carefully review) the tests first, and let the tests define "done". Tests are precise in a way a prompt can't be: "page numbers start at 1" is ambiguous until a test says offset(1, 50) == 0 and offset(0, 50) throws. Then the assistant's job is to make them pass, and you can verify that in seconds instead of reasoning about the code line by line.

A workflow that holds up:

  1. Describe the change in small steps, as you would split a PR. Give the assistant the relevant files, an example of the house style, and the constraints ("use the existing HttpClientFactory", "no new dependencies").
  2. Agree the tests first. Write them, or have the assistant draft them and review them before any implementation exists. Check they fail for the right reason.
  3. Generate the implementation, run the tests, the linters and the type checker. Iterate on failures by pasting the actual error, not a paraphrase.
  4. Review the diff yourself, in the same order as any review: correctness, design, security, tests, readability. If you can't explain a line, you can't approve it.
  5. You are the author of record. The PR has your name on it; "the AI wrote it" isn't a defence in a postmortem. Say in the description which parts were generated if your team asks for it.

AI reviewers (Copilot code review and similar) are useful as a first pass that catches typos, obvious bugs and missing null checks before a human looks. They complement human review; they don't replace the person who understands what the change is for.

Do

  • Merge small changes to main at least daily, with unfinished work behind flags.
  • Keep PRs reviewable in one sitting (roughly under 400 hand-written lines), and stack them when they depend on each other.
  • Write commit messages and PR descriptions that explain why, and lint the convention automatically.
  • Review in priority order: correctness, design, security, tests, readability, then nits.
  • Label comments (issue, suggestion, question, nit, praise) and say clearly what blocks.
  • Respond to reviews within a business day.
  • Automate every mechanical check as a required CI gate, mirrored in fast local hooks.
  • Turn repeated review comments into checklists, tests and lint rules.
  • Record decisions that are costly to reverse as ADRs in the repo.
  • Keep docs next to the code and change them in the same PR.
  • Give AI assistants tests as the spec, and review their output like anyone else's.

Don't

  • Keep long-lived feature branches that merge once a month.
  • Send 2,000-line PRs, or mix refactoring, formatting and behaviour changes in one.
  • Write "fix", "wip", "changes" as the only record of a change on main.
  • Rewrite history others have built on, or use --force instead of --force-with-lease.
  • Spend review time on things a formatter or linter could check.
  • Approve a diff you didn't understand, or comment on the person instead of the code.
  • Let PRs wait days for a first response.
  • Leave feature flags in the code after they're fully rolled out.
  • Keep architecture knowledge only in people's heads or in a wiki nobody updates.
  • Merge AI-generated code, or new dependencies, that nobody has read.

Pitfalls

The rubber stamp. A team's review approval rate was 99%, with a median review time of four minutes for PRs of 900 lines. An authorization check was missing in a new endpoint for three months. Fix: smaller PRs, a description that says where to look, and reviewers who are honest about what they checked ("I reviewed the API layer only; someone from payments should check the ledger part"). Measure PR size and time-to-first-review, not approval counts.

Death by nits. Every PR got thirty comments about naming and spacing, rounds took a week, and juniors stopped sending PRs until they were "perfect", which made them huge. Fix: a formatter and linter in CI, nit: labels that are explicitly optional, and the rule that a PR which improves code health gets approved even if it isn't how you'd have written it.

The force-push that ate a colleague's work. Two people pushed to the same branch. One rebased and ran git push --force, silently discarding the other's two commits. Fix: --force-with-lease always (alias it), branch protection on shared branches, and a team agreement about who owns a branch. git reflog on the overwritten machine can usually recover the commits.

The red build everyone ignores. A flaky test failed about one run in five, so people re-ran CI until it went green. A real failure in the same test went unnoticed for a week. Fix: treat flaky tests as bugs. Quarantine them with an owner and a deadline, and fix the cause (time, ordering, shared state; see testing strategy). A required gate that people routinely bypass is worse than none.

The ADR nobody could find. The team had written good ADRs, in a wiki space that was migrated and lost. A new lead reversed a decision whose reason was "the vendor's API rate-limits per tenant", and production fell over. Fix: ADRs live in the repo (docs/adr/), are linked from the code they affect, and are superseded, never deleted.

The plausible package. An assistant suggested pip install fastapi-jwt-helper. It didn't exist when the model was trained; an attacker registered it later, with a post-install script that read environment variables. Fix: every new dependency is a review item: does it exist, who maintains it, how many users, is it the official one? Lockfiles, SCA and a private registry with an allow-list for production builds.

Checklist

  • main is always releasable; branches live hours to a couple of days; unfinished work hides behind flags with an owner and an expiry date.
  • PRs are small, single-purpose and self-reviewed, with a description that says what, why, how it was tested and where to start reading.
  • Commit messages (or squash PR titles) follow Conventional Commits and are linted; history on main builds at every commit.
  • --force-with-lease, pull.rebase, rerere and rebase.updateRefs are configured.
  • Reviewers read the description first and work through correctness, design, security, tests and readability before nits.
  • Comments are labelled, explain the reason, and say what blocks; the review ends with a summary.
  • First response to a PR comes within one business day; CODEOWNERS routes reviews automatically.
  • CI gates (format, build, lint, tests, coverage of changed lines, SCA, secret scan) are required by branch protection, and the same checks run in local hooks.
  • Repeated review comments are turned into tests, checklists or lint rules.
  • Significant decisions are ADRs in the repo; the README gets a newcomer to a passing test run in under an hour.
  • AI-generated code and new dependencies get the same review as any other code, with tests agreed first.

Self-check

Your team uses GitFlow and releases monthly. Every release week is a merge-conflict marathon. What would you change first, and what has to be in place before you can?

Move toward trunk-based development: short-lived branches merged to main at least daily, so conflicts stay small and are found while the change is fresh. Before you can, you need things that make merging unfinished work safe: a required CI pipeline that people trust (fast and not flaky), feature flags so incomplete features can merge switched off, and small PRs so daily merging is realistic. Release branches can stay if you need to support old versions, but cut them from main and fix bugs on main first, then cherry-pick.

A colleague's PR is 1,800 lines: a new feature, a rename across 40 files, and a dependency upgrade. How do you respond, constructively?

Ask for it to be split, and offer a concrete plan: the dependency upgrade alone (mechanical, CI verifies it), then the rename alone (mechanical, skim it), then the feature on top, ideally as a stack so the author isn't blocked. Explain why: you'd review the feature far more carefully without 1,400 lines of noise around it. If splitting is genuinely impossible right now, ask for a description that says which files are mechanical and where the real logic is, and review the logic first. Next time, suggest the author check in early with a draft PR.

You rebased your feature branch onto main and the commit hashes all changed. Why? And when is this a problem?

A commit's hash covers its content and its parent's hash. Rebasing gives your first commit a new parent (the tip of main), so its hash changes, which changes the parent of the next commit, and so on up the branch. It's a problem only if somebody else has those old commits: a colleague who branched from yours, or a pushed branch someone has checked out. They now have commits that look like duplicates, and pushing requires a force-push. That's why the golden rule is to rewrite only commits nobody else has built on, and to use --force-with-lease.

Your commit history since v2.3.1 contains: fix(api): handle empty cart, feat(search): filter by date, docs: fix typo, and refactor(core)!: drop .NET 6 support. What's the next version, and why?

3.0.0. The ! on the refactor marks a breaking change, which forces a MAJOR bump regardless of the type; the feat alone would have given 2.4.0 and the fix alone 2.3.2. docs doesn't affect the version. (If the project were still at 0.x, many tools would bump the minor version instead, because in semver 0.x anything may change.)

A reviewer leaves 12 comments: 9 about formatting, 2 about naming, and 1 noting that a new endpoint doesn't check that the order belongs to the caller. What should change, on both sides?

The authorization comment is the only one that matters; it should be labelled issue (blocking) and stated first, because it's a security hole (IDOR). The 9 formatting comments shouldn't exist: add the formatter to the editor, a pre-commit hook and CI, and the whole category disappears. The naming comments should be labelled nit or suggestion so the author knows they're optional. The author should fix the authorization check, add a test that another user gets a 403/404, and search for the same missing check in other endpoints, then maybe propose a policy or analyzer that makes it hard to forget.

An AI assistant generated a 300-line service and 20 passing tests in two minutes. What do you check before you approve it?

That the tests actually specify the behaviour: read the assertions, check they don't mock the unit under test, and break the code on purpose (or run mutation testing) to confirm the tests fail. Check every new dependency exists and is the real, maintained package. Then review like any PR: correctness (edge cases, errors, concurrency), design fit (does it use our existing clients, error handling and patterns?), security (input handling, authz, secrets, logging), readability. If you can't explain a line, ask or rewrite it. Better still, next time agree the tests first and generate in smaller steps.
