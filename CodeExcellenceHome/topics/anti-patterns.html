DESIGN PATTERNS

Anti-Patterns & Code Smells

God objects, anemic models, service locator, primitive obsession, shotgun surgery and their escape routes.

Intermediate~35 min studyBuilds on: Design Principles: SOLID, DRY, KISS, YAGNIUpdated 2026-11-03

The problem: code that fights every change

A team gets a simple ticket: "add a Platinum customer tier with 15% off and free express shipping". The estimate is half a day. Here is what they find:

public class OrderManager                                   // 3,400 lines, 41 fields, 120 methods
{
    public decimal Checkout(string customerId, string tier, bool express, bool giftWrap, bool isTest)
    {
        var db = ServiceLocator.Get<IDb>();                 // hidden dependency
        if (tier == "Gold") discount = 0.10m;               // tier rules #1 of 7, in 7 files
        else if (tier == "gold") discount = 0.10m;          // someone fixed a bug in one copy
        var rate = Settings.Current.TaxRate;                // static global, changed by tests
        var stock = _inventory.CheckAsync(sku).Result;      // blocks a thread-pool thread
        try { _mailer.Send(receipt); }
        catch (Exception) { /* emails are flaky, ignore */ }
        if (total > 250) shipping = 0;                      // what is 250? in which currency?
        // ... 300 more lines
    }
}

Half a day becomes two weeks. Tier names are compared as strings in seven files, one of them lowercase. OrderManager does pricing, stock, email and PDFs, so every change collides with someone else's. The tests are flaky because two of them write the same static tax rate. Under Black Friday load the site hangs with low CPU, because .Result holds threads that the continuations need.

None of these lines is a bug on its own. Each is an anti-pattern: a solution that looks reasonable locally, is common enough to have a name, and makes the code steadily more expensive to change. Naming them gives you a vocabulary for code review ("this is feature envy") and, more usefully, a known way out.

An anti-pattern is a recurring solution whose costs show up later than its benefits. Learn to spot the smell early, know the refactoring that removes it, and know when it is actually fine. A smell is a reason to look closer, not an automatic defect.

This page builds on design principles: most smells here are a broken principle with a name. It also links to the patterns that fix them in creational patterns, structural patterns, behavioral patterns and functional patterns.

The mental model: smells at five scales

Smells live at different scales, and the cost of fixing them grows with the scale. A magic number takes a minute to name. A big ball of mud can take years to untangle.

Smell You feel it as First move out
God object every change touches the same file, merge conflicts extract class along field clusters
Anemic domain model rules duplicated across services move behaviour onto the entity
Primitive obsession swapped arguments, validation everywhere value objects / branded types
Feature envy a method full of other.X move method to the data's owner
Shotgun surgery one change, many files gather the knowledge into one type
Service locator hidden dependencies, runtime failures constructor injection
Singleton abuse / global state flaky tests, order dependence inject an instance, scope it in DI
Leaky abstraction "fast" call that is really N queries make the cost visible, batch
Golden hammer the same tool for every problem compare two options before choosing
Premature abstraction interfaces with one implementation, unused options inline it, wait for the third case
Copy-paste divergence a fix lands in one copy only extract after the rule of three
Boolean flag params Export(r, true, false, true) separate methods, enum, options object
Magic numbers/strings if (x > 250) named constants, enums, config
Exception control flow slow paths, swallowed errors TryX, Result types, explicit checks
Sync over async hangs under load, deadlocks async all the way
Distributed monolith deploy 6 services together async events, own your data
Big ball of mud nobody can explain the structure find cycles, cut edges, strangle

The rest of the page takes each smell in turn: what it is, a smell detector checklist, an interactive visual where the cost is dynamic, a before/after refactoring, and when the "smell" is actually the right call.

Class-level smells

God object

A god object (or god class, or blob) knows and does too much: OrderManager, Utils, Helper, AppService, MainForm. It starts as a reasonable home for "order stuff" and grows because adding a method to the class everyone already depends on is always the easiest path. Eventually it has dozens of fields, hundreds of methods, and every feature branch edits it.

The cost is not the line count. It is that unrelated reasons to change share one file: the pricing team, the warehouse team and the email team all edit OrderManager, so changes collide, tests need every dependency mocked, and nobody can hold the class in their head.

Smell detector: god object

  • The class name is vague (Manager, Service, Helper, Utils, Processor) or names the whole domain.
  • More than ~10 constructor dependencies, or tests need a page of mocks before the first assertion.
  • Methods split into groups that use disjoint fields (low cohesion; LCOM4 > 1).
  • It is in the top 5 most-changed files in git log and causes most merge conflicts.
  • You can't describe what it does without the word "and".

The visualizer below runs the cohesion measurement from design principles. Each method lists the fields it uses. Methods that share a field belong together; the algorithm merges them step by step (union-find) and the number of groups left is LCOM4. Each group is a class waiting to be extracted. Try the presets, or type your own class.

The default class splits into four groups: ordering (cart, stock, prices, warehouse), payments (payments, ledger), documents (smtp, templates, pdf) and audit. The shopping-cart preset is the counter-example: five methods, one group, LCOM4 = 1. A long class can still be cohesive.

public class OrderManager
{
    private readonly IDb _db; private readonly IPaymentGateway _payments;
    private readonly ILedger _ledger; private readonly ISmtp _smtp;
    private readonly ITemplates _templates; private readonly IPdf _pdf;
    private readonly IStock _stock; private readonly IPrices _prices;

    public void ReserveStock(Order o) { /* stock */ }

    public void EmailReceipt(Receipt r) { /* smtp, templates */ }
    public byte[] RenderInvoicePdf(Order o) { /* templates, pdf */ }
}

// One class per field cluster. Each has one reason to change.
public sealed class OrderPlacement(IStock stock, IPrices prices)
{
    public Order Place(Cart cart) { /* ... */ }
    public void Reserve(Order o) { /* ... */ }
}
public sealed class Billing(IPaymentGateway payments, ILedger ledger)
{
    public Receipt Charge(Order o) { /* ... */ }
    public void Refund(Order o) { /* ... */ }
}

{
    public void Email(Receipt r) { /* ... */ }
    public byte[] InvoicePdf(Order o) { /* ... */ }
}
// A thin coordinator (or a handler per use case) composes them:
public sealed class CheckoutHandler(OrderPlacement place, Billing billing, ReceiptDocuments docs)
{
    public Receipt Handle(Cart cart)
    {
        var order = place.Place(cart);
        var receipt = billing.Charge(order);
        docs.Email(receipt);
        return receipt;
    }
}

How to get out safely. Don't rewrite. Pin current behaviour with characterization tests, then extract one field cluster at a time, leaving the old method delegating until every caller has moved.

When it's fine. A composition root (Program.cs, main.go) legitimately knows everything. So does a facade, as long as it only delegates. A 300-line script that runs once is not worth splitting. Size alone is not the smell; mixed responsibilities are.

Anemic domain model

In an anemic domain model, the domain objects are bags of getters and setters, and all the rules live in "service" classes that pull the data out, decide, and push it back. Martin Fowler named it in 2003: you pay for an object model (ORM mapping, classes) but get procedural code. Because the object can't protect itself, every service that touches it must remember every rule, and some of them won't.

Smell detector: anemic domain model

  • Entities have public setters for everything and no methods besides getters/setters.
  • Services named after entities (OrderService, CustomerService) hold if (order.Status == ...) logic.
  • The same validation appears in the controller, the service and the import job.
  • Invalid objects are easy to create (new Order { Status = Shipped, Lines = null }).
  • Feature envy is everywhere: service methods mostly read other objects' fields.
public class Order
{
    public OrderStatus Status { get; set; }
    public List<OrderLine> Lines { get; set; } = new();
    public decimal Total { get; set; }
}

public class OrderService
{
    public void Cancel(Order order, string reason)
    {
        if (order.Status == OrderStatus.Shipped)
            throw new InvalidOperationException("Already shipped");
        order.Status = OrderStatus.Cancelled;   // AdminService does the same, minus the check
    }
}

public class Order
{
    private readonly List<OrderLine> _lines = new();
    public OrderStatus Status { get; private set; } = OrderStatus.Draft;
    public IReadOnlyList<OrderLine> Lines => _lines;
    public decimal Total => _lines.Sum(l => l.Price * l.Qty);

    public void AddLine(Sku sku, int qty, decimal price)
    {
        if (Status != OrderStatus.Draft) throw new InvalidOperationException("Order is locked");
        if (qty <= 0) throw new ArgumentOutOfRangeException(nameof(qty));
        _lines.Add(new OrderLine(sku, qty, price));
    }

    public void Cancel(string reason)
    {
        if (Status == OrderStatus.Shipped) throw new InvalidOperationException("Already shipped");
        Status = OrderStatus.Cancelled;
    }
}

When it's fine. Anemic is not always wrong:

  • CRUD with little logic. If the "rules" are "save what the form sent", a rich model is ceremony. A data class plus validation attributes is honest.
  • DTOs, API contracts, messages, view models are supposed to be data only. The smell is when the domain model looks like a DTO.
  • Functional style. Immutable records plus pure functions over them (functional core) is not anemic: the data can't be put into an invalid state, because it can't be mutated at all, and constructors validate. The smell is mutable data with rules elsewhere.

Primitive obsession

Primitive obsession is using string, int, decimal and bool for domain concepts that have rules: an email address, a money amount with a currency, a customer id, a percentage. The type system can't tell a CustomerId from an OrderId when both are string, so it can't stop you swapping them, and every function that receives one has to re-validate it (or trust that someone did).

Smell detector: primitive obsession

  • Several parameters of the same primitive type in a row (string, string, string).
  • The same validation (Regex.IsMatch(email, ...), amount >= 0) in many places.
  • Parallel parameters that always travel together: amount + currency, lat + lng, start + end.
  • Comments explaining the format: // ISO country code, // cents, // UTC.
  • Bugs where units are mixed: seconds vs milliseconds, cents vs euros.

Every language can express a small validated value type; how cheap it is differs:

public readonly record struct Money
{
    public decimal Amount { get; }
    public string Currency { get; }
    public Money(decimal amount, string currency)
    {
        if (amount < 0) throw new ArgumentOutOfRangeException(nameof(amount));
        if (currency is not { Length: 3 }) throw new ArgumentException("ISO 4217 code", nameof(currency));
        (Amount, Currency) = (amount, currency.ToUpperInvariant());
    }
    public Money Add(Money other) => other.Currency == Currency
        ? new Money(Amount + other.Amount, Currency)
        : throw new InvalidOperationException("Currency mismatch");
}

public readonly record struct CustomerId(Guid Value);   // can't be passed as an OrderId

public record Money(BigDecimal amount, String currency) {
    public Money {                                   // compact constructor validates
        if (amount.signum() < 0) throw new IllegalArgumentException("negative");
        if (currency == null || currency.length() != 3) throw new IllegalArgumentException("ISO 4217");
        currency = currency.toUpperCase(Locale.ROOT);
    }
    public Money add(Money other) {
        if (!other.currency.equals(currency)) throw new IllegalStateException("Currency mismatch");
        return new Money(amount.add(other.amount), currency);
    }
}

public record CustomerId(UUID value) {}

    if cents < 0 {
        return Money{}, errors.New("negative amount")
    }
    if len(currency) != 3 {
        return Money{}, errors.New("ISO 4217 code expected")
    }
    return Money{cents, strings.ToUpper(currency)}, nil

func (m Money) Add(o Money) (Money, error) {
    if m.currency != o.currency {
        return Money{}, errors.New("currency mismatch")
    }
    return Money{m.cents + o.cents, m.currency}, nil
}

class Money {
  private constructor(readonly amount: number, readonly currency: string) {}
  static of(amount: number, currency: string): Money {
    if (amount < 0) throw new RangeError("negative amount");
    if (currency.length !== 3) throw new RangeError("ISO 4217 code expected");
    return new Money(amount, currency.toUpperCase());
  }
  add(o: Money): Money {
    if (o.currency !== this.currency) throw new Error("currency mismatch");
    return Money.of(this.amount + o.amount, this.currency);
  }
}

The differences are about cost. C# readonly record struct and Java records are one line for the simple id case and allocate nothing extra (the struct) or very little. Go's defined types (type CustomerID string) are free, but a constant string still converts implicitly to them, so unexported fields plus a constructor are what really protect Money. Python's NewType vanishes at runtime and only helps if you run a type checker. TypeScript is structural, so two string aliases are the same type; the "brand" intersection is the standard trick to make them different. Money in floating point (number, double) is its own bug: use integer cents or a decimal type.

When it's fine. Inside a small private function, or at the boundary where you parse JSON or database rows, primitives are normal. Convert to the value type as soon as you've parsed, and back at the very end. Don't wrap every int loop counter: wrap concepts that have rules or that get confused with each other.

Feature envy

A method has feature envy when it is more interested in another class's data than in its own: it reads five fields from customer and none from this. The method is in the wrong place. Wherever the data changes shape, this method must change too, but it lives somewhere else, so people don't find it. It's the class-level version of the Law of Demeter problem.

Smell detector: feature envy

  • A method's body is mostly other.X, other.Y, other.Z, with few or no this. accesses.
  • Chains like order.Customer.Address.Country.TaxRules.
  • The same set of fields of one class is read together in several places.
  • A method's parameters are one object, and every line reads from it.

The visualizer counts whose members a method touches, in order. When most reads belong to one other object, it suggests moving the method there. When the reads are split between two other objects, it suggests splitting the method so each part moves to its data.

public class InvoiceService
{
    private readonly Rates _rates;
    public decimal LoyaltyDiscount(Customer customer, Order order)
    {
        var pct = customer.Tier switch { Tier.Gold => 0.10m, Tier.Silver => 0.05m, _ => 0m };
        if (customer.YearsActive > 5) pct += 0.02m;
        if (customer.IsEmployee) pct = Math.Max(pct, 0.20m);
        if (customer.Country == "NO") pct = Math.Min(pct, _rates.NorwayCap);
        return order.Total * pct;
    }
}

public class Customer
{
    // The rule now lives next to the data it depends on.
    public decimal LoyaltyPercent(decimal countryCap)
    {
        var pct = Tier switch { Tier.Gold => 0.10m, Tier.Silver => 0.05m, _ => 0m };
        if (YearsActive > 5) pct += 0.02m;
        if (IsEmployee) pct = Math.Max(pct, 0.20m);
        return Country == "NO" ? Math.Min(pct, countryCap) : pct;
    }
}

public class InvoiceService
{
    private readonly Rates _rates;
    public decimal LoyaltyDiscount(Customer customer, Order order)
        => order.Total * customer.LoyaltyPercent(_rates.NorwayCap);
}

When it's fine. Some patterns separate behaviour from data on purpose: a Strategy or Visitor operates on another object's data so that you can vary the algorithm independently; mappers and serializers read every field of a DTO by definition; reporting queries read many entities. Feature envy is a smell when the logic is a rule of that object that will change when the object changes.

Shotgun surgery

Shotgun surgery is the opposite of a god object: one change forces small edits in many places. Adding a customer tier means touching pricing, shipping, the email templates, the admin UI, the reports and the CSV export, each with its own if (tier == "Gold"). The danger is the place you don't find. Search is the only tool, and search is literal: someone wrote "gold" in lowercase, or tier.StartsWith("G").

The visualizer simulates the ticket "add a Platinum tier". In the scattered design, the developer searches for a term; every file the search finds gets updated, and every file it misses ships a bug. Switch to the consolidated design (one CustomerTier type that owns the rules) and the same ticket is one file.

Smell detector: shotgun surgery

  • A feature request's diff touches many files with one or two lines each.
  • The same switch/if over a type code (tier, status, country) appears in several classes.
  • "Did you remember to also update X?" is a regular code-review comment.
  • git log shows sets of files that always change together but live in different modules.
  • Bugs where "it works everywhere except the export" (the place nobody remembered).
// Pricing.cs
if (customer.Tier == "Gold") discount = 0.10m;
// Shipping.cs
var free = customer.Tier == "Gold" || customer.Tier == "Silver";
// ReceiptEmail.cs
var badge = customer.Tier == "Gold" ? "★ Gold member" : "";
// CsvExport.cs
row.Add(customer.Tier.ToLower() == "gold" ? "G" : "S");
// ... and 4 more files

// CustomerTier.cs: everything a tier means, in one place.
public sealed record CustomerTier(string Name, decimal Discount, bool FreeShipping, string Badge, string ExportCode)
{
    public static readonly CustomerTier Standard = new("Standard", 0.00m, false, "", "S");
    public static readonly CustomerTier Silver   = new("Silver",   0.05m, true,  "Silver member", "V");
    public static readonly CustomerTier Gold     = new("Gold",     0.10m, true,  "★ Gold member", "G");
    public static readonly CustomerTier Platinum = new("Platinum", 0.15m, true,  "◆ Platinum",    "P"); // the whole ticket
}
// Callers ask the tier: customer.Tier.Discount, customer.Tier.FreeShipping, customer.Tier.Badge ...

Replacing the scattered conditional with a type that owns the variation is the classic "replace conditional with polymorphism" (or, when the variants only differ in data, "replace type code with a table/record", as above). If tiers differ in behaviour, use a Strategy per tier; if the set is closed and you prefer functions, a discriminated union with an exhaustive match makes the compiler find every place for you.

When it's fine. A change that crosses layers (a new field goes in the database, the API, and the UI) touches several files by nature. Vertical slices (one folder per feature with its endpoint, handler and query) keep those edits next to each other. The smell is when one business rule is spread across many places.

Dependency and state smells

Service locator

A service locator is a registry that code calls to fetch its dependencies: ServiceLocator.Get<IDb>(), provider.GetService<T>() inside a business class, Spring's context.getBean(...), a global registry["mailer"]. It looks like dependency injection, because a container is involved, but it inverts the benefit. The class's constructor no longer tells you what it needs, so the dependencies are hidden, they fail at run time instead of start-up, and every test has to configure the global registry. The full comparison is in DI fundamentals.

Smell detector: service locator

  • IServiceProvider, ApplicationContext, Injector or a global Container passed into or referenced from business classes.
  • Static ServiceLocator.Current, Locator.Get, registry.get("...") calls inside methods.
  • Tests start with "register these five fakes in the global container" and must reset it afterwards.
  • Missing registrations are discovered by a user, not by start-up validation.
// Smell: the class asks for the whole container
public class CheckoutHandler(IServiceProvider sp)
{
    public void Handle(Cart c) => sp.GetRequiredService<IMailer>().Send(/* ... */);
}

// Fix: ask for what you use; register with builder.Services and
// turn on ValidateOnBuild/ValidateScopes so mistakes fail at start-up.
public class CheckoutHandler(IDb db, IMailer mailer, TimeProvider clock)
{
    public void Handle(Cart c) => mailer.Send(/* ... */);
}

// Smell: reaching into the Spring context
@Service
class CheckoutHandler {
    @Autowired ApplicationContext ctx;
    void handle(Cart c) { ctx.getBean(Mailer.class).send(/* ... */); }
}

// Fix: constructor injection (no @Autowired needed with one constructor)
@Service
class CheckoutHandler {
    private final Mailer mailer;
    private final Clock clock;
    CheckoutHandler(Mailer mailer, Clock clock) { this.mailer = mailer; this.clock = clock; }
    void handle(Cart c) { mailer.send(/* ... */); }
}

# Smell: a module-level registry looked up at call time
REGISTRY: dict[str, object] = {}

def handle(cart):
    REGISTRY["mailer"].send(...)


# Fix: pass collaborators in; wire them once in main() or with FastAPI's Depends
class CheckoutHandler:
    def __init__(self, db: Db, mailer: Mailer, clock: Callable[[], datetime]):
        self._db, self._mailer, self._clock = db, mailer, clock

    def handle(self, cart):
        self._mailer.send(...)

// Smell: package-level registry
var services = map[string]any{}

func Handle(c Cart) { services["mailer"].(Mailer).Send( /* ... */ ) } // panics if missing

// Fix: dependencies are struct fields set by a constructor; main() wires them.
type CheckoutHandler struct {
    db     DB
    mailer Mailer
    now    func() time.Time
}

func NewCheckoutHandler(db DB, m Mailer, now func() time.Time) *CheckoutHandler {
    return &CheckoutHandler{db: db, mailer: m, now: now}
}

// Smell: a global container queried inside methods
class CheckoutHandler {
  handle(c: Cart) { container.get<Mailer>("mailer").send(/* ... */); }
}

// Fix: constructor parameters (with or without a DI library such as NestJS or tsyringe)
class CheckoutHandler {
  constructor(private readonly db: Db, private readonly mailer: Mailer, private readonly now: () => Date) {}
  handle(c: Cart) { this.mailer.send(/* ... */); }
}

When it's fine. Framework glue that genuinely can't use constructors: the composition root itself, a factory that creates per-request objects (IServiceScopeFactory in a background service), attribute/filter infrastructure, or a plugin host resolving types by name. Keep it at the edge, never in domain code.

Singleton abuse and global state

A singleton is fine as a lifetime ("one instance per application"). The anti-pattern is the static, mutable, globally reachable singleton: Settings.Current.TaxRate = 0.25m from anywhere, Cache.Instance, Logger.Default, a module-level dict in Python, a package var in Go. Any code can read it without declaring it and change it without telling anyone, so every function that touches it has a hidden input and a hidden output (exactly what pure functions avoid).

The first place it bites is tests. Test runners run tests in parallel and in an order they choose. The visualizer runs two tests, A and B, that each set a tax rate and then read it back. You choose the interleaving; it also counts how many of the 20 possible interleavings fail. With the static global, test A passes when run alone and fails when B sneaks in between its write and its read. With an injected config, every interleaving passes.

Smell detector: singleton abuse and global state

  • static (or module-level, or package-level) fields that are written after start-up.
  • X.Instance / X.Current / getInstance() called from inside business logic.
  • Tests pass alone and fail together, or need [Collection]/@NotThreadSafe/-p 1 to be stable.
  • Tests contain "reset" calls in setup/teardown for static state.
  • DateTime.Now, Random.Shared, Environment reads deep inside the domain (ambient globals).
public static class TaxConfig { public static decimal Rate = 0.20m; }

public class PriceCalculator
{
    public decimal Gross(decimal net) => net * (1 + TaxConfig.Rate);   // hidden input
}

[Fact] public void Uses_reduced_rate()
{
    TaxConfig.Rate = 0.05m;                                              // hidden output: leaks into other tests
    Assert.Equal(105m, new PriceCalculator().Gross(100m));
}

public sealed record TaxConfig(decimal Rate);

public class PriceCalculator(TaxConfig tax)
{
    public decimal Gross(decimal net) => net * (1 + tax.Rate);
}

// Program.cs: still exactly one instance, but the container owns it
builder.Services.AddSingleton(new TaxConfig(builder.Configuration.GetValue<decimal>("Tax:Rate")));

[Fact] public void Uses_reduced_rate()
    => Assert.Equal(105m, new PriceCalculator(new TaxConfig(0.05m)).Gross(100m));

The fix keeps "one instance" but moves it from a static field to the container, as explained in why a DI singleton beats a static singleton. The same move in other ecosystems: a Spring @Bean (singleton scope is the default), a Go struct created in main and passed down, a Python object created in main() or a FastAPI dependency, a TypeScript module that exports a factory instead of an instance. For time, inject TimeProvider (.NET 8+), java.time.Clock, or a now function.

When it's fine. Immutable globals are constants, not state: static readonly lookup tables, compiled regexes, HttpClient / JsonSerializerOptions instances configured once and never changed. Logging facades (ILogger<T> via DI, or SLF4J's static loggers) are an accepted compromise because they are write-only and have no effect on behaviour.

Leaky abstractions

Joel Spolsky's Law of Leaky Abstractions: "all non-trivial abstractions, to some degree, are leaky". An abstraction hides details so you can ignore them, until the hidden details (latency, failure modes, memory, ordering) start dominating behaviour and you have to understand what's underneath anyway. The anti-pattern is designing or using an abstraction that hides a cost so well that callers can't see it, then acting surprised in production.

The classic case is an ORM's lazy loading. order.Customer.Name reads like a field access, but if the customer isn't loaded, it runs a SQL query. In a loop, that is the N+1 query problem: one query for the list, plus one per item. Step through the visualizer with lazy loading, then switch to Include or a batched IN (...) query and compare the round trips. Change the round-trip time to see why the same code is fine on a laptop and slow in the cloud.

Other leaks you will meet:

  • Remote calls that look local. A repository interface backed by an HTTP service; a "getter" that calls another microservice. Latency, timeouts and partial failure don't exist in the interface but dominate in practice (see resilience).
  • IEnumerable / Iterable hiding a query. Enumerating twice runs the query twice (lazy sequences).
  • Generic repositories over IQueryable. IRepository<T>.Query() leaks the ORM's translation rules: a C# method call that EF can't translate fails at run time.
  • Caches that hide staleness: callers can't tell fresh data from five-minute-old data (caching).

Smell detector: leaky abstraction

  • Performance depends on how the caller uses the API (order of calls, which properties are touched).
  • The SQL log shows the same query shape repeated with different ids.
  • To use the abstraction correctly you must read its implementation.
  • Interfaces that return IQueryable, lazy collections or proxies across layer boundaries.
  • Method names that hide I/O: GetPrice() that calls a remote service without Async or a cancellation token.

The fix is to make the cost visible and batchable. Every ecosystem's data layer has the same three options: eager-load in the query, batch-load with IN (...), or write the query by hand.

// EF Core: eager load, and see the SQL in development
var orders = await db.Orders
    .Include(o => o.Customer)
    .Where(o => o.Date == today)
    .AsSplitQuery()            // optional: avoid huge JOIN row duplication
    .ToListAsync(ct);
// options.LogTo(Console.WriteLine, LogLevel.Information) shows every query

// JPA / Hibernate: fetch join or an entity graph
@Query("select o from Order o join fetch o.customer where o.date = :d")
List<Order> findWithCustomer(@Param("d") LocalDate d);

// or: @EntityGraph(attributePaths = "customer")
// spring.jpa.properties.hibernate.default_batch_fetch_size=50 batches the rest

# SQLAlchemy 2.x: selectinload issues ONE extra "WHERE id IN (...)" query
stmt = (
    select(Order)
    .where(Order.date == today)
    .options(selectinload(Order.customer))
)
orders = session.scalars(stmt).all()
# Django equivalent: Order.objects.filter(date=today).select_related("customer")

// Go has no lazy-loading ORM in the standard toolkit: queries are explicit,
// so N+1 is visible as a query inside a loop. Batch it.
rows, err := db.QueryContext(ctx,
    `SELECT o.id, c.name FROM orders o
     JOIN customers c ON c.id = o.customer_id
     WHERE o.date = $1`, today)

// Prisma: include runs a second batched query, not one per order
const orders = await prisma.order.findMany({
  where: { date: today },
  include: { customer: true },
});
// GraphQL resolvers: use DataLoader to batch per-field lookups into one IN query

When it's fine. All abstractions leak; that alone is not a reason to drop them. Keep the ORM, keep lazy loading for admin screens that touch one record. Just know the leak, log the SQL, and put a test or a query-count assertion on the hot paths.

Design-process smells

Golden hammer

"If all you have is a hammer, everything looks like a nail." The golden hammer is reaching for the tool you know best, or the one that worked last time, regardless of the problem: microservices for a three-person team, Kafka for a queue of ten messages an hour, a NoSQL store for highly relational data, regex for parsing HTML, a design pattern in every class, or the whole team's favourite framework for a 50-line script.

Smell detector: golden hammer

  • Architecture decisions without a written alternative ("we'll use X" with no "instead of Y because").
  • The same technology appears in every design doc, regardless of scale or shape.
  • Workarounds to make the tool fit (fake request/reply over a log, joins in application code over a key-value store).
  • The reason given is familiarity, or a conference talk, not a property of the problem.

Way out. Write a short decision record with two options and the simplest one that could work. Ask what the problem needs (consistency, latency, volume, query shape, team size), then which tool has those properties. Spikes are cheap; migrations are not.

When it's fine. Standardising on a few well-understood tools is a real benefit: shared expertise, one way to operate, fewer pager surprises. "Boring technology" is a deliberate choice. The smell is when the standard tool is clearly wrong for the shape of the problem and nobody is allowed to say so.

Premature abstraction and speculative generality

Speculative generality is building for needs you imagine: an IPaymentProcessorFactoryProvider for the one payment provider, a plugin system nobody plugs into, abstract base classes with one subclass, configuration options for things that never vary, a Repository<T> wrapper over an ORM that is already a repository. Premature abstraction is the closely related habit of extracting a shared function or base class after seeing the second similar piece of code, before you know what actually varies.

Both cost you twice. You pay to build and read the indirection now, and you pay again when the real second case arrives and doesn't fit the shape you guessed. Sandi Metz's summary: "duplication is far cheaper than the wrong abstraction". A wrong abstraction grows parameters and boolean flags (if (isLegacy) ...) until every caller passes a different combination, which is the flag parameter smell.

Smell detector: speculative generality

  • Interfaces with exactly one implementation and no test double, no second assembly boundary, no plugin need.
  • Abstract classes with one subclass; generic type parameters that are always the same type.
  • Parameters, options or hooks that every caller passes the same value for, or nobody uses.
  • Names with stacked suffixes: FactoryProvider, ManagerFactory, BaseAbstractHandler.
  • "We might need to support X later" in the PR description, with no ticket for X.
public interface IReportFormatterFactory { IReportFormatter Create(ReportKind kind); }
public interface IReportFormatter { string Format(Report r, FormatOptions o); }
public abstract class ReportFormatterBase : IReportFormatter { /* template method nobody overrides */ }
public sealed class CsvReportFormatter : ReportFormatterBase { /* the only one */ }
public sealed class FormatOptions { public bool Legacy { get; init; } public string? Culture { get; init; } } // always default

public static class CsvReport
{
    public static string Format(Report r) => /* 20 straightforward lines */;
}
// Need a second format later? Extract an interface from two concrete, working versions.

When abstraction up front is right. When the variation is known, not imagined: a public library API that can't break later, an interface at an I/O boundary that you need to fake in tests, a plugin point you are contractually building, or a module boundary between teams. The rule of thumb is the rule of three: write it once, tolerate it twice, abstract on the third time, when you can see what really varies. See also YAGNI.

Copy-paste and divergence

Copy-paste is the fastest way to write the second version of something. The anti-pattern is what happens next: the copies diverge. A bug is fixed in one copy; a rule changes in two of three; someone copies the stale copy to create a fourth. Eventually nobody knows which version is right, and the copies disagree in production.

Smell detector: copy-paste divergence

  • Duplicate-code reports (SonarQube, PMD CPD, jscpd, pylint duplicate-code, dupl for Go) show blocks with small differences.
  • A bug fix PR touches one file, and the same bug is reported again a month later from another screen.
  • Functions named ValidateOrder2, calcNew, handler_copy.
  • Similar code that differs in one literal or one condition, with no comment saying why.

Way out. Extract the shared knowledge into one function, type or table, and make the differences explicit parameters. Before extracting, ask whether the copies represent the same rule or two rules that happen to look alike today. DRY is about knowledge, not text: two validation rules owned by different teams that coincidentally match should stay separate, or you'll couple them (the premature abstraction above). See DRY, WET and the rule of three.

When it's fine. Tests often read better with some repetition (each test self-contained). Copying across service boundaries can be intentional, to avoid a shared library that couples deploys. Generated code is duplicated by design.

Code-level smells

Boolean flag parameters

Export(report, true, false, true, false). What does the third true mean? A flag argument says "this method does two different things, and the caller picks one". Each flag doubles the behaviours the method has, and the signature can't say which combinations make sense. The visualizer enumerates every combination for a set of flags and marks the ones your rules say are nonsense. Each still compiles.

Smell detector: boolean flag parameters

  • Call sites with bare true/false literals that need a comment or an IDE hint to read.
  • The method body starts with if (flag) { ...one thing... } else { ...another... }.
  • Pairs of flags that contradict each other (dryRun and overwrite, includeDeleted and onlyDeleted).
  • A flag added to an existing shared method "so it works for my case too" (a wrong abstraction growing).

There are three ways out, and the right one depends on what the flag does. If it switches the whole behaviour, split the method (Preview vs Export). If it chooses one of several modes, use an enum. If several flags are independent options, use a named options object (or keyword arguments).

public enum Delivery { Download, Email }
public sealed record ExportOptions(bool Zip = false, bool Overwrite = false);

public void Export(Report r, Delivery delivery, ExportOptions? options = null) { /* ... */ }
public ExportPreview Preview(Report r) { /* dry run is a different operation */ }

Export(report, Delivery.Email, new(Zip: true));     // reads like a sentence

enum Delivery { DOWNLOAD, EMAIL }
record ExportOptions(boolean zip, boolean overwrite) {
    static ExportOptions defaults() { return new ExportOptions(false, false); }
    ExportOptions withZip() { return new ExportOptions(true, overwrite); }
}

void export(Report r, Delivery delivery, ExportOptions options) { /* ... */ }
ExportPreview preview(Report r) { /* ... */ }

export(report, Delivery.EMAIL, ExportOptions.defaults().withZip());

from enum import Enum


class Delivery(Enum):
    DOWNLOAD = "download"
    EMAIL = "email"

When it's fine. A single, obviously named boolean whose meaning is clear at the call site with named arguments (list.Sort(descending: true), Python's sorted(xs, reverse=True)). Setters like SetVisible(bool) aren't flags: the boolean is the data, not a switch between behaviours.

Magic numbers and strings

A magic number is an unexplained literal with meaning: if (total > 250), Thread.Sleep(3000), status == 4, role == "adm". The reader can't tell what it means, which unit it is in, or whether the 250 in Shipping.cs is the same rule as the 250 in Checkout.cs. Changing it means searching for a number, which also finds every unrelated 250. Magic strings add typos that compile ("Gold" vs "gold", as in shotgun surgery).

Smell detector: magic numbers and strings

  • Numeric literals other than 0, 1 and -1 in conditions, timeouts, sizes and calculations.
  • The same literal in several files.
  • Durations without units (Sleep(3000), timeout=30).
  • String comparisons against status, role or type names.
  • Analyzers already flag them: Sonar S109, Checkstyle MagicNumber, ESLint no-magic-numbers, pylint magic-value-comparison, gomnd.
if (order.Total > 250 && customer.Country == "DE") shipping = 0;
if (user.Role == "adm") ShowAuditLog();
await Task.Delay(3000);

public static class ShippingRules
{
    public static readonly Money FreeShippingThreshold = new(250m, "EUR");   // from the 2024 pricing policy
}
public enum Role { Customer, Support, Admin }

if (order.Total >= ShippingRules.FreeShippingThreshold && customer.Country == Country.Germany) shipping = Money.Zero;
if (user.Role == Role.Admin) ShowAuditLog();
await Task.Delay(TimeSpan.FromSeconds(3));          // the unit is in the type

Name the concept (not the value: TWO_HUNDRED_FIFTY = 250 is no better), put units in types (TimeSpan, Duration, time.Duration, timedelta), and move values that change per environment or per business decision to configuration. Fixed sets of strings become enums or union types.

When it's fine. Literals whose meaning is the literal itself: x * 2 to double, % 2 == 0 for even, 100 in a percentage formula, HTTP status codes in tests (Assert.Equal(404, ...)), and test data. Over-extracting (const int Zero = 0) is noise.

Exception-driven control flow

Exceptions are for situations the code can't handle locally: a bug, a broken invariant, an unavailable database. Using them for expected outcomes (validation, "not found", "end of input", "user said no") is the anti-pattern. It is slow (capturing a stack trace costs microseconds, hundreds of times a normal return), it hides the outcome from the signature, and broad catch blocks end up swallowing real bugs along with the expected case.

Smell detector: exception-driven control flow

  • try { int.Parse(s) } catch { ... } around input you expect to be invalid sometimes.
  • catch (Exception) that returns a default, logs nothing, or has an empty body.
  • Exceptions thrown and caught in the same method, or used to break out of nested loops.
  • Profiling shows exception throwing on the hot path; first-chance exception counters are high.
  • Custom exceptions like OrderNotFoundException thrown for every 404.

How "exceptional" an expected failure should be depends on the language's conventions, which is why the fixes differ:

// Smell
int qty;
try { qty = int.Parse(input); } catch (FormatException) { qty = 1; }

// Fix: Try pattern for expected failure; exceptions for bugs.
int qty = int.TryParse(input, out var n) && n > 0 ? n : 1;

// For domain outcomes, return a result type the caller must look at:
public Result<Order, OrderError> Place(Cart cart) { /* ... */ }

// Java has no TryParse; wrap the check once and return Optional.
static Optional<Integer> tryParseInt(String s) {
    if (s == null || !s.matches("-?\\d{1,9}")) return Optional.empty();
    return Optional.of(Integer.parseInt(s));
}
int qty = tryParseInt(input).filter(n -> n > 0).orElse(1);

// Lookups: map.getOrDefault / repo.findById(id) returning Optional, not a thrown NotFound.

# Python's culture is EAFP ("easier to ask forgiveness"): narrow try/except IS idiomatic.
def parse_qty(text: str) -> int:
    try:
        n = int(text)
    except ValueError:          # narrow, expected, cheap enough in Python
        return 1
    return n if n > 0 else 1

# The smell in Python is the BROAD catch that hides bugs:
#     except Exception: pass
print(parse_qty("3"), parse_qty("x"), parse_qty("-2"))   # 3 1 1

// Go: errors are values. The anti-pattern is panic/recover as control flow.
n, err := strconv.Atoi(input)
if err != nil || n <= 0 {
    n = 1
}

// Expected outcomes are sentinel errors the caller checks with errors.Is:
var ErrNotFound = errors.New("order not found")
if errors.Is(err, ErrNotFound) { /* 404 */ }

// Return a discriminated union for expected outcomes; throw for bugs.
type ParseResult = { ok: true; value: number } | { ok: false; error: string };

function parseQty(s: string): ParseResult {
  const n = Number(s);
  return Number.isInteger(n) && n > 0 ? { ok: true, value: n } : { ok: false, error: `bad qty: ${s}` };
}
const r = parseQty(input);
const qty = r.ok ? r.value : 1;

The full treatment of Result/Either and railway-oriented composition is in functional patterns.

When it's fine. Truly exceptional paths: a missing config file at start-up, a lost database connection, an invariant violation. In Python, narrow try/except KeyError and StopIteration are the language's normal protocol. Crossing a boundary that can only signal failure by throwing (some framework callbacks) is fine; catch at the edge and translate.

Sync over async

Sync over async is blocking a thread to wait for asynchronous work: .Result, .Wait(), .GetAwaiter().GetResult() in C#, future.get() / join() on a shared pool in Java, or a blocking call inside an async event loop in Python and JavaScript. It feels harmless because it works on your machine. Under load it starves the thread pool: every blocked thread is a thread that can't run the continuations that would unblock the others. The pool slowly adds threads (in .NET, roughly one or two per second once it is starved), so requests pile up, latency explodes, and the process looks hung with low CPU. In apps with a single-threaded synchronization context (WinForms, WPF, classic ASP.NET) it deadlocks outright.

The visualizer runs a small thread pool. Each request starts (S), awaits I/O for three ticks, and then needs a thread to run its continuation (C). With .Result, the starting thread stays blocked until its own continuation has run on another thread. Run a burst of 8 requests on 4 threads in both modes and compare the Gantt charts and the thread count. For the theory, see thread-pool starvation.

Smell detector: sync over async

  • .Result, .Wait(), GetAwaiter().GetResult(), Task.Run(...).Result in request-handling code.
  • CompletableFuture.join() / get() inside code that itself runs on ForkJoinPool.commonPool().
  • requests.get, time.sleep or a CPU loop inside async def; fs.readFileSync in a Node request handler.
  • Thread count climbing steadily under load, with long latency and low CPU (dotnet-counters: thread pool queue length).
  • async void methods, or sync interfaces implemented by calling async code.
// Smell: blocks a pool thread for the whole I/O wait
public IActionResult Get(int id) => Ok(_client.GetStockAsync(id).Result);

// Fix: async all the way up to the framework
public async Task<IActionResult> Get(int id, CancellationToken ct)
    => Ok(await _client.GetStockAsync(id, ct));

// Smell: blocking join() inside an async stage on the shared common pool
CompletableFuture.supplyAsync(() -> stockClient.getAsync(id).join());

// Fix 1: compose instead of blocking
stockClient.getAsync(id).thenApply(Stock::available);

// Fix 2 (Java 21+): virtual threads make blocking cheap; write plain blocking code
try (var exec = Executors.newVirtualThreadPerTaskExecutor()) {
    exec.submit(() -> stockClient.get(id));
}

import asyncio


# Smell: a blocking call inside the event loop freezes every other request
async def get_stock_bad(item_id):
    import time
    time.sleep(0.05)            # stands in for requests.get(...): blocks the whole loop
    return item_id


# Fix: use an async client (httpx.AsyncClient, aiohttp), or push blocking work to a thread
async def get_stock(item_id):
    await asyncio.sleep(0.05)   # or: await asyncio.to_thread(blocking_call, item_id)
    return item_id


async def main():
    return await asyncio.gather(*(get_stock(i) for i in range(20)))

print(len(asyncio.run(main())))   # 20 requests in ~0.05 s, not 1 s

// Go has no async/await colouring: blocking a goroutine is normal and cheap,
// because the runtime parks it and reuses the OS thread.

// The Go version of this smell: holding a scarce resource while you wait.
mu.Lock()

import { readFile } from "node:fs/promises";

// Smell: synchronous I/O in a request handler blocks the single event-loop thread

The rules are in async all the way. The difference across ecosystems is instructive: in C#, Python and JavaScript, async is a property of the function's type ("coloured functions"), so mixing sync and async needs care at every boundary. Go and Java 21 virtual threads make blocking cheap at the runtime level, which removes this particular smell (but not the ones about holding locks).

When it's fine. Main in an old console app before async Task Main existed; a one-off script; tests in frameworks that don't support async (rare today). If you must, block at the very top, once, never in library code.

Architecture smells

Distributed monolith

A distributed monolith is a system split into services that still can't change or run independently. Every request walks a synchronous chain of HTTP calls; services share a database; deploys have to be coordinated; one service's outage takes down the others. You got the operational cost of microservices (network, serialization, observability, partial failure) and kept the coupling of a monolith.

The arithmetic is unforgiving. If a request synchronously needs five services, each 99.9% available, the request succeeds only when all of them do: 0.999⁵ ≈ 99.5%, about 3.6 hours of failures a month instead of 43 minutes. Latencies add up too. The visualizer multiplies availability and sums latency along your chain, then checks the result with a Monte Carlo of 20,000 requests. Switch to "async events + local data": each service keeps a local copy of what it needs (updated by events), so only the first service is on the request path.

Smell detector: distributed monolith

  • "We have to deploy Orders, Pricing and Stock together" (lock-step releases, shared version numbers).
  • Services read and write the same database tables.
  • One user request fans out into a deep synchronous call chain; a slow service makes everything slow.
  • A shared "common" library with domain models that every service must upgrade at once.
  • Teams can't ship without another team's change.

Distributed monolith

  • Synchronous chains: availability multiplies down.
  • Shared database: schema changes need every team.
  • Lock-step deploys, shared domain library.

Independent services

  • Each service owns its data; others get it via events or APIs.
  • Asynchronous messages for anything not needed in the response.
  • Contracts versioned; deploy one service at a time.

Modular monolith

  • Often the honest answer: one deployable, strict module boundaries.
  • In-process calls, one database with schema per module.
  • Split a module out later, when it has a real reason to scale or ship alone.

When it's fine. A few synchronous calls are normal; queries that need fresh data across services have to call. The smell is when the coupling makes the "micro" in microservices impossible. More in distributed architecture.

Big ball of mud

Brian Foote and Joseph Yoder's 1997 paper: "a haphazardly structured, sprawling, sloppy, duct-tape-and-baling-wire, spaghetti-code jungle". A big ball of mud has no recognisable architecture: every module depends on every other, often in cycles, so nothing can be understood, tested or replaced on its own. It isn't designed; it's what every other smell on this page adds up to over years of deadline pressure.

The measurable part is dependency cycles. If Orders uses Billing, Billing uses Customer and Customer uses Orders, those three are one module in practice: you can't build, test, version or extract any of them alone. The visualizer runs Tarjan's algorithm on your module graph to find every tangle (strongly connected component) in one pass, then tries removing each edge inside the largest tangle and suggests the cut that shrinks it the most.

Smell detector: big ball of mud

  • Nobody can draw the architecture, or the drawing doesn't match the code.
  • Dependency tools (NDepend, ArchUnit, dependency-cruiser/madge, import-linter, go list) report cycles between modules or namespaces.
  • Every change needs a full regression run because "anything could break".
  • New developers take months to become productive; knowledge lives in a few people.
  • Layers exist in folder names only: the UI calls the database, the domain references the web framework.

Some ecosystems prevent the worst of it: Go refuses to compile import cycles between packages, and .NET and Maven/Gradle reject cyclic project references. Cycles between namespaces or classes inside one project are still allowed in all five languages, so add an architecture test that fails the build:

Way out. Not a rewrite (big-bang rewrites of mud usually produce new mud, late). Find the cycles, cut the cheapest edges by inverting dependencies (dependency inversion) or by publishing events, draw module boundaries around what's left, then enforce them with the tests above. Replace the worst areas incrementally with the strangler fig, below.

Refactoring safely: characterization tests and the strangler

Every "way out" above is a refactoring of code that is in production. Two techniques make that safe.

1Pin the behaviour

Write characterization tests: call the code with real-looking inputs and assert whatever it returns today, bugs included. Snapshot/approval tests (Verify, ApprovalTests, syrupy, Jest snapshots) make this fast.

2Make the change easy

Small, behaviour-preserving steps with IDE refactorings: extract method, extract class, move method, introduce parameter object. Commit after each green run.

3Then make the easy change

Only now add the feature or fix the bug, in the newly clean place. Kent Beck: "make the change easy (warning: this may be hard), then make the easy change".

4Strangle what is too big to refactor

Put a facade or routing layer in front, send one use case at a time to new code, and delete the old path when traffic reaches zero.

Use git as a smell detector. git log --format= --name-only | sort | uniq -c | sort -rn | head lists the most-changed files: your god objects. Files that keep appearing in the same commits but live in different folders are your shotgun surgery. Hotspots (high churn × high complexity) are where refactoring pays back first.

Deciding what to fix first

1Is it causing incidents now?

Sync over async, N+1 on a hot path, swallowed exceptions, flaky tests from global state. Fix these first; they cost money every day.

2Is it in a hotspot?

High churn plus high complexity: god objects, shotgun surgery, copy-paste. Refactor as part of the next feature that touches it.

3Will it spread?

Service locators, flag parameters and magic strings get copied as "how we do it here". Stop new instances in review and with analyzers.

4Is it stable and rarely touched?

Leave it. Ugly code that never changes costs almost nothing. Refactoring it adds risk without payback.

Pitfalls

The refactoring rewrite. A team "fixed" a 6,000-line god class by rewriting it from scratch over four months; the new version missed dozens of undocumented edge cases and was rolled back. Fix: characterization tests first, then extract one cluster at a time, shipping after each step.

Swapping one smell for another. Breaking up a god object into twelve classes with interfaces, factories and one implementation each traded a god object for speculative generality. Fix: extract along the cohesion groups the code actually has, and add interfaces only where you need a seam.

DRY across bounded contexts. Two services shared a Customer class "to avoid duplication"; every change to it needed both teams and a lock-step deploy (a distributed monolith in miniature). Fix: duplicate the data shape per context and translate at the boundary.

.Result in a constructor. An ASP.NET Core service loaded settings with GetSettingsAsync().Result in its constructor, registered as scoped. Fine in testing; under load, every request blocked a thread and the pool starved within seconds of a traffic spike. Fix: load once at start-up (IHostedService or await in Program.cs), inject the result.

Smell metrics as targets. A team enforced "no class over 200 lines"; developers split classes at line 199 into OrderManagerPart2. Fix: use metrics to find candidates for review, not as gates. Cohesion and change patterns matter more than size.

Checklist

  • Classes have one reason to change; vague names (Manager, Helper, Utils) are challenged in review.
  • Domain objects protect their invariants; setters aren't public by default.
  • Concepts with rules (money, ids, emails, durations) have their own types.
  • Each business rule lives in one place; type-code switches aren't repeated across files.
  • Dependencies arrive through constructors; no locator calls or mutable statics in business code.
  • Hot data-access paths have query counts checked (log the SQL in development).
  • New abstractions are justified by two or three real cases, not by "later".
  • No bare true/false arguments; no unexplained literals; units are in types.
  • Exceptions for the unexpected; Try/Result/Optional for expected failures; no empty catch.
  • Async code is async all the way; no .Result, .Wait(), readFileSync or time.sleep on request paths.
  • Module dependencies are acyclic and enforced by an architecture test in CI.
  • Services own their data, and a request's synchronous call chain is short.

Self-check

A class has 800 lines, but LCOM4 = 1. Is it a god object?

Probably not. LCOM4 = 1 means every method is connected through shared fields: the class has one cohesive responsibility, it's just big. Look for long methods to extract within the class instead. A 200-line class with LCOM4 = 3 is the stronger smell: three classes in one.

Your tests pass individually and fail when run together. What smell do you suspect, and how do you prove it?

Shared mutable state: a static field, a singleton with mutable properties, a module-level dict, or an environment variable. Run the failing pair in both orders, or with the runner's random-order option, and log the shared value at each step. The fix is to make the state an injected instance per test.

A page lists 200 orders and runs 201 SQL queries. Name the smell and two fixes.

The N+1 query problem, a leaky abstraction from lazy loading. Fix by eager loading in the original query (Include, join fetch, select_related, Prisma include) or by batching the lookups into one WHERE id IN (...) query (selectinload, default_batch_fetch_size, DataLoader).

Five services in a synchronous chain are each 99.9% available. What is the best-case availability of the request?

0.999⁵ ≈ 0.995, so 99.5%: about 3.6 hours of failed requests per 30-day month, versus about 43 minutes for one service. Retries can help with transient errors but add latency; the structural fix is fewer synchronous hops.

You see the same eight-line validation block in two places. Should you extract it now?

Not automatically. Ask whether it's the same rule (same owner, must change together) or two rules that look alike today. If it's the same knowledge, extract it. If unsure, wait for the third case (rule of three); duplication is cheaper than the wrong abstraction.

Why does blocking with .Result hurt an ASP.NET Core app even though there is no synchronization context to deadlock on?

The blocked thread can't do any other work while it waits, and the continuation that would complete the task needs another pool thread. Under a burst, all threads end up blocked waiting for continuations that are queued behind them. The pool adds threads slowly, so throughput collapses and latency grows: thread-pool starvation.
