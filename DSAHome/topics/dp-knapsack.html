DYNAMIC PROGRAMMING

Knapsack Family

0/1 vs unbounded vs bounded knapsack, why loop direction matters, coin change, subset sum and target sum.

Intermediate → Advanced~60 min studyBuilds on: The DP FrameworkUpdated 2026-11-03

Where this page fits

The DP Framework gave you the five-step recipe (state, transition, base cases, order, answer). 1D & Grid DP applied it to positions in a sequence or a grid, and showed how to roll a table into one row. This page adds one new idea: a budget. You have a pile of items, each with a cost, and a limit on the total cost. Which items do you pick?

That one shape covers a surprising number of problems: knapsack itself, coin change, subset sum, partitioning an array into equal halves, assigning + and − signs to reach a target, choosing strings under two budgets, and counting schemes that make a minimum profit. They all use the same table. Only the operator changes (max, min, OR, +), plus one detail that trips up almost everyone: the direction of the inner loop.

Knapsack DP indexes the table by the budget that is still free: dp[c] is the best you can do with the items seen so far and capacity c, and each item either is skipped (dp[c]) or is placed into the last w units (dp[c − w] + v). Everything on this page is that sentence with a different operator, a different loop direction, or a second budget.

The one decision in every cell

Take the classic problem: items with weights wt[i] and values val[i], a bag of capacity W; each item can be taken at most once (that is what "0/1" means). Maximise the total value.

Brute force tries all 2ⁿ subsets. DP notices that the only thing the future needs to know about your earlier choices is how much capacity they used up. Two different subsets of the first i items that leave the same capacity free are interchangeable, and you only need to remember the better one. That gives the state.

1 · STATEdp[i][c]

The best total value using only the first i items, with total weight at most c.

2 · TRANSITIONLast decision: item i in or out?

Skip: dp[i−1][c]. Take (if w ≤ c): dp[i−1][c−w] + v. Keep the larger.

3 · BASE CASESRow 0 is all zeros

With no items, every capacity is worth 0. Capacity 0 is worth 0 in every row.

4 · ORDERRow by row

Row i reads only row i−1, so fill rows top to bottom; any column order works in 2D.

5 · ANSWERdp[n][W]

All items considered, full capacity. Walk back up the table to list the items.

Here is that transition as a picture. Item i weighs 3 and is worth 4. The row above (items 1 … i−1) only knows item 1 (weight 1, value 1).

Watch the whole table fill, then walk it back

Step through the table below. In every cell, the green arrow is the option that won and the blue one lost. When the table is full, the walk back starts at the bottom-right corner. In each row it asks: does this cell equal the one directly above? If yes, the item was skipped (go straight up). If no, only "take" can explain the value, so the item is in the answer (go up and left by its weight).

Why the walk back works. Every cell was produced by exactly one of two arrows. If dp[i][c] == dp[i−1][c], then skipping item i already reaches this value, so some optimal answer does not use it. Otherwise only the take arrow can produce it. Following the producing arrows from (n, W) back to row 0 replays one optimal set of decisions. This only works with the full 2D table: the one-row version below throws away the rows you would need.

Template: 0/1 knapsack with reconstruction

def knapsack_01(wt: list[int], val: list[int], W: int) -> tuple[int, list[int]]:
    n = len(wt)
    dp = [[0] * (W + 1) for _ in range(n + 1)]       # dp[i][c]: first i items, capacity c
    for i in range(1, n + 1):
        w, v = wt[i - 1], val[i - 1]
        for c in range(W + 1):
            dp[i][c] = dp[i - 1][c]                    # skip item i
            if w <= c and dp[i - 1][c - w] + v > dp[i][c]:
                dp[i][c] = dp[i - 1][c - w] + v        # take item i
    chosen, c = [], W
    for i in range(n, 0, -1):                          # walk back from the corner
        if dp[i][c] != dp[i - 1][c]:                   # only "take" explains this cell
            chosen.append(i - 1)
            c -= wt[i - 1]
    return dp[n][W], chosen[::-1]

public static (int Best, List<int> Items) Knapsack01(int[] wt, int[] val, int W)
{
    int n = wt.Length;
    var dp = new int[n + 1, W + 1];                    // dp[i, c]: first i items, capacity c
    for (int i = 1; i <= n; i++)
    {
        int w = wt[i - 1], v = val[i - 1];
        for (int c = 0; c <= W; c++)
        {
            dp[i, c] = dp[i - 1, c];                    // skip item i
            if (w <= c) dp[i, c] = Math.Max(dp[i, c], dp[i - 1, c - w] + v);   // take item i
        }
    }
    var items = new List<int>();
    for (int i = n, c = W; i >= 1; i--)                 // walk back from the corner
        if (dp[i, c] != dp[i - 1, c]) { items.Add(i - 1); c -= wt[i - 1]; }
    items.Reverse();
    return (dp[n, W], items);
}

Time O(n·W), space O(n·W). If you only need the value, the next section cuts the space to O(W).

One row: why the 0/1 loop runs backward

Row i reads only row i−1, so the rolling-array idea from 1D & Grid DP applies: keep one row and overwrite it in place for each item. The danger is the take arrow. It reads dp[c − w], a cell to the left of dp[c]. Whether that cell still holds the old value (row i−1) or already holds the new one (row i) depends entirely on which direction you sweep.

Now step through it with real items. The top row is a frozen copy of the values before the current item, so you can compare. Cells tagged ×2 or ×3 contain the item more than once. Run the default input backward, then switch the loop to forward and run it again: same code, one changed range, and the answer jumps from 8 to 11.

def knapsack_01_1d(wt: list[int], val: list[int], W: int) -> int:
    dp = [0] * (W + 1)                         # dp[c]: best value with capacity c
    for w, v in zip(wt, val):
        for c in range(W, w - 1, -1):          # BACKWARD: dp[c - w] is still the old row
            dp[c] = max(dp[c], dp[c - w] + v)
    return dp[W]

public static int Knapsack01OneRow(int[] wt, int[] val, int W)
{
    var dp = new int[W + 1];                   // dp[c]: best value with capacity c
    for (int k = 0; k < wt.Length; k++)
        for (int c = W; c >= wt[k]; c--)       // BACKWARD: dp[c - w] is still the old row
            dp[c] = Math.Max(dp[c], dp[c - wt[k]] + val[k]);
    return dp[W];
}

Time O(n·W), space O(W). Notice the loop stops at c = w: cells with c < w cannot take the item, so they keep their old value without being touched.

"At most c" or "exactly c"? The initial row decides. With dp = [0] * (W + 1), every capacity starts as "empty bag, value 0", so dp[c] means "best with weight at most c" and the answer is dp[W]. With dp[0] = 0 and every other cell −∞, only sums that are actually built become finite, so dp[c] means "best with weight exactly c". Use the second when the problem says "exactly", for example filling a target sum precisely (worked problem 3).

The knapsack family

The 0/1 rule is one of four ways an item can be used. Each one keeps the same table and changes only how an item is processed.

Unbounded knapsack: flip the loop

If every item comes in unlimited supply, the bug from the previous section becomes the feature. Sweeping forward lets dp[c] read a dp[c − w] that already contains the item, so the item can be stacked again and again. In 2D terms, the take arrow now comes from the same row (dp[i][c − w]) instead of the row above: "take one copy of item i, and you may still take more".

def knapsack_unbounded(wt: list[int], val: list[int], W: int) -> int:
    dp = [0] * (W + 1)
    for w, v in zip(wt, val):
        for c in range(w, W + 1):              # FORWARD: reuse is allowed
            dp[c] = max(dp[c], dp[c - w] + v)
    return dp[W]

public static int KnapsackUnbounded(int[] wt, int[] val, int W)
{
    var dp = new int[W + 1];
    for (int k = 0; k < wt.Length; k++)
        for (int c = wt[k]; c <= W; c++)       // FORWARD: reuse is allowed
            dp[c] = Math.Max(dp[c], dp[c - wt[k]] + val[k]);
    return dp[W];
}

Time O(n·W), space O(W). For max/min problems the two loops of unbounded knapsack can be swapped (capacity outside, items inside) without changing the answer. For counting they cannot, as the coin-change section below shows.

Bounded knapsack: k copies become log k items

Now each item i has a stock cnt[i]. Unrolling it into cnt[i] separate 0/1 items is correct but slow: O(W · Σcnt). The fix is binary splitting. Bundle the copies into pieces of 1, 2, 4, 8, … copies, with whatever is left over as a last piece. Each piece is one ordinary 0/1 item (weight and value multiplied by its size). Every count from 0 to k can be written as a sum of some of the pieces, so the 0/1 choice over pieces can still express "take q copies" for every q.

Why does every count work? The powers 1, 2, …, 2ᵗ⁻¹ reach every number from 0 to 2ᵗ − 1 (that is just binary). The leftover piece r is at most 2ᵗ, so adding it shifts that whole range up by r and the two ranges overlap with no gap, reaching every number up to k.

def knapsack_bounded(wt: list[int], val: list[int], cnt: list[int], W: int) -> int:
    dp = [0] * (W + 1)
    for w, v, k in zip(wt, val, cnt):
        b = 1
        while k > 0:
            take = min(b, k)                   # pieces of 1, 2, 4, ... copies, then the rest
            k -= take
            b *= 2
            pw, pv = take * w, take * v
            for c in range(W, pw - 1, -1):     # each piece is an ordinary 0/1 item
                dp[c] = max(dp[c], dp[c - pw] + pv)
    return dp[W]

public static int KnapsackBounded(int[] wt, int[] val, int[] cnt, int W)
{
    var dp = new int[W + 1];
    for (int i = 0; i < wt.Length; i++)
    {
        for (int b = 1, k = cnt[i]; k > 0; b *= 2)
        {
            int take = Math.Min(b, k);         // pieces of 1, 2, 4, ... copies, then the rest
            k -= take;
            int pw = take * wt[i], pv = take * val[i];
            for (int c = W; c >= pw; c--)      // each piece is an ordinary 0/1 item
                dp[c] = Math.Max(dp[c], dp[c - pw] + pv);
        }
    }
    return dp[W];
}

Time O(W · Σ log cnt[i]), space O(W). There is an even faster O(n·W) method: for a fixed item, the cells c, c − w, c − 2w, … form a chain, and "take up to k copies" is a sliding-window maximum along that chain, which a monotone deque computes in O(1) per cell. It is covered in State Machines & DP Optimisations. For counting the window is just a running sum, which worked problem 7 uses.

Group knapsack: at most one item per group

Sometimes items come in groups and you may take at most one from each group: one face per die, one "how many coins from this pile" option per pile, one element per matrix row. The trick is the loop nesting. Put the group's items inside the backward capacity loop. Then, for a fixed capacity c, every option in the group is compared against the old row, and the cell keeps only the best one, so two items from the same group can never be combined.

def knapsack_groups(groups: list[list[tuple[int, int]]], W: int) -> int:
    dp = [0] * (W + 1)
    for group in groups:                       # group = [(weight, value), ...]
        for c in range(W, -1, -1):             # backward over capacity ...
            for w, v in group:                 # ... options INSIDE: at most one per group
                if w <= c:
                    dp[c] = max(dp[c], dp[c - w] + v)
    return dp[W]

public static int KnapsackGroups(List<(int W, int V)[]> groups, int W)
{
    var dp = new int[W + 1];
    foreach (var group in groups)
        for (int c = W; c >= 0; c--)           // backward over capacity ...
            foreach (var (w, v) in group)      // ... options INSIDE: at most one per group
                if (w <= c) dp[c] = Math.Max(dp[c], dp[c - w] + v);
    return dp[W];
}

Time O(W · total items), space O(W). If you swap the two inner loops (items outside, capacity inside), each option becomes its own 0/1 item and two options from the same group can be taken together, which is a different problem.

Four questions, one table

The table stays the same while the question changes. Only the operator and the starting row change. This is the semiring idea from The DP Framework, applied to knapsack:

Question Cell type Starting row Combine skip and take Example
Best value, weight at most c int all 0 max(dp[c], dp[c−w] + v) 0/1 knapsack
Best value, weight exactly c int dp[0] = 0, rest −∞ max(dp[c], dp[c−w] + v) 1449
Can some subset sum to c? bool dp[0] = True, rest False dp[c] or dp[c−w] 416, subset sum
How many ways to make c? int dp[0] = 1, rest 0 dp[c] + dp[c−w] 494, 518, 377
Fewest items to make c? int dp[0] = 0, rest ∞ min(dp[c], dp[c−w] + 1) 322, 279

dp[0] = 1 for counting is not a hack: there is exactly one way to make 0, the empty selection. Every way to make c is "a way to make c − w, plus this item", so counts flow from that single empty selection.

Coin change: fewest coins

Coin Change (322): given coin denominations (unlimited supply) and an amount, return the fewest coins that sum to it, or −1. It is an unbounded knapsack where each coin has value 1 and you minimise. Think about the last coin: if the last coin is c, the rest is an optimal way to pay a − c. So dp[a] = 1 + min over coins c ≤ a of dp[a − c].

Run the default (coins 1, 3, 4, amount 6). Greedy takes 4 first and then needs 1 + 1, three coins in total. The DP finds 3 + 3, two coins. Greedy only works for special coin systems (like 1, 5, 10, 25); the DP works for every coin system.

def coin_change(coins: list[int], amount: int) -> int:
    INF = amount + 1                           # more coins than could ever be needed
    dp = [0] + [INF] * amount                  # dp[a]: fewest coins summing to a
    for a in range(1, amount + 1):
        for c in coins:                        # which coin is the last one?
            if c <= a and dp[a - c] + 1 < dp[a]:
                dp[a] = dp[a - c] + 1
    return dp[amount] if dp[amount] <= amount else -1

public static int CoinChange(int[] coins, int amount)
{
    int inf = amount + 1;                      // more coins than could ever be needed
    var dp = new int[amount + 1];              // dp[a]: fewest coins summing to a
    Array.Fill(dp, inf);
    dp[0] = 0;
    for (int a = 1; a <= amount; a++)
        foreach (int c in coins)               // which coin is the last one?
            if (c <= a && dp[a - c] + 1 < dp[a]) dp[a] = dp[a - c] + 1;
    return dp[amount] <= amount ? dp[amount] : -1;
}

Time O(amount · coins), space O(amount). Using amount + 1 as "infinity" means dp[a − c] + 1 cannot overflow, which matters in C# where int.MaxValue + 1 silently wraps around to a negative number.

Pitfall: treating "unreachable" as 0 or −1 inside the table. If dp[a] = −1 means unreachable, then dp[a − c] + 1 = 0 looks like the best possible answer and the min picks it. Keep a large sentinel inside the table and translate to −1 only at the very end.

Counting ways: why loop order matters

Coin Change II (518) asks for the number of combinations that make the amount, so 1 + 2 and 2 + 1 are the same way. Combination Sum IV (377), despite its name, asks for the number of ordered sequences, so 1 + 2 and 2 + 1 are different. Both use the same recurrence, ways[a] += ways[a − c]. The only difference is which loop is outside.

The visualizer lists the actual ways in each column, not only the counts. Run it once with coins outside, then switch to amounts outside: the red dashed chips are the same coins in a different order, counted again.

def change(amount: int, coins: list[int]) -> int:
    ways = [1] + [0] * amount                  # ways[0] = 1: the empty selection
    for c in coins:                            # coins OUTER: combinations (518)
        for a in range(c, amount + 1):
            ways[a] += ways[a - c]
    return ways[amount]


def combination_sum4(nums: list[int], target: int) -> int:
    ways = [1] + [0] * target
    for a in range(1, target + 1):             # amounts OUTER: ordered sequences (377)
        for x in nums:
            if x <= a:
                ways[a] += ways[a - x]
    return ways[target]

public static int Change(int amount, int[] coins)
{
    var ways = new int[amount + 1];
    ways[0] = 1;                               // the empty selection
    foreach (int c in coins)                   // coins OUTER: combinations (518)
        for (int a = c; a <= amount; a++)
            ways[a] += ways[a - c];
    return ways[amount];
}

public static int CombinationSum4(int[] nums, int target)
{
    var ways = new long[target + 1];           // intermediate counts may pass 2^31
    ways[0] = 1;
    for (int a = 1; a <= target; a++)          // amounts OUTER: ordered sequences (377)
        foreach (int x in nums)
            if (x <= a) ways[a] = unchecked(ways[a] + ways[a - x]);
    return (int)ways[target];
}

Both are O(amount · coins) time and O(amount) space. In 377 some intermediate ways[a] can overflow even though the final answer fits in 32 bits. Python does not care. In C#, wrap-around arithmetic is exact modulo 2⁶⁴, so the final value is still right after the cast.

The 2D picture explains the loop order. "Coins outer" is the rolled form of the table ways[i][a] = ways using only the first i coin types. That table can only build multisets in coin order. "Amounts outer" has no coin dimension at all: its state is just the amount, and the last coin can be anything. A state with no "which items have I used" information cannot avoid counting orders separately.

Subset sum: true or false, and the bitset trick

Partition Equal Subset Sum (416): can the array be split into two parts with equal sums? Both parts must sum to S/2, so the question becomes "does some subset sum to S/2?" (if S is odd, the answer is immediately no). That is 0/1 knapsack with booleans: ok[c] = ok[c] or ok[c − x], backward.

def can_partition(nums: list[int]) -> bool:
    S = sum(nums)
    if S % 2:
        return False
    half = S // 2
    ok = [True] + [False] * half               # ok[c]: some subset sums to c
    for x in nums:
        for c in range(half, x - 1, -1):       # 0/1: backward
            ok[c] = ok[c] or ok[c - x]
    return ok[half]

public static bool CanPartition(int[] nums)
{
    int S = nums.Sum();
    if (S % 2 != 0) return false;
    int half = S / 2;
    var ok = new bool[half + 1];               // ok[c]: some subset sums to c
    ok[0] = true;
    foreach (int x in nums)
        for (int c = half; c >= x; c--)        // 0/1: backward
            ok[c] |= ok[c - x];
    return ok[half];
}

Time O(n · S), space O(S).

Look at what one item does to the boolean row: every true cell s makes cell s + x true. That is a shift. If the whole row is stored as the bits of one integer, the inner loop collapses to bits |= bits << x. A CPU shifts and ORs 64 bits per instruction, so this runs about 64 times faster, and in Python it is also far shorter, because Python integers have unlimited size.

The same row answers three different questions. Switch the "question" selector: subset sum checks bit target, partition checks bit S/2, and Last Stone Weight II (worked problem 1) looks for the highest set bit at or below S/2.

def can_partition_bits(nums: list[int]) -> bool:
    S = sum(nums)
    if S % 2:
        return False
    bits = 1                                   # bit s set <=> some subset sums to s
    for x in nums:
        bits |= bits << x                      # old sums, plus every old sum + x
    return (bits >> (S // 2)) & 1 == 1

// using System.Collections;
public static bool CanPartitionBits(int[] nums)
{
    int S = nums.Sum();
    if (S % 2 != 0) return false;
    var bits = new BitArray(S / 2 + 1);        // bit s set <=> some subset sums to s
    bits[0] = true;
    foreach (int x in nums)
    {
        var shifted = new BitArray(bits);      // copy, then move bit s to bit s + x
        shifted.LeftShift(x);                  // bits past the end fall off
        bits.Or(shifted);
    }
    return bits[S / 2];
}

Time O(n · S / 64), space O(S / 64) machine words. BitArray.LeftShift moves bits towards higher indices, which is what "every sum + x" needs. In C++ you would use std::bitset<N> the same way.

Target Sum: turn signs into a subset

Target Sum (494): put + or − in front of every number so the total equals target. Count the ways. With 2ⁿ sign patterns this looks like backtracking, but one line of algebra turns it into subset counting.

Two quick exits come out of the algebra: if |T| > S no pattern reaches it, and if S + T is odd then P is not a whole number. Zeros are a nice check of your understanding: a 0 can be +0 or −0, so it doubles the count. The DP gets that right automatically, because ways[c] += ways[c − 0] doubles every cell.

def find_target_sum_ways(nums: list[int], target: int) -> int:
    S = sum(nums)
    if abs(target) > S or (S + target) % 2:
        return 0
    P = (S + target) // 2                      # sum of the numbers that get '+'
    ways = [1] + [0] * P                       # ways[c]: subsets summing to c
    for x in nums:
        for c in range(P, x - 1, -1):          # 0/1 counting: backward
            ways[c] += ways[c - x]
    return ways[P]

public static int FindTargetSumWays(int[] nums, int target)
{
    int S = nums.Sum();
    if (Math.Abs(target) > S || (S + target) % 2 != 0) return 0;
    int P = (S + target) / 2;                  // sum of the numbers that get '+'
    var ways = new int[P + 1];                 // ways[c]: subsets summing to c
    ways[0] = 1;
    foreach (int x in nums)
        for (int c = P; c >= x; c--)           // 0/1 counting: backward
            ways[c] += ways[c - x];
    return ways[P];
}

Time O(n · P), space O(P). You can also use the smaller of the two groups, N = (S − T) / 2, as the target. It gives the same count with a shorter row when T is positive.

The ± transform shows up everywhere. "Split into two groups and minimise the difference" (1049, 2035), "assign signs to hit a target" (494), "two teams with equal strength" (416). In every case, choose one group and treat the other as "everything else". The question becomes a subset sum, with a target derived from S.

Two budgets: Ones and Zeroes

Ones and Zeroes (474): pick as many binary strings as possible using at most m zeros and n ones in total. Each string has two weights. The state must remember both remaining budgets, so the "row" becomes a 2D grid indexed by (zeros, ones). Everything else is still 0/1 knapsack: value 1 per string, and both budget loops run backward so every read sees the grid from before the current string.

The arrow always points from (i − z, j − o), up and to the left. Because both loops run from high to low, that source cell has not been touched yet for this string. The full solution is worked problem 2.

When the table is too big: pseudo-polynomial time

O(n·W) looks polynomial, but W is a number in the input, not the size of the input. Writing W = 10⁹ takes ten digits, yet the table needs a billion columns. Each extra digit in W multiplies the work by 10. Algorithms like this are called pseudo-polynomial: fast when the numbers are small, hopeless when they are large. (Knapsack is NP-hard, so no truly polynomial algorithm is known.) Before writing a knapsack DP, check the sizes, then pick the right tool:

DP over value instead of weight

Swap the roles. Let minW[v] be the lightest subset whose value is exactly v. That is a 0/1 "fewest/min" knapsack with the value as the budget. The answer is the largest v with minW[v] ≤ W. Use it when the weights are huge but the values are small.

def knapsack_by_value(wt: list[int], val: list[int], W: int) -> int:
    V = sum(val)
    INF = float("inf")
    min_w = [0] + [INF] * V                    # min_w[v]: lightest subset with value exactly v
    for w, v in zip(wt, val):
        for t in range(V, v - 1, -1):          # 0/1: backward over the value budget
            min_w[t] = min(min_w[t], min_w[t - v] + w)
    return max(t for t in range(V + 1) if min_w[t] <= W)

public static int KnapsackByValue(int[] wt, int[] val, long W)
{
    int V = val.Sum();
    var minW = new long[V + 1];                // minW[v]: lightest subset with value exactly v
    Array.Fill(minW, long.MaxValue / 2);
    minW[0] = 0;
    for (int k = 0; k < wt.Length; k++)
        for (int t = V; t >= val[k]; t--)      // 0/1: backward over the value budget
            minW[t] = Math.Min(minW[t], minW[t - val[k]] + wt[k]);
    for (int t = V; ; t--)
        if (minW[t] <= W) return t;            // minW[0] = 0 guarantees a stop
}

Time O(n · Σv), space O(Σv). This is also the basis of the classic approximation scheme: round the values down to a coarser scale, then run this exact DP on the smaller numbers.

Meet in the middle

With n = 40 items, 2⁴⁰ ≈ 10¹² subsets is too many, but 2 × 2²⁰ ≈ 2 million is easy. Split the items into two halves, list every subset sum of each half, and sort. A subset of all the items is just a left-half subset plus a right-half subset, so "best sum ≤ W" becomes "best pair A[i] + B[j] ≤ W". Two sorted lists can be merged with two pointers: as A[i] grows, the best partner B[j] can only shrink.

def best_sum_at_most(nums: list[int], W: int) -> int:
    def subset_sums(arr: list[int]) -> list[int]:
        sums = [0]
        for x in arr:
            sums += [s + x for s in sums]      # every old subset, without and with x
        return sums

    h = len(nums) // 2
    A = sorted(subset_sums(nums[:h]))
    B = sorted(subset_sums(nums[h:]))
    i, j, best = 0, len(B) - 1, 0
    while i < len(A) and j >= 0:
        if A[i] + B[j] <= W:
            best = max(best, A[i] + B[j])      # fits: try a bigger A[i]
            i += 1
        else:
            j -= 1                             # too big for this and every later A[i]
    return best

public static long BestSumAtMost(long[] nums, long W)
{
    static List<long> SubsetSums(IEnumerable<long> arr)
    {
        var sums = new List<long> { 0 };
        foreach (long x in arr)
        {
            int count = sums.Count;
            for (int k = 0; k < count; k++) sums.Add(sums[k] + x);   // without and with x
        }
        sums.Sort();
        return sums;
    }
    int h = nums.Length / 2;
    var A = SubsetSums(nums.Take(h));
    var B = SubsetSums(nums.Skip(h));
    long best = 0;
    for (int i = 0, j = B.Count - 1; i < A.Count && j >= 0; )
    {
        if (A[i] + B[j] <= W) { best = Math.Max(best, A[i] + B[j]); i++; }   // fits: try a bigger A[i]
        else j--;                                                          // too big for every later A[i]
    }
    return best;
}

Time O(2^(n/2) · n) for generating and sorting, space O(2^(n/2)). Assumes non-negative numbers and W ≥ 0, so the empty subset (sum 0) is always a valid fallback. For "closest to a goal" instead of "at most W", check the pair on both sides of the crossing point, as in worked problem 6.

Recognize it, cost it, avoid the traps

Recognize a knapsack when:

  • you choose a subset (or a multiset) of items, and a sum of some attribute must stay under, or exactly hit, a number that is small (up to about 10⁴–10⁵);
  • the problem says "partition into two groups", "assign + or −", "make the amount", "reach exactly", "at most m of this and n of that";
  • the order of the chosen items does not matter (if it does, as in 377, the state is the amount alone and the "items" loop goes inside);
  • brute force is 2ⁿ, but the number of distinct sums is small. That gap is what the table exploits.

Pitfall: a forward loop in a 0/1 problem. for c in range(x, half + 1) in Partition Equal Subset Sum lets each number be reused, so [1, 5] (S = 6, half = 3) wrongly returns true: 1 + 1 + 1 = 3. Fix: 0/1 means range(half, x − 1, −1). Say "once → backward" out loud every time you write the loop.

Pitfall: "exactly" with a row of zeros. If the problem needs the total to equal the target exactly (1449, "fill the bag completely"), starting with dp = [0] * (W + 1) silently allows leftover capacity, because every cell already counts as reachable. Fix: start with dp[0] = 0 and every other cell −∞ (or +∞ for minimisation), and treat unreachable cells as impossible.

Pitfall: swapping the loops of a counting DP. Max/min knapsack gives the same answer with either loop order. Counting does not: amounts outer counts sequences (377), coins outer counts multisets (518). Fix: decide first whether 1 + 2 and 2 + 1 are the same answer.

Pitfall: reconstructing from the one-row table. After compression, the information about which rows changed is gone, so you cannot walk back. Fix: keep the 2D table, or keep the one-row DP plus a boolean table took[i][c] (n·W bits) recording whether the take arrow won, then walk back with it.

Pitfall: Target Sum edge cases. Negative targets, odd S + T, and |T| > S all have to return 0 before you compute P, otherwise you index a negative or fractional cell. Fix: the two guard checks in the template, in that order.

Worked problems

1. Last Stone Weight II: smashing is just signs

LeetCode 1049 Medium. Repeatedly smash two stones x ≤ y: both vanish if equal, otherwise one stone of weight y − x remains. Return the smallest possible final weight (or 0).

Key insight. Every smash subtracts one stone from another, so the final stone is a signed sum of all the original weights: some get +, some get −. Conversely, any split into two teams can be produced by a suitable smashing order. So the answer is the smallest |team A − team B| = S − 2·A with A ≤ S/2. That is subset sum: find the largest reachable sum at or below S/2. Try "last stone weight II" in the bitset visualizer above with 2,7,4,1,8,1 to see A = 11 and the answer 1.

Solution: subset sum up to S/2, O(n·S) 
def last_stone_weight_ii(stones: list[int]) -> int:
    S = sum(stones)
    bits = 1                                   # bit a set <=> some team can weigh a
    for x in stones:
        bits |= bits << x
    for a in range(S // 2, -1, -1):            # heaviest team that is at most S/2
        if bits >> a & 1:
            return S - 2 * a
    return S

public static int LastStoneWeightII(int[] stones)
{
    int S = stones.Sum(), half = S / 2;
    var ok = new bool[half + 1];               // ok[a]: some team can weigh a
    ok[0] = true;
    foreach (int x in stones)
        for (int c = half; c >= x; c--) ok[c] |= ok[c - x];
    for (int a = half; ; a--)                  // heaviest team that is at most S/2
        if (ok[a]) return S - 2 * a;
}

Time O(n·S) (divided by 64 for the bitset), space O(S).

2. Ones and Zeroes: two budgets at once

LeetCode 474 Medium. Choose the largest subset of binary strings whose total count of 0s is at most m and of 1s at most n.

Key insight. Each string is an item with two weights (its zeros and its ones) and value 1. The capacity becomes a pair, so the one-row DP becomes a one-grid DP dp[i][j]. Both loops run backward so the cell (i − z, j − o) still holds the grid from before this string (see the Ones and Zeroes visualizer above).

Solution: 0/1 knapsack over a 2D budget, O(L·m·n) 
def find_max_form(strs: list[str], m: int, n: int) -> int:
    dp = [[0] * (n + 1) for _ in range(m + 1)]  # dp[i][j]: most strings within i zeros, j ones
    for s in strs:
        z = s.count("0")
        o = len(s) - z
        for i in range(m, z - 1, -1):           # both budgets backward: each string once
            for j in range(n, o - 1, -1):
                dp[i][j] = max(dp[i][j], dp[i - z][j - o] + 1)
    return dp[m][n]

public static int FindMaxForm(string[] strs, int m, int n)
{
    var dp = new int[m + 1, n + 1];             // dp[i, j]: most strings within i zeros, j ones
    foreach (string s in strs)
    {
        int z = s.Count(ch => ch == '0'), o = s.Length - z;
        for (int i = m; i >= z; i--)            // both budgets backward: each string once
            for (int j = n; j >= o; j--)
                dp[i, j] = Math.Max(dp[i, j], dp[i - z, j - o] + 1);
    }
    return dp[m, n];
}

Time O(L·m·n) for L strings (plus the time to count characters), space O(m·n).

3. Form Largest Integer With Digits That Add up to Target: exact fill, then greedy rebuild

LeetCode 1449 Hard. Painting digit d costs cost[d − 1]. Return the largest number (as a string) whose total cost is exactly target, or "0".

Key insight. Two separate questions. First: a number with more digits is always larger, so maximise the digit count. That is unbounded knapsack with value 1 per digit and an exact fill, so start from −∞ everywhere except dp[0] = 0. Second: among numbers with the most digits, the biggest has the largest possible first digit, then the largest possible second digit, and so on. Rebuild from the left. Try digits 9 down to 1, and accept digit d if dp[t − cost[d]] == dp[t] − 1, which means the rest can still be completed with exactly the right number of digits. The DP table is what makes the greedy rebuild safe.

Solution: unbounded exact-fill DP plus a greedy walk, O(9·target) 
def largest_number(cost: list[int], target: int) -> str:
    NEG = float("-inf")
    dp = [0] + [NEG] * target                  # dp[t]: most digits with cost EXACTLY t
    for t in range(1, target + 1):
        for c in cost:
            if c <= t and dp[t - c] + 1 > dp[t]:
                dp[t] = dp[t - c] + 1
    if dp[target] < 0:
        return "0"
    out, t = [], target
    while t > 0:                               # biggest digit that keeps an optimal finish
        for d in range(9, 0, -1):
            c = cost[d - 1]
            if c <= t and dp[t - c] == dp[t] - 1:
                out.append(str(d))
                t -= c
                break
    return "".join(out)

public static string LargestNumber(int[] cost, int target)
{
    const int NEG = int.MinValue / 2;
    var dp = new int[target + 1];              // dp[t]: most digits with cost EXACTLY t
    Array.Fill(dp, NEG);
    dp[0] = 0;
    for (int t = 1; t <= target; t++)
        foreach (int c in cost)
            if (c <= t && dp[t - c] + 1 > dp[t]) dp[t] = dp[t - c] + 1;
    if (dp[target] < 0) return "0";
    var sb = new System.Text.StringBuilder();
    for (int t = target; t > 0; )               // biggest digit that keeps an optimal finish
        for (int d = 9; d >= 1; d--)
        {
            int c = cost[d - 1];
            if (c <= t && dp[t - c] == dp[t] - 1) { sb.Append((char)('0' + d)); t -= c; break; }
        }
    return sb.ToString();
}

Time O(9·target) for both the DP and the rebuild, space O(target). The NEG sentinel is int.MinValue / 2, so NEG + 1 cannot overflow.

4. Profitable Schemes: clamp the dimension you only need a threshold of

LeetCode 879 Hard. Crime i needs group[i] members and earns profit[i]. With n members in total, count the subsets of crimes that earn at least minProfit (modulo 10⁹ + 7).

Key insight. Two budgets again: members (a real capacity) and profit (a threshold). Profit can sum to 10,000, but the problem only cares whether it reaches minProfit. So store "profit at least p" for p = 0 … minProfit. A scheme that needs profit ≥ p after a crime that earns gain needs only profit ≥ max(0, p − gain) before it. Everything above minProfit collapses into one column.

Solution: 0/1 counting over (members, clamped profit), O(crimes · n · minProfit) 
def profitable_schemes(n: int, min_profit: int, group: list[int], profit: list[int]) -> int:
    MOD = 10**9 + 7
    # dp[g][p]: schemes using at most g members whose profit is at least p
    dp = [[0] * (min_profit + 1) for _ in range(n + 1)]
    for g in range(n + 1):
        dp[g][0] = 1                           # the empty scheme: profit 0 >= 0
    for need, gain in zip(group, profit):
        for g in range(n, need - 1, -1):       # 0/1 over members: backward
            for p in range(min_profit + 1):
                dp[g][p] = (dp[g][p] + dp[g - need][max(0, p - gain)]) % MOD
    return dp[n][min_profit]

public static int ProfitableSchemes(int n, int minProfit, int[] group, int[] profit)
{
    const int MOD = 1_000_000_007;
    var dp = new int[n + 1, minProfit + 1];    // dp[g, p]: at most g members, profit at least p
    for (int g = 0; g <= n; g++) dp[g, 0] = 1; // the empty scheme
    for (int k = 0; k < group.Length; k++)
    {
        int need = group[k], gain = profit[k];
        for (int g = n; g >= need; g--)        // 0/1 over members: backward
            for (int p = 0; p <= minProfit; p++)
                dp[g, p] = (dp[g, p] + dp[g - need, Math.Max(0, p - gain)]) % MOD;
    }
    return dp[n, minProfit];
}

Time O(crimes · n · minProfit), space O(n · minProfit). The profit loop can go in either direction, because it reads row g − need, a different row that has not been updated for this crime yet (every crime needs at least one member).

5. Tallest Billboard: make the difference the state

LeetCode 956 Hard. Weld rods into two supports of equal height (unused rods are allowed). Return the largest possible height, or 0.

Key insight. Each rod has three choices: left, right, or unused. Tracking both heights is O(S²) states. But equal heights only care about the difference. Let dp[d] be the tallest possible shorter side when taller − shorter = d. A rod r either goes on the taller side (d grows by r), or on the shorter side (d shrinks by r, or flips to r − d if the shorter side overtakes the taller). The answer is dp[0]. This "track the difference, store the best of one side" idea works for any "two groups must balance" problem.

Solution: DP keyed by the height difference, O(n·S) 
def tallest_billboard(rods: list[int]) -> int:
    S = sum(rods)
    dp = [-1] * (S + 1)                        # dp[d]: tallest shorter side when the gap is d
    dp[0] = 0
    for r in rods:
        cur = dp[:]                            # option 1: rod unused (and read only the old row)
        for d in range(S + 1):
            s = dp[d]
            if s < 0:
                continue
            if d + r <= S:                     # option 2: rod on the taller side
                cur[d + r] = max(cur[d + r], s)
            if r <= d:                         # option 3a: shorter side grows, still shorter
                cur[d - r] = max(cur[d - r], s + r)
            else:                              # option 3b: shorter side overtakes
                cur[r - d] = max(cur[r - d], s + d)
        dp = cur
    return dp[0]

public static int TallestBillboard(int[] rods)
{
    int S = rods.Sum();
    var dp = new int[S + 1];                   // dp[d]: tallest shorter side when the gap is d
    Array.Fill(dp, -1);
    dp[0] = 0;
    foreach (int r in rods)
    {
        var cur = (int[])dp.Clone();           // option 1: rod unused
        for (int d = 0; d <= S; d++)
        {
            int s = dp[d];
            if (s < 0) continue;
            if (d + r <= S) cur[d + r] = Math.Max(cur[d + r], s);         // taller side
            if (r <= d) cur[d - r] = Math.Max(cur[d - r], s + r);         // shorter, still shorter
            else cur[r - d] = Math.Max(cur[r - d], s + d);                // shorter overtakes
        }
        dp = cur;
    }
    return dp[0];
}

Time O(n·S), space O(S). Copying the row is the simplest way to get 0/1 behaviour when a transition can move both left and right, so neither loop direction is safe.

6. Partition Array Into Two Arrays to Minimize Sum Difference: meet in the middle with a size

LeetCode 2035 Hard. Split 2n numbers (n ≤ 15, values up to ±10⁷) into two arrays of n each, minimising the absolute difference of their sums.

Key insight. Values up to 10⁷, and negative, rule out a sum-indexed table. But n ≤ 15 means each half has only 2¹⁵ subsets. The chosen array takes k numbers from the left half and n − k from the right half, so group the subset sums of each half by size. For each k and each left sum a, the best partner b from the right half (size n − k) is the one that makes 2(a + b) closest to S. Sort each size group and binary search for it.

Solution: subset sums grouped by size, sorted, binary searched, O(2ⁿ · n) 
from bisect import bisect_left

def minimum_difference(nums: list[int]) -> int:
    n = len(nums) // 2
    S = sum(nums)

    def sums_by_size(half: list[int]) -> list[list[int]]:
        by = [[] for _ in range(n + 1)]
        for mask in range(1 << n):
            s = cnt = 0
            for i in range(n):
                if mask >> i & 1:
                    s += half[i]
                    cnt += 1
            by[cnt].append(s)
        return by

    left, right = sums_by_size(nums[:n]), sums_by_size(nums[n:])
    for group in right:
        group.sort()
    best = float("inf")
    for k in range(n + 1):
        B = right[n - k]                       # k from the left, n - k from the right
        for a in left[k]:
            i = bisect_left(B, (S - 2 * a) / 2)    # b closest to (S - 2a) / 2
            for j in (i - 1, i):
                if 0 <= j < len(B):
                    best = min(best, abs(S - 2 * (a + B[j])))
    return best

// using System.Numerics;
public static int MinimumDifference(int[] nums)
{
    int n = nums.Length / 2;
    long S = nums.Sum(x => (long)x);
    List<long>[] SumsBySize(int offset)
    {
        var by = new List<long>[n + 1];
        for (int k = 0; k <= n; k++) by[k] = new List<long>();
        for (int mask = 0; mask < 1 << n; mask++)
        {
            long s = 0;
            for (int i = 0; i < n; i++) if ((mask >> i & 1) == 1) s += nums[offset + i];
            by[BitOperations.PopCount((uint)mask)].Add(s);
        }
        return by;
    }
    var left = SumsBySize(0);
    var right = SumsBySize(n);
    foreach (var g in right) g.Sort();
    long best = long.MaxValue;
    for (int k = 0; k <= n; k++)
    {
        var B = right[n - k];                  // k from the left, n - k from the right
        foreach (long a in left[k])
        {
            long want = S - 2 * a;             // make 2b as close to this as possible
            int lo = 0, hi = B.Count;          // first index with 2 * B[i] >= want
            while (lo < hi) { int mid = (lo + hi) / 2; if (2 * B[mid] < want) lo = mid + 1; else hi = mid; }
            if (lo < B.Count) best = Math.Min(best, Math.Abs(want - 2 * B[lo]));
            if (lo > 0) best = Math.Min(best, Math.Abs(want - 2 * B[lo - 1]));
        }
    }
    return (int)best;
}

Time O(2ⁿ · n) to enumerate and sort the 2 × 2ⁿ sums (n is the half size, at most 15), plus O(2ⁿ · n) for the binary searches. Space O(2ⁿ). Comparing 2·B[i] with S − 2a keeps everything in integers.

7. Count of Sub-Multisets With Bounded Sum: bounded counting with a sliding window

LeetCode 2902 Expert. Count the sub-multisets of nums (sum of nums ≤ 2·10⁴) whose sum lies in [l, r], modulo 10⁹ + 7. Equal values are indistinguishable.

Key insight. Group equal values: value v appears k times, so it is a bounded item, "take 0 … k copies". The new count is new[s] = dp[s] + dp[s − v] + … + dp[s − k·v], which is k + 1 terms. Neighbouring cells on the same chain (s and s − v) share k of those terms, so new[s] = new[s − v] + dp[s] − dp[s − (k + 1)·v]: a sliding window sum, O(1) per cell. Zeros never change the sum, so they just multiply the answer by (zeros + 1). Values with sum ≤ 2·10⁴ have at most about 200 distinct values, so the total work is about 4·10⁶.

Solution: group equal values, sliding-window bounded knapsack, O(S · distinct values) 
from collections import Counter

def count_sub_multisets(nums: list[int], l: int, r: int) -> int:
    MOD = 10**9 + 7
    cnt = Counter(nums)
    zeros = cnt.pop(0, 0)
    S = sum(nums)
    dp = [1] + [0] * S                         # dp[s]: sub-multisets so far with sum s
    for v, k in cnt.items():                   # value v, available k times
        new = dp[:]                            # cells s < v: only "0 copies" fits
        for s in range(v, S + 1):
            new[s] = (dp[s] + new[s - v]) % MOD                # window gains dp[s]
            if s >= (k + 1) * v:
                new[s] = (new[s] - dp[s - (k + 1) * v]) % MOD  # and loses k+1 copies back
        dp = new
    return (zeros + 1) * sum(dp[l:r + 1]) % MOD

public static int CountSubMultisets(IList<int> nums, int l, int r)
{
    const int MOD = 1_000_000_007;
    var cnt = new Dictionary<int, int>();
    foreach (int x in nums) cnt[x] = cnt.GetValueOrDefault(x) + 1;
    int zeros = cnt.GetValueOrDefault(0);
    cnt.Remove(0);
    int S = nums.Sum();
    var dp = new long[S + 1];                  // dp[s]: sub-multisets so far with sum s
    dp[0] = 1;
    foreach (var (v, k) in cnt)                // value v, available k times
    {
        var nw = (long[])dp.Clone();           // cells s < v: only "0 copies" fits
        for (int s = v; s <= S; s++)
        {
            nw[s] = (dp[s] + nw[s - v]) % MOD;                         // window gains dp[s]
            if (s >= (long)(k + 1) * v)
                nw[s] = (nw[s] - dp[s - (k + 1) * v] + MOD) % MOD;     // and loses k+1 copies back
        }
        dp = nw;
    }
    long total = 0;
    for (int s = l; s <= Math.Min(r, S); s++) total = (total + dp[s]) % MOD;
    return (int)(total * (zeros + 1) % MOD);
}

Time O(S · d) where d ≤ about √(2S) is the number of distinct values, space O(S). The C# version adds MOD before taking %, because % in C# keeps the sign of a negative left side.

Check yourself

In the 2D 0/1 table the column order inside a row does not matter. Why does it suddenly matter with one row?

In 2D, row i reads only row i−1, which is already complete, so any order works. With one row, "row i−1" and "row i" live in the same array. The take arrow reads dp[c − w], to the left. Going right to left, that cell has not been overwritten yet, so it is still row i−1 (item used once). Going left to right, it may already be row i (item used again).

You run Coin Change II with the amount loop outside and coins 1, 2 for amount 3. What do you get, and what did you actually count?

3 instead of 2. With amounts outer, ways[a] sums over every possible last coin, so 1 + 2 and 2 + 1 are both counted: you counted ordered sequences (Combination Sum IV). Coins outer forces each multiset to be built in sorted order, so it is counted once.

Target Sum with nums = [0, 0, 1] and target = 1. What is the answer, and how does the DP get it?

4: the 1 must be +, and each 0 can be +0 or −0, so 2 × 2 = 4. S = 1, P = (1 + 1) / 2 = 1. For each 0 the update ways[c] += ways[c − 0] doubles every cell, giving ways[0] = 4 after the zeros, and then the 1 moves those 4 ways to ways[1].

A problem has n = 100 items and W = 10⁹. Is O(n·W) fine "because it is polynomial"?

No. That is 10¹¹ cell updates. O(n·W) is pseudo-polynomial: polynomial in the value of W, but exponential in the number of digits needed to write W. Look for a small quantity to index by instead: small values (DP over value), small n (meet in the middle), or extra structure (greedy, a special coin system).

In group knapsack you put the items loop outside the capacity loop. What changes?

Each item becomes its own 0/1 item, so the DP may take several items from the same group. Keeping the items loop inside the backward capacity loop means that for each capacity, every option in the group is compared against the row from before the group, and only the best option is kept.

Why is dp[i][c] != dp[i−1][c] enough to conclude that item i was taken, even when there are ties?

The cell was computed as max(skip, take) with skip = dp[i−1][c]. If the cell differs from skip, take must have produced it, so taking item i is part of an optimal solution. If they are equal, skipping is optimal (take may tie, but skip is a valid choice). Either way you follow a branch that really achieves the value, so the walk back always rebuilds a correct, optimal set.

Profitable Schemes: why is it safe to merge every profit ≥ minProfit into one column?

The question only asks whether profit reaches minProfit, and profit never decreases when you add crimes. A scheme with profit 7 and one with profit 9 behave identically for every future decision when minProfit = 5, so they belong in the same state. Merging them makes the table independent of the total profit.
