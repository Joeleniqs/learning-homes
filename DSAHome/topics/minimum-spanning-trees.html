Minimum Spanning Trees

Kruskal with union-find and Prim with a heap, the cut property made visual, and MST-in-disguise problems.

Intermediate → Advanced~40 min studyBuilds on: Union-Find (Disjoint Set Union), Heaps & Priority QueuesUpdated 2026-11-03

Why minimum spanning trees exist

You have n cities and a list of roads you could build, each with a price. Every city must be reachable from every other, and you want to spend as little as possible. You don't care how long any particular trip is; you only care about the total cost of what you build. Replace roads with cables, pipes, wires or friendships, and this is the minimum spanning tree (MST) problem.

The answer is always a tree. If the roads you build contain a cycle, you can delete the most expensive road on it and every city is still connected, more cheaply. So the cheapest connected network never has a cycle, and a connected graph with no cycle on n nodes is a tree with exactly n − 1 edges.

This page builds on two earlier ones. Union-Find gives Kruskal its "would this edge close a cycle?" test in near-constant time, and Heaps & Priority Queues gives Prim its frontier. If either feels shaky, skim it first; here they are used, not re-taught.

The MST rule (the cut property). Split the nodes into any two groups. The lightest edge crossing between the groups is safe: some minimum spanning tree contains it. Every MST algorithm is this rule applied over and over to a cleverly chosen split. Kruskal scans all edges from lightest to heaviest and keeps an edge exactly when it joins two different components (union-find). Prim grows one tree and always adds the cheapest edge leaving it (a heap). Both are greedy, both never undo a choice, and both give the same total weight.

What MSTs are not: an MST does not give shortest paths. The tree path between two cities can be much longer than the direct route between them, because the MST optimises the sum of all edges built, not any individual trip. If the question is "fastest way from A to B", go to Shortest Paths. If it is "cheapest way to connect everything", or "the best possible worst edge on a route", you are in the right place.

Why greedy works: cuts and cycles

Greedy algorithms are usually wrong. MST is the famous case where greed is provably right, and the proof is one picture. Understanding it is what lets you trust Kruskal and Prim, and it is also what lets you solve the hard problems at the end of this page, which all come down to "which swaps keep the tree minimal?".

Step through the exchange argument

Pick a side S (any set of nodes), and the visualizer walks through the proof on a real graph: it lists the crossing edges, takes the lightest one e, builds a spanning tree T that avoids e, finds the cycle that e closes in T, picks the other crossing edge f on that cycle, and swaps. Try different sides; the argument never fails.

Three things are worth noticing as you play:

  1. The cut can be anything. Two nodes, half the graph, one lonely node. The lightest crossing edge is always safe. Algorithms differ only in which cuts they choose.
  2. "Some MST", not "the MST". If two crossing edges tie for lightest, either one is safe, and they lead to different (equally cheap) trees. If all weights are distinct the MST is unique.
  3. The proof is constructive. "Swap f out, put e in" is a real operation on trees, and it reappears later: critical edges, second-best MSTs and MST updates are all built from it.

The cycle property: what to throw away

The mirror image of the cut property tells you which edges are never needed.

So the MST can be built in two opposite ways: keep adding the safe (lightest crossing) edges, or keep deleting the heaviest edge of some cycle. Kruskal does both at once: an edge that joins two components is the lightest edge across the cut around one of them, and an edge whose ends are already connected is the heaviest edge on the cycle it would close.

A few consequences that come up constantly:

  • Distinct weights ⇒ unique MST. Ties are the only reason two MSTs can differ, and even then all MSTs have the same total and the same sorted list of edge weights.
  • Only the order of weights matters. Adding a constant to every edge, multiplying by a positive number, squaring non-negative weights, or applying any increasing function leaves the MST unchanged. That is why a "minimise the product" problem with weights > 0 is an MST on log w, and why negative weights are perfectly fine (unlike Dijkstra).
  • The MST minimises the maximum edge too. Among all spanning trees, the MST also has the smallest possible largest edge, and the MST path between two nodes is a path whose largest edge is as small as possible. That is the bottleneck trick later on.

Kruskal: sorted edges plus union-find

Kruskal's algorithm is three lines of idea:

  1. Sort all edges by weight, lightest first.
  2. Walk down the list. For each edge u–v, ask the union-find whether u and v are already connected.
  3. If not, take the edge (union u and v). If they are, skip it: it would close a cycle, and it is the heaviest edge on that cycle. Stop once you have n − 1 edges.

Why is a taken edge safe? When Kruskal takes u–v, look at the cut "u's current component versus everything else". Every lighter edge crossing that cut was seen earlier, and it was skipped only if its ends were already connected, which means it does not cross this cut at all. So u–v is the lightest crossing edge, and the cut property says it is safe.

The template

class DSU:
    def __init__(self, n):
        self.parent = list(range(n))
        self.size = [1] * n
        self.count = n                           # number of components

    def find(self, x):
        root = x
        while self.parent[root] != root:
            root = self.parent[root]
        while self.parent[x] != root:            # path compression
            self.parent[x], x = root, self.parent[x]
        return root

    def union(self, a, b):
        ra, rb = self.find(a), self.find(b)
        if ra == rb:
            return False                         # already connected: a cycle
        if self.size[ra] < self.size[rb]:
            ra, rb = rb, ra
        self.parent[rb] = ra                     # small tree under big tree
        self.size[ra] += self.size[rb]
        self.count -= 1
        return True


def kruskal(n, edges):
    """edges: (u, v, w) with nodes 0..n-1.
    Returns (total, tree_edges), or (None, forest_edges) if the graph is disconnected."""
    dsu = DSU(n)
    total, tree = 0, []
    for u, v, w in sorted(edges, key=lambda e: e[2]):
        if len(tree) == n - 1:
            break                                # already spanning: the rest only close cycles
        if dsu.union(u, v):                      # joins two components: safe by the cut property
            total += w
            tree.append((u, v, w))
    return (total, tree) if len(tree) == n - 1 else (None, tree)

public class DSU
{
    private readonly int[] parent, size;
    public int Count { get; private set; }      // number of components

    public DSU(int n)
    {
        parent = new int[n]; size = new int[n]; Count = n;
        for (int i = 0; i < n; i++) { parent[i] = i; size[i] = 1; }
    }

    public int Find(int x)
    {
        int root = x;
        while (parent[root] != root) root = parent[root];
        while (parent[x] != root) { int next = parent[x]; parent[x] = root; x = next; }
        return root;
    }

    public bool Union(int a, int b)
    {
        int ra = Find(a), rb = Find(b);
        if (ra == rb) return false;              // already connected: a cycle
        if (size[ra] < size[rb]) (ra, rb) = (rb, ra);
        parent[rb] = ra; size[ra] += size[rb]; Count--;
        return true;
    }
}

// edges: (u, v, w) with nodes 0..n-1. Returns the MST weight, or -1 if disconnected.
// Pass a list as `tree` to also collect the chosen edges.
public long Kruskal(int n, List<(int u, int v, int w)> edges, List<(int u, int v, int w)> tree = null)
{
    var dsu = new DSU(n);
    long total = 0; int taken = 0;
    foreach (var e in edges.OrderBy(e => e.w))
    {
        if (taken == n - 1) break;               // already spanning
        if (!dsu.Union(e.u, e.v)) continue;      // would close a cycle
        total += e.w; taken++;
        tree?.Add(e);
    }
    return taken == n - 1 ? total : -1;
}

Cost: O(E log E) for the sort, plus O(E·α(V)) for the unions, so O(E log E) overall (which is the same as O(E log V), because E < V²). Memory is the edge list plus two arrays of size V. If the graph is disconnected, the same loop builds a minimum spanning forest: one MST per component, and dsu.count tells you how many components there are.

Details that matter in practice:

  • Sort stability doesn't matter for the total, but it decides which MST you get when weights tie. Problems that ask for "the" tree with ties usually accept any.
  • The early stop (len(tree) == n − 1) is free speed: on random inputs the last edges are the heavy ones, and they would all be rejected anyway.
  • Self-loops are rejected automatically (find(u) == find(u)), and parallel edges are handled automatically (the lighter copy is seen first). Neither needs special code.

Prim: grow one tree with a heap

Prim's algorithm starts at any node and grows a single tree. The cut is always "nodes already in the tree" versus "everything else", so the safe edge is simply the cheapest edge leaving the tree. A min-heap holds candidate edges; pop the cheapest, and if its far end is new, take it and push that node's edges.

This is the lazy version: the heap may still hold edges whose far end has already joined the tree (stale entries). Instead of deleting them, you skip them when they are popped. That is the same trick Dijkstra uses, and it is why the two algorithms look almost identical: Prim's key is "weight of the one edge into the tree", Dijkstra's key is "length of the whole path from the source".

Step through Prim

The heap is shown as a sorted list (the real heap is a tree in an array, but only its minimum matters here). Blue edges are the frontier, the purple rows are entries just pushed, and red rows are stale entries that will be skipped when they reach the top.

import heapq


def prim(n, edges, start=0):
    """Lazy Prim. edges: (u, v, w). Returns the MST weight, or None if disconnected."""
    adj = [[] for _ in range(n)]
    for u, v, w in edges:
        adj[u].append((w, v))
        adj[v].append((w, u))
    in_tree = [False] * n
    heap = [(0, start)]                  # (weight of the edge into node, node)
    total = taken = 0
    while heap and taken < n:
        w, u = heapq.heappop(heap)
        if in_tree[u]:
            continue                     # stale: u joined the tree through a cheaper edge
        in_tree[u] = True
        total += w
        taken += 1
        for wx, x in adj[u]:
            if not in_tree[x]:
                heapq.heappush(heap, (wx, x))
    return total if taken == n else None

// Lazy Prim. Returns the MST weight, or -1 if the graph is disconnected.
public long Prim(int n, List<(int u, int v, int w)> edges, int start = 0)
{
    var adj = new List<(int to, int w)>[n];
    for (int i = 0; i < n; i++) adj[i] = new List<(int to, int w)>();
    foreach (var (u, v, w) in edges) { adj[u].Add((v, w)); adj[v].Add((u, w)); }
    var inTree = new bool[n];
    var heap = new PriorityQueue<int, int>();          // element: node, priority: edge weight into it
    heap.Enqueue(start, 0);
    long total = 0; int taken = 0;
    while (taken < n && heap.TryDequeue(out int u, out int w))
    {
        if (inTree[u]) continue;                        // stale entry
        inTree[u] = true; total += w; taken++;
        foreach (var (x, wx) in adj[u])
            if (!inTree[x]) heap.Enqueue(x, wx);
    }
    return taken == n ? total : -1;
}

Cost: every edge is pushed at most twice (once from each end), so O(E log E) = O(E log V) time and O(E) heap memory. An eager Prim keeps at most one entry per node (with decrease-key, or with an indexed heap) and brings the heap down to O(V); in Python and C# the lazy version is simpler and just as fast in practice.

The start node does not matter: any start gives an MST with the same total. If the graph is disconnected, Prim only spans the start node's component, so taken < n is your "impossible" signal.

Kruskal or Prim?

Both are correct and both are O(E log V) with a heap. The choice is about the shape of the input.

Input looks like Use Why
An edge list [u, v, w] Kruskal sort + DSU, 15 lines, no adjacency list needed
An adjacency list, or "grow from this node" Heap Prim no global sort; natural with a start node
Points in the plane, or a full cost matrix (complete graph) Dense Prim, O(V²) never materialise V²/2 edges; compute each cost on the fly
You also need connectivity facts (components, which edges joined what) Kruskal the DSU is a by-product you can query
Edges arrive sorted already, or weights are small integers Kruskal the sort disappears (or becomes a bucket sort)
A parallel machine, or "cheapest edge out of each component" is easy to compute Borůvka log V rounds of independent work

Dense Prim: O(V²) with no heap at all

When every pair of nodes is an edge (points in the plane with a distance, a full matrix of costs), E ≈ V²/2. A heap would cost O(V² log V); Kruskal would need to build and sort all V²/2 edges. Dense Prim does better by keeping one number per node, dist[v] = the cheapest edge from v into the tree so far, and scanning the array to find the minimum. V rounds of an O(V) scan plus an O(V) relaxation is O(V²), which is optimal for a complete graph because you must at least look at every pair.

def prim_dense(n, cost):
    """O(V^2) Prim for complete graphs. cost(i, j) gives the edge weight
    (return float('inf') for 'no edge'). Returns the MST weight, or None if disconnected."""
    INF = float("inf")
    dist = [INF] * n                     # cheapest edge from v into the tree
    in_tree = [False] * n
    total = 0
    if n:
        dist[0] = 0
    for _ in range(n):
        u = -1
        for i in range(n):               # O(V) scan replaces the heap
            if not in_tree[i] and (u == -1 or dist[i] < dist[u]):
                u = i
        if dist[u] == INF:
            return None                  # nothing reaches the rest
        in_tree[u] = True
        total += dist[u]
        for v in range(n):               # relax every edge out of u
            if not in_tree[v]:
                c = cost(u, v)
                if c < dist[v]:
                    dist[v] = c
    return total

// O(V^2) Prim for complete graphs. cost(i, j) returns long.MaxValue for "no edge".
// Returns the MST weight, or -1 if disconnected.
public long PrimDense(int n, Func<int, int, long> cost)
{
    var dist = new long[n]; var inTree = new bool[n];
    Array.Fill(dist, long.MaxValue);
    if (n > 0) dist[0] = 0;
    long total = 0;
    for (int k = 0; k < n; k++)
    {
        int u = -1;
        for (int i = 0; i < n; i++)              // O(V) scan replaces the heap
            if (!inTree[i] && (u == -1 || dist[i] < dist[u])) u = i;
        if (dist[u] == long.MaxValue) return -1;
        inTree[u] = true; total += dist[u];
        for (int v = 0; v < n; v++)              // relax every edge out of u
            if (!inTree[v]) dist[v] = Math.Min(dist[v], cost(u, v));
    }
    return total;
}

For n = 1000 points that is about 10⁶ steps, against roughly 10⁷ for Kruskal on 5·10⁵ edges, and with no edge list in memory. If you also need the tree itself, keep a link[v] array (the tree node that gave dist[v] its value) as the visualizer does; the MST edges are (link[v], v) for every v except the start.

Borůvka: every component picks at once

The third classic algorithm is the oldest (1926). Each round, every component picks the cheapest edge leaving it, and all picks are added together. Each pick is safe by the cut property (cut = that component versus the rest), and because every component merges with at least one other, the number of components at least halves each round.

def boruvka(n, edges):
    """Returns the MST weight, or None if disconnected. Ties broken by edge index."""
    dsu, total = DSU(n), 0
    while dsu.count > 1:
        best = [-1] * n                          # cheapest edge leaving each root
        for i, (u, v, w) in enumerate(edges):
            ru, rv = dsu.find(u), dsu.find(v)
            if ru == rv:
                continue
            for r in (ru, rv):
                if best[r] == -1 or (w, i) < (edges[best[r]][2], best[r]):
                    best[r] = i
        merged = False
        for i in set(best):
            if i != -1:
                u, v, w = edges[i]
                if dsu.union(u, v):
                    total += w
                    merged = True
        if not merged:
            return None                          # some component has no way out
    return total

You will rarely write Borůvka for a plain MST; Kruskal is shorter. It earns its place when the graph is implicit and "the cheapest edge out of this component" has a clever answer. In the XOR-MST (edge weight = a[i] xor a[j] over all pairs), a binary trie answers that query in O(log A), and Borůvka turns an impossible V² edge set into O(V log V log A).

Variants and tricks

Maximum spanning tree

Sort descending (or negate every weight) and run Kruskal unchanged. The cut property flips to "the heaviest crossing edge is safe". Use it when edges are capacities, reliabilities or similarities and you want the strongest tree. For "maximise the product of probabilities" with 0 < p ≤ 1, a maximum spanning tree on the raw p works, because only the order matters.

Bottleneck (minimax) paths

"Find a route from s to t whose largest edge is as small as possible." The answer is the s–t path inside any MST, and you don't even need the whole tree: run Kruskal and stop the moment s and t are connected. The edge that connected them is the answer.

Why it works: just before that edge was added, s and t were in different components of the graph made of all strictly lighter edges. Every s–t path has to leave s's component somewhere, through an edge that is no lighter. So no path can do better, and the path that now exists does exactly that well. Switch the goal to maximise the smallest edge (the widest road, the heaviest truck) and the same scan runs heaviest-first.

Three ways to solve a bottleneck problem, all correct:

Approach Cost When it is the best fit
Kruskal until s and t connect O(E log E) an edge list or a grid; one pair
Dijkstra with max(d, w) instead of d + w O(E log V) a start node and a grid; you may stop at t early
Binary search on the answer + BFS/DSU "is s connected using edges ≤ X?" O(E log W) the check is easy but the structure is odd

When you get many queries "is there a path from p to q using only edges < L?", sort the queries by L and sweep the edges once, adding to a DSU (an offline sweep, worked through on the Union-Find page). If the queries must be answered online, build the MST once and answer "maximum edge on the tree path" with binary lifting, or build a Kruskal reconstruction tree (every union creates a new parent node whose value is the edge weight; the answer is the value of the LCA).

The virtual node: nodes that cost something on their own

Sometimes a node can be "served" either by connecting it to a neighbour or by paying its own price (dig a well, install a generator, buy a licence). Add one extra node standing for "the outside source", and give it an edge to every node i whose weight is i's own price. Now every choice is an edge, and the cheapest plan is an MST on n + 1 nodes.

The trick is the same "virtual node" idea used in Union-Find for borders and roofs, and in multi-source BFS: one fake node turns "many possible starting points" into an ordinary graph.

Forced and forbidden edges

  • Must include edge e: union its ends (and add its weight) before the loop, then run Kruskal as usual. The result is the cheapest spanning tree containing e.
  • Must exclude edge e: skip it in the loop. If the result is disconnected, e is a bridge and every spanning tree needs it.

Those two operations are exactly how you classify edges. An edge is critical (in every MST) if excluding it makes the total go up or disconnects the graph. It is pseudo-critical (in some MSTs but not all) if it is not critical but forcing it in still gives the minimum total. Everything else is in no MST.

Second-best MST and "MST through edge e"

Take the MST T with weight W. Adding a non-tree edge e = u–v closes exactly one cycle, the tree path u ⇝ v plus e. Removing the heaviest tree edge on that path gives the cheapest spanning tree that contains e: W + w(e) − maxOnPath(u, v).

That one formula answers several classic questions:

  • Second-best MST: the minimum of that formula over all non-tree edges. (A second-best tree always differs from some MST by one swap.)
  • For every edge e, the cheapest spanning tree containing e (Codeforces 609E): W for tree edges, the formula for the rest.
  • Is the MST unique? It is unique exactly when no non-tree edge has w(e) == maxOnPath(u, v).
  • An edge weight decreased: add the edge and drop the heaviest edge on the cycle it closes, in O(V). A tree edge increased: remove it and reconnect the two halves with the lightest crossing edge, in O(E).

maxOnPath for one pair is a DFS in O(V). For all pairs, run a BFS from every node in O(V²); for many queries on a big tree, use binary lifting (up[k][v] together with mx[k][v], the heaviest edge on the 2ᵏ-step jump), which gives O(log V) per query.

MSTs in disguise

Many problems never say "spanning tree". Look for these shapes:

  • "Connect all of them at minimum total cost" with a cost per pair: points (Manhattan or Euclidean), servers, islands. That is an MST, usually dense Prim.
  • "The minimum possible value of the maximum…" along a route, or "the smallest threshold that makes s and t connected": a bottleneck path. Kruskal-until-connected, Dijkstra with max, or binary search.
  • "Each item can be served alone at a price, or linked to another": a virtual node.
  • "Keep the graph connected for everybody while removing as many edges as possible": a spanning tree per person, sharing the common edges first (Remove Max Number of Edges, below).
  • "Which edges are essential?": forced/forbidden Kruskal runs (critical edges), or bridges if weights don't matter (see Advanced Graphs).

And a few that look like MSTs but are not:

  • A directed graph. "Every node reachable from the root, minimum total" is a minimum arborescence, solved by the Chu–Liu/Edmonds algorithm. Kruskal and Prim give wrong answers on directed edges.
  • Connecting only some of the nodes (a required subset, with others optional) is the Steiner tree problem, which is NP-hard in general. Small subsets: bitmask DP over the required nodes plus shortest paths.
  • A path or a route (visit everyone, minimise the length) is a travelling-salesman flavour, not a tree.
  • Minimum Score of a Path Between Two Cities asks for the smallest edge reachable at all from city 1 (walks may repeat roads), which is just the minimum edge in 1's component, not a bottleneck path.

Recognize it when

Recognize a minimum spanning tree when

  • You must connect everything (all nodes reachable from each other) and pay for each edge you build, minimising the total.
  • The input is points with a distance or a full cost matrix, and the answer is "the cheapest network": dense Prim.
  • The answer is the best possible worst edge on a route (smallest max effort, lowest water level, widest bandwidth): a bottleneck path, the MST path between s and t.
  • Nodes can be served on their own at a price: add a virtual node and its edges.
  • You must decide which edges are in every / some / no optimal tree: forced and forbidden Kruskal runs.
  • Queries ask "connected using only edges below a threshold?": sort and sweep with a DSU, or query the MST.
  • The weights are only compared, never added along a path: any increasing transformation (log, square, negate for max) keeps the same tree.
Algorithm Time Memory Best for
Kruskal (sort + DSU) O(E log E) O(V + E) edge lists, sparse graphs, bottleneck queries
Lazy Prim (binary heap) O(E log V) O(V + E) adjacency lists, growing from a start node
Dense Prim (array scan) O(V²) O(V) complete graphs: points, matrices
Borůvka O(E log V) O(V + E) implicit graphs with a fast "cheapest edge out" query; parallel
Critical / pseudo-critical (2E Kruskal runs) O(E² α(V)) O(V + E) E up to a few hundred
Second-best MST (BFS from every node) O(V² + E log E) O(V²) V up to a few thousand
Second-best MST (binary lifting) O(E log V) O(V log V) large graphs, or many "max on path" queries

Pitfalls: the actual bug and its fix

  1. Not checking that the graph is connected. Kruskal happily returns the weight of a spanning forest, and Prim the weight of the start node's component. Fix: check taken == n − 1 (Kruskal) or taken == n (Prim) and return −1 when the problem says "impossible".
  2. Using an MST for shortest paths. The tree minimises the total of all edges, not the distance between two nodes. Fix: if the question is "from A to B, as short as possible", use Shortest Paths. Only bottleneck (max-edge) questions follow the MST.
  3. Running Kruskal or Prim on a directed graph. The cut property needs undirected edges. Fix: a minimum arborescence (Chu–Liu/Edmonds), or check whether the problem really is undirected.
  4. Off-by-one node ids. LeetCode numbers cities 1 … n; DSU(n) then fails on node n, and DSU(n + 1) leaves node 0 as an extra component so the connectivity check fails. Fix: subtract 1 on the way in, or use n + 1 and expect count == 2.
  5. Building all V² edges for points and then sorting them. For n = 1000 that is 500 000 edges and a large sort; in Python it is often too slow. Fix: dense Prim with on-the-fly distances.
  6. Lazy Prim without the stale check. Without if in_tree[u]: continue, a node is added twice and its weight is counted twice. Fix: skip popped nodes that are already in the tree.
  7. Integer overflow of the total. 10⁵ edges of weight 10⁹ is 10¹⁴. Fix: long totals in C#.
  8. Comparing the "forced" run with the wrong baseline in critical-edge problems. A run that skips an edge and leaves the graph disconnected must count as "more expensive". Fix: return infinity (not the forest weight) when the result is not spanning.
  9. Borůvka with unbroken ties. Two components may each pick a different edge of equal weight between them, and the picks together close a cycle. Fix: compare (w, index), and still union through the DSU.
  10. Minimax by the sum. Dijkstra with d + w minimises the total, not the largest edge. Fix: relax with max(d, w) or use Kruskal-until-connected.
  11. Forgetting the virtual node in the node count. With n houses plus the source you have n + 1 nodes and need n edges. Fix: DSU(n + 1) and node 0 as the source.

Worked problems

1. Min Cost to Connect All Points Medium

Given n ≤ 1000 points on a plane, the cost of connecting two points is their Manhattan distance |x1 − x2| + |y1 − y2|. Return the minimum cost to make all points connected.

Key insight. Every pair is a possible edge, so this is an MST on a complete graph with about 500 000 edges. Building and sorting them works in C# but is wasteful; dense Prim computes each distance on the fly in O(n²) time and O(n) memory, exactly the input shape it was made for.

Solution: dense Prim with Manhattan distance 
def min_cost_connect_points(points):
    def manhattan(i, j):
        return abs(points[i][0] - points[j][0]) + abs(points[i][1] - points[j][1])
    return prim_dense(len(points), manhattan)

public long MinCostConnectPoints(int[][] points)
{
    return PrimDense(points.Length, (i, j) =>
        Math.Abs(points[i][0] - points[j][0]) + Math.Abs(points[i][1] - points[j][1]));
}

Complexity: O(n²) time, O(n) memory. With Kruskal it is O(n² log n) time and O(n²) memory. For n up to 10⁵ points with Manhattan distance, there is a known reduction to O(n) candidate edges (for each point, only the nearest neighbour in each of 8 octants can be an MST edge), found with a sweep and a Fenwick tree; then Kruskal on those edges.

2. Connecting Cities With Minimum Cost Medium

There are n cities labelled 1 … n and a list connections[i] = [x, y, cost] of possible bidirectional roads. Return the minimum cost to connect all cities, or −1 if it is impossible.

Key insight. This is the textbook MST on an edge list, so Kruskal is the shortest correct code. The only traps are the 1-based labels and the "impossible" case, which shows up as fewer than n − 1 accepted edges.

Solution: Kruskal with a connectivity check 
def minimum_cost(n, connections):
    total, _ = kruskal(n, [(x - 1, y - 1, c) for x, y, c in connections])
    return -1 if total is None else total

public long MinimumCost(int n, int[][] connections)
{
    var edges = connections.Select(c => (c[0] - 1, c[1] - 1, c[2])).ToList();
    return Kruskal(n, edges);                    // -1 when the cities can't all be connected
}

Complexity: O(E log E) time, O(n + E) memory.

3. Optimize Water Distribution in a Village Hard

There are n houses. House i can get water by building a well inside it at cost wells[i − 1], or by being connected through pipes to a house that has water. pipes[j] = [a, b, cost] is a bidirectional pipe between houses a and b. Return the minimum total cost to supply water to every house.

Key insight. A well is a cost that belongs to one node, which a spanning tree cannot express. Add a virtual node 0 ("the ground water") with an edge 0–i of weight wells[i − 1]. Every house must be connected to node 0 through some chain of pipes and exactly one well, so the cheapest plan is an MST on n + 1 nodes. Several wells can be chosen; each is one edge to node 0.

Solution: virtual node + Kruskal 
def min_cost_to_supply_water(n, wells, pipes):
    edges = [(0, i + 1, cost) for i, cost in enumerate(wells)]     # node 0 = digging a well
    edges += [(a, b, cost) for a, b, cost in pipes]
    total, _ = kruskal(n + 1, edges)
    return total

public long MinCostToSupplyWater(int n, int[] wells, int[][] pipes)
{
    var edges = new List<(int u, int v, int w)>();
    for (int i = 0; i < n; i++) edges.Add((0, i + 1, wells[i]));   // node 0 = digging a well
    foreach (var p in pipes) edges.Add((p[0], p[1], p[2]));
    return Kruskal(n + 1, edges);
}

Complexity: O((n + P) log(n + P)) time. The answer always exists, because node 0 is connected to every house.

4. Path With Minimum Effort Medium

Given a grid of heights, walk from the top-left to the bottom-right moving up, down, left or right. A route's effort is the largest absolute height difference between two consecutive cells on it. Return the minimum effort.

Key insight. "Minimise the largest step" is a bottleneck path. Every pair of adjacent cells is an edge whose weight is the height difference. Add edges from the smallest difference upward, and the first edge that connects the two corners is the answer: before it, they were separated by strictly smaller edges. Dijkstra with max instead of + also works and is shown on the Shortest Paths page; seeing both is the best way to understand why minimax problems sit between the two topics.

Solution: Kruskal until the corners connect 
def minimum_effort_path(heights):
    R, C = len(heights), len(heights[0])
    if R * C == 1:
        return 0
    edges = []
    for r in range(R):
        for c in range(C):
            i = r * C + c
            if c + 1 < C:
                edges.append((abs(heights[r][c] - heights[r][c + 1]), i, i + 1))
            if r + 1 < R:
                edges.append((abs(heights[r][c] - heights[r + 1][c]), i, i + C))
    edges.sort()
    dsu = DSU(R * C)
    for w, a, b in edges:
        dsu.union(a, b)
        if dsu.find(0) == dsu.find(R * C - 1):
            return w                     # the edge that finally joins the corners
    return 0

public int MinimumEffortPath(int[][] heights)
{
    int R = heights.Length, C = heights[0].Length;
    if (R * C == 1) return 0;
    var edges = new List<(int w, int a, int b)>();
    for (int r = 0; r < R; r++)
        for (int c = 0; c < C; c++)
        {
            int i = r * C + c;
            if (c + 1 < C) edges.Add((Math.Abs(heights[r][c] - heights[r][c + 1]), i, i + 1));
            if (r + 1 < R) edges.Add((Math.Abs(heights[r][c] - heights[r + 1][c]), i, i + C));
        }
    edges.Sort();
    var dsu = new DSU(R * C);
    foreach (var (w, a, b) in edges)
    {
        dsu.Union(a, b);
        if (dsu.Find(0) == dsu.Find(R * C - 1)) return w;   // the edge that joins the corners
    }
    return 0;
}

Complexity: O(RC log(RC)) time for the sort, O(RC) memory. Swim in Rising Water is the same problem with cell weights instead of edge weights (an edge between neighbours costs max(h1, h2)).

5. Remove Max Number of Edges to Keep Graph Fully Traversable Hard

An undirected graph on n nodes (1 … n) has three edge types: type 1 can be used only by Alice, type 2 only by Bob, type 3 by both. Remove as many edges as possible so that both Alice and Bob can still reach every node from every other. Return the number removed, or −1 if it is impossible even with all edges.

Key insight. Each person needs a spanning tree of their own usable edges, and we want to keep as few edges as possible. A shared edge does the job of two private edges at once, so it is never worse to take shared edges first. Run a Kruskal-style pass (all weights equal) on type-3 edges in both DSUs, then type-1 edges in Alice's DSU and type-2 in Bob's. Every edge that joined nothing new can be removed.

Solution: two DSUs, shared edges first 
def max_num_edges_to_remove(n, edges):
    alice, bob = DSU(n + 1), DSU(n + 1)          # node 0 is unused
    kept = 0
    for t, u, v in edges:
        if t == 3:
            joined = alice.union(u, v)
            bob.union(u, v)                      # both DSUs are identical so far
            kept += joined
    for t, u, v in edges:
        if t == 1:
            kept += alice.union(u, v)
        elif t == 2:
            kept += bob.union(u, v)
    if alice.count != 2 or bob.count != 2:       # 1 component + the unused node 0
        return -1
    return len(edges) - kept

public int MaxNumEdgesToRemove(int n, int[][] edges)
{
    var alice = new DSU(n + 1); var bob = new DSU(n + 1);   // node 0 is unused
    int kept = 0;
    foreach (var e in edges)
        if (e[0] == 3)
        {
            bool joined = alice.Union(e[1], e[2]);
            bob.Union(e[1], e[2]);                          // both DSUs are identical so far
            if (joined) kept++;
        }
    foreach (var e in edges)
    {
        if (e[0] == 1 && alice.Union(e[1], e[2])) kept++;
        else if (e[0] == 2 && bob.Union(e[1], e[2])) kept++;
    }
    if (alice.Count != 2 || bob.Count != 2) return -1;      // 1 component + node 0
    return edges.Length - kept;
}

Complexity: O(E·α(n)) time, O(n) memory. Why "shared first" is safe: by the exchange argument, if an optimal solution uses a private edge where a shared edge could connect the same two components, swapping in the shared edge serves both people and never increases the count.

6. Find Critical and Pseudo-Critical Edges in Minimum Spanning Tree Hard

Given a connected weighted graph with n ≤ 100 nodes and E ≤ 200 edges, return two lists of edge indices: critical edges, which appear in every MST, and pseudo-critical edges, which appear in some MSTs but not all.

Key insight. Compute the MST weight W once. Edge i is critical exactly when the best spanning tree without i is heavier than W (or does not exist). Otherwise, edge i is pseudo-critical exactly when the best spanning tree forced to contain i still weighs W. Both are one Kruskal run on the presorted edges. The critical visualizer above steps through this exact loop.

Solution: 2E Kruskal runs, skip or force 
def find_critical_and_pseudo_critical_edges(n, edges):
    order = sorted(range(len(edges)), key=lambda i: edges[i][2])

    def mst(skip=-1, force=-1):
        dsu, total = DSU(n), 0
        if force != -1:
            u, v, w = edges[force]
            dsu.union(u, v)
            total += w
        for i in order:
            if i != skip:
                u, v, w = edges[i]
                if dsu.union(u, v):
                    total += w
        return total if dsu.count == 1 else float("inf")    # not spanning = infinitely bad

    base = mst()
    critical, pseudo = [], []
    for i in range(len(edges)):
        if mst(skip=i) > base:
            critical.append(i)
        elif mst(force=i) == base:
            pseudo.append(i)
    return [critical, pseudo]

public IList<IList<int>> FindCriticalAndPseudoCriticalEdges(int n, int[][] edges)
{
    var order = Enumerable.Range(0, edges.Length).OrderBy(i => edges[i][2]).ToArray();
    long Mst(int skip, int force)
    {
        var dsu = new DSU(n); long total = 0;
        if (force != -1) { dsu.Union(edges[force][0], edges[force][1]); total += edges[force][2]; }
        foreach (int i in order)
            if (i != skip && dsu.Union(edges[i][0], edges[i][1])) total += edges[i][2];
        return dsu.Count == 1 ? total : long.MaxValue;      // not spanning = infinitely bad
    }
    long baseW = Mst(-1, -1);
    var critical = new List<int>(); var pseudo = new List<int>();
    for (int i = 0; i < edges.Length; i++)
    {
        if (Mst(i, -1) > baseW) critical.Add(i);
        else if (Mst(-1, i) == baseW) pseudo.Add(i);
    }
    return new List<IList<int>> { critical, pseudo };
}

Complexity: O(E log E + E²·α(n)) time, O(n + E) memory. A faster O(E log E) solution processes each group of equal-weight edges together: contract the components formed by lighter edges, then an edge of the group is in no MST if it is a self-loop after contraction, critical if it is a bridge in the group's contracted multigraph, and pseudo-critical otherwise (bridges: see Advanced Graphs).

7. Second-Best Minimum Spanning Tree Expert

Given a connected undirected graph with positive weights (parallel edges allowed), return the weight of the cheapest spanning tree that is different from a fixed MST (as a set of edges), or −1 if the graph has only one spanning tree. If several MSTs tie, the answer equals the MST weight.

Key insight. Some second-best tree differs from the MST in exactly one swap: add a non-tree edge u–v, remove the heaviest tree edge on the path u ⇝ v. So build the MST, precompute mx[s][x] = the heaviest edge on the tree path from s to x (one BFS per node over the tree), and minimise W + w − mx[u][v] over the non-tree edges.

Solution: MST + best single swap 
from collections import deque


def second_best_mst(n, edges):
    order = sorted(range(len(edges)), key=lambda i: edges[i][2])
    dsu, W, in_mst = DSU(n), 0, [False] * len(edges)
    adj = [[] for _ in range(n)]
    for i in order:
        u, v, w = edges[i]
        if dsu.union(u, v):
            W += w
            in_mst[i] = True
            adj[u].append((v, w))
            adj[v].append((u, w))
    mx = [[0] * n for _ in range(n)]             # mx[s][x]: heaviest edge on the tree path s ~> x
    for s in range(n):
        seen = [False] * n
        seen[s] = True
        q = deque([s])
        while q:
            x = q.popleft()
            for y, w in adj[x]:
                if not seen[y]:
                    seen[y] = True
                    mx[s][y] = max(mx[s][x], w)
                    q.append(y)
    best = -1
    for i, (u, v, w) in enumerate(edges):
        if not in_mst[i] and u != v:             # a self-loop can never be swapped in
            cand = W + w - mx[u][v]
            if best == -1 or cand < best:
                best = cand
    return best

public long SecondBestMst(int n, int[][] edges)
{
    var order = Enumerable.Range(0, edges.Length).OrderBy(i => edges[i][2]).ToArray();
    var dsu = new DSU(n); long W = 0; var inMst = new bool[edges.Length];
    var adj = new List<(int to, int w)>[n];
    for (int i = 0; i < n; i++) adj[i] = new List<(int to, int w)>();
    foreach (int i in order)
    {
        int u = edges[i][0], v = edges[i][1], w = edges[i][2];
        if (!dsu.Union(u, v)) continue;
        W += w; inMst[i] = true;
        adj[u].Add((v, w)); adj[v].Add((u, w));
    }
    var mx = new int[n, n];                      // heaviest edge on the tree path s ~> x
    for (int s = 0; s < n; s++)
    {
        var seen = new bool[n]; seen[s] = true;
        var q = new Queue<int>(); q.Enqueue(s);
        while (q.Count > 0)
        {
            int x = q.Dequeue();
            foreach (var (y, w) in adj[x])
                if (!seen[y]) { seen[y] = true; mx[s, y] = Math.Max(mx[s, x], w); q.Enqueue(y); }
        }
    }
    long best = -1;
    for (int i = 0; i < edges.Length; i++)
    {
        int u = edges[i][0], v = edges[i][1];
        if (inMst[i] || u == v) continue;        // a self-loop can never be swapped in
        long cand = W + edges[i][2] - mx[u, v];
        if (best == -1 || cand < best) best = cand;
    }
    return best;
}

Complexity: O(E log E + V²) time and O(V²) memory, fine for V up to a few thousand. For large V, replace the all-pairs table with binary lifting on the MST (up[k][v], mx[k][v]), which answers each maxOnPath(u, v) in O(log V) for O(E log V) total. Some judges ask for the strictly second-best tree; then also track the second-largest distinct edge on each path, and use it when w == maxOnPath.

Self-check

Does the MST contain the shortest path between every pair of nodes?

No. Take a triangle with edges A–B 2, B–C 2, A–C 3. The MST is A–B + B–C (total 4), so the tree path from A to C has length 4, while the direct edge A–C has length 3. The MST minimises the sum of all edges built, not the length of any one route. What the MST path does minimise is the largest edge on the route (the bottleneck): here max(2, 2) = 2 < 3.

Can MST algorithms handle negative edge weights?

Yes, with no change at all. Kruskal and Prim only compare weights, and the cut property holds for any real numbers. You could add a large constant to every edge to make them positive, and since every spanning tree has exactly n − 1 edges, every tree's total shifts by the same amount. (This is the big difference from Dijkstra, which adds weights along a path and breaks on negative edges.)

Every node picks its single cheapest edge. Is the union of those edges an MST?

Each picked edge is safe (cut property, cut = that node versus the rest), so all of them belong to the MST when weights are distinct. But they are usually not enough: on 0–1 (1), 2–3 (1), 1–2 (5), nodes 0 and 1 pick 0–1, nodes 2 and 3 pick 2–3, and nobody picks 1–2. You get components, not a tree. Repeating the step on the components until one remains is exactly Borůvka's algorithm.

Why can Kruskal stop as soon as it has taken n − 1 edges?

A forest on n nodes with n − 1 edges is connected: every edge taken reduced the component count by one, from n down to 1. Every later edge would have both ends in the single remaining component, so every one of them would be rejected. Stopping early skips that wasted work; on a typical input it is most of the edge list.

In lazy Prim, how large can the heap get, and does it matter?

Every edge can be pushed twice (once from each end), so the heap can hold O(E) entries, of which many become stale. That makes it O(E log E) time, which equals O(E log V) since log E ≤ 2 log V. It only matters for memory on huge dense graphs, and there you should be using dense Prim anyway. An eager Prim with an indexed heap (decrease-key) keeps at most V entries.

One edge weight drops. How do you update the MST without recomputing it?

If the edge is already in the tree, nothing changes: the tree only got cheaper and is still minimal. If it is not, add it: it closes one cycle with the tree path between its ends. Remove the heaviest edge on that cycle (cycle property). That is O(V) with a DFS along the tree. If an edge in the tree gets heavier, remove it, which splits the tree in two, and reconnect with the lightest edge crossing between the halves (cut property), in O(E).

Your graph is directed: "every city must be reachable from the capital". Why is Kruskal wrong?

Kruskal treats u→v and v→u as the same connection and builds a tree that may need to traverse some edges backwards. In a directed graph the cut property fails: the lightest edge into a set of nodes might point the wrong way for the root. The right problem is a minimum arborescence rooted at the capital, solved by the Chu–Liu/Edmonds algorithm in O(VE): every node picks its cheapest incoming edge, cycles are contracted with adjusted weights, and the process repeats.

Path With Minimum Effort: Kruskal or Dijkstra?

Both are correct. Kruskal sorts all ~2RC edges and adds them until the corners connect: simple, and the "why" is the bottleneck property of the MST. Dijkstra runs from the start with max(d, w) as the path cost and can stop as soon as the target is popped, so it often explores less of the grid. Binary search on the effort plus a BFS is a third option. If you only remember one, remember that the answer to "minimise the maximum" is a threshold, and all three are ways to find the smallest threshold that connects the corners.
