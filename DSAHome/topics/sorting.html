Sorting Algorithms

Animated bubble, insertion, merge, quick, heap, counting and radix sorts; stability, quickselect and custom comparators.

Beginner → Advanced~60 min studyBuilds on: Recursion & the Call StackUpdated 2026-11-03

What it is and when you need it

Sorting puts values in order. On its own that sounds like housekeeping, but in problem solving it is a move: you pay O(n log n) once, and in exchange questions about the whole array turn into questions about neighbours. Duplicates become adjacent, the closest pair becomes adjacent, the extremes move to the ends, and every lookup becomes a binary search.

The rule. If the answer does not depend on the original order of the input, ask "what if it were sorted?" before anything else. If the order does matter, sort (value, index) pairs so you keep it.

This page has two halves. The first half opens up the algorithms themselves, each one animated from a real run: the three simple sorts, merge sort with its recursion tree, quicksort with both classic partitions, heapsort, stability, the lower bound, and the non-comparison sorts that beat it. The second half is about using sorting: comparators, quickselect, sort-then-sweep, sorting to unlock a greedy choice, cyclic sort and inversion counting, then a ladder of real problems. You will want Recursion for merge sort and quicksort, and Complexity Analysis for the cost arguments.

Simple sorts: O(n²)

Bubble, selection, insertion. A few lines each, in place. Fine up to a few thousand values, and insertion sort is the best algorithm there is for tiny or nearly-sorted arrays.

Comparison sorts: O(n log n)

Merge, quick, heap, and the library hybrids built from them. This is the floor for any algorithm that only compares: you cannot do better in the worst case.

Non-comparison sorts: O(n)

Counting, radix, bucket. They look inside the keys (digits, small ranges) instead of comparing them. Linear time, but only when the keys cooperate.

The simple sorts, and the number that explains them

Before the fast algorithms, it pays to understand three slow ones properly, because one idea explains all of them: the inversion. An inversion is a pair of positions i < j with a[i] > a[j], i.e. a pair that is in the wrong order. A sorted array has 0 inversions; a reversed array has the maximum, n(n−1)/2.

Swapping two adjacent values that are out of order removes exactly one inversion. So any algorithm that only swaps neighbours (bubble sort, insertion sort) must do exactly "number of inversions" swaps. That is O(n²) on average, but it is O(n) when the input is nearly sorted. Keep that number in mind; it comes back in merge sort, in the stability section, and in the hard problems at the end.

Bubble sort

Compare each neighbour pair, swap if out of order, repeat. Each pass carries the largest remaining value to the end. The one useful refinement is the early exit: a pass with no swaps proves the array is sorted. Step through it and watch the swap counter: it always finishes equal to the inversion count.

Selection sort

Find the minimum of the unsorted part, swap it to the front, repeat. It does n(n−1)/2 comparisons no matter what (even on sorted input), but at most n − 1 swaps. That makes it the right choice only in one odd situation: writes are far more expensive than reads. Its long-distance swap is also why it is not stable, which you will see in the stability section.

Insertion sort: the one you should actually know

Insertion sort keeps a sorted prefix and inserts the next value into it, the way you sort a hand of cards. The inner loop shifts larger values one slot right and drops the key into the gap. It is stable, in place, adaptive (it does one shift per inversion, so a nearly-sorted array costs O(n)), and has tiny constant factors. Every serious library sort switches to insertion sort for ranges of about 16 to 32 elements.

def insertion_sort(a: list[int]) -> None:
    for i in range(1, len(a)):
        key, j = a[i], i - 1          # lift a[i] out; a[0..i) is sorted
        while j >= 0 and a[j] > key:  # strict > keeps equal keys in order (stable)
            a[j + 1] = a[j]           # shift right into the hole
            j -= 1
        a[j + 1] = key                # drop the key into the hole

public static void InsertionSort(int[] a)
{
    for (int i = 1; i < a.Length; i++)
    {
        int key = a[i], j = i - 1;       // lift a[i] out; a[0..i) is sorted
        while (j >= 0 && a[j] > key)     // strict > keeps equal keys in order (stable)
        {
            a[j + 1] = a[j];             // shift right into the hole
            j--;
        }
        a[j + 1] = key;                  // drop the key into the hole
    }
}

Insight: "shift" beats "swap" Bubble sort and insertion sort perform the same number of exchanges, but insertion sort moves the key in a hole: one write per step instead of three. On nearly-sorted data it is the fastest sort in this whole page, which is exactly why Timsort and introsort finish small runs with it.

Merge sort: split in half, trust the recursion, merge

Merge sort is the cleanest example of divide and conquer. Split the array in half, sort each half recursively, then merge the two sorted halves. Merging is easy because the smallest remaining value is always one of the two heads: compare them, take the smaller, advance. That is the same two-sequence walk as merging two sorted arrays in Two Pointers.

The visualizer draws the recursion tree with one row per depth. Going down, nodes are only split (dashed). Coming back up, the active node merges its two children: the amber cells are the heads under comparison, faded cells are already consumed, and the blue cells are the merged output so far.

Notice three things while you step:

  • Nothing is compared on the way down. All the work happens in merges.
  • Ties go left (<=). Values from the left half were earlier in the input, so equal values keep their order: merge sort is stable.
  • The cost is the same on every input. Sorted, reversed or random, every level does about n work, and there are log₂ n levels. The price is O(n) extra memory for the merge buffer.
def merge_sort(a: list[int]) -> None:
    buf = a[:]                                  # one scratch buffer, reused by every merge

    def sort(lo: int, hi: int) -> None:         # sorts a[lo:hi], hi exclusive
        if hi - lo <= 1:
            return
        mid = (lo + hi) // 2
        sort(lo, mid)
        sort(mid, hi)
        if a[mid - 1] <= a[mid]:
            return                              # halves already in order: O(n) on sorted input
        buf[lo:hi] = a[lo:hi]
        i, j = lo, mid
        for k in range(lo, hi):
            if j >= hi or (i < mid and buf[i] <= buf[j]):   # <= : ties go left (stable)
                a[k] = buf[i]
                i += 1
            else:
                a[k] = buf[j]
                j += 1

    sort(0, len(a))

public static void MergeSort(int[] a)
{
    var buf = new int[a.Length];                // one scratch buffer, reused by every merge
    Sort(0, a.Length);

    void Sort(int lo, int hi)                   // sorts a[lo..hi), hi exclusive
    {
        if (hi - lo <= 1) return;
        int mid = lo + (hi - lo) / 2;
        Sort(lo, mid);
        Sort(mid, hi);
        if (a[mid - 1] <= a[mid]) return;       // halves already in order
        Array.Copy(a, lo, buf, lo, hi - lo);
        int i = lo, j = mid;
        for (int k = lo; k < hi; k++)
            a[k] = (j >= hi || (i < mid && buf[i] <= buf[j])) ? buf[i++] : buf[j++];
    }
}

Variations worth knowing

  • Bottom-up merge sort skips recursion: merge runs of width 1, then 2, then 4, … until one run covers the array. Same O(n log n), no call stack, and it is how merge sort is usually done on linked lists (Sort List wants O(1) extra space, which bottom-up merging of list nodes achieves because relinking nodes needs no buffer).
  • Natural merge sort first finds the runs that are already sorted and only merges those. That is the heart of Timsort: real data is full of sorted runs, so it often runs in close to O(n).
  • External sorting. When data does not fit in memory, sort chunks that do, write them out, then do a k-way merge of the chunk files with a heap (Heaps and Priority Queues). Merge sort's sequential access pattern is why databases use it.
  • Merge sort as a counting engine. The merge step sees every "crossing" pair of the two halves in sorted order. That lets you count inversions, smaller-elements-after-self, reverse pairs and range sums in O(n log n). There is a full section on it below.

Quicksort: partition first, then recurse

Merge sort does trivial splitting and clever merging. Quicksort is the mirror image: clever splitting and no merging at all. Pick a pivot, rearrange the range so smaller values are on its left and larger ones on its right (partition), then recurse on the two sides. When the recursion returns, the array is sorted, because every pivot already sits where it belongs.

Everything interesting is in the partition. There are two classic schemes, and both are worth stepping through.

Lomuto partition: one scanner

Move the pivot to the end. A single scanner j walks left to right; i marks the end of the "smaller than pivot" region. When a[j] < pivot, swap it to position i and grow the region. At the end, swap the pivot into slot i: it is now in its final sorted position.

Hoare partition: two scanners meeting

Hoare's original scheme runs i from the left and j from the right. i stops on a value that belongs on the right (≥ pivot), j stops on a value that belongs on the left (≤ pivot), and one swap fixes both. When they cross, everything up to j is ≤ pivot and everything after is ≥ pivot. It makes about three times fewer swaps than Lomuto, and because both scanners stop on equal values, an array full of duplicates still splits down the middle.

Pitfall: mixing up what each partition returns Lomuto returns the pivot's final index p, so you recurse on [lo, p − 1] and [p + 1, hi]. Hoare returns a split point j with the pivot somewhere in the range, so you recurse on [lo, j] and [j + 1, hi]. Using Lomuto's recursion with Hoare's partition skips elements; using Hoare's with a pivot taken from a[hi] can return j = hi and recurse forever on the same range.

The whole algorithm, and the worst case

Now the full sort. Each call partitions its range (dashed box), the pivot turns green for good, and the two sides are pushed as new calls. Switch the steps to "every comparison" to see every scanner move. Then try the classic trap: the default input sorted (1,2,3,…) with pivot rule last. Every partition is lopsided, the recursion depth becomes n, and comparisons hit n(n−1)/2.

Why is quicksort still the default in so many libraries? Its inner loop is a tight, cache-friendly scan with almost no data movement, it sorts in place, and with a random pivot (or median-of-3) the expected cost is about 1.39 n log₂ n comparisons on every input. The bad case needs the pivot to be an extreme value again and again, which random choice makes vanishingly rare. Production versions add three guards:

  1. Insertion sort for small ranges (below ~16 elements): recursion overhead dominates there.
  2. Recurse on the smaller side, loop on the larger. That caps the stack at O(log n) even when splits are bad.
  3. Introsort fallback: if the recursion depth passes about 2·log₂ n, switch that range to heapsort. That guarantees O(n log n) worst case. This is what C#'s Array.Sort and C++'s std::sort do.
import random

def quick_sort(a: list[int]) -> None:
    def partition(lo: int, hi: int) -> int:     # Hoare; a[lo..j] <= pivot <= a[j+1..hi]
        p = random.randint(lo, hi)
        a[lo], a[p] = a[p], a[lo]               # pivot value at the front, never at hi
        pivot, i, j = a[lo], lo - 1, hi + 1
        while True:
            i += 1
            while a[i] < pivot:
                i += 1
            j -= 1
            while a[j] > pivot:
                j -= 1
            if i >= j:
                return j
            a[i], a[j] = a[j], a[i]

    def sort(lo: int, hi: int) -> None:         # inclusive bounds
        while hi - lo >= 16:
            j = partition(lo, hi)
            if j - lo < hi - j:                 # recurse into the smaller side,
                sort(lo, j)                     # loop on the larger: O(log n) stack
                lo = j + 1
            else:
                sort(j + 1, hi)
                hi = j
        for k in range(lo + 1, hi + 1):         # small range: insertion sort
            key, m = a[k], k - 1
            while m >= lo and a[m] > key:
                a[m + 1] = a[m]
                m -= 1
            a[m + 1] = key

    sort(0, len(a) - 1)

public static void QuickSort(int[] a)
{
    Sort(0, a.Length - 1);

    int Partition(int lo, int hi)               // Hoare; a[lo..j] <= pivot <= a[j+1..hi]
    {
        int p = Random.Shared.Next(lo, hi + 1);
        (a[lo], a[p]) = (a[p], a[lo]);          // pivot value at the front, never at hi
        int pivot = a[lo], i = lo - 1, j = hi + 1;
        while (true)
        {
            do i++; while (a[i] < pivot);
            do j--; while (a[j] > pivot);
            if (i >= j) return j;
            (a[i], a[j]) = (a[j], a[i]);
        }
    }

    void Sort(int lo, int hi)                   // inclusive bounds
    {
        while (hi - lo >= 16)
        {
            int j = Partition(lo, hi);
            if (j - lo < hi - j) { Sort(lo, j); lo = j + 1; }   // smaller side recursively
            else { Sort(j + 1, hi); hi = j; }
        }
        for (int k = lo + 1; k <= hi; k++)      // small range: insertion sort
        {
            int key = a[k], m = k - 1;
            while (m >= lo && a[m] > key) { a[m + 1] = a[m]; m--; }
            a[m + 1] = key;
        }
    }
}

Tip: three-way quicksort for heavy duplicates If the input has only a handful of distinct values (say, 10⁶ values in 0..9), split into < pivot | = pivot | > pivot with the Dutch national flag partition from Two Pointers. The whole = block is final in one pass and never recursed into. The quickselect template later on this page uses exactly that partition.

Heapsort: a sorted array grown from a heap

Heapsort treats the array as a complete binary tree: the children of index i are 2i + 1 and 2i + 2. First it heapifies the array into a max-heap (every parent ≥ its children) by sifting down every internal node, bottom-up. Then it repeats: swap the root (the maximum) with the last heap cell, shrink the heap by one, and sift the new root down. The sorted region grows from the right.

Heapsort is the only one of the three O(n log n) classics that is both in place and O(n log n) in the worst case, which is why introsort uses it as its safety net. In practice it is slower than quicksort, because sift-down jumps around memory (index i to 2i) and defeats the cache, and it is not stable. The heap itself is far more useful than heapsort: see Heaps and Priority Queues for top-k, k-way merge and scheduling.

def heap_sort(a: list[int]) -> None:
    def sift_down(i: int, size: int) -> None:
        while (c := 2 * i + 1) < size:
            if c + 1 < size and a[c + 1] > a[c]:
                c += 1                          # the bigger child
            if a[i] >= a[c]:
                return                          # heap property holds
            a[i], a[c] = a[c], a[i]
            i = c

    n = len(a)
    for i in range(n // 2 - 1, -1, -1):         # heapify: O(n) total
        sift_down(i, n)
    for end in range(n - 1, 0, -1):
        a[0], a[end] = a[end], a[0]             # max goes to its final slot
        sift_down(0, end)

public static void HeapSort(int[] a)
{
    int n = a.Length;
    for (int i = n / 2 - 1; i >= 0; i--) SiftDown(i, n);   // heapify: O(n) total
    for (int end = n - 1; end > 0; end--)
    {
        (a[0], a[end]) = (a[end], a[0]);                    // max goes to its final slot
        SiftDown(0, end);
    }

    void SiftDown(int i, int size)
    {
        int c;
        while ((c = 2 * i + 1) < size)
        {
            if (c + 1 < size && a[c + 1] > a[c]) c++;       // the bigger child
            if (a[i] >= a[c]) return;                       // heap property holds
            (a[i], a[c]) = (a[c], a[i]);
            i = c;
        }
    }
}

Insight: why heapify is O(n), not O(n log n) Half the nodes are leaves and never move. A quarter sit one level up and sift at most 1 step, an eighth at most 2 steps, and so on. The total is n·(1/4 + 2/8 + 3/16 + …) = n. Building a heap from an unsorted array is linear; it is the n extractions that cost n log n.

Stability: do equal keys keep their order?

A sort is stable if values with equal keys come out in the same relative order they went in. With plain integers you cannot tell the difference. It matters as soon as records carry more than the key: sort orders by date after sorting them by customer, and a stable sort keeps each day's orders grouped by customer.

The visualizer gives each key a subscript showing where it appeared in the input (3a is the first 3, 3b the second). Run each algorithm on the same keys and read the final row: the stable ones keep a before b before c inside every group of equal keys.

Where instability comes from:

  • Selection sort swaps the minimum over a long distance and can jump it past an equal key: [2a, 2b, 1] swaps 2a with 1 and gives [1, 2b, 2a].
  • Heapsort scrambles everything into heap order first.
  • Quicksort partitions swap values over long distances.
  • Insertion sort and merge sort are stable only because of one character: insertion uses a[j] > key (strict), merge takes the left head on <=. Flip either and they become unstable.

Know your library. Python's list.sort and sorted are always stable. C#'s Array.Sort and List<T>.Sort are not (they are introsort). LINQ's OrderBy/ThenBy are stable. Java sorts objects stably (TimSort) but primitives with dual-pivot quicksort, where stability is meaningless anyway. C++ has std::sort (unstable) and std::stable_sort.

How fast can sorting be? The n log n wall

Every algorithm so far learns about the input only by comparing two values. That model has a hard limit, and the argument is short enough to remember.

Picture the algorithm as a decision tree: each comparison is a node with two outcomes (yes/no), and each leaf is a final answer, one particular reordering. All n! orderings of distinct values need different reorderings, so the tree needs at least n! leaves. A binary tree of height h has at most 2ʰ leaves, so h ≥ log₂(n!). By Stirling, log₂(n!) ≈ n log₂ n − 1.44 n. Some input must therefore cost about n log₂ n comparisons: merge sort and heapsort are optimal up to constant factors.

The same argument gives other useful bounds: checking whether all values are distinct needs Ω(n log n) comparisons too (in this model), which is why the O(n) answer to "contains duplicate" uses a hash set, which is not a comparison. And merging k sorted lists of total size n needs Ω(n log k).

The way to beat n log n is to stop comparing.

Beating n log n: counting, radix and bucket sort

These sorts look inside the keys. They are not general purpose, but when they apply they run in linear time, and their ideas (histograms, prefix sums, buckets by value) power a large family of interview problems.

Counting sort

If the keys are integers in a small range 0..k−1, count how many of each there are. A prefix sum over the counts (see Prefix Sums) then tells each key where its block ends. Walk the input from the back and drop each value into the last free slot of its block: walking backwards is what keeps equal keys in input order, so the sort is stable.

def counting_sort(a: list[int], k: int) -> list[int]:
    """Stable sort of values in 0..k-1. O(n + k) time and space."""
    count = [0] * k
    for v in a:
        count[v] += 1                     # histogram
    for v in range(1, k):
        count[v] += count[v - 1]          # count[v] = how many values are <= v = end of v's block
    out = [0] * len(a)
    for v in reversed(a):                 # from the back: equal values keep their order
        count[v] -= 1
        out[count[v]] = v
    return out

public static int[] CountingSort(int[] a, int k)
{
    var count = new int[k];
    foreach (int v in a) count[v]++;                    // histogram
    for (int v = 1; v < k; v++) count[v] += count[v - 1]; // end of v's block
    var output = new int[a.Length];
    for (int i = a.Length - 1; i >= 0; i--)             // from the back: stable
        output[--count[a[i]]] = a[i];
    return output;
}

When the values are bare integers with nothing attached, you can skip the prefix sums and just write each value count[v] times. The prefix-sum version is the one that sorts records by a key, and it is the engine inside radix sort.

Radix sort

What if the keys are large, say up to 10⁹? Split each key into digits and run one stable counting sort per digit, starting from the least significant. After pass d, the keys are sorted by their last d digits; stability guarantees that ties on the current digit keep the order from the previous passes. The padded zeros in the visualizer are the digits that a short number "has" for free.

The cost is O(d · (n + b)) for d digits in base b. Real implementations use base 256 (one byte per pass), so 32-bit keys take 4 linear passes. That beats O(n log n) once n is large, and it is how GPUs and some databases sort integers.

def radix_sort(a: list[int]) -> list[int]:
    """LSD radix sort for non-negative ints, one stable pass per byte."""
    a, shift, big = list(a), 0, max(a, default=0)
    while big >> shift:
        start = [0] * 257
        for v in a:
            start[((v >> shift) & 255) + 1] += 1
        for d in range(256):
            start[d + 1] += start[d]      # start[d] = first slot of digit d's block
        out = [0] * len(a)
        for v in a:                       # forward walk + start slots = stable
            d = (v >> shift) & 255
            out[start[d]] = v
            start[d] += 1
        a, shift = out, shift + 8
    return a

public static int[] RadixSort(int[] input)
{
    var a = (int[])input.Clone();
    int big = a.Length == 0 ? 0 : a.Max();
    for (int shift = 0; shift < 32 && (big >> shift) > 0; shift += 8)
    {
        var start = new int[257];
        foreach (int v in a) start[((v >> shift) & 255) + 1]++;
        for (int d = 0; d < 256; d++) start[d + 1] += start[d];   // first slot of each digit
        var output = new int[a.Length];
        foreach (int v in a) output[start[(v >> shift) & 255]++] = v;  // stable
        a = output;
    }
    return a;
}

Tip: negative numbers and other keys For signed integers, add an offset (v − min) first or flip the sign bit, so negatives sort below positives. Strings of equal length sort with LSD radix too (one pass per character from the right). Variable-length strings use MSD radix (most significant first, recursing into buckets), which is a close cousin of a trie.

Bucket sort

Bucket sort splits the range of values into m equal buckets, drops each value into its bucket, sorts each bucket (insertion sort is fine, they are small), and concatenates them.

Bucket thinking shows up far more often in problems than bucket sort itself: "Top K Frequent Elements" buckets values by frequency (index = count, at most n), "Maximum Gap" uses buckets to prove where the answer must be, and "Contains Duplicate III" uses buckets of width t + 1 so that any close pair is in the same or an adjacent bucket.

Sort Time Extra space Use it when
Counting O(n + k) O(n + k) Integer keys in a small range k (ages, grades, letters, colours)
Radix (LSD) O(d · (n + b)) O(n + b) Many fixed-width integer or string keys
Bucket O(n) expected O(n + m) Keys spread roughly uniformly over a known range

Sorting in practice: built-ins, keys and comparators

In real code and in interviews you call the library sort. What you must know is what it guarantees and how to tell it what "in order" means.

Language Call Algorithm Stable?

Keys versus comparators

There are two ways to describe an order:

  • A key function maps each item to something that already sorts the way you want, usually a tuple: (−age, name). Python calls the key once per item, so it is fast. This is the idiomatic Python way.
  • A comparator takes two items and returns negative (first goes first), zero (tie) or positive. It can express orders that no simple key can, like Largest Number below. C# Comparison<T>, Java Comparator and Python's functools.cmp_to_key all work this way.

Here is one order (age descending, then name ascending) written every useful way:

from functools import cmp_to_key

people = [("ann", 31), ("bob", 25), ("cat", 31), ("dan", 25), ("eve", 40)]

# 1. Tuple key. Negate numbers to reverse just that field.
by_key = sorted(people, key=lambda p: (-p[1], p[0]))

# 2. Two stable passes, least important key first.
#    reverse=True still keeps ties in their current order.
two_pass = sorted(people, key=lambda p: p[0])
two_pass.sort(key=lambda p: p[1], reverse=True)

# 3. Comparator: negative means p goes first.
def cmp(p, q):
    if p[1] != q[1]:
        return q[1] - p[1]                    # fine in Python: ints never overflow
    return (p[0] > q[0]) - (p[0] < q[0])      # three-way compare of strings
by_cmp = sorted(people, key=cmp_to_key(cmp))

assert by_key == two_pass == by_cmp == [
    ("eve", 40), ("ann", 31), ("cat", 31), ("bob", 25), ("dan", 25)]

var people = new List<(string Name, int Age)>

Pitfall: the subtraction comparator (a, b) => a - b overflows for large values: int.MinValue - 1 wraps to int.MaxValue, so a very small number compares as larger. In C# and Java use a.CompareTo(b) / Integer.compare(a, b). Python ints do not overflow, so a - b is safe there.

Pitfall: comparators that are not a total order A comparator must be consistent: if a < b and b < c then a < c, and cmp(a, b) must be the negation of cmp(b, a). Random or "approximately equal" comparators (|a − b| < ε counts as equal) break this. Java then throws "Comparison method violates its general contract", C# may throw InvalidOperationException or silently mis-sort, and binary search on the result is undefined.

Argsort: sorting positions instead of values

Often you need the sorted order and where each value came from: the original index, a second array that must move together with the first, or each value's rank. Sort the indices by value, or sort (value, index) pairs.

nums = [30, 10, 20, 10]
order = sorted(range(len(nums)), key=lambda i: nums[i])   # [1, 3, 2, 0]: stable, so 1 before 3
pairs = sorted((v, i) for i, v in enumerate(nums))        # [(10, 1), (10, 3), (20, 2), (30, 0)]
rank = {v: r for r, v in enumerate(sorted(set(nums)))}    # {10: 0, 20: 1, 30: 2}: compression

int[] nums = { 30, 10, 20, 10 };
int[] order = Enumerable.Range(0, nums.Length)
                        .OrderBy(i => nums[i]).ToArray();  // [1, 3, 2, 0]: stable
var keys = (int[])nums.Clone();
var idx = Enumerable.Range(0, nums.Length).ToArray();
Array.Sort(keys, idx);                                     // sorts keys, moves idx along (unstable)
var rank = nums.Distinct().Order()
               .Select((v, r) => (v, r)).ToDictionary(t => t.v, t => t.r);

The rank map is coordinate compression: it maps up to 10⁵ values spread over ±10⁹ onto 0..m−1, so they can index an array or a Fenwick tree. Hashing Patterns covers it in more depth.

Quickselect: the k-th element without sorting everything

To find the median or the k-th smallest value you do not need the whole array sorted. Partition once around a pivot: the pivot lands at its final index p. If k is left of p, the answer is in the left side; if right, in the right side. Throw the other side away and repeat. Unlike quicksort you recurse into one side only.

Each round keeps only one side, and a random pivot discards a constant fraction of the range on average, so the total work is a geometric series: n + n/2 + n/4 + … ≈ 2n with perfect pivots, and about 3.4n comparisons in expectation with random ones. That is O(n) expected. The worst case is still O(n²); the median-of-medians pivot rule fixes that in theory at a large constant factor. The template below uses a three-way partition so arrays full of duplicates do not degrade it.

import random

def kth_smallest(a: list[int], k: int) -> int:
    """k is 1-based. Expected O(n). Rearranges a."""
    lo, hi, target = 0, len(a) - 1, k - 1
    while True:
        pivot = a[random.randint(lo, hi)]
        lt, i, gt = lo, lo, hi        # a[lo:lt] < pivot, a[lt:i] == pivot, a[gt+1:hi+1] > pivot
        while i <= gt:
            if a[i] < pivot:
                a[lt], a[i] = a[i], a[lt]
                lt += 1
                i += 1
            elif a[i] > pivot:
                a[gt], a[i] = a[i], a[gt]
                gt -= 1               # the value swapped in is unseen: do not advance i
            else:
                i += 1
        if target < lt:
            hi = lt - 1               # answer is in the < block
        elif target > gt:
            lo = gt + 1               # answer is in the > block
        else:
            return pivot              # target index falls inside the == block

public static int KthSmallest(int[] a, int k)    // k is 1-based; rearranges a
{
    int lo = 0, hi = a.Length - 1, target = k - 1;
    while (true)
    {
        int pivot = a[Random.Shared.Next(lo, hi + 1)];
        int lt = lo, i = lo, gt = hi;
        while (i <= gt)
        {
            if (a[i] < pivot) { (a[lt], a[i]) = (a[i], a[lt]); lt++; i++; }
            else if (a[i] > pivot) { (a[gt], a[i]) = (a[i], a[gt]); gt--; }
            else i++;
        }
        if (target < lt) hi = lt - 1;
        else if (target > gt) lo = gt + 1;
        else return pivot;
    }
}

Pattern: sort, then sweep

The most common use of sorting in problems: sort by one coordinate, then make one pass that only ever compares the current item with what it has accumulated so far. Sorting is what makes the local decision correct. For intervals, after sorting by start, an interval can only overlap the last merged block: everything earlier ends before that block starts.

The same sort-then-sweep shape solves Meeting Rooms (any overlap at all?), Insert Interval, Interval List Intersections, Minimum Arrows, the skyline (with a heap), and "Car Fleet" below. The full treatment, including sweep lines with events (+1 at a start, −1 at an end), is in Intervals and Sweep Line.

Pattern: sort to unlock a greedy choice

Many optimization problems have a simple greedy solution once the input is in the right order, and no simple solution otherwise. The skill is choosing the sort key, and the proof is usually an exchange argument: take any optimal answer, swap its first choice for the greedy one, and show it is still valid and no worse.

Non-overlapping Intervals / activity selection end keep each interval that starts after the last kept end

Choosing the wrong key is the classic mistake: for activity selection, sorting by start or by length both fail on small counterexamples. More on proving greedy choices in Greedy.

Pattern: cyclic sort for values 1..n

When an array of length n holds values that should be 1..n (with some missing, duplicated or out of range), every value has a home: index v − 1. Walk the array and keep swapping the current value to its home until the current slot holds something that cannot move (already home, out of range, or a duplicate whose home is taken). Each swap puts one value home for good, so there are at most n swaps: O(n) time, O(1) space, and afterwards any slot i with nums[i] != i + 1 tells you i + 1 is missing.

def find_missing(nums: list[int]) -> list[int]:
    """Values should be 1..n. Returns the absent ones. O(n) time, O(1) extra."""
    i, n = 0, len(nums)
    while i < n:
        v = nums[i]
        if 1 <= v <= n and nums[v - 1] != v:   # v has a home, and the home is not taken by a v
            nums[i], nums[v - 1] = nums[v - 1], v
        else:
            i += 1                             # slot i is settled for now
    return [i + 1 for i in range(n) if nums[i] != i + 1]

public static List<int> FindMissing(int[] nums)
{
    int i = 0, n = nums.Length;
    while (i < n)
    {
        int v = nums[i];
        if (v >= 1 && v <= n && nums[v - 1] != v)
            (nums[i], nums[v - 1]) = (nums[v - 1], v);
        else i++;
    }
    var missing = new List<int>();
    for (int j = 0; j < n; j++)
        if (nums[j] != j + 1) missing.Add(j + 1);
    return missing;
}

After the placement loop, the same scan answers the whole family: the misplaced values at those slots are the duplicates (Find All Duplicates), the first bad slot is the first missing positive, and Set Mismatch is one of each.

Pitfall: Python's left-to-right tuple assignment nums[i], nums[nums[i] - 1] = nums[nums[i] - 1], nums[i] looks like a swap, but Python assigns nums[i] first, so the second target nums[nums[i] - 1] is computed from the new nums[i] and the value lands in the wrong slot. Read the value into a local (v = nums[i]) and index with v, as the template does. Do the same in C#: a local makes the swap obviously correct in any language.

Pattern: counting inversions with merge sort

Counting pairs i < j with a[i] > a[j] by brute force takes O(n²). Merge sort does it in O(n log n). The inversions inside each half are counted by the recursion; the merge only counts pairs with one value in each half. When the merge takes a value from the right half, that value is smaller than every value still waiting on the left, and all of those were earlier in the array. So it adds mid − i inversions in one step.

def count_inversions(a: list[int]) -> int:
    a, buf = a[:], a[:]                         # work on a copy

    def sort(lo: int, hi: int) -> int:          # sorts a[lo:hi], returns inversions inside it
        if hi - lo <= 1:
            return 0
        mid = (lo + hi) // 2
        inv = sort(lo, mid) + sort(mid, hi)
        buf[lo:hi] = a[lo:hi]
        i, j = lo, mid
        for k in range(lo, hi):
            if j >= hi or (i < mid and buf[i] <= buf[j]):
                a[k] = buf[i]
                i += 1
            else:
                inv += mid - i                  # buf[j] beats every remaining left value
                a[k] = buf[j]
                j += 1
        return inv

    return sort(0, len(a))

public static long CountInversions(int[] input)
{
    var a = (int[])input.Clone();
    var buf = new int[a.Length];
    return Sort(0, a.Length);

    long Sort(int lo, int hi)                    // up to n(n-1)/2: needs long
    {
        if (hi - lo <= 1) return 0;
        int mid = lo + (hi - lo) / 2;
        long inv = Sort(lo, mid) + Sort(mid, hi);
        Array.Copy(a, lo, buf, lo, hi - lo);
        int i = lo, j = mid;
        for (int k = lo; k < hi; k++)
        {
            if (j >= hi || (i < mid && buf[i] <= buf[j])) a[k] = buf[i++];
            else { inv += mid - i; a[k] = buf[j++]; }
        }
        return inv;
    }
}

The family that uses this trick: Count of Smaller Numbers After Self (sort indices, credit each left value with the number of right values taken before it), Reverse Pairs (a[i] > 2·a[j], counted with a separate pointer pass before each merge), Count of Range Sum (merge sort over prefix sums) and Global and Local Inversions. All of them also have a Fenwick tree solution over compressed values; merge sort needs no extra structure.

Recognize it when

  • The answer does not depend on input order: pairs, groups, closest values, overlapping intervals, "can these be arranged".
  • You see intervals, meetings, events, deadlines: sort by start or by end, then sweep.
  • The problem asks for the k-th something, a median, or the top k: quickselect, heap or bucket.
  • Values are in 1..n (or 0..n) in an array of length n, and the problem wants O(1) space: cyclic sort.
  • You must count pairs i < j with a condition on a[i] versus a[j] (inversions, smaller after self, reverse pairs): merge sort, or a Fenwick tree.
  • Keys are small integers (grades, ages, colours, letters): counting sort beats n log n.
  • A greedy idea almost works but fails on some order of the input: try sorting first and look for an exchange argument.

When it does not work

  • The original order is the point. Subarray and substring problems (max subarray, sliding windows, "subarray sum equals k") lose their meaning after sorting. Reach for Prefix Sums, Sliding Window or a hash map.
  • You need original indices back. Sorting the bare values loses them. Sort (value, index) pairs, or use a hash map (Two Sum is O(n) with one).
  • O(n) is required and keys are general. A comparison sort cannot meet an O(n) bound. Use hashing (duplicates, frequency), counting/bucket sort (small ranges), or a heap of size k.
  • The data keeps changing. Re-sorting after every insert costs O(n log n) per update. Keep a heap, a balanced BST (SortedList/SortedSet, sortedcontainers.SortedList) or a Fenwick tree.

Pitfall: sorted() versus .sort() Python's a.sort() sorts in place and returns None, so a = a.sort() throws your list away. sorted(a) returns a new list. In C#, Array.Sort and List.Sort are in place, while LINQ's OrderBy returns a new lazy sequence: nothing is sorted until you enumerate it, and list.OrderBy(...) on its own line does nothing at all.

Pitfall: relying on stability you do not have Sorting by name and then calling List<T>.Sort by age in C# does not keep names in order within each age, because List.Sort is unstable. Either sort once with a full comparator (age, then name), or use OrderBy(...).ThenBy(...).

Pitfall: sorting inside a loop Sorting a growing list on every iteration turns an O(n log n) idea into O(n² log n). If you need "the smallest so far" repeatedly, you need a heap; if you need order statistics over a changing set, you need a sorted container.

Pitfall: string order is not numeric order sorted(["10", "9", "100"]) gives ["10", "100", "9"]. Convert to numbers first, or sort by (len(s), s) for non-negative integer strings without leading zeros. In C#, culture-aware string.Compare also differs from ordinal order ("a" < "B" in most cultures but not ordinally); use StringComparer.Ordinal in algorithmic code.

Worked problems

1. Merge Intervals

Merge all overlapping intervals. Insight: sort by start; then an interval can only overlap the last merged block, because every earlier block ends before that block starts. This is the sweep visualizer above. Note <=: [1, 4] and [4, 5] touch, and LeetCode counts that as overlapping.

Solution: O(n log n) time, O(n) output 
def merge(intervals: list[list[int]]) -> list[list[int]]:
    intervals.sort(key=lambda iv: iv[0])
    out: list[list[int]] = []
    for s, e in intervals:
        if out and s <= out[-1][1]:               # overlaps (or touches) the last block
            out[-1][1] = max(out[-1][1], e)       # extend; e may be inside the block
        else:
            out.append([s, e])
    return out

public static int[][] Merge(int[][] intervals)
{
    Array.Sort(intervals, (x, y) => x[0].CompareTo(y[0]));
    var output = new List<int[]>();
    foreach (var iv in intervals)
    {
        if (output.Count > 0 && iv[0] <= output[^1][1])
            output[^1][1] = Math.Max(output[^1][1], iv[1]);
        else
            output.Add(new[] { iv[0], iv[1] });
    }
    return output.ToArray();
}

2. Kth Largest Element in an Array

Insight: the k-th largest is the (n − k + 1)-th smallest, so quickselect finds it in O(n) expected. If the values arrive as a stream, or you are told not to modify the array, keep a min-heap of size k instead: its root is the k-th largest seen so far. Both are shown; reach for the heap first in an interview unless O(n) is asked for.

Solution: O(n) expected (quickselect) or O(n log k) (heap) 
import heapq

def find_kth_largest(nums: list[int], k: int) -> int:
    return kth_smallest(nums, len(nums) - k + 1)   # quickselect template from above

def find_kth_largest_heap(nums: list[int], k: int) -> int:
    heap: list[int] = []
    for v in nums:
        heapq.heappush(heap, v)
        if len(heap) > k:
            heapq.heappop(heap)                     # drop the smallest: it can't be in the top k
    return heap[0]

public static int FindKthLargest(int[] nums, int k) =>
    KthSmallest(nums, nums.Length - k + 1);          // quickselect template from above

public static int FindKthLargestHeap(int[] nums, int k)
{
    var heap = new PriorityQueue<int, int>();         // min-heap by priority
    foreach (int v in nums)
    {
        heap.Enqueue(v, v);
        if (heap.Count > k) heap.Dequeue();           // drop the smallest
    }
    return heap.Peek();
}

3. Largest Number

Arrange non-negative integers to form the largest number, e.g. [3, 30, 34, 5, 9] → "9534330". Insight: neither numeric nor plain string order works ("3" vs "30": string order puts 30 last but 330 > 303). The right order compares concatenations: put x before y when x + y > y + x.

Solution: O(n log n) comparisons of O(digits) each 
from functools import cmp_to_key

def largest_number(nums: list[int]) -> str:
    s = [str(x) for x in nums]
    # negative = x first; x goes first when x + y is the bigger concatenation
    s.sort(key=cmp_to_key(lambda x, y: (y + x > x + y) - (y + x < x + y)))
    res = "".join(s)
    return "0" if res[0] == "0" else res          # [0, 0] must give "0", not "00"

public static string LargestNumber(int[] nums)
{
    var s = nums.Select(x => x.ToString()).ToArray();
    Array.Sort(s, (x, y) => string.CompareOrdinal(y + x, x + y));
    var res = string.Concat(s);
    return res[0] == '0' ? "0" : res;
}

4. Non-overlapping Intervals

Remove the minimum number of intervals so the rest do not overlap. Insight: this is "keep the maximum number of non-overlapping intervals". Sort by end; always keep the interval that finishes first, because it leaves the most room for everything else (the exchange argument in the greedy figure). Here touching ([1, 2], [2, 3]) is allowed, so the test is s >= end.

Solution: O(n log n) time, O(1) extra 
def erase_overlap_intervals(intervals: list[list[int]]) -> int:
    intervals.sort(key=lambda iv: iv[1])          # by END
    kept, end = 0, float("-inf")
    for s, e in intervals:
        if s >= end:                              # fits after the last kept interval
            kept += 1
            end = e
    return len(intervals) - kept

public static int EraseOverlapIntervals(int[][] intervals)
{
    Array.Sort(intervals, (x, y) => x[1].CompareTo(y[1]));   // by END
    int kept = 0;
    long end = long.MinValue;
    foreach (var iv in intervals)
        if (iv[0] >= end) { kept++; end = iv[1]; }
    return intervals.Length - kept;
}

5. First Missing Positive

Find the smallest missing positive integer in O(n) time and O(1) extra space. Insight: the answer is in 1..n + 1 (n slots can hold at most 1..n). That makes it a cyclic-sort problem: send every value in 1..n home to index v − 1, ignore the rest, then the first slot that does not hold i + 1 is the answer. Step through it in the cyclic sort visualizer above.

Solution: O(n) time, O(1) extra 
def first_missing_positive(nums: list[int]) -> int:
    n = len(nums)
    for i in range(n):
        while 1 <= nums[i] <= n and nums[nums[i] - 1] != nums[i]:
            v = nums[i]                           # local first: see the swap pitfall
            nums[i], nums[v - 1] = nums[v - 1], v
    for i in range(n):
        if nums[i] != i + 1:
            return i + 1
    return n + 1

public static int FirstMissingPositive(int[] nums)
{
    int n = nums.Length;
    for (int i = 0; i < n; i++)
        while (nums[i] >= 1 && nums[i] <= n && nums[nums[i] - 1] != nums[i])
        {
            int v = nums[i];
            (nums[i], nums[v - 1]) = (nums[v - 1], v);
        }
    for (int i = 0; i < n; i++)
        if (nums[i] != i + 1) return i + 1;
    return n + 1;
}

6. Car Fleet

Cars drive toward target; a faster car that catches a slower one joins its fleet. Count the fleets that arrive. Insight: sort cars by position, closest to the target first. Each car's solo arrival time is (target − p) / s. Walking backwards from the target, a car forms a new fleet only if it would arrive later than the slowest fleet ahead of it; otherwise it catches up and merges. This is sort-then-sweep with a running maximum.

Solution: O(n log n) time, O(n) for the sort 
def car_fleet(target: int, position: list[int], speed: list[int]) -> int:
    fleets, slowest = 0, 0.0
    for p, s in sorted(zip(position, speed), reverse=True):   # closest to target first
        t = (target - p) / s
        if t > slowest:                       # cannot catch the fleet ahead: new fleet
            fleets += 1
            slowest = t
    return fleets

public static int CarFleet(int target, int[] position, int[] speed)
{
    var order = Enumerable.Range(0, position.Length).ToArray();
    Array.Sort(order, (i, j) => position[j].CompareTo(position[i]));  // closest first
    int fleets = 0;
    double slowest = 0;
    foreach (int i in order)
    {
        double t = (double)(target - position[i]) / speed[i];
        if (t > slowest) { fleets++; slowest = t; }
    }
    return fleets;
}

7. Count of Smaller Numbers After Self

For each nums[i], count the values to its right that are smaller. Insight: this is inversion counting, but per element. Merge sort an array of indices by value. When the merge takes a left element, every right element already taken (j − mid of them) is smaller and was originally to its right, so credit that many to the left element. Ties go left, so equal values are not counted.

Solution: O(n log n) time, O(n) space 
def count_smaller(nums: list[int]) -> list[int]:
    n = len(nums)
    res, idx = [0] * n, list(range(n))
    buf = idx[:]

    def sort(lo: int, hi: int) -> None:
        if hi - lo <= 1:
            return
        mid = (lo + hi) // 2
        sort(lo, mid)
        sort(mid, hi)
        buf[lo:hi] = idx[lo:hi]
        i, j = lo, mid
        for k in range(lo, hi):
            if j >= hi or (i < mid and nums[buf[i]] <= nums[buf[j]]):
                res[buf[i]] += j - mid            # right values already taken are smaller
                idx[k] = buf[i]
                i += 1
            else:
                idx[k] = buf[j]
                j += 1

    sort(0, n)
    return res

public static IList<int> CountSmaller(int[] nums)
{
    int n = nums.Length;
    var res = new int[n];
    var idx = Enumerable.Range(0, n).ToArray();
    var buf = new int[n];
    Sort(0, n);
    return res;

    void Sort(int lo, int hi)
    {
        if (hi - lo <= 1) return;
        int mid = lo + (hi - lo) / 2;
        Sort(lo, mid);
        Sort(mid, hi);
        Array.Copy(idx, lo, buf, lo, hi - lo);
        int i = lo, j = mid;
        for (int k = lo; k < hi; k++)
        {
            if (j >= hi || (i < mid && nums[buf[i]] <= nums[buf[j]]))
            {
                res[buf[i]] += j - mid;
                idx[k] = buf[i++];
            }
            else idx[k] = buf[j++];
        }
    }
}

8. Maximum Gap

Return the largest difference between neighbours in sorted order, in O(n) time. Insight: pigeonhole. With n values spanning lo..hi, the average gap is (hi − lo) / (n − 1), so the maximum gap is at least that. Make buckets of width size = max(1, (hi − lo) // (n − 1)), which is no larger than the average gap. Two values in the same bucket differ by less than size, so the maximum gap can never be inside a bucket. It is always between the max of one non-empty bucket and the min of the next. Keep only each bucket's min and max.

Solution: O(n) time, O(n) space 
def maximum_gap(nums: list[int]) -> int:
    n = len(nums)
    if n < 2:
        return 0
    lo, hi = min(nums), max(nums)
    if lo == hi:
        return 0
    size = max(1, (hi - lo) // (n - 1))
    m = (hi - lo) // size + 1
    bmin: list[int | None] = [None] * m
    bmax: list[int | None] = [None] * m
    for v in nums:
        b = (v - lo) // size
        bmin[b] = v if bmin[b] is None else min(bmin[b], v)
        bmax[b] = v if bmax[b] is None else max(bmax[b], v)
    best, prev = 0, lo
    for b in range(m):
        if bmin[b] is not None:                 # skip empty buckets
            best = max(best, bmin[b] - prev)    # gap from the previous non-empty bucket
            prev = bmax[b]
    return best

public static int MaximumGap(int[] nums)
{
    int n = nums.Length;
    if (n < 2) return 0;
    int lo = nums.Min(), hi = nums.Max();
    if (lo == hi) return 0;
    int size = Math.Max(1, (hi - lo) / (n - 1));
    int m = (hi - lo) / size + 1;
    var bmin = new int[m];
    var bmax = new int[m];
    var used = new bool[m];
    Array.Fill(bmin, int.MaxValue);
    Array.Fill(bmax, int.MinValue);
    foreach (int v in nums)
    {
        int b = (v - lo) / size;
        used[b] = true;
        bmin[b] = Math.Min(bmin[b], v);
        bmax[b] = Math.Max(bmax[b], v);
    }
    int best = 0, prev = lo;
    for (int b = 0; b < m; b++)
    {
        if (!used[b]) continue;
        best = Math.Max(best, bmin[b] - prev);
        prev = bmax[b];
    }
    return best;
}

Self-check

Why does every library sort switch to insertion sort for small ranges?

On a handful of values the O(n²) term is tiny, and insertion sort has the lowest overhead of any sort: no recursion, no buffer, sequential memory access, and one shift per inversion. Below roughly 16 to 32 elements it beats quicksort and merge sort in practice.

Selection sort runs on [2a, 2b, 1]. Is the result stable?

No. The first pass finds the minimum 1 and swaps it with 2a, giving [1, 2b, 2a]. The long-distance swap jumped 2a over its equal twin 2b. Insertion sort on the same input gives [1, 2a, 2b].

Quicksort with "last element" pivots is given an already sorted array. What happens, and what are two fixes?

Each pivot is the maximum of its range, so every partition is n − 1 versus 0. The recursion depth is n and the comparisons total n(n − 1)/2: O(n²), and possibly a stack overflow. Fixes: pick a random pivot (or median-of-3), and/or fall back to heapsort past a depth limit (introsort). Recursing on the smaller side caps the stack at O(log n) either way.

You need to sort records by age, keeping the existing name order for equal ages, in C#. What do you call?

records.OrderBy(r => r.Age), which is stable, or one List.Sort with a comparator that breaks ties by name explicitly. Calling List.Sort by age alone is not enough: it is introsort and may reorder equal ages.

The lower bound says sorting needs Ω(n log n). How does counting sort run in O(n + k)?

The bound only covers algorithms that learn about the input by comparing pairs. Counting sort never compares two values: it uses each value directly as an array index, which extracts far more than one bit of information per step. The price is that it only works for integer keys in a small range.

Why does LSD radix sort need each pass to be stable?

After sorting by the last digit, the order inside each group of equal next digits must be preserved so that ties on the current digit are still sorted by the digits already processed. An unstable pass would scramble that and the final order would only be sorted by the most significant digit.

Why is quickselect O(n) on average when quicksort is O(n log n)?

Quicksort recurses into both sides, so every level of the recursion tree costs n in total. Quickselect keeps only one side, so the sizes shrink geometrically: n + n/2 + n/4 + … ≤ 2n with good pivots (and still a constant multiple of n in expectation with random ones).

Sorting intervals by start works for Merge Intervals. Why does Non-overlapping Intervals sort by end instead?

Merging needs to know whether the next interval touches what is already merged, and sorting by start guarantees it can only touch the last block. Non-overlapping Intervals is a selection problem: the interval that ends first leaves the most room, and the exchange argument proves keeping it is safe. By start, a long early interval like [1, 100] would be kept and block everything.

When should you not sort?

When the original order is part of the question (subarrays, substrings, windows), when you must return original indices and cannot carry them, when O(n) is required for general keys (use a hash map instead), and when the data changes between queries (use a heap or a sorted container).

DefaultLibrary sort, O(n log n). Python: stable Timsort. C#: unstable introsort; LINQ OrderBy is stable.
Insertion sortShift, don't swap. O(n + inversions): best for tiny or nearly-sorted data.
Merge sortSplit, recurse, merge with <= (stable). Always n log n, O(n) buffer.
QuicksortRandom pivot; Lomuto → recurse [lo, p−1], [p+1, hi]; Hoare → [lo, j], [j+1, hi].
HeapsortHeapify O(n), then n × (swap root to end, sift down). In place, worst-case n log n.
Lower boundComparisons need log₂ n! ≈ n log n. Beat it only by not comparing.
Counting / radixHistogram → prefix sums → place from the back. Radix = stable pass per digit, LSD first.
ComparatorsTuple keys; CompareTo, never a − b; must be a consistent total order.
