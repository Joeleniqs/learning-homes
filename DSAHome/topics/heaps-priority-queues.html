Heaps & Priority Queues

Sift-up/sift-down animated on tree and array views; top-K, two-heaps median, k-way merge and greedy scheduling.

Intermediate → Advanced~55 min studyUpdated 2026-11-03

What a heap is for

A priority queue answers one question fast, again and again: which item is the best right now? "Best" means smallest, largest, earliest deadline, cheapest path, most frequent: whatever the priority is. Items keep arriving and leaving, and after every change the question is asked again.

A binary heap is the standard way to build one. It does not keep everything sorted. It keeps only enough order to answer that one question:

Operation Binary heap Sorted array Unsorted array Balanced BST
Peek at the best O(1) O(1) O(n) O(log n)
Insert O(log n) O(n) (shifting) O(1) O(log n)
Remove the best O(log n) O(1) or O(n) O(n) O(log n)
Build from n items O(n) O(n log n) O(1) O(n log n)
Find / delete an arbitrary item O(n) O(log n) / O(n) O(n) O(log n)
Memory one array, no pointers one array one array a node per item

The one rule (heap property). In a min-heap every parent is ≤ both of its children; in a max-heap, ≥. Nothing is promised about siblings or cousins. So the root is the minimum (or maximum), and nothing else in the array is "in order". When a problem keeps asking for the current smallest / largest / next while the set changes, reach for a heap.

The partial order is the trick. Fully sorting costs O(n log n) up front and O(n) per insertion; a heap only repairs one root-to-leaf path per change, and a path in a complete tree of n nodes has about log₂ n nodes. With a million items that is 20 steps.

The array is the tree

A binary heap is a complete binary tree: every level is full except possibly the last, which fills from the left. A complete tree has no gaps, so it fits in an array level by level, and the parent / child links become arithmetic. There are no pointers at all.

Index formulas for a 0-based array: parent of i is (i - 1) // 2; children are 2*i + 1 and 2*i + 2; a node is a leaf when 2*i + 1 >= n, so the leaves are exactly n//2 … n-1 (half the array). Many textbooks use 1-based arrays, where the children are 2i and 2i + 1 and the parent is i // 2. Do not mix the two.

Two consequences you will use constantly:

  • The tree has height ⌊log₂ n⌋. Any operation that walks one path from the root to a leaf, or back up, is O(log n).
  • Appending to the array adds the next leaf in level order, and removing the last element removes the last leaf. Both keep the tree complete for free. That is why push and pop always work through the last array slot.

Push and pop: repair one path

Both operations first keep the shape right (add or remove the last slot), then fix the order along a single path:

  • push(x), sift-up: append x as the new last leaf. Only the path from that leaf to the root can now be out of order. While x beats its parent, swap them. At most one swap per level.
  • pop(), sift-down: the answer is h[0]. Move the last element into the root (the array stays gap-free), then sift it down: compare it with its better child (the smaller one in a min-heap) and swap while that child beats it.

Why the better child? After the swap the child becomes the parent of its old sibling. If you promoted the worse child, it would sit above a better sibling and break the rule right there. Promoting the better one keeps both sides valid.

Type operations below. Switch between min-heap and max-heap; the code is identical apart from the comparison.

Here is the whole data structure written out. You rarely write it in an interview (both languages ship one), but writing it once makes every heap bug obvious later. heapq uses exactly this array layout.

class MinHeap:
    def __init__(self, items=()):
        self.h = list(items)
        for i in range(len(self.h) // 2 - 1, -1, -1):   # heapify: O(n), see below
            self._down(i)

    def __len__(self):
        return len(self.h)

    def peek(self):
        return self.h[0]

    def push(self, x):
        h = self.h
        h.append(x)                                    # new last leaf
        i = len(h) - 1
        while i > 0 and h[i] < h[(i - 1) // 2]:        # sift up
            p = (i - 1) // 2
            h[i], h[p] = h[p], h[i]
            i = p

    def pop(self):
        h = self.h
        top, last = h[0], h.pop()                      # detach the last leaf
        if h:
            h[0] = last                                # it fills the hole at the root
            self._down(0)
        return top

    def _down(self, i):
        h, n = self.h, len(self.h)
        while 2 * i + 1 < n:
            c = 2 * i + 1
            if c + 1 < n and h[c + 1] < h[c]:          # pick the smaller child
                c += 1
            if h[i] <= h[c]:
                break
            h[i], h[c] = h[c], h[i]
            i = c

public class MinHeap
{
    private readonly List<int> h;

    public MinHeap(IEnumerable<int>? items = null)
    {
        h = new List<int>(items ?? Enumerable.Empty<int>());
        for (int i = h.Count / 2 - 1; i >= 0; i--) Down(i);   // heapify: O(n)
    }

    public int Count => h.Count;
    public int Peek() => h[0];

    public void Push(int x)
    {
        h.Add(x);                                            // new last leaf
        int i = h.Count - 1;
        while (i > 0 && h[i] < h[(i - 1) / 2])               // sift up
        {
            int p = (i - 1) / 2;
            (h[i], h[p]) = (h[p], h[i]);
            i = p;
        }
    }

    public int Pop()
    {
        int top = h[0];
        h[0] = h[^1];                                        // last leaf fills the root
        h.RemoveAt(h.Count - 1);
        if (h.Count > 0) Down(0);
        return top;
    }

    private void Down(int i)
    {
        int n = h.Count;
        while (2 * i + 1 < n)
        {
            int c = 2 * i + 1;
            if (c + 1 < n && h[c + 1] < h[c]) c++;           // pick the smaller child
            if (h[i] <= h[c]) break;
            (h[i], h[c]) = (h[c], h[i]);
            i = c;
        }
    }
}

Off-by-one in sift-down. The loop condition is "has a left child" (2*i + 1 < n); the right child needs its own check (c + 1 < n) before you compare it. Forgetting that reads past the end, and in Python h[c + 1] may silently read a stale value if you pop lazily. Also note the order in pop: take the last element out first, then put it at the root; if the heap had one element, there is nothing to put back.

Heapify: building a heap in O(n)

Given n items up front, you could push them one by one: O(n log n). Bottom-up heapify is faster. Every leaf is already a one-node heap. Walk the parents from the last one (n//2 - 1) back to the root, and sift each one down. When you reach node i, both of its subtrees are already heaps, so a single sift-down makes the subtree at i a heap too.

Why is that O(n) and not O(n log n)? A sift-down from node i costs at most the height of i (its distance to the bottom), not the height of the whole tree. And most nodes are near the bottom:

Use it whenever all the items are known at the start: heapq.heapify(list) in Python, or the PriorityQueue constructor that takes a collection in C#. It turns "push n times" into one linear pass, and it is in place.

Heapsort: pop everything

Popping a heap until it is empty yields the items in order, so a heap is also a sorting algorithm. The in-place version uses a max-heap: swap the root (the maximum) with the last slot of the heap, shrink the heap by one, sift down, repeat. The sorted tail grows from the right.

def heap_sort(a: list[int]) -> list[int]:
    def down(i, n):                          # max-heap sift-down within a[:n]
        while 2 * i + 1 < n:
            c = 2 * i + 1
            if c + 1 < n and a[c + 1] > a[c]:
                c += 1
            if a[i] >= a[c]:
                break
            a[i], a[c] = a[c], a[i]
            i = c

    n = len(a)
    for i in range(n // 2 - 1, -1, -1):      # build a max-heap: O(n)
        down(i, n)
    for end in range(n - 1, 0, -1):
        a[0], a[end] = a[end], a[0]          # the max goes to its final slot
        down(0, end)                         # the heap shrinks by one
    return a

public static int[] HeapSort(int[] a)
{
    void Down(int i, int n)                  // max-heap sift-down within a[0..n)
    {
        while (2 * i + 1 < n)
        {
            int c = 2 * i + 1;
            if (c + 1 < n && a[c + 1] > a[c]) c++;
            if (a[i] >= a[c]) break;
            (a[i], a[c]) = (a[c], a[i]);
            i = c;
        }
    }

    int n = a.Length;
    for (int i = n / 2 - 1; i >= 0; i--) Down(i, n);
    for (int end = n - 1; end > 0; end--)
    {
        (a[0], a[end]) = (a[end], a[0]);
        Down(0, end);
    }
    return a;
}

Heapsort is O(n log n) in the worst case and uses O(1) extra space, but it is not stable and its jumps around the array are cache-unfriendly, so library sorts prefer merge sort or quicksort variants. See Sorting Algorithms for the comparison. In practice you will rarely sort with a heap; you will use one when you only need part of the order, which is the rest of this page.

Heaps in Python and C

Both standard libraries give you an array-backed binary heap. Their personalities differ, and most heap bugs in interviews come from these differences.

Tuples that tie compare their next field. heappush(h, (dist, node)) works for ints, but when two distances tie Python compares the nodes. If they are ListNodes or dicts you get TypeError: '<' not supported. Put a unique, comparable tie-breaker in the middle: (dist, i, node) with i an index or a running counter. C# never compares elements (only priorities), so it has no such crash, but its tie order is arbitrary: if the problem demands "smallest index first on ties", encode that in the priority, e.g. a tuple priority (dist, index).

Negation for a max-heap. Push -x and negate again when you read: -h[0], -heappop(h). Forgetting one of the two negations is the classic bug. For tuples negate only the priority field: (-count, letter) pops the highest count, and ties then go to the smallest letter. Negating strings is impossible; if you need "largest string first", wrap it in a class with a reversed __lt__, or use another key.

heapreplace vs heappushpop. heapreplace(h, x) pops first, so it returns the old minimum even if x is smaller. heappushpop(h, x) returns x immediately when x is smaller than the root, without touching the heap. For "keep the k largest", if x > h[0]: heapreplace(h, x) is the clearest form. Both do one sift instead of two.

Top-k: a heap of size k

"The k largest", "the k-th largest", "the k most frequent", "the k closest". Sorting everything is O(n log n). A heap that never holds more than k items does it in O(n log k) time and O(k) memory, and it works on a stream you cannot store.

The surprising part is the direction: for the k largest you keep a min-heap. Its root is the weakest of the current top k, the bar a newcomer has to beat. If a new number does not beat the bar, it can never be in the top k, and you drop it in O(1).

You want Keep Root means Replace the root when
k largest / k-th largest min-heap of size k the k-th largest so far x > root
k smallest / k-th smallest max-heap of size k (Python: push -x) the k-th smallest so far x < root
k most frequent min-heap of (count, value) the least frequent of the top k count > root count
k closest to a target max-heap of (distance, …) the farthest of the k closest distance < root distance 
def find_kth_largest(nums: list[int], k: int) -> int:
    heap = []                              # min-heap, never more than k items
    for x in nums:
        if len(heap) < k:
            heapq.heappush(heap, x)
        elif x > heap[0]:                  # beats the weakest of the top k
            heapq.heapreplace(heap, x)
    return heap[0]

public static int FindKthLargest(int[] nums, int k)
{
    var heap = new PriorityQueue<int, int>();          // min-heap, at most k items
    foreach (int x in nums)
    {
        if (heap.Count < k) heap.Enqueue(x, x);
        else if (x > heap.Peek()) heap.DequeueEnqueue(x, x);
    }
    return heap.Peek();
}

When a heap is not the best tool. If all n numbers are in memory and you need only the k-th element once, quickselect is O(n) on average (and is what nth_element does in C++). If the values are small integers or counts bounded by n, bucket sort gives O(n) (see Top K Frequent below). The heap wins when data streams in, when k is much smaller than n, or when you need the answer again after every update.

Merging k sorted sequences

You have k sorted lists and want one sorted output. At every step the next output element is the smallest of the k current fronts, because each list's front is the smallest thing left in that list. Keep exactly those k fronts in a min-heap. Pop the smallest, output it, and push the next element from the same list. The heap never holds more than k entries, so each of the N output elements costs O(log k).

def merge_k_sorted(lists: list[list[int]]) -> list[int]:
    heap = [(lst[0], i, 0) for i, lst in enumerate(lists) if lst]
    heapq.heapify(heap)                    # (value, which list, position)
    out = []
    while heap:
        val, i, j = heapq.heappop(heap)
        out.append(val)
        if j + 1 < len(lists[i]):          # that list's next element replaces it
            heapq.heappush(heap, (lists[i][j + 1], i, j + 1))
    return out

public static List<int> MergeKSorted(int[][] lists)
{
    var heap = new PriorityQueue<(int List, int Pos), int>();
    for (int i = 0; i < lists.Length; i++)
        if (lists[i].Length > 0) heap.Enqueue((i, 0), lists[i][0]);
    var output = new List<int>();
    while (heap.TryDequeue(out var at, out int val))
    {
        output.Add(val);
        if (at.Pos + 1 < lists[at.List].Length)
            heap.Enqueue((at.List, at.Pos + 1), lists[at.List][at.Pos + 1]);
    }
    return output;
}

The same frontier idea solves problems that do not look like merging at all:

  • Kth Smallest Element in a Sorted Matrix: each row is a sorted list. Pop k times from a heap of row fronts.
  • Find K Pairs with Smallest Sums: the pairs (i, j) for a fixed i form a sorted list (as j grows). Seed the heap with (nums1[i] + nums2[0], i, 0) and advance j.
  • Ugly Number II / Super Ugly Number: every ugly number times 2, 3 or 5 is a sorted stream; merge them (and skip duplicates).
  • Smallest Range Covering Elements from K Lists: keep one front per list in a min-heap plus the current maximum of the fronts; the range is [heap min, max]; advance the list that owns the minimum.

Python already has it. heapq.merge(*sorted_iterables) is a lazy k-way merge built on this exact idea. Use it in real code; write the loop yourself in interviews, because the follow-ups (linked lists, matrices, pairs) need the explicit (value, list, position) form.

Two heaps: the running median

The median needs the middle of the data, and a heap only exposes an end. So split the data in two at the middle and give each half its own heap, oriented so that both tops face the middle:

Adding a number: put it on the correct side (≤ top of lo goes to lo), then rebalance if one side became too big by moving that side's top across. Moving a top keeps the order rule: the largest of the small half is still ≤ everything in the large half. Each add is at most three heap operations, O(log n); reading the median is O(1).

The same split solves Sliding Window Median (add one number and remove one per step; removal needs the lazy deletion below) and IPO-like "two orders" problems. The full Find Median from Data Stream solution is worked problem 6.

Greedy scheduling with heaps

Many greedy algorithms say "at every moment, pick the best available option". If options become available over time and the best one keeps changing, the "best available" is a heap. Three shapes cover most problems.

Meeting rooms: the resource that frees up first

How many rooms do the meetings need? Process meetings in start order and keep a min-heap of the end times of busy rooms. When a meeting starts, only one room is worth checking: the one that frees up first, the root. If even that room is still busy, every room is busy, so open a new one.

def min_meeting_rooms(intervals: list[list[int]]) -> int:
    intervals.sort()                         # by start time
    ends = []                                # min-heap: one end time per room
    for s, e in intervals:
        if ends and ends[0] <= s:            # the earliest-free room is free by s
            heapq.heapreplace(ends, e)
        else:
            heapq.heappush(ends, e)
    return len(ends)

public static int MinMeetingRooms(int[][] intervals)
{
    var ends = new PriorityQueue<int, int>();          // one end time per room
    foreach (var iv in intervals.OrderBy(iv => iv[0]))
    {
        if (ends.Count > 0 && ends.Peek() <= iv[0]) ends.DequeueEnqueue(iv[1], iv[1]);
        else ends.Enqueue(iv[1], iv[1]);
    }
    return ends.Count;
}

The heap never shrinks, and it ends with the number of rooms, which is the maximum number of meetings running at the same time. A sweep over sorted start and end times gives the same count without a heap (see Intervals & Sweep Line). The heap version wins as soon as you must know which room: Meeting Rooms III, Process Tasks Using Servers and Single-Threaded CPU all keep two heaps, one of idle resources (by index or weight) and one of busy resources (by the time they free up), and move resources between them as time advances.

Task scheduler: the most work left goes first

Tasks A–Z, each takes one tick, and two copies of the same task must be at least n ticks apart. Minimize the total time. Greedy rule: at every tick run the ready task with the most copies left. A task that has just run goes into a FIFO cooldown queue with the time it becomes ready again. The heap chooses, the queue remembers.

def least_interval(tasks: list[str], n: int) -> int:
    heap = [(-c, t) for t, c in Counter(tasks).items()]
    heapq.heapify(heap)                      # most copies left on top
    cool = deque()                           # (ready_time, -copies_left, task)
    time = 0
    while heap or cool:
        time += 1
        if heap:
            c, t = heapq.heappop(heap)
            if c + 1:                        # copies left after this run
                cool.append((time + n, c + 1, t))
        if cool and cool[0][0] == time:      # cooldown over: ready again
            _, c, t = cool.popleft()
            heapq.heappush(heap, (c, t))
    return time

public static int LeastInterval(char[] tasks, int n)
{
    var count = new int[26];
    foreach (char t in tasks) count[t - 'A']++;
    var heap = new PriorityQueue<int, int>();          // copies left; priority -copies: max-heap
    foreach (int c in count) if (c > 0) heap.Enqueue(c, -c);
    var cool = new Queue<(int Ready, int Left)>();
    int time = 0;
    while (heap.Count > 0 || cool.Count > 0)
    {
        time++;
        if (heap.TryDequeue(out int c, out _) && c > 1)
            cool.Enqueue((time + n, c - 1));
        if (cool.Count > 0 && cool.Peek().Ready == time)
        {
            var (_, left) = cool.Dequeue();
            heap.Enqueue(left, -left);
        }
    }
    return time;
}

The heap simulation produces a real schedule. If you only need the length, there is a closed form, and the picture explains it:

def least_interval_formula(tasks: list[str], n: int) -> int:
    counts = Counter(tasks).values()
    top = max(counts)
    ties = sum(1 for c in counts if c == top)
    return max(len(tasks), (top - 1) * (n + 1) + ties)

public static int LeastIntervalFormula(char[] tasks, int n)
{
    var count = new int[26];
    foreach (char t in tasks) count[t - 'A']++;
    int top = count.Max();
    int ties = count.Count(c => c == top);
    return Math.Max(tasks.Length, (top - 1) * (n + 1) + ties);
}

IPO: unlock by one key, choose by another

You start with capital w and may finish at most k projects. Project i needs capital[i] to start and adds profits[i] when done. Two different orders are involved, and each gets its own structure:

  • Unlocking depends on capital, and capital only grows. Sort projects by capital and sweep a pointer forward; a project, once affordable, stays affordable.
  • Choosing depends on profit: among unlocked projects, take the most profitable. That is a max-heap of profits.
def find_maximized_capital(k: int, w: int, profits: list[int], capital: list[int]) -> int:
    projects = sorted(zip(capital, profits))
    avail, i = [], 0                         # max-heap of unlocked profits (negated)
    for _ in range(k):
        while i < len(projects) and projects[i][0] <= w:
            heapq.heappush(avail, -projects[i][1])
            i += 1
        if not avail:
            break                            # nothing affordable, ever
        w -= heapq.heappop(avail)            # minus a negative: add the profit
    return w

public static int FindMaximizedCapital(int k, int w, int[] profits, int[] capital)
{
    int n = profits.Length, next = 0;
    int[] order = Enumerable.Range(0, n).OrderBy(i => capital[i]).ToArray();
    var avail = new PriorityQueue<int, int>();          // profit; priority -profit: max-heap
    for (int round = 0; round < k; round++)
    {
        while (next < n && capital[order[next]] <= w)
        {
            int p = profits[order[next++]];
            avail.Enqueue(p, -p);
        }
        if (!avail.TryDequeue(out int best, out _)) break;
        w += best;
    }
    return w;
}

Why greedy is safe here. Taking the most profitable affordable project gives the largest capital after this round. Larger capital unlocks a superset of projects, so no other choice can lead to a better future. Most heap-greedy proofs have this shape: the heap's choice leaves you in a state at least as good as any alternative, so an exchange argument finishes it (see Greedy Algorithms). Recognise the pattern "sorted pointer for availability + heap for selection" in Course Schedule III, Maximum Performance of a Team, Minimum Cost to Hire K Workers and Single-Threaded CPU.

Lazy deletion: removing what you cannot find

A heap can remove its top in O(log n), but removing an arbitrary element means finding it first, which is O(n): the array is not searchable. Neither heapq nor PriorityQueue has a decrease-key or a fast delete. The standard workaround is to not delete at all:

  1. When an item becomes invalid (it left a window, its priority changed, it was cancelled), just remember that it is invalid: an index check, a "removed" counter, or a newer value in a dist array.
  2. When you look at the top, first pop invalid tops until the top is valid. Buried invalid entries do no harm: they are never returned, because they are discarded the moment they reach the top.
def max_sliding_window_heap(nums: list[int], k: int) -> list[int]:
    heap, out = [], []
    for i, x in enumerate(nums):
        heapq.heappush(heap, (-x, i))        # max-heap by value, remember the index
        while heap[0][1] <= i - k:           # stale top: it left the window
            heapq.heappop(heap)
        if i >= k - 1:
            out.append(-heap[0][0])
    return out

public static int[] MaxSlidingWindowHeap(int[] nums, int k)
{
    var heap = new PriorityQueue<int, int>();          // element: index; priority: -value
    var output = new List<int>();
    for (int i = 0; i < nums.Length; i++)
    {
        heap.Enqueue(i, -nums[i]);
        while (heap.Peek() <= i - k) heap.Dequeue();   // stale top: it left the window
        if (i >= k - 1) output.Add(nums[heap.Peek()]);
    }
    return output.ToArray();
}

The cost: the heap can hold up to n entries instead of k, so operations are O(log n) instead of O(log k). Each entry is pushed once and popped once, so the total stays O(n log n). The ways to know an entry is stale:

Problem Entry Stale when
Sliding window max / median (value, index) or a value index ≤ i − k, or a removed[value] counter is positive
Dijkstra / Prim (dist, node) dist > best[node]: a shorter path was found later
Updatable priorities (stock prices, leaderboards) (priority, id, version) version != current_version[id]
Cancelled tasks / timers (time, id) id in cancelled

Sizes lie under lazy deletion. len(heap) counts stale entries too. If the algorithm depends on sizes (two heaps that must stay balanced), keep your own counters of valid items per heap and balance on those. Worked problem 7 does exactly that.

Dijkstra preview: the heap as a frontier

Shortest paths with non-negative weights are the most famous heap algorithm. The heap holds (tentative distance, node). The top is the closest node not yet settled, and its distance is final, because any other route to it would pass through a node that is at least as far and then add non-negative weights. When a shorter path to v is found, push a new entry. The old one becomes stale and is skipped when popped: lazy deletion standing in for decrease-key.

def dijkstra(n: int, edges: list[tuple[int, int, int]], src: int) -> list[float]:
    adj = [[] for _ in range(n)]
    for u, v, w in edges:                    # undirected, w >= 0
        adj[u].append((v, w))
        adj[v].append((u, w))
    dist = [math.inf] * n
    dist[src] = 0
    heap = [(0, src)]
    while heap:
        d, u = heapq.heappop(heap)
        if d > dist[u]:
            continue                         # stale entry: u improved later
        for v, w in adj[u]:
            if d + w < dist[v]:
                dist[v] = d + w
                heapq.heappush(heap, (d + w, v))
    return dist

public static int[] Dijkstra(int n, int[][] edges, int src)
{
    var adj = new List<(int To, int W)>[n];
    for (int i = 0; i < n; i++) adj[i] = new();
    foreach (var e in edges) { adj[e[0]].Add((e[1], e[2])); adj[e[1]].Add((e[0], e[2])); }
    var dist = new int[n];
    Array.Fill(dist, int.MaxValue);                    // int.MaxValue = unreachable
    dist[src] = 0;
    var heap = new PriorityQueue<int, int>();
    heap.Enqueue(src, 0);
    while (heap.TryDequeue(out int u, out int d))
    {
        if (d > dist[u]) continue;                     // stale entry
        foreach (var (v, w) in adj[u])
            if (d + w < dist[v]) { dist[v] = d + w; heap.Enqueue(v, d + w); }
    }
    return dist;
}

This is a preview. Shortest Paths covers Dijkstra properly (path reconstruction, grids, "cheapest flights with at most k stops", why negative edges break it, and Bellman-Ford). Prim's minimum spanning tree uses the same heap loop with edge weight instead of total distance (Minimum Spanning Trees).

Pitfalls and a debugging checklist

The wrong direction. The k largest need a min-heap of size k; the k smallest need a max-heap. A max-heap of all n items "works" but costs O(n) memory and O(n + k log n) time, and it misses the point on a stream. Before you write the first line, say out loud what the root means: "the k-th largest so far", "the room that frees up first".

Treating the heap as sorted. h[1] is not the second smallest (it is one of the two children of the root), and iterating h or UnorderedItems gives heap order, not sorted order. To get the k best in order, pop k times or sort the heap's contents at the end.

Changing an item while it is inside the heap. If you mutate the priority of an object that is already in the heap (node.dist = 3), nobody sifts it, and the heap property is silently broken. The heap does not know. Push a new entry and skip the old one later (lazy deletion), or rebuild with heapify. The same goes for h.append(x) or h.sort() on a list you are using with heapq: either keep using only heapq functions on it, or call heapify again.

Empty heaps. h[0] and heappop(h) raise IndexError on an empty list; Peek() and Dequeue() throw InvalidOperationException. Guard with if h: or use TryPeek / TryDequeue. After lazy pops, the heap can become empty inside your loop, so guard there too.

Debugging checklist

  1. What does the root mean, in one sentence? Is the heap a min-heap or a max-heap, and does every push and every read agree on the sign?
  2. What exactly is in one entry? If it is a tuple, which field breaks ties, and can that field always be compared?
  3. What is the size bound? "At most k", "one per list", "one per busy room", or "everything, with stale entries"? Check that pushes and pops keep it.
  4. Can an entry become invalid while it sits in the heap? Then you need a staleness test at every top read.
  5. Run the edge cases: k = 1, k = n, all values equal, an empty list among the inputs, negative numbers (with negation), and ties.

Recognize it when

  • "k-th largest / smallest", "top k", "k closest", "k most frequent", especially on a stream. Size-k heap with the opposite orientation.
  • Several sorted sources and you need the global order, or the k-th element across them: one front per source in a heap.
  • "Median" (or any percentile) of data that keeps changing. Two heaps.
  • A simulation where at each moment you take the best available option and options appear or expire over time: rooms, servers, CPU tasks, courses, projects. Heap, often plus a sort by arrival time.
  • "Minimum cost / time to reach", with non-negative weights: Dijkstra. Grid flood fills where you always extend the lowest wall (Trapping Rain Water II, Swim in Rising Water) are the same idea.
  • You keep needing min or max of a set that also needs removals: a heap with lazy deletion (or a balanced BST / SortedList if you need both ends and arbitrary deletes).
  • The best item is only ever needed at one end and the data is static: just sort. A heap pays off when the set changes between queries.

Worked problems

1. Kth Largest Element in a Stream Easy

Design a class that is given k and some initial numbers, then receives numbers one at a time and must return the k-th largest so far after each one. Insight: this is the top-k visualizer turned into a class. The heap keeps the k largest; its root is the answer, and add is one comparison plus at most one O(log k) sift.

Solution: O(n log k) to build, O(log k) per add, O(k) space 
class KthLargest:
    def __init__(self, k: int, nums: list[int]):
        self.k = k
        self.heap = nums[:]
        heapq.heapify(self.heap)                  # O(n)
        while len(self.heap) > k:
            heapq.heappop(self.heap)              # keep only the k largest

    def add(self, val: int) -> int:
        if len(self.heap) < self.k:
            heapq.heappush(self.heap, val)
        elif val > self.heap[0]:
            heapq.heapreplace(self.heap, val)     # val joins, the old k-th leaves
        return self.heap[0]

public class KthLargest
{
    private readonly int k;
    private readonly PriorityQueue<int, int> heap = new();   // min-heap of the k largest

    public KthLargest(int k, int[] nums)
    {
        this.k = k;
        foreach (int x in nums) Add(x);
    }

    public int Add(int val)
    {
        if (heap.Count < k) heap.Enqueue(val, val);
        else if (val > heap.Peek()) heap.DequeueEnqueue(val, val);
        return heap.Peek();
    }
}

2. Top K Frequent Elements Medium

Return the k most frequent values (any order). Insight: count with a hash map, then it is top-k on the counts: a min-heap of (count, value) of size k. Because counts are integers between 1 and n, there is also an O(n) answer: bucket the values by count and read the buckets from the highest count down.

Solution: O(n log k) with a heap, O(n) with buckets 
def top_k_frequent(nums: list[int], k: int) -> list[int]:
    count = Counter(nums)
    heap = []                                     # min-heap of (freq, value), size <= k
    for v, f in count.items():
        heapq.heappush(heap, (f, v))
        if len(heap) > k:
            heapq.heappop(heap)                   # drop the least frequent
    return [v for f, v in heap]


def top_k_frequent_bucket(nums: list[int], k: int) -> list[int]:
    count = Counter(nums)
    buckets = [[] for _ in range(len(nums) + 1)]  # buckets[f] = values seen f times
    for v, f in count.items():
        buckets[f].append(v)
    out = []
    for f in range(len(nums), 0, -1):
        for v in buckets[f]:
            out.append(v)
            if len(out) == k:
                return out
    return out

public static int[] TopKFrequent(int[] nums, int k)
{
    var count = new Dictionary<int, int>();
    foreach (int x in nums) count[x] = count.GetValueOrDefault(x) + 1;
    var heap = new PriorityQueue<int, int>();          // value; priority = frequency
    foreach (var (v, f) in count)
    {
        heap.Enqueue(v, f);
        if (heap.Count > k) heap.Dequeue();            // drop the least frequent
    }
    return heap.UnorderedItems.Select(p => p.Element).ToArray();
}

public static int[] TopKFrequentBucket(int[] nums, int k)
{
    var count = new Dictionary<int, int>();
    foreach (int x in nums) count[x] = count.GetValueOrDefault(x) + 1;
    var buckets = new List<int>[nums.Length + 1];
    foreach (var (v, f) in count) (buckets[f] ??= new List<int>()).Add(v);
    var output = new List<int>();
    for (int f = nums.Length; f > 0 && output.Count < k; f--)
        if (buckets[f] != null)
            foreach (int v in buckets[f])
                if (output.Count < k) output.Add(v);
    return output.ToArray();
}

Top K Frequent Words adds a twist: ties must be broken alphabetically, and the output must be sorted. With a size-k min-heap the "worst" entry must be on top, so the worst is the lower count, and on equal counts the alphabetically larger word. That needs a reversed string order, which heapq cannot express by negation. The easy route: heapq.nsmallest(k, count, key=lambda w: (-count[w], w)), or sort by that key.

3. K Closest Points to Origin Medium

Return the k points closest to (0, 0). Insight: "k smallest distances" means a max-heap of size k: the root is the farthest of the points kept so far, and a new point replaces it only when it is closer. Compare squared distances; there is no need for sqrt. The index i in the tuple is the tie-breaker, so two points at the same distance never compare their lists.

Solution: O(n log k) time, O(k) space 
def k_closest(points: list[list[int]], k: int) -> list[list[int]]:
    heap = []                                     # max-heap by distance: (-d, i)
    for i, (x, y) in enumerate(points):
        d = x * x + y * y
        if len(heap) < k:
            heapq.heappush(heap, (-d, i))
        elif d < -heap[0][0]:                     # closer than the farthest kept
            heapq.heapreplace(heap, (-d, i))
    return [points[i] for _, i in heap]

public static int[][] KClosest(int[][] points, int k)
{
    var heap = new PriorityQueue<int[], int>(Comparer<int>.Create((a, b) => b.CompareTo(a)));  // max-heap
    foreach (var p in points)
    {
        int d = p[0] * p[0] + p[1] * p[1];
        if (heap.Count < k) heap.Enqueue(p, d);
        else if (heap.TryPeek(out _, out int far) && d < far) heap.DequeueEnqueue(p, d);
    }
    return heap.UnorderedItems.Select(e => e.Element).ToArray();
}

4. Reorganize String Medium

Rearrange the letters so that no two adjacent letters are equal, or return "" if that is impossible. Insight: the task scheduler with n = 1. Always place the letter with the most copies left, except the one you just placed, which sits out one turn (held) and goes back into the heap after the next letter. If the heap runs dry while a letter is still held, no valid arrangement exists; that happens exactly when some letter appears more than (len + 1) // 2 times.

Solution: O(n log 26) = O(n) time, O(26) extra space 
def reorganize_string(s: str) -> str:
    heap = [(-c, ch) for ch, c in Counter(s).items()]
    heapq.heapify(heap)
    out, held = [], None                          # held: the letter that must sit out one turn
    while heap:
        c, ch = heapq.heappop(heap)
        out.append(ch)
        if held:
            heapq.heappush(heap, held)            # last turn's letter is allowed again
        held = (c + 1, ch) if c + 1 < 0 else None
    return "" if held else "".join(out)

public static string ReorganizeString(string s)
{
    var count = new int[26];
    foreach (char ch in s) count[ch - 'a']++;
    var heap = new PriorityQueue<int, int>();          // letter; priority -copies left
    for (int c = 0; c < 26; c++) if (count[c] > 0) heap.Enqueue(c, -count[c]);
    var sb = new System.Text.StringBuilder();
    int held = -1;                                     // the letter sitting out one turn
    while (heap.TryDequeue(out int c, out _))
    {
        sb.Append((char)('a' + c));
        count[c]--;
        if (held >= 0) heap.Enqueue(held, -count[held]);
        held = count[c] > 0 ? c : -1;
    }
    return held >= 0 ? "" : sb.ToString();
}

5. Merge k Sorted Lists Hard

Merge k sorted linked lists into one. Insight: the k-way merge visualizer with nodes instead of indices: the heap holds the current head of each list, and popping a node means "link it to the tail and push its next". In Python the tuple is (val, i, node): i is the list index, unique among the heap's entries (each list has at most one node in the heap), so ties never reach the ListNode. The pointer handling is the dummy-head technique from Linked Lists.

Solution: O(N log k) time, O(k) extra space 
def merge_k_lists(lists: list[ListNode | None]) -> ListNode | None:
    heap = [(node.val, i, node) for i, node in enumerate(lists) if node]
    heapq.heapify(heap)
    dummy = tail = ListNode()
    while heap:
        _, i, node = heapq.heappop(heap)
        tail.next = node                          # reuse the node, no copying
        tail = node
        if node.next:
            heapq.heappush(heap, (node.next.val, i, node.next))
    return dummy.next

public static ListNode? MergeKLists(ListNode?[] lists)
{
    var heap = new PriorityQueue<ListNode, int>();     // node; priority = its value
    foreach (var node in lists) if (node != null) heap.Enqueue(node, node.val);
    var dummy = new ListNode();
    var tail = dummy;
    while (heap.TryDequeue(out var node, out _))
    {
        tail.next = node;
        tail = node;
        if (node.next != null) heap.Enqueue(node.next, node.next.val);
    }
    return dummy.next;
}

The heap-free alternative. Merge the lists in pairs, like the merge step of merge sort: k lists → k/2 → k/4 … Each round touches all N nodes, and there are log₂ k rounds: also O(N log k), with O(1) extra space if the merging is iterative. Merging list after list into one growing result is O(N·k), the slow answer interviewers are waiting for you to improve.

6. Find Median from Data Stream Hard

Support addNum(num) and findMedian(). Insight: the two-heaps visualizer. This version is branch-free: every number goes into lo, then lo's largest moves to hi (so the order rule holds automatically), then hi gives one back if it became bigger. Three heap operations, the same O(log n), and no comparison to get wrong.

Solution: O(log n) add, O(1) median, O(n) space 
class MedianFinder:
    def __init__(self):
        self.lo = []                              # max-heap (negated): the smaller half
        self.hi = []                              # min-heap: the larger half

    def addNum(self, num: int) -> None:
        heapq.heappush(self.lo, -num)
        heapq.heappush(self.hi, -heapq.heappop(self.lo))   # lo's largest moves up
        if len(self.hi) > len(self.lo):
            heapq.heappush(self.lo, -heapq.heappop(self.hi))

    def findMedian(self) -> float:
        if len(self.lo) > len(self.hi):
            return float(-self.lo[0])
        return (-self.lo[0] + self.hi[0]) / 2

public class MedianFinder
{
    private readonly PriorityQueue<int, int> lo = new(Comparer<int>.Create((a, b) => b.CompareTo(a)));  // max-heap
    private readonly PriorityQueue<int, int> hi = new();                                                // min-heap

    public void AddNum(int num)
    {
        lo.Enqueue(num, num);
        int moved = lo.Dequeue();                      // lo's largest moves up
        hi.Enqueue(moved, moved);
        if (hi.Count > lo.Count)
        {
            int back = hi.Dequeue();
            lo.Enqueue(back, back);
        }
    }

    public double FindMedian() =>
        lo.Count > hi.Count ? lo.Peek() : ((double)lo.Peek() + hi.Peek()) / 2;
}

The follow-ups. "All numbers are in 0..100": keep 101 counters and walk them to the middle, O(100) per query. "99% are in 0..100": counters for the range plus two small heaps (or just counts) for the outliers below and above. Note the (double) in C#: lo.Peek() + hi.Peek() can overflow int before the division.

7. Sliding Window Median Hard

Return the median of every window of size k. Insight: the two heaps of problem 6, plus lazy deletion for the number that leaves. The difficulty is that a heap's length now includes stale entries, so the heaps cannot be balanced by len. Instead, track the change in valid(lo) − valid(hi) during each step: the leaving number y counts against the side it lives on, the entering number x for the side it joins. That change is −2, 0 or +2, and one move of a top fixes ±2. Stale tops are popped at the end of the step, so both tops are always valid when the median is read.

Solution: O(n log n) time, O(n) space 
def median_sliding_window(nums: list[int], k: int) -> list[float]:
    lo, hi = [], []                               # lo: max-heap (negated), hi: min-heap
    gone = Counter()                              # value -> stale copies still in a heap
    for x in nums[:k]:
        heapq.heappush(lo, -x)
    for _ in range(k // 2):                       # the larger half moves to hi
        heapq.heappush(hi, -heapq.heappop(lo))

    def median() -> float:
        return float(-lo[0]) if k % 2 else (-lo[0] + hi[0]) / 2

    out = [median()]
    for i in range(k, len(nums)):
        x, y = nums[i], nums[i - k]               # x enters, y leaves
        gone[y] += 1
        balance = -1 if y <= -lo[0] else 1        # change in valid(lo) - valid(hi)
        if x <= -lo[0]:
            heapq.heappush(lo, -x)
            balance += 1
        else:
            heapq.heappush(hi, x)
            balance -= 1
        if balance > 0:                           # lo has one valid item too many
            heapq.heappush(hi, -heapq.heappop(lo))
        elif balance < 0:                         # hi has one valid item too many
            heapq.heappush(lo, -heapq.heappop(hi))
        while lo and gone[-lo[0]]:                # now drop stale tops
            gone[-lo[0]] -= 1
            heapq.heappop(lo)
        while hi and gone[hi[0]]:
            gone[hi[0]] -= 1
            heapq.heappop(hi)
        out.append(median())
    return out

public static double[] MedianSlidingWindow(int[] nums, int k)
{
    var lo = new PriorityQueue<int, int>(Comparer<int>.Create((a, b) => b.CompareTo(a)));  // max-heap
    var hi = new PriorityQueue<int, int>();                                                // min-heap
    var gone = new Dictionary<int, int>();             // value -> stale copies still in a heap
    foreach (int x in nums.Take(k)) lo.Enqueue(x, x);
    for (int t = 0; t < k / 2; t++) { int m = lo.Dequeue(); hi.Enqueue(m, m); }

    double Median() => k % 2 == 1 ? lo.Peek() : ((double)lo.Peek() + hi.Peek()) / 2;
    void Prune(PriorityQueue<int, int> h)
    {
        while (h.Count > 0 && gone.GetValueOrDefault(h.Peek()) > 0) { gone[h.Peek()]--; h.Dequeue(); }
    }

    var output = new List<double> { Median() };
    for (int i = k; i < nums.Length; i++)
    {
        int x = nums[i], y = nums[i - k];
        gone[y] = gone.GetValueOrDefault(y) + 1;
        int balance = y <= lo.Peek() ? -1 : 1;
        if (x <= lo.Peek()) { lo.Enqueue(x, x); balance++; }
        else { hi.Enqueue(x, x); balance--; }
        if (balance > 0) { int m = lo.Dequeue(); hi.Enqueue(m, m); }
        else if (balance < 0) { int m = hi.Dequeue(); lo.Enqueue(m, m); }
        Prune(lo);
        Prune(hi);
        output.Add(Median());
    }
    return output.ToArray();
}

Why the moved top is never stale. At the start of a step both tops are valid. If the balance is +2, the leaving y was on the hi side and x joined lo, so lo's top is either its old valid top or x; both are valid. The −2 case is symmetric. Only the final pruning ever meets a stale top. In C#, a SortedList-like structure with duplicates (or two SortedSet<(value, index)>) avoids lazy deletion entirely, at the cost of more code.

Self-check

You want the k largest numbers of a stream. Why is the right heap a min-heap?

The heap is a club of the k largest so far, and the only member you ever need to inspect is the one who would be thrown out next: the smallest of the club. A min-heap puts exactly that number at the root. A newcomer is compared with it once: if it is bigger, it replaces the root (O(log k)); otherwise it is ignored (O(1)). With a max-heap the smallest member would be somewhere among the leaves, and you would have to keep all n numbers.

Pushing n items one by one costs O(n log n). Why does heapify on the same n items cost only O(n)?

heapify sifts down, starting from the last parent. The cost of a sift-down is the height of the node below it, and most nodes are near the bottom: n/2 leaves cost 0, n/4 nodes cost at most 1, n/8 cost at most 2, and so on. The sum n·(1/4 + 2/8 + 3/16 + …) is less than n. Pushing one by one sifts up, and the cost is the depth above the node, which is about log n for half of the nodes. Same tree, but the cheap direction is used for the many nodes at the bottom.

In a min-heap's sift-down, why must the parent swap with the smaller of its two children?

After the swap, the promoted child becomes the parent of the other child. If you promote the smaller child, it is ≤ its sibling, so the heap property holds at that node. Promote the larger child instead and it now sits above a smaller sibling: the property is broken at a node you have already left, and nothing will ever fix it. Example: parent 9, children 2 and 5. Swapping 9 with 5 puts 5 above 2.

Dijkstra with heapq pushes a node again every time its distance improves. Why is if d > dist[u]: continue correct, and what happens without it?

heapq has no decrease-key, so an improved distance is pushed as a new entry and the old one stays in the heap. The new one is smaller, so it is popped first and settles the node with the true distance. When the old entry surfaces later, its d is larger than dist[u]: it is stale and describes a path we already beat. Without the check, the node's edges are relaxed again with a worse distance: the answer stays correct (nothing improves), but the work can grow far past O(E log E) on dense graphs.

Running median: the invariants are "every value in lo ≤ every value in hi" and "len(lo) is len(hi) or one more". Why do they make the median O(1)?

Together they say: lo is exactly the smaller half of the data, sorted or not, with the extra element when n is odd. The middle element(s) of the sorted data are then the largest of lo and the smallest of hi: precisely the two roots. Odd n: the median is lo's root. Even n: it is the average of both roots. Nothing else in either heap ever matters, which is why they can stay unsorted.

Heap [3, 5, 8]. What do heapreplace(h, 1) and heappushpop(h, 1) return, and what is left in the heap?

heapreplace pops first: it returns 3 and leaves [1, 5, 8], so the 1 is now inside even though it is smaller than everything. heappushpop pushes first: 1 is the smallest, so it comes straight back out. It returns 1 and the heap is unchanged, [3, 5, 8]. For "keep the k largest" you want the second behaviour, or guard heapreplace with if x > h[0], as the snippets on this page do.

Your C# simulation enqueues tasks with equal priority and expects them back in arrival order. It works on small tests and fails on large ones. Why?

PriorityQueue<TElement, TPriority> is not stable: among equal priorities the order is whatever the sifts happen to produce, and it changes as the heap grows. The same is true of heapq if you push (priority, item) and rely on item order. Make the tie-break explicit: use a priority of (priority, sequenceNumber) (a value tuple compares field by field) or pass a custom IComparer.
