Complexity Analysis

Big-O growth you can see, amortized cost, recursion trees and the Master theorem, and what 10^8 operations per second really buys you.

Beginner → Advanced~50 min studyUpdated 2026-11-03

What Big-O measures

Big-O counts how the work grows, not how long it takes. Count the basic steps as a function of the input size n, keep the fastest-growing term, and drop the constant in front. That one number predicts whether your solution survives n = 10⁵ before you write a line of code.

A stopwatch measures one machine, one language and one input. Big-O measures the shape of the cost: if n doubles, does the work double (O(n)), quadruple (O(n²)) or barely move (O(log n))? Shapes are what decide whether code finishes. A 100× faster computer buys a constant factor; a better complexity class buys a factor that keeps growing with n.

Three rules do almost all of the work:

Rule Example Result
Drop constant factors 3n + 3n = 6n O(n)
Keep only the dominant term n² + 100n + 10⁶ O(n²)
Different inputs get different letters loop over a, then over b O(a + b), not O(n)
Nested independent loops multiply for each of m rows, scan n columns O(m·n)
Logs: the base does not matter log₂ n = 3.32 · log₁₀ n O(log n)

Insight Big-O is a tool for comparing ideas before coding them. When two ideas are in the same class, pick the simpler one. When they are in different classes, the better class wins for large n, and the constraints tell you exactly how large n gets.

Best, average and worst case are separate questions. Quicksort is Θ(n log n) on average and Θ(n²) in the worst case; a hash lookup is O(1) expected and O(n) worst case. When nobody says which, they mean the worst case, except for hashing, where "O(1)" means expected.

What 10⁸ operations per second buys you

A compiled language (C#, Java, C++, Go) does roughly 10⁸ simple operations per second: additions, comparisons, array reads. CPython does about 10⁷. Judges usually allow 1–2 seconds. Combine the two and the constraint n tells you the target complexity:

n up to Target complexity Typical techniques
10–11 O(n!), O(n·n!) permutations, brute-force orderings
20–25 O(2ⁿ), O(n·2ⁿ) subsets, bitmask DP
40 O(2^(n/2)) meet in the middle
100–500 O(n³) Floyd–Warshall, interval DP
1,000–5,000 O(n²) all pairs, 2-D DP
10⁵–10⁶ O(n log n) sorting, heaps, binary search, segment trees
10⁷–10⁸ O(n) one pass, two pointers, prefix sums
10⁹–10¹⁸ (a value, not a count) O(log n), O(√n) or O(1) binary search on the answer, fast power, math

Tip Big-O hides constants, and constants are real. A "simple operation" is a few machine instructions. A Python dict lookup, a C# LINQ step, or an allocation is 10–100 of them. When you are within 10× of the budget, count the expensive operations in the hot loop, not just the class. The Problem-Solving Playbook has an interactive budget calculator.

Counting operations through loops

To analyse code, find the line that runs the most and count how many times it runs. Four rules cover nearly every loop:

  1. Sequential blocks add. Loop A then loop B is O(A + B), which is the larger of the two.
  2. Nested loops multiply, but only when the inner loop's range does not depend on shared state. Count the inner iterations for each outer value and add them up.
  3. Look at how the loop variable changes. i += 1 runs n times, i += k runs n/k times, i *= 2 or i //= 2 runs log n times, and i*i <= n runs √n times.
  4. Look for pointers that never move back. If an inner while advances a pointer that never resets, its total over the whole run is at most n, however nested it looks.

Pick a loop shape below and step through it. The counter tallies every execution of the innermost line, and the final step compares your count with the formula for n = 10 up to 10⁴ by actually running the loop.

Loop Count Class
for i in range(n) n O(n)
for i … for j in range(n) n² O(n²)
for i … for j in range(i + 1, n) n(n−1)/2 O(n²)
while n > 1: n //= 2 ⌊log₂ n⌋ O(log n)
for i … j = 1; while j < n: j *= 2 n·⌈log₂ n⌉ O(n log n)
for i in 1..n: for j in range(i, n+1, i) n·(1 + ½ + … + 1/n) ≈ n ln n O(n log n)
for i … while j < n and ok(j): j += 1 (j never resets) ≤ 2n O(n) amortized
i = 1; while i*i <= n: i += 1 ⌊√n⌋ O(√n)
for i … for j … for k (all to n) n³ O(n³)

Pitfall A single line can hide a loop. if x in my_list, my_list.index(x), s[i:j], list.pop(0), "".join(...), sorted(...) in Python, or list.Contains(x), str.Substring, list.RemoveAt(0) and .ToList() in C# are each O(n) or worse. Put one inside a loop and an "O(n)" solution becomes O(n²). See hidden costs below.

log n: the halving intuition

log₂ n answers one question: how many times can you halve n before reaching 1? For a million that is 20 times; for a billion, 30; for 10¹⁸, 60. Any algorithm that throws away a constant fraction of the remaining work at each step (binary search, balanced-tree descent, fast exponentiation, Euclid's gcd) runs in O(log n) steps.

Type any n up to 10¹⁵ and count the halvings. Notice the binary representation: integer-halving deletes the last binary digit, so the number of steps is just the number of binary digits minus one.

Insight The base of the log is a constant factor (log₂ n = log₃ n · log₂ 3), so Big-O ignores it. But the thing being halved matters: binary search over values up to 10⁹ costs about 30 iterations whatever the array length, and binary search over the answer of a problem costs log(range) × the cost of the feasibility check.

Amortized analysis: paying for rare expensive steps

Some operations are usually cheap and occasionally very expensive. Appending to a Python list or a C# List<T> is one write, until the backing array is full. Then the whole array is copied into a block twice as big. A single append can cost O(n), yet n appends cost O(n) in total, so each append is O(1) amortized.

Run the appends and watch the cost of each one (bars) and the running average (purple line). Compare doubling, ×1.5 (what CPython and many C++ libraries do, trading copy cost for memory) and +4. The bank variable is the accounting method described below.

There are three ways to argue an amortized bound. They all give the same answer; pick whichever is easiest to explain.

Method Idea Dynamic array argument
Aggregate Bound the total cost of any sequence of m operations, then divide by m. Copies sum to 1 + 2 + 4 + … < 2m, writes are m, so total < 3m.
Banker's (accounting) Charge every operation a fixed price; cheap ones save the surplus, expensive ones spend it. The bank must never go negative. Charge 3: one for the write, two saved. When the array of size k is full, the k/2 items added since the last resize saved k credits, exactly enough to copy all k.
Potential Define a potential Φ of the data structure; amortized cost = actual cost + ΔΦ. Φ = 2·size − capacity. A resize drops Φ by about the copy cost.

The potential method on a binary counter

The potential method is the most general of the three, and a binary counter shows it cleanly. Incrementing a counter flips the trailing 1s to 0 and then one 0 to 1. Incrementing 0111 1111 flips 8 bits, but most increments flip only one or two.

def increment(bits: list[int]) -> int:
    """Add 1 to a little-endian list of bits; return how many bits flipped."""
    i = 0
    while i < len(bits) and bits[i] == 1:
        bits[i] = 0                  # each trailing 1 becomes 0 (the carry)
        i += 1
    if i == len(bits):
        bits.append(1)               # the counter grows by one bit
    else:
        bits[i] = 1
    return i + 1                     # i resets plus one set

bits, flips = [], 0
for _ in range(1000):
    flips += increment(bits)
print(flips)                         # 1994 < 2 · 1000

static int Increment(List<int> bits)            // little-endian; returns flips
{
    int i = 0;
    while (i < bits.Count && bits[i] == 1) bits[i++] = 0;   // the carry
    if (i == bits.Count) bits.Add(1); else bits[i] = 1;
    return i + 1;
}

static void CounterDemo()
{
    var bits = new List<int>();
    long flips = 0;
    for (int k = 0; k < 1000; k++) flips += Increment(bits);
    Console.WriteLine(flips);                   // 1994 < 2 · 1000
}

Let the potential Φ be the number of 1 bits. An increment that clears t trailing 1s does t + 1 actual flips, and changes Φ by −t (cleared) + 1 (set). Its amortized cost is actual + ΔΦ = (t + 1) + (1 − t) = 2, whatever t is. Φ starts at 0 and never goes negative, so m increments cost at most 2m flips in total. The expensive increments are paid for by the 1 bits that cheap increments left behind.

Amortized is not "average case"

Average case assumes something about the input (random data). It can be wrong on adversarial inputs: quicksort with a bad pivot, a hash table under collision attack.

Amortized is a worst-case guarantee

It holds for every sequence of operations: any m appends cost O(m) in total, whatever the data. Only individual operations may spike.

Amortized arguments are everywhere in interview problems. Each one rests on something that only moves forward or is removed at most once:

  • Two pointers and sliding windows: the left pointer moves at most n times in total.
  • Monotonic stack: each element is pushed once and popped at most once, so 2n stack operations in total. See Monotonic Stack & Queue.
  • Union-find with path compression and union by rank: nearly O(1) per operation (inverse Ackermann).
  • Hash table resizing: the same doubling argument as the dynamic array.

Pitfall Amortized bounds hide spikes. If one request out of a million may take 50 ms because a large list resizes, a latency-sensitive service will notice. When you know the final size, preallocate: [0] * n in Python, new List<int>(n) in C#.

Recursion trees and the Master theorem

A recursive algorithm's cost is a recurrence: T(n) = (work done by the calls) + (work done here). To solve one, draw the recursion tree. Each level lists its subproblems, and the cost is the sum of all levels.

For the common shape T(n) = a·T(n/b) + O(n^d) (a calls, each on a 1/b-sized input, plus n^d work outside the calls), level i has aⁱ subproblems of size n/bⁱ. So its work is aⁱ·(n/bⁱ)^d = n^d · (a/b^d)ⁱ. That is a geometric series with ratio a/b^d, and the ratio decides everything:

Case Condition Level work going down T(n) Examples
1 · root-heavy a < b^d (log_b a < d) shrinks Θ(n^d) T(n)=2T(n/4)+n → Θ(n); quickselect T(n/2)+n → Θ(n)
2 · balanced a = b^d equal on every level Θ(n^d log n) merge sort → Θ(n log n); binary search T(n/2)+1 → Θ(log n)
3 · leaf-heavy a > b^d grows Θ(n^(log_b a)) tree traversal 2T(n/2)+1 → Θ(n); Karatsuba 3T(n/2)+n → Θ(n^1.585)

Set a, b and d below and step through the levels. The bars on the right are each level's total work. Watch them shrink (case 1), stay flat (case 2) or grow (case 3). Randomize cycles through classic algorithms.

Not every recurrence fits a·T(n/b) + n^d. Draw the tree anyway:

Recurrence Tree Solution Where it shows up
T(n) = T(n−1) + 1 a chain of n calls Θ(n) linear recursion, recursive sum
T(n) = T(n−1) + n chain, level k costs n−k Θ(n²) selection sort, quicksort's worst case
T(n) = 2T(n−1) + 1 full binary tree of depth n Θ(2ⁿ) Towers of Hanoi, subsets
T(n) = T(n−1) + T(n−2) + 1 lopsided binary tree Θ(φⁿ) ≈ Θ(1.618ⁿ) naive Fibonacci (see Recursion)
T(n) = T(n/2) + n n + n/2 + n/4 + … Θ(n) quickselect (expected), median of medians
T(n) = T(√n) + 1 n, √n, n^¼ … Θ(log log n) van Emde Boas trees
T(n) = T(n/3) + T(2n/3) + n uneven tree, ≤ n per level, log₃/₂ n levels Θ(n log n) uneven splits (Akra–Bazzi handles these)

Tip For memoized recursion and DP, the recursion tree is the wrong picture. Count distinct states × work per state instead: memoized Fibonacci has n states and O(1) work each, so it is O(n), not O(2ⁿ).

Space complexity: the stack counts too

Space complexity counts the extra memory an algorithm needs on top of its input: arrays, hash maps, the output if you build it, and every stack frame that is alive at the same time. A recursive function that goes n calls deep uses O(n) stack even if it allocates nothing.

Choose a program and watch the stack and its depth over time. Fib makes many calls but never goes deeper than n; recursive binary search goes log n deep; the loop version never pushes a second frame.

Structure Extra space
A few counters and pointers O(1)
Recursion of depth d O(d), even with no allocations
Balanced divide and conquer (merge sort tree) O(log n) stack, plus merge sort's O(n) buffer
Hash map or set of seen items O(n) worst case, O(alphabet) for fixed alphabets
2-D DP table m × n O(m·n), often reducible to O(n) with a rolling row
Output of size k (all subsets, all paths) O(k), usually reported separately

Pitfall Deep recursion crashes before it gets slow. CPython's default recursion limit is 1,000 frames (RecursionError), and a .NET thread on Windows has 1 MB of stack by default (roughly ten to a hundred thousand small frames), and a StackOverflowException cannot be caught: the process dies. A DFS on a path-shaped graph or a degenerate tree with n = 10⁵ will crash in both. Use an explicit stack (see Recursion) or, in Python, sys.setrecursionlimit together with a bigger thread stack (threading.stack_size).

Best, worst, average and expected

"Quicksort is O(n log n)" is only half a statement. Which inputs are we talking about? The same code can have very different costs depending on the data it receives, so complexities come with a case attached:

Case Meaning Quicksort, first element as pivot Hash set lookup
Best the luckiest input of size n Θ(n log n): every pivot is the median Θ(1)
Worst the unluckiest input of size n Θ(n²): already sorted input, every split is 0 / n−1 Θ(n): every key in one bucket
Average averaged over a distribution of inputs (usually: all orders equally likely) Θ(n log n) Θ(1) with a good hash
Expected averaged over the algorithm's own coin flips, for the worst input Θ(n log n) with a random pivot Θ(1) with a randomised hash

When a complexity is quoted without a case, it means worst case, except for hashing, where O(1) means expected. Interviewers and judges care about the worst case because test sets include adversarial inputs: sorted arrays, all-equal values, and keys chosen to collide.

Average case: a bet on the input

Assumes the data is random. A judge that feeds sorted arrays to a first-element-pivot quicksort gets Θ(n²) every time, and nothing in the code can change that.

Expected case: a bet on your own dice

The algorithm randomises (random pivot, random hash seed). Every input is then fast with high probability, because an adversary cannot predict the coin flips. Python and .NET both randomise string hashes per process for this reason.

Pitfall A quicksort or quickselect with a fixed pivot (first, last or middle element) is a time bomb on sorted or crafted inputs. Pick the pivot with random.randint(lo, hi) / Random.Shared.Next(lo, hi + 1), and use three-way partitioning so that many equal values do not cause Θ(n²) either. Library sorts are already safe: Python's Timsort and .NET's introsort are O(n log n) in the worst case.

Several variables, and output-sensitive bounds

Many inputs have more than one size, and collapsing them into a single n hides the real cost. Keep every independent size in the bound until you know how they relate:

Input Typical bound Why it does not reduce to O(n)
Graph with V vertices and E edges, BFS / DFS O(V + E) E ranges from 0 to about V²; O(V²) and O(V) are both wrong in general
Same graph stored as an adjacency matrix O(V²) scanning a row costs V even when the vertex has 2 neighbours
m × n grid O(m·n) "n" usually means one side, so the grid has n² cells
n words of length up to L in a hash set O(n·L) hashing and comparing a string costs O(L), not O(1)
Sorting n strings of length L O(n·L·log n) each comparison may read the whole string
Two sorted arrays of sizes m and n, merge O(m + n) they can differ wildly: m = 5, n = 10⁶
Binary search of each of m queries in n items O(m log n) swap the roles and you get O(n log m): pick the cheaper
Top k of n with a heap O(n log k) equals O(n log n) only when k is close to n

Output-sensitive bounds. When the answer itself can be large, the cost depends on its size k as well as on n. Listing all subsets is Θ(n·2ⁿ) because that is how much output there is; no algorithm can do better. A range query on a sorted array that returns the k matching items is O(log n + k): the log n finds the start and the k copies out the answer. Write k into the bound, and say which part is the search and which part is the reporting.

Pitfall "O(n) with a hash set of words" is O(n·L), and the L matters. Word Ladder with 5,000 words of length 10 that tries 26 letters at each position computes 5,000 × 10 × 26 neighbour strings of length 10, about 1.3·10⁷ character operations. That is fine. Count it as "26 L² per word" and it is easy to see why L = 100 would not be.

Hidden costs: one line, many operations

Big-O analysis goes wrong most often on library calls that look like one step:

Code Looks like Actually Fix
Python x in some_list / C# list.Contains(x) O(1) O(n) scan use a set / HashSet<T>
Python lst.pop(0), lst.insert(0, x) / C# list.RemoveAt(0), Insert(0, x) O(1) O(n) shift collections.deque / Queue<T>, LinkedList<T>
Python s[i:j], lst[i:j] / C# s.Substring, list.GetRange O(1) O(j − i) copy pass indices; C# AsSpan() slices without copying
s += ch in a loop (C# string) O(n) total O(n²): a new string each time "".join(parts) / StringBuilder
sorted(...) / Array.Sort inside a loop O(1) O(n log n) each time sort once, or keep a heap / SortedSet
len(x), Count, Length O(1) O(1): stored fine
C# LINQ .Count() or .ElementAt(i) on a lazy query (after Where, Select), .ToList() O(1) O(n): re-runs the query materialise once; use List<T> indexing
Hash lookup with a bad hash (all keys collide) O(1) O(n) good hashes; tuples or records as keys, not mutable lists
max(lst) / lst.Max() each iteration O(1) O(n) maintain the max, or use a heap / monotonic deque
Building str(n) or BigInteger arithmetic on huge numbers O(1) O(digits) or worse keep numbers bounded (modular arithmetic)

Recognize the trap when

  • A loop body calls a method on a collection that is as big as the input.
  • The solution is "O(n)" but times out at n = 10⁵: look for a hidden O(n) inside the loop.
  • Strings are built up character by character, or sliced repeatedly in recursion.
  • Recursion passes arr[1:] or s[1:]: every call copies, turning O(n) into O(n²).

Lower bounds: knowing when to stop

Big-O gives an upper bound: the algorithm takes at most this long. A lower bound (Ω) says no algorithm can do better, and it tells you when to stop optimising. Three arguments cover most cases:

  1. You must read the input. If every item can change the answer, any correct algorithm is Ω(n). A max, a sum or a "does x appear" over unsorted data cannot be sublinear.
  2. You must write the output. Listing all permutations is Ω(n·n!), however clever the code.
  3. Each yes/no question halves the possibilities, at best. If there are N possible answers and each comparison has two outcomes, you need at least log₂ N comparisons in the worst case.

The third argument proves that comparison sorting needs Ω(n log n). An array of n distinct items can be in n! orders, and the algorithm must tell all of them apart. Each comparison splits the remaining candidates into two groups, so its decision tree needs n! leaves and therefore depth at least log₂(n!) ≈ n log₂ n − 1.44n.

Problem Lower bound Matching algorithm How to beat it (outside the model)
Find max / sum of unsorted data Ω(n) one pass impossible: must read every item
Search a sorted array by comparisons Ω(log n) binary search hashing gives O(1) expected for exact matches
Sort by comparisons Ω(n log n) merge sort, heapsort counting / radix sort, O(n + k), when keys are small integers
Element distinctness by comparisons Ω(n log n) sort, then scan neighbours a hash set, O(n) expected
Generate all subsets Ω(2ⁿ · n) output backtracking impossible: the output is that big

A lower bound holds only inside its model. "Sorting is Ω(n log n)" assumes the algorithm learns about the items only by comparing them. Counting sort reads the values as array indices, which is a different model, and it sorts n integers in [0, k) in O(n + k). When your solution matches the lower bound in the model you are using, stop optimising the complexity. Then either change the model (hashing, counting) or improve the constant factor.

Template: measure it with a doubling experiment

When you are unsure of the class, measure it. Run the code at n and 2n and take the ratio of the times: about 2 means O(n), a bit over 2 means O(n log n), about 4 means O(n²), about 8 means O(n³). The exponent is log₂(ratio). Timings are noisy (tiny n is dominated by overhead, large n by cache misses that push a linear ratio toward 2.5–3), so read the trend over several doublings rather than one ratio.

import random
import time

def doubling_experiment(solve, make_input, start=1_000, rounds=6):
    """Print time(2n) / time(n); the exponent of n is log2 of that ratio."""
    prev, n = None, start
    for _ in range(rounds):
        data = make_input(n)
        t0 = time.perf_counter()
        solve(data)
        t = time.perf_counter() - t0
        ratio = t / prev if prev else float("nan")
        print(f"n={n:>9,}  {t * 1000:9.2f} ms  ratio {ratio:5.2f}")
        prev, n = t, n * 2

# Example: has_duplicate with a set should print ratios near 2.
doubling_experiment(lambda a: len(set(a)) < len(a),
                    lambda n: [random.randrange(n) for _ in range(n)], start=100_000)

using System.Diagnostics;

static void DoublingExperiment(Action<int[]> solve, Func<int, int[]> makeInput,
                               int start = 1_000, int rounds = 6)
{
    double prev = double.NaN;
    for (int r = 0, n = start; r < rounds; r++, n *= 2)
    {
        int[] data = makeInput(n);
        solve(data);                                   // warm-up: JIT compiles the code
        var sw = Stopwatch.StartNew();
        solve(data);
        double ms = sw.Elapsed.TotalMilliseconds;
        Console.WriteLine($"n={n,9:N0}  {ms,9:F2} ms  ratio {ms / prev,5:F2}");
        prev = ms;
    }
}

// Example: a HashSet duplicate check should print ratios near 2.
var rng = new Random(1);
DoublingExperiment(a => _ = new HashSet<int>(a).Count < a.Length,
                   n => Enumerable.Range(0, n).Select(_ => rng.Next(n)).ToArray(), start: 100_000);

Measure with inputs large enough that each run takes at least tens of milliseconds, and in C# run once untimed first so the JIT has compiled the code. Small inputs measure noise, and the first .NET call measures compilation.

Worked analyses

Each problem shows how the analysis drives the solution: estimate the brute force, compare it with the budget, find what makes it slow, and prove the better bound.

1 · Contains Duplicate Easy

Return whether any value appears twice; n ≤ 10⁵. Three ideas, three classes. All pairs: n(n−1)/2 ≈ 5·10⁹ comparisons, too slow. Sort, then compare neighbours: O(n log n) ≈ 1.7·10⁶. A hash set: O(n) expected. The analysis also shows the trade: sorting needs O(1) extra space if you may modify the input; the set needs O(n).

Solution: three versions with their costs 
def has_dup_pairs(nums: list[int]) -> bool:          # O(n²) time, O(1) space
    n = len(nums)
    return any(nums[i] == nums[j] for i in range(n) for j in range(i + 1, n))

def has_dup_sort(nums: list[int]) -> bool:           # O(n log n) time
    s = sorted(nums)                                 # O(n) space for the copy
    return any(s[i] == s[i + 1] for i in range(len(s) - 1))

def has_dup_set(nums: list[int]) -> bool:            # O(n) expected time, O(n) space
    seen = set()
    for x in nums:
        if x in seen:                                # O(1) expected: a hash lookup
            return True
        seen.add(x)
    return False

public bool HasDupPairs(int[] nums)                  // O(n²) time, O(1) space
{
    for (int i = 0; i < nums.Length; i++)
        for (int j = i + 1; j < nums.Length; j++)
            if (nums[i] == nums[j]) return true;
    return false;
}

public bool HasDupSort(int[] nums)                   // O(n log n) time
{
    int[] s = (int[])nums.Clone();                   // O(n) space; sort in place for O(1)
    Array.Sort(s);
    for (int i = 0; i + 1 < s.Length; i++)
        if (s[i] == s[i + 1]) return true;
    return false;
}

public bool HasDupSet(int[] nums)                    // O(n) expected time, O(n) space
{
    var seen = new HashSet<int>();
    foreach (int x in nums)
        if (!seen.Add(x)) return true;               // Add returns false if present
    return false;
}

Replacing seen with a list makes x in seen an O(n) scan and silently brings back O(n²).

2 · Sqrt(x) Easy

Return ⌊√x⌋ for 0 ≤ x ≤ 2³¹ − 1 without a library square root.

Analysis. Trying k = 0, 1, 2, … until k² > x costs √x ≈ 46,341 steps: fine, but binary search over k ∈ [0, x] needs only log₂ 2³¹ = 31 steps. The predicate "k² ≤ x" is monotone (true, true, …, false), which is what binary search needs.

Solution: binary search on the answer, O(log x) time, O(1) space 
def my_sqrt(x: int) -> int:
    lo, hi = 0, x                  # invariant: lo*lo <= x < (hi+1)*(hi+1)
    while lo < hi:
        mid = (lo + hi + 1) // 2   # round up so lo = mid always makes progress
        if mid * mid <= x:
            lo = mid
        else:
            hi = mid - 1
    return lo

public int MySqrt(int x)
{
    long lo = 0, hi = x;           // long: mid * mid overflows int
    while (lo < hi)
    {
        long mid = (lo + hi + 1) / 2;
        if (mid * mid <= x) lo = mid;
        else hi = mid - 1;
    }
    return (int)lo;
}

Each iteration halves [lo, hi], so there are at most 32 iterations. In C# the product mid * mid needs long: 46,341² overflows a 32-bit int.

3 · Longest Consecutive Sequence Medium

Given an unsorted array (n ≤ 10⁵), return the length of the longest run of consecutive integers, in O(n).

Analysis. Sorting gives O(n log n), but the problem asks for O(n). Put everything in a set and walk forward from each number. That looks like O(n²): a loop with a while inside. The trick is to start walking only from numbers that begin a run (x − 1 is not in the set). Then each number is stepped over by exactly one walk, so the inner loop runs at most n times in total: an amortized argument.

Solution: set + walk from run starts, O(n) expected time, O(n) space 
def longest_consecutive(nums: list[int]) -> int:
    s = set(nums)
    best = 0
    for x in s:
        if x - 1 in s:             # not the start of a run: skip
            continue
        y = x
        while y + 1 in s:          # total over all starts: <= n steps
            y += 1
        best = max(best, y - x + 1)
    return best

public int LongestConsecutive(int[] nums)
{
    var s = new HashSet<int>(nums);
    int best = 0;
    foreach (int x in s)
    {
        if (s.Contains(x - 1)) continue;   // only walk from run starts
        int y = x;
        while (s.Contains(y + 1)) y++;     // each value visited by one walk
        best = Math.Max(best, y - x + 1);
    }
    return best;
}

Iterate over the set, not the array: with many duplicates of a run start, walking from every copy would be O(n²) again.

4 · Count Primes Medium

Count the primes below n, n ≤ 5·10⁶.

Analysis. Trial division up to √k for each k costs about n√n / 2 ≈ 5·10⁹: too slow. The sieve of Eratosthenes crosses out multiples of each prime p, starting from p². The work is n/2 + n/3 + n/5 + … over primes, which is n·(sum of 1/p) = O(n log log n), practically linear. Crossing out multiples of every number, not just primes, would be the harmonic sum n·(1 + ½ + ⅓ + …) = O(n log n), which is still fine. That is the harmonic loop shape from the counter above.

Solution: sieve of Eratosthenes, O(n log log n) time, O(n) space 
def count_primes(n: int) -> int:
    if n < 3:
        return 0
    is_prime = bytearray([1]) * n
    is_prime[0] = is_prime[1] = 0
    p = 2
    while p * p < n:                       # p only up to √n
        if is_prime[p]:
            # slice assignment crosses out p², p²+p, ... in C speed
            is_prime[p * p::p] = bytes(len(range(p * p, n, p)))
        p += 1
    return sum(is_prime)

public int CountPrimes(int n)
{
    if (n < 3) return 0;
    var composite = new bool[n];
    for (long p = 2; p * p < n; p++)
        if (!composite[p])
            for (long m = p * p; m < n; m += p)   // starts at p²: smaller ones done
                composite[m] = true;
    int count = 0;
    for (int k = 2; k < n; k++) if (!composite[k]) count++;
    return count;
}

The Python version uses slice assignment so that the inner loop runs in C. The class is the same as a Python for loop, but the constant is about 50× smaller, and that matters at 5·10⁶ in Python.

5 · Kth Largest Element in an Array Medium

Return the k-th largest of n ≤ 10⁵ numbers.

Analysis. Sorting: O(n log n). A min-heap of size k: O(n log k). Quickselect partitions around a random pivot and recurses into one side only: T(n) = T(n/2) + n on average, which is root-heavy (case 1), so O(n) expected. A bad pivot every time gives T(n) = T(n−1) + n = O(n²). A random pivot makes that astronomically unlikely, whatever the input.

Solution: heap O(n log k), and quickselect O(n) expected 
import heapq
import random

def kth_largest_heap(nums: list[int], k: int) -> int:
    heap = []                              # the k largest so far; root = smallest
    for x in nums:
        heapq.heappush(heap, x)
        if len(heap) > k:
            heapq.heappop(heap)            # O(log k)
    return heap[0]

def kth_largest_select(nums: list[int], k: int) -> int:
    target = len(nums) - k                 # index in ascending order
    lo, hi = 0, len(nums) - 1
    a = nums[:]
    while True:
        p = a[random.randint(lo, hi)]      # random pivot: expected O(n)
        lt = [x for x in a[lo:hi + 1] if x < p]
        eq = [x for x in a[lo:hi + 1] if x == p]
        gt = [x for x in a[lo:hi + 1] if x > p]
        a[lo:hi + 1] = lt + eq + gt        # 3-way split handles duplicates
        if target < lo + len(lt):
            hi = lo + len(lt) - 1
        elif target < lo + len(lt) + len(eq):
            return p
        else:
            lo = lo + len(lt) + len(eq)

public int KthLargestHeap(int[] nums, int k)
{
    var heap = new PriorityQueue<int, int>();          // min-heap by value
    foreach (int x in nums)
    {
        heap.Enqueue(x, x);
        if (heap.Count > k) heap.Dequeue();            // O(log k)
    }
    return heap.Peek();
}

public int KthLargestSelect(int[] nums, int k)
{
    int[] a = (int[])nums.Clone();
    int target = a.Length - k, lo = 0, hi = a.Length - 1;
    var rng = new Random();
    while (true)
    {
        int p = a[rng.Next(lo, hi + 1)];
        int lt = lo, i = lo, gt = hi;                  // Dutch-flag 3-way partition
        while (i <= gt)
        {
            if (a[i] < p) { (a[lt], a[i]) = (a[i], a[lt]); lt++; i++; }
            else if (a[i] > p) { (a[i], a[gt]) = (a[gt], a[i]); gt--; }
            else i++;
        }
        if (target < lt) hi = lt - 1;
        else if (target > gt) lo = gt + 1;
        else return p;
    }
}

The 3-way split matters: with many equal values, a 2-way partition can put almost everything on one side every time and degrade to O(n²).

6 · Search a 2D Matrix II Medium

Rows and columns of an m × n matrix are sorted ascending. Is target present?

Analysis. Binary search in each row: O(m log n). Better: start at the top-right corner. If the value is too big, the whole column below is too big, so move left; if too small, the whole row to the left is too small, so move down. Each step discards a row or a column, so there are at most m + n steps: O(m + n), the staircase shape again.

Solution: staircase search, O(m + n) time, O(1) space 
def search_matrix(matrix: list[list[int]], target: int) -> bool:
    r, c = 0, len(matrix[0]) - 1          # top-right corner
    while r < len(matrix) and c >= 0:
        v = matrix[r][c]
        if v == target:
            return True
        if v > target:
            c -= 1                        # column c is too big from row r down
        else:
            r += 1                        # row r is too small left of c
    return False

public bool SearchMatrix(int[][] matrix, int target)
{
    int r = 0, c = matrix[0].Length - 1;
    while (r < matrix.Length && c >= 0)
    {
        int v = matrix[r][c];
        if (v == target) return true;
        if (v > target) c--;              // discard a column
        else r++;                         // discard a row
    }
    return false;
}

r only increases and c only decreases. Bounding the total movement of each pointer is the whole proof, the same argument as in two pointers.

7 · Merge k Sorted Lists Hard

Merge k sorted linked lists with N nodes in total into one sorted list (k ≤ 10⁴, N ≤ 10⁵ or more).

Analysis. Three natural approaches, three different bounds, and they only separate when you keep both variables, N and k:

Approach Cost Why
Merge list 1 into list 2, the result into list 3, … O(N·k) with k equal lists of N/k, the growing result is re-read k times: N/k · (1 + 2 + … + k) ≈ N·k/2
Collect all values, sort, rebuild O(N log N) ignores the fact that the lists are already sorted
Min-heap holding the head of each list O(N log k) N pops and pushes on a heap that never holds more than k nodes
Merge pairs in rounds (tournament) O(N log k) log₂ k rounds, each one reads all N nodes once

With N = 10⁵ and k = 10⁴, sequential merging costs about 5·10⁸ node visits, while the heap needs about 10⁵ × 14 ≈ 1.4·10⁶ heap steps. When k is small (k = 2) all approaches are linear, which is why examples with two lists never reveal the difference.

Solution: a min-heap of list heads, O(N log k) time, O(k) extra space 
import heapq

def merge_k_lists(lists):
    # (value, list index, node): the index breaks ties, nodes are never compared
    heap = [(node.val, i, node) for i, node in enumerate(lists) if node]
    heapq.heapify(heap)                         # O(k)
    dummy = tail = ListNode()
    while heap:                                 # N iterations
        _, i, node = heapq.heappop(heap)        # O(log k)
        tail.next = node
        tail = node
        if node.next:
            heapq.heappush(heap, (node.next.val, i, node.next))
    return dummy.next

public ListNode? MergeKLists(ListNode?[] lists)
{
    var pq = new PriorityQueue<ListNode, int>();    // priority = node value
    foreach (var node in lists)
        if (node != null) pq.Enqueue(node, node.val);
    var dummy = new ListNode();
    var tail = dummy;
    while (pq.Count > 0)                            // N iterations
    {
        var node = pq.Dequeue();                    // O(log k)
        tail.next = node;
        tail = node;
        if (node.next != null) pq.Enqueue(node.next, node.next.val);
    }
    return dummy.next;
}

The heap holds at most one node per list, so it has at most k entries and each operation is O(log k). The nodes are relinked rather than copied, so the extra space is just the heap. In Python the list index i in the tuple matters: two equal values would otherwise make heapq compare two ListNodes and raise TypeError.

Recognize it, common costs, pitfalls

When complexity analysis decides the problem

  • The constraints are the hint. n ≤ 20 invites 2ⁿ, n ≤ 10⁵ demands O(n log n) or better, and n ≤ 10¹⁸ means O(log n) or a formula.
  • "Follow up: can you do it in O(n)?" means the obvious O(n log n) is not the intended answer.
  • A loop whose inner pointer never moves back (two pointers, sliding window, monotonic stack) is O(n) in total, even though it is nested.
  • "Repeatedly halve", "double until", "the answer is monotone" mean a log factor.
  • The same subproblem is recomputed in a recursion tree, which means memoization turns exponential into polynomial.

The costs you will use most often:

Operation Python C# Cost
Index, append, pop at end a[i], a.append, a.pop() list[i], Add, RemoveAt(Count-1) O(1), append amortized
Insert or delete at front or middle a.insert(0, x), a.pop(0) Insert(0, x), RemoveAt(0) O(n)
Both ends collections.deque LinkedList<T>, or a ring buffer O(1)
Membership in a list x in a list.Contains(x) O(n)
Hash set or map: add, find, remove set, dict HashSet<T>, Dictionary<K,V> O(1) expected, O(n) worst
Sorted map: add, find, floor or ceiling sortedcontainers (not built in) SortedSet<T>, SortedDictionary O(log n)
Heap push, pop heapq.heappush, heappop PriorityQueue<T,P> O(log n); peek O(1)
Build a heap from n items heapq.heapify new PriorityQueue(items) O(n)
Sort sorted, list.sort Array.Sort, List.Sort O(n log n)
Slice or copy k items a[i:j], s[i:j] Substring, AsSpan (no copy) O(k); a span is O(1)
String concatenation in a loop s += c s += c O(n²) total; use "".join or StringBuilder

Pitfalls that cost the most

  • Dropping a term that is not small. O(n + m) is not O(n) when m (edges, the length of a second string, the value range) can be bigger than n.
  • Forgetting the cost of building keys. Hashing a string of length L costs O(L); so does tuple(state) as a memo key. A memo with n states and O(L) keys is O(n·L).
  • Confusing amortized with worst case. A single append can cost O(n). Usually harmless, but it matters for latency-sensitive code and for "every operation in O(1)" designs.
  • Treating expected as guaranteed. Hash tables and quickselect are fast in expectation; adversarial inputs (anti-hash tests in contests) can break unrandomized versions.
  • Ignoring the recursion stack. A "O(1) space" recursive solution uses O(depth) stack, and deep recursion crashes Python at about 1,000 frames.
  • Counting the output as free. Generating all subsets is Ω(n·2ⁿ) because that is the size of the output, whatever the algorithm.

Self-check

One loop does 2n steps and another does n + 1,000,000 steps. Are both O(n)? Is either one slow?

Both are O(n): constants and added constants disappear in Big-O. That does not make them equally fast. For n = 1,000, the second does about 1,000× more work; for n = 10⁸ the difference is under 1%. Big-O tells you how cost grows; for a fixed n, compare actual counts.

What does this cost? for i in range(1, n + 1): for j in range(i, n + 1, i): work()

The inner loop runs n/i times for each i, so the total is n·(1 + ½ + ⅓ + … + 1/n) ≈ n·ln n = O(n log n). This is the harmonic loop shape. It is how "for each d, visit all multiples of d" (divisor sums, sieves) stays fast.

Building a string of length n with s += c in a loop: what is the cost, and why?

Strings are immutable in both Python and C#, so each += copies the whole string so far: 1 + 2 + … + n = O(n²). (CPython sometimes optimizes in-place appends, but do not rely on it.) Collect the pieces in a list and "".join them, or use StringBuilder in C#: O(n) total, by the same doubling argument as dynamic arrays.

Solve with the Master theorem: T(n) = 3T(n/3) + n, T(n) = 4T(n/2) + n², T(n) = T(n/2) + 1.

Compare d with log_b a:

  • 3T(n/3) + n: log₃ 3 = 1 = d, balanced → Θ(n log n).
  • 4T(n/2) + n²: log₂ 4 = 2 = d, balanced → Θ(n² log n).
  • T(n/2) + 1: log₂ 1 = 0 = d, balanced → Θ(log n) (binary search).

Check the first one in the Master theorem player above with a = 3, b = 3, d = 1.

Your recursive DFS is O(n) time and passes small tests, but crashes on n = 10⁵. Why, and what is the fix?

The recursion depth equals the longest path, which can be n on a path-shaped graph or degenerate tree. Python stops at about 1,000 frames (RecursionError); C# overflows its stack and kills the process. Time was never the problem, stack space was. Rewrite with an explicit stack (a list or Stack<T>), which lives on the heap, or raise the limit and stack size in Python.

Dynamic array append, hash set lookup, quickselect: which is amortized O(1)/O(n), which is expected, and what is the difference?
  • Append is amortized O(1): a guarantee about any sequence of m operations (total ≤ 3m), even though one append can cost O(n). No randomness involved.
  • Hash lookup is expected O(1): an average over the hash function's behaviour; a bad set of keys can make every lookup O(n).
  • Quickselect is expected O(n): an average over the random pivots; every input is fine on average, but an unlucky run can take O(n²).

Amortized bounds are worst-case over a sequence; expected bounds are averages over chance.

Your solution sorts n integers with a comparison sort and then scans once: O(n log n). Can any comparison-based method do better? Can anything?

Not with comparisons: sorting by comparisons is Ω(n log n), because the decision tree needs n! leaves. Leaving the model can help. If the values are integers in a small range [0, k), counting sort runs in O(n + k). If you only needed sorting to find duplicates or pairs, a hash set answers that in O(n) expected without sorting at all.
