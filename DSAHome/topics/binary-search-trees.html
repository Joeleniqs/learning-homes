TREES

Binary Search Trees

Search, insert and delete visualized; validating with bounds, inorder tricks, k-th smallest, and why balance matters.

Beginner → Advanced~45 min studyBuilds on: Tree TraversalsUpdated 2026-11-03

A binary search tree is binary search that you can keep editing. A sorted array answers "is x here?", "what comes just before x?" and "what is the 5th smallest?" in O(log n), but inserting one key costs O(n) because everything after it shifts. A BST stores the same sorted order as shape: smaller keys go left, larger keys go right. Each comparison still throws away half the candidates, and an insert or delete only touches one root-to-leaf path. This page shows every operation step by step: the comparison path, the window of values each node is allowed to hold, the three delete cases, the rotations that keep the tree short, and the library classes (C# SortedSet, Python bisect and SortedList) that do all of it for you in an interview.

The invariant. For every node v, every key in v's left subtree is smaller than v, and every key in v's right subtree is larger. Two consequences carry the whole topic: (1) at any node you know which side x must be on, so search, insert and delete walk a single path and cost O(h); (2) an inorder traversal visits the keys in sorted order. h is about log₂ n when the tree is balanced, and n when it degenerates into a chain.

Prerequisites: Tree Traversals (the TreeNode class, the level-order array format, iterative inorder) and Binary Search (a BST search is binary search on a linked structure). Recursion & the Call Stack explains the "return the new subtree" style used by insert and delete. Later: Tree Problem Patterns for general LCA, diameter and serialization, and Hashing for when you need membership only and not order.

The invariant in one picture

Read the picture twice. Top-down, it is a decision tree: to find 7, compare with 8 (go left), with 3 (go right), with 6 (go right), done. Bottom-up, it is a sorted list folded into a tree: drop every node straight down and the keys land in the order 1, 3, 4, 6, 7, 8, 10, 13, 14. That projection is exactly what an inorder traversal reads.

Operation Sorted array Hash set BST (balanced) BST (degenerate)
contains(x) O(log n) O(1) average O(log n) O(n)
insert / delete O(n) (shift) O(1) average O(log n) O(n)
min / max O(1) O(n) O(log n) O(n)
floor / ceiling / successor O(log n) O(n) O(log n) O(n)
k-th smallest / rank O(1) / O(log n) O(n log n) O(log n) with sizes O(n)
iterate in order O(n) O(n log n) (sort) O(n) O(n)

The BST column is why ordered sets exist. Whenever a problem mixes updates with order questions (nearest value, how many smaller, next free slot, k-th), a balanced BST or its library version is usually the tool.

Duplicates. The textbook BST stores distinct keys, and LeetCode BST problems almost always promise that. If you must allow repeats, pick one convention and apply it everywhere: "equal goes right" (left is strictly smaller, right is greater or equal), or store a count field in the node. Validation, search and delete must all use the same rule, otherwise a duplicate ends up on the side your search never looks at.

Search, floor and ceiling

To search for x, start at the root. If x equals the node, stop. If x is smaller, everything in the right subtree is even bigger, so the right subtree cannot contain x: go left. Otherwise go right. Fall off the tree and x is not present. That is binary search, except that "the middle" is whatever key sits at the current node.

Floor (largest key ≤ x) and ceiling (smallest key ≥ x) use the same walk with one extra variable. When the current key is smaller than x, it is a floor candidate, and a better one could only be further right. When it is bigger than x, it is a ceiling candidate and a better one could only be further left. Remember the latest candidate; when you fall off the tree it is the answer. The visualizer dims every subtree a comparison rules out.

Try x = 13 with floor: the walk goes 20 (too big), 8 (candidate, go right), 12 (better candidate, go right), 14 (too big, go left), 13 is missing, so it falls off and returns 12. Switch to ceiling and the same path collects 20, then 14. Every candidate you remember sits on the path you walked, which is why one O(h) walk is enough.

def search_bst(root, x):
    cur = root
    while cur and cur.val != x:
        cur = cur.left if x < cur.val else cur.right     # the other side cannot contain x
    return cur                                           # the node, or None


def floor_bst(root, x):
    """Largest key <= x, or None."""
    best, cur = None, root
    while cur:
        if cur.val == x:
            return x
        if cur.val < x:
            best = cur.val           # a candidate; a closer one can only be to the right
            cur = cur.right
        else:
            cur = cur.left
    return best


def ceiling_bst(root, x):
    """Smallest key >= x, or None."""
    best, cur = None, root
    while cur:
        if cur.val == x:
            return x
        if cur.val > x:
            best = cur.val           # a candidate; a closer one can only be to the left
            cur = cur.left
        else:
            cur = cur.right
    return best

public static class BstSearch
{
    public static TreeNode Search(TreeNode root, int x)
    {
        var cur = root;
        while (cur is not null && cur.val != x)
            cur = x < cur.val ? cur.left : cur.right;
        return cur;
    }

    // Largest key <= x, or null.
    public static int? Floor(TreeNode root, int x)
    {
        int? best = null;
        for (var cur = root; cur is not null; )
        {
            if (cur.val == x) return x;
            if (cur.val < x) { best = cur.val; cur = cur.right; }
            else cur = cur.left;
        }
        return best;
    }

    // Smallest key >= x, or null.
    public static int? Ceiling(TreeNode root, int x)
    {
        int? best = null;
        for (var cur = root; cur is not null; )
        {
            if (cur.val == x) return x;
            if (cur.val > x) { best = cur.val; cur = cur.left; }
            else cur = cur.right;
        }
        return best;
    }
}

Min and max are the two extreme walks: keep going left (or right) until there is no child. Lower (largest key strictly below x) and higher (smallest key strictly above x) are floor and ceiling without the == x early return: treat equality as "too big" for lower and "too small" for higher.

Insert: follow the search, attach where it falls off

A new key goes exactly where an unsuccessful search for it ends. Walk down as if searching; when the next child pointer is empty, hang a new leaf there. Nothing else moves, so the invariant still holds everywhere: the new key was compared with every ancestor and went to the correct side of each.

The strip under the tree is the sorted list of keys inserted so far. Each comparison narrows the window of values the new key could have, from (−∞, ∞) to an interval between two neighbours; the leaf you create is the gap between its predecessor and successor.

Now change "insertion order" to sorted (worst case) below. The same keys, inserted smallest first, produce a chain leaning right: every new key is bigger than everything so far, so it walks the whole spine. Inserting n sorted keys costs 1 + 2 + … + n = O(n²) comparisons, and every later search is O(n).

def insert_into_bst(root, x):
    """LeetCode 701. Iterative: O(h) time, O(1) extra space."""
    node = TreeNode(x)
    if root is None:
        return node
    cur = root
    while True:
        if x < cur.val:
            if cur.left is None:
                cur.left = node
                return root
            cur = cur.left
        else:
            if cur.right is None:
                cur.right = node
                return root
            cur = cur.right


def insert_rec(node, x):
    """Recursive: return the (possibly new) root of this subtree."""
    if node is None:
        return TreeNode(x)
    if x < node.val:
        node.left = insert_rec(node.left, x)     # re-link: the child may have been None
    else:
        node.right = insert_rec(node.right, x)
    return node

public static class BstInsert
{
    public static TreeNode InsertIntoBST(TreeNode root, int x)
    {
        var node = new TreeNode(x);
        if (root is null) return node;
        var cur = root;
        while (true)
        {
            if (x < cur.val)
            {
                if (cur.left is null) { cur.left = node; return root; }
                cur = cur.left;
            }
            else
            {
                if (cur.right is null) { cur.right = node; return root; }
                cur = cur.right;
            }
        }
    }

    public static TreeNode InsertRec(TreeNode node, int x)
    {
        if (node is null) return new TreeNode(x);
        if (x < node.val) node.left = InsertRec(node.left, x);
        else node.right = InsertRec(node.right, x);
        return node;
    }
}

The recursive version shows a pattern you will reuse for delete, trim and AVL insert: the function returns the root of the subtree after the change, and the caller stores it back (node.left = insert_rec(node.left, x)). It removes every "is this the root? which side was I on?" special case, because each call only ever fixes its own subtree.

Delete: three cases

Deleting is the only BST operation with real thinking in it. Find the node, then look at its children.

  1. Leaf. Remove it: the parent's pointer becomes None.
  2. One child. Splice it out: the parent points straight to the only child. That child's subtree was already on the correct side of the parent (it sat inside the deleted node's window, which is inside the parent's), so the invariant survives.
  3. Two children. You cannot splice, because two subtrees need one parent slot. Replace the key with its inorder successor, the smallest key in the right subtree. The successor is bigger than everything on the left (it came from the right) and smaller than everything else on the right (it is the minimum there), so it is the one key that fits. Then delete the successor from the right subtree, which is case 1 or 2: the successor is the leftmost node, so it has no left child. The predecessor (largest on the left) works just as well.

The visualizer runs the recursive LeetCode 450 solution. The cards on the right are the call stack: each call returns the new root of its subtree and the caller re-links it.

Try deleting 50 (the root, two children), 20 (a leaf), 40 (two children whose successor 45 is a leaf) and 70.

def delete_node(root, key):
    """LeetCode 450. Copies the successor's key into the node. O(h)."""
    if root is None:
        return None                                  # key not in the tree
    if key < root.val:
        root.left = delete_node(root.left, key)
    elif key > root.val:
        root.right = delete_node(root.right, key)
    else:
        if root.left is None:                        # leaf, or right child only
            return root.right
        if root.right is None:                       # left child only
            return root.left
        succ = root.right                            # two children:
        while succ.left:                             #   leftmost of the right subtree
            succ = succ.left
        root.val = succ.val                          #   copy the key up
        root.right = delete_node(root.right, succ.val)   # and remove the old copy
    return root


def delete_node_relink(root, key):
    """Same result, but moves the successor NODE instead of copying its value."""
    if root is None:
        return None
    if key < root.val:
        root.left = delete_node_relink(root.left, key)
    elif key > root.val:
        root.right = delete_node_relink(root.right, key)
    else:
        if root.left is None:
            return root.right
        if root.right is None:
            return root.left
        parent, succ = root, root.right
        while succ.left:
            parent, succ = succ, succ.left
        if parent is not root:
            parent.left = succ.right                 # unhook succ (it has no left child)
            succ.right = root.right
        succ.left = root.left
        return succ                                  # succ takes root's place
    return root

public static class BstDelete
{
    public static TreeNode DeleteNode(TreeNode root, int key)
    {
        if (root is null) return null;
        if (key < root.val) root.left = DeleteNode(root.left, key);
        else if (key > root.val) root.right = DeleteNode(root.right, key);
        else
        {
            if (root.left is null) return root.right;
            if (root.right is null) return root.left;
            var succ = root.right;
            while (succ.left is not null) succ = succ.left;
            root.val = succ.val;
            root.right = DeleteNode(root.right, succ.val);
        }
        return root;
    }

    public static TreeNode DeleteNodeRelink(TreeNode root, int key)
    {
        if (root is null) return null;
        if (key < root.val) { root.left = DeleteNodeRelink(root.left, key); return root; }
        if (key > root.val) { root.right = DeleteNodeRelink(root.right, key); return root; }
        if (root.left is null) return root.right;
        if (root.right is null) return root.left;
        TreeNode parent = root, succ = root.right;
        while (succ.left is not null) { parent = succ; succ = succ.left; }
        if (parent != root)
        {
            parent.left = succ.right;
            succ.right = root.right;
        }
        succ.left = root.left;
        return succ;
    }
}

Copying the value is shorter and is what most interview answers do. Re-linking matters when nodes carry more than a key (satellite data, or outside references to node objects that must stay valid): after a value copy, the node object that held 50 now holds 60, which surprises any caller still pointing at it.

Successor and predecessor

Delete needed the successor of a node with a right subtree. In general there are two cases, and the top-down version handles both without parent pointers: walk from the root as if searching for p, and every time you turn left at a node, that node is bigger than p and becomes the best successor so far. It is just "higher(p)" from the search section.

def inorder_successor(root, p):
    """LeetCode 285: the node with the smallest key > p.val, or None. O(h)."""
    succ, cur = None, root
    while cur:
        if p.val < cur.val:
            succ = cur          # bigger than p: candidate; look left for a closer one
            cur = cur.left
        else:
            cur = cur.right
    return succ


def inorder_predecessor(root, p):
    pred, cur = None, root
    while cur:
        if p.val > cur.val:
            pred = cur          # smaller than p: candidate; look right for a closer one
            cur = cur.right
        else:
            cur = cur.left
    return pred

public static class BstNeighbors
{
    public static TreeNode InorderSuccessor(TreeNode root, TreeNode p)
    {
        TreeNode succ = null;
        for (var cur = root; cur is not null; )
        {
            if (p.val < cur.val) { succ = cur; cur = cur.left; }
            else cur = cur.right;
        }
        return succ;
    }

    public static TreeNode InorderPredecessor(TreeNode root, TreeNode p)
    {
        TreeNode pred = null;
        for (var cur = root; cur is not null; )
        {
            if (p.val > cur.val) { pred = cur; cur = cur.right; }
            else cur = cur.left;
        }
        return pred;
    }
}

With parent pointers (LeetCode 510) you can do it from the node itself: if it has a right child, go right once and then left to the bottom; otherwise climb while you are a right child, and the next parent is the answer.

Validate: windows, not parents

The most common BST bug is checking only each node against its children. The tree below passes that check and is not a BST.

The fix is to pass down a window (lo, hi). The root may be anything. Going left, the upper bound tightens to the parent's key; going right, the lower bound tightens. Every node must sit strictly inside the window it inherits, and that window encodes every ancestor's constraint at once. The visualizer prints each node's window beneath it; try the default tree, where 6 sits under 7 (fine locally) but in 10's right subtree.

import math


def is_valid_bst(root):
    """LeetCode 98, recursive bounds. O(n) time, O(h) stack."""
    def ok(node, lo, hi):
        if node is None:
            return True
        if not (lo < node.val < hi):
            return False
        return ok(node.left, lo, node.val) and ok(node.right, node.val, hi)
    return ok(root, -math.inf, math.inf)

public static class BstValidate
{
    // Nullable bounds: no sentinel can collide with int.MinValue / int.MaxValue keys.
    public static bool IsValidBST(TreeNode root) => Ok(root, null, null);

    static bool Ok(TreeNode node, int? lo, int? hi)
    {
        if (node is null) return true;
        if ((lo is int a && node.val <= a) || (hi is int b && node.val >= b)) return false;
        return Ok(node.left, lo, node.val) && Ok(node.right, node.val, hi);
    }
}

Sentinel bounds overflow. LeetCode 98 includes nodes equal to int.MinValue and int.MaxValue. Starting with lo = int.MinValue and the test node.val > lo wrongly rejects a node holding int.MinValue. Use nullable bounds (above), long bounds, or Python's math.inf. Equally valid: an inorder traversal that checks each key is strictly bigger than the previous one (worked problem 1).

Inorder is sorted order: iterators, k-th smallest, rank

Because inorder visits a BST in sorted order, every "sorted" question becomes a traversal question: the k-th smallest is the k-th node inorder, two keys that sum to a target can be found with two inorder streams (one forward, one backward), the minimum gap between keys is the minimum gap between inorder neighbours, and a corrupted BST shows up as a dip in the inorder sequence.

The iterative inorder from Tree Traversals can be cut into pieces and resumed, which is exactly what an iterator is. Keep a stack holding the left spine; next() pops the smallest remaining node, then pushes the left spine of its right subtree. Each node is pushed and popped once, so n calls cost O(n) total: O(1) amortised per call, O(h) memory.

class BSTIterator:
    """LeetCode 173."""

    def __init__(self, root):
        self.stack = []
        self._push_left(root)

    def _push_left(self, node):
        while node:
            self.stack.append(node)
            node = node.left

    def next(self) -> int:
        node = self.stack.pop()              # smallest key not yet returned
        self._push_left(node.right)          # its successors come next
        return node.val

    def hasNext(self) -> bool:
        return bool(self.stack)


def kth_smallest(root, k):
    """LeetCode 230. Stops after k pops: O(h + k)."""
    stack, cur = [], root
    while True:
        while cur:
            stack.append(cur)
            cur = cur.left
        cur = stack.pop()
        k -= 1
        if k == 0:
            return cur.val
        cur = cur.right

public class BSTIterator
{
    private readonly Stack<TreeNode> stack = new();

    public BSTIterator(TreeNode root) => PushLeft(root);

    private void PushLeft(TreeNode node)
    {
        for (; node is not null; node = node.left) stack.Push(node);
    }

    public int Next()
    {
        var node = stack.Pop();
        PushLeft(node.right);
        return node.val;
    }

    public bool HasNext() => stack.Count > 0;
}

public static class KthSmallestBst
{
    public static int KthSmallest(TreeNode root, int k)
    {
        var stack = new Stack<TreeNode>();
        var cur = root;
        while (true)
        {
            for (; cur is not null; cur = cur.left) stack.Push(cur);
            cur = stack.Pop();
            if (--k == 0) return cur.val;
            cur = cur.right;
        }
    }
}

Reverse inorder (right, node, left) visits keys from largest to smallest. LeetCode 538/1038 "Convert BST to Greater Tree" is one reverse inorder pass with a running sum: each node becomes itself plus everything bigger.

def convert_bst(root):
    """LeetCode 538: node.val += sum of all larger keys."""
    running, stack, cur = 0, [], root
    while stack or cur:
        while cur:
            stack.append(cur)
            cur = cur.right          # mirror of inorder: right spine first
        cur = stack.pop()
        running += cur.val
        cur.val = running
        cur = cur.left
    return root

public static class GreaterTree
{
    public static TreeNode ConvertBST(TreeNode root)
    {
        int running = 0;
        var stack = new Stack<TreeNode>();
        var cur = root;
        while (stack.Count > 0 || cur is not null)
        {
            for (; cur is not null; cur = cur.right) stack.Push(cur);
            cur = stack.Pop();
            running += cur.val;
            cur.val = running;
            cur = cur.left;
        }
        return root;
    }
}

Order statistics: k-th in O(h) with subtree sizes

The inorder walk costs O(h + k), which is O(n) for k near n. LeetCode 230's follow-up asks: what if the tree is modified often and you query k-th often? Augment each node with the size of its subtree. Then at any node the rank of that node inside its subtree is size(left) + 1, and you know which side the k-th key is on without visiting the other side.

The code is in worked problem 3 below.

This only helps if h stays small, so in practice the sizes live inside a balanced tree, and rotations must recompute the size of the two nodes they move (size = 1 + size(left) + size(right)). The same "store a summary of the subtree in the node" idea gives segment trees; see Segment Trees, Fenwick Trees & Sparse Tables, which are often the easier way to answer rank queries over a fixed range of values.

Range queries: prune whole subtrees

To sum (or list, or count) the keys in [lo, hi], a plain traversal visits all n nodes. The invariant lets you skip subtrees: if a node is below lo, its whole left subtree is even smaller, so only its right subtree can contribute; symmetrically above hi. Only nodes on the two boundary paths and the nodes actually inside the range are visited: O(h + m) for m reported keys.

Dimmed subtrees were never entered. Shrink the range to lo = 13, hi = 13 and the walk becomes a single search.

def range_sum_bst(node, lo, hi):
    """LeetCode 938."""
    if node is None:
        return 0
    if node.val < lo:
        return range_sum_bst(node.right, lo, hi)     # node and its left side too small
    if node.val > hi:
        return range_sum_bst(node.left, lo, hi)      # node and its right side too big
    return node.val + range_sum_bst(node.left, lo, hi) + range_sum_bst(node.right, lo, hi)


def trim_bst(node, lo, hi):
    """LeetCode 669: drop every key outside [lo, hi], return the new root."""
    if node is None:
        return None
    if node.val < lo:
        return trim_bst(node.right, lo, hi)          # node goes, and its whole left side
    if node.val > hi:
        return trim_bst(node.left, lo, hi)
    node.left = trim_bst(node.left, lo, hi)
    node.right = trim_bst(node.right, lo, hi)
    return node

public static class BstRange
{
    public static int RangeSumBST(TreeNode node, int lo, int hi)
    {
        if (node is null) return 0;
        if (node.val < lo) return RangeSumBST(node.right, lo, hi);
        if (node.val > hi) return RangeSumBST(node.left, lo, hi);
        return node.val + RangeSumBST(node.left, lo, hi) + RangeSumBST(node.right, lo, hi);
    }

    public static TreeNode TrimBST(TreeNode node, int lo, int hi)
    {
        if (node is null) return null;
        if (node.val < lo) return TrimBST(node.right, lo, hi);
        if (node.val > hi) return TrimBST(node.left, lo, hi);
        node.left = TrimBST(node.left, lo, hi);
        node.right = TrimBST(node.right, lo, hi);
        return node;
    }
}

Trim is "return the new subtree root" again: when a node falls outside the range, the answer for its position is the trimmed version of its one surviving side, which slots straight into the parent's pointer.

Lowest common ancestor in a BST

In a general binary tree the LCA needs a full postorder search (see Tree Problem Patterns). In a BST, keys tell you where p and q are. While both are smaller than the current node, both live on the left, so the LCA does too; while both are bigger, go right. The first node where they split (one on each side, or the node equals one of them) is the lowest node that has both below it.

def lowest_common_ancestor(root, p, q):
    """LeetCode 235. O(h) time, O(1) space."""
    cur = root
    while cur:
        if p.val < cur.val and q.val < cur.val:
            cur = cur.left
        elif p.val > cur.val and q.val > cur.val:
            cur = cur.right
        else:
            return cur          # split point, or cur is p or q
    return None

public static class BstLca
{
    public static TreeNode LowestCommonAncestor(TreeNode root, TreeNode p, TreeNode q)
    {
        var cur = root;
        while (cur is not null)
        {
            if (p.val < cur.val && q.val < cur.val) cur = cur.left;
            else if (p.val > cur.val && q.val > cur.val) cur = cur.right;
            else return cur;
        }
        return null;
    }
}

The distance between two keys in a BST follows directly: depth(p) + depth(q) − 2 · depth(LCA), each depth being one search from the LCA.

Building a balanced BST from sorted data

Given sorted keys, the best possible tree puts the middle key at the root, so each side gets half. Recurse on both halves and every root-to-leaf path has length ⌊log₂ n⌋ or so. This is binary search's recursion tree, frozen into nodes.

def sorted_array_to_bst(nums):
    """LeetCode 108. O(n): every key becomes one node."""
    def build(lo, hi):                   # inclusive range
        if lo > hi:
            return None
        mid = (lo + hi) // 2
        node = TreeNode(nums[mid])
        node.left = build(lo, mid - 1)
        node.right = build(mid + 1, hi)
        return node
    return build(0, len(nums) - 1)


def balance_bst(root):
    """LeetCode 1382: flatten by inorder (sorted!), then rebuild."""
    vals, stack, cur = [], [], root
    while stack or cur:
        while cur:
            stack.append(cur)
            cur = cur.left
        cur = stack.pop()
        vals.append(cur.val)
        cur = cur.right
    return sorted_array_to_bst(vals)

public static class BuildBalanced
{
    public static TreeNode SortedArrayToBST(int[] nums) => Build(nums, 0, nums.Length - 1);

    static TreeNode Build(int[] a, int lo, int hi)
    {
        if (lo > hi) return null;
        int mid = lo + (hi - lo) / 2;
        return new TreeNode(a[mid], Build(a, lo, mid - 1), Build(a, mid + 1, hi));
    }

    public static TreeNode BalanceBST(TreeNode root)
    {
        var vals = new List<int>();
        var stack = new Stack<TreeNode>();
        for (var cur = root; stack.Count > 0 || cur is not null; )
        {
            for (; cur is not null; cur = cur.left) stack.Push(cur);
            cur = stack.Pop();
            vals.Add(cur.val);
            cur = cur.right;
        }
        return SortedArrayToBST(vals.ToArray());
    }
}

Rebuilding from scratch is O(n), which is fine once but far too slow after every insert. That is the job of self-balancing trees.

Why balance matters, and how trees stay balanced

A plain BST has no control over its own shape. Every operation is O(h), and h depends only on the insertion order. Random orders give an expected height of about 2.99 · log₂ n, but real inputs are often sorted, nearly sorted, or adversarial (a LeetCode test with 10⁵ increasing keys turns your O(n log n) solution into O(n²) and your recursion into a stack overflow). Self-balancing trees repair the shape after each insert or delete in O(log n) extra work, using one primitive.

Rotations

A rotation changes which of two nodes is the parent while keeping the inorder sequence fixed, so the BST property cannot break. A right rotation at z moves the left child y up, z down to the right, and hands y's right subtree B over to z as its new left subtree (B's keys are between y and z, so it belongs there). Left rotation is the mirror. Every balanced-tree scheme (AVL, red-black, treap, splay) is a policy for when to rotate.

class AVLNode:
    def __init__(self, val):
        self.val, self.left, self.right, self.height = val, None, None, 1


def height(n):
    return n.height if n else 0


def update(n):
    n.height = 1 + max(height(n.left), height(n.right))


def rotate_right(z):
    y = z.left
    z.left = y.right            # B moves across
    y.right = z
    update(z)                   # z is now below y: fix it first
    update(y)
    return y                    # caller re-links: parent.child = rotate_right(z)


def rotate_left(z):
    y = z.right
    z.right = y.left
    y.left = z
    update(z)
    update(y)
    return y

public class AVLNode
{
    public int val, height = 1;
    public AVLNode left, right;
    public AVLNode(int v) => val = v;
}

public static class Rotations
{
    public static int Height(AVLNode n) => n?.height ?? 0;
    public static void Update(AVLNode n) => n.height = 1 + Math.Max(Height(n.left), Height(n.right));

    public static AVLNode RotateRight(AVLNode z)
    {
        var y = z.left;
        z.left = y.right;
        y.right = z;
        Update(z);
        Update(y);
        return y;
    }

    public static AVLNode RotateLeft(AVLNode z)
    {
        var y = z.right;
        z.right = y.left;
        y.left = z;
        Update(z);
        Update(y);
        return y;
    }
}

AVL trees: heights differ by at most one

An AVL tree stores each node's height and keeps the balance factor height(left) − height(right) in {−1, 0, +1} at every node. After an ordinary insert, walk back up the path (the recursion unwinding does this for free) and update heights. The first node whose balance reaches ±2 is fixed with one or two rotations, depending on the shape of the path from it to the new key.

Watch the visualizer insert 10, 20, 30: a straight right-right line, so one left rotation at 10. Then 25 and 28 create a zig-zag under 30 (left, then right: LR), fixed by two rotations. Every frame shows each node's height and balance underneath it; red marks the node that tipped over.

def avl_insert(node, x):
    if node is None:
        return AVLNode(x)
    if x < node.val:
        node.left = avl_insert(node.left, x)
    elif x > node.val:
        node.right = avl_insert(node.right, x)
    else:
        return node                                  # no duplicates
    update(node)
    b = height(node.left) - height(node.right)
    if b > 1:                                        # left side too tall
        if x > node.left.val:                        # LR: straighten the zig-zag first
            node.left = rotate_left(node.left)
        return rotate_right(node)                    # LL
    if b < -1:                                       # right side too tall
        if x < node.right.val:                       # RL
            node.right = rotate_right(node.right)
        return rotate_left(node)                     # RR
    return node

public static class Avl
{
    public static AVLNode Insert(AVLNode node, int x)
    {
        if (node is null) return new AVLNode(x);
        if (x < node.val) node.left = Insert(node.left, x);
        else if (x > node.val) node.right = Insert(node.right, x);
        else return node;
        Rotations.Update(node);
        int b = Rotations.Height(node.left) - Rotations.Height(node.right);
        if (b > 1)
        {
            if (x > node.left.val) node.left = Rotations.RotateLeft(node.left);
            return Rotations.RotateRight(node);
        }
        if (b < -1)
        {
            if (x < node.right.val) node.right = Rotations.RotateRight(node.right);
            return Rotations.RotateLeft(node);
        }
        return node;
    }
}

After an insert, one fix (single or double rotation) restores the subtree to its height before the insert, so nothing above it changes: at most two rotations per insert. Deletes can need a rotation at every level on the way up, still O(log n). The guarantee: an AVL tree with n nodes has height below 1.44 · log₂(n + 2), because the sparsest AVL tree of height h has Fibonacci-many nodes.

Red-black trees: what your standard library uses

A red-black tree colours each node red or black and keeps two rules: no red node has a red child, and every path from a node down to a missing child passes the same number of black nodes. So the longest path (alternating red and black) is at most twice the shortest (all black): h ≤ 2 · log₂(n + 1). It is looser than AVL (slightly taller trees, slightly slower lookups) but needs fewer rotations per update, which is why general-purpose libraries choose it. Fixes after insert are recolourings plus at most two rotations.

You will not be asked to code one in an interview. What you need is the cost model it gives you:

C# SortedSet<T> SortedDictionary<K, V> red-black tree
C# n/a SortedList<K, V> sorted arrays: O(n) insert, O(log n) lookup by key, O(1) by index

Other balanced designs worth knowing by name: treaps (random priorities, heap-ordered, so the shape is that of a random insertion order), splay trees (move each accessed node to the root, amortised O(log n)), B-trees (fat nodes with hundreds of keys, used by databases and file systems because one node is one disk page), and skip lists (a probabilistic linked-list alternative, used by Redis sorted sets).

Ordered sets in practice: C# and Python

In an interview you almost never write a balanced tree; you use one. The queries you need are the four neighbours (floor, ceiling, lower, higher), min, max, delete, and sometimes "k-th" or "how many are smaller".

Choosing the tool

Recognise the BST shape of a problem.

  • "Given a BST…" and the question is about order (k-th, closest, successor, range, minimum difference): walk the tree using comparisons, or traverse inorder and treat it as a sorted array.
  • "Is this a valid BST / fix this BST": pass (lo, hi) windows down, or check the inorder sequence for dips.
  • "Build a BST from…": sorted input means middle as root; preorder means bounds recursion (worked problem 4).
  • Updates mixed with "nearest value", "how many smaller", "next free slot", "values within t": an ordered set (SortedSet, SortedList), possibly over a sliding window.
  • Membership only, no order: a hash set is simpler and faster (Hashing).
  • Only the min or max ever matters: a heap (Heaps & Priority Queues).
  • Rank / k-th over a fixed range of integer values: a Fenwick tree may be simpler than an augmented BST.

Pitfalls

Checking only parent and child. A node must fit the window set by all of its ancestors, not just its parent. See the trap figure in the validation section: every edge looks right and the tree is still invalid.

Dropping the returned subtree. In the recursive style, insert(node.left, x) without node.left = … builds the new node and throws it away (when the child was None). Every recursive modifier (insert, delete, trim, AVL insert) must store the result back into the parent's pointer.

Assuming O(log n). A plain BST is only as good as its shape. Sorted input makes it a linked list: O(n) per operation and, with recursion, n stack frames. Python's default recursion limit is 1,000, and a deep C# recursion throws a StackOverflowException that cannot be caught. On untrusted input prefer the iterative search, insert and inorder versions, or use a balanced library structure.

Duplicates on the wrong side. If inserts send equal keys right, then search must also continue right on equality (to find all copies), validation must allow node.val == lo on the right side, and delete must pick which copy to remove. Mixing conventions silently loses keys. Simplest: store a count per key.

Bounds that overflow. int.MinValue - 1, x + t and x - t in C# can wrap around. Use long for computed bounds (LeetCode 220 needs it: values reach ±2³¹ − 1 and t reaches 2³¹ − 1) or nullable bounds for validation.

Changing a sorted collection while enumerating it. Removing from a SortedSet inside foreach over the same set (or one of its views) throws InvalidOperationException. Collect the keys first, or use RemoveWhere. Python's SortedList is just as unsafe: iterate over a copy (list(sl.irange(a, b))).

Worked problems

1. Validate Binary Search Tree (Medium)

LeetCode 98. Return whether a binary tree is a valid BST with strictly increasing keys.

Insight. The bounds recursion above is one answer. The other uses the second superpower: a tree is a BST exactly when its inorder sequence is strictly increasing. Walk inorder iteratively, remember only the previous key, and fail at the first key that is not bigger. No recursion (so no stack overflow on a chain) and no sentinel problems, because prev starts as "nothing yet" rather than a fake minimum.

Solution: iterative inorder, compare with the previous key 
def is_valid_bst_inorder(root):
    prev = None
    stack, cur = [], root
    while stack or cur:
        while cur:
            stack.append(cur)
            cur = cur.left
        cur = stack.pop()
        if prev is not None and cur.val <= prev:
            return False                 # a dip: order broken
        prev = cur.val
        cur = cur.right
    return True

public static class ValidateInorder
{
    public static bool IsValidBST(TreeNode root)
    {
        int? prev = null;
        var stack = new Stack<TreeNode>();
        var cur = root;
        while (stack.Count > 0 || cur is not null)
        {
            for (; cur is not null; cur = cur.left) stack.Push(cur);
            cur = stack.Pop();
            if (prev is int p && cur.val <= p) return false;
            prev = cur.val;
            cur = cur.right;
        }
        return true;
    }
}

O(n) time in the worst case, but it stops at the first violation. O(h) space for the stack.

2. Two Sum IV: Input is a BST (Easy)

LeetCode 653. Return whether two different nodes have keys that add up to k.

Insight. A hash set of seen values works on any tree (O(n) space). Using the BST gives the two-pointer algorithm from Two Pointers without copying the keys into an array: run two iterators, one forward (smallest first) and one backward (largest first). If the sum is too small, advance the forward one; too big, advance the backward one; stop when they meet. Space drops to O(h).

Solution: forward and backward BST iterators as two pointers 
def find_target(root, k):
    def push(stack, node, forward):
        while node:
            stack.append(node)
            node = node.left if forward else node.right

    lo, hi = [], []                      # lo top = smallest unused, hi top = largest unused
    push(lo, root, True)
    push(hi, root, False)
    while lo and hi and lo[-1].val < hi[-1].val:
        s = lo[-1].val + hi[-1].val
        if s == k:
            return True
        if s < k:
            node = lo.pop()
            push(lo, node.right, True)   # next larger key
        else:
            node = hi.pop()
            push(hi, node.left, False)   # next smaller key
    return False

public static class TwoSumBst
{
    static void Push(Stack<TreeNode> st, TreeNode node, bool forward)
    {
        while (node is not null) { st.Push(node); node = forward ? node.left : node.right; }
    }

    public static bool FindTarget(TreeNode root, int k)
    {
        var lo = new Stack<TreeNode>();
        var hi = new Stack<TreeNode>();
        Push(lo, root, true);
        Push(hi, root, false);
        while (lo.Count > 0 && hi.Count > 0 && lo.Peek().val < hi.Peek().val)
        {
            int s = lo.Peek().val + hi.Peek().val;
            if (s == k) return true;
            if (s < k) Push(lo, lo.Pop().right, true);
            else Push(hi, hi.Pop().left, false);
        }
        return false;
    }
}

O(n) time, O(h) space. The lo.val < hi.val test is the "pointers have not crossed" check.

3. Kth Smallest Element in a BST, with updates (Medium)

LeetCode 230. Return the k-th smallest key. Follow-up: the BST is modified often and k-th is asked often.

Insight. The basic answer is the iterator: pop k times, O(h + k) (see kth_smallest above and the iterator visualizer with k = 6). The follow-up wants O(h) per query, which needs each node to know its subtree size (the augmented-tree figure). Walking down, compare k with size(left) + 1.

Solution: both versions, and how to keep sizes current

The plain version is kth_smallest / KthSmallestBst.KthSmallest from the inorder section. For the follow-up, store sizes:

class SizeNode:
    def __init__(self, val):
        self.val, self.left, self.right, self.size = val, None, None, 1


def size(n):
    return n.size if n else 0


def os_insert(node, x):
    """Insert a new distinct key, keeping sizes correct on the path."""
    if node is None:
        return SizeNode(x)
    if x < node.val:
        node.left = os_insert(node.left, x)
    else:
        node.right = os_insert(node.right, x)
    node.size += 1
    return node


def os_kth(node, k):
    """k-th smallest, 1-based. O(h)."""
    while node:
        r = size(node.left) + 1                  # rank of node in its subtree
        if k == r:
            return node.val
        if k < r:
            node = node.left
        else:
            k -= r                               # skip the left subtree and node
            node = node.right
    return None


def os_rank(node, x):
    """How many keys are < x. O(h)."""
    r = 0
    while node:
        if x <= node.val:
            node = node.left
        else:
            r += size(node.left) + 1
            node = node.right
    return r

public class SizeNode
{
    public int val, size = 1;
    public SizeNode left, right;
    public SizeNode(int v) => val = v;
}

public static class OrderStatistics
{
    static int Size(SizeNode n) => n?.size ?? 0;

    public static SizeNode Insert(SizeNode node, int x)
    {
        if (node is null) return new SizeNode(x);
        if (x < node.val) node.left = Insert(node.left, x);
        else node.right = Insert(node.right, x);
        node.size++;
        return node;
    }

    public static int? Kth(SizeNode node, int k)
    {
        while (node is not null)
        {
            int r = Size(node.left) + 1;
            if (k == r) return node.val;
            if (k < r) node = node.left;
            else { k -= r; node = node.right; }
        }
        return null;
    }

    public static int Rank(SizeNode node, int x)
    {
        int r = 0;
        while (node is not null)
        {
            if (x <= node.val) node = node.left;
            else { r += Size(node.left) + 1; node = node.right; }
        }
        return r;
    }
}

Deletes decrement size on the path the same way inserts increment it. To get O(log n) in the worst case, the sizes must live in a balanced tree, and every rotation recomputes size for the two nodes it moves, bottom one first, exactly like update recomputes heights in the AVL code.

Interview phrasing: "plain inorder is O(h + k). With frequent queries I'd store subtree sizes, which makes k-th and rank O(h); combined with a balanced tree that is O(log n) per query and per update."

4. Construct BST from Preorder Traversal (Medium)

LeetCode 1008. Rebuild the BST whose preorder traversal is given.

Insight. For a general tree you need preorder and inorder (see Tree Traversals). For a BST, the inorder is just the sorted preorder, so preorder alone is enough, and you do not even need to sort. Read the preorder left to right with a shared index; each call builds a subtree whose keys must stay below an upper bound hi. The next key becomes the subtree root if it fits; its left subtree takes keys below the new root, its right subtree takes keys below hi. A key that does not fit belongs to some ancestor's right side, so the call returns None and lets that ancestor take it. Each key is read once: O(n). The same idea serialises a BST compactly (LeetCode 449): write the preorder, rebuild with bounds, no null markers needed.

Solution: one pass with an upper bound 
import math


def bst_from_preorder(preorder):
    i = 0

    def build(hi):
        nonlocal i
        if i == len(preorder) or preorder[i] > hi:
            return None                  # next key belongs to an ancestor's right side
        node = TreeNode(preorder[i])
        i += 1
        node.left = build(node.val)      # keys below node.val
        node.right = build(hi)           # keys between node.val and hi
        return node

    return build(math.inf)

public static class FromPreorder
{
    public static TreeNode BstFromPreorder(int[] preorder)
    {
        int i = 0;
        TreeNode Build(long hi)
        {
            if (i == preorder.Length || preorder[i] > hi) return null;
            var node = new TreeNode(preorder[i++]);
            node.left = Build(node.val);
            node.right = Build(hi);
            return node;
        }
        return Build(long.MaxValue);
    }
}

O(n) time, O(h) recursion depth. The lower bound is never checked because preorder order guarantees it: by the time a key is read, every smaller key that belongs further left has already been consumed.

5. Convert Sorted List to Binary Search Tree (Medium)

LeetCode 109. Same as LeetCode 108, but the sorted keys come as a singly linked list (ListNode with val and next).

Insight. Finding the middle of a list costs O(n), so "middle as root" naively is O(n log n). Flip it around: an inorder traversal of the finished tree visits the keys in list order. So build the tree in inorder: recurse on the left half's size first (no list access), then take the current list node as the root and advance the list pointer, then build the right half. The list is consumed exactly in order, once: O(n). Same shape of answer as the balanced visualizer, because the same index splits are used.

Solution: simulate inorder over index ranges 
def sorted_list_to_bst(head):
    n, p = 0, head
    while p:
        n += 1
        p = p.next
    cur = head

    def build(lo, hi):                   # builds list positions [lo, hi)
        nonlocal cur
        if lo >= hi:
            return None
        mid = (lo + hi) // 2
        left = build(lo, mid)            # consumes positions lo..mid-1
        node = TreeNode(cur.val, left)   # cur is now position mid
        cur = cur.next
        node.right = build(mid + 1, hi)
        return node

    return build(0, n)

public static class ListToBst
{
    public static TreeNode SortedListToBST(ListNode head)
    {
        int n = 0;
        for (var p = head; p is not null; p = p.next) n++;
        var cur = head;
        TreeNode Build(int lo, int hi)
        {
            if (lo >= hi) return null;
            int mid = (lo + hi) / 2;
            var left = Build(lo, mid);
            var node = new TreeNode(cur.val, left);
            cur = cur.next;
            node.right = Build(mid + 1, hi);
            return node;
        }
        return Build(0, n);
    }
}

O(n) time, O(log n) recursion depth. The alternative, slow/fast pointers to find each middle (see Linked Lists), is O(n log n) and also accepted.

6. Recover Binary Search Tree (Medium)

LeetCode 99. Exactly two nodes of a BST had their keys swapped. Fix the tree without changing its structure.

Insight. Look at the inorder sequence. Swapping two keys of a sorted list creates descents (places where a key is bigger than the next one). If the swapped keys are adjacent in inorder, there is one descent and both keys are in it. Otherwise there are two: the first wrong key is the bigger key of the first descent, the second wrong key is the smaller key of the last descent. Record them during an inorder walk and swap their values at the end. The visualizer below marks each descent as it is found.

Solution: inorder walk, track descents 
def recover_tree(root):
    first = second = prev = None
    stack, cur = [], root
    while stack or cur:
        while cur:
            stack.append(cur)
            cur = cur.left
        cur = stack.pop()
        if prev and prev.val > cur.val:      # a descent
            if first is None:
                first = prev                 # first descent: the bigger key is wrong
            second = cur                     # last descent: the smaller key is wrong
        prev = cur
        cur = cur.right
    first.val, second.val = second.val, first.val

public static class RecoverBst
{
    public static void RecoverTree(TreeNode root)
    {
        TreeNode first = null, second = null, prev = null;
        var stack = new Stack<TreeNode>();
        var cur = root;
        while (stack.Count > 0 || cur is not null)
        {
            for (; cur is not null; cur = cur.left) stack.Push(cur);
            cur = stack.Pop();
            if (prev is not null && prev.val > cur.val)
            {
                first ??= prev;
                second = cur;
            }
            prev = cur;
            cur = cur.right;
        }
        (first.val, second.val) = (second.val, first.val);
    }
}

O(n) time, O(h) space. The follow-up asks for O(1) space: run the same descent check inside a Morris inorder traversal (see Tree Traversals), and swap only after the walk has removed all its threads.

7. Contains Duplicate III (Hard)

LeetCode 220. Is there a pair of indices i ≠ j with |i − j| ≤ indexDiff and |nums[i] − nums[j]| ≤ valueDiff?

Insight. The index condition is a sliding window of the last indexDiff values. The value condition asks whether any value in that window lies in [x − t, x + t]. An unordered window cannot answer that quickly, but an ordered set can: the only candidate worth checking is the ceiling of x − t (the smallest window value that is not too small). If it exists and is ≤ x + t, we are done.

Solution: sliding window in an ordered set, one ceiling query per step 
from sortedcontainers import SortedList


def contains_nearby_almost_duplicate(nums, index_diff, value_diff):
    window = SortedList()
    for i, x in enumerate(nums):
        j = window.bisect_left(x - value_diff)          # ceiling(x - t)
        if j < len(window) and window[j] <= x + value_diff:
            return True
        window.add(x)
        if i >= index_diff:
            window.remove(nums[i - index_diff])         # keep only the last index_diff values
    return False

public static class NearbyAlmostDuplicate
{
    public static bool ContainsNearbyAlmostDuplicate(int[] nums, int indexDiff, int valueDiff)
    {
        var window = new SortedSet<long>();
        for (int i = 0; i < nums.Length; i++)
        {
            long x = nums[i];
            if (window.Count > 0 && window.Max >= x - valueDiff)
            {
                long c = window.GetViewBetween(x - valueDiff, window.Max).Min;   // ceiling(x - t)
                if (c <= x + valueDiff) return true;
            }
            window.Add(x);
            if (i >= indexDiff) window.Remove(nums[i - indexDiff]);
        }
        return false;
    }
}

O(n log k) time, O(k) space for k = indexDiff. A set (not a multiset) is enough: if two equal values were ever in the window together, the second would already have returned True. long keeps x ± t from overflowing. There is also an O(n) answer: buckets of width t + 1 keyed by x // (t + 1); two values in the same bucket are close, so only the neighbouring buckets need a check (see Hashing).

8. Maximum Sum BST in Binary Tree (Hard)

LeetCode 1373. In an arbitrary binary tree, find the maximum key sum of any subtree that is a BST (0 if all are negative, since the empty tree counts).

Insight. Checking each subtree separately is O(n²). Instead, compute bottom-up (postorder) a summary of each subtree: its minimum, its maximum and its sum, with a marker for "not a BST". A node roots a BST exactly when both children do and max(left) < node.val < min(right), which is the window rule seen from below. Return (−∞, +∞) for "not a BST": that pair fails every parent's comparison, so the failure propagates for free. Empty subtrees return (+∞, −∞, 0), which every parent accepts.

Solution: postorder (min, max, sum) summaries 
import math


def max_sum_bst(root):
    best = 0

    def go(node):                        # -> (lo, hi, total) of this subtree
        nonlocal best
        if node is None:
            return math.inf, -math.inf, 0
        llo, lhi, ls = go(node.left)
        rlo, rhi, rs = go(node.right)
        if lhi < node.val < rlo:         # both sides are BSTs and fit around node
            total = ls + node.val + rs
            best = max(best, total)
            return min(llo, node.val), max(rhi, node.val), total
        return -math.inf, math.inf, 0    # poison: no ancestor can be a BST

    go(root)
    return best

public static class MaxSumBstSolver
{
    public static int MaxSumBST(TreeNode root)
    {
        int best = 0;
        (long lo, long hi, int sum) Go(TreeNode node)
        {
            if (node is null) return (long.MaxValue, long.MinValue, 0);
            var l = Go(node.left);
            var r = Go(node.right);
            if (l.hi < node.val && node.val < r.lo)
            {
                int total = l.sum + node.val + r.sum;
                best = Math.Max(best, total);
                return (Math.Min(l.lo, node.val), Math.Max(r.hi, node.val), total);
            }
            return (long.MinValue, long.MaxValue, 0);
        }
        Go(root);
        return best;
    }
}

O(n) time, O(h) recursion. This "return a small tuple from each child and combine" pattern is the core of Tree Problem Patterns. The tree can be a 40,000-node chain, so in Python add sys.setrecursionlimit(100_000) (or convert to an iterative postorder).

Self-check

Of the 6 orders in which you can insert the keys 1, 2, 3, how many give a tree with only two levels? How many different tree shapes appear in total?

Two orders, (2, 1, 3) and (2, 3, 1), put 2 at the root and give the balanced tree. The other four give chains: (1, 2, 3), (1, 3, 2), (3, 2, 1) and (3, 1, 2), each a different shape. So 5 distinct shapes, which is the Catalan number C₃ = 5 and the answer to LeetCode 96 for n = 3. Only a third of random orders are balanced here, but for large n random orders are balanced on average (height about 3 log₂ n); sorted orders never are.

When deleting a node with two children, why can the successor always be removed with the easy cases?

The successor is the leftmost node of the right subtree. If it had a left child, that child would be smaller and still in the right subtree, so it would be further left: contradiction. With no left child it is a leaf (case 1) or has only a right child (case 2), so it can be spliced out.

Is the tree [5, 4, 6, null, null, 3, 7] a valid BST? Which check catches it?

No. 3 is the left child of 6, which is fine locally (3 is smaller than 6), but it lies in 5's right subtree, so it must be bigger than 5. Its window is (5, 6). The window check rejects it, and so does the inorder check: the inorder sequence is 4, 5, 3, 6, 7, with a dip after 5.

Preorder is [8, 5, 1, 7, 10, 12]. Draw the BST. What is its inorder sequence, and why didn't you need it?

8 is the root. 5, 1, 7 are smaller, so they form the left subtree: 5 with children 1 and 7. 10 and 12 form the right subtree: 10 with right child 12. The inorder is the sorted list 1, 5, 7, 8, 10, 12. You never need it as input because sorting the keys always produces it, which is why preorder alone determines a BST.

Using a C# SortedSet<int> with 10⁶ keys, which of these is O(log n): GetViewBetween(a, b), view.Min, view.Count?

Creating the view and reading Min or Max are O(log n): the view is lazy and walks one path. Count walks every key in the range, O(k), and recounts after every change to the set. Also watch out for an empty view, whose Min and Max return default(int) = 0 instead of throwing.

A right rotation at z changes three pointers. Which subtree changes parent, and why can't the rotation break the BST property?

Subtree B (y's old right child) moves from y to become z's left child. Every key in B is between y and z, which is exactly the window of z's left child after the rotation. A, B and C keep their contents and the inorder sequence stays A, y, B, z, C, so the tree is still sorted.
