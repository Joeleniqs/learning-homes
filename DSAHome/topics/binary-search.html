Binary Search

One boundary template to rule them all: first-true search, rotated arrays, search on the answer, and real-valued bisection.

Beginner → Expert~60 min studyUpdated 2026-11-03

What binary search really is

Most people learn binary search as “look for a number in a sorted array”. That version is a special case, and it is the source of nearly every off-by-one bug. The real idea is much bigger and much simpler:

The invariant. If a yes/no question p(i) is false, false, …, false, true, true, …, true over a range, you can find the first true in O(log n) probes by keeping lo at the edge of the known-false zone and hi at the edge of the known-true zone, and halving the unknown gap between them.

Everything on this page is that one sentence: lower and upper bound, exact match, first and last occurrence, insert position, rotated arrays, peaks, “minimum speed / capacity / days” problems, k-th smallest, square roots and the median of two sorted arrays. You only have to choose p and the range. The loop never changes.

Why you need it. A sorted array of a billion elements needs at most 30 probes (2³⁰ ≈ 10⁹). More importantly, the same trick works when there is no array at all: if you can answer “is speed k fast enough?”, you can binary search the speed. That is what turns many “looks like DP or brute force” problems into O(n log range).

Intuition: halving what you know

Picture the range as three zones. Left of lo, everything is known F. From hi onward, everything is known T. In between is the unknown gap. One probe at mid reveals p(mid), and because p is monotone that single answer also settles one whole side of the gap.

Watch the boundary search find a target

Step through it. The dimmed cells are gone for good; the strip on the right shows the candidate count halving. Try a target that is absent, one smaller than everything, and one larger than everything.

The predicate strip: lo and hi are walls of knowledge

Here the second row is the predicate itself. Cells start as “?” and turn into known F or T as the walls move. Pick different questions: notice that count and last occurrence are just a second search with > instead of ≥.

The one template

Memorise this and nothing else. It returns the first index in [lo, hi) where pred is true, or hi if there is none.

def first_true(lo: int, hi: int, pred) -> int:
    """Smallest i in [lo, hi) with pred(i) true; hi if none.
    pred must be monotone: F...F T...T on [lo, hi)."""
    while lo < hi:                      # unknown gap [lo, hi) is non-empty
        mid = lo + (hi - lo) // 2       # lo <= mid < hi, never overflows
        if pred(mid):
            hi = mid                    # mid is T: answer is mid or left of it
        else:
            lo = mid + 1                # mid is F: answer is strictly right
    return lo                           # lo == hi == the boundary

/// Smallest i in [lo, hi) with pred(i) true; hi if none.
/// pred must be monotone: F...F T...T on [lo, hi).
public static int FirstTrue(int lo, int hi, Func<int, bool> pred)
{
    while (lo < hi)                       // unknown gap [lo, hi) is non-empty
    {
        int mid = lo + (hi - lo) / 2;     // lo <= mid < hi, never overflows
        if (pred(mid)) hi = mid;          // mid is T: answer is mid or left of it
        else lo = mid + 1;                // mid is F: answer is strictly right
    }
    return lo;                            // lo == hi == the boundary
}

Cost: O(log(hi − lo)) calls to pred, O(1) extra space. If pred costs C, the total is O(C · log range).

Every choice in those eight lines has a reason:

Line Why it is written this way
hi is exclusive (len(a), not len(a) − 1) The answer may be “nobody qualifies”. Index n represents that, so it must be a possible return value.
while lo < hi The gap [lo, hi) is non-empty exactly when lo < hi. When it is empty, lo is the answer. No extra check after the loop.
mid = lo + (hi − lo) // 2 Rounds down, so lo ≤ mid < hi: mid is always a real index inside the gap and pred(mid) never reads past the end.
hi = mid mid is T, so it might be the first T. Keep it in play by putting it on the T side of the wall.
lo = mid + 1 mid is F, so it can never be the answer. Moving past it is what guarantees progress.

Why it always terminates Because mid < hi, the update hi = mid strictly shrinks the gap; because lo = mid + 1 > lo, so does the other branch. Precisely: a gap of size g becomes ⌊g/2⌋ on a T and ⌈g/2⌉ − 1 on an F. Both are at most g/2, so after ⌈log₂(g + 1)⌉ probes the gap is empty and the loop cannot spin.

Deriving everything from first_true

Each classic question is one predicate and one line of interpretation:

upper bound: first a[i] > t a[i] > t U = first_true(0, n, p)

def lower_bound(a, t):            # first index with a[i] >= t  (== bisect_left)
    return first_true(0, len(a), lambda i: a[i] >= t)

def upper_bound(a, t):            # first index with a[i] > t   (== bisect_right)
    return first_true(0, len(a), lambda i: a[i] > t)

def search(a, t):                 # leftmost index of t, or -1
    i = lower_bound(a, t)
    return i if i < len(a) and a[i] == t else -1

def search_range(a, t):           # [first, last] occurrence, or [-1, -1]
    lo = lower_bound(a, t)
    if lo == len(a) or a[lo] != t:
        return [-1, -1]
    return [lo, upper_bound(a, t) - 1]

def count(a, t):
    return upper_bound(a, t) - lower_bound(a, t)

public static int LowerBound(int[] a, int t) => FirstTrue(0, a.Length, i => a[i] >= t);
public static int UpperBound(int[] a, int t) => FirstTrue(0, a.Length, i => a[i] > t);

public static int Search(int[] a, int t)          // leftmost index of t, or -1
{
    int i = LowerBound(a, t);
    return i < a.Length && a[i] == t ? i : -1;
}

public static int[] SearchRange(int[] a, int t)   // [first, last] occurrence
{
    int lo = LowerBound(a, t);
    if (lo == a.Length || a[lo] != t) return new[] { -1, -1 };
    return new[] { lo, UpperBound(a, t) - 1 };
}

public static int Count(int[] a, int t) => UpperBound(a, t) - LowerBound(a, t);

All O(log n) time and O(1) space. (The lambdas cost a delegate call per probe in C#; inline the loop on a hot path.)

Overflow-safe mid

(lo + hi) / 2 is the most famous bug in the history of binary search: it sat in Java's Arrays.binarySearch for nine years. With 32-bit int, lo + hi overflows once both are above about 1.07 billion, mid goes negative, and you index out of range. Python integers never overflow, but C#, Java, C++ and Go all do.

Form Safe? Notes
(lo + hi) / 2 ❌ in C#/Java Overflows when lo + hi > int.MaxValue.
lo + (hi - lo) / 2 ✅ hi − lo fits because 0 ≤ lo ≤ hi. Also correct for negative lo (the difference is never negative, so truncation equals floor).
(int)((uint)lo + (uint)hi >> 1) ✅ for lo, hi ≥ 0 The trick .NET's own Array.BinarySearch uses. Java writes (lo + hi) >>> 1.
(lo + hi) // 2 in Python ✅ Arbitrary-precision ints, and // floors even for negatives.

Pitfall: truncation versus floor with negative bounds When you binary search an answer that can be negative (say the range is [−10⁹, 10⁹]), C#'s (lo + hi) / 2 rounds toward zero, so for lo = −3, hi = −2 it gives −2 = hi. With hi exclusive that reads outside the range; with the lo = mid variant it loops forever. lo + (hi − lo) / 2 is always a floor because hi − lo ≥ 0. Use it everywhere.

Infinite loops: why lo = mid needs the upper mid

def last_true(lo, hi, pred):
    """pred is T...T F...F on [lo, hi] and pred(lo) is true. Returns the last true."""
    while lo < hi:
        mid = lo + (hi - lo + 1) // 2   # upper mid: lo < mid <= hi
        if pred(mid):
            lo = mid
        else:
            hi = mid - 1
    return lo

def classic_search(a, t):             # exact match only; any copy of t
    lo, hi = 0, len(a) - 1
    while lo <= hi:
        mid = lo + (hi - lo) // 2
        if a[mid] == t:
            return mid
        if a[mid] < t:
            lo = mid + 1
        else:
            hi = mid - 1
    return -1

/// pred is T...T F...F on [lo, hi] and pred(lo) is true. Returns the last true.
public static int LastTrue(int lo, int hi, Func<int, bool> pred)
{
    while (lo < hi)
    {
        int mid = lo + (hi - lo + 1) / 2;   // upper mid: lo < mid <= hi
        if (pred(mid)) lo = mid;
        else hi = mid - 1;
    }
    return lo;
}

public static int ClassicSearch(int[] a, int t)   // exact match only
{
    int lo = 0, hi = a.Length - 1;
    while (lo <= hi)
    {
        int mid = lo + (hi - lo) / 2;
        if (a[mid] == t) return mid;
        if (a[mid] < t) lo = mid + 1;
        else hi = mid - 1;
    }
    return -1;
}

Library calls: Python bisect and C# Array.BinarySearch

Python. bisect.bisect_left(a, x) is exactly lower bound and bisect.bisect_right(a, x) is upper bound. Both take optional lo and hi, and since Python 3.10 a key= function that is applied to the elements (not to x). insort_left / insort_right insert while keeping order, but the insert itself is O(n) because lists shift.

A neat trick: range objects support indexing, so bisect can search a predicate over integers without building a list.

from bisect import bisect_left, bisect_right, insort

a = [1, 3, 3, 5, 5, 5, 5, 8, 9, 12]
bisect_left(a, 5), bisect_right(a, 5)      # (3, 7)
bisect_right(a, 5) - bisect_left(a, 5)     # 4 copies

# Search on the answer with no hand-written loop (Python 3.10+):
# first k in [1, hi] with feasible(k) True. False < True, so bools sort F...F T...T.
k = 1 + bisect_left(range(1, hi + 1), True, key=feasible)

int[] a = { 10, 20, 30, 40 };
int r = Array.BinarySearch(a, 25);     // -3: not found
int insertAt = r >= 0 ? r : ~r;        // ~(-3) == 2: 25 belongs at index 2

var list = new List<int> { 10, 20, 30, 40 };
int idx = list.BinarySearch(35);
if (idx < 0) list.Insert(~idx, 35);    // keeps the list sorted

int[] d = { 5, 5, 5, 5, 5, 5, 5 };
Array.BinarySearch(d, 5);              // 3 here: ANY matching index, not the first

C#. Array.BinarySearch, List<T>.BinarySearch and MemoryExtensions.BinarySearch (for spans) return the index of a match if one exists. Otherwise they return the bitwise complement of the insertion point: ~i = −i − 1, which is always negative, so “found” and “not found” share one int. Apply ~ again to recover the index of the first element larger than the value (or Length).

Variants and sub-patterns

Rotated sorted arrays

Rotating a sorted array ([3,5,8,10,12,15,18,22,27,31] → [15,18,22,27,31,3,5,8,10,12]) breaks “sorted” but keeps a lot of structure: two ascending runs and one cliff. Two monotone facts survive, and each gives a binary search.

  • Find the minimum / rotation point: first_true(0, n, lambda i: a[i] <= a[-1]). Compare with the last element, not the first: with no rotation at all, a[i] ≤ a[0] is T only at index 0 and the predicate is not F…T.
  • Search a target, two passes: find the rotation point k, then run lower bound on [k, n) if t ≤ a[-1], else on [0, k). Pure template, easy to get right.
  • Search a target, one pass: at each mid, one of [lo..mid] or [mid..hi] is sorted (the cliff can only be on one side). Range-check the target against the sorted side; that tells you which half to keep.

Duplicates (LeetCode 81 and 154). With duplicates, a[lo] == a[mid] == a[hi] tells you nothing about which side holds the cliff ([1,1,1,0,1] versus [1,0,1,1,1]). The standard fix is to shrink by one (hi -= 1, after checking a[hi]), which keeps correctness but degrades the worst case to O(n). No algorithm can do better on all-equal-but-one input.

Peak finding: binary search without a sorted array

A peak is an element larger than both neighbours (with a[−1] = a[n] = −∞). The array is not sorted and the “slope” strip is not monotone, yet binary search works because it only needs one thing: a boundary is guaranteed to exist inside [lo, hi]. If a[mid] < a[mid+1], climbing right must eventually come down (the far end is −∞), so a peak lies in (mid, hi]. Otherwise a peak lies in [lo, mid]. The invariant “there is a peak in [lo, hi]” survives every step.

The general principle Binary search does not need global monotonicity. It needs an invariant of the form “an answer exists in [lo, hi]” and a probe that can always discard half while preserving it. Monotone predicates are the most common way to get that, not the only one. The same reasoning solves bitonic (“mountain”) arrays: find the peak, then binary search each monotone side.

Search on the answer

This is where binary search becomes a superpower. When a problem asks for the minimum (or maximum) value X such that something is possible, and making X bigger never makes it impossible, then feasible(X) is F…F T…T over the answer range. Binary search that range and simulate feasible at each probe.

The recipe has four questions. Answer them out loud before coding:

1 · ANSWERWhat number am I choosing?

Speed, capacity, days, max sum, distance, time.

2 · CHECKGiven X, can I verify fast?

Usually a greedy O(n) simulation.

3 · MONOTONEDoes X+1 stay feasible?

If yes: min-feasible = first true. If it flips the other way: max-feasible.

4 · BOUNDSSmallest and largest sane X

lo must be a legal input to check; hi must be surely feasible.

def min_eating_speed(piles: list[int], h: int) -> int:
    def feasible(k: int) -> bool:               # O(n)
        return sum((p + k - 1) // k for p in piles) <= h

    # answer is in [1, max(piles)]; max(piles) is always feasible (h >= len(piles))
    return first_true(1, max(piles), feasible)  # hi = max(piles) acts as the known-T wall

public static int MinEatingSpeed(int[] piles, int h)
{
    bool Feasible(int k)                         // O(n)
    {
        long hours = 0;                          // long: n * 1e9 hours overflows int
        foreach (int p in piles) hours += (p + k - 1L) / k;
        return hours <= h;
    }
    return FirstTrue(1, piles.Max(), Feasible);  // max(piles) is always feasible
}

O(n log M) time, M = max(piles); O(1) space. Note the trick: passing hi = max(piles) as the exclusive bound is fine because we know max(piles) is feasible, so the search never needs to return anything above it.

Minimise the maximum, maximise the minimum “Minimise the largest piece” (split array, ship capacity, painters) is min-feasible: bigger limits are easier, so F…F T…T. “Maximise the smallest gap” (magnetic balls, aggressive cows) is max-feasible: bigger gaps are harder, so T…T F…F, and the answer is first_true(not feasible) − 1. Both phrases are a loud hint to search on the answer.

K-th smallest by counting

To find the k-th smallest element of something huge and implicit (all pairwise distances, a multiplication table, a sorted matrix, all fractions p/q), binary search the value with p(x) = count(elements ≤ x) ≥ k. The count is monotone in x, and the first x that reaches k is always an actual element: the count only jumps at real values. The whole game is writing count in O(n) or O(n log n), often with two pointers.

Real-valued bisection

With real numbers there is no “next value”, so there is no + 1: both branches assign mid. The loop stops on precision, not on lo == hi. Two safe stopping rules:

  • Fixed iteration count (for _ in range(100)): each halving gains one bit, and a double has 53, so 60–100 iterations reach full precision from any sane range. It cannot loop forever. Prefer this.
  • Width tolerance (while hi − lo > eps): readable, but if eps is smaller than the gap between adjacent doubles near the answer (for example eps = 1e−12 when the answer is near 10⁶), mid stops changing and the loop never ends.
def sqrt_real(x: float) -> float:
    lo, hi = 0.0, max(1.0, x)            # for x < 1, sqrt(x) > x
    for _ in range(100):                 # ~1 bit per iteration; cannot hang
        mid = (lo + hi) / 2
        if mid * mid >= x:
            hi = mid
        else:
            lo = mid
    return (lo + hi) / 2

def my_sqrt(x: int) -> int:              # LeetCode 69: floor(sqrt(x)) with integers only
    # last m with m*m <= x  ==  (first m with m*m > x) - 1
    return first_true(0, x + 1, lambda m: m * m > x) - 1

public static double Sqrt(double x)
{
    double lo = 0, hi = Math.Max(1.0, x);    // for x < 1, sqrt(x) > x
    for (int it = 0; it < 100; it++)         // ~1 bit per iteration; cannot hang
    {
        double mid = (lo + hi) / 2;
        if (mid * mid >= x) hi = mid; else lo = mid;
    }
    return (lo + hi) / 2;
}

public static int MySqrt(int x)              // floor(sqrt(x)); long avoids m*m overflow
    => (int)(FirstTrueLong(0, (long)x + 1, m => m * m > x) - 1);

public static long FirstTrueLong(long lo, long hi, Func<long, bool> pred)
{
    while (lo < hi)
    {
        long mid = lo + (hi - lo) / 2;
        if (pred(mid)) hi = mid; else lo = mid + 1;
    }
    return lo;
}

Real bisection is O(log(range/ε)) iterations. The integer version is O(log x) and exact.

Median of two sorted arrays: binary search a partition

The hardest classic (LeetCode 4) is the same template in disguise. Do not search for the median value; search for how many elements of the shorter array A belong to the lower half of the merged order. Call that i. The lower half must hold half = (m + n + 1) // 2 elements, so j = half − i of them come from B. A cut is correct exactly when every left element is ≤ every right element, which (both arrays being sorted) reduces to two cross comparisons.

Why the first true i is valid: p(i) gives B[j−1] ≤ A[i] directly; and p(i−1) being false means A[i−1] < B[j], the other half of the condition. Searching the shorter array keeps j inside B for every i, and makes it O(log min(m, n)).

Recognize it when

Recognize it when

  • The input is sorted (or sorted after rotation), and you need a position, a count, a first/last, or a closest value.
  • The task says “minimum X such that …” or “maximum X such that …”, and a bigger X is clearly easier (or harder).
  • Phrases like minimise the maximum, maximise the minimum, “at least”, “within D days”, “at speed k”.
  • The answer range is huge (10⁹, 10¹⁸) but checking one candidate is cheap: O(n log range) beats anything that iterates the range.
  • K-th smallest over an implicit sorted set (pair distances, matrix, multiplication table, fractions).
  • A real-valued answer “within 10⁻⁶”.
  • The constraints demand O(log n) per query, or O(n log n) overall with n ≈ 10⁵.
Use Time Space Notes
Search a sorted array (any bound) O(log n) O(1) 30 probes for 10⁹ elements
Rotated array search / find min O(log n) O(1) O(n) worst case with duplicates
Peak element O(log n) O(1) Any peak, not the global max
Search on the answer O(C · log R) O(1) + check C = cost of feasible, R = answer range
K-th smallest by counting O(n · log R) O(1) Count with two pointers inside
Median of two sorted arrays O(log min(m, n)) O(1) Partition search
Real bisection O(log(R/ε)) O(1) Or a fixed 100 iterations

Pitfalls

Using equality as the predicate p(i) = a[i] == t is F…F T…T F…F, not monotone, so “first true” is meaningless. Fix: search a[i] >= t and check equality once, after the loop.

hi = len(a) − 1 with the half-open loop If hi starts at n − 1 but you use while lo < hi and hi = mid, the search can return n − 1 even when p(n − 1) is false, because “no answer” has no slot. Fix: hi = n (exclusive), or verify p(lo) after the loop.

lo = mid with a floor mid Spins forever on a two-element gap. Fix: ceiling mid for that branch, or rewrite as first_true(not p) − 1.

Overflow: in mid, and inside the check (lo + hi) / 2 overflows int; so does mid * mid in an integer square root, and summing hours or loads across 10⁵ items of size 10⁹. Fix: lo + (hi − lo) / 2, and long for products and running sums in C#.

Lower bound of the answer range breaks the check Ship capacity with lo = 1: the greedy “start a new day when the next package does not fit” silently accepts a package heavier than the capacity. Fix: lo = max(weights), the smallest capacity that can carry every package at all.

Floating-point loops that never end while hi − lo > 1e−12 around 10⁶ can stall when mid rounds to lo or hi. Fix: a fixed number of iterations, or a relative tolerance.

Trusting Array.BinarySearch for the first copy With duplicates it returns some matching index (3 in a run of seven 5s). Fix: your own lower bound when position among equals matters.

Worked problems

Every solution below reuses first_true / FirstTrue from the template section. The interesting part is always the same: name the predicate, prove it is F…F T…T, pick the range.

1. Find First and Last Position Medium

Given a sorted array with duplicates, return [first, last] index of target, or [−1, −1], in O(log n).

Insight. First copy = first a[i] ≥ t. Last copy = (first a[i] > t) − 1. Two template calls, no special cases. The predicate strip visualizer shows both passes.

Solution: two boundary searches 
def search_range(nums: list[int], target: int) -> list[int]:
    lo = lower_bound(nums, target)                   # first a[i] >= target
    if lo == len(nums) or nums[lo] != target:
        return [-1, -1]                              # target absent
    return [lo, upper_bound(nums, target) - 1]       # last = first a[i] > target, minus 1

public static int[] SearchRange(int[] nums, int target)
{
    int lo = LowerBound(nums, target);               // first a[i] >= target
    if (lo == nums.Length || nums[lo] != target) return new[] { -1, -1 };
    return new[] { lo, UpperBound(nums, target) - 1 };
}

O(log n) time, O(1) space.

2. Find Minimum in Rotated Sorted Array Medium

A sorted array of distinct values was rotated. Return its minimum in O(log n).

Insight. a[i] ≤ a[−1] is F on the first run and T on the second (see the rotated picture above). The minimum is the first true. If the array was not rotated, every element is ≤ the last one and the answer is index 0, as it should be.

Solution: first index with a[i] ≤ a[−1] 
def find_min(nums: list[int]) -> int:
    last = nums[-1]
    return nums[first_true(0, len(nums), lambda i: nums[i] <= last)]

public static int FindMin(int[] nums)
{
    int last = nums[^1];
    return nums[FirstTrue(0, nums.Length, i => nums[i] <= last)];
}

O(log n) time, O(1) space.

3. Search in Rotated Sorted Array Medium

Return the index of target in a rotated sorted array of distinct values, or −1.

Insight. Two clean options. Two passes: find the rotation point with problem 2, decide which run can hold the target (t ≤ a[−1] means the right run), lower-bound inside it. One pass: one side of mid is always sorted; if the target is inside that side’s range go there, else go to the other side. The visualizer above runs the one-pass version.

Solution: both versions 
def search_two_pass(a: list[int], t: int) -> int:
    n = len(a)
    k = first_true(0, n, lambda i: a[i] <= a[-1])     # start of the second run
    lo, hi = (k, n) if t <= a[-1] else (0, k)         # the only run that can hold t
    i = first_true(lo, hi, lambda i: a[i] >= t)       # lower bound inside that run
    return i if i < hi and a[i] == t else -1

def search_one_pass(a: list[int], t: int) -> int:
    lo, hi = 0, len(a) - 1                            # closed interval [lo, hi]
    while lo <= hi:
        mid = (lo + hi) // 2
        if a[mid] == t:
            return mid
        if a[lo] <= a[mid]:                           # left half [lo..mid] is sorted
            if a[lo] <= t < a[mid]: hi = mid - 1
            else:                   lo = mid + 1
        else:                                         # right half [mid..hi] is sorted
            if a[mid] < t <= a[hi]: lo = mid + 1
            else:                   hi = mid - 1
    return -1

public static int SearchTwoPass(int[] a, int t)
{
    int n = a.Length, last = a[^1];
    int k = FirstTrue(0, n, i => a[i] <= last);       // start of the second run
    (int lo, int hi) = t <= last ? (k, n) : (0, k);   // the only run that can hold t
    int i = FirstTrue(lo, hi, i => a[i] >= t);
    return i < hi && a[i] == t ? i : -1;
}

public static int SearchOnePass(int[] a, int t)
{
    int lo = 0, hi = a.Length - 1;                    // closed interval [lo, hi]
    while (lo <= hi)
    {
        int mid = lo + (hi - lo) / 2;
        if (a[mid] == t) return mid;
        if (a[lo] <= a[mid])                          // left half is sorted
        {
            if (a[lo] <= t && t < a[mid]) hi = mid - 1;
            else lo = mid + 1;
        }
        else                                          // right half is sorted
        {
            if (a[mid] < t && t <= a[hi]) lo = mid + 1;
            else hi = mid - 1;
        }
    }
    return -1;
}

Both O(log n) time, O(1) space. The a[lo] <= a[mid] uses <= because when lo == mid the one-element left side is sorted.

4. Capacity to Ship Packages Within D Days Medium

Packages go in order; each day the ship carries a prefix of the remaining ones up to its capacity. Find the least capacity that ships everything in days days.

Insight. Search on the answer. feasible(cap) = greedy: keep loading until the next package would overflow, then start a new day. More capacity never needs more days, so F…F T…T. Range: [max(w), sum(w)]: anything below max(w) cannot lift the heaviest package; sum(w) ships everything in one day.

Solution: first feasible capacity 
def ship_within_days(weights: list[int], days: int) -> int:
    def feasible(cap: int) -> bool:                   # greedy is optimal for a fixed cap
        need, load = 1, 0
        for w in weights:
            if load + w > cap:                        # does not fit: start the next day
                need, load = need + 1, 0
            load += w
        return need <= days

    return first_true(max(weights), sum(weights), feasible)  # sum(weights) is always feasible

public static int ShipWithinDays(int[] weights, int days)
{
    bool Feasible(int cap)                            // greedy is optimal for a fixed cap
    {
        int need = 1, load = 0;
        foreach (int w in weights)
        {
            if (load + w > cap) { need++; load = 0; } // start the next day
            load += w;
        }
        return need <= days;
    }
    return FirstTrue(weights.Max(), weights.Sum(), Feasible);
}

O(n log S) time with S = sum(weights); O(1) space. Why greedy is right for a fixed cap: packing as much as possible today can only leave less for later days, never more.

5. Magnetic Force Between Two Balls Medium

Place m balls in baskets at the given positions to maximise the minimum distance between any two balls.

Insight. Max-feasible. can_place(d) greedily puts a ball in the first basket and then in every basket at least d after the last ball. Larger d is harder, so can_place is T…T F…F. The answer is the last true, which is first_true(not can_place) − 1, with no ceiling-mid trickery.

Solution: last feasible distance 
def max_distance(position: list[int], m: int) -> int:
    position.sort()
    def can_place(d: int) -> bool:                    # greedy: leftmost legal basket each time
        count, last = 1, position[0]
        for p in position:
            if p - last >= d:
                count, last = count + 1, p
        return count >= m

    span = position[-1] - position[0]
    # can_place(1) is True (m <= n); can_place(span + 1) is False
    return first_true(1, span + 1, lambda d: not can_place(d)) - 1

public static int MaxDistance(int[] position, int m)
{
    Array.Sort(position);
    bool CanPlace(int d)                              // greedy: leftmost legal basket each time
    {
        int count = 1, last = position[0];
        foreach (int p in position)
            if (p - last >= d) { count++; last = p; }
        return count >= m;
    }
    int span = position[^1] - position[0];
    return FirstTrue(1, span + 1, d => !CanPlace(d)) - 1;
}

O(n log n + n log R) time with R = span; O(1) extra space besides the sort.

6. Split Array Largest Sum Hard

Split nums (non-negative) into k non-empty contiguous parts to minimise the largest part sum.

Insight. It is problem 4 wearing a different coat: “largest part sum ≤ cap” is “ship capacity cap”, and “k parts” is “k days”. If greedy needs at most k pieces it can always split further to use exactly k (each split only lowers sums). The DP alternative is O(k·n²); binary search on the answer is O(n log S).

Solution: minimise the maximum 
def split_array(nums: list[int], k: int) -> int:
    def pieces(cap: int) -> int:                      # fewest parts with every sum <= cap
        count, run = 1, 0
        for x in nums:
            if run + x > cap:
                count, run = count + 1, 0
            run += x
        return count

    return first_true(max(nums), sum(nums), lambda cap: pieces(cap) <= k)

public static int SplitArray(int[] nums, int k)
{
    int Pieces(long cap)                              // fewest parts with every sum <= cap
    {
        int count = 1; long run = 0;
        foreach (int x in nums)
        {
            if (run + x > cap) { count++; run = 0; }
            run += x;
        }
        return count;
    }
    long lo = nums.Max(), hi = nums.Sum(x => (long)x);   // the sum can exceed int
    while (lo < hi)
    {
        long mid = lo + (hi - lo) / 2;
        if (Pieces(mid) <= k) hi = mid; else lo = mid + 1;
    }
    return (int)lo;
}

O(n log S) time, O(1) space.

7. Find K-th Smallest Pair Distance Hard

Among all n(n−1)/2 pairs, return the k-th smallest |a[i] − a[j]|. n up to 10⁴, so listing pairs (5·10⁷) is too slow.

Insight. K-th smallest by counting. Sort; count_le(d) = number of pairs with distance ≤ d, computed by a sliding window in O(n): for each right end r, advance l while a[r] − a[l] > d; then r − l pairs end at r. The first d with count_le(d) ≥ k is the answer, and it is a real distance because the count only changes at real distances.

Solution: binary search the distance, count with two pointers 
def smallest_distance_pair(nums: list[int], k: int) -> int:
    nums.sort()
    def count_le(d: int) -> int:                      # pairs with distance <= d
        count, l = 0, 0
        for r, x in enumerate(nums):
            while x - nums[l] > d:
                l += 1
            count += r - l                            # pairs (l..r-1, r)
        return count

    # count_le(max - min) = all pairs >= k, so hi is a safe exclusive-or-answer wall
    return first_true(0, nums[-1] - nums[0], lambda d: count_le(d) >= k)

public static int SmallestDistancePair(int[] nums, int k)
{
    Array.Sort(nums);
    int CountAtMost(int d)                            // pairs with distance <= d
    {
        int count = 0, l = 0;
        for (int r = 0; r < nums.Length; r++)
        {
            while (nums[r] - nums[l] > d) l++;
            count += r - l;
        }
        return count;
    }
    return FirstTrue(0, nums[^1] - nums[0], d => CountAtMost(d) >= k);
}

O(n log n + n log R) time with R = max − min; O(1) extra space.

8. Median of Two Sorted Arrays Expert

Return the median of two sorted arrays in O(log min(m, n)).

Insight. Binary search the cut i in the shorter array with p(i) = A[i] ≥ B[half − i − 1] (the partition picture above). Out-of-range neighbours count as −∞ on the left and +∞ on the right.

Solution: first-true partition 
from math import inf

def find_median_sorted_arrays(A: list[int], B: list[int]) -> float:
    if len(A) > len(B):
        A, B = B, A                                   # search the shorter array
    m, n = len(A), len(B)
    half = (m + n + 1) // 2                           # size of the left half
    # first i in [0, m) with A[i] >= B[half-i-1]; m if none
    i = first_true(0, m, lambda i: A[i] >= B[half - i - 1])
    j = half - i
    left = max(A[i - 1] if i > 0 else -inf, B[j - 1] if j > 0 else -inf)
    if (m + n) % 2:
        return float(left)                            # odd: the left half holds the median
    right = min(A[i] if i < m else inf, B[j] if j < n else inf)
    return (left + right) / 2

public static double FindMedianSortedArrays(int[] A, int[] B)
{
    if (A.Length > B.Length) (A, B) = (B, A);         // search the shorter array
    int m = A.Length, n = B.Length, half = (m + n + 1) / 2;
    int i = FirstTrue(0, m, i => A[i] >= B[half - i - 1]);
    int j = half - i;
    long left = Math.Max(i > 0 ? A[i - 1] : long.MinValue, j > 0 ? B[j - 1] : long.MinValue);
    if ((m + n) % 2 == 1) return left;                // odd: the left half holds the median
    long right = Math.Min(i < m ? A[i] : long.MaxValue, j < n ? B[j] : long.MaxValue);
    return (left + right) / 2.0;
}

O(log min(m, n)) time, O(1) space. Inside the search i < m ≤ n gives half − i − 1 ≥ 0, so B[half − i − 1] is always a real element.

Self-check

Your predicate is a[i] == t. Why is first_true wrong, and what do you use instead?

Equality is F…F T…T F…F on a sorted array with duplicates, and F…F T F…F with one copy: not monotone. Probes can land on an F to the right of the T’s and discard them. Search the monotone a[i] ≥ t and check a[i] == t once at the end.

With lo, hi = 0, n and while lo < hi, can mid ever equal n?

No. While lo < hi, mid = lo + (hi − lo) // 2 < hi ≤ n, so a[mid] is always in range. The value n is only ever returned, meaning “no true in range”.

You need the last index where p holds and p is T…T F…F. What is the shortest correct code?

first_true(lo, hi, lambda i: not p(i)) − 1. Negating flips T…T F…F into F…F T…T, the first true of not p is the first F, and the cell before it is the last T. This sidesteps the ceiling-mid variant entirely. (If it returns lo − 1, no index satisfies p.)

Array.BinarySearch(a, 25) on [10, 20, 30, 40] returns −3. What does that mean?

25 is absent and would be inserted at index ~(−3) = 2, between 20 and 30. The method returns the bitwise complement of the insertion point so that every “not found” result is negative (insertion point 0 becomes −1, not 0).

Why must Koko’s search start at speed 1 and not 0, and why may it end at max(piles)?

Speed 0 makes feasible divide by zero, and it is never a valid answer anyway. max(piles) eats any pile in one hour, so the total is len(piles) ≤ h: it is guaranteed feasible. That is what lets it serve as the exclusive “known T” wall.

Why is peak finding a binary search even though the array is unsorted?

The invariant is “a peak exists in [lo, hi]”, not “the array is sorted”. If a[mid] < a[mid+1], walking right from mid + 1 must go down eventually (the outside is −∞), so a peak lies in (mid, hi]. Otherwise mid itself or something left of it is a peak. Either way half is discarded and the invariant still holds.

In the median partition, why search the shorter array?

j = half − i must stay in [0, n]. With m ≤ n, every i ∈ [0, m] gives a legal j, and in the loop B[half − i − 1] is always a real element. It also makes the cost O(log min(m, n)).
