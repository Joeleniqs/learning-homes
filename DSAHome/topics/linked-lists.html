LINKED LISTS, STACKS, QUEUES & HEAPS

Linked Lists

Pointer rewiring you can watch: reversal, dummy heads, fast/slow cycle detection, merging, and LRU cache design.

Beginner → Advanced~50 min studyUpdated 2026-11-03

What a linked list really is

An array is one block of memory: element i lives at base + i · size, so you can jump to it in O(1). A linked list gives that up. Each element is a separate node that can live anywhere in memory and holds a reference to the next node. You can't jump to the i-th node; you walk to it. In return, if you are already standing at a node, you can insert or remove next to it in O(1) without shifting anything.

The one rule. Every linked-list algorithm is a short sequence of pointer writes. Before you overwrite a link, make sure something else still references whatever that link was keeping alive. Draw the boxes and arrows, and the bugs become visible.

Array / dynamic array

Index O(1), append amortized O(1), insert or delete in the middle O(n) because everything after it shifts. Cache-friendly. In practice the right default: Python list, C# List<T>.

Singly linked list

Index O(n). Insert or delete after a node you hold: O(1). Deleting a node itself needs its predecessor, so you usually walk with prev. One pointer per node.

Doubly linked list

Each node also has prev, so you can unlink any node you hold in O(1). This is what you pair with a hashmap for LRU caches and ordered sets. C# LinkedList<T> is one.

Where linked lists show up. Interview problems hand you a ListNode head and forbid converting to an array ("in place", "O(1) extra space"). Real systems use them inside other structures: hash-table chaining, LRU caches, free lists, adjacency lists in graphs, the deque behind Python's collections.deque, and the undo history in an editor. The skills you are really learning are pointer rewiring and reasoning about references, which carry over to trees and graphs.

Here is the node type used on this page. It is exactly LeetCode's definition, plus two helpers to convert to and from plain lists while testing.

class ListNode:
    def __init__(self, val=0, next=None):
        self.val = val
        self.next = next

def build(values):                    # [1, 2, 3] -> 1 -> 2 -> 3
    dummy = tail = ListNode()
    for v in values:
        tail.next = ListNode(v)
        tail = tail.next
    return dummy.next

def to_list(head):                    # 1 -> 2 -> 3 -> [1, 2, 3]
    out = []
    while head:
        out.append(head.val)
        head = head.next
    return out

public class ListNode
{
    public int val;
    public ListNode next;
    public ListNode(int val = 0, ListNode next = null) { this.val = val; this.next = next; }
}

public static ListNode Build(params int[] values)
{
    var dummy = new ListNode();
    var tail = dummy;
    foreach (int v in values) { tail.next = new ListNode(v); tail = tail.next; }
    return dummy.next;
}

public static List<int> ToList(ListNode head)
{
    var res = new List<int>();
    for (var p = head; p != null; p = p.next) res.Add(p.val);
    return res;
}

Python and C# reality check. Python has no built-in singly linked list; collections.deque is a doubly linked list of blocks and is what you use for queues. C# has LinkedList<T>, a doubly linked list whose LinkedListNode<T> handles let you Remove(node), AddBefore and AddAfter in O(1). Interview problems almost always use the hand-rolled ListNode above, so practise with that.

The mental model: labels and arrows

Two kinds of statement appear in every linked-list solution, and they do completely different things. Mixing them up causes most linked-list bugs.

Read the assignment target. x = ... (plain name on the left) never changes the list. x.next = ... (a field on the left) always does. When you trace code, redraw an arrow only for the second kind. Garbage collection does the rest: a node that nothing references is gone.

The basic traversal is the same in every problem. The loop condition decides where you stop:

  • while curr: visits every node and stops with curr = null.
  • while curr.next: stops on the last node, which you need when appending.
  • while prev.next: with prev starting at a dummy lets you inspect each node while holding its predecessor, which you need when deleting.
def length(head):
    n, curr = 0, head
    while curr:                 # visits every node; curr ends as None
        n += 1
        curr = curr.next        # moves a label, changes nothing
    return n

public static int Length(ListNode head)
{
    int n = 0;
    for (var curr = head; curr != null; curr = curr.next) n++;
    return n;
}

Pointer surgery: insert and delete with a dummy head

A singly linked node can only change what comes after it. To insert at position k, or to delete the node at position k, you must stop on the node before k. That creates an ugly special case at k = 0, where there is no node before. The fix is a dummy (sentinel) node placed in front of the head, so every real node has a predecessor. At the end you return dummy.next, which is the right head even if the original head was removed or replaced.

Without a dummy

if k == 0:
    return head.next       # special case
prev = head
for _ in range(k - 1):
    prev = prev.next
prev.next = prev.next.next
return head

Two code paths, and it crashes on an empty list.

With a dummy

dummy = ListNode(0, head)
prev = dummy
for _ in range(k):
    prev = prev.next
prev.next = prev.next.next
return dummy.next

One code path. The head is no longer special.

Step through an insert. Watch the order of the two writes: the new node is hooked to the rest of the list first, so the old link can be replaced safely.

Now the same two writes in the wrong order. The first write destroys the only reference to the rest of the list, and the second write reads the link that was just written.

Deleting is one write: the predecessor bypasses the victim. Try k = 0 to see that the dummy makes deleting the head identical to any other delete.

Removing every node with a given value has one extra subtlety. After a removal, the new prev.next hasn't been checked yet, so prev must stay where it is. Try 6,6,6 to remove everything, including the head.

def insert_at(head, k, x):
    dummy = ListNode(0, head)
    prev = dummy
    for _ in range(k):                   # stop on the node before position k
        prev = prev.next
    prev.next = ListNode(x, prev.next)   # the right side runs first: node.next = rest, then splice
    return dummy.next

def delete_at(head, k):
    dummy = ListNode(0, head)
    prev = dummy
    for _ in range(k):
        prev = prev.next
    prev.next = prev.next.next           # bypass
    return dummy.next

def remove_elements(head, x):            # LeetCode 203
    dummy = ListNode(0, head)
    prev = dummy
    while prev.next:
        if prev.next.val == x:
            prev.next = prev.next.next   # stay put: the new prev.next is unchecked
        else:
            prev = prev.next
    return dummy.next

public static ListNode InsertAt(ListNode head, int k, int x)
{
    var dummy = new ListNode(0, head);
    var prev = dummy;
    for (int i = 0; i < k; i++) prev = prev.next;
    prev.next = new ListNode(x, prev.next);
    return dummy.next;
}

public static ListNode DeleteAt(ListNode head, int k)
{
    var dummy = new ListNode(0, head);
    var prev = dummy;
    for (int i = 0; i < k; i++) prev = prev.next;
    prev.next = prev.next.next;
    return dummy.next;
}

public static ListNode RemoveElements(ListNode head, int x)
{
    var dummy = new ListNode(0, head);
    var prev = dummy;
    while (prev.next != null)
    {
        if (prev.next.val == x) prev.next = prev.next.next;
        else prev = prev.next;
    }
    return dummy.next;
}

Three classic surgery bugs.

  1. Lost tail: writing prev.next = node before node.next = prev.next. Rule: wire the new node's outgoing link first.
  2. Skipped duplicates: advancing prev right after a deletion. With 1 → 6 → 6 → 2 and x = 6, the second 6 survives.
  3. Null dereference: touching p.next.next without checking p.next. Every .next you read must belong to a node you know is not null; write the guard into the loop condition (while fast and fast.next).

Delete a node when you only hold that node (LeetCode 237, not the tail). You can't reach its predecessor, so copy the next node's value into it and delete the next node instead: node.val = node.next.val; node.next = node.next.next. It is a trick, not a pattern, because it moves values instead of nodes.

Reversal: the pattern behind a dozen problems

Reversing a list in place is the most reused linked-list move. Reverse in groups, reverse a range, palindrome checks, reordering and adding numbers stored in reverse all build on it. The whole idea is one invariant:

Each iteration does four things, always in this order: save nxt = curr.next, flip curr.next = prev, then advance prev = curr and curr = nxt. Step through it, then try the one-node and two-node lists.

Skip the save and see what happens. After the first flip, curr.next points backwards, so curr = curr.next walks backwards too, straight to null.

The recursive version reads differently but does the same flips, in the opposite order: from the tail back to the head while the call stack unwinds. The key line is head.next.next = head. After the recursive call returns, head.next still points at the node that is now the tail of the reversed suffix, so that node's next is set back to head. See Recursion for the "trust the call" habit.

def reverse(head):
    prev, curr = None, head
    while curr:
        nxt = curr.next       # 1) save
        curr.next = prev      # 2) flip
        prev = curr           # 3) advance prev
        curr = nxt            # 4) advance curr
    return prev

def reverse_recursive(head):
    if head is None or head.next is None:
        return head
    new_head = reverse_recursive(head.next)
    head.next.next = head     # the node after me points back at me
    head.next = None          # I am the tail for now
    return new_head

public static ListNode Reverse(ListNode head)
{
    ListNode prev = null, curr = head;
    while (curr != null)
    {
        var nxt = curr.next;  // 1) save
        curr.next = prev;     // 2) flip
        prev = curr;          // 3) advance prev
        curr = nxt;           // 4) advance curr
    }
    return prev;
}

public static ListNode ReverseRecursive(ListNode head)
{
    if (head == null || head.next == null) return head;
    var newHead = ReverseRecursive(head.next);
    head.next.next = head;
    head.next = null;
    return newHead;
}

Python's one-line swap is order-sensitive. curr.next, prev, curr = prev, curr, curr.next is correct: the right side is evaluated first, then the targets are assigned left to right, and curr.next is assigned while curr is still the old node. Reorder the targets to curr, curr.next, prev = ... and curr.next is written on the new curr, silently corrupting the list. When in doubt, use the four explicit lines.

Reverse only positions left..right

Reverse Linked List II asks you to reverse a range in one pass. The elegant method keeps two fixed anchors: pre, the node before the range, and curr, the first node of the range. Then, right − left times, it lifts the node after curr and moves it to the front of the range (right after pre). curr is never reassigned; it simply drifts to the end of the range as nodes jump over it.

def reverse_between(head, left, right):
    dummy = ListNode(0, head)
    pre = dummy
    for _ in range(left - 1):
        pre = pre.next
    curr = pre.next
    for _ in range(right - left):
        move = curr.next
        curr.next = move.next        # unhook move
        move.next = pre.next         # move points at the current front
        pre.next = move              # move becomes the front
    return dummy.next

public static ListNode ReverseBetween(ListNode head, int left, int right)
{
    var dummy = new ListNode(0, head);
    var pre = dummy;
    for (int i = 0; i < left - 1; i++) pre = pre.next;
    var curr = pre.next;
    for (int i = 0; i < right - left; i++)
    {
        var move = curr.next;
        curr.next = move.next;
        move.next = pre.next;
        pre.next = move;
    }
    return dummy.next;
}

Reverse in groups of k

Reverse Nodes in k-Group is the hard version: reverse every full block of k nodes and leave a short tail alone. It is three moves you already know, in a loop:

  1. From the anchor group_prev, walk k steps to find kth. If you hit null, the remaining nodes form a short group, so stop.
  2. Reverse the group with an ordinary reversal, but start with prev = group_next instead of null. The group's first node then points directly at the next group, so that side is stitched automatically.
  3. Stitch the front: group_prev.next = kth. The old first node is now the group's last node, so it becomes the next group_prev.

The full solution is worked problem 1 below.

Fast and slow pointers on a list

Two pointers that move at different speeds, or at the same speed with a fixed gap, answer position questions in one pass without knowing the length. Two Pointers develops this family on arrays (including the full proof of Floyd's algorithm); here you see it on real nodes.

Middle of the list. fast moves two nodes per round and slow moves one. When fast can't take two more steps, slow is in the middle. With while fast and fast.next, an even-length list gives the second middle; with while fast.next and fast.next.next it gives the first middle, which is what you want when you split a list into two halves for merge sort.

Remove the n-th node from the end. Instead of different speeds, use the same speed with a fixed gap. Move fast n + 1 steps ahead of slow, then move both until fast falls off the end. slow is then exactly on the node before the target. Starting both at a dummy covers the case where the target is the head itself.

def middle_node(head):               # second middle for even n
    slow = fast = head
    while fast and fast.next:
        slow = slow.next
        fast = fast.next.next
    return slow

def remove_nth_from_end(head, n):
    dummy = ListNode(0, head)
    fast = slow = dummy
    for _ in range(n + 1):           # gap of n + 1 links
        fast = fast.next
    while fast:
        fast = fast.next
        slow = slow.next
    slow.next = slow.next.next       # slow is just before the target
    return dummy.next

public static ListNode MiddleNode(ListNode head)
{
    ListNode slow = head, fast = head;
    while (fast != null && fast.next != null)
    {
        slow = slow.next;
        fast = fast.next.next;
    }
    return slow;
}

public static ListNode RemoveNthFromEnd(ListNode head, int n)
{
    var dummy = new ListNode(0, head);
    ListNode fast = dummy, slow = dummy;
    for (int i = 0; i <= n; i++) fast = fast.next;
    while (fast != null) { fast = fast.next; slow = slow.next; }
    slow.next = slow.next.next;
    return dummy.next;
}

Cycle detection. A corrupted list may loop back on itself, and then while curr never ends. Floyd's algorithm detects this in O(1) space. Phase 1: if fast reaches null, there is no cycle; otherwise fast gains one node per step inside the loop and must land on slow. Phase 2: restart one pointer at the head and move both one step at a time. They meet at the entrance of the cycle. Set the tail's target with the second input (-1 = no cycle); the indices under the nodes help you check μ (the tail length) and λ (the loop length).

def has_cycle(head):
    slow = fast = head
    while fast and fast.next:
        slow, fast = slow.next, fast.next.next
        if slow is fast:             # identity, not equal values
            return True
    return False

def detect_cycle(head):              # LeetCode 142: the entrance node or None
    slow = fast = head
    while fast and fast.next:
        slow, fast = slow.next, fast.next.next
        if slow is fast:
            break
    else:
        return None                  # loop ended without break: no cycle
    p = head
    while p is not slow:
        p, slow = p.next, slow.next
    return p

public static bool HasCycle(ListNode head)
{
    ListNode slow = head, fast = head;
    while (fast != null && fast.next != null)
    {
        slow = slow.next;
        fast = fast.next.next;
        if (slow == fast) return true;    // reference equality for classes
    }
    return false;
}

public static ListNode DetectCycle(ListNode head)
{
    ListNode slow = head, fast = head;
    while (true)
    {
        if (fast == null || fast.next == null) return null;
        slow = slow.next;
        fast = fast.next.next;
        if (slow == fast) break;
    }
    var p = head;
    while (p != slow) { p = p.next; slow = slow.next; }
    return p;
}

Why phase 2 works, in one line. When they meet, slow has walked some distance d and fast 2d; the difference d is a whole number of loops. A pointer that walks μ more steps from the meeting point therefore lands where a pointer walking μ steps from the head lands: at the entrance. The picture with μ, λ and the meeting point is on Two Pointers.

Merging: two lists, then k lists

Merging two sorted lists is the list version of the merge step in merge sort. You don't create nodes; you relink the existing ones. A dummy gives tail somewhere to stand before the first node is chosen, and when one list runs out, the other is attached with a single assignment because it is already sorted and already linked.

In the visualizer each node is drawn in the column it will occupy in the result, with list a on top and list b below. Watch tail zigzag between the two rows.

def merge_two(a, b):
    dummy = tail = ListNode()
    while a and b:
        if a.val <= b.val:           # <= keeps equal keys in order (stable)
            tail.next, a = a, a.next
        else:
            tail.next, b = b, b.next
        tail = tail.next
    tail.next = a or b               # attach the leftover in O(1)
    return dummy.next

public static ListNode MergeTwoLists(ListNode a, ListNode b)
{
    var dummy = new ListNode();
    var tail = dummy;
    while (a != null && b != null)
    {
        if (a.val <= b.val) { tail.next = a; a = a.next; }
        else { tail.next = b; b = b.next; }
        tail = tail.next;
    }
    tail.next = a ?? b;
    return dummy.next;
}

Merging k lists. With N nodes in total across k lists, there are three approaches:

  • Merge one at a time (result = merge(result, list_i)): the growing result is re-walked k times, so O(N·k).
  • Heap of fronts: keep the current front of each list in a min-heap of size k. Pop the smallest, append it, and push its successor. That is O(N log k). Heaps are covered in depth in Heaps and Priority Queues.
  • Divide and conquer: merge the lists in pairs, then the results in pairs, and so on, like the bottom-up passes of merge sort. There are log k rounds, each touching all N nodes once, so it is also O(N log k) with no heap.

Both O(N log k) versions are in worked problem 2.

Combining patterns: palindrome and reorder

Many medium problems are three patterns glued together: find the middle, reverse the back half, then walk both halves together. A singly linked list can't walk backwards, so you make the back half walk backwards by reversing it.

Palindrome Linked List compares the front half with the reversed back half, outside-in. For odd length the middle node ends up at the end of both halves and is compared with itself, which is harmless. Try a non-palindrome such as 1,2,3,1.

Reorder List (L0 → Ln → L1 → Ln−1 → …) cuts the list after the middle, reverses the back half, and weaves the two halves together. The weave saves both successors before rewiring: two saves, then two writes.

def is_palindrome(head):
    slow = fast = head
    while fast and fast.next:
        slow, fast = slow.next, fast.next.next
    back = reverse(slow)
    p, q, ok = head, back, True
    while q:
        if p.val != q.val:
            ok = False
            break
        p, q = p.next, q.next
    reverse(back)                    # restore the caller's list
    return ok

def reorder_list(head):
    if not head:
        return
    slow = fast = head
    while fast and fast.next:
        slow, fast = slow.next, fast.next.next
    second, slow.next = slow.next, None     # cut after the middle
    second = reverse(second)
    first = head
    while second:
        t1, t2 = first.next, second.next    # save both successors
        first.next, second.next = second, t1
        first, second = t1, t2

public static bool IsPalindrome(ListNode head)
{
    ListNode slow = head, fast = head;
    while (fast != null && fast.next != null) { slow = slow.next; fast = fast.next.next; }
    var back = Reverse(slow);
    bool ok = true;
    for (ListNode p = head, q = back; q != null; p = p.next, q = q.next)
        if (p.val != q.val) { ok = false; break; }
    Reverse(back);
    return ok;
}

public static void ReorderList(ListNode head)
{
    if (head == null) return;
    ListNode slow = head, fast = head;
    while (fast != null && fast.next != null) { slow = slow.next; fast = fast.next.next; }
    var second = Reverse(slow.next);
    slow.next = null;
    var first = head;
    while (second != null)
    {
        ListNode t1 = first.next, t2 = second.next;
        first.next = second;
        second.next = t1;
        first = t1;
        second = t2;
    }
}

Intersection of two lists

Two lists may merge into a shared tail (a "Y" shape). You must return the first shared node, compared by identity, not by value. Counting both lengths and advancing the longer list by the difference works. The two-pointer trick is shorter: each pointer walks its own list and then switches to the other list's head. Both pointers then walk a + c + b nodes before reaching the junction, so they arrive together.

def get_intersection_node(head_a, head_b):
    pa, pb = head_a, head_b
    while pa is not pb:
        pa = pa.next if pa else head_b
        pb = pb.next if pb else head_a
    return pa

public static ListNode GetIntersectionNode(ListNode headA, ListNode headB)
{
    ListNode pa = headA, pb = headB;
    while (pa != pb)
    {
        pa = pa == null ? headB : pa.next;
        pb = pb == null ? headA : pb.next;
    }
    return pa;
}

Extra pointers: copying a list with random links

In Copy List with Random Pointer, each node also has a random field that can point anywhere in the list, or to null. You must build a deep copy whose random fields point at copies, never at originals. The difficulty: when you copy node X, the copy of X.random may not exist yet.

The easy fix is a hashmap original → copy, filled in one pass and wired in a second pass. The O(1)-space trick stores that map inside the list: insert each copy directly after its original, so original.next is the copy. Then copy.random = original.random.next, and finally unweave the two lists.

The full solution, in both versions, is worked problem 3.

Doubly linked lists and the LRU cache

An LRU (least recently used) cache holds at most capacity keys. get and put must both run in O(1), and when the cache is full, the key that was used longest ago is evicted. Two structures, each covering the other's weakness:

  • A hashmap key → node finds any entry in O(1), but has no notion of order.
  • A doubly linked list keeps entries in recency order (most recent next to the head). It can move or remove a node in O(1), but only if you already hold that node. The hashmap gives you the node.

The list must be doubly linked because removing a node requires changing its predecessor, and only a prev pointer gives you the predecessor without a walk. Two sentinel nodes (head and tail) mean every real node always has a real neighbour on each side, so the unlink and insert code has no null checks at all.

Step through the classic LeetCode example (capacity 2), then try your own sequence of operations. Detached nodes drop below the list while they are being moved.

class Node:
    __slots__ = ("key", "val", "prev", "next")
    def __init__(self, key=0, val=0):
        self.key, self.val = key, val
        self.prev = self.next = None

class LRUCache:
    def __init__(self, capacity: int):
        self.cap = capacity
        self.map = {}                              # key -> Node
        self.head, self.tail = Node(), Node()      # sentinels
        self.head.next, self.tail.prev = self.tail, self.head

    def _unlink(self, n):
        n.prev.next, n.next.prev = n.next, n.prev

    def _push_front(self, n):
        n.prev, n.next = self.head, self.head.next
        self.head.next.prev = n
        self.head.next = n

    def get(self, key: int) -> int:
        if key not in self.map:
            return -1
        node = self.map[key]
        self._unlink(node)
        self._push_front(node)                     # now most recent
        return node.val

    def put(self, key: int, value: int) -> None:
        if key in self.map:
            self._unlink(self.map.pop(key))
        node = self.map[key] = Node(key, value)
        self._push_front(node)
        if len(self.map) > self.cap:
            lru = self.tail.prev                   # least recent
            self._unlink(lru)
            del self.map[lru.key]

public class LRUCache
{
    private readonly int cap;
    private readonly Dictionary<int, LinkedListNode<(int Key, int Val)>> map = new();
    private readonly LinkedList<(int Key, int Val)> order = new();   // First = most recent

    public LRUCache(int capacity) { cap = capacity; }

    public int Get(int key)
    {
        if (!map.TryGetValue(key, out var node)) return -1;
        order.Remove(node);              // O(1): we hold the node itself
        order.AddFirst(node);
        return node.Value.Val;
    }

    public void Put(int key, int value)
    {
        if (map.TryGetValue(key, out var old)) order.Remove(old);
        map[key] = order.AddFirst((key, value));
        if (map.Count > cap)
        {
            var lru = order.Last;
            order.RemoveLast();
            map.Remove(lru.Value.Key);
        }
    }
}

Library shortcut. Python's collections.OrderedDict is a hashmap plus a doubly linked list, so an LRU cache is move_to_end(key) on every access and popitem(last=False) to evict. Interviewers often accept it once you have explained the structure underneath, but be ready to write the version above. In C#, LinkedList<T>.Remove(node) is O(1) only when you pass the node; Remove(value) searches the list in O(n).

from collections import OrderedDict

class LRUCacheOD:
    def __init__(self, capacity):
        self.cap, self.d = capacity, OrderedDict()

    def get(self, key):
        if key not in self.d:
            return -1
        self.d.move_to_end(key)              # most recent at the end
        return self.d[key]

    def put(self, key, value):
        self.d[key] = value
        self.d.move_to_end(key)
        if len(self.d) > self.cap:
            self.d.popitem(last=False)       # least recent at the front

Pitfalls and a debugging checklist

Pitfall: losing the rest of the list curr.next = prev before saving curr.next cuts the only path to the remaining nodes, and they are gone (in C# and Python they become garbage). Rule: before you overwrite a .next, make sure some variable still holds what it pointed to. Step through the "bug" visualizer in the Reversal section to see this happen.

Pitfall: a cycle you created yourself After reordering, partitioning or splitting, the old last node may still point into the middle of the new list. Printing it then loops forever. Always terminate the new tail explicitly (tail.next = None). Partition List and Reorder List both fail this way when the line is missing.

Pitfall: dereferencing null fast.next.next needs fast and fast.next to be non-null, in that order (fast and fast.next). Before any x.next, ask yourself: "can x be null here?" Typical cases are an empty list, a single node, and the last step of a loop.

Pitfall: off by one in the gap To delete a node you must stand on the node before it. That is why Remove Nth uses a gap of n + 1 starting from a dummy, and why Reverse Between walks left − 1 steps from the dummy. Check the edges with tiny inputs: n equal to the length (delete the head) and left = 1.

Pitfall: comparing values instead of nodes Intersection, cycle detection and the random-pointer map are all about node identity. In Python use is (and dictionary keys are compared by identity for objects without __eq__). In C#, == on a class compares references, which is what you want, unless someone has overloaded it.

Pitfall: Python tuple assignment order a.next, a = b, a.next is fine. All right-hand values are computed first, then assigned left to right. a, a.next = a.next, b instead sets a first and then writes .next on the new a. When in doubt, use a temporary.

Debugging checklist. Draw three nodes and the pointers on paper, then for each line of code:

  1. Which arrow changes? Draw the new arrow and cross out the old one.
  2. Is every node still reachable from some variable?
  3. After the loop: does head (or dummy.next) point at the new first node, and does the last node point to null?
  4. Run the cases: empty list, 1 node, 2 nodes, the operation at the head, the operation at the tail.

Recognize it when

  • The input is a linked list: the answer is almost always O(1) extra space with pointer moves, plus a dummy if the head can change.
  • You need O(1) insert/delete in the middle of an ordered collection, and you can reach the position directly (through a hashmap): LRU, LFU, ordered dictionaries, browser history, undo lists.
  • A question about a position you don't know in advance (middle, k-th from the end, the start of a cycle): fast and slow pointers.
  • You need to walk backwards in a singly linked list: reverse that part (or use a stack, which costs O(n) space).
  • Sorting a linked list: merge sort, because merging is natural and needs no random access.

Worked problems

1. Reverse Nodes in k-Group Hard

Reverse the list in blocks of k; a final block shorter than k stays as it is. Insight: it is "reverse between" repeated. Keep group_prev (the node before the current block). First check that k nodes exist (find the k-th node; if missing, stop). Then reverse exactly k nodes, using the node after the block as the initial prev, so the reversed block is already attached to the rest. Finally stitch the block back: group_prev.next becomes the old k-th node, and the old first node becomes the new group_prev. The visualizer in the Reversal section runs exactly this.

Solution: O(n) time, O(1) extra space 
def reverse_k_group(head, k):
    dummy = ListNode(0, head)
    group_prev = dummy
    while True:
        kth = group_prev
        for _ in range(k):                 # is there a full block?
            kth = kth.next
            if not kth:
                return dummy.next
        group_next = kth.next
        prev, curr = group_next, group_prev.next   # block attaches to the rest
        while curr is not group_next:
            nxt = curr.next
            curr.next = prev
            prev, curr = curr, nxt
        first = group_prev.next            # old first, now last of the block
        group_prev.next = kth              # old k-th, now first
        group_prev = first

public static ListNode ReverseKGroup(ListNode head, int k)
{
    var dummy = new ListNode(0, head);
    var groupPrev = dummy;
    while (true)
    {
        var kth = groupPrev;
        for (int i = 0; i < k; i++)
        {
            kth = kth.next;
            if (kth == null) return dummy.next;
        }
        var groupNext = kth.next;
        ListNode prev = groupNext, curr = groupPrev.next;
        while (curr != groupNext)
        {
            var nxt = curr.next;
            curr.next = prev;
            prev = curr;
            curr = nxt;
        }
        var first = groupPrev.next;
        groupPrev.next = kth;
        groupPrev = first;
    }
}

2. Merge k Sorted Lists Hard

Insight: at every moment the next output node is the smallest of the k current fronts. A min-heap gives that in O(log k). In Python, nodes aren't comparable, so push (val, i, node): the unique index i breaks ties before Python ever tries to compare two nodes. The divide-and-conquer version needs only merge_two.

Solution: O(N log k) time; heap O(k) space, divide and conquer O(1) extra space 
import heapq

def merge_k_lists(lists):
    heap = [(node.val, i, node) for i, node in enumerate(lists) if node]
    heapq.heapify(heap)
    dummy = tail = ListNode()
    while heap:
        _, i, node = heapq.heappop(heap)
        tail.next = tail = node
        if node.next:
            heapq.heappush(heap, (node.next.val, i, node.next))
    return dummy.next

def merge_k_lists_dc(lists):
    if not lists:
        return None
    step = 1
    while step < len(lists):               # rounds: pairs, then pairs of pairs...
        for i in range(0, len(lists) - step, step * 2):
            lists[i] = merge_two(lists[i], lists[i + step])
        step *= 2
    return lists[0]

public static ListNode MergeKLists(ListNode[] lists)
{
    var pq = new PriorityQueue<ListNode, int>();
    foreach (var node in lists)
        if (node != null) pq.Enqueue(node, node.val);
    var dummy = new ListNode();
    var tail = dummy;
    while (pq.TryDequeue(out var node, out _))
    {
        tail.next = node;
        tail = node;
        if (node.next != null) pq.Enqueue(node.next, node.next.val);
    }
    return dummy.next;
}

public static ListNode MergeKListsDC(ListNode[] lists)
{
    if (lists.Length == 0) return null;
    for (int step = 1; step < lists.Length; step *= 2)
        for (int i = 0; i + step < lists.Length; i += step * 2)
            lists[i] = MergeTwoLists(lists[i], lists[i + step]);
    return lists[0];
}

tail.next = tail = node in Python assigns left to right: first tail.next = node (on the old tail), then tail = node. That is correct here, but it is exactly the kind of line the tuple-order pitfall warns about. Write two lines if it makes you hesitate.

3. Copy List with Random Pointer Medium

Insight: the only hard part is finding "the copy of X" for any X. A hashmap answers it directly. The weave answers it with X.next, because the copy was inserted right after X. Unweaving must restore the original list exactly; the judge checks it.

Solution: hashmap O(n) space, or weave O(1) extra space 
class Node:                                 # LeetCode's node: val, next, random
    def __init__(self, x, next=None, random=None):
        self.val, self.next, self.random = x, next, random

def copy_random_list(head):                 # two passes with a map
    copy = {None: None}
    p = head
    while p:
        copy[p] = Node(p.val)
        p = p.next
    p = head
    while p:
        copy[p].next = copy[p.next]
        copy[p].random = copy[p.random]
        p = p.next
    return copy[head]

def copy_random_list_weave(head):           # O(1) extra space
    if not head:
        return None
    p = head
    while p:                                # 1. A → A' → B → B' ...
        p.next = Node(p.val, p.next)
        p = p.next.next
    p = head
    while p:                                # 2. the copy of X.random is X.random.next
        if p.random:
            p.next.random = p.random.next
        p = p.next.next
    new_head, p = head.next, head
    while p:                                # 3. unweave both lists
        c = p.next
        p.next = c.next
        c.next = c.next.next if c.next else None
        p = p.next
    return new_head

public class Node
{
    public int val;
    public Node next, random;
    public Node(int v, Node nxt = null) { val = v; next = nxt; }
}

public static Node CopyRandomList(Node head)
{
    var copy = new Dictionary<Node, Node>();
    for (var p = head; p != null; p = p.next) copy[p] = new Node(p.val);
    for (var p = head; p != null; p = p.next)
    {
        copy[p].next = p.next == null ? null : copy[p.next];
        copy[p].random = p.random == null ? null : copy[p.random];
    }
    return head == null ? null : copy[head];
}

public static Node CopyRandomListWeave(Node head)
{
    if (head == null) return null;
    for (var p = head; p != null; p = p.next.next) p.next = new Node(p.val, p.next);
    for (var p = head; p != null; p = p.next.next)
        if (p.random != null) p.next.random = p.random.next;
    var newHead = head.next;
    for (var p = head; p != null; p = p.next)
    {
        var c = p.next;
        p.next = c.next;
        c.next = c.next?.next;
    }
    return newHead;
}

4. Sort List Medium

Sort a linked list in O(n log n). Insight: merge sort fits lists perfectly. Splitting needs only the middle, and merging is the merge_two you already have, with no extra array. Split at the first middle (start fast at head.next), otherwise a 2-node list splits into 2 + 0 and the recursion never ends.

Solution: O(n log n) time, O(log n) recursion stack 
def sort_list(head):
    if not head or not head.next:
        return head
    slow, fast = head, head.next            # first middle for even length
    while fast and fast.next:
        slow, fast = slow.next, fast.next.next
    right, slow.next = slow.next, None      # cut into two halves
    return merge_two(sort_list(head), sort_list(right))

public static ListNode SortList(ListNode head)
{
    if (head == null || head.next == null) return head;
    ListNode slow = head, fast = head.next;
    while (fast != null && fast.next != null) { slow = slow.next; fast = fast.next.next; }
    var right = slow.next;
    slow.next = null;
    return MergeTwoLists(SortList(head), SortList(right));
}

The strict O(1)-space follow-up is bottom-up merge sort: merge runs of size 1, 2, 4, … in place with a dummy and a "split off the first n nodes" helper. It is the same idea as the divide-and-conquer figure above, but on a single list.

5. Add Two Numbers Medium

Digits are stored in reverse order (ones first), for example 342 + 465 = 807 as 2→4→3 + 5→6→4 = 7→0→8. Insight: this is grade-school addition from the right, and the reversed order means the list starts at the right. Loop while either list or the carry is left; a missing digit counts as 0.

Solution: O(max(m, n)) time 
def add_two_numbers(l1, l2):
    dummy = tail = ListNode()
    carry = 0
    while l1 or l2 or carry:
        s = carry + (l1.val if l1 else 0) + (l2.val if l2 else 0)
        carry, digit = divmod(s, 10)
        tail.next = ListNode(digit)
        tail = tail.next
        l1 = l1.next if l1 else None
        l2 = l2.next if l2 else None
    return dummy.next

public static ListNode AddTwoNumbers(ListNode l1, ListNode l2)
{
    var dummy = new ListNode();
    var tail = dummy;
    int carry = 0;
    while (l1 != null || l2 != null || carry != 0)
    {
        int s = carry + (l1?.val ?? 0) + (l2?.val ?? 0);
        carry = s / 10;
        tail.next = new ListNode(s % 10);
        tail = tail.next;
        l1 = l1?.next;
        l2 = l2?.next;
    }
    return dummy.next;
}

Add Two Numbers II stores the digits most significant first. Either reverse both lists, add, and reverse the result, or push the digits onto two stacks (see Stacks and Queues) and build the answer by inserting at the front.

6. Partition List Medium

Put all nodes with value < x before the others, keeping the original relative order within each group. Insight: build two lists with two dummies, lo and hi, appending each node to one of them, then join lo_tail.next = hi.next. The line that is easy to forget is hi_tail.next = None: the last node of the high list may still point at a low node, and that creates a cycle.

Solution: O(n) time, O(1) extra space, stable 
def partition(head, x):
    lo = lo_tail = ListNode()
    hi = hi_tail = ListNode()
    while head:
        if head.val < x:
            lo_tail.next = lo_tail = head
        else:
            hi_tail.next = hi_tail = head
        head = head.next
    hi_tail.next = None                     # cut the old link: no accidental cycle
    lo_tail.next = hi.next
    return lo.next

public static ListNode Partition(ListNode head, int x)
{
    ListNode lo = new ListNode(), hi = new ListNode();
    ListNode loTail = lo, hiTail = hi;
    for (; head != null; head = head.next)
    {
        if (head.val < x) { loTail.next = head; loTail = head; }
        else { hiTail.next = head; hiTail = head; }
    }
    hiTail.next = null;
    loTail.next = hi.next;
    return lo.next;
}

Self-check

Why does a dummy head remove the special cases?

Every edit to a list changes the .next of the node before the position. The first real node has no node before it, so without a dummy "insert/delete at the head" must reassign head instead. The dummy gives every real node a predecessor, so one code path covers all positions, and dummy.next is always the current head, even if the old head was deleted.

In iterative reversal, what goes wrong if you skip nxt = curr.next?

curr.next = prev overwrites the only reference to the rest of the list. The next line, curr = curr.next, then moves backwards to prev, and the remaining nodes are unreachable. On 1→2→3 you get 1 pointing at null and the loop ends with only one node.

Remove Nth From End: why a gap of n + 1, and why start both pointers at a dummy?

When fast is null, slow is exactly n + 1 links behind it, so slow is the node before the n-th from the end, which is the node whose .next you have to change. If the target is the head itself, the node before it is the dummy, which only exists if you started there.

LRU: why a doubly linked list, and why store the key in each node?

Moving or evicting a node means unlinking it, and that changes its predecessor's next. With only next pointers, finding the predecessor is an O(n) walk. prev gives it in O(1). The key is needed at eviction time: you get the node from tail.prev and must also delete its hashmap entry, and the node is the only place that knows which key it belongs to.

Why is merging k lists one after another O(N·k), but the heap version O(N log k)?

Merging one after another re-walks the growing result every time: with k lists of N/k nodes, the result has N/k, 2N/k, … nodes, about N·k/2 steps in total. The heap version touches each node once (one pop and one push at O(log k) each), and the pairwise version has log k rounds that each touch every node once.

Intersection: why does while pa is not pb terminate when the lists don't intersect?

Each pointer walks its own list, then switches, so after a + b steps both are at null at the same time. null is null is true and the loop exits, returning null. Each pointer switches only once, so there is no infinite ping-pong.

In Palindrome Linked List with odd length, what happens to the middle node?

slow stops on the middle node and the reversal starts there, so the middle becomes the last node of the reversed back half. The front half still reaches it too (its predecessor's next was never changed). The comparison ends by comparing the middle with itself, which always matches. No special case is needed.
