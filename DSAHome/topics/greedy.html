BACKTRACKING & GREEDY

Greedy Algorithms

When a local choice is globally safe: exchange arguments, interval scheduling, jump games, gas station and Huffman coding.

Intermediate → Expert~55 min studyBuilds on: Sorting AlgorithmsUpdated 2026-11-03

What greedy is, and why it is dangerous

A greedy algorithm builds the answer one decision at a time, and at each step it takes the option that looks best right now: the earliest-ending meeting, the largest coin, the cheapest edge. Then it never reconsiders. No backtracking, no table of subproblems. It does one pass, usually after a sort or with a heap, so the cost is typically O(n log n).

Greedy is correct only when the locally best choice is safe: some optimal solution contains it. Prove that safety with an exchange argument or a "stays ahead" argument, or break it with a counterexample, before you trust it.

The picture below shows the difference from the two other ways of exploring choices. Backtracking walks the whole decision tree. Dynamic programming visits each distinct state once and compares all choices. Greedy follows one root-to-leaf path and ignores everything else, which makes it the fastest of the three and the only one that can be confidently wrong.

Every greedy algorithm on this page has the same three ingredients, and it is worth naming them before writing any code:

  1. An order. Usually a sort key (end time, ratio, difference, deadline) or a priority queue that always hands you the current best.
  2. A choice rule. Take it, skip it, or replace the worst thing you took earlier.
  3. A safety argument. Why some optimal solution agrees with that choice. Without this, you are guessing.

Most of the skill is in the third item, so the page starts there.

Proving a greedy choice is safe

There are two standard proofs. Both are short once you see the picture, and doing them on paper (even informally) is the fastest way to find out whether your rule is wrong.

The exchange argument

Take any optimal solution O. Find the first place where it disagrees with the greedy solution G. Show that you can swap O's choice for G's choice without making O worse. Now O agrees with G for one more step and is still optimal. Repeat until O is G. So G is optimal.

Run it. The problem: n jobs on one machine, minimise the sum of completion times (equivalently, the average waiting time). The visualizer starts from an arbitrary order and swaps adjacent inversions one at a time. Watch the total: it never goes up. The labels on top (×k) show how many completion times include each job, which is why the shortest jobs belong at the front where they are counted the most.

def min_total_completion(times):
    total = finish = 0
    for t in sorted(times):        # shortest job first
        finish += t                # this job's completion time
        total += finish
    return total

public static long MinTotalCompletion(int[] times)
{
    var sorted = (int[])times.Clone();
    Array.Sort(sorted);                   // shortest job first
    long total = 0, finish = 0;
    foreach (int t in sorted)
    {
        finish += t;                      // this job's completion time
        total += finish;
    }
    return total;
}

The same argument proves many sort keys you will meet below: Two City Scheduling (sort by cost difference), Boats to Save People (pair the heaviest with the lightest), and the deadline order in Course Schedule III. The question to ask is always: if two neighbours are in the "wrong" order, does swapping them help or at least not hurt?

Greedy stays ahead

The second proof compares progress instead of swapping. Show by induction that after k steps, the greedy partial solution is at least as good as the first k steps of any solution, by some measure. If greedy is never behind, it cannot finish behind.

The classic case is interval scheduling: pick the most non-overlapping intervals. The greedy rule is "take the interval that ends earliest among those that start after the last one taken". The measure is the end time of the k-th chosen interval.

def max_non_overlapping(intervals):
    count, end = 0, float("-inf")
    for s, e in sorted(intervals, key=lambda iv: iv[1]):   # earliest end first
        if s >= end:            # starts after the last chosen one ends
            count += 1
            end = e
    return count

public static int MaxNonOverlapping(int[][] intervals)
{
    var byEnd = intervals.OrderBy(iv => iv[1]).ToArray();   // earliest end first
    int count = 0;
    long end = long.MinValue;
    foreach (var iv in byEnd)
    {
        if (iv[0] >= end)       // starts after the last chosen one ends
        {
            count++;
            end = iv[1];
        }
    }
    return count;
}

Interval greedy has its own page, with merging, sweeps and meeting rooms: Intervals and sweep line. Note that sorting by start or by length does not work here. A long interval that starts first can block three short ones, and a short interval can overlap two long disjoint ones. Both are quick counterexamples, which is the next tool.

When greedy fails: find the counterexample

A greedy rule that sounds right is the most common wrong answer in interviews. The fastest defence is to try small adversarial inputs, and the best source of those is a brute force or DP that you compare against.

Coin change with coins {1, 3, 4} and amount 6 is the standard example. Greedy takes 4, then 1, then 1: three coins. The optimum is 3 + 3: two coins. The visualizer runs both: greedy's steps, then the DP table best[x] = 1 + min(best[x − c]) filled left to right. With the canonical coins {1, 5, 10, 25} the two always agree; try {1, 7, 10} with amount 14.

Why did it fail? Taking the 4 is not safe: no optimal solution for 6 contains a 4. The exchange argument breaks too: you cannot swap the 3 + 3 for a 4 without adding a coin. Coin systems where greedy works are called canonical. Real currencies are designed to be canonical, but a problem statement's coins are not, so use the DP from Dynamic programming.

The knapsack shows the same split, and it is the cleanest illustration of why a greedy proof works in one problem and fails in its sibling:

Fractional knapsack: greedy is optimal

You may take any fraction of an item. Sort by value per unit weight and pour. Exchange argument: if an optimal bag holds some weight of a worse-ratio item while a better-ratio item is not fully used, swap an equal weight of the two. Value goes up or stays the same. O(n log n).

0/1 knapsack: greedy fails

Items are all or nothing. The best-ratio item may leave a gap that nothing fits into, and the exchange no longer works because you cannot swap "an equal weight". Use the O(n · W) DP from Knapsack DP.

def fractional_knapsack(items, capacity):      # items: [(weight, value)]
    total = 0.0
    for w, v in sorted(items, key=lambda it: it[1] / it[0], reverse=True):
        if capacity == 0:
            break
        take = min(w, capacity)                # all of it, or what still fits
        total += v * take / w
        capacity -= take
    return total

public static double FractionalKnapsack(int[][] items, int capacity)   // items: [weight, value]
{
    double total = 0;
    foreach (var it in items.OrderByDescending(it => (double)it[1] / it[0]))
    {
        if (capacity == 0) break;
        int take = Math.Min(it[0], capacity);  // all of it, or what still fits
        total += (double)it[1] * take / it[0];
        capacity -= take;
    }
    return total;
}

Test a greedy before you trust it. Write the obvious brute force (all subsets, all orders, or the DP), generate a few hundred random inputs with n ≤ 8, and compare. It takes five minutes, and it catches almost every wrong greedy rule. Every visualizer on this page was checked this way.

Is it greedy? A decision guide

Signals that greedy is likely: the problem asks for a max count or min cost with no interaction between far-apart choices; a natural sort order makes the decision for each item local; the answer only gets worse if you delay a "free" good choice. Signals against: a choice now changes what is possible later in a way you cannot summarise (coin change, 0/1 knapsack, edit distance); or the problem asks for the number of ways.

Reach and frontiers: Jump Game I and II

nums[i] is the longest jump allowed from index i. Jump Game I asks whether the last index is reachable. The trap is to simulate jumps (which jump do you take?) and end up in a backtracking search. The greedy view throws the individual jumps away and tracks one number: the frontier reach, the farthest index reachable so far. Every index up to reach is reachable, because you can always jump shorter. So the reachable set is always a prefix, and one number describes it.

Jump Game II asks for the minimum number of jumps (the last index is guaranteed reachable). That is a shortest path in a graph where i has an edge to every index in i+1 … i+nums[i], so think BFS. BFS levels here are contiguous ranges: level 0 is [0, 0], level 1 is everything reachable from level 0, and so on. So you do not need a queue: scan the current level, remember the farthest landing far, and when the scan reaches the end of the level, that is one jump and the next level ends at far.

def can_jump(nums):
    reach = 0                          # every index <= reach is reachable
    for i, step in enumerate(nums):
        if i > reach:
            return False               # a gap: nothing reaches i
        reach = max(reach, i + step)
    return True


def jump(nums):
    jumps = end = far = 0              # end: last index of the current BFS level
    for i in range(len(nums) - 1):     # never jump *from* the last index
        far = max(far, i + nums[i])
        if i == end:                   # level fully scanned: one more jump
            jumps += 1
            end = far
    return jumps

public static bool CanJump(int[] nums)
{
    int reach = 0;                         // every index <= reach is reachable
    for (int i = 0; i < nums.Length; i++)
    {
        if (i > reach) return false;       // a gap: nothing reaches i
        reach = Math.Max(reach, i + nums[i]);
    }
    return true;
}

public static int Jump(int[] nums)
{
    int jumps = 0, end = 0, far = 0;       // end: last index of the current BFS level
    for (int i = 0; i < nums.Length - 1; i++)
    {
        far = Math.Max(far, i + nums[i]);
        if (i == end)                      // level fully scanned: one more jump
        {
            jumps++;
            end = far;
        }
    }
    return jumps;
}

Both are O(n) time and O(1) space. Why is it safe to jump to the level's end "later"? We never commit to a specific landing index. jumps counts levels, and the BFS level of an index is its true shortest distance. The greedy part is the observation that levels are intervals, so one pointer replaces the queue. The loop stops at n − 2 because reaching index n − 1 must not count a jump out of it.

Pitfall: looping to len(nums) in Jump Game II If the loop includes the last index and it happens to equal end, you count one extra jump. [0] should give 0 and [2, 1] should give 1; both come out one too high with the longer loop.

Prefix balance: Gas Station

n stations on a circle. Station i gives gas[i], and driving to i + 1 costs cost[i]. Return the start station from which you can drive all the way round, or −1 (the answer is unique if it exists). Brute force tries every start: O(n²).

Two observations make it O(n). The visual is the running sum of gas[i] − cost[i]:

  1. Feasibility is global. If the total of gas − cost is negative, no start works: the car burns more than it gets on any full lap. If it is ≥ 0, some start works.
  2. Failure eliminates a whole block. If you start at s and the tank first goes negative after station i, then no station between s and i can be a start either. Each of those was reached from s with a tank ≥ 0, so starting there means arriving at i with less fuel than this failing run. Jump the start straight to i + 1.

The picture also gives a one-line characterisation: the answer is the station right after the minimum of the prefix sum. From there, the running sum only goes up relative to that low point, all the way round the circle. The two-pointer reset and "argmin of the prefix sum + 1" are the same algorithm written two ways.

def can_complete_circuit(gas, cost):
    total = tank = start = 0
    for i in range(len(gas)):
        diff = gas[i] - cost[i]
        total += diff                  # whole-loop balance
        tank += diff                   # fuel since the current start
        if tank < 0:                   # start..i all fail
            start, tank = i + 1, 0
    return start if total >= 0 else -1

public static int CanCompleteCircuit(int[] gas, int[] cost)
{
    int total = 0, tank = 0, start = 0;
    for (int i = 0; i < gas.Length; i++)
    {
        int diff = gas[i] - cost[i];
        total += diff;                     // whole-loop balance
        tank += diff;                      // fuel since the current start
        if (tank < 0)                      // start..i all fail
        {
            start = i + 1;
            tank = 0;
        }
    }
    return total >= 0 ? start : -1;
}

Why is start correct at the end even though we never checked the wrap-around part? From start to n − 1 the tank stays ≥ 0 (we never reset after it). The part from 0 to start − 1 has a combined balance of total − (balance from start to the end), and since total ≥ 0, the fuel collected from start to the end covers that deficit. That is the prefix-minimum argument in words.

Two passes: Candy

Children stand in a line with ratings. Each child gets at least one candy, and a child with a higher rating than a neighbour must get more than that neighbour. Minimise the total.

The difficulty is that each child has two constraints pointing in opposite directions, and a single left-to-right pass cannot see a long decreasing run coming. The greedy fix is to split the constraints: one pass satisfies only the left-neighbour rule with the smallest possible numbers, a second pass satisfies only the right-neighbour rule, and each child takes the max of the two.

def candy(ratings):
    n = len(ratings)
    left = [1] * n
    for i in range(1, n):                      # left-neighbour rule only
        if ratings[i] > ratings[i - 1]:
            left[i] = left[i - 1] + 1
    right = [1] * n
    for i in range(n - 2, -1, -1):             # right-neighbour rule only
        if ratings[i] > ratings[i + 1]:
            right[i] = right[i + 1] + 1
    return sum(max(l, r) for l, r in zip(left, right))

public static int Candy(int[] ratings)
{
    int n = ratings.Length;
    var left = Enumerable.Repeat(1, n).ToArray();
    for (int i = 1; i < n; i++)                // left-neighbour rule only
        if (ratings[i] > ratings[i - 1]) left[i] = left[i - 1] + 1;
    var right = Enumerable.Repeat(1, n).ToArray();
    for (int i = n - 2; i >= 0; i--)           // right-neighbour rule only
        if (ratings[i] > ratings[i + 1]) right[i] = right[i + 1] + 1;
    int total = 0;
    for (int i = 0; i < n; i++) total += Math.Max(left[i], right[i]);
    return total;
}

Why is this minimal? left[i] is the least value any valid assignment can give child i, because the rising run that ends at i forces it. The same holds for right[i]. So every valid assignment gives at least max(left[i], right[i]), and this assignment achieves exactly that and is valid. The two-pass trick, solve each direction's constraint separately, then combine, also appears in Product of Array Except Self and Trapping Rain Water.

Counting greedy: Task Scheduler and Reorganize String

Task Scheduler

CPU tasks are letters; identical tasks need at least n other slots (tasks or idle) between them. Find the shortest schedule. You could simulate with a max-heap: each round of n + 1 slots, run the n + 1 most frequent remaining tasks. But there is a closed form, and the picture explains it.

Let maxc be the highest frequency. Its copies need maxc − 1 full gaps, so draw maxc rows ("frames") of width n + 1, each starting with that task. Every other task fits in column order without breaking the gap, because its copies land in different rows. Empty cells in the full rows are idle slots, and the last row holds only the tasks that tie for maxc.

Try n = 1 in the visualizer: the other tasks no longer fit in the frames, the rows simply grow wider, and nothing is ever idle. That is why the answer is a max:

from collections import Counter

def least_interval(tasks, n):
    freq = Counter(tasks).values()
    maxc = max(freq)
    cnt_max = sum(1 for f in freq if f == maxc)
    return max(len(tasks), (maxc - 1) * (n + 1) + cnt_max)

public static int LeastInterval(char[] tasks, int n)
{
    var freq = new int[26];
    foreach (char t in tasks) freq[t - 'A']++;
    int maxc = freq.Max();
    int cntMax = freq.Count(f => f == maxc);
    return Math.Max(tasks.Length, (maxc - 1) * (n + 1) + cntMax);
}

O(n) time. The formula is a lower bound (the frames are forced by the most frequent task; and you cannot run fewer slots than tasks), and the column-filling picture shows it is achieved. When you can prove a lower bound and match it with a construction, you are done, and that pattern recurs in many greedy proofs.

Reorganize String

Rearrange a string so that no two adjacent characters are equal, or return "". This is Task Scheduler with n = 1, but you must output the arrangement. Same insight: the most frequent character is the only threat. It fits if and only if maxc ≤ ceil(len / 2). Construct it by filling the even indices first, most frequent character first, then the odd indices.

from collections import Counter

def reorganize_string(s):
    cnt = Counter(s)
    n = len(s)
    if max(cnt.values()) > (n + 1) // 2:
        return ""
    res = [""] * n
    i = 0
    for ch, c in sorted(cnt.items(), key=lambda kv: -kv[1]):   # most frequent first
        for _ in range(c):
            res[i] = ch
            i += 2
            if i >= n:
                i = 1                  # evens are full: switch to odds
    return "".join(res)

public static string ReorganizeString(string s)
{
    var cnt = new Dictionary<char, int>();
    foreach (char ch in s) cnt[ch] = cnt.GetValueOrDefault(ch) + 1;
    int n = s.Length;
    if (cnt.Values.Max() > (n + 1) / 2) return "";
    var res = new char[n];
    int i = 0;
    foreach (var (ch, c) in cnt.OrderByDescending(kv => kv.Value).Select(kv => (kv.Key, kv.Value)))
    {
        for (int k = 0; k < c; k++)
        {
            res[i] = ch;
            i += 2;
            if (i >= n) i = 1;             // evens are full: switch to odds
        }
    }
    return new string(res);
}

The heap alternative (always place the most frequent character that differs from the previous one) also works and generalises to "at least k apart" (Rearrange String k Distance Apart), but the slot-filling version is O(n) and has nothing to get wrong.

Cut as early as possible: Partition Labels and arrows

Partition Labels: split a string into as many parts as possible so that each letter appears in at most one part, and return the part sizes. The greedy rule: a part that contains letter c must extend at least to last[c], the last occurrence of c. Scan left to right, stretch end to cover every letter seen, and cut the moment i == end. Cutting there is safe because no cut can be earlier (some letter would be split), and cutting as early as allowed leaves the most room for the remaining parts: greedy stays ahead on the position of each cut.

def partition_labels(s):
    last = {c: i for i, c in enumerate(s)}
    sizes, start, end = [], 0, 0
    for i, c in enumerate(s):
        end = max(end, last[c])        # this part must reach last[c]
        if i == end:                   # nothing inside reaches further
            sizes.append(end - start + 1)
            start = i + 1
    return sizes

public static IList<int> PartitionLabels(string s)
{
    var last = new int[26];
    for (int i = 0; i < s.Length; i++) last[s[i] - 'a'] = i;
    var sizes = new List<int>();
    int start = 0, end = 0;
    for (int i = 0; i < s.Length; i++)
    {
        end = Math.Max(end, last[s[i] - 'a']);   // this part must reach last[c]
        if (i == end)                            // nothing inside reaches further
        {
            sizes.Add(end - start + 1);
            start = i + 1;
        }
    }
    return sizes;
}

This is interval merging in disguise: each letter is the interval [first[c], last[c]], and the parts are the merged groups of overlapping intervals.

Minimum Number of Arrows to Burst Balloons is the mirror image. Balloons are intervals; one vertical arrow bursts every balloon it touches. Sort by end and shoot each arrow at the end of the first balloon not yet burst: that point is the furthest right you can shoot while still hitting it, so it hits as many later balloons as possible (an exchange argument against any arrow placed further left). This is the same earliest-end greedy as interval scheduling, counting the groups instead of the chosen intervals. The full family (merge, insert, meeting rooms, sweep lines) lives in Intervals and sweep line.

def find_min_arrow_shots(points):
    arrows, end = 0, float("-inf")
    for s, e in sorted(points, key=lambda p: p[1]):
        if s > end:                    # not burst by the last arrow
            arrows += 1
            end = e                    # shoot at this balloon's right edge
    return arrows

public static int FindMinArrowShots(int[][] points)
{
    int arrows = 0;
    long end = long.MinValue;
    foreach (var p in points.OrderBy(p => p[1]))
    {
        if (p[0] > end)                // not burst by the last arrow
        {
            arrows++;
            end = p[1];                // shoot at this balloon's right edge
        }
    }
    return arrows;
}

Note s > end here but s >= end in interval scheduling: touching balloons share a point, so one arrow bursts both. The comparison is the problem's definition of "overlap", so read it carefully every time.

Sort by the right key

Many greedy problems are "sort, then make one obvious decision per item". The work is in choosing the key, and the exchange argument is how you find it: take two items in the wrong order and ask what swapping them does.

Assign Cookies and Boats to Save People

Assign Cookies: child i is content with a cookie of size ≥ g[i]; each child gets at most one cookie. Maximise content children. Sort both; give each child, least greedy first, the smallest cookie that satisfies them. Using a bigger cookie than necessary can only take a cookie away from a greedier child later.

Boats to Save People: each boat carries at most two people and at most limit weight. Minimise boats. Sort; the heaviest person must go in some boat, and the best partner for them is the lightest person (if the lightest does not fit, nobody does). Two pointers from both ends; this is the two pointers pattern with a greedy pairing proof.

def find_content_children(g, s):
    g, s = sorted(g), sorted(s)
    child = 0
    for cookie in s:                   # smallest cookies first
        if child < len(g) and cookie >= g[child]:
            child += 1                 # smallest cookie that satisfies this child
    return child


def num_rescue_boats(people, limit):
    people = sorted(people)
    i, j, boats = 0, len(people) - 1, 0
    while i <= j:
        if people[i] + people[j] <= limit:
            i += 1                     # lightest rides with the heaviest
        j -= 1                         # heaviest always leaves
        boats += 1
    return boats

public static int FindContentChildren(int[] g, int[] s)
{
    var gs = g.OrderBy(x => x).ToArray();
    int child = 0;
    foreach (int cookie in s.OrderBy(x => x))  // smallest cookies first
        if (child < gs.Length && cookie >= gs[child])
            child++;                           // smallest cookie that satisfies this child
    return child;
}

public static int NumRescueBoats(int[] people, int limit)
{
    var p = people.OrderBy(x => x).ToArray();
    int i = 0, j = p.Length - 1, boats = 0;
    while (i <= j)
    {
        if (p[i] + p[j] <= limit) i++;         // lightest rides with the heaviest
        j--;                                   // heaviest always leaves
        boats++;
    }
    return boats;
}

Two City Scheduling

2n people fly to city A or city B; person i costs aCost or bCost, and exactly n must go to each city. Minimise the total. Sending everyone to B first costs Σ bCost; then moving person i to A changes the total by aCost − bCost. So pick the n people with the smallest difference aCost − bCost for A. The key is not either cost but their difference: how much you save by choosing A.

def two_city_sched_cost(costs):
    costs = sorted(costs, key=lambda c: c[0] - c[1])   # most "A is cheaper" first
    n = len(costs) // 2
    return sum(c[0] for c in costs[:n]) + sum(c[1] for c in costs[n:])

public static int TwoCitySchedCost(int[][] costs)
{
    var sorted = costs.OrderBy(c => c[0] - c[1]).ToArray();   // most "A is cheaper" first
    int n = sorted.Length / 2, total = 0;
    for (int i = 0; i < sorted.Length; i++)
        total += i < n ? sorted[i][0] : sorted[i][1];
    return total;
}

Greedy plus a heap: the best option among those available

In the problems so far the sort alone decided everything. A harder family has two orders: one decides when an option becomes available (capital, deadline, distance), and another decides which available option is best (profit, duration, fuel). Sort by the first; keep the available options in a heap ordered by the second.

IPO: unlock by capital, choose by profit

You have capital w and may finish at most k projects. Project i needs capital[i] to start and adds profits[i] when done. Maximise the final capital. At any moment the right move is to take the most profitable affordable project: it gives the most capital now, and more capital can only unlock more projects later. Capital never decreases, so the set of affordable projects only grows: a pointer over the projects sorted by capital adds them to a max-heap of profits as they unlock.

import heapq

def find_maximized_capital(k, w, profits, capital):
    projects = sorted(zip(capital, profits))       # unlock order
    heap, i = [], 0                                # max-heap of unlocked profits
    for _ in range(k):
        while i < len(projects) and projects[i][0] <= w:
            heapq.heappush(heap, -projects[i][1])
            i += 1
        if not heap:
            break                                  # nothing affordable, ever
        w -= heapq.heappop(heap)                   # best unlocked profit
    return w

public static int FindMaximizedCapital(int k, int w, int[] profits, int[] capital)
{
    var projects = capital.Zip(profits, (c, p) => (c, p)).OrderBy(x => x.c).ToArray();
    var heap = new PriorityQueue<int, int>();      // max-heap via negated priority
    int i = 0;
    for (int round = 0; round < k; round++)
    {
        while (i < projects.Length && projects[i].c <= w)
        {
            heap.Enqueue(projects[i].p, -projects[i].p);
            i++;
        }
        if (heap.Count == 0) break;                // nothing affordable, ever
        w += heap.Dequeue();                       // best unlocked profit
    }
    return w;
}

O((n + k) log n). The same "sweep one order, heap the other" shape solves Maximum Performance of a Team, Single-Threaded CPU and Minimum Cost to Hire K Workers (worked problem 3 below).

Course Schedule III: take it, and regret the longest

Courses have a duration and a last day; you take one at a time starting on day 1. Maximise the number of courses. Two facts:

  1. For a fixed set of courses, doing them in order of deadline is best (exchange argument: swapping two adjacent courses into deadline order never makes either finish too late). So process courses sorted by deadline.
  2. When the current course does not fit, you must drop one course. The count is the same whichever one you drop, so drop the longest: the one that frees the most time. That might be the course just added.

The invariant is "greedy stays ahead": after each course, we hold the largest possible number of courses among the deadlines seen so far, and among all sets of that size, the one with the least total time.

import heapq

def schedule_course(courses):
    heap, time = [], 0                             # max-heap of kept durations
    for d, last in sorted(courses, key=lambda c: c[1]):
        time += d
        heapq.heappush(heap, -d)                   # take it tentatively
        if time > last:                            # too late: drop the longest
            time += heapq.heappop(heap)            # adds -longest
    return len(heap)

public static int ScheduleCourse(int[][] courses)
{
    var heap = new PriorityQueue<int, int>();      // max-heap of kept durations
    int time = 0;
    foreach (var c in courses.OrderBy(c => c[1]))
    {
        time += c[0];
        heap.Enqueue(c[0], -c[0]);                 // take it tentatively
        if (time > c[1]) time -= heap.Dequeue();   // too late: drop the longest
    }
    return heap.Count;
}

This "take it, and undo the worst choice when a constraint breaks" pattern is worth memorising. It is how greedy handles problems where a choice looks good now but may need to be revised: the heap remembers the choices so the worst one can be retracted in O(log n). Minimum Number of Refueling Stops (worked problem 2) uses the reverse: postpone the choice and make it retroactively, from a heap of the options you passed.

Huffman coding: merge the two lightest

Give each symbol a binary code so that no code is a prefix of another (so a bit stream decodes unambiguously), minimising the total bits Σ weight × code length. Codes are root-to-leaf paths in a binary tree, so the code length is the leaf's depth. Heavy symbols should be shallow and light ones deep.

Huffman's greedy: repeatedly merge the two lightest trees into one whose weight is their sum. The exchange argument: in some optimal tree, the two lightest symbols are siblings at the deepest level (if a heavier symbol were deeper, swapping it with a lighter one would not increase the cost). Merging them reduces the problem to n − 1 symbols, where the merged node stands for both. Every merge adds its weight to the total, because every leaf below it gets one bit longer.

import heapq

def huffman_codes(freq):                           # {symbol: weight}
    heap = [(w, i, sym) for i, (sym, w) in enumerate(freq.items())]
    heapq.heapify(heap)                            # i breaks ties
    nxt = len(heap)
    while len(heap) > 1:
        w1, _, a = heapq.heappop(heap)             # the two lightest trees
        w2, _, b = heapq.heappop(heap)
        heapq.heappush(heap, (w1 + w2, nxt, (a, b)))
        nxt += 1
    codes = {}

    def walk(t, code):
        if isinstance(t, str):
            codes[t] = code or "0"                 # a lone symbol still needs 1 bit
            return
        walk(t[0], code + "0")
        walk(t[1], code + "1")

    walk(heap[0][2], "")
    return codes

public sealed record HNode(int Weight, char Symbol, HNode? Left, HNode? Right);

public static Dictionary<char, string> HuffmanCodes(Dictionary<char, int> freq)
{
    var heap = new PriorityQueue<HNode, (int, int)>();    // (weight, id) breaks ties
    int id = 0;
    foreach (var (sym, w) in freq) heap.Enqueue(new HNode(w, sym, null, null), (w, id++));
    while (heap.Count > 1)
    {
        var a = heap.Dequeue();                           // the two lightest trees
        var b = heap.Dequeue();
        var m = new HNode(a.Weight + b.Weight, '\0', a, b);
        heap.Enqueue(m, (m.Weight, id++));
    }
    var codes = new Dictionary<char, string>();
    void Walk(HNode t, string code)
    {
        if (t.Left is null) { codes[t.Symbol] = code.Length > 0 ? code : "0"; return; }
        Walk(t.Left, code + "0");
        Walk(t.Right!, code + "1");
    }
    Walk(heap.Dequeue(), "");
    return codes;
}

O(n log n) with a heap. The same "always combine the two smallest" greedy solves Minimum Cost to Connect Sticks (cost of joining = sum of lengths; the total cost is exactly Huffman's total), and optimal merge order for sorted files. When the merge cost is not additive like this, or only adjacent piles may be merged (Minimum Cost to Merge Stones), greedy fails and you need interval DP.

Recognize it, and avoid the classic bugs

Recognize greedy when

  • The problem asks for a maximum count or minimum cost, not for the number of ways or a list of all answers.
  • There is a natural order (end time, deadline, ratio, difference, position), and once items are in that order each decision looks local.
  • A "take the best available now" step does not reduce what is possible later. It may even increase it (capital in IPO, reach in Jump Game).
  • The constraints are large (n up to 10⁵ or more), so O(n log n) is expected and a DP over pairs of states would be too slow.
  • You can phrase a lower bound and a construction that meets it (Task Scheduler, Reorganize String).

Pitfall: trusting a rule because it passes the examples "Take the largest coin" passes {1, 5, 10, 25} every time and fails on {1, 3, 4}. "Pick the shortest interval" passes most hand-made examples. Before coding, spend two minutes trying to break the rule on tiny inputs, or compare against a brute force on random inputs. If you cannot state why the choice is safe, assume it is not.

Pitfall: the wrong sort key Interval scheduling sorted by start, Two City sorted by aCost, hiring workers sorted by wage alone: each is a plausible key that fails. Find the key with the exchange argument: write down what changes when two neighbours swap, and sort so that no swap improves the answer.

Pitfall: > versus >= at the boundary Interval scheduling treats [1, 3] and [3, 5] as compatible (s >= end). Balloons that touch at 3 are burst by one arrow, so a new arrow is needed only when s > end. Gas Station resets when the tank goes below zero, not at zero. Write the boundary case down as a test before you write the comparison.

Pitfall: overflow in the doubling greedies In Patching Array miss doubles on every patch; with n near 2³¹ − 1, miss passes int.MaxValue and wraps negative, and the loop never ends. Use long in C# (Python ints are unbounded). The same applies to sums of products in Minimum Cost to Hire K Workers.

Worked problems

1 · Remove Duplicate Letters Medium

Remove duplicate letters so that every letter appears once and the result is the smallest in lexicographic order among all such results. Example: "cbacdcbc" → "acdb".

Insight: build the answer left to right in a stack. When the new letter c is smaller than the top of the stack, and the top letter appears again later, pop it: putting c earlier makes the string smaller, and the popped letter can still be placed later. If the top does not appear again, it must stay. This is the greedy "make the earliest position as small as possible", implemented with a monotonic stack. Letters already in the stack are skipped, since their position is already the best one available.

Solution: monotonic stack with last occurrences, O(n) 
def remove_duplicate_letters(s):
    last = {c: i for i, c in enumerate(s)}
    stack, in_stack = [], set()
    for i, c in enumerate(s):
        if c in in_stack:
            continue
        while stack and c < stack[-1] and last[stack[-1]] > i:
            in_stack.remove(stack.pop())       # it comes back later: place it then
        stack.append(c)
        in_stack.add(c)
    return "".join(stack)

public static string RemoveDuplicateLetters(string s)
{
    var last = new int[26];
    for (int i = 0; i < s.Length; i++) last[s[i] - 'a'] = i;
    var inStack = new bool[26];
    var stack = new System.Text.StringBuilder();
    for (int i = 0; i < s.Length; i++)
    {
        char c = s[i];
        if (inStack[c - 'a']) continue;
        while (stack.Length > 0 && c < stack[^1] && last[stack[^1] - 'a'] > i)
        {
            inStack[stack[^1] - 'a'] = false;  // it comes back later: place it then
            stack.Length--;
        }
        stack.Append(c);
        inStack[c - 'a'] = true;
    }
    return stack.ToString();
}

Each letter is pushed and popped at most once: O(n) time and O(alphabet) space. Remove K Digits is the same stack with a budget of k pops instead of the "appears later" condition.

2 · Minimum Number of Refueling Stops Hard

A car starts with startFuel litres (one litre per mile) and must reach target. Stations at increasing positions offer some fuel each. Return the minimum number of stops, or −1.

Insight: do not decide at a station whether to stop. Drive as far as the fuel allows and remember every station passed in a max-heap. When you run dry, retroactively stop at the best station you passed: the one with the most fuel. Any solution with s stops reaches at most as far as taking the s largest passed stations, so greedy stays ahead on "distance reachable with s stops". It is Jump Game II with a heap: each stop extends the frontier as much as possible.

Solution: max-heap of passed stations, O(n log n) 
import heapq

def min_refuel_stops(target, start_fuel, stations):
    heap, reach, stops, i = [], start_fuel, 0, 0   # reach: farthest position so far
    while reach < target:
        while i < len(stations) and stations[i][0] <= reach:
            heapq.heappush(heap, -stations[i][1])  # passed it: may stop there later
            i += 1
        if not heap:
            return -1                              # stranded
        reach -= heapq.heappop(heap)               # best station passed
        stops += 1
    return stops

public static int MinRefuelStops(int target, int startFuel, int[][] stations)
{
    var heap = new PriorityQueue<int, int>();      // max-heap of passed fuel
    long reach = startFuel;                        // farthest position so far
    int stops = 0, i = 0;
    while (reach < target)
    {
        while (i < stations.Length && stations[i][0] <= reach)
        {
            heap.Enqueue(stations[i][1], -stations[i][1]);   // may stop there later
            i++;
        }
        if (heap.Count == 0) return -1;            // stranded
        reach += heap.Dequeue();                   // best station passed
        stops++;
    }
    return stops;
}

O(n log n) time, O(n) space. There is also an O(n²) DP (dp[s] = farthest reach with s stops), which is a good way to check the greedy: the greedy reproduces the DP's values.

3 · Minimum Cost to Hire K Workers Hard

Worker i has a quality and a minimum wage. Hire exactly k workers; pay must be proportional to quality within the group, and nobody may get less than their minimum. Minimise the total pay.

Insight: within a group, one worker is the captain: the one with the highest ratio wage / quality. Everyone is paid captain_ratio × quality, so the cost is ratio × (sum of qualities). Sort workers by ratio. When worker j is the captain, the others must have a ratio ≤ theirs (earlier in the order), and to minimise the cost we want the k − 1 smallest qualities among them. A max-heap of qualities keeps the k smallest seen so far, removing the largest when it grows too big. Two orders again: ratio decides who is eligible, quality decides who is best.

Solution: sort by ratio, max-heap of qualities, O(n log n) 
import heapq

def mincost_to_hire_workers(quality, wage, k):
    workers = sorted((w / q, q) for q, w in zip(quality, wage))
    heap, qsum, best = [], 0, float("inf")         # max-heap of qualities
    for ratio, q in workers:                       # this worker is the captain
        heapq.heappush(heap, -q)
        qsum += q
        if len(heap) > k:
            qsum += heapq.heappop(heap)            # drop the largest quality
        if len(heap) == k:
            best = min(best, ratio * qsum)
    return best

public static double MincostToHireWorkers(int[] quality, int[] wage, int k)
{
    var workers = quality.Select((q, i) => (ratio: (double)wage[i] / q, q))
                         .OrderBy(w => w.ratio).ToArray();
    var heap = new PriorityQueue<int, int>();      // max-heap of qualities
    long qsum = 0;
    double best = double.MaxValue;
    foreach (var (ratio, q) in workers)            // this worker is the captain
    {
        heap.Enqueue(q, -q);
        qsum += q;
        if (heap.Count > k) qsum -= heap.Dequeue();   // drop the largest quality
        if (heap.Count == k) best = Math.Min(best, ratio * qsum);
    }
    return best;
}

Sometimes the popped quality is the current worker's own. Then the step computes ratio × qsum for a group whose highest ratio is lower. Paying that group at this higher rate is still legal, just too expensive, so the value is never below the true optimum and cannot win wrongly. O(n log n).

4 · Patching Array Hard

Given a sorted array nums and n, add the fewest numbers ("patches") so that every integer in [1, n] is a sum of some subset of the array.

Insight: keep miss, the smallest total you cannot build yet; everything in [1, miss − 1] is buildable. If the next number x ≤ miss, adding it extends the range to [1, miss + x − 1]. If x > miss, nothing can ever build miss, so you must patch some value ≤ miss. Patching miss itself doubles the range, and any smaller patch reaches less: greedy stays ahead on miss.

Solution: track the first unbuildable total, O(len(nums) + log n) 
def min_patches(nums, n):
    miss, i, patches = 1, 0, 0                     # [1, miss) is buildable
    while miss <= n:
        if i < len(nums) and nums[i] <= miss:
            miss += nums[i]                        # extend with a given number
            i += 1
        else:
            miss += miss                           # patch with miss: doubles reach
            patches += 1
    return patches

public static int MinPatches(int[] nums, int n)
{
    long miss = 1;                                 // long: miss doubles past int range
    int i = 0, patches = 0;
    while (miss <= n)
    {
        if (i < nums.Length && nums[i] <= miss)
            miss += nums[i++];                     // extend with a given number
        else
        {
            miss += miss;                          // patch with miss: doubles reach
            patches++;
        }
    }
    return patches;
}

Each patch at least doubles miss, so there are at most about log₂ n patches. The same "smallest unbuildable sum" idea answers the classic "smallest positive integer that is not a subset sum of this sorted array" in one pass.

5 · Minimum Number of Taps to Open to Water a Garden Hard

A garden spans [0, n]; tap i waters [i − ranges[i], i + ranges[i]]. Return the fewest taps that cover the whole garden, or −1.

Insight: this is Jump Game II after one transformation. For each left end, record the farthest right end any tap reaches from there: reach[left] = max(right). Now "from position i you can extend coverage to reach[i]" is exactly a jump array, and the BFS-level greedy counts taps. Failure is a level whose farthest reach does not move past its own end. Video Stitching is the same problem with clips instead of taps.

Solution: interval cover as Jump Game II, O(n) 
def min_taps(n, ranges):
    reach = [0] * (n + 1)
    for i, r in enumerate(ranges):
        left = max(0, i - r)
        reach[left] = max(reach[left], i + r)      # best right end from this left end
    taps = end = far = 0
    for i in range(n):
        far = max(far, reach[i])
        if i == end:                               # current coverage used up
            if far <= i:
                return -1                          # a gap nobody covers
            taps += 1
            end = far
    return taps

public static int MinTaps(int n, int[] ranges)
{
    var reach = new int[n + 1];
    for (int i = 0; i <= n; i++)
    {
        int left = Math.Max(0, i - ranges[i]);
        reach[left] = Math.Max(reach[left], i + ranges[i]);   // best right end from here
    }
    int taps = 0, end = 0, far = 0;
    for (int i = 0; i < n; i++)
    {
        far = Math.Max(far, reach[i]);
        if (i == end)                              // current coverage used up
        {
            if (far <= i) return -1;               // a gap nobody covers
            taps++;
            end = far;
        }
    }
    return taps;
}

O(n) time and space. Recognising that an interval-cover problem is a jump game is the whole trick; the sort-by-start greedy also works in O(n log n).

Self-check

Interval scheduling: why sort by end time and not by start time or by length?

The earliest-ending interval leaves the most room for everything after it, and "stays ahead" proves it: the k-th greedy pick ends no later than anyone's k-th pick. Sorting by start fails on one long interval that starts first and covers several short ones. Sorting by length fails on a short interval that overlaps two long, mutually disjoint ones.

Greedy coin change works for {1, 5, 10, 25} but not for {1, 3, 4}. How would you check a new coin system?

Compare greedy with the coin-change DP for every amount up to the sum of the two largest coins; if a coin system is non-canonical, a counterexample exists below that bound. For {1, 3, 4} the DP finds 6 = 3 + 3 against greedy's 4 + 1 + 1. In an interview, just use the DP: it is O(amount × coins) and always right.

Gas Station: the tank goes negative at station i when starting from s. Why can you skip every start between s and i?

Every station k in s+1 … i was reached from s with a tank ≥ 0. Starting at k instead means arriving at the same places with that non-negative amount less, so the tank still goes negative by i. All of them fail, and the next candidate is i + 1.

Course Schedule III: when the new course makes you late, why drop the longest course rather than the new one?

You must drop exactly one course either way, so the count is the same. Dropping the longest leaves the smallest total time, which can only help future courses fit. If the new course is the longest, then dropping it is the same rule. The heap makes "find the longest" O(log n).

Jump Game II is a shortest path. Why does it not need a BFS queue?

From index i you can land anywhere in i+1 … i+nums[i], so every BFS level is a contiguous range. A range is described by its two ends, so end (where the current level stops) and far (where the next level will stop) replace the queue. O(n) time, O(1) space.

Huffman: why does the total number of bits equal the sum of all merged weights?

Each merge puts its two subtrees one level deeper, so every symbol under the merged node gains one bit. That adds exactly the merged weight to Σ weight × depth. Summing over all merges counts each symbol once per ancestor, which is its depth.

Minimum Cost to Hire K Workers: why sort by wage / quality?

The group's pay rate is set by its highest ratio (otherwise that worker gets less than their minimum). Sorting by ratio means that when you reach worker j, every earlier worker can join a group with j as captain at j's rate. Then only the sum of qualities matters, so you keep the k smallest qualities in a heap.
