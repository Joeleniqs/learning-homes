Shortest Paths

BFS, 0-1 BFS, Dijkstra, Bellman-Ford, Floyd-Warshall and A* animated, and a chart to pick the right one every time.

Intermediate → Expert~80 min studyBuilds on: Graph Fundamentals: BFS & DFS, Heaps & Priority QueuesUpdated 2026-11-03

One question, six algorithms

"What is the cheapest way from A to B?" is one of the most common questions in all of programming: GPS routes, network packets, game AI, currency exchange, word ladders, puzzle solvers, and a long list of interview problems that never say the word "graph". The question is always the same. The right algorithm depends on what the edge weights look like, and choosing the wrong one gives either wrong answers (Dijkstra with negative edges) or a time-out (Bellman-Ford when BFS would do).

This page assumes Graph Fundamentals (adjacency lists and BFS) and Heaps & Priority Queues (which previewed Dijkstra). BFS is linked, not re-taught; Dijkstra is taken all the way down here. The chart below is the map of the whole page. Every box has its own section, an animated visualizer and a template you can type from memory.

The shortest-path rule. Every algorithm here repeats one move, relaxation: if dist[u] + w < dist[v]: dist[v] = dist[u] + w. They differ only in the order in which edges get relaxed. BFS relaxes in layers (all weights equal). Dijkstra always relaxes from the closest unsettled node (needs weights ≥ 0). 0-1 BFS does the same with a deque. Bellman-Ford relaxes every edge V − 1 times, in any order (negatives OK, finds negative cycles). Floyd-Warshall relaxes through one allowed stop-over node at a time (all pairs). A DAG is relaxed once, in topological order. Pick the cheapest order that is still correct for your weights.

How to read the visualizers on this page: amber is what is happening right now (the node being settled, the edge being relaxed), blue is tentative (found, but could still improve), green is final, red is a relaxation that did not help or a value that is wrong, and purple is the reconstructed answer path. The small number under a node is its current distance; ∞ means "not reached yet".

Relaxation: the one move behind everything

Keep two arrays: dist[v], the cheapest route to v found so far, and parent[v], the node it came from. Start with dist[src] = 0 and every other entry ∞. Relaxing an edge u → v with weight w asks one question: is "best route to u, then this edge" better than the best route to v I know?

Three facts make every algorithm on this page work:

  1. Distances only go down. A relaxation never increases dist[v], and dist[v] is always the length of a real route (or ∞). So dist[v] is an upper bound that tightens over time.
  2. Optimal substructure. If s → … → u → v is a shortest route to v, then its s → … → u part is a shortest route to u. (If there were a cheaper way to u, you would use it and get a cheaper way to v.) So once dist[u] is right, one relaxation of u → v makes dist[v] right along that route.
  3. The answer is stable. When no edge can be relaxed any more, dist[v] ≤ dist[u] + w holds for every edge (the "triangle inequality"), and that is exactly the condition for dist to be the true shortest distances, as long as no negative cycle exists.

So the algorithms only have to answer: in what order do I relax, so that I don't waste work? Relax a node's edges before its distance is final and you may have to do it again. Dijkstra never has to, BFS never has to, Bellman-Ford does up to V − 1 times.

Reconstructing the path

Algorithms compute distances; problems often want the route. Record parent[v] = u whenever a relaxation succeeds. At the end, follow parents back from the target and reverse:

def path_to(parent, t):
    """Nodes from the source to t; call it only when dist[t] < inf."""
    path = []
    while t != -1:
        path.append(t)
        t = parent[t]
    return path[::-1]

public List<int> PathTo(int[] parent, int t)
{
    // Nodes from the source to t; call it only when dist[t] is finite.
    var path = new List<int>();
    for (int x = t; x != -1; x = parent[x]) path.Add(x);
    path.Reverse();
    return path;
}

The parents form a tree rooted at the source (every node has one parent, and following parents always ends at the source), so one run answers "how do I get to every node". If a problem wants all shortest routes, a single parent is not enough: keep the full set of edges with dist[u] + w == dist[v], which forms the shortest-path DAG (used below to count routes).

Dijkstra: settle the closest node, repeat

Dijkstra is BFS for weighted graphs. BFS grows the explored region one layer at a time because every edge costs 1. With weights, the "next layer" is simply the unsettled node with the smallest tentative distance. A min-heap finds it in O(log V), and the picture below proves its distance can never improve again.

Step through Dijkstra

The graph is undirected; type your own edges, or change the source and target. Watch three things: the heap (smallest first, red entries are stale), the distance table (each row turns green exactly once and then never changes), and the final frame, where the parent pointers draw the shortest-path tree and the route to the target.

Things to notice while you step:

  1. Every node is settled once, in order of distance: 0, 3, 4, 1, 6, 5, 2 for the default graph (distances 0, 1, 3, 4, 6, 8, 9). Settling order = sorted distances. That is the invariant.
  2. The same node can be in the heap several times. Node 5 is pushed with 9 (via 4) and later with 8 (via 6). Instead of finding and updating the old entry, this version pushes a new one and skips the old one when it comes out (d > dist[u]). This is lazy deletion, and it is what you write in interviews: Python's heapq and C#'s PriorityQueue have no decrease-key.
  3. You may stop at the target. When the target is popped, its distance is final. Problems with one target can return right there, which often halves the work.

The template

import heapq
from math import inf


def build_adj(n, edges, directed=True):
    adj = [[] for _ in range(n)]
    for u, v, w in edges:
        adj[u].append((v, w))
        if not directed:
            adj[v].append((u, w))
    return adj


def dijkstra(n, adj, src):
    """adj[u] = [(v, w), ...] with every w >= 0. Returns (dist, parent)."""
    dist = [inf] * n
    parent = [-1] * n
    dist[src] = 0
    heap = [(0, src)]
    while heap:
        d, u = heapq.heappop(heap)
        if d > dist[u]:
            continue                        # stale entry: u was settled with less
        for v, w in adj[u]:
            nd = d + w
            if nd < dist[v]:
                dist[v] = nd
                parent[v] = u
                heapq.heappush(heap, (nd, v))
    return dist, parent

public List<(int v, int w)>[] BuildAdj(int n, IEnumerable<(int u, int v, int w)> edges, bool directed = true)
{
    var adj = new List<(int v, int w)>[n];
    for (int i = 0; i < n; i++) adj[i] = new List<(int v, int w)>();
    foreach (var (u, v, w) in edges)
    {
        adj[u].Add((v, w));
        if (!directed) adj[v].Add((u, w));
    }
    return adj;
}

// long.MaxValue means "unreachable".
public (long[] dist, int[] parent) Dijkstra(int n, List<(int v, int w)>[] adj, int src)
{
    var dist = new long[n];
    var parent = new int[n];
    Array.Fill(dist, long.MaxValue);
    Array.Fill(parent, -1);
    var pq = new PriorityQueue<int, long>();
    dist[src] = 0;
    pq.Enqueue(src, 0);
    while (pq.TryDequeue(out int u, out long d))
    {
        if (d > dist[u]) continue;                      // stale entry
        foreach (var (v, w) in adj[u])
        {
            long nd = d + w;
            if (nd < dist[v]) { dist[v] = nd; parent[v] = u; pq.Enqueue(v, nd); }
        }
    }
    return (dist, parent);
}

Cost. Each successful relaxation pushes one entry, so the heap sees at most E pushes and E pops: O((V + E) log V) time (log E = O(log V)), O(V + E) memory. Two variants are worth knowing by name:

  • Dense Dijkstra, O(V²): no heap; each round scan all unsettled nodes for the smallest dist. On a complete graph (E ≈ V²) this beats the heap, exactly like dense Prim on the MST page.
  • Decrease-key with an indexed heap or a Fibonacci heap: O(E + V log V) on paper. In practice the lazy version is as fast or faster, and it is the one to write.

Pitfalls: the three bugs that break Dijkstra in interviews

  1. Marking a node visited when it is pushed instead of when it is popped. That is BFS thinking; a later, cheaper route would be ignored. Fix: a node is final only when it comes out of the heap.
  2. Forgetting the stale check. Without if d > dist[u]: continue the answer is still right, but a node's edges are scanned once per stale entry; on dense graphs that is a time-out. Fix: keep the one-line check.
  3. Pushing (node, dist) instead of (dist, node) in Python. Tuples compare left to right, so the heap is ordered by node id and the algorithm silently becomes wrong. Fix: distance first. In C# the priority is a separate argument, so this cannot happen.

Counting shortest paths

Many problems ask "how many different shortest routes?" (for example LeetCode 1976). Dijkstra settles nodes in order of distance, and every shortest route into v arrives from a node with a strictly smaller distance (weights ≥ 1), which has already been settled. So counting works in the same pass: on a strictly better route, replace the count; on an equally good one, add it.

With zero-weight edges this breaks: a 0-edge between two nodes at the same distance means neither is "earlier", so the count can be read before it is complete. Then compute dist first, and count along the shortest-path DAG in topological order (or in order of dist with ties broken by a topological order of the 0-edges).

Many sources at once

"Distance from each cell to the nearest hospital" is not one Dijkstra per hospital. Push all sources into the heap with distance 0 and run once. It is the same as adding a virtual super-source joined to each real source with a weight-0 edge, which is the idea of multi-source BFS carried over to weights. If you also store which source each node came from, you get a Voronoi partition of the graph for free.

Why negative edges break Dijkstra

The proof in the figure above needs "the rest of a route only adds ≥ 0". One negative edge removes that, and the textbook algorithm (a node is settled forever when popped) returns a wrong answer. Switch the visualizer to the lazy version to see the other side of the story.

The honest summary, because many tutorials get it wrong:

  • Textbook Dijkstra (a done set, never revisit) is wrong with negative edges, as shown.
  • Lazy Dijkstra as in the template above (re-push whenever dist improves, no done set) is still correct with negative edges as long as there is no negative cycle, because a node whose dist improves is simply processed again. But a node can now be processed many times, and there are graphs where this takes exponential time. With a negative cycle it never stops.
  • So with negative edges use Bellman-Ford (or SPFA, its queue-based variant) and get a guaranteed O(V·E). Do not "fix" negatives by adding a constant to every edge: a route with more edges gets a bigger penalty, so the shortest route can change.

0-1 BFS: when every weight is 0 or 1

A surprising number of problems have only two edge costs: "moving along an arrow is free, changing direction costs 1", "walking on empty cells is free, removing an obstacle costs 1", "using an existing road is free, building one costs 1". Dijkstra solves them, but a deque does it in linear time.

The rule: pop from the front; a weight-0 neighbour has the same distance, so it goes to the front; a weight-1 neighbour has distance + 1, so it goes to the back. The deque then holds at most two distinct distances, d and d + 1, in sorted order, which is all Dijkstra's heap ever needed to provide.

This is LeetCode 2290 (Minimum Obstacle Removal to Reach Corner): entering a hatched cell costs 1. Watch the deque: free cells jump to the front and are explored immediately, so the search floods every cell reachable at the current cost before paying for a single obstacle. A cell can be pushed twice (once at d + 1, later at d through the front), which is why the stale check stays.

from collections import deque


def zero_one_bfs(n, adj, src):
    """adj[u] = [(v, w), ...] with every w in {0, 1}."""
    dist = [inf] * n
    dist[src] = 0
    dq = deque([(0, src)])
    while dq:
        d, u = dq.popleft()
        if d > dist[u]:
            continue
        for v, w in adj[u]:
            if d + w < dist[v]:
                dist[v] = d + w
                if w == 0:
                    dq.appendleft((d, v))       # same layer: front
                else:
                    dq.append((d + 1, v))       # next layer: back
    return dist

public long[] ZeroOneBfs(int n, List<(int v, int w)>[] adj, int src)
{
    var dist = new long[n];
    Array.Fill(dist, long.MaxValue);
    dist[src] = 0;
    var dq = new LinkedList<(long d, int u)>();          // .NET has no Deque<T>; this is one
    dq.AddLast((0, src));
    while (dq.Count > 0)
    {
        var (d, u) = dq.First!.Value;
        dq.RemoveFirst();
        if (d > dist[u]) continue;
        foreach (var (v, w) in adj[u])
        {
            if (d + w >= dist[v]) continue;
            dist[v] = d + w;
            if (w == 0) dq.AddFirst((d, v));             // same layer: front
            else dq.AddLast((d + 1, v));                 // next layer: back
        }
    }
    return dist;
}

Cost: O(V + E). The same idea extends to small integer weights 0 … K with K + 1 buckets ("Dial's algorithm"), but in interviews 0/1 is the case that matters.

Bellman-Ford: relax everything, V − 1 times

Bellman-Ford gives up on choosing a clever order. Each round relaxes every edge once, in whatever order the list has. It is slower, O(V·E), but it has no requirements on the weights, and it tells you when the question has no answer.

Step through the rounds

The table on the right is the history: one row per round. Edges are scanned in the order you type them, and the default order is deliberately bad (edges listed "backwards" from the source), so it needs every round. Re-type the same edges in the order 0-1, 1-2, 2-5, 5-4, 4-3, ... and it finishes after round 1 plus the check round.

Negative cycles

Now give it a graph with a cycle 1 → 2 → 4 → 1 of total weight −1 − 3 + 2 = −2. Every lap makes the route cheaper, so "shortest" does not exist for anything on or after that cycle. After V − 1 rounds an edge still relaxes, which can only happen if a negative cycle is reachable.

def bellman_ford(n, edges, src):
    """edges = [(u, v, w)]. dist[v] is -inf when a negative cycle can make it as small as you like."""
    dist = [inf] * n
    dist[src] = 0
    for _ in range(n - 1):
        changed = False
        for u, v, w in edges:
            if dist[u] != inf and dist[u] + w < dist[v]:
                dist[v] = dist[u] + w
                changed = True
        if not changed:
            break                                   # early exit: nothing moves any more
    adj = [[] for _ in range(n)]
    for u, v, _ in edges:
        adj[u].append(v)
    # one extra round: whatever still improves is on or behind a negative cycle
    bad = deque(v for u, v, w in edges if dist[u] != inf and dist[u] + w < dist[v])
    while bad:
        x = bad.popleft()
        if dist[x] == -inf:
            continue
        dist[x] = -inf
        bad.extend(adj[x])
    return dist

// long.MaxValue = unreachable, long.MinValue = minus infinity (behind a negative cycle).
public long[] BellmanFord(int n, List<(int u, int v, int w)> edges, int src)
{
    var dist = new long[n];
    Array.Fill(dist, long.MaxValue);
    dist[src] = 0;
    for (int round = 0; round < n - 1; round++)
    {
        bool changed = false;
        foreach (var (u, v, w) in edges)
            if (dist[u] != long.MaxValue && dist[u] + w < dist[v]) { dist[v] = dist[u] + w; changed = true; }
        if (!changed) break;
    }
    var adj = new List<int>[n];
    for (int i = 0; i < n; i++) adj[i] = new List<int>();
    foreach (var (u, v, _) in edges) adj[u].Add(v);
    var bad = new Queue<int>();
    foreach (var (u, v, w) in edges)
        if (dist[u] != long.MaxValue && dist[u] + w < dist[v]) bad.Enqueue(v);
    while (bad.Count > 0)
    {
        int x = bad.Dequeue();
        if (dist[x] == long.MinValue) continue;
        dist[x] = long.MinValue;
        foreach (int y in adj[x]) bad.Enqueue(y);
    }
    return dist;
}

Three things people get wrong about this code:

  • The dist[u] != inf guard. In Python inf + (−3) is still inf, so it only saves time; in C# long.MaxValue + (−3) is a huge finite number, and without the guard an unreachable node "relaxes" its neighbours.
  • Detecting any negative cycle, not only reachable ones. The code above only sees cycles reachable from src. To ask "does the graph contain a negative cycle anywhere?", start with every dist = 0 (a virtual source with 0-edges to all nodes).
  • Printing the cycle. Keep parent[]. Take any node x that relaxed in round V and walk x = parent[x] V times: you are now guaranteed to be on the cycle. Walk parents again until you return to that node.

SPFA ("Shortest Path Faster Algorithm") is Bellman-Ford with a queue: only nodes whose dist just changed get their edges relaxed. It is often much faster on random graphs but has the same O(V·E) worst case, and adversarial tests exist; prefer plain Bellman-Ford unless you know the data. Johnson's algorithm runs Bellman-Ford once from a virtual source to get potentials h(v), reweights every edge to w + h(u) − h(v) ≥ 0, then runs Dijkstra from every node: all-pairs with negative edges in O(V·E log V).

At most k edges: Cheapest Flights Within K Stops

Bellman-Ford's counting argument has a gift: after round i, dist holds the cheapest route with at most i edges, but only if every round reads the values from the previous round. Relax in place, and a single round can chain several edges together (u gets improved and then immediately used to improve v), so "at most k + 1 flights" silently becomes "any number of flights".

Switch the mode to in place (bug) on the default input: round 1 already chains 0 → 1 → 2 and round 2 then reaches 3 with 400, a three-flight route that violates k = 1. The correct answer, 700, uses two flights. The fix is one line: new = dist[:] and read from dist, write to new. The code is in worked problem 2 below.

Floyd-Warshall: every pair at once

When the problem asks about many pairs on a small graph (V up to a few hundred), run one algorithm that fills an V × V matrix: three nested loops, five lines of code, negative edges allowed.

What the visualizer shows: in phase k, the only values read are row k and column k (blue cross), because every candidate is d[i][k] + d[k][j]. Those cells cannot change during phase k (d[k][k] = 0, so going through k to reach k gains nothing), so updating the matrix in place is safe. That is why Floyd-Warshall needs only one matrix, unlike the k-stops trap above.

def floyd_warshall(n, edges):
    d = [[0 if i == j else inf for j in range(n)] for i in range(n)]
    nxt = [[i if i == j else -1 for j in range(n)] for i in range(n)]
    for u, v, w in edges:
        if w < d[u][v]:                     # keep the cheapest parallel edge
            d[u][v] = w
            nxt[u][v] = v
    for k in range(n):                      # k MUST be the outer loop
        dk = d[k]
        for i in range(n):
            dik = d[i][k]
            if dik == inf:
                continue
            di = d[i]
            for j in range(n):
                if dik + dk[j] < di[j]:
                    di[j] = dik + dk[j]
                    nxt[i][j] = nxt[i][k]   # first step towards j: same as towards k
    return d, nxt                           # d[i][i] < 0 means a negative cycle through i


def fw_path(nxt, i, j):
    if nxt[i][j] == -1:
        return []
    path = [i]
    while i != j:
        i = nxt[i][j]
        path.append(i)
    return path

public (long[,] d, int[,] next) FloydWarshall(int n, List<(int u, int v, int w)> edges)
{
    const long INF = long.MaxValue;
    var d = new long[n, n];
    var next = new int[n, n];
    for (int i = 0; i < n; i++)
        for (int j = 0; j < n; j++) { d[i, j] = i == j ? 0 : INF; next[i, j] = i == j ? i : -1; }
    foreach (var (u, v, w) in edges)
        if (w < d[u, v]) { d[u, v] = w; next[u, v] = v; }
    for (int k = 0; k < n; k++)
        for (int i = 0; i < n; i++)
        {
            if (d[i, k] == INF) continue;
            for (int j = 0; j < n; j++)
                if (d[k, j] != INF && d[i, k] + d[k, j] < d[i, j])
                {
                    d[i, j] = d[i, k] + d[k, j];
                    next[i, j] = next[i, k];
                }
        }
    return (d, next);
}

Cost: O(V³) time, O(V²) memory. V = 400 is 64 million simple steps: fine in C#, a few seconds in plain Python (hoisting d[i] and d[k] into locals as above roughly halves it). The same three loops solve other "all pairs" questions by changing the two operations: reachability (reach[i][j] |= reach[i][k] and reach[k][j], the transitive closure), widest path (max(min(...))), or minimax (min(max(...))).

Shortest paths on a DAG

If the graph has no cycles, there is an order in which every edge goes forward: the topological order. Relax nodes in that order and each node's dist is final before its edges are used, with no heap and any weights, in O(V + E). Flip min to max and you get the longest path, which is NP-hard on general graphs but trivial on a DAG (critical path scheduling, longest increasing chains).

def dag_shortest(n, edges, src):
    adj = [[] for _ in range(n)]
    indeg = [0] * n
    for u, v, w in edges:
        adj[u].append((v, w))
        indeg[v] += 1
    order, q = [], deque(i for i in range(n) if indeg[i] == 0)
    while q:                                    # Kahn's algorithm
        u = q.popleft()
        order.append(u)
        for v, _ in adj[u]:
            indeg[v] -= 1
            if indeg[v] == 0:
                q.append(v)
    dist = [inf] * n
    dist[src] = 0
    for u in order:                             # every edge goes forward in this order
        if dist[u] == inf:
            continue
        for v, w in adj[u]:
            dist[v] = min(dist[v], dist[u] + w)
    return dist

public long[] DagShortest(int n, List<(int u, int v, int w)> edges, int src)
{
    var adj = new List<(int v, int w)>[n];
    var indeg = new int[n];
    for (int i = 0; i < n; i++) adj[i] = new List<(int v, int w)>();
    foreach (var (u, v, w) in edges) { adj[u].Add((v, w)); indeg[v]++; }
    var q = new Queue<int>(Enumerable.Range(0, n).Where(i => indeg[i] == 0));
    var dist = new long[n];
    Array.Fill(dist, long.MaxValue);
    dist[src] = 0;
    while (q.Count > 0)
    {
        int u = q.Dequeue();                    // Kahn order: relax as nodes come out
        foreach (var (v, w) in adj[u])
        {
            if (dist[u] != long.MaxValue) dist[v] = Math.Min(dist[v], dist[u] + w);
            if (--indeg[v] == 0) q.Enqueue(v);
        }
    }
    return dist;
}

State-space search: when the node is not enough

Many hard problems are shortest paths on a graph you have to invent. The vertices are states: everything you need to know to decide what can happen next. Two questions design the graph:

  1. What do I need to remember? Position, plus stops used, walls broken, coupons left, keys collected, time modulo something, the direction you are facing...
  2. What does a move cost, and how do costs combine? Usually a sum, but "the worst step on the route" (max) or "the probability of success" (product) also work with Dijkstra, as long as extending a route can never make it better.

Three cost rules on the same grid

The visualizer runs Dijkstra on a height map with three different definitions of "the cost of a route". Only one line of code changes. Try all three on the same heights: the routes are different, and in every case the first pop of the bottom-right cell is the answer.

  • Effort (LeetCode 1631, Path With Minimum Effort): the cost of a route is its largest single height step. nd = max(d, |h[next] − h[cur]|). This is also a bottleneck problem, solved by Kruskal on the MST page.
  • Swim (LeetCode 778, Swim in Rising Water): you may enter a cell once the water reaches its height, so a route costs its highest cell. nd = max(d, h[next]). Worked problem 4.
  • Sum (LeetCode 64, Minimum Path Sum, but with all four directions): nd = d + h[next]. With moves only right and down, this is plain grid DP; with all four directions it needs Dijkstra.

Why max works: the proof needs "a route's cost never decreases when it gets longer". max(d, x) ≥ d always, so it holds. A rule that fails it, such as "cost = the last step only", breaks Dijkstra exactly like a negative edge. And for "maximise the probability" (LeetCode 1514), multiply by values ≤ 1, use a max-heap, and the same argument works in reverse: a route's probability never increases when it gets longer.

A state with a resource: one discount coupon

A classic pattern (CSES "Flight Discount"): you may halve the price of one flight. State = (city, coupon used: 0 or 1). From (u, 0) you can fly normally to (v, 0) or use the coupon to (v, 1); from (u, 1) only normal flights. Twice the nodes, the same Dijkstra.

def cheapest_with_coupon(n, flights, src, dst):
    """flights = [(u, v, price)], directed. One flight may be bought at price // 2."""
    adj = build_adj(n, flights)
    dist = [[inf, inf] for _ in range(n)]         # dist[city][coupon used]
    dist[src][0] = 0
    heap = [(0, src, 0)]
    while heap:
        d, u, used = heapq.heappop(heap)
        if d > dist[u][used]:
            continue
        if u == dst:
            return d                              # first pop of dst in ANY layer is optimal
        for v, w in adj[u]:
            moves = [(d + w, used)]
            if not used:
                moves.append((d + w // 2, 1))     # spend the coupon on this flight
            for nd, nu in moves:
                if nd < dist[v][nu]:
                    dist[v][nu] = nd
                    heapq.heappush(heap, (nd, v, nu))
    return -1

public long CheapestWithCoupon(int n, List<(int u, int v, int w)> flights, int src, int dst)
{
    var adj = BuildAdj(n, flights);
    var dist = new long[n, 2];
    for (int i = 0; i < n; i++) { dist[i, 0] = long.MaxValue; dist[i, 1] = long.MaxValue; }
    dist[src, 0] = 0;
    var pq = new PriorityQueue<(int u, int used), long>();
    pq.Enqueue((src, 0), 0);
    while (pq.TryDequeue(out var s, out long d))
    {
        if (d > dist[s.u, s.used]) continue;
        if (s.u == dst) return d;
        foreach (var (v, w) in adj[s.u])
        {
            void Push(long nd, int nu) { if (nd < dist[v, nu]) { dist[v, nu] = nd; pq.Enqueue((v, nu), nd); } }
            Push(d + w, s.used);
            if (s.used == 0) Push(d + w / 2, 1);
        }
    }
    return -1;
}

The general recipe: dist is indexed by the whole state, the heap holds whole states, and the goal test asks "is this any state at the target?". The cost is O(S log S) for S = (number of states + transitions), so check S before you start: V × (k + 1) for k stops, R × C × (k + 1) for k walls, V × 2K for K keys.

Two tricks: reverse the graph, merge the sources

  • Distance from every node TO one target. Running Dijkstra from each node is V runs. Instead reverse every edge (u → v becomes v → u) and run once from the target. In an undirected graph the reversed graph is the same graph, so just run from the target.
  • Distance to the nearest of many sources. Push all sources at distance 0 (the super-source picture). Works for BFS, 0-1 BFS and Dijkstra alike.
  • Is edge (u, v, w) on some shortest s → t route? Compute ds from s and dt from t (reversed). The edge is on one exactly when ds[u] + w + dt[v] == ds[t]. A node v is on one when ds[v] + dt[v] == ds[t]. (LeetCode 3123.)
  • Routes that must pass through a meeting point. Two travellers that must merge and continue to one destination: three runs (from s1, from s2, and from the destination on the reversed graph), then try every meeting node. Worked problem 7.

A*: Dijkstra with a sense of direction

Dijkstra expands nodes in rings around the source, even in the opposite direction from the target. If you can estimate the remaining distance, you can expand more promising nodes first.

Each node gets a key f = g + h: g is the real cost from the start (what Dijkstra uses), h is a heuristic estimate of the cost to the target. The rules that keep A* optimal:

  • Admissible: h never overestimates the true remaining cost. Then the first time the target is popped, its g is optimal.
  • Consistent (monotone): h(u) ≤ w(u, v) + h(v) for every edge. Then, like Dijkstra, each node is final when popped, and the stale-skip template works unchanged. On a grid with unit moves, Manhattan distance is consistent; for 8-direction moves use Chebyshev; for free movement in the plane, straight-line distance.
  • Why it works: A* is exactly Dijkstra on the reweighted edges w + h(v) − h(u), which are ≥ 0 precisely when h is consistent. Same trick as Johnson's potentials.

Compare the three frontier orders on the same grid. Dijkstra (order by g) floods everything near S, including the dead end on the left. Greedy best-first (order by h only) is fastest but walks into the trap behind the wall and returns a longer route. A expands about half of what Dijkstra does and still returns the shortest route. With h = 0, A is Dijkstra; with the perfect h, it walks straight to the target.

def astar_grid(grid, start, target):
    """grid = list of strings, '#' = wall, unit moves in 4 directions."""
    R, C = len(grid), len(grid[0])
    tr, tc = target

    def h(r, c):
        return abs(r - tr) + abs(c - tc)              # Manhattan: never overestimates

    g = {start: 0}
    heap = [(h(*start), 0, start)]
    while heap:
        f, gc, (r, c) = heapq.heappop(heap)
        if gc > g[(r, c)]:
            continue
        if (r, c) == target:
            return gc
        for nr, nc in ((r - 1, c), (r + 1, c), (r, c - 1), (r, c + 1)):
            if 0 <= nr < R and 0 <= nc < C and grid[nr][nc] != "#":
                ng = gc + 1
                if ng < g.get((nr, nc), inf):
                    g[(nr, nc)] = ng
                    heapq.heappush(heap, (ng + h(nr, nc), ng, (nr, nc)))
    return -1

public int AStarGrid(string[] grid, (int r, int c) start, (int r, int c) target)
{
    int R = grid.Length, C = grid[0].Length;
    int H(int r, int c) => Math.Abs(r - target.r) + Math.Abs(c - target.c);
    var g = new int[R, C];
    for (int i = 0; i < R; i++) for (int j = 0; j < C; j++) g[i, j] = int.MaxValue;
    g[start.r, start.c] = 0;
    var pq = new PriorityQueue<(int r, int c, int gc), (int f, int h)>();
    pq.Enqueue((start.r, start.c, 0), (H(start.r, start.c), H(start.r, start.c)));
    int[] dr = { -1, 1, 0, 0 }, dc = { 0, 0, -1, 1 };
    while (pq.TryDequeue(out var s, out _))
    {
        if (s.gc > g[s.r, s.c]) continue;
        if ((s.r, s.c) == target) return s.gc;
        for (int k = 0; k < 4; k++)
        {
            int nr = s.r + dr[k], nc = s.c + dc[k];
            if (nr < 0 || nc < 0 || nr >= R || nc >= C || grid[nr][nc] == '#') continue;
            int ng = s.gc + 1;
            if (ng < g[nr, nc]) { g[nr, nc] = ng; pq.Enqueue((nr, nc, ng), (ng + H(nr, nc), H(nr, nc))); }
        }
    }
    return -1;
}

A* shines with one source, one target and a good geometric heuristic: maps, grids, puzzles (sliding tiles with the sum of Manhattan distances of the tiles). For "all distances from the source" it has nothing to offer, and an inadmissible heuristic (for example Manhattan distance on a grid with diagonal moves) can return a wrong answer.

Recognize it when

Recognize a shortest-path problem when

  • The question says minimum cost / time / number of moves to get from a start to a goal, and moves have costs.
  • The "graph" is hidden: grid cells, words that differ by one letter, lock combinations, (position, extra info) states. If you can list "from here I can go there at this price", it is a graph.
  • Moves cost 0 or 1 ("free if you follow the arrow, 1 to change it", "1 to remove an obstacle"): 0-1 BFS.
  • A limit on the number of edges (at most k stops, at most k operations): Bellman-Ford for k + 1 rounds with a copy, or Dijkstra/BFS on (node, used).
  • Weights can be negative, or the question is "can I make infinite profit?" (arbitrage, positive cycles in a game): Bellman-Ford and negative-cycle detection.
  • Many pairs of a small graph, or a threshold count for every node: Floyd-Warshall.
  • The cost of a route is its worst step (max) or its probability (product): Dijkstra with a different combine rule.
  • "How many shortest routes?", "is this edge on some shortest route?": Dijkstra plus counting, or distances from both ends.
Algorithm Weights Time Memory Use it for
BFS all equal O(V + E) O(V) unweighted graphs, grids, word ladders
0-1 BFS 0 or 1 O(V + E) O(V) "free or pay 1" moves
Dijkstra (binary heap, lazy) ≥ 0 O((V + E) log V) O(V + E) the default for one source
Dijkstra (dense, no heap) ≥ 0 O(V²) O(V) complete graphs, E ≈ V²
DAG relaxation any O(V + E) O(V + E) acyclic graphs, longest paths
Bellman-Ford any O(V·E) O(V) negative edges, negative cycles, at most k edges
SPFA any O(V·E) worst, often fast O(V) random graphs with negatives (risky on adversarial tests)
Floyd-Warshall any O(V³) O(V²) all pairs, V ≤ ~400, transitive closure
Johnson any, no negative cycle O(V·E log V) O(V + E) all pairs on sparse graphs with negatives
A* (consistent h) ≥ 0 O((V + E) log V) worst, far less in practice O(V) one target with a good geometric estimate
State-space Dijkstra ≥ 0 O(S log S), S = states + transitions O(S) resources: stops, keys, walls, coupons

Pitfalls: the actual bug and its fix

  1. Dijkstra on negative edges. The textbook version returns wrong answers; the lazy version can blow up exponentially. Fix: Bellman-Ford (or Johnson for all pairs).
  2. A visited set marked on push. Later, cheaper routes are ignored. Fix: final on pop; on push only update dist.
  3. Heap entries in the wrong order. (node, dist) sorts by node. Fix: (dist, node) in Python; priority = dist in C#.
  4. K stops relaxed in place. One round chains several flights and the stop limit is ignored. Fix: read from last round's copy, write into a new array.
  5. Dijkstra on (node) when the problem has a resource. "Visited per node" throws away a route that is more expensive but has stops (or fuel, or walls) left, and that route may be the only one that works. Fix: put the resource in the state, dist[node][used].
  6. Overflow at infinity. int.MaxValue + w wraps to a negative number in C# and "improves" everything. Fix: skip unreachable nodes before adding, or use long with an explicit != INF guard.
  7. Answers that need a modulus, compared after the modulus. Distances must be compared exactly; only the counts are taken mod 10⁹ + 7. Fix: long distances, modded counts.
  8. Counting shortest paths with 0-weight edges. A node's count can be read before all its equal-distance predecessors were added. Fix: compute dist first, then count on the shortest-path DAG in topological order.
  9. Floyd-Warshall with k as an inner loop. It looks the same and gives wrong answers. Fix: for k outermost, always.
  10. Adding a constant to make weights non-negative. Routes with more edges get penalised more, so the best route changes. Fix: Johnson's potentials, or Bellman-Ford.
  11. Forgetting unreachable targets. max(dist) is ∞, dist[t] is ∞. Fix: convert to −1 (or whatever the problem says) at the end.
  12. Stopping at the first push of the target. Only the first pop is final (BFS is the exception, because every edge costs the same). Fix: if u == target: return d right after the stale check.

Worked problems

1. Network Delay Time Medium

A signal is sent from node k in a network of n nodes (labelled 1 … n). times[i] = [u, v, w] means the signal takes w time to travel from u to v (directed). Return the time until all nodes have received it, or −1 if some never do.

Key insight. Every node receives the signal at its shortest-path distance from k, so the answer is the largest of all shortest distances. Weights are non-negative: one Dijkstra, then a max. Size the arrays n + 1 to use the labels directly (node 0 is unused, and is skipped in the max).

Solution: Dijkstra, then the farthest node 
def network_delay_time(times, n, k):
    adj = build_adj(n + 1, times)
    dist, _ = dijkstra(n + 1, adj, k)
    worst = max(dist[1:])
    return -1 if worst == inf else worst

public int NetworkDelayTime(int[][] times, int n, int k)
{
    var adj = BuildAdj(n + 1, times.Select(t => (t[0], t[1], t[2])));
    var (dist, _) = Dijkstra(n + 1, adj, k);
    long worst = dist.Skip(1).Max();
    return worst == long.MaxValue ? -1 : (int)worst;
}

Complexity: O((n + E) log n) time, O(n + E) memory.

2. Cheapest Flights Within K Stops Medium

There are n cities and flights[i] = [from, to, price]. Return the cheapest price from src to dst with at most k stops (so at most k + 1 flights), or −1.

Key insight. "At most k + 1 edges" is exactly what k + 1 rounds of Bellman-Ford compute, if every round reads the previous round's values (see the visualizer above). The trap with Dijkstra: keeping one dist per city discards a pricier route that used fewer stops, which may be the only one that still fits under the limit. If you prefer Dijkstra, use the state (city, flights used).

Solution: k + 1 Bellman-Ford rounds with a copy 
def find_cheapest_price(n, flights, src, dst, k):
    dist = [inf] * n
    dist[src] = 0
    for _ in range(k + 1):                  # k stops = at most k + 1 flights
        new = dist[:]                       # read last round, write this round
        for u, v, w in flights:
            if dist[u] + w < new[v]:
                new[v] = dist[u] + w
        dist = new
    return -1 if dist[dst] == inf else dist[dst]

public int FindCheapestPrice(int n, int[][] flights, int src, int dst, int k)
{
    var dist = new int[n];
    Array.Fill(dist, int.MaxValue);
    dist[src] = 0;
    for (int round = 0; round <= k; round++)
    {
        var next = (int[])dist.Clone();     // read last round, write this round
        foreach (var f in flights)
            if (dist[f[0]] != int.MaxValue && dist[f[0]] + f[2] < next[f[1]])
                next[f[1]] = dist[f[0]] + f[2];
        dist = next;
    }
    return dist[dst] == int.MaxValue ? -1 : dist[dst];
}

Complexity: O(k · E) time, O(n) memory.

3. Minimum Cost to Make at Least One Valid Path in a Grid Hard

Each cell of an R × C grid holds a sign: 1 = go right, 2 = left, 3 = down, 4 = up. Starting at the top-left, you follow the signs. Changing a cell's sign costs 1 (once per cell). Return the minimum cost so that following the signs reaches the bottom-right cell.

Key insight. Moving from a cell in the direction its sign points costs 0; moving in any of the other three directions means changing that sign, cost 1. That is a graph with weights 0 and 1: 0-1 BFS. A cell never needs to be changed twice, because a shortest route never visits a cell twice.

Solution: 0-1 BFS over cells 
def min_cost_valid_path(grid):
    R, C = len(grid), len(grid[0])
    dirs = [(0, 1), (0, -1), (1, 0), (-1, 0)]          # signs 1, 2, 3, 4
    dist = [[inf] * C for _ in range(R)]
    dist[0][0] = 0
    dq = deque([(0, 0, 0)])
    while dq:
        d, r, c = dq.popleft()
        if d > dist[r][c]:
            continue
        if (r, c) == (R - 1, C - 1):
            return d
        for i, (dr, dc) in enumerate(dirs):
            nr, nc = r + dr, c + dc
            if 0 <= nr < R and 0 <= nc < C:
                w = 0 if grid[r][c] == i + 1 else 1    # follow the sign, or pay to change it
                if d + w < dist[nr][nc]:
                    dist[nr][nc] = d + w
                    if w == 0:
                        dq.appendleft((d, nr, nc))
                    else:
                        dq.append((d + 1, nr, nc))
    return dist[R - 1][C - 1]

public int MinCostValidPath(int[][] grid)
{
    int R = grid.Length, C = grid[0].Length;
    int[] dr = { 0, 0, 1, -1 }, dc = { 1, -1, 0, 0 };   // signs 1, 2, 3, 4
    var dist = new int[R, C];
    for (int i = 0; i < R; i++) for (int j = 0; j < C; j++) dist[i, j] = int.MaxValue;
    dist[0, 0] = 0;
    var dq = new LinkedList<(int d, int r, int c)>();
    dq.AddLast((0, 0, 0));
    while (dq.Count > 0)
    {
        var (d, r, c) = dq.First!.Value;
        dq.RemoveFirst();
        if (d > dist[r, c]) continue;
        if (r == R - 1 && c == C - 1) return d;
        for (int i = 0; i < 4; i++)
        {
            int nr = r + dr[i], nc = c + dc[i];
            if (nr < 0 || nc < 0 || nr >= R || nc >= C) continue;
            int w = grid[r][c] == i + 1 ? 0 : 1;
            if (d + w >= dist[nr, nc]) continue;
            dist[nr, nc] = d + w;
            if (w == 0) dq.AddFirst((d, nr, nc)); else dq.AddLast((d + 1, nr, nc));
        }
    }
    return dist[R - 1, C - 1];
}

Complexity: O(R · C) time and memory. Dijkstra would also pass, with an extra log factor.

4. Swim in Rising Water Hard

An n × n grid holds distinct heights. At time t the water level is t everywhere, and you can swim between 4-adjacent cells when both are at height ≤ t (swimming itself takes no time). Return the earliest time you can get from the top-left to the bottom-right cell.

Key insight. A route is usable at time t exactly when its highest cell is ≤ t. So the cost of a route is the max height on it, and we want the route that minimises that max. Dijkstra with max instead of + (the start already costs its own height). Extending a route can only keep or raise its max, so the first pop of the target is optimal. Try the visualizer with the swim rule:

Solution: Dijkstra on the maximum height 
def swim_in_water(grid):
    n = len(grid)
    best = [[inf] * n for _ in range(n)]
    best[0][0] = grid[0][0]
    heap = [(grid[0][0], 0, 0)]
    while heap:
        t, r, c = heapq.heappop(heap)
        if t > best[r][c]:
            continue
        if (r, c) == (n - 1, n - 1):
            return t
        for nr, nc in ((r - 1, c), (r + 1, c), (r, c - 1), (r, c + 1)):
            if 0 <= nr < n and 0 <= nc < n:
                nt = max(t, grid[nr][nc])           # wait until the water covers the next cell
                if nt < best[nr][nc]:
                    best[nr][nc] = nt
                    heapq.heappush(heap, (nt, nr, nc))
    return -1

public int SwimInWater(int[][] grid)
{
    int n = grid.Length;
    var best = new int[n, n];
    for (int i = 0; i < n; i++) for (int j = 0; j < n; j++) best[i, j] = int.MaxValue;
    best[0, 0] = grid[0][0];
    var pq = new PriorityQueue<(int r, int c), int>();
    pq.Enqueue((0, 0), grid[0][0]);
    int[] dr = { -1, 1, 0, 0 }, dc = { 0, 0, -1, 1 };
    while (pq.TryDequeue(out var cell, out int t))
    {
        if (t > best[cell.r, cell.c]) continue;
        if (cell.r == n - 1 && cell.c == n - 1) return t;
        for (int k = 0; k < 4; k++)
        {
            int nr = cell.r + dr[k], nc = cell.c + dc[k];
            if (nr < 0 || nc < 0 || nr >= n || nc >= n) continue;
            int nt = Math.Max(t, grid[nr][nc]);
            if (nt < best[nr, nc]) { best[nr, nc] = nt; pq.Enqueue((nr, nc), nt); }
        }
    }
    return -1;
}

Complexity: O(n² log n) time, O(n²) memory. Two other correct approaches show how the topics connect: binary search on t with a BFS check, or adding cells in order of height to a union-find until the corners join (Kruskal-style, as for minimax paths on the MST page).

5. Find the City With the Smallest Number of Neighbors at a Threshold Distance Medium

There are n cities (0 … n − 1) and undirected weighted edges. For each city count how many other cities are within distanceThreshold. Return the city with the smallest count; if several tie, the one with the greatest number.

Key insight. The question needs the distance between every pair (n ≤ 100), which is Floyd-Warshall's home ground: one O(n³) run, then one count per row. Each undirected edge goes in both directions. Scanning cities in increasing order and replacing on ≤ gives the tie-break for free.

Solution: Floyd-Warshall, then count per row 
def find_the_city(n, edges, distance_threshold):
    both = [(u, v, w) for u, v, w in edges] + [(v, u, w) for u, v, w in edges]
    d, _ = floyd_warshall(n, both)
    best, answer = inf, -1
    for i in range(n):
        cnt = sum(1 for j in range(n) if j != i and d[i][j] <= distance_threshold)
        if cnt <= best:                         # "<=": ties go to the larger index
            best, answer = cnt, i
    return answer

public int FindTheCity(int n, int[][] edges, int distanceThreshold)
{
    var both = new List<(int u, int v, int w)>();
    foreach (var e in edges) { both.Add((e[0], e[1], e[2])); both.Add((e[1], e[0], e[2])); }
    var (d, _) = FloydWarshall(n, both);
    int best = int.MaxValue, answer = -1;
    for (int i = 0; i < n; i++)
    {
        int cnt = 0;
        for (int j = 0; j < n; j++) if (j != i && d[i, j] <= distanceThreshold) cnt++;
        if (cnt <= best) { best = cnt; answer = i; }   // ties go to the larger index
    }
    return answer;
}

Complexity: O(n³) time, O(n²) memory. Running Dijkstra from every city, O(n · E log n), is the alternative for sparse graphs with many more cities.

6. Number of Ways to Arrive at Destination Medium

n intersections, undirected roads[i] = [u, v, time] with time ≥ 1. Return how many different routes from 0 to n − 1 take the shortest possible time, modulo 10⁹ + 7.

Key insight. Count while running Dijkstra (the "ways" visualizer above). Since every time is ≥ 1, all shortest routes into v come from nodes with a strictly smaller distance, which are popped, and therefore complete, before v. Strictly better route: copy the count. Equal route: add it. Distances can reach about 2 · 10¹⁴, so they must be long and compared without the modulus.

Solution: Dijkstra with a ways[] array 
def count_paths(n, roads):
    MOD = 10**9 + 7
    adj = build_adj(n, roads, directed=False)
    dist = [inf] * n
    ways = [0] * n
    dist[0], ways[0] = 0, 1
    heap = [(0, 0)]
    while heap:
        d, u = heapq.heappop(heap)
        if d > dist[u]:
            continue
        for v, w in adj[u]:
            nd = d + w
            if nd < dist[v]:                        # strictly shorter: start over
                dist[v] = nd
                ways[v] = ways[u]
                heapq.heappush(heap, (nd, v))
            elif nd == dist[v]:                     # another shortest route
                ways[v] = (ways[v] + ways[u]) % MOD
    return ways[n - 1]

public int CountPaths(int n, int[][] roads)
{
    const long MOD = 1_000_000_007;
    var adj = BuildAdj(n, roads.Select(r => (r[0], r[1], r[2])), directed: false);
    var dist = new long[n];
    var ways = new long[n];
    Array.Fill(dist, long.MaxValue);
    dist[0] = 0; ways[0] = 1;
    var pq = new PriorityQueue<int, long>();
    pq.Enqueue(0, 0);
    while (pq.TryDequeue(out int u, out long d))
    {
        if (d > dist[u]) continue;
        foreach (var (v, w) in adj[u])
        {
            long nd = d + w;
            if (nd < dist[v]) { dist[v] = nd; ways[v] = ways[u]; pq.Enqueue(v, nd); }
            else if (nd == dist[v]) ways[v] = (ways[v] + ways[u]) % MOD;
        }
    }
    return (int)ways[n - 1];
}

Complexity: O((n + E) log n) time, O(n + E) memory.

7. Minimum Weighted Subgraph With the Required Paths Hard

A directed weighted graph with n nodes, and three nodes src1, src2 and dest. Choose a set of edges such that both src1 and src2 can reach dest using only chosen edges. Return the minimum total weight of the chosen edges, or −1.

Key insight. In an optimal choice the two routes run separately, meet at some node m, and share the rest of the way to dest (sharing can only save weight). So the answer is the minimum over all m of d(src1, m) + d(src2, m) + d(m, dest). The first two terms are Dijkstra from each source. The third is "distance to dest from every node": one Dijkstra from dest on the reversed graph. Three runs, then one loop.

Solution: three Dijkstras and a meeting point 
def minimum_weight(n, edges, src1, src2, dest):
    fwd = build_adj(n, edges)
    rev = build_adj(n, [(v, u, w) for u, v, w in edges])
    a, _ = dijkstra(n, fwd, src1)
    b, _ = dijkstra(n, fwd, src2)
    c, _ = dijkstra(n, rev, dest)                   # c[m] = distance from m TO dest
    best = min(a[m] + b[m] + c[m] for m in range(n))
    return -1 if best == inf else best

public long MinimumWeight(int n, int[][] edges, int src1, int src2, int dest)
{
    var fwd = BuildAdj(n, edges.Select(e => (e[0], e[1], e[2])));
    var rev = BuildAdj(n, edges.Select(e => (e[1], e[0], e[2])));
    var a = Dijkstra(n, fwd, src1).dist;
    var b = Dijkstra(n, fwd, src2).dist;
    var c = Dijkstra(n, rev, dest).dist;           // c[m] = distance from m TO dest
    long best = long.MaxValue;
    for (int m = 0; m < n; m++)
        if (a[m] != long.MaxValue && b[m] != long.MaxValue && c[m] != long.MaxValue)
            best = Math.Min(best, a[m] + b[m] + c[m]);
    return best == long.MaxValue ? -1 : best;
}

Complexity: O((n + E) log n) time, O(n + E) memory. The guard against long.MaxValue matters in C#: adding two "infinities" overflows to a negative number that would win the minimum.

8. Currency Arbitrage Expert

rates[i][j] is how many units of currency j you get for one unit of currency i (0 when there is no market). Find a sequence of trades that starts and ends with the same currency and ends with more money than it started with, and return the currencies in trading order; return an empty list if no such cycle exists.

Key insight. A cycle is profitable when the product of its rates is > 1. Logarithms turn products into sums: product > 1 ⇔ Σ log(rate) > 0 ⇔ Σ −log(rate) < 0. So give each market the weight −log(rate), and a profitable cycle is a negative cycle. Bellman-Ford finds one: start every currency at distance 0 (a virtual source), run n rounds, and remember the last node that relaxed in round n. That node is on or behind a negative cycle, so step back along parent n times to land on it, then walk the parents once around to read the cycle.

Solution: −log weights + Bellman-Ford cycle extraction 
import math


def find_arbitrage(rates):
    n = len(rates)
    edges = [(i, j, -math.log(rates[i][j]))
             for i in range(n) for j in range(n) if i != j and rates[i][j] > 0]
    dist = [0.0] * n                     # virtual source: every currency starts at 0
    parent = [-1] * n
    x = -1
    for _ in range(n):                   # the n-th round only relaxes on a negative cycle
        x = -1
        for u, v, w in edges:
            if dist[u] + w < dist[v] - 1e-12:      # tolerance for floating-point noise
                dist[v] = dist[u] + w
                parent[v] = u
                x = v
    if x == -1:
        return []
    for _ in range(n):                   # step back n times: now x is ON the cycle
        x = parent[x]
    cycle, y = [x], parent[x]
    while y != x:
        cycle.append(y)
        y = parent[y]
    return cycle[::-1]                   # parents point backwards; reverse for trading order

public List<int> FindArbitrage(double[][] rates)
{
    int n = rates.Length;
    var edges = new List<(int u, int v, double w)>();
    for (int i = 0; i < n; i++)
        for (int j = 0; j < n; j++)
            if (i != j && rates[i][j] > 0) edges.Add((i, j, -Math.Log(rates[i][j])));
    var dist = new double[n];                       // virtual source: all start at 0
    var parent = new int[n];
    Array.Fill(parent, -1);
    int x = -1;
    for (int round = 0; round < n; round++)
    {
        x = -1;
        foreach (var (u, v, w) in edges)
            if (dist[u] + w < dist[v] - 1e-12) { dist[v] = dist[u] + w; parent[v] = u; x = v; }
    }
    if (x == -1) return new List<int>();
    for (int i = 0; i < n; i++) x = parent[x];      // now x is on the cycle
    var cycle = new List<int> { x };
    for (int y = parent[x]; y != x; y = parent[y]) cycle.Add(y);
    cycle.Reverse();
    return cycle;
}

Complexity: O(n · E) = O(n³) time for a full rate table, O(n²) memory. In real markets fees and rounding matter; the tolerance stops floating-point noise from reporting a "profit" of 10⁻¹⁶. The same reduction (−log turns "maximise a product" into "minimise a sum") also solves Path with Maximum Probability with plain Dijkstra, because −log p ≥ 0 when p ≤ 1.

Self-check

Why does plain BFS give shortest paths on an unweighted graph but not on a weighted one?

BFS settles nodes in order of number of edges. When every edge costs the same, fewer edges means cheaper, so that order is the order of distance and the first visit is optimal. With weights, a route of three cheap edges can beat one expensive edge, but BFS has already settled the far node through the expensive edge. Dijkstra fixes this by settling in order of total weight instead of edge count.

In lazy Dijkstra the same node can sit in the heap several times. Why is that fine, and how big can the heap get?

Every push corresponds to a successful relaxation, and there are at most E of those (each edge relaxes at most once, when its tail is settled). So the heap holds at most E + 1 entries, and log E ≤ 2 log V: the complexity is unchanged. The out-of-date entries are recognised on the way out (d > dist[u]) and skipped in O(1) each.

You add 10 to every edge weight to get rid of negative edges, then run Dijkstra. What goes wrong?

A route with k edges gets 10k added, so routes are no longer compared fairly: one with fewer edges gains an advantage. Example: s → t directly with weight 3, or s → a → t with weights 2 and −1 (total 1). After adding 10, the direct route costs 13 and the other 21, so the answer flips. The correct reweighting is Johnson's: w + h(u) − h(v) with potentials h from one Bellman-Ford run, which adds the same h(s) − h(t) to every s → t route.

Why must k be the outermost loop in Floyd-Warshall?

The DP claim is "after phase k, d[i][j] is the best route whose stop-overs are all in {0..k}". Phase k builds on the claim for k − 1, and it needs all of row k and column k to be finished for {0..k−1} before it starts. With k inside, d[i][j] is decided once, from values that are not finished yet, and it is never revisited. It works on some inputs, which is what makes the bug dangerous.

Can Dijkstra stop as soon as it pushes the target into the heap?

No: a push is a tentative distance, and a cheaper route may still be found (in the default Dijkstra visualizer, node 2 is pushed with 10 and finally settled at 9). It can stop when the target is popped (after the stale check), because at that moment its distance is final. BFS is the exception: with equal weights the first time you see a node is already optimal.

How do you find the longest simple path between two nodes?

In general you can't efficiently: longest simple path is NP-hard (it contains Hamiltonian path). Negating the weights and running Bellman-Ford fails exactly when there is a cycle, because a positive cycle becomes a negative one. On a DAG it is easy: relax in topological order with max instead of min, O(V + E). And with a bitmask over a small number of nodes (≤ 20), a DP over (mask, last node) works in O(2ⁿ · n²).

A* returned a route that is longer than the true shortest one. What is the most likely cause?

The heuristic overestimates somewhere (it is not admissible). Typical case: Manhattan distance on a grid that also allows diagonal moves, where a diagonal step covers Manhattan distance 2 for cost 1. Use a lower bound for the move set (Chebyshev for 8 directions, straight-line distance for free movement), or scale the heuristic down.

A problem allows you to break at most k walls. Why does Dijkstra (or BFS) with one dist per cell fail, and how big is the fixed version?

Two routes can reach the same cell, one shorter with no walls left and one longer with walls to spare. If dist is kept per cell, the longer one is discarded, but it may be the only one that can get through a later wall. The future depends on (cell, walls left), so that is the state: dist[r][c][k] with R · C · (k + 1) states and four moves each. (Equivalently, keep per cell the most walls left seen so far and only re-visit with more.)
