DYNAMIC PROGRAMMING

The DP Framework

Recursion → memoization → tabulation → space optimisation, visualised on one problem; how to design state and transitions.

Beginner → Advanced~70 min studyBuilds on: Recursion & the Call StackUpdated 2026-11-03

What dynamic programming is (and is not)

Dynamic programming (DP) has a reputation for being clever. It is mostly bookkeeping. It sits on top of Recursion: you write the honest recursive solution first, notice that it solves the same subproblem again and again, and then arrange to solve each subproblem once.

DP = recursion + overlapping subproblems + optimal substructure. Name every subproblem by a small state, express each state's answer through smaller states, and solve every distinct state exactly once, in an order where everything it reads is already solved.

Each of the three ingredients does a different job:

1. A recursive structure

The answer for a big input is built from answers for smaller inputs of the same kind. "Cheapest way to reach step 7" uses "cheapest way to reach step 6" and "step 5". Without this there is nothing to reuse.

2. Overlapping subproblems

Different branches of the recursion ask the same question. That is the waste DP removes. If every subproblem is asked only once (merge sort, binary search), memoising saves nothing: that is plain divide and conquer.

3. Optimal substructure

An optimal answer is made of optimal answers to its subproblems. Then "keep only the best value per state" loses nothing. It fails for things like longest simple path: the best sub-path may reuse a vertex the rest of the path needs.

Here is the waste in one picture. f(i) is the recursive function of the running example below, and it calls f(i-1) and f(i-2) exactly like Fibonacci does. Every red box repeats work that was already done in a green box to its left.

Now the cure. Store each answer the first time it is computed (a memo). The second time f(3) is asked, return the stored value immediately. The tree collapses into the picture below. Each question becomes a node, each "reads" becomes an arrow, and there are only 6 nodes and 8 arrows.

Insight Exponential recursion is usually not exponential work. It is a small number of distinct questions asked an exponential number of times. Count the distinct questions (the states). If that count is polynomial, DP makes the algorithm polynomial.

The running example: Min Cost Climbing Stairs

The rest of this page follows one problem through every stage. It is LeetCode 746:

cost[i] is the price of stepping off stair i. From stair i you climb to i + 1 or i + 2. You may start on stair 0 or stair 1 for free. Return the minimum cost to reach the top, which is one past the last stair (index n).

Greedy fails here (always step onto the cheaper next stair). With cost = [1, 100, 1, 1, 1, 100, 1, 1, 100, 1] it gets trapped next to the 100s. We need to compare whole routes, and there are exponentially many of them. That is exactly the situation DP was made for.

The five-step recipe

Every DP solution, from Climbing Stairs to bitmask DP, answers the same five questions. Write them down in words before writing code. Most DP bugs are a step that was skipped or answered vaguely.

1 · STATEWhat does one cell mean?

"dp[i] = the minimum cost to stand on stair i." One full sentence with units. The state must hold everything the future needs to know.

2 · TRANSITIONHow does a cell follow from smaller ones?

Look at the last decision: you arrived from i−1 or from i−2. dp[i] = min(dp[i−1] + cost[i−1], dp[i−2] + cost[i−2]).

3 · BASE CASESWhich cells need no recurrence?

dp[0] = dp[1] = 0 (free start). Base cases are exactly the cells where the transition would read outside the table.

4 · ORDERIn what order are cells filled?

Every cell after the cells it reads: i = 2, 3, …, n. Top-down recursion finds this order for you.

5 · ANSWERWhere is the answer?

dp[n]. It is not always the last cell: sometimes it is max(dp), or dp[0] when you fill backwards.

The last decision idea in step 2 deserves its own picture. Do not try to think about the whole route at once. Ask only: what was the very last move into this state, and what did it cost? Every option gives a smaller state plus a local cost, and the best option wins.

Now watch the recipe run. The card highlights the step being applied, then the table fills cell by cell. The dashed outline marks the cells the current cell reads. Switch problems to see the same five steps produce four different DPs. The counting DP (Climbing Stairs) adds, the optimizing ones take min or max, and Unique Paths is the same recipe in two dimensions.

Choosing the state: what does the future need to know?

Step 1 is the creative step. The rule:

Insight The state must capture everything about the past that affects the future, and nothing else. If two partial solutions with the same state could have different best futures, the state is missing information. If the state stores details the future never uses, it is too large and the DP is slower than it needs to be.

Add a rule to the stairs problem and watch the state grow: you may not make two 2-step climbs in a row. Now dp[i] alone is not enough. Whether you may climb two from stair i depends on how you got to stair i. So the state gains a dimension: dp[i][last], where last says whether the previous move was a 2-step climb.

Common ways a state grows, all covered later in the DP track:

The future depends on… Add to the state Example Topic
how many items or how much budget is left a capacity w 0/1 knapsack, coin change Knapsack Family

which sub-range is still unsolved a pair (l, r) burst balloons, matrix chain Interval & Tree DP

what you are holding (stock, cooldown) a small mode flag buy/sell stock 1D & Grid DP
the last choice made (colour, jump size) the last choice paint house, frog jump worked problems below

Running time = number of states × work per transition. Stairs: n states × 2 options = O(n). With the "no two 2-steps" rule: 2n states × at most 2 options, still O(n). Keep this product in mind while designing: if it is 10⁹, change the state.

Four stages on one problem

DP is not one leap. It is four small, mechanical refactors of the recursive solution, and every one of them keeps the answer identical. Learn them as a pipeline:

STAGE 1Plain recursion

Correct and short, but O(1.618ⁿ) time. O(n) stack depth.

STAGE 2Memoization (top-down)

Add a cache keyed by the state. O(n) time, O(n) memo plus O(n) stack.

STAGE 3Tabulation (bottom-up)

Fill an array in dependency order. O(n) time, O(n) table, no recursion.

STAGE 4Space optimisation

Keep only the cells still to be read. O(n) time, O(1) space.

Stage 1: the honest recursion

Write the recurrence directly. Do not optimize yet. This version is your specification: short enough to be obviously right, and later stages are checked against it.

def min_cost_climbing_stairs(cost: list[int]) -> int:
    n = len(cost)

    def f(i: int) -> int:                    # min cost to stand on stair i
        if i < 2:
            return 0                         # free start on stair 0 or 1
        return min(f(i - 1) + cost[i - 1],   # last move: one stair
                   f(i - 2) + cost[i - 2])   # last move: two stairs
    return f(n)                              # the top is index n

public static int MinCostClimbingStairs(int[] cost)
{
    // f(i) = min cost to stand on stair i
    int F(int i) => i < 2
        ? 0                                                    // free start
        : Math.Min(F(i - 1) + cost[i - 1], F(i - 2) + cost[i - 2]);
    return F(cost.Length);                                     // the top is index n
}

Stage 2: memoization (top-down DP)

Add a cache keyed by the state; nothing else changes. In Python, functools.cache on an inner function gives a fresh cache for every call of the outer function. In C#, use an array when the state is a small integer, with a sentinel (null, or -1 when −1 is impossible) for "not computed".

from functools import cache

def min_cost_climbing_stairs(cost: list[int]) -> int:
    n = len(cost)

    @cache                                   # fresh cache per call: no stale answers
    def f(i: int) -> int:
        if i < 2:
            return 0
        return min(f(i - 1) + cost[i - 1], f(i - 2) + cost[i - 2])
    return f(n)
# O(n) time: n + 1 states, O(1) work each. O(n) memo + O(n) recursion depth.

public static int MinCostClimbingStairs(int[] cost)
{
    int n = cost.Length;
    var memo = new int?[n + 1];                 // null = not solved yet
    int F(int i)
    {
        if (i < 2) return 0;
        if (memo[i] is int known) return known; // memo hit: O(1)
        int best = Math.Min(F(i - 1) + cost[i - 1], F(i - 2) + cost[i - 2]);
        memo[i] = best;
        return best;
    }
    return F(n);
}
// O(n) time, O(n) memo + O(n) stack.

Stage 3: tabulation (bottom-up DP)

Replace the calls by array reads and loop over the states in an order where every read cell is already filled. Here that order is simply i = 2, 3, …, n.

def min_cost_climbing_stairs(cost: list[int]) -> int:
    n = len(cost)
    dp = [0] * (n + 1)                       # dp[i] = min cost to stand on stair i
    for i in range(2, n + 1):                # dp[0] = dp[1] = 0 already
        dp[i] = min(dp[i - 1] + cost[i - 1], dp[i - 2] + cost[i - 2])
    return dp[n]
# O(n) time, O(n) space, no recursion at all.

public static int MinCostClimbingStairs(int[] cost)
{
    int n = cost.Length;
    var dp = new int[n + 1];                    // dp[0] = dp[1] = 0 by default
    for (int i = 2; i <= n; i++)
        dp[i] = Math.Min(dp[i - 1] + cost[i - 1], dp[i - 2] + cost[i - 2]);
    return dp[n];
}

Stage 4: keep only what is still needed

dp[i] reads only the two previous cells. Once dp[i] exists, dp[i-2] is never read again, so two variables replace the whole array.

def min_cost_climbing_stairs(cost: list[int]) -> int:
    a = b = 0                                # a = dp[i-2], b = dp[i-1]
    for i in range(2, len(cost) + 1):
        a, b = b, min(b + cost[i - 1], a + cost[i - 2])
    return b
# O(n) time, O(1) space.

public static int MinCostClimbingStairs(int[] cost)
{
    int a = 0, b = 0;                           // a = dp[i-2], b = dp[i-1]
    for (int i = 2; i <= cost.Length; i++)
        (a, b) = (b, Math.Min(b + cost[i - 1], a + cost[i - 2]));
    return b;
}

Top-down vs bottom-up, side by side

Both stages fill the same table with the same values. They differ only in the order of filling and in who decides that order. Top-down starts at the answer and lets the recursion discover what it needs (watch the call stack grow down to the base cases before anything is finalised). Bottom-up starts at the base cases and sweeps forward. The #k tag on each cell shows the order in which it became final. Try the grid problem too: top-down finalises cells in a very different order, and the values still match exactly.

Top-down (memoization)

  • Write it straight from the recurrence; the order comes for free.
  • Visits only the states reachable from the answer (good when most states are irrelevant, e.g. Frog Jump, sparse knapsack).
  • Easy to add pruning or early exits.
  • Costs: recursion depth (Python stops at about 1000 frames by default; C# overflows the stack around 10⁴–10⁵ frames), and hashing overhead if the memo is a dictionary.

Bottom-up (tabulation)

  • No recursion: no stack limits, and tight loops are 2–10× faster.
  • Makes the dependency footprint visible, which is what enables space optimisation.
  • Required for the advanced speed-ups (prefix sums over the table, monotonic deque, convex hull trick).
  • Costs: you must work out a valid order yourself, and you compute every state even when only a few matter.

Tip In an interview, write top-down first: it is the fastest route to a correct answer. Convert to bottom-up only when there is a reason, such as a recursion depth over about 10⁴, a need for O(1) space, or a speed-up that needs the table.

The state-space DAG: what every DP really computes

Draw every state as a node and every transition as an edge from the smaller state to the larger one, weighted by the cost of that move. Because each transition moves to a "smaller" subproblem, the graph has no cycles: it is a DAG. The DP table is just the list of node values, and the iteration order is a topological order of this DAG. This is the same idea as the DP section in Topological Sort.

This view explains three things at once:

  1. Why the order matters. A node's value must come after the values of all its predecessors, which is the definition of a topological order.
  2. Why the running time is states × transitions. Every node is visited once and every edge is relaxed once: O(V + E).
  3. Why DP fails on cyclic structures. If the "subproblem graph" has a cycle (a grid where you may move in all four directions, for example), there is no valid order. You then need a real shortest-path algorithm such as BFS or Dijkstra instead of DP.

Optimize, count, or decide: same DAG, different operators

The same graph answers different questions depending on how you combine along a path and how you choose between paths:

Question Along a path (⊗) Across paths (⊕) Base value Unreachable value
Minimum cost + min 0 +∞
Maximum value + max 0 −∞
Number of ways × (each edge counts 1) + 1 0
Is it possible? and or true false
Probability × + 1 0

Switch the question in the visualizer below, mark a few stairs as broken, and watch the identical sweep compute a minimum, a count, or a yes/no answer. The blue edges are the incoming edges the current node reads. That set never changes; only the operator does.

def stairs_three_ways(cost: list[int], broken: set[int]):
    n, INF = len(cost), float("inf")
    best, ways, ok = [INF] * (n + 1), [0] * (n + 1), [False] * (n + 1)
    for i in range(n + 1):                   # states in topological order
        if i in broken:
            continue                         # no edges into a broken stair
        if i < 2:                            # edge START -> i (free start)
            best[i], ways[i], ok[i] = 0, 1, True
        for j in (i - 1, i - 2):             # edges j -> i, paying cost[j]
            if j >= 0:
                best[i] = min(best[i], best[j] + cost[j])   # optimize: (min, +)
                ways[i] += ways[j]                          # count:    (+, x)
                ok[i] = ok[i] or ok[j]                      # decide:   (or, and)
    return best[n], ways[n], ok[n]

public static (long Best, long Ways, bool Ok) StairsThreeWays(int[] cost, HashSet<int> broken)
{
    int n = cost.Length;
    const long INF = long.MaxValue / 4;         // headroom so INF + cost cannot overflow
    var best = new long[n + 1]; var ways = new long[n + 1]; var ok = new bool[n + 1];
    Array.Fill(best, INF);
    for (int i = 0; i <= n; i++)                // states in topological order
    {
        if (broken.Contains(i)) continue;
        if (i < 2) { best[i] = 0; ways[i] = 1; ok[i] = true; }  // edge START -> i
        for (int j = i - 1; j >= Math.Max(0, i - 2); j--)       // edges j -> i
        {
            best[i] = Math.Min(best[i], best[j] + cost[j]);     // optimize
            ways[i] += ways[j];                                 // count
            ok[i] |= ok[j];                                     // decide
        }
    }
    return (best[n], ways[n], ok[n]);
}

Pitfall: the base value of a counting DP is 1, not 0 "How many ways to climb 0 stairs?" One: the empty walk. Setting ways[0] = 0 makes every count 0. In the semiring table, the base is the identity of the along-path operator: 0 for +, 1 for ×, true for and.

Evaluation order

Bottom-up DP is correct only when each cell is computed after every cell it reads. Draw the dependency arrows of one cell; the loop order must sweep in the direction that the arrows point away from.

The visualizer counts paths in a grid (each cell reads up and left) using five different orders. Three are valid; two read cells that are still 0 and produce wrong answers. A red dashed cell means "read before it was computed". Notice that anti-diagonal order is valid even though it is not row-major: any topological order works.

How to pick the order

  • Write the transition, then list the indices on the right-hand side (i-1, j-1, l+1, w-wt…).
  • Each index that is smaller than on the left forces that loop to run upward; each index that is larger forces it to run downward.
  • For intervals (l, r) reading (l+1, r) and (l, r-1), loop by length, or loop l downward and r upward.
  • If no order works because the dependencies form a cycle, it is not a DP over these states. Add a dimension (often "steps used") or use a shortest-path algorithm.

Space optimisation

A cell's dependency footprint is the set of cells it reads. Once no future cell reads a value, the value can be forgotten. This visualizer shows three classic shrinks: two variables for 1D, two rows for a grid, and one row updated in place. Faded cells are gone from memory.

def min_path_sum(grid: list[list[int]]) -> int:
    R, C = len(grid), len(grid[0])
    row = [0] * C                            # row[c] holds dp[r-1][c] until overwritten
    for r in range(R):
        for c in range(C):
            if r == 0 and c == 0:
                row[c] = grid[0][0]
            elif r == 0:
                row[c] = row[c - 1] + grid[r][c]           # only from the left
            elif c == 0:
                row[c] = row[c] + grid[r][c]               # only from above (old value)
            else:
                row[c] = min(row[c], row[c - 1]) + grid[r][c]  # above = old, left = new
    return row[-1]
# O(R*C) time, O(C) space: one row instead of R rows.

public static int MinPathSum(int[][] grid)
{
    int R = grid.Length, C = grid[0].Length;
    var row = new int[C];                        // row[c] = dp[r-1][c] until overwritten
    for (int r = 0; r < R; r++)
        for (int c = 0; c < C; c++)
        {
            if (r == 0 && c == 0) row[c] = grid[0][0];
            else if (r == 0) row[c] = row[c - 1] + grid[r][c];
            else if (c == 0) row[c] += grid[r][c];
            else row[c] = Math.Min(row[c], row[c - 1]) + grid[r][c];
        }
    return row[C - 1];
}

Insight: in-place rows work because of timing When the loop reaches row[c], the cells to its left were already overwritten with this row's values (exactly the "left" neighbour), while row[c] itself still holds last row's value (exactly the "above" neighbour). If a transition needed the old left neighbour (the diagonal dp[r-1][c-1], as in edit distance), save it in a temporary variable before overwriting. If it needed dp[r-1][c+something], reverse the loop, which is the 0/1-knapsack trick in Knapsack Family.

When not to compress. If you must reconstruct the choices (the actual route, not just its cost), you usually need the full table or a parent array. Compress only after you know the value alone is enough. Hirschberg's trick recovers paths in linear space, but it is rarely worth the complexity in practice.

Reconstructing the answer

The table stores values. To recover choices, either save a parent pointer when each cell picks its best option, or re-derive the choice afterwards. Re-deriving means walking back from the answer cell and asking which neighbour, plus its move cost, explains the value. Both run in time proportional to the length of the answer.

def min_cost_route(cost: list[int]) -> tuple[int, list[int]]:
    n = len(cost)
    dp, par = [0] * (n + 1), [-1] * (n + 1)  # par[i] = the stair we came from
    for i in range(2, n + 1):
        one, two = dp[i - 1] + cost[i - 1], dp[i - 2] + cost[i - 2]
        dp[i], par[i] = (one, i - 1) if one <= two else (two, i - 2)
    route, i = [], n
    while i >= 2:                            # follow the pointers back to a start stair
        i = par[i]
        route.append(i)
    return dp[n], route[::-1]                # stairs stood on, in order

# min_cost_route([1, 100, 1, 1, 1, 100, 1, 1, 100, 1]) -> (6, [0, 2, 4, 6, 7, 9])

public static (int Cost, List<int> Route) MinCostRoute(int[] cost)
{
    int n = cost.Length;
    var dp = new int[n + 1];
    var par = new int[n + 1];                   // par[i] = the stair we came from
    for (int i = 2; i <= n; i++)
    {
        int one = dp[i - 1] + cost[i - 1], two = dp[i - 2] + cost[i - 2];
        (dp[i], par[i]) = one <= two ? (one, i - 1) : (two, i - 2);
    }
    var route = new List<int>();
    for (int i = n; i >= 2; ) { i = par[i]; route.Add(i); }
    route.Reverse();
    return (dp[n], route);
}

Tip To list all optimal solutions, keep every tied predecessor (a list instead of one parent) and run a DFS backwards over these "optimal edges". To get the lexicographically smallest solution, fill the table backwards (dp[i] = best from i to the end) and then walk forwards, picking the smallest choice that still achieves dp[i].

DP vs greedy vs backtracking vs divide and conquer

All four break a problem into choices. They differ in how many options they keep alive:

The classic trap is coin change with arbitrary denominations. Greedy ("take the biggest coin that fits") is optimal for 1, 5, 10, 25 but not for 1, 3, 4: for 6 it takes 4 + 1 + 1 (three coins), while 3 + 3 uses two. Step through both side by side. The DP row is filled once; the purple chain is the optimal choice walked back from dp[amount].

Greedy DP Backtracking
Keeps per step one choice best value per state the current partial solution
Correct when an exchange argument proves the local choice safe optimal substructure + a polynomial number of states always (it tries everything)
Typical time O(n) or O(n log n) states × transitions exponential, cut down by pruning
Signal words "intervals", "earliest deadline", "always take…" "minimum/maximum", "number of ways", "is it possible", n ≤ 10³–10⁴ "all", "every", "list", n ≤ 15–20

Greedy is DP with a proof. When a greedy algorithm is correct, the DP over the same states would always pick the same option. The proof lets you skip computing the others. If you cannot find the proof quickly, write the DP. It is never wrong when the state is right.

Templates you will reuse

Top-down with a multi-part state

import sys
from functools import cache

def solve(grid: list[list[int]]) -> int:
    R, C = len(grid), len(grid[0])
    sys.setrecursionlimit(max(1000, 4 * R * C))   # depth can reach R + C here; be generous

    @cache                                        # key = the full argument tuple (r, c)
    def f(r: int, c: int) -> int:                 # STATE in words: best cost to reach (r, c)
        if r == 0 and c == 0:                     # BASE
            return grid[0][0]
        best = float("inf")
        if r > 0:
            best = min(best, f(r - 1, c))         # TRANSITION: last move was down
        if c > 0:
            best = min(best, f(r, c - 1))         # ... or right
        return best + grid[r][c]

    return f(R - 1, C - 1)                        # ANSWER location

public static long Solve(int[][] grid)
{
    int R = grid.Length, C = grid[0].Length;
    var memo = new Dictionary<(int, int), long>();     // value-tuple keys hash by value
    long F(int r, int c)
    {
        if (r == 0 && c == 0) return grid[0][0];
        if (memo.TryGetValue((r, c), out long known)) return known;
        long best = long.MaxValue;
        if (r > 0) best = Math.Min(best, F(r - 1, c));
        if (c > 0) best = Math.Min(best, F(r, c - 1));
        return memo[(r, c)] = best + grid[r][c];
    }
    return F(R - 1, C - 1);
}
// For dense integer states, a long[R, C] filled with -1 is 3-10x faster than a Dictionary.

Bottom-up skeleton

def solve_bottom_up(n: int, m: int) -> int:
    INF = float("inf")
    dp = [[INF] * (m + 1) for _ in range(n + 1)]   # never [[INF] * (m+1)] * (n+1): shared rows!
    dp[0][0] = 0                                   # base case(s)
    for i in range(n + 1):                         # an order where every read cell is ready
        for j in range(m + 1):
            if dp[i][j] == INF:
                continue                           # unreachable state: nothing to push
            # "push" style: relax every state this one leads to
            if i + 1 <= n:
                dp[i + 1][j] = min(dp[i + 1][j], dp[i][j] + 1)
            if j + 1 <= m:
                dp[i][j + 1] = min(dp[i][j + 1], dp[i][j] + 1)
    return dp[n][m]

public static int SolveBottomUp(int n, int m)
{
    const int INF = int.MaxValue / 2;              // headroom: INF + cost stays positive
    var dp = new int[n + 1, m + 1];
    for (int i = 0; i <= n; i++)
        for (int j = 0; j <= m; j++) dp[i, j] = INF;
    dp[0, 0] = 0;
    for (int i = 0; i <= n; i++)
        for (int j = 0; j <= m; j++)
        {
            if (dp[i, j] == INF) continue;
            if (i + 1 <= n) dp[i + 1, j] = Math.Min(dp[i + 1, j], dp[i, j] + 1);
            if (j + 1 <= m) dp[i, j + 1] = Math.Min(dp[i, j + 1], dp[i, j] + 1);
        }
    return dp[n, m];
}

Pull vs push Pull (the stairs code): each cell reads its predecessors, dp[i] = min(dp[i-1] + …, dp[i-2] + …). Push (the skeleton above): each finished cell relaxes its successors, dp[next] = min(dp[next], dp[i] + …). They compute the same thing over the same DAG. Push is handy when it is easier to say where a state goes than where it came from (Frog Jump, game simulations, "from day d buy a 7-day pass").

Recognize it when

Recognize DP when

  • The question asks for a minimum, maximum, number of ways, or yes/no over a huge set of choice sequences: "fewest coins", "how many paths", "can you reach", "longest subsequence".
  • You can describe a partial solution by a few small integers (an index, a remaining budget, a last choice, a mask), and the future depends only on those.
  • The brute force recursion branches and you can spot the same arguments recurring.
  • Constraints fit states × transitions: n ≤ 10⁵ with O(1) transitions, n ≤ 5000 for an O(n²) table, n ≤ 500 for O(n³) intervals, n ≤ 20 for bitmasks.
  • Greedy feels plausible but you can build a small counterexample (as with coins 1, 3, 4).

Pitfalls

Wrong base case Optimizing DPs must start unreachable states at the identity of the choice operator (+∞ for min, −∞ for max), not 0. With dp = [0] * (amount + 1), Coin Change happily reports 0 coins for unreachable amounts. Counting DPs need ways[empty] = 1. Fix: write the base cases in step 3 of the recipe before coding, and test the smallest inputs (n = 0, 1, 2).

Off-by-one table dimensions Decide whether index i means "item i" or "the first i items" and say it in the state sentence. "First i items" needs a table of size n + 1 and reads nums[i - 1]. Most DP index bugs come from mixing the two conventions inside one recurrence. The stairs answer dp[n] lives one past the last stair, so the table has n + 1 cells.

Iteration order that reads unfinished cells A 0/1 knapsack with a single row looped upward reads dp[w - wt] after this item already updated it, so it silently uses the item twice (which is unbounded knapsack). Fix: derive the loop direction from the transition's indices, as in the evaluation-order section.

Python: the mutable-default memo def f(i, memo={}) creates one dictionary when the function is defined, shared by every call forever. The second test case reads the first test's answers. Same bug: @cache on a module-level function that reads a global array you later change. Fix: put @cache on an inner function (a fresh cache per outer call), pass the memo explicitly, or call f.cache_clear().

Recursion depth Python raises RecursionError at about 1000 frames; top-down over n = 10⁵ fails. sys.setrecursionlimit(10**6) helps, but deep recursion can still crash the interpreter. For very deep recursion, run it in a threading.Thread with a raised threading.stack_size, or go bottom-up. In C#, a StackOverflowException cannot be caught and kills the process; anything deeper than about 10⁴ frames should be bottom-up.

C#: memo keys that never match Dictionary<int[], long> and Dictionary<List<int>, long> compare keys by reference, so a freshly built new[] { i, j } never hits and the memo silently does nothing (the code is still exponential). Fix: use value tuples Dictionary<(int, int), long>, a packed key (long)i * W + j, or a plain long[,] array. String keys like $"{i},{j}" are correct but allocate on every lookup.

Overflow at "infinity" In C#, int.MaxValue + cost wraps to a large negative number that then wins every Math.Min. Fix: use int.MaxValue / 2 as INF (so INF + INF still fits), or long, and test >= INF for "unreachable". Counting DPs overflow too: apply % MOD after every addition and keep sums in long.

A memo key that is not the whole state If the recursive function also reads something that changes, such as a visited set, a running total, or a global flag, then two calls with the same arguments can return different answers, and caching by the arguments alone is wrong. Fix: every input that affects the result must be in the key. If that is impossible (a full visited set on a general graph), the problem is not a polynomial DP over those states.

Worked problems

1. Delete and Earn: reduce to a DP you already know

LeetCode 740 Medium. Taking a number x earns x points and deletes every x − 1 and x + 1. Maximize the points.

Key insight. Once you take one copy of x, take all of them: the neighbours are already deleted. So bucket by value: pts[v] = v × count(v). Now the rule "taking v forbids v − 1 and v + 1" is exactly House Robber on the value line: adjacent values are adjacent houses.

Solution: bucket + House Robber, O(n + maxValue)

State: after processing values 0..v, take = best total if v was taken, skip = best total if it was not. Transition: take' = skip + pts[v] (only allowed if v − 1 was skipped), skip' = max(take, skip).

def delete_and_earn(nums: list[int]) -> int:
    pts = [0] * (max(nums) + 1)
    for x in nums:
        pts[x] += x                          # taking value x earns every copy
    take = skip = 0                          # best so far if the previous value was taken / skipped
    for v in range(len(pts)):
        take, skip = skip + pts[v], max(take, skip)
    return max(take, skip)

public static int DeleteAndEarn(int[] nums)
{
    var pts = new int[nums.Max() + 1];
    foreach (int x in nums) pts[x] += x;        // taking value x earns every copy
    int take = 0, skip = 0;
    foreach (int p in pts) (take, skip) = (skip + p, Math.Max(take, skip));
    return Math.Max(take, skip);
}

Time O(n + V), space O(V) for the buckets, where V is the largest value. When V is huge (10⁹), sort the distinct values instead and treat non-consecutive values as non-adjacent houses.

2. Minimum Cost For Tickets: a DP over time with look-back

LeetCode 983 Medium. You travel on given days of the year. Passes cost costs = [1-day, 7-day, 30-day]. Find the cheapest way to cover every travel day.

Key insight. Ask about the last decision: which pass covers the latest travel day d? If it is a 7-day pass, it covers d−6..d, and everything before must be covered by dp[d−7]. Define dp[d] = cheapest cover for all travel days ≤ d. Non-travel days cost nothing extra: dp[d] = dp[d−1].

Solution: dp over calendar days, O(last day) 
def mincost_tickets(days: list[int], costs: list[int]) -> int:
    travel, last = set(days), days[-1]
    dp = [0] * (last + 1)                    # dp[d] = cheapest cover of travel days <= d
    for d in range(1, last + 1):
        if d not in travel:
            dp[d] = dp[d - 1]                # nothing new to cover
            continue
        dp[d] = min(dp[d - 1] + costs[0],            # 1-day pass on day d
                    dp[max(0, d - 7)] + costs[1],    # 7-day pass covering d-6..d
                    dp[max(0, d - 30)] + costs[2])   # 30-day pass covering d-29..d
    return dp[last]

public static int MincostTickets(int[] days, int[] costs)
{
    var travel = new HashSet<int>(days);
    int last = days[^1];
    var dp = new int[last + 1];                 // dp[d] = cheapest cover of travel days <= d
    for (int d = 1; d <= last; d++)
    {
        if (!travel.Contains(d)) { dp[d] = dp[d - 1]; continue; }
        dp[d] = Math.Min(dp[d - 1] + costs[0],
                Math.Min(dp[Math.Max(0, d - 7)] + costs[1],
                         dp[Math.Max(0, d - 30)] + costs[2]));
    }
    return dp[last];
}

Time O(D) and space O(D), where D ≤ 365 is the last travel day. If days could reach 10⁹, index the DP by travel-day position instead and use a pointer (or binary search) to find the first day not covered by each pass. That makes it O(n).

3. Paint House: the state remembers the last choice

LeetCode 256 Medium (and Paint House II Hard). Paint n houses with k colours, no two neighbours the same colour, minimum total cost.

Key insight. Whether you may paint house i red depends only on the colour of house i − 1. So the state is (house, colour of this house): dp[i][c] = cost[i][c] + min over c' ≠ c of dp[i−1][c']. That is O(n·k²). The Hard version needs O(n·k): keep the best and second-best values of the previous row. The min over c' ≠ c is the best one, unless c is the best colour, in which case it is the second-best.

Solution: O(n·k) with best and second-best 
def min_cost_paint(costs: list[list[int]]) -> int:
    if not costs:
        return 0
    k = len(costs[0])
    prev = [0] * k                           # prev[c] = best total so far with the last house colour c
    for row in costs:
        b1 = b2 = float("inf"); i1 = -1      # best / second best of prev, and best's colour
        for c, v in enumerate(prev):
            if v < b1:
                b1, b2, i1 = v, b1, c
            elif v < b2:
                b2 = v
        prev = [row[c] + (b2 if c == i1 else b1) for c in range(k)]
    return min(prev)

public static int MinCostPaint(int[][] costs)
{
    if (costs.Length == 0) return 0;
    int k = costs[0].Length;
    var prev = new int[k];
    foreach (var row in costs)
    {
        int b1 = int.MaxValue, b2 = int.MaxValue, i1 = -1;
        for (int c = 0; c < k; c++)
        {
            if (prev[c] < b1) { b2 = b1; b1 = prev[c]; i1 = c; }
            else if (prev[c] < b2) b2 = prev[c];
        }
        var cur = new int[k];
        for (int c = 0; c < k; c++) cur[c] = row[c] + (c == i1 ? b2 : b1);
        prev = cur;
    }
    return prev.Min();
}

Time O(n·k), space O(k). With k = 1 and n > 1 there is no valid painting (b2 stays infinite); LeetCode's constraints exclude that case.

4. Knight Dialer: counting walks with a rolling array

LeetCode 935 Medium. A chess knight dials an n-digit number on a phone keypad, starting on any digit. Count the distinct numbers, modulo 10⁹ + 7.

Key insight. The state is (digits dialled, current digit): what came earlier does not matter. Draw the knight moves as a graph and a surprise appears. It is an 8-cycle, plus 0 bridging 4 and 6, plus a lonely 5. Each step is "every digit sends its count to its neighbours".

Solution: O(10·n) time, O(1) space 
MOD = 10**9 + 7
MOVES = [[4, 6], [6, 8], [7, 9], [4, 8], [0, 3, 9], [], [0, 1, 7], [2, 6], [1, 3], [2, 4]]

def knight_dialer(n: int) -> int:
    ways = [1] * 10                          # ways[d] = numbers of the current length ending on d
    for _ in range(n - 1):
        nxt = [0] * 10
        for d in range(10):
            for e in MOVES[d]:               # one knight move d -> e extends each of them
                nxt[e] = (nxt[e] + ways[d]) % MOD
        ways = nxt
    return sum(ways) % MOD

static readonly int[][] Moves =
{
    new[] { 4, 6 }, new[] { 6, 8 }, new[] { 7, 9 }, new[] { 4, 8 }, new[] { 0, 3, 9 },
    Array.Empty<int>(), new[] { 0, 1, 7 }, new[] { 2, 6 }, new[] { 1, 3 }, new[] { 2, 4 },
};

public static int KnightDialer(int n)
{
    const int MOD = 1_000_000_007;
    var ways = Enumerable.Repeat(1L, 10).ToArray();
    for (int step = 1; step < n; step++)
    {
        var next = new long[10];
        for (int d = 0; d < 10; d++)
            foreach (int e in Moves[d]) next[e] = (next[e] + ways[d]) % MOD;
        ways = next;
    }
    return (int)(ways.Sum() % MOD);
}

Time O(n), space O(1). The step is a fixed linear map (a 10 × 10 matrix), so for n around 10¹⁸ you would raise that matrix to a power in O(10³ log n) instead of stepping n times.

5. Number of Ways to Stay in the Same Place: bound the state space

LeetCode 1269 Hard. A pointer starts at index 0 of an array of length arrLen. Each step moves left, right, or stays, never leaving the array. Count the ways to be back at 0 after exactly steps steps, with arrLen up to 10⁶.

Key insight. The state is (steps taken, position). The naive table is steps × arrLen = 500 × 10⁶, far too big. But a position farther than steps / 2 can never get back to 0 in time, so those states contribute nothing. Capping the width at min(arrLen, steps/2 + 1) makes the table 500 × 251.

Solution: O(steps · min(arrLen, steps)) time, O(width) space 
def num_ways(steps: int, arr_len: int) -> int:
    MOD = 10**9 + 7
    width = min(arr_len, steps // 2 + 1)     # farther than steps/2 can never come back
    ways = [0] * width
    ways[0] = 1                              # before any step: at index 0
    for _ in range(steps):
        nxt = [0] * width
        for p in range(width):
            v = ways[p]                      # stayed
            if p > 0:
                v += ways[p - 1]             # came from the left
            if p + 1 < width:
                v += ways[p + 1]             # came from the right
            nxt[p] = v % MOD
        ways = nxt
    return ways[0]

public static int NumWays(int steps, int arrLen)
{
    const int MOD = 1_000_000_007;
    int width = Math.Min(arrLen, steps / 2 + 1);
    var ways = new long[width];
    ways[0] = 1;
    for (int s = 0; s < steps; s++)
    {
        var next = new long[width];
        for (int p = 0; p < width; p++)
        {
            long v = ways[p];
            if (p > 0) v += ways[p - 1];
            if (p + 1 < width) v += ways[p + 1];
            next[p] = v % MOD;
        }
        ways = next;
    }
    return (int)ways[0];
}

The general lesson: before allocating a table, ask which states are actually reachable and useful. Pruning dead states is often the whole difficulty of a Hard DP.

6. Frog Jump: a sparse state, where top-down shines

LeetCode 403 Hard. Stones sit at sorted positions. The frog starts on the first stone; its first jump is 1 unit, and if its last jump was k, the next is k − 1, k or k + 1, always forward. Can it reach the last stone?

Key insight. The position alone is not a state: from the same stone, a frog that arrived with jump 5 has different options from one that arrived with jump 2. The state is (stone, last jump). Jump sizes are at most about the number of stones, so there are O(n²) states, but only a few are reachable. Top-down memo explores just those. The bottom-up version pushes from each stone in increasing position order: sorted positions are a topological order because jumps only go forward.

Solution: push DP over (stone, jump), O(n²) worst case 
def can_cross(stones: list[int]) -> bool:
    jumps = {s: set() for s in stones}       # jumps[s] = jump sizes that can land on s
    jumps[stones[0]].add(0)
    for s in stones:                         # increasing position = topological order
        for k in jumps[s]:
            for step in (k - 1, k, k + 1):
                if step > 0 and s + step in jumps:
                    jumps[s + step].add(step)
    return bool(jumps[stones[-1]])

public static bool CanCross(int[] stones)
{
    var jumps = stones.ToDictionary(s => s, _ => new HashSet<int>());
    jumps[stones[0]].Add(0);
    foreach (int s in stones)                    // increasing position = topological order
        foreach (int k in jumps[s])
            for (int step = k - 1; step <= k + 1; step++)
                if (step > 0 && jumps.TryGetValue(s + step, out var landing))
                    landing.Add(step);
    return jumps[stones[^1]].Count > 0;
}

The sets of jumps form the DP table: one cell per (stone, jump) pair. A positive step always lands on a different stone, so no set is modified while it is being iterated. Time and space O(n²) in the worst case.

7. Student Attendance Record II: design the state as a tiny machine

LeetCode 552 Hard. Count the length-n strings over {P, A, L} with fewer than 2 As in total and never 3 consecutive Ls, modulo 10⁹ + 7.

Key insight. What does the future need to know about the prefix? Only how many A's so far (0 or 1) and how many L's at the end (0, 1 or 2). That gives 6 states, and each character is a transition between them. Any "count strings that avoid a pattern" problem works this way: build the automaton, then count walks.

Solution: 6-state counting DP, O(n) 
def check_record(n: int) -> int:
    MOD = 10**9 + 7
    dp = [[1, 0, 0], [0, 0, 0]]              # dp[a][l]; the empty record is in state (0, 0)
    for _ in range(n):
        nxt = [[0, 0, 0], [0, 0, 0]]
        for a in range(2):
            for l in range(3):
                v = dp[a][l]
                if not v:
                    continue
                nxt[a][0] = (nxt[a][0] + v) % MOD                # P
                if a == 0:
                    nxt[1][0] = (nxt[1][0] + v) % MOD            # A (only one allowed)
                if l < 2:
                    nxt[a][l + 1] = (nxt[a][l + 1] + v) % MOD    # L (at most two in a row)
        dp = nxt
    return sum(map(sum, dp)) % MOD

public static int CheckRecord(int n)
{
    const int MOD = 1_000_000_007;
    var dp = new long[2, 3];
    dp[0, 0] = 1;                                // the empty record
    for (int day = 0; day < n; day++)
    {
        var next = new long[2, 3];
        for (int a = 0; a < 2; a++)
            for (int l = 0; l < 3; l++)
            {
                long v = dp[a, l];
                if (v == 0) continue;
                next[a, 0] = (next[a, 0] + v) % MOD;                       // P
                if (a == 0) next[1, 0] = (next[1, 0] + v) % MOD;           // A
                if (l < 2) next[a, l + 1] = (next[a, l + 1] + v) % MOD;    // L
            }
        dp = next;
    }
    long total = 0;
    foreach (long v in dp) total += v;
    return (int)(total % MOD);
}

Time O(6n), space O(1). The same automaton-plus-counting design solves "strings avoiding a pattern", "binary strings without k consecutive ones", and many digit-DP problems in Bitmask & Digit DP.

Check yourself

A recursive solution makes 2,692,537 calls for n = 30 but only 59 with a memo. What property made that possible, and what would break it?

Overlapping subproblems: the recursion asks the same question (f(k) for the same k) over and over, so caching each answer once leaves just one call per distinct state (plus the cache hits). It breaks if the function's result depends on anything outside its arguments (a mutated global, a visited set), because then the same arguments do not mean the same question.

Coin Change with dp = [0] * (amount + 1) returns 0 for coins = [2], amount = 3. Which recipe step is wrong?

Step 3, the base cases. Only dp[0] = 0 is a real base case; every other amount must start at +∞ (unreachable) so that min can only lower it via a real coin. Starting at 0 claims "3 is reachable with 0 coins". At the end, map ∞ back to −1.

A grid DP reads dp[r-1][c] and dp[r][c+1]. In what order must you fill the table?

Rows top to bottom (the up-neighbour must be done), and within a row columns right to left (the right-neighbour must be done). Any order where every arrow points from a finished cell to the current cell is valid; this one is the simplest.

You squeezed a 2D table into one row and the answers are now too large. The recurrence reads only dp[i-1][w] and dp[i-1][w-wt]. What happened?

You looped w upward, so dp[w - wt] was already overwritten with this row's value before dp[w] read it: each item got used more than once. Loop w downward so every read still sees the previous row.

Why does "best total so far" (a number) not belong in a memo key, while "money left" in a budget problem does?

The key must be exactly what the future depends on. With a remaining budget, different values allow different future choices, so it is state. A running best total does not change what you can do next; it is the value the DP computes. Putting it in the key multiplies the states without benefit, and usually means the recurrence should return "best from here" instead of carrying "best so far".

When is a greedy choice safe and DP unnecessary, using coin systems as the example?

When an exchange argument proves that some optimal solution always begins with the greedy choice. For coins {1, 5, 10, 25}, "take the largest coin that fits" is provably optimal. For {1, 3, 4} and amount 6, greedy gives 4 + 1 + 1 (3 coins) but 3 + 3 (2 coins) is better, so you need DP. If you cannot prove greedy correct, try a small counterexample search before trusting it.

Cheat sheet

DefinitionDP = recursion + overlapping subproblems + optimal substructure. Solve each distinct state once.
RecipeState in words, transition, base cases, evaluation order, answer location. Write all five before coding.
Find the transitionAsk "what was the last decision?" and branch on its options.
State testEverything the future depends on, nothing it does not. More information = more states.
ComplexityTime = states × transitions per state. Space = states, or less with rolling rows.
Basesmin: +∞, max: −∞, count: 0 with ways[empty] = 1, feasible: False with ok[empty] = True.
OrderTopological order of the dependency arrows. Same row reads: watch the loop direction.
Top-downFast to write, visits only reachable states. Watch recursion depth (Python ~1000, C# stack).
Bottom-upNo recursion, enables rolling arrays. Must fill every state in a valid order.
ReconstructStore the argmin/argmax choice per cell, or re-derive it, and walk back from the answer.
Python@cache on an inner function; never memo={} defaults; never [[0]*m]*n.
C#Tuple or packed-long keys, not arrays; int.MaxValue / 2 as INF; long + % MOD for counts.
