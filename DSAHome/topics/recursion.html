Recursion & the Call Stack

Watch frames push and pop, read recursion trees, design base cases and the 'leap of faith', and see where memoization comes from.

Beginner → Intermediate~50 min studyBuilds on: Complexity AnalysisUpdated 2026-11-03

What recursion is

A recursive function solves a problem by trusting itself on a smaller copy of the same problem. Answer the tiny cases directly (the base case), make every other call strictly smaller, and combine the smaller answer into yours. If those three things hold, the function is correct by induction. You never need to trace the whole chain in your head.

Recursion is not a trick for factorials. It is the natural shape of anything self-similar: a tree is a node plus two smaller trees, a list is a head plus a shorter list, a sorted array is two sorted halves merged, and "all subsets" is "subsets without the first item, plus the same with it". Whenever the problem contains smaller copies of itself, recursion lets the code say exactly that, and nothing else.

This page builds on Complexity Analysis (recursion trees, the stack as space). It is also the foundation for everything that follows: Tree Traversals, Backtracking, Sorting (merge sort and quicksort) and Dynamic Programming are all recursion with one extra idea added.

The same function in code. Notice that it reads like the definition of a sum, not like a procedure:

def total(nums, i=0):
    if i == len(nums):               # base case: empty suffix
        return 0
    return nums[i] + total(nums, i + 1)   # my layer + trusted rest

static int Total(int[] nums, int i = 0)
{
    if (i == nums.Length) return 0;          // base case: empty suffix
    return nums[i] + Total(nums, i + 1);     // my layer + trusted rest
}

Insight: pass an index, not a slice total(nums[1:]) reads nicely but copies the list on every call: O(n) per call, O(n²) in total. Passing a start index i keeps each call O(1). The same applies to strings (s[1:]) and to C# Skip(1).ToArray().

The leap of faith: a design method

Tracing recursion is how you check it. Designing it is a different skill, and it follows the same four questions every time:

1 · DEFINEWhat does f(x) return?

One precise sentence. "height(node) = number of nodes on the longest path down from node." Vague definitions make bugs.

2 · SHRINKWhich smaller inputs?

A shorter list, a child node, half the array, n−1, n/2. Every call must move strictly closer to a base case.

3 · TRUSTAssume they are solved

Write the combine step using f on the smaller inputs as if it were a library function that already works.

4 · BASEStop at the smallest

Which inputs cannot shrink further? Answer them directly. Check that every path reaches one.

Walk through it for reverse a string, a typical first problem:

  1. Define: rev(s, i, j) reverses s[i..j] in place.
  2. Shrink: after swapping the outer pair, the inside s[i+1..j-1] is a smaller copy.
  3. Trust: rev(s, i+1, j-1) reverses the inside. Swap the ends, call it, done.
  4. Base: when i >= j there are 0 or 1 characters: nothing to do.
def reverse_string(s: list[str]) -> None:
    def rev(i, j):
        if i >= j:                    # 0 or 1 chars: already reversed
            return
        s[i], s[j] = s[j], s[i]       # my layer: the outer pair
        rev(i + 1, j - 1)             # trust: the inside
    rev(0, len(s) - 1)

public void ReverseString(char[] s)
{
    void Rev(int i, int j)
    {
        if (i >= j) return;                    // 0 or 1 chars
        (s[i], s[j]) = (s[j], s[i]);           // my layer
        Rev(i + 1, j - 1);                     // trust: the inside
    }
    Rev(0, s.Length - 1);
}

Tracing to design (slow, error-prone)

"rev(0,4) swaps, calls rev(1,3), which swaps, calls rev(2,2), which returns, then rev(1,3) returns, then…"

You run out of working memory at depth 3, and you still have not decided what the function means.

Defining to design (fast, provable)

"rev(i, j) reverses s[i..j]. If the inside is reversed and I swap the ends, the whole range is reversed."

One layer, one sentence. Trace only afterwards, on a tiny input, to check the base case.

Base cases: the part that actually goes wrong

Most recursion bugs are base-case bugs. Ask three questions:

Question Typical mistake Fix
Does every path hit a base case? fib(n) handles n == 1 but is called with n == 0 Cover the whole smallest range: if n < 2: return n
Is the base case the right value? count_paths returns 0 for the empty path instead of 1 Ask "how many ways to do nothing?" (usually 1) and "best of nothing?" (0, −∞ or +∞)
Does the input strictly shrink? solve(lo, hi) recurses on (lo, mid) with mid = (lo + hi + 1) // 2 when hi = lo + 1 Check the two-element case by hand; it is where off-by-one recursions loop forever

Tip: prefer the emptiest base case total([]) = 0 is better than total([x]) = x: it handles the empty input for free and needs no special case. For trees, if node is None: return … at the top is almost always cleaner than checking node.left and node.right before every call.

The call stack, frame by frame

When a function calls itself, the current call does not disappear. It is paused in a stack frame that remembers its arguments, its local variables and the exact line to resume at. The new call gets its own frame on top. When it returns, its frame is popped and the paused frame below resumes with the returned value in hand.

So recursion has two phases. Going down (the winding phase), frames pile up and nothing is computed yet. Coming back up (the unwinding phase), each frame finishes its pending work, like n * … in factorial. Pick a program and step through it. Watch which frame is running (amber), which are paused (blue) and what each paused frame is waiting to do.

Things to notice as you step:

  • factorial(n) pushes n frames before any multiplication happens. All the work happens on the way back up. Depth is n, so space is O(n).
  • The tail-call version carries an accumulator, so nothing is pending when it recurses. In theory the frame could be reused; Python and C# do not do that, so the stack still grows to n. See tail recursion below.
  • fib(n) makes two calls per frame. The stack only ever holds one path from the root, so it stays at most n deep even though the number of calls explodes.
  • power(2, n) by halving recurses on n/2. Depth is the number of binary digits of n: log₂ n frames for 2⁴⁰.

Pitfall: StackOverflowException cannot be caught in C# In Python a too-deep recursion raises RecursionError, which you can catch, and sys.setrecursionlimit raises the limit (the real C stack can still overflow beyond about 10⁴–10⁵ frames). In .NET a stack overflow kills the whole process; try/catch does not help. If depth can reach about 10⁴ or more (a degenerate tree, a long linked list, n up to 10⁵), use an explicit stack or a loop.

Recursion trees: where the time goes

The call stack shows one moment. The recursion tree shows the whole run: each node is one call, its children are the calls it makes. Two numbers fall out of the picture:

  • Time = (number of nodes) × (work per node, excluding the recursive calls).
  • Space = (height of the tree) × (frame size), plus whatever you allocate.

For fib, every node makes two calls, so the tree has about 1.6ⁿ nodes. But look at the labels: fib(3) is computed again and again, and fib(2) even more. Step through and watch the call counts on the right.

The tree has exponentially many nodes but only n + 1 distinct labels. That gap, many calls but few distinct arguments, is the definition of overlapping subproblems. Cache each answer the first time you compute it and every later call becomes a lookup. Switch the mode to with memo (cache) and the tree collapses: one full path down the left, and every right child is an instant cache hit.

from functools import cache

@cache                          # memo keyed by the arguments
def fib(n: int) -> int:
    if n < 2:
        return n
    return fib(n - 1) + fib(n - 2)

# The same thing by hand (works for unhashable state too):
def fib_memo(n, memo=None):
    if memo is None:
        memo = {}
    if n < 2:
        return n
    if n not in memo:
        memo[n] = fib_memo(n - 1, memo) + fib_memo(n - 2, memo)
    return memo[n]

static long Fib(int n, Dictionary<int, long>? memo = null)
{
    memo ??= new Dictionary<int, long>();
    if (n < 2) return n;
    if (memo.TryGetValue(n, out var hit)) return hit;
    long r = Fib(n - 1, memo) + Fib(n - 2, memo);
    memo[n] = r;
    return r;
}
Version Calls Time Space
Plain recursion ≈ 1.6ⁿ (fib(40) ≈ 3.3 × 10⁸) O(φⁿ) O(n) stack
Memoized 2n − 1 O(n) O(n) memo + O(n) stack
Bottom-up loop none O(n) O(1) with two variables

Insight: memoization needs a pure function A cache is only valid if the answer depends on the arguments alone. If the function reads or mutates outer state (a running path list, a global counter), two calls with the same arguments can return different results and the memo silently gives wrong answers. Make every input that changes the answer an argument; that set of arguments is the DP state. This is the bridge to Dynamic Programming.

Pitfall: mutable default arguments in Python def f(n, memo={}) creates one dict when the function is defined and shares it across every top-level call, including calls on different inputs in the same test run. Use memo=None and create it inside, as above, or @cache on an inner function.

Divide and conquer

Divide and conquer is recursion with a specific shape: split the input into independent parts, solve each part recursively, then combine the answers. Merge sort is the cleanest example: split the array in half, sort each half (trust!), then merge two sorted lists in linear time.

Step through it below. The top half of the picture is the split phase going down; the bottom half is the merge phase coming back up. The merge also counts inversions (pairs i < j with a[i] > a[j]): whenever an item from the right half jumps ahead of items still waiting in the left half, it forms an inversion with each of them. That one extra line is the whole idea behind several Hard problems.

def merge_sort(a: list[int]) -> list[int]:
    if len(a) <= 1:                       # base: already sorted
        return a
    mid = len(a) // 2
    left = merge_sort(a[:mid])            # trust: sorted left half
    right = merge_sort(a[mid:])           # trust: sorted right half
    out, i, j = [], 0, 0
    while i < len(left) and j < len(right):
        if left[i] <= right[j]:           # <= keeps the sort stable
            out.append(left[i]); i += 1
        else:
            out.append(right[j]); j += 1
    out.extend(left[i:]); out.extend(right[j:])
    return out

static int[] MergeSort(int[] a)
{
    if (a.Length <= 1) return a;                  // base: already sorted
    int mid = a.Length / 2;
    int[] left = MergeSort(a[..mid]);             // trust: sorted halves
    int[] right = MergeSort(a[mid..]);
    var res = new int[a.Length];
    int i = 0, j = 0, k = 0;
    while (i < left.Length && j < right.Length)
        res[k++] = left[i] <= right[j] ? left[i++] : right[j++];
    while (i < left.Length) res[k++] = left[i++];
    while (j < right.Length) res[k++] = right[j++];
    return res;
}

Divide and conquer appears in many disguises. The split does not have to be "two halves", and the combine step is where the problem lives:

Problem Split Combine
Merge sort / count inversions two halves merge, counting right-before-left jumps
Pow(x, n) n → n/2 (one call, reused) square, times x if n is odd
Different Ways to Add Parentheses every operator position all pairs (left result, right result)
Build tree from preorder + inorder root splits inorder into left and right attach the two subtrees
Majority element / max subarray (D&C version) two halves look at the crossing case

Recursion on trees: return what the parent needs

Trees are recursive by definition, so tree code is almost always a post-order recursion: get an answer from each child, combine them at the node, return the result upwards. The design question is always the same: what does my parent need from me?

Choose a question below and step through. The same skeleton answers all of them; only the combine line changes. Watch the diameter case closely: the function returns the height (what the parent needs) but records the best path through the node in an outer variable (what the question asks). Separating "what I return" from "what I record" is the key to every "path in a tree" problem.

def diameter_of_binary_tree(root) -> int:
    best = 0
    def height(node) -> int:          # returns: what the parent needs
        nonlocal best
        if node is None:
            return 0
        l, r = height(node.left), height(node.right)
        best = max(best, l + r)       # records: the answer we want
        return 1 + max(l, r)
    height(root)
    return best

public int DiameterOfBinaryTree(TreeNode? root)
{
    int best = 0;
    int Height(TreeNode? node)            // returns what the parent needs
    {
        if (node is null) return 0;
        int l = Height(node.left), r = Height(node.right);
        best = Math.Max(best, l + r);     // records the answer
        return 1 + Math.Max(l, r);
    }
    Height(root);
    return best;
}

Tip: sentinels instead of a second pass "Is the tree balanced?" can be written as abs(height(l) - height(r)) <= 1 and balanced(l) and balanced(r), but that recomputes heights: O(n²) on a path. Instead return the height, or −1 to mean "already unbalanced", and short-circuit as soon as either child returns −1. One pass, O(n). The visualizer's "is it balanced?" mode shows the −1 travelling up.

Recursion on linked lists

A linked list is a node followed by a shorter list, so list recursion follows the same leap of faith. To reverse a list: trust reverse(head.next) to reverse everything after head and hand back the new head. After that call, head.next still points at the node that is now the tail of the reversed part. Point that node back at head, cut head's forward arrow, and return the same new head.

Merging two sorted lists is the other classic. The smaller head goes first, and its next is "the merge of everything else":

def merge_two_lists(a, b):
    if a is None:
        return b
    if b is None:
        return a
    if a.val <= b.val:
        a.next = merge_two_lists(a.next, b)
        return a
    b.next = merge_two_lists(a, b.next)
    return b

public ListNode? MergeTwoLists(ListNode? a, ListNode? b)
{
    if (a is null) return b;
    if (b is null) return a;
    if (a.val <= b.val) { a.next = MergeTwoLists(a.next, b); return a; }
    b.next = MergeTwoLists(a, b.next);
    return b;
}

Pitfall: list recursion is O(n) deep Lists are the worst case for depth: every node adds a frame. These versions are perfect for understanding and for n up to about 10³, but with n = 5 × 10⁴ they overflow Python's default limit and risk the .NET stack. In production, and when the constraints say n ≤ 10⁵, write the iterative version: three pointers for reversal, a dummy head for merging. See Linked Lists.

Tail recursion, and why it does not save you

A call is a tail call when it is the very last thing the function does: return f(x), with nothing left to compute afterwards. return n * fact(n - 1) is not a tail call, because the multiplication waits. Rewrite with an accumulator and it becomes one:

def fact(n, acc=1):
    if n <= 1:
        return acc
    return fact(n - 1, acc * n)   # tail call: nothing pending

# What a tail call really is: a loop in disguise
def fact_loop(n):
    acc = 1
    while n > 1:                  # same state (n, acc), updated in place
        acc, n = acc * n, n - 1
    return acc

static long Fact(int n, long acc = 1)
{
    if (n <= 1) return acc;
    return Fact(n - 1, acc * n);      // tail call: nothing pending
}

static long FactLoop(int n)
{
    long acc = 1;
    while (n > 1) { acc *= n; n--; }  // same state, updated in place
    return acc;
}

In languages with tail-call elimination (Scheme, and often Scala with @tailrec), the compiler reuses the frame and a tail-recursive function runs in O(1) stack. Python never does this (by design), and C# does not guarantee it: the 64-bit JIT sometimes emits a tail call in Release builds, but you cannot rely on it, and Debug builds never do. So in both languages:

Relying on tail recursion

"It is tail-recursive, so it uses constant stack."

Still n frames deep in Python and C#. fact(5000) raises RecursionError, and a long C# chain can kill the process.

Using it as a design step

Write the accumulator version to find the loop state (n, acc), then turn it into a while loop mechanically: the arguments become variables and the tail call becomes "update and continue".

Recursion without recursion: an explicit stack

Any recursion can be run with your own stack: the stack holds what the call stack would have held. This removes the depth limit (your list lives on the heap) and gives you control (you can pause, stop early or interleave). The price is that you must store by hand whatever the paused frame needed to remember.

  • Preorder is easy: nothing happens after the recursive calls, so pop, output, push the children (right first so that left is popped first).
  • Inorder needs the node to wait until its left subtree is done: walk left pushing every node, then pop one, output it and go right.
  • Postorder, and any recursion with work after the calls, needs the frame to remember how far it got. Push (node, seen): the first pop schedules the children and pushes the node back as seen, and the second pop does the "after" work.
def postorder(root):
    out, stack = [], [(root, False)] if root else []
    while stack:
        node, seen = stack.pop()
        if seen:                      # children done: "after the calls"
            out.append(node.val)
            continue
        stack.append((node, True))    # come back to me later
        if node.right:
            stack.append((node.right, False))
        if node.left:                 # pushed last, so handled first
            stack.append((node.left, False))
    return out

public IList<int> Postorder(TreeNode? root)
{
    var output = new List<int>();
    var stack = new Stack<(TreeNode node, bool seen)>();
    if (root is not null) stack.Push((root, false));
    while (stack.Count > 0)
    {
        var (node, seen) = stack.Pop();
        if (seen) { output.Add(node.val); continue; }
        stack.Push((node, true));                    // revisit later
        if (node.right is not null) stack.Push((node.right, false));
        if (node.left is not null) stack.Push((node.left, false));
    }
    return output;
}

Insight: a frame is just a tuple The general recipe: a frame = (arguments, locals the code still needs, where to resume). For a function that calls itself k times, seen becomes a small integer "stage" (0 = before the first call, 1 = after it, …). Every recursive algorithm, including DFS on graphs with millions of nodes, can be converted this way. In interviews, mention it when the depth can reach 10⁵.

Recursion or a loop?

Every recursion can become a loop and every loop can become a recursion, so the choice is about clarity and limits, not power.

Situation Prefer Why
Tree or nested input with depth O(log n) or small Recursion The code mirrors the data; depth is never a problem.
One smaller call and nothing pending (tail shape) Loop It is a loop; recursion only adds frames.
Linked list or path-shaped input with n ≥ 10⁴ Loop or explicit stack O(n) depth overflows the stack.
Generate all, try every choice Recursion The undo-on-return structure is natural; depth = number of choices.
Overlapping subproblems Recursion + memo first, then bottom-up if the depth or speed matters Top-down is easier to get right; bottom-up has no depth limit and lower constants.
Graph DFS on 10⁵–10⁶ nodes Explicit stack A long chain is common in graphs; a crash is not an acceptable failure mode.

When you must keep a deep recursion (for example a contest solution or a quick script), you can give it a bigger stack. Treat this as a tool for scripts and contests, not for services:

import sys, threading

def main():
    def depth(n):                      # deliberately deep: n frames
        return 0 if n == 0 else 1 + depth(n - 1)
    print(depth(200_000))

sys.setrecursionlimit(1_000_000)       # Python's own frame counter
threading.stack_size(128 * 1024 * 1024)  # real C stack for new threads (Windows caps near 256 MB)
t = threading.Thread(target=main)
t.start()
t.join()

// Run deep recursion on a thread with a 512 MB stack.
static int Depth(int n) => n == 0 ? 0 : 1 + Depth(n - 1);

static void RunDeep()
{
    int result = 0;
    var t = new Thread(() => result = Depth(200_000), maxStackSize: 512 * 1024 * 1024);
    t.Start();
    t.Join();
    Console.WriteLine(result);
}

Pitfall: raising only the recursion limit sys.setrecursionlimit(10**6) alone does not add stack memory. It only lets Python go deeper before raising RecursionError, so the interpreter can then crash hard with a segmentation fault. Raise the limit and run the work on a thread with a bigger stack, or better, remove the depth.

Templates

Five shapes cover nearly every recursive solution. Learn to name which one you are writing before you write it.

1 · Reduce by one (or by half) and combine

The answer for x is built from the answer for one smaller input. Factorial, sum of a list, power, reverse, "K-th symbol". Time = depth × work per call.

def solve(x):
    if is_base(x):
        return base_answer(x)
    sub = solve(smaller(x))          # exactly one recursive call
    return combine(x, sub)

# Example: x**n by halving, O(log n) calls
def my_pow(x: float, n: int) -> float:
    if n < 0:
        return 1 / my_pow(x, -n)
    if n == 0:
        return 1.0
    half = my_pow(x, n // 2)         # call once, use twice
    return half * half * (x if n % 2 else 1)

// Example: x^n by halving, O(log n) calls
static double MyPow(double x, long n)
{
    if (n < 0) return 1 / MyPow(x, -n);
    if (n == 0) return 1.0;
    double half = MyPow(x, n / 2);       // call once, use twice
    return n % 2 == 0 ? half * half : half * half * x;
}

2 · Post-order on a tree: return up, record aside

Each node combines its children's answers. Return what the parent needs; keep the global best in an outer variable. O(n) time, O(h) stack.

def tree_answer(root):
    best = initial
    def dfs(node):
        nonlocal best
        if node is None:
            return empty_value           # e.g. 0 height, 0 sum
        l, r = dfs(node.left), dfs(node.right)
        best = better(best, through(node, l, r))
        return up(node, l, r)            # what the parent needs
    dfs(root)
    return best

int TreeAnswer(TreeNode? root)
{
    int best = 0;                        // initial
    int Dfs(TreeNode? node)
    {
        if (node is null) return 0;      // empty value
        int l = Dfs(node.left), r = Dfs(node.right);
        best = Math.Max(best, l + r);    // record: through this node
        return 1 + Math.Max(l, r);       // return: what the parent needs
    }
    Dfs(root);
    return best;
}

3 · Divide and conquer

Split into independent parts, solve each, combine. The cost follows the Master theorem: two halves plus linear combine gives O(n log n).

def dc(lo, hi):                          # solve a[lo:hi]
    if hi - lo <= 1:
        return leaf(lo, hi)
    mid = (lo + hi) // 2
    left, right = dc(lo, mid), dc(mid, hi)
    return merge(left, right, lo, mid, hi)   # the problem lives here

Result Dc(int lo, int hi)                // solve a[lo..hi)
{
    if (hi - lo <= 1) return Leaf(lo, hi);
    int mid = lo + (hi - lo) / 2;
    var left = Dc(lo, mid);
    var right = Dc(mid, hi);
    return Merge(left, right, lo, mid, hi);
}

4 · Memoized recursion (top-down DP)

Same as any recursion, plus a cache keyed by the full state. Time = (number of distinct states) × (work per state).

from functools import cache

def count_ways(n: int) -> int:           # e.g. climb 1 or 2 steps
    @cache
    def f(i):
        if i == n:
            return 1                     # one way to do nothing more
        if i > n:
            return 0
        return f(i + 1) + f(i + 2)
    return f(0)

static long CountWays(int n)
{
    var memo = new long?[n + 2];
    long F(int i)
    {
        if (i == n) return 1;
        if (i > n) return 0;
        return memo[i] ??= F(i + 1) + F(i + 2);
    }
    return F(0);
}

5 · Generate all: one branch per choice

Each call makes one decision and recurses on the rest. The output size drives the cost, so 2ⁿ subsets or n! permutations is the best possible. This is the doorway to Backtracking.

def subsets(nums: list[int]) -> list[list[int]]:
    out, cur = [], []
    def go(i):
        if i == len(nums):
            out.append(cur.copy())       # copy: cur keeps changing
            return
        go(i + 1)                        # choice 1: skip nums[i]
        cur.append(nums[i])              # choice 2: take nums[i]
        go(i + 1)
        cur.pop()                        # undo before returning
    go(0)
    return out

public IList<IList<int>> Subsets(int[] nums)
{
    var output = new List<IList<int>>();
    var cur = new List<int>();
    void Go(int i)
    {
        if (i == nums.Length) { output.Add(new List<int>(cur)); return; }
        Go(i + 1);                       // skip nums[i]
        cur.Add(nums[i]);                // take nums[i]
        Go(i + 1);
        cur.RemoveAt(cur.Count - 1);     // undo
    }
    Go(0);
    return output;
}

Complexity of recursive code

Draw (or imagine) the recursion tree, then multiply:

Time = number of calls × work per call (not counting the work inside the child calls). Space = maximum depth × frame size plus anything you allocate, such as slices, memo tables and output.

f(n-1) + O(1) (factorial, list) n O(1) O(n) O(n)
f(n/2) + O(1) (power, binary search) log n O(1) O(log n) O(log n)
f(n-1) + f(n-2) (plain fib) ≈ 1.6ⁿ O(1) O(φⁿ) O(n)
same, memoized 2n − 1 O(1) O(n) O(n)
2·f(n/2) + O(n) (merge sort) ≈ 2n O(size) O(n log n) O(log n)

Tip: depth limits from the constraints n ≤ 10³: any recursion is fine. n ≤ 10⁴: recursion along n is risky in Python (raise the limit) and fine in C#. n ≥ 10⁵ with O(n) depth: use a loop or an explicit stack. Depth O(log n) (halving, balanced trees, merge sort) is always safe: log₂ 10⁹ is only 30.

Recognize it, and the usual pitfalls

Signals that recursion is the natural fit

  • The input is recursive: a tree, nested lists or brackets ("3[a2[c]]"), an expression, a file system.
  • The problem says "all" combinations, subsets, permutations, partitions or ways to parenthesise.
  • The answer for n is defined via smaller n: a recurrence, a grammar, "row n is built from row n−1".
  • You can split the input into independent parts and combine them: halves, left and right of a root, both sides of an operator.
  • The problem is a game or a choice at each step, and you want the best outcome (this becomes memoized recursion).

Pitfalls checklist

  1. No base case, or one that is never reached. Check n = 0, n = 1, the empty list, None, and odd/even sizes when halving.
  2. The input does not shrink on some path (for example mid rounding up when hi = lo + 1): infinite recursion.
  3. Exponential blow-up from recomputing the same state. Count distinct arguments; if they are far fewer than the calls, memoize.
  4. Hidden copies: s[1:], nums[:mid], list(path) at every node, string concatenation in a loop. Pass indices and copy only at the leaves.
  5. Shared mutable state: a path list appended to the output without copying (every result ends up empty), or def f(x, memo={}).
  6. Forgetting to undo a choice in generate-all recursion (cur.pop(), visited.remove).
  7. Depth: CPython's default limit is 1,000; .NET has about 1 MB of stack per thread and an overflow kills the process. Long chains need a loop.
  8. Mixing "returned" and "recorded" values in tree problems: return what the parent needs, and record the answer separately.

Worked problems

Seven problems, from a two-line recursion to a Hard divide and conquer. For each one, find the smaller copy of the problem first; the code follows from it.

1 · K-th Symbol in Grammar Medium

Row 1 is 0. Each row replaces 0 → 01 and 1 → 10. Return the k-th symbol (1-indexed) of row n, with n up to 30. Row 30 has 2²⁹ symbols, so building it is out of the question.

Smaller copy: symbol k of row n is produced by symbol ⌈k/2⌉ of row n − 1. A left child (k odd) copies its parent; a right child (k even) flips it. So the answer is one walk up the tree: n calls, O(n) time.

Solution: walk up to the parent

def kthGrammar(n: int, k: int) -> int:
    if n == 1:
        return 0
    parent = kthGrammar(n - 1, (k + 1) // 2)
    return parent if k % 2 == 1 else 1 - parent

public int KthGrammar(int n, int k)
{
    if (n == 1) return 0;
    int parent = KthGrammar(n - 1, (k + 1) / 2);
    return k % 2 == 1 ? parent : 1 - parent;
}

O(n) time and O(n) stack. Unrolled, the answer is the parity of the number of 1 bits in k − 1, which gives an O(1) version: bin(k - 1).count("1") % 2.

2 · Find the Winner of the Circular Game Medium

n friends sit in a circle; counting k at a time, the k-th person leaves, and counting restarts from the next one. Who is last? (The Josephus problem.)

Smaller copy: after the first person leaves, the game continues with n − 1 people, starting from the position just after the one removed. If f(n−1) is the winner's 0-based seat in that smaller game, then in the original numbering it is k seats further around: f(n) = (f(n−1) + k) mod n. The base case is one person, who wins at seat 0.

Solution: re-number the smaller circle

def findTheWinner(n: int, k: int) -> int:
    def seat(m):                     # 0-based winner among m people
        if m == 1:
            return 0
        return (seat(m - 1) + k) % m
    return seat(n) + 1

public int FindTheWinner(int n, int k)
{
    int Seat(int m) => m == 1 ? 0 : (Seat(m - 1) + k) % m;
    return Seat(n) + 1;
}

O(n) time and O(n) stack versus O(n·k) to simulate. It is a tail-shaped recursion over m, so it unrolls into w = 0; for m in 2..n: w = (w + k) % m. That loop form is the one to use for n = 10⁵.

3 · Decode String Medium

Expand "3[a2[c]]" into "accaccacc". Brackets nest arbitrarily.

Smaller copy: the text inside a bracket is itself an encoded string. Write parse() to read until the matching ] (or the end) and return the decoded text. When it meets k[, it calls itself for the inside and repeats the result k times. A shared index i walks the input once. This is recursive descent, the standard way to parse anything nested.

Solution: recursive descent with a shared index

def decodeString(s: str) -> str:
    i = 0
    def parse() -> str:
        nonlocal i
        out, num = [], 0
        while i < len(s):
            c = s[i]
            i += 1
            if c.isdigit():
                num = num * 10 + int(c)
            elif c == "[":
                out.append(parse() * num)    # trust: decodes the inside
                num = 0
            elif c == "]":
                break                        # end of this level
            else:
                out.append(c)
        return "".join(out)
    return parse()

public string DecodeString(string s)
{
    int i = 0;
    string Parse()
    {
        var sb = new StringBuilder();
        int num = 0;
        while (i < s.Length)
        {
            char c = s[i++];
            if (char.IsDigit(c)) num = num * 10 + (c - '0');
            else if (c == '[')
            {
                string inner = Parse();          // trust: decodes the inside
                for (int r = 0; r < num; r++) sb.Append(inner);
                num = 0;
            }
            else if (c == ']') break;            // end of this level
            else sb.Append(c);
        }
        return sb.ToString();
    }
    return Parse();
}

Time is linear in the size of the output; the stack depth is the bracket nesting depth. The same skeleton parses arithmetic (Basic Calculator), Lisp expressions and chemical formulas (Number of Atoms).

4 · Construct Binary Tree from Preorder and Inorder Traversal Medium

Rebuild a tree (with distinct values) from its preorder and inorder traversals.

Smaller copy: preorder starts with the root. Find that value in inorder: everything to its left is the left subtree and everything to its right is the right subtree, and each of those is the same problem on a smaller range. Preorder lists the whole left subtree before the right one, so if the recursion builds left before right, it can simply consume preorder from a shared pointer.

Solution: split the inorder range, consume preorder in order

def buildTree(preorder: list[int], inorder: list[int]):
    pos = {v: i for i, v in enumerate(inorder)}    # O(1) root lookup
    it = iter(preorder)                            # roots, in call order

    def build(lo: int, hi: int):                   # subtree of inorder[lo:hi]
        if lo == hi:
            return None
        val = next(it)
        node = TreeNode(val)
        node.left = build(lo, pos[val])            # left first: preorder order
        node.right = build(pos[val] + 1, hi)
        return node

    return build(0, len(inorder))

public TreeNode? BuildTree(int[] preorder, int[] inorder)
{
    var pos = new Dictionary<int, int>();
    for (int i = 0; i < inorder.Length; i++) pos[inorder[i]] = i;
    int next = 0;                                  // shared preorder pointer
    TreeNode? Build(int lo, int hi)                // subtree of inorder[lo..hi)
    {
        if (lo == hi) return null;
        int val = preorder[next++];
        var node = new TreeNode(val);
        node.left = Build(lo, pos[val]);           // left first: preorder order
        node.right = Build(pos[val] + 1, hi);
        return node;
    }
    return Build(0, inorder.Length);
}

O(n) time with the value → index map; calling inorder.index(val) instead makes it O(n²) on a path-shaped tree. The depth equals the tree height, so a degenerate tree with n = 3000 needs the recursion limit raised in Python. The same split works for inorder + postorder: consume postorder from the end and build the right subtree first.

5 · Different Ways to Add Parentheses Medium

Given "2*3-4*5", return the results of every way to fully parenthesise it: [-34, -14, -10, -10, 10].

Smaller copy: whichever operator is evaluated last splits the expression into a left part and a right part, and each part is the same problem on a shorter string. For every operator: get all results on the left, all on the right, and combine every pair. Memoize on the substring bounds, because the same sub-expressions appear under many splits.

Solution: split at every operator, memoize by bounds

from functools import cache

def diffWaysToCompute(expression: str) -> list[int]:
    @cache
    def ways(lo: int, hi: int) -> tuple[int, ...]:    # expression[lo:hi]
        res = []
        for i in range(lo, hi):
            op = expression[i]
            if op in "+-*":
                for a in ways(lo, i):
                    for b in ways(i + 1, hi):
                        res.append(a + b if op == "+" else a - b if op == "-" else a * b)
        if not res:                                   # no operator: a number
            res.append(int(expression[lo:hi]))
        return tuple(res)                             # immutable: safe to cache
    return list(ways(0, len(expression)))

public IList<int> DiffWaysToCompute(string expression)
{
    var memo = new Dictionary<(int, int), List<int>>();
    List<int> Ways(int lo, int hi)                    // expression[lo..hi)
    {
        if (memo.TryGetValue((lo, hi), out var hit)) return hit;
        var res = new List<int>();
        for (int i = lo; i < hi; i++)
        {
            char op = expression[i];
            if (op != '+' && op != '-' && op != '*') continue;
            foreach (int a in Ways(lo, i))
                foreach (int b in Ways(i + 1, hi))
                    res.Add(op == '+' ? a + b : op == '-' ? a - b : a * b);
        }
        if (res.Count == 0) res.Add(int.Parse(expression.AsSpan(lo, hi - lo)));
        return memo[(lo, hi)] = res;
    }
    return Ways(0, expression.Length);
}

There are O(n²) distinct (lo, hi) states, and the work is dominated by the size of the output, which is Catalan in the number of operators. The same "pick the last operation" split solves Unique Binary Search Trees II (pick the root) and Burst Balloons (pick the last balloon).

6 · Strobogrammatic Number III Hard

Count the numbers in [low, high] (strings of up to 15 digits) that look the same when rotated 180°. The digits map as 0→0, 1→1, 6→9, 8→8, 9→6.

Smaller copy: a strobogrammatic number of length L is a valid outer pair wrapped around a strobogrammatic middle of length L − 2. Fill the string from both ends inward: positions i and j get a pair, then recurse on (i+1, j−1). Two base cases: i > j (complete) and i == j (a single middle digit, which must map to itself: 0, 1 or 8). Generate every length between len(low) and len(high), and compare as strings only when the length equals a bound's length.

Solution: build from the outside in

def strobogrammaticInRange(low: str, high: str) -> int:
    pairs = [("0", "0"), ("1", "1"), ("6", "9"), ("8", "8"), ("9", "6")]
    count = 0

    def fill(buf: list[str], i: int, j: int) -> None:
        nonlocal count
        L = len(buf)
        if i > j:                                  # every position filled
            s = "".join(buf)
            if (L == len(low) and s < low) or (L == len(high) and s > high):
                return
            count += 1
            return
        for a, b in pairs:
            if i == 0 and a == "0" and L > 1:      # no leading zero
                continue
            if i == j and a != b:                  # middle: 0, 1 or 8
                continue
            buf[i], buf[j] = a, b
            fill(buf, i + 1, j - 1)

    for L in range(len(low), len(high) + 1):
        fill([""] * L, 0, L - 1)
    return count

public int StrobogrammaticInRange(string low, string high)
{
    var pairs = new (char a, char b)[] { ('0', '0'), ('1', '1'), ('6', '9'), ('8', '8'), ('9', '6') };
    int count = 0;
    void Fill(char[] buf, int i, int j)
    {
        int L = buf.Length;
        if (i > j)
        {
            var s = new string(buf);
            if (L == low.Length && string.CompareOrdinal(s, low) < 0) return;
            if (L == high.Length && string.CompareOrdinal(s, high) > 0) return;
            count++;
            return;
        }
        foreach (var (a, b) in pairs)
        {
            if (i == 0 && a == '0' && L > 1) continue;     // no leading zero
            if (i == j && a != b) continue;                // middle: 0, 1 or 8
            buf[i] = a; buf[j] = b;
            Fill(buf, i + 1, j - 1);
        }
    }
    for (int L = low.Length; L <= high.Length; L++) Fill(new char[L], 0, L - 1);
    return count;
}

Equal-length digit strings compare correctly as strings, which is why the check only runs when L matches a bound's length. Length 15 has 4 · 5⁶ · 3 = 187,500 candidates, so generating everything is fast. The recursion depth is only L/2. Strobogrammatic Number II is the same generator returning the strings.

7 · Count of Smaller Numbers After Self Hard

For each nums[i], count the elements to its right that are strictly smaller. With n up to 10⁵, the O(n²) double loop is too slow.

Smaller copy: merge sort the indices by value. During a merge, the left half's items were originally to the left of the right half's items. When a left item is placed, every right item already placed is smaller and was originally to its right. Add that count (j - mid) to the left item's answer. Each level of the recursion adds the cross-half counts, and the halves handle themselves. Replay the merge sort visualizer with this in mind: its inversion counter is exactly the sum of these answers.

Solution: merge sort on indices, count right-side jumps

def countSmaller(nums: list[int]) -> list[int]:
    n = len(nums)
    res, idx = [0] * n, list(range(n))

    def sort(lo: int, hi: int) -> None:           # sorts idx[lo:hi] by value
        if hi - lo <= 1:
            return
        mid = (lo + hi) // 2
        sort(lo, mid)
        sort(mid, hi)
        merged, j = [], mid
        for i in range(lo, mid):
            while j < hi and nums[idx[j]] < nums[idx[i]]:
                merged.append(idx[j])              # smaller right item jumps ahead
                j += 1
            res[idx[i]] += j - mid                 # all of them were to my right
            merged.append(idx[i])
        merged.extend(idx[j:hi])
        idx[lo:hi] = merged

    sort(0, n)
    return res

public IList<int> CountSmaller(int[] nums)
{
    int n = nums.Length;
    var res = new int[n];
    var idx = Enumerable.Range(0, n).ToArray();
    var tmp = new int[n];
    void Sort(int lo, int hi)                          // sorts idx[lo..hi)
    {
        if (hi - lo <= 1) return;
        int mid = (lo + hi) / 2;
        Sort(lo, mid);
        Sort(mid, hi);
        int j = mid, k = lo;
        for (int i = lo; i < mid; i++)
        {
            while (j < hi && nums[idx[j]] < nums[idx[i]]) tmp[k++] = idx[j++];
            res[idx[i]] += j - mid;                    // right items that jumped ahead
            tmp[k++] = idx[i];
        }
        while (j < hi) tmp[k++] = idx[j++];
        Array.Copy(tmp, lo, idx, lo, hi - lo);
    }
    Sort(0, n);
    return res;
}

O(n log n) time, O(n) extra space and O(log n) depth, so it is safe for n = 10⁵. Ties are not counted because the comparison is strict. The same merge-and-count idea solves Reverse Pairs (count a[i] > 2·a[j] with a separate two-pointer pass before merging) and Count of Range Sum (on prefix sums).

Self-check

Plain recursive fib(n) makes about 1.6ⁿ calls. How much stack space does it use?

O(n). Only the frames on the current root-to-leaf path are alive at once, and the longest path is fib(n) → fib(n−1) → … → fib(1): n frames. Calls measure time and depth measures space; they are different numbers. Step through fib in the call-stack visualizer and watch the depth counter.

What does this cost? def rev(s): return "" if not s else rev(s[1:]) + s[0]

O(n²) time and O(n²) total allocation. There are n calls, but each s[1:] copies up to n characters, and each + builds a new string. The work per call is O(n), not O(1). Pass an index (or reverse a list in place) to get O(n). Recursion cost is always calls × work per call, and slicing hides the work.

Compare return f(n // 2) * f(n // 2) with h = f(n // 2); return h * h for computing a power.

The first makes two identical calls per level: T(n) = 2T(n/2) + O(1) = O(n) calls, which throws away the whole point of halving. The second makes one call per level: T(n) = T(n/2) + O(1) = O(log n). When the two branches are identical, call once and reuse the result. When they differ but overlap, memoize.

You add @cache to a recursive function that appends to a shared path list and reads len(path). The answers become wrong. Why?

The result depends on path, which is not an argument, so two calls with the same arguments can legitimately return different values, and the cache returns whichever came first. A memo is valid only for a pure function of its arguments. Put every value that affects the answer into the arguments (that set is the DP state), or do not memoize. Generate-all backtracking with a shared path is usually not memoizable for this reason.

Your recursive tree DFS passes random tests but crashes on a test with n = 10⁵. What is the likely input, and what are two fixes?

A degenerate tree (every node has only one child) has depth n = 10⁵: far beyond CPython's 1,000-frame default and risky for the 1 MB .NET stack, where an overflow kills the process. Fixes: (1) rewrite it with an explicit stack (preorder, inorder or postorder with (node, seen) frames); (2) in Python, raise sys.setrecursionlimit and run the work in a threading.Thread started after threading.stack_size(...) has been raised. In C#, you can likewise start a Thread with a larger maxStackSize. Option 1 is the robust one.

Is return 1 + count(node.next) a tail call? Would it matter in C#?

No. The 1 + still has to run after the call returns, so the frame must stay. The accumulator form return count(node.next, acc + 1) is a tail call, but neither Python nor C# guarantees eliminating it, so both versions use O(n) stack. Treat tail recursion as a stepping stone: once the state is (node, acc), write while node: acc += 1; node = node.next.

A recursive "count the ways" function returns 0 for its base case remaining == 0, and every answer comes out as 0. What is wrong?

Reaching remaining == 0 means you found one complete way, so it must return 1. Ways are counted by adding the leaves that return 1; if every leaf returns 0, every sum is 0. Ask "how many ways are there to do nothing more?": exactly one. Return 0 only for dead ends (overshooting, out of bounds). The same care applies to minimum problems (an impossible branch returns +∞, not 0).
