The Problem-Solving Playbook

A visual decision map from input size, shape and question type to the right technique, plus a repeatable interview/contest workflow.

Beginner → Expert~60 min studyUpdated 2026-11-03

The one idea

The constraints choose the algorithm. Read n first: it tells you the slowest complexity that still fits. Then the shape of the input and the question being asked narrow that budget to two or three patterns. You recognise the problem before you solve it.

Most "hard" problems are a known pattern in disguise. This page is the map that every other topic hangs on. It covers three filters (size, shape and question), a list of phrases that give the pattern away, a fixed workflow for when you are stuck, and a practice loop that makes recognition automatic. Each pattern then has its own page: two pointers, sliding window, prefix sums, binary search and the rest. If Big-O notation is rusty, read Complexity Analysis alongside this page.

The solving workflow

Use the same seven steps every time, in an interview, a contest or a hard practice problem. The order matters. Most failed attempts skip step 3 and try to jump straight to the clever solution.

1 · UNDERSTANDRestate it

Inputs, output, constraints. What exactly is returned? Read n and the value ranges.

2 · EXAMPLESWork 2–3 by hand

One normal, one tiny, one nasty. Solve them on paper before any code.

3 · BRUTE FORCESay the slow version

Try everything. State its complexity. It is your correctness oracle.

4 · BOTTLENECKFind the repeated work

Which inner loop asks the same question over and over?

5 · OPTIMISEAnswer it faster

Hash map, prefix sum, heap, sort, monotonic stack, memo. Check against the budget.

6 · CODEWrite it cleanly

Name variables by meaning; state the loop invariant in a comment.

7 · TESTEdge cases

Empty, one item, duplicates, negatives, no answer, overflow. Trace one by hand.

Steps 1–2: understand, then make examples

Restate the problem in one sentence of your own, including what is returned: a count, an index, the item itself, or a boolean. Then copy down the constraints: n, the value range, and whether values can be negative, repeated or unsorted. These numbers drive every decision that follows. Work the examples by hand. The steps you take on paper are often the algorithm, written slowly.

Steps 3–5: brute force, bottleneck, optimise

The brute force is not a waste of time. It proves you understand the problem. It gives you a checker for random tests. Most importantly, it shows where the time goes. Almost every optimisation removes one specific kind of repeated work:

The repeated work (bottleneck) The tool that removes it Typical gain
Summing a range again and again Prefix sums O(n) → O(1) per query
Searching for a partner or complement Hash map / set O(n) → O(1)
Linear search in sorted data, or a monotone yes/no Binary search O(n) → O(log n)
Re-scanning for the min/max of a sliding range Monotonic deque O(k) → O(1) amortized
Scanning ahead for the next greater/smaller item Monotonic stack O(n²) → O(n) total
Repeatedly taking the smallest/largest of a changing set Heap O(n) → O(log n)
Restarting a window from scratch Sliding window / two pointers O(n²) → O(n)
Solving the same subproblem again Memoization / DP exponential → polynomial
Range queries with updates Fenwick / segment tree O(n) → O(log n)
"Are these two connected?" asked many times Union-find O(n) → ~O(1)

Step through both versions of Subarray Sum Equals K below. Watch the operation counter: the brute force adds once per subarray, while the optimised version does one lookup per element.

Steps 6–7: code, then try to break it

Write the optimised version with names that carry meaning (need, seen, lo, hi), not a, b, c. Put the invariant in one comment, for example # window [lo, hi] has no repeated character. Then test on purpose. Run the edge-case checklist below, and trace your smallest example through the code line by line. If you wrote the brute force, compare the two on random small inputs (stress test template). That catches almost every remaining bug.

Tip: narrate in interviews Say each step out loud: "Brute force is O(n²), which is 10¹⁰ at this size, so too slow. The inner loop is searching for a complement, so a hash map makes it O(n)." Interviewers score the reasoning, and the narration keeps you on the workflow.

The workflow on a clock

In a 45-minute interview the steps get a rough budget. The exact numbers matter less than two rules: do not code before you can state the algorithm and its complexity, and leave time to test.

Minutes Step What to say or produce Warning sign
0–5 Understand, examples Restate the problem; ask about n, value ranges, duplicates, empty input; walk through one example Coding in the first 3 minutes
5–10 Brute force "Try every pair: O(n²), about 10¹⁰ at n = 10⁵, too slow." Skipping it, then having no fallback
10–18 Bottleneck, optimise Name the repeated work and the structure that removes it; state the new complexity Hoping a pattern fits without checking its precondition
18–35 Code Clear names, the invariant as a comment, helper functions for side tasks Long silences: narrate what each block does
35–45 Test Trace the smallest example; run the edge-case checklist aloud; fix the bugs you find Saying "I think it works" without a trace

If you are still stuck at minute 15, say so and code the brute force cleanly. A correct O(n²) with a clear explanation of the bottleneck beats an unfinished O(n). Interviewers often give a hint once you have shown exactly where the time goes.

Size → feasible complexity

A typical judge runs about 10⁸ simple operations per second in compiled languages (C++, C#, Java, Go) and about 10⁷ in Python. Problem setters choose n so that the intended solution just fits. So n tells you, almost exactly, which complexity they have in mind:

Type any n into the calculator below, choose the language speed, and step through the classes. Each one is costed against the budget. The last frame names the slowest class that fits, which is usually the intended one.

Insight: n is a hint, and so is the value range A big value range, like nums[i] ≤ 10⁹ with n ≤ 10⁵, means you cannot index an array by value. Use a hash map, sort and compress, or binary search over values (about 30 halvings). A small value range, like 0 ≤ nums[i] ≤ 100 or an amount ≤ 10⁴, invites counting arrays or a DP dimension indexed by value.

Same problem, three sizes

The size filter is the strongest of the three. The clearest way to see that is to keep the problem fixed and change only n. Take Longest Increasing Subsequence: return the length of the longest strictly increasing subsequence (not necessarily contiguous) of an array.

The bottleneck in the O(n²) DP is the inner question: "among earlier values smaller than x, which one ends the longest run?". The fast version replaces it with a sorted list, tails, where tails[k] is the smallest value that can end an increasing run of length k + 1. Each new x either extends the longest run (append) or improves one tail (replace the first tail ≥ x). That is a single binary search.

from bisect import bisect_left

def lis_quadratic(nums: list[int]) -> int:          # n ≤ ~3,000
    dp = [1] * len(nums)                            # dp[i]: longest ending at i
    for i in range(len(nums)):
        for j in range(i):
            if nums[j] < nums[i]:
                dp[i] = max(dp[i], dp[j] + 1)
    return max(dp, default=0)

def lis_fast(nums: list[int]) -> int:               # n ≤ ~10⁶
    tails = []                                      # sorted, strictly increasing
    for x in nums:
        k = bisect_left(tails, x)                   # first tail ≥ x
        if k == len(tails):
            tails.append(x)                         # x extends the longest run
        else:
            tails[k] = x                            # same length, smaller end
    return len(tails)

public static int LisQuadratic(int[] nums)          // n ≤ ~10,000
{
    var dp = new int[nums.Length];
    int best = 0;
    for (int i = 0; i < nums.Length; i++)
    {
        dp[i] = 1;
        for (int j = 0; j < i; j++)
            if (nums[j] < nums[i]) dp[i] = Math.Max(dp[i], dp[j] + 1);
        best = Math.Max(best, dp[i]);
    }
    return best;
}

public static int LisFast(int[] nums)               // n ≤ ~10⁷
{
    var tails = new List<int>();                    // sorted, strictly increasing
    foreach (int x in nums)
    {
        int k = tails.BinarySearch(x);
        if (k < 0) k = ~k;                          // not found: insertion point
        if (k == tails.Count) tails.Add(x);         // x extends the longest run
        else tails[k] = x;                          // same length, smaller end
    }
    return tails.Count;
}

tails is not itself an increasing subsequence of the input; only its length is meaningful. bisect_left (first tail ≥ x) gives strictly increasing runs, while bisect_right would allow equal values (non-decreasing). C#'s BinarySearch returns any match when x is present, which is fine here because the values in tails are distinct. The same staircase applies to many problems: pairs with a property (n² → sort + two pointers), subarray sums (n² → prefix sums + hash map), and range queries (n·q → prefix sums or a Fenwick tree).

Question type → technique

The third filter is the verb in the question. "Count", "minimise", "does it exist", "list all" and "shortest" each have their own families of techniques:

The question asks… Reach for Why it fits
Count the ways / how many DP, prefix sums + hash map, combinatorics Counts add up over disjoint cases. "Modulo 10⁹+7" almost always means DP.
Minimise / maximise a value DP, greedy, binary search on the answer, heap Optimal substructure gives DP. A safe local choice gives greedy. A monotone "can we do it with X?" check gives binary search.
Does one exist? / is it possible? Hash set, BFS/DFS, union-find, boolean DP Reachability and membership. Stop at the first witness.
List every solution Backtracking The output itself is exponential, so prune early: choose, explore, un-choose.
k-th smallest / top k Heap of size k, quickselect, binary search on the value Do not sort everything. Keep only k items, or count how many are ≤ x.
Shortest path / fewest steps BFS (unit edges), Dijkstra / 0-1 BFS (weights) BFS visits nodes in order of distance. Dijkstra does the same when edges have weights.
Longest / shortest contiguous part Sliding window, prefix sums + hash map "Contiguous" means a window or a difference of prefixes.
Order with dependencies Topological sort "a before b" is a directed edge. A valid order exists only if there is no cycle.
Many range queries / updates Prefix sums (static), Fenwick / segment tree (dynamic) Precompute once, then answer each query in O(1) or O(log n).
Next greater / smaller element Monotonic stack Each element waits on the stack until its answer arrives.

Pitfall: signals are hints, not proofs "Subarray" suggests a sliding window, but a sliding window needs monotonicity: growing the window must only ever push the quantity one way. With negative numbers that breaks, and you need prefix sums instead. Always check the pattern's precondition (sorted? non-negative? acyclic? weights ≥ 0?) before committing.

When you are stuck: ten reframing moves

Sometimes no signal fires. Then change the question rather than staring at it. Each move below turns an unfamiliar problem into one that has a known pattern. Go down the list and ask "does this apply?":

# Move Ask yourself Classic example
1 Sort it Does the order of the input matter to the answer? If not, sorting may expose structure. 3Sum, Merge Intervals, Meeting Rooms (two pointers, intervals)
2 Fix one thing If I fix one index, value or endpoint, is the rest easy? 3Sum fixes i, then two pointers; "subarray ending at j" fixes the right end
3 Turn it around Is the complement or the reverse problem easier? Count the bad ones, run time backwards, start from the target. Bricks Falling (add bricks back with union-find), Rotting Oranges from every rotten cell
4 Guess the answer Can I check a candidate answer quickly, and does feasibility change only once? Koko, Split Array Largest Sum (binary search on the answer)
5 Count contributions Instead of looping over every subarray or pair, how much does each element contribute to the total? Sum of Subarray Minimums (worked problem 5 below)
6 Think about the last step What is the last choice in an optimal solution? What is left once it is made? Coin Change, House Robber, Burst Balloons (DP)
7 Make it a graph Are there states and moves between them? Then "fewest moves" is BFS. Word Ladder, Open the Lock (graphs)
8 Precompute Is the same range, prefix or lookup asked again and again? Range sums, Product Except Self (prefix sums)
9 Solve a smaller version Solve n = 1, 2, 3 by hand. Can the answer for n be built from n − 1? Climbing Stairs, Gray Code, K-th Symbol (recursion)
10 Relax a constraint Drop one rule (allow repeats, ignore one dimension) and solve that. Then add the rule back. Russian Doll Envelopes: sort by width, then LIS on the heights

Insight: write the brute force, then ask "what does it recompute?" Most moves come from looking at the brute force rather than the problem. Two nested loops over (i, j) suggest fixing one end (move 2) or counting contributions (move 5). A loop over candidate answers suggests binary search (move 4). Recursion that revisits the same arguments suggests memoisation (move 6). The brute force is a map of the waste.

Worked problems

Each problem runs the full workflow: signals → brute force → bottleneck → the insight → code. Try each one before opening the solution.

1 · Subarray Sum Equals K Medium

Count the contiguous subarrays that sum to k; values can be negative and n ≤ 2·10⁴.

Signals: "contiguous subarrays", "sum equals k", "negative". Brute force: O(n²) over all (i, j). Bottleneck: for each end j, searching for starts i. Insight: sum(i..j) = pre[j+1] − pre[i], so count earlier prefixes equal to pre − k. You already watched it in the visualizer above.

Solution: prefix sums + hash map, O(n) time, O(n) space 
from collections import defaultdict

def subarray_sum(nums: list[int], k: int) -> int:
    seen = defaultdict(int)
    seen[0] = 1                      # the empty prefix: subarrays starting at 0
    count = pre = 0
    for x in nums:
        pre += x
        count += seen[pre - k]       # earlier prefixes that leave exactly k
        seen[pre] += 1
    return count

public int SubarraySum(int[] nums, int k)
{
    var seen = new Dictionary<int, int> { [0] = 1 };   // the empty prefix
    int count = 0, pre = 0;
    foreach (int x in nums)
    {
        pre += x;
        if (seen.TryGetValue(pre - k, out int c)) count += c;
        seen[pre] = seen.GetValueOrDefault(pre) + 1;
    }
    return count;
}

Update seen[pre] after the lookup. Otherwise, when k = 0, the current prefix pairs with itself and counts an empty subarray.

2 · Longest Substring Without Repeating Characters Medium

Return the length of the longest substring with all distinct characters (n ≤ 5·10⁴).

Signals: "longest substring" plus a validity rule. Brute force: check every substring, O(n²) or O(n³). Bottleneck: restarting from every left end. Insight: once s[lo..hi] has no repeats, the next valid window never starts before lo, so lo only moves forward. Remember each character's last index and jump lo past a repeat.

Solution: variable sliding window, O(n) time, O(alphabet) space 
def length_of_longest_substring(s: str) -> int:
    last = {}                         # char -> last index seen
    best = lo = 0
    for hi, ch in enumerate(s):
        if last.get(ch, -1) >= lo:    # repeat inside the window
            lo = last[ch] + 1         # jump past it
        last[ch] = hi
        best = max(best, hi - lo + 1)
    return best

public int LengthOfLongestSubstring(string s)
{
    var last = new Dictionary<char, int>();
    int best = 0, lo = 0;
    for (int hi = 0; hi < s.Length; hi++)
    {
        if (last.TryGetValue(s[hi], out int p) && p >= lo) lo = p + 1;
        last[s[hi]] = hi;
        best = Math.Max(best, hi - lo + 1);
    }
    return best;
}

The >= lo check matters. A character last seen before the window, as in "abba" when the second a arrives, must not drag lo backwards.

3 · Koko Eating Bananas Medium

Find the minimum integer eating speed that finishes all piles within h hours (pile sizes up to 10⁹).

Signals: "minimum speed", "within h hours", a huge answer range. Brute force: try speeds 1, 2, 3, …, up to 10⁹ checks. Bottleneck: trying every candidate answer. Insight: feasibility is monotone: if speed s works, s + 1 works too. So binary search the first speed that works, with about 30 checks of O(n) each.

Solution: binary search on the answer, O(n log max) time, O(1) space 
def min_eating_speed(piles: list[int], h: int) -> int:
    def hours(speed: int) -> int:
        return sum((p + speed - 1) // speed for p in piles)   # ceil division

    lo, hi = 1, max(piles)            # max(piles) always works
    while lo < hi:                    # find the first speed that works
        mid = (lo + hi) // 2
        if hours(mid) <= h:
            hi = mid                  # works: answer is mid or smaller
        else:
            lo = mid + 1              # too slow: answer is bigger
    return lo

public int MinEatingSpeed(int[] piles, int h)
{
    int lo = 1, hi = piles.Max();
    while (lo < hi)
    {
        int mid = lo + (hi - lo) / 2;
        long hours = 0;                                  // can exceed int
        foreach (int p in piles) hours += (p + (long)mid - 1) / mid;
        if (hours <= h) hi = mid; else lo = mid + 1;
    }
    return lo;
}

4 · Course Schedule Medium

Given n courses and prerequisite pairs [a, b] (b before a), decide whether all courses can be finished.

Signals: "prerequisite", "before", "finish all". Model: a directed graph. Insight: every course can be taken exactly when the graph has no cycle. Kahn's algorithm repeatedly takes a course with no remaining prerequisites. If it takes all n, there was no cycle.

Solution: topological sort (Kahn), O(V + E) time and space 
from collections import deque

def can_finish(n: int, prerequisites: list[list[int]]) -> bool:
    adj = [[] for _ in range(n)]
    indeg = [0] * n
    for a, b in prerequisites:        # b must come before a
        adj[b].append(a)
        indeg[a] += 1
    q = deque(i for i in range(n) if indeg[i] == 0)
    taken = 0
    while q:
        u = q.popleft()
        taken += 1
        for v in adj[u]:
            indeg[v] -= 1
            if indeg[v] == 0:         # all its prerequisites are done
                q.append(v)
    return taken == n                 # leftovers sit on a cycle

public bool CanFinish(int n, int[][] prerequisites)
{
    var adj = new List<int>[n];
    for (int i = 0; i < n; i++) adj[i] = new List<int>();
    var indeg = new int[n];
    foreach (var p in prerequisites) { adj[p[1]].Add(p[0]); indeg[p[0]]++; }

    var q = new Queue<int>();
    for (int i = 0; i < n; i++) if (indeg[i] == 0) q.Enqueue(i);
    int taken = 0;
    while (q.Count > 0)
    {
        int u = q.Dequeue(); taken++;
        foreach (int v in adj[u]) if (--indeg[v] == 0) q.Enqueue(v);
    }
    return taken == n;
}

5 · Sum of Subarray Minimums Medium

Return the sum of min(sub) over every contiguous subarray, modulo 10⁹ + 7 (n ≤ 3·10⁴).

Signals: "every subarray", a sum over all of them, and n too big for n² in Python (9·10⁸). Brute force: for each start, extend to the right while keeping a running minimum: O(n²). Bottleneck: the same minimum is added again and again for overlapping subarrays. Insight: count contributions (move 5 above). arr[m] is the minimum of every subarray that starts after the previous smaller value and ends before the next smaller-or-equal value. Those walls come from a monotonic stack: when a value is popped, the value that pops it is its right wall and the value beneath it is its left wall.

Solution: contribution counting with a monotonic stack, O(n) time, O(n) space 
def sum_subarray_mins(arr: list[int]) -> int:
    MOD = 10**9 + 7
    n = len(arr)
    stack = []                                  # indices, values increasing
    total = 0
    for i in range(n + 1):
        cur = arr[i] if i < n else float("-inf")    # sentinel flushes the stack
        while stack and arr[stack[-1]] >= cur:  # i is m's right wall
            m = stack.pop()
            left = stack[-1] if stack else -1   # previous strictly smaller
            total += arr[m] * (m - left) * (i - m)
        stack.append(i)
    return total % MOD

public int SumSubarrayMins(int[] arr)
{
    const long MOD = 1_000_000_007;
    int n = arr.Length;
    var stack = new Stack<int>();                   // indices, values increasing
    long total = 0;
    for (int i = 0; i <= n; i++)
    {
        long cur = i < n ? arr[i] : long.MinValue;  // sentinel flushes the stack
        while (stack.Count > 0 && arr[stack.Peek()] >= cur)
        {
            int m = stack.Pop();                    // i is m's right wall
            int left = stack.Count > 0 ? stack.Peek() : -1;
            total = (total + (long)arr[m] * (m - left) * (i - m)) % MOD;
        }
        stack.Push(i);
    }
    return (int)total;
}

Ties need care. Use a strict wall on one side and a non-strict wall on the other, so a subarray whose minimum appears twice is counted exactly once (here the rightmost copy owns it: the equal value to its left is not a wall, while the equal value to its right is). Making both walls strict double-counts, and making both non-strict misses those subarrays. The same contribution-plus-monotonic-stack shape solves Largest Rectangle in Histogram and Sum of Subarray Ranges. See Monotonic stack & queue.

6 · Sliding Window Maximum Hard

Return the maximum of every window of size k (n ≤ 10⁵).

Signals: "every window of size k", "maximum". Brute force: O(n·k), up to 10¹⁰. Bottleneck: re-scanning each window for its max. Insight: an element that is smaller than a newer element can never be a window maximum again, so throw it away. A deque holding indices with decreasing values keeps the current max at its front.

Solution: monotonic deque, O(n) time, O(k) space 
from collections import deque

def max_sliding_window(nums: list[int], k: int) -> list[int]:
    dq, out = deque(), []             # indices; nums[dq] strictly decreasing
    for i, x in enumerate(nums):
        while dq and nums[dq[-1]] <= x:
            dq.pop()                  # dominated: can never be a max again
        dq.append(i)
        if dq[0] <= i - k:
            dq.popleft()              # front slid out of the window
        if i >= k - 1:
            out.append(nums[dq[0]])
    return out

public int[] MaxSlidingWindow(int[] nums, int k)
{
    var dq = new LinkedList<int>();               // indices, values decreasing
    var res = new int[nums.Length - k + 1];
    for (int i = 0; i < nums.Length; i++)
    {
        while (dq.Count > 0 && nums[dq.Last!.Value] <= nums[i]) dq.RemoveLast();
        dq.AddLast(i);
        if (dq.First!.Value <= i - k) dq.RemoveFirst();
        if (i >= k - 1) res[i - k + 1] = nums[dq.First.Value];
    }
    return res;
}

Each index is pushed once and popped at most once, so the total work is O(n) even though there is a loop inside a loop.

7 · Split Array Largest Sum Hard

Split nums (non-negative) into k contiguous parts and minimise the largest part's sum.

Signals: "minimise the largest", "k parts". DP over (index, parts) works in O(k·n²). Insight: ask the yes/no question instead: "can we split so that every part is ≤ cap?" Greedy answers it in O(n): extend the current part until it would overflow. The answer is monotone in cap, so binary search over [max, sum].

Solution: binary search on the answer + greedy check, O(n log sum) 
def split_array(nums: list[int], k: int) -> int:
    def pieces(cap: int) -> int:      # fewest parts if no part may exceed cap
        count, cur = 1, 0
        for x in nums:
            if cur + x > cap:
                count, cur = count + 1, 0
            cur += x
        return count

    lo, hi = max(nums), sum(nums)
    while lo < hi:
        mid = (lo + hi) // 2
        if pieces(mid) <= k:
            hi = mid                  # feasible: try a smaller cap
        else:
            lo = mid + 1
    return lo

public int SplitArray(int[] nums, int k)
{
    long lo = nums.Max(), hi = nums.Sum(x => (long)x);
    while (lo < hi)
    {
        long mid = lo + (hi - lo) / 2;
        if (Pieces(nums, mid) <= k) hi = mid; else lo = mid + 1;
    }
    return (int)lo;
}

static int Pieces(int[] nums, long cap)
{
    int count = 1; long cur = 0;
    foreach (int x in nums)
    {
        if (cur + x > cap) { count++; cur = 0; }
        cur += x;
    }
    return count;
}

Why is "≤ k parts" enough when the problem needs exactly k? Any split into fewer parts can be cut further without making the largest part bigger, because n ≥ k.

8 · Shortest Path Visiting All Nodes Expert

In an undirected graph with n ≤ 12 nodes, find the length of the shortest walk that visits every node. You may start anywhere and revisit nodes and edges.

Signals: "n ≤ 12" means exponential state; "shortest" with unit edges means BFS; "visits every node" means the state must remember which nodes are done. Insight: run BFS over states (node, visited-mask). There are n·2ⁿ ≈ 49,000 states. Start from every node at once (multi-source), and the first state whose mask is full is the answer.

Solution: BFS over (node, mask), O(2ⁿ · n²) time, O(2ⁿ · n) space 
from collections import deque

def shortest_path_length(graph: list[list[int]]) -> int:
    n = len(graph)
    full = (1 << n) - 1
    q = deque((i, 1 << i) for i in range(n))     # start everywhere
    seen = set(q)
    steps = 0
    while q:
        for _ in range(len(q)):                   # one BFS layer
            u, mask = q.popleft()
            if mask == full:
                return steps
            for v in graph[u]:
                state = (v, mask | (1 << v))
                if state not in seen:
                    seen.add(state)
                    q.append(state)
        steps += 1
    return 0

public int ShortestPathLength(int[][] graph)
{
    int n = graph.Length, full = (1 << n) - 1;
    var seen = new bool[n, 1 << n];
    var q = new Queue<(int node, int mask)>();
    for (int i = 0; i < n; i++) { q.Enqueue((i, 1 << i)); seen[i, 1 << i] = true; }

    for (int steps = 0; q.Count > 0; steps++)
    {
        for (int size = q.Count; size > 0; size--)
        {
            var (u, mask) = q.Dequeue();
            if (mask == full) return steps;
            foreach (int v in graph[u])
            {
                int next = mask | (1 << v);
                if (!seen[v, next]) { seen[v, next] = true; q.Enqueue((v, next)); }
            }
        }
    }
    return 0;
}

The general lesson: when the plain graph is too small to hold the answer, add what you must remember to the state, then run the usual algorithm on the bigger graph.

Template: stress test against the brute force

When the stakes are high, keep the brute force and let the computer look for the counterexample. Generate thousands of tiny random inputs (n ≤ 8, values in −3..3, so that duplicates, zeros and negatives are common) and check that the fast and slow versions agree. When they disagree, the failing input is already small enough to trace by hand. Every solution on this page was checked this way.

import random

def stress(fast, slow, gen, trials: int = 3000, seed: int = 1):
    """Compare two solutions on random small inputs; return the first mismatch."""
    random.seed(seed)                              # fixed seed: failures replay
    for _ in range(trials):
        args = gen()
        got, want = fast(*args), slow(*args)
        if got != want:
            print(f"MISMATCH {args}: fast={got} slow={want}")
            return args
    print(f"OK: {trials} random cases agree")
    return None

def gen_subarray_sum():
    n = random.randint(0, 8)                       # tiny: easy to trace by hand
    nums = [random.randint(-3, 3) for _ in range(n)]
    return nums, random.randint(-4, 4)

def slow_subarray_sum(nums, k):                    # obviously correct, O(n³)
    return sum(sum(nums[i:j]) == k
               for i in range(len(nums)) for j in range(i + 1, len(nums) + 1))

# stress(subarray_sum, slow_subarray_sum, gen_subarray_sum)

static int[]? Stress(Func<int[], int, int> fast, Func<int[], int, int> slow,
                     int trials = 3000, int seed = 1)
{
    var rng = new Random(seed);                    // fixed seed: failures replay
    for (int t = 0; t < trials; t++)
    {
        int n = rng.Next(0, 9);                    // tiny: easy to trace by hand
        var nums = new int[n];
        for (int i = 0; i < n; i++) nums[i] = rng.Next(-3, 4);
        int k = rng.Next(-4, 5);
        int got = fast(nums, k), want = slow(nums, k);
        if (got != want)
        {
            Console.WriteLine($"MISMATCH [{string.Join(",", nums)}] k={k}: fast={got} slow={want}");
            return nums;
        }
    }
    Console.WriteLine($"OK: {trials} random cases agree");
    return null;
}

Three habits make stress tests effective:

  • Keep inputs tiny and values narrow. Most bugs live in duplicates, zeros, empty inputs and equal neighbours, and a narrow value range produces them constantly. Large random inputs mostly test the easy path.
  • Make the slow version obviously correct, even if it is O(n³) or exponential. Its only job is to be right. If it shares code or ideas with the fast version, it can share the bug too.
  • Compare the right thing. If several answers are valid (any index, any order), compare a canonical form (sorted output, the value at the index) or check the answer's properties instead of exact equality.

Recognition is a memory skill, so practise it the way memory works best: retrieve, space it out, mix it up. Reading solutions feels productive, but recognition only becomes automatic when you have to produce the answer yourself.

Self-check

n ≤ 10⁵ and your idea is O(n²). Is it worth coding?

No. (10⁵)² = 10¹⁰ operations, about 100 seconds in C# and far longer in Python. The constraint is telling you to look for O(n log n) or O(n). Find the inner loop (the bottleneck) and ask which structure answers its question faster.

Why does a sliding window fail for "subarray sum equals k" when values can be negative?

A sliding window shrinks from the left when the sum is "too big", assuming that adding elements only increases the sum and removing them only decreases it. With negative values that monotonicity is gone: a too-big window can become valid by growing. Use prefix sums with a hash map, which make no monotonicity assumption.

A problem has n ≤ 20. What does that suggest, and why?

Exponential is allowed: 2²⁰ ≈ 10⁶, and even 2²⁰ · 20 ≈ 2·10⁷ fits. Think subsets as bitmasks, bitmask DP, or backtracking with pruning. For n ≤ 40, think meet in the middle (2 × 2²⁰). The setter picked a small n on purpose, because a polynomial solution probably does not exist.

The answer is "the minimum X such that the condition holds" and X can be up to 10⁹. What is the move?

Check whether feasibility is monotone: if X works, does every larger X work? If yes, binary search over X, which takes about 30 iterations, and write a feasible(X) check that is usually greedy and O(n). Total O(n log range).

When can you trust a greedy choice instead of DP?

When you can argue that some optimal solution makes the greedy choice. This is the exchange argument: swapping any other choice for the greedy one never makes things worse. If you cannot argue it, brute-force tiny inputs and compare. Coin change with coins {1, 3, 4} and amount 6 breaks greedy (4+1+1 instead of 3+3), so it needs DP.

The problem says "return the answer modulo 10⁹+7". What does that tell you?

The true answer is astronomically large, so it is almost certainly a count. That points to DP or combinatorics, not enumeration. It also tells you to apply % MOD after every addition or multiplication, and in C# to multiply in long.

You have been stuck for 20 minutes. What do you do?

Go back to the workflow. (1) Write the brute force, even if it is slow. (2) Name its bottleneck in words. (3) Look the bottleneck up in the bottleneck table and the signal table. (4) Solve a smaller or special case: sorted input, n = 2, or only non-negative values. (5) Still stuck? Read only the key insight, close it, write the code yourself, and schedule a re-solve.

A problem asks for a total over all O(n²) subarrays, with n ≤ 10⁵. Which reframing move fits, and what does it need?

Count contributions (move 5). For each element, count the subarrays in which it is the one that matters (the minimum, the maximum, the first occurrence), multiply its value by that count, and sum. You need the boundaries of each element's region, which usually come from a monotonic stack or a prefix count, so the total drops from O(n²) to O(n) or O(n log n).
