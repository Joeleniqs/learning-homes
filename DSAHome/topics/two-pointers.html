Two Pointers

Opposite-end, same-direction and fast/slow pointers: why moving one pointer is safe, with partitioning and k-sum.

Beginner → Advanced~50 min studyBuilds on: Complexity AnalysisUpdated 2026-11-03

What it is and when you need it

Two pointers is the art of searching a space of pairs (or triples, or "keep/skip" decisions) without enumerating it. You keep two indices into a sequence and, at every step, move exactly one of them. The brute force looks at O(n²) pairs; two pointers looks at O(n), because each move throws away a whole family of candidates at once.

The invariant. A pointer may only move past an element after you have proved that element cannot take part in any better answer. Every correct two-pointer algorithm is that proof, repeated n times.

It comes in three families. You already know the cost model from Complexity Analysis; here is the shape of each family.

Brute force: O(n²)

Test every pair (i, j). Easy to write, and correct. Too slow past about 10⁴ elements, and it ignores the structure (sortedness, order) you were handed.

Hash set: O(n) time, O(n) space

Great for unsorted pair-sum ("Two Sum I") where you must return original indices. Useless for "closest", "max area", "count pairs ≤ x", and in-place rewrites.

Two pointers: O(n) time, O(1) space

Needs a monotone structure: sorted values, a fixed order to preserve, or a functional graph. In exchange it answers ordering questions (closest, maximum, count) that hashing cannot.

Intuition: you are walking a staircase through the pair matrix

Write every pair of a sorted array as a matrix: row i, column j, cell = a[i] + a[j] (only j > i matters). Because the array is sorted, every row increases to the right and every column increases downward. That single fact is the whole algorithm.

Start at the top-right cell, the smallest plus the largest. If the sum is too small, every other cell in that row is to the left, so it is even smaller: the entire row is dead, so move down (lo++). If the sum is too big, every other cell in that column is below, so it is even bigger: the entire column is dead, so move left (hi--). Each test kills a full line of the matrix, so after at most n − 1 tests nothing is left.

Drive it yourself. Try a target that does not exist: the staircase still ends after at most n − 1 tests, having proved there is no answer.

Insight Two pointers is not "a trick for sorted arrays". It is pruning by monotonicity. Whenever the answer space is a matrix whose rows and columns are monotone in the quantity you compare, a single corner-to-corner walk visits O(n) cells and certifies the rest. Container With Most Water, Trapping Rain Water and "count pairs below x" are the same walk with a different "which line is dead?" rule.

Opposite ends

The template: pair with a target sum

The loop condition is lo < hi because a pair needs two different indices. Each branch is justified by one row or one column of the matrix above.

def pair_with_sum(a: list[int], target: int) -> tuple[int, int] | None:
    """a is sorted ascending. O(n) time, O(1) space."""
    lo, hi = 0, len(a) - 1
    while lo < hi:
        s = a[lo] + a[hi]
        if s == target:
            return lo, hi
        if s < target:
            lo += 1        # a[lo] + (anything left of hi) < target: row lo is dead
        else:
            hi -= 1        # a[hi] + (anything right of lo) > target: column hi is dead
    return None

public static (int Lo, int Hi)? PairWithSum(int[] a, int target)
{
    // a is sorted ascending. O(n) time, O(1) space.
    int lo = 0, hi = a.Length - 1;
    while (lo < hi)
    {
        long s = (long)a[lo] + a[hi];          // long: two ints can overflow
        if (s == target) return (lo, hi);
        if (s < target) lo++;                  // row lo is dead
        else hi--;                             // column hi is dead
    }
    return null;
}

If the input is not sorted, sorting costs O(n log n) and destroys the original indices. When the problem wants indices (LeetCode "Two Sum" I), use a hash map instead; when it wants values, counts, or "closest", sort and walk.

Counting pairs: add a whole row at once

When the question is "how many pairs have a[i] + a[j] < target?", the matrix view tells you more than "dead or alive": if a[lo] + a[hi] < target, then every cell in row lo up to hi is also below target. You can count hi − lo pairs in one step.

def count_pairs_below(a: list[int], target: int) -> int:
    """Pairs i < j with a[i] + a[j] < target; a sorted. O(n)."""
    lo, hi, count = 0, len(a) - 1, 0
    while lo < hi:
        if a[lo] + a[hi] < target:
            count += hi - lo   # a[lo] works with every index in (lo, hi]
            lo += 1
        else:
            hi -= 1            # a[hi] fails even with the smallest partner
    return count

public static long CountPairsBelow(int[] a, long target)
{
    int lo = 0, hi = a.Length - 1;
    long count = 0;
    while (lo < hi)
    {
        if ((long)a[lo] + a[hi] < target) { count += hi - lo; lo++; }
        else hi--;
    }
    return count;
}

Counting pairs in a range [L, U] is then countBelow(U + 1) − countBelow(L): the same "exactly = at most − at most" subtraction you will meet again in Sliding Window.

Container with most water: a different "dead line" rule

Lines of height h[i] stand at positions i; pick two that hold the most water, (j − i) · min(h[i], h[j]). Nothing is sorted here, yet two pointers still works, because the proof only needs the shorter wall.

k-Sum: fix one, two-pointer the rest

3Sum is "for each anchor a[i], find pairs in the suffix summing to target − a[i]". Sorting turns that inner search into the O(n) walk above, so 3Sum is O(n²) and k-Sum is O(n^(k−1)). Sorting also makes duplicates adjacent, which is how you avoid emitting the same triplet twice without a hash set:

  • Anchor: skip a[i] if it equals a[i − 1]. Compare backward: the previous anchor already produced every triplet that starts with this value.
  • After a hit: move both pointers (keeping either one would force the other to the same value), then skip further copies of the values just used.

The same idea generalizes to any k: recurse on the anchor until two numbers remain, then walk. The start index start is what keeps tuples in non-decreasing index order (no permutations of the same tuple).

def k_sum(nums: list[int], target: int, k: int) -> list[list[int]]:
    """All unique k-tuples (by value) summing to target. O(n^(k-1)) after sorting."""
    nums = sorted(nums)

    def two_sum(start: int, t: int) -> list[list[int]]:
        out, lo, hi = [], start, len(nums) - 1
        while lo < hi:
            s = nums[lo] + nums[hi]
            if s < t or (lo > start and nums[lo] == nums[lo - 1]):
                lo += 1                      # too small, or a value we already paired
            elif s > t or (hi < len(nums) - 1 and nums[hi] == nums[hi + 1]):
                hi -= 1
            else:
                out.append([nums[lo], nums[hi]])
                lo += 1
                hi -= 1
        return out

    def rec(start: int, t: int, k: int) -> list[list[int]]:
        if k == 2:
            return two_sum(start, t)
        out = []
        for i in range(start, len(nums) - k + 1):
            if i > start and nums[i] == nums[i - 1]:
                continue                     # same anchor value: same answers
            for rest in rec(i + 1, t - nums[i], k - 1):
                out.append([nums[i]] + rest)
        return out

    return rec(0, target, k)

public static IList<IList<int>> KSum(int[] input, long target, int k)
{
    int[] nums = (int[])input.Clone();
    Array.Sort(nums);
    return Rec(0, target, k);

    IList<IList<int>> Rec(int start, long t, int k)
    {
        var res = new List<IList<int>>();
        if (k == 2)
        {
            int lo = start, hi = nums.Length - 1;
            while (lo < hi)
            {
                long s = (long)nums[lo] + nums[hi];        // long: 4Sum overflows int
                if (s < t || (lo > start && nums[lo] == nums[lo - 1])) lo++;
                else if (s > t || (hi < nums.Length - 1 && nums[hi] == nums[hi + 1])) hi--;
                else res.Add(new List<int> { nums[lo++], nums[hi--] });
            }
            return res;
        }
        for (int i = start; i < nums.Length - k + 1; i++)
        {
            if (i > start && nums[i] == nums[i - 1]) continue;
            foreach (var rest in Rec(i + 1, t - nums[i], k - 1))
            {
                var tuple = new List<int> { nums[i] };
                tuple.AddRange(rest);
                res.Add(tuple);
            }
        }
        return res;
    }
}

The duplicate check must look backward. if nums[i] == nums[i + 1]: continue looks forward and skips the first copy, so [-1, -1, 2] is never found: the first -1 is skipped, and the second -1 has only [2] to its right. Compare with the previous element and only when i > start.

Same direction: a reader and a writer

Here both pointers start at the left and move right. r (read) visits every element once; w (write) marks the end of the answer built so far. The invariant splits the array into three regions:

The keep predicate is the only thing that changes between problems. Switch modes in the visualizer: "keep at most two copies" compares with a[w − 2] (the last two kept values, not the last two read values), and "move zeroes" swaps instead of copying so the zeroes travel to the back.

def keep_at_most_k(a: list[int], k: int) -> int:
    """a sorted. Keep each value at most k times, in place. Returns new length."""
    w = 0
    for r in range(len(a)):
        if w < k or a[r] != a[w - k]:   # compare with the k-th last KEPT value
            a[w] = a[r]
            w += 1
    return w


def move_zeroes(a: list[int]) -> None:
    """Stable for the non-zeros; zeroes end up at the back. In place."""
    w = 0
    for r in range(len(a)):
        if a[r] != 0:
            a[w], a[r] = a[r], a[w]
            w += 1

public static int KeepAtMostK(int[] a, int k)
{
    int w = 0;
    for (int r = 0; r < a.Length; r++)
        if (w < k || a[r] != a[w - k])     // compare with the k-th last KEPT value
            a[w++] = a[r];
    return w;
}

public static void MoveZeroes(int[] a)
{
    int w = 0;
    for (int r = 0; r < a.Length; r++)
        if (a[r] != 0)
        {
            (a[w], a[r]) = (a[r], a[w]);
            w++;
        }
}

Two sequences walked in lockstep are the same family: is s a subsequence of t? advances i in s only on a match and j in t always. Backspace String Compare walks both strings from the right, skipping characters cancelled by #, in O(1) extra space.

Partitioning: the Dutch national flag

Sorting an array of 0s, 1s and 2s (or "less than / equal to / greater than a pivot") in one pass needs three pointers that maintain four regions. This is also the 3-way partition that keeps quicksort fast on many duplicates (see Sorting Algorithms).

def three_way_partition(a: list[int], p: int) -> tuple[int, int]:
    """Rearranges a into  < p | == p | > p.  Returns (lo, hi) bounds of the == block."""
    lo, mid, hi = 0, 0, len(a) - 1
    while mid <= hi:                      # [mid, hi] is the unknown region
        if a[mid] < p:
            a[lo], a[mid] = a[mid], a[lo]
            lo += 1
            mid += 1
        elif a[mid] > p:
            a[mid], a[hi] = a[hi], a[mid]
            hi -= 1                       # do not advance mid: new a[mid] is unseen
        else:
            mid += 1
    return lo, hi

public static (int Lo, int Hi) ThreeWayPartition(int[] a, int p)
{
    int lo = 0, mid = 0, hi = a.Length - 1;
    while (mid <= hi)                         // [mid, hi] is the unknown region
    {
        if (a[mid] < p) { (a[lo], a[mid]) = (a[mid], a[lo]); lo++; mid++; }
        else if (a[mid] > p) { (a[mid], a[hi]) = (a[hi], a[mid]); hi--; }
        else mid++;
    }
    return (lo, hi);
}

Here the condition is mid <= hi, not <: when mid == hi there is still one unclassified cell.

Fast and slow pointers on an array

Treat an array whose values are valid indices as a linked list: from index i go to nums[i]. Every node has exactly one outgoing edge, so a walk from any start must eventually repeat, tracing a "ρ" (rho): a tail of length μ that leads into a cycle of length λ. Floyd's tortoise-and-hare finds where the tail enters the cycle with two pointers and O(1) memory. The same algorithm on real linked lists is in Linked Lists.

Find the Duplicate Number (n + 1 values, each in 1..n, exactly one value repeated) is exactly this: no value is 0, so nothing points back to index 0 and the walk from 0 has a real tail. The repeated value d is the node that two indices point to, one from the tail and one from inside the cycle, so d is the cycle entrance.

def find_duplicate(nums: list[int]) -> int:
    """n + 1 values in 1..n. O(n) time, O(1) space, nums not modified."""
    slow = fast = 0
    while True:                    # do-while: both start equal at 0
        slow = nums[slow]
        fast = nums[nums[fast]]
        if slow == fast:
            break
    slow2 = 0
    while slow != slow2:
        slow, slow2 = nums[slow], nums[slow2]
    return slow

public static int FindDuplicate(int[] nums)
{
    int slow = 0, fast = 0;
    do
    {
        slow = nums[slow];
        fast = nums[nums[fast]];
    } while (slow != fast);          // do-while: both start equal at 0
    int slow2 = 0;
    while (slow != slow2)
    {
        slow = nums[slow];
        slow2 = nums[slow2];
    }
    return slow;
}

Merging two sorted arrays from the back

nums1 holds m sorted values followed by n empty slots; merge nums2 (n sorted values) into it in place. Writing from the front overwrites nums1 values you have not read yet. Writing from the back is always safe, because the back is the free space.

def merge_into(nums1: list[int], m: int, nums2: list[int], n: int) -> None:
    """nums1 has length m + n; its last n cells are free. O(m + n), O(1) extra."""
    i, j, w = m - 1, n - 1, m + n - 1
    while j >= 0:
        if i >= 0 and nums1[i] > nums2[j]:
            nums1[w] = nums1[i]
            i -= 1
        else:
            nums1[w] = nums2[j]
            j -= 1
        w -= 1

public static void MergeInto(int[] nums1, int m, int[] nums2, int n)
{
    int i = m - 1, j = n - 1, w = m + n - 1;
    while (j >= 0)
    {
        if (i >= 0 && nums1[i] > nums2[j]) nums1[w--] = nums1[i--];
        else nums1[w--] = nums2[j--];
    }
}

The same trick, "the largest result goes last, and you know where last is", solves Squares of a Sorted Array: the largest square is at one of the two ends, so fill the output from the back with opposite-end pointers.

Trapping rain water: deciding one side early

Water above bar i is min(maxLeft(i), maxRight(i)) − h[i]. The prefix/suffix-max solution needs two O(n) arrays. Two pointers needs none, because of one lemma:

Lemma. The pointer that moves is always the shorter one, so the taller of h[lo] and h[hi] is the tallest bar seen so far on either side. If h[lo] < h[hi], the true right maximum of lo is at least h[hi] ≥ lmax, so min(lmax, maxRight) = lmax is already known: settle lo now.

Step through it and watch the dashed lmax/rmax lines: the pointer on the lower side settles its bar immediately, because the other side is guaranteed to have a wall at least as tall.

def trap(h: list[int]) -> int:
    """O(n) time, O(1) space."""
    lo, hi = 0, len(h) - 1
    lmax = rmax = water = 0
    while lo < hi:
        if h[lo] < h[hi]:          # h[hi] >= every bar seen, so the left side decides
            lmax = max(lmax, h[lo])
            water += lmax - h[lo]
            lo += 1
        else:                      # h[lo] >= every bar seen, so the right side decides
            rmax = max(rmax, h[hi])
            water += rmax - h[hi]
            hi -= 1
    return water

public static int Trap(int[] h)
{
    int lo = 0, hi = h.Length - 1, lmax = 0, rmax = 0, water = 0;
    while (lo < hi)
    {
        if (h[lo] < h[hi])
        {
            lmax = Math.Max(lmax, h[lo]);
            water += lmax - h[lo++];
        }
        else
        {
            rmax = Math.Max(rmax, h[hi]);
            water += rmax - h[hi--];
        }
    }
    return water;
}

Recognize it when

  • The input is sorted, or the answer does not depend on the original order, so you may sort.
  • You need a pair or triple with a sum, difference or product condition, or you need the closest, the best, or a count.
  • The problem says in place or O(1) extra space and asks you to remove, compact, partition or merge.
  • The answer is set by the smaller of two sides (water, area, a min/max pair).
  • Values are indices into the same array (1..n in an array of n + 1): think linked list, then think Floyd.
  • A brute force that scans j for every i has an inner loop whose start only moves forward. That monotonicity is the whole requirement, and it also leads into Sliding Window.

When it does not work

  • Unsorted input where you need indices. Sorting loses them. Use a hash map (Hashing Patterns), or sort (value, index) pairs.
  • No monotone structure. If moving a pointer can make the quantity go either way, no row or column is ever provably dead. Example: pair sum with a non-monotone f(a[i], a[j]).
  • Many independent queries. For "does a pair with sum t exist?" over 10⁵ different t, rerunning the O(n) walk costs O(nq). Precompute instead.

Pitfall: lo <= hi versus lo < hi A pair needs two different indices, so pair problems use lo < hi. With <=, a = [5], target 10 "finds" 5 + 5. Use <= only when one element alone is a valid answer: "min + max ≤ target" over subsequences counts the single element [x] when 2x ≤ target, and the Dutch flag must still classify the cell at mid == hi.

Pitfall: advancing mid after swapping with hi The value that arrives at mid from hi has never been inspected. With pivot 1, [1, 2, 0]: the 2 at mid = 1 is swapped with the 0 at hi, giving [1, 0, 2]; advancing mid skips that 0, the loop ends, and a 0 is left after a 1. Only the lo swap may advance mid, because what comes from lo is known to equal the pivot.

Pitfall: overflow in k-Sum (C#, Java, C++) 4Sum with values near ±10⁹ sums four ints; nums[a] + nums[b] + nums[c] + nums[d] silently wraps in int. Compute in long ((long)nums[a] + …) and keep target − nums[i] in long too, as the template does.

Pitfall: Floyd that never starts slow = fast = 0; while slow != fast: … exits immediately because they start equal. Use a do-while (C#) or while True … break (Python), or take the first step before the loop.

Pitfall: merging from the front Writing nums1[0] first destroys an unread nums1 value whenever nums2[0] is smaller. Fill from the back, and loop on j >= 0: once nums2 is exhausted, the rest of nums1 is already in place.

Pitfall: "keep at most two" compared with the wrong neighbour if a[r] != a[r - 2] compares with the read history, which has already been overwritten. [1,1,1,2,2,3] then returns [1,1,2,3]: by the time r = 4 looks at a[2], that cell already holds a written 2, so the second 2 is dropped. Compare with the written answer: a[w − 2].

Worked problems

1. 3Sum

All unique triplets summing to 0. Insight: sort, then each anchor is a pair-sum walk on its suffix; duplicates are adjacent, so skip them by comparing with the previous value. The visualizer above runs exactly this. Extra pruning: once nums[i] > 0, every remaining triple is positive.

Solution: O(n²) time, O(1) extra (besides output and sort) 
def three_sum(nums: list[int]) -> list[list[int]]:
    nums.sort()
    n, res = len(nums), []
    for i in range(n - 2):
        if nums[i] > 0:
            break                                  # smallest of the triple is positive
        if i > 0 and nums[i] == nums[i - 1]:
            continue                               # same anchor value, same triples
        lo, hi = i + 1, n - 1
        while lo < hi:
            s = nums[i] + nums[lo] + nums[hi]
            if s < 0:
                lo += 1
            elif s > 0:
                hi -= 1
            else:
                res.append([nums[i], nums[lo], nums[hi]])
                lo += 1
                hi -= 1
                while lo < hi and nums[lo] == nums[lo - 1]:
                    lo += 1
                while lo < hi and nums[hi] == nums[hi + 1]:
                    hi -= 1
    return res

public static IList<IList<int>> ThreeSum(int[] nums)
{
    Array.Sort(nums);
    var res = new List<IList<int>>();
    int n = nums.Length;
    for (int i = 0; i < n - 2; i++)
    {
        if (nums[i] > 0) break;
        if (i > 0 && nums[i] == nums[i - 1]) continue;
        int lo = i + 1, hi = n - 1;
        while (lo < hi)
        {
            int s = nums[i] + nums[lo] + nums[hi];
            if (s < 0) lo++;
            else if (s > 0) hi--;
            else
            {
                res.Add(new List<int> { nums[i], nums[lo], nums[hi] });
                lo++; hi--;
                while (lo < hi && nums[lo] == nums[lo - 1]) lo++;
                while (lo < hi && nums[hi] == nums[hi + 1]) hi--;
            }
        }
    }
    return res;
}

2. Container With Most Water

Maximize (j − i) · min(h[i], h[j]). Insight: the shorter wall's every other partner is narrower and no taller-limited, so its row is dead (the figure in the opposite-ends section). Ties: move either; both walls are then capped by the same height.

Solution: O(n) time, O(1) space 
def max_area(h: list[int]) -> int:
    lo, hi, best = 0, len(h) - 1, 0
    while lo < hi:
        best = max(best, (hi - lo) * min(h[lo], h[hi]))
        if h[lo] < h[hi]:
            lo += 1
        else:
            hi -= 1
    return best

public static int MaxArea(int[] h)
{
    int lo = 0, hi = h.Length - 1, best = 0;
    while (lo < hi)
    {
        best = Math.Max(best, (hi - lo) * Math.Min(h[lo], h[hi]));
        if (h[lo] < h[hi]) lo++; else hi--;
    }
    return best;
}

3. Number of Subsequences That Satisfy the Given Sum Condition

Count non-empty subsequences whose min + max ≤ target (mod 10⁹ + 7). Insight: a subsequence only cares about its min and max, so order is irrelevant: sort. Fix the minimum at lo; if a[lo] + a[hi] ≤ target, every element in (lo, hi] may be in or out freely, giving 2^(hi − lo) subsequences in one step. That is the counting walk from earlier, with 2^k instead of k. Loop on lo <= hi, because [a[lo]] alone is valid when 2·a[lo] ≤ target.

Solution: O(n log n) time, O(n) space 
def num_subseq(nums: list[int], target: int) -> int:
    MOD = 10**9 + 7
    nums.sort()
    n = len(nums)
    pow2 = [1] * n
    for i in range(1, n):
        pow2[i] = pow2[i - 1] * 2 % MOD
    lo, hi, ans = 0, n - 1, 0
    while lo <= hi:
        if nums[lo] + nums[hi] <= target:
            ans = (ans + pow2[hi - lo]) % MOD   # a[lo] is the min; (lo, hi] free
            lo += 1
        else:
            hi -= 1                             # a[hi] too big even for the smallest min
    return ans

public static int NumSubseq(int[] nums, int target)
{
    const int Mod = 1_000_000_007;
    Array.Sort(nums);
    int n = nums.Length;
    var pow2 = new int[n];
    pow2[0] = 1;
    for (int i = 1; i < n; i++) pow2[i] = (int)(pow2[i - 1] * 2L % Mod);
    int lo = 0, hi = n - 1;
    long ans = 0;
    while (lo <= hi)
    {
        if (nums[lo] + nums[hi] <= target) { ans = (ans + pow2[hi - lo]) % Mod; lo++; }
        else hi--;
    }
    return (int)ans;
}

4. Shortest Subarray to be Removed to Make Array Sorted

Remove one contiguous subarray so the rest is non-decreasing; minimise its length. Insight: what remains is a sorted prefix a[0..i] glued to a sorted suffix a[j..] with a[i] ≤ a[j]. As i grows, a[i] grows, so the smallest valid j only moves right: same-direction pointers over two monotone pieces.

Solution: O(n) time, O(1) space 
def find_length_of_shortest_subarray(a: list[int]) -> int:
    n = len(a)
    r = n - 1
    while r > 0 and a[r - 1] <= a[r]:
        r -= 1                       # a[r:] is the longest sorted suffix
    if r == 0:
        return 0                     # already sorted
    ans = r                          # keep only the suffix
    j = r
    for i in range(n):
        if i > 0 and a[i] < a[i - 1]:
            break                    # prefix stopped being sorted
        while j < n and a[j] < a[i]:
            j += 1                   # smallest suffix start that can follow a[i]
        ans = min(ans, j - i - 1)
    return ans

public static int FindLengthOfShortestSubarray(int[] a)
{
    int n = a.Length, r = n - 1;
    while (r > 0 && a[r - 1] <= a[r]) r--;
    if (r == 0) return 0;
    int ans = r, j = r;
    for (int i = 0; i < n; i++)
    {
        if (i > 0 && a[i] < a[i - 1]) break;
        while (j < n && a[j] < a[i]) j++;
        ans = Math.Min(ans, j - i - 1);
    }
    return ans;
}

6. Find K-th Smallest Pair Distance

Return the k-th smallest |a[i] − a[j]| over all pairs. Insight: n² distances are too many to list, but "how many pairs have distance ≤ d?" is a same-direction two-pointer count in O(n) on the sorted array, and that count grows with d. So binary search on d for the smallest value whose count is at least k. Two pointers become the feasibility check inside binary search on the answer.

Solution: O(n log n + n log W) time, where W = max − min 
def smallest_distance_pair(nums: list[int], k: int) -> int:
    nums.sort()

    def pairs_within(d: int) -> int:
        count, l = 0, 0
        for r in range(len(nums)):
            while nums[r] - nums[l] > d:
                l += 1                  # l only moves right as r grows
            count += r - l              # pairs (l..r-1, r)
        return count

    lo, hi = 0, nums[-1] - nums[0]
    while lo < hi:
        mid = (lo + hi) // 2
        if pairs_within(mid) >= k:
            hi = mid
        else:
            lo = mid + 1
    return lo

public static int SmallestDistancePair(int[] nums, int k)
{
    Array.Sort(nums);
    int lo = 0, hi = nums[^1] - nums[0];
    while (lo < hi)
    {
        int mid = lo + (hi - lo) / 2;
        if (PairsWithin(mid) >= k) hi = mid; else lo = mid + 1;
    }
    return lo;

    long PairsWithin(int d)
    {
        long count = 0;
        for (int r = 0, l = 0; r < nums.Length; r++)
        {
            while (nums[r] - nums[l] > d) l++;
            count += r - l;
        }
        return count;
    }
}

Self-check

In Container With Most Water, why is moving the taller wall never useful?

The water level is capped by the shorter wall, which stays. Moving the taller wall inward shrinks the width and can raise the level at most up to the short wall's height, so the area can only fall. The short wall, in contrast, has already met its best possible partner, the farthest one.

Two Sum I gives an unsorted array and asks for the original indices. Is two pointers a good fit?

Not directly. Sorting costs O(n log n) and scrambles the indices, so you would have to sort (value, index) pairs. A hash map of value → index answers in one O(n) pass. Two pointers wins when you need values, counts, closest sums or O(1) space.

Dutch flag: why may mid advance after the swap with lo but not after the swap with hi?

Everything in [lo, mid) is known to equal the pivot, so the value swapped into mid from lo is already classified (or lo == mid, the same cell). The value swapped in from hi comes from the unknown region and must still be inspected.

Find the Duplicate: why must the walk start at index 0?

All values are in 1..n, so no edge points to node 0: it has in-degree 0 and cannot be on the cycle. Starting there guarantees a real tail whose end is the cycle entrance, the node with two incoming edges, which is the duplicate. Starting inside the cycle would give an "entrance" that is just the start node.

How do you count pairs with L ≤ a[i] + a[j] ≤ U in O(n log n)?

Sort, then count(sum ≤ U) − count(sum ≤ L − 1), each computed with the counting walk (count += hi − lo; lo++ when the pair fits, else hi--). Counting "at most" is monotone and easy; "between" is a difference of two "at most"s.

Trapping water: h[lo] == h[hi]. Which pointer do you move, and why is it safe?

Either. Both are the tallest seen so far on their side, so each side's running max is at most the other pointer's height. Whichever you settle, its water runningMax − h is exact. The template moves hi on ties.

What single property must a problem have for "move one pointer" to be correct?

Monotonicity that makes a whole family of candidates provably useless after one comparison: sorted values (rows and columns of the pair matrix are monotone), a "limited by the smaller side" objective, or a writer that can never overtake the reader. No such proof means no two-pointer algorithm.
