Where this page fits

The DP Framework gave you a five-step recipe: state, transition, base cases, order, answer. This page applies that recipe about twenty times to the two most common DP shapes:

  • 1D DP: the state is one index into a sequence (houses, digits, days, array positions).
  • Grid DP: the state is one cell of a grid or triangle.

A few problems need a little extra in the state: "do I hold a stock right now?" or "where is the second walker?". Those are still 1D or grid DPs with a small tag attached, and they appear at the end of each part.

In 1D and grid DP the state is a position, and every cell reads a fixed pattern of nearby cells (its stencil). Draw the stencil before writing code. It gives you the recurrence, the loop direction, and how much memory you really need.

1D DP over prefixes

The prefix question

Most 1D problems give you a sequence a[0..n-1] and ask for something about the whole sequence. The standard state is

dp[i] = the answer for the first i items a[0..i-1].

The table has n + 1 cells, and dp[0] is the empty prefix. Paying for one extra cell buys you a base case that is almost always obvious (0 loot, 1 way, True) and a loop with no special cases.

Three different 1D states. Say which one you mean.

  • First i items (dp[i] covers a[:i]): House Robber, Decode Ways, Word Break. Answer dp[n].
  • Ending exactly at i (the run must use a[i]): Kadane, LIS. Answer max(dp), because the best run can end anywhere.
  • Starting at i (dp[i] covers a[i:]): Jump Game, many "from here to the end" problems. Fill right to left, answer dp[0].

Off-by-one bugs in 1D DP almost always come from mixing two of these in one solution.

To find the transition, ask the framework's question: what is the last decision? For a prefix, the last decision is about the last item (or the last piece). The table is then the bookkeeping for that one decision.

House Robber: take or skip

LeetCode 198 Medium. Houses in a row hold nums[i] cash. You cannot rob two adjacent houses. Maximize the loot.

1 · STATEdp[i]

Best loot using only the first i houses.

2 · TRANSITIONLast house i−1: skip or rob

Skip: dp[i−1]. Rob: house i−2 is forbidden, so dp[i−2] + nums[i−1]. Take the max.

3 · BASEdp[0] = 0, dp[1] = nums[0]

No houses, no cash. One house: rob it.

4 · ORDERi = 2 … n

Each cell reads the two cells on its left.

5 · ANSWERdp[n]

Walk back to list the robbed houses.

Step through it. Above each new cell you see two arcs: skip from dp[i-1] and +cash from dp[i-2]. The green one wins. In the final frame, the walk back marks the houses that were robbed: wherever dp[i] ≠ dp[i-1], house i-1 was taken.

def rob(nums: list[int]) -> int:
    n = len(nums)
    dp = [0] * (n + 1)                   # dp[i] = best loot from the first i houses
    if n:
        dp[1] = nums[0]
    for i in range(2, n + 1):
        dp[i] = max(dp[i - 1],                  # skip house i-1
                    dp[i - 2] + nums[i - 1])    # rob it, so house i-2 is skipped
    return dp[n]


def rob_two_vars(nums: list[int]) -> int:
    prev2 = prev1 = 0                    # dp[i-2] and dp[i-1]: all the stencil reads
    for x in nums:
        prev2, prev1 = prev1, max(prev1, prev2 + x)
    return prev1


def rob_circle(nums: list[int]) -> int:   # LeetCode 213
    if len(nums) == 1:
        return nums[0]
    return max(rob_two_vars(nums[:-1]),   # never rob the last house
               rob_two_vars(nums[1:]))    # never rob the first house

public static int Rob(int[] nums)
{
    int n = nums.Length;
    var dp = new int[n + 1];                    // dp[i] = best loot from the first i houses
    if (n > 0) dp[1] = nums[0];
    for (int i = 2; i <= n; i++)
        dp[i] = Math.Max(dp[i - 1],             // skip house i-1
                         dp[i - 2] + nums[i - 1]); // rob it, so house i-2 is skipped
    return dp[n];
}

static int RobRange(int[] nums, int lo, int hi)  // rob nums[lo..hi] with two variables
{
    int prev2 = 0, prev1 = 0;
    for (int i = lo; i <= hi; i++)
        (prev2, prev1) = (prev1, Math.Max(prev1, prev2 + nums[i]));
    return prev1;
}

public static int RobCircle(int[] nums)          // LeetCode 213
{
    if (nums.Length == 1) return nums[0];
    return Math.Max(RobRange(nums, 0, nums.Length - 2),  // never rob the last house
                    RobRange(nums, 1, nums.Length - 1)); // never rob the first house
}

House Robber II (LeetCode 213) puts the houses in a circle, so the first and last are neighbours. You do not need a new DP. Every valid plan leaves house 0 or house n−1 unrobbed, so solve two straight lines and keep the better one. Switch the visualizer to circle to watch both passes.

Insight When a constraint wraps around (a circle) or links two far-apart choices, split into cases that each remove the link, solve each with the ordinary DP, and combine. The same trick fixes "first and last item interact" in many problems, for example Maximum Sum Circular Subarray (918).

Decode Ways: counting with validity checks

LeetCode 91 Medium. A = 1, …, Z = 26. Count the ways to split a digit string into letters. "226" → "BZ", "VF", "BBF" → 3.

The last decision is the last letter. It used either the last digit alone or the last two digits. These two cases never produce the same decoding, so in a counting DP you add them. Each case has a validity check:

  • One digit: valid if it is not '0' (there is no letter 0).
  • Two digits: valid if they form 10…26. "05" is not a letter, and neither is "27".

Arcs above the table come from the one-digit case and arcs below from the two-digit case. A red arc is an invalid piece that contributes 0. Try 2101, 100 (answer 0), 1111111111 (Fibonacci numbers!) and 27.

def num_decodings(s: str) -> int:
    n = len(s)
    dp = [0] * (n + 1)                   # dp[i] = ways to decode s[:i]
    dp[0] = 1                            # the empty prefix has one (empty) decoding
    for i in range(1, n + 1):
        if s[i - 1] != "0":              # last letter = one digit 1..9
            dp[i] += dp[i - 1]
        if i >= 2 and "10" <= s[i - 2:i] <= "26":   # last letter = two digits 10..26
            dp[i] += dp[i - 2]
    return dp[n]

public static int NumDecodings(string s)
{
    int n = s.Length;
    var dp = new int[n + 1];             // dp[i] = ways to decode s[..i]
    dp[0] = 1;                           // the empty prefix has one (empty) decoding
    for (int i = 1; i <= n; i++)
    {
        if (s[i - 1] != '0') dp[i] += dp[i - 1];            // one digit 1..9
        if (i >= 2 && (s[i - 2] == '1' || (s[i - 2] == '2' && s[i - 1] <= '6')))
            dp[i] += dp[i - 2];                             // two digits 10..26
    }
    return dp[n];
}

Pitfall: comparing two-digit strings "10" <= s[i-2:i] <= "26" works in Python only because both sides have exactly two characters, so string order equals numeric order. Converting with int(s[i-2:i]) and checking 10 <= x <= 26 is safer when you are unsure. Checking x <= 26 alone is a classic bug: "06" becomes 6, but a leading zero is not a letter.

Word Break: look back over every split

LeetCode 139 Medium. Can s be split into words from a dictionary (words may repeat)?

Here the last piece can have any length, so ok[i] looks back at every j < i: "is s[:j] splittable and is s[j:i] a word?" This is a feasibility DP: OR over the options, base case ok[0] = True.

Notice how many j are skipped instantly because ok[j] is False: a bad prefix can never become good. The final frame follows parent pointers (the j that made each cell True) to print one valid split. Try s = aaaaaaab with words a,aa,aaa. Brute-force recursion explodes there, but the DP stays at O(n²) checks.

def word_break(s: str, words: list[str]) -> bool:
    vocab, n = set(words), len(s)
    longest = max(map(len, vocab))       # no word is longer: limits how far back to look
    ok = [False] * (n + 1)               # ok[i]: s[:i] splits into dictionary words
    ok[0] = True
    for i in range(1, n + 1):
        for j in range(max(0, i - longest), i):   # last word = s[j:i]
            if ok[j] and s[j:i] in vocab:
                ok[i] = True
                break
    return ok[n]

public static bool WordBreak(string s, IList<string> words)
{
    var vocab = new HashSet<string>(words);
    int n = s.Length, longest = words.Max(w => w.Length);
    var ok = new bool[n + 1];            // ok[i]: s[..i] splits into dictionary words
    ok[0] = true;
    for (int i = 1; i <= n; i++)
        for (int j = Math.Max(0, i - longest); j < i && !ok[i]; j++)
            ok[i] = ok[j] && vocab.Contains(s[j..i]);   // last word = s[j..i]
    return ok[n];
}

Time O(n · L · L) with L = longest word (L split points, each slice and hash costs O(L)). Word Break II (LeetCode 140) asks for all splits. Keep a list of parents per cell and backtrack through them. The output can be exponential, so the DP only prunes dead ends (cells where ok is False).

Jump Game: when the DP collapses into a greedy

LeetCode 55 Medium: from index i you may jump up to nums[i] steps right. Can you reach the last index? LeetCode 45 Medium: what is the fewest number of jumps?

The honest DP for 55 is a "starting at i" state: good[i] = any(good[j] for j in i+1 .. i+nums[i]). That is O(n²). Now look at the table as it fills right to left. Only the leftmost good index matters: if you can reach any good index, you can reach that one, because it lies inside the same jump range. So the whole table collapses into one variable, last_good.

For 45, dp[i] = fewest jumps to reach i. Indices reachable with k jumps form a contiguous block, so the DP is really a breadth-first search over indices, done one block (layer) at a time. Switch modes to see both.

def can_jump(nums: list[int]) -> bool:
    last_good = len(nums) - 1            # leftmost index known to reach the end
    for i in range(len(nums) - 2, -1, -1):
        if i + nums[i] >= last_good:     # i can land on a good index
            last_good = i
    return last_good == 0


def jump(nums: list[int]) -> int:
    jumps = end = far = 0                # indices <= end are reachable with `jumps` jumps
    for i in range(len(nums) - 1):
        far = max(far, i + nums[i])      # farthest landing spot from this layer
        if i == end:                     # this layer is fully scanned
            jumps, end = jumps + 1, far
    return jumps

public static bool CanJump(int[] nums)
{
    int lastGood = nums.Length - 1;      // leftmost index known to reach the end
    for (int i = nums.Length - 2; i >= 0; i--)
        if (i + nums[i] >= lastGood) lastGood = i;
    return lastGood == 0;
}

public static int Jump(int[] nums)
{
    int jumps = 0, end = 0, far = 0;     // indices <= end are reachable with `jumps` jumps
    for (int i = 0; i < nums.Length - 1; i++)
    {
        far = Math.Max(far, i + nums[i]);
        if (i == end) { jumps++; end = far; }   // this layer is fully scanned
    }
    return jumps;
}

Greedy is a DP whose table you proved you do not need. Write the DP first, watch which cells actually decide the answer, and only then shrink it. That is a much safer path to a greedy solution than guessing one. Jump Game VII and Frog Jump are cases where the full DP is still needed.

1D DP over "ending at i"

Why some problems need "ends exactly here"

Try to write a prefix DP for Maximum Subarray (LeetCode 53): best[i] = largest sum of a contiguous subarray inside a[:i]. What is best[i+1]? Either the best subarray avoids a[i] (that is best[i]), or it ends at a[i]. The prefix state cannot tell you about the second case. "Best anywhere in the prefix" has forgotten whether that subarray touches the right edge, and only a subarray touching the edge can be extended.

So store exactly the missing fact:

cur[i] = the largest sum of a subarray that ends exactly at index i.

A run ending at i either is a[i] alone or extends the best run ending at i−1. That gives the whole of Kadane's algorithm: cur[i] = max(a[i], cur[i−1] + a[i]), and the answer is max(cur), because the best subarray can end anywhere.

If the answer is a contiguous piece (subarray, substring) or a chain whose next element depends on the last one (increasing subsequence), use the state "ends exactly at i" and take the max over all i at the end.

Kadane and its product twin

Maximum Product Subarray (LeetCode 152) looks like the same problem with × instead of +. But a negative number flips the order: the smallest (most negative) product ending at i−1, times a negative a[i], can become the largest. So the state needs two numbers per index:

  • hi[i] = largest product of a subarray ending at i
  • lo[i] = smallest product of a subarray ending at i

Each is the max (or min) of three candidates: a[i] alone, hi[i−1]·a[i], lo[i−1]·a[i]. Run the visualizer in both modes. In product mode, watch the rows swap roles every time a[i] is negative.

def max_subarray(nums: list[int]) -> int:
    cur = best = nums[0]                 # cur = best sum of a run ENDING here
    for x in nums[1:]:
        cur = max(x, cur + x)            # restart at x, or extend the previous run
        best = max(best, cur)            # the answer can end anywhere
    return best


def max_product(nums: list[int]) -> int:
    hi = lo = best = nums[0]             # largest / smallest product ending here
    for x in nums[1:]:
        cands = (x, hi * x, lo * x)      # restart, extend hi, extend lo
        hi, lo = max(cands), min(cands)  # a negative x swaps which one wins
        best = max(best, hi)
    return best

public static int MaxSubArray(int[] nums)
{
    int cur = nums[0], best = nums[0];   // cur = best sum of a run ENDING here
    for (int i = 1; i < nums.Length; i++)
    {
        cur = Math.Max(nums[i], cur + nums[i]);   // restart, or extend
        best = Math.Max(best, cur);
    }
    return best;
}

public static int MaxProduct(int[] nums)
{
    long hi = nums[0], lo = nums[0], best = nums[0];   // largest / smallest product ending here
    for (int i = 1; i < nums.Length; i++)
    {
        long x = nums[i], a = hi * x, b = lo * x;
        hi = Math.Max(x, Math.Max(a, b));
        lo = Math.Min(x, Math.Min(a, b));
        best = Math.Max(best, hi);
    }
    return (int)best;
}

Pitfall: updating hi before computing lo hi = max(x, hi*x, lo*x) followed by lo = min(x, hi*x, lo*x) uses the new hi in the second line, which is a different (wrong) recurrence. Compute both from the old values: use a tuple assignment in Python, or temporaries a, b in C#. This is the same rule as the rolling-array rule in the framework: never overwrite a cell that something later in the same step still reads.

Insight Kadane is a DP with a one-cell stencil, rolled into one variable. Two famous variants follow from the state:

  • Circular max subarray (918): the answer is either a normal run or total − (minimum run), so run Kadane for max and for min.
  • Delete at most one element (1186): add a second state, "ending at i, one deletion used". That is a two-row state machine like the stock problems below.

Longest Increasing Subsequence, O(n²)

LeetCode 300 Medium. Find the length of the longest strictly increasing subsequence (not necessarily contiguous).

The next element of an increasing subsequence must be larger than the last element. So the state must remember where the subsequence ends:

dp[i] = length of the longest increasing subsequence that ends at index i.

The last decision is: which element came just before a[i]? Any j < i with a[j] < a[i] works, so dp[i] = 1 + max(dp[j] for j < i if a[j] < a[i]), or 1 if there is none. This is stencil B (look back at every j), so it costs O(n²).

In the O(n²) mode, the green arc is the best predecessor and the blue arcs are the other smaller values that were considered. Larger (or equal) values get no arc at all: they cannot come before a[i]. The final frame follows the stored predecessor of the best cell to print one LIS.

Longest Increasing Subsequence, O(n log n) with patience sorting

There is a second view of the same problem. Deal the numbers one at a time onto piles, like the card game patience:

  • Put x on the leftmost pile whose top is ≥ x.
  • If no pile qualifies, start a new pile on the right.

The number of piles at the end equals the LIS length. The pile tops (tails: the card placed last on each pile, drawn lowest in the figure) always increase from left to right, so "leftmost top ≥ x" is a binary search (bisect_left), and the whole algorithm is O(n log n).

Switch the visualizer to patience mode to watch the binary search pick each pile.

from bisect import bisect_left


def length_of_lis(nums: list[int]) -> int:
    n = len(nums)
    dp = [1] * n                         # dp[i] = longest increasing run ENDING at i
    for i in range(n):
        for j in range(i):
            if nums[j] < nums[i]:        # nums[i] can follow nums[j]
                dp[i] = max(dp[i], dp[j] + 1)
    return max(dp)


def length_of_lis_fast(nums: list[int]) -> int:
    tails = []                           # tails[k] = smallest end of a run of length k+1
    for x in nums:
        k = bisect_left(tails, x)        # leftmost pile whose top is >= x
        if k == len(tails):
            tails.append(x)              # x extends the longest run: new pile
        else:
            tails[k] = x                 # same length, smaller end: better
    return len(tails)

public static int LengthOfLIS(int[] nums)
{
    int n = nums.Length;
    var dp = new int[n];                 // dp[i] = longest increasing run ENDING at i
    for (int i = 0; i < n; i++)
    {
        dp[i] = 1;
        for (int j = 0; j < i; j++)
            if (nums[j] < nums[i]) dp[i] = Math.Max(dp[i], dp[j] + 1);
    }
    return dp.Max();
}

public static int LengthOfLISFast(int[] nums)
{
    var tails = new List<int>();         // tails[k] = smallest end of a run of length k+1
    foreach (int x in nums)
    {
        int k = tails.BinarySearch(x);
        if (k < 0) k = ~k;               // not found: ~k is the insertion point
        if (k == tails.Count) tails.Add(x);
        else tails[k] = x;
    }
    return tails.Count;
}

Pitfall: strict versus non-decreasing bisect_left gives a strictly increasing LIS: an equal value replaces the existing top instead of starting a new pile. For the longest non-decreasing subsequence, use bisect_right. In C#, List.BinarySearch returns some index of an equal element when there are duplicates. Because tails is strictly increasing here, there is at most one, so it behaves like bisect_left. For the non-decreasing variant, write your own upper-bound search.

tails is not an LIS itself. After [1, 5, 6, 2], tails = [1, 2, 6], but 1, 2, 6 is not a subsequence in order. Only its length is meaningful. To print an actual LIS, store for each element the index of the current top of the pile to its left (the back-pointer arrows in the figure), then follow the pointers from the top of the last pile. LIS variants (Russian dolls, counting LIS, LIS in 2D, minimum deletions) continue in Sequence & String DP.

State-machine DP: the stock problems

One row per state

The six "Best Time to Buy and Sell Stock" problems are one idea with different rules. Each day you are in a state: holding a share, or not holding one (and sometimes "just sold", or "on my second trade"). Draw the states as nodes and the allowed moves as edges. Then

dp[s][i] = the best cash balance at the end of day i, if you end that day in state s.

Buying moves you to hold and costs −price. Selling moves you back and earns +price. Doing nothing keeps you in the same state at no cost. Each cell takes the max over its incoming edges from day i−1. That is the whole method: a state machine plus one DP column per day.

The visualizer has four rule sets. The top shows the machine, with the edge used for the current cell lit up. The table below it has one row per state and one column per day. The last frame walks the winning arrows back to list the actual trades.

def max_profit_unlimited(prices: list[int], fee: int = 0) -> int:   # 122 / 714
    hold, cash = -prices[0], 0           # own a share / own nothing
    for p in prices[1:]:
        hold, cash = max(hold, cash - p), max(cash, hold + p - fee)
    return cash


def max_profit_cooldown(prices: list[int]) -> int:                 # 309
    hold, sold, rest = -prices[0], float("-inf"), 0
    for p in prices[1:]:
        hold, sold, rest = (max(hold, rest - p),    # buy only from rest
                            hold + p,               # sell today
                            max(rest, sold))        # one day after a sale
    return max(sold, rest)


def max_profit_two(prices: list[int]) -> int:                      # 123
    b1 = b2 = -prices[0]
    s1 = s2 = 0
    for p in prices[1:]:
        b1, s1, b2, s2 = (max(b1, -p),              # 1st buy
                          max(s1, b1 + p),          # 1st sale
                          max(b2, s1 - p),          # 2nd buy spends 1st profit
                          max(s2, b2 + p))          # 2nd sale
    return s2

public static int MaxProfitUnlimited(int[] prices, int fee = 0)    // 122 / 714
{
    int hold = -prices[0], cash = 0;     // own a share / own nothing
    for (int i = 1; i < prices.Length; i++)
        (hold, cash) = (Math.Max(hold, cash - prices[i]),
                        Math.Max(cash, hold + prices[i] - fee));
    return cash;
}

public static int MaxProfitCooldown(int[] prices)                  // 309
{
    int hold = -prices[0], sold = int.MinValue / 2, rest = 0;
    for (int i = 1; i < prices.Length; i++)
        (hold, sold, rest) = (Math.Max(hold, rest - prices[i]),   // buy only from rest
                              hold + prices[i],                    // sell today
                              Math.Max(rest, sold));               // one day after a sale
    return Math.Max(sold, rest);
}

public static int MaxProfitTwo(int[] prices)                       // 123
{
    int b1 = -prices[0], s1 = 0, b2 = -prices[0], s2 = 0;
    for (int i = 1; i < prices.Length; i++)
    {
        int p = prices[i];
        (b1, s1, b2, s2) = (Math.Max(b1, -p), Math.Max(s1, b1 + p),
                            Math.Max(b2, s1 - p), Math.Max(s2, b2 + p));
    }
    return s2;
}

Why is s2 alone the answer for 123? A second trade may buy and sell on the same day, which earns 0, so s2 ≥ s1 always. Allowing an "empty" trade keeps the code free of special cases.

Pitfall: −∞ in C# sold starts as "impossible", which is −∞. int.MinValue + price overflows and wraps to a huge positive number. Use int.MinValue / 2 (adding a price still stays very negative) or a long. In Python, float("-inf") is safe, but it turns the result into a float if it ever wins.

When the state machine has many states, or the number of trades k is large, the same DP gets optimised with tricks such as "unlimited when k ≥ n/2". More state-machine problems, and DP speed-ups, are covered in State Machines & DP Optimisations.

Grid DP

Counting and minimising paths

The classic grid setting: a robot starts at the top-left and may move only right or down. Every route into cell (r, c) comes from the cell above or the cell to the left, so

  • counting (Unique Paths 62, Unique Paths II 63): ways[r][c] = ways[r−1][c] + ways[r][c−1], and a rock forces 0;
  • minimising (Minimum Path Sum 64): cost[r][c] = grid[r][c] + min(cost[r−1][c], cost[r][c−1]), and a rock is +∞.

Same stencil (C), same loop order, different operator. This is the framework's semiring view in action: + combines options when counting, min combines them when optimising.

Each new cell draws two arrows, from above and from the left. In count mode both arrows contribute. In min mode the cheaper one is green and the other is grey. A rock is drawn as a wall and contributes nothing. The last frame of min mode walks back along the green arrows to show the cheapest route. Try a grid where the first row has a rock: everything to its right in row 0 becomes unreachable.

def unique_paths_with_obstacles(grid: list[list[int]]) -> int:   # 1 = rock
    R, C = len(grid), len(grid[0])
    ways = [[0] * C for _ in range(R)]
    for r in range(R):
        for c in range(C):
            if grid[r][c] == 1:
                continue                          # a rock: 0 ways through it
            if r == 0 and c == 0:
                ways[r][c] = 1
            else:
                ways[r][c] = (ways[r - 1][c] if r else 0) + (ways[r][c - 1] if c else 0)
    return ways[R - 1][C - 1]


def min_path_sum(grid: list[list[int]]) -> int:
    R, C = len(grid), len(grid[0])
    INF = float("inf")
    cost = [[INF] * C for _ in range(R)]
    for r in range(R):
        for c in range(C):
            if r == 0 and c == 0:
                cost[r][c] = grid[0][0]
            else:
                cost[r][c] = grid[r][c] + min(cost[r - 1][c] if r else INF,
                                              cost[r][c - 1] if c else INF)
    return cost[R - 1][C - 1]

public static int UniquePathsWithObstacles(int[][] grid)          // 1 = rock
{
    int R = grid.Length, C = grid[0].Length;
    var ways = new int[R, C];
    for (int r = 0; r < R; r++)
        for (int c = 0; c < C; c++)
        {
            if (grid[r][c] == 1) continue;                // a rock: 0 ways through it
            if (r == 0 && c == 0) { ways[r, c] = 1; continue; }
            ways[r, c] = (r > 0 ? ways[r - 1, c] : 0) + (c > 0 ? ways[r, c - 1] : 0);
        }
    return ways[R - 1, C - 1];
}

public static int MinPathSum(int[][] grid)
{
    int R = grid.Length, C = grid[0].Length;
    var cost = new int[R, C];
    for (int r = 0; r < R; r++)
        for (int c = 0; c < C; c++)
        {
            if (r == 0 && c == 0) { cost[r, c] = grid[0][0]; continue; }
            int best = int.MaxValue;
            if (r > 0) best = Math.Min(best, cost[r - 1, c]);
            if (c > 0) best = Math.Min(best, cost[r, c - 1]);
            cost[r, c] = grid[r][c] + best;
        }
    return cost[R - 1, C - 1];
}

Edges of the grid: three clean ways to handle them

  • Guards (as above): x if r else 0. Explicit, but noisy.
  • Padding: allocate (R+1) × (C+1), put the neutral value (0 for counts, ∞ for minimums) in row 0 and column 0, and seed one cell so the start works. The loop then has no ifs. Remember that dp[r+1][c+1] now means cell (r, c).
  • Fill the first row and first column first, then loop from (1, 1). Common in interview answers. Be careful: a rock in row 0 blocks everything to its right.

Without rocks, the count has a closed form: a route is any order of R−1 downs and C−1 rights, so there are C(R+C−2, R−1) of them. The DP is still worth knowing, because every variant (rocks, costs, required cells, at most k turns) breaks the formula but not the table.

Triangle: fill bottom-up and the edges disappear

LeetCode 120 Medium. From the top of a number triangle, step to one of the two adjacent numbers in the row below. Minimise the sum.

Top-down, the cells on the left and right edges have only one parent, which means special cases. Bottom-up, every cell has exactly two children: best[r][i] = tri[r][i] + min(best[r+1][i], best[r+1][i+1]), the last row is its own base case, and the answer is the single cell at the top. Choosing the direction where every cell has the same number of dependencies is a habit worth building.

def minimum_total(triangle: list[list[int]]) -> int:
    best = triangle[-1][:]               # best[i] = min path sum from (row, i) to the bottom
    for r in range(len(triangle) - 2, -1, -1):
        for i in range(r + 1):           # left to right: best[i+1] is still the row below
            best[i] = triangle[r][i] + min(best[i], best[i + 1])
    return best[0]

public static int MinimumTotal(IList<IList<int>> triangle)
{
    var best = triangle[^1].ToArray();   // best[i] = min path sum from (row, i) to the bottom
    for (int r = triangle.Count - 2; r >= 0; r--)
        for (int i = 0; i <= r; i++)     // left to right: best[i+1] is still the row below
            best[i] = triangle[r][i] + Math.Min(best[i], best[i + 1]);
    return best[0];
}

The 1D array is one row of the table. Cell i reads best[i] and best[i+1] from the row below. Going left to right, best[i+1] has not been overwritten yet, so one array is enough. Going right to left would read a value from the current row: the same bug as the 0/1 knapsack loop direction you will meet in Knapsack Family.

Maximal Square: why the minimum of three

LeetCode 221 Medium. In a 0/1 matrix, find the largest all-1 square.

side[r][c] = side of the largest all-1 square whose bottom-right corner is (r, c).

This is an "ending at" state again, in two dimensions: the corner is pinned, and the answer is max(side)². If matrix[r][c] = 1, then side[r][c] = 1 + min(up, left, diagonal). The picture explains why it is the minimum.

def maximal_square(matrix: list[list[str]]) -> int:
    R, C = len(matrix), len(matrix[0])
    side = [[0] * (C + 1) for _ in range(R + 1)]   # padded: side[r+1][c+1] is cell (r, c)
    best = 0
    for r in range(R):
        for c in range(C):
            if matrix[r][c] == "1":
                side[r + 1][c + 1] = 1 + min(side[r][c + 1],    # up
                                             side[r + 1][c],    # left
                                             side[r][c])        # diagonal
                best = max(best, side[r + 1][c + 1])
    return best * best                   # the problem asks for the area

public static int MaximalSquare(char[][] matrix)
{
    int R = matrix.Length, C = matrix[0].Length, best = 0;
    var side = new int[R + 1, C + 1];    // padded: side[r+1, c+1] is cell (r, c)
    for (int r = 0; r < R; r++)
        for (int c = 0; c < C; c++)
            if (matrix[r][c] == '1')
            {
                side[r + 1, c + 1] = 1 + Math.Min(side[r, c + 1],       // up
                                         Math.Min(side[r + 1, c],       // left
                                                  side[r, c]));         // diagonal
                best = Math.Max(best, side[r + 1, c + 1]);
            }
    return best * best;                  // the problem asks for the area
}

Dungeon Game: when the DP must run backwards

LeetCode 174 Hard. A knight walks right/down from the top-left to the princess at the bottom-right. Each cell adds or removes health. If health ever drops to 0, he dies. What is the minimum starting health?

The natural forward DP fails. "Best so far" at a cell needs two numbers: the health required up to here, and the health left now. Neither one alone decides which route will be better later, so there is no single value to store.

So flip the state:

need[r][c] = minimum health you must have when entering (r, c) to reach the princess alive.

After this cell, you go to whichever neighbour asks for less: min(need[r+1][c], need[r][c+1]). This cell changes health by d[r][c], so you must arrive with that amount minus d[r][c], and never less than 1: need[r][c] = max(1, min(down, right) − d[r][c]). Fill from the bottom-right corner backwards (stencil D).

def calculate_minimum_hp(dungeon: list[list[int]]) -> int:
    R, C = len(dungeon), len(dungeon[0])
    INF = float("inf")
    need = [[INF] * (C + 1) for _ in range(R + 1)]   # sentinel row and column of INF
    need[R][C - 1] = need[R - 1][C] = 1              # step "past" the princess with 1 HP
    for r in range(R - 1, -1, -1):
        for c in range(C - 1, -1, -1):
            nxt = min(need[r + 1][c], need[r][c + 1])        # the cheaper way onward
            need[r][c] = max(1, nxt - dungeon[r][c])         # never below 1
    return need[0][0]

public static int CalculateMinimumHP(int[][] dungeon)
{
    int R = dungeon.Length, C = dungeon[0].Length;
    var need = new int[R + 1, C + 1];
    for (int r = 0; r <= R; r++)
        for (int c = 0; c <= C; c++) need[r, c] = int.MaxValue;   // sentinels
    need[R, C - 1] = need[R - 1, C] = 1;            // step "past" the princess with 1 HP
    for (int r = R - 1; r >= 0; r--)
        for (int c = C - 1; c >= 0; c--)
        {
            int nxt = Math.Min(need[r + 1, c], need[r, c + 1]);
            need[r, c] = Math.Max(1, nxt - dungeon[r][c]);
        }
    return need[0, 0];
}

Run the DP backwards when…

  • the quantity is a requirement on the start (minimum starting health, money, fuel) rather than a total collected;
  • a forward state would need to remember the whole history (a running minimum and a running sum);
  • the answer cell is the start (dp[0][0]), and the end has a simple fixed value.

Jump Game (from index i, can I reach the end?) and Triangle are backward DPs for the same reason.

Cherry Pickup: two walkers at once

LeetCode 741 Hard. Walk from top-left to bottom-right (right/down), then back (left/up), picking cherries (1); thorns (−1) block. A cherry picked once is gone. Maximise the cherries.

The tempting plan is a greedy: run the best path, remove its cherries, run the best path again. It fails. The first walk can grab a few extra cherries by taking a route that splits the remaining cherries into places a single second walk cannot both reach.

The fix has two steps:

  1. A walk back from the end to the start is just a forward walk in reverse. So the problem becomes two walkers going forward at the same time.
  2. Move them in lockstep. After t steps, each walker is on anti-diagonal r + c = t. Knowing t and the two rows r1, r2 fixes both cells. If the walkers share a cell, they share it at the same time, so the cherry is counted once, and the double-counting problem disappears.

The visualizer shows the layer t table (rows = A's row, columns = B's row) next to the layer t−1 table it reads from. Only pairs with r1 ≤ r2 are needed, because the walkers are interchangeable. The last frame replays both routes on the grid.

def cherry_pickup(grid: list[list[int]]) -> int:
    n = len(grid)
    NEG = float("-inf")
    prev = [[NEG] * n for _ in range(n)]           # prev[r1][r2] at layer t-1
    prev[0][0] = grid[0][0]
    for t in range(1, 2 * n - 1):
        cur = [[NEG] * n for _ in range(n)]
        for r1 in range(max(0, t - n + 1), min(n - 1, t) + 1):
            for r2 in range(r1, min(n - 1, t) + 1):          # walkers are symmetric
                c1, c2 = t - r1, t - r2
                if grid[r1][c1] == -1 or grid[r2][c2] == -1:
                    continue                                 # a thorn blocks this pair
                best = max(prev[a][b] for a in (r1 - 1, r1) for b in (r2 - 1, r2)
                           if 0 <= a <= b < n)               # 4 ways to arrive
                if best == NEG:
                    continue
                gain = grid[r1][c1] + (grid[r2][c2] if r1 != r2 else 0)
                cur[r1][r2] = best + gain
        prev = cur
    return max(0, prev[n - 1][n - 1])

public static int CherryPickup(int[][] grid)
{
    int n = grid.Length, NEG = int.MinValue / 2;
    var prev = new int[n, n];
    for (int a = 0; a < n; a++) for (int b = 0; b < n; b++) prev[a, b] = NEG;
    prev[0, 0] = grid[0][0];
    for (int t = 1; t <= 2 * n - 2; t++)
    {
        var cur = new int[n, n];
        for (int a = 0; a < n; a++) for (int b = 0; b < n; b++) cur[a, b] = NEG;
        for (int r1 = Math.Max(0, t - n + 1); r1 <= Math.Min(n - 1, t); r1++)
            for (int r2 = r1; r2 <= Math.Min(n - 1, t); r2++)        // walkers are symmetric
            {
                int c1 = t - r1, c2 = t - r2;
                if (grid[r1][c1] == -1 || grid[r2][c2] == -1) continue;
                int best = NEG;
                for (int a = r1 - 1; a <= r1; a++)
                    for (int b = r2 - 1; b <= r2; b++)
                        if (a >= 0 && a <= b) best = Math.Max(best, prev[a, b]);
                if (best == NEG) continue;
                cur[r1, r2] = best + grid[r1][c1] + (r1 != r2 ? grid[r2][c2] : 0);
            }
        prev = cur;
    }
    return Math.Max(0, prev[n - 1, n - 1]);
}

Why a <= b? We only keep pairs with r1 ≤ r2. If walker A came from row r1 and B from row r2 − 1 < r1, the walkers swapped sides, and that same situation is stored with the names swapped. Since r1 ≤ r2 and each row moves by at most one, the swapped case only happens when r1 = r2, and the swapped pair (r1, r1−1) is the same situation as (r1−1, r1), which is already one of the four combinations. Recognize it when

Recognize 1D / grid DP when

  • The input is one sequence and the decision at each position depends only on a few nearby positions (adjacent houses, the last one or two digits, the previous day).
  • The answer is a contiguous piece (subarray, substring, square): use "ends exactly at i" and take the max over all i.
  • The answer is a subsequence with an order condition (increasing, divisible chain): "ends at i" plus a look-back over all j < i, often sped up with binary search.
  • There is a small set of modes you can be in (holding / not holding, k trades used, cooldown): one DP row per mode, a state machine between them.
  • Movement on a grid is monotone (only right/down, or row by row downwards). No cycles means the cells already form a DAG in reading order. If moves can go in all four directions, it is a shortest-path problem (BFS or Dijkstra), not a grid DP.
  • "Go there and come back", or "two robots": walk both at once, with the step count as a shared clock.

Pitfalls

Answer in the wrong cell For a prefix state the answer is dp[n]; for "ending at i" it is max(dp); for a backward DP it is dp[0]. Returning dp[n-1] from Kadane or LIS passes the examples and fails when the best run ends early. Say the state sentence out loud, then ask "which cell answers the question?"

Grids built with list multiplication [[0] * C] * R creates one row object referenced R times. Writing dp[1][0] = 5 changes every row. Always use [[0] * C for _ in range(R)]. In C#, prefer new int[R, C] (one block, no aliasing) or a jagged array built in a loop.

Forgetting the obstacle on the first row or column "The first row is all 1s" is only true without rocks. A rock at (0, 2) makes (0, 3), (0, 4), … unreachable. Either loop over the whole grid with guards (as above) or carry the zero forward when you pre-fill the edges. Also check whether the start or end cell itself is a rock: the answer is 0.

Overwriting a value you still need In-place updates (hi/lo in Maximum Product, the stock states, the diagonal in Maximal Square) are correct only if each new value is computed from the old values. Use tuple assignment in Python and C#, or save the old value in a temporary first.

Unreachable states that look like zero In Cherry Pickup, Dungeon Game and the stock cooldown, some states are impossible (a thorn, a sentinel, "sold" on day 0). If they start at 0, the max happily uses them. Start impossible states at −∞ (or +∞ for minimum DPs), skip them explicitly, and use int.MinValue / 2 in C# so that adding to them cannot overflow.

Worked problems

1. Partition Array for Maximum Sum: the last piece has a length

LeetCode 1043 Medium. Split arr into contiguous pieces of length at most k. Every element of a piece becomes the piece's maximum. Maximise the total.

Key insight. This is Word Break with numbers. Ask about the last piece: it is arr[i−len..i−1] for some len from 1 to k, it contributes len × max(piece), and what is left is a smaller prefix. dp[i] = max over len of dp[i−len] + len × max(arr[i−len:i]). Grow the piece leftwards from i−1 so the running max costs O(1) per step.

Solution: prefix DP with a look-back of k, O(n·k) 
def max_sum_after_partitioning(arr: list[int], k: int) -> int:
    n = len(arr)
    dp = [0] * (n + 1)                   # dp[i] = best total for arr[:i]
    for i in range(1, n + 1):
        top = 0
        for length in range(1, min(k, i) + 1):    # the last piece is arr[i-length:i]
            top = max(top, arr[i - length])       # running max as the piece grows left
            dp[i] = max(dp[i], dp[i - length] + top * length)
    return dp[n]

public static int MaxSumAfterPartitioning(int[] arr, int k)
{
    int n = arr.Length;
    var dp = new int[n + 1];             // dp[i] = best total for arr[..i]
    for (int i = 1; i <= n; i++)
    {
        int top = 0;
        for (int len = 1; len <= Math.Min(k, i); len++)   // the last piece is arr[(i-len)..i]
        {
            top = Math.Max(top, arr[i - len]);
            dp[i] = Math.Max(dp[i], dp[i - len] + top * len);
        }
    }
    return dp[n];
}

Time O(n·k), space O(n). Because dp[i] reads only dp[i−k..i−1], a circular buffer of size k + 1 would make the space O(k).

2. Russian Doll Envelopes: sort so that LIS does the rest

LeetCode 354 Hard. Envelope (w, h) fits in another if both dimensions are strictly smaller. How many can you nest?

Key insight. Sort by width, and the problem becomes an LIS on heights. One trap: two envelopes with the same width cannot nest, but an increasing run of heights would chain them. Sort equal widths by height descending. Then equal-width envelopes appear in decreasing height order, so a strictly increasing run can never take two of them. With n up to 10⁵, use the patience-sorting LIS.

Solution: sort by (w ascending, h descending), then patience LIS, O(n log n) 
from bisect import bisect_left


def max_envelopes(envelopes: list[list[int]]) -> int:
    envelopes.sort(key=lambda e: (e[0], -e[1]))   # width up, height down within a width
    tails = []                                    # patience piles over the heights
    for _, h in envelopes:
        k = bisect_left(tails, h)
        if k == len(tails):
            tails.append(h)
        else:
            tails[k] = h
    return len(tails)

public static int MaxEnvelopes(int[][] envelopes)
{
    Array.Sort(envelopes, (a, b) => a[0] != b[0] ? a[0].CompareTo(b[0]) : b[1].CompareTo(a[1]));
    var tails = new List<int>();         // patience piles over the heights
    foreach (var e in envelopes)
    {
        int k = tails.BinarySearch(e[1]);
        if (k < 0) k = ~k;
        if (k == tails.Count) tails.Add(e[1]); else tails[k] = e[1];
    }
    return tails.Count;
}

Time O(n log n), space O(n). The same trick handles "box stacking" style problems whenever one dimension can be sorted away.

3. Best Time to Buy and Sell Stock IV: k trades as a longer machine

LeetCode 188 Hard. At most k transactions. Maximise the profit.

Key insight. Use the chain machine from the figure above with 2k states: buy[j] = best balance while holding the share of trade j, sell[j] = best balance after completing trade j. Each day, buy[j] = max(buy[j], sell[j−1] − p) and sell[j] = max(sell[j], buy[j] + p). One more observation removes the worst case: a profitable trade needs at least two days, so if 2k ≥ n the limit never binds, and the unlimited greedy (sum of every price rise) is the answer.

Solution: 2k-state machine, O(n·k) time, O(k) space 
def max_profit_k(k: int, prices: list[int]) -> int:
    n = len(prices)
    if 2 * k >= n:                       # the limit cannot bind: take every rise
        return sum(max(0, prices[i] - prices[i - 1]) for i in range(1, n))
    buy = [float("-inf")] * (k + 1)      # buy[j]: holding during trade j
    sell = [0] * (k + 1)                 # sell[j]: finished j trades (sell[0] = 0)
    for p in prices:
        for j in range(1, k + 1):        # j upward: same-day buy+sell only earns 0
            buy[j] = max(buy[j], sell[j - 1] - p)
            sell[j] = max(sell[j], buy[j] + p)
    return sell[k]

public static int MaxProfitK(int k, int[] prices)
{
    int n = prices.Length;
    if (2 * k >= n)                      // the limit cannot bind: take every rise
    {
        int total = 0;
        for (int i = 1; i < n; i++) total += Math.Max(0, prices[i] - prices[i - 1]);
        return total;
    }
    var buy = new int[k + 1]; var sell = new int[k + 1];
    Array.Fill(buy, int.MinValue / 2);   // holding during trade j: impossible so far
    foreach (int p in prices)
        for (int j = 1; j <= k; j++)
        {
            buy[j] = Math.Max(buy[j], sell[j - 1] - p);
            sell[j] = Math.Max(sell[j], buy[j] + p);
        }
    return sell[k];
}

Updating in place within one day is safe here: a buy and a sell on the same day cancel out (−p + p = 0), so using a just-updated value can never create profit that does not exist. That is why this machine tolerates the in-place order, while Maximum Product does not. Faster versions (O(n log n) with a "regret" heap, or the λ-optimisation) are in State Machines & DP Optimisations.

4. Minimum Falling Path Sum II: speed up the transition, not the state

LeetCode 1289 Hard. Pick one element from each row of an n × n grid. Adjacent rows must use different columns. Minimise the sum.

Key insight. dp[r][c] = grid[r][c] + min(dp[r−1][j] for j ≠ c). Done directly, that is O(n) per cell and O(n³) overall. But "the minimum of a row, excluding one column" only ever needs the row's two smallest values: if c is the column of the smallest, use the second smallest; otherwise use the smallest. Precompute them once per row and every cell costs O(1).

Solution: keep the best two of the previous row, O(n²) 
def min_falling_path_sum(grid: list[list[int]]) -> int:
    prev = grid[0][:]
    for row in grid[1:]:
        order = sorted(range(len(prev)), key=prev.__getitem__)[:2]   # columns of the 2 smallest
        lo1 = order[0]
        lo2 = order[1] if len(order) > 1 else order[0]
        prev = [x + prev[lo2 if c == lo1 else lo1] for c, x in enumerate(row)]
    return min(prev)

public static int MinFallingPathSum(int[][] grid)
{
    int n = grid.Length;
    var prev = (int[])grid[0].Clone();
    for (int r = 1; r < n; r++)
    {
        int lo1 = -1, lo2 = -1;                     // columns of the two smallest
        for (int c = 0; c < n; c++)
            if (lo1 < 0 || prev[c] < prev[lo1]) { lo2 = lo1; lo1 = c; }
            else if (lo2 < 0 || prev[c] < prev[lo2]) lo2 = c;
        var cur = new int[n];
        for (int c = 0; c < n; c++)
            cur[c] = grid[r][c] + prev[c == lo1 ? lo2 : lo1];
        prev = cur;
    }
    return prev.Min();
}

Time O(n²) (the Python sorted makes it O(n² log n), which is still fine; a two-variable scan as in the C# version is O(n²)). For n = 1, there is one row and nothing to exclude. "Best two" is the standard trick whenever the transition is "best over all, except one"; Paint House II (265) uses it too.

5. Cherry Pickup II: two robots moving down together

LeetCode 1463 Hard. Two robots start at the top-left and top-right corners. Each step, each robot moves down one row, to column c−1, c or c+1. They collect the cherries on their cells (once if they share one). Maximise the total.

Key insight. The row is a shared clock, exactly like the anti-diagonal in Cherry Pickup. The state is (row, c1, c2). Each state has 3 × 3 = 9 predecessors in the row above. Roll the rows: only an n × n layer of column pairs is live at a time.

Solution: dp over (row, c1, c2) with 9 transitions, O(R·C²·9) 
def cherry_pickup_ii(grid: list[list[int]]) -> int:
    R, C = len(grid), len(grid[0])
    NEG = float("-inf")
    prev = [[NEG] * C for _ in range(C)]           # prev[c1][c2] for the row above
    prev[0][C - 1] = grid[0][0] + (grid[0][C - 1] if C > 1 else 0)
    for r in range(1, R):
        cur = [[NEG] * C for _ in range(C)]
        for c1 in range(C):
            for c2 in range(C):
                best = max((prev[a][b] for a in (c1 - 1, c1, c1 + 1) if 0 <= a < C
                            for b in (c2 - 1, c2, c2 + 1) if 0 <= b < C), default=NEG)
                if best == NEG:
                    continue                      # this pair is unreachable
                gain = grid[r][c1] + (grid[r][c2] if c1 != c2 else 0)
                cur[c1][c2] = best + gain
        prev = cur
    return max(max(row) for row in prev)

public static int CherryPickupII(int[][] grid)
{
    int R = grid.Length, C = grid[0].Length, NEG = int.MinValue / 2;
    var prev = new int[C, C];
    for (int a = 0; a < C; a++) for (int b = 0; b < C; b++) prev[a, b] = NEG;
    prev[0, C - 1] = grid[0][0] + (C > 1 ? grid[0][C - 1] : 0);
    for (int r = 1; r < R; r++)
    {
        var cur = new int[C, C];
        for (int c1 = 0; c1 < C; c1++)
            for (int c2 = 0; c2 < C; c2++)
            {
                int best = NEG;
                for (int a = c1 - 1; a <= c1 + 1; a++)
                    for (int b = c2 - 1; b <= c2 + 1; b++)
                        if (a >= 0 && a < C && b >= 0 && b < C) best = Math.Max(best, prev[a, b]);
                cur[c1, c2] = best == NEG ? NEG : best + grid[r][c1] + (c1 != c2 ? grid[r][c2] : 0);
            }
        prev = cur;
    }
    int ans = 0;
    foreach (int v in prev) ans = Math.Max(ans, v);
    return ans;
}

Time O(R·C²), space O(C²). Marking unreachable pairs as −∞ matters: in the first rows, a robot cannot yet be far from its corner, and treating those pairs as 0 would let it "teleport".

Check yourself

Kadane returns cur after the loop instead of best. On which input does it fail, and why?

On any input where the best subarray ends before the last element, for example [5, −10, 1]: cur ends at 1, but the answer is 5. cur means "best run ending at the last index". The answer is the max over all end positions, so you must track best = max(best, cur).

Why does Decode Ways add the one-digit and two-digit cases while House Robber takes the max of skip and rob?

Decode Ways counts: the two cases produce disjoint sets of decodings (the last letter has different lengths), so the totals add. House Robber optimises: you want the single best plan, so you pick the better option. Same stencil, different operator, as in the framework's semiring table.

After processing [3, 5, 6, 2, 4] with patience sorting, what is tails, and is it an increasing subsequence of the input?

[3] → [3, 5] → [3, 5, 6] → 2 replaces 3: [2, 5, 6] → 4 replaces 5: [2, 4, 6]. Length 3 is correct (3, 5, 6). But 2, 4, 6 is not a subsequence in order (6 comes before 2 and 4). tails[k] only records the smallest possible end of a run of length k + 1.

In Dungeon Game, why is it max(1, min(down, right) − d) and not min(down, right) − d?

If the cell gives a big potion (d large), min(down, right) − d can be 0 or negative, which would say "enter with 0 health". The knight dies at 0 the moment he arrives, before the potion matters. Health must be at least 1 at every moment, so the requirement is clamped at 1.

You roll Unique Paths into one row and loop c from right to left. What do you get?

Wrong counts. row[c] += row[c−1] must read the new left value (this row) and the old row[c] (the row above). Going right to left, row[c−1] still holds the row above, so you compute up + up-left, which counts different moves. The loop direction must follow the stencil: left neighbour first.

Why does Cherry Pickup fail if you run "best path, delete its cherries, best path again"?

The first path is chosen without knowing about the second. The greedy first path might take a few more cherries while leaving the rest split into two areas that a single return trip cannot both reach; a slightly worse first path could leave everything on one route. Optimising both walks jointly, with state (t, r1, r2), removes the problem.
